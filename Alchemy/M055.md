false_positive_notes: |
  Scheduled and machine-generated mail is the dominant source of regular-looking port-25 traffic and it must be modelled before anything else. Cron-driven reports, monitoring and alerting mail, backup and job-completion notifications, billing runs, newsletter and marketing platforms, log shippers that mail digests, and health-check probes all produce outbound SMTP on a timer - some of them on intervals every bit as tight as an implant's. The separators are destination and payload - scheduled mail goes to a small, stable set of internal or well-known relays and carries recognisable message volume, while an implant's destination is a host with no mail role and its sessions are small and uniform regardless of how much mail the device is handling. Mail queue retry logic is the second trap - RFC-compliant MTAs retry failed deliveries on backoff schedules, which produces repeated sessions to the same destination at regular-ish and sometimes exponentially spaced intervals, so always join candidate flows against the gateway's own delivery logs and drop anything the queue can account for. Monitoring systems that check SMTP reachability from a probe host are a third, and they are easy to allowlist once by source. Note too that a 100-second jitter window is wide enough to defeat a naive fixed-interval test but narrow relative to real mail timing - tune on interval *variance within a band* rather than on exact periodicity, or the jitter will hide the beacon from the model built to find it. Finally, the interval is operator-configurable and persisted to a state file, so it can be changed at any time - a model that only knows 600-699 seconds will miss the next build. Score on regularity as a property, not on the specific published values.

The interval is stored in a hidden file at `/var/lib/.db`, can be changed by the operator, and persists across restarts - command code `1576` sets it. The implant's configuration schema provides three host and port pairs, of which the analysed build populated one; command code `842` overwrites the host and port tables at runtime. BPF Rekoobe's filter matched TCP/UDP/SCTP IPv4 and UDP IPv6 where source and destination port both equal 25, and its reverse shell connected to the attacker's port 25 while spoofing `/sniper/autorun/rblsmtpd --start -n 9`.
  Why T1008 is the anchor and not simply T1071.003. The three-slot host and port table with a runtime-overwrite command is the fallback-channel structure, and it is what makes this a modelling problem rather than a blocklist problem. A single hardcoded destination could be handled by a firewall rule. A rotating table, repointable mid-session by command `842`, means the destination is not a stable feature - the timing is. Rapid7 also documents two parallel C2 addressing strategies across the six builds - attacker-registered domains in three samples, hardcoded consumer-broadband IPs in the other three - so a model keyed on domain reputation misses half the fleet by design.
  The hand-built TLS layer is a strong corroborating feature. Rapid7 found the TLS layer "hand-built rather than linked from a standard cryptographic library," with a fixed `ClientHello` template compiled into the binary including a 40-entry cipher suite list and a fixed extension ordering, and peer authentication deferred entirely to the application layer via a shared-secret handshake carrying the magic value `1571` (`0x0623`). A fixed, compiled-in `ClientHello` produces a stable and unusual TLS client fingerprint. Add JA3/JA4 on port-25 sessions as a feature - a gateway's real `STARTTLS` sessions carry the fingerprint of whatever MTA and TLS library the vendor shipped, and a second distinct fingerprint on the same port from the same host is a high-weight signal that needs no timing at all.
  Feature set to score per (source host, destination IP, port 25) pair over a rolling 14-to-30-day window.
  - Interval regularity - coefficient of variation of inter-session start deltas. Score the low tail. A beacon with a 100-second jitter on a 600-second base has a CV near 0.05; a real mail queue is an order of magnitude higher.
  - Band containment - the fraction of intervals falling inside a single narrow window (for example, the tightest window containing 90 percent of observations, expressed as a proportion of the median interval). This is the feature that survives jitter, where a fixed-period test does not.
  - Session-size uniformity - standard deviation of bytes sent per session, normalised by the mean. Status check-ins reporting a fixed field set are near-constant in size; mail delivery is not.
  - Volume decorrelation - correlation between the host's outbound port-25 session count and its inbound mail volume over the same buckets. A gateway's real egress tracks its ingress. A beacon does not care.
  - Destination mail role - does the destination have an MX record, a mail-server banner, a PTR consistent with mail infrastructure, and an ASN consistent with hosting rather than consumer broadband?   - Duty cycle - sessions continuing at the same cadence outside business hours and through periods when the gateway is handling no mail at all.
  - TLS fingerprint novelty - a JA3/JA4 on port 25 from this host that is not the fingerprint its MTA normally presents.
  - Process attribution where host telemetry exists - the sending process is not a mail service. Rapid7's mitigation guidance puts this first.
  Ranking and triage. Rank descending on a weighted combination with interval regularity and band containment carrying the most weight, destination mail role and TLS fingerprint novelty next. Investigate the top candidates by joining against the gateway's own delivery logs - a beacon has no corresponding queue entries, which is the single cleanest disconfirmation available and should be the first check on every candidate.

A host that scores here should be swept immediately with [[H366]] for a packet socket holding a BPF filter, with [[H367]] for an unlinked executable and the staging sequence, and with [[H368]] for shared objects mapped from unowned paths. # M055

The implant picked port 25 for the same reason a thief picks a delivery uniform.

AVERAT runs on mail security gateways. Its command and control connects outbound to port 25 and speaks real SMTP — `EHLO`, then `STARTTLS` — before starting its own encrypted session inside. On a device whose entire function is sending mail to arbitrary mail exchangers on the internet, there is no firewall rule to write, no protocol anomaly to flag, and nothing in a flow record that distinguishes the beacon from the device doing its job. Rapid7 made the point plainly: the traffic is indistinguishable from legitimate work.

Except for the clock.

Rapid7 measured check-ins every 600 to 699 seconds. That is a ten-minute base with a hundred-second jitter window — enough randomness to defeat a test for fixed periodicity, and nowhere near enough to look like a mail queue. Real outbound SMTP from a gateway is driven by mail it has been handed: bursty, correlated with what came in, concentrated in business hours, and spread across the destination MXes its users actually write to. The beacon is none of those things. It arrives when the timer fires, whether the gateway is relaying ten thousand messages or none at all.

So the feature that works is not periodicity, it is *variance*. Score the regularity of inter-session intervals and the tightness of the band they fall into, and the jitter stops being camouflage.

Two more features come almost free. The sessions are status check-ins carrying a fixed field set — hostname, user, OS version, interfaces, logged-in users — so their sizes barely move, while mail deliveries vary with the mail. And the TLS is hand-built: a fixed `ClientHello` compiled into the binary, with a 40-entry cipher list and fixed extension ordering, which produces a stable and distinctly non-MTA JA3/JA4 fingerprint on a port where only one fingerprint should ever appear.

The reason this has to be a model rather than a rule is the destination. The configuration holds three host-and-port slots, command `842` overwrites them at runtime, and across six builds Rapid7 found two deliberate addressing strategies — attacker-registered domains in half, hardcoded consumer-broadband IPs in the rest. Block one address and the table rotates. The timing does not.

## Why

- **Port and protocol are the wrong discriminators on this device class.** A mail gateway sending SMTP to an arbitrary MX is the device working correctly. Any control keyed on port, direction or protocol passes the beacon by construction, which is exactly why it was chosen.
- **Jitter defeats periodicity tests but not variance tests.** A 100-second window on a 600-second base yields an interval coefficient of variation near 0.05. A real mail queue, with retries and demand-driven bursts, is an order of magnitude noisier. Scoring the low tail inverts the evasion.
- **The destination is designed to rotate; the cadence is not.** Three configurable host slots plus a runtime overwrite command means address-based detection is a treadmill. Timing is the stable property, which is what makes this a scoring problem.
- **Check-in payloads are uniform because the report is fixed.** A constant field set produces near-constant session sizes, giving a second independent feature that needs no timestamps at all.
- **Egress should track ingress on a mail gateway, and for a beacon it does not.** Correlating outbound port-25 session counts against inbound mail volume is a cheap feature that captures the beacon's indifference to the device's actual workload.
- **A compiled-in `ClientHello` is a fingerprint the operator did not mean to leave.** Hand-rolled TLS with fixed cipher ordering looks nothing like the vendor MTA's library. A second JA3/JA4 on port 25 from one host is high-signal on its own.
- **The delivery log is the cleanest disconfirmation available.** A real session has a queue entry behind it. A beacon has none. Joining candidates against the gateway's own mail logs resolves most of them in one query, which keeps the triage cost low enough to run this continuously.
- **The destination address class is a feature, not just context.** Rapid7's recovered relays were a fuel retailer's NAS, an obsolete embedded appliance and a CCTV recorder on domestic lines. "Mail-role hostname that resolves to consumer broadband" is a narrow and productive filter.
