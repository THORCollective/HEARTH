  Administrators, inventory tools and compliance scanners perform exactly this enumeration by design, and they do it at high fan-out. Configuration management, vulnerability scanners, software asset management and security product health checks will all outrank an adversary on raw fan-out. This hunt is unusable without allowlisting those service accounts and collectors first, and the allowlist is the bulk of the work.
  A newly onboarded scanner, or an existing one given a wider scope, produces a step change that looks exactly like the target. Correlate against change records before escalating, and prefer per-principal baselines over fleet-wide thresholds so a new collector shows up as a new principal rather than as an anomaly on an established one.

notes: |
  Platform - Windows, in a domain environment. The analysis runs on process-execution and file-share telemetry plus two inventories; the inventory comparison is the part most environments do not have ready.
  Why this is a model-assisted hunt rather than a rule - security software discovery has no malicious signature. The commands are built-in, the arguments are ordinary, and administrators run them constantly, which is why the technique is usually dismissed. What distinguishes the adversary case is entirely relative and volumetric: how many distinct hosts one principal asked, in how short a window, compared with what that principal normally does, and where activity went afterwards. None of those are expressible as a static threshold that generalises across environments.
  What the report states - CrowdStrike describes the campaign as showing "the adversary building endpoint sensor evasion directly into their agentic workflow, including instructions to identify hosts without the CrowdStrike Falcon sensor." At a global pharmaceutical organisation the operator instructed the agents to "find Windows machines in the domain without Falcon, judging by tasklist and folder listings", using what CrowdStrike identifies as red-team slang for the sensor. The purpose is stated plainly: "Incorporating sensor coverage checks directly into the agentic workflow allows the adversary to concentrate follow-on activity on unprotected hosts." In the technique table CrowdStrike maps this to security software discovery with the observable "Inventoried endpoint sensor coverage". The report also records that across these engagements the agents "pursued multiple attack paths in parallel" and "shifted to alternative approaches when a path failed".
  The two enumeration methods are deliberately different, and both are named - a process listing answers "is the sensor running", and a folder listing answers "is the sensor installed". The second works against hosts where the first is blocked or where the service is stopped, and it is also the one that shows up in share-access telemetry rather than in process telemetry. A hunt that covers only process execution misses half of what the instruction described.
  The feature set to score, per principal per rolling window:
  1. Distinct remote hosts for which a security-software presence query was issued. This is the primary fan-out measure.
  2. Rate, as distinct hosts per minute. An agent framework compresses a domain-wide sweep into a window no human typist produces, and this is the feature that separates agent-driven enumeration from manual reconnaissance more cleanly than the total does.
  3. Ratio against that principal's own trailing baseline, rather than an absolute count, so that an established scanner does not have to be re-justified every run.
  4. Breadth of method. A principal using both process enumeration and vendor-directory listing against the same host set is doing something more deliberate than a tool that only does one.
  5. Query specificity. Enumeration naming security vendor products or their install directories is more interesting than a generic full process list, because it reveals what the caller was looking for.
  6. The correlation feature, below, which is what turns a ranked list into a finding.
  The correlation feature, and why it is the point - enumeration alone cannot be separated from administration by intent. What can be separated is what happened next. Take the set of hosts queried in the sweep, split it by whether each host reports to a security product, and then measure where follow-on activity landed: remote service creation, remote scheduled tasks, admin share writes, interactive logons. If follow-on activity is distributed across the queried set roughly in proportion to its size, the sweep was probably inventory. If it is concentrated on the subset with no sensor, the sweep was targeting. Compute that concentration as a simple ratio of observed to expected, and require the comparison against a known-clean historical window described in the false-positive notes, because an estate can produce this concentration on its own.
  Check 1 - fan-out, over the retained window. Advanced hunting keeps 30 days, so the lookback is capped there:
  ```kusto
  let lookback = 30d;
  let bin_size = 1h;
  let discovery_tools = dynamic(["tasklist.exe", "sc.exe", "net.exe", "net1.exe", "wmic.exe", "powershell.exe", "pwsh.exe"]);
  DeviceProcessEvents
  | where Timestamp > ago(lookback)
  | where FileName in~ (discovery_tools)
  | where ProcessCommandLine has_any ("/s ", "-ComputerName", "/node:", "\\\\")
  | extend RemoteTarget = extract(@"(?i)(?:/s\s+|/node:|-ComputerName\s+|\\\\)([A-Za-z0-9._-]{3,})", 1, ProcessCommandLine)
  | where isnotempty(RemoteTarget)
  | summarize DistinctTargets = dcount(RemoteTarget), Queries = count(),
              Methods = make_set(FileName, 8), SampleCommand = any(ProcessCommandLine)
            by AccountName, DeviceName, TimeBin = bin(Timestamp, bin_size)
  | where DistinctTargets > 25
  | extend TargetsPerMinute = round(todouble(DistinctTargets) / 60.0, 2)
  | order by DistinctTargets desc
  ```
  Every `let` is used. The fan-out floor of 25 distinct targets in an hour is a starting point for a mid-sized domain and must be recalibrated locally - in a small environment it will be too high to ever fire, and in a large one it will return every management tool. Recalibrate it from the distribution of your own allowlisted collectors rather than from this number.
  Check 2 - the folder-listing half, which process telemetry cannot see. Security Event ID 5145 records the relative target of a share access, so a sweep that lists vendor install directories over administrative shares appears there: filter 5145 records whose relative target names a security vendor directory under a Program Files path, and aggregate by subject account and source address rather than by target server. A single account touching that path on dozens of servers within an hour is the same fan-out signal arriving through a different channel. Note that 5145 is high-volume and often not collected; confirm before concluding anything from its silence.
  Check 3 - the inventory difference, which is worth computing whether or not anything fires. Compare the authoritative asset inventory against security product enrolment and produce the list of hosts that exist but do not report. That list is what the adversary was trying to build. Having it first means a sweep can be scored against known ground truth, and it has standalone value: CrowdStrike's own recommendation is to deploy an endpoint sensor "across the environment, including on servers considered inaccessible from the public internet". In most estates this comparison is the single most useful output of this hunt, because it is actionable without any adversary being present.
  Inference, not stated by CrowdStrike - the entire feature set, the query, the fan-out floor, the rate measure, the correlation ratio and the inventory-difference method are mine. CrowdStrike published the operator instruction and its purpose, not a detection approach, and did not publish enumeration volumes, timing, or the commands the agents actually ran. The regular-expression extraction in check 1 is a heuristic over command-line text and will both miss remote invocations expressed in other forms and match some local ones.
  Pairing - [[H439]] covers the same operator's framework residue on hosts and in cloud accounts, and is the string-matching counterpart to this behavioural hunt. This one survives the operator renaming their working directory; that one does not, which is why they are published together.
  Closest existing coverage - no existing hunt scores security software discovery as a targeting step, and none correlates enumeration results with where follow-on activity subsequently landed. [[B057]] is adjacent in purpose rather than method: it inventories edge appliances precisely because they carry no endpoint agent, which is the same blind-spot problem approached from the asset side, and it is a useful prerequisite for check 3 here.

# M067

Security software discovery usually sits near the bottom of a hunting backlog. Administrators enumerate installed products constantly, the commands are built in, and there is no malicious variant of asking a host what is running on it. The technique is real but the signal is poor.

It changes character when the enumeration is the targeting step. CrowdStrike recovered an operator instruction from an ARTEX controller telling the agents to "find Windows machines in the domain without Falcon, judging by tasklist and folder listings," and states what that buys the adversary: "Incorporating sensor coverage checks directly into the agentic workflow allows the adversary to concentrate follow-on activity on unprotected hosts." The enumeration is not reconnaissance for its own sake. It is a map of where the defender cannot see, built before anything noisy happens.

Two details in that instruction are worth separating. A process listing answers whether the sensor is *running*; a folder listing answers whether it is *installed*. The second still works where the first is blocked or where a service has been stopped, and it surfaces in share-access telemetry rather than process telemetry. A hunt built only on process execution covers half the instruction.

The distinguishing feature is fan-out compressed into time. An agent framework can ask a whole domain in minutes, which is not a pattern a human administrator at a keyboard produces. But fan-out alone ranks every legitimate scanner above the adversary, so the ranking is only a candidate list — the allowlist of collectors and management accounts is most of the work, and it has to come first.

What converts the list into a finding is where activity went next. Split the swept host set by whether each host reports to a security product, then measure where remote service creation, remote scheduled tasks, admin share writes and interactive logons actually landed. Proportionate distribution looks like inventory. Concentration on the hosts with no sensor looks like targeting. One caution belongs on that inference, and it is a real one: uninstrumented hosts tend to be old, flat and poorly managed, which is also where legitimate administration concentrates. Compare against a known-clean historical window before believing the correlation.

The most valuable output of this hunt may not be a detection at all. Computing the difference between the authoritative asset inventory and security product enrolment produces exactly the list the adversary was trying to assemble — and that list is worth having whether or not anyone swept for it.

## Why

- The enumeration precedes the noisy activity, so catching it is catching the targeting decision rather than its consequences.
- An agent framework compresses a domain-wide sweep into minutes, which produces a rate signature that manual administration does not, and rate separates the cases better than volume does.
- The two methods named in the instruction land in different telemetry sources, so covering only process execution leaves the installed-but-not-running case unobserved.
- The technique is normally dismissed as low value precisely because administrators share the behavior, which makes it an attractive place for an adversary to spend time.
- Correlating enumeration with subsequent lateral movement is what supplies intent, since no single query can be malicious on its own.
- The prerequisite inventory comparison is independently useful: knowing which hosts exist but do not report is actionable with no adversary in the picture, and it is the ground truth the rest of the scoring needs.
