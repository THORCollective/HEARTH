false_positive_notes: |
  Legitimate automation is also fast, also non-interactive, and also bursty — which is why raw rate is the wrong feature and the model has to score shape. Terraform and Bicep plan/apply cycles enumerate enormous numbers of resources at machine speed; Azure Policy, Defender for Cloud, CSPM tools, backup services, cost-management scrapers and inventory agents all sustain high read volumes indefinitely; and a genuine platform-team teardown of a dead environment produces a real delete burst. The separating features are provenance and breadth rather than speed: sanctioned automation runs on a schedule you can enumerate, from egress ranges you own, with a user agent tied to its tooling, against a resource scope that matches one workload, and its delete bursts are preceded by deployment operations and accompanied by a change ticket. Label every known pipeline identity and its windows before scoring, and treat the model's output as a ranking to triage, not an alert — the top of the ranking should be dominated by newly-onboarded automation you had not yet labelled, and that labelling work is itself the value. Suppress any principal whose burst correlates to an approved change window, and require the cadence-regularity feature to co-occur with at least one provenance anomaly before a principal is escalated, since regularity alone describes every well-written script in the tenant.
notes: |
  Platform: Azure (IaaS control plane). Driven by Microsoft Threat Intelligence, "Storm-3168: Agentic-driven cloud attacks using compromised service principals" (September 25, 2026). Microsoft's own conclusion was that "the timing between different operations and division of work using multiple service principals and overlapping token streams" indicated automated execution — that is a statement about distributional shape, not about any single observable, which is why this is a model-assisted hunt rather than a rule. The reported ground truth: 300+ successful read operations over 15.5 hours, then 100+ deletion attempts inside 7 minutes, with `python-requests/2.34.2` as the user agent.
  Feature engineering, per service principal per 1-hour bin, from AzureActivity - (1) Operation rate: count of operations, and count normalized against that principal's own 30-day per-hour distribution as a z-score or robust percentile rank. (2) Inter-arrival regularity: mean and coefficient of variation of the gap between consecutive operations. This is the load-bearing feature — human portal work is heavy-tailed and irregular, an agent loop is tightly clustered, and a CI/CD run is regular but short and bounded by a deployment. Compute CV over at least 30 operations to keep it stable. (3) Breadth: distinct resource providers, distinct resource types, distinct resource groups and distinct subscriptions touched. Storm-3168 spanned compute, storage, web, Key Vault, SQL, locks and Recovery Services — a spread no single application workload has RBAC for or reason to touch. (4) Read/write ratio and its inversion: ratio of read to write/delete operations in the bin, plus the delta against the previous bin. The discovery-to-destruction pivot shows up as a ratio collapsing from near-1.0 to near-0.0 between adjacent bins, which is a far sharper signal than the delete count alone. (5) Provenance novelty: whether `CallerIpAddress`, its ASN, and the user agent have been seen for this principal before, expressed as a novelty indicator rather than a blocklist. (6) Failure texture: fraction of operations returning `Failed`, and whether failures cluster on one resource type. Storm-3168's SQL deletions failed on an unsupported API version — an agent that does not adapt to a failure and keeps issuing the same malformed call is behaving unlike both a human and a tested pipeline.
  Cross-principal coordination features - Aggregate at the tenant level, not just per principal: for each 5-minute window, count distinct principals with concurrently-valid tokens issued inside the window (from `AADServicePrincipalSignInLogs`), and compute the Jaccard overlap of the resource sets they touched. Division of labour shows up as several principals with high combined breadth but low pairwise resource overlap in the same window — they are partitioning the tenant, not duplicating work. This feature is what distinguishes an orchestrated multi-identity operation from several unrelated pipelines that happen to run on the same cron.
  Modelling approach - Start unsupervised and per-principal rather than global, because ARM behaviour is wildly heterogeneous across identities: fit an isolation forest or robust Mahalanobis distance on each principal's own 30-day feature history and rank current bins by deviation. A global model trained across all principals will simply learn that "high volume" is normal for the three biggest CSPM identities and flag every small one. Then layer a simple deterministic escalation on top of the ranking: escalate when a high-deviation bin also carries provenance novelty, and page when the read/write inversion feature fires on a principal already flagged. Do not attempt a supervised classifier — destructive cloud incidents are too rare in any one tenant to provide labels, and the useful output here is a ranked worklist plus an enriched identity inventory.
  Validation and tuning - Backtest against known deployment windows: a correctly tuned model should rank approved Terraform applies highly on rate and regularity but low on breadth and provenance novelty, and the combined score should put them below any unlabelled identity. Measure precision at the top 20 ranked principal-hours per week; if the same labelled pipelines dominate week over week, the provenance features are underweighted. Re-fit monthly, and re-fit immediately after any credential rotation, since a rotation changes token issuance patterns.
  Operational output - A weekly ranked table of principal-hours with the contributing features shown per row, so a triager can see *why* a principal ranked — cadence, breadth, provenance or inversion — rather than a bare score. Feed confirmed-benign rows back into the labelled automation inventory maintained by [[B055]]; every suppression should become a documented identity, not a filter.
  Cross-technique: [[B055]] supplies the per-principal baseline and labelled automation inventory this model consumes, and [[H339]] is the targeted hunt for the `listKeys` credential harvesting that occurred inside Storm-3168's discovery phase.

# M050

Microsoft's September 25, 2026 report on Storm-3168 is unusual in that the detection conclusion is explicitly distributional. The actor authenticated compromised service principals against Azure Resource Manager and ran more than 300 successful read operations over 15.5 hours, enumerating subscriptions, virtual machines, resource groups, storage accounts, web apps, App Service plans, resource locks and Recovery Services vaults, before inverting into roughly 100 deletion attempts inside seven minutes. What Microsoft identified as the signature of agent-driven execution was not any individual API call — every one of them was authorized by an existing role assignment — but "the timing between different operations and division of work using multiple service principals and overlapping token streams."

That framing matters for defenders because it locates the detectable property in the wrong place for a rule. Any threshold on ARM operation volume is already exceeded daily by CSPM scanners and Terraform; any rule on resource deletion fires after the damage; and any blocklist on `python-requests` is trivially changed and also matches legitimate SDK use. The durable signal is that an agent loop, a human in the portal, and a tested deployment pipeline each leave characteristically different distributions of inter-operation latency, resource-type breadth, and read-to-write ratio. This hunt scores those distributions per identity so the long discovery phase — 15.5 hours in which nothing was destroyed and everything was reversible — becomes the detection opportunity instead of the seven-minute window at the end.

## Why

- The intrusion offered a fifteen-hour detection window and a seven-minute damage window, and only a cadence-and-breadth model addresses the former. By the time deletion operations appear in `AzureActivity`, storage accounts, Key Vaults and Function Apps are already gone and backup protection locks have already been targeted; the discovery phase is where response is still cheap.
- Rule-based detection is structurally defeated here because every operation was authorized. There is no failed authorization, no privilege escalation and no anomalous permission grant to key on — the compromised principals simply used the roles they legitimately held, so the only thing left to measure is how they used them.
- Agentic and scripted execution is becoming the default operating mode for cloud intrusion, which makes cadence a durable rather than incidental feature. Infrastructure, user agents and even the credentials rotate per victim, but an orchestrator driving ARM in a loop cannot avoid producing low-variance inter-operation timing and resource-type breadth far wider than any single workload's legitimate scope.
- The cross-principal coordination features detect something no per-identity monitoring can see. Several principals partitioning a tenant between them each look modest in isolation; the tell is high combined breadth with low pairwise resource overlap inside the same short window, which is only computable at tenant scope.
- The model's false positives are productive rather than wasted work: the identities that rank highest before tuning are overwhelmingly unlabelled automation, and labelling them produces the service-principal inventory most tenants lack, which is the prerequisite for every other identity-centric cloud detection.
