false_positive_notes: |
  Several ordinary mechanisms make a static path's response size vary, and the model has to account for them before scoring anything. Content negotiation and compression are the big one - the same asset returned with and without gzip or brotli produces two very different byte counts, so either normalise on uncompressed size where the log carries it or segment the distribution by content-encoding. Range requests and partial content (HTTP 206) legitimately return arbitrary sizes and should be excluded or modelled separately. Firmware upgrades and portal theme changes replace the assets wholesale, so the distribution must be segmented by build and re-learned after each change window; without that, every upgrade produces a fleet-wide spike of outliers. Error pages substituted for missing assets give a consistent small size, which is harmless but should not be learned as the path's norm. Genuinely dynamic endpoints exist in every portal - authentication, session and EPA endpoints are supposed to vary - so the model is restricted to paths that serve files, and those paths are enumerable from the web root inventory rather than guessed. Finally, note that a quiet appliance may simply lack enough history for a stable per-path distribution; treat low-sample paths as unscored rather than as anomalies, and let them accumulate.
notes: |
  Platform: Citrix NetScaler ADC and Gateway, and any VPN or application portal with forwarded access logs. Driven by Google Threat Intelligence Group / Mandiant, "Defending Against Active Exploitation of Citrix NetScaler ADC and Gateway Appliances" (29 September 2026), covering CVE-2026-88772 and CVE-2026-88771. The seed is Mandiant's published triage command, verbatim - `grep -E "/vpn/media/|/vpn/scripts/|/vpn/theme/" /var/log/httpaccess.log* | awk '$9 ~ /200|404/ && $10 > 5000'` - which flags requests to those three path prefixes returning more than five kilobytes. That command is a fixed threshold against three hardcoded paths on one appliance, run by hand during incident response. The modelling work here is to replace the constant with a learned per-path distribution, the hardcoded prefixes with the portal's actual file inventory, and the single-appliance grep with a continuous estate-wide score. Mandiant also documented the matching webshell family WHIPSHOT, which reads chunked command data from `X-UX` HTTP headers (hunted in [[H360]]), the handler-directive persistence that places PHP behind non-PHP extensions (hunted in [[H358]]), and the access-log scrubbing that makes any single appliance's logs untrustworthy.
  Why size is the right feature - The operator controls the URL, the extension, the status code and the log. A `.ico` path returning HTTP 200 is a deliberate choice, and so is deleting the line afterwards. What the operator does not control is that command output is bigger and more variable than an icon. A static asset path has, in effect, one correct response size per firmware build - the file's size, modulo compression. Any path whose size distribution has meaningful variance is either genuinely dynamic or is not serving the file it appears to serve, and the web-root inventory settles which.
  Feature set - For each request, after segmenting by firmware build and content-encoding -
  - **Size deviation from the path's own history** - the primary feature. Use a robust measure (median and median absolute deviation, or a high percentile) rather than mean and standard deviation, because a handful of webshell responses would otherwise inflate the very baseline they should stand out against.
  - **Size mismatch against the file on disk** - join the path to the web-root inventory from [[B057]]. A response materially larger than the file it claims to serve is the cleanest single signal in the model, and it needs no history at all.
  - **Variance where there should be none** - score the *path*, not just the request. A static asset path whose size distribution has a non-trivial spread is anomalous as a path, which catches a webshell whose individual responses are each unremarkable.
  - **Status and size interaction** - Mandiant's command deliberately includes 404s. A 404 returning kilobytes is a webshell answering while pretending the file is missing; this is a strong standalone rule and cheap to implement.
  - **Client concentration** - the share of a path's anomalous responses attributable to one source IP, ASN or user agent. A real asset is fetched by every portal user; a webshell is driven by one operator. Fold in whether that client ever performs a normal portal authentication.
  - **Request-side size** - inbound request bytes or header length, where logged. WHIPSHOT carries command data in chunked `X-UX` headers, so an unusually large header block on a GET for a static asset is a direct consequence of the transport design, independent of what comes back.
  - **Directory novelty** - whether the path sits in a client plug-in or media staging directory that has historically served a small, fixed set of files, and whether this specific filename has been requested before.
  Scoring approach - A simple, explainable ensemble beats a learned classifier here, and there is no labelled data to train one on anyway. Compute a per-request robust z-score on size within its path and build; add rule-based boosts for a response exceeding the on-disk file size, for a large-bodied 404, and for an oversized request header block; multiply by a client-concentration factor. Rank and review the top of the list daily rather than alerting on a threshold - the output is small because most paths have no variance at all, which is exactly why this works on appliances where almost everything is static.
  Validation before trusting the output - Reconstruct the known case. Take any appliance's log history, pick a static asset path, and confirm that the model's unscored baseline for that path is tight; then confirm the model surfaces a synthetic response an order of magnitude larger. A model whose baseline for a `.ico` path already has wide variance is being fed compressed and uncompressed responses together, or is spanning a firmware upgrade - fix the segmentation before interpreting any score.
  Log-source independence is the point - Mandiant observed the operator scrubbing access-log lines for the staging paths. Any analysis that reads the appliance's own on-box log is analysing a record the attacker edits. Run this against the forwarded copy in the SIEM and, where one exists, against the reverse proxy or WAF in front of the portal. The scrubbing then becomes its own detection - a period where the proxy logged requests to portal asset paths and the appliance did not.
  Relationship to the discrete hunts - [[H358]] finds the handler directive, [[H359]] the setuid shell, [[H360]] the tunnel and its internal pivot, and [[B057]] builds the appliance baseline all four depend on. This model is for the case where none of those can be run - the appliance is vendor-managed, shell access needs a change request, or the estate has too many devices to inspect by hand - and for continuous monitoring after the appliances have been checked once. It needs nothing but logs that are already being forwarded.

# M054

Buried in Mandiant's September 2026 NetScaler report is a one-line triage command that is smarter than it looks:

```
grep -E "/vpn/media/|/vpn/scripts/|/vpn/theme/" /var/log/httpaccess.log* | awk '$9 ~ /200|404/ && $10 > 5000'
```

Requests to the portal's own static asset directories, returning 200 or 404, with a response body over five kilobytes. The reasoning behind it is the useful part. The operator controls everything about how the webshell looks in a log — the path (`/vpn/media/something.ico`), the extension, the status code, and whether the line survives at all, since Mandiant also observed access-log scrubbing. What the operator cannot control is that an icon is an icon and command output is not.

A static asset path has one correct size per firmware build. A webshell's responses are whatever the command printed. That makes response size the one feature in the log that the attacker's disguise does not reach.

Mandiant's version is a fixed 5KB threshold against three hardcoded prefixes, run by hand on one appliance during an incident. The modelling version learns each path's own size distribution, joins it to the portal's file inventory so a response can be compared against the file it claims to serve, scores paths for having variance at all, and runs continuously across every appliance from logs already in the SIEM.

## Why

- **Size is the feature outside the operator's control.** URL, extension, method and status are all chosen; the response body is whatever `id` or `cat` produced. A disguise that is perfect in every logged field still fails on byte count.
- **Static paths make an unusually clean baseline.** Most anomaly models fight wide, drifting distributions. Here the expected variance for a given path and build is close to zero, so outliers are stark and the daily review queue is short.
- **The on-disk join needs no history.** Comparing a response size against the size of the file that path serves — available from the [[B057]] inventory — flags a webshell on its first request, before any distribution has been learned.
- **It works where nobody can touch the appliance.** Vendor-managed devices, change-controlled estates and large fleets all block the shell-command hunts. This needs only forwarded access logs.
- **It is immune to the log scrubbing, if run on the right copy.** Analysing the forwarded or upstream-proxy record defeats on-box editing, and turns the discrepancy between the two copies into an independent detection.
- **A large-bodied 404 is nearly free to implement.** Mandiant's inclusion of 404s is the sharpest single rule in the command: a file the server says does not exist does not return kilobytes.
- **Oversized request headers catch the transport directly.** WHIPSHOT chunks its commands across `X-UX` headers, so an outsized header block on a GET for a static file is a structural consequence of the design rather than an incidental artefact.
