false_positive_notes: |
  The benign population that produces high iteration counts is real, identifiable and largely static, which is what makes this model workable — but it is also dense enough that an unbaselined threshold will surface nothing but engineers. Software developers and data scientists iterate on scripts continuously and that is the entire job; CI/CD agents and build servers execute large numbers of similar commands with small parameter differences; automated test harnesses run parameterised variants by design; infrastructure-as-code and configuration-management tooling (Ansible, Terraform, DSC, Puppet) generate near-identical command lines across hosts by construction; installers and update agents retry on failure; and security tooling itself — vulnerability scanners, BAS platforms, red-team infrastructure and atomic-test runners — is explicitly built to produce exactly this shape. Any organisation running breach-and-attack simulation will light this model up on schedule, and those runs must be enumerated and excluded by host and account before the model is believed.
  Four features do the separating and the model should require several of them rather than any single one. CONTEXT is the strongest: a developer's iteration happens on a developer's workstation, under their own account, with an IDE, shell or CI agent as the parent, in a project directory, during working hours, and it has been happening every week for a year. The same shape on a domain controller, a file server, a finance workstation, or under a service account is the finding. SEMANTIC TARGET is second: benign iteration converges on building or testing an application, while the clusters in the source report converge on credential files, shadow copies, permission checks and proxy deployment — weight variants whose text references `ntds`, `SAM`, `vssadmin`, `reg save`, `net user`, `whoami /priv`, `icacls`, or a SOCKS listener far above variants that reference a package manager. NOVELTY is third: a host that has never produced this behaviour before and produced fifty instances of it this afternoon is categorically different from a host that does it daily. And PROVENANCE is fourth — scripts arriving from an external host on a non-standard port immediately before execution is not what a developer's workflow looks like.
  Two honest limitations. First, this model scores a WORKING STYLE rather than a technique, so a high score is a prioritisation signal and never an alert on its own; every output needs a human to look at what the variants actually did, and the model should feed a triage queue rather than a detection pipeline. Second, the technique-ID mapping is necessarily approximate — ATT&CK has no identifier for "the operator used a language model", so the hunt is anchored on the interpreters actually executed (`T1059.003` for the batch iteration, `T1059.006` for the Python variants) with `T1106` for the API-level execution the tooling performs. Do not read the technique IDs as the subject of the hunt; the subject is the distribution, and the IDs describe what the distribution is made of.
notes: |
  Why tempo is a defensible detection surface and not a novelty - every other axis in this campaign is cheap for the adversary to change. The scripts are regenerated on demand and share no hashes, the proxy is rebuilt nine times, the infrastructure is disposable, and the techniques themselves are ordinary. What cannot be changed without giving up the productivity advantage is the RATE and the SHAPE of iteration, because that is a direct consequence of having a model in the loop. An operator who slows down to look human has surrendered the reason for using the tooling at all. That is an unusually durable property to build an analytic on.
  Feature 1, near-duplicate variant bursts - compute minhash or simhash signatures over normalised command-line and script text (lowercase, strip paths, collapse whitespace, replace GUIDs, IPs, ports and long hex or base64 runs with placeholder tokens). Cluster at a Jaccard similarity band of roughly 0.7 to 0.95 - the band matters, because above ~0.98 is re-running the SAME artefact, which is ordinary automation, and below ~0.6 is unrelated work. The target signal is the middle: textually different, semantically the same. Count distinct cluster members per host-user per sliding 60-minute window and per 24-hour window.
  Feature 2, sequential-version detection - parse executed and written filenames for a trailing version token (`_v1`..`_v9`, `-1`..`-9`, `.1`..`.9`, date or build suffixes) and detect a monotonically increasing series from one host or one source within a short window. `socktz_v8.exe` followed by `socktz_v9.exe` is the canonical case. This feature is cheap, needs no clustering, and is worth deploying on its own on day one while the similarity model is being tuned - it is the single highest-precision element of the whole hunt.
  Feature 3, semantic-intent weighting - score each cluster by whether its members reference credential material, shadow copies, permission enumeration, proxy or tunnel setup, or directory writes. This is what prevents the model from ranking a developer's afternoon above an intrusion, and it is the feature that ties this analytic back to [[B053]], which baselines the shadow-copy and credential-file half of the same incident.
  Feature 4, failure-retry-succeed shape - the distinctive arc is a run of non-zero exits or short-lived processes followed by a successful one with materially different text. Legitimate automation usually fails identically and repeatedly, or succeeds first time; an operator working through a model fails DIFFERENTLY each time, because each attempt is a new generation rather than a retry.
  Feature 5, adjacent staging - successive tool versions retrieved from one host, frequently an open directory on a non-standard port. Unit 42 observed `hxxp[:]//167.148.195[.]53:8888/socktz_v9.exe`. Pair a download from a bare-IP HTTP URL on a non-standard port with execution of the downloaded file within seconds, and weight higher when previous siblings from the same directory were fetched earlier the same day.
  Scoring and output - combine the five features into a per-host-per-day score, fit percentiles per host ROLE rather than estate-wide (a build server and a domain controller have no business sharing a threshold), and review the top tail daily. The output is a ranked triage queue with the member variants attached, not an alert. Start by running it retrospectively over 60 days of history to see the shape of the estate's own benign tail before choosing any cut-off - the review of that tail typically identifies the BAS platform, the CI fleet and three developers, and after excluding them the queue is usually short.
  Verbatim artefacts from the source report, for retrospective search only - `CL-CRI-1163` (Brazilian financial sector, initial access by resume-themed phishing attachment in February 2026, staging pivot through a vulnerable WordPress site) - open directory `167.148.195[.]53:8888`, tooling `socktz_v8.exe` and `socktz_v9.exe` (Go-based SOCKS5 proxy, versions 1-9 observed), AI-iteration filenames `exploit_creative.py`, `exploit_careful.py`, `rce_focused.py` and `_output`-suffixed siblings, malware SHA-256 `a38b2cf8beff32a276eed8783723ecf8cc53d7dc88669e1b998dddc4db6fe996` and `87bf8bc8b4a2cf34f0af1afe161f123a3d200e77f6c6f41b81bf6ae66ee172ec`. `CL-CRI-1131` (Mexican transportation) - self-hosted NextChat LLM interface at `178.128.87[.]160:3000`, DuckDNS C2 `m-doxa-apodo`, `m-doxa-geo`, `m-doxa-intel`, `m-doxa-vacunas` and `m-doxa-sre` under `duckdns[.]org`, exfiltration to `62.171.185[.]97`, additional activity from `165.22.184[.]26`.
  A cheap adjacent query worth running regardless - a SELF-HOSTED LLM interface reachable from the intrusion infrastructure is itself an artefact. NextChat on TCP 3000 was observed in this campaign; an estate seeing outbound connections from a server to a bare IP on port 3000, 8080 or 7860 carrying chat-completion-shaped traffic is worth a look independent of this model. Egress to commercial model-provider APIs from servers that have no business calling them belongs in the same query.

# M048

Unit 42's report on AI-assisted intrusions in Latin America documents two unrelated clusters, and the most useful thing in it is not an indicator. It is a rhythm. In the Brazilian financial cluster, the operators' own open directory held `exploit_creative.py`, `exploit_careful.py` and `rce_focused.py` side by side — three named strategies for the same objective, with their outputs written to `_output`-suffixed siblings — alongside nine sequential builds of a Go SOCKS5 proxy, `socktz_v1.exe` through `socktz_v9.exe`. In the Mexican transportation cluster the same shape shows up as batch scripts retrying credential collection, permission-checking between attempts.

Human operators do not work like this. Nine versioned builds of a proxy in a single engagement is not tradecraft, it is a compile-run-read-the-error loop running at machine speed with a person supervising. And conventional automation does not work like this either: a scheduled job re-runs the same artefact, byte for byte. What sits between those two — textually distinct, semantically identical, produced in bursts, converging on a goal through variation rather than repetition — is the signature of a model in the loop, and it is a distribution rather than an indicator. That makes it an Alchemy problem: the detection is a clustering and scoring exercise over text similarity and timing, not a query anyone can express as a search string.

## Why

- **It scores the one thing the adversary cannot cheaply change.** The scripts are regenerated per engagement and share no hashes. The proxy is rebuilt nine times over. The infrastructure is disposable and the techniques are ordinary. The iteration rate is not incidental to any of that — it is the entire reason for adopting the tooling, and an operator who throttles it to look human has given up the advantage that made them adopt it. Durable analytics are built on things the adversary is unwilling to give up.
- **A rule cannot express it, because the signal is in the relationship between events rather than in any event.** No individual command line here is suspicious. `exploit_careful.py` is a filename. A batch script that copies a file is a batch script that copies a file. What distinguishes the intrusion is that forty of them, all slightly different and all aimed at the same objective, executed inside an hour on a host that had never seen anything like it. That is a property of a distribution, which is precisely the case where model-assisted detection earns its keep over signatures.
- **The similarity band is the whole trick, and it is why naive deduplication misses this.** Above roughly 0.98 similarity you are looking at ordinary automation re-running an identical artefact; below about 0.6 you are looking at unrelated work. The adversarial signal lives in the middle — different text, same meaning — which is exactly the band that both exact-match deduplication and loose keyword grouping throw away. Getting the band right converts an unusable feature into a precise one.
- **One sub-feature is high-precision enough to ship immediately.** Monotonic version series in executed filenames — `socktz_v8.exe` then `socktz_v9.exe`, fetched from the same open directory within the hour — needs no clustering, no baseline, and almost no compute. It can go into production on day one while the similarity model is still being fitted, and it is the single sharpest element of the analytic.
- **Running it is how an organisation finds out what its own benign tail looks like, which it will need regardless.** The first pass over sixty days of history reliably surfaces the BAS platform, the CI fleet and a handful of developers. Enumerating those is work that has to happen before any behavioural analytic on execution volume can be trusted, and it produces a reusable exclusion set. The intrusion-detection value is the goal; the inventory of what legitimately iterates in the estate is the consolation prize, and it is not a small one.
