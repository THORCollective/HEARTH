  separate the populations are the ordering and the failure ratio: a legitimate new workload is deployed

# M040

Unit 42's investigation into an AI-assisted intrusion contains one detail that reframes what a stolen
cloud key is worth. The actor breached a publicly accessible web service, mapped it with an automated
service discovery tool, scraped hard-coded tokens and service passwords out of code repositories — and
then, in Unit 42's words, "turned the victim's AI endpoints into post-compromise infrastructure — using
the company's compute power to perpetrate future moves."

The key was not used to reach data. It was used to reach a model, and the model was used to run the rest
of the attack. MITRE ATLAS has a name for this — `AML.T0043`, LLM invocations via stolen API keys — and
ATT&CK now covers it as T1496.004, Cloud Service Hijacking. Sysdig named the general pattern LLMjacking
in 2024, and what has changed since is the motive: early cases resold access, this one used the victim`s
inference capacity as operational tooling for the intrusion in progress.

It is worth being direct about the limits of the source report. Unit 42 does not name the provider, the
API calls, or the IAM actions, and offers no detection queries — the observable behaviours it does give
are generic: structured Markdown files passing information between agents, Python caches and paired
asset folders, and "bursty API requests, rapid 401/200 HTTP state shifts." That last one is the useful
piece, and it happens to describe precisely what the well-documented public detection work on this
technique also describes.

That convergence is why this is worth building as an analytic rather than waiting for better reporting.
The behaviour has a fingerprint that shows up consistently across cases:

**Enumerate, then invoke.** An actor with a found key does not know what it can reach. They list the
model catalogue and check availability before they invoke anything. A legitimate workload was deployed
with its model IDs in configuration and never enumerates at all. The ordering is the feature.

**Authorization failures scattered through the sequence.** The rapid 401/200 alternation Unit 42
describes is a principal discovering its own permissions at runtime. A production workload knows what it
is permitted to call; its denied-to-allowed ratio is essentially zero. This is probably the single
strongest feature in the model and it is available in CloudTrail with no additional configuration.

**A principal with no inference history.** The identity invoking the model has never done so before.
Standing alone this is a weak feature — every legitimate new AI project also starts here, and AI adoption
is growing fast enough that first-use events are common — which is exactly why it has to be scored
jointly with the ordering and failure features rather than alerted on.

**Region and network novelty.** Actors prefer regions the organization has not enabled and does not
watch, and they arrive from hosting-provider or proxy ASNs. Both are cheap to compute given a register of
enabled regions and a list of the organization's own egress ranges.

One field deserves specific mention because it is unusually clean. Bedrock records
`additionalEventData.callWithBearerToken = true` for API-key authenticated requests and omits it for
SigV4-signed ones. That single boolean separates long-lived key usage from role-assumed workload usage
without any modelling, and most organizations have never looked at it.

The reason to score this rather than threshold it is the same reason it is hard: the calls are
legitimate. They are authorized, well-formed, and structurally identical to the organization's own AI
traffic. There is no malformed request to catch and no permission boundary being crossed. What is
anomalous is the joint pattern — this identity, doing this for the first time, in this order, from
there, with that failure ratio — and joint rarity across weak features is precisely what a scoring model
does and a rule cannot.

The upstream half of the chain is worth hunting at the same time, because it is where this is cheapest
to stop. The credentials came from hard-coded secrets in code repositories. Any key surfaced by secret
scanning should be checked against the inference history described here before it is quietly rotated —
rotation closes the hole but tells you nothing about whether it was already used.

[[M039]] covers the adjacent pattern of adversaries renting trusted web services rather than registering
infrastructure, which is the same borrowed-legitimacy logic applied to delivery and exfiltration.
[[H226]] and [[B042]] cover resource hijacking in its older, compute-oriented forms, which is a useful
contrast: the detection there can lean on sustained resource consumption, and here it cannot.

## Why

- **The compute being stolen is now operational tooling, not just a resale commodity.** Earlier
  LLMjacking cases monetized access. In Unit 42's investigation the actor used the victim's inference
  capacity to run the attack against the victim. That changes the severity calculation: this is not a
  billing problem with a security label, it is an active intrusion using infrastructure the defender
  owns, logs and pays for — and every request is authorized, so nothing objects.
- **The denied-to-allowed ratio is a strong feature that is already being collected.** A deployed
  workload was configured with the models it may call and produces essentially no authorization
  failures. A principal exploring what a found key can reach produces a scatter of them, which is exactly
  the "rapid 401/200 state shifts" the source report describes. CloudTrail captures this by default, so
  the feature costs nothing to compute and is one of the few that separates the populations cleanly on
  its own.
- **Enumeration before invocation is a behavioural tell that legitimate workloads never produce.**
  Applications do not list the foundation model catalogue at runtime; their model IDs are in
  configuration. An actor must enumerate because they do not know what the key reaches. Ordering, not
  volume, is the discriminator — which matters because volume is where the benign and malicious
  distributions overlap most.
- **First-use anomaly detection alone will fail, and it is worth designing around that rather than
  discovering it in production.** Organizational AI adoption is growing fast enough that new principals
  invoking models for the first time is an everyday event. Any analytic weighted primarily on first-use
  will produce a steady stream of false positives and be switched off within a month. Weighting the
  ordering and failure-ratio features heavily and first-use lightly is the difference between something
  that survives and something that does not.
- **`callWithBearerToken` is a free, unmodelled discriminator sitting unused in most estates.** It is a
  single boolean that separates long-lived API-key authentication from role-assumed workload
  authentication. Long-lived keys are the ones that leak into repositories, which is precisely how this
  intrusion began. Simply reporting on which principals use bearer-token authentication against
  inference endpoints is a useful exercise independent of any scoring.
- **The credential source is a hunt of its own, and rotation is not the end of it.** The keys came from
  hard-coded tokens and service passwords in code repositories. Most organizations run secret scanning
  and treat a hit as a rotation ticket. Joining every discovered key to the inference history described
  here answers the question rotation does not: whether it was used before it was found, and what it
  reached.
- **This is where resource hijacking detection has to change technique.** Cryptomining could be caught by
  sustained resource consumption and characteristic network destinations. Inference abuse produces
  ordinary API traffic to the provider's own endpoints in bursts that resemble legitimate batch work.
  The consumption signal that carried the older detections is gone, which is what forces the identity and
  sequence modelling here.
