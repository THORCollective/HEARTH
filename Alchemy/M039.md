  is not a hunt where the noise can be tuned away — it must be modelled. Cloud object storage underpins
  software distribution, vendor updaters, CDNs, mobile applications, backup products and most SaaS file
  handling, and paste and text-storage sites are used daily by developers and support staff for
  legitimate reasons. Any scoring that treats a request to `aliyuncs.com` or a paste site as inherently
  suspicious will drown. Four cautions on specific features. First, first-seen bucket rarity decays badly
  in estates with many software vendors, because every vendor release cycle introduces new buckets — pin
  rarity to the (process, bucket) pair rather than the bucket alone, since a known updater reaching a new
  bucket for its own product is routine while a browser reaching a first-seen bucket for a ZIP is not.

# M039

Two unrelated campaigns reported in the same week reached the same conclusion about infrastructure, from
opposite ends of the intrusion.

Microsoft's counterfeit software download campaign, attributed to Silver Fox, needed somewhere to host
payload archives that would not be blocked and would not look strange to a user downloading software.
It used Alibaba Cloud OSS: `newopt001.oss-cn-hongkong.aliyuncs.com/innstll.1.0.61.zip` and
`upitem.oss-cn-hangzhou.aliyuncs.com`. Mandiant's BREEZE COMET, a financially motivated actor targeting
Brazilian payment infrastructure, needed somewhere to send harvested cloud secrets and CI/CD tokens
from inside a victim network without tripping data-loss controls. It used `dontpad.com`, a public paste
site.

Same reasoning, different direction. The adversary stops acquiring infrastructure and starts renting
the reputation of infrastructure the target already trusts.

This breaks the standard defensive response in a way worth being precise about, because it is not the
usual "the IOCs rotate" complaint. `aliyuncs.com` is a real cloud provider serving enormous legitimate
traffic. Paste sites are used daily by developers. Both terminate TLS at reputable providers with valid
certificates, both frequently sit on a proxy allowlist already, and both have genuinely good reputation
scores — because the reputation is real. It is being borrowed, not forged. Blocking the domain is not
an option anyone will accept, and reputation scoring returns exactly the answer the adversary is
counting on.

So the model cannot score the service. It has to score the *interaction*, and there are four features
that carry most of the signal.

**Direction, relative to the service's normal role.** Cloud object storage, from an endpoint's point of
view, is a download service. Paste sites are a read service. An endpoint POSTing several kilobytes to a
paste site, or uploading to a storage tenancy that is not yours, is anomalous by role rather than by
volume — and a few kilobytes of stolen AWS keys is far too small for any volumetric DLP threshold to
notice.

**Sub-resource rarity, keyed to the process.** The domain is common; the bucket is not. A first-seen
bucket subdomain is a meaningful event, but only in context — a known vendor updater reaching a new
bucket for its own product is a release, while `msedge.exe` fetching a ZIP from a bucket nothing in the
estate has ever touched is a delivery. Pinning rarity to the (process, bucket) pair rather than the
bucket alone is what stops this feature from decaying to noise in an estate with many software vendors.

**Payload class against declared type.** Objects staged for delivery are archives and executables, often
served as `application/octet-stream` with a mismatched extension. The useful comparison is three-way —
declared content type, observed magic bytes, and file extension — rather than any filename check, since
Microsoft observed the same archive name serving two content-distinct payloads within roughly 69
seconds. Server-side regeneration at that cadence makes hashes and names worthless and makes shape the
only stable thing about the object.

**Tenancy ownership.** The highest-value single feature in the whole model is cheap: a request to a
provider you use, to a tenancy you do not own. Most organizations can enumerate their own buckets in an
afternoon and have never expressed that list to their proxy.

Microsoft's own guidance points at the same conclusion from the endpoint side and is worth adopting
directly: pivot on `FileOriginUrl` and `FileOriginReferrerUrl` rather than on either host, because the
pairing of landing page to delivery host survives the rotation of both. Their infrastructure analysis
found the impersonation domains clustered by ASN and nameserver rather than by netblock or geography,
which is the same lesson at the registration layer — the durable relationships are structural, not
addressable.

This analytic is deliberately scoped to the *web services* half of resource development. [[M020]] covers
the domains half — string-similarity and freshness scoring of look-alike registered domains — and the
two are complementary rather than overlapping: M020 models infrastructure the adversary registered, this
one models infrastructure they merely rented. [[H292]] covers what the delivered payload from the
Microsoft campaign does once it executes.

## Why

- **Blocklists and reputation scoring both fail here by construction, not by lag.** The usual objection
  to IOC-based defence is that indicators go stale. This is a different and harder problem: the indicator
  is a service with genuinely excellent reputation, enormous legitimate traffic, valid TLS, and very
  likely an existing proxy allowlist entry. There is no version of the blocklist that works, which is
  what forces a scoring model rather than making one merely preferable.
- **Direction is a strong, cheap feature that most log pipelines throw away.** Bytes-sent and
  bytes-received per transaction are usually normalized out or aggregated to session totals. Restoring
  them makes the analytic possible, because an endpoint uploading to a paste site is anomalous by the
  service's role regardless of size — and size is exactly what will not help, since a few kilobytes of
  stolen cloud credentials sits far below any volumetric threshold anyone has configured.
- **Tenancy ownership is the highest-yield feature and almost nobody has expressed it.** Most
  organizations use cloud object storage and can enumerate their own buckets quickly, yet very few have
  told any control which storage tenancies are theirs. Once that list exists, "our provider, not our
  bucket" becomes a single high-signal feature that requires no behavioural modelling at all and would
  have flagged the Microsoft campaign's staging on the first request.
- **Server-side payload regeneration makes content-based indicators structurally useless.** Microsoft
  observed two content-distinct copies of the same-named archive written roughly 69 seconds apart. At
  that cadence, hashes describe one download and nothing else. Modelling the shape of the transaction —
  who fetched, from where, what class of object, in which direction — is not a fallback for when the
  hash is unavailable, it is the only stable description of the behaviour.
- **Two unrelated actors converged on this in the same reporting week, from opposite directions.** A
  Chinese-speaking commodity-malware operation used it for delivery and a Brazilian financially motivated
  group used it for exfiltration. That convergence suggests the pattern is being adopted because it works
  generally against current controls, not because of any shared tooling — which makes an analytic that
  generalizes across services considerably more valuable than a rule for either campaign.
- **Scoring the sub-resource rather than the domain is what keeps the model alive as buckets rotate.**
  Buckets and paste URLs are cheap and disposable; the provider is not. Keying rarity to the bucket or
  URL path, and pinning it to the initiating process, means the model does not need to have seen this
  campaign before — a first-seen bucket serving an archive to a browser scores the same whether it is
  Silver Fox or whoever replaces them.
