title: Scoring endpoint traffic to legitimate SaaS platforms for bidirectional C2 — process rarity, interval regularity, and flow asymmetry
hypothesis: >-
  Every campaign type in July 2026's Korean APT reporting routed command and control through a service you
  cannot block: commands over a **PubNub** channel with base64 results returned, staging and follow-on scripts
  from **GitHub**, decoys from **Google Drive**, and bidirectional exfil-and-retrieval through **Dropbox**.
  Domain reputation is worthless here — these domains are years old, correctly signed, and already whitelisted —
  and blocking them wholesale breaks the business. What does not generalise across the estate is WHICH PROCESS
  on WHICH HOST talks to them, HOW REGULARLY, and IN WHICH DIRECTION. Score each (host, process, SaaS
  destination) tuple over a rolling window on the joint extremity of process-destination novelty, interval
  regularity, upload/download asymmetry, and session-count-to-data-volume ratio, against 90 days of the estate's
  own history — because the beacon that hides perfectly inside `api.dropboxapi.com` is still a non-browser
  process contacting it every 300 seconds from a host that never has before.

required_data_sources:
  - Web proxy / secure web gateway logs — full URL or at minimum host + path prefix, HTTP method, bytes_sent, bytes_received, user_agent, authenticated user, source host, timestamp, and session duration. The upload/download byte counts are the single most important fields in this hunt and are frequently truncated or dropped at ingest
  - Zeek `conn.log` and `ssl.log` (or equivalent NSM) — `id.orig_h`, `id.resp_h`, `orig_bytes`, `resp_bytes`, `duration`, `conn_state`, and SNI `server_name`. Zeek's connection records are what beaconing analysis (RITA and equivalents) consumes; SNI carries the destination even without TLS inspection
  - Sysmon Event ID 3 (NetworkConnect) and Defender XDR DeviceNetworkEvents — **RemoteUrl, RemoteIP, RemotePort, InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessCommandLine, InitiatingProcessParentFileName**. Process attribution is what makes this hunt work; a netflow-only version cannot distinguish the corporate Dropbox client from an AutoIt script
  - Sysmon Event ID 22 (DNSQuery) / DeviceEvents `DnsQueryResponse` — resolution of `*.pubnub.com`, `ps.pndsn.com`, `*.dropboxapi.com`, `api.github.com`, `raw.githubusercontent.com`, `*.googleapis.com` attributed to the querying process. Catches the lookup even when the connection is short-lived
  - Sysmon Event ID 1 / Windows Security 4688 — full lineage and OriginalFileName for whatever process is making the connections, which is how a renamed interpreter is still identified
  - DNS server or DNS-layer gateway logs (Umbrella, Cloudflare Gateway) — estate-wide resolution counts per SaaS domain, giving the denominator for "how many hosts have ever contacted this service"
  - CASB / SaaS tenant audit logs where available — corporate Dropbox, GitHub Enterprise, and Google Workspace tenant logs let you subtract sanctioned account activity from the population, leaving unsanctioned use
  - Software and role inventory — which hosts legitimately run the Dropbox client, Git, developer tooling, or a business function that uses these APIs. Without this the model has no denominator and will rank the engineering department first, forever
  - 90 days of retained history for all of the above — the model scores against the estate's own past, so the lookback IS a data source, not a convenience
false_positive_notes: |
  Traffic to these services is enormous and overwhelmingly legitimate. That is the entire premise of the
  technique and the reason this is scored rather than thresholded. Enumerate these populations before treating
  any score as actionable:
  - Sanctioned file-sync clients. `Dropbox.exe`, `OneDrive.exe`, `googledrivesync.exe` maintain long-lived
    connections with regular keepalives that look exactly like beaconing on an interval metric. They are also
    enormous in volume and stable in profile — they should score near zero forever, and if they do not, the
    per-process baseline is not working.
  - Developer workstations and CI runners. `git.exe`, `curl.exe`, package managers, IDEs, and language
    toolchains hit `api.github.com`, `raw.githubusercontent.com` and `*.googleapis.com` constantly and at
    machine cadence. This is the largest and most stubborn benign population.
  - Mobile-adjacent and IoT platforms legitimately using PubNub — some line-of-business and building-management
    applications do. Where this exists it is a small, nameable set of hosts.
  - Browsers, which contact all of these for ordinary reasons and should be modelled separately or excluded
    from the process-novelty feature entirely (their destination set is unbounded by design).
  - Backup, telemetry, crash-reporting, and update agents.
  - Security tooling enriching indicators against GitHub-hosted rule repositories.
  The model must therefore:
  (1) BASELINE PER (host, process, destination-service), never globally. A CI runner pulling from GitHub every
      four minutes has a stable, recognisable, enormous profile — regularity is normal FOR IT. The signal is a
      process whose own history is silent suddenly speaking on a schedule.
  (2) TREAT SANCTIONED CLIENTS AS ENUMERATED POPULATIONS WITH THEIR OWN BASELINES, never as global
      suppressions. A blanket exclusion on "Dropbox.exe" is a name an adversary can simply adopt — the source
      report's own tradecraft includes renaming interpreters for exactly this reason. Per-identity baselining
      still catches a masquerading binary because the PATH and signer differ.
  (3) WEIGHT PROCESS NOVELTY ABOVE VOLUME. The adversary's traffic is small; the benign traffic is huge. Any
      feature that rewards volume ranks the file-sync clients first.
  (4) SCORE BROWSERS SEPARATELY OR NOT AT ALL on the novelty axis, while still scoring browser-child processes.
  (5) EXPECT THE FIRST 2–3 WEEKS to be dominated by unmodelled developer and agent populations. Enumerate and
      name them before treating any score as actionable, and re-baseline after major tooling changes.
notes: |
  PLATFORM: Windows endpoints and servers (the source campaigns are Windows), though the network-side features
  are platform-agnostic and the model applies unchanged to macOS and Linux hosts where process attribution
  exists.

  SOURCE: AhnLab ASEC, "July 2026 Threat Trend Report on APT Attacks (South Korea)" (2026-08-27), tagged
  Kimsuky. The report cites no ATT&CK IDs; this mapping is derived from described behaviour. Per-type C2:
  Type A receives commands over a **PubNub channel** and exfiltrates results base64-encoded; Type B stages from
  an actor-run **GitHub** repository or **Google Drive**; Type C pulls decoys and follow-on scripts from
  **GitHub**; Type D uses **Dropbox** for both exfiltration and BAT retrieval — bidirectional, which is the
  defining property of T1102.002 as opposed to the one-way T1102.003. The report's own framing is that most C2
  here is legitimate-service abuse.

  WHY THIS IS ALCHEMY AND NOT A RULE — the rubric, walked. Flames rejected: there is no discrete IOC. The
  destinations are legitimate, years-old, correctly-signed services that appear on every allowlist; the actor's
  account names, repository names, and channel identifiers are per-campaign and unpublished; and TLS hides the
  content. A rule of the form "alert on Dropbox traffic" returns the estate. Embers was a serious contender and
  is the closest neighbour — one could frame this as set membership, "has this process ever contacted this
  service before," the same shape as [[B037]] and [[B038]]. It was rejected because the scale and the legitimate
  first-time rate are different in kind: developer tooling contacts new GitHub and Google endpoints legitimately
  every day, browsers contact everything, and the edge set never converges. That is precisely the Alchemy
  trigger — rule-based detection too noisy to be operational at scale, requiring per-entity distributions
  rather than a lookup. Set membership is retained as the single highest-weighted FEATURE (Feature 1), not as
  the decision.

  THE MODEL:
  - UNIT OF SCORING: the tuple (host, process image + signer + path, destination service), plus a per-host
    aggregate over the window. Score both — the tuple catches the individual implant, the aggregate catches a
    host that has started talking to three unusual services at once.
  - WINDOW: rolling 24 hours for interval and asymmetry features; 90 days of history for the baselines.
  - FEATURE 1 — PROCESS-DESTINATION NOVELTY (highest weight). Has this (process, destination service) pair ever
    been observed on this host in 90 days? On any host in the estate? A first-ever pair is the atomic unit here
    and it is the feature the adversary cannot avoid generating: their implant is, by definition, a process that
    has not spoken to this service before. Exclude browsers from this feature; score everything else.
  - FEATURE 2 — INTERVAL REGULARITY. Coefficient of variation of inter-connection intervals, plus a
    Fourier/autocorrelation check for a dominant period, scored against that process's own historical
    distribution. Machine cadence is the point; a low CV across dozens of connections is strong. Jitter
    degrades this feature deliberately — which is why it is one of six and not the model.
  - FEATURE 3 — FLOW ASYMMETRY. Ratio of bytes_sent to bytes_received per session and aggregated per window.
    Command retrieval is small-down; result exfiltration is larger-up. MITRE's own detection guidance names
    "a client sending significantly more data than it receives" as the network-data anomaly to look for, and
    the Type D Dropbox pattern is both directions through one service, which is a distinctive shape rather than
    a generic upload.
  - FEATURE 4 — SESSION-COUNT-TO-VOLUME RATIO. Many small sessions moving little data is a beacon. Few large
    sessions is a file sync. This single ratio separates the implant from the sanctioned Dropbox client better
    than any absolute threshold, because it is scale-free.
  - FEATURE 5 — PROCESS PLAUSIBILITY. Is the connecting process one that has any business making outbound
    connections at all? An AutoIt interpreter, `pythonw.exe` from a temp path, `mshta.exe`, `wscript.exe`,
    `regsvr32.exe`, or a renamed binary (OriginalFileName ≠ image name) contacting a SaaS API is near-decisive
    on its own. Weight it heavily; it is cheap and it is the feature that ties this hunt to the endpoint hunts.
  - FEATURE 6 — PATH AND SIGNER OF THE CONNECTING BINARY. Running from `C:\ProgramData\`, `%APPDATA%`, or
    `%TEMP%`, unsigned or invalidly signed. Does not detect on its own; ranks decisively when combined.
  - FEATURE 7 — SERVICE RARITY IN THE ESTATE. What fraction of hosts have ever contacted this service? PubNub
    in a typical enterprise is near zero, GitHub is near universal on engineering subnets and near zero
    elsewhere. Compute per subnet or per host-role, never estate-wide, or the engineering department dominates
    the queue permanently.
  - FEATURE 8 — UPSTREAM COUPLING (near-decisive when present). Did this host, in the preceding hours, open an
    LNK from email, spawn PowerShell from `explorer.exe`, write an executable into `ProgramData`, or register
    a scheduled task under an update-themed name? Joining the C2 score to [[H275]], [[H276]] and [[B040]]
    findings turns a ranked anomaly into an incident.
  - SCORING: convert each feature to an empirical percentile against the relevant historical distribution and
    combine MULTIPLICATIVELY, so joint extremity is required. High regularity alone is a file-sync client;
    high novelty alone is a developer trying something new; novelty AND regularity AND asymmetry AND an
    implausible process is the implant.
  - OUTPUT: a ranked review queue of (host, process, service) clusters showing the contributing feature values,
    the connection timeline, and the process lineage — not a bare score. Render the interval plot; a beacon is
    recognisable to a human in about two seconds and that is the strongest argument the model can make for
    itself.

  START WITH PUBNUB, TODAY, BEFORE THE MODEL EXISTS. In most enterprises the true baseline for
  `*.pubnub.com` / `ps.pndsn.com` is zero. It is a legitimate real-time messaging platform with real customers,
  which is why it has clean reputation and why nobody blocks it — and also why almost no corporate Windows
  endpoint has any reason to contact it. A single DNS or proxy query for that domain across the estate is a
  five-minute exercise with a plausible chance of a finding, and it needs none of the modelling above. Do that
  first; build the model for the services where the answer is not zero.

  VALIDATION: replay against a known-clean 90-day window and confirm the top of the queue is enumerable,
  nameable populations — file-sync clients, CI runners, developer workstations. If it is not, those populations
  are unmodelled and the baseline work is incomplete. Then, with authorisation, run a red-team implant beaconing
  through a Dropbox or GitHub account at a 5-minute interval with jitter from a non-developer host, and confirm
  it ranks above the sanctioned Dropbox client. If it does not, novelty and process plausibility are
  underweighted relative to regularity.

  ALSO DO THE CHEAP THINGS. Alert on any non-browser, non-inventoried process contacting these APIs. Alert on
  script interpreters making outbound HTTPS at all. Block PubNub outright if no business function uses it.
  This model is the layer that catches the case those rules structurally cannot — a sanctioned-looking process
  on a sanctioned service — not a replacement for them.

# M036

Seven campaign types in one month's reporting, and between them the command channel ran over PubNub, GitHub, Google Drive, and Dropbox. Not one actor-registered domain among them. Nothing to sinkhole, nothing to add to a blocklist, nothing a domain-age heuristic will ever flag — these services are years old, correctly signed, already on your allowlist, and used by your business.

Blocking them is not available. Inspecting them mostly is not either. What remains is metadata, and the metadata is still telling: the implant is a process that has never contacted this service before, connecting on a schedule a human would not keep, sending more than it receives, in dozens of small sessions that move almost no data — from a host whose entire history with that service is silence.

None of those features works alone. A file-sync client is perfectly regular. A developer's first pull from a new repository is perfectly novel. The signal is joint extremity across all of them at once, scored against each entity's own past rather than a global threshold, because the only thing that distinguishes the implant from the Dropbox client is context that varies host by host.

## Why

- **Reputation and domain age fail completely here, and they are what most C2 detection rests on.** The standard pipeline — newly registered domains, low-reputation destinations, threat-intel feed matches — has exactly zero coverage of a Dropbox API endpoint. That is the whole reason actors moved to trusted SaaS, and it means the absence of alerts on these destinations is not evidence of absence. Anything built here has to work from behaviour, because every identity-based signal has already been conceded.

- **Process attribution is what makes the problem tractable at all.** Netflow can tell you a host talked to `api.dropboxapi.com`; thousands do, all day. Sysmon EID 3 or `DeviceNetworkEvents` tells you it was `AutoIt3.exe` running from `C:\ProgramData`, which is not ambiguous. This is why the model is scored per (host, process, service) rather than per destination — the destination carries no information, and the process carries almost all of it. An estate that collects proxy logs but not process-attributed network events cannot run this hunt, and finding that out is itself worth the exercise.

- **Novelty is the feature the adversary cannot avoid generating.** They can jitter the interval, pad the payload, match a plausible user-agent, and pick the same service your business already uses. They cannot make their implant a process that has previously contacted that service on that host, because it did not exist there before. Weighting first-ever (process, service) pairs above every volumetric feature targets the objective rather than any particular implementation of it, and it is the feature that survives a careful operator.

- **Per-entity baselining is the difference between a usable queue and a permanent list of developers.** Regularity is the intuitive beacon signal and it fails immediately in a real estate: `Dropbox.exe` keepalives and CI runners polling GitHub are more regular than most implants, at far greater volume. A global threshold either sits above them and misses everything or sits below them and returns them forever. Scoring each feature against the specific process's own distribution makes "normal for a CI runner" and "normal for an AutoIt script" separate statements, and no absolute number ever has to be chosen.

- **Never suppress by process name, because renaming is already in this actor's toolkit.** A blanket exclusion for `Dropbox.exe` is an instruction the adversary can follow — and the same reporting describes renaming interpreters and registering `pythonw.exe` under a disguised name precisely to inherit trust. Baselining per identity, keyed on path and signer rather than filename, still catches a masquerading binary because the path and signature differ even when the name does not. A suppression is a gift; a baseline is not.

- **PubNub is a free finding available before any of this is built.** It is a legitimate real-time messaging platform, which is exactly why it has clean reputation and why nobody blocks it — and also why a corporate Windows endpoint has essentially no reason to contact it. In most enterprises the honest baseline is zero. One DNS query across the estate for `*.pubnub.com` and `ps.pndsn.com` is five minutes of work with a real chance of returning something, and it requires none of the modelling. Do the zero-baseline services first; model the ones where the answer is not zero.

- **The multiplicative combination is what keeps the queue short, and it is a deliberate design choice.** Additive scoring lets one extreme feature carry a candidate to the top, which is how these models fill with file-sync clients scoring maximum on regularity. Requiring joint extremity — novel AND regular AND asymmetric AND implausible-process — means the sanctioned populations, each extreme on exactly one axis, sit near the bottom permanently without ever being suppressed.

- **Upstream coupling turns a score into an incident, and the other hunts in this batch supply it.** A novel beacon to GitHub is an anomaly. A novel beacon to GitHub from a host that opened an LNK from email four hours ago, wrote an interpreter into `ProgramData`, and registered a scheduled task calling itself a OneDrive update is the reported chain reproducing itself in your telemetry. Both halves are events most estates already collect and almost never join, and the join is the highest-value feature in the model.

- **Render the intervals, don't just score them.** A number attached to a host is something an analyst has to trust. A plot showing forty connections spaced 300 seconds apart, from a process nobody recognises, is something they can see. Models that emit scores get ignored; models that emit a picture of the beacon get worked, and that is a requirement here rather than a presentation preference.
