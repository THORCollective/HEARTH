hypothesis: >-
  An autonomous agent driving Azure Resource Manager with stale knowledge of the API surface generates a distinctive repair sequence: a request returns HTTP 400, and within roughly 20 to 120 seconds the same identity reissues a request whose URL path is identical and whose only difference is the `api-version` parameter or the HTTP method, and that request returns HTTP 200. A sequence model over (identity, normalised resource path, api-version, method, status) scores this self-correction pattern, which separates agent-driven control-plane activity from both human operators - who correct over minutes with intervening reads - and pipelines, which never correct at all because their api-versions are pinned in code.

false_positive_notes: |
  The HTTP 400 half of this pattern is common and benign on its own; it is the *repair* that is rare. Expect these and model them out rather than filtering on status alone:
  - SDK and CLI upgrades. A new `azure-cli`, Terraform provider or ARM SDK release changes default api-versions for a whole fleet at once. This produces a fleet-wide step change at a single point in time, not a per-resource correction loop, and the before/after versions are both well-known releases. Hold a changelog of tool versions per identity so an upgrade day can be labelled rather than investigated repeatedly.
  - Retry logic with version fallback. Some vendor tooling (backup products, CSPM scanners, migration utilities) deliberately probes several api-versions to support mixed-age tenants. These are high-volume, perfectly periodic, and iterate versions in a fixed order across every resource of a type - the opposite of a targeted correction against one resource path. Allowlist the application ID after confirming the fallback ladder is identical across resources.
  - Preview-feature work by a human engineer. An engineer bisecting api-versions in a portal or notebook session produces the same corrections, but with intervening reads, long and irregular gaps, and activity confined to a single resource group. The inter-request gap distribution is the separator: agent repair clusters tightly in the tens of seconds, human repair spreads over minutes with a long tail.
  - Resource providers that genuinely return 400 for unsupported-but-valid combinations (a feature not enabled in a region, a SKU mismatch). These do not resolve on a version change, so the required HTTP 200 on the follow-up excludes them.
  Because the benign shapes above are defined by their *distribution* rather than by a field value, a static rule on "400 followed by 200" is unusable in a tenant of any size. That is why this is modelled rather than alerted.
notes: |
  Why this is a model and not a rule - a tenant of moderate size produces thousands of HTTP 400 control-plane responses a day from SDK drift, deprecated versions and pipeline churn, and the absolute count scales with how many resources and tools a tenant has. The signal is a joint condition over five fields (same identity, same normalised path, different api-version or method, short gap, 400 then 200) whose benign rate is set by the tenant's own tooling mix. There is no threshold that transfers between tenants, so the deliverable is a per-identity score against that tenant's own repair-behaviour distribution.
  Feature construction - for each Azure Activity log or `CloudAuditEvents` record, derive:
  - `identity`: the service principal object ID or the user principal name from the caller claims.
  - `path_norm`: the request URI with the query string removed and GUIDs replaced by a placeholder, so `/subscriptions/<guid>/resourceGroups/rg1/providers/Microsoft.KeyVault/vaults/v1/secrets` is stable across subscriptions.
  - `api_version`: the `api-version` query parameter, parsed out before normalisation.
  - `method`: GET, POST, PUT, PATCH, DELETE.
  - `status`: the HTTP response status code.
  - `gap_seconds`: seconds since the previous record for the same (`identity`, `path_norm`).
  Then label a *repair pair* as two records for one identity and one `path_norm` where the earlier has `status == 400`, the later has `status == 200`, `gap_seconds` is between 5 and 300, and either `api_version` or `method` differs while `path_norm` is identical.
  Model - score each identity per day on four features and rank, rather than alerting on any one:
  - repair-pair count, and repair pairs as a fraction of that identity's 400 responses (an agent repairs nearly everything it breaks; drift produces 400s that are never repaired).
  - the median and interquartile range of `gap_seconds` across repair pairs. Microsoft's observed gaps were approximately 28, 60 and 80 seconds, so a tight cluster in that band with a small IQR is the strong form; a wide spread is a human.
  - the count of distinct `path_norm` values repaired, and the count of distinct resource providers touched, in the same hour. One identity repairing paths across `Microsoft.KeyVault`, `Microsoft.Sql` and `Microsoft.Insights` in an hour is the reported shape.
  - whether the repaired api-version is one this identity has never used before, against the 30-day (identity, provider, api-version) history.
  An isolation forest or a simple robust z-score over these four features is sufficient; the discriminating power is in the features, not the estimator. Rank daily and review the top identities.
  Sample Defender XDR query to extract the raw pairs for modelling (export, then score offline):
  ```kql
  let lookback = 30d;
  let ops = CloudAuditEvents
      | where Timestamp > ago(lookback)
      | where DataSource == "Azure Resource Manager"
      | extend Uri = tostring(RawEventData.uri),
               Method = tostring(RawEventData.httpMethod),
               Status = toint(RawEventData.statusCode),
               Identity = tostring(RawEventData.claims.appid)
      | where isnotempty(Uri) and isnotempty(Identity)
      | extend ApiVersion = extract(@"api-version=([0-9A-Za-z\-\.]+)", 1, Uri)
      | extend PathNorm = replace_regex(tostring(split(Uri, "?")[0]),
                              @"[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}", "<guid>")
      | project Timestamp, Identity, PathNorm, ApiVersion, Method, Status;
  let failures = ops | where Status == 400;
  let successes = ops | where Status == 200;
  failures
  | join kind=inner (successes | project SuccessTime = Timestamp, Identity, PathNorm,
                                         SuccessVersion = ApiVersion, SuccessMethod = Method)
      on Identity, PathNorm
  | where SuccessTime between (Timestamp + 5s .. Timestamp + 300s)
  | where SuccessVersion != ApiVersion or SuccessMethod != Method
  | extend GapSeconds = datetime_diff('second', SuccessTime, Timestamp)
  | summarize RepairPairs = count(),
              MedianGap = percentile(GapSeconds, 50),
              DistinctPaths = dcount(PathNorm),
              Versions = make_set(strcat(ApiVersion, "->", SuccessVersion), 20)
        by Identity, bin(Timestamp, 1h)
  | order by RepairPairs desc
  ```
  The `between (Timestamp + 5s .. Timestamp + 300s)` bound is load-bearing: a join on `Identity` and `PathNorm` alone over a 30-day lookback pairs a failure on one day with an unrelated success on another. `CloudAuditEvents` retains 30 days in Defender XDR advanced hunting, which is the ceiling for the extraction query; keep the derived features in your own store if you want a longer baseline. Check the field names against your own tenant's `RawEventData` shape before running this - the Azure Activity log schema places the request URI differently depending on resource provider and on whether the record came through the legacy or the current schema, and some providers omit it entirely. Where the URI is absent, fall back to the `operationName` plus `properties` pair, which loses the api-version and therefore loses this hunt's primary feature.
  Attribution and pivot - Core filter: for every identity that ranks high, pull its Entra ID service principal sign-ins for the same window and record `IPAddress`, `UserAgent` and `ResourceDisplayName`. Microsoft reports that the repair sequences it observed originated from the same address as the credential-abuse activity in the same campaign. Strong red flags: the repairs are the identity's first-ever activity against a resource provider; the repaired paths are Key Vault `secrets` paths, which is where Microsoft observed this starting; the identity's sign-in came from an address with no history in the tenant.
  Expected, not observed by Microsoft: the method-change half of the pattern is stated by Microsoft only in summary - that "failed cloud API requests were followed by changes to HTTP methods or API versions and subsequent HTTP 200 responses" - while all three worked examples it gives are api-version changes. Model both, but weight api-version changes higher, and do not claim a method-swap example from this report.
  Expected, not observed by Microsoft: the same repair shape should appear on AWS and Google Cloud control planes, where an agent working from stale API knowledge produces `InvalidParameterValue` or `400` followed by a corrected call. Microsoft's report covers Azure Resource Manager only.

# M068

Microsoft Threat Intelligence documents something unusual in an intrusion driven by an agentic AI framework: not just that the agent was fast, but that it visibly *learned* against the control plane. Microsoft writes that the agent's operations on a victim's Azure Resource Manager instance "demonstrated sequences consistent with adaptive troubleshooting, where failed cloud API requests were followed by changes to HTTP methods or API versions and subsequent HTTP 200 responses."

The three examples Microsoft gives are precise enough to build a feature on. "A batch of ARM requests attempting to enumerate secret metadata across multiple Azure Key Vault resources returned HTTP 400 (Bad Request)." Those requests had specified a data-plane api-version against a control-plane endpoint. "Approximately 28 seconds after the first failed response, a batch rerun began against the same vault resource paths using the ARM API version 2023-07-01 and returned HTTP 200." A second case involved a GET for an Azure SQL server's firewall rules, retried about 60 seconds later with a supported version, where - in Microsoft's words - "The URL changed only in its api-version parameter." A third involved an Application Insights query endpoint, repaired about 80 seconds later.

That shape is hard for anything else in a tenant to produce. A pipeline pins its api-version in code and therefore fails forever rather than correcting. SDK drift produces failures nobody fixes until someone upgrades the tool. A human engineer does correct api-versions, but over minutes, with reads in between, and confined to whatever they happen to be working on. An agent corrects in tens of seconds, across unrelated resource providers, and at a rate approaching one repair per failure.

This is deliberately a different instrument from M050, which already models agent-driven ARM activity in this tenant - M050 scores *cadence and volume*, the near-constant inter-operation latency and sustained read rate that no human reproduces. An operator who throttles their agent, or runs it in short bursts, defeats a cadence model while still producing repair pairs, because the repairs come from the model's knowledge of the API being stale rather than from how fast it is driven. The two are complementary features over the same telemetry, and a tenant running both is covered against both evasions.

## Why

- The repair sequence is a side effect of how a language model knows an API, not of how the operator configures their tooling. Cloud API surfaces version faster than any model's training data, so an agent that reasons its way to a request will keep guessing api-versions and keep correcting them. Changing infrastructure, user agents or request rate does not remove that.
- Microsoft's own timings give the model a calibrated prior. Gaps of approximately 28, 60 and 80 seconds, with the URL differing only in `api-version`, define a narrow band to score against - specific enough to separate from human correction without being a brittle threshold.
- Where the agent repairs is itself intelligence. In the reported case the first repaired batch was aimed at enumerating secret metadata across multiple Key Vaults, which places the detection opportunity before the secrets are read rather than after they are exfiltrated. Microsoft notes elsewhere in the same report that an agent went from finding a secret in public code to exfiltrating Key Vault data in five minutes, so a signal that fires on the failed enumeration is worth more than one that fires on the successful read.
- Modelling is the only workable form. Every tenant generates benign HTTP 400s at a rate set by its own tooling mix, and both the volume and the shape of benign version drift differ by orders of magnitude between a two-subscription estate and a managed-service provider. A ranked per-identity score against the tenant's own distribution transfers; a count does not.
