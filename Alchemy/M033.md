title: Scoring build and developer hosts on the breadth of distinct credential-CLI token retrievals from a single non-interactive parent
hypothesis: >-
  A worm that lands in a developer or build environment does not read one secret — it sweeps. ChainDrop's
  collector called `gh auth token`, `gcloud config config-helper`, `az account get-access-token` and
  `azd auth token`, dumped the whole process environment, walked shell histories and SSH keys, then used each

  commands inside a short window, on a host whose historical profile is narrow and stable. Score each

false_positive_notes: |
  Every command in this hunt is a documented, sanctioned developer or CI operation, and the naive query is
  unusable on a build estate. Expect substantial legitimate volume from:
  - CI/CD jobs that authenticate to multiple clouds by design — a deployment pipeline touching GitHub, Azure and
    GCP in one run is completely normal and will show high BREADTH.
  - Terraform, Pulumi, Helm, Docker and Kubernetes tooling shelling out to cloud CLIs for credentials.
  - Developer setup and onboarding scripts, and dotfile bootstrap.
  - Secret-scanning and posture tools (including TruffleHog) run deliberately by security teams.
  - IDE cloud extensions refreshing tokens in the background.
  This is precisely why the hunt is scored rather than thresholded. The model must:
  (1) Build the profile PER (host, parent-process identity) — a named deployment pipeline with a stable
      multi-cloud profile scores near zero forever, because breadth is normal FOR IT. The signal is a parent whose
      own history is narrow suddenly going wide.
  (2) Treat known CI job identities and signed tooling as named populations with their own baselines, not as
      global suppressions.
  (3) Weight NOVELTY heavily — a parent process identity first seen in the last 24 hours that immediately
      exhibits high breadth is the strongest single contributor.
  (4) Require non-interactivity. A developer typing these at a prompt in an interactive session is the dominant
      benign case and should be scored down hard.
  Expect the first two weeks of scoring to be dominated by unmodelled CI identities. Enumerate and name them
  before treating any score as actionable, and re-baseline after major pipeline changes.

  PLATFORM: Windows (developer workstations and Windows build agents, via Defender XDR / Sysmon). Linux
  self-hosted runners are deliberately out of scope here — [[B020]] already baselines dependency-install behaviour
  on those, and the two should be read together.

  (2026-08-04), corroborated by Elastic Security Labs, "Shai-Hulud strikes again: CHAINDROP worm hits 400+ npm

  WHAT THE WORM ACTUALLY DID: a malicious npm package's `preinstall` lifecycle hook launched `setup.mjs`, which
  loaded an obfuscated Bun bundle (`Math_*.js`). The collector harvested the full process environment, credential
  files, shell histories, SSH keys, GitHub Actions runner memory, workflow secrets and OIDC tokens, then — the
  important part — "used available credentials to call service APIs, verify access, and retrieve additional
  secrets." Stolen npm tokens were used to download each package the identity could publish, inject the bundle,
  add a preinstall hook, bump the patch version and republish, which is the worm loop. Exfiltration went to
  `npm-cache[.]com` with a fallback of creating a public GitHub repo described "Shai-Hulud: Here We Go Again",
  AES-256-GCM encrypted with an RSA-OAEP-wrapped key. C2 domain rotation was driven by an on-chain contract.

  MICROSOFT'S PUBLISHED KQL (reproduced verbatim — the campaign-specific starting point this model generalises):

    DeviceProcessEvents
       | where Timestamp > ago(3d)
       | where ProcessCommandLine has_any ('gh auth token', 'gcloud config config-helper',
                                           'az account get-access-token', "azd auth token")
       | where InitiatingProcessFileName in~ ("bun", "bun.exe")
       | where InitiatingProcessFolderPath contains "bun-dl-"
            or InitiatingProcessCommandLine has "node_modules"

    DeviceProcessEvents
        | where Timestamp > ago(3d)
        | where FileName in~ ("node", "node.exe")
        | where ProcessCommandLine in~ ("node setup.mjs", "node  setup.mjs")

    DeviceFileEvents
    | where Timestamp > ago(3d)
    | where SHA256 in~ ("9fc2570b7cef51c1b8df116d144d11ff4096357be7d2c4c6367cfc2509cf1bcc",
                        "fd3ca4007b225fdf8de7af4345a19179d5efa8c4bb9205f88cda806e5684b1eb",
                        "54dc7ea54a1317cca0e890a2770630cf7fa6c97813e0cb9d2caa93012b350668")

  WHY THIS NEEDS A MODEL AND NOT A RULE: the KQL above is excellent and should be deployed as-is for THIS
  campaign. It is also pinned to four command strings, one runtime (`bun`), one loader name (`setup.mjs`) and
  three hashes. Every one of those is a free variable for the attacker — the next wave uses `deno`, or `node`
  directly, or calls the cloud SDKs in-process with no child execution at all for some of the credentials. The
  durable, campaign-independent claim is behavioural: a non-interactive parent that has never done this before
  suddenly enumerating credentials across MANY distinct providers in seconds. That is a rarity-scoring problem,
  and it is also why a per-host static threshold fails — a deployment pipeline legitimately touching three clouds
  would trip it every run.

  THE MODEL:
  - UNIT OF SCORING: the (host, parent-process identity, time-window) tuple. Parent-process identity should be a
    stable key — image path plus command-line skeleton with volatile arguments normalised — not a raw PID.
  - WINDOW: rolling 5 minutes for the burst score; 90 days of history for the baseline.
  - FEATURE 1 — BREADTH (highest weight): the count of DISTINCT credential-retrieval operations under one parent
    in the window. Build the vocabulary by CAPABILITY, not by literal string, so it survives tool substitution:
      * source forge tokens — `gh auth token`, `gh auth status --show-token`, `glab auth`, git credential helpers
      * cloud tokens — `az account get-access-token`, `azd auth token`, `gcloud config config-helper`,
        `gcloud auth print-access-token`, `aws sts get-session-token`, `aws configure get`
      * package registries — reads of `.npmrc`, `.yarnrc*`, `.pypirc`, `~/.docker/config.json`
      * secret stores — `vault read/kv get`, `kubectl get secret`, cloud secret-manager CLI reads
      * bulk environment/secret capture — full environment dump, `printenv`/`Get-ChildItem Env:`, shell history
        reads, `~/.ssh/id_*` reads
      * secret scanners — TruffleHog, gitleaks, and equivalents invoked by a non-security parent
  - FEATURE 2 — BURST RATE: distinct operations per unit time. Automated sweeps complete in seconds; a human or a
    pipeline step is spread across a build.
  - FEATURE 3 — NON-INTERACTIVITY: parent has no interactive logon session (4624 LogonType 2/10), no console, and
    is descended from a package-manager lifecycle script or a runtime downloaded at install time.
  - FEATURE 4 — PARENT NOVELTY: first-seen age of the parent-process identity on this host. A parent identity
    under 24 hours old carries the most weight in the whole model.
  - FEATURE 5 — PATH PROVENANCE: parent executing from `node_modules`, a runtime download directory
    (`bun-dl-*` and equivalents), `%TEMP%`, or a package cache rather than an installed program directory.
  - FEATURE 6 — VALIDATION FOLLOW-THROUGH: outbound API calls to the corresponding provider endpoints within
    minutes of each token retrieval. This is the behaviour Microsoft singles out — the malware does not just
    collect, it USES each credential to verify and expand. Collection alone is ambiguous; collection immediately
    followed by validation across multiple providers is close to conclusive.
  - FEATURE 7 — PUBLISH/EGRESS COUPLING: `npm publish` or registry write activity, or egress to a
    registry-lookalike domain, from the same parent lineage within the window.
  - SCORING: score each feature against the (host, parent-identity) historical distribution — z-score or
    empirical percentile — and combine multiplicatively so that JOINT extremity is required. A parent scoring
    high on breadth alone is a multi-cloud pipeline; a parent scoring high on breadth AND novelty AND
    non-interactivity AND validation follow-through is the worm.
  - OUTPUT: a ranked queue of (host, parent-identity, window) tuples with the contributing feature values, so an
    analyst sees WHY something ranked rather than a bare score. Review the top of the queue daily, not an alert.

  VALIDATION: replay the model against a known-clean 90-day window and confirm the top-ranked results are
  enumerable named CI identities; then replay against the ChainDrop KQL hits (if any) and confirm they rank above
  the CI population. If the model cannot separate them, the CI identities are not yet named and the baseline work
  is incomplete.

  ALSO DEPLOY THE STATIC RULES: the Microsoft KQL above and the three SHA256 values are high-fidelity for the
  current wave and cost nothing. This model is the layer that survives the next one, not a replacement.

  Shai-Hulud v2 wave generically), T1528 (Steal Application Access Token — what the cloud CLI calls actually

# M033

Microsoft's ChainDrop KQL is good, and you should deploy it today:

```kusto
DeviceProcessEvents
   | where ProcessCommandLine has_any ('gh auth token', 'gcloud config config-helper',
                                       'az account get-access-token', "azd auth token")
   | where InitiatingProcessFileName in~ ("bun", "bun.exe")
```

It is also pinned to four command strings, one runtime, one loader filename and three hashes. The worm changes any of those with a one-line edit. What it cannot change without giving up the campaign is the reason it ran those commands: it needed to find out what the compromised identity could reach, and the only way to do that is to ask every provider in turn.

That produces a shape. One parent process, non-interactive, minutes old, running out of `node_modules`, asking GitHub *and* Azure *and* Google *and* the npm config *and* the SSH directory what credentials exist — and then immediately calling each provider's API to check whether they work. A deployment pipeline that legitimately touches three clouds looks superficially similar on breadth alone, which is exactly why a threshold fails and a joint score does not: the pipeline has done this every day for a year, and this parent has never existed before.

## Why

- **Breadth is the one feature the attacker cannot economise on.** The worm's whole purpose is to find every credential the host can reach so it can republish packages and propagate. It could switch runtimes, rename the loader, obfuscate the strings, or call cloud SDKs in-process — but narrowing the sweep would defeat the point of the sweep. Scoring breadth against a parent's own history targets the objective rather than the implementation.
- **Per-host thresholds are the wrong unit and would fail loudly.** Build estates are heterogeneous by design: a Terraform pipeline touching three clouds is normal, and a front-end developer's laptop calling `az account get-access-token` once is not. A single global number is simultaneously too noisy for the first and too permissive for the second. Baselining per (host, parent identity) makes "normal for a deployment job" and "normal for this laptop" two different statements, which is the only way this is operable.
- **Parent novelty does the heaviest lifting and is nearly free to compute.** Legitimate automation has stable, long-lived, recognisable process identities. A parent that first appeared twenty minutes ago because a dependency install pulled down a runtime and executed it is anomalous before it does anything at all. Combining first-seen age with credential breadth is a two-feature model that would have caught this campaign, and it needs no training data beyond your own process history.
- **Validation follow-through is the feature that separates theft from housekeeping.** Microsoft's write-up is explicit that the modules "do not merely scan files for token patterns; they use available credentials to call service APIs, verify access, and retrieve additional secrets." Plenty of tooling reads a credential file. Almost nothing reads five different providers' credentials and then immediately exercises all five. That sequence is the strongest single discriminator available, and it lives in network telemetry you already collect.
- **The consequence of missing it is not one host.** The credentials being swept are npm publish tokens, GitHub PATs, cloud keys and CI OIDC tokens. A successful sweep does not end in data theft on that machine — it ends in poisoned packages republished under a trusted publisher's name, which is how 400+ packages fell in one wave. Detection latency on a developer endpoint converts directly into blast radius across everyone downstream.
- **HEARTH had the campaign but not the shape.** [[H087]] covers the Shai-Hulud v2 wave and [[B020]] baselines Linux CI runners, but nothing scored credential-enumeration breadth on Windows developer and build hosts, and no existing hunt referenced these CLI token commands at all. This is the durable layer under a set of hunts that are otherwise all pinned to specific campaigns.
