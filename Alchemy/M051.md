false_positive_notes: |
  Task inventories contain a lot of lexically odd but legitimate names, and each will trip one feature. Vendor codenames and product names (`OneDrive Reporting Task`, `GoogleUpdateTaskMachineUA`, `CCleanerSkipUAC`, `ZoomUpdate`) are not dictionary words; build the vendor lexicon from software inventory and from the task `<Author>` and action publisher, and zero out tokens found in it. Camel-cased or concatenated names (`UserTask-S-1-5-21...`, `MicrosoftEdgeUpdateTaskMachineCore`) should be split on case and punctuation before scoring. GUID and SID suffixes are high-entropy but already handled by other analytics, so strip them. Non-English administrators and localised software will produce legitimate non-English words; add the relevant language word lists rather than lowering the threshold. What survives these filters and still scores high — several tokens that each contain a real stem but are not words themselves, in a folder tree no other host has — is the population this model exists to find.
notes: |
  Platform: Windows. Driven by Huntress, "The Tale of Two INC Ransom Notes: A Ransomware Timeline" (September 2026). The intruder (possibly an initial access broker, per Huntress) registered `\Nonweighise\Cancellationizing\Illuminateers` running `C:\ProgramData\Vendettister\jocularities.ps1` with C2 `throughoutes[.]net`, 17 days before an INC affiliate deployed ransomware to at least 175 endpoints. Most names in that set — task folders, task name, description words, script folder, script file and C2 domain — follow the same pattern (`nationhood` and `jocularities` are real words): a real English stem plus one or more suffixes that do not belong to it. [[H349]] hunts the same artefact with structural rules; this model scores the names themselves so that the same generator is caught when it is paired with a different action or a shallower folder tree. Huntress published no detection queries; the model below is derived from the reported names. Its applicability to other families using word-list generators is an inference, not something Huntress observed.
  Why a model rather than a rule - The generated names are designed to look ordinary. Character entropy of "Cancellationizing" is indistinguishable from real long English words, so entropy rules miss it. A plain dictionary-miss rule drowns in vendor names and codenames. The pattern that separates them is a combination: a token is not a word, but a real word or stem is embedded at its start, and several such tokens appear together, in a place where the fleet has never seen them. No single threshold captures that, but a small weighted score does.
  Feature engineering, per task - Tokenise the folder path segments, the task leaf name, and the `<Description>` text, splitting on backslash, whitespace, camel case, digits and punctuation, and lowercasing. For each alphabetic token of length 6 or more, compute: (1) Whole-word hit — the token is in the English word list or the vendor lexicon. (2) Stem hit — the longest dictionary word or lemma that is a prefix of the token covers at least 60% of its length. (3) Suffix-stack indicator — the remainder after the stem is itself a common English suffix or a concatenation of two (`-izing`, `-ers`, `-ister`, `-es`, `-ish`, `-ness`, `-ation`). A token with a stem hit, a suffix-stack remainder and no whole-word hit is a pseudo-word. Per task, aggregate: pseudo-word count and fraction; folder depth; whether the root folder appears in the vendor lexicon; description word count and whether consecutive description words form any common bigram (a coherence proxy — `nationhood kinestheticization` does not); and whether the action runs a script interpreter from `C:\ProgramData` or a user-writable path. Finally add fleet prevalence: the number of hosts on which the same root folder and the same leaf name exist.
  Scoring approach - Treat it as ranking, not classification. A simple additive score works well as a start: pseudo-word fraction across path and name (heaviest weight), plus a bonus for a description that is also mostly pseudo-words with no common bigrams, plus a task path with two or more folder levels above the leaf name, with a root not in the vendor lexicon, plus a script-interpreter action from ProgramData, multiplied by an inverse-prevalence factor so that a name found on one host outranks one found on a hundred. Review the top 25 per week. Once analysts have labelled a few hundred, a logistic regression over the same features gives calibrated weights, but the additive form is usually enough.
  Validation and tuning - Seed the evaluation with the INC names above and synthetic names from the same recipe (take random nouns and verbs from the word list and append one or two inappropriate suffixes) mixed into a real task inventory; all of them should land in the top 1%. Check the other direction by confirming that `\Microsoft\Windows\...` tasks, browser updaters, OEM tasks and your own IT tasks score near zero; if any vendor family ranks high, add its tokens to the vendor lexicon rather than loosening the pseudo-word rule. Apply the same scorer to ProgramData folder names, script file names and DNS query names from the same hosts as a secondary signal, since the INC generator named its script folder, script file and C2 domain the same way (not observed beyond this one intrusion; offered as an extension).
  Operationalising - Score new tasks from Event ID 4698 in near real time and push anything above threshold to [[H349]]-style triage. Re-score the full fleet task inventory weekly as a retro-hunt, since a broker foothold can sit untouched for weeks before an affiliate arrives, as it did here.
  Cross-technique: pair with [[H349]] for the rule-based hunt on the same artefact, with [[B040]] for the baseline of update-themed task names (the other common disguise), with [[B050]] for task enumeration integrity, and with [[H350]] for the second-phase remote-access agent from the same intrusion.

# M051

The scheduled task that opened Huntress's INC Ransom timeline is worth looking at word by word. The folder path was `\Nonweighise\Cancellationizing\Illuminateers`. The description was "nationhood kinestheticization preironish fictionallyes". The script it ran was `C:\ProgramData\Vendettister\jocularities.ps1`, and the C2 domain was `throughoutes[.]net`.

Most of those are not words, but almost all of them contain one. "Cancellation" plus "izing". "Illuminate" plus "ers". "Fictionally" plus "es". "Vendetta" plus "ister". Something assembled these from a word list and bolted on suffixes until the result looked plausible at a glance. Few rules catch that, because the names have the letter frequencies of normal English, they are not GUIDs, and they are too long and varied to match on.

They are still detectable, because real task names do not look like this. Vendor tasks use product names that recur across thousands of hosts. Administrators use descriptive phrases. Neither produces a two-level folder tree of stem-plus-suffix pseudo-words that exists on one machine. Scoring task names on that morphology, and weighting by how rare the folder tree is across the fleet, turns an inventory of tens of thousands of tasks into a short ranked list.

## Why

- The generator's evasion is its fingerprint. Stacking suffixes onto real stems defeats entropy and randomness heuristics, but it leaves a pattern — stem present, whole word absent, suffix inappropriate — that a word list and a few string operations can measure directly.
- Scoring the name catches the same generator in different wrappers. A rule keyed on folder depth or on a ProgramData PowerShell action misses the next foothold that uses one folder level and an executable, while the naming morphology stays the same.
- Fleet prevalence removes most of the noise cheaply. Legitimate odd names belong to products installed on many hosts, and a generated name is unique to the victim, so an inverse-prevalence weight pushes vendor codenames down without maintaining a large allowlist.
- It is built for the dwell window. The INC foothold existed for 17 days before the ransomware stage; weekly retro-scoring of the whole task inventory is exactly the cadence that finds a broker's access before it is sold on.
- The same scorer extends to adjacent artefacts. Folder names, script names and DNS query names from the same intrusion followed the same recipe, so one model covers several places where the generator shows up.
