false_positive_notes: |
  Obfuscation scoring has a well-earned reputation for drowning its owner, and the reason is almost always
  that it was fitted to the wrong population. Long, high-entropy, heavily-escaped command lines are
  completely normal in several large and legitimate classes: software deployment and configuration
  management (SCCM, Intune, Ansible, Chef and Puppet all emit enormous generated command lines), CI and
  build agents, installer bootstrappers, antivirus and backup product scheduled actions, database and
  ETL jobs with inline SQL, and anything that passes base64 or JSON as an argument. Developer workstations
  are worse again, because minified JavaScript, generated code, test fixtures and one-liner shell
  pipelines all score highly and all are benign. Three practices keep this usable. First, fit per host
  role - build agents, developer workstations, servers and user endpoints each get their own distribution,
  because a single estate-wide percentile makes every engineer an outlier and hides the one laptop that
  matters. Second, score the FEATURES rather than the length. Length and entropy alone select for
  generated-but-legitimate commands; chained replace operations and repeated non-dictionary token
  substitution select for deliberate reconstruction, which generated tooling does not do because it has no
  reason to. Third, require a context gate on the output - the script host or interpreter was launched by

  The published obfuscation, exactly as reported, and why the specifics are not the hunt. The RAR
  attachment held a VBScript which checked for `notepad.exe`, read that file hexadecimal data, extracted
  the characters `s` and `l` from it, and used them to assemble the final executable name `powershell`.
  AhnLab describes this as "an obfuscation technique designed to make analysis and detection more
  difficult", and it is an unusually pure example - the two characters the detection engineer would search
  for are not present anywhere in the attacker code, they are borrowed from a Microsoft binary that is
  present on every Windows host. The PowerShell stage then rebuilt its own command through repeated token
  substitution with the published rules `Axis` to S, `Longar` to O, `Hoimulz` to the dollar sign and
  `Humoled` to C. Both legs are campaign-specific. Searching for `Axis` or for `notepad.exe` byte reads
  produces a detection with a shelf life measured in weeks, which is why this is modelled as a score.
  The feature set, which is the actual deliverable. Per command line and per script block, compute:
  count of `-replace` operators and `.Replace(` calls; maximum chain depth of those operations in a single
  expression; count of distinct repeated tokens of length four or more that are not dictionary words and
  not known identifiers; ratio of those tokens to total token count; character-level Shannon entropy;
  count of `[char]` and `[convert]::ToChar` and `chr(` conversions; count of `-f` format operators and
  `-join` and `+` concatenation operators in a single expression; count of `[scriptblock]::Create`,
  `Invoke-Expression`, `iex`, `&(` and `.Invoke()` late-binding constructs; presence of backtick escapes
  inside a token; presence of caret escapes inside a token for cmd; mixed-case interpreter names;
  proportion of non-alphanumeric characters; and total length. Normalise each feature against the host-role
  population and combine. Keep the model simple and interpretable - a weighted score or an isolation forest
  over these features, not an opaque classifier - because the output has to be explained to whoever works
  the queue.
  The highest-value single feature, stated separately because it is the one most likely to be omitted:
  chain depth of substitution operations. A legitimate generated command may be long and may be
  high-entropy, but it does not contain six chained `-replace` calls whose combined effect is to spell a
  cmdlet name. That construct exists only to defeat a string match.
  Sample implementation sketch of the scoring pass over exported command lines.
  `import re, math; def feats(c): toks = re.findall(r"[A-Za-z]{4,}", c); return {"repl": len(re.findall(r"-replace|\.Replace\(", c, re.I)), "chars": len(re.findall(r"\[char\]|ToChar|chr\(", c, re.I)), "fmt": len(re.findall(r"-f\b|-join|\+", c)), "late": len(re.findall(r"scriptblock\]::Create|Invoke-Expression|\biex\b", c, re.I)), "ent": -sum((c.count(x)/len(c))*math.log2(c.count(x)/len(c)) for x in set(c)) if c else 0, "len": len(c)}`
  Sample KQL to build the candidate population with the context gate applied - run this before any scoring,
  because it is the cheap half of the work.
  `DeviceProcessEvents | where Timestamp > ago(90d) | where FileName in~ ("powershell.exe","pwsh.exe","cmd.exe","wscript.exe","cscript.exe","mshta.exe") | where InitiatingProcessFileName in~ ("winword.exe","excel.exe","outlook.exe","powerpnt.exe","explorer.exe","chrome.exe","msedge.exe","firefox.exe","7zfm.exe","winrar.exe","rar.exe","opera.exe") or InitiatingProcessFolderPath has_any (@"\AppData\", @"\Downloads\", @"\Temp\", @"\Users\Public\") | extend ReplaceCount = countof(ProcessCommandLine, "-replace") + countof(tolower(ProcessCommandLine), ".replace("), CharCount = countof(tolower(ProcessCommandLine), "[char]"), Late = countof(tolower(ProcessCommandLine), "invoke-expression") + countof(tolower(ProcessCommandLine), "scriptblock]::create") | where ReplaceCount >= 2 or CharCount >= 3 or Late >= 1 | project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine, InitiatingProcessFileName, ReplaceCount, CharCount, Late | order by ReplaceCount desc`
  Sample KQL for the script-block leg, which sees the reconstruction logic before it runs.
  `DeviceEvents | where Timestamp > ago(90d) | where ActionType == "PowerShellCommand" | extend S = tostring(parse_json(AdditionalFields).Command) | extend Repl = countof(tolower(S), "-replace") + countof(tolower(S), ".replace(") | where Repl >= 4 | project Timestamp, DeviceName, AccountName, InitiatingProcessFileName, Repl, S | order by Repl desc`
  The byte-mining leg, and an honest statement of its telemetry problem. A script host reading the body of
  a binary under `System32` to harvest characters is a conceptually excellent signal and a practically
  awkward one, because neither Windows Security auditing nor Sysmon records file reads by default - Sysmon
  has no file-read event, and object-access auditing on System32 is not something most estates can afford to
  turn on. Where an EDR product does expose file-read telemetry, the query is trivial and very high
  precision: `wscript.exe` or `cscript.exe` opening `notepad.exe` for read has no benign explanation. Where
  it does not, the leg is reachable two other ways - the script text itself, visible in 4104 or on disk,
  will contain the file path and a byte or hex read; and the behaviour implies the script host ran at all,
  which the context gate above already captures. Do not build the hunt on the file read.
  Validation and tuning. Positive controls are easy to generate safely with Atomic Red Team T1027.010
  tests and with Invoke-Obfuscation output, and both should land in the top percentile of the score. The
  more important test is the negative one: export a week of command lines from a build agent and a
  deployment server, score them, and confirm the top of that ranking is generated-but-legitimate rather
  than empty. If deployment tooling outranks the atomic tests, the feature weights are measuring length
  rather than reconstruction.

# M058

The VBScript needed the letters `s` and `l`. It did not contain them. It read them out of `notepad.exe`.

That is the detail in AhnLab's quote-request phishing report that is worth sitting with. The script checks that `C:\Windows\System32\notepad.exe` is present, reads its hexadecimal data, extracts two characters from the bytes of a Microsoft binary that exists on every Windows host on earth, and uses them to finish assembling the string `powershell`. The characters a detection engineer would grep for are not in the attacker's code at all. They were borrowed.

The PowerShell stage underneath it does the same thing in a different dialect — repeated token substitution, with AhnLab publishing the mapping: `Axis` becomes S, `Longar` becomes O, `Hoimulz` becomes a dollar sign, `Humoled` becomes C.

Now, the trap. Those four tokens are sitting right there, and they are a perfectly good IOC, and writing a rule for them produces a detection that will be dead within a month. `Axis` is not the technique. Neither is `notepad.exe`. The technique is that the command had to be *rebuilt at runtime*, and rebuilding costs work, and the work is visible.

So count the work. Chained `-replace` operations and their maximum depth in a single expression. Repeated non-dictionary tokens and their density. `[char]` and char-code arithmetic. `-f` format chains, `-join`, concatenation runs. Late binding through `[scriptblock]::Create`, `iex`, `&(`. Backtick escapes inside tokens on PowerShell, caret escapes inside tokens on cmd. Entropy. Length.

Then — and this is the part that decides whether the hunt is useful or abandoned in a week — rank against the environment's own distribution, per host role.

Obfuscation scoring has a bad reputation and it earns it honestly, because long, ugly, high-entropy command lines are completely ordinary. SCCM and Intune emit them. Ansible emits them. Installer bootstrappers, backup agents, ETL jobs and CI runners all emit them. A developer workstation emits them before lunch. Fit one estate-wide percentile and every engineer is an outlier while the one laptop you care about sits at the median.

Two things fix it. Score the *features* rather than the length, because generated tooling is long and high-entropy but has no reason to spell a cmdlet name out of six chained substitutions — that construct exists solely to defeat a string match. And gate the output on context: the interpreter was launched by Office, a browser, an archive utility or Explorer, or from a user-writable path. Deployment tooling is launched by a service. That one condition removes most of the benign mass for free.

One honest limitation. The byte-mining leg — a script host reading a System32 binary for its bytes — is the most beautiful signal in this report and the hardest to collect. Sysmon has no file-read event, and object-access auditing on System32 is not something most estates can afford to leave on. Where an EDR exposes file reads it is trivial and near-perfect. Where it does not, you reach the same behaviour through the script text, which names the path. Do not build the hunt on the read.

## Why

- **The published tokens are worthless as a durable detection and excellent as a worked example.** `Axis`, `Longar`, `Hoimulz`, `Humoled` will not appear twice. The reconstruction they perform will appear constantly.
- **Byte-mining from a Microsoft binary defeats string matching completely.** The characters the detection would search for exist only in `notepad.exe`. No amount of signature tuning reaches content the attacker never wrote down.
- **Replace-chain depth is the feature that separates malicious from generated.** Deployment tooling produces long and entropic command lines. It does not produce six nested substitutions that spell a cmdlet, because it has no adversary to hide from.
- **A fixed threshold cannot work here and a population-relative one can.** Build agents, developer laptops, servers and office endpoints have genuinely different normals. One percentile across all of them is a guarantee of both floods and misses.
- **The context gate does more work than the model does.** Interpreter launched by Office, a browser, an archive tool or Explorer, or running from a user-writable path. Legitimate generated commands come from services and agents, so this single condition is the cheapest precision available.
- **Interpretability is operational, not aesthetic.** Whoever works the queue has to say why a command line ranked where it did. A weighted score over named features survives that; a black-box classifier gets switched off.
- **Negative controls matter more than positive ones.** Atomic Red Team obfuscation tests will score highly and prove nothing. Scoring a week of build-agent output and finding legitimate generated commands at the top is the test that tells you the weights measure reconstruction rather than length.
- **The file-read leg should be used where it exists and never depended on.** Native Windows logging does not provide it. Saying so up front stops the hunt being built on telemetry the estate does not have.
