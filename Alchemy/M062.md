title: "Scoring credential-store breadth — one process reaching across unrelated secret families in a single short window"
hypothesis: >-
  Every legitimate consumer of stored secrets is narrow. A browser reads its own profile. A password manager opens its own vault. An SSH client reads the keys under one user's .ssh. A VPN client reads its own configuration. No ordinary process reads browser login data, a password-manager vault, VPN profiles, SSH private keys, FTP client configuration and cryptocurrency wallet files within the same few minutes, because nothing legitimate needs secrets from six unrelated applications at once. A stealer does exactly that, and its target list is supplied by its operator at runtime rather than fixed in the binary, so no static set of paths characterises every infection. Scoring processes on the number of distinct secret families they touch in a short window, against a per-host baseline of what that host's processes normally touch, detects the collection step without needing to know which targets the operator enabled.

false_positive_notes: |
  Backup, DLP, EDR and search-indexing agents read broadly by design and will score at the top of any breadth metric. They are the dominant false positive and must be handled by identity rather than by threshold: allowlist them by image path and signer, and review the allowlist when agents are added, because an unallowlisted new agent will look exactly like a stealer on its first run.
  Migration and profile-transfer tooling legitimately crosses families. Browser import wizards read competing browsers' profiles; password managers import from other managers; developer-environment setup scripts touch SSH keys and cloud credentials together. These cluster around onboarding and device replacement, so correlate hits against joiner and refresh activity before escalating.
  Security assessment tooling produces true positives that are authorised. Credential-audit scanners and red-team tooling will trip this by design. Keep an authorised-activity calendar and check it first.
  A high score is not evidence of exfiltration. Breadth measures collection, not egress. Pair every hit with the network and archive-staging evidence before treating it as a confirmed theft.
  SACL auditing is not free and is easy to get wrong. Applying audit entries to broad directory trees generates very large 4663 volume and can affect performance. Apply SACLs narrowly, to the specific files and folders in the family map, with read access only, and measure the event volume on a pilot group before estate-wide deployment.
  Defender XDR cannot substitute for the read telemetry. DeviceFileEvents records creates, modifies, renames and deletes but no reads, so the collection step is invisible there. Use it for the staging and archive half of the model, and 4663 or EDR telemetry for the breadth half.
  Per-host baselining is required, not optional. A developer workstation legitimately has SSH keys, cloud credentials and several browsers in play; a kiosk has one browser and nothing else. A single estate-wide threshold is simultaneously too loose for the first and too tight for the second.
notes: |
  Family map - The model depends on a curated mapping from path pattern to secret family. Keep roughly these families, each with its own patterns, and keep them deliberately coarse so that a stealer touching two browsers counts as one family rather than two:
  - Browser credentials and cookies: Chromium `User Data\*\Login Data`, `User Data\*\Cookies`, `User Data\Local State`, and the Gecko `logins.json` and `key4.db` profile files.
  - Password manager vaults: the on-disk vault and local database files for the managers deployed in your estate.
  - Private keys and certificates: `%USERPROFILE%\.ssh\`, PuTTY key files, exported PFX and PEM files, and user certificate store exports.
  - Remote access and VPN configuration: client configuration and saved-profile directories for the VPN and remote-access clients in use.
  - File transfer clients: saved-site and credential files for FTP and SFTP clients.
  - Cloud and developer credentials: `%USERPROFILE%\.aws\credentials`, `.azure`, `.kube\config`, `.docker\config.json`, `.npmrc`, `.git-credentials`.
  - Database tooling: saved-connection files for database clients.
  - Cryptocurrency wallets: wallet data directories and wallet extension storage.
  Scoring - For each tuple of host, process instance and 10-minute window, compute:
  1. `Families` - the count of distinct families accessed.
  2. `Span` - the elapsed time between the first and last access. Collection is fast; a process that touches six families across a working day is behaving differently from one that does it in nine seconds.
  3. `NoveltyHost` - whether this process image has ever accessed each family on this host in the previous 30 days.
  4. `NoveltyEstate` - the fraction of hosts in the estate where this process image accesses credential families at all. A process that does this on one host out of ten thousand is the interesting case.
  5. `Signer` - unsigned, or signed by a publisher not otherwise present in the estate, as a multiplier rather than a gate.
  Score high when `Families` exceeds the host's 30-day 99th percentile for any single process, or when `Families` is four or more with `Span` under five minutes and `NoveltyHost` true. Rank by `Families` descending, then by `NoveltyEstate` ascending. Thresholds belong per host class: derive them, do not import them.
  Why a threshold and not a rule - Any single-family access is far too common to alert on, and the combination is what carries the signal, so the detection has to be computed over a window rather than matched per event. The target set is also operator-supplied: configuration arrives from the C2 and determines what is collected, with ASEC recording targets spanning "web browsers, instant messengers, email clients, password managers, note-taking applications", "VPNs, remote access programs, database management tools, FTP and SSH tools", "Cloud storage, AI and development tools", and "Cryptocurrency wallets, gaming platforms", plus key material and documents: "Certificates, SSH keys, cryptocurrency wallet files, various configuration files, and document files". ASEC also notes "the actual scope of information collection may vary depending on the settings transmitted by the C2 server", which is precisely why breadth generalises where a path list does not.
  Corroboration, where read telemetry is thin - If SACLs are not deployed, approximate the model from the write side, which Defender XDR does record. A process that creates many files in one staging directory, or writes an archive, shortly before an outbound connection, is the same behaviour observed one step later:
  ```kql
  let staging = DeviceFileEvents
    | where Timestamp > ago(30d) and ActionType == "FileCreated"
    | summarize Created = count(), FirstWrite = min(Timestamp), LastWrite = max(Timestamp),
                Names = make_set(FileName, 25)
              by DeviceName, FolderPath, InitiatingProcessId, InitiatingProcessFileName
    | where Created >= 10 and LastWrite - FirstWrite < 5m;
  let egress = DeviceNetworkEvents
    | where Timestamp > ago(30d) and ActionType == "ConnectionSuccess"
    | project ConnTime = Timestamp, DeviceName, InitiatingProcessId, RemoteUrl, RemoteIP, RemotePort;
  staging
  | join kind=inner (egress) on $left.DeviceName == $right.DeviceName,
        $left.InitiatingProcessId == $right.InitiatingProcessId
  | where ConnTime between (FirstWrite .. LastWrite + 10m)
  | project FirstWrite, ConnTime, DeviceName, FolderPath, Created, Names,
            InitiatingProcessFileName, RemoteUrl, RemoteIP, RemotePort
  | order by Created desc
  ```
  The join window is required: joining on device and process alone across a 30-day lookback would pair staging activity with unrelated later connections.
  Operational notes - Run the scoring daily over a rolling 30-day baseline, and keep the top twenty rows rather than an alert threshold until the per-host distributions are stable. Expect the first two weeks to be allowlist construction, dominated by backup and security agents.
  Related coverage - [[H419]] hunts the injection step that this family uses to host its collection inside explorer.exe, which means a high-scoring process may be `explorer.exe` itself rather than an unsigned binary; the `NoveltyHost` term is what keeps that case visible. [[M030]] scores unrelated in-memory tradecraft and is complementary rather than overlapping.

# M062

AhnLab ASEC's October 2026 analysis of a Rust-written infostealer distributed as cracked software describes a collection scope wide enough that it defeats the usual way of hunting credential theft. The confirmed configuration targeted browsers, instant messengers, email clients, password managers, note-taking applications, VPNs, remote access programs, database management tools, FTP and SSH tools, cloud storage, AI and development tools, cryptocurrency wallets and gaming platforms — and, beyond stored account data, "Certificates, SSH keys, cryptocurrency wallet files, various configuration files, and document files".

Crucially, that list is not a property of the sample. The malware sends a host profile to its C2 and receives configuration back that determines what it collects, and ASEC notes "the actual scope of information collection may vary depending on the settings transmitted by the C2 server". So a hunt built on a list of target paths is built on one operator's choices on one day. Two infections of the same family can have disjoint target sets.

What does not vary is the shape. Whatever the operator selects, one process ends up reading secrets belonging to several unrelated applications within a few minutes. That is the anomaly worth modelling, because it is a property of being a stealer rather than a property of any configuration. And it is genuinely a scoring problem rather than a rule: each individual access is unremarkable and extremely common, the combination is what matters, the count has to be computed over a window, and the normal count varies enormously between a developer workstation and a kiosk.

The telemetry constraint shapes the design. Reads of credential files are not recorded by Sysmon, and the Defender XDR file table records creates, modifies, renames and deletes but no reads. The breadth signal therefore comes from SACL-based object-access auditing on a narrowly curated set of credential paths, or from EDR handle telemetry where a product exposes it. Where neither is available, the model can be approximated one step later, from the staging writes and the outbound connection that follow collection.

## Why

- The target list is operator-controlled at runtime, so path-based detection is structurally incomplete. Breadth is a property of the behaviour rather than of the configuration, which is why it survives the operator changing their mind between victims.
- No legitimate process needs secrets from unrelated applications at once. Every honest consumer of stored credentials is scoped to its own application, which gives this model an unusually clean separation — the exceptions are enumerable agents, not a long tail.
- A static threshold cannot work across the estate. A developer workstation legitimately has cloud credentials, SSH keys and several browsers in daily use while a kiosk has one browser, so the comparison has to be against the host's own history. That requirement is what makes this model-assisted rather than rule-based.
- Speed is a usable second dimension. Legitimate cross-family access, such as a browser import or a developer environment setup, is spread out and user-driven; collection is a burst. Pairing family count with elapsed span removes much of the remaining noise at no extra collection cost.
- It catches the behaviour even when the process identity is stolen. This family injects into explorer.exe, so the collecting process may be a signed Microsoft binary; a per-host novelty term flags Explorer suddenly reading six credential families when it never has before, which a signer-based or path-based approach would wave through.
