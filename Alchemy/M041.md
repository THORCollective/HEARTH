false_positive_notes: >-
  Rarity is not maliciousness, and the single largest failure mode of this analytic is treating the two
  as the same thing. A correctly built estate contains many legitimately rare setuid binaries, and the
  model must be calibrated to rank rather than to alert. The specific populations that will fill the top
  of an uncalibrated ranking are predictable. Vendor and commercial software installs setuid helpers that
  exist on the handful of hosts running that product - backup agents, hardware management and RAID
  utilities, licence managers, HPC schedulers such as Slurm, virtualisation helpers, and the
  `ssh-keysign`, `fusermount`, `pmount` and `Xorg.wrap` family that appear only on hosts with a
  particular role. Development hosts and build agents accumulate setuid binaries from compilation and
  testing that exist nowhere else and are entirely legitimate. Containers are the sharpest edge: an image
  running on three pods produces a 0.1% fleet prevalence that means nothing at all, which is why
  prevalence must be computed per role and per image and why image identity is a required input rather
  than an enrichment. Four calibration cautions follow from this. First, weight package ownership
  heavily - an unowned setuid binary is a far stronger feature than a rare owned one, and an owned binary
  whose mode diverges from its package manifest is stronger still. Second, weight location: a rare setuid
  binary under `/opt/vendor` is a different object from a rare setuid binary under `/tmp` or a service
  account home, and path class should multiply the rarity score rather than be one term among many.
  Third, weight arrival: a binary that has existed since the host was imaged is weaker than one whose
  setuid bit was set last Tuesday by a process that was not a package manager, so first-seen date and the
  identity of the `chmod` caller belong in the score. Fourth, do not let the denominator lie - if
  telemetry coverage is partial, prevalence is computed over instrumented hosts only, and an
  under-instrumented host group will appear to contain rare binaries purely as an artefact of collection.
  Publish coverage alongside the ranking so that this is visible rather than silently priced in. Finally,
  expect the first run to return an inventory problem rather than an intrusion. That is the correct
  outcome and the unexplained rows are a standing remediation backlog, not a tuning failure.

# M041

Elastic Security Labs' Linux privilege-escalation framework contains a small methodological decision that
is easy to read past. For detecting abuse of setuid binaries that are not on anybody's list of known
helpers, they do not attempt to enumerate the legitimate set. They match
`stringcontains(process.executable, process.command_line)` — a binary invoked directly by its own path —
explicitly so the logic works "without hardcoded binary lists."

That choice is an admission about scale, and it is the right one. Nobody maintains a complete, current
list of every setuid binary that legitimately exists across a mixed Linux estate of distributions,
versions, container images, vendor appliances and developer workstations. Any allowlist is stale the day
after it is written, and the gap between the list and reality is exactly where an attacker's binary sits.

But refusing to enumerate leaves a question open, and it is the question an analyst actually has when the
rule fires: is this binary supposed to be here? A name means nothing in isolation. What answers it is
prevalence. If a setuid binary appears on every host with the same role, it is part of that role's build,
whatever it is called. If it appears on one host out of four thousand comparable ones, no package owns
it, and its setuid bit was set nine days ago by a shell rather than by a package manager, that is the
finding — and it is the finding whether or not the binary has ever executed.

That is the difference between this analytic and [[H299]]. H299 is a query over execution events, keyed
on the privilege transition and its immediate context, and it is the right instrument when a root
transition has happened and you want to know whether the lineage around it looks like exploitation.
M041 is a scoring model over the whole estate's filesystem and execution history, and it answers a
different question: across everything that *could* produce a root transition, which candidates are
statistically out of place. The two are complementary — the ranking produced here is what tells an
analyst which of H299's results to open first, and it surfaces the staged binary that has not run yet,
which no execution-based query can do.

The model has two halves that should be built in order.

The static half is the inventory, and it is valuable before any scoring exists. One row per
`(host or image, path, SHA-256, mode, owner, package, package-verifies, first-seen)`, collected fleet-wide
via osquery's `suid_bin` table or a periodic `find / -perm -4000 -o -perm -2000`. The prevalence score is
then simply the fraction of comparable hosts carrying that `(path, SHA-256)` pair — with *comparable*
doing the load-bearing work. Prevalence computed estate-wide across mixed roles and images is not merely
noisy, it is wrong in a specific direction: it makes every role-specific binary look rare and buries the
genuinely anomalous one among hundreds of them. Compute within role, within distribution, and within
container image.

The dynamic half scores executions against history. For each privileged execution, the features that
carry signal are the binary's fleet prevalence, whether any package owns it, whether the path is in a
writable or non-standard directory, how recently the setuid bit was set and by what, whether this
account has ever invoked this binary before, whether this parent process class has ever invoked it
before, and whether the binary has a known GTFOBins primitive. Score them jointly. Individually every
one of these has a large benign population; the conjunction of unowned, rare, recently-set and
newly-parented does not.

Two inputs prevent the model from producing confident nonsense, and both are easy to omit. Mount options
matter because a setuid bit on a `nosuid` filesystem is inert, and ranking an unexploitable file above a
live one wastes the analyst attention this model exists to allocate. Telemetry coverage matters because
prevalence is a fraction, and an under-instrumented host group manufactures apparent rarity out of
nothing. Publish the coverage figure next to the ranking rather than letting it sit inside the
denominator unseen.

The output is a ranked register, refreshed on the inventory cadence, with an owner-confirmed disposition
per row: expected, expected-with-review, or unexplained. The unexplained rows are the backlog. On a first
run there will be more of them than anyone wants, most will be legitimate vendor software nobody had
documented, and working through them is what converts this from an anomaly score into a baseline that
makes the next month's diff a short list.

## Why

- It answers the question the rule cannot. Elastic's allowlist-free logic correctly detects the execution
  of an unknown setuid binary, but leaves an analyst holding a path with no way to judge it; fleet
  prevalence, package ownership and first-seen date turn that path into a ranked, decidable finding.
- Prevalence is robust to the thing that breaks allowlists. A curated list of legitimate helpers is stale
  the day it is written and cannot cover a heterogeneous estate; a prevalence model recomputes itself
  from the estate's own current state and degrades gracefully as the estate changes.
- It sees staged capability before it is used. A setuid root binary dropped into a service account home
  or `/usr/local/bin` as a persistence and re-escalation primitive produces no execution event until the
  actor returns, so an execution-only hunt is blind to it while a filesystem inventory is not.
- The by-product is a hardening backlog with a natural priority order. The same inventory identifies
  unnecessary setuid bits on binaries such as `chfn`, `chsh`, `newgrp` and `ssh-keysign`, filesystems
  missing `nosuid`, and package-mode divergence — ranked by how rare and how exploitable each one is,
  which is a better remediation queue than a compliance scan produces.
