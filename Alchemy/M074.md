title: "Scoring cloud identities on audience breadth, not request volume: a workload that asks for one token asking for twelve is a sweep, and the threshold is per-identity"
hypothesis: >-
  Credential theft in a cloud build estate is not detectable by volume, because the platform is
  designed to issue tokens constantly and every agent, SDK and orchestrator asks for them. It is
  detectable by breadth and by sequence. Elastic''s analysis of the agent-framework PyPI compromise
  gives the shape - on any Azure resource with a managed identity, the stealer requested a separate
  access token for each of twelve resources, among them Azure Resource Manager, Microsoft Graph,
  Key Vault, Storage, Azure AI Foundry, Azure Machine Learning, Container Registry and Azure
  DevOps, and it read IMDS instance metadata alongside them to learn the subscription, resource
  group and VM the tokens belonged to. A real workload does not behave this way. A container that
  writes blobs asks for a Storage token; a job that reads a secret asks for a Key Vault token; an
  orchestrator asks for Resource Manager. The set each identity legitimately needs is small, stable
  over time, and specific to that identity - which makes the model a per-identity profile of
  requested audiences rather than a global threshold. Score each identity and host on three
  measures: how many distinct audiences were requested in a short window, how many of those are
  outside that identity''s historical set, and whether a credential-file read or environment sweep
  immediately preceded the first request. A static rule cannot express this because the normal set
  differs per identity and the anomalous count is small in absolute terms - the signal is the
  deviation, not the number.

false_positive_notes: |
  Multi-service workloads legitimately need several audiences, and some platform components need many. Orchestrators, backup services, policy engines, cost-management agents and platform bootstrap code can all request tokens for a wide set of resources by design. The per-identity profile is what keeps these from dominating the output - a platform component with a historically broad set is not anomalous for being broad, only for changing.

  New deployments have no history and will score as anomalous on their first run. Hold new identities in a warm-up state for a defined period rather than alerting on them, and reconcile the first observed audience set against the deployment's declared permissions. A new identity whose first act is to request twelve audiences is still worth reading immediately.

  SDK behaviour can inflate audience counts without any adversary. Some client libraries pre-fetch tokens for related services, and some retry across audiences when a request fails, which produces bursts that look like breadth. Profile per identity and per SDK version where that is visible, and treat an unchanged pattern across a version bump as the expected case.

  Request-level detail is frequently missing. Many pipelines record only that a host connected to the metadata address, not which resource was requested, which collapses the entire model to a connection count and makes it useless. Verify the audience field exists in the data before building anything on it; this is the most common reason this hunt silently fails.

  Scoring short-lived containers is genuinely hard, because the identity may outlive many hosts and each host sees only a fragment of the pattern. Aggregate per identity first and per host second, and carry the job identifier so fragments can be reassembled from pipeline logs.

  The twelve-audience count comes from one stealer and is not a threshold to hard-code. Other samples will request fewer, and a careful operator will request exactly one. A deviation score of one unfamiliar audience, preceded by a credential-file sweep, should outrank a familiar burst of six.

  Finally, this model scores requests, not outcomes. Elastic notes that it is unclear whether the malformed Azure DevOps OIDC requests return a usable token at all, so a high score establishes attempted escalation and a need to review what the identity then did - it does not establish that a token was obtained.
notes: |
  Model inputs, per token request - timestamp; host and, where applicable, container and job identifier; requesting process name, parent process and command line; identity principal; requested resource or audience; endpoint used, meaning IMDS, a local identity endpoint, a pipeline OIDC endpoint or a GitHub Actions OIDC endpoint; response status; and whether instance metadata was read in the same session.

  Baseline construction - 30 days per identity, longer where retention allows, producing for each identity the set of audiences ever requested, the median and ninety-fifth percentile count of distinct audiences per hour, the set of processes that legitimately request tokens, and the usual endpoint. Keep the sets, not just the counts; the set-difference is the feature that carries the signal.

  Scoring, three components, summed and ranked - the output is a ranked list to read, not a binary alert:

  - **Breadth.** Distinct audiences requested by one identity, from one host, within a 5-minute window. Score it against that identity's own ninety-fifth percentile rather than a fixed number. A count exceeding the historical maximum is the strongest single feature in the model.
  - **Novelty.** The number of requested audiences outside the identity's historical set, weighted by sensitivity - Key Vault, Resource Manager, Storage and Container Registry weigh more than telemetry endpoints, because those are the ones that convert a token into data or into further access.
  - **Precedence.** Whether a credential-file read, an environment-variable sweep, or a read of other processes' environments occurred on the same host within the preceding few minutes. This is the sequence Elastic's own prebuilt rule names - package runtime secret file access followed by an IMDS request - and it is what distinguishes a workload initialising from a collector escalating. On Linux the specific precursor to look for is a process reading many `/proc/<pid>/environ` paths, which the agent-framework stealer did for up to 300 processes.

  Suggested implementation sketch, to be fitted to the estate's platform - aggregate token requests into per-identity, per-host, 5-minute buckets; compute distinct audience count and the set difference against the identity's 30-day profile; join the file-access and process-environment reads on host and time with a bounded window; and rank by the summed score. The join window matters - correlating secret reads to token requests on host alone over a long lookback will pair unrelated days and produce a model that scores everything.

  Triage path for a high-scoring result - identify the requesting process and whether it was a declared pipeline step or an interpreter started by package installation; pull the identity's role assignments to establish what a minted token could reach; review the identity's sign-ins and the data-plane logs of each requested resource for the token lifetime; and check the host for the delivery artefacts, which for this compromise are `agent_framework_meta.pth`, `_telemetry.py`, `af_runtime_diag.pth` and `af_runtime_diag.py` in `site-packages`, and outbound requests to `webhook.site` with the user agents `af-runtime-diagnostics/1` or `runtime-diagnostics/1`.

  Why a model rather than a rule - three reasons, each of which has sunk a static threshold in this problem space. The normal audience set is per-identity, so one global threshold is simultaneously too noisy for platform components and too permissive for single-purpose workloads. The anomalous counts are small in absolute terms, so a rule tuned to catch twelve audiences misses an operator who asks for two of the right ones. And the strongest feature is a set difference against history, which a rule cannot express at all without the history being materialised first. The complementary static detections still belong in place - H513 holds the deterministic version of this for the specific endpoints and audiences - but the generalisation needs scoring.

  Hardening that shrinks the model's job - a managed identity scoped to exactly the resources its workload uses makes breadth structurally impossible, because requests for other audiences fail. The inventory leg in B043 and B055 is the prerequisite for that, and every identity whose scope cannot be justified is a finding in its own right regardless of this hunt.

  Scope note: H513 is the deterministic counterpart of this hunt, covering the specific IMDS audiences, the Azure DevOps `SYSTEM_OIDCREQUESTURI` call and the GitHub Actions token request as named artefacts; this hunt generalises the same behaviour to any identity and any audience set through a per-identity profile, which is the part a rule cannot carry. M033 scores a credential sweep in a build environment but keys on stored credential families being read rather than on tokens being minted, and it does not model audience breadth. B055 baselines service principals from the cloud side, including which legitimately read storage keys and at what rate, which is the measurement this model consumes. B043 covers managed identity inventory. H351 and H427 cover the `.pth` delivery mechanism and are the upstream pivot, not an overlap.

# M074

The agent-framework stealer asked the Azure Instance Metadata Service for twelve access tokens — Resource Manager, Graph, Key Vault, Storage, AI Foundry, Machine Learning, Container Registry, Azure DevOps and others — then read the instance metadata to find out which subscription, resource group and virtual machine it had just acquired credentials for.

Every one of those requests was legitimate in form. IMDS is there to issue tokens, the identity was entitled to them, and the platform logged nothing unusual. Which is the problem with detecting this by volume: cloud compute asks for tokens all day long, and a build estate asks for more than most.

What a real workload does not do is ask for everything. A container that writes blobs needs a Storage token. A job that reads a configuration secret needs a Key Vault token. An orchestrator needs Resource Manager. The set is small, it is stable, and crucially it is different for every identity — so the interesting quantity is not how many tokens an identity requested but how many of them it had never requested before.

That is why this is a model and not a rule. The threshold lives per identity, the anomalous counts are small in absolute terms, and the strongest feature is a set difference against that identity's own history.

## Why

- Volume is the wrong axis and most detection content uses it. Token issuance is the platform working as designed, so a count-based rule either fires constantly on orchestrators or never fires on the single-purpose workloads where a sweep is most visible.
- Breadth generalises past any one campaign. The agent-framework stealer requested twelve audiences; the next one will request a different number. A per-identity profile of requested audiences catches both, and catches the careful operator who requests exactly the two that matter — because for most identities, those two are also new.
- The sequence is as informative as the counts. A secret-file read or a sweep of other processes' environment variables immediately before the first token request separates a collector escalating from a workload initialising. Elastic's own prebuilt rule encodes exactly that pairing, which is a useful signal that the sequence holds up in production telemetry.
- Minted tokens leave no trace at the point of use, so issuance is the only place to stand. Once a token exists it is correctly signed and correctly scoped, and its use inside Key Vault or Storage looks like the identity doing its job.
- Building the model forces the inventory that actually fixes this. An identity scoped to exactly what its workload needs cannot sweep, because the other requests fail — and the audience profile this hunt builds is the evidence for right-sizing every identity in the estate.
