title: Detecting deliberately throttled SharePoint, OneDrive and Exchange collection by per-identity relative measures
hypothesis: >-
  An adversary operating a stolen Microsoft 365 session collects mailbox and file content at a rate
  they have deliberately tuned to stay under the alerting line - Microsoft observed under 1,000 files
  per hour, chosen specifically to blend with legitimate usage. That single fact invalidates the whole
  class of static-threshold detection, because whatever absolute number is picked, the operator is
  already sitting beneath it, and lowering the number floods the queue with legitimate bulk activity
  that runs at far higher volume than the attack. The features that survive a throttled adversary are
  RELATIVE ones - is this volume, this user agent, this ISP, this application, this hour normal FOR
  THIS IDENTITY - together with structural tells that do not depend on rate at all - headless REST
  access to Exchange with no interactive account object, access through an anonymous proxy, and a
  client library appearing where a browser or sync client belongs. Model per-identity deviation rather
  than absolute count, and the throttle the adversary applied stops protecting them.

false_positive_notes: |
  Bulk retrieval from Microsoft 365 is overwhelmingly legitimate, and several benign populations are larger and faster than the adversary this hunt targets. OneDrive first sync on a newly provisioned or rebuilt device pulls an entire personal drive in one pass and is the single biggest generator of high-count `SyncDownloadedFull` events - that ActionType is dominated by legitimate first sync and should carry the lowest weight of the four. E-discovery, legal hold and compliance collection do exactly what exfiltration looks like, by design and with authorisation. Backup, archiving and tenant-migration tooling reads everything on a schedule. Departing-employee archiving, where an administrator or the leaver themselves bulk-downloads a mailbox or drive before an account is closed, is both common and shaped precisely like the target behaviour, and it is worth resolving against the HR leaver process rather than against a suppression list. `ODMTADemand` is a benign Microsoft service agent that will appear in anonymous-proxy and high-volume results and must be excluded explicitly, as the third query does. Two cautions about the durability of the features themselves. The `python-httpx` user agent is a TOOLING artefact with a short half-life - it identifies the library the operator happened to use, and it stops working the day they change it or set a browser string, so it must never be the gate on a detection. Equally, legitimate automation, scripts and integrations also present non-browser user agents, so the string alone is not evidence of anything. The relative features - `UncommonForUser` for ISP and user agent, per-identity volume percentile, first-seen ISP for that account - are what remain true across tooling changes, and they are what the model should weight. Finally, understand what an empty result means. If Defender for Cloud Apps is not connected, `CloudAppEvents` is empty and the silence is meaningless. If `RawEventData` is not retained, the Exchange REST query cannot resolve the real actor and the anonymous-proxy query cannot compute file size, so both degrade quietly rather than failing loudly. Confirm ingestion before treating a clean result as a clean tenant.
notes: |
  Model shape - a per-identity anomaly score over cloud application activity, computed in 1 to 2 hour bins, in which absolute volume is an INPUT rather than the decision. (1) PER-IDENTITY VOLUME DEVIATION, heaviest weight - this hour's file-access count expressed as a percentile against that account's own 30-day distribution, so a user who normally touches 20 files and today touches 400 scores far above a records manager whose daily normal is 4,000. (2) UNCOMMON-FOR-USER SIGNALS, heavy - the `UncommonForUser` field flagging ISP or UserAgent, and first-seen-ever ISP for that account, which are durable because they are defined relative to the identity rather than to a string. (3) HEADLESS ACCESS STRUCTURE, heavy - Exchange REST activity where `AccountObjectId` is empty, meaning the access is non-interactive, with the true actor recovered from `RawEventData.TokenObjectId`. (4) ANONYMOUS PROXY, heavy - `IsAnonymousProxy` true, which has almost no legitimate bulk-download population once `ODMTADemand` is excluded. (5) SESSION PROVENANCE - whether the Entra sign-in behind the token came from a compliant managed device. (6) USER-AGENT TOOLING TELL, LIGHT and explicitly a booster not a gate - `python-httpx` and similar library strings. (7) SENSITIVITY OF WHAT WAS REACHED, applied as a final multiplier from labels on the sites and mailboxes touched. Weight 1 through 5 as the model; treat 6 as evidence that raises an already-scored hit, never as the reason it appeared.
  The throttle is the whole point - Microsoft observed these operators collecting at under 1,000 files per hour, a rate chosen to sit below common alerting thresholds. Any static number you pick is therefore a number the adversary has already priced in. The thresholds appearing in Microsoft's queries below (500 Exchange REST events per hour, 100 files per 2 hours, 1,000 events or 5 GB per 2 hours) are starting points for finding the loud cases and must be refitted per tenant; the model above is what catches the quiet ones.
  Query 1, Exchange Online exfiltration via REST - the elegant part of this query is `isempty(AccountObjectId)`, which isolates HEADLESS, non-interactive REST access to Exchange, and the recovery of the real actor from `RawEventData.TokenObjectId`. `ApplicationId` 20893 is Exchange Online and Outlook Web REST. The three `AccountDisplayName` values are worth understanding rather than copying - `One Outlook Web` is the web client, while `9199bf20-a13f-4107-85dc-02114787ef48` and `d3590ed6-52b3-4102-aeff-aad2292ab01c` are the well-known first-party client IDs for Outlook Mobile and Microsoft Office, appearing here AS display names because the access is token-driven rather than user-driven.
  CloudAppEvents | where isempty(AccountObjectId) | where ApplicationId == '20893' | where AccountDisplayName in ("One Outlook Web", "9199bf20-a13f-4107-85dc-02114787ef48", "d3590ed6-52b3-4102-aeff-aad2292ab01c") | where isnotempty(IPAddress) | extend AccountObjectId = tostring(RawEventData.TokenObjectId) | summarize ExchangeRestEventCount=count() by IPAddress, AccountObjectId, bin(Timestamp,1h) | where ExchangeRestEventCount >= 500
  Query 2, SharePoint and OneDrive collection keyed on an uncommon user agent - `ApplicationId` 20892 is SharePoint Online and 15600 is OneDrive for Business. The durable clause here is `UncommonForUser has_any("ISP","UserAgent")`, which is a per-identity relative measure; the `python-httpx` clause is the perishable one and should be relaxed to any non-browser, non-sync-client agent once the query is in production, or it will stop working silently the moment the operator changes library.
  CloudAppEvents | where ApplicationId == "20892" or ApplicationId == "15600" | where ActionType in ("FileDownloaded", "FileAccessed", "SyncDownloadedFull") | where isnotempty(AccountObjectId) | where isnotempty(IPAddress) | where isnotempty(UserAgent) | where UncommonForUser has_any("ISP","UserAgent") | where UserAgent has 'python-httpx' | project Timestamp, AccountObjectId, IPAddress, ISP, UserAgent | summarize FilesAccessedLastWindow = count() by AccountObjectId, IPAddress, ISP, UserAgent, bin(Timestamp,2h) | where FilesAccessedLastWindow >=100
  Query 3, high-volume access through an anonymous proxy - covers all three application IDs and adds `FilePreviewed`, which matters because previewing renders content without generating a download event. `IsAnonymousProxy` is close to a standalone signal for bulk retrieval; the `ODMTADemand` exclusion removes a benign Microsoft service agent that would otherwise dominate the output. Note that file size is summed from `RawEventData.FileSizeBytes`, so this query silently returns zero bytes if the raw blob is not retained.
  CloudAppEvents | where ApplicationId in (20892, 20893, 15600) | where ActionType in~ ("FileDownloaded", "FileAccessed", "FilePreviewed") | where IsAnonymousProxy == true | where UserAgent !has "ODMTADemand" | extend FileSizeBytes = coalesce(tolong(RawEventData.FileSizeBytes), 0) | summarize FileSizeBytes = sum(FileSizeBytes), FirstSeen = min(Timestamp), LastSeen = max(Timestamp), EventCount = count(), ActionTypes = make_set(ActionType), Applications = make_set(Application) by AccountObjectId, IPAddress, TimeBucket = bin(Timestamp, 2h), UserAgent, ISP | extend FileSizeGB = round(FileSizeBytes / 1024.0 / 1024.0 / 1024.0, 2) | where FileSizeGB >= 5 or EventCount >= 1000 | order by EventCount desc
  Query 4, mailbox and attachment reconnaissance in Graph - this one runs against `GraphAPIAuditEvents` rather than `CloudAppEvents` and sits chronologically BEFORE the three above, finding the enumeration of `/messages` and `/mailfolders` that precedes attachment retrieval. The `AttachmentRequests >= 3` branch is deliberately separate from the volume branch, because attachment pulls are far rarer than message listing and a small number of them is already interesting.
  GraphAPIAuditEvents | where Timestamp > ago(24h) | where toint(ResponseStatusCode) between (200 .. 299) | extend Uri = tolower(RequestUri), ActorId = coalesce(AccountObjectId, ServicePrincipalId, ApplicationId), Path = tostring(split(tolower(RequestUri), "?")[0]) | where Uri has_any ("/messages", "/mailfolders", "/attachments") | summarize Requests=count(), DistinctPaths=dcount(Path), MessageRequests=countif(Uri has "/messages"), AttachmentRequests=countif(Uri has "/attachments"), TotalResponseBytes=sum(coalesce(ResponseSize, 0)), SampleUris=make_set(RequestUri, 12) by ActorId, IpAddress, ApplicationId, bin(Timestamp, 30m) | where (Requests >= 8 and DistinctPaths >= 4) or AttachmentRequests >= 3 | order by AttachmentRequests desc
  Reference values to keep at hand - `ApplicationId` 20893 is Exchange Online and Outlook Web REST, 20892 is SharePoint Online, 15600 is OneDrive for Business. Relevant `ActionType` values are `FileDownloaded`, `FileAccessed`, `FilePreviewed` and `SyncDownloadedFull`, the last of which is dominated by legitimate first sync. The anomaly fields are `UncommonForUser`, which flags ISP and UserAgent among others, and `IsAnonymousProxy`. `ODMTADemand` is a benign Microsoft service agent and must be excluded wherever anonymous-proxy or high-volume filters are used.
  Output shape and triage - a ranked list per identity per 2-hour bin carrying the account object ID, the resolved token object ID where the access was headless, source IP and ISP, user agent, application, action-type mix, event count, summed file size in GB, the account's own 30-day volume percentile, which `UncommonForUser` flags were set, whether the proxy was anonymous, and the sensitivity labels of what was reached. Triage in this order - was the session interactive or headless, was the device compliant, is this volume abnormal for THIS user rather than in absolute terms, and what was the classification of the content. Escalate on the combination of headless or anonymous-proxy access plus an above-percentile volume for that identity; the raw byte count is context for the impact statement, not the trigger.
  Cross-reference - the discovery phase that typically precedes this collection is already covered by [[H169]], which scores post-AiTM Microsoft Graph reconnaissance by category breadth within a session, and by [[M022]], which does the per-identity baseline version of the same measure. This hunt is deliberately scoped to the COLLECTION half and does not restate either. The two halves are strongest run together - a Graph breadth hit from [[H169]] followed within the hour by a per-identity volume anomaly here is a far more specific finding than either alone - and the identity pivot for both is [[H329]], the MFA-device-registration event that usually opens the intrusion.
  Why this is Alchemy rather than Flames - the adversary has explicitly tuned their rate to defeat static thresholds, so the detection cannot BE a static threshold. Every action taken is a permitted operation by an authenticated identity against data it is entitled to read, and at a volume deliberately chosen to be unremarkable. The only durable discriminator is deviation from that specific identity's own history - its normal volume, hours, ISP and client - which requires a per-tenant, per-user baseline and produces a score rather than a verdict. That is a model, not a rule.

# M046

The most consequential sentence in Microsoft's passkey social-engineering analysis is a small one about pace: the operators collected at under a thousand files an hour, and they did it on purpose, to blend with legitimate usage. That is an adversary who has read the detection literature. It means any absolute threshold a defender picks has already been priced in, and it means the obvious corrective - lowering the threshold - runs straight into the fact that legitimate bulk activity in Microsoft 365 is much larger and much faster than the attack. A OneDrive first sync on a new laptop will beat this operator's hourly rate without trying. E-discovery will too, and so will backup, and so will an administrator archiving a leaver's mailbox. Against a throttled adversary inside a noisy legitimate population, counting stops working. What still works is comparison: this account does not normally download four hundred files, has never connected from this ISP, has never presented this user agent, and has never accessed Exchange through a token with no interactive account attached. Those are relative measures, they are computed per identity, and the adversary cannot throttle their way beneath them without also abandoning the collection.

## Why

- **A stated adversary throttle is a stated defeat of static detection, and should be treated as such.** When the reporting tells you the operator deliberately stayed under a thousand files an hour, it is telling you the number you were going to pick is already wrong. The correct response is not a smaller number - it is to stop asking how much and start asking how much compared to this identity's own history, which is a question the throttle does not answer.
- **The legitimate bulk population is bigger than the attack, which inverts the usual assumption.** In most hunts the adversary is the outlier by volume. Here they are deliberately mid-pack, sitting beneath first sync, e-discovery, backup, migration and leaver archiving. Any model that ranks by absolute count therefore ranks the legitimate populations above the adversary permanently, no matter how it is tuned.
- **Some of the strongest features do not involve rate at all.** Exchange REST access with an empty `AccountObjectId` is structurally headless, whatever its volume; `IsAnonymousProxy` has almost no benign bulk-download population once the Microsoft service agent is excluded; a first-seen ISP for an account is a fact about the account, not about the traffic. These carry weight at any pace, which is precisely what is needed against an operator who has chosen their pace carefully.
- **Separate the durable features from the perishable ones explicitly, and weight them accordingly.** `python-httpx` is real, it was observed, and it is worth matching - but it identifies a library, and libraries change between campaigns and sometimes between hosts. `UncommonForUser` and per-identity percentile describe a relationship between an actor and its own history, which survives every tooling change. Build the model on the second kind and let the first kind raise a score that already exists.
- **Half the value of running this is discovering what you cannot see.** The Exchange REST query depends on `RawEventData.TokenObjectId` and the proxy query on `RawEventData.FileSizeBytes`, so a tenant that flattens or drops the raw blob gets degraded results with no error. Defender for Cloud Apps must be connected for `CloudAppEvents` to exist at all. Establishing those two facts is a concrete deliverable independent of whether the hunt finds anything.
