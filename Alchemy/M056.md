  A real-time adversary-in-the-middle phishing kit does not steal a password, it steals a session. The
  victim types credentials into a pixel-perfect Google sign-in replica; the operator's server relays
  them to the genuine Google endpoint, relays back whichever MFA challenge Google asks for, and walks

false_positive_notes: |
  Source and fingerprint discontinuity within one session has a long list of innocent causes and this model will be useless unless they are modelled first. Ordinary ones - corporate VPN connect and disconnect mid-session, split-tunnel changes, a laptop moving from office wifi to a mobile hotspot, carrier-grade NAT and mobile networks rotating addresses, roaming between cell and wifi, and cloud-proxied browsing (secure web gateways, Cloudflare WARP, iCloud Private Relay) which deliberately presents hosting-ASN addresses for genuine users. Browser and OS updates change user-agent strings legitimately, sometimes mid-day across a fleet. Users genuinely sign in from several devices in quick succession, and shared or kiosk machines produce fingerprint churn by design. Legitimate automation also looks like a session being used from somewhere the human is not - mail clients, mobile sync, backup and archiving tools, e-discovery, and any SaaS integration holding a delegated token. The features that survive all of this - *simultaneity*, because a VPN change is sequential while a relay produces credential entry and session use that overlap or occur within seconds from two different networks; *direction*, since legitimate movement is usually consumer-to-consumer or consumer-to-corporate while a relay runs consumer-to-hosting; *the preceding click*, because a relay is always preceded by the victim's browser reaching a non-Google host and upgrading to a WebSocket, which a VPN change never is; and *challenge timing*, as a relayed MFA prompt carries the round-trip latency of the operator's server and tends to sit at the slow tail of the distribution. Build the per-user travel and ASN baseline over thirty days before scoring anything, allowlist the privacy-relay and SWG ASNs your own estate uses, and treat single-feature hits as noise - this model is only credible on feature conjunction. Note finally that the kit collects `navigator.languages`, screen dimensions and mobile status precisely so the operator *can* match the victim's client, so fingerprint discontinuity may be partially suppressed by a careful operator; the network-geometry and timing features do not depend on it and should carry more weight.

  Platform: Google Workspace primarily, with the same model applying to Entra ID and any IdP fronting a browser sign-in. Driven by Cisco Talos, "UAT-11985 - AI-assisted event lures delivering real-time Google AitM phishing" (October 2026). Talos published no ATT&CK IDs; the mappings here are assigned.
  Published kit architecture (Talos, verbatim where quoted). The campaign targeted "individuals affiliated with Taiwan research organizations," impersonating the Taiwan European Union Centre, NCCU Institute of International Relations and Taiwan Research Institute. Lures were AI-assisted - "nearly identical syntactic structures despite discussing different geopolitical topics, suggesting the content was generated from a reusable prompt template." The actor also attached event posters "scraped from legitimate websites" with "maliciously altered" QR codes, anticipating that recipients "might print and display these posters on office bulletin boards" - expanding into quishing and reaching secondary victims who never received the email. Hyperlinks displayed legitimate-looking Google Forms URLs whose `href` went elsewhere; the fake form then "forcibly redirects the user to a spoofed Google login page."
  The relay (Talos, verbatim). The kit "employs a dual-channel architecture including HTTP POST and WebSocket to synchronize Google's authentication state in real time. This mechanism effectively bypasses multi-factor authentication (MFA) to harvest complete, authenticated session tokens." HTTP POST carries "initial browser fingerprints, credential and challenge submissions during user interaction, and periodic heartbeat polls"; WebSocket "streams real-time instructions to the phishing page via this channel, dictating exactly which MFA challenge screen to render." The named events - `google_login_start` (sends "locale, user agent, screen dimensions, and mobile-device status"), `google_input_identifier` (the server relays the identifier to real Google "to verify whether the account exists and determines whether a passkey-based flow is enabled"), and `google_login_check` (sends "the password, account identifier, and browser user-agent information"; the server forwards to Google and "if the credentials are accepted and Google requires additional authentication, the server returns the MFA challenge type and layout"). Locale support is `zh-CN`, `zh-TW` and `en`, selected on `navigator.languages`. A hidden `<section>` holds an iframe with ID `google-success-frame` loading `/google-login-assets/operation-success.html` with `sandbox="allow-scripts"`. The JavaScript is "embedded at the end of the HTML document" using "advanced string rotation obfuscation" - a static array of Base64 strings rotated at runtime by a `while(!![]) { push/shift }` shuffle loop, which defeats automated static deobfuscation. Talos assesses with moderate confidence the UI was authored by a native Simplified Chinese speaker, from the localisation architecture (base object in `zh-CN`, other locales derived at runtime) and mainland lexical choices such as `账号`, `计算机`, `邮箱`, `无痕浏览窗口` and `访客模式`.
  Why this is a scoring problem and not a rule. The sign-in that results from a successful relay is, from the identity provider's perspective, completely valid - correct password, correctly satisfied MFA challenge, a real session token. There is no failed authentication, no impossible-travel violation at the moment of creation (the victim really is where they are), and no Conditional Access signal unless device compliance is enforced. The anomaly is not in any single event; it is in the *geometry* of the session - the relationship between where credentials were entered, where the challenge was satisfied, and where the token is subsequently used. Only a model that reasons across those can see it. This is also why passkeys matter so much here: the kit explicitly checks "whether a passkey-based flow is enabled," because a phishing-resistant method breaks the relay outright rather than being relayed through it.
  Feature set to score per successful sign-in, over a rolling 30-day per-user baseline.
  - Source transition within session - whether the IP that completed authentication differs from the IP first using the session, and whether the two occur within seconds rather than minutes.
  - ASN and address class - a transition from consumer or corporate space to hosting or VPS space, which is the relay operator's position. Weight this heavily; weight it *down* for the privacy-relay and SWG ASNs your own users legitimately traverse.
  - Simultaneity - overlapping or near-overlapping activity from two distinct networks. A VPN change is sequential; a relay is concurrent, because the victim and the operator are both holding the same session.
  - Preceding non-IdP destination - did the user's browser reach a newly-registered or low-reputation host, and perform a WebSocket upgrade, in the minutes before the sign-in? This is the single most specific feature available and it comes from proxy or SWG logs rather than from the IdP.
  - Challenge latency - time between MFA prompt issuance and satisfaction. A relayed challenge carries the operator server's round trip and clusters at the slow tail.
  - Device-fingerprint discontinuity - user agent, platform, screen dimensions and device ID disagreement between authentication and session use. Treat as corroborating rather than decisive, since the kit collects exactly these fields in `google_login_start` so that the operator can match them.
  - Authentication-method weakness - the sign-in satisfied a relayable factor (SMS, TOTP, push approval) rather than a phishing-resistant one. Not an anomaly by itself, but it is the precondition for the whole technique and belongs in the score.
  - Post-sign-in action profile - mail-rule creation, OAuth grant, mass mailbox read, contact or calendar enumeration, or delegate addition within the first hour. This confirms rather than predicts, and should be used to validate the model rather than to trigger it.
  Ranking and triage. Rank descending on a weighted conjunction, with simultaneity, ASN-class transition and the preceding WebSocket upgrade carrying the most weight. For each top candidate, pull the full session timeline and ask the user directly whether they signed in from both places - a relay produces a session the victim genuinely does not recognise using, which is the fastest available confirmation. Then revoke sessions and re-enrol the factor, since the password alone is not what was lost.
  Scope and relationship to existing coverage. HEARTH already hunts the post-takeover persistence that follows AiTM session theft in [[H329]] (an extra device added to an existing Entra MFA method after vishing-led AiTM). This hunt deliberately targets the *session-creation* moment rather than the persistence that follows, and scores it from the IdP and network side rather than from the identity-audit side. [[H303]] covers a separate phishing-delivery anomaly. The quishing leg is worth noting as an operational caveat rather than a hunt - a QR code on a printed poster produces a victim with no email artefact at all, so email-gateway telemetry will under-count the campaign's reach and the sign-in side is the only place those victims appear.

# M056

The thing UAT-11985's phishing kit steals is not a password. By the time the victim finishes typing, the operator already has an authenticated session — and the victim has one too, briefly, which is the part that makes it hard to see.

Talos documented the architecture in October 2026. The victim lands on a replica Google sign-in page. The page collects their locale, user agent, screen dimensions and mobile-device status and ships them to the operator's server over HTTP POST as a `google_login_start` event. When the victim enters an identifier, the server relays it to the real Google to learn whether the account exists and whether a passkey flow is enabled. When they enter a password, `google_login_check` forwards it to Google, Google replies with whichever MFA challenge it wants, and the operator's server pushes an instruction back down a WebSocket telling the fake page exactly which challenge screen to render. The victim satisfies it. The operator keeps the session.

MFA was not bypassed in the sense of being broken. It was *relayed* — asked and answered through a man in the middle, in real time, over a persistent socket built for exactly that latency.

Now consider what the identity provider logged. A correct password. A correctly satisfied second factor. A session token issued to a user who really was sitting at their desk in Taipei. No failures, no impossible travel at the moment of creation, no Conditional Access violation unless device compliance was enforced. Every individual field is valid. There is no rule to write.

What is wrong is the *geometry*. Credentials were entered from one network and the session was used from another, within seconds, with the second one sitting in hosting space rather than consumer space. The MFA challenge took longer to satisfy than usual, because a round trip through the operator's server is a real round trip. And minutes before any of it, the victim's browser reached a host that was not Google and upgraded the connection to a WebSocket — which is the single most specific artefact in the whole chain, and it lives in proxy logs rather than in the IdP.

One honest limitation belongs in the design. The kit collects the victim's user agent, locale and screen dimensions on purpose, which means a careful operator can match them and suppress the fingerprint-discontinuity feature. The network-geometry and timing features do not depend on the operator's carelessness, so they should carry the weight.

The lure deserves a note too. Talos found the emails were AI-assisted — "nearly identical syntactic structures despite discussing different geopolitical topics" — and that the attached event posters were real posters, scraped from legitimate sites, with the QR codes swapped. The actor anticipated someone printing one and pinning it to an office noticeboard. Those secondary victims never receive an email at all, which means email-gateway telemetry structurally under-counts the campaign and the sign-in side is the only place they ever appear.

## Why

- **A relayed session is valid in every field the IdP records.** Correct password, satisfied challenge, real token. Nothing fails, so detection has to come from relationships between events rather than from any event's contents.
- **Simultaneity separates a relay from a VPN change.** Legitimate source transitions are sequential — disconnect, reconnect. A relay is concurrent, because the victim and the operator hold the same session at the same moment from two different networks.
- **The direction of the ASN transition is the signal, not the transition itself.** Users move between consumer and corporate space constantly. Consumer-to-hosting, at the instant of session creation, is the operator's seat.
- **The WebSocket upgrade to a non-IdP host is the most specific feature available.** It is also the one a VPN change never produces, and it comes free from proxy or SWG logs that most identity-side hunts never join against.
- **Relayed MFA is slower than local MFA.** The operator's round trip shows up in challenge-satisfaction latency, giving an independent feature that needs no network data at all.
- **The kit's own fingerprint collection tells you which features to distrust.** `google_login_start` exists so the operator can impersonate the victim's client. Scoring heavily on user-agent discontinuity means trusting the operator to be lazy.
- **The passkey check is the mitigation, stated by the attacker.** The kit asks Google "whether a passkey-based flow is enabled" because phishing-resistant factors break the relay rather than passing through it. Where a scored session satisfied SMS, TOTP or push, that is both the finding and the fix.
- **Confirmation is unusually easy once a session is ranked.** The victim genuinely does not recognise the second source. Asking resolves most candidates in one conversation — and the remediation is session revocation and factor re-enrolment, not a password reset.
- **Quishing victims exist only in the sign-in data.** A modified QR code on a printed poster leaves no mail artefact, so any estimate of campaign reach drawn from the email gateway is wrong by construction.
