  A real-time adversary-in-the-middle kit that relays credentials server-side leaves no anomaly inside
  the identity provider's own logs, because the identity provider never sees the victim. Talos
  documented UAT-11985's Google kit doing exactly this: the victim types into a replica sign-in page,
  the operator's server forwards the identifier, password and MFA response to the real Google service,
  and a WebSocket tells the fake page which challenge screen to render next. The resulting Workspace
  `login_success` therefore comes from the operator's server, while the victim is shown a fake success
  frame and never holds a Google session at all. The pair that exposes the relay spans two data sources
  - the victim's browser reaching a young, non-Google host and upgrading to a WebSocket in the proxy or
  web-gateway log, and, within minutes, a Workspace sign-in for that same user from an address that is
  not the user's own egress, is new for that user, or sits in hosting space. Score each successful
  sign-in on that cross-source conjunction and rank the ones where both halves are present.

false_positive_notes: |
  Each half of the conjunction is common on its own. WebSocket upgrades to non-Google hosts are everywhere -
  chat and collaboration tools, trading and news dashboards, browser-based IDEs, support widgets and any
  modern single-page application - and a meaningful share of them go to recently registered or rarely
  visited domains. Sign-ins from an address the user has not used before are also routine: travel, a new
  home router, mobile carriers rotating carrier-grade NAT, and users connecting through secure web gateways,
  Cloudflare WARP or iCloud Private Relay, which deliberately present hosting-ASN addresses for genuine users.
  The model is only credible on the conjunction and on the timing between the halves - the same user, the
  non-Google WebSocket first, the sign-in within minutes, and the sign-in IP different from the egress the
  proxy recorded for that user at that moment. Allowlist your own egress, SWG and privacy-relay ranges before
  scoring, and allowlist well-established WebSocket destinations by estate-wide prevalence rather than by name.
  One structural blind spot needs stating plainly: a victim who scans a QR code on a phone off the corporate
  network produces no proxy record at all, so the proxy half is missing for exactly the quishing victims this
  campaign reached. For those users the model degrades to the Workspace-only features, which are much weaker.

  Why the identity provider alone cannot see it. Because the operator's server submits the credentials and the
  challenge response, the only sign-in Google records is the operator's. There is no victim-side Google session
  to compare it against, so models that look for one session used from two networks - [[M042]] for Entra, which
  scores provenance discontinuity between a victim's genuine traffic and the relay's - have nothing to pair
  inside the IdP for this kit. The victim's half of the event exists only outside the IdP, in the browser's
  traffic to the phishing host. That is why this model is cross-source. [[H258]] covers a related Okta case
  scored on multi-IP device enrolment.
  Feature set, scored per Workspace `login_success`, against a rolling 30-day per-user baseline.
  - Preceding relay contact (proxy) - the same user's browser reached a non-Google host and performed a WebSocket
    upgrade in the 15 minutes before the sign-in. Weight up when the host is recently registered or visited by very
    few users estate-wide. This is the anchor feature; without it the score should stay low.
  - Egress mismatch (proxy against IdP) - the sign-in IP is not the egress address the proxy recorded for that user
    in the same window. A user signing in from their own browser signs in from their own egress; a relay does not.
  - Source novelty (IdP) - the sign-in IP or its ASN has not appeared for that user in 30 days.
  - Address class (IdP plus enrichment) - the sign-in IP sits in hosting or VPS space. Weight down for the estate's
    own SWG and privacy-relay ranges.
  - Relayable factor (IdP) - the `login_challenge` that preceded the success used a relayable method (SMS, TOTP,
    Google prompt) rather than a security key or passkey. A precondition, not an anomaly, but it belongs in the score.
  - Google's own verdict (IdP) - a `suspicious_login` event, or a later `user_signed_out_due_to_suspicious_session_cookie`,
    for the same user. Corroborating; Google's session-cookie protection firing afterwards is strong confirmation.
  - Post-sign-in actions (IdP and Gmail) - mail filter or forwarding changes, OAuth token grants, or delegate additions
    within the first hour. Confirms rather than predicts; use it to validate the model, not to trigger it.
  Expected, not observed by Talos - the operator's server sitting in hosting infrastructure, and the sign-in arriving
  within seconds to minutes of the WebSocket session. Both follow from a real-time relay but are not measured in the
  report. The Workspace login audit carries no user-agent or device identifier and no challenge-issued timestamp, so
  fingerprint discontinuity and MFA-challenge latency cannot be scored from it; do not build features on them.
  Sample join, as schematic SQL - map the field names to your proxy schema and Workspace export.
  `WITH ws AS (SELECT user, dest_host, src_egress_ip, ts FROM proxy WHERE upgrade = 'websocket' AND NOT REGEXP_CONTAINS(dest_host, r'(^|\.)(google|gstatic|googleapis|googleusercontent|youtube)\.com$')), li AS (SELECT actor_email AS user, ip_address, ip_asn, ts FROM workspace_login WHERE event_name = 'login_success') SELECT li.user, li.ts, li.ip_address, li.ip_asn, ws.dest_host, ws.src_egress_ip, ws.ts AS ws_ts FROM li JOIN ws ON li.user = ws.user AND ws.ts BETWEEN TIMESTAMP_SUB(li.ts, INTERVAL 15 MINUTE) AND li.ts WHERE li.ip_address != ws.src_egress_ip`
  Ranking and triage. Rank descending with the relay-contact and egress-mismatch features carrying the most weight.
  For each top candidate, pull the user's proxy record around the WebSocket host and ask the user whether they
  signed in to Google at that time - the victim saw a success screen, so they will usually say yes, and the useful
  question is which page they were on when they did. Then revoke the user's sessions and re-enrol the factor, since
  the password alone is not what was lost. A passkey or security key is the mitigation - Talos shows the kit checks
  for a passkey flow and renders a passkey prompt when one is enabled; inference, not stated by Talos: a
  phishing-resistant credential is bound to the real origin and should fail when relayed.

  The quishing leg is an operational caveat rather than a hunt - a QR code on a printed poster produces a victim with

# M056

The phishing kit Talos documented for UAT-11985 does not hand the victim a Google session at all. It hands one to the operator, and shows the victim a picture of success.

The victim lands on a replica Google sign-in page, reached through a fake Google Form. When they type an identifier, the operator's server relays it to the real Google service to learn whether the account exists and whether a passkey flow is enabled. When they type a password, the server forwards it, Google asks for a second factor, and the server pushes an instruction down a WebSocket telling the fake page which challenge screen to show. The victim answers it. The operator's server submits the answer. Then a hidden iframe called `google-success-frame` tells the victim everything worked.

So think about what Google logged. One `login_success`, from the operator's server. Correct password, satisfied challenge. That is the whole record. The victim never signed in to Google — their browser was talking to the phishing host the entire time. Models that look for one session used from two places at once have nothing to pair here, because inside the identity provider there is only one place.

The other half of the event is outside the identity provider. Minutes before that sign-in, the victim's browser reached a host that was not Google and upgraded the connection to a WebSocket. That lives in proxy or web-gateway logs. Put the two side by side — same user, WebSocket to a young non-Google host, then a Google sign-in for that user from an address that is not the user's own egress — and the relay shows up in a way neither source can show alone.

Two honest limitations. The Workspace login audit carries no user agent, no device identifier and no challenge-issued timestamp, so the fingerprint and latency features that look attractive on paper cannot be computed; leave them out. And victims who scanned a QR code on a phone off the corporate network have no proxy record, which is the half this model leans on. Talos found the actor expected exactly that kind of victim — real event posters, scraped from legitimate sites, with the QR codes swapped, in the hope someone would pin one to a noticeboard.

## Why

- **The identity provider sees only the operator.** The relay submits the credentials and the challenge response itself, so Google records one valid sign-in and no victim session to compare it against.
- **The victim's half is in the proxy log.** A WebSocket upgrade to a young, rarely visited non-Google host minutes before a sign-in is the anchor feature, and it is the one identity-side models never join against.
- **Egress mismatch is computable and sharp.** The proxy knows the user's egress at that moment. A sign-in from somewhere else, minutes after the WebSocket, is the relay's address.
- **Score only what the logs carry.** The Workspace login audit has no user agent, device ID or challenge timing. Features built on fields that do not exist produce a model that cannot run.
- **Google's own detections are corroboration worth wiring in.** `suspicious_login` and a later `user_signed_out_due_to_suspicious_session_cookie` for the same user strengthen a candidate cheaply.
- **The passkey prompt is the mitigation to push.** The kit checks for a passkey flow and renders a prompt for one; a phishing-resistant credential bound to the real origin should not survive the relay.
- **Quishing victims are the blind spot.** A QR code scanned on a phone off-network leaves no proxy record and no mail artefact. For those users this model degrades to the weak IdP-only features, and campaign reach measured from email is an undercount.
