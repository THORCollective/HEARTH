hypothesis: >-
  A remote-access agent spreading through its own connected sessions and a remote-access agent being
  deployed by the IT team produce the same event on every individual host — a new RMM client installs
  and calls home. They differ only in the SHAPE of the enrolment across the estate over time. A
  managed rollout radiates from deployment infrastructure, follows the organisation's asset topology,
  lands on machines that share an owner or a site, and stops when the target list is exhausted. A
  self-propagating installation radiates from whichever hosts were already connected, crosses
  organisational boundaries that a rollout respects, shows host-to-host timing consistent with
  transmission rather than scheduling, and does not stop. Build the enrolment graph — nodes are hosts,
  edges are first-seen agent installs attributed to a parent host or session — and score connected
  components on branching factor, cross-boundary edges and inter-arrival timing rather than on any
  property of the agent binary.

false_positive_notes: |
  The dominant legitimate population is deployment itself, and it can look startlingly similar at small scale. Genuine producers of dense, fast, wide agent-install graphs: an MSP onboarding a new client estate; an IT-led RMM migration or replacement, which installs the new agent everywhere in days and is often performed with unusual urgency; imaging and reimaging waves, where the agent appears on many hosts at once because it is baked into the gold image rather than because it spread; VDI and non-persistent desktop pools, which can create hundreds of apparently new hosts per day and will dominate any first-seen analysis unless excluded by device role; and automated software-deployment tooling pushing the agent on a schedule. Several structural features separate these from propagation and should be weighted accordingly. Rollouts are attributable to DEPLOYMENT infrastructure as the install parent, so the edge points back to a management server rather than to a peer workstation. Rollouts respect organisational boundaries — subnet, site, business unit, management scope — because the target list was built from them, while propagation crosses whatever the connected sessions happened to span. Rollouts are bounded and terminate; propagation continues. Rollout inter-arrival times cluster around scheduling artefacts such as maintenance windows or policy refresh intervals, while propagation times cluster around however long the operator takes per host. The most reliable single discriminator is not any of these, though — it is INSTANCE IDENTITY. A component whose agents all report to an authorised relay is a rollout no matter how it is shaped; a component reporting to an unrecognised relay is a finding no matter how small. The model should therefore treat instance identity as a hard partition applied BEFORE scoring, not as another weighted feature, or a well-run rollout will bury a three-host intrusion. Finally, sparse telemetry produces phantom edges: if first-seen timestamps come from a scanner that runs daily rather than from real-time events, the ordering within a day is arbitrary and the graph will invent parent-child relationships that do not exist. Validate timestamp provenance before trusting any structure the model reports.
notes: |
  Why this is modelled rather than ruled - Per-host, a rogue agent install and a sanctioned one are the same event with the same fields; the information that distinguishes them does not exist on any single host and only appears in the relationships between installs. That is a graph property, and no per-event rule can express it. The Huntress case that motivates this was described as worm-LIKE precisely because the judgement came from observing installations across unrelated hosts, not from anything on any one of them.
  Graph construction - Nodes are hosts. Edges are directed first-install events, attributed where possible to a source. Edge attribution by decreasing confidence: (1) RMM server audit log showing session A transferred or executed files against host B — the strongest and should be used wherever the organisation controls the server; (2) process lineage, where the installer parent is an existing remote-access client on a peer host, or the installer arrived over SMB or an admin share from an identifiable source; (3) temporal-plus-topological inference, where B installs within a short window of A and shares a subnet or credential scope — this is the weakest and should be marked as inferred so downstream scoring can discount it. Partition the graph by INSTANCE IDENTIFIER before anything else, so each agent tenancy is its own set of components.
  Component features to score - branching factor (mean and max out-degree; a rollout from a management server is a star with one very high-degree node, while propagation is a bushy tree with many moderate-degree nodes, and that difference in DEGREE DISTRIBUTION SHAPE is more informative than any single count); depth (a star has depth 1; propagation produces chains, and depth greater than 2 is difficult to produce by deployment); inter-arrival time distribution between parent and child installs (regular and clustered at scheduling boundaries for rollouts, irregular and hands-on-keyboard-paced for propagation); cross-boundary edge fraction (share of edges crossing subnet, site, business unit or management scope); the share of endpoint nodes that are unmanaged or absent from the asset inventory; whether the component is still growing at scoring time; and the relay or instance identifier reputation, including whether it appears in the authorised register at all.
  Scoring approach - Keep it interpretable. A weighted additive score over the features above, with instance identity as a hard pre-filter, will outperform a learned model at this data volume and, more importantly, can be explained to the person who has to act on it. Unrecognised instance identifier should dominate the score so heavily that a two-node component with an unknown relay outranks a two-hundred-node component with a known one. Reserve graph-embedding or community-detection approaches for environments with genuinely many concurrent agent tenancies, where the simple partition stops being sufficient.
  Beaconing as a corroborating signal - For each candidate component, compute the periodicity of outbound connections from its member hosts to the relay: inter-packet or inter-session interval regularity, jitter as a fraction of the interval, and payload size consistency. RMM agents legitimately beacon, so periodicity alone proves nothing — the useful comparison is BETWEEN components. Two agent populations on the same estate with materially different beacon profiles is a strong indication they are not the same deployment, and this is computable without any threat intelligence.
  Output - a ranked list of CONNECTED COMPONENTS, not of hosts. Each entry carries the instance identifier and relay, the member host list, the inferred propagation edges with their attribution confidence, the component's feature vector in plain language, and whether it is still growing. Ranking components rather than hosts is what makes this operationally different from an alert feed: the analyst is handed a candidate incident with its scope already computed, which is the expensive part of the investigation.
  Validation - Backtest against known IT rollouts, which are abundant, well-documented and make excellent labelled negatives, and against any historically confirmed rogue-agent incident as positives. Measure precision at a fixed daily review budget. Test explicitly for the failure mode that matters: a small propagation component running concurrently with a large legitimate migration. If the migration outranks the intrusion, the instance-identity partition is not being weighted hard enough.
  Relationship to the signature hunts - H306 detects the execution behaviour of a rogue ScreenConnect instance on a single host through its process lineage, and is higher precision. This model answers the different question that follows a hit: how far has it spread, which hosts are in scope, and is it still moving. Run H306 for detection and this for scoping, and use the unauthorised-instance inventory as the shared input to both.

# M043

Huntress described the rogue ScreenConnect activity they observed as worm-like, and the wording is precise about where the evidence lived. Nothing on any single machine said "worm". Each host showed a remote-access agent installing and connecting to a relay, which is what happens every day in any managed environment. The conclusion came from the pattern across hosts that had no business relationship with one another.

That is the gap this model fills. A rogue agent install and a sanctioned one are the same event with the same fields, and the information that separates them does not exist on any individual host — it exists in the relationships between installs. A managed rollout radiates from deployment infrastructure, respects the organisational boundaries its target list was built from, lands in scheduling-shaped time clusters, and terminates when the list is exhausted. A self-propagating installation radiates from whichever hosts were already connected, crosses boundaries indifferently, arrives at hands-on-keyboard pace, and keeps going. Those are graph properties: branching factor, depth, cross-boundary edge fraction, inter-arrival distribution.

One design decision carries most of the value, and it is deliberately not a machine-learning decision. Instance identity — which relay and which tenancy the agent reports to — should be a hard partition applied before any scoring, not another weighted feature. An organisation running a genuine two-thousand-host RMM migration will produce the largest, densest, fastest-growing component in the graph by a wide margin, and if instance identity is merely one signal among several, that migration will outrank a three-host intrusion every time. Partitioning first means a two-node component reporting to an unrecognised relay surfaces above a two-hundred-node component reporting to a known one, which is the correct ordering.

The output is a ranked list of connected components rather than hosts, because the scope is the expensive part of this investigation and the graph has already computed it. H306 handles detection on a single host through process lineage; this handles the question that immediately follows — how far it went, and whether it is still moving.

## Why

- The evidence for propagation is structurally absent from single-host telemetry. Every individual install looks like routine IT activity, so the judgement can only be made from relationships between hosts, which is a graph computation and not something any per-event rule can express.
- Legitimate deployment and malicious propagation overlap on every per-host field and separate cleanly on structure. Branching shape, tree depth, cross-boundary edges and inter-arrival timing are all computable from telemetry most environments already collect, and all four differ systematically between the two populations.
- Instance identity as a hard pre-filter prevents the model's most likely failure. Without it, a well-run RMM migration reliably buries a small intrusion, which is exactly the scenario in which the model most needs to work.
- Beacon-profile comparison between components gives a corroborating signal that needs no threat intelligence at all. RMM agents all beacon, so periodicity proves nothing in isolation, but two agent populations on one estate with materially different beacon profiles are demonstrably not the same deployment.
- The output is scoped incidents rather than alerts. Handing an analyst a connected component with its member hosts, its propagation edges and its growth status already computed removes the most time-consuming stage of the response, and ranking by component keeps the review budget tied to investigations rather than to events.
- Labelled data for validation is unusually easy to obtain here. Legitimate rollouts are frequent, documented and make excellent negatives, so the model can be backtested honestly rather than tuned on intuition.
