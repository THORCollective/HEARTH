title: "Scoring CloudTrail read bursts by inter-call spacing and resource breadth, then linking bursts across quiet weeks by source address rather than by a fixed correlation window"
hypothesis: >-
  An agent working through a prepared list of resources produces a call-spacing distribution no human and
  almost no application generates: dozens of identical API reads a couple of milliseconds apart from one
  role session, each one against a different resource. A fixed threshold on call count catches the largest
  version of this and misses the rest, because what counts as a burst depends on the role; the same role
  that reads two secrets a day is a different population from a deployment role that touches hundreds of
  resources an hour. So score each role session on the shape of its activity - median and minimum
  inter-call interval, distinct resources per unit time, how concentrated its reads are in one event name
  - against that role's own history. Then solve the second half of the problem the first half creates: the
  same operator returns after a fortnight, so the bursts have to be linked by source address over a window
  long enough to span the gap, not by a correlation window short enough to be cheap.

false_positive_notes: |
  Fast, broad, repetitive API reads are what cloud automation is, so the benign population is enormous and the model must be fitted per role rather than per account.
  - Infrastructure-as-code and configuration-management tooling is the dominant benign population and it is genuinely faster than any attacker. A Terraform refresh, a CloudFormation drift check or an inventory scanner will read hundreds of resources in seconds. These must be enumerated as roles, not filtered as events, and they belong in their own population with their own reference distribution.
  - Backup, tagging, cost-reporting, compliance-scanning and CSPM products behave identically to an enumeration sweep by design, and frequently run from a vendor-controlled address outside the environment. Where the vendor address is known and documented, record it; where it is not, this scoring will surface it, which is a useful inventory outcome rather than an incident.
  - SDK pagination inflates call counts without inflating resource breadth. Three thousand calls that walked one paginated result set are one logical operation. Score distinct resources rather than calls, and treat call count as a secondary feature, or paginating clients will dominate the ranking permanently.
  - Retry storms produce tight spacing with low breadth. A throttled or failing client hammers the same resource milliseconds apart. The breadth feature separates this cleanly, and errorCode separates it further; keep both or retries will read as sweeps.
  - CloudTrail timestamp resolution and delivery order are not guaranteed to be uniform across services and regions. Compute spacing within a single session and a single event name before comparing across them, and treat any negative or zero interval as a data-quality observation rather than as an infinitely fast call.
  - Cross-burst linkage by source address breaks behind shared egress. An attacker behind a cloud provider NAT and a legitimate client behind the same NAT will link to each other. Carry the ASN and whether the address belongs to a hosting provider as features, and require at least one other shared element - the same role, the same session name pattern, the same unusual user agent - before reporting two bursts as one operation.
  - A long lookback is expensive. This scoring is a scheduled aggregation, not a streaming rule, and running it daily over 90 days of CloudTrail in a query layer is the intended shape; attempting it in an alerting pipeline will either cost too much or get the window shortened until it no longer works.
notes: |
  Source reporting is Elastic Security Labs' November 13, 2026 analysis of a CyberStrikeAI server operating in four AWS accounts with credentials from eight identities between September 30 and October 16, 2026. The headline measurement is the reason for this hunt: "one server read 56 EC2 user data scripts in 141 milliseconds", which Elastic records in its timeline as a "burst at about 2.5 ms per call", noting that "the spacing is consistent with tooling working through a prepared list of instance IDs, not a person at a console" and that "all 57 calls that day came from the same assumed-role session."
  Why the spacing matters more than the count - Elastic explains what the reads were for: "each call asked for the userData attribute, the startup script attached to an instance. These scripts often hold hardcoded API keys, database credentials, bootstrap secrets, SSH keys, or certificates." A count threshold catches the large sweep. The spacing distribution catches the same behaviour at a quarter of the volume, which matters because the operator that returns will not necessarily run 56 calls again. Elastic also recorded the lower-volume version of the same shape elsewhere in the intrusion: "three GetCallerIdentity calls in one second, across three accounts."
  Why this is an Alchemy hunt and how it differs from the existing ones - [[M050]] scores Azure service principals on operation cadence and parallelism to separate agent-driven enumeration from human and CI/CD automation, and [[M068]] scores machine-speed request repair on the Azure control plane. This is the AWS instance-role and CloudTrail counterpart, a platform split in the sense of the HEARTH category rules: the identity model is different - assumed-role sessions named after instances rather than service principals - the telemetry is different, and the feature that carries the most weight here, millisecond inter-call spacing within one session, is not available in the Azure activity log at the same resolution. [[M048]] scores burst-and-iterate tempo on hosts rather than in cloud audit logs. The reference distribution this hunt consumes is built by [[B072]], and the discrete pair-based hunt it complements is [[H474]].
  Feature set, per role session - Minimum, 5th-percentile and median inter-call interval; the count of calls whose interval to the previous call is under 10 milliseconds; distinct resources touched; distinct resources per minute at the session peak; the Gini or Herfindahl concentration of calls across event names, because a sweep is one event name repeated while automation is usually a mix; ratio of successes to errorCode responses; whether the session name matches an instance ID; whether the source address is inside the environment per [[B072]]; the address's ASN and whether it is a hosting provider; and the number of distinct accounts the same address touched inside an hour.
  Scoring approach - Per role, compare the session against that role's own history using a median-absolute-deviation z-score per feature, summed. Do not assume normality: inter-call interval distributions in CloudTrail are heavily right-skewed with a long tail of idle gaps, so a mean-and-standard-deviation model will be dragged around by the tail and will under-report exactly the tight clusters this hunt exists to find. Compute the spacing features on the log of the interval. Weight distinct-resources-per-minute and the sub-10-millisecond call count most heavily, and treat raw call count as a tiebreak only.
  Interim thresholds while the per-role model is being built - Elastic published two detections that work as starting points and should be run on day one rather than waiting for the scoring to be fitted: "AWS EC2 Bulk User Data Enumeration alerts when one principal and source IP read userData from more than 20 distinct instances in 10 minutes, and AWS STS GetCallerIdentity Bulk Account Enumeration alerts when three or more distinct non-role identities call GetCallerIdentity from the same external IP and ASN in 10 minutes." Elastic describes both as "high-severity, low false positive". They are not a substitute for the scoring, because a 19-instance sweep passes both.
  The second half, which is the part most programmes get wrong - Elastic opens with it: "then it went quiet for 14 days and came back. That gap did more damage than the burst, because fixed correlation windows cannot span two weeks." Its conclusion is specific about the remedy: "medium and low severity alerts are good candidates for correlation, but only by source IP, and the correlation window needs to be flexible because AI-assisted activity is irregular. Here, 56 requests landed in 141 milliseconds, later steps came hours to days apart, and the operator returned after 14 days. A short fixed window would have split this intrusion into unrelated alerts." So the second output of this hunt is not a score but a grouping: cluster all scored sessions and alerts over 90 days by source address and ASN, and report the cluster rather than the session. In the reported case this is what made 78 individually unremarkable medium and low alerts into one intrusion - 83% of them on day one, then "a few targeted actions per day", then nothing for a fortnight, then a return visit touching a fourth account that had not appeared before.
  Sample ES|QL for the spacing feature, as a starting point to be run over a CloudTrail index and then fed into the scoring rather than alerted on directly:
  ```esql
  FROM logs-aws.cloudtrail-*
  | WHERE @timestamp > NOW() - 90 days
  | WHERE event.action == "DescribeInstanceAttribute"
  | EVAL Esql.session = MV_FIRST(aws.cloudtrail.user_identity.arn)
  | STATS Esql.call_count        = COUNT(*),
          Esql.distinct_targets  = COUNT_DISTINCT(aws.cloudtrail.request_parameters.instanceId),
          Esql.window_start      = MIN(@timestamp),
          Esql.window_end        = MAX(@timestamp)
        BY Esql.session, source.ip,
           Esql.minute = DATE_TRUNC(1 minute, @timestamp)
  | EVAL Esql.span_ms = DATE_DIFF("milliseconds", Esql.window_start, Esql.window_end)
  | EVAL Esql.mean_gap_ms = CASE(Esql.call_count > 1,
                                 Esql.span_ms / (Esql.call_count - 1),
                                 NULL)
  | WHERE Esql.distinct_targets >= 10 AND Esql.mean_gap_ms < 100
  | SORT Esql.mean_gap_ms ASC
  ```
  Every computed value here is derived in the query rather than recalled: the mean gap is the span divided by the number of intervals, which for the reported burst is 141 milliseconds across 55 intervals, or about 2.5 milliseconds per call, matching Elastic's figure. The 10-target and 100-millisecond values are deliberately looser than Elastic's published rule so that the output is a candidate population for scoring rather than an alert, and they should be replaced by the per-role percentiles from [[B072]] once that baseline exists.
  Expected, not observed by Elastic - The inter-call spacing distribution of legitimate automation in the affected accounts, and therefore any statement about how separable the two populations are in a given environment. Elastic reports the attacker's spacing precisely and states that it "points to automated tooling", and is careful that "none of this proves an LLM agent was making decisions, but it matches how an agentic platform works through a list of credentials and targets." It does not publish a comparison against the benign automation in those accounts, which is why the separation here is a locally fitted model rather than a published boundary.
  Scope - Every AWS account in the organisation, including non-production, and with a retention window that genuinely spans weeks. The hunt degrades to a count threshold if the query layer can only reach back seven days, and in that configuration it would have reported the first day of the reported intrusion and none of the rest.

# M072

Fifty-six EC2 user data scripts in 141 milliseconds. About two and a half milliseconds per call, every one of them against a different instance, all from the same assumed-role session.

That is not a person. It is not really a decision, either — it is a prepared list of instance IDs being walked. Those `userData` scripts are where bootstrap secrets, API keys, database credentials and SSH keys go to be forgotten, so walking the list is a reasonable thing for an agent to want to do.

Elastic shipped a rule for it: more than twenty distinct instances read by one principal and source address inside ten minutes. Good rule. It would also have missed a nineteen-instance sweep, and there is no reason the next operator reads fifty-six.

What does not change when the volume drops is the shape. Dozens of identical reads, milliseconds apart, each against a different resource, from one session. The useful question is not *how many* but *how close together, how broad, and how unlike this role's own history*.

Which raises the problem that fitting this per-account does not work. Terraform is faster than the attacker. A CSPM scanner reads more resources before breakfast than this intrusion did all day. The populations only separate per role, against each role's own past.

And then there is the half that most programmes get wrong, which Elastic puts in its first paragraph: after the burst, the server went quiet for fourteen days and came back.

Seventy-eight alerts. All medium or low. Sixty-five on day one, a trickle for two days, silence for a fortnight, then a return visit into a fourth account that had never appeared before. Every alert individually dismissible, and the only thing tying them together was the source address.

A one-hour correlation window would have seen four unrelated incidents. So the second output of this hunt is not a score at all — it is a grouping, by address, over ninety days.

## Why

- **Spacing survives a volume change; a count threshold does not.** The operator controls how many resources to read and does not control that an agent issues calls two milliseconds apart. Scoring the interval distribution keeps working when the next sweep is deliberately smaller, which is the obvious adaptation once published thresholds are known.
- **Breadth is the feature that separates sweeps from retries and pagination.** Tight spacing alone matches a throttled client hammering one resource and an SDK walking a paginated result. Distinct resources per minute cuts both of those out without any tuning, which is why it carries more weight here than call count.
- **The per-role reference is what makes the model usable at all.** Legitimate cloud automation is faster and broader than any attacker, so a global threshold is either blind or drowning. Comparing a session against its own role's history is the only framing where the signal exists, and it is the reason this is a scoring hunt rather than a rule.
- **Long-gap grouping is the difference between four incidents and one.** The reported operation spanned sixteen days with a fourteen-day pause. No fixed correlation window short enough to run cheaply can span that, so the linkage has to be a scheduled aggregation over a long retention period, joined on address and network rather than on identity.
- **Every alert in the reported case was medium or low, and that was correct.** A first-time `GetCallerIdentity`, a `GetSessionToken`, a `SendCommand` from a rare user — none of those deserves a high severity on its own. Waiting for a high-severity cloud alert on this behaviour is waiting for something that is not coming, and that is precisely the gap a scoring hunt fills.
