hypothesis: >-
  Beacon-interval analysis is built for implants that check in every few minutes and jitter to hide. The NIK C2 implant inverts the problem: it polls an HTTP endpoint roughly every 250 milliseconds while holding a separate TLS WebSocket open on port 443 for the actual command channel. At that cadence a single host issues on the order of 345,600 requests a day to one URI path — a rate so far above anything an interval-and-jitter model is tuned for that it falls out the bottom of the distribution rather than the top, and the near-zero variance that would normally be the tell is instead the dominant feature. Score hosts on the conjunction: an extreme request rate to a single path from one process, a long-lived TLS session to the same destination, near-zero inter-arrival variance, and a near-constant small payload size.

false_positive_notes: |
  High-rate polling is a real legitimate pattern and this model will find all of it on the first run. Expect telemetry and monitoring agents, trading and market-data clients, collaboration apps with presence channels, CI agents polling job queues, and browser-based dashboards that long-poll. Fit the rate distribution per host class and per process, not fleet-wide.
  Long-lived WebSockets are entirely normal — chat, collaboration, notification and remote-desktop products all hold them open for hours. A WebSocket alone scores nothing. What scores is a WebSocket *paired* with a separate sub-second HTTP polling loop from the same process to the same destination, which is a redundant design that legitimate software has no reason to adopt.
  Certificate pinning is a security feature and many legitimate applications pin. Where a TLS-inspecting proxy is deployed, the useful signal is not that pinning exists but that a session from an unsanctioned process *fails or bypasses* inspection while still succeeding — and that signal is only available if inspection is actually in path.
  A host behind a proxy that aggregates or coalesces requests may show a much lower observed rate than the implant's actual cadence. Fit on observed rate and treat the 250-millisecond figure from the report as the implant's design rather than as an expected measurement.
  Near-zero inter-arrival variance is the model's strongest feature and also the one most easily destroyed by the collection path. Log aggregation that rounds timestamps to the second makes the variance feature unusable, and a per-second count becomes the only available proxy. Confirm timestamp resolution before weighting this feature.
  A result where the destination resolves to a sanctioned monitoring vendor is a tuning outcome, not a finding. Allowlist on the triple of signer, image path and destination, since the image name is the field an operator controls — this implant sets its own masquerade name.
notes: |
  Platform - Windows.
  What the report states - Cisco Talos describes the implant as "a Go-based, 64-bit Windows remote access tool that grants persistent control over compromised hosts using a resilient dual-channel C2 architecture. It communicates over TLS-secured WebSockets on port 443 alongside an HTTP fallback polling loop every 250 milliseconds, protecting all traffic with AES-256-GCM encryption derived from a hardcoded seed." On resilience: "To survive takedowns, the implant routes traffic across three prioritized C2 tiers, which are runtime-updated URLs, an embedded encrypted server list, and a hardcoded fallback address."
  The polling channel in detail - "The HTTP polling channel runs independently. Every approximately 250 milliseconds, the agent collects a fresh snapshot of victim state hostname, watchdog status, local IP, username, current timestamp, and system uptime encrypts it in the same wire format and posts it to the" update endpoint. The endpoint table gives six paths: `/api/c2/update` for the reconnaissance beacon, `/api/c2/result` for command output, `/api/c2/screen` for screenshot upload, `/api/c2/file_chunk` for file exfiltration, `/api/c2/rproxy_up` for reverse proxy upstream data, and `/api/c2/ws` for the WebSocket command channel.
  Why the rate is the feature - 250 milliseconds is 4 requests a second, which is 345,600 requests in a day from a single host to a single path. Computed rather than estimated: 86,400 divided by 0.25. For comparison, the beacon intervals that interval-and-jitter detection is built around sit between 30 seconds and several minutes. A model tuned for that range does not flag this; it either discards the host as a service account or never surfaces it at all, because the anomaly is at the wrong end of the scale.
  And the variance is the corroborating feature. The report says "approximately 250 milliseconds", so there is no jitter design here — unlike a conventional beacon, where jitter is deliberately introduced to defeat exactly this analysis. A fixed sub-second cadence with near-zero inter-arrival variance is a signature of machine polling with no evasion budget spent on timing.
  Why the WebSocket matters even though it is quiet - the commands arrive over the WebSocket, and that channel carries very little volume: a command in, a result out. Volumetric analysis on bytes will rank it near the bottom. The polling loop, meanwhile, carries almost no information of value — a state snapshot the operator rarely needs. So the channel that matters is invisible to volume-based detection and the channel that is loud is nearly contentless. Pairing them is what makes the model work: neither flow is interesting alone and the combination is close to unique.
  Why TLS inspection will not help - "it is wrapped in a TLS session using a custom certificate configuration that pins to a specific certificate rather than validating against the system's certificate authority store. This prevents standard TLS interception proxies from observing traffic." So content inspection is unavailable by design, and the usable features are all metadata: rate, variance, duration, payload size, destination, and the TLS client fingerprint.
  Features to compute, per process and destination pair - score and weight rather than threshold:
  - **Request rate percentile** to a single URI path, against the fitted per-host-class distribution. Four per second sustained is the design; fit on observed rate, which a proxy may coalesce.
  - **Inter-arrival standard deviation** relative to the mean, over a rolling window. A conventional beacon with jitter produces a wide ratio; this produces a very narrow one. Weight this only where timestamp resolution is sub-second.
  - **Concurrent long-lived session to the same destination** from the same process, on port 443, with a duration measured in hours.
  - **Payload size variance** on the polling requests. The report describes a fixed field set — hostname, watchdog status, local IP, username, timestamp, uptime — so the encrypted body should be small and nearly constant in length.
  - **Destination rotation on failure**: "If the HTTP POST fails, the agent rotates to the next server address before retrying", so a host cycling through a small set of destinations after errors, rather than backing off, is scoring evidence.
  - **Distinct URI paths under one prefix** from one process. Six sibling paths under a common prefix, several of them used only once, is a different shape from a REST client.
  - **Process identity**: unsigned, in a user-writable path, or carrying a masqueraded name. The report records the implant setting its masquerade name to a system process name and renaming its binary in the Windows temp directory to impersonate a legitimate system process, so the name is adversary-controlled and must not be used as an allowlist key.
  Candidate-generation query - the cheap pass that produces the population to score. `DeviceNetworkEvents` timestamps are not reliable at sub-second resolution, so count per minute rather than attempting interval analysis here:
  ```kql
  DeviceNetworkEvents
  | where Timestamp > ago(30d)
  | where ActionType == "ConnectionSuccess"
  | summarize conns = count(), ports = make_set(RemotePort, 5),
              urls = make_set(RemoteUrl, 5), firstSeen = min(Timestamp)
          by DeviceId, DeviceName, InitiatingProcessId, InitiatingProcessFileName,
             InitiatingProcessFolderPath, RemoteIP, bin(Timestamp, 1m)
  | where conns >= 60
  | summarize minutesSustained = count(), peakPerMinute = max(conns),
              totalConns = sum(conns), processPath = any(InitiatingProcessFolderPath)
          by DeviceName, InitiatingProcessFileName, RemoteIP
  | where minutesSustained >= 10
  | order by peakPerMinute desc
  ```
  Sixty connections a minute is one a second — a deliberately low floor, because connection reuse means the observed connection count will usually be far below the request count. The `minutesSustained` filter is what separates a burst from a polling loop.
  Pairing the two channels - the scoring feature that does the real work. Both bindings are used and the window is bounded, since a join on `DeviceId` alone over thirty days correlates unrelated days:
  ```kql
  let polling = DeviceNetworkEvents
      | where Timestamp > ago(30d)
      | where isnotempty(RemoteUrl)
      | summarize reqs = count(), paths = dcount(RemoteUrl), pathSet = make_set(RemoteUrl, 8),
                  pollStart = min(Timestamp), pollEnd = max(Timestamp)
              by DeviceId, DeviceName, InitiatingProcessId, InitiatingProcessFileName, RemoteIP
      | where reqs >= 500;
  let sessions = DeviceNetworkEvents
      | where Timestamp > ago(30d)
      | where RemotePort == 443
      | summarize sessionStart = min(Timestamp), sessionEnd = max(Timestamp), flows = count()
              by DeviceId, InitiatingProcessId, RemoteIP
      | extend durationMinutes = datetime_diff('minute', sessionEnd, sessionStart)
      | where durationMinutes >= 60;
  polling
  | join kind=inner (sessions) on DeviceId, InitiatingProcessId, RemoteIP
  | project DeviceName, InitiatingProcessFileName, RemoteIP, reqs, paths, pathSet,
            durationMinutes, pollStart, pollEnd
  | order by reqs desc
  ```
  One process, one destination, hundreds of requests, *and* a session to the same destination open for an hour or more. That conjunction is the model's core and is what no single-channel analysis expresses.
  Inter-arrival variance, where the data supports it - this needs a proxy or Zeek with sub-second timestamps, not Defender. Compute the mean and standard deviation of inter-arrival gaps per process-destination pair over a rolling ten-minute window, and score on the ratio. A conventional jittered beacon produces a coefficient of variation in the tens of percent; fixed machine polling produces a small fraction of that. Where the collection path rounds to the second, drop this feature rather than computing it on rounded values — a rounded series will look perfectly regular regardless of what the implant actually did, which manufactures the result the model is looking for.
  Indicators from the report - the observed server is `87.120.196[.]120` resolving `total-sitevv[.]lol`, with a TLS certificate whose serial is `7d16381a9de823943b5a0987dbd0f26edf22052b`, JARM `28d28d28d00000000042d42d0000001f361a1bf80ed39a1e352adeb016a07b`, and Common Name `nik-panel` — a value Talos notes "matches strings embedded within the implant binary". The agent identifier format is given as `ag_` followed by sixteen hexadecimal characters. The embedded build path is `/opt/nik_panel/data/build_52b79724a1fc4b8f/main.go`.   A note on the JARM and certificate values - these are infrastructure indicators with a short shelf life and are listed for retrospective search rather than as the basis of the hunt. The scored shape is what survives the operator moving hosts.
  Expected, not observed by Talos - the report gives no payload sizes for the polling requests, no measured inter-arrival distribution, and no observed daily request volume, so the 345,600 figure above is arithmetic from the stated 250-millisecond cadence rather than a measurement, and the payload-size-variance feature is derived from the stated field list rather than from reported byte counts. Talos does not say whether the polling cadence changes while a WebSocket is connected, nor whether it backs off under error conditions beyond rotating to the next address; both would materially change the fitted distributions, so the model should be refitted against whatever a confirmed host actually produces. The AES key is reported as derived from the seed; this hunt does not depend on either value.

# M065

Every beacon-detection model in production assumes the implant is trying to be quiet. Interval-and-jitter analysis, periodicity scoring, Fourier methods on connection timing — all of them are tuned for a check-in somewhere between thirty seconds and a few minutes, with deliberate jitter layered on to break the pattern. The NIK C2 implant does the opposite and gets the same result.

Cisco Talos describes a "resilient dual-channel C2 architecture" where the implant "communicates over TLS-secured WebSockets on port 443 alongside an HTTP fallback polling loop every 250 milliseconds". Four requests a second. Sustained, that is 345,600 requests to a single URI path from a single host in a day. A model looking for suspicious regularity in the thirty-second-to-five-minute band does not rank that highly — it discards it as a service, or never generates the candidate at all.

The second inversion is about where the information is. The loud channel carries nothing much: the polling POST sends "a fresh snapshot of victim state hostname, watchdog status, local IP, username, current timestamp, and system uptime", which an operator barely needs. The commands ride the WebSocket, which is nearly silent in volume terms — a command in, a result out. So volumetric ranking points at the contentless channel and byte-count analysis buries the one that matters.

Content inspection is off the table too. The WebSocket is "wrapped in a TLS session using a custom certificate configuration that pins to a specific certificate rather than validating against the system's certificate authority store. This prevents standard TLS interception proxies from observing traffic."

What is left is metadata, and metadata is enough — because the redundancy that makes this implant resilient is also what makes it distinctive. Legitimate software picks one transport. An agent that holds a WebSocket open to a destination *and* polls the same destination over HTTP four times a second is spending bandwidth to survive takedowns, and nothing with a product manager behind it is built that way. Score the pair: extreme request rate to one path, near-zero inter-arrival variance, a concurrent hours-long session to the same destination, and a near-constant small payload.

One caveat that belongs in the model rather than the write-up: the variance feature is only real if the collection path preserves sub-second timestamps. Log aggregation that rounds to the second will make any series look perfectly regular, which produces exactly the finding the model is hunting for and none of the evidence.

## Why

- The cadence is outside the range every deployed beacon model is tuned for, so this implant evades periodicity detection by being too fast rather than too irregular — and the sign of the anomaly is the opposite of what those models look for.
- The informative channel is the quiet one. Volumetric and byte-count ranking will surface the polling loop, which carries a state snapshot of little value, and will rank the WebSocket carrying actual tasking near the bottom.
- Certificate pinning removes content inspection by design, which is stated in the vendor analysis rather than inferred, so the hunt has to be built on metadata features from the outset.
- The redundancy is the signature. Two concurrent transports to one destination from one process is a deliberate anti-takedown design with no legitimate analogue, and it is only visible if the two flows are joined rather than analysed separately.
- Destination rotation on failure replaces exponential backoff. A host that cycles through a short list of addresses after errors instead of slowing down is behaving like an implant with a tiered server list, which is exactly what the report describes.
- Timestamp manipulation closes off the usual shortcuts. With PE timestamps zeroed and filesystem times set to a 1979 epoch artefact across every sample, file-time ordering cannot establish a timeline — so network-side behaviour is not just one option for finding these hosts, it is the one that still works.
