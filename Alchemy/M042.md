title: "Scoring Entra ID sessions on network-provenance discontinuity to surface adversary-in-the-middle relay without user-agent signatures"
hypothesis: >-
  An adversary-in-the-middle relay produces a geometric anomaly that no single log line contains: one
  authenticated session is used from two populations of network infrastructure that a real user cannot
  simultaneously occupy. The victim's genuine traffic arrives from corporate egress or a familiar
  consumer ISP; the operator's replayed traffic arrives from a residential-proxy resale range or a
  cheap cloud host, often in a different country and a different ASN class, minutes later. Static rules
  for this fail in both directions — a fixed "two countries in one hour" threshold drowns in VPN users
  and travellers, and an allowlist of scripted user agents is defeated by an operator who copies a
  browser string. Model it instead: build a per-user distribution of network provenance from historical
  sign-ins, then score each session on how improbable its observed provenance mix is for THAT user,
  weighted by the infrastructure class of the anomalous leg. The output is a ranked queue of sessions,
  not an alert, and it detects the relay by its shape rather than by any string the attacker chooses.

false_positive_notes: |
  A provenance model has a large and genuinely legitimate anomalous population, and it must be designed so that these land as LOW scores rather than as suppressed alerts. The main sources: corporate VPN and split-tunnelling, where a user's traffic legitimately alternates between the VPN concentrator ASN and their home ISP within one session — this is the single largest contributor and must be handled by learning the organisation's own VPN ranges as a named class, not by learning them per user; business travel and relocation, which produce sustained rather than momentary provenance shifts and are separable on duration; mobile users whose carrier NAT reassigns them across ASNs mid-session; cloud desktop, VDI and remote browser isolation products that legitimately place a user's session in hosting ASN space permanently; third-party SaaS integrations and security or DLP vendors that access M365 on a user's behalf from cloud ranges; and international organisations where cross-border access is the norm rather than the exception. Two design choices prevent these from dominating the queue. First, score against the PER-USER distribution rather than an organisational threshold, so a consultant who has connected from eleven countries this quarter is not flagged for a twelfth while a user who has only ever connected from one office is flagged for their second. Second, weight by infrastructure CLASS rather than by geographic distance — a corporate-to-VPN transition should carry almost no weight regardless of the country change, while any transition into a residential-proxy or proxy-resale range should carry heavy weight regardless of how close it is, because that class of infrastructure has effectively no legitimate enterprise use case. Expect the first two weeks of output to be dominated by VPN and travel; that period is the calibration phase, and the correct response is to enrich the class labels, not to raise the threshold. Note also that geo-IP is imprecise enough that country-level inference produces spurious "impossible travel" on its own, which is why ASN and infrastructure class carry the model rather than location.
notes: |
  Why this is modelled rather than ruled - Three properties of the behaviour defeat static detection. The relayed token is MFA-satisfied, so every authentication-quality field looks correct. Neither the IP change nor the device change is reflected in the token request, so the deltas a rule would test are frequently absent from the record entirely. And the legitimate anomalous population (VPN, travel, mobile NAT, VDI) overlaps the malicious one on every field except infrastructure class and per-user rarity, which are distributional properties rather than per-event ones. A per-user probabilistic score is the smallest construction that captures both.
  Feature set - Per session (grouped by `SessionId` or correlation identifier, spanning both interactive and non-interactive events) compute: the set of distinct ASNs observed and the count; the set of distinct infrastructure CLASSES observed; whether any leg falls in a residential-proxy, proxy-resale, hosting or Tor class; the per-user historical frequency of each observed ASN (a Bayesian smoothed estimate, so a never-before-seen ASN gets a defined probability rather than zero); the per-user historical frequency of each infrastructure class; time delta between the first and last leg; the count of distinct countries and the minimum implied velocity between consecutive legs; whether the session includes both interactive and non-interactive events and whether the non-interactive leg originates from a different ASN than the interactive one; user-agent class consistency across legs; whether the resource application set for the session is novel for that user; and the `AuthenticationRequirement` and `ConditionalAccessStatus` of each leg.
  The highest-weight single feature - the INTERACTIVE-TO-NON-INTERACTIVE PROVENANCE SPLIT. In a normal session the interactive sign-in and the subsequent non-interactive token refreshes come from the same network. In a relay, the interactive leg is the victim and the non-interactive legs are the operator, so the split falls exactly along that boundary. Computing the probability that a user's non-interactive traffic originates from an ASN never seen in their interactive traffic is a narrowly targeted feature that maps directly onto the attack's structure, and it is the feature most worth implementing first if the full model is out of reach.
  Modelling approach - Start with a per-user categorical model over ASN and infrastructure class with additive (Laplace) smoothing, producing a negative-log-likelihood surprise score per session leg, then aggregate per session with a max-plus-mean combination so that one extremely improbable leg is not diluted by many ordinary ones. Multiply by a class-risk weight: proxy-resale and Tor highest, commercial VPN and hosting moderate, consumer ISP low, known corporate and owned-cloud near zero. This is deliberately a simple, inspectable model — an analyst must be able to read WHY a session scored, because the output feeds a human review queue. Only move to isolation forest, a Gaussian mixture over embedded features, or a sequence model once the categorical baseline is calibrated and its failure modes are understood; the added accuracy is small relative to the loss of explainability at this stage.
  Cold start and population guards - Users with fewer than the minimum history days, newly created accounts, and shared or service identities must be routed to a separate rule-based path rather than scored, because a sparse distribution makes almost everything look surprising. Conversely, cap the influence of very high-volume identities so that a single automation account cannot dominate the queue.
  Output and thresholds - Emit a RANKED QUEUE with a fixed review budget (for example the top 20 sessions per day) rather than a fixed score threshold. A fixed threshold silently changes in sensitivity as the population drifts; a fixed budget keeps analyst load constant and makes precision directly measurable. Each queue entry must carry the score, the top three contributing features in plain language, the ASN and class of each leg, and the per-user historical frequency of the anomalous ASN — the last of these is what lets an analyst close a benign case in seconds.
  Validation - Label historically confirmed AiTM compromises and confirmed-benign VPN and travel sessions, and measure precision at the review budget rather than ROC AUC, which is misleading at this class imbalance. Re-fit the per-user distributions on a rolling window so that a genuine relocation is absorbed within a couple of weeks instead of alerting indefinitely. Test explicitly against the evasion that matters: score a synthetic session in which the operator's user agent perfectly mimics the victim's browser, and confirm the model still ranks it — if it does not, the user-agent features are carrying too much weight and the provenance features too little.
  Relationship to the signature-based hunts - H302 hunts the same campaign through the replay engine's `python-requests` user agent and the `Dsreg/` device registration that follows. That hunt is higher precision and should run first; this model exists for the operator who does not leave a library string behind. In the Knight Office campaign the geometry was consistent even where the strings were not — callbacks fronted through Comcast residential space flagged by Spur as a resale operator, token replay from Tencent Cloud ranges — which is the shape this model learns rather than the addresses.

# M042

The Knight Office campaign gave defenders a gift in the form of a `python-requests/2.34.2, OAuth2:Token` user-agent string sitting in the non-interactive sign-in log, and H302 hunts exactly that. The problem with building a programme on it is that it is one line of code away from disappearing. An operator who sets a browser user agent on the replay engine removes the entire signature, and the environment goes dark on a technique that already bypasses multi-factor authentication by design.

What that operator cannot easily remove is the geometry. An adversary-in-the-middle relay necessarily involves two parties using one authenticated session from two different places. The victim's traffic arrives from wherever the victim actually is — corporate egress, a home ISP, a mobile carrier. The operator's traffic arrives from the infrastructure they rented, which in this campaign meant residential-proxy resale ranges for callbacks and cheap cloud hosting for the replay itself. Those two populations are distinguishable not by distance but by kind, and in a relay they split along a specific and structurally meaningful boundary: the interactive sign-in belongs to the victim, and the non-interactive token refreshes belong to the operator.

That split is the feature worth building around, and it is why this belongs in Alchemy rather than Flames. A static rule cannot express it. "Two countries in an hour" flags every VPN user and every traveller and misses a relay operating from the same country. "Non-browser user agent" is defeated by a string change. What works is a per-user distribution — how improbable is this particular provenance mix for *this* user — weighted by infrastructure class, because a corporate-to-VPN transition should count for almost nothing while any transition into proxy-resale space should count heavily regardless of geography. The model is deliberately kept simple and inspectable: a smoothed categorical distribution over ASN and class, a surprise score, a class-risk weight, and a fixed daily review budget instead of a threshold. An analyst has to be able to read why a session ranked, because the output is a queue for humans, not an alert.

## Why

- The signature this campaign happened to leave is one configuration change from vanishing. Building detection solely on the replay engine's user-agent string creates coverage that expires the moment an operator decides to mimic a browser, on a technique that already defeats MFA.
- Every authentication-quality field looks correct during token replay, so the fields an analyst or a rule would normally test carry no signal. Neither the IP change nor the device change is reflected in the token request, which forces detection onto distributional properties rather than per-event ones.
- The legitimate anomalous population overlaps the malicious one almost completely on the obvious axes. VPN users, travellers, mobile NAT and VDI all produce multi-ASN sessions, which is precisely why a fixed organisational threshold fails in both directions and a per-user distribution is the smallest construction that separates them.
- Infrastructure class carries information that geography does not. Residential-proxy resale ranges have effectively no legitimate enterprise use case, while a cross-border corporate VPN hop is routine — so weighting by kind rather than by distance inverts the usual impossible-travel logic in a way that matches how these operations are actually provisioned.
- The interactive-versus-non-interactive provenance split maps directly onto the structure of a relay, where one leg is the victim and the other is the operator. That makes it a narrowly targeted feature rather than a generic anomaly signal, and it is implementable on its own if the full model is out of reach.
- A ranked queue with a fixed review budget keeps analyst load constant and makes precision measurable, which is what allows an anomaly detection of this kind to survive contact with an operational SOC instead of being tuned into irrelevance.
