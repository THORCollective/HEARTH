id: M063
category: Alchemy
title: "Scoring API clients against the mobile app population — finding the reimplemented client that signs requests correctly because it extracted the key from the APK"
hypothesis: >-
  When an API trusts a request signature computed inside a mobile application, the only thing standing between an attacker and the production API is the secrecy of a key shipped to every device that installs the app. Once that key is extracted, the attacker's own client produces signatures that verify, so every authentication and authorization check the server performs returns a pass. Nothing about the individual request is wrong. What is wrong is the client: a reimplemented script does not carry the app's TLS stack, does not emit the SDK's exact header set, does not perform the launch sequence the app performs before it reaches a data endpoint, does not pause the way a person tapping a screen pauses, and does not arrive from a mobile carrier network. None of those differences is decisive on its own and none is expressible as a rule, because each varies legitimately across devices, versions and regions. Scored together against the distribution of the real app population per endpoint, the reimplemented client separates cleanly.

false_positive_notes: |
  Legitimate non-app clients exist in almost every estate and will score highly. Internal test harnesses, partner integrations, synthetic monitoring, load tests and the organization's own QA automation all talk to production APIs without being the app. Enumerate and label them before scoring; they are the single largest source of high scores and they are stable, so labelling them once is durable.
  Old and modified app builds look partly reimplemented. Users on long-outdated versions ship old SDKs with different header sets, and rooted or instrumented devices alter TLS stacks. Keep released-version context in the model so a stale-but-real version scores differently from a version string that was never released.
  Corporate and VPN egress breaks the network-provenance term. Users on enterprise Wi-Fi, VPNs or privacy relays arrive from datacenter ASNs legitimately, which is why connection type must be one scored term among several rather than a filter. In regions where carrier-grade NAT dominates, the term carries less signal and should be weighted down for that region.
  TLS fingerprints are not stable forever. OS upgrades, library updates and new device models change JA4 values on a normal cadence, so a fingerprint not seen before is weak evidence by itself. Score novelty against the population rather than against an allowlist, and expect a step change in novel fingerprints after a major mobile OS release.
  A perfectly emulated client will score low, and this model does not claim otherwise. An attacker who replays the app's exact header set from a mobile-carrier address at human-like intervals defeats every term here. That is the case for fixing the authorization model rather than detecting the client, which is what the source report actually recommends.
  High score is not abuse. These requests are correctly signed and may be authorized; the model ranks clients for review, and the confirmation is whether the identity's data access makes sense for that account, not the score.
notes: |
  Platform - The API backend and its edge, on Linux or a managed gateway. This is a server-side model; nothing is collected from mobile devices beyond attestation the application already performs.
  What JPCERT/CC observed - The October 2026 investigation into attack infrastructure behind unauthorized-access incidents in Japan found that "One notable characteristic of these attacks was that the attackers analyzed Android application packages (APK files) to identify APIs and exploit them". On one server the team found APK files alongside Blutter, for reverse-engineering Flutter applications, and jadx, for analyzing Android applications, with directories such as `apk_extract/` and filenames such as `strings_libapp.txt` suggesting extraction of strings from native libraries.
  The appendix states the outcome that defines this model. Analysis of a real Flutter application's `libapp.so` "revealed an embedded RSA private key, API authentication mechanisms, and the logic used to generate request signatures", and the request-signing process was reproduced, "enabling a standalone Python client to access the production API without using the legitimate application". JPCERT/CC's recommendations name the defensive consequence directly: "Do not rely solely on request-signing mechanisms or code obfuscation within the application", and "Account for the possibility that the API may be accessed by clients other than the legitimate application."
  Why this has to be a model - The signature verifies. Every rule a gateway can express about the request itself - is it signed, is the signature correct, is the identity known, is the endpoint permitted - returns a pass, because the attacker holds the same key the app holds. The discriminating information is not in any single request but in how this client's behaviour compares to the population of real app installs, and every one of those comparison terms varies legitimately: header sets differ by app version, TLS fingerprints differ by device and OS, timing differs by user, and network type differs by region. A static threshold on any one term is simultaneously too tight for a region on carrier-grade NAT and too loose for a datacenter-hosted script, which is what makes this model-assisted rather than rule-based.
  Scoring terms - Compute per authenticated identity, per endpoint, over a rolling window. Each term is a comparison against the legitimate population for that endpoint, not an absolute:
  1. `FingerprintRarity` - the fraction of the endpoint's traffic sharing this client's JA4 value. Real app installs cluster into a modest number of fingerprints by OS and device generation; a reimplemented client in a scripting language sits in a fingerprint bucket of one.
  2. `HeaderDivergence` - the edit distance between this client's header set and order and the modal header profile for the app version it claims. SDKs emit a stable, ordered set; hand-built clients send a minimal set and in a different order.
  3. `BootstrapAbsence` - whether the identity reached a data endpoint without the launch sequence the app performs first. A real client fetches configuration, feature flags and session state before it can reach most data; a script requests the data endpoint alone.
  4. `TimingRegularity` - the coefficient of variation of inter-request intervals. Human interaction is irregular and bursty; automation is periodic even when it is deliberately slowed.
  5. `ProvenanceMismatch` - whether the source ASN is a datacenter or hosting network rather than a mobile carrier, weighted per region to account for VPN and corporate egress.
  6. `VersionImplausibility` - whether the claimed app version was ever released, and whether its claimed SDK matches the headers actually sent. A client that pins a version string it read out of the binary will drift from the released set over time.
  7. `AccessBreadth` - the number of distinct object or record identifiers this identity requested, against the endpoint's own distribution. Extraction looks like enumeration regardless of how well the client is disguised.
  Combining and thresholding - Rank identities by a weighted sum, with `FingerprintRarity`, `BootstrapAbsence` and `AccessBreadth` carrying the most weight because they are the hardest for an attacker to fix without reimplementing the app wholesale. Score high when any three terms exceed the endpoint's 99th percentile in the same window, and treat `AccessBreadth` above the 99.9th percentile as sufficient on its own. Derive every percentile per endpoint and per region from the population; do not import a threshold from another deployment, because the shape of a login endpoint's client population is nothing like that of a bulk-export endpoint.
  Starting query, the population shape - Build the per-endpoint client distribution first; the model is meaningless before this exists:
  ```kql
  let window = 30d;
  let traffic = ApiGatewayLogs
      | where TimeGenerated > ago(window)
      | where isnotempty(ClientIdentity) and isnotempty(Endpoint);
  traffic
  | summarize requests = count(), identities = dcount(ClientIdentity),
              share = count() * 1.0 / toscalar(traffic | count())
          by Endpoint, Ja4Fingerprint, AppVersion
  | order by Endpoint asc, requests desc
  ```
  Both bindings are used. The fingerprints with a meaningful `share` are the real app population for that endpoint; everything in the long tail is the candidate set for the remaining terms.
  Candidate query, rarity and breadth together - The two strongest terms, computed per identity:
  ```kql
  let window = 30d;
  let endpointTotals = ApiGatewayLogs
      | where TimeGenerated > ago(window)
      | summarize endpointRequests = count() by Endpoint;
  let fingerprintTotals = ApiGatewayLogs
      | where TimeGenerated > ago(window)
      | summarize fpRequests = count() by Endpoint, Ja4Fingerprint;
  let perClient = ApiGatewayLogs
      | where TimeGenerated > ago(window)
      | summarize requests = count(), objects = dcount(ObjectId),
                  firstSeen = min(TimeGenerated), lastSeen = max(TimeGenerated),
                  asns = make_set(SourceAsn, 5), versions = make_set(AppVersion, 5)
              by ClientIdentity, Endpoint, Ja4Fingerprint;
  perClient
  | join kind=inner (fingerprintTotals) on Endpoint, Ja4Fingerprint
  | join kind=inner (endpointTotals) on Endpoint
  | extend fingerprintShare = fpRequests * 1.0 / endpointRequests
  | extend span = lastSeen - firstSeen
  | where fingerprintShare < 0.001
  | summarize arg_max(objects, *) by ClientIdentity
  | project ClientIdentity, Endpoint, Ja4Fingerprint, requests, objects,
            fingerprintShare, asns, versions, span
  | order by objects desc
  ```
  The `0.001` share cut is a starting value for isolating the long tail, not a tuned threshold; set it from where the endpoint's own fingerprint distribution actually falls away. Every `let` is used. The fingerprint total is computed in its own binding rather than inside the per-client aggregation, because a count taken inside a group keyed on `ClientIdentity` would only ever equal that client's own request count and the share would collapse to one.
  Timing-regularity term - Compute the coefficient of variation of inter-request gaps per identity. A value near zero is machine-paced; real app traffic sits well above it. `prev()` over a time-ordered partition gives the gaps, and identities with fewer than roughly thirty requests should be excluded because the statistic is unstable on small samples.
  What a confirmed hit means - The extracted secret is a shared key present in every installed copy of the application, so it cannot be revoked for one attacker. Confirmation therefore triggers an application release and a server-side change, not a credential reset: move authorization to the server as the report advises, so that holding the signing key proves only that a request was formed by some copy of the app and never that the caller may read a given record. In the interim, rate limiting per identity and per object-enumeration pattern reduces the extraction rate without fixing the flaw.
  Scope note on the endpoint inventory - The endpoints at risk are those reachable by the mobile client, which is frequently a superset of the documented web API. Build the inventory from the app's own API surface, by the same decompilation route the attackers used, rather than from the public documentation. An endpoint nobody on the defending side knows exists cannot be in the model.
  Reference indicators - JPCERT/CC lists three attack-server addresses in its appendix: `210.149.87[.]120`, `118.26.36[.]16` and `69.10.51[.]162`. These identify infrastructure from that investigation and are useful for retrospective log searches, but the model deliberately does not depend on them, since a reimplemented client can be run from anywhere.
  Adjacent coverage - [[H426]] covers the SSRF redirect bypass found on the same attack servers, against endpoints located by the same APK analysis, and the two hunts share an endpoint inventory. [[M062]] scores credential-store breadth on endpoints and is the host-side analogue of breadth scoring; this model scores client identity against a population rather than process behaviour against a host. No existing HEARTH hunt covers mobile application reverse-engineering or API client fingerprinting; a search of the corpus for APK, Flutter and mobile-application analysis returns nothing, which is why this is a new model rather than an extension.

# M063

JPCERT/CC published an investigation in October 2026 into the infrastructure behind a series of unauthorized-access incidents in Japan involving the leakage of personal information. Examining attacker-controlled servers, the team found APK files sitting alongside Blutter and jadx — tools for reverse-engineering Flutter and Android applications — with directories such as `apk_extract/` and files such as `strings_libapp.txt`. The characteristic the report leads with is that "the attackers analyzed Android application packages (APK files) to identify APIs and exploit them".

The appendix explains what that yields. Analysis of a real Flutter application's `libapp.so` "revealed an embedded RSA private key, API authentication mechanisms, and the logic used to generate request signatures", and reproducing the signing process was "enabling a standalone Python client to access the production API without using the legitimate application".

That last clause is the entire detection problem. The attacker's client signs requests with the application's real key, so the signature verifies. Every control a gateway can apply to the request — is it signed, is the signature valid, is the identity known, is the endpoint allowed — returns a pass, because these are not forged requests. They are genuine requests from an illegitimate client. JPCERT/CC's recommendations say so plainly: "Do not rely solely on request-signing mechanisms or code obfuscation within the application", and defenders should "Account for the possibility that the API may be accessed by clients other than the legitimate application."

What remains is the client, and the client is where a reimplementation shows. A Python script does not carry the app's TLS stack, does not emit the SDK's exact ordered header set, does not run the configuration and session calls the app makes before it can reach a data endpoint, does not pause the way a person tapping a screen pauses, and usually does not arrive from a mobile carrier network. Every one of those signals also varies legitimately — by app version, device generation, user, region and corporate egress — which is why none of them can be a rule. Scored together against the real population for a given endpoint, the long tail that contains the reimplemented client is small and reviewable.

The remediation this model points at is not a detection. A key extracted from an application is present in every installed copy and cannot be revoked for one holder, so the fix is the one the report recommends: authenticate and authorize on the server, and stop treating possession of the signing key as evidence of anything beyond the request having been formed by some copy of the app.

## Why

- Rule-based controls are structurally blind here, because the requests are correctly signed. This is not a tuning problem that a better signature check solves; it is a case where the only remaining information is distributional, which is what makes a model the right instrument.
- Every candidate signal varies legitimately across the real population. Header sets change with app version, TLS fingerprints change with device and OS, timing changes with the user, and network type changes with region and VPN use, so each has to be scored against that endpoint's own distribution rather than compared to a fixed value.
- Access breadth survives a good disguise. An attacker who perfectly emulates the client still has to enumerate records to extract data, and per-endpoint breadth percentiles catch the objective even when the client fingerprint does not.
- The population baseline has independent value. Knowing which client fingerprints, versions and networks legitimately reach each endpoint is also the inventory needed to retire old app versions safely and to spot partner integrations nobody documented.
- The endpoints at risk are frequently ones defenders have not inventoried. Attackers enumerate them by decompiling the mobile app, so the authoritative endpoint list comes from the app package rather than from API documentation, and a model built only over documented endpoints will miss the ones that were actually reached.
