title: "Ransomware that encrypts nothing: mshta.exe relaunching a locally generated HTML lock screen in a five-second batch loop, with a SystemLock Run key and the MBR copied out first"
hypothesis: >-
  An operator who wants payment without the cost and noise of file encryption can take the screen instead. The NIK C2 implant builds a self-contained HTML ransom page at runtime from a hardcoded template, writes it to the Windows temp directory, writes a batch file that launches it with `mshta.exe` inside an infinite loop with a five-second timeout, and registers an `HKCU` Run key so it returns at every logon. Before any of that, it reads the first sector of `\\.\PhysicalDrive0` through PowerShell and saves it as a backup file. Because no files are encrypted, every control and every triage habit built around mass file modification reports clean — so the hunt has to key on the generation and relaunch machinery instead: a raw physical-drive read, an HTML file created in a temp directory and immediately opened by `mshta.exe`, and a `cmd.exe` parent restarting it on a five-second cadence.

false_positive_notes: |
  `mshta.exe` opening a local HTML file is used by a long tail of legitimate installers, OEM tooling and internal line-of-business applications, and HTA is still a supported application format. The discriminators are the location (a temp directory), the age of the target (created seconds before), and the parent (`cmd.exe` in a loop rather than an installer or a shortcut).
  Backup, imaging and disk-utility software legitimately reads `\\.\PhysicalDrive0`, and so do some endpoint agents and partitioning tools. Those are signed, installed, and run on a schedule. An unsigned or recently-arrived process, or a PowerShell session, doing the same read is a different population.
  `HKCU` Run key writes are extremely common on a managed fleet. The useful filter is the *value*: a `cmd /c` invocation pointing at a `.cmd` or `.bat` file in a temp directory has very few legitimate producers.
  A five-second relaunch cadence will also match some legitimate watchdogs and kiosk-mode shells. Scope by host class: a kiosk or digital-signage estate will produce this legitimately and a user fleet will not.
  Do not expect the usual ransomware evidence, and do not treat its absence as a clear. The report is explicit: "It does not encrypt any files, which means it leaves no forensic trail of file modification timestamps or encryption markers." Mass-file-modification detections, canary files and backup-deletion alerts will all be silent on a host that is fully locked.
  The MBR read and the lock screen are separate operator-driven steps in the report's description, so a host may show one without the other. Treat each as sufficient to investigate on its own rather than requiring both.
notes: |
  Platform - Windows.
  What the report states - Cisco Talos describes NIK C2 as "a new AI-integrated command-and-control (C2) framework in the wild", with a "Go-based, 64-bit Windows remote access tool" implant. The destructive module is listed in the command-surface table under "Boot Ransomware" as: "Master Boot Record raw backup via PowerShell disk read and Screen-locking ransomware via LOLbin, registry persistence, crypto payment demand."
  The sequence, from the report - first the MBR step: the module "executes PowerShell to execute a raw disk copy command that reads directly from the physical drive device path" and "writes the first sector, which is Master Boot Record (MBR), to a file named" a backup file "in the Windows temporary directory." Then the page: "the module constructs a complete self-contained HTML lock screen code entirely at runtime from a hardcoded format string, parameterized with actor supplied Bitcoin and USDT wallet addresses, prices, contact email, timer duration, and custom text from the C2 command message, allowing the actor to fully customize the ransom demands."
  Then the relaunch loop, which is the most hunt-friendly sentence in the report: "It then generates a Windows batch script that calls mshta.exe with the path to the HTML file, followed by an infinite loop construct with a five-second timeout between iterations, ensuring that if the user somehow closes the window it reopens within five seconds." The artefact names Talos recovered are `lock_screen.html`, `lock_start.bat`, `mbr_backup.bin` and a Run key named `SystemLock`. The Run key is written with a `reg add` command "under the current user's autostart path, pointing to a" `cmd /c` "invocation of the batch file, so the lock screen is executed on every user's logon." And on top of the Run key: "Additionally, a background goroutine is spawned that continuously monitors and relaunches the lock screen process."
  Why this defeats ransomware detection as usually built - Talos sets out the design rationale: "It does not encrypt any files, which means it leaves no forensic trail of file modification timestamps or encryption markers. It relies entirely on a screen lock, which is considerably faster to deploy than a file encryption ransomware." Nearly all deployed ransomware detection is built on mass file modification, entropy change, shadow-copy deletion or canary-file access. None of those occur. What does occur is `mshta.exe` execution, a temp-directory HTML write, a registry Run key, and a raw disk read — four events that are individually unremarkable and jointly specific.
  Primary query - mshta opening a freshly created local HTML file. The age of the target is the discriminator, so this joins the file write to the execution inside a bounded window; a join on `DeviceId` alone over a long lookback correlates unrelated days:
  ```kql
  let htmlWrites = DeviceFileEvents
      | where Timestamp > ago(30d)
      | where ActionType in ("FileCreated", "FileRenamed", "FileModified")
      | where FileName endswith ".html" or FileName endswith ".htm" or FileName endswith ".hta"
      | where FolderPath has_any (@"\Temp\", @"\AppData\Local\Temp", @"\Windows\Temp")
      | project WriteTime = Timestamp, DeviceId, DeviceName, HtmlPath = FolderPath,
                HtmlName = FileName, Writer = InitiatingProcessFileName,
                WriterPath = InitiatingProcessFolderPath;
  let mshta = DeviceProcessEvents
      | where Timestamp > ago(30d)
      | where FileName =~ "mshta.exe"
      | project ExecTime = Timestamp, DeviceId, MshtaCmd = ProcessCommandLine,
                Parent = InitiatingProcessFileName, ParentCmd = InitiatingProcessCommandLine;
  htmlWrites
  | join kind=inner (mshta) on DeviceId
  | where ExecTime between (WriteTime .. WriteTime + 5m)
  | where MshtaCmd has HtmlName
  | project WriteTime, ExecTime, DeviceName, HtmlPath, HtmlName, Writer, WriterPath,
            MshtaCmd, Parent, ParentCmd
  | order by ExecTime desc
  ```
  The relaunch cadence - this is what separates a one-off HTA from a lock screen. Count `mshta.exe` starts per device per minute; a five-second loop produces roughly twelve starts a minute and keeps producing them:
  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where FileName =~ "mshta.exe"
  | summarize starts = count(), cmds = make_set(ProcessCommandLine, 3),
              parents = make_set(InitiatingProcessFileName, 3)
          by DeviceId, DeviceName, bin(Timestamp, 1m)
  | where starts >= 6
  | order by starts desc
  ```
  Six per minute is a deliberately generous floor: the loop waits five seconds *between* iterations, so the observed rate depends on how long the page stays open before the user closes it, and on a host where the user is not fighting the window there may be only one long-lived process. Treat a high count as strong evidence and a low count as uninformative rather than exculpatory.
  The batch file and the Run key. Note that a `.cmd` or `.bat` file is never a process `FileName` — batch scripts run under `cmd.exe` — so the script has to be hunted as a file write and as a `cmd.exe` command-line operand, never as a process name:
  ```kql
  DeviceRegistryEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("RegistryValueSet", "RegistryKeyCreated")
  | where RegistryKey has @"\Software\Microsoft\Windows\CurrentVersion\Run"
  | where RegistryValueData has_any (".cmd", ".bat", "mshta", @"\Temp\")
  | project Timestamp, DeviceName, InitiatingProcessAccountName, RegistryKey,
            RegistryValueName, RegistryValueData,
            InitiatingProcessFileName, InitiatingProcessCommandLine
  | order by Timestamp desc
  ```
  The raw disk read. Reading the first sector of the physical drive is the step that happens *before* the lock and is therefore the earliest warning, and it is also the one a `DeviceEvents` `PowerShellCommand` query cannot find — that ActionType holds cmdlet *names* such as `Get-Content` or `New-Object`, never script text or device paths. Use 4104 `ScriptBlockText` for the content, and process command lines for the invocation:
  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where ProcessCommandLine has_any (@"\\.\PhysicalDrive", @"\\.\physicaldrive")
  | project Timestamp, DeviceName, AccountName, FileName, FolderPath, ProcessCommandLine,
            InitiatingProcessFileName, InitiatingProcessCommandLine
  | order by Timestamp desc
  ```
  On-premises equivalents - Sysmon Event ID 1 gives the `mshta.exe` command line with `ParentImage` and `ParentCommandLine`, which is where the `cmd /c` loop becomes visible. Sysmon Event ID 11 covers the HTML and batch writes. Sysmon Event ID 13 covers the Run key write — and note that Sysmon 12 and 13 do not log registry *reads*, so there is no way to see the key being consumed at logon, only written. Where Sysmon Event ID 9 (RawAccessRead) is enabled it records the physical-drive access directly, which is the cleanest signal available for the MBR step; most configurations leave it off because of volume, so check whether it is on before relying on a negative. If 4688 is the only process source, the fields are `New_Process_Name` and `Creator_Process_Name` rather than Sysmon's `Image` and `ParentImage`, and command-line capture has to be enabled separately or the HTML path operand will not be recorded.
  Triage on a locked host - the page is local and parameterised, so it is also evidence. Preserve `lock_screen.html` before removing it: it carries the actor-supplied Bitcoin and USDT addresses, the price, the contact email and the timer, all of which are intelligence rather than noise. Then remove the Run key, kill the relaunch loop and the monitoring process together — the report describes both a Run key and a background goroutine that "continuously monitors and relaunches the lock screen process", so removing one leaves the other.
  Why the MBR backup matters for response - the module reads and saves the first sector rather than overwriting it, and the report separately describes a bootkit-preparation feature that surveys boot type and Secure Boot state and stages a placeholder file. Talos describes that staged file as a marker rather than a payload, noting it "can be overwritten by the actual bootkit binary delivered through the implant's file-upload or file-write command handlers." So a host that shows the MBR read should be checked for boot-level tampering before it is returned to service, and the saved sector should be preserved for comparison against the live one.
  Expected, not observed by Talos - the report does not give the PowerShell cmdlet or syntax used for the raw disk read, so the query above matches on the device path rather than on a command shape, and a reader should not assume `Get-Content` or any particular method. It does not state whether the Run key is removed when the operator retracts the lock (the module is described as a controller that can "prepare, deploy, and retract" the payload, without detailing the retraction artefacts). It also does not say the five-second loop is what produces repeated `mshta.exe` process creations as opposed to one persistent process, so the per-minute count above is a derived expectation rather than a reported observation. Indicators from the report for the active infrastructure are the IP `87.120.196[.]120` resolving `total-sitevv[.]lol`, a TLS certificate with serial `7d16381a9de823943b5a0987dbd0f26edf22052b` and JARM `28d28d28d00000000042d42d0000001f361a1bf80ed39a1e352adeb016a07b` whose Common Name is `nik-panel`.
  Pairing - [[M065]] covers the C2 channel the same implant uses to deliver this command, which is the better hunt for finding affected hosts *before* a lock is deployed; the two are the before and after of the same intrusion.
  Closest existing coverage - nothing in the corpus currently covers extortion without encryption. The nearest hunts by technique are the `mshta.exe` and HTA execution work in [[H240]] and [[H331]], which cover remote and inline HTA payloads as an execution vector rather than a locally generated ransom page relaunched in a loop. [[H222]] is the nearest hunt on the raw-disk leg and runs in the opposite direction: it covers a non-system binary issuing large sequential *writes* to a physical drive and reinitialising partition structures to destroy data, where this covers a single-sector *read* taken to preserve the MBR ahead of possible boot-level tampering — opposite intent, opposite impact, different techniques. [[H423]] is the nearest hunt by shape — a file written to a chosen path from data already inside the dropper, with no network fetch to catch — and differs in subject entirely.

# H435

Most ransomware detection in production is really mass-file-modification detection: entropy change across a share, shadow copies deleted, a canary file touched, a backup agent screaming. The screen-locking module in NIK C2 produces none of that, and Cisco Talos is explicit about why that was the design: "It does not encrypt any files, which means it leaves no forensic trail of file modification timestamps or encryption markers. It relies entirely on a screen lock, which is considerably faster to deploy than a file encryption ransomware."

What it does produce is a short, specific chain of ordinary Windows events. The module builds a "complete self-contained HTML lock screen code entirely at runtime from a hardcoded format string, parameterized with actor supplied Bitcoin and USDT wallet addresses, prices, contact email, timer duration, and custom text from the C2 command message". It writes the page to the temp directory. Then: "It then generates a Windows batch script that calls mshta.exe with the path to the HTML file, followed by an infinite loop construct with a five-second timeout between iterations, ensuring that if the user somehow closes the window it reopens within five seconds."

Persistence is doubled. A `reg add` writes a Run key named `SystemLock` "under the current user's autostart path, pointing to a" `cmd /c` "invocation of the batch file, so the lock screen is executed on every user's logon" — and separately, "a background goroutine is spawned that continuously monitors and relaunches the lock screen process." Remove one and the other brings it back.

Ahead of all of that is the quietest and most interesting step: the module reads the first sector of the physical drive through PowerShell and saves it to a backup file. Nothing is overwritten. An operator who is preserving the MBR is an operator who intends to modify it, and the same implant has a separate feature that surveys boot type and Secure Boot state and stages a placeholder for a bootkit. That makes the raw disk read the earliest observable in the destructive chain and the one worth alerting on rather than hunting.

So the hunt is four events, each unremarkable alone: a process reading `\\.\PhysicalDrive0`; an HTML file created in a temp directory; `mshta.exe` opening that file within seconds of it appearing; and a Run key whose value is a `cmd /c` pointing at a batch script in temp.

## Why

- Every control built for ransomware is structurally blind to this. No encryption means no entropy change, no mass modification, no shadow-copy deletion and no canary trigger — the detections that would normally fire are not failing, they are correctly reporting that nothing matching their definition happened.
- The impact is immediate and the deployment is cheap, which makes it attractive at the tail end of an intrusion where an operator is out of time. Speed of deployment is the property Talos names as the advantage.
- The relaunch machinery is the signal. A locally created HTML file opened by `mshta.exe` within seconds of being written, restarted by a `cmd.exe` loop, is a shape with almost no legitimate producers outside kiosk estates.
- Persistence is deliberately redundant, so a response that kills the window or deletes the Run key alone will appear to work and then fail. The hunt output needs to name both the key and the monitoring process.
- The raw disk read is a warning rather than an impact. Preserving the MBR is preparation, and the same implant stages for bootkit delivery, so this is the point in the chain where intervention still prevents something worse.
- The ransom page itself is intelligence. Because it is generated locally and parameterised per victim, the file on disk holds the wallet addresses, price, contact address and timer — which is a better artefact than anything that would survive a file-encrypting deployment.
