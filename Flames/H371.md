false_positive_notes: |
  Each primitive here is individually common and the combination is not. `Get-Date` is one of the most-used cmdlets in existence - it appears in essentially every logging, reporting, backup, maintenance and deployment script ever written, so time queries alone carry no signal whatsoever and must never be the filter on their own. `Stop-Process` and `taskkill` are likewise routine in administrative tooling. Legitimate time-gated automation is real and widespread - maintenance windows, backup schedules, after-hours patching, overnight batch jobs and license-reclamation scripts all branch on the hour. What has no good explanation is the specific join - a script that queries local time *and* terminates an interactive diagnostic tool *and* does so only during hours when nobody is expected to be at the console. Scope on that conjunction and the noise collapses. A second real false-positive class is kiosk, VDI, exam-proctoring, classroom-management and endpoint-lockdown software, which deliberately blocks or closes Task Manager as a policy control; these are identifiable by vendor, are usually deployed via policy rather than a loose script in `%TEMP%`, and typically block it outright rather than waiting an hour. Group Policy's own "Remove Task Manager" setting is the sanctioned way to do this and produces no process-termination events at all, which is a useful contrast - a sanctioned control prevents, whereas this script reacts. Third, `taskmgr.exe` genuinely does exit often and for ordinary reasons, so the termination leg needs the *cause* - Sysmon Event ID 10 showing a script host opening `taskmgr.exe` with terminate rights - rather than the mere absence of the process; Event ID 5 cannot supply it. Fourth, services legitimately stop and start, but a service that stops each time `taskmgr.exe` launches and restarts when it exits has no maintenance explanation. Finally note the misspelling - `Taskgmr.ps1` transposes two letters of `Taskmgr`, so a name-based search must be fuzzy or it will miss both this sample and the next one.

  Core filter, the script leg. PowerShell script-block logging (4104) where a block references a diagnostic or monitoring tool (`taskmgr`, `perfmon`, `resmon`, `procexp`, `procmon`) in the same block as a service-control primitive (`Stop-Service`, `Start-Service`, `Set-Service`, `sc.exe stop`, `net stop`) or a termination primitive (`Stop-Process`, `taskkill`, `.Kill()`). A time query (`Get-Date`, `[DateTime]::Now`, `(Get-Date).Hour`) in the same block raises the rank. This is the pairing Huntress's own "PowerShell Scriptblock - Task Manager Aware Service Control" rule matches, and it does not depend on the service name. Triage fields - the full script block, the invoking parent process, the account, the file path the script was run from, the service it controls, and the hours the logic branches on.
  Sample Splunk SPL over Event ID 4104.
  `index=windows EventCode=4104 ScriptBlockText="*taskmgr*" (ScriptBlockText="*Stop-Service*" OR ScriptBlockText="*Start-Service*" OR ScriptBlockText="*Stop-Process*" OR ScriptBlockText="*taskkill*") | eval time_gated=if(match(ScriptBlockText, "(?i)Get-Date|\\[DateTime\\]::Now"), 1, 0) | table _time host UserID Path time_gated ScriptBlockText`
  Sample KQL over Defender XDR. Defender has no table carrying script-block text - `DeviceEvents` with `ActionType == "PowerShellCommand"` records one cmdlet name per row - so aggregate the cmdlets per PowerShell process instead; the Task Manager reference itself is only visible in 4104.
  `DeviceEvents | where Timestamp > ago(30d) | where ActionType == "PowerShellCommand" | extend Cmd = tostring(parse_json(AdditionalFields).Command) | summarize Cmds = make_set(Cmd, 200) by DeviceId, DeviceName, InitiatingProcessId, InitiatingProcessCommandLine | where Cmds has "Get-Process" and Cmds has_any ("Stop-Service", "Start-Service", "Stop-Process") and Cmds has "Get-Date" | project DeviceName, InitiatingProcessId, InitiatingProcessCommandLine, Cmds`
  Core filter, the effect leg. Even without the script, its behaviour shows. A service that enters the stopped state shortly after each `taskmgr.exe` launch and the running state shortly after it exits (System 7036) is the service-control half. A PowerShell process opening `taskmgr.exe` with terminate rights is the kill half - Sysmon Event ID 10 where `TargetImage` ends in `taskmgr.exe` and `GrantedAccess` includes `PROCESS_TERMINATE` (`0x0001`).
  Sample Splunk SPL - PowerShell opening Task Manager with terminate rights.
  `index=windows source="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=10 TargetImage="*\\taskmgr.exe" (SourceImage="*\\powershell.exe" OR SourceImage="*\\pwsh.exe") | eval ga=tonumber(replace(GrantedAccess, "0x", ""), 16) | where ga % 2 == 1 | table _time host SourceImage TargetImage GrantedAccess`
  Sample KQL - when Task Manager gets opened, by hour of day. Defender `DeviceProcessEvents` records launches only, not terminations, so this shows the launch pattern to correlate against the service toggles.
  `DeviceProcessEvents | where Timestamp > ago(30d) | where FileName =~ "taskmgr.exe" | summarize Launches = count(), Hours = make_set(hourofday(Timestamp)) by DeviceName, Day = bin(Timestamp, 1d) | where Launches >= 5 | order by Launches desc`
  Core filter, the service leg. The miner's service was created as `MicrosoftEdgeUpdateSvc`, named to resemble the real Edge Update service (`edgeupdate`), and runs `msedge.exe` from the Temp folder as SYSTEM. Service creation with a binary path under a Temp folder is cheap to query - System 7045 or Security 4697.
  `index=windows (EventCode=7045 OR EventCode=4697) (Service_Name="MicrosoftEdgeUpdateSvc" OR Service_File_Name="*\\Temp\\*" OR ServiceFileName="*\\Temp\\*") | table _time host Service_Name ServiceName Service_File_Name ServiceFileName Service_Account`
  Core filter, the AhsayCBS exploitation leg. Huntress published four Sigma rules in its threat-intel repository under `2026/2026-10/AhsayCBS_XMRig_Miner` and describes the logic of all four - "PowerShell Scriptblock - Task Manager Aware Service Control" (the script leg above), "WinRing0 Driver Downloaded via Command Line" (a command line naming WinRing0 alongside a URL), "Unexpected Child Process from AhsayCBS Service," which "flags any process spawned by `cbssvcX64.exe` or `cbssvcX86.exe` outside the service's normal startup and maintenance commands," noting that "because AhsayCBS runs its web app inside the service process, commands from an uploaded JSP webshell appear as direct children of the service"; and "Fake Edge Binary Launched with Daemonized Flag," which "flags Edge-named binaries that carry the `msedge_exe` original file name or run with `--daemonized`," where "a renamed NSSM and the XMRig miner posed as Microsoft Edge." The last two generalise well - any child of a backup or management service process, and any Edge-named binary running from `%TEMP%` or carrying a flag the real browser does not accept.
  Corroborating legs worth running in the same sweep. `WinRing0x64.sys` is a legitimate signed low-level hardware-access driver bundled with mining and overclocking tools - its presence on a server is anomalous on its own and is a vulnerable-driver concern independent of this campaign. Miner egress on port 8029 to a Monero pool is a cheap network query. And a `.jsp` file created in the AhsayCBS web application directory by the service process rather than by a deployment is the webshell leg; the same structure for Oracle middleware is in [[H365]] and for IIS in [[H364]].
  Containment note. Huntress recommends restricting AhsayCBS management interface web access to trusted IPs or behind a VPN, and advises that any host showing these IOCs be fully re-imaged from a trusted backup, "as attackers have been able to hide secondary backdoors for extended persistence." A hunt that confirms the miner should therefore assume additional persistence is present rather than treating the miner as the whole intrusion.

# H371

Of everything in this intrusion — the authentication bypass, the SYSTEM-level RCE, the JSP webshell, the Monero miner wearing Microsoft Edge's name — the detail worth building a hunt on is a PowerShell script that watches for Task Manager.

The script is named `Taskgmr.ps1`, which transposes two letters of `Taskmgr`. Its main job, per Huntress, is simple: when Task Manager opens, it stops `MicrosoftEdgeUpdateSvc` — the service the actors created to keep the XMRig miner running — and when Task Manager closes, it starts it again. Whoever opens Task Manager to find out why the server is slow sees nothing using the CPU. On top of that, it kills Task Manager outright at 18:00 and if it is left open for more than an hour overnight, keyed to the endpoint's local `Get-Date` rather than UTC.

That last choice is suggestive, though the reading is ours rather than Huntress's. If you are writing scheduled automation across a server estate, UTC is the reliable choice. An operator picks local time when local time is the thing they care about — and the reason to care about an individual server's wall clock is that it approximates the working day of the person who might be sitting in front of it.

What makes this huntable is that each piece is ordinary on its own and the pairing is not. Checking for a process is routine. Stopping and starting a service is routine. A script that stops a service *because* Task Manager opened, and restarts it *because* Task Manager closed, is not maintenance automation — Huntress built a Sigma rule on exactly that pairing, and it holds whatever the service is called. The effect is visible without the script too: a service that toggles in step with `taskmgr.exe` launches, and PowerShell opening `taskmgr.exe` with terminate rights.

The rest of the intrusion supplies cheap corroboration. Huntress published four Sigma rules for it, and two generalise well past this campaign: any process spawned by the AhsayCBS service — because the web app runs inside the service, so webshell commands appear as its direct children — and any Edge-named binary carrying `--daemonized` or the `msedge_exe` original filename, which is how a renamed NSSM and XMRig both presented. `WinRing0x64.sys` on a backup server is its own red flag, legitimate signed driver or not.

## Why

- **The service toggle is the main behaviour and the cleanest signal.** Stopping a service when Task Manager opens and restarting it when Task Manager closes hides the miner from the one tool an administrator reaches for first. That pairing has no maintenance explanation.
- **The conjunction is the detection, and each half alone is worthless.** Process checks, service control and time queries are all routine. Requiring a diagnostic-tool reference and a service-control or kill primitive in the same script block collapses an enormous baseline to a readable list.
- **Choosing local time over UTC suggests the target of the evasion (our inference).** UTC is correct for scheduling; local time fits modelling an administrator's day.
- **It inverts the usual relationship between miner and detection.** Cryptominers are normally found by CPU load or pool traffic, both of which operators tune to stay quiet. The anti-observation script is a second, independent artefact that exists precisely *because* the miner is noisy.
- **Hour-of-day branching is a structural property, not a signature.** The specific hours — 18:00, overnight, the one-hour threshold — will change in the next build. A script whose logic differs by hour will not.
- **The effect is detectable even if the script is never recovered.** A service that stops and restarts in step with `taskmgr.exe` launches (System 7036), and PowerShell opening `taskmgr.exe` with terminate rights (Sysmon Event ID 10), are standalone queries. Sysmon Event ID 5 cannot supply the cause — it records only that a process ended.
- **Sanctioned Task Manager blocking looks nothing like this.** Group Policy's "Remove Task Manager" prevents launch and generates no termination events. Kiosk and proctoring software blocks outright rather than waiting an hour. A reactive kill from a loose script in `%TEMP%` is a different shape entirely.
- **The misspelling is a lesson about name-based hunting.** `Taskgmr.ps1` would be missed by an exact search for `Taskmgr`. Hunt the behaviour; use the name only for retrospective scoping.
- **A confirmed miner is not the end of the intrusion.** Huntress advises full re-imaging because secondary backdoors were hidden for extended persistence, and the RCE ran as SYSTEM. Treat the miner as an indicator of access, not as the scope.
