title: "A vendor-named directory at the root of the system drive — a second-stage component written to `C:\\Microsoft\\Vault` out of the dropper's own embedded data"
hypothesis: >-
  Windows creates a small, fixed set of directories at the root of the system drive, and software that installs itself there is rare enough to enumerate. `C:\Microsoft` is not one of them, and no Microsoft product installs to it, so a path that reads as a vendor directory while sitting one level off the root is a deliberate choice by whoever created it. Aokigahara's clipper handler writes its second-stage component beneath `C:\Microsoft\Vault`, and it does so from data already carried inside the dropper rather than by downloading it, so there is no network fetch to catch and no download artefact to hash. The file creation itself is the first and cheapest place this is visible, and file-creation telemetry sees it directly. A hunt that enumerates what legitimately exists at the root of the drive and reports everything else turns this from a family-specific indicator into a durable one.

false_positive_notes: |
  Plenty of legitimate software writes to the root of the system drive, and this hunt will find all of it on the first run. That first run is the point: build the approved inventory from it, then the hunt reports only new arrivals. Common legitimate residents include vendor installer caches, driver and firmware staging directories, build and toolchain roots, SQL Server data directories, virtual machine disk stores and temporary extraction directories left behind by installers.
  Hardware vendor and OEM tooling is the largest single source. Dell, HP, Lenovo, Intel and NVIDIA management and driver components all stage at or near the drive root on managed fleets. Allowlist them by directory name together with the signer of the writing process, not by name alone, since the name is the part an adversary controls.
  Developer and build hosts are legitimately untidy at the root. Toolchain installs, package caches and CI working directories accumulate there, so a build agent will produce far more volume than a user workstation. Scope by host class and derive the approved inventory per class.
  The name on its own is not the finding. A directory called `Microsoft` at the drive root is suspicious because no Microsoft product installs there, but the decisive evidence is the writing process: an unsigned image, or one running from a user-writable path, writing an executable component into it. Resolve the writer before escalating.
  Do not treat a missing clipboard signal as a cleared alert. The dropper handler "does not access the clipboard" itself, so clipboard telemetry on the writing process will be empty by design. The clipboard behaviour belongs to the component it deploys, and that component may not have run yet.
  Writes from `C:\Microsoft\Vault` should not be confused with the legitimate credential vault. Windows Credential Manager stores data under the roaming and local `Microsoft\Vault` and `Microsoft\Credentials` directories inside a user profile, which is a different location entirely. Match on the full path anchored at the drive root, not on the trailing `Microsoft\Vault` fragment, or every host in the estate will match.
notes: |
  Platform - Windows. The behaviour is a file write to a fixed path, so it is visible on any host with file-creation telemetry and needs no special instrumentation.
  What the report states - Check Point describes the handler pair as `clipper` and `clipper_drop`, which "Drops a clipper component beneath" the path `C:\Microsoft\Vault`, "using embedded data." It is explicit that the deploying handler is not the clipboard component: "The handler itself does not access the clipboard; it deploys the component responsible for clipboard manipulation." It is also explicit about the limits of its own analysis: "The targeted cryptocurrency wallets or address formats have not been confirmed." So this hunt covers the deployment step, and the clipboard function is attributed to the component rather than characterised here.
  Two observations that are mine, not the vendor's - Neither of the following is stated in the report, and both should be read as analysis rather than as reported fact. First, `C:\Microsoft` is not a directory any Microsoft product creates or installs into, which is what makes the name an inversion of the usual masquerade: most masquerading puts an adversary file in a legitimate directory, and this puts a legitimate-looking directory somewhere nothing legitimate lives. Second, the `Vault` leaf shares its name with the Windows Credential Manager vault directories, which could plausibly cause an analyst skimming a path list to read it as a Windows component; the report does not say the name was chosen for that reason.
  Why the write is the best place to catch this - The component arrives from "embedded data", so there is no download: no DNS lookup, no HTTP fetch, no file-from-internet zone marker, and nothing for network telemetry to see. Equally, the component has not executed yet at the moment it is written, so process and clipboard telemetry have nothing. The file creation is the earliest observable event in the chain and the only one guaranteed to exist.
  Primary query, the family-specific path - Start narrow to confirm presence, 30-day Defender retention:
  ```kql
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("FileCreated", "FileRenamed", "FileModified")
  | where FolderPath startswith @"C:\Microsoft\"
  | project Timestamp, DeviceName, FolderPath, FileName, SHA256,
            InitiatingProcessFileName, InitiatingProcessFolderPath,
            InitiatingProcessCommandLine, InitiatingProcessAccountName,
            InitiatingProcessParentFileName
  | order by Timestamp desc
  ```
  Generalised query, the durable version - The path is one operator's choice and will change. What generalises is the shape: a new first-level directory under the drive root receiving a write from a process that is not an installer. Replace the allowlist with the estate's own approved inventory:
  ```kql
  let approvedRoots = dynamic(["Windows", "Program Files", "Program Files (x86)",
                               "ProgramData", "Users", "PerfLogs", "Recovery",
                               "System Volume Information", "$Recycle.Bin",
                               "$WinREAgent", "EFI", "Intel", "Drivers",
                               "OneDriveTemp", "Documents and Settings"]);
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("FileCreated", "FileRenamed", "FileModified")
  | where FolderPath startswith "C:\\"
  | extend firstLevel = tostring(split(substring(FolderPath, 3), "\\")[0])
  | where isnotempty(firstLevel)
  | where firstLevel !in~ (approvedRoots)
  | summarize writes = count(), files = make_set(FileName, 20),
              writers = make_set(InitiatingProcessFolderPath, 10),
              firstSeen = min(Timestamp), lastSeen = max(Timestamp)
          by DeviceName, firstLevel
  | order by firstSeen desc
  ```
  `substring(FolderPath, 3)` drops the `C:\` prefix so the first path element is the directory immediately under the root; `split` then yields it. Run this once to build `approvedRoots` for the estate, then keep it as a monthly report of new arrivals rather than an alert.
  Signer triage on the written component - A component dropped from embedded data is very unlikely to carry a valid signature, and `DeviceFileEvents` has no signature columns, so the signer has to be joined in. The join is on SHA1, and both bindings are used:
  ```kql
  let dropped = DeviceFileEvents
      | where Timestamp > ago(30d)
      | where FolderPath startswith @"C:\Microsoft\"
      | where ActionType in ("FileCreated", "FileRenamed")
      | project Timestamp, DeviceName, FolderPath, FileName, SHA1;
  let certs = DeviceFileCertificateInfo
      | project SHA1, Signer, IsSigned, IsTrusted, SignatureType;
  dropped
  | join kind=leftouter (certs) on SHA1
  | project Timestamp, DeviceName, FolderPath, FileName, SHA1, Signer, IsSigned, IsTrusted
  | order by Timestamp desc
  ```
  Sysmon equivalent - The same first half works from Sysmon Event ID 11, with one configuration caveat worth checking before trusting a negative result: many Sysmon configurations include file-creation rules scoped to user-profile and temp directories and never match the drive root, so a host can be fully instrumented and still produce nothing here. Confirm the running configuration covers `C:\` before concluding the path is absent.
  Follow-on, the clipboard half - Once the component executes, the behaviour is clipboard monitoring and substitution, which is already covered: [[H158]] hunts the persistent clipboard-polling thread that scans for wallet address patterns and replaces them before the victim pastes. Run it against any host that produces a hit here. Because Check Point did not confirm the wallet types or address formats this component targets, [[H158]] rather than this hunt is where the address-pattern logic belongs.
  Pairing with the rest of the infection - A host with a write to this path has already run the collection stage. The AI and developer credential sweep is in [[H422]], the baseline that scopes it is [[B066]], and the upload fingerprint that confirms exfiltration is in [[H424]]. The clipper is the monetisation component rather than the theft, so a hit here should widen the investigation backwards, not narrow it to cryptocurrency.
  Response - Preserve the component before deleting it; its presence is the only artefact that identifies which build of the dropper ran, and the dropper may already have removed its own staging. Check for any persistence that launches the component, since a clipboard monitor is only useful if it runs on every logon.
  Closest existing coverage - [[H158]] is the nearest hunt by subject and covers the clipboard polling and address substitution this component performs once it runs, which is why the address-pattern logic is left there; this hunt covers only the write that precedes execution, and the two do not overlap in telemetry. [[H418]] is the nearest hunt by shape - a configuration file written into a Windows system directory by the service binary that reads it - and differs in that it keys on a file written into a directory that legitimately exists, where this keys on the directory itself having no legitimate reason to exist.
  Adjacent coverage - [[H158]] covers the clipboard polling and substitution this component performs. [[H418]] covers a configuration file written into a Windows system directory by the service binary that reads it, which is the same class of observation applied to a different directory. [[M021]] scores clipper-adjacent activity volumetrically. [[H422]] and [[H424]] are the other two stages of this family.

# H423

Check Point Research's October 2026 analysis of the Aokigahara infostealer lists a pair of handlers, `clipper` and `clipper_drop`, whose job is not to touch the clipboard but to deploy something that will. The report records the staging location plainly: the handler "Drops a clipper component beneath" the path `C:\Microsoft\Vault`, "using embedded data."

Three details in that one sentence make it worth hunting. The component comes from embedded data, so nothing is downloaded and no network or download-provenance telemetry will see it arrive. The deploying handler is not the clipboard component — "The handler itself does not access the clipboard; it deploys the component responsible for clipboard manipulation" — so behavioural clipboard detection has nothing to fire on at deployment time. And the destination is a path at the root of the system drive wearing a vendor's name.

That last point is the durable part. Masquerading usually works by putting an adversary's file somewhere legitimate, which is why so much detection is built around unexpected files in `System32` or `Program Files`. This is the inverse: a directory that looks like it belongs to a vendor, created somewhere no vendor installs. Windows creates a short and well-known set of directories at the root of the system drive, and `C:\Microsoft` is not among them, so the name carries no legitimacy at all once the location is taken into account. That observation is not in the report; it is the reason the generalised query below enumerates what belongs at the root and reports everything else, rather than matching one path string that the next build will change.

Check Point is clear about where its analysis stops. "The targeted cryptocurrency wallets or address formats have not been confirmed", so this hunt deliberately covers only the deployment step and hands the clipboard behaviour to existing coverage rather than inventing address patterns the vendor did not observe.

The practical value is timing. The write happens before the component runs, before any clipboard is substituted, and before any cryptocurrency moves. It is the earliest point in the clipper chain where anything is observable, and ordinary file-creation telemetry sees it without additional instrumentation.

## Why

- The write is the only guaranteed observable in the chain. The component is carried in the dropper rather than fetched, so there is no network event, no DNS lookup and no download artefact; and it has not executed yet, so there is no process or clipboard event either.
- Detection sits before the loss. A clipper monetises by silently substituting a wallet address at paste time, which is a transaction the victim authorises and no control reverses. Catching the deployment is the difference between an incident and an unrecoverable transfer.
- The location generalises past this family. A newly created first-level directory under the drive root that receives writes from something other than an installer is a small, reviewable population in any estate, and reviewing it monthly costs almost nothing once the approved inventory exists.
- Vendor-named directories in illegitimate locations defeat name-based reasoning. Analysts and allowlists alike treat `Microsoft` as reassuring, and a path fragment ending in `Microsoft\Vault` matches the real Credential Manager directories closely enough to be waved through by anyone matching on the tail rather than anchoring at the root.
- A hit reframes the whole investigation. The clipper is the last stage of this family, not the first, so a host that reaches deployment has already had its browser, wallet, developer and AI credentials collected and very likely uploaded.
