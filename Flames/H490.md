false_positive_notes: |
  Legitimate SoftEther VPN Bridge deployments do exist, and they also create an `SEVPNBRIDGE` service and reference the SoftEther Project in the registry. They differ in every other respect: the executable is the official `vpnbridge_x64.exe` or a locally built equivalent whose PE metadata names SoftEther rather than a generic network monitor, the install directory contains `hamcore.se2` as a separate file, and the configuration is the plaintext `vpn_bridge.config` in the stock format rather than a `setting.conf` beginning with `RCEN`. Reconcile the host against the authorised software inventory before investigating further.

  Commercial network-monitoring products legitimately carry version resources describing themselves as network monitors. Those products do not register a service named `SEVPNBRIDGE`, and they are normally signed by a recognisable publisher.   File and PE-metadata sweep (EDR file inventory, Sysmon Event ID 11, DeviceFileEvents) - Core filter: executables anywhere outside `C:\Program Files\` and `C:\Program Files (x86)\` whose version resource `FileDescription` or `ProductName` contains `Network Monitor` or whose `CompanyName` contains `Network Systems Solutions`, and separately any executable whose `OriginalFilename` is `netcapa.exe`. Triage values are `file path`, `SHA256`, `OriginalFilename`, `FileDescription`, `CompanyName`, `FileVersion`, `signer` and `file size`. Pivot: for each hit, check whether the version resource still reads `4, 44, 0, 9807` - Rapid7 notes the version field is the only metadata field left unchanged against the stock `vpnbridge_x64.exe`, so a generic network-monitor description carrying a SoftEther 4.44 build number is the single highest-value combination in this hunt. Strong red flags: the binary is unsigned or self-signed; the PDB path `C:\Users\Administrator\Desktop\SoftEtherVPN_Stable\SoftEtherVPN_Stable\SoftEtherVPN_Stable\src\DebugFiles\pdb\x64_Release\vpnbridge.pdb` is present in the file's strings, which Rapid7 observed in the analysed sample and which means the tool "doesn't hide its identity from reverse engineers, only external interactions".

  KQL - Defender XDR, oversized unsigned binaries claiming to be network monitors, joined to signer state. Note `DeviceImageLoadEvents` and `DeviceFileEvents` carry no signature columns, so the signer must come from `DeviceFileCertificateInfo` on SHA1. Keep the lookback at or under `ago(30d)`, which is the advanced-hunting retention limit.

      let candidates =
          DeviceFileEvents
          | where Timestamp > ago(30d)
          | where ActionType in ("FileCreated", "FileModified")
          | where FileName endswith ".exe"
          | where not (FolderPath startswith @"C:\Program Files")
          | where not (FolderPath startswith @"C:\Windows\WinSxS")
          | project Timestamp, DeviceId, DeviceName, FileName, FolderPath, SHA1, SHA256, InitiatingProcessFileName, InitiatingProcessCommandLine;
      let signers =
          DeviceFileCertificateInfo
          | where Timestamp > ago(30d)
          | project SHA1, Signer, IsSigned, IsTrusted;
      candidates
      | join kind=leftouter signers on SHA1
      | where isempty(Signer) or IsTrusted == false
      | project Timestamp, DeviceName, FileName, FolderPath, SHA256, Signer, IsSigned, IsTrusted, InitiatingProcessFileName, InitiatingProcessCommandLine
      | order by Timestamp desc

  Run that to shortlist unsigned or untrusted executables written outside Program Files, then read the version resources of the shortlist on the host - the advanced-hunting tables do not expose `OriginalFilename`, `FileDescription` or `CompanyName`, so the metadata test has to happen on the endpoint or in an EDR file-inventory product that collects those fields.

  Configuration and resource-archive artefacts (Sysmon Event ID 11, DeviceFileEvents, host sweep) - Core filter: a file named `setting.conf` created in the same directory as an unsigned executable, and no `hamcore.se2` in that directory. Confirm the encryption marker by reading the first four bytes - the stock loader reads a plaintext `vpn_bridge.config`, whereas this build reads a custom-encrypted file that starts with the magic bytes `RCEN` in ASCII. A one-line check on a suspect host, with the path quoted so a space in it does not split the argument:

      powershell -NoProfile -Command "Get-Content -Path 'C:\path\to\setting.conf' -Encoding Byte -TotalCount 4 | ForEach-Object { [char]$_ } | Join-String"

  Rapid7 publishes a Python script on the Rapid7 Intelligence GitHub repository that decrypts such files with the actor's custom RC4-like cipher, and the decrypted configuration is where the cascade destination lives - in every case Rapid7 examined the VPN was configured to bridge, or cascade, a remote network into the local one, and in the cases that were not likely deliberate tests the remote address sat inside AS 20473, belonging to The Constant Company, LLC. Treat a decrypted cascade destination in that ASN, or in its subsidiary Vultr, as corroborating the Webworm attribution. Strong red flags: `setting.conf` present with no `vpn_bridge.config` and no `hamcore.se2`; the executable is roughly 1.5 MB larger than the official build of the same version.

  Service and registry artefacts (System Event ID 7045, Security Event ID 4697, Sysmon Event IDs 12 and 13) - Core filter: a service install whose service name is `SEVPNBRIDGE` and whose `ImagePath` does not point at an approved SoftEther installation, or any registry key creation under `HKLM\SOFTWARE\` containing `SoftEther` on a host that is not in the authorised VPN-software inventory. Rapid7 notes the rebranding is inconsistent - occurrences of "SoftEther VPN" are replaced by "NtMonitor VPN" in debug banners, service names, registry keys, the server's HTTP 401 error page and firewall rule names, yet the service name used by the entry point is still `SEVPNBRIDGE` and many registry key paths still reference the "SoftEther Project". That inconsistency is the hunt's leverage: look for both spellings. Triage values are `service name`, `service file name`, `service account`, `start type`, `registry key path`, `registry value data` and `initiating process command line`. Correlation: the service install and the `setting.conf` write land on the same host inside a few minutes, usually under a SYSTEM or local-administrator context.

  Host firewall rules (Windows Filtering Platform rule changes, Security Event ID 5156 context, `netsh advfirewall firewall show rule name=all`) - Core filter: inbound allow rules whose display name contains `NtMonitor`, or inbound allow rules created by the suspect executable. Rapid7 records that, using stock SoftEther functionality, the tool adds rules to the system firewall, and that firewall rule names are among the strings rebranded to "NtMonitor VPN". A rule named for a product that is not in the software inventory is a high-confidence pivot back to the binary that created it. B073 in this batch baselines what normally creates inbound allow rules so this leg is runnable.

H491 covers the network half - the renamed HTTP endpoints and the custom PNG watermark - and the two should be run together. # H490

Rapid7 published analysis on November 19, 2026 of what it believes to be a previously unknown custom SoftEther-based tool, attributed to the China-aligned APT Webworm with moderate confidence. Webworm has been documented deploying open-source SoftEther VPN into compromised government networks to maintain low-profile, long-term access. After that tactic was publicly reported, the actor rebuilt the SoftEther VPN Bridge from source — version 4.44, build 9807 — with the detection surface methodically removed. Rapid7's assessment is that the actor "prioritizes stealth above raw capability": beyond the changes it describes, no additional malware functionality was identified. There is no backdoor and no command-execution capability added; the value of the tool is covert network access that no longer looks like SoftEther.

ESET had already noted Webworm shifting away from custom malware toward dual-use tools such as SoftEther VPN. Rapid7 frames this build as a hybrid of the two approaches — "stock SoftEther software that is not trojanized, but rebuilt from source in a way that erases much of its detection fingerprint." This hunt targets that erasure. Each individual change the actor made is cheap to redo, but the structural consequences are not: a SoftEther service name with no `hamcore.se2` beside it, an encrypted `setting.conf` where a plaintext `vpn_bridge.config` belongs, and a binary inflated by the archive it now carries internally.

## Why

- The actor removed exactly the artefacts a detection engineer would reach for first. The `hamcore.se2` resource archive is required at runtime and normally sits next to the executables, which Rapid7 assesses is precisely why the actor minimised it, packed it into the executable as a PE resource, and wrote a custom resource directory walk to load it. The configuration was renamed and encrypted because stock SoftEther stores it in plaintext in a recognisable format. Hunting the absence of those files, rather than their presence, inverts the actor's own work.
- Signature and reputation controls did not catch it. At the time of Rapid7's analysis only one anti-virus vendor on VirusTotal detected the sample, despite it having been public since January. A clean verdict on an unsigned network-monitor binary in a government environment is not reassurance.
- The rebranding is incomplete, and that is durable. The entry point still registers `SEVPNBRIDGE` and many registry paths still name the "SoftEther Project", while the user-visible strings say "NtMonitor VPN". An actor who wants to fix that has to change the service-management code, not just a string table, so the dual-spelling search survives the next round of cosmetic edits.
- Rapid7 explicitly expects the branding, HTTP endpoints and watermark to be swapped next, and recommends defenders in the government sector familiarise themselves with intrinsic SoftEther VPN behaviour. That is a baselining instruction, which is why this hunt ships alongside B073 rather than on its own.
