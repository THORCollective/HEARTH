false_positive_notes: |
  Developer Mode and unpacked extensions are completely normal on engineering workstations. Anyone building or debugging a browser extension loads it from a directory, and web developers attach to Chrome with the DevTools Protocol routinely. Host role does most of the filtering here - an unpacked extension on a developer's machine is expected, the same thing on a finance or clinical workstation is not.

  The `debugger` permission itself has legitimate holders. Several well-known extensions use the DevTools Protocol for genuine features, including accessibility tooling, session-recording and web-testing extensions, and some password managers and automation helpers. This is a permission to inventory and reconcile against an approved list, not a permission to alert on blindly. The useful question is whether the extension holding it came from the Web Store and whether anyone approved it.

  Automation frameworks produce the same debugging signals. Selenium, Puppeteer and Playwright all drive Chromium through the DevTools Protocol, and CI agents and RPA tooling do so constantly. If those run in the estate, exclude their service accounts and hosts explicitly rather than trying to distinguish them by shape.

  The name `Google Chrome` is this campaign's choice and is trivially changed - Unit 42 publishes it because it is what these two samples used. Treat the string as one indicator and the structure as the hunt - any extension whose declared name mimics the browser, the vendor, or a built-in feature is the same play.

  Unit 42 states the second sample it pivoted to was version 1.6.112 and shared the same hard-coded API key and C2 server as 1.6.111. Version numbers and extension IDs will differ in the next build; the manifest permission set is the more durable pivot.
notes: |
  Leg one, how the extension got there (extension inventory, plus DeviceFileEvents or Sysmon 11) - Core filter: an extension present in a browser profile that did not come from the Web Store. The structural tell of a Developer Mode sideload is a manifest and extension payload written directly into a profile's `Extensions` tree, or an extension directory living outside it entirely, by a process that is not the browser's own updater.

      DeviceFileEvents
      | where Timestamp > ago(30d)
      | where FileName =~ "manifest.json"
      | where FolderPath has_any (@"\User Data\", @"\Extensions\", @"\Default\")
      | where InitiatingProcessFileName !in~ ("chrome.exe", "msedge.exe", "setup.exe", "MicrosoftEdgeUpdate.exe", "GoogleUpdate.exe")
      | project Timestamp, DeviceName, FolderPath, InitiatingProcessFileName,
                InitiatingProcessFolderPath, InitiatingProcessCommandLine, InitiatingProcessAccountName
      | order by Timestamp desc

  Thirty days is the whole Defender advanced hunting retention, so do not reach further back than `ago(30d)` here. `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, which is the right shape for this leg - the question is who wrote the manifest, not who read it. Note the two delivery artefacts Unit 42 names, `folderextension.crx` and `folderextension.zip`, served from `hxxps[:]//oskeysetup[.]com/files/`; a `.crx` or a `.zip` landing in a Downloads folder and an extension directory appearing shortly after is the sideload sequence in two events.

  Leg two, the permission (manifest content review) - Core filter: `"debugger"` in the manifest's permissions array. This is the single highest-value field in the whole hunt, because it is what the remote-control module needs and what produces the banner the extension's name is chosen to disguise. Collect every installed extension's `manifest.json`, parse the permissions, and rank by blast radius. The combination Unit 42 describes - `debugger` together with broad host permissions covering every site the user visits, plus `tabs`, `storage` and `webRequest` - is a near-complete browser implant in five declarations. An extension requesting `debugger` that is not on an approved list is worth opening regardless of anything else in this hunt.

  Leg three, the browser's own command line (Sysmon 1 or 4688) - Core filter: a Chromium browser launched with `--load-extension=`, `--remote-debugging-port=`, `--remote-debugging-pipe` or `--disable-extensions-except=`. Field names matter - Sysmon exposes `Image`, `ParentImage` and `IntegrityLevel`; Windows Security 4688 exposes `New_Process_Name` and `Creator_Process_Name` and carries no Sysmon-style integrity field, so a 4688 query written with Sysmon field names returns nothing and returns it silently.

      Sysmon Event ID 1 where Image ends with "\chrome.exe" or "\msedge.exe"
        and CommandLine contains any of
          "--load-extension=", "--disable-extensions-except=",
          "--remote-debugging-port=", "--remote-debugging-pipe"

  A distinction worth keeping straight, because it changes which leg fires. The `--remote-debugging-port` switch is the *external* route to the DevTools Protocol and is what H240 hunts for a different family. This extension uses the *in-page* route: `chrome.debugger` from inside an installed extension, which needs no command-line switch at all. So leg three will be silent for this specific implant and is included because it catches the adjacent technique cheaply; legs one and two are the ones that fire here.

  Leg four, the artefacts and the egress - Unit 42 publishes two SHA-256 hashes, `930898e8b65e9cf4e2595ac4092042a707cca8922751e723ad8b86260655154a` for `folderextension.crx` and `ea8d30c42e758559e78bd1fe97f8849011beb7f24c7f092a066a5a62fa7fbe6f` for `folderextension.zip`, and two addresses - `31.42.184[.]213`, which hosted `oskeysetup[.]com`, and `193.149.176[.]62`, which accessed compromised accounts. Sweep file hashes across the estate and the two addresses across proxy and DNS. The domain `oskeysetup[.]com` sits inside the wider apex-domain pattern Unit 42 documents for this ecosystem - authentication and access keywords such as `sso`, `mfa`, `okta`, `passkey`, `oskey` and `secure`, combined with system and account operation keywords such as `enroll`, `setup`, `install` and `connect` - so a proxy sweep for your own organisation name as a subdomain label under newly-seen domains of that shape is a cheap adjacent check.

  What the implant collects, for scoping a hit. Unit 42 lists global keyloggers, local and session storage and IndexedDB data across all sites, authentication cookies targeting Microsoft and Google accounts, page scanning for QR codes to capture login and MFA tokens, and webcam streaming. Treat a confirmed install as a full session-token compromise for every site the user visited while it was active, not as a credential-theft event for one application. Cookie theft at this level survives a password reset, so containment has to include session revocation.

  Expected, not observed by Unit 42 - the report does not say how the victim was induced to enable Developer Mode, only that the sideload required it. Given that the same clusters gain access by vishing while posing as internal IT support, a help-desk-shaped instruction is the obvious vector, but the report does not attest it. Unit 42 also assesses only with moderate confidence that CL-CRI-1192, which Google tracks as UNC6671, developed the extension, and says there is currently no evidence it is shared with other Com-affiliated attackers.

  Scope note on existing coverage. A grep of every hunt body for `chrome.debugger` and for `DevTools Protocol` finds no hunt covering an extension that holds the debugger permission. The near neighbours are different mechanisms: H240 covers a browser launched in headless mode with remote debugging for WebRTC command and control, which is the command-line route rather than the extension API; H305 covers an attacker defeating Chrome's keyed-MAC validation of its own preferences to register an extension it did not install, which is a different install path for a different goal; H469 covers an extension as implant through broad host permissions and a relaxed sandbox content-security policy, which is the closest in spirit but turns on CSP and host permissions rather than on the DevTools Protocol. This hunt is the debugger-permission case specifically.

# H515

Chrome tells you when something is driving it. A banner appears across the top of the window reading `Google Chrome started debugging this browser`, and it appears precisely because an extension has taken hold of the DevTools Protocol. It is one of the better warnings the browser gives.

So the operator named the extension `Google Chrome`.

Unit 42 found it during an investigation attributed to CL-CRI-1192, the cluster Google tracks as UNC6671. The extension was manifest version 1.6.111, it was not on the Chrome Web Store, it came from `oskeysetup[.]com`, and the victim had to sideload it by hand using Developer Mode. Once active it installed global keyloggers, swept local storage, session storage and IndexedDB across every site, harvested Microsoft and Google authentication cookies, scanned pages for QR codes to lift login and MFA tokens, and streamed the webcam. Through `chrome.debugger` it also gave operators a remote-control channel: hidden screenshots, synthetic input events, clipboard theft, and the ability to navigate the browser wherever they liked.

A pivot on the file turned up a sibling, version 1.6.112, talking to the same C2 with the same hard-coded API key.

What makes this huntable is that the operator had to spend two things to get it installed. They had to put a manifest on disk, and they had to ask for the `debugger` permission. Neither is deniable afterwards.

## Why

- The `debugger` permission is the hunt. An extension that holds it can screenshot, inject input, read the clipboard and steer navigation on every page, which is the whole remote-control module in one declaration. Enumerating manifests and ranking by permission is a one-time sweep that costs nothing and does not depend on knowing this campaign's names or hashes.
- A Developer Mode sideload cannot hide its install path. Web Store extensions arrive through the browser's own updater; this one arrived as files written into a profile directory by something else. That difference is visible in file telemetry even when the extension ID, name and version all change.
- The disguise names the detection. The extension is called `Google Chrome` only because Chrome's warning banner says `Google Chrome started debugging this browser` — so the presence of the banner, and the reason an operator would bother to blunt it, both point at the same permission.
- Cookie and session theft at browser scope outlives credential resets. The implant harvests authentication cookies and QR-code MFA tokens across all sites, so containment means revoking sessions, not rotating a password. Finding it early is worth considerably more than finding it late.
- It is an alternative to credential phishing, not a replacement, and it sits downstream of a vishing call. Unit 42 assesses with moderate confidence that this cluster built the extension as another way to extract credentials from desktop and laptop devices running Chromium-based browsers — which means the identity-side hunts and this endpoint-side hunt are looking at two ends of the same intrusion.
