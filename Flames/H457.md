title: "An Inno Setup temporary runner launches numbered staged executables and reports each payload attempt back to rotating infrastructure with a fixed offer-execution query contract"
hypothesis: >-
  A user-launched installer promoted as cracked software, a game, an activator or an unofficial utility unpacks an Inno Setup-style temporary runner into a per-session temporary directory and launches a sequence of numbered staged executables from it. Between stages the runner reports to rotating callback infrastructure using randomized URL paths but a fixed query-string contract that names the delivery family and the per-offer result, so one installation session produces several callbacks that correlate by session and affiliate value. The hunt is that contract plus the temporary-directory execution pattern, because the callback domains are short-lived while the query structure and the staged filenames persist across lure categories.

false_positive_notes: |
  Inno Setup is a legitimate and extremely widely used installer framework, so the framework artefacts alone are not a finding.
  - Legitimate Inno-packaged software produces the same temporary runner path shape and the same `/SL5`, `/SPAWNWND` and `/FIRSTWND` argument set. The discriminators are the numbered staged payload names, the multi-offer sequence, and the callback contract - not the presence of an Inno temporary directory.
  - Developer and IT workstations run installers constantly, including unsigned internal builds from temporary paths. Scope the first pass to the callback contract, which has no legitimate population, and use the temporary-directory execution only to build the session once a callback has been seen.
  - Pay-per-install and bundling behaviour also exists in software users genuinely chose to install, including some freeware with opt-in offers. That does not make it benign in an enterprise, but it changes the response from incident to software-policy enforcement, so record which branch actually installed.
  - Domain-based hunting ages out fast here. Microsoft's own guidance is explicit that "Domain-only matches are leads, not confirmation", because the campaign rotates callback domains frequently while preserving the same query structure.
  - Antivirus-blocked offers still generate callbacks, with a failure result and sometimes local error text. A host with only failed-offer callbacks was protected rather than compromised, which is a triage outcome rather than a false positive.
notes: |
  Source reporting is Microsoft Threat Intelligence's November 3, 2026 analysis of a fake-download campaign delivering multiple monetization payloads through trojanized Inno Setup-style installers. The persistence and proxyware half of the same campaign is hunted in [[H456]].
  The callback contract - Core filter: outbound HTTP where the query string carries the delivery-family marker together with a per-offer result value. Microsoft publishes the observed structure as `http:///?sis=&fz=&d=inno&r=offer_execution&ko=no&o=&a=&dn=&spot=&t=&cr=`, with `d` often set to `inno`, `r` set to `offer_execution` or `offer_execution_fail`, `sis` stable within an installer session, `a` stable across related requests as an affiliate or distribution-partner identifier, `o` changing per offer, `dn` or `on` changing with the offer or retrieval path, and `spot` incrementing through the session. Microsoft's published advanced hunting query for this stage:
  ```kql
  DeviceNetworkEvents
  | where RemoteUrl has "d=inno"
  | where RemoteUrl has_any ("r=offer_execution", "r=offer_execution_fail")
  | project Timestamp, DeviceName, RemoteUrl, InitiatingProcessFileName
  ```
  Triage values are the full `RemoteUrl` including every parameter, the initiating process name and path, and the device. Group by the session value and the affiliate value to reconstruct one installation session, then count distinct offer identifiers to see how many payloads were attempted. Microsoft's observed offer and download-network pairs include `o=1712` / `dn=507` as the primary first-stage offer, `o=1720` / `dn=536` for the distributed-compute branch, `o=1727` / `dn=564` for the proxyware branch, `o=1729` / `dn=566`, `o=331` / `dn=244`, `o=1674` / `dn=440`, `o=1675` / `dn=441`, `o=1681` / `dn=447` and `o=1730` / `dn=567`. Note that `DeviceNetworkEvents` only populates `RemoteUrl` for some connection types, so a proxy or NGFW URL log is the more complete source where one exists - and the campaign uses plain HTTP for these callbacks, which means the query string is visible without interception.
  Ordering caveat worth carrying into triage: Microsoft states that "In some endpoint detection and response (EDR) traces, child payloads launched before or around the r=offer_execution callback", so the callback is not reliably the earliest evidence and should not be treated as the prevention point.
  Numbered staging from a per-session temporary directory - Core filter: process creation from an Inno temporary path where the image name follows the numbered or runner pattern. Microsoft's published query:
  ```kql
  DeviceProcessEvents
  | where FolderPath has @"\AppData\Local\Temp\is-"
  | where FileName matches regex @"(?i)^(eld[0-9]+|set_[0-9]+|FirstFast(?:\[1\])?|SecondRunner(?:\[1\])?)\.exe$"
  | project Timestamp, DeviceName, FileName, FolderPath, InitiatingProcessFileName, SHA256
  ```
  The `[1]` in two of those names is the Internet Explorer and WinINet cache-collision suffix, which is why those payloads arrive with a bracketed index - a durable tell that the file was downloaded rather than unpacked. Triage values are `FolderPath`, `FileName`, `SHA256`, the initiating process and its command line. In the Echo Client chain Microsoft documents the sequence as the user-launched lure from `%USERPROFILE%\Downloads\Echo Client\`, then `Echo Client.tmp` under `%TEMP%\is-*.tmp\` with `/SL5=`, then a child `Echo Client.exe` with `/SPAWNWND=` and `/FIRSTWND=`, then the temporary runner continuing, then `eld0.exe`, `eld1.exe`, `eld3.exe`, `eld4.exe` and `eld5.exe` from the same temporary directory. Microsoft notes that the arguments together with the temporary path and the numbered stage names provide more durable indicators than the original lure filename, and that chain depth varied by session - one lure reached several monetization branches while others exposed fewer stages.
  Unattended installation of the final payload - Core filter: process creation where an installer or MSI is launched with silent switches by a parent that is itself a staged payload from a temporary directory. The reported switches are `/qn`, `/S`, `/quiet` and `/norestart`. Sample query joining the staging and the silent install inside one session:
  ```kql
  let lookback = 30d;
  let staged = DeviceProcessEvents
      | where Timestamp > ago(lookback)
      | where FolderPath has @"\AppData\Local\Temp\is-"
      | project StageTime = Timestamp, DeviceId, DeviceName,
                StagePid = ProcessId, StageFile = FileName, StageCmd = ProcessCommandLine;
  let silent = DeviceProcessEvents
      | where Timestamp > ago(lookback)
      | where ProcessCommandLine has_any ("/qn", "/quiet", "/norestart", " /S ")
      | project InstallTime = Timestamp, DeviceId, InstallFile = FileName,
                InstallCmd = ProcessCommandLine, InstallParent = InitiatingProcessFileName;
  staged
  | join kind=inner silent on DeviceId
  | where InstallTime between (StageTime .. StageTime + 15m)
  | project StageTime, InstallTime, DeviceName, StageFile, StageCmd, InstallFile, InstallCmd, InstallParent
  | order by StageTime desc
  ```
  The `between (StageTime .. StageTime + 15m)` bound is load-bearing: a join on `DeviceId` alone across a 30-day lookback pairs a staging event on one day with an unrelated silent install on another. Keep the lookback at `ago(30d)` or less, because Defender XDR advanced hunting retains 30 days and silently truncates longer windows.
  The confirmed branches and their artefacts - Core filter: software inventory and file-creation telemetry for the three outcomes Microsoft confirmed. The proxyware branch installs components under `C:\Program Files\WorldProxyPool\` including `sdk-agent.exe`, `sdk-agent.updater.exe` and `watchdog.ps1`, with the scheduled-task set hunted in [[H456]]. The distributed-compute branch installs under `C:\Program Files\BOINC\` and `C:\ProgramData\BOINC\` with components including `ce-installer_7.14.2_vbox-7.2.8.exe`, `ce_7.14.2_windows_x86_64.exe`, `charityengine.exe`, `boinc.exe`, `boinctray.exe`, `boinc.scr`, `boincscr.exe`, `wrapper_2022110901_windows_x86_64.exe`, `ce11.exe` and `VirtualBox-7.2.8-r173730.msi`. The adware-style branch installs `AdvancedWindowsManager.exe` and `Windows Updater.exe` under paths resembling `%APPDATA%\AW Manager\Windows Manager 1.0.0\` or `C:\Program Files (x86)\AW Manager\Windows Manager\`, delivered via `Windows Manager - Postback Johan.msi`. A VirtualBox MSI arriving on a workstation during an installer session is a particularly useful pivot, because the compute branch brings a hypervisor with it and that is rarely sanctioned on a standard endpoint.
  Infrastructure as a lead only - Core filter: Microsoft's published domain list for the observed callback infrastructure, usable as a retrospective sweep. Their query:
  ```kql
  DeviceNetworkEvents
  | where RemoteUrl has_any ("orbittrack.cfd", "prairielink.cfd", "willowbox.xyz", "stonestation.cfd", "foldlodge.xyz", "friendsanchor.xyz", "fallport.cfd", "wishcourt.cfd", "cratebase.cfd", "belieftrack.cfd", "beliefdesk.xyz", "companyharbor.xyz", "signalpane.cfd", "inkact.xyz", "wishgrove.cfd")
  | project Timestamp, DeviceName, RemoteUrl, RemotePort, InitiatingProcessFileName
  ```
  Microsoft's hunting note sets the right expectation for this stage, and for the hunt as a whole: "the durable hunting signal is the combination of the callback pattern, Inno temporary execution, staged filenames, and related installer-session activity". Correlation: every domain in that list sits on `.cfd` or `.xyz`, so a standing watch on newly observed low-reputation top-level domains contacted by a process running from a temporary directory extends the hunt past this indicator set. Microsoft also advises grouping events by device, time window, and available session or affiliate fields, then correlating the callbacks with the temporary execution, staged filenames, scheduled-task creation and monetization-software activity.

# H457

Microsoft Threat Intelligence described this campaign on November 3, 2026. It targets people searching for cracked commercial software, free games, activators, plugins and unofficial utilities - the observed lures include cracked audio plugins, PC games, Roblox executors, auto-clickers, driver tools and fake utility installers.

What makes it worth a hunt is not the lure but the machinery behind it. The installer is a delivery platform. It unpacks an Inno Setup-style temporary runner, launches a series of numbered staged executables, and reports each payload attempt back to rotating infrastructure with a fixed query-string contract naming the offer, the affiliate, the download network, the placement slot and the result. Offers succeed or fail independently inside one session, so a single installation can produce several callbacks and install more than one unrelated product.

Three monetization branches were confirmed: a proxyware agent that routes third-party traffic through the device, a distributed-compute client that brings its own hypervisor, and adware-style utility software. The affected machine becomes a monetized asset in several ways at once.

The infrastructure rotates and the lure filenames are arbitrary, but two things hold still. The query-string contract is stable because the affiliate accounting depends on it. And the staged filenames and temporary-path argument pattern are properties of the delivery framework rather than of any one campaign, which is why Microsoft treats them as more durable indicators than the lure name.

## Why

- The callback contract has no benign population. A query string carrying the delivery-family marker together with a per-offer execution result is specific to this affiliate accounting scheme, which means the first-pass query returns leads rather than volume, and it keeps working as domains rotate.
- Every callback is an accounting record, so the telemetry reconstructs the whole session. Grouping by the session and affiliate values shows how many offers were attempted, which succeeded, which were blocked by antivirus, and therefore exactly which software needs removing - information that is otherwise expensive to assemble from endpoint artefacts alone.
- The outcome is a compound compromise rather than a single infection. One session can leave proxyware with SYSTEM scheduled tasks, a distributed-compute client, a hypervisor installation and adware, from unrelated operators. Treating it as one piece of malware and removing one product leaves the rest running.
- Hunting the framework artefacts covers future campaigns. The numbered staged names, the per-session temporary directory and the bracketed cache-collision suffix are properties of how the payloads are fetched and unpacked, so they outlive this campaign's lure set and domain set.
- The entry point is policy-adjacent and therefore fixable. Every confirmed case starts with a user running software from an untrusted source, which gives a concrete prevention lever - download reputation, prevalence-based execution blocking, and software-source policy - alongside the detective work.
