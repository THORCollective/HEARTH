false_positive_notes: |
  `msiexec.exe` runs constantly and legitimately in any managed estate. Software deployment, patching, Configuration Manager, Intune, Chocolatey and vendor updaters all invoke it many times a day, often with service parents and sometimes with switches that look unusual in isolation. The discriminator is not that `msiexec.exe` ran but that it ran without naming anything to install.

  The package-less invocation is not unique to malware either. `msiexec.exe /v`, repair and rollback operations, and the `/y` and `/z` DLL-registration switches can appear without a visible package path, and some installers re-launch `msiexec.exe` as a child with internal arguments. Build the baseline of how `msiexec.exe` is legitimately called in your estate first, because that baseline is what makes the empty-command-line case stand out.

  Named pipes are extremely high-volume and almost entirely benign. Windows itself, RPC, every EDR agent, SQL Server, print services and most enterprise software create pipes continuously, so pipe creation alone is pure noise. The finding is a pipe created in the same process tree as a package-less installer host, not a pipe on its own.

  `notepad.exe` as a shellcode host is well-known tradecraft and widely abused beyond this family, so a `notepad.exe` anomaly here is weak attribution evidence even when it is a strong detection. Treat the host-process identity as a ranking signal rather than a family indicator.

  Kaspersky states plainly that the host process path can be changed. An allowlist or blocklist of image names will therefore be bypassed by an operator who edits one configuration field, and the next build may host its jobs in anything. The durable parts of this hunt are the structure - a process created solely to receive remote shellcode over a pipe - and the parent relationship, not the image name.

  The XOR key `604902af7b70b271` will not appear in standard telemetry at all, because payload bytes crossing a named pipe are not captured by any default endpoint event. It is included as forensic confirmation on a recovered sample or a memory image, not as a hunting input.
notes: |
  Leg one, the package-less installer (Sysmon 1 or 4688) - Core filter: `msiexec.exe` whose command line names no `.msi`, no `.msp` and no product GUID. This is the cheapest query in the hunt and the one most likely to fire first.

      DeviceProcessEvents
      | where Timestamp > ago(30d)
      | where FileName =~ "msiexec.exe"
      | where ProcessCommandLine !contains ".msi" and ProcessCommandLine !contains ".msp"
      | where ProcessCommandLine !matches regex @"\{[0-9A-Fa-f\-]{36}\}"
      | where InitiatingProcessFileName !in~ ("services.exe", "svchost.exe", "ccmexec.exe", "explorer.exe", "msiexec.exe")
      | project Timestamp, DeviceName, ProcessCommandLine, InitiatingProcessFileName,
                InitiatingProcessFolderPath, InitiatingProcessCommandLine, AccountName
      | order by Timestamp desc

  Thirty days is the whole Defender advanced hunting retention. The exclusion list is a starting point drawn from normal deployment parents and must be replaced with the estate's own inventory - leaving it generic will either hide the finding or flood the result. Rank by parent: a parent running from `C:\ProgramData`, a user profile directory, or a temporary path is the OpsAgent loader shape; a parent that is a signed deployment agent is almost certainly legitimate.

  Leg two, the pipe beside it (Sysmon 17 and 18) - Core filter: a named pipe created within seconds of the host process, by the same tree. Event 17 gives the creating process and Event 18 the connecting one, which matters because the implant and the hosted job sit on opposite ends - the implant creates the pipe and feeds shellcode in, the host process reads it. Both ends inside one process tree, with one end being a package-less `msiexec.exe`, is the structural finding. Kaspersky does not publish the pipe name for these jobs, so this leg has to be built on the relationship rather than on a string.

  Leg three, the injection (Sysmon 10). The job host is created and then written into, so a process-access handle onto the fresh `msiexec.exe` or `notepad.exe` is expected. Kaspersky describes two modes - Legacy, using `CreateProcessA` and `NtCreateThreadEx`, which also produces a Sysmon Event ID 8 remote-thread event; and DbgInjector, which creates the process in DEBUG state, sets a hardware breakpoint and redirects RIP without creating a new thread, producing no Event ID 8 at all. H517 covers that second mode in full. For this hunt the consequence is that a missing remote-thread event does not clear the host - check for the access handle regardless.

  Leg four, what the job actually was, for scoping. Map the host process to the likely command - `notepad.exe` indicates `monitor`, the keylogging command, which Kaspersky says manages keylogging through subcommands that start, stop and configure logging threads; `msiexec.exe` covers the rest, including `mimikatz_spawn`, `execute_assembly`, `pth_spawn`, `runpe` and `screenshot_service start`. Because nothing is embedded, an on-disk scan will not tell you which ran. Pivot instead to effects - LSASS access from the host process points at `mimikatz_spawn`; .NET runtime DLLs loading into a package-less `msiexec.exe` points at `execute_assembly`, since that command runs .NET shellcode via an injected loader; a logon-type-9 authentication or anomalous outbound SMB points at `pth_spawn`. Treat any confirmed hit as a credential compromise pending evidence otherwise, because the two most likely jobs both target credentials.

  Leg five, the C2 leg (Sysmon 3 or DeviceNetworkEvents). The shellcode arrives from the C2, so the implant - not necessarily the host process - holds a network connection at the time of the job. Kaspersky states the C2 protocol runs over WebSocket with TLS, and that the Rust rewrite initially communicates via HTTP POST requests to retrieve commands before an upgrade command establishes a persistent WebSocket connection over TLS. On infrastructure, the implant uses AWS-generated CloudFront CDN subdomains as C2 endpoints, and Kaspersky warns that because these domains operate on shared infrastructure, their underlying IP addresses cannot serve as reliable standalone IOCs. The published domains are `d19v1tntmz2i98[.]cloudfront[.]net` and `d35htktbyt7nxc[.]cloudfront[.]net`, plus `157.20.104[.]111`. Hunt the domains and the process-to-CloudFront relationship rather than the IP space.

  On-disk artefacts worth sweeping alongside. Kaspersky publishes the implant's staging paths, all of which use the same filename - `C:\ProgramData\Microsoft\Windows\Caches\syscache.dat`, `C:\Users\{username}\AppData\Local\Microsoft\Windows\Caches\syscache.dat`, `C:\Users\{username}\AppData\Local\Microsoft\CLR_v4.0\syscache.dat`, `{modulepath}\syscache.dat` and `{TempPath}\syscache.dat`. A file named `syscache.dat` in any of those trees is a direct indicator and is independent of this hunt's process logic.

  Scope note on existing coverage. A grep of every hunt body for a named pipe feeding shellcode returns nothing. `msiexec` appears in 30 hunt files, so the LOLBin itself is well covered, but on different mechanisms - the existing hunts address `msiexec` fetching a remote package, `msiexec` as an installer-based delivery vector, and `msiexec` in loader chains, none of which is a package-less `msiexec` created purely as an injection target fed over a pipe. H506 is the nearest structural neighbour in the corpus, covering a named pipe used as a local input channel into an interactive shell for a different actor, and H517 is the same implant's injection mode and the natural pivot from any hit here.

# H518

Kaspersky's analysis of OpsAgent contains a sentence that is really a detection brief: no command contains embedded mimikatz or PTH binaries.

The implant has a `mimikatz_spawn` command. It does not have Mimikatz. When an operator runs that command, OpsAgent creates a host process, creates a named pipe, and asks the C2 to send the shellcode down it, XOR-encrypted with the key `604902af7b70b271`. Kaspersky's read on why is straightforward — the design keeps the implant small and lets operators deliver custom payloads remotely. A signature-based sweep of the binary finds a small WebSocket client and nothing incriminating, because the incriminating part never touches disk.

The host process is, by default, `msiexec.exe`. For the keylogging command it is `notepad.exe` instead.

Which leaves a shape rather than a file. A Windows Installer process with nothing to install. A Notepad with no document. A named pipe created next to it a fraction of a second earlier by a parent that is not a deployment agent. And then, shortly after, something reading LSASS.

The image name is configurable and Kaspersky says so. The structure is not: to run remote shellcode in a separate process, you need a process that exists for no other reason, and a channel to feed it.

## Why

- A package-less `msiexec.exe` is a cheap, high-yield query that most estates have never run. Legitimate Windows Installer invocations overwhelmingly name an MSI, an MSP or a product GUID, so the absence of all three is a tight filter over an extremely noisy process name.
- The credential tooling is only ever in memory, which changes the response. Because nothing is embedded, file-based scanning and hash sweeps cannot tell you whether `mimikatz_spawn` ran. The process shape is the only durable evidence, and it has to be caught while the job host exists.
- The pipe and the host process are two events that are individually meaningless and jointly diagnostic. Pipe creation is among the noisiest things Windows does and a package-less installer has innocent variants — but one creating the other inside a second, from a non-deployment parent, has no benign version.
- It bridges to the injection problem next door. The same implant can host these jobs via DbgInjector, which creates no remote thread at all, so a hunter who checks only Sysmon Event ID 8 will see the job host and conclude nothing was injected into it.
- Finding the job host tells you what to reset. Mapping host image to likely command — `notepad.exe` to keylogging, `msiexec.exe` to credential dumping, pass-the-hash and .NET execution — converts a single process anomaly into a scoped set of follow-up questions about credentials, keystrokes and lateral movement.
- The file-path indicators cost nothing to add. `syscache.dat` under four named directory trees is a direct sweep that runs independently of all the process logic above and corroborates any shape-based hit.
