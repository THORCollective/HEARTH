false_positive_notes: |
  - Infrastructure-as-code pipelines (Terraform, CDK, Pulumi, CloudFormation) legitimately federate through GitHub OIDC, chain into deploy roles, and call `UpdateAssumeRolePolicy` when they manage roles. Some also call `CreateAccessKey` for legacy service users, such as SMTP or third-party integration users. The legitimate version usually has all of the following:
    - a protected default-branch or `environment:` subject
    - a stable session name
    - runner egress IPs
    - a change ticket or merged PR
    - the new key written to a secrets store in the same session (`CreateSecret` or `PutSecretValue`) and first used from known application infrastructure
    Baseline these per role and repository rather than excluding the IAM APIs.
  - Plan-on-PR workflows routinely assume read-only roles from `pull_request` subjects. Restrict the hunt to chains that reach an IAM write, not every PR-context federation.
  - Scheduled key-rotation jobs create keys too, but they normally run from Lambda or a dedicated rotation role, not from a GitHub OIDC chain.
  - A trust policy with `"AWS": "*"` is benign only when a restrictive condition is present, such as `aws:PrincipalOrgID` or an explicit account list. Review the condition block before dismissing it.
  - Do not depend on the `wfx-` session prefix or the `wfx-docs` branch name. They are campaign-specific and easy to change. The durable signal is a non-default-ref subject combined with role chaining and an IAM credential or trust write.
notes: |
  AWS CloudTrail management events (STS federation)
  - Core filter: event name `AssumeRoleWithWebIdentity`, identity provider ending in `token.actions.githubusercontent.com`, and a web identity subject of `repo:<org>/<repo>:pull_request` or `repo:<org>/<repo>:ref:refs/heads/<branch>`, where the branch is not the repository's default or release branch. Baseline out `ref:refs/heads/main`, `ref:refs/tags/*`, and `environment:<prod>` subjects per role. Adjust if your org has customized the OIDC subject template.
  - Triage values: `web identity subject`, `audience`, `role ARN`, `role session name`, `issued temporary access key ID`, `source IP address`, `user agent`.
  - Strong red flags:
    - A role session name starting with `wfx-`, or any name that differs from the role's baseline. The official credentials action defaults to `GitHubActions`.
    - A subject branch of `wfx-docs`, or any branch first seen in the last 24 hours.
    - An exchange from an IP outside GitHub-hosted runner ranges and your self-hosted runner egress.
  
  AWS CloudTrail (STS role chaining)
  - Core filter: event name `AssumeRole` where the caller is an assumed-role session whose `access key ID` matches an `issued temporary access key ID` from the federation step.
  - Correlation: follow the chain one hop at a time (caller key to issued key) for up to 60 minutes, because chained sessions are capped at one hour. Record every `target role ARN` and `recipient account ID`.
  - Strong red flags:
    - Hops into roles the repository has never deployed through.
    - Hops into a second AWS account.
    - Three or more distinct target roles within 5 minutes.
    - `AccessDenied` errors mixed with successes, which suggests someone is trying role ARNs taken from repository files.
  
  AWS CloudTrail (IAM persistence writes)
  - Core filter: event source `iam.amazonaws.com` with event name `CreateAccessKey` or `UpdateAssumeRolePolicy`, where the caller's chain traces back to a GitHub OIDC session from the first section. Widen to `CreateLoginProfile`, `PutRolePolicy`, and `AttachRolePolicy` for adjacent persistence.
  - Triage values: `target user name`, `new access key ID` (from the response), `role name`, `trust policy document`, `error code`.
  - Strong red flags:
    - A trust policy containing `"AWS": "*"` or `"Principal": "*"` with no organization condition.
    - A GitHub federated statement whose subject condition was widened to `repo:*`.
    - Keys created for human, admin, or break-glass users.
    - `LimitExceeded` errors against users who already hold two keys.
  
  AWS CloudTrail (post-persistence use)
  - Pivot: the first event signed with the `new access key ID`, plus any later `AssumeRole` into a role whose trust was rewritten.
  - Triage values: `source IP address`, `user agent`, `caller account ID`, the first API names called.
  - Strong red flags:
    - First use from VPS or VPN address space rather than runner or application egress.
    - An opening `GetCallerIdentity` followed by IAM or Secrets Manager enumeration.
    - An `AssumeRole` into the rewritten role from an account outside your AWS Organization.
  - Correlation: check IAM Access Analyzer for a new external-access finding on the same role.
  
  GitHub organization or enterprise audit log
  - Correlation: join the repository named in the subject claim, within 15 minutes before or after the STS event, to:
    - `workflows.delete_workflow_run` events
    - pushes of commits titled `ci: restore` or `ci: cleanup`
    - pull requests titled `docs: dependency audit notes`
  - Triage values: `actor`, `repository`, `workflow run ID`, `head branch`, `actor IP` (when IP disclosure is enabled).
  - Strong red flags: a run deleted within about a minute of finishing by the same actor who pushed the branch. In that case CloudTrail becomes the remaining record of what the job did in AWS.

# H488

The wfx-loot campaign (StepSecurity tracks it as WFX Phantom) began around 12:45 UTC on November 10, 2026. The operator used stolen credentials from 4,837 GitHub accounts to probe 61,764 repositories for write access. They did this by opening pull requests titled `docs: dependency audit notes` from a `wfx-docs` branch. Where the account had write access, they delivered an approximately 1,500-line shell stealer in one of three ways: modifying an existing workflow, adding a new workflow on a short-lived branch, or planting an npm install hook. Aikido confirmed secret theft from at least 1,835 targets. After the job ran, the operator pushed a `ci: restore` or `ci: cleanup` revert and deleted the workflow run and its logs, often within 12 to 60 seconds. That leaves little evidence inside GitHub.

The stealer collects Actions secrets, the workflow token, OIDC and runtime tokens, cloud credentials, and developer-tool credentials. It also exchanges GitHub OIDC tokens for temporary AWS, Azure, and GCP sessions. Public analyses describe the following AWS steps:
- Role sessions named `wfx-<pid>`.
- Chaining into other IAM roles referenced in the repository.
- Calling `iam:CreateAccessKey` to mint long-lived keys for IAM users.
- Calling `iam:UpdateAssumeRolePolicy` to rewrite role trust so that any principal can assume the role.

The defensive precondition is a role trust policy that accepts broad GitHub subjects, such as `repo:<org>/<repo>:*`. A policy like that accepts `pull_request` and arbitrary-branch subjects as readily as the protected default branch.

Session names, collection IPs, and PR titles can all change. Some things cannot: the token exchange must appear in CloudTrail as `AssumeRoleWithWebIdentity` with a subject claim that names the repository and ref, and persistence requires an IAM write API. This hunt follows that lineage from the federated session to the IAM credential or trust write, and then to the first use of whatever was created.

## Why

- Rotating GitHub secrets does not undo this. wfx-loot (November 10, 2026 onward) stole CI secrets from at least 1,835 repositories, and its AWS path turns a short OIDC job session into IAM user keys and opened trust policies that outlive both the run and secret rotation. Responders who only rotate GitHub secrets leave that AWS access in place.
- The hunt targets steps the operator cannot avoid, not rotating indicators. Session names, collection IPs, PR titles, and branch names can all change. But the federation must appear as `AssumeRoleWithWebIdentity` with a subject claim that names the repository and ref, and lasting access requires an IAM write such as `CreateAccessKey` or `UpdateAssumeRolePolicy`.
- The evidence is in default logging. CloudTrail management events record STS and IAM calls without data-event logging. Temporary access key IDs link each chained hop, and the new key ID in the `CreateAccessKey` response links directly to its first use. This holds even when the GitHub workflow run and logs were deleted within a minute.
- False positives are controllable with a per-role baseline. Legitimate IAM writes from CI come from protected-branch or environment subjects, with stable session names and runner egress, and the keys end up in a secrets store. A `pull_request` or newly created branch subject whose chain ends in a key minted for another user, or in a wildcard trust policy, has almost no legitimate baseline.
