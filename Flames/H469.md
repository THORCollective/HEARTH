title: "A browser extension presenting itself as a PDF viewer holds host permissions for every site, runs operator JavaScript inside a sandboxed iframe reached through an offscreen document, and keeps a WebSocket open to its controller for as long as the browser is running"
hypothesis: >-
  An operator who owns a browser extension does not need malware on the host. The extension is the implant: it asks for host permissions covering every site the user visits, declares a sandbox with a relaxed content-security policy so arbitrary operator JavaScript can be evaluated inside it, and uses an offscreen document to hold a persistent connection that outlives any single tab. Code arrives from the controller at runtime rather than shipping in the package, so the installed files are small and uninteresting and the capability lives entirely in what gets sent. The observable chain is an installed extension whose declared permission set is out of all proportion to its stated purpose, an extension installed from outside the official store or by a command-line utility rather than by the user, and a long-lived WebSocket from the browser to a destination that is not an approved service.

false_positive_notes: |
  Extensions are a legitimate and heavily used part of how people work, and broad permissions are genuinely common in useful software.
  - Many popular, legitimate extensions request host permissions for all sites. Password managers, ad blockers, accessibility tools, grammar checkers, screenshot tools and translation extensions all need to touch every page to do their job. Breadth of permission is the starting population, not the finding.
  - Extensions legitimately named for document handling exist in quantity. PDF utilities, viewers, converters and annotators are among the most-installed categories, so the name on its own means nothing - the comparison that matters is the name against the permission set.
  - Offscreen documents and sandboxed pages are documented, supported features. The offscreen document exists precisely because background service workers are short-lived, and sandboxed pages exist to run untrusted content. Legitimate extensions use both. The combination becomes interesting when the sandbox exists to evaluate code fetched from a remote host.
  - Extensions open WebSockets for legitimate reasons. Collaboration tools, live dashboards, chat integrations and developer tooling maintain persistent connections by design. Destination reputation and whether the service is approved does the work here, not the presence of the connection.
  - Developers load unpacked extensions constantly. On engineering workstations, developer mode and locally-loaded extensions are routine and expected. Treat developer populations separately rather than suppressing the signal estate-wide.
  - An extension inventory is only as good as its collection method. Enterprise browser reporting, endpoint agents and direct directory collection each miss different cases - notably unpacked extensions loaded from disk and extensions in secondary browser profiles. State which method was used, because a clean inventory from an incomplete collector is not a clean result.
notes: |
  Source reporting is Unit 42's November 2026 analysis of Falcon, a browser-focused command-and-control framework which Unit 42 assesses with high confidence to be a variant of the same core framework as PeckBirdy, reported by Trend Micro in January 2026. This hunt covers the extension; the credentialed-request and download-interception capabilities it enables are [[H470]]. The closest existing hunts are [[H305]], which covers installing a Chrome extension without the Web Store and the preference-validation problem that creates, [[H066]], which covers extensions impersonating legitimate software, and [[H271]], which covers native messaging host registration - a different bridge out of the browser. None of them cover the manifest-level permission and architecture profile this hunt keys on.
  Why the extension and not the implant - Falcon has two parts. There is a browser implant that runs in a page context, generated per session and obfuscated per victim, which Unit 42 describes as XOR encoding each character with a one-byte key and converting the result into integers - so the page-level artefact is a list of integers and a decoder, different every time, with nothing stable to match. And there is the extension, which is the durable, enumerable, inspectable half. The manifest is plain text on disk and does not change between victims, which is why the hunt targets it.
  Core filter 1, the permission-to-purpose mismatch - The single highest-value check, and it needs no telemetry beyond an inventory. Unit 42 reports the extension "masquerades as a PDF reader" using the name PDF Viewer, with the description Portable Document Format and version 2026.5.13.1, and that it "requests a total of 40 permissions that grant the operator full control over the victim browser", with `<all_urls>` in `host_permissions`. The hunt is therefore a ratio rather than a rule: rank installed extensions by declared permission count and host-permission breadth, then read the top of that list against what each extension claims to do. A document viewer does not need the browsing history, the download manager, the cookie store, the clipboard and every site. A triage collection on Windows:
  ```powershell
  $roots = @(
    "$env:LOCALAPPDATA\Google\Chrome\User Data",
    "$env:LOCALAPPDATA\Microsoft\Edge\User Data"
  )
  foreach ($root in $roots) {
    if (-not (Test-Path $root)) { continue }
    Get-ChildItem -Path $root -Filter 'manifest.json' -Recurse -ErrorAction SilentlyContinue |
      ForEach-Object {
        try { $m = Get-Content $_.FullName -Raw | ConvertFrom-Json } catch { return }
        [pscustomobject]@{
          Name        = $m.name
          Version     = $m.version
          PermCount   = @($m.permissions).Count
          HostPerms   = ($m.host_permissions -join ',')
          HasSandbox  = [bool]$m.sandbox
          HasOffscr   = (Test-Path (Join-Path $_.DirectoryName 'offscreen.html'))
          WebAccess   = ($m.web_accessible_resources | ConvertTo-Json -Compress -Depth 4)
          Path        = $_.DirectoryName
        }
      } |
      Sort-Object PermCount -Descending |
      Format-Table Name, Version, PermCount, HasSandbox, HasOffscr, HostPerms -AutoSize
  }
  ```
  Enumerate every browser profile, not just the default one. Triage values are the extension name and version, the permission count, the host-permission list, and whether the package contains an offscreen document and declares a sandbox.
  Core filter 2, the architecture fingerprint - More specific than permission breadth, and present in the package on disk. Unit 42 documents the structure: a background service worker creates an offscreen document, the offscreen document creates an iframe loading a sandboxed page, and the sandbox is where operator code is evaluated - Unit 42 notes "the sandbox acts as a code execution environment, allowing eval execution". The code itself is not shipped: the offscreen document "delays execution for 2 seconds to allow the message bus to be established before sending a request to the C2 server to download the Falcon implant", and the downloaded code is executed "by appending a script tag to the sandbox.html document body". A candidate package therefore carries a recognisable file set - Unit 42 lists 14 files including `sandbox.html`, `sandbox.js`, `offscreen.html`, `offscreen.js`, `background.js`, `content-script.js` and `analytics-core.js` - and the manifest declares both a sandbox and `web_accessible_resources`. The combination of a declared sandbox, an offscreen document, and a web-accessible script that the content script injects into every page is the fingerprint. Note that the file names are this framework operator convention and a rebuild can rename them; the structural combination is the durable part.
  Core filter 3, the page-context bridge - Unit 42 explains why the extension needs a web-accessible resource at all: the content script "runs in an isolated context and only has access to the webpage’s Document Object Model (DOM)" but not its JavaScript context, so to reach full page context it "injects a script tag into the page pointing to chrome-extension://<extension ID>/analytics-core.js". That injected file then hooks `window.fetch`, `XMLHttpRequest.open` and `XMLHttpRequest.send` to intercept requests and responses from the page and any third-party scripts on it. For a hunter, an extension that declares a script in `web_accessible_resources` and injects it into every page is doing something a page-scoped tool does not need to do, and it is the mechanism behind the credential and traffic collection.
  Core filter 4, how it got installed - Unit 42 states plainly that "we are currently unaware of how an operator is deploying these browser extensions" and that the operator likely tricks a target into installing it. There is, however, direct evidence of tooling: the management panel shows two uploaded tools, `firefox.zip` described as plugins for silently installing Firefox and `browser.exe` described as plugins for silently installing Chrome, and Unit 42 notes it has "not been able to recover a sample for further analysis". Hunt for the installation routes rather than the installer: browser processes launched with extension-loading or developer-mode switches, writes into the extension directories by a process that is not the browser or its updater, and writes to the browser extension-management and force-install policy keys by anything that is not the management agent. Expected, not observed by Unit 42: the mechanism those utilities use - the panel describes them but no sample was recovered, so any specific installation technique attributed to them would be an invention.
  Core filter 5, the connection that stays open - Unit 42 reports the implant "establishes a TLS encrypted WebSocket connection to maintain a persistent connection as long as the browser tab of the affected webpage is open" and sends `{"heartbeat":"1"}` every minute, resetting the timer on every inbound message - so, as Unit 42 notes, "an actively engaged session never emits standalone heartbeats". That last detail matters for a timing-based hunt: a fixed-interval beacon is only visible while the session is idle, and an operator actively working the session produces irregular traffic instead. Hunt for long-lived WebSocket upgrades from the browser process to destinations outside the approved service list, with attention to sessions whose duration tracks browser uptime rather than page lifetime. The extension-hosted connection is the durable one, because the offscreen document survives tab closure.
  Core filter 6, the collection surface, for scoping a confirmed case - Unit 42 documents what the extension gathers: the background service worker monitors the browser credential store, cookies, history and downloads, caching collected items first-in-first-out up to 500 intercepted requests; a clipboard hijacker adds listeners for every cut, copy and paste event and can apply operator-defined pattern replacements stored under a `clipboard_replacer_rules` key in extension local storage; a separate module scrapes direct messages from X and Twitter when the user is authenticated; and Discord messages, friend lists and Zalo chat databases are collected through the same passive network hooking. For a confirmed case this is the exposure list, and the clipboard replacement capability in particular needs calling out to the affected user, because it silently rewrites what they paste.
  Scope - Managed Windows and macOS endpoints running Chromium-family browsers and Firefox. Unit 42 reports the two extensions are functionally identical, so the hunt applies to both engines even though the manifest field names differ.

# H469

The extension is called PDF Viewer. Its description is Portable Document Format. Its icon is a document icon.

It requests forty permissions and host access to every site the victim visits.

Unit 42 found it as part of Falcon, a command-and-control framework built around the browser rather than the operating system. The package on disk is unremarkable — fourteen small files, nothing obviously malicious in them — because the capability does not ship with the extension. It is downloaded.

The route is worth following, because every step is a documented, supported browser feature. The background service worker creates an offscreen document, which exists so extensions can hold work that outlives a short-lived worker. The offscreen document builds a message bus, waits two seconds for it to settle, then fetches the implant code from the controller. It passes that code to a sandboxed iframe — sandboxes exist to run untrusted content, and this one is declared with a policy permitting `eval`. The sandbox appends the fetched code as a script tag and runs it. A TLS WebSocket opens to the controller and stays open.

Meanwhile the content script is injected into every page, and because it cannot reach a page's JavaScript context from its isolated world, it injects a second file — declared web-accessible in the manifest — directly into the page. That file hooks `fetch` and `XMLHttpRequest`, so every request and response on every page the victim loads passes through the operator's code.

Nothing here is an exploit. It is a manifest.

The implant in the page is obfuscated per victim and regenerated per session, so there is nothing stable to match on there. The extension is the opposite: a plain-text manifest, sitting on disk, saying exactly what it can do.

## Why

- **The manifest is a confession, and it is readable without any security tooling.** A document viewer asking for every site, the download manager, the cookie store, the credential store, the clipboard and the browsing history is a contradiction that needs no detection engineering — only an inventory and someone to read it.
- **The per-session obfuscation puts the detection in the wrong place if you let it.** The page implant is XOR-encoded with a per-session key and regenerated for every victim, which defeats signatures by construction. The extension does not change. Choosing which half to hunt is the whole design decision here.
- **Everything the operator uses is a supported feature, so nothing malfunctions or gets blocked.** Offscreen documents, sandboxed pages, web-accessible resources and content scripts are documented platform capabilities with legitimate uses. The platform is not being broken; it is being used exactly as specified, toward an end it was not designed for.
- **The code arrives at runtime, which means scanning the package tells you very little.** An installed-file hash, an archive review, even a careful read of the JavaScript in the bundle will not reveal the capability, because the capability is fetched from a server after installation. That pushes the hunt toward declared permissions and architecture rather than content.
- **The heartbeat is only regular when nobody is working.** A one-minute beacon sounds like an easy timing detection until you notice the timer resets on every inbound message. While an operator is actively in the session there are no standalone heartbeats at all, so interval analysis finds the idle sessions and misses the active ones.
- **The clipboard capability makes this an immediate user-safety conversation, not just an incident.** The extension can intercept every copy and paste and rewrite what lands, with operator-supplied rules. For a confirmed case that changes the remediation urgency and it changes what the affected person needs to be told.
