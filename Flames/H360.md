false_positive_notes: |
  A NetScaler legitimately originates a great deal of internal traffic — it is a proxy by trade. It health-checks backend services, authenticates users against LDAP, RADIUS, TACACS and Kerberos, resolves DNS, syncs time, writes syslog, and talks to management systems. So "appliance connects to internal host" is the appliance's job and is useless on its own. What is not its job is reaching destinations that are not configured as services or service groups in its own configuration. That gives the hunt a precise and auditable allowlist - the appliance's running configuration enumerates every backend it is supposed to contact, so any internal flow to an IP and port not present in that configuration is anomalous by the device's own definition. The strong secondary discriminators are protocol and port diversity (a service-group health check is narrow and repetitive; a pivot is broad and exploratory, often hitting 445, 3389, 22 and 1433) and direction of novelty (first-ever contact with a subnet the appliance has never touched). notes: |
  Platform: Citrix NetScaler ADC and Gateway appliances (FreeBSD-based management plane), plus the internal network the appliance fronts. Driven by Google Threat Intelligence Group / Mandiant, "Defending Against Active Exploitation of Citrix NetScaler ADC and Gateway Appliances" (29 September 2026), covering CVE-2026-88772 and CVE-2026-88771. Mandiant names two malware families - WHIPSHOT, a PHP web shell acting as the tunneling front end, and SLAPSHOT, a Python proxy and tunneler. The published artefacts - IPC files `/tmp/.uxdport` and `/tmp/.uxdlock`; the C2 request headers `HTTP_X_UX` and `HTTP_X_UX_[0-9]+` for chunked transport, alongside `HTTP_NSC_LDAP` and `HTTP_NSC_CLIENTTYPE`; loopback forwarding via `fsockopen` to `127.0.0.1`; and the launch command, published verbatim, `nohup <python> -c 'import base64;exec(base64.b64decode("<payload>"))' /tmp/.uxdport /tmp/.uxdlock > /dev/null 2>&1 </dev/null &`. Mandiant's YARA rule `G_APT_Tunneler_SLAPSHOT_1` documents the wire protocol verbs — `"open"`, `"conn"`, `"push"`, `"pull"`, `"exch"`, `"close"`, `"ping"` — and parameters `"sid"`, `"host"`, `"port"`, `"data"`, plus the `UXD_IDLE_EXIT` string. `G_APT_Backdoorwebshell_WHIPSHOT_1` keys on the `X_UX` headers together with the `/tmp/.uxd*` paths and `fsockopen`/`127.0.0.1`, at a filesize under 50KB. Mandiant published no ATT&CK IDs; the mappings here are assigned.
  Why the headers are the clever part - The front end takes its instructions from HTTP headers rather than from the URL or the body. Request data is chunked across `X-UX-1`, `X-UX-2` and so on, which means the request looks like a GET for a static asset, the URL in the access log is unremarkable, and no suspicious parameter ever appears in a query string. Header values are also the field least likely to be logged - most web access log formats record method, path, status and size, and nothing else. Mandiant's own observation that the operator scrubbed access-log lines for the staging paths is almost redundant given how little the log would have shown anyway.
  Appliance leg (primary) - Mandiant's published triage commands - `ls -la /tmp/.uxdport* /tmp/.uxdlock` and `ps aux | grep -E "python.*(\.uxd|uxdport|uxdlock|base64)"`. Generalise the process check rather than matching the literal filenames - any `python` process on a NetScaler with `-c` and `base64` on its command line, or any process launched with `nohup` and output redirected to `/dev/null` with stdin closed, is outside the appliance's normal process set. Triage - the process start time bounds when the tunnel went live; the IPC file mtimes bound when it was last used; and the parent process tells you whether it was launched from the webshell (web server user) or from a shell. Pair with the webshell configuration hunt in [[H358]] and the setuid root shell in [[H359]] — Mandiant observed all three on the same intrusions.
  Network leg (works without appliance access, and is the one a SIEM can run today) - Core filter - internal flows whose source is the appliance NSIP or a SNIP, to a destination IP and port pair that does not appear in the appliance's configured services, service groups, authentication servers, DNS, NTP or syslog targets. Triage fields - destination port distribution, count of distinct destinations per hour, first-seen date for each destination, and whether any flow carries an interactive protocol. Strong red flags - SMB (445), RDP (3389), SSH (22), WinRM (5985/5986) or database ports sourced from the appliance; a sudden widening in the number of distinct internal destinations the appliance contacts; and successful authentications on internal services whose source IP is the appliance for accounts that are not the appliance's service accounts.
  Sample KQL for the authentication pivot - `let applianceIPs = dynamic(["10.0.0.0"]); DeviceLogonEvents | where Timestamp > ago(30d) | where RemoteIP in (applianceIPs) | summarize logons = count(), accounts = make_set(AccountName, 50), hosts = dcount(DeviceName) by RemoteIP, LogonType | order by hosts desc` — replace the placeholder with the real NSIP and SNIPs. The appliance authenticating *to* internal hosts, as opposed to validating user credentials against a directory, is the signal; a NetScaler has no reason to log on to a file server.
  Hunting the stored front end - Where a file listing of the appliance web root is available, the WHIPSHOT front end is a sub-50KB file containing `X_UX` header references together with `fsockopen` and `127.0.0.1`. Because [[H358]] shows the file will not have a `.php` extension, search by content and by file type rather than by name — `grep -rl "X_UX" /var/netscaler/gui/ /netscaler/ns_gui/ /var/vpn/` is a short, high-yield pass that does not depend on knowing the extension the operator chose.
  Relationship to existing tunneling hunts - HEARTH's existing protocol-tunneling coverage is endpoint-centric and keys on a tunneling binary being staged and run on a host with an agent. This hunt is about an appliance with no agent being turned into the proxy itself, where the inbound leg is indistinguishable from legitimate portal traffic and the only internal evidence is the appliance appearing as a source in places it has never been. The detection content is therefore network-side and configuration-side, not process-side.

# H360

The NetScaler intrusions Mandiant documented in September 2026 did not stop at a webshell. They turned the appliance into a proxy.

The front end is WHIPSHOT, a PHP file reached through the normal HTTPS portal. It takes its input from custom headers — `X-UX`, and `X-UX-1`, `X-UX-2` and so on for chunking — rather than from the URL or the request body, then forwards the data over loopback with `fsockopen` to `127.0.0.1`. The back end is SLAPSHOT, a Python daemon launched with `nohup <python> -c 'import base64;exec(base64.b64decode("<payload>"))' /tmp/.uxdport /tmp/.uxdlock > /dev/null 2>&1 &`, which finds the front end through those two `/tmp` files and opens the real connections to internal hosts. Its wire protocol is small and legible in Mandiant's YARA rule: `open`, `conn`, `push`, `pull`, `exch`, `close`, `ping`, with `sid`, `host`, `port` and `data`.

What this buys the operator is a tunnel whose inbound leg is ordinary TLS to a VPN portal that is supposed to receive ordinary TLS from the internet, and whose outbound leg is sourced from a device that is supposed to talk to internal servers. Both halves look like the appliance doing its job.

The asymmetry a hunter can exploit is that the appliance's own configuration is an explicit, auditable list of every internal destination it is meant to contact. Traffic outside that list is the tunnel.

## Why

- **Both legs hide inside the device's legitimate role.** An appliance receiving internet TLS and originating internal connections is not an anomaly in the abstract. Only the *destinations* betray it — which is why the appliance's configured service list is the right allowlist.
- **The headers evade the logs you keep.** Standard access log formats record method, path, status and size, not header values. Command data carried in `X-UX` headers leaves nothing incriminating in the log even before the operator scrubs it.
- **No agent, no process telemetry.** EDR does not run on a NetScaler, so the Python daemon, the IPC files and the backgrounded base64 exec are only visible to someone who looks on the box. This hunt therefore has to be written as appliance commands, and Mandiant published them.
- **The internal leg is the detection most organisations can actually run.** NetFlow and authentication logs already exist, already contain the appliance's IP, and will show the pivot without anyone touching the device — useful when the appliance is managed by another team or a vendor.
- **Port diversity is a durable discriminator.** Health checks are narrow and repetitive; a human pivoting is broad and exploratory. A step change in the number of distinct internal destinations and ports the appliance touches does not depend on knowing this malware family.
- **It changes the blast radius of the compromise.** A webshell on the edge is bad; a routed path from the internet into the internal network through a trusted device is an intrusion into everything behind it, and it should be scoped and contained as such.
