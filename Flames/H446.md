false_positive_notes: |
  Enabling an inference service is a normal thing for a developer to do, and this hunt is only workable in organisations that can say which projects are *supposed* to have it. Expect:
  - Genuine first use. A team starting an AI project enables the service, creates a key and runs a smoke test. The separators are the identity type (a human principal in a dev project, not a service account in a production project), the absence of a region fan-out, and the spend curve that follows - a smoke test produces cents, not a vertical line.
  - Infrastructure-as-code. Terraform, Pulumi and Deployment Manager enable services as a side effect of applying a module, often several at once, from a CI identity. These are recognisable by the enablement arriving in a batch with unrelated services, by the user agent, and by a matching pipeline run. Allowlist the CI service account *and* require the enablement to be absent from the repository's committed configuration before escalating.
  - Cloud-provider-initiated enablement. Some services get enabled transitively when another is enabled, or during a provider migration. These show the provider's own principal or a service agent as the caller rather than a customer identity.
  - Sandbox and training accounts, where enablement is constant and expected. Scope this hunt out of them explicitly rather than tuning it down everywhere.
  The sharpest reduction is to invert the logic: rather than alerting on enablement, maintain the allowlist of (project, service, region) tuples that should exist and alert on anything outside it. That turns a noisy event into a short, stable exception list.

Triage values: `userIdentity.type`, `userIdentity.arn`, `userIdentity.accessKeyId`, `sourceIPAddress`, `userAgent`, `awsRegion`, `requestParameters`, `errorCode`. Correlation: within 60 minutes of the entitlement call, look for `iam:CreateAccessKey`, `iam:CreateUser`, `iam:AttachUserPolicy` or `sts:GetFederationToken` by the same `accessKeyId`, then for `bedrock:InvokeModel` / `InvokeModelWithResponseStream` from the new key. Strong red flags: the same entitlement call repeated across three or more regions inside an hour; `errorCode` `AccessDenied` on the first region followed by a success in another (region shopping); an `accessKeyId` beginning `ASIA` (a temporary session) performing the enablement.
  Google Cloud Audit Logs - Core filter: `protoPayload.methodName` `google.api.serviceusage.v1.ServiceUsage.EnableService` where `protoPayload.request.serviceIds` or the resource name includes `aiplatform.googleapis.com` or `generativelanguage.googleapis.com`, in a project with no prior enablement. Triage values: `protoPayload.authenticationInfo.principalEmail`, `protoPayload.requestMetadata.callerIp`, `callerSuppliedUserAgent`, `resource.labels.project_id`, `protoPayload.authorizationInfo`. Correlation: within the same hour, `google.api.apikeys.v2.ApiKeys.CreateKey`, `google.iam.admin.v1.CreateServiceAccountKey`, or `SetIamPolicy` granting `roles/aiplatform.user`. Strong red flags: the principal is a service account whose name suggests an unrelated function; `callerSuppliedUserAgent` is a generic HTTP client rather than a Google SDK or the console; the enabling principal is one that was itself created in the previous 24 hours.
  Azure Activity log - Core filter: `Microsoft.CognitiveServices/accounts/write` creating an AI Foundry or OpenAI resource, or `.../deployments/write` creating a model deployment, in a subscription with no prior AI resource. Triage values: `caller`, `callerIpAddress`, `identity.claims.appid`, `resourceGroup`, `properties.requestbody`, `status`. Correlation: `Microsoft.CognitiveServices/accounts/listKeys/action` and `Microsoft.CognitiveServices/accounts/regenerateKey/action` by the same caller shortly after, and a deployment of a premium model SKU. Strong red flags: the caller is a service principal; the resource is created in a region the subscription has no other resources in.
  Billing as the confirming signal - Core filter: hourly cost per project per AI service, flagged when a service that billed `$0` in the previous 30 days bills anything at all, and separately when hourly spend exceeds that project's prior 30-day maximum. Mandiant reports charges "exceeding $100,000 USD in a single day, with cumulative charges at some organizations reaching $1 million USD before access was revoked", so a daily budget alert is too coarse to be useful here - set the granularity to one hour. Note that cloud billing data lands with a delay (typically hours), which is why the control-plane enablement event, not the bill, is the primary detection; use spend to confirm and to size the incident.
  Pivot to the data plane - Core filter: once an unauthorised enablement is confirmed, pull every inference invocation for that project and key. Mandiant observed an actor who "subscribed victim accounts to Pay-As-You-Go agreements, selecting premium foundation models and launching high-volume inference streams", and another who "executed more than 500,000 LLM API calls in less than eight hours". HEARTH's M040 scores the invocation side of this per principal, region and model; this hunt is upstream of it and fires on the control plane, which is the only part that is still quiet.
  Expected, not observed by Mandiant: enablement of a *self-hosted* inference stack inside the victim environment (a GPU instance running vLLM or Ollama provisioned by the stolen identity) should produce the analogous signal in compute provisioning rather than service enablement. Mandiant does report GPU provisioning and quota-increase requests in the same intrusions; it does not describe the enablement of a self-hosted serving stack as the detection point.

# H446

Google Threat Intelligence Group reports a class of intrusion it calls LLMJacking: financially motivated actors who compromise cloud identities and monetise the victim's access to foundation models, either by running their own inference on the victim's bill or by reselling that access through "LLM Mixers" - routing gateways that pool stolen keys and sell access to underground subscribers. GTIG observed "fraudulent charges associated with resource consumption exceeding $100,000 USD in a single day, with cumulative charges at some organizations reaching $1 million USD before access was revoked."

The detection opportunity GTIG highlights is specific, and it is not where most organisations are looking. In its own words: "In multiple incidents that Mandiant investigated, LLM services were not enabled at the time of compromise. Abuse of access keys allowed the threat actor to modify and enable LLM API services (e.g. Bedrock, Gemini API, etc.). Once enabled, the threat actor can use the APIs to generate massive bills to the organization in just minutes or hours." GTIG's guidance is to "prioritize detection of modifications to LLM accounts and services and treat any unauthorized enablement as a critical security event."

That inverts the usual assumption. A monitoring programme built around anomalous *inference usage* has nothing to compare against in a project that has never run inference - there is no baseline, no normal model mix, no normal spend. The enablement call is the moment a project acquires an AI attack surface, and it is a single, low-volume, high-fidelity control-plane event in every major cloud.

This hunt is deliberately upstream of HEARTH's M040, which models managed-inference invocations per principal on enumerate-then-invoke sequencing, region novelty and burst shape. M040 cannot see this at all: it begins once inference calls exist. Here the signal is that a service was turned on, a key was minted to use it, and nobody asked for either.

## Why

- Spend is the slowest alarm in the chain. GTIG reports six-figure charges inside a single day, and cloud billing data arrives hours late, so a budget alert is a post-mortem. The enablement call is logged within seconds of being made.
- Service enablement is rare and attributable. In a project that already runs AI workloads it is a one-time event; in a project that does not, it should never happen. That makes it one of the few cloud control-plane events where an exception-list approach - allowlist the (project, service, region) tuples that are meant to exist - is genuinely practical rather than aspirational.
- The follow-on key creation ties the enablement to intent. GTIG reports that "UNC6993 attempted to generate additional API keys and enable associated services within victim cloud projects, quickly accumulating over $100,000 USD in billing charges." Enablement plus key minting by the same non-human identity in the same window is a much narrower claim than either event alone.
- This is now a durable adversary objective rather than an opportunistic one. GTIG tracks a division of labour between access brokers and the operators who monetise the access, and assesses that actors "will increasingly prioritize LLMJacking over traditional resource theft like cryptojacking, driven by the immediate, high-margin monetization enabled by emerging underground LLM Mixers." A detection built on the enablement step survives changes in which models and which resale ecosystem are fashionable.
