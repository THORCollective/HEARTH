  MQTT is a real protocol with real business users, so the hunt must be scoped rather than fired blindly on port 8883. Genuine MQTT clients cluster in three populations, and each should be enumerated once and recorded rather than re-triaged weekly. First, OT, building-management and IoT gateways — HVAC controllers, badge readers, digital signage, manufacturing historians — legitimately speak MQTT, but they are a small, static, well-known set of hosts that almost never overlaps with the general workstation and server estate; if MQTT appears on a finance laptop or a domain controller, the population argument alone is decisive. Second, a handful of commercial agents embed MQTT for telemetry, but they connect to a vendor-owned broker hostname, not to `broker.hivemq.com`, which is a free public test broker with no legitimate enterprise role — treat any connection to a public test broker as in-scope regardless of which process made it. Third, developers genuinely do test against `broker.hivemq.com` while learning the protocol; this is the one recurring benign match, and it is distinguishable because the connecting process is an interpreter, an IDE or a CLI tool running from a user profile, the session is short, and it is not backed by a service registration. # H309

Kaspersky's Securelist documented the Toy Ghouls cluster deploying a pair of Rust backdoors — `mqtt-bird-agent` and `matrix-bird-agent` — delivered over WinRM with Evil-WinRM and WinRM-fs, installed as Windows services under names that impersonate stock Microsoft components, and driven entirely over third-party messaging infrastructure. This hunt targets the MQTT variant. Its design goal is to own no infrastructure at all: the C2 rendezvous is `broker.hivemq.com`, a free public MQTT broker intended for protocol testing, reached on TCP 8883 with ordinary TLS. Status, metrics, command-request and command-response each ride a distinct topic path keyed by a per-victim cluster identifier. Against a control stack tuned for attacker-registered domains, young certificates and anomalous TLS, that destination is invisible — it is a real service with a real reputation. The detectable part is the host: a service binary in `%PROGRAMDATA%`, a `config.toml` beside it, a ChaCha20-Poly1305 sealed configuration in the registry keyed to the machine's own `MachineGuid`, and a long-lived 8883 session opened by a process that `services.exe` started.

## Why

- **It defeats the reputation layer by construction, not by evasion.** Nothing about `broker.hivemq.com` is suspicious and nothing needs to be — the adversary registered no domain, bought no certificate and stood up no server, so newly-observed-domain, NRD, DGA and certificate-age controls have nothing to score. Detection has to move to the endpoint and to the port, because the destination will never look wrong.
- **Port 8883 is a near-perfect discriminator in a normal enterprise.** MQTT's TLS port is IANA-registered and unambiguous, and the legitimate population that speaks it — OT gateways, building management, IoT concentrators — is small, static and knowable. A workstation, file server or domain controller opening 8883 is outside that population by definition, which turns a protocol port into a high-signal filter rather than a noisy one.
- **The persistence shape is self-incriminating independent of this campaign.** No in-box Windows service runs its binary from `%PROGRAMDATA%`. A service registration (7045/4697) whose `ImagePath` resolves there, while its display name claims to be a Control Panel or telemetry component, is worth hunting on its own merits and will survive every IOC rotation in this cluster.
- **The configuration artefacts give triage a decisive answer.** The implant writes `config.toml` on first run and then seals it into the registry under a key bound to `MachineGuid` — so the presence of both a plaintext TOML beside a service binary and an opaque `SealedConfig` blob is not something a responder has to interpret. It is either the implant mid-installation or it is not, and the machine-bound key means the evidence cannot be reconstructed from a copy taken off-host.
