hypothesis: >-
  A staged payload from a bundled installer registers a proxyware agent as a set of three SYSTEM-level scheduled tasks in a single burst - an agent task that runs at system startup with highest privileges, a watchdog task that re-launches the agent on a short recurring interval through a hidden non-interactive PowerShell script, and an updater task that runs hourly - then starts the agent task immediately rather than waiting for the next boot. The hunt is the burst and its shape, not the product name: three tasks created by one parent process within minutes, all running as SYSTEM with highest privileges, at least one of them invoking PowerShell with no visible window, pointing at binaries under a program directory created in the same session.

false_positive_notes: |
  Multi-task registration by one installer is exactly how legitimate software installs, so the volume here comes from software deployment rather than from attacks.
  - Enterprise agents routinely create an agent-plus-updater-plus-watchdog trio as SYSTEM with highest privileges. EDR and AV, backup clients, RMM tools, patch management, VPN clients, telemetry agents and driver updaters all do it. Allowlist by the triple of task path, action binary path and the binary's Authenticode signer, and refresh the list after each deployment wave.
  - Short-interval recurring tasks are not unusual on their own. Health checks, licence checks and inventory agents frequently run every five or ten minutes. The discriminator is the combination of a short interval with a script interpreter as the action and a parent that was itself a temporary file.
  - Hidden and non-interactive PowerShell is standard practice in legitimate administration, because showing a console window to a user running a SYSTEM task is undesirable. Treating hidden PowerShell as a finding by itself produces an unworkable queue; it is only meaningful here as one element of the burst.
  - Software bundled with a legitimate application can look identical to this chain, including distributed-compute clients that users genuinely opted into. Check whether the program directory also carries an uninstall entry, a publisher-signed binary and a plausible install path before escalating.
  - Managed software distribution produces fleet-wide bursts at the same moment. A burst that appears on hundreds of hosts within one deployment window is almost certainly a package; a burst on one host, parented by a process from a user temporary directory, is the case to work.
notes: |
  The reporting behind this hunt is Microsoft Threat Intelligence's November 3, 2026 analysis of a fake-download campaign that uses trojanized Inno Setup-style installers to deliver multiple monetization payloads in one session. See [[H457]] for the delivery half of the same campaign. In the WorldProxyPool branch a staged `eld4.exe` payload created three SYSTEM-level tasks for components under `C:\Program Files\WorldProxyPool\`.
  The reported task set, as Microsoft describes it - `WorldProxyPoolAgent` runs `sdk-agent.exe` at system startup as SYSTEM with highest privileges, and the installer also started it immediately with `schtasks.exe /Run`; `WorldProxyPoolWatchdog` runs a hidden, non-interactive PowerShell watchdog script every five minutes as SYSTEM with highest privileges; `WorldProxyPoolUpdater` runs `sdk-agent.updater.exe update` hourly as SYSTEM with highest privileges. The report names `watchdog.ps1` as a representative artefact and says the watchdog invokes PowerShell with hidden and non-interactive execution options. It does not print the exact switches, so the switch list in the query below is an expected form rather than an observed one - match on the behaviour (`<Hidden>` in the task XML, or any of the window-suppression switches) rather than on one spelling.
  The burst itself - Core filter: three or more scheduled tasks created inside a short window on one host, attributable to the same parent process, all with a SYSTEM principal and highest-privilege run level. Windows Security 4698 is the reliable source because the event body carries the whole task XML, so the principal, the run level, every trigger and the action command line are all in one record. Triage values are the task name and path, `<UserId>` or `<LogonType>` from the principal block, `<RunLevel>`, each `<Trigger>` with its interval, the `<Exec><Command>` and `<Arguments>`, the subject user who registered the task, and the process that issued the registration. Sample Defender XDR query for the burst shape:
  ```kql
  let lookback = 30d;
  DeviceEvents
  | where Timestamp > ago(lookback)
  | where ActionType == "ScheduledTaskCreated"
  | extend TaskName = tostring(parse_json(tostring(AdditionalFields)).TaskName)
  | summarize TaskNames = make_set(TaskName, 10), DistinctTasks = dcount(TaskName),
              FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
      by DeviceId, DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath,
         InitiatingProcessId, Window = bin(Timestamp, 10m)
  | where DistinctTasks >= 3
  | order by FirstSeen desc
  ```
  Confirm the `AdditionalFields` key name for task registrations in your own tenant before relying on it, since the payload shape of `DeviceEvents` varies by action type; the Security 4698 path needs no such check and should be the primary source where that log is collected. Strong red flags are an `InitiatingProcessFolderPath` under `%TEMP%` or an Inno temporary directory, and a burst where the three task names share a product-style prefix that does not appear in software inventory.
  The hidden watchdog - Core filter: a scheduled task whose action is `powershell.exe` or `pwsh.exe` and whose repetition interval is five or ten minutes, where the task XML sets `<Settings><Hidden>true</Hidden></Settings>` or the action line suppresses the window. Sample query over task creation events, with the switch list marked as expected rather than observed:
  ```kql
  let lookback = 30d;
  let hiddenSwitches = dynamic(["-w hidden", "-windowstyle hidden", "-WindowStyle Hidden",
                                "-noni", "-NonInteractive", "-nop", "-NoProfile"]);
  DeviceProcessEvents
  | where Timestamp > ago(lookback)
  | where InitiatingProcessFileName in~ ("svchost.exe", "taskeng.exe", "schtasks.exe")
  | where FileName in~ ("powershell.exe", "pwsh.exe")
  | where ProcessCommandLine has_any (hiddenSwitches)
  | where AccountName in~ ("system", "local system")
  | project Timestamp, DeviceId, DeviceName, AccountName, ProcessCommandLine,
            InitiatingProcessFileName, InitiatingProcessCommandLine, FolderPath
  | order by Timestamp desc
  ```
  A scheduled PowerShell action is launched by the Task Scheduler service, so the initiating process on a Defender XDR process event is `svchost.exe` under default settings on current Windows rather than `taskeng.exe`, which was the host on older builds - keep both plus `schtasks.exe` in the filter so the query works across a mixed fleet. To see what the watchdog script actually does, use PowerShell Script Block Logging Event ID 4104 and read `ScriptBlockText`: `DeviceEvents` with `ActionType == "PowerShellCommand"` records cmdlet names only, never script text or the contents of `watchdog.ps1`, and the most it can offer is a `make_set` of cmdlet names per process. Correlation: the watchdog exists to restart the agent, so expect repeated short-lived process creations of the agent binary at the task interval, which is itself a durable signal after the task is removed.
  Immediate start rather than next boot - Core filter: `schtasks.exe` executed with `/Run` within minutes of the registration of the same task name, or Microsoft-Windows-TaskScheduler/Operational Event ID 200 (action started) for a startup-trigger task with no intervening reboot. An installer that cannot wait for a reboot is a behavioural tell that distinguishes monetization payloads from managed software deployment, which generally can wait. Triage values are the `schtasks.exe` command line, its parent, and the interval between the 4698 and the action start.
  Where the agent lives and what it does - Core filter: a new directory under `C:\Program Files\` or `C:\Program Files (x86)\` created in the same session as the task burst, containing an agent binary, an updater binary and a PowerShell script, with uninstall metadata written under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\`. Microsoft reports that WorldProxyPool wrote uninstall metadata under its own registry key, which means the product is designed to look installed rather than hidden. Correlation: confirm the impact by pairing the host with egress telemetry - a proxyware agent routes third-party traffic through the device, so the flow signature is many short-lived inbound-initiated-looking sessions and a sustained outbound-to-inbound byte ratio unlike anything the user generates. Strong red flags are an agent binary with no Authenticode signature or a signer absent from software inventory, and sustained traffic from a workstation outside working hours at a volume the user's own activity cannot explain.

# H456

Microsoft Threat Intelligence published this campaign on November 3, 2026. Users searching for cracked commercial software, free games, activators, plugins and unofficial utilities run a trojanized Inno Setup-style installer, which delivers several monetized payloads - the delivery system calls them "offers" - during one installation session.

One of the three confirmed monetization branches installs WorldProxyPool, a proxyware agent that routes third-party internet traffic through the affected device. The staged payload that installs it does something that is easy to see once you are looking for it: it registers three scheduled tasks in one burst, all as SYSTEM with highest privileges, then immediately starts the first of them with `schtasks.exe /Run` instead of waiting for the next boot.

The middle task is the interesting one. It runs a PowerShell watchdog every five minutes with hidden, non-interactive execution options, whose job is to put the agent back if anything stops it. That single task supplies the persistence, the self-healing and the window suppression at once, and it is the reason removing the agent binary alone does not clear the host.

This hunt deliberately keys on the burst rather than on WorldProxyPool. Monetization branches rotate - Microsoft confirmed three in this campaign and the offer and download-network IDs change constantly - but an installer that wants an agent to survive on a machine it does not administer has few options other than a cluster of privileged tasks created at once.

## Why

- Three SYSTEM tasks registered by one parent process inside a few minutes is a narrow, countable shape that ordinary user activity never produces, and it is visible in a single Windows Security event type whose body contains the principal, the run level, the triggers and the action command line together.
- The watchdog is what makes the infection durable, and it is the part incident response most often misses. Deleting the agent binary while a five-minute SYSTEM task still exists to reinstall or restart it produces an apparently clean host that re-infects itself within minutes, so the task set has to be the unit of remediation.
- Hidden non-interactive PowerShell is unremarkable in isolation and damning in context. Alone it is how administrators avoid flashing consoles at users; as the action of a short-interval SYSTEM task created by a process running from a temporary directory it is a different claim entirely, which is why this hunt requires the combination.
- The impact is measurable independently of the artefacts. A proxyware agent exists to sell the host's bandwidth, so the same device shows a traffic profile - sustained, off-hours, third-party-destined - that no user story explains. That gives a second, orthogonal confirmation path if the task set has already been cleaned up.
- The entry point is user-driven and recurring, not a one-time exploit. As long as people search for cracked software, this delivery chain keeps arriving, with new offer IDs, new domains and new monetization partners behind the same installation behaviour.
