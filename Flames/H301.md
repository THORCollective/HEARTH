false_positive_notes: |
  SYSVOL does contain legitimate non-obvious files, and the first inventory will return a list that needs dispositioning rather than escalating. Expected and benign: logon, logoff, startup and shutdown scripts under the `Scripts\` directories, which are supposed to be there and may legitimately be `.bat`, `.vbs`, `.ps1` or `.cmd` — their presence is normal, though their CONTENT still deserves a read; custom ADM and ADMX administrative templates; Group Policy Preferences XML for drive maps, printers, scheduled tasks and registry settings; `GPT.INI`, `GptTmpl.inf` and `Registry.pol`; corporate wallpaper, screensaver and branding assets, which are a genuinely common legitimate reason for images to live in SYSVOL and are the single largest source of noise in this hunt; certificate and CRL files placed for autoenrolment; and software installation `.aas` files and MSI packages published through Group Policy Software Installation, which is a legacy but still-used deployment method that legitimately puts installers in or near SYSVOL. Each of these should be dispositioned once by path and hash and recorded in the baseline (B046), after which the hunt runs as a diff and produces almost nothing. Two structural notes that keep the false-positive rate low: DFSR replication and SYSVOL repair operations rewrite file timestamps across the tree without changing content, so hash rather than mtime is the reliable comparison field; and organisations that have never inventoried SYSVOL frequently find genuinely old abandoned content from migrations and departed administrators, which is not an attack but is worth removing, since it is precisely the clutter an attacker would hide a file among. Finally, a staged file is not always malicious even when unexpected — administrators do use SYSVOL as a convenient world-readable share, which is itself the misuse that makes the technique viable.
notes: |
  The core inventory query - Core filter: enumerate every file under `\\<domain>\SYSVOL\<domain>\Policies\` recursively and group by extension. The expected set is small: `.pol`, `.inf`, `.ini`, `.xml`, `.adm`, `.admx`, `.adml`, `.aas`, plus scripts inside `Scripts\Startup\`, `Scripts\Shutdown\`, `Scripts\Logon\` and `Scripts\Logoff\`. Everything else goes on a review list. Strong red flags in decreasing order of urgency - `.exe`, `.dll`, `.sys`, `.msi` or `.ps1` OUTSIDE the Scripts directories; archives (`.zip`, `.7z`, `.cab`); images and loose text files at the domain policies root rather than inside a policy subdirectory; any file whose owner is not an administrative principal or SYSTEM; and any file written within the last 30 days that does not correspond to a recorded change. In the Kaspersky PAYLOAD intrusion the staged files were `payload.jpg` and `hello.txt`, placed directly in the domain SYSVOL path and then referenced by wallpaper and lock-screen policy settings.
  Joining a staged file to the policy that distributes it - Core filter: extract every UNC path appearing in policy settings and join it against the file inventory. Sources for the UNC strings - the `Get-GPOReport` XML for user-facing settings, `Registry.pol` parsed for registry-policy values (wallpaper, lock screen, and any policy that takes a path), GPP XML files for drive maps and file copies, and the `Scripts.ini` / `psscripts.ini` files that register startup and logon scripts. Any UNC reference that resolves to a file NOT on the approved inventory is the finding. This join is the part of the hunt that distinguishes a file merely sitting in SYSVOL from a file the whole domain is actively being told to fetch.
  Monitoring the write, once the inventory is clean - Core filter: Security event 4663 with `Accesses: WriteData` or Sysmon event 11 on the policies tree. Triage values - `Object Name`, `Subject Account Name`, `Process Name`, `Subject Logon ID`. Strong red flags - a write by an account outside the GPO administrator allowlist from B046; a write from a WORKSTATION rather than a domain controller or management server; a write whose process is not a Group Policy management tool; and a write immediately followed by a 5136 modification to `gPCFileSysPath` or to a policy that references the new file. A SACL on the policies directory is a prerequisite for 4663 to fire at all — verify it exists, because its absence is the most common silent failure here and makes the inventory the only available control.
  The write-access question, independent of any staged file - Core filter: resolve effective write permissions on the SYSVOL policies tree and on each policy subdirectory. Only Domain Admins, Enterprise Admins, Domain Controllers and SYSTEM should hold write. Any other principal — a service account, a delegated OU admin group, `Authenticated Users` through an inherited misconfiguration — is a standing finding that should be remediated regardless of whether anything has been staged, because it converts a single compromised account into domain-wide code distribution. Enumerate this even when the file inventory comes back clean; it is the more durable result.
  Measuring blast radius after a hit - Core filter: once a staged file is identified, its distribution is measurable rather than estimated. Endpoint telemetry will show hosts reading the UNC path, and the Group Policy History registry key `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Group Policy\History\` records which policies each host processed and when. Because these keys persist on disk after the event log has rolled, they remain the reliable scoping pivot late in an investigation.
  Why the file-type check outperforms content analysis - The staged content is attacker-chosen and can be anything, so signature or reputation analysis of the file itself generalises poorly. The CONSTRAINT the attacker cannot escape is placement: for Group Policy to distribute the file to every domain member, it must sit in a share whose legitimate contents are a short and stable list. Hunting the type-versus-location mismatch is therefore durable across payloads, and it is one recursive directory listing — which makes it one of the highest-yield checks available per unit of effort in an Active Directory environment.

# H301

SYSVOL has a property no other share in an Active Directory environment has: every domain-joined machine reads it automatically, as SYSTEM, from a path Windows trusts by design. That is the point of the share — it is how Group Policy delivers its content. It is also, for an attacker who can write to it, a distribution channel that reaches the entire estate without a single host-to-host file transfer.

The Kaspersky PAYLOAD ransomware analysis shows the mechanic at its simplest. The operators placed two files, `payload.jpg` and `hello.txt`, directly in the domain SYSVOL path, then used Group Policy to point every machine's wallpaper and lock screen at them. No dropper, no lateral file copy, no endpoint process. Group Policy performed the distribution, and every host fetched the payload from a UNC path that its own security model treats as authoritative. The same channel carries anything else that can be referenced from a policy setting — a startup script, a GPP file copy, a published MSI.

What makes this worth hunting is an asymmetry the attacker cannot design around. The staged content is entirely under their control and can be anything, so analysing the file itself generalises badly. But the *placement* is forced: for Group Policy to distribute it, the file must sit in a share whose legitimate contents are a short and remarkably stable list — `Registry.pol`, `GptTmpl.inf`, `GPT.INI`, ADM and ADMX templates, GPP XML, and scripts inside the Scripts directories. An image, a loose text file, an archive or an executable outside that structure is anomalous on file type alone, before any behavioural reasoning, and finding it costs one recursive directory listing.

That is why this hunt leads with an inventory rather than a detection. Most organisations have never enumerated SYSVOL, and the first pass typically returns a mix of genuinely benign corporate branding assets, abandoned content from migrations long since completed, and occasionally something that should not be there — each of which is worth dispositioning once and recording. The second half of the hunt is the join that turns a curiosity into a finding: extract every UNC path referenced by a policy setting and match it against the inventory, because a file merely sitting in SYSVOL is untidy, while a file the entire domain is being instructed to fetch is a distribution event. The most durable output, though, is neither of those. It is the answer to who can write to the policies tree at all — a question that should have a very short answer and frequently does not. H300 covers the firewall-disable policy the same intrusion linked at the domain root, and B046 holds the SYSVOL file-type baseline this hunt diffs against.

## Why

- SYSVOL reaches every domain-joined machine automatically and with SYSTEM privileges, so write access to it is equivalent to code distribution across the estate — without any of the lateral movement, remote execution or file transfer that endpoint detection is built to catch.
- The attacker controls the payload but not its placement. Content analysis generalises poorly because the file can be anything; the type-versus-location mismatch is forced by the delivery mechanism and therefore stays true across payloads and campaigns.
- The legitimate file-type list is short and stable, which makes this one of the rare hunts answerable by inventory rather than by behavioural analysis. A single recursive listing produces a reviewable result, with no baseline period and no event correlation required.
- The UNC-reference join separates clutter from distribution. Matching every path referenced in policy settings against the file inventory identifies which staged files the domain is actively being told to fetch, which is the difference between an untidy share and an active delivery channel.
- The write-permission review is valuable whether or not anything is found. SYSVOL policies-tree write access belonging to anything other than the small expected set of administrative principals is a standing misconfiguration that turns one compromised account into domain-wide distribution, and it is remediable immediately.
- Blast radius is measurable rather than estimated. Group Policy History registry keys persist on each host after the event logs have rolled, so the set of machines that processed a given policy can be reconstructed late in an investigation — which is usually when the question is actually asked.
