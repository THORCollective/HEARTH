false_positive_notes: |
  api.github.com is one of the most heavily used API hosts in any organisation that writes software, and the hunt will return developer tooling in volume on any engineering estate. The filter that matters is not the destination but the initiating process and the host role - git, the GitHub CLI, package managers, IDEs, CI agents and update clients on developer workstations are the expected callers. A Java host process, a Python host process, Sandboxie Start, or the Sysinternals screen magnifier holding a sustained conversation with the GitHub API on a government file server is not.

  Legitimate automation does poll the GitHub API on a schedule, and some of it polls as often as this implant does, so request periodicity alone is a weak signal. Treat the sequence as the evidence instead - a label applied and removed on the same issue repeatedly, interleaved with repository contents reads, is not a shape any real client produces.

  The X-CSRF-TOKEN header is the strongest single discriminator but it is only visible where the proxy terminates TLS or the client is configured to log headers. Where that telemetry does not exist, the hunt degrades to process attribution plus the path sequence, which is still workable.

  Rate limiting and secondary rate limiting will make a real implant's traffic look bursty and irregular rather than smooth, so do not require a clean interval.

  GitHub Enterprise Server and GitHub Enterprise Cloud with data residency use different hostnames, so an estate that has moved off github.com entirely should treat any api.github.com traffic as unexpected by default, which makes this hunt considerably cheaper to run.

  Leg one, process attribution (Defender XDR DeviceNetworkEvents, or Sysmon 3 joined to Sysmon 1) - Core filter: outbound connections to api.github.com whose initiating process is not on the estate's expected GitHub-caller list, aggregated per device and process so a single curl invocation does not read the same as a resident channel.

      let devTools = dynamic(["git.exe","gh.exe","code.exe","devenv.exe","node.exe","python.exe",

      DeviceNetworkEvents
      | where Timestamp > ago(30d)
      | where RemoteUrl has "api.github.com" or RemoteUrl has "github.com"
      | where InitiatingProcessFileName !in~ (devTools)
      | summarize Connections = count(), FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
          by DeviceId, DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath,
             InitiatingProcessParentFileName
      | where Connections >= 10 and LastSeen - FirstSeen > 1h
      | order by Connections desc

  Defender advanced hunting retains 30 days, so `ago(30d)` is the widest window available; anything longer is silently truncated. Red flags in the result, in rough order of weight - the initiating process runs from a path under `C:\Windows\System32` or `C:\ProgramData` rather than a software installation directory; the process is a signed, legitimate binary whose name has nothing to do with development work, and the report names javaw.exe, start.exe, pythonw.exe and zoomit.exe as the four it observed; the parent is services.exe, meaning the channel is running as a Windows service; the host is a server or a non-developer workstation.

  Leg two, the request sequence (web proxy records for api.github.com) - Core filter, run as three separate searches over the same window and correlated on source host and session:

  - `POST /repos/<owner>/<repo>/issues` where the request body contains the literal word problem in the title field and the word code in the body field. These are two fixed English words in a JSON body, which makes the create request the most specific single artefact in the channel.
  - `POST` and `DELETE` on `/repos/<owner>/<repo>/issues/<number>/labels` and `/labels/bug`, repeating against the same issue number. A real client applies a label once. This implant applies and removes it as its keep-alive, and both requests carry a `?rd=` query parameter holding random alphanumeric characters, which the API ignores - no GitHub client library emits that parameter.
  - `GET /repos/<owner>/<repo>/contents` followed by `GET /repos/<owner>/<repo>/contents/main.<8 chars>.<4 chars>.js` and the `.kmap`, `.pmap`, `.apmap`, `.swp` and `.tmp` variants, plus `PUT` requests to the same naming pattern on a different repository. Two different repositories in the same session, one read-only and one written to, is the two-repository split the report describes.

  A proxy-side regular expression for the filename family, which is distinctive enough to stand on its own: `main\.[A-Za-z0-9]{8}(\.[A-Za-z0-9]{4})?\.js(\.(map|kmap|pmap|apmap|swp|tmp))?$`. Also search for the plug-in names `scr.ts`, `pr.ts`, `kl.ts`, `channel.ts`, `abchannel.ts` and `ab2channel.ts` as the final path element of a GitHub contents read - TypeScript files fetched through the Contents API by a non-developer process on a file server is not a thing that happens by accident.

  Header-level filters where TLS is terminated - any request to api.github.com carrying an `X-CSRF-TOKEN` header, and any request whose `Authorization` header uses the older `token ` prefix rather than `Bearer `. The commit message the implant writes is the literal string `commit from INSOMNIA`, which appears in the body of both the GitHub `PUT` and, per part two of the report, the Microsoft Graph `PUT` used by its sibling GraphDoor - a single string that catches both backdoors if commit payloads are logged.

  Leg three, tying it to disk - any host that leg one or leg two surfaces should be checked for the loader trio described in part one of the report, which H505 hunts directly - a legitimate signed executable, a sideloaded loader DLL from a fixed list of names, and an encrypted `config.ini` in the same directory. The pairing is what turns a proxy finding into an incident.

  Decryption chain, for anyone recovering artefacts rather than hunting live traffic - command files are Base64-decoded, then XOR-decrypted with the filename itself as the key, yielding JSON with a `key` field holding an AES key and a `sec` field holding the Base64-encoded, AES-256-ECB-encrypted command data. Results travel the same path in reverse. Plug-ins use a two-stage routine - AES-256-ECB with the hard-coded key `12345678901234567890123456789012`, then a rolling 16-byte XOR whose key for each block is the ciphertext of the preceding block, with a fixed initialisation key for the first. The filename-as-XOR-key design means a recovered filename is a recovered key.

  Scope note: H357 is the closest existing hunt and the overlap is deliberate - it also treats GitHub as a two-layer control channel with Contents API tasking and an Issues-based fallback. The distinctions are the ones a hunter would actually query on. H357 keys on a dead-drop resolver that activates after a 401 and searches Issues for date-matching text; this hunt keys on an always-on label-toggle heartbeat against a single issue number, a two-repository public-read and private-write split, the `main.<code>.js.*` filename family and the `X-CSRF-TOKEN` header. B064 is the baseline that makes either hunt cheap to run, and M036 covers multi-service dead-drop routing at the campaign level rather than one protocol. H504 covers the Ably half of the same implant's channel, which runs concurrently.

# H503

Kaspersky's GReAT published Operation ShadowCloud on 17 November 2026, in two parts. The campaign hit government organisations in Asia and Africa, using the legitimate MeshCentral agent to drop two new backdoors whose only distinguishing feature, from a network defender's point of view, is that neither one needs infrastructure you can block. This hunt covers the first: GitDoor, which runs its whole control channel through the GitHub REST API.

The design is worth understanding before querying it. Two repositories under one disposable account split the roles — a public one the implant reads tasking and plug-ins from, and a private one, reachable only with the embedded personal access token, that it writes results to. Identity and session come from a GitHub issue the implant opens on start, titled with a generated GUID and bodied with an eight-character victim code. The issue number from that response becomes the implant's handle, and the channel's keep-alive is applying and removing the `bug` label on it, over and over, each cycle followed by a read of the download repository's contents.

Everything that moves is a file whose name encodes who it is for and what channel it belongs to, with extensions `kmap`, `pmap`, `apmap`, `swp`, `tmp` or nothing at all, all of them dressed up as JavaScript and source-map files. The report lists nine throwaway GitHub accounts, the earliest created in September 2024, which places the infrastructure preparation at least two years before publication.

## Why

- The destination cannot be blocked and will not be. Any organisation that writes software needs `api.github.com`, and the implant's traffic is ordinary TLS to a universally allowlisted host. That removes the network-reputation layer entirely and leaves process attribution as the first real control — which is a question most estates can answer and almost none ask.
- The label-toggle loop is a protocol artefact no legitimate client produces. Applying and removing one label on one issue indefinitely, each request carrying a random cache-busting query parameter, is a heartbeat wearing an API's clothes. It is visible in proxy logs without decrypting anything.
- The `X-CSRF-TOKEN` header is a free discriminator. The GitHub REST API does not use it, so its presence on a request to `api.github.com` is a client that was written to look busy rather than one that read the documentation.
- The filename family ties network evidence to host evidence and to the sibling backdoor. The same `main.<code>.js.map` naming and the same `commit from INSOMNIA` commit message appear in GraphDoor's SharePoint uploads, so one regular expression spans both halves of the campaign.
- The command set behind the channel is a full intrusion toolkit, not a downloader — the report enumerates COFF modules for Mimikatz, browser cookie theft from process memory, PetitPotam coercion, service and scheduled-task creation, and an interactive WinPTY shell. Finding the channel early is the difference between a contained host and a domain.
