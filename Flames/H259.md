     Reading `"Claude Code-credentials"`, `"Chrome Safe Storage"`, `"Slack Safe Storage"`, or an SSO/VPN entry
     from a process that does not own it is the highest-fidelity variant of this hunt.

     and "...to Suspicious Web Service" rules cover this leg.

     (`--dangerously-skip-permissions` and equivalents) on a host that also produced a keychain read should be
     reviewed regardless of the outcome of steps 3–4; it is a standing control failure.
  6. CORROBORATE INTENT — read the agent's own session transcript / project files (e.g. under `~/.claude/`) to
     establish whether a human asked for this or whether it originated from injected instructions in repository
     content, an MCP tool response, or a fetched web page.

# H259

`security find-generic-password -a <user> -w -s "Claude Code-credentials"` prints an AI coding agent's OAuth token to standard output in cleartext. It uses an Apple-signed in-box binary, it needs no elevation, and — this is the awkward part — it is documented, expected behavior for the agent itself. Elastic says so plainly in the report this hunt comes from.

That means the string alone is worthless as a detection. The interesting question is not *was the command run* but *who ran it and what happened to the output*. When the parent chain is an interactive Terminal, a developer is pulling their own token. When the parent chain is a shell spawned by the agent — an agent launched with permission checks disabled — and the same session then POSTs to a Cloudflare quick tunnel that did not exist an hour ago, the answer is different.

HEARTH had no coverage of credential access against AI agent tooling at all: zero hunts referenced `find-generic-password`, and none treated a coding agent as an attacker-controlled parent process.

## Why

- **The trusted-parent problem is genuinely new and mostly unmonitored.** Detection engineering has spent a decade learning that Office spawning PowerShell is bad and that a signed binary in System32 is usually fine. A coding agent is a signed, user-approved, extremely-high-privilege process whose entire job is to spawn shells and read files. Every heuristic built around "unusual parent" reads it as normal, and it typically runs on the one endpoint in the estate that holds cloud keys, source access, and production credentials at once.
- **The credential being stolen is a bearer token for an agent that can execute code.** This is not a password to one SaaS app. An agent OAuth token can be replayed to drive the agent itself, which makes the credential access step and the execution step the same step. That collapses the usual dwell time between "stole a secret" and "used a secret."
- **Permission-bypass flags convert a human approval gate into nothing.** The normal design assumes a person confirms sensitive child-process execution. Running with `--dangerously-skip-permissions` or equivalent removes that, and it is a configuration you can hunt for directly and remediate — which makes this one of the rare hunts that also produces a concrete hardening action.
- **The service-ownership mismatch generalizes far past this one campaign.** "A process read a keychain service it does not own" is a durable, environment-independent claim. It catches infostealers reading `Chrome Safe Storage`, it catches an agent reading another agent's token, and it survives the attacker renaming binaries or changing tunnel providers. Elastic's building-block rules exist precisely because the raw event is too common; the ownership comparison is what turns it into signal.
