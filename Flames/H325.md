false_positive_notes: |
  `node` executing a `.js` file from a LaunchAgent is not by itself anomalous on a developer Mac — plenty of engineers run local services, watchers, language servers and self-built tooling out of `~/Library/LaunchAgents`, and some of those legitimately point at a script rather than an app bundle. That population is real and it is the reason the script-interpreter condition cannot stand alone. What removes nearly all of it in one step is the label reconciliation - a developer's own agent is labelled something like `com.<theirname>.<project>` or `local.<something>`, and critically it does NOT claim to be Microsoft, Intel, Adobe, Google or Apple. The precise, generalisable filter is therefore a reverse-DNS label whose domain component asserts a vendor identity that no installed application bundle identifier on that host corroborates. Two of the three observed labels fail that test in a way that is not even arguable - Intel Driver & Support Assistant has no macOS build whatsoever, so `com.intel.dsa.helper` on a Mac is impersonating software that cannot exist there, and Microsoft Edge's real updater is labelled `com.microsoft.EdgeUpdater` and ships a signed Mach-O, so `com.microsoft.edgeupdate` running `msedge_update.js` out of `~/.config/` is a masquerade with no benign counterpart. The third, `com.harsh.requireobject`, is a different kind of tell - it makes no vendor claim at all, and a personal-looking domain component in an agent nobody on the endpoint team can attribute to a named developer is worth a question regardless. Managed-software populations to expect and enumerate once - Jamf, Munki, Kandji, Microsoft AutoUpdate (`com.microsoft.autoupdate.helper` / `com.microsoft.update.agent`, which are genuine and signed), CrowdStrike, Zscaler, Docker, Homebrew services. Note also that the "harsh" and "intel" labels and every domain listed here are rotatable campaign detail - the structural conditions are not. An empty result is ambiguous in a specific way worth writing down - most macOS estates have no persistent file-creation telemetry over `~/Library/LaunchAgents/` at all, and a point-in-time `launchctl list` only shows what is currently loaded, so a clean sweep may mean the collection never existed rather than that the host is clean. Confirm you have ESF CREATE/WRITE coverage on those three directories before recording a true negative.

# H325

Securelist documented Mirage Kitten targeting aviation and FinTech organisations across the Middle East and Africa, with victims in Egypt, Ethiopia and Afghanistan, using a new malware set built around two Node.js RATs — NodeRabbit and PollCat. Initial access runs through LinkedIn recruiter personas who send "coding challenge" archives containing trojanized npm packages bundled directly into `node_modules`. On macOS the implant persists with user-level LaunchAgents, and the labels it chose are the interesting part. `com.intel.dsa.helper` claims to be Intel Driver & Support Assistant — a product that ships only for Windows and has no macOS build at all, so the label asserts the existence of software that cannot legitimately be on the machine. `com.microsoft.edgeupdate` claims to be Edge's updater, but Edge on macOS updates via `com.microsoft.EdgeUpdater` and a bundled signed binary, not a `.js` file executed out of `~/.config/microsoft-edge-update/`. The third, `com.harsh.requireobject.plist`, makes no vendor claim whatsoever; "harsh" reads as an operator or developer artefact left in the domain component of a reverse-DNS label. Underneath all three is the same structure — a LaunchAgent whose `ProgramArguments` invokes `node` against a script, rather than pointing at a signed application binary.

## Why

- **Two of these masquerades are semantically impossible, not merely suspicious.** A detection whose benign population is empty by construction is worth more than one tuned down to low volume. Intel Driver & Support Assistant does not exist for macOS, so nothing legitimate can ever produce `com.intel.dsa.helper` on a Mac; and Microsoft's real Edge updater has a different label and is a signed Mach-O, so the reported combination has no honest counterpart either. Both are standing rules, not hunt-and-tune exercises.
- **The reverse-DNS label is a claim the endpoint can be made to verify.** Every LaunchAgent label asserts an identity, and macOS already carries the ground truth to check it against — the `CFBundleIdentifier` of every installed application. Reconciling the domain component of each loaded label against that inventory converts a subjective "does this look odd?" into a mechanical join that a script can run fleet-wide. That is the part of this hunt that survives when the campaign rotates every filename and domain in the report.
- **The process name is legitimate, so image-name rules return nothing.** The agent is `node`, or a copied Node.js binary, which means any rule keyed on a suspicious executable name is blind here by design. The signal lives entirely in the argument vector and the launchd parentage — a script interpreter invoked by `launchd` against a `.js` file in `Application Support` or a dotfile directory. Writing the rule against argv is not a refinement; it is the only place the behaviour is visible.
- **`~/.config/` on macOS is a convention mismatch that gives the operator away.** Dotfile directories under `$HOME` are Linux and cross-platform tooling convention. Microsoft ships nothing to `~/.config/microsoft-edge-update/` on a Mac. A payload placed there reflects a codebase written for Linux and ported without adjusting its paths — the same tell that the Node.js runtime choice and the `node_modules` delivery both point at.
- **The plists are binary, which quietly defeats the obvious grep.** LaunchAgent plists are routinely stored in binary format, so a sweep that greps `~/Library/LaunchAgents/` for vendor strings returns clean on a compromised host. Reading them through `plutil -p` or converting to XML first is not a stylistic preference — it is the difference between a true negative and a collection failure that looks identical to one.
