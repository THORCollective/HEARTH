hypothesis: >-
  A selective watering hole does not serve an exploit; it serves a decision. Injected, obfuscated
  JavaScript on a legitimate site first checks that the visitor is on Windows and, in some builds, that
  the page domain matches the site the operator compromised, then loops a status request to an
  operator-controlled server on a fixed path carrying a timestamp parameter. The server's reply decides
  whether this visitor sees the attack: an HTTP 200 leaves the page alone, and no response causes the
  script to replace the page with a counterfeit Chrome certificate warning rendered in the site's own
  language, with an added install button. Clicking it POSTs the current URL to a second fixed path and
  starts an MSI download from a storage bucket the operator took over. After the installer runs, the
  implant calls a third fixed path, and the fake warning stops appearing for that visitor. The hunt is
  web-proxy shaped: three distinct URI paths on a host that is not the site, an MSI from cloud storage
  immediately after a legitimate-site visit, and an installer whose arrival has no software-request record.

required_data_sources:
  - 'Web proxy, secure web gateway or TLS-inspecting egress logs with full URI path and query string, referrer, HTTP method, response status and content type - the three callback paths are the detection and they are invisible in domain-only or SNI-only logging'
  - 'Proxy or gateway records of downloaded file type and size, including downloads from cloud storage providers, so an MSI retrieved from a storage bucket is identifiable and attributable to the session that preceded it'
  - 'Sysmon Event ID 11 and DeviceFileEvents for installer packages written to browser download directories, with the originating browser process as the writer'
  - 'Sysmon Event ID 1 and DeviceProcessEvents for msiexec executions and for any process whose parent lineage traces to a browser download, with full command lines'
  - 'Browser history and download telemetry where an endpoint agent collects it, so the legitimate site visited immediately before a download is recoverable during triage'
  - 'DNS query logs with the requesting host, so the operator host can be pivoted on across the estate even where proxy logging is incomplete'
  - 'Sysmon Event ID 12 and 13 and DeviceRegistryEvents for HKCU and HKLM Run key writes, which is the persistence location the delivered backdoor is reported to use'
  - 'An inventory of which hosts are permitted to install software and a record of software requests, so an installer arriving with no corresponding request is separable from sanctioned installation'
false_positive_notes: |
  The fixed paths are specific enough to be near-zero noise, but the surrounding behaviours - MSI downloads, certificate warnings, obfuscated page scripts - are all ordinary.
  - Real certificate warnings happen constantly, on internal sites with self-signed certificates, during certificate expiry, and behind TLS-inspecting proxies. A user reporting a certificate warning is not a finding. The finding is a certificate warning followed by a download, because a genuine Chrome interstitial does not offer an installer.
  - Obfuscated JavaScript is everywhere on the commercial web. Analytics, anti-bot, paywall and advertising code are all minified and frequently obfuscated with public services. Do not hunt obfuscation; hunt the three request paths, which are specific strings on hosts unrelated to the sites serving them.
  - Cloud storage is a normal software-distribution channel, and many legitimate vendors ship installers from buckets. The discriminator is sequence and provenance: a bucket download in the same session as a visit to an unrelated legitimate site, with no software-request record, on a host that does not normally install software.
  - Periodic requests to a third-party host with a cache-busting timestamp parameter are a common analytics and heartbeat pattern. Match on the path, not on the presence of a timestamp, or every telemetry beacon in the estate will match.
  - The three paths are one campaign's choices and will change. They are worth searching for directly today because they cost nothing and are unambiguous, but the durable form of this hunt is the sequence - legitimate-site visit, then third-party status requests, then a cloud-storage MSI, then a Run key write - which survives a rename.
  - The delivered backdoor is reported to check whether a browser is running before executing, so a host where the installer ran but the implant did not may show the download and nothing else. Absence of post-install activity does not mean the download was benign.
notes: |
  Source reporting is Check Point Research's November 10, 2026 report on CopperDragon, assessed as a possible digital quartermaster supplying the Sparrow framework to several China-nexus actors. This hunt covers the SilentDelivery cluster, which CPR reports beginning in early 2026 and targeting high-profile organizations mainly in Europe and Asia. CPR reports the compromised sites were "related to the government, shipping, and IT and research sectors", in one case exploited "using an XSS attack on an unsensitized input field", with targeting primarily in "the Czech Republic, Germany, France, Taiwan, Nepal, Hong Kong and Indonesia." The passive Windows implant from the same report is covered in [[H479]] and the post-exploitation host configuration in [[H484]].
  The lure, as CPR describes it - "The attackers first compromised legitimate websites frequently visited by their intended targets." When a visitor arrived, CPR reports, "a heavily obfuscated JavaScript payload injected into the page completely replaced the legitimate content with a Google Chrome SSL certificate warning" rendered in the language of the site, and the warning blocked access and instructed the user to install a certificate-repair utility, which "deployed either a previously undocumented backdoor called SquadC or, in some cases, a variant of SparrowDoor." The injected script is obfuscated with jsjiami, a public service, and CPR reports it "first checks whether the user is running Windows" and in some builds also verifies that the page domain matches the site the operator compromised.
  The three paths, which are the detection - CPR documents the full exchange. The script "starts a loop that repeatedly sends status-check requests to the C2 server at `/image-check?t=<datetime>`", and these "are used to fingerprint the user based on IP and geolocation and determine whether to continue the attack and hijack the webpage." The gating is inverted from what a reader expects: "if the server returns HTTP 200, the webpage is left unchanged and the user can access the website normally. If the server does not respond, the script hijacks the webpage and displays the fake certificate error." On the click, "the script sends a POST request to the C2 server at `/report-url`", carrying the compromised site's URL in its JSON body, while simultaneously starting "the download of an MSI package containing the next-stage backdoor from an attacker-controlled S3 bucket." CPR notes it identified "three S3 buckets that we believe were compromised by the threat actor" hosting that payload. Finally, "after the user executes the backdoor, it sends a request to the C2 server at `/register-ip`, indicating a successful compromise. The fake certificate error will not appear the next time the user visits the compromised website."
  No existing HEARTH coverage - Grepped the corpus for fake certificate errors, browser-rendered install lures and watering-hole delivery and found nothing on this access pattern. [[H277]] and [[H313]] cover ClickFix-style paste chains, which share the idea of a browser-presented instruction but differ entirely in mechanism: there the user copies and runs a command, here the user downloads and runs an installer, and the gating and reporting callbacks have no equivalent in the paste chains.
  Core filter 1, the three paths - The highest-value check, and a direct search. In proxy or gateway logs, hunt requests whose URI path is `/image-check` with a timestamp parameter, `/report-url` with method POST, or `/register-ip`, on any host. Triage values are the destination host, the referrer - which names the compromised legitimate site - the requesting internal host, the user, and whether a download followed. A `/report-url` POST is the strongest of the three because it only occurs after a click, so it marks a user who acted rather than one who was merely fingerprinted.
  Core filter 2, the download provenance - Hunt for MSI packages downloaded from cloud storage and written into a browser download directory, then correlate backwards to the site visited immediately before. CPR's chain means the referrer for the bucket download is the compromised legitimate site, which is an unusual pairing: a government, shipping or research site does not distribute installers from a third-party bucket. Where proxy logging records content type, filter on the installer type rather than on the extension, since the file name is operator-chosen.
  Core filter 3, the absent paper trail - The simplest and most generalisable check. Select every installer package written to a browser download directory in the window and join against software-request records and the list of hosts permitted to install software. An installer that arrived with no request, on a host whose user does not install software, is worth triaging regardless of which campaign delivered it.
  Core filter 4, the inverted gate, for interpreting what you find - The operator server returning 200 means the attack is withheld, and silence means it proceeds. The practical consequences are worth stating because they are counterintuitive. First, a host that made `/image-check` requests and saw no fake warning was still fingerprinted and still selected against, so it belongs in the investigation. Second, blocking the operator host at the proxy after the injection is present causes the script to see no response and therefore to hijack the page, so a block should be paired with getting the injection removed from the site rather than treated as sufficient on its own. CPR is explicit about the purpose of the gate: it lets the operator "control the attack and stop displaying the fake certificate error after a successful compromise, thus reducing the likelihood of raising the user's suspicions."
  Sample Defender XDR query for the callbacks and the download, within the 30-day advanced hunting retention and with the join bounded to one session rather than to the whole lookback:
  ```kusto
  let lookback = 30d;
  let callbacks =
      DeviceNetworkEvents
      | where Timestamp > ago(lookback)
      | where RemoteUrl has_any ("/image-check", "/report-url", "/register-ip")
      | project cb_time = Timestamp, DeviceId, DeviceName, RemoteUrl, RemoteIP,
                InitiatingProcessFileName;
  let installers =
      DeviceFileEvents
      | where Timestamp > ago(lookback)
      | where ActionType == "FileCreated"
      | where FileName endswith ".msi"
      | where InitiatingProcessFileName in~ ("chrome.exe", "msedge.exe", "firefox.exe", "brave.exe")
      | project dl_time = Timestamp, DeviceId, FileName, FolderPath, SHA256,
                InitiatingProcessFileName, FileOriginUrl;
  callbacks
  | join kind=leftouter installers on DeviceId
  | where isnull(dl_time) or dl_time between (cb_time .. cb_time + 30m)
  | summarize paths_seen = make_set(RemoteUrl, 10),
              operator_hosts = make_set(RemoteIP, 10),
              installers_seen = make_set(FileName, 10),
              origin_urls = make_set(FileOriginUrl, 10),
              first_seen = min(cb_time)
            by DeviceName
  | sort by first_seen desc
  ```
  The download join is a `leftouter` and bounded to thirty minutes for two separate reasons: a host that was fingerprinted but never shown the lure produces callbacks and no download and must still appear, and an unbounded join on DeviceId would pair a callback with an unrelated installer from a different week.
  The alternative delivery route, for scoping - CPR also found SquadC delivered by spear phishing, in an archive uploaded to VirusTotal from Indonesia and configured to reach the same address as the watering-hole chain. The archive contains an LNK named to look like a DOCX "abusing the ftp.exe LOLBin for command execution", a batch script carried as `_rels/info.dll` and executed through `ftp.exe`, a CAB holding the loader components as `_rels/.rels.log`, and an empty decoy PDF. An `ftp.exe` process executing a script file is a separate and very cheap check worth running alongside this hunt.
  What the implant does once installed, for corroboration - CPR reports SquadC "achieves persistence by manipulating the registry Run key under a key WindowsUpdateAssist", supports a small command set including directory listing via `cmd /C dir`, file write and delete, arbitrary command execution and full-screen screenshot capture, and "can be configured to run only if a browser is currently running on the host", checking process names against a fixed list of `chrome.exe`, `msedge.exe`, `edge.exe`, `firefox.exe` and `brave.exe`. That last check is a sandbox-evasion measure that follows from the delivery method, since a browser is expected to be open on a real victim.
  Expected, not observed by Check Point - The content of the MSI's custom actions and how the installer achieves execution of the loader. CPR describes the package as containing the next-stage backdoor and reports the loader's three-stage in-memory decryption, but does not document the installer internals, so filter 3 above keys on an unexplained installer rather than on an installer property.
  Scope - Any organisation whose staff browse sector-specific legitimate sites, which is all of them, and particularly government, shipping, research and IT organizations in the regions CPR names. The hunt depends entirely on URI-level egress logging; an environment with only domain-level or SNI-level records cannot run filters 1 and 2, and establishing that gap is a worthwhile outcome in itself.

# H485

The page you asked for is gone, and in its place is a Chrome certificate warning — in your own language, matching the version of Chrome you are running, blocking the site you came to read. It suggests you install a certificate fix.

Chrome has never offered to install anything.

Check Point traced this to the SilentDelivery cluster of the CopperDragon ecosystem: legitimate government, shipping, IT and research sites compromised specifically because the intended targets read them. Injected, obfuscated JavaScript checks you are on Windows, sometimes checks the page's own domain, and then asks the operator what to do about you.

That is the part worth pausing on, and the logic runs backwards from the intuition. The script polls a status path on the operator's server. If the server answers HTTP 200, the page is left alone and you read the site normally. If the server says nothing, the script hijacks the page and shows you the fake warning.

So the operator's silence is the attack, and the operator's reply is the mercy. It lets them fingerprint by address and geolocation, pick who is worth burning the lure on, and switch the warning off for anyone already compromised so nobody gets suspicious twice.

Click install, and the script POSTs the current URL to a second path while an MSI downloads from an S3 bucket the operators took over. Run it, and the implant calls a third path to register itself. The warning never appears for you again.

Three fixed paths. `/image-check` with a timestamp, a POST to `/report-url`, and `/register-ip`. They will change in the next campaign, so search for them today — it costs one query — and build the durable version around the sequence: a visit to a real site, then status requests to somewhere else, then an installer out of cloud storage that nobody requested.

One operational note. If you block the operator's host at the proxy while the injection is still on the site, the script sees no response, and the fake warning fires for everyone. Block it, but get the injection pulled too.

## Why

- **The three callback paths are unambiguous and almost free to check.** They are specific strings on hosts unrelated to the sites serving them, so a single proxy query separates fingerprinted hosts from clicked hosts — and the POST to the report path only happens after a human acted, which makes it the highest-value row in the result.
- **The delivery exploits nothing, so there is no vulnerability to patch.** The user downloads an installer and runs it, on a Windows host, from what looks like a browser security prompt. Patch level is irrelevant; the controls that matter are URI-level egress visibility and whether unrequested installers can arrive at all.
- **Operator gating means the lure is invisible to normal testing.** Browse the compromised site from a sandbox, a different country, or a cloud address, and the server will likely answer 200 and show you a clean page. A campaign that only fires for selected visitors will not reproduce for an analyst trying to confirm it, which is precisely why log-side hunting is the right approach.
- **Fingerprinted is not the same as untouched.** A host that made status requests and never saw the warning was still profiled and still considered. Treating only the hosts that downloaded something as in-scope understates the targeting, and the callback log is the only record that the rest were selected against.
- **The counterfeit interstitial is a strong teaching artefact.** Real certificate warnings are common and users are trained to click through them. One that offers software is categorically different, and that distinction is simple enough to put in front of staff — which is rare for an initial-access technique.
