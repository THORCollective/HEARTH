false_positive_notes: |
  Failure volume alone is a poor signal in any mail tenant and this hunt deliberately does not use it. Internet-exposed Exchange and M365 tenants absorb continuous opportunistic credential stuffing, so a baseline of thousands of daily failures against a handful of interfaces is normal and tells you nothing. The feature that carries signal is *distinct-interface breadth for one principal in a short window*, and that has a much shorter list of benign explanations. The real ones - a migration or coexistence period, where a mailbox genuinely authenticates through Autodiscover, EWS and MAPI as a client reconfigures itself, and hybrid environments where on-premises and cloud endpoints are both in play; a user with several legitimate clients at once, such as Outlook desktop, Outlook mobile, a native iOS or Android mail app over ActiveSync, and a third-party client over EWS or IMAP, which can plausibly touch four interfaces; mailbox-migration and archiving tooling, backup products, e-discovery and compliance scanners, and mail-enabled line-of-business integrations, all of which authenticate as service identities across EWS, MAPI and Remote PowerShell by design; and monitoring systems that synthetically probe multiple endpoints for availability, which are the closest benign analogue to this technique and should be allowlisted once by source identity and IP. The discriminators that survive - breadth above roughly five or six distinct interfaces for a *user* principal, failures concentrated at the start of the sequence with any success arriving late, a single source IP or ASN driving the whole fan-out, the sequence completing in minutes rather than spread across a working day, and the same source repeating the pattern across many different mailbox identities. Note also that success here is the dangerous outcome and may be a single event among many failures - rank on breadth and then read the whole sequence, rather than filtering to failures and losing the one line that matters.
notes: |
  Platform: Microsoft 365 / Office Suite and on-premises Exchange Server. Driven by CISA, FBI and partner advisory AA26-281A, "Chinese Government-linked Cyber Threat Actors Combine Automated and Hands-on Hacking Tools to Steal Sensitive Data" (released week of 8 October 2026), covering activity enabled by Integrity Technology Group. The advisory maps both T1110.001 Password Guessing and T1110.003 Password Spraying to this tool.
  Published interface list (AA26-281A, verbatim). EBurst is "an open source Python-based tool" used "to target accounts in the Microsoft Office365 Cloud environment," and it "compromises email accounts on Microsoft Exchange servers using multiple interfaces for password spraying [T1110.003] and password guessing [T1110.001] against each supplied email address." Based on the tool's own ReadMe, those interfaces are - Exchange Control Panel (ECP); Exchange Web Services (EWS); Offline Address Book (OAB); Outlook Web Access (OWA); Remote Procedure Call (RPC); Application Programming Interface (API); Messaging Application Programming Interface (MAPI); PowerShell; Autodiscover; and Microsoft-Server-ActiveSync. The advisory states plainly - "Network defenders should include these interfaces when defending against EBurst."
  Why breadth is the detection and count is not. Password spraying is already well covered as a volumetric problem, including in HEARTH - see [[H040]] for the RDP form of it. What makes EBurst distinct is the *protocol sweep per identity*. The tool is not guessing which password works, it is guessing which door is unlocked. Every one of these ten interfaces has its own authentication stack, its own throttling behaviour, its own Conditional Access applicability, and its own logging destination - which is exactly why trying all ten is worth the operator's time. For a defender that converts into a feature with almost no benign analogue - count `DISTINCT clientAppUsed` (or the on-premises virtual-directory equivalent) per `UserPrincipalName` per hour, and rank descending.
  Core filter, cloud. In Entra ID sign-in logs, aggregate non-interactive and interactive sign-ins by principal and hour, counting distinct `clientAppUsed` values. The legacy-auth values that map onto EBurst's interface list are the high-weight ones - `Exchange Web Services`, `Exchange ActiveSync`, `IMAP4`, `POP3`, `MAPI Over HTTP`, `Offline Address Book`, `Autodiscover`, `Exchange Online PowerShell`, `Other clients`. Triage fields - the distinct interface set, source IP and ASN, `ResultType` sequence in time order, whether Conditional Access was applied or reported "not applied" per interface, and the user agent string.
  Sample KQL - interface breadth per principal, ranked.
  `AADSignInEventsBeta | where Timestamp > ago(14d) | summarize Interfaces = make_set(ClientAppUsed), InterfaceCount = dcount(ClientAppUsed), Attempts = count(), Failures = countif(ErrorCode != 0), Successes = countif(ErrorCode == 0), SourceIPs = dcount(IPAddress), FirstSeen = min(Timestamp), LastSeen = max(Timestamp) by AccountUpn, bin(Timestamp, 1h) | where InterfaceCount >= 5 | extend WindowMinutes = datetime_diff('minute', LastSeen, FirstSeen) | order by InterfaceCount desc, Successes desc`
  Sample KQL - the inverse view, one source driving breadth across many identities.
  `AADSignInEventsBeta | where Timestamp > ago(14d) | summarize Identities = dcount(AccountUpn), Interfaces = dcount(ClientAppUsed), Successes = countif(ErrorCode == 0) by IPAddress, bin(Timestamp, 1h) | where Identities >= 5 and Interfaces >= 4 | order by Successes desc, Identities desc`
  Core filter, on-premises. The same shape reads out of IIS logs. Each interface is a distinct virtual directory - `/ecp`, `/EWS`, `/OAB`, `/owa`, `/rpc`, `/api`, `/mapi`, `/PowerShell`, `/Autodiscover`, `/Microsoft-Server-ActiveSync`. Count distinct virtual directories per `cs-username` per hour, with 401 and 403 status sequences, and join against Event ID 4625 on the Exchange server for the authentication-failure side. On-premises is where the technique is most likely to succeed, because interface-level throttling and modern-auth enforcement are both weaker there than in Exchange Online.
  What a confirmed hit means and where to pivot. The advisory's intrusion chain continues directly - SoftEther VPN installed for persistence and named `conhost.exe` or `dllhost.exe` to pass as a Windows binary [T1036.003], downloaded via PowerShell or LOLBins on Windows and `curl` or `wget` on Linux, configured to reconnect on startup. Then mailbox collection via a PHP bot built from `Curlc4.txt` that interfaces with the EWS API [T1114.002], and exfiltration of compressed, custom-encrypted mail archives, which is hunted separately in [[H370]]. A successful guess should therefore be walked forward to new authentication-method registration on the compromised identity, to any SoftEther or unexpected VPN client installation, and to the mail-archive staging in [[H370]]. The advisory also notes the actors restricted access to some exfiltrated data to IP addresses from Xiamen, China.
  Mitigations the advisory emphasises, which double as scoping questions. Implement MFA for all services; disable unused services and ports; apply timely patches. For this hunt specifically, the useful version is - which of these ten interfaces are still reachable, and which are exempt from Conditional Access? An interface that is reachable and unprotected is the one EBurst will succeed against, and enumerating them is a one-time exercise that tells you where to look first.
  Scope note. AA26-281A also maps T1595.002 Vulnerability Scanning for the actors' reconnaissance with BBScan, dirsearch, Fscan, ksubdomain, masscan, NMAP, OneForAll, ShuiZe, wpscan and the MicroScan platform. T1595.002 is `PRE` platform - adversary-side reconnaissance - so it cannot carry a host or tenant hunt under the platform-match rule and is deliberately not generated here.

# H369

The useful thing about EBurst is that it tells you what it is going to do. Its own ReadMe lists the interfaces.

Exchange Control Panel. Exchange Web Services. Offline Address Book. Outlook Web Access. RPC. The REST API. MAPI. Remote PowerShell. Autodiscover. ActiveSync. Ten of them, and per CISA's October 2026 advisory on activity enabled by Integrity Technology Group, the tool works each supplied email address through all of them.

That is a different operation from the password spray most detections are tuned for. A spray takes one password and walks it across a thousand accounts, staying under the per-account lockout threshold. EBurst does something closer to the opposite: it takes one identity and walks it across every front door the mail platform exposes, because those doors are not equivalent. Each has its own authentication stack, its own throttling, its own Conditional Access applicability, and — the part that matters most — its own logging destination. The operator is not guessing which password works. They are guessing which door is unlocked.

For a defender that is a gift, because the resulting telemetry has an almost unique shape. A real user has one mail client, and that client speaks one protocol. Nobody authenticates to ECP, then OAB, then MAPI, then ActiveSync, then Remote PowerShell inside the same few minutes. There is no human workflow that produces it and no legitimate client that needs to.

So the feature is breadth, not volume. Count distinct authentication interfaces per principal per hour and rank descending. Failure counts — the usual signal — are nearly worthless here, because any internet-facing mail tenant absorbs continuous opportunistic stuffing and the baseline is already thousands a day. Worse, filtering to failures can drop the single line that matters, since a successful guess is one success buried in a long sequence of failures.

CISA put the operational instruction plainly: "Network defenders should include these interfaces when defending against EBurst." The sharpest version of that advice is to go and find out which of the ten are still reachable in your tenant, and which are exempt from Conditional Access. Those are the ones the tool will succeed against.

## Why

- **The fan-out across protocols has no benign analogue at the high end.** One identity, five or more distinct authentication interfaces, inside an hour, from one source — a real mail client cannot generate this, and the few legitimate multi-interface cases are service identities and migrations that allowlist cleanly once.
- **It is a detection that does not depend on volume thresholds.** Lockout-evading sprays are specifically designed to stay under count-based rules. Breadth is orthogonal to rate, so an operator who slows down to avoid throttling still produces the signature.
- **Each interface logs somewhere different, which is why the operator tries them all.** That same fragmentation is the defender's problem too — the pattern is only visible once cloud sign-in logs and the ten on-premises virtual directories are read as one dataset. Assembling that view is most of the work.
- **The attempt sequence localises the weak door.** Reading failures and successes in time order across the interface set shows exactly which stack accepted the credential. That is both the incident answer and the hardening answer, from one query.
- **On-premises is where this succeeds.** Interface-level throttling and modern-auth enforcement are weaker on Exchange Server than in Exchange Online, so the IIS virtual-directory view deserves equal weight to the Entra sign-in view rather than being treated as the legacy case.
- **The inverse aggregation finds the campaign, not just the victim.** Grouping by source IP instead of by principal surfaces one operator sweeping many mailboxes — and CISA notes the actors restricted access to some exfiltrated data to addresses in Xiamen, China.
- **Success leads somewhere specific, so the pivot is known in advance.** The advisory's chain continues into SoftEther VPN persistence disguised as `conhost.exe` or `dllhost.exe`, EWS-based mailbox collection via a PHP bot, and custom-encrypted mail archives — the last of which is hunted in [[H370]].
