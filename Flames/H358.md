false_positive_notes: |
  A stock NetScaler appliance does not register non-PHP extensions as PHP, and does not alias `/vpn/media/` paths into `/var/netscaler/gui/vpn/scripts/`. Both directives are effectively zero-baseline, which is what makes this a high-confidence hunt rather than a scoring exercise. The realistic sources of noise are operational rather than benign-malicious ambiguity. Citrix firmware upgrades legitimately rewrite `httpd.conf`, so compare against the configuration shipped by the exact firmware build in use rather than against last month's copy of the file, and re-baseline after every upgrade. Customised VPN portal themes do place files under `/var/vpn/theme/` and can legitimately add assets — but they add images and stylesheets, not ASCII files that parse as PHP. Third-party monitoring or support bundles occasionally stage scripts on the appliance; confirm those with the vendor rather than dismissing them, because this is precisely the disguise the intrusion uses.   Platform: Citrix NetScaler ADC and Gateway appliances (FreeBSD-based). Driven by Google Threat Intelligence Group / Mandiant, "Defending Against Active Exploitation of Citrix NetScaler ADC and Gateway Appliances" (29 September 2026), covering exploitation of CVE-2026-88772 and CVE-2026-88771, with CVE-2026-88773 through CVE-2026-88778 referenced in the Citrix bulletin. Mandiant reports two distinct configuration-based persistence methods, published verbatim. Method A, package-handler masquerading - `php_flag engine on`, a `<FilesMatch "\.deb$">` block setting `Header set Cache-Control "no-cache"`, and `AddHandler application/x-httpd-php .deb`. Method B, icon aliasing and signature-file handling - `php_flag engine on#`, `AliasMatch ^/vpn/media/(.+).ico$ /var/netscaler/gui/vpn/scripts/linux/$1.sig`, and `AddHandler application/x-httpd-php .sig`. The staged filenames Mandiant lists include `nginstaller` (with numeric variants), `e6ee7c85.sig`, `nsgclient.sig`, `nsginstaller.deb` and `nsgclient.deb`. The PHP webshell family is WHIPSHOT; the Python proxy deployed alongside it is SLAPSHOT, hunted separately in [[H360]]. Mandiant published five YARA rules with this report; `G_Hunting_Config_NetScaler_PHP_1` targets exactly the configuration tampering this hunt describes, and `G_APT_Backdoorwebshell_WHIPSHOT_1` targets the webshell. Mandiant did not publish ATT&CK IDs for this report; the mappings here are assigned.
  Why the configuration is the right thing to hunt, not the file - Every appliance-compromise playbook says "search the web root for new PHP files". This intrusion defeats that completely. The dropped files end in `.deb`, `.sig` and `.ico`, so an extension-driven sweep skips them, a file-type expectation of "binary package" is satisfied by the name, and the files live in client plug-in staging directories that are supposed to contain installers. The thing that cannot be disguised is the instruction telling Apache to execute them, because it must be literal, it must sit in a configuration file the appliance parses, and there is no legitimate version of it.
  Configuration leg (primary) - Mandiant's own published command is the fastest first pass - `grep -En -i "application/x-httpd-php|php_flag|AliasMatch" /etc/httpd.conf`. Run the same grep against `/nsconfig/httpd.conf` and `/flash/nsconfig/httpd.conf`, because the persistent copies are what survive reboot and are what a restored-but-reinfected appliance will show. Triage - any `AddHandler`/`AddType` line whose extension is not `.php`; any `AliasMatch` whose target is under `/var/netscaler/gui/`, `/netscaler/ns_gui/` or `/var/vpn/`; any `php_flag engine on` in a context that did not previously have it, including the trailing-`#` variant Mandiant observed. Generalise past the two observed extensions - the detection is "a non-PHP extension registered as PHP", not "`.deb` or `.sig` registered as PHP", since the operator can pick any extension on the next appliance.
  File-inventory leg (independent of the configuration) - Mandiant's published triage commands - `file /var/netscaler/gui/vpn/scripts/linux/* /var/netscaler/gui/vpns/scripts/vista/* /var/netscaler/gui/vpns/scripts/mac/* /netscaler/ns_gui/vpn/media/* 2>/dev/null | grep -E "ASCII text|PHP script"` and `grep -rlE "<\?php|eval\(|base64_decode\(|shell_exec\(" /var/netscaler/gui/ /netscaler/ns_gui/ /var/vpn/ /netscaler/portal/ 2>/dev/null`. The first is the stronger of the two conceptually - those directories are meant to hold client installers and media, so *any* ASCII text file in them is an anomaly regardless of what it contains, which catches an obfuscated shell that the keyword grep would miss.
  Log leg (works without appliance shell access) - Mandiant's published commands - `grep -E -i "\.(deb|sig|rpm|tgz|sh|so|dat|ico|png|html)" /var/log/httperror*` and `grep -E "/vpn/media/|/vpn/scripts/|/vpn/theme/" /var/log/httpaccess.log* | awk '$9 ~ /200|404/ && $10 > 5000'`. The second encodes the key insight - a static-asset path returning a response larger than five kilobytes is command output, not an icon. That size-based angle is generalised into a scoring hunt in [[M054]], which is the better form where access logs are centralised and a per-path size distribution can be built.
  Corroborating appliance events - Mandiant reports that exploitation of CVE-2026-88772 bypasses authentication and triggers an unhandled termination of the NetScaler Packet Processing Engine. The resulting log lines are published verbatim - `qat0: Process <PID> NSPPE-<##> exit with orphan rings 5:500` followed by `pitboss[<##>]: pitboss <DATETIME> NOT restarting NSPPE-<##> (<PID>)` in `/var/log/messages`, and an `SSL_HANDSHAKE_FAILURE` entry citing `ClientVersion DTLSv1.0` and `CipherSuite "TLS1-AES-256-CBC-SHA"` with `Reason "Handshake failure-Internal Error"`. Core dumps under `/var/core/` from the same window are worth preserving before any reboot. These are exploitation-time artefacts, so they bound the intrusion start date even when the webshell itself is found weeks later.
  Response note - Because the persistence lives in configuration and, per [[H360]], in a setuid root shell, a firmware upgrade alone does not evict the attacker if the configuration is restored from a compromised backup. Treat a confirmed hit as requiring credential and session invalidation on the appliance, review of saved configuration files, and rotation of anything the appliance could see, not just patching.

# H358

Mandiant's September 2026 report on in-the-wild NetScaler exploitation describes a webshell that never appears as a webshell.

After exploiting CVE-2026-88772 for unauthenticated root, the operator edits the appliance's Apache configuration. One variant adds `php_flag engine on`, a `<FilesMatch "\.deb$">` block, and `AddHandler application/x-httpd-php .deb` — teaching the web server to execute Debian package files as PHP. Another adds `AliasMatch ^/vpn/media/(.+).ico$ /var/netscaler/gui/vpn/scripts/linux/$1.sig` together with `AddHandler application/x-httpd-php .sig`, so a request for what looks like a favicon under the VPN portal's media path is served by a PHP file sitting in the Linux client plug-in directory with a `.sig` extension.

The staged files are named to fit: `nsginstaller.deb`, `nsgclient.deb`, `nsgclient.sig`, `e6ee7c85.sig`, `nginstaller` with numeric suffixes. A responder sweeping the appliance for new `.php` files finds nothing. A responder listing the client plug-in directory sees installer-shaped names in the directory that holds installers.

What the operator cannot hide is the configuration line that makes any of it work. `AddHandler application/x-httpd-php` for anything other than `.php`, on a Citrix appliance, has no legitimate form — and Mandiant published the exact grep for it.

## Why

- **It defeats the standard appliance sweep.** "Find new PHP files in the web root" is the first move in every edge-device compromise playbook, and extension-based disguise plus a plug-in staging directory beats it outright. The handler directive is the only part that must be literal.
- **The baseline is zero, not low.** Stock NetScaler firmware registers no non-PHP extension as PHP and aliases no media path into a scripts directory. That makes this one of the rare hunts where a single grep match is a finding rather than a candidate.
- **It survives the obvious remediation.** Configuration-resident persistence comes back if a compromised saved configuration is restored, and it lives in files (`/nsconfig/httpd.conf`, `/flash/nsconfig/httpd.conf`) that administrators deliberately preserve across upgrades.
- **Edge appliances are where EDR is not.** There is no agent on a NetScaler, so the detection surface is its own configuration, its own logs and its own filesystem — which means the hunt has to be written as appliance commands, and Mandiant published them.
- **The file-type check generalises past the IOCs.** Asking "is there any ASCII text file in a directory that should hold only binaries" catches the next variant's extension choice without knowing it in advance.
- **The exploitation artefacts date the intrusion.** The NSPPE crash and `pitboss` non-restart lines, plus the DTLSv1.0 handshake failure, give a timestamp for initial access that is independent of the webshell's own file times, which the operator can trivially alter.
- **Log scrubbing means absence proves nothing.** Mandiant observed anti-forensic scrubbing of access-log lines for the staging paths, so the file and configuration legs have to be run even when the logs look clean.
