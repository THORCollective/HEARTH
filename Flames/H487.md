  Core filter 1, the label-location contradiction - The highest-value check, and it needs no knowledge of this framework. Enumerate every plist in `~/Library/LaunchAgents`, `/Library/LaunchAgents` and `/Library/LaunchDaemons` and parse the `Label` key. Any label beginning `com.apple.` in a user LaunchAgents directory is a contradiction, because Apple ships its agents in the system paths and never into a user Library directory. Triage values are the label, the path of the plist, the `ProgramArguments` target, whether `RunAtLoad` and `KeepAlive` are set, any `StartInterval`, the plist's creation time, and the signing state of the referenced binary.
  Core filter 2, what the agent points at - For every launch item not on the allowlist, collect the referenced executable's signing state. A launch item whose target is unsigned or ad-hoc signed, sits outside an application bundle, and carries an Apple-style label is the shape to escalate. `codesign -dvvv` gives the authority chain and team identifier and `spctl -a -vvv` gives the notarisation verdict; both are read-only and fast enough to run fleet-wide through a management platform.
  Core filter 3, the beacon variance - Confirmation rather than detection. For a host surfaced by filters 1 or 2, compute the standard deviation of inter-connection intervals per destination for the process the agent launches. Elastic reports a five-second check-in with no jitter, which produces a variance near zero - a shape neither human activity nor most legitimate polling produces, because almost everything that polls adds jitter or backs off. Compute the variance rather than matching five seconds, so the check survives the operator changing the default.
  Sample host-side enumeration, read-only, suitable for running through a management platform:
  ```bash
  set -u
  for dir in "$HOME/Library/LaunchAgents" /Library/LaunchAgents /Library/LaunchDaemons; do
    [ -d "$dir" ] || continue
    for plist in "$dir"/*.plist; do
      [ -e "$plist" ] || continue
      label=$(/usr/libexec/PlistBuddy -c 'Print :Label' "$plist" 2>/dev/null || echo "NO_LABEL")
      prog=$(/usr/libexec/PlistBuddy -c 'Print :ProgramArguments:0' "$plist" 2>/dev/null \
             || /usr/libexec/PlistBuddy -c 'Print :Program' "$plist" 2>/dev/null || echo "NONE")
      ral=$(/usr/libexec/PlistBuddy -c 'Print :RunAtLoad' "$plist" 2>/dev/null || echo "-")
      ka=$(/usr/libexec/PlistBuddy -c 'Print :KeepAlive' "$plist" 2>/dev/null || echo "-")
      si=$(/usr/libexec/PlistBuddy -c 'Print :StartInterval' "$plist" 2>/dev/null || echo "-")
      case "$dir" in
        "$HOME/Library/LaunchAgents")
          case "$label" in
            com.apple.*) flag="APPLE_LABEL_IN_USER_DIR" ;;
            *)           flag="-" ;;
          esac ;;
        *) flag="-" ;;
      esac
      signer="unsigned_or_unknown"
      if [ "$prog" != "NONE" ] && [ -e "$prog" ]; then
        signer=$(codesign -dvvv "$prog" 2>&1 | awk -F'=' '/^Authority/ {print $2; exit}')
        [ -n "$signer" ] || signer="unsigned_or_unknown"
      fi
      printf '%s\t%s\t%s\tRunAtLoad=%s\tKeepAlive=%s\tStartInterval=%s\t%s\n' \
        "$flag" "$label" "$prog" "$ral" "$ka" "$si" "$signer"
    done
  done
  ```
  The `flag` column is the whole point: it only fires for the label-location contradiction, so the output can be collected fleet-wide and filtered to one grep. Pair it with `launchctl list` to catch an item that is loaded but whose plist has since been removed, which the directory walk alone will miss.
  Unified Log corroboration - Where no plist write was captured, launchd still records loading and respawning an agent by label. A predicate scoped to the launchd subsystem and the suspect label recovers the load history, and because `KeepAlive` causes a respawn on every exit, a persistent implant generates far more respawn records than a well-behaved agent - which is a useful secondary signal on a host where the plist timestamp has been tampered with.
  The framework's other defaults, for pivoting from a confirmed host - Elastic lists several that are worth checking once a Mac is confirmed, because the same operator typically has Windows and web footholds too: webshell requests carrying a user agent naming the framework's own webshell component and a `pass` form field, and a web server process running an operating-system probe command that echoes a marked string. Elastic also notes that the framework answers a block by "switching proxies, User-Agents, and forwarding headers, falling back to free proxies in the target's own country and then Tor", so blocking a destination address should be paired with removing the persistence rather than treated as containment.
  Expected, not observed by Elastic - The on-disk path the macOS implant is staged at, and the protocol and destination shape of the five-second check-in. Elastic names the LaunchAgent label and the check-in interval but does not publish the binary location or the beacon's transport, so filters 2 and 3 above are written against signing provenance and interval variance rather than against a reported path or a destination.
  Scope - macOS endpoints, and in particular estates where Macs are managed with lighter telemetry than the Windows fleet, which is the common case. The label-location check is worth running as a standing control independent of this framework: it is one grep over a fleet-wide inventory, and the expected result is empty.

# H487

The LaunchAgent is labelled `com.apple.systemupdate`.

It is in a user's `~/Library/LaunchAgents` directory.

Those two facts cannot both be innocent, and you do not need to know anything about the implant to see why. Apple's own launch items live in the system paths. Apple does not drop agents into a user's Library folder. So an Apple-form label sitting in a user directory is a label making a claim its own location contradicts.

That is the whole first filter, and it is one grep over a fleet-wide inventory with an expected result of nothing.

Elastic found this as one of the stock persistence defaults in CyberStrikeAI, a complete offensive operator console that builds its own implants, runs C2 listeners and a webshell manager, and takes operator instructions over Telegram, Slack, Discord and DingTalk. On Windows the same implant persists as a scheduled task or Run key called `SystemUpdate`. On Linux it appends a line to `.bashrc` ending in `# cs`, or drops an `@reboot` cron entry. On macOS it is this plist.

And the beacon gives it away a second time. Elastic reports the implant checks in every five seconds with no jitter. Not approximately five seconds — five seconds, because nobody changed a build-time default. That produces an inter-arrival variance of essentially zero, which almost nothing legitimate does; real polling clients add jitter, back off on failure, or drift.

Do not hunt for five seconds, though. That number is published now, and it is the first thing an operator will change. Hunt the variance, which still works at thirty seconds or five minutes.

Two caveats worth keeping. A managed Mac has dozens of legitimate launch items, so the software inventory is a prerequisite rather than a refinement. And some vendors do pick Apple-adjacent labels out of sloppiness — which is why the signature of the binary behind the label is the second question, not an afterthought.

## Why

- **The contradiction is structural, so it survives renaming.** The operator can call the label anything, but if they want Apple's authority they have to use Apple's form, and Apple's form in a user directory is wrong by construction. A check built on that logic outlives this particular label string.
- **It is a single fleet-wide grep with an empty expected answer.** Parse the `Label` key out of every plist in the three launch directories and filter for an Apple prefix in a user path. That is cheap enough to run on a schedule and decisive enough to act on, which is the best possible combination for a persistence check.
- **The platform split is real, not bookkeeping.** The Windows version of this implant is covered separately because nothing transfers: different artefact, different telemetry, different responders. ESF file events and launchd plist keys have no Windows analogue, and the Apple-naming trick has no Windows equivalent at all.
- **Zero jitter is a tell that only exists because defaults go unchanged.** Frameworks ship for capability, not stealth — Elastic notes several of these defaults name the framework outright. A perfectly regular beacon is the sound of a build-time constant, and computing variance per destination costs one aggregation over data most environments already have.
- **macOS estates are usually the thinner half of the telemetry.** Launch items, signing state and unified log predicates are all available through a management platform without deploying anything new, which makes this a hunt most organizations can actually execute on their Macs rather than one that needs a tooling project first.
