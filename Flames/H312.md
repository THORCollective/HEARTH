Third-party products legitimately register their own dynamic virtual channels and are the main source of unfamiliar-but-benign names — virtual desktop and thin-client stacks (Citrix, VMware Horizon, Teradici), USB and smart-card redirectors, Teams/Zoom media-optimisation plugins, and printing or scanner redirection products all do this, and their channel names are vendor-branded and stable over time. # H312

Kaspersky's reporting on NightEagle describes a pivot that never touches the perimeter. Having reached a host over RDP, the operators used `rdp2tcp` to carry arbitrary TCP traffic *inside* the existing RDP session as a virtual channel. RDP virtual channels are a legitimate extensibility mechanism — clipboard sync, printer redirection, audio, smart cards and display control all ride them — and a tunnel that uses one inherits their invisibility: no new listening port, no second outbound connection, no firewall rule to add, nothing for egress filtering to evaluate. The connection an analyst sees is the authorised RDP session that was already approved. What makes this huntable is that Windows records every virtual channel open and close by name, in `Microsoft-Windows-RemoteDesktopServices-RdpCoreTS/Operational` events 132 and 148. The legitimate vocabulary is small and stable, so the detection reduces to enumerating the known names and reviewing whatever is left. The same operators reached these sessions in the first place through Microsoft dev tunnels exposing 3389 over `devtunnels.ms`, which is the companion condition worth hunting alongside.

## Why

- **The tunnel is invisible to every network control by design.** Because the forwarded traffic is multiplexed into an already-established, already-authorised RDP stream, segmentation rules, egress filtering and port-based monitoring have nothing to act on. The only place the pivot is observable is in the host's own RDP subsystem logging, which means this behaviour is either caught here or not caught at all.
- **The legitimate channel vocabulary is small enough to allowlist exhaustively.** Unlike most "unusual X" hunts, this one has a genuinely bounded benign set — a couple of dozen RemoteFX/RDS channels plus a stable, vendor-branded list from any VDI and redirection products in use. Enumerating it once turns an open-ended anomaly question into a short standing exception list, which is what makes the hunt sustainable rather than a one-off.
- **It degrades gracefully against an operator who renames the channel.** A signature on the literal `rdp2tcp` is trivially evaded by choosing a random name, but the allowlist formulation is not — an unknown name is an unknown name regardless of what it is. That is why this is written as enumerate-and-review rather than as a string match.
- **The required log is on by default and almost never collected, so the hunt has value even when it returns nothing.** RdpCoreTS/Operational ships enabled on every Windows Server and is one of the least commonly forwarded channels in the estate. Running this hunt establishes whether that telemetry exists at all on jump hosts and domain controllers — and an empty result usually means the log is not reaching the SIEM rather than that no tunnelling occurred.
