false_positive_notes: |
  This pair is a normal deployment idiom, so the discriminators are the caller and the address, not the calls.
  - Configuration-management and deployment tooling does exactly this. A pipeline role that pulls a SecureString secret and then runs AWS-RunShellScript on a fleet is the legitimate version of this sequence. Enumerate the roles that are supposed to call SendCommand at all - usually a small set - and treat the rest of the account as the hunt population.

Those arrive with AWS service principals or with the SSM service's own user agents rather than as an assumed-role session named after an instance ID; filter on the userIdentity, not on the event name.

Build the address allowlist from the instance inventory and the NAT and VPC endpoint addresses before hunting, because an unmaintained allowlist turns this into an alert on every deployment.

  Source reporting is Elastic Security Labs' November 13, 2026 analysis of a CyberStrikeAI server that worked through stolen AWS credentials in four accounts between September 30 and October 16, 2026. Elastic records that on October 2 one identity, aliased `container-role`, read an encrypted SSM parameter and then issued SendCommand: "Within 29 seconds, a third role read an encrypted SSM parameter and then issued an SSM SendCommand." Elastic calls this "the highest-risk activity in the data" and lists as a behavioral indicator "GetParameter with decryption followed within a minute by SSM SendCommand from the same role."
  Closest existing HEARTH coverage - [[H462]] covers a long-lived AWS access key leaked by an unauthenticated endpoint that enumerates and overwrites a distribution bucket, and [[H442]] covers CI tokens that end up reading AWS Secrets Manager. Both are secret-access hunts; neither reaches remote execution, and no existing hunt keys on the Systems Manager execution path. [[M032]] and the GetCallerIdentity hunts cover cloud account discovery rather than the secret-to-execution pair.
  Core filter 1, the ordered pair - The single highest-value check. In CloudTrail, select `ssm:GetParameter` or `ssm:GetParameters` where `requestParameters.withDecryption` is true, then look for an `ssm:SendCommand` by the same `userIdentity.arn` and the same session within a short window. Triage values are the parameter name, the document name on the SendCommand, the instance IDs or tag targets it was aimed at, the source address, and the user agent. A decrypting read of a parameter the role has never read before, followed by SendCommand against instances the role does not normally target, is the strong finding.
  Core filter 2, where the session came from - Elastic notes that "the three role sessions were named after EC2 instance IDs, so the credentials came from instance profiles" and that "using them from an outside IP means they were taken from the instances, for example through SSRF or host compromise." Compare `sourceIPAddress` on every call by an `AssumedRole` session whose `sessionContext.sessionIssuer.userName` matches an instance profile against the inventory of that instance's own addresses and the account's NAT egress. An instance-profile session calling from an address that is neither is the condition that makes the pair in filter 1 an intrusion rather than a deployment.
  Core filter 3, what actually ran - CloudTrail will not tell you. Elastic states plainly that "the audit log does not show what the command was or whether it succeeded," and recommends reviewing SSM command history "to see what ran," checking "for abuse of AWS-managed documents, AWS-RunShellScript and AWS-RunPowerShellScript or custom documents." Pull `ListCommandInvocations` for the command ID and the retained command output for the same window. If command output is not being retained to S3 or CloudWatch Logs, this hunt can establish that execution happened and not what it did - which is itself worth reporting as a telemetry gap before the hunt runs.
  Sample Defender-independent check in CloudTrail via Athena, over a table of flattened CloudTrail records:
  ```sql
  WITH reads AS (
    SELECT useridentity.arn            AS principal,
           eventtime                   AS read_time,
           json_extract_scalar(requestparameters, '$.name') AS parameter_name,
           sourceipaddress
    FROM cloudtrail_logs
    WHERE eventsource = 'ssm.amazonaws.com'
      AND eventname IN ('GetParameter', 'GetParameters')
      AND json_extract_scalar(requestparameters, '$.withDecryption') = 'true'
      AND from_iso8601_timestamp(eventtime) > current_timestamp - interval '30' day
  ),
  execs AS (
    SELECT useridentity.arn            AS principal,
           eventtime                   AS exec_time,
           json_extract_scalar(requestparameters, '$.documentName') AS document_name,
           sourceipaddress
    FROM cloudtrail_logs
    WHERE eventsource = 'ssm.amazonaws.com'
      AND eventname = 'SendCommand'
      AND from_iso8601_timestamp(eventtime) > current_timestamp - interval '30' day
  )
  SELECT r.principal, r.parameter_name, e.document_name, r.sourceipaddress,
         date_diff('second', from_iso8601_timestamp(r.read_time),
                             from_iso8601_timestamp(e.exec_time)) AS gap_seconds
  FROM reads r
  JOIN execs e
    ON r.principal = e.principal
   AND r.sourceipaddress = e.sourceipaddress
   AND from_iso8601_timestamp(e.exec_time)
       BETWEEN from_iso8601_timestamp(r.read_time)
           AND from_iso8601_timestamp(r.read_time) + interval '5' minute
  ORDER BY gap_seconds ASC
  ```
  The join is bounded to five minutes on purpose. A join on principal alone over a 30-day lookback correlates a deployment in one week with a secret read in another and returns nothing a hunter can act on.
  Severity context - Elastic reports that both of these calls arrived as low or medium alerts: "AWS SSM SendCommand Execution by Rare User" at low severity and "AWS Systems Manager SecureString Parameter Request with Decryption Flag" at medium, two alerts out of 78 across 16 days. The pair is what raises them, and Elastic's conclusion about correlation applies directly: "Only the shared source IP showed they belonged to one intrusion."
  Infrastructure, for retrospective hunting only - Elastic attributes the activity to a CyberStrikeAI server at 43[.]240[.]29[.]11, with 43[.]240[.]29[.]28 and 43[.]240[.]29[.]33 sharing its hosting, FOFA fid and self-signed certificate (serial number 3356730520974368630, issuer and subject CN CyberStrikeAI). Elastic notes that "as of November, none of the three is serving that interface, so treat the IPs as indicators for retrospective hunting." Use them to scope a look-back, not as the detection.

# H474

Two API calls, 29 seconds apart.

A role read an encrypted parameter out of Systems Manager, asking for it decrypted. Then the same role told Systems Manager to run a command.

Both calls are things a deployment role does on a normal Tuesday. Elastic's rules fired on each of them — one low severity, one medium — two alerts in a pile of 78 spread across sixteen days. Nothing in that pile looked like an emergency.

What made it one was the ordering and the address. The role was an EC2 instance role: its session was named after an instance ID, which means its credentials came from an instance profile, which means they were taken off the instance. And the calls arrived from a server in Hong Kong.

So the shape is: credentials lifted from a host, used from outside to unlock a secret, and the secret used — immediately — to make something run. The last step is the one CloudTrail will not explain. It records that a command was sent. It does not record what the command was.

That is the asymmetry worth hunting. If the only place a SendCommand's contents exist is SSM command history, and that history is not retained anywhere, then the audit trail ends one step before the part that mattered.

## Why

- **It reaches execution without touching a shell.** Systems Manager is the sanctioned path for running things on instances, so an operator using it inherits the account's own tooling and leaves no SSH session, no new process parent, and no inbound connection to notice. The telemetry that covers this is CloudTrail, not the endpoint.
- **The pair is specific where the parts are not.** A decrypting SecureString read is common. A SendCommand is common. A decrypting read followed within seconds by a SendCommand from the same session is a credential being fetched for an immediate purpose, and that narrows a noisy event space to something a hunter can work.
- **The session name gives away where the credentials came from.** Instance-profile sessions are named after the instance. That makes the external-source-address check cheap and near-unambiguous: the instance has a known address, the account has a known NAT, and anything else means the credentials are being used somewhere the instance is not.
- **Low severity is the point, not an accident.** Every alert in this intrusion was medium or low, because every action was individually routine. A programme that waits for a high-severity alert on cloud credential abuse of this shape will wait a long time, which is why this is a hunt rather than a rule.
- **It tells you whether your command history is worth anything.** The hunt's third filter is a question about your own retention. Finding the SendCommand and then being unable to say what it ran is a finding about the logging pipeline, and it is better to learn that during a hunt than during an incident.
