false_positive_notes: |
  Organization-wide workflow rollouts, from repository templating tools, Dependabot, Renovate, or internal platform bots, also create branches and add workflow files across many repositories. Those normally come from GitHub App installations (actor ends in `[bot]`, programmatic access type GitHub App), open pull requests, and leave their runs in place. They do not download a log and delete the run seconds later. Developers testing a workflow on a scratch branch sometimes delete their own runs, but that happens in one repository, usually from a browser user agent, and often minutes to days after completion. Scheduled run-retention or cleanup jobs delete runs in bulk, but the runs are days or weeks old and there is no matching per-run log download. CI log archivers that ship run logs to a SIEM download every log but never delete runs, and they run as known service identities from stable IPs. Feature-branch deploy workflows can legitimately assume AWS roles from non-default branches. Baseline branch-name patterns and role assumptions per repository, and escalate only when the branch first appeared within minutes of the role assumption and was created by a token that also deleted runs. Engineers sometimes use CI keys from a corporate VPN or bastion. Allowlist known corporate egress for the Secrets Manager section, but still treat CI-key use outside runners as a hygiene finding. Public-repository runs held at `action_required` are not false positives: the payload did not run, but the token that pushed the branch is compromised and must be revoked.

  GitHub enterprise or organization audit log (streamed) - Core filter: action `workflows.completed_workflow_run` followed by `workflows.delete_workflow_run` for the same `workflow run ID` within `60 seconds`. Limit to runs whose triggering event is `push` and whose `head branch` was created less than ~15 minutes before the run. The known variant uses a `ci-sync-` prefix plus six hex or base36 characters and the workflow file `.github/workflows/sync-check.yml`, but do not require those names. Triage values: `actor`, `hashed token`, `programmatic access type`, `user agent`, `actor IP`, `repository`, `head branch`, `workflow file path`, `conclusion`. Correlation: group by `hashed token` (fallback `actor` + `actor IP` + `user agent`) over a 1-hour window and alert at 3+ distinct repositories showing the new branch -> run -> delete chain. Strong red flags: the deleting identity is a human user token rather than a GitHub App installation; user agent `gheist`; public-repository runs on the same branch pattern stuck at conclusion `action_required` (the payload was held, but the token is still compromised).

Triage values: `actor`, `actor IP`, `user agent`, `request method`, `URL path`, `repository`. Pivot: look back 30 minutes for `git.clone` of private repositories and `git.push` creating new refs by the same identity. Then look forward for the same `actor IP` authenticating as several different users or bot accounts within minutes, which indicates a stolen token pool being cycled. False positive check: API request events can redact `hashed token`, so join them to the workflow run events on `actor`, `actor IP`, and timestamp. Strong red flags: log download and run deletion seconds apart with a non-browser user agent; one source IP rotating through multiple identities; clone-then-plant ordering on private repositories.
  
  Repository branch and commit inventory - Core filter: non-default branches whose only change from the default branch is one new file under `.github/workflows/` with an `on: push` trigger. Within that file, flag steps that serialize the whole secrets context (`toJSON(secrets)`) or pipe `env` into an encoder such as `base32` or `base64`. Also flag a job `environment:` matrix that enumerates every deployment environment, and any `runs-on: self-hosted` job added on the same branch. Triage values: `branch name`, `commit message`, `commit author`, `pusher`, `signature verification status`, `file path`. Pivot: deleting the run does not remove the branch, so each hit maps directly to the repository, organization, and environment secrets that must be rotated. Strong red flags: unsigned commit authored as the token owner; commit message `ci: sync config`; branch never opened as a pull request.
  
  AWS CloudTrail (STS, GitHub OIDC) - Core filter: event name `AssumeRoleWithWebIdentity` with identity provider `token.actions.githubusercontent.com` where the `web identity subject` contains `ref:refs/heads/ci-sync-` or any branch outside the repository's normal deploy refs. Triage values: `role ARN`, `web identity subject`, `role session name`, `source IP address`, `user agent`, `issued access key ID`. Pivot: follow the issued session's `access key ID` into Secrets Manager, SSM Parameter Store, and S3 reads. Review the role trust policy for a `token.actions.githubusercontent.com:sub` condition that wildcards refs (`repo:<org>/<repo>:*`). Strong red flags: a role assumption from a branch created minutes earlier by a user token. This shows the organization's own push-triggered workflows executed on the planted branch even when GitHub-side logs are missing.
  
  AWS CloudTrail (Secrets Manager and long-lived CI keys) - Core filter: `ListSecrets` followed by `GetSecretValue` or `BatchGetSecretValue` by an IAM user access key (`AKIA` prefix) stored as a GitHub Actions secret, or by a role session issued to a workflow. Limit to cases where the `source IP address` falls outside the GitHub-hosted runner ranges (GitHub `meta` API `actions` list) and known self-hosted runner egress. Triage values: `access key ID`, `user name`, `source IP address`, `user agent`, `error code`, distinct `secret ID` count. Correlation: hours, not minutes, after a planted run in a repository that held that key (keep a 72-hour window). Also check for a preceding `GetCallerIdentity` from the same IP and bursts of `AccessDenied`. Strong red flags: first-seen ASN, VPS, or residential egress for a key previously seen only from runners; a distinct secret count far above that key's baseline.

# H442

Wiz Research (Rami McCarthy and Hila Ramati, October 25, 2026) has tracked the Gheist campaign since September 15, 2026. The operator takes stolen GitHub tokens and, for every repository each token can reach, creates a branch named `ci-sync-` plus six random characters. On that branch it commits one unsigned workflow file (`.github/workflows/sync-check.yml`, commit message `ci: sync config`) authored as the token owner. The push trigger starts the workflow, which prints the job environment and the entire secrets context in base32 so GitHub's verbatim log masking does not redact it. Setting `permissions: {}` limits the job's own token but not the secrets context. A later variant spreads the job across every deployment environment to reach environment-scoped production secrets. The operator then downloads the run log through the GitHub REST API (user agent `gheist`) and deletes the run seconds after it finishes. The secrets leave through GitHub itself, so there is no attacker domain or outbound connection to block. Wiz recovered more than 13,500 planted branches from more than 850 compromised accounts, and two tool variants run in parallel (hex vs. base36 branch suffixes). In enterprise organizations Wiz saw the operator cycle through tokens of several users and service accounts within minutes and clone private repositories before planting. Hours later, the organization's cloud credentials were used to enumerate AWS Secrets Manager. CloudTrail also showed the organization's own push-triggered workflows running on the planted branches and assuming AWS roles through GitHub OIDC. That is evidence of execution even where GitHub-side logs were unavailable. Since July 28, 2026, GitHub holds suspected malicious workflow runs in public github.com repositories until a collaborator approves them; every public Gheist run Wiz checked sat at `action_required`. That hold does not apply to private repositories or GitHub Enterprise Server. On October 19 one variant added a `runs-on: self-hosted` job (`sync-host`) for repositories with registered self-hosted runners. It sweeps the runner host for token formats, private keys, `.env` files, Terraform state, shell history, process environments, Docker-socket host access, cloud instance credentials, runner credential files, and Kubernetes service account tokens. This hunt targets the behavior chain rather than the rotating names: stolen token -> fresh branch containing only a new workflow file -> push-triggered run -> API log pull -> deletion within a minute -> off-runner use of the exposed CI credentials.

## Why

- It is current and hits the repositories that matter. Gheist has run since September 15, 2026 across 850+ accounts and 13,500+ planted branches. GitHub's July 28, 2026 approval hold only covers public github.com repositories, so private repositories and GitHub Enterprise Server still execute the planted workflow, and that is where Wiz saw production secrets dumped and AWS Secrets Manager enumerated.
- It targets an invariant chokepoint rather than rotating names. Whatever the branch prefix, workflow filename, encoding, or user agent, the operator must get a push-triggered workflow to run in the victim repository, read the log back through GitHub's API, and delete the run to shrink the evidence window. The stolen CI keys must then be used from somewhere other than the runner. The pull-then-delete-within-a-minute pairing and off-runner key use survive changes to `ci-sync-` and `gheist`.
- There is no C2 egress to block, but every stage is still recorded. The GitHub audit log records workflow completion and deletion with token hash, user agent, and IP. The planted branch persists after the run is deleted. GitHub OIDC writes the branch ref into the CloudTrail web identity subject, so execution is provable from AWS even when GitHub logs were not retained.
- False positives can be bounded with structural filters. Legitimate fleet-wide workflow changes come from GitHub Apps that open pull requests and leave runs intact, and retention jobs delete days-old runs. Requiring a human-user token, a new branch with a single workflow file, and a log pull plus deletion within 60 seconds across 3+ repositories leaves very little benign overlap.
