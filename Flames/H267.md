false_positive_notes: |
  SYSVOL is read constantly and legitimately — every domain-joined machine pulls policy from it on a schedule.
  The naive "someone read SYSVOL" query is unusable. Expect legitimate volume from:
  - Normal Group Policy refresh from every domain member, every 90-120 minutes. This is the dominant traffic and
    it reads the specific policies applicable to that machine or user, not all of them.
  - Group Policy Management Console, AGPM, and GPO backup/reporting tooling run by AD administrators.
  - AD posture and audit tooling — PingCastle, Purple Knight, BloodHound/SharpHound collection, ADRecon,
    Microsoft's own Security Compliance Toolkit. These deliberately do exactly what this hunt looks for. They are
    the single most important benign population to enumerate first; several will also query `description` and
    `ms-Mcs-AdmPwd`.
  - Backup agents and DFSR replication traffic between domain controllers.
  - Migration and consolidation projects reading policy trees wholesale.
  The separators, in order of strength:
  (1) FAN-OUT vs. APPLICABILITY. A member computer reads the handful of policies that apply to it. A sweep reads
      every GUID directory under Policies\, in sequence, in one burst. Count distinct policy GUIDs touched per
      account per 10-minute window and compare against that principal's own history.
  (2) THE LITERAL STRING. `cpassword` appearing in a command line, a script block, or a `findstr`/`Select-String`
      pattern has no benign explanation outside a sanctioned assessment. This is the highest-fidelity single
      event in the hunt.
  (3) WHO. Group Policy refresh runs as the machine account or SYSTEM. A sweep by a normal interactive user
      account, or by a service account that has never enumerated policy before, is the anomaly. Filter on the
      principal type before anything else.
  (4) FILE SELECTIVITY. Policy refresh reads registry.pol and the specific extension files it needs. A sweep
      reaches for Groups.xml / Services.xml / ScheduledTasks.xml / DataSources.xml / Printers.xml specifically —
      the five GPP files that can hold cpassword.
  (5) LDAP CO-OCCURRENCE. The same session querying `(samaccountname=svc_*)` and pulling `description` / `info`,
      or filtering on `(ms-Mcs-AdmPwd=*)`, within minutes of the SYSVOL sweep. Two independent credential-source
      searches from one principal is a hunting objective, not administration.
  Enumerate your AD assessment tooling and its service accounts as a named population, with a change window, and
  score against that. Do not suppress SYSVOL reads or the filenames.

    ([adsisearcher]'(samaccountname=svc_*)') ... $_.Properties['info']
    $_.Properties['description']

    DirectorySearcher Filter '(msDS-AllowedToDelegateTo=*)'  [delegation enum]

  THE FIVE GPP FILES THAT CAN CARRY cpassword:

    \\<domain>\SYSVOL\<domain>\Policies\{GUID}\Machine|User\Preferences\Groups\Groups.xml
                                              .../Preferences\Services\Services.xml
                                              .../Preferences\ScheduledTasks\ScheduledTasks.xml
                                              .../Preferences\DataSources\DataSources.xml
                                              .../Preferences\Printers\Printers.xml

  WHY THIS STILL WORKS IN 2026: MS14-025 stopped administrators from *creating* new GPP passwords, but it did
  not remove existing ones. Any Groups.xml written before May 2014 and never cleaned up is still readable by
  every authenticated user in the domain, and the 32-byte AES key that decrypts cpassword has been public since
  Microsoft documented it in MSDN. The credential recovered is typically a local administrator or service
  account pushed to every machine in an OU — which is why it goes straight to lateral movement. There is no
  exploit and no elevation involved: this is a read of a share that, by design, everyone can read.

  STARTING QUERY — Windows Security 5145 on DCs (Splunk-style):

    index=wineventlog EventCode=5145 ShareName="\\\\*\\SYSVOL"
    | where like(RelativeTargetName, "%Policies%")
    | eval GpoGuid=mvindex(split(RelativeTargetName,"\\"),2)
    | bin _time span=10m
    | stats dc(GpoGuid) AS distinct_gpos, values(RelativeTargetName) AS files
            BY _time, SubjectUserName, IpAddress
    | where distinct_gpos > 15 AND NOT match(SubjectUserName, "\$$")

  The `\$$` exclusion drops machine accounts, which is where nearly all legitimate policy-refresh volume lives.
  Tune `distinct_gpos` to your estate — the right number is "meaningfully above what this principal has ever
  done before," not a fixed constant.

  STARTING QUERY — the literal-string path (Defender XDR):

    DeviceProcessEvents
    | where Timestamp > ago(30d)
    | where ProcessCommandLine has_any ("cpassword", "Get-GPPPassword", "gpp-decrypt")
       or (ProcessCommandLine has "SYSVOL" and ProcessCommandLine has_any ("findstr", "Select-String", "-Recurse"))

  REMEDIATION CONTEXT worth reporting alongside any finding: run
  `Get-ChildItem \\<domain>\SYSVOL -Recurse -Include *.xml | Select-String cpassword` yourself. If it returns
  anything, the credential is already public to every domain user and rotating it is the finding — the hunt for
  who read it is secondary.

# H267

The cheapest domain credential in most Active Directory estates is not in LSASS. It is in a file that every authenticated user is allowed to read.

`MS14-025` stopped administrators from creating new Group Policy Preferences passwords in 2014. It did not delete the ones already written. If a `Groups.xml` from 2013 is still sitting in a policy folder, its `cpassword` attribute is still there, still readable by every domain user, and still decryptable with the 32-byte AES key Microsoft published on MSDN. The operator in this report walked SYSVOL for exactly that, then read the `description` and `info` attributes off every `svc_*` account over LDAP, because the other place administrators write passwords is a comment field. They found service-account credentials both ways, and used them to reach the domain controller over SMB and WinRM the same day.

The detection problem is that SYSVOL is read constantly and legitimately. The detection *solution* is that a machine reading its own policy and an operator sweeping every policy in the domain look nothing alike once you count distinct GPO GUIDs per principal per window — and that the string `cpassword` in a command line has no innocent explanation at all.

## Why

- **The credential this yields is pre-privileged and pre-distributed.** A GPP password is not one user's password — it is typically a local administrator or service account that Group Policy pushed to every machine in an OU. Recovering one is functionally equivalent to recovering local admin across a whole slice of the estate, which is why in the source intrusion it went straight to SMB and WinRM against a domain controller rather than to further discovery. The blast radius of a single missed read is not one host.

- **There is no exploit, no elevation, and no malware — which is exactly why it evades most coverage.** The operator authenticated as a normal domain user and read a share they are permitted to read. No EDR detonation, no LSASS handle, no suspicious binary, no privilege escalation event. Detection stacks tuned to process behaviour see nothing. The only place this is visible is domain-controller file-share auditing, which many estates leave at 5140 granularity or disable entirely because of volume.

- **Fan-out separates the two populations cleanly, without a static threshold.** A domain member pulls the handful of policies that apply to it. An operator enumerating the domain walks every GUID under `Policies\` in one burst. Counting distinct GPO GUIDs per non-machine account per 10-minute window, scored against that principal's own history, splits legitimate refresh from a sweep without needing to guess a magic number — and it survives the operator changing tooling, because the fan-out is the objective, not an implementation detail.

- **The literal string gives you a near-zero-false-positive second trigger.** `cpassword`, `Get-GPPPassword`, and `gpp-decrypt` appearing in a command line or a PowerShell script block have exactly one meaning outside a scheduled security assessment. That is a rare thing: a cheap, high-fidelity indicator sitting alongside a noisy behavioural one, where either can fire independently. Deploy both.

- **The LDAP half doubles the coverage for free and catches the LAPS pivot.** The same session that swept SYSVOL also ran `(samaccountname=svc_*)` pulling `info` and `description`, and `(ms-Mcs-AdmPwd=*)` to find which machines have LAPS-managed passwords the account can read. Those are separate credential sources reached by the same reasoning, they are logged in the same session, and an `ms-Mcs-AdmPwd` filter from a non-administrative principal is itself a strong signal. Correlating the two searches within one logon session turns two medium-confidence events into one high-confidence one.

- **Running the hunt finds the vulnerability even when it finds no adversary.** Unlike most hypothesis hunts, this one has a guaranteed deliverable: a recursive `Select-String cpassword` across SYSVOL either returns nothing, or returns a credential that every domain user in the organisation has been able to read for over a decade. That result is worth the hunt regardless of whether anyone was looking.

- **HEARTH had no T1552.006 coverage at all,** despite it being one of the oldest and most reliably productive credential-access paths in Active Directory and a standard first move for a hands-on-keyboard operator with a low-privilege foothold.
