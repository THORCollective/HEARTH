  The `security` command line tool is a normal administrative tool on macOS and developers run it deliberately.   What the report states, verbatim - "A second investigation revealed an attack chain in which a compromised macOS endpoint, infected via a trojanized application, was scripted to scrape credentials from the macOS keychain specifically associated with the Anthropic Claude Code AI assistant." Talos frames the significance as follows: "This direct targeting of AI-related secrets highlights an emerging threat, where attackers seek to compromise not only traditional user and system credentials but also those tied to AI platforms, which may grant access to additional sensitive data and advanced automation capabilities." The remediation Talos draws from it is: "These incidents highlight the critical need for organizations to implement strong MFA and robust credential management practices, especially for AI platforms and development tools."
  What the report does not state, and therefore what this hunt infers - Talos says the endpoint "was scripted to scrape credentials" but does not name the script, the interpreter, the command, the keychain item label, or the trojanized application. Every command below is my reconstruction of how a keychain read of that shape is performed on macOS, not a vendor-published indicator. Talos also does not say whether the read succeeded, nor how the script obtained authorization to read the item - which matters, because a caller that is not in an item''s access control list normally triggers an authorization prompt rather than silently returning the secret. Treat the authorization question as open during triage rather than assuming a silent read.
  Why the keychain and not a file - on macOS the credential for an AI coding assistant is held as a keychain item rather than as a file in the home directory, which is the platform difference that makes this its own hunt. The related Windows behaviour, where the equivalent secrets sit in files on disk, is covered separately; see the pairing note below.
  The telemetry anchor - the Endpoint Security Framework is the right source and `ES_EVENT_TYPE_NOTIFY_EXEC` is the right event, because the distinguishing detail is in the argument vector rather than in the binary path. `/usr/bin/security` executing is unremarkable. `/usr/bin/security` executing with `find-generic-password` and a specific service name, from a parent that is not a shell, is the hunt. Note that the ESF has no network events, so the exfiltration leg of this chain has to be picked up from network telemetry rather than from the same event stream.
  Check 1 - targeted keychain reads, by responsible process. Collect exec events for the keychain tooling and triage on the parent rather than the child:
  ```shell
  log show --last 7d --style compact \
    --predicate 'subsystem == "com.apple.securityd"' 2>/dev/null | tail -100
  ```
  In an ESF-backed product the equivalent query is every `ES_EVENT_TYPE_NOTIFY_EXEC` where the target path is `/usr/bin/security` and the argument vector contains `find-generic-password`, `find-internet-password` or `dump-keychain`, grouped by responsible application bundle. Rank the result by how few distinct service names each process asked for: a credential helper asks for its own item repeatedly over weeks, and a stealer asks for a short list once.
  Check 2 - who opened the keychain file at all. This catches a reader that parses the database directly instead of shelling out to `security`:
  ```shell
  ls -la ~/Library/Keychains/ /Library/Keychains/ 2>/dev/null
  ```
  Against ESF, this is `ES_EVENT_TYPE_NOTIFY_OPEN` on `login.keychain-db` filtered to responsible processes that are not `securityd`, not the user''s known credential helpers, and not an interactive shell. A read of the raw database file by an application bundle is a stronger signal than a `security` invocation, because there is less legitimate reason for it.
  Check 3 - the responsible bundle''s signature and install age. The report''s delivery vector is a trojanized application, so the bundle is the pivot:
  ```shell
  codesign -dvvv --verbose=4 /Applications/Suspect.app 2>&1 | head -20
  spctl --assess --type execute --verbose /Applications/Suspect.app 2>&1
  ```
  A bundle whose signature is ad-hoc, absent, revoked, or issued to an identity unrelated to the product it claims to be, and which was installed within days of the keychain read, is the shape Talos describes. Substitute the real bundle path for the placeholder above.
  Check 4 - the provider side, which is where a successful theft actually shows. Endpoint telemetry can show the read; only the AI platform''s own audit records show the credential being used afterwards from somewhere else. Pull API key last-used timestamps and source addresses for the affected account and compare them against the user''s known locations and working hours. If the stolen credential is an OAuth refresh token rather than a long-lived key, revocation has to happen provider-side, because rotating anything on the endpoint does not invalidate it.
  Scoping note - run this only against hosts that actually have an AI coding assistant configured. Without that inventory the hunt has no denominator, and a clean result across a fleet that mostly does not use these tools says nothing at all.
  Related finding in the same report, not hunted here - Talos separately describes "an internal threat actor who was hired under false credentials abused their privileged access to install AI-powered development tools, such as GitHub Copilot CLI and Anthropic Claude Code." Talos states that investigation "did not find evidence of malicious activity or data theft", so it is recorded here as context rather than turned into a hypothesis.
  Pairing and closest existing coverage - [[H422]] is the nearest existing hunt and is the deliberate platform counterpart: it covers the same class of secret read in one sweep on Windows, where the credentials are files on disk, and it explicitly notes the keychain-based macOS case as the other half of the split. This hunt is that other half, and the two should be run together on a mixed fleet. [[H409]] is adjacent but different in kind - it covers an installer repointing an agent''s model endpoint so that data leaves with the conversation, which is configuration tampering rather than credential theft. [[H284]] covers a macOS stealer that replaces the executable inside an installed wallet application and mentions keychain theft in passing, but its subject is wallet applications and wholesale credential collection rather than a narrow read of an AI platform secret.

# H436

Most macOS stealers are indiscriminate: they unlock the login keychain and take what is in it. The chain Cisco Talos describes in its Q3 2026 incident response trends did something narrower. A compromised endpoint, infected through a trojanized application, "was scripted to scrape credentials from the macOS keychain specifically associated with the Anthropic Claude Code AI assistant."

Selectivity is what makes this worth its own hunt. Going after one named item means the operator knew what they wanted before they arrived. An AI coding assistant's stored credential is not a password for a website — it is an API key or an OAuth refresh token for an account that carries billing, conversation history, and, on a developer workstation, a working connection to repositories and local tooling. Talos puts the stakes directly: attackers now "seek to compromise not only traditional user and system credentials but also those tied to AI platforms, which may grant access to additional sensitive data and advanced automation capabilities."

The hunt has to key on narrowness, because breadth is what the usual detections look for. A process that opens the login keychain and enumerates everything is already suspicious to most tooling. A process that asks for two or three named service items and exits is quieter, faster, and in argument-capture terms almost indistinguishable from the credential helpers that do the same thing legitimately all day. The separation is the responsible process: a credential helper is signed, is listed in the item's access control list, and asks for its own secret repeatedly over weeks. The chain Talos describes is an application bundle that asked once.

Two honest limits belong on this hunt. First, Talos does not say how the script was authorized to read the item. A caller absent from an item's ACL normally raises an authorization prompt rather than silently returning the secret, so whether this read was silent is an open question during triage, not an assumption. Second, the Endpoint Security Framework has no network events, so this telemetry can show the credential being read but never the credential leaving. The evidence that a stolen key was actually used sits in the AI provider's own audit log — key last-used timestamps and source addresses — and that is also the only place revocation takes effect.

## Why

- A targeted read of one named keychain item is a different behavior from a wholesale keychain dump, and detections tuned to the wholesale case will pass over it.
- The stolen secret is a credential for a service outside the organization's control, so the usual containment move — reimage the host, rotate local secrets — does not revoke it. Only the provider can.
- On a developer workstation the AI assistant's credential is adjacent to source code, repository access and local tooling, which makes it an access-development prize rather than a nuisance.
- The platform split is real and not cosmetic: the same secrets are files on Windows and keychain items on macOS, which means different telemetry, different queries and a different hunt.
- The distinguishing field is the argument vector, not the binary path, so this hunt fails silently in any deployment that records the exec of `/usr/bin/security` without its arguments. That is worth confirming before trusting a clean result.
