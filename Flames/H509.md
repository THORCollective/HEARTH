title: "Persistence that walks: an implant copies its own three files to a new directory, signals Global\\ExitEvent, kills its own parent seven seconds later, and deletes the loader behind it"
hypothesis: >-
  An implant on a Windows host has relocated itself and destroyed its previous copy, and the move
  leaves a recognisable sequence rather than a single artefact. Kaspersky documents a ShadowCloud
  plug-in named moveDir.ts that exists only to move the infection. Given a target path, it compares
  it against the current backdoor path; if they differ it creates the target directory, copies the
  legitimate host executable across, iterates a fixed list of nineteen loader DLL names and copies
  whichever are present at the current path, copies the encrypted config.ini payload, then launches
  the legitimate executable from the new location. Having started the new instance it creates an
  exit event named Global\ExitEvent, waits for it to be signalled, sleeps eight seconds, and
  terminates the old backdoor process. The second branch is the one that erases evidence. If the
  target path equals the current path, the plug-in enumerates running processes to find the
  backdoor''s parent, and when the parent''s executable name is identical to the backdoor''s own it
  signals Global\ExitEvent, pauses seven seconds, terminates the parent process, pauses one more
  second, and - if a delete-files flag is set - deletes the parent''s executable, the config.ini
  payload and the loader DLL from the parent''s directory. The hunt is therefore a correlation
  across minutes on one host: an identical three-file set appearing in a new directory, a
  same-named parent and child pair, a process terminating its own parent, and the original
  directory being emptied of exactly the files H505 looks for.

false_positive_notes: |
  Software updates and installers legitimately copy a file set into a new directory and then terminate the old process, so the copy-and-exit shape on its own is ordinary. Three things separate this from an update - the mover is not an installer or an update service, the destination is not a versioned application directory, and the file set includes an opaque `config.ini` rather than a normal application payload. Reconcile the acting process first.

  Portable applications relaunched from a new location by a user produce a similar process pair, including a same-named parent and child. The discriminator is the termination - a portable app does not kill its own parent on a timer, and it does not delete the parent's executable afterwards.

  `Global\ExitEvent` is a plausible-looking generic name and some legitimate software does create similarly bland event objects, so an exact match is suggestive rather than conclusive on its own. Treat it as the glue that joins the file and process legs on a host already surfaced by one of them.

  The parent-termination leg will surface legitimate process-management software - supervisors, service wrappers, crash handlers and some EDR components routinely terminate other processes, and a few terminate parents. Build the short expected list once; the remainder is small.

  Sysmon Event ID 5 records that a process ended but not who ended it, so a query written against Event 5 cannot answer the question this hunt asks. Use Event ID 10 and look for a granted access mask that includes `PROCESS_TERMINATE` (0x0001), then correlate to the Event 5 for the target.

  File deletion telemetry is the weakest link in most estates. Defender XDR reports deletes through `DeviceFileEvents`, but Sysmon only records deletions if Event ID 23 or 26 are configured, and many deployments omit them because of volume. Where deletes are not logged, the hunt inverts - look for the arrival of the trio in the new directory and for the absence of the files in the old one at the next inventory, which is a slower but still workable signal.

  The seven-second and eight-second pauses are the plug-in's hard-coded timings as reported, not a measured interval across samples, and an operator can change them. Use them to recognise the sequence in a timeline, not as query thresholds.
notes: |
  Leg one, the same content in two places (DeviceFileEvents, hash-matched) - Core filter: a file hash that appears as a create in one directory and a delete in another on the same device within a bounded window. Hash matching matters here because the host executable keeps its legitimate name and signature at both locations, so a name-based query cannot tell the copy from the original.

      let window = 2h;
      let creates =
          DeviceFileEvents
          | where Timestamp > ago(30d) and ActionType in ("FileCreated","FileModified")
          | where isnotempty(SHA256)
          | project CreateTime = Timestamp, DeviceId, DeviceName, NewPath = FolderPath, FileName, SHA256,
                    Mover = InitiatingProcessFileName, MoverPath = InitiatingProcessFolderPath;
      let deletes =
          DeviceFileEvents
          | where Timestamp > ago(30d) and ActionType == "FileDeleted"
          | where isnotempty(SHA256)
          | project DeleteTime = Timestamp, DeviceId, OldPath = FolderPath, SHA256;
      creates
      | join kind=inner deletes on DeviceId, SHA256
      | where OldPath != NewPath
      | where DeleteTime between (CreateTime .. CreateTime + window)
      | project CreateTime, DeleteTime, DeviceName, FileName, OldPath, NewPath, SHA256, Mover, MoverPath
      | order by CreateTime desc

  Thirty days is the full Defender advanced hunting retention and `window` bounds the correlation so unrelated days are not paired - both `let` values are used. Strengthen the result by requiring at least two of the three file types in the same new directory - an executable, a DLL from the nineteen-name list, and `config.ini`. The loader names are reproduced in H505 and are the same list this plug-in iterates.

  Leg two, the same-named parent and child (Sysmon 1, or 4688) - Core filter: a process creation where the image file name equals the parent image file name and the two image paths differ. That is the relocation in a single event, and it is rare enough to read directly.

      Sysmon Event ID 1 where Image file name == ParentImage file name
        and the directory part of Image != the directory part of ParentImage

  On Windows Security 4688 the equivalent compares `New_Process_Name` with `Creator_Process_Name`; the Sysmon field names do not exist there, and a query that mixes them returns an empty result with no error. Red flags - either path is under `C:\Windows\System32` or `C:\ProgramData`; the image is one of the four signed sideload hosts the report names, javaw.exe, start.exe, pythonw.exe or zoomit.exe; the new directory was created minutes earlier.

  Leg three, the termination (Sysmon 10) - Core filter: a process access event where the target is the accessing process's own parent and the granted access includes terminate rights. Sysmon 10 carries `SourceImage`, `TargetImage` and `GrantedAccess`; `PROCESS_TERMINATE` is `0x0001`, so masks such as `0x1` and `0x1fffff` qualify. Pair each hit with the Event ID 5 for the target to confirm the kill landed, and read the gap - the reported sequence signals the event, waits seven seconds, terminates the parent, waits one more second, and then deletes files, so a timeline showing a kill about seven seconds after an object signal and deletions about a second after the kill is this plug-in rather than a crash handler.

  Leg four, the event object (EDR object telemetry, or live inspection) - Any object named `Global\ExitEvent`, and more usefully, that name appearing on a host that leg one, two or three already surfaced. Where object creation is not logged, enumerate `\BaseNamedObjects` on the suspect host with Sysinternals WinObj. The same suite uses several named objects with distinctive conventions - shared-memory sections called `Local\sm`, `Local\pc` and `Local\pcs` followed by the owning process ID, a named pipe called `p` followed by the process ID, and the keylogger's `keylogger###Global\OneDriveStandaloneUpdater` object that H508 covers.

  What a hit means for response, which is the practical reason to run this hunt - the files H505 would have found are gone from the directory the incident report names, and they are now somewhere else under a legitimate vendor name. Containment that scopes on the original path cleans an empty directory. Scope on the hash and on the three-file composition instead, and sweep every directory the mover wrote to. If the delete-files branch ran, the loader DLL and the encrypted payload no longer exist to be collected, so the surviving evidence is the process timeline, the new copy, and the network artefacts in H503, H504 and H507.

  Scope note: H298 is the closest existing hunt and the distinction is direction. H298 covers an operator-commanded uninstall - a service or Run value removed and a batch file that erases the loader, the payload and itself, ending the infection. This hunt covers a move, where the same three files are planted somewhere new before the old copy is destroyed, and the infection continues; the discriminating evidence is the hash-matched create preceding the delete, the same-named parent and child pair, and the parent being terminated by its own child. H505 is the hunt for the trio at rest and the primary pivot in both directions - before the move and after it.

# H509

Most anti-forensic routines delete things. This one moves house first.

`moveDir.ts` is a ShadowCloud plug-in whose entire purpose is to relocate the infection. Hand it a target path and it copies the legitimate host executable, whichever of nineteen known loader DLL names are present, and the encrypted `config.ini` payload into the new directory, then starts the legitimate executable from there. The new instance signals an event object called `Global\ExitEvent`, and the old one — after an eight-second pause — exits.

The second branch is the interesting one. If the target path is the same as the current path, the plug-in instead goes looking for its own parent process, and checks whether the parent's executable name matches its own. When it does, it signals `Global\ExitEvent`, waits seven seconds, terminates the parent, waits one more second, and then, if a flag is set, deletes the parent's executable, its `config.ini` and its loader DLL. A process killing its own identically-named parent and then erasing the parent's files from disk is not a shape that has an innocent twin.

For a defender, the consequence is specific and unpleasant: the three files from the incident report are no longer where the incident report says they are, and the directory they were in may be empty. Scoping containment on a path cleans nothing.

## Why

- It breaks path-based scoping, which is how most containment is written. An indicator list naming `C:\windows\system32\config.ini` is correct and useless after this plug-in runs. Hunting the hash and the three-file composition survives the move; hunting the path does not.
- The move is visible as a correlation even when each half is invisible alone. A create in one directory and a delete of the same hash in another, within the same couple of hours on one device, is a query that needs no indicators at all — only file hashes, which Defender XDR already records.
- A same-named parent and child in different directories is a one-event finding. It is rare, it is cheap to query, and it is the relocation caught in the act rather than reconstructed afterwards.
- Terminating your own parent is close to unique. Supervisors kill children, not the other way round, so a Sysmon 10 event where the target is the source's parent and the access mask includes terminate rights is a very short list on any estate.
- Knowing the timings makes a timeline readable. Signal, then roughly seven seconds, then a kill, then roughly one second, then deletions — a sequence that identifies this plug-in in a noisy host timeline without any string matching at all.
