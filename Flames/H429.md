  A code editor on a developer Mac loaded a tampered extension, and the loader that ran on module load did three things that outlive the extension itself: it appended an attacker public key to the signed-in user's `~/.ssh/authorized_keys`, it wrote a user LaunchAgent at `~/Library/LaunchAgents/com.apple.sysmond.plist` whose configured action is a shell script at `~/.config/.smt`, and it started an `autossh` or `ssh` retry loop that requests reverse forwarding back to port 22 on the workstation. false_positive_notes: |
  Legitimate remote-development tooling writes SSH material on developer Macs constantly. VS Code Remote-SSH, JetBrains Gateway, Cursor's own remote features and `ssh-copy-id` run by the user all touch `~/.ssh/`. The discriminator is direction: those tools write `~/.ssh/config`, `known_hosts` and private keys, and they append to `authorized_keys` on the *remote* host, not on the laptop in front of you. An append to the local `authorized_keys` on a workstation is the unusual event.
  Real monitoring software legitimately installs LaunchAgents and LaunchDaemons, and some of it is named after what it monitors. Microsoft is explicit that the name is not the finding: "Inspect each startup object's configured action before removal; names alone are not sufficient to distinguish malicious objects from legitimate monitoring software." Resolve the `Program`/`ProgramArguments` value before escalating.
  `autossh` is a legitimate package and some engineers install it deliberately for long-lived port forwards to lab equipment. Those forwards are normally local (`-L`) or dynamic (`-D`), configured in `~/.ssh/config`, and point at hosts the engineer can name. A remote forward (`-R`) whose target is `localhost:22` on the engineer's own laptop is the shape that is hard to explain.
  Hosts where the user is a platform or SRE engineer will produce the most noise on the SSH half and the least on the LaunchAgent half. Scope by host class and build the approved LaunchAgent inventory per class.
  A negative result on the plist path does not clear a host. Microsoft notes that "the presence of an artifact alone does not establish that the startup mechanism ran successfully", and the converse also holds: Cursor reports that "errors and administrator-permission requirements blocked SSH access on most macOS and Windows hosts", yet the loader "could still attempt to plant its SSH key, establish persistence, and report host information." Check the key and the beacon independently of the agent.
notes: |
  Platform - macOS. The Windows half of the same loader is a different telemetry problem and a different hunt; see the pairing note below.
  What the report states - Microsoft Threat Intelligence analysed the injected JavaScript from a tampered `anthropic.claude-code` package (versions 2.1.313 and 2.1.312) served briefly from the Cursor extension marketplace on October 29, 2026. The loader "runs when the extension module loads and attempts to add an attacker-controlled Secure Shell (SSH) key, enable the local SSH service, establish reverse SSH forwarding, configure persistence, and report host details." Microsoft confirmed the packages "were never published nor distributed from Microsoft Visual Studio Marketplace and from npm @antropic-ai/claude-code", and that Anthropic's systems were not compromised. The macOS persistence row of the report's table reads: "User LaunchAgent with RunAtLoad and KeepAlive", with key artifacts `~/Library/LaunchAgents/com.apple.sysmond.plist`, `~/.config/.smt` and `~/.config/.smtk`.
  The tunnel shape, verbatim - The report gives the arguments: "-N -R '*:0:localhost:22'". It also explains what the zero means, which matters because it is easy to misread: "The remote port value 0 asks the server to allocate a port; it does not change the local target from port 22." On the retry behaviour: "On Unix-like systems it prefers autossh, falling back to ssh; on Windows it uses a hidden PowerShell loop. The loops wait sixty seconds after SSH exits before retrying."
  The two key roles - There are two distinct SSH identities and conflating them wastes triage time. One is an Ed25519 *public* key appended to the local `authorized_keys`, marked with the comment `svc-telemetry`, which authorises inbound access to the workstation account. The other is a *private* key decoded to a hidden temporary file for the outbound connection; the report describes the name as ".stk_ followed by ten hexadecimal characters derived from the hostname and home directory".
  What the loader collected, and what it did not - The report is careful here and the hunt should be too: the reconnaissance looks for "environment-variable names containing terms such as KEY, TOKEN, SECRET, PASS, AWS, or GCP, keeping up to forty matches", and then "The callback sends matching environment-variable names, not values." So an affected host has had its secret *inventory* disclosed, not necessarily its secrets. Scope credential rotation on evidence, not on this step alone.
  Why the LaunchAgent is the strongest anchor - Microsoft notes that "Removing or updating the extension does not remove artifacts written outside its installation directory", which is exactly why the plist is the durable observable: it survives the extension being pulled, the marketplace takedown and the user updating. The report also records that "Cursor's reported server takedown does not remove artifacts already present on a device."
  Primary query - the three fixed artefact paths, for macOS endpoints in Defender. Microsoft's own published query keys on the SHA-256 and the filenames; this adds the parent process, which is the part that generalises:
  ```kql
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where DeviceType == "Workstation" or isempty(DeviceType)
  | where FileName in~ (".smt", ".smtk", "com.apple.sysmond.plist", "authorized_keys")
      or FileName startswith ".stk_"
  | project Timestamp, DeviceName, ActionType, FolderPath, FileName, SHA256,
            InitiatingProcessFileName, InitiatingProcessFolderPath,
            InitiatingProcessCommandLine, InitiatingProcessParentFileName
  | order by Timestamp desc
  ```
  `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, which is fine here: every artefact in this chain is written. It carries no signature columns either, so if a written file needs a signer it has to be joined from `DeviceFileCertificateInfo` on SHA1.
  The generalised query - an editor writing a LaunchAgent. The filenames are one operator's choice; the lineage is the durable part. No legitimate build of a code editor writes into `~/Library/LaunchAgents/`:
  ```kql
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("FileCreated", "FileRenamed", "FileModified")
  | where FolderPath has "/Library/LaunchAgents/"
  | where InitiatingProcessFileName has_any ("Cursor", "Code", "Code Helper", "Electron",
                                             "node", "bun", "npm", "npx", "sh", "bash", "zsh")
  | summarize writes = count(), plists = make_set(FileName, 10),
              cmds = make_set(InitiatingProcessCommandLine, 5),
              firstSeen = min(Timestamp)
          by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath
  | order by firstSeen desc
  ```
  The tunnel query - the argument shape rather than the destination. Defender populates `ProcessCommandLine` for macOS execs, and the remote-forward target is the discriminating token:
  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where FileName in~ ("ssh", "autossh")
  | where ProcessCommandLine has "-R"
  | where ProcessCommandLine has_any ("localhost:22", "127.0.0.1:22", ":0:localhost:22")
  | project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine,
            InitiatingProcessFileName, InitiatingProcessCommandLine, InitiatingProcessParentFileName
  | order by Timestamp desc
  ```
  ESF equivalent, where Defender is not deployed - the exec half is `ES_EVENT_TYPE_NOTIFY_EXEC` filtered on an executable basename of `ssh` or `autossh` with `-R` in `argv`, and the persistence half is `ES_EVENT_TYPE_NOTIFY_CREATE`, `_WRITE` and `_RENAME` under `~/Library/LaunchAgents/` and `~/.config/`. Two instrumentation caveats worth confirming before trusting a clean result: the ESF has no network events, so the tunnel's destination has to come from a network sensor or from the argument vector, and many ESF client configurations are scoped to system paths and never see writes inside a user home.
  Confirming the agent actually loaded - the plist existing and launchd honouring it are different facts. Query the Unified Log for the agent label rather than inferring from the file:
  ```shell
  log show --last 7d --predicate 'subsystem == "com.apple.xpc.launchd"' --info | grep -i sysmond
  launchctl list | grep -i sysmond
  ```
  Live triage on a suspect host - read the configured action before touching anything, because the name is designed to stop you from doing that:
  ```shell
  /usr/libexec/PlistBuddy -c Print ~/Library/LaunchAgents/com.apple.sysmond.plist
  grep -n 'svc-telemetry' ~/.ssh/authorized_keys
  ssh-keygen -l -f ~/.ssh/authorized_keys
  ls -la ~/.config/.smt ~/.config/.smtk
  ps -Ao pid,ppid,user,command | grep -E '(auto)?ssh .*-R'
  ```
  Expected, not observed by Microsoft - the report does not say that `~/.config/.smt` reconstructs its identity on every launch *on macOS specifically*; it says "On Unix-like systems, the .smt script reconstructs the persistent .smtk identity when it runs, then starts its own SSH retry loop", which covers macOS and Linux together. Treat a missing `.smtk` at triage time as inconclusive rather than as evidence the chain did not run.
  Indicators from the report - the configured destination is `134.209.82[.]225`, the reconnaissance endpoint is `hxxp://134[.]209[.]82[.]225:8099/beacon`, the installed authorisation key carries the comment `svc-telemetry` with fingerprint `SHA256:0Z6R+DF64Do2nwQic8a7kkfDLNNk4IiK+2U2Rci4htk`, the JavaScript entry point is `ecb58cb29078d9646ad1dcdbe51526f2d9cfea06be5fb2ab183e8ecc3ab6bf15`, and the decoded tunnel private-key file is `7e0a52885fadee05544a9e99eb18c792bec05900a5e1a66d68f8383decb0e278`. Microsoft is explicit that "Contextual strings and paths require behavioral correlation and should not be treated as conclusive evidence of compromise on their own."
  Response - preserve before cleanup, then treat the key and the agent as separate removals. Confirm the key against the published fingerprint before deleting the entry, and preserve unrelated keys and legitimate remote-development configuration. Microsoft's framing of the access question is the right one for triage: "A running SSH process does not necessarily mean the attacker gained access."
  Pairing - [[H430]] is the Windows half of the same loader, where the retry loop is a hidden PowerShell loop and the persistence is a scheduled task named after SysMon rather than a LaunchAgent. [[B067]] is the baseline that makes both practical, by establishing which processes legitimately write SSH material and which developer hosts legitimately run an SSH listener at all.

# H429

On October 29, 2026, a tampered copy of the `anthropic.claude-code` extension was served from the Cursor extension marketplace for roughly eleven hours. Microsoft Threat Intelligence analysed the injected JavaScript and found a loader that "runs when the extension module loads" — before the extension's own code — and then "attempts to add an attacker-controlled Secure Shell (SSH) key, enable the local SSH service, establish reverse SSH forwarding, configure persistence, and report host details."

The interesting part for a hunter is not the delivery. It is that every artefact the loader leaves behind is written *outside* the extension directory, which Microsoft states plainly: "Removing or updating the extension does not remove artifacts written outside its installation directory." The marketplace listing is gone, the server is taken down, and an affected Mac still has an authorised key it did not have before, a LaunchAgent that restarts a tunnel, and a script in `~/.config/` that rebuilds the tunnel identity when it runs.

The macOS persistence is a user LaunchAgent at `~/Library/LaunchAgents/com.apple.sysmond.plist`, configured — in the report's words — as a "User LaunchAgent with RunAtLoad and KeepAlive". The name is the whole trick. `com.apple.sysmond` reads as an Apple system daemon and sorts next to the real ones in any directory listing, and Microsoft's remediation guidance is built around not trusting it: "Inspect each startup object's configured action before removal; names alone are not sufficient to distinguish malicious objects from legitimate monitoring software."

The tunnel is a reverse forward, started outbound so nothing has to reach the laptop first. The arguments are given as "-N -R '*:0:localhost:22'", and the report heads off the obvious misreading: "The remote port value 0 asks the server to allocate a port; it does not change the local target from port 22." On macOS the retry loop prefers `autossh` and falls back to `ssh`, waiting sixty seconds between attempts.

Two things about this chain make it worth a dedicated hunt rather than an IOC sweep. First, the parent is a code editor. Nothing in a legitimate build of Cursor, VS Code or their helper processes writes a LaunchAgent, so the lineage is a durable signal that survives every filename in the report changing. Second, access and artefacts came apart: Cursor reports that "errors and administrator-permission requirements blocked SSH access on most macOS and Windows hosts", and Microsoft notes the loader "could still attempt to plant its SSH key, establish persistence, and report host information." A host can be fully instrumented, show no successful inbound session, and still be holding an attacker's authorised key.

## Why

- The artefacts outlive the delivery. The extension has been pulled and the tunnel server taken down, so the only remaining evidence on an affected Mac is the key, the plist and the scripts — none of which any takedown removes.
- The lineage generalises past this campaign. A code editor or its helper writing into `~/Library/LaunchAgents/` is an event with no legitimate explanation, and it will still be the right query the next time an extension marketplace is abused.
- A local `authorized_keys` append on a workstation inverts the normal direction of developer SSH activity. Remote-development tooling writes config, known_hosts and private keys locally and appends authorised keys on the *remote* side; an append on the laptop grants inbound access to whoever holds the matching private key.
- The masquerade is aimed at the responder, not the sensor. `com.apple.sysmond` on macOS and a task named after SysMon on Windows are both chosen so that a human scanning a list of startup objects moves past them, which is why the hunt resolves the configured action rather than the label.
- Reverse forwarding to `localhost:22` makes the workstation reachable without any inbound firewall change, and the sixty-second retry loop means a single blocked connection attempt tells you nothing about whether the channel ever worked.
