title: "Requests leaving a workstation carry the user's own session cookies because an operator is driving the browser as a proxy, and downloads the user starts are cancelled and re-issued from an operator URL while keeping the original filename"
hypothesis: >-
  An operator who controls a browser does not need to steal the session, because they can borrow it in place. Requests are composed on the operator side, sent into the browser, and issued from it with the credential store attached, so every request carries the victim's live cookies and arrives at the application as that user from that device - defeating device binding, token theft detection and conditional access alike. The same position allows the operator to intervene in downloads: a download event is cancelled, removed from the browser's own history, and re-issued against an operator-controlled URL with the original filename preserved, so the user sees the file they asked for and the host records an executable that arrived from somewhere else. The observable chain is application-side requests from a legitimate session whose pattern does not match human browsing, a download whose recorded source host does not match the site the user was on, and a file present on disk with no corresponding entry in the browser's download history.

false_positive_notes: |
  Browsers are automated legitimately and constantly, and the honest versions of this traffic look much the same from the application side.
  - Test automation, synthetic monitoring and accessibility tooling drive browsers with real sessions and produce machine-cadence request patterns. Scope the application-side checks to human user populations and allowlist the automation accounts, or those accounts will dominate every result.
  - Password managers, single-sign-on helpers and some security products issue requests with the user credential store attached by design. That is their function. The approved-extension inventory is the discriminator, not the behaviour.
  - Download managers, antivirus scanners, corporate proxies and content-inspection products legitimately interfere with downloads, including cancelling and re-issuing them, rewriting the source, and leaving a file on disk whose provenance does not match the originating page. Characterise what the organisation’s own stack does to a download before treating a mismatch as hostile.
  - Content delivery networks and redirect chains make source-host mismatch normal for legitimate downloads. A file requested from a vendor site routinely arrives from an unrelated CDN hostname. The finding is a mismatch against a destination with no relationship to the vendor, not any mismatch.
  - Browser download history is cleared by users, by privacy settings and by cleanup utilities, so a file with no history entry is weak on its own. It is corroboration for a download whose source does not match the page, not a finding by itself.
  - Session reuse from a single device over a long period is the normal state of a logged-in user. There is no new authentication event to anchor on, which is what makes this hard - the finding has to come from request pattern and from the extension inventory, not from an impossible-travel or new-device signal, neither of which will fire.
notes: |
  Source reporting is Unit 42's November 2026 analysis of Falcon, a browser-focused command-and-control framework assessed with high confidence to be a variant of the same core framework as PeckBirdy, reported by Trend Micro in January 2026. This hunt covers two capabilities the extension provides once installed; the extension itself and its permission profile are [[H469]]. The closest existing hunts are [[H144]], which covers abusing a Windows accessibility framework to read what is on screen - a different mechanism reaching a similar place - and [[H328]] and [[H066]], which cover extension-delivered compromise rather than what an installed extension then does with the session. No existing hunt covers a browser operated as a credentialed proxy or download substitution.
  Why this defeats the controls that were built for stolen sessions - The last several years of session-theft defence assume the token leaves the device: token binding, device-bound credentials, conditional access on device compliance, impossible-travel analytics, and detection of a cookie replayed from a new address. None of them apply here. Unit 42 reports that Falcon allows an operator "to use a victim’s browser as a proxy server and to use the victim’s browser data store, including session cookies and credentials for requests", with the background service worker setting the fetch options "to use the victim credential store in the request". The request originates on the victim device, from the victim browser, with the victim session - because it is the victim browser. Unit 42 states the result directly: this "enables an operator to browse resources using the identity of the victim, allowing for session hijacking and access to internal network resources". That last phrase is the part to carry into a threat model, because it includes internal applications the operator could not otherwise reach at all.
  Core filter 1, request pattern inside a legitimate session - Since neither the device nor the session nor the address changes, the only remaining discriminator is behaviour. Hunt application access logs for sessions whose request pattern does not look like a person: bursts of sequential requests with no think time, systematic enumeration of paths or object identifiers, retrieval of resources with no corresponding page view, and activity continuing at machine cadence through periods when the user is otherwise idle. Prioritise internal applications and administrative interfaces, because those are the ones Unit 42 names as newly reachable. Triage values are the session identifier, the request sequence with timestamps, the user agent, and whether an interactive page load preceded each resource fetch.
  Core filter 2, the request path through the extension - For endpoint-side confirmation it helps to know the route Unit 42 documents, because it explains which process the traffic appears to come from. The operator configures a proxy against the Falcon server, requests are encapsulated in a JavaScript snippet and sent to the implant, the sandbox executes it and calls a handler which "sends a message on the Chrome runtime message bus", and the background service worker constructs the request. The response is "Base64-encoded and returned in JSON via the C2 WebSocket". So the outbound application traffic is attributed to the browser process, the exfiltration path is the WebSocket from the same process, and the two are concurrent - a browser process sustaining a long-lived WebSocket to an unapproved destination while issuing an unusual volume of requests to an internal application is the correlation to build, with a bounded time window on the join rather than a correlation on process identity over a long lookback.
  Core filter 3, the download that was swapped - A separate capability with cleaner host-side evidence. Unit 42 reports the extension installs a listener for `chrome.downloads.onCreated` events, applies operator-defined intercept rules, and where a URL matches "cancels the original file transfer and removes the download from the Chrome download history", re-issuing it against a URL built by encoding the target and appending it to the operator redirect URL. Unit 42 gives the example of a rule intercepting all executable downloads from Google domains, and notes the consequence precisely: "The download retains the original filename and will appear to the victim as ChromeSetup.exe while the origins will show as evil[.]com." That example destination is illustrative rather than an indicator. Hunt for executables and installers in user download directories where the recorded source host has no relationship to the vendor the filename implies, and compare the zone identifier against both the filename and the page the user was on. Note that the common installer names are the targets here precisely because they are expected, so the filename is the thing being trusted and must not be the thing filtered on.
  Core filter 4, the file with no history entry - Because the extension removes the entry, the browser download database and the file system disagree. Hunt for files in download directories with no matching row in the browser download history for the same profile, then correlate against process-execution telemetry for subsequent execution of that file. A triage collection on Windows, taking a copy because the database is locked while the browser runs:
  ```powershell
  $profiles = Get-ChildItem "$env:LOCALAPPDATA\Google\Chrome\User Data" -Directory -ErrorAction SilentlyContinue |
              Where-Object { Test-Path (Join-Path $_.FullName 'History') }
  foreach ($p in $profiles) {
    $src = Join-Path $p.FullName 'History'
    $dst = Join-Path $env:TEMP ("hist_" + $p.Name + ".db")
    Copy-Item $src $dst -Force -ErrorAction SilentlyContinue
    "copied download history for profile $($p.Name) to $dst"
  }
  Get-ChildItem "$env:USERPROFILE\Downloads" -File -ErrorAction SilentlyContinue |
    ForEach-Object {
      $zone = Get-Content -Path $_.FullName -Stream Zone.Identifier -ErrorAction SilentlyContinue
      [pscustomobject]@{
        Name       = $_.Name
        Written    = $_.LastWriteTime
        SizeBytes  = $_.Length
        HostUrl    = ($zone | Select-String -Pattern 'HostUrl' | ForEach-Object { $_.Line })
        RefererUrl = ($zone | Select-String -Pattern 'ReferrerUrl' | ForEach-Object { $_.Line })
      }
    } | Format-Table -AutoSize
  ```
  Query the copied history database for its download rows with any SQLite client and reconcile against the file listing. A file on disk with a zone identifier naming an unrelated host, and no row in the history, is the strong case.
  Core filter 5, the collection that rides the same session - Useful for scoping rather than detecting. Unit 42 reports that an operator can upload JavaScript which uses the user Gmail session cookie to enumerate authenticated accounts and then collect mail - date, sender, receiver, subject, body and attachments - and that the same passive hooking collects Discord messages and friend lists and Zalo chat databases, because those applications use JSON over HTTP. For a confirmed case, the exposure is every application the user was signed into during the window, which is a different and larger question than which credentials were stored.
  Core filter 6, where to start if you only do one thing - The extension inventory in [[H469]]. Every capability in this hunt requires the extension to be installed, so a permission-profile review across the estate finds the cause directly, rather than inferring it from application logs where the activity is designed to be indistinguishable from the user. The application-side checks here matter most for scoping a known case and for the population where extension inventory collection is incomplete.
  Scope - Managed endpoints running Chromium-family browsers and Firefox, plus the application-side logs for internal and SaaS applications those users reach. Unit 42 reports the Firefox and Chrome extensions are functionally identical, so both engines are in scope.

# H470

Every defence built for stolen session cookies assumes the cookie leaves the device.

Token binding. Device-bound credentials. Conditional access on device compliance. Impossible travel. Alerting on a session replayed from a new address. All of it watches for the session showing up somewhere it should not be.

Falcon never moves the session. Unit 42 found that an operator can use the victim's browser as a proxy: requests are composed on the operator side, sent into the browser, and issued from there with the credential store attached. The request leaves the right device, from the right browser, with the right cookies, because it is the right browser. Unit 42 notes this gives the operator access to internal network resources — applications they had no path to at all.

There is nothing for the identity stack to catch. No new authentication. No new device. No new address. The user is sitting at the machine while it happens.

The second capability is cruder and leaves better evidence. The extension listens for download events. When a download matches an operator rule, it cancels the transfer, deletes the entry from the browser's own download history, and re-issues the request against an operator URL with the target encoded onto the end. The filename survives. Unit 42's example: the user sees `ChromeSetup.exe`, and the origin shows a host that has nothing to do with Google.

So the file on disk has the name the user expected, a source host that makes no sense, and no row in the download history to contradict either.

The honest starting point is not the application logs. It is asking which extensions are installed, and what they are allowed to do.

## Why

- **This is the session-theft defence gap, stated as plainly as it gets.** Binding a token to a device stops a token that travels. It does nothing about an operator issuing requests from inside the bound device. Any control whose logic is "is this session where we expect it" answers yes here, every time.
- **Internal applications become reachable, which changes the blast radius.** A stolen cookie gets an operator into whatever is internet-facing. A browser proxy gets them into whatever the user can reach — intranet applications, admin consoles, internal APIs that were never meant to be exposed and are often correspondingly under-defended.
- **There is no authentication event to anchor the investigation on.** Detection and forensics both normally start from a sign-in. Here the sign-in was the user's, days earlier, and entirely legitimate. That forces the analysis onto request cadence and shape, which is weaker evidence and needs the application logs that teams least often have.
- **Download substitution converts browser control into code execution, with the provenance laundered.** The user asked for an installer and got an installer, with the right name. The usual check a careful person performs — does this file look like what I asked for — passes. The mismatch lives in the zone identifier and in a history entry that was deleted.
- **The deleted history entry is a disagreement between two records on the same host.** The file system says a file arrived; the browser says it never downloaded one. That contradiction is cheap to test at scale and does not require knowing anything about the operator or the rule set.
- **The extension inventory answers in one query what the application logs can only hint at.** Every capability here depends on an installed extension with broad permissions. Hunting the consequence is hard by design; hunting the cause is an inventory and a sort.
