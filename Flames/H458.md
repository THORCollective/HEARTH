false_positive_notes: |
  The individual events each have a legitimate population, and the policy change is rare enough to alert on directly in most estates.
  - `execInstalledOnly` is legitimately toggled during some vendor-supported troubleshooting, driver work and third-party agent installations. Those changes should correspond to a change record, originate from a named engineer's session, and be reverted. Alert on all of them and close the explained ones; the volume is low enough that this is practical.
  - Root SSH to an ESXi host is normal in estates that have not yet moved administration into vCenter, and it is routine during storage or networking break-fix work. Baseline which hosts accept SSH, from which sources, and during which maintenance windows before treating a session as suspicious.
  - Backup, replication and monitoring products legitimately run as root on the host and execute their own binaries. Those binaries are usually installed as VIBs, which is precisely why they do not trip `execInstalledOnly` - a product that needs the policy disabled to function is a finding to escalate with the vendor rather than an allowlist entry.
  - Blocked non-installed execution attempts also occur when an administrator copies a diagnostic tool to a host and tries to run it. That is the same first step as this chain, so the discriminator is what happens next: an administrator who is blocked usually stops or installs the tool properly, while this chain disables the control.
  - Log wiping removes the evidence this hunt reads, so an absent or truncated shell log is itself a finding rather than a clean result. Remote syslog forwarding is what makes the hunt possible, and verifying that forwarding is live on every host is part of running it.
notes: |
  Source reporting is Kaspersky GERT's analysis of two ransomware cases in virtualized environments, covering a BlackNevas intrusion against ESXi and a The Gentlemen intrusion against Proxmox. The Proxmox half is hunted in [[H459]], and the credential-path precondition both cases share is baselined in [[B070]]. The ESXi case began with ransomware activity on a Windows system in a virtualized domain controller segment, where UserAssist artefacts recorded execution of the AnyDesk RMM tool and GMER binaries.
  How the credential was obtained matters for scoping - the environment used PRTG Network Monitor to monitor its virtual infrastructure, the PRTG deployment had broad access to the ESXi hosts, and the same root password was reused across several nodes. Kaspersky's summary of the structural problem is worth keeping in the hunt's framing: "This design joined monitoring, credential storage, and direct administration into one attack path." So when this chain fires on one host, the monitoring platform and every host sharing its credential are in scope immediately.
  The blocked first attempt - Core filter: ESXi shell and hostd logs showing an execution attempt denied by the execution policy. In the reported timeline, root uploaded a file named `esx`, then ran `chmod 777 esx` followed by `./esx /log`, and the attempt failed with the error "Execution of non-installed file prevented". Triage values are the invoking user, the source IP of the SSH session, the full command, the file path, and the exact denial string. Correlation: tie the upload to the session by timestamp - the file arrives inside an SSH session, so the same session ID covers transfer, chmod and the blocked run. Strong red flags are a `chmod 777` or `chmod a+x` against a file in a non-standard directory, and a short single-word binary name with no path, which is what an operator uses when they expect to run it once.
  The policy change itself - Core filter: an advanced-setting write turning the execution policy off. The reported command is:
  ```sh
  esxcli system settings advanced set -o /User/execInstalledOnly -i 0
  ```
  That is the single highest-value line in the whole chain, because it has no routine administrative purpose and it converts a blocked host into an executable one. Verify the syntax parses on your own hosts before building a filter on it - the shell form above is valid under `sh` and is reproduced from the report. Triage values are the setting path, the old and new integer values, the invoking user, the session source IP, and whether a matching vCenter task exists. A change with no corresponding vCenter task was made directly on the host, which is the point Kaspersky draws out - direct SSH access let the actor authenticate as root, upload a binary, and change a security setting without first passing through vCenter role controls. Kaspersky's remediation guidance states the detection requirement plainly: alert when `execInstalledOnly`, Secure Boot enforcement, Lockdown Mode, SSH, local accounts, exception users, firewall rules, or remote logging settings change.
  The successful execution and the wipe - Core filter: execution of the same path immediately after the policy change, with datastore and log-handling switches. On the second host in the same incident the reported commands were `chmod a+x esx && chmod 777 esx`, then `./esx /selftest`, then `nohup ./esx /p /vmfs/ /depth 5 /log /wipe`, then `./esx /depth 5 /log /wipe`. Triage values are the full argument list, the use of `nohup` to survive session termination, the datastore path passed as the target, and the recursion depth. The `/selftest` run before the real one is a useful tell on its own: an operator validating a tool on a host they intend to encrypt. Strong red flags are `nohup` plus a `/vmfs/` path argument in one command line, and any argument that names log handling, since an encryptor that also wipes is deliberately removing the record this hunt depends on.
  Fan-out on the shared credential - Core filter: successful root SSH authentications to two or more hosts from different source addresses inside a short window, where the hosts are known to share a password. Kaspersky's second host showed an SSH connection by root from a different network range at the same time as the first host was being encrypted, which means the fan-out is concurrent rather than sequential and a per-host alert will fire several times in parallel. Correlation: group authentication events by the account name across all hosts and look for a count of distinct hosts per hour that no named administrator produces. Pivot: whatever system held the credential - a monitoring server, a connection manager, a password note - becomes the next investigation target, not the hypervisor.
  Where to look when the logs are gone - Core filter: evidence outside the host. If shell and auth logs were wiped and forwarding was not configured, the surviving sources are the storage array's write-throughput metrics, vCenter's own event stream, network flow records showing the SSH sessions, and the virtual machine files themselves. Correlation: a near-simultaneous write-rate spike across datastores on several hosts, with no backup job scheduled, dates the encryption window even with no host log at all.

# H458

Kaspersky's Global Emergency Response Team investigated two ransomware cases in virtualized environments. The first one is an unusually clean illustration of a control that worked, and then did not.

The intrusion reached a Windows system in a virtualized domain controller segment first. The environment monitored its virtual infrastructure with PRTG Network Monitor, and that PRTG deployment held credentials with broad access to the ESXi hosts. The same root password was reused across several nodes. One compromise of the monitoring platform therefore produced administrative access to the hypervisors it was watching.

On the host, the operator uploaded a binary over SSH, made it executable, and ran it. `execInstalledOnly` blocked it: the host refused to run a file that had not arrived as an installed package. That is the control doing its job.

It lasted one command. The same root session wrote `/User/execInstalledOnly` to `0` with `esxcli`, re-ran the binary, and encrypted the datastore - passing switches that also wiped logs. Minutes later the same credential was in use on a second host on a different network range, doing the same thing.

The hunt is the ordering. Each event on its own has an innocent explanation. A blocked non-installed execution, followed by someone turning off the policy that blocked it, followed by a successful run of the same file, does not.

## Why

- The policy change is a single-line, high-signal event with almost no legitimate daily use, and it tells you the operator already holds root. Unlike most hypervisor detections, there is no noisy precursor to filter - the alert fires on a configuration write that an estate can reasonably expect to review every single time.
- The blocked attempt is a free early warning. ESXi records the denial before anything is encrypted, which places the hunt before impact rather than after it, and distinguishes this from datastore-encryption detections that only fire once virtual machines are already down.
- Credential reuse makes the blast radius knowable in advance. The same root password across nodes means one recovered secret reaches every host that shares it, so a hit on one host immediately scopes the response to a known set rather than to an unknown one. Kaspersky's point that monitoring, credential storage and direct administration had been joined into one path is the reusable lesson, not an incidental detail.
- The anti-forensic step is in the same command line as the impact. The encryptor's own switches handle log wiping, so the evidence disappears as part of normal operation rather than as a separate cleanup phase. That makes remote syslog forwarding a prerequisite of the hunt, and verifying forwarding on every host a finding-generating exercise in its own right.
- A control that the daily administrative credential can switch off is a speed bump, not a boundary. Pairing `execInstalledOnly` with Secure Boot and TPM-backed configuration protection, keeping SSH stopped by default, and routing administration through vCenter are the structural fixes this hunt argues for, and the hunt measures whether they are in place.
