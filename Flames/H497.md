false_positive_notes: |
  Legitimate administration does produce some of these artefacts individually. Backup and replication products read VMDKs, and support engineers do unpack diagnostic bundles onto hosts. The distinguishing facts are the method and the path: supported backup software reads virtual disks through the vSphere Storage APIs for Data Protection from a registered backup proxy, not by invoking a Python script against a raw `/dev/disks/` device path from an interactive root shell on the hypervisor.

  ESXi ships a restricted Python runtime and some VMware-supplied scripts use it, so a Python process on an ESXi host is not automatically malicious. What is not routine is Python being invoked with a raw disk device path and a `-flat.vmdk` path with a partition suffix as arguments, which is the specific invocation shape Mandiant recorded.

  Hidden directories on datastores occasionally appear from administrative scripts and from products that stage temporary data. Reconcile each one against the storage team's records rather than assuming; the suspicious case is a dot-prefixed directory created from an interactive root session and deleted a short time later after an archive was copied out of it.

  Authorised-key additions to the ESXi root account can be legitimate when automation or a configuration-management system manages the host. Register those keys explicitly by fingerprint so an unregistered key is a finding by difference, and note that Mandiant observed the corresponding private key staged on a separate compromised Linux appliance at `/tmp/123.key`, so the key pair's other half may be recoverable elsewhere in the environment.

  Mandiant describes the staged toolset as a suspected VMware-specific toolset and names the archive it arrived in and the script that was run, but does not publish the script itself or attribute it to a public project. Treat the tool as unidentified rather than naming a specific public utility in an investigation write-up.

  The assertion that no guest-side telemetry is produced is a property of offline disk access rather than something Mandiant measures. It follows from the files being read from the VMDK by the hypervisor rather than by any process in the guest, but confirm against the guest's own logs for the window before concluding the guest saw nothing.
notes: |
  Execution leg (ESXi shell and syslog forwarded off the host) - Core filter: any `python` or `python3` process on an ESXi host whose command line contains `/dev/disks/`, `vml.`, `-flat.vmdk` or a partition suffix of the form `:part` followed by a digit. Mandiant recorded the extraction as a repeated sequence of a Python script invoked with a device flag naming a raw disk under `/dev/disks/vml.` and a subcommand, first listing the disk, then reading file information, then extracting named paths out of a `-flat.vmdk` partition into a local directory. The paths taken were the Windows NTDS directory, `Windows/System32/config/SYSTEM`, `Windows/System32/config/SECURITY` and `Windows/System32/dns`. Also filter on `tar` extracting a gzipped archive on the host, which is how the toolset arrived. Triage values are `ESXi hostname`, `full command line`, `working directory`, `principal`, `session source address`, `timestamp` and `parent process`. Strong red flags: the arguments name a VMDK belonging to a domain controller; the extraction targets `config/SYSTEM` or `config/SECURITY`, which are only useful together with NTDS; several extractions run back to back within minutes.

  ESXi does not log shell command execution anywhere useful by default, and this is the single most important collection prerequisite for the hunt. Mandiant's hardening guidance for this campaign states directly that remote syslog forwarding captures the execution of `tar` and the Python VMFS script over SSH, exposing the extraction of NTDS.dit and registry hives in real time, and that forwarding bash command execution to a SIEM bypasses local anti-forensics such as `.bash_history` deletion. Configure it before the hunt, not after.

  Staging and datastore leg (datastore inventory, ESXi shell records) - Core filter: directories on a VMFS volume whose name begins with a dot, and any `scp` invocation whose target or source path is inside one. Mandiant recorded a hidden directory named `.a` created on a VMFS volume, an inbound SCP connection established to it, and afterwards an archive named `o.tar.gz` copied out and the directory deleted. A sweep that finds the staging area while it still exists:

      find /vmfs/volumes -maxdepth 2 -name '.*' -type d -exec ls -la {} \; 2>/dev/null

  Triage values are `volume name`, `directory path`, `creation time`, `deletion time`, `contents and sizes`, and the `principal` and `source address` of the session that created it. Strong red flags: a dot-prefixed directory containing a `.tar.gz` of a few hundred megabytes or more; the directory is removed within hours of creation; the volume also hosts a domain controller's disks.

  Persistence leg (authorised-keys collection) - Core filter: any change to `/etc/ssh/keys-root/authorized_keys` on an ESXi host, and any key whose fingerprint is not in the approved register. Mandiant observed the actor add an SSH public key to the root account's authorised keys, with the matching OpenSSH RSA private key staged on a compromised Linux appliance so it could authenticate outbound to ESXi without a password. Collect fingerprints rather than key bodies for comparison:

      for h in $ESXI_HOSTS; do ssh "root@$h" "ssh-keygen -lf /etc/ssh/keys-root/authorized_keys" ; done

  Strong red flags: a key added outside a change window; a key whose comment field does not match any known automation account; the same public key present on several hosts, which indicates one operator key distributed across the estate.

  Network leg (flow records) - Core filter: SSH sessions to ESXi management interfaces from internal hosts that are not registered management sources, and outbound or lateral transfers from ESXi with a large send volume. Mandiant records the archives being downloaded from the Linux appliance to the Remote Support appliance over HTTP GET, from where the actor likely exfiltrated them - so the hypervisor's own egress may show nothing, and the useful measurement is the ESXi-to-appliance leg rather than ESXi-to-internet. A time-bounded correlation is needed here: take the window around each extraction command and look only at transfers inside it, because joining on host alone across a long lookback will pair unrelated backup traffic.

  Identity impact and response - If an extraction is confirmed, the credential exposure is the entire domain, not one host. NTDS plus the SYSTEM hive is sufficient to recover every account's credential material offline, and the SECURITY hive adds cached secrets and trust material, so scope the response as a domain-wide credential compromise - including the `krbtgt` account - rather than as a single-host incident. The `Windows/System32/dns` directory taken alongside them yields the internal name space, which is reconnaissance for the next phase. Determine from the datastore inventory which guest the VMDK belonged to before deciding scope; this is why the domain-controller-to-datastore mapping is a listed data source.

  Scope note: HEARTH's existing hunts cover credential-store theft from inside Windows - H121, H180, H116, H324 and the baselines B015, B016 and B053 all approach NTDS and hive access from guest-side telemetry - and the hypervisor hunts H061, H065, H074, H077, H458 and H480 cover VIB acceptance levels, rogue VM provisioning, rogue virtual NICs, `execInstalledOnly` and Host Profile SSH enablement. Nothing covers reading a guest's disk from the hypervisor, which is the case where every guest-side detection in that first group is structurally blind. H495 covers the vCenter credential theft that produced the ESXi access used here, and H496 the backdoor that held the foothold on the Linux appliance the data was moved through.

# H497

Mandiant and Google Threat Intelligence Group's November 19, 2026 analysis of ARMORY CASTLE ends with the actor on an ESXi host, holding root, using a WinSCP client to enumerate the file system, attached disks and mounted VMFS volumes. What followed is the part of the campaign with the widest consequences and the least telemetry.

The actor created a hidden directory named `.a` on a VMFS volume, established an SCP connection to it, unpacked a suspected VMware-specific Python toolset from a gzipped archive, and used it to read files directly out of a guest virtual machine's flat VMDK addressed by raw device path. The files taken were the Windows NTDS directory, the SYSTEM and SECURITY registry hives, and the DNS configuration directory. The results were archived, copied off over SCP, and the hidden directory deleted.

Taking NTDS and the SYSTEM hive together is sufficient to recover the credential material for every account in the domain, offline, at the actor's leisure. Doing it from the hypervisor means no process ran in the guest, no logon was recorded, and no guest-side security product had anything to observe. Mandiant's assessment of the broader campaign — deep platform expertise, substantial resource backing, three specialised malware sets and two zero-days — is visible most clearly in this step, which required no vulnerability at all once hypervisor root was held.

## Why

- Every guest-side detection for this credential theft is structurally blind to it. Hunting `ntdsutil`, volume shadow copies, `esentutl`, LSASS access or domain-controller logons will return nothing, because the domain controller was never touched. The only place the activity exists is the hypervisor's shell history and the datastore.
- The artefacts are distinctive and low-volume where they can be collected. A Python interpreter on an ESXi host with a `/dev/disks/` device path and a `-flat.vmdk` partition argument is not something any supported workflow produces. Neither is a dot-prefixed directory on a VMFS volume that appears, receives an archive, and disappears.
- The hunt's hardest requirement is also its cheapest fix. ESXi records shell activity locally and discards it; Mandiant's hardening guidance for this same campaign notes that remote syslog forwarding captures exactly the `tar` and Python executions this hunt looks for, in real time, and survives local history deletion. Without that forwarding there is no retrospective answer; with it, the hunt is a string filter.
- The response scope depends on identifying the guest, which makes the datastore-to-domain-controller mapping part of the hunt rather than part of the aftermath. A confirmed extraction is a domain-wide credential compromise including `krbtgt`, and the stolen DNS directory tells the actor where to go next.
