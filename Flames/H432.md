id: H432
category: Flames
title: "A runit service script on an SD-WAN controller that remounts the writable overlay executable and ptrace-injects a shared object into every running vdaemon before starting the real service"
hypothesis: >-
  On a Cisco SD-WAN controller, persistence does not look like a new process — it looks like an extra two lines at the top of a service launcher that still starts the legitimate service afterwards. UAT-11473 modified the runit `run` script for `sshd`, had it remount `/rootfs.rw` executable and background a loader script, and that loader enumerated running `vdaemon` PIDs, wrote them to a file under `/tmp`, and used a ptrace injector to load a shared object into each one. Nothing new listens, nothing new appears in a process list, and the implant ends up executing inside the daemon that already holds the control-plane session state. The hunt is a three-part file-and-process check on the service launchers, the PID list, and the set of shared objects actually mapped into `vdaemon`.

false_positive_notes: |
  Legitimate Cisco service launchers do themselves manipulate the writable overlay. The report records that on the aaamgr launcher, the deletion of the writable-overlay PAM configurations for sshd and login before remounting the writable overlay executable is part of the legitimate script — so the remount alone is not the finding. The finding is a remount in a launcher where the vendor image does not have one, or a remount followed by a background invocation of a script that is not in the image.
  Vendor patches and software upgrades legitimately rewrite service launchers, so a diff taken across an upgrade boundary will light up everything. Re-baseline immediately after any planned upgrade and keep the image hash of the version actually running, not of the version you believe is running.
  Shared objects legitimately appear in `vdaemon` maps: the platform OpenSSL, libc and the Cisco platform libraries are all expected. Compare the mapped-object set against a known-good controller of the same role and software version, not against a mental model of what should be loaded.
  `ptrace` has legitimate users on these platforms during vendor-directed troubleshooting. A TAC engagement that attached a debugger will look like injection in audit records. Correlate with change records before escalating.
  Absence of evidence is weak here and should be stated as such in any triage note. The report records timestomping in the staging sequence ("touch --reference= and chmod --reference= staging commands copied reference file metadata"), so file timestamps cannot be used to establish when a launcher was modified, and a launcher whose mtime matches its neighbours is not thereby clean.
notes: |
  Platform - Linux-based Cisco SD-WAN controller appliances (the report names evidence from vSmart and vBond roles). This is not a hunt for endpoint EDR; it is an on-box integrity and memory-mapping check, because the controllers have no endpoint agent.
  What the report states - Cisco Talos identified UAT-11473 exploiting CVE-2026-20127, "an authentication bypass vulnerability in Cisco SD-WAN Catalyst Controller instances", then installing a framework Talos tracks as KeyDrift. Targeting "spans across space and satellite services, defense and aerospace technology, and policy research", and Talos assesses with high confidence that the operating infrastructure of UAT-11473 overlaps considerably with the covert access network that Talos calls Silent Train, attributed to Volt Typhoon.
  The execution anchor, verbatim - "KeyDrift uses Cisco SD-WAN runit service paths as its primary execution anchor." For the sshd deployment: "the actor modifies the service run script, remounts /rootfs.rw executable, launches a malicious script" in the background, "and then starts the legitimate sshd service." The report describes the launcher as preserving normal behaviour while "adding two malicious lines before service execution."
  The injection chain - the loader script "enumerates running vdaemon PIDs, records them in" a file under `/tmp`, and invokes the injector component to inject the PolyFlame shared object "into each process." Talos maps the injector to T1055.008 with the note "rsshd injects libdssl.so into vdaemon by PID", and maps the interposition to T1574.006 with the note "PolyFlame uses dlsym(RTLD_NEXT, ...), dlopen, and runtime interposition."
  Why vdaemon is the target - the report is explicit about what the injected module gets for free: being resident in `vdaemon` provides "access to all in-process state: DTLS session keys, vEdge topology, OMP routes, and policy tables." There is no need to sniff a wire or crack a session when the implant executes inside the process that already holds the keys.
  The second launcher, and the cleanest single indicator in the report - a variant masquerades as the `aaamgr` service, executed by a malicious runit service under `/etc/sv/aaamgr/` with `aaamgrd` and a modified `run` launcher. Talos then supplies the fact that makes this checkable in one command: "The legitimate Cisco aaamgr component is a Python package; it does not normally appear as a compiled ELF runit service." A compiled ELF at that service path is wrong by construction, independent of hashes.
  The packed loader - "aaamgrd is a statically linked ELF64 executable with no section headers, a single RWE loader segment, and an RC4-encrypted embedded ELF payload." Its anti-analysis is described as: "It performs an anti-debug check by deobfuscating /proc/%d/status and TracerPid: and exits if a tracer is present." A single read-write-execute segment with no section headers is a structural property, not a signature, and `readelf` reports it without needing to run anything.
  Why network detection will not carry this hunt - "No hardcoded IPv4 addresses, binding ports, callback domains, URLs, host headers, or polling interval were recovered from the analyzed PolyFlame samples", and the module is "designed for in-band control or tasking over Cisco SD-WAN control-plane traffic rather than a conventional fixed external beacon." There is no beacon to find and no destination to block. The observables are on the box.
  Check 1 - the service launchers against the vendor image. Run this per controller and diff the output against a known-good appliance of the same role and software version:
  ```shell
  for svc in /etc/sv/*/; do
    printf '=== %s\n' "$svc"
    sha256sum "$svc/run" 2>/dev/null
    grep -nE 'remount|rootfs\.rw|&[[:space:]]*$|nohup|/tmp/' "$svc/run" 2>/dev/null
  done
  ls -1 /etc/sv/ | sort > /tmp/sv_actual.txt
  ```
  Two things to look for, both named in the report: a `mount` with a remount of `/rootfs.rw` to executable in a launcher the vendor image does not have one in, and a backgrounded invocation of a script that is not part of the image. Compare `/tmp/sv_actual.txt` against the service list from a known-good controller; a service directory present only on the suspect box is the aaamgr case.
  Check 2 - the ELF-versus-Python test on the aaamgr service path. This is the single highest-confidence check in the hunt because it does not depend on any indicator:
  ```shell
  file /etc/sv/aaamgr/* 2>/dev/null
  for f in /etc/sv/aaamgr/*; do
    [ -f "$f" ] && readelf -hS "$f" 2>/dev/null | head -20
  done
  ```
  An ELF64 binary here contradicts the vendor architecture. A section-header count of zero on that ELF corroborates the packed loader the report describes.
  Check 3 - what is actually mapped into vdaemon. The injected object is resident in a legitimate process, so a process list will not show it and a file hunt will only find it if it is still on disk:
  ```shell
  for pid in $(pgrep -x vdaemon); do
    printf '=== pid %s\n' "$pid"
    tr '\0' ' ' < /proc/$pid/cmdline; echo
    awk '$6 ~ /\.so/ {print $6}' /proc/$pid/maps | sort -u
    awk '$2 ~ /rwx/ {print}' /proc/$pid/maps
  done
  ```
  The first `awk` lists every mapped shared object for comparison against a known-good controller; `libdssl.so` is the name Talos recovered, but a name comparison is the weak version of this check and the set comparison is the strong one. The second `awk` reports anonymous read-write-execute mappings, which is where an unpacked payload lives and which should be absent in a clean daemon.
  Check 4 - the loader's PID file and the overlay mount state:
  ```shell
  ls -la /tmp/system-vdaemon 2>/dev/null && cat /tmp/system-vdaemon
  mount | grep -E 'rootfs\.rw'
  ```
  The PID list file is a deliberate artefact of the loader rather than an accident, and the mount output answers whether the overlay is currently executable — which it should not be in steady state.
  Check 5 - ptrace, where the platform allows auditd. The injector works by ptrace attach, so the syscall is the event:
  ```shell
  auditctl -a always,exit -F arch=b64 -S ptrace -k keydrift_ptrace
  ausearch -k keydrift_ptrace -i 2>/dev/null | tail -50
  ```
  This is a forward-looking control rather than a retrospective one: if the rule was not loaded before the intrusion, `ausearch` will return nothing and that result means nothing. Say so explicitly in the triage note rather than recording it as a negative finding.
  Collection discipline - read these facts from an off-box collection path wherever possible. The report records PAM tampering by the packed loader and timestomping in the staging sequence, so a shell on the compromised controller is not a trustworthy vantage point for either file metadata or authentication state. Collect the Cisco admin-tech bundle, and compare against a bundle taken from a known-good controller of the same version.
  Coverage already published by the vendor - Talos lists Snort SIDs for CVE-2026-20127 as 65938 and 65958, and for the artefacts in the blog as "Snort v2: 67387 through 67416" and "Snort v3: 7:44 through 7:73". Network IPS coverage addresses the exploitation attempt; it does not address a controller that was already compromised, which is what this hunt is for.
  Expected, not observed by Talos - the report does not state how UAT-11473 achieved the initial write to `/etc/sv`, beyond the authentication bypass; it does not resolve the tasking format ("exact command format unresolved" is the report's own entry for PolyFlame); and it records the `vdaemon.conf` file as never recovered. The auditd rule above and the read-write-execute mapping check are both my additions rather than vendor-published detections, and neither was used by Talos to find this activity.
  Pairing - [[H433]] covers the collection half of the same framework: the SSL_read hook that harvests data-plane keying material from decrypted control traffic and stages it encrypted in `/var/tmp`. A controller that produces a hit here should be checked against that hunt immediately, because residence and collection were deployed together.
  Closest existing coverage - [[B057]] is the nearest existing work and is a baseline rather than a hunt: it inventories edge appliances precisely because they have no EDR agent, no software inventory entry and no file integrity monitoring, and it is the right prerequisite for this hunt. [[H317]] covers a Cisco Secure Firewall Management Center intrusion reaching root through a legitimate management utility, which is a different Cisco platform, a different vulnerability and a different persistence mechanism. [[H353]] is the nearest hunt by shape — a service unit with a legitimate-sounding name plus timestomping — but on a Linux mail server with systemd rather than a controller appliance with runit.

# H432

The thing that makes this intrusion hard is that KeyDrift never adds a process. Cisco Talos describes the execution anchor plainly — "KeyDrift uses Cisco SD-WAN runit service paths as its primary execution anchor" — and the mechanism is two extra lines at the top of a service launcher that otherwise does exactly what it always did: remount the writable overlay as executable, background a loader script, then start the legitimate `sshd`. The service comes up. `sv status` looks right. Nothing new is listening.

The loader then enumerates the running `vdaemon` PIDs, writes them to a file under `/tmp`, and ptrace-injects a shared object into each one. From that point the implant is executing inside the daemon that holds the control plane, which Talos spells out: being resident there provides "access to all in-process state: DTLS session keys, vEdge topology, OMP routes, and policy tables."

Two properties of this design decide what a hunt can look like. First, there is nothing on the network to find: "No hardcoded IPv4 addresses, binding ports, callback domains, URLs, host headers, or polling interval were recovered from the analyzed PolyFlame samples", because tasking rides in-band on control-plane traffic rather than on a fixed external beacon. Second, there is no endpoint agent on these controllers, so the hunt is an on-box integrity and memory-mapping exercise rather than a query against a data lake.

The report also hands over one check that needs no indicators at all. A variant masquerades as the `aaamgr` service under `/etc/sv/aaamgr/`, and Talos notes: "The legitimate Cisco aaamgr component is a Python package; it does not normally appear as a compiled ELF runit service." A compiled ELF at that path is wrong by construction. `file` answers it in one command, and `readelf` corroborates it — the loader is "a statically linked ELF64 executable with no section headers, a single RWE loader segment, and an RC4-encrypted embedded ELF payload," which is a structural description rather than a signature.

One caveat belongs in every triage note on this hunt: the report records timestomping in the staging sequence, with `touch --reference=` and `chmod --reference=` copying metadata from a reference file. File times on these controllers cannot be used to establish when anything changed, and a launcher whose mtime matches its neighbours has told you nothing.

## Why

- Persistence that modifies an existing launcher and then starts the real service leaves the service healthy, so every health-based and availability-based check passes while the implant is resident.
- Injection into `vdaemon` puts the implant where the DTLS session keys, OMP routes and policy tables already are, which removes the need for any of the network-visible steps a hunter would normally look for.
- There is no beacon and no destination, by design and by vendor analysis, so blocklists, DNS reputation and egress filtering contribute nothing — the observables are all on the box.
- One check is decisive and cheap: a compiled ELF under a service path whose legitimate implementation is a Python package contradicts the platform architecture, independent of any hash or name.
- The controllers have no EDR, no inventory and no file integrity monitoring, which is exactly why the comparison has to be against a known-good appliance of the same role and software version rather than against expectations.
- Timestomping removes the easiest triage shortcut. Any conclusion drawn from file modification times on a suspect controller is unsound, and the hunt has to rest on content and mappings instead.
