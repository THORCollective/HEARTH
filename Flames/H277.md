false_positive_notes: |
  `attrib.exe` runs legitimately, and the `+h` half of this on its own is genuinely noisy. The `+h +s` pair
  against a user-writable staging directory is much narrower, but enumerate these before calling anything
  malicious:
  - Software installers and updaters that hide their own working directories under `C:\ProgramData\` —
    this is the largest benign population and it is real. The separator is the parent process: an MSI or
    a signed vendor updater rather than an interactively-spawned shell.
  - `desktop.ini` handling and Explorer folder customisation, which routinely sets `+s +h` on `desktop.ini`
    files specifically. Filter on the filename, not on the technique.
  - Login scripts, SCCM/Intune packages, and GPO startup scripts that hide configuration directories. These
    run as SYSTEM or as a deployment account, from a consistent path, on many hosts at once — the opposite
    profile to a single user pasting a command into a terminal.
  - Backup, imaging, and disk-utility software hiding recovery partitions or catalogs.
  - Game launchers and DRM.
  The separators that actually work, in order of strength:
  (1) PARENT PROCESS. A vendor installer chain is benign; `WindowsTerminal.exe -> powershell.exe -> cmd.exe ->
      attrib.exe` in a user's interactive session is the campaign.
  (2) DIRECTORY AGE. Legitimate software hides a directory it has owned for months. This chain hides a
      directory created minutes earlier — join the attrib event to Sysmon EID 11 file creations for the same
      path and check the delta.
  (3) DIRECTORY NAME. `C:\ProgramData\f47f2a8c21c9df4e` is a 16-character hex string with no vendor name in it.
      Legitimate `ProgramData` subdirectories are named after their product. A high-entropy or purely
      hexadecimal directory name under `ProgramData` is close to conclusive on its own.
  (4) FLEET PREVALENCE. A vendor's hidden directory appears on hundreds of hosts with the same name. This one
      appears on one host, with a name seen nowhere else in the estate.

  PLATFORM: Windows. T1564.001 is also defined for Linux and macOS, but this hunt is Windows-only — `attrib.exe`
  and the `+s` system attribute have no equivalent on the other platforms, and the delivery chain is
  Windows Terminal / PowerShell specific.

  SOURCE: Microsoft Threat Intelligence, "TerminalFix campaign deploys a reverse tunnel through multistage
  intrusion" (2026-08-28). The report maps this step explicitly: "T1564.001 Hide Artifacts: Hidden Files and
  Directories | The attrib +h +s command is applied to the payload directory." The staging path named in the
  report is `C:\ProgramData\f47f2a8c21c9df4e`, created by a pasted PowerShell command that downloads a ZIP with
  a custom User-Agent, extracts it, and runs `1.bat`, which launches `LockScreenContentServer.exe` silently.

  WHAT THE TERMINALFIX TWIST CHANGES. Ordinary ClickFix steers the victim to the Win+R Run dialog. TerminalFix
  steers them to Windows Terminal or PowerShell instead, which Microsoft notes increases "the likelihood that
  complex, multi-line scripts execute successfully" — the Run dialog mangles multi-line payloads, a terminal
  does not. Two consequences for hunting: the process ancestry runs through `WindowsTerminal.exe`/`wt.exe`
  rather than `explorer.exe`, and the pasted payload is long enough to be worth capturing in full via script
  block logging. If your existing ClickFix detection keys on `explorer.exe -> powershell.exe`, it does not fire
  on this campaign.

  DETECTION — PROCESS EXECUTION. Hunt `attrib.exe` (or any image whose `OriginalFileName` is `ATTRIB.EXE`,
  which catches a renamed copy) where the command line contains both `+h` and `+s`, and the target path is
  under a user-writable root. Sample Defender XDR advanced hunting query:

      DeviceProcessEvents
      | where FileName =~ "attrib.exe" or InitiatingProcessCommandLine has "attrib"
      | where ProcessCommandLine has "+h" and ProcessCommandLine has "+s"
      | where ProcessCommandLine has_any (@"\ProgramData\", @"\Users\Public\", @"\AppData\",
                                          @"\Temp\", @"\Windows\Temp\")
      | where not(ProcessCommandLine has "desktop.ini")
      | project Timestamp, DeviceName, AccountName, ProcessCommandLine,
                InitiatingProcessFileName, InitiatingProcessCommandLine,
                InitiatingProcessParentFileName

  Then pivot on the directory: join to `DeviceFileEvents` for `FolderPath startswith` the hidden directory in
  the preceding 10 minutes to recover the payload names and the writing process.

  DETECTION — THE REST OF THE CHAIN, from the same report, verbatim. These are the published Microsoft queries
  and they should be run alongside the attrib hunt, because any one of them corroborates it:

      DeviceProcessEvents
      | where InitiatingProcessFileName =~ "powershell.exe"
      | where FileName =~ "cmd.exe" and ProcessCommandLine has_all (@"\ProgramData\", "1.bat", "LockScreenContentServer.exe")

      DeviceImageLoadEvents
      | where InitiatingProcessFileName =~ "LockScreenContentServer.exe"
      | where FileName =~ "dui70.dll"
      | extend path = tostring(parse_path(FolderPath).DirectoryPath)
      | where path =~ InitiatingProcessFolderPath
      | where not(path has_any (@"\Windows\System32", @"\Windows\SysWOW64", @"\winsxs\", @"\program files"))

      DeviceProcessEvents
      | where FileName in~ ("pythonw.exe", "python.exe")
      | where ProcessCommandLine has_all ("client.py", "--server", "--uuid", "cert.pem", "gitnow.dev")

  Note: as published, the last query renders `cert.pem` and `gitnow.dev` with curly quotes, which will not parse
  in KQL. Convert to straight quotes before running.

  COMMAND-LINE PATTERNS TO HUNT DIRECTLY: `attrib +h +s C:\ProgramData\<hex>`, `attrib +s +h` (argument order
  varies), and the same with `/d` or `/s /d` for recursive directory application. Attackers also reach the same
  result through PowerShell — `(Get-Item <path> -Force).Attributes = 'Hidden,System'` or
  `Set-ItemProperty -Path <path> -Name Attributes -Value 'Hidden, System'` — which produces no `attrib.exe`
  process at all. Cover that variant via script block logging (EID 4104) searching for `Hidden` adjacent to
  `System` in an `Attributes` assignment; a hunt that only watches `attrib.exe` has a trivially available blind
  spot.

  IOCs FROM THE SOURCE REPORT: staging path `C:\ProgramData\f47f2a8c21c9df4e`; `1.bat`;
  `LockScreenContentServer.exe` executing outside `C:\Windows\SystemApps`; `dui70.dll` unsigned with a forged
  2104 timestamp; persistence name `LockScreenContentServer_MuODG5yBM`; implant files `client.py` and
  `cert.pem` run under `pythonw.exe`; C2 `gitnow[.]dev` over 443; stego image hosts
  `bestsocialmedianewspapper[.]com` and `offlineupdater[.]com`; compromised site `linked-log[.]com`. Treat the
  hashes and domains as perishable and the directory-hiding behaviour as durable.

  CATEGORY: Flames. Embers was seriously considered and the answer was to write BOTH — [[B039]] baselines the
  estate's existing hidden-plus-system directories, because the false-positive population here (installers that
  legitimately hide their own `ProgramData` folders) is real and is best resolved by an inventory rather than
  by a filter list that ages badly. This Flames hunt stands on its own because the behaviour has discrete,
  queryable IOCs — a specific process (`attrib.exe`), a specific flag pair (`+h +s`), a specific parent lineage
  (interactive shell rather than installer), and a specific path class — which is exactly the Flames trigger.
  Alchemy was rejected: there is no volumetric or statistical component. The event is rare, the flag pair is
  binary, and directory-name entropy — the one feature that could be scored — is better used as a triage sort
  than as a model.

# H277

A user pastes a command into Windows Terminal because a counterfeit Cloudflare Turnstile widget told them to. The command downloads a ZIP, extracts it to `C:\ProgramData\f47f2a8c21c9df4e`, and runs `1.bat`. Then it does one more small thing that is easy to overlook in the noise of a multistage chain: it runs `attrib +h +s` against that directory.

That single call is worth hunting on its own. The `+h` attribute alone hides a folder from a default Explorer view — but plenty of users tick "show hidden files." Adding `+s` marks it as a protected operating system file, which keeps it invisible even then, because that requires a second, separate setting almost nobody changes. The attacker is not hiding from your EDR with this; they are hiding from the human who goes looking after something feels wrong.

And unlike the hashes, the domains, and the payload names — all of which change next campaign — the folder-hiding step is structural. The chain needs a working directory that survives on disk, holds the side-loading pair, and does not invite curiosity. Every rebuild of this tradecraft will do something equivalent.

## Why

- **The flag pair is the signal, and it is much rarer than either flag alone.** `attrib +h` fires on installers, on `desktop.ini` handling, on half the software in the building. `+h +s` together, applied to a directory under `ProgramData` or `AppData`, is a deliberate choice to defeat the "show hidden files" setting specifically. That is a materially smaller population, and it is one that a hunter can actually work through by hand in an afternoon.

- **The parent process settles almost every false positive without a filter list.** Legitimate hiding of a `ProgramData` directory is done by an installer or an updater — an MSI, a signed vendor binary, a deployment agent running as SYSTEM. The malicious case is `WindowsTerminal.exe -> powershell.exe -> cmd.exe -> attrib.exe` inside an interactive user session. Keying the hunt on lineage rather than on an allowlist of vendor paths means it does not decay as software inventory changes, which is the usual failure mode of ClickFix detections.

- **Directory age turns one event into a timeline.** Joining the `attrib` call to file-creation events for the same path is a two-minute pivot that answers the question outright. A vendor hides a folder it has had since installation; this chain hides a folder it created ninety seconds ago, having just extracted a signed executable and an unsigned DLL into it. The extraction, the hide, and the launch all fall inside a few minutes and one process tree.

- **The directory name is a free discriminator that most detections ignore.** `C:\ProgramData\f47f2a8c21c9df4e` carries no product name — it is sixteen hex characters, generated per victim, and also reused as the fake "Cloudflare ID" shown to the user. Legitimate `ProgramData` subdirectories are named after the thing that made them. Scoring subdirectory names under `ProgramData` for entropy and absence from the fleet gives a ranked triage list at effectively no cost, and it survives the campaign's IOC rotation entirely.

- **TerminalFix breaks ClickFix detections that assume the Run dialog.** The pivot from Win+R to Windows Terminal is not cosmetic — it changes the process ancestry that most published ClickFix rules key on, and it exists specifically so that longer, multi-line payloads execute cleanly. Teams that built a rule around `explorer.exe -> powershell.exe` in 2025 have a rule that does not fire on this. Hunting the attrib step catches the chain regardless of which host application the paste landed in.

- **Catching this step catches the intrusion before it becomes a network problem.** What the hidden directory delivers is a signed Python runtime and a `client.py` that opens a TLS WebSocket to `gitnow[.]dev` and relays arbitrary TCP into the internal network. Microsoft's guidance is explicit that an affected host should be treated as a network pivot point, with credential rotation "including domain admin accounts if the host was domain-joined." The attrib call happens minutes before the AD reconnaissance and hours before the tunnel matters. It is the cheapest place in the chain to intervene.

- **The PowerShell variant is the obvious evasion and is trivially covered.** Setting `.Attributes = 'Hidden,System'` on a directory object achieves the same result with no `attrib.exe` process created. Any hunt built solely on process creation has a bypass that costs the adversary one line of code. Adding a script-block-logging query for the attribute assignment closes it, which is why EID 4104 is listed as a required source rather than a nice-to-have.
