false_positive_notes: |
  `svchost.exe` running from anywhere other than `System32` or `SysWOW64` is not a tuning problem — the genuine binary only ever runs from those two paths, so a path-based filter on the exact name is close to zero-false-positive and should be a standing detection rather than a periodic hunt. The broader half of the hunt, "anything executing from `C:\PerfLogs`", needs a little more care. `C:\PerfLogs` is created by Windows for Performance Monitor data collector sets and is empty by default on virtually every system; where an organisation genuinely uses data collector sets, the directory holds `.blg`, `.etl` and report `.xml` files written by `C:\Windows\System32\taskeng.exe` or the Performance Logs and Alerts service — not `.exe` or `.dll` files, and nothing executes from it. A small number of OEM diagnostic utilities and a few vendor support bundles stage temporary files there; those are identifiable by signature and by being single-run rather than persistent. Treat an unsigned or signature-mismatched executable in that path as a finding, not a candidate. Note that attackers choose `C:\PerfLogs` precisely because it is often excluded from AV scanning and from file-integrity monitoring, so an absence of alerts on the path is expected rather than reassuring.

  Why the tunnel rather than the ransomware - The encryption stage is the last thing to happen and the easiest to detect, which is to say the least useful thing to detect. GOST is an open-source Go tunneling tool, so it is not inherently malicious, is not well covered by signature detection, and persists the operator's access across reboots and credential resets. Catching the tunnel catches the intrusion during the staging phase — while `procdump` and `RClone` are still being set up and before `win.exe` runs.
  Name-and-path leg (primary, highest confidence) - Core filter - process creation where the image file name is `svchost.exe` and the image path does not begin `C:\Windows\System32\` or `C:\Windows\SysWOW64\`. This is a one-line query, it has effectively no legitimate matches, and it should be promoted to an alert. Triage fields - full image path, SHA256, signer status, parent process, `User`, and the command line (Huntress's title notes how little command line there was to work with, which is itself the point - path and parentage carry the detection where the command line does not). Extend the same logic to the other high-value impersonated names - `lsass.exe`, `services.exe`, `csrss.exe`, `winlogon.exe`, `taskhostw.exe`, `explorer.exe` - each of which has exactly one legitimate directory.
  Sample KQL - system binary names running from the wrong directory.
  `let systemNames = dynamic(["svchost.exe","lsass.exe","services.exe","csrss.exe","winlogon.exe","smss.exe","taskhostw.exe","spoolsv.exe","dllhost.exe"]); DeviceProcessEvents | where Timestamp > ago(30d) | where FileName in~ (systemNames) | where not(FolderPath startswith @"C:\Windows\System32" or FolderPath startswith @"C:\Windows\SysWOW64" or FolderPath startswith @"C:\Windows\WinSxS") | project Timestamp, DeviceName, AccountName, FileName, FolderPath, SHA256, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessFolderPath | order by Timestamp desc`
  Staging-directory leg (catches the rest of the toolkit) - Core filter - any process creation or image load whose path is under `C:\PerfLogs`, plus any file creation of `.exe`, `.dll` or `.bin` in that tree. In this intrusion the same directory held the tunnel, `procdump.exe` and `RClone`, so a hit on any one of them should immediately be widened to a full directory listing with hashes and creation times — that listing is effectively the operator's toolkit inventory and dates each stage of the intrusion. `C:\PerfLogs` is the specific path Huntress observed; run the same query shape against the sibling staging directories that recur across ransomware intrusions - `C:\Users\Public`, `C:\ProgramData`, `C:\Windows\Temp` and `C:\storage` (where this intrusion's ransomware binary sat).
  Sideload leg - Core filter - Sysmon Event ID 7 where the loading image is the masquerading `svchost.exe` and the loaded module is `config.dll` from the same directory. A generic and more durable form of this is any image load of a DLL from the same user-writable directory as its loading executable, where that executable is not signed by the DLL's signer. The real `svchost.exe` loads service DLLs named in the registry from `System32`; it never loads a `config.dll` sitting next to it.
  Network leg - Core filter - outbound connections from a process whose image path is user-writable, to an external IP, sustained rather than one-shot. Triage - destination ASN and hosting provider, connection duration and byte symmetry. A tunnel shows long-lived connections with bidirectional flow, unlike a downloader's short asymmetric burst. The observed C2 `64.227.4.134` is a retrospective search term, not the detection.
  Chain pivots - A hit here should be walked forward to the LSASS access from `procdump.exe` ([[H266]] and [[H108]] cover ProcDump-based credential theft), to the `RClone` exfiltration leg ([[H182]] and [[H127]]), and to the recovery-impairment stage. Note that this intrusion's shadow copy removal used `Get-WmiObject Win32_Shadowcopy , Remove-WmiObject` from PowerShell rather than `vssadmin delete shadows`, so detections keyed on `vssadmin` would not have fired — the same blind spot [[H348]] documents for `reagentc` and `diskpart`. Walk backward to the RDP logon that started it - Huntress names workstation `C1IFRYXI` as the source, so Event ID 4624 type 10 from an unrecognised workstation name is where the timeline begins.
  How this differs from the existing masquerading hunts - [[H253]] hunts a service registered as "Cloud Sync Service" running a `svchost32.exe` binary from AppData - a *near* miss on the name, established as a service, found through service-creation telemetry. This hunt is the *exact* name from a different staging path with no service involved, found through image-path and module-load telemetry, and its function is tunneling rather than persistence-by-service. Both are worth having because they fire on different telemetry and neither query returns the other's case.

# H361

Huntress titled their October 2026 Akira write-up "Up a Creek Without a Command Line," which tells you what the investigation was working with. The useful consequence for hunters is that everything in this intrusion has to be caught by path, parentage and module loads rather than by reading arguments.

The staging directory was `C:\PerfLogs` — a folder Windows creates for Performance Monitor and which is empty on essentially every system, writable without admin rights, and routinely excluded from scanning. Into it went `procdump.exe` for LSASS, `RClone` for exfiltration, and, in a `Temp` subfolder, a file named `svchost.exe` that loads a neighbouring `config.dll` and is in fact a GOST tunnel beaconing to `64.227.4.134`. The ransomware itself ran later from `C:\storage\win.exe`.

The entry point was RDP from a workstation called `C1IFRYXI`. On the way to encryption the operator stopped four Bitdefender services by name and deleted shadow copies with `Get-WmiObject Win32_Shadowcopy , Remove-WmiObject` — not `vssadmin`, so the detection most environments have for that step never fired.

The highest-value query in all of this is also the simplest: a process named `svchost.exe` running from anywhere other than `System32` or `SysWOW64`. There is no legitimate instance of that.

## Why

- **The name/path mismatch is as close to a free detection as Windows offers.** The real `svchost.exe` runs only from `System32` or `SysWOW64`. One query, no baselining, no tuning, and it catches the operator's tunnel directly.
- **The tunnel is the durable access, not the ransomware.** GOST keeps the operator in through reboots and password resets. Detecting at the tunnel stage catches the intrusion while `procdump` and `RClone` are still being staged, which is the difference between an investigation and a recovery.
- **GOST is a legitimate open-source tool.** It is not reliably caught by signature-based controls, and its presence is best found structurally — wrong name, wrong path, sustained outbound connection — rather than by hash.
- **`C:\PerfLogs` is chosen for a reason.** It is empty by default, user-writable, and commonly excluded from AV scanning and file integrity monitoring. The absence of alerts from that path is the attacker's objective, not evidence that nothing is there.
- **One hit enumerates the whole toolkit.** Because the operator reused the directory for the tunnel, the credential dumper and the exfiltration tool, listing it with hashes and timestamps reconstructs the intrusion's stages in a single step.
- **The command line was not available, and the hunt does not need it.** Image path, parent process and module loads carry this detection, which matters in exactly the environments where command-line auditing is incomplete.
- **It flags a `vssadmin` blind spot on the way past.** Shadow copies were removed through WMI cmdlets, so this intrusion sidesteps the most widely deployed recovery-impairment rule — worth confirming in your own environment while the hunt is open.
