false_positive_notes: |
  Node.js is a mainstream runtime and a great many benign things embed it. Developer workstations have it installed legitimately, often several versions at once through `nvm-windows`, `fnm` or `volta`, all of which unpack releases into per-user directories under `%LOCALAPPDATA%` or `%APPDATA%` — so "node.exe running from AppData" is normal on a developer endpoint and must not be hunted in isolation. Electron applications ship their own Node runtime inside the app bundle; VS Code, its extensions, and language servers spawn `node.exe` constantly; and CI agents unpack runtimes on demand by design. The separating features are host role, path shape and provenance. The malicious pattern is a runtime appearing on a host with no development function, unpacked into a path that imitates a Microsoft component location rather than a version manager's own directory, fetched ad hoc minutes before first execution, and immediately making outbound connections to infrastructure unrelated to any package registry. Scope this hunt to non-developer hosts first — servers, domain controllers, finance and HR endpoints, VDI — where the false positive rate collapses to near zero, and use software inventory to exclude hosts with a managed installation before widening. Note also that a version manager's path (`%LOCALAPPDATA%\nvm\v18.19.0\`, `%LOCALAPPDATA%\fnm_multishells\`, `%APPDATA%\npm`) is a legitimate and recognisable shape; the report's `\Microsoft\Assemblies\41f2\` is not, and that distinction is the point.
notes: |
  Platform: Windows. Driven by the Deception.Pro operational report "[Op Report] KongTuke ClickFix to SystemBC: HoK Intrusion" (September 2026), which records Node.js v18.19.0 and v22.23.1 fetched from `nodejs.org` and executed as `node.exe` from `C:\Users\<user>\AppData\Local\Microsoft\Assemblies\41f2\node-v18.19.0-win-x64\node.exe`, with the resulting process beaconing to `158.23.165.124` and `35.194.62.236` and moving roughly 4.5 GB. The report's own hunting guidance calls for `node.exe` under AppData in "masquerading paths like \Assemblies\41f2\" correlated with nodejs.org downloads and immediate outbound C2.
  Bring-your-own-interpreter, and why it is not a supply-chain hunt - The existing HEARTH coverage for malicious Node activity targets the package ecosystem: [[H333]] hunts a counterfeit npm package firing its loader at application runtime, [[H233]] covers import-time Node loader persistence, and [[H326]] covers fake VS Code extensions and git hooks. All three assume a development context and a package as the delivery vehicle. This hunt is the inverse: no package, no registry, no `package.json`, and frequently no development context at all. The operator brings the interpreter itself as a tool, exactly as others bring `python.exe` or a portable PowerShell build, because an interpreted payload can be re-obfuscated per run — the report notes the associated EtherRAT re-obfuscates on every execution, which defeats hashing entirely — while the process image on disk stays a genuine, valid Microsoft-and-OpenJS-signed binary.
  Path masquerade as the primary anchor - Core filter (Sysmon Event ID 11 / DeviceFileEvents): creation of `node.exe` anywhere under `%LOCALAPPDATA%` or `%APPDATA%` where the path is *not* a known version-manager or application directory. The observed path imitates a Microsoft component location: `AppData\Local\Microsoft\Assemblies\41f2\`. `%LOCALAPPDATA%\Microsoft\` legitimately holds Office, OneDrive, Teams, Edge and IME data, so a developer runtime unpacked beneath it is structurally wrong, and the short hex directory name (`41f2`) is a generated identifier rather than a version string. Strong red flags: the parent directory name is 4-8 hex characters; the full archive layout (`node-v*-win-x64\` containing `node.exe`, `npm.cmd`, `node_modules\`) appears under a `Microsoft\` ancestor; and the file-create burst completes within seconds of an archive download, indicating extraction rather than installation.
  Sample KQL — Node runtime unpacked outside managed and version-manager paths:
  `DeviceFileEvents | where Timestamp > ago(30d) | where FileName =~ "node.exe" | where FolderPath has_any (@"\AppData\Local\", @"\AppData\Roaming\") | where not(FolderPath has_any (@"\nvm", @"\fnm", @"\volta", @"\npm\", @"\Programs\Microsoft VS Code", @"\Yarn\", @"\pnpm")) | project Timestamp, DeviceName, InitiatingProcessAccountName, FolderPath, FileName, SHA256, InitiatingProcessFileName, InitiatingProcessCommandLine | order by Timestamp desc`
  Sysmon Event ID 1 / 4688 / DeviceProcessEvents — execution shape - Core filter: `node.exe` whose `FolderPath` is user-writable and whose parent is not a development tool. Triage fields: `ProcessCommandLine`, `FolderPath`, `AccountName`, `InitiatingProcessFileName`, `InitiatingProcessCommandLine`, `SHA256`. Strong red flags: `-e` or `--eval` with inline JavaScript, or `-p`, which executes code with no script file to recover afterwards; a script argument pointing at a `.js` file in `%TEMP%`, `%APPDATA%` or the same hex directory; `--no-warnings`, `--experimental-*` or `--max-old-space-size` on a host with no build workflow; a parent of `cmd.exe`, `conhost.exe`, `powershell.exe`, `wscript.exe`, `mshta.exe` or a sideloaded signed binary rather than `code.exe`, a terminal, or a CI agent. In this intrusion the initial access was a ClickFix `conhost --headless cmd /v /c` chain, so a `conhost.exe` or `cmd.exe` ancestor is particularly interesting — and note the signed `TRegSvr.exe` sideloading `vclimg370.bpl` appears in the same chain.
  Sysmon Event ID 3 / DeviceNetworkEvents — the disqualifying leg - Core filter: outbound connections from a `node.exe` running in a non-managed path. Legitimate Node egress goes to package registries (`registry.npmjs.org`, an internal Artifactory or Nexus), language-server localhost ports, or the application's own API. Strong red flags: connections to bare IP literals with no DNS resolution; sustained high-volume transfer (the report records ~4.5 GB to `158.23.165.124` and `35.194.62.236`); DNS or TLS SNI to public Ethereum RPC providers — `mainnet.gateway.tenderly.co`, `rpc.flashbots.net`, `rpc.mevblocker.io`, `eth.merkle.io`, `eth.drpc.org`, `eth-mainnet.public.blastapi.io`, `ethereum-rpc.publicnode.com` — which in this intrusion was the EtherHiding channel the Node process used to resolve its real C2 from a smart contract at `0xd8b8d42f2af83914fbf4316dbe3af0a7f577fbde`. That blockchain-resolver behaviour is hunted in its own right by [[H270]]; here it serves as high-confidence corroboration that a flagged `node.exe` is the implant.
  Download provenance - Core filter: proxy or DNS records for `nodejs.org` (and its `dist` paths) from a host with no development role, followed within minutes by the file-create burst above. `nodejs.org` is legitimate infrastructure, so this is provenance rather than an indicator — its value is that a managed installation arrives through software distribution, not through an ad hoc download by an interactive shell on a file server. The same intrusion fetched FFmpeg from `gyan.dev` in the same manner, so treat repeated ad hoc developer-tool downloads on one host inside one window as a strong pattern in itself.
  Retro-hunt note - Because `node.exe` is validly signed and unmodified, hash-based retro-hunts return only the legitimate runtime and are worthless here. Retro-hunt on the *path* and on the parent-child pair instead; both are preserved in EDR process telemetry long after the payload script has been deleted.
  Cross-technique: pair with [[H342]] (FFmpeg `gdigrab` capture) and [[H270]] (blockchain dead-drop C2 resolution), both from this same intrusion, and with [[B045]] which baselines what package-manager install scripts and external-IP lookups are legitimate per host.

# H343

The Deception.Pro report on a KongTuke ClickFix intrusion documents an operator who, mid-intrusion, downloaded official Node.js builds — v18.19.0 and v22.23.1 — from `nodejs.org`, unpacked them into `C:\Users\<user>\AppData\Local\Microsoft\Assemblies\41f2\node-v18.19.0-win-x64\`, and ran `node.exe` from there. That process then beaconed out, polling public Ethereum RPC providers to resolve its real command-and-control address from a smart contract, and ultimately moved around 4.5 GB.

This is bring-your-own-interpreter, and it is a rational choice. Every static detection an implant has to survive — hashes, YARA signatures, signature verification, reputation scoring, even most memory scanning — applies to the executable image. If the executable image is an unmodified, properly signed Node.js release from the official distribution, all of it passes cleanly. The malicious logic lives in JavaScript, which can be fetched at runtime, held in memory, passed via `--eval`, or re-obfuscated on every single execution, as the report notes EtherRAT does. There is nothing left on disk for a signature to match.

Two things make it huntable anyway. The first is the path: `%LOCALAPPDATA%\Microsoft\Assemblies\41f2\` is a deliberate masquerade — `%LOCALAPPDATA%\Microsoft\` is where Office, OneDrive, Teams and Edge keep data, and a Node runtime unpacked under it is structurally wrong in a way that legitimate version managers, which use their own recognisable directories, never are. The second is host role. A Node runtime appearing for the first time on a file server, a domain controller or a finance workstation is not ambiguous, and it is exactly the population an interactive intruder reaches for.

## Why

- Signature-based detection is structurally defeated here, and knowing that redirects effort to what still works. The binary is a genuine signed release, so hash lists, reputation and YARA all pass; only path, parent process, and network provenance retain any discriminating power, and all three are recorded in ordinary EDR process telemetry.
- Existing coverage points the wrong way. HEARTH's Node-related hunts target the package ecosystem — counterfeit npm packages, import-time loaders, malicious extensions — and all assume a development context with a package as the delivery vehicle. This intrusion had no package and no development context, which is exactly the gap that lets a team believe Node abuse is covered when this variant is invisible to them.
- The path masquerade is a deliberate, reusable choice rather than an accident, which makes it a durable anchor. Hiding a developer runtime under `%LOCALAPPDATA%\Microsoft\` with a hex-named parent directory is doing work for the adversary — it buys plausibility against a human analyst scrolling a process list — and that same choice is what separates it cleanly from every legitimate version manager's directory layout.
- An interpreted payload defeats retro-hunting by hash but not by lineage. Once the script is deleted there is nothing to scan for, yet the `conhost.exe` → `cmd.exe` → `node.exe` parentage and the unmanaged path persist in process telemetry, so a retrospective sweep can still establish first execution and scope weeks later.
- The corroborating network behaviour is unusually distinctive. A Node process on a non-developer host querying public Ethereum RPC endpoints has no benign explanation in an enterprise, so when it co-occurs with a flagged path the verdict is effectively settled without malware analysis.
