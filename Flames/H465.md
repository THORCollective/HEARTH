false_positive_notes: |
  The whole point of this interface is to accept arbitrary code, so the hunt cannot key on arbitrary code running - it has to key on who submitted it and what the code did afterwards.
  - Submitting shell commands through a job API is the product working as designed. Researchers legitimately submit jobs that run shell commands, install packages, and invoke system tools, and a framework worker parenting a shell is an ordinary event in a working cluster. The discriminators are the submission source address and whether the job's behaviour resembles a model workload at all.
  - Running the GPU inventory tool is the single most normal thing to do on a GPU host. Every framework, every scheduler, every researcher and most container entrypoints run it. It is only interesting when its output leaves the host to a destination that is not the organisation's own monitoring, which is the pairing to hunt rather than the invocation.
  - Reverse-shell-shaped network code appears in legitimate distributed workloads. These frameworks open sockets between nodes constantly, and debugging tooling, remote-interpreter sessions and notebook kernels all look structurally similar. Scope the outbound check to destinations outside the cluster subnets and outside the approved egress list.
  - Keys are added to authorized_keys legitimately, including by automation. Configuration management, provisioning scripts and onboarding all do it. The finding is a write performed by the framework's own service account from a process in the framework's worker lineage, not a write by the configuration-management agent.
  - Loopback-bound does not mean unreachable, and all-interfaces-bound does not mean exposed. A service bound to all interfaces behind a strict perimeter may be fine, and a loopback-bound dashboard can still sit beside a sibling component that listens broadly - which is exactly the configuration in the reported case. Check the component inventory rather than inferring exposure from one bind address.
  - Historical probing is noise until something succeeds. An internet-facing port collects probes continuously, so the finding is a submission that was accepted and ran, which the application log distinguishes from a connection that was refused.

  Source reporting is Elastic Security Labs' November 12, 2026 analysis of REF3364, a Linux cryptomining intrusion across three Linux GPU hosts. This hunt covers the initial-access and persistence route; the telemetry-falsification component from the same intrusion is [[H464]] and the statistical form of the compute-hijack detection is [[M070]]. The closest existing hunts are [[H283]], which covers post-exploitation staging in `/tmp` after an exposed AI inference gateway is exploited - the same class of exposed AI infrastructure, but the staging behaviour rather than the submission interface - and [[H450]], which covers a web-application service account using already-installed tooling after a web flaw becomes command execution. No existing hunt covers Ray or an unauthenticated job-submission interface.
  What the exposure actually is - Elastic reports that on the first host, "the dashboard on Ray's head node listened only on the local loopback interface" while "the job agent remained reachable from the internet and accepted job submissions without authentication", and that the actor "used this interface to execute commands through Ray". This is the detail worth carrying into an environment review: the component an administrator thinks of as the exposed one was correctly restricted, and the one that mattered was not. Ray's own documentation is explicit that the framework provides no authentication and expects to run inside a trusted network boundary, so an internet-reachable job agent is a configuration exposure rather than a vulnerability, and it will not appear in any patch-level inventory.
  Core filter 1, the reachable interface - Start with the environment rather than the telemetry, because this check finds the exposure before an intrusion and takes minutes. Enumerate every host running the framework, list its listening sockets with bound addresses, and compare that against what is reachable from outside. A per-host check:
  ```bash
  set -u
  ss -ltnp 2>/dev/null | awk 'NR==1 || /ray|python/'
  ss -ltnp 2>/dev/null | awk '$4 !~ /^127\.|^\[::1\]/ {print "NON-LOOPBACK LISTENER: " $4 "  " $NF}'
  pgrep -af 'ray|raylet|gcs_server|dashboard|job_agent' 2>/dev/null
  ```
  Triage values are the bound address for each framework port, the owning process, and whether an external scan confirms reachability. A loopback-bound dashboard beside a broadly-bound agent is the reported configuration, so finding one component restricted is not evidence that the others are.
  Core filter 2, the submission record - The application log is the authoritative source for who submitted what, and it is the one place the whole intrusion is attributable. Elastic gives a dated sequence to pattern-match against: "October 22, 2026: external probes first appeared in the Ray logs", then on October 24 a submitted job that "ran the NVIDIA System Management Interface (nvidia-smi) and sent the GPU inventory to an external server", then on October 25 "a Python reverse-shell job that connected to an external listener". Hunt for submitted job entrypoints whose content is a shell command or an inline interpreter invocation rather than a module or script in the cluster's own code, and for any submission whose source address is outside the cluster and outside the approved client ranges. Strong red flags are an inline `python -c` or `bash -c` entrypoint, an entrypoint that names a socket library, and a submission from an address with no prior history on that interface.
  Core filter 3, the shell under the worker - Core filter: a shell or interpreter whose process ancestry runs back to a framework worker and whose network behaviour leaves the cluster. Hunt process-execution telemetry for `/bin/sh`, `/bin/bash`, `python` or `python3` whose parent lineage includes the framework's worker or agent processes, then correlate against outbound connections by the same process to a destination outside the cluster subnets. Elastic reports that "the reverse shell ran under the local account that owned the Ray session", which gives the account to pivot on for everything that follows. Expected, not observed by Elastic: a specific reverse-shell one-liner - the report characterises it as a Python reverse-shell job and names the listener as external, but does not publish the code, so a hunt keyed on a particular payload string would be keyed on an invention.
  Core filter 4, the persistence write - The highest-signal single check in the whole hunt, because unlike every other step it has no legitimate explanation in this lineage. Elastic reports the actor "subsequently added an SSH key to that account's authorized_keys file to establish persistent access". Hunt for creates and modifies of `~/.ssh/authorized_keys` in any home directory where the writing process is not the configuration-management agent, with particular attention to the framework's service account. Triage values are the written path, the writing process and its parent, the account, and the key comment and fingerprint - then compare every key present against the inventory of keys that are supposed to exist. A shell check for triage:
  ```bash
  set -u
  for f in /home/*/.ssh/authorized_keys /root/.ssh/authorized_keys; do
    [ -f "$f" ] || continue
    echo "== $f  (mtime $(stat -c %y "$f"))"
    ssh-keygen -l -f "$f" 2>/dev/null
  done
  ```
  Correlate the file mtime against the submission log and the process telemetry; a key whose mtime falls inside a window of unauthenticated job submissions is the case.
  Core filter 5, what came next on this host - Once root was obtained the toolkit was staged under `/opt/vadi_`, a kernel module was built through Dynamic Kernel Module Support with an initramfs loader added, the NVIDIA management library was replaced, and a separate backdoor was registered as a systemd service. That sequence is the pivot list for a confirmed case: check for an out-of-tree kernel module built on the host, a driver library that no package owns ([[H464]]), a systemd unit whose name resembles a hardware or networking component ([[H280]] covers that masquerade pattern), and a dot-prefixed staging directory under `/opt`. Elastic's closing recommendation is to "check who can submit jobs and whether GPU monitoring libraries have been modified", which is the two-hunt pair this and [[H464]] implement.
  Scope - Any host running a distributed-computing or model-serving framework with a submission or control API: Ray head and worker nodes, and by extension the same configuration question for notebook servers, model-serving endpoints and workflow schedulers on the same estate. The framework-specific strings differ; the shape - an unauthenticated control plane reachable from outside, used as an API rather than exploited - does not.

# H465

The operator did not exploit anything.

Elastic Security Labs traced an intrusion across three Linux GPU hosts back to a Ray job agent that was reachable from the internet and accepted job submissions without authentication. Ray exists to run submitted code on a cluster. Reaching it was the whole attack.

The configuration is worth sitting with. The dashboard — the part an administrator thinks of as the exposed web interface — was correctly bound to loopback. The job agent, sitting beside it, was not. One component was locked down and the other was the front door, and from outside there was no difference.

The sequence in the logs reads like someone learning a new API. Probes appear on October 22. On October 24 a submitted job runs `nvidia-smi` and sends the GPU inventory to an external server — the operator checking what the hardware is worth. On October 25 a job carries a Python reverse shell to an external listener.

The shell ran as the account that owned the Ray session, and the operator did the ordinary thing: appended an SSH key to that account's `authorized_keys`. From that point the job agent was no longer needed.

After root, the rest of the toolkit went in — a kernel rootkit, a swapped GPU monitoring library, a backdoor as a systemd service. By then process listings and GPU telemetry on those hosts were both answering to someone else. The submission log and the key write were the honest records.

## Why

- **There is no vulnerability to track here, so nothing in a patch inventory will ever flag it.** Ray does not ship authentication and documents that it expects a trusted network. An internet-reachable job agent is a correct, up-to-date installation in the wrong place, which means the only way to find it is to ask what is listening and what is reachable.
- **The exposed component was not the one that looked exposed.** A loopback-bound dashboard is reassuring and, in this case, irrelevant. That asymmetry generalises to every AI-infrastructure framework with a multi-component control plane, and it is why the check has to enumerate all listeners rather than confirm the obvious one.
- **GPU estates concentrate value and dilute ownership.** They are expensive, shared between teams, frequently stood up by researchers rather than platform engineering, and often excluded from the standard build. That combination produces exactly this configuration, and the economics mean an operator who finds one gets paid for it immediately.
- **The reconnaissance step is a gift, if you are collecting it.** Before doing anything else the operator asked the host what cards it had and shipped the answer out. A GPU inventory tool running and its output leaving to a destination that is not your monitoring is a narrow, early, high-confidence signal — hours or days ahead of the miner.
- **The persistence write is the one step with no innocent reading.** A key appended to the framework service account's `authorized_keys`, by a process descended from a framework worker, is not something a legitimate workload does. When the rest of the host's telemetry has been subverted, that file and the submission log are what is left.
