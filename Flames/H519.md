hypothesis: >-
  Reinstalling Windows is supposed to be the end of an infection, and this implant is built to make
  it the beginning of the next one. Talos documents that the Overlord RAT used by UAT-12643
  establishes pre-boot persistence via the Windows Recovery Environment OEM script path - it first
  removes any previous version of itself, then sets up the OEM environment directly under
  %TARGETOSDRIVE%\Recovery\OEM\, generates a random 20-character file name with each character
  picked individually at random from a fixed character set, writes its own executable there, and
  wraps a launch command into a Windows batch script with the .bat extension. It then backs up the
  existing WinRE reset configuration file and modifies ResetConfig.xml, which governs what WinRE
  does during a reset, creating one from scratch if none exists or patching it to append the
  malicious batch scripts as registered OEM tasks. Talos notes the use of %TARGETOSDRIVE% is
  significant, because that environment variable only exists and resolves correctly inside the WinRE
  pre-boot environment, not in normal Windows. Hunt for writes into a Recovery\OEM directory, for
  ResetConfig.xml being created or modified, and for the literal string %TARGETOSDRIVE% appearing in
  a file or command line on a running system, where it cannot legitimately resolve.

false_positive_notes: |
  `Recovery\OEM` is a documented and supported extension point, not an attacker invention. OEMs legitimately place recovery customisations, branding and restore scripts there, and `ResetConfig.xml` exists precisely so that vendors can register tasks to run during a push-button reset. On vendor-imaged hardware, expect legitimate content and establish what shipped with the image before treating anything as anomalous.

  Enterprise imaging and deployment tooling also touches this area. Some build pipelines, recovery-media creation tools and endpoint management agents write to the recovery tree or reconfigure WinRE, and Windows servicing itself updates the WinRE image periodically - the January 2024 and later WinRE servicing updates are a well-known example of legitimate recovery-partition modification at scale. Correlate timing against patch windows.

  The directory is frequently invisible to the tooling that would otherwise catch this. The recovery partition is normally unmounted and unlettered, and several endpoint agents exclude it or the `Recovery` tree from real-time file monitoring for performance reasons. That means a silent result is more likely to indicate missing visibility than absence of the technique - verify the path is actually monitored before drawing a conclusion.

  The 20-character random filename defeats any filename-based rule by design. Talos states each character is picked individually at random from a fixed character set, meaning every installation produces a uniquely named file. Hunt the location and the write event, never the name. The accompanying `.bat` is the more tractable artefact because its extension is fixed.

  Talos does not state how the RAT obtained the privileges needed to write to the recovery tree or modify `ResetConfig.xml`, beyond noting the RAT first verifies that the current process is running with administrative privilege before its anti-removal routine. Administrative rights are the reasonable inference for the recovery-path write as well, but the report does not attest the mechanism, so do not assume a specific elevation path when scoping.
notes: |
  Leg one, writes into the recovery tree (DeviceFileEvents or Sysmon 11) - Core filter: any file created or modified under a `Recovery\OEM` path, with the writing process captured. This is the primary query and it should be close to silent in a steady-state estate.

      DeviceFileEvents
      | where Timestamp > ago(30d)
      | where ActionType in ("FileCreated", "FileModified", "FileRenamed")
      | where FolderPath has @"\Recovery\OEM" or FileName =~ "ResetConfig.xml"
      | project Timestamp, DeviceName, FolderPath, FileName, SHA256,
                InitiatingProcessFileName, InitiatingProcessFolderPath,
                InitiatingProcessCommandLine, InitiatingProcessAccountName
      | order by Timestamp desc

  Thirty days is the whole Defender advanced hunting retention. `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, which suits this leg exactly - the question is who wrote into the recovery tree. Triage on the writing process: a vendor recovery tool or a servicing component during a patch window is expected; anything running from a user profile, `ProgramData`, or a temporary directory is not. Rank a `.bat` and a 20-character extensionless or randomly-named executable appearing in the same directory within seconds of each other as the top finding, because that pairing is the mechanism in two events.

  Leg two, `ResetConfig.xml` specifically. Talos describes a careful sequence - the RAT backs up the existing WinRE reset configuration file before modifying it, then either creates `ResetConfig.xml` from scratch if none exists or patches it to append the malicious batch scripts as registered OEM tasks. Two consequences for hunting. First, a backup copy of the file may be sitting next to it, which is both corroboration and a way to diff what changed. Second, on a machine that never had OEM customisation, the mere existence of `ResetConfig.xml` is anomalous - there is nothing to have created it. Where the file exists, read it and enumerate the registered tasks; any task pointing at a randomly-named binary in `Recovery\OEM` is the finding, and any task at all on a non-OEM image deserves an explanation.

  Leg three, the `%TARGETOSDRIVE%` string as a hunting token. This is the most distinctive artefact in the whole technique and it is nearly free to search for. Talos states the variable only exists and resolves correctly inside the WinRE pre-boot environment, not in normal Windows, which means the command Talos publishes:

      cmd.exe /c start %TARGETOSDRIVE%\Recovery\OEM\"random_stub_name"

  is specifically crafted to work at recovery time, not during a regular session. Searching running-system telemetry and file content for the literal string `%TARGETOSDRIVE%` is therefore high-signal: in a normal Windows session the variable is undefined, so legitimate software has no reason to emit it, and an unresolved `%TARGETOSDRIVE%` in a process command line would simply fail. Grep script and configuration files across the estate for it, and alert on it appearing in any command line.

  Leg four, the primary persistence that sits alongside. Talos describes the RAT's primary approach as a registry autorun entry under the current user's hive, with a randomised value name pointing to the RAT binary located in the Network folder of the local user profile application data folder. That gives a second, far more conventional artefact to pivot on - a Run key value whose name is random and whose data points into an `AppData` `Network` subdirectory. Hunt both, because the two mechanisms are deliberately independent and remediation of one leaves the other.

  Why this matters for incident response specifically. The entire premise of a reimage is that it is a clean boundary. This implant registers itself as an OEM task so that, in Talos's words, whenever the victim triggers "Reset this PC" whether from within Windows Settings or from the recovery boot menu, Windows Recovery Environment will execute the RAT's payload before restoring the operating system, ensuring the implant survives a full system reset. So remediation guidance has to be explicit: a push-button reset is not sufficient containment on a host where this is present, and the recovery partition has to be inspected and rebuilt rather than trusted. Pair this with the RAT's anti-termination behaviour, covered in H520, which makes the process itself resistant to being killed - together they are a deliberate strategy of making both the process and the machine hard to clean.

  Chain context from the same report, for scoping a hit. Talos observed three initial access vectors, none of whose delivery to victims it observed - weaponised LNK files abusing `MpCmdRun.exe -DownloadFile` and `certutil -urlcache -f`, covered in H521; an HTA dropper executed by `mshta.exe` using `MSXML2.ServerXMLHTTP` to fetch the payload as raw binary and `ADODB.Stream` to write it to `%TEMP%\s.exe`; and a weaponised MSBuild project file `dl.xml` carrying an inline C# `CodeTaskFactory` task that compiles and executes in memory with a spoofed `Microsoft BITS/7.8` User-Agent. The RAT itself is Go-based and modular, with 35 commands spanning surveillance, file system, process control, script execution, a reverse SOCKS proxy for lateral movement, and HTTP-based plugin downloads with reflective DLL injection at runtime. Talos assesses with low confidence that UAT-12643 is North Korea-aligned, based on TTP overlaps with known North Korean APT actors.

  Scope note on existing coverage. A grep of every hunt body for `TARGETOSDRIVE`, for `ResetConfig` and for `Recovery\OEM` returns nothing. `WinRE` and `Recovery Environment` appear in five files but on unrelated ground - H348 and H423 reference recovery and boot configuration in the context of different mechanisms, and B024, B030 and B065 are baselines that mention recovery tooling in passing. No existing hunt covers persistence registered as a WinRE OEM reset task. The closest conceptual neighbours are the bootkit and pre-OS hunts in the corpus, which turn on firmware and boot-record modification rather than on the recovery environment's own documented extension point.

# H519

The standard advice for a compromised endpoint is to flatten it. Reset this PC, restore the image, move on. It is the one remediation step everybody trusts.

Talos found an implant that treats the reset as a delivery mechanism.

The Overlord RAT variant used by UAT-12643 keeps an ordinary Run-key autorun as its primary persistence. Its secondary route is considerably more interesting: it writes a copy of itself into `%TARGETOSDRIVE%\Recovery\OEM\` under a randomly generated 20-character filename, wraps a launch command in a `.bat`, backs up the existing WinRE reset configuration, and then patches `ResetConfig.xml` to register that batch file as an OEM task. `Recovery\OEM` and `ResetConfig.xml` are both supported extension points — they exist so hardware vendors can run restore logic during a push-button reset. The implant simply signs up.

The result is that the victim's cleanest available remediation step runs the malware before restoring the operating system.

The giveaway is the environment variable. `%TARGETOSDRIVE%` only exists inside WinRE; in a running Windows session it is undefined and resolves to nothing. Talos notes this is significant precisely because it shows the command was crafted for recovery time rather than for a normal session — and it means that string appearing anywhere on a live system is an artefact with no legitimate explanation.

## Why

- It defeats the remediation everyone falls back on. If a reimage via push-button reset is the containment plan, this persistence survives it and the incident silently reopens. That makes the hunt a prerequisite for trusting any reset-based remediation, not just another persistence check.
- `%TARGETOSDRIVE%` is a free, near-zero-false-positive string search. The variable cannot resolve outside WinRE, so legitimate software running under Windows has no reason to write or invoke it. Grepping scripts and command lines for it is one of the cheapest high-confidence checks available.
- `ResetConfig.xml` on a machine that never had OEM customisation has no innocent origin. Where no vendor recovery content shipped with the image, nothing legitimate creates that file, so its existence is the finding rather than its contents.
- The recovery tree is a monitoring blind spot, which is presumably the point. The recovery partition is usually unmounted and unlettered, and agents frequently exclude it for performance. Confirming the path is even in scope converts this hunt from a query into an instrumentation fix.
- The random filename forces the hunt into the right shape. Because every installation produces a unique 20-character name, filename rules are useless and location-plus-writer is the only durable approach — which is also the approach that catches the next variant.
- It pairs with anti-removal by design. The same RAT sets itself as a critical process so that killing it bluescreens the host, covered in H520. One mechanism resists cleaning the process, the other resists cleaning the machine, and recognising them as a pair changes the response plan.
