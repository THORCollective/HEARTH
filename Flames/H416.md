false_positive_notes: |
  Yggdrasil has legitimate users, and they are the main source of confusion rather than noise. Research, hobbyist and resilient-connectivity deployments do exist. On a managed corporate estate an installed mesh client is almost always either unsanctioned personal software or an implant, but confirm against your software inventory before escalating, and check whether any research or networking team has a documented deployment.
  The 200::/7 range is not assigned by anything in an enterprise. It was deprecated by the IETF in 2004, so a socket bound in that range is not the product of normal addressing, DHCPv6 or SLAAC. The practical false positive is a lab or test host where someone installed the client deliberately.
  Peer addresses are volunteer-operated and change. The public peer list is maintained in the open and is amended regularly, so a static IOC list built today will decay. Re-derive the list periodically from the public source rather than freezing it, and remember the sample set here carries its own embedded list which may not match the current public one.
  Other overlay and mesh software will surface in the same socket hunt. Tailscale, ZeroTier, Nebula and similar products create their own address ranges and, unlike this one, usually do create an adapter. They are a different finding, not a false positive, and are worth enumerating while you are looking.
  There is no tunnel adapter to alert on. The backdoor is built on a userspace stack, which the report notes has "the benefit of not needing to create a tunnel interface". Any detection logic that expects a new network adapter, a TAP/TUN device or a routing-table change will not fire. Do not treat the absence of an adapter as evidence of absence.
  IPv6 may be partially disabled in your estate, which does not help as much as it appears to. The peer connections themselves are IPv4-reachable TCP in many cases; the IPv6 addressing is internal to the overlay.
notes: |
  Host socket check - the cheapest and most decisive signal. A process holding a socket with a local or remote address in `0200::/7` is not the result of any normal addressing on a Windows estate. Collect estate-wide via live response or a scheduled inventory:
  ```powershell
  Get-NetTCPConnection |
    Where-Object { $_.LocalAddress -like '2??:*' -or $_.RemoteAddress -like '2??:*' } |
    Select-Object LocalAddress, LocalPort, RemoteAddress, RemotePort, State, OwningProcess
  ```
  Confirm the match falls inside `0200::/7` rather than a global-unicast address that merely starts with a 2, then resolve `OwningProcess` to an image path and signer. The address is derived from an Ed25519 public key the backdoor generates at each start, so the specific address changes every run and is useless as an IOC; the range is the durable part.
  Peer connections - Core filter: outbound connections from a non-browser, non-updater process to the published mesh peer addresses. Derive the destination list from the peer appendix in the ESET report and from the publicly maintained peer repository; the samples analysed "contain the same embedded list of 32 peers from which three are randomly picked", so an infected host contacts only three of them and the set differs per host. Triage values: `RemoteIP`, `RemotePort`, `InitiatingProcessFileName`, `InitiatingProcessFolderPath`, `InitiatingProcessCommandLine`, `InitiatingProcessParentFileName`. Peer URIs carry their own scheme and port, so build the filter from address plus port as published rather than assuming a standard port.
  ```kql
  let peers = dynamic([]);   // populate from the report appendix and the public peer list
  DeviceNetworkEvents
  | where Timestamp > ago(30d)
  | where ActionType == "ConnectionSuccess"
  | where RemoteIP in (peers)
  | summarize Connections = count(), Peers = dcount(RemoteIP), PeerSet = make_set(RemoteIP, 10),
              FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
            by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath
  | order by FirstSeen asc
  ```
  Three distinct peers contacted by one process is the expected shape; one or two indicates partial connectivity rather than a different family.
  Process and persistence shape - The backdoor is Go-built and runs as a Windows service. ESET records the service name `ieupdate` and installation paths including `C:\windows\system32\updater.exe`, `C:\Windows\system32\krbtman.exe`, `C:\windows\system32\windowsdefendersvc.exe`, `%localappdata%\Microsoft\OneDrive\OneDriveLiveUpdater.exe` and `%userprofile%\Downloads\ieupdate.exe`. Note the collision ESET calls out: `krbtman.exe` is the backdoor on some machines and the standalone SOCKS5 server on others, so the filename alone does not tell you which tool you have.
  Startup delay - Some samples carry "a 10-minute startup delay, likely to avoid immediately connecting to the Yggdrasil network on execution, helping to evade detection". A service process that starts and makes no network connection for roughly ten minutes, then begins contacting three unrelated internet hosts, is a usable triage pattern where process start and first connection can be correlated.
  Mesh-side traffic shape - Inside the overlay the backdoor reaches its server over HTTPS on port 443 and exchanges JSON POST bodies with four message types: `checkin`, `tasking`, `result` and `getfile`. The configured beacon interval in the embedded default configuration is five minutes. None of this is visible without overlay access, so treat it as triage knowledge for host-side artefacts rather than as a network filter.
  Companion proxy - A standalone Go SOCKS5 server deployed in the same activity listens on `127.0.0.1` port `33690`, bound to loopback so only the local machine can reach it, and is intended to be reached from outside via the backdoor's port-exposure command. A loopback listener on that port with no local client connecting to it is corroborating evidence on a host that already looks suspicious.
  Mitigation that doubles as a detection - ESET notes that although hosting the server in the mesh "may prevent network security tools from detecting outbound connections to it", blocking the public peer addresses is a viable mitigation. Blocking them at the egress point also converts every future infection attempt into a denied-connection log entry naming the responsible process.
  Configuration artefacts - The on-disk configuration files are covered in [[H418]]; the service-masquerade pattern in this intrusion set overlaps the service-naming hunt in [[H412]].

# H416

ESET's October 2026 report on MythicRatatoskr documents a Go backdoor used in a UAC-0099 intrusion at a Ukrainian grain logistics company that was later handed to Sandworm, which carried out a data-wiping attack two months after initial access. The backdoor's distinguishing feature is where its C2 server lives: inside the Yggdrasil network, which ESET describes as "a decentralized mesh network that implements an experimental routing scheme in which the IPv6 communication between the nodes is end-to-end protected."

The consequence for a defender is that the C2 address is not reachable, resolvable or blockable from the ordinary internet. The configured server address is an IPv6 address inside the overlay, and the report notes that the host's own overlay address "is derived from the public key in the 200::/7 subnet range, which was deprecated by IETF in 2004" — and, because a fresh Ed25519 key pair is generated at every start, that address changes on each run. What the host actually emits is unremarkable TCP to a few volunteer-run mesh peers. Reputation feeds, domain blocklists and TLS inspection all have nothing to work with.

The backdoor also removes the artefact that would normally give an overlay client away. It is built on `yggstack`, a userspace network stack, which the report says has "the benefit of not needing to create a tunnel interface". So there is no new adapter, no TAP device and no routing change to inventory.

Two signals survive all of that. The first is the socket: a Windows host with a `0200::/7` address bound to a process is not something normal addressing produces, and the range is stable across samples even though the address is not. The second is the peer set: every sample carries the same embedded list of 32 peers and picks three at random, so an infected host maintains connections to three internet addresses that are published, enumerable, and have no relationship with the business. ESET's own mitigation advice — block the public peers — is the same list the hunt runs on.

## Why

- The address that matters is unreachable, so the hunt has to key on the join rather than the conversation. Connections to the public peer set are the only part of this channel that crosses a boundary an enterprise controls, and they are both enumerable and published.
- The `0200::/7` socket is a near-zero-false-positive host artefact. The range was deprecated in 2004 and is assigned by nothing in an enterprise, which makes a single socket inventory sweep across the estate a decisive check that needs no network visibility at all.
- The missing tunnel adapter invalidates the obvious detection. Teams that watch for new network adapters, TUN/TAP devices or routing-table changes to catch overlay clients will not see this one, so the gap is worth closing deliberately rather than assuming existing coverage applies.
- The behaviour outlasts the campaign. The report found indications a Linux variant may also exist, and the mesh is public infrastructure available to anyone, so the join pattern is likely to recur in unrelated intrusions. A peer-list and socket-range hunt generalises in a way that a hash or a service name does not.
- The stakes here were not espionage alone. Access from this intrusion was handed off and used to deploy a wiper via Group Policy two months later, so finding the mesh backdoor is finding the dwell time before destruction.
