false_positive_notes: |
  Azure Storage endpoints are contacted legitimately and constantly, which is exactly why the actor chose them, so the hostname alone is worthless as a discriminator and must never be the filter. The real benign populations are concrete and enumerable - browsers fetching assets and blobs, Azure SDK-based line-of-business applications, Azure Functions and WebJobs hosts, Application Insights and diagnostics agents (Table Storage is a standard telemetry sink), backup and archiving agents, Office and OneDrive components, and Storage Explorer or `az`/`azcopy` tooling on engineering machines. Every one of those is a signed binary running from `Program Files`, `Program Files (x86)`, `%PROGRAMDATA%` under a vendor directory, or the Windows directory, and every one of them talks to a storage account your organisation owns. The discriminator that survives all of them is the pair (requesting process path and signature, storage account name). An unsigned binary in `%APPDATA%` or `%LOCALAPPDATA%` reaching a storage account that appears in no asset inventory, no Terraform state and no Azure subscription you control is the finding. Scope the hunt to the environment you actually have - an organisation with no Azure Storage footprint can treat any `table.core.windows.net` resolution as a standing lead and be done in one query, while an organisation with a large Azure footprint must first enumerate its own storage account names, allowlist them by the leftmost FQDN label, and then hunt on requesting-process path and signature. An empty result is ambiguous in two specific ways. If Sysmon Event ID 22 is not deployed or `Image` is not retained, you have no process attribution and a clean result means only that you cannot see the thing you are looking for, not that it is absent. If your only visibility is a proxy or firewall that logs by IP or SNI without process context, a true positive will be sitting in that data indistinguishable from legitimate Azure traffic - and note that [[H323]] documents the same intrusion actively stripping the host's proxy configuration on a schedule, which means the proxy path is deliberately blinded on precisely the hosts that matter. Treat a proxy-only clean result as a collection gap, not a true negative.

# H322

Huntress documented a modular remote access trojan delivered through a tampered Exodus cryptocurrency wallet installer, hitting four unrelated protected organisations between late July and mid August 2026 — three of them inside a single 85-minute window on 2026-08-18. The interesting part is not the loader, it is the transport. The RAT never contacts an attacker-registered domain. It runs its whole command-and-control channel over the Azure Table Storage REST API, so every request lands on `*.table.core.windows.net`: a Microsoft-owned hostname with valid Microsoft TLS, spotless reputation, and no newly-registered-domain heuristic that could possibly fire. The observed accounts were `lgapistorage123` and `winapi`, both writing to a table called `ftable434`, with `PartitionKey` holding the bot ID and `RowKey` prefixed `B` for beacon, `T_` for tasking and `R_` for results. Six modules — command execution, file management, browser credential theft, SOCKS, hidden VNC relayed through the victim's own `chrome.exe`, and a LuaJIT scripting engine — are loaded entirely in memory. Because the destination is unhuntable by reputation, the only durable discriminator left is *which process* is talking to it.

## Why

- **Reputation-based detection has nothing to grade here, by construction.** Domain age, registrar, certificate issuer, ASN and hostname reputation all return "Microsoft, clean" because the answer is genuinely Microsoft and genuinely clean. Every control tuned to score the destination is neutralised in a single design decision, and no amount of threat-intel feed subscription changes that. The hunt has to move up the stack to process attribution, which is exactly the telemetry most organisations collect but never pivot on.
- **The request triad survives the rotation that kills every IOC-based hunt.** Storage accounts are free, instantly provisioned and disposable, so `lgapistorage123` and `winapi` have a shelf life measured in days. What does not change is the protocol the implant speaks: poll one table with a `GET`, write the answer back as an `R_` row with a `PUT`, then `DELETE` the `T_` row to acknowledge it. That sequence is a behavioral signature of a task queue implemented on a key-value store, and it will look the same under the next account name, the next table name and the next campaign.
- **The `%APPDATA%`-versus-`Program Files` split does the work that the hostname cannot.** Every legitimate caller of Azure Storage in an enterprise is a signed binary from a vendor-installed location talking to a storage account the organisation owns. The intersection of "unsigned binary under a user profile" and "storage account absent from your own inventory" is close to empty in normal operation, which turns a hopeless hostname filter into a short, reviewable list.
- **Answering "does my estate use Azure Storage at all?" changes the hunt from hard to trivial.** Organisations with no Azure footprint can treat any `table.core.windows.net` resolution as a standing alert and finish in one query. Organisations with a large footprint have to enumerate their own account names first and then filter on process path. Either way the difficulty is knowable before the hunt starts rather than discovered halfway through triage, which makes this a good candidate for a standing detection rather than a one-off sweep.
- **The proxy path is being actively blinded on the same hosts.** The companion behavior in [[H323]] is a scheduled task that repeatedly clears the user's proxy configuration to force egress onto a direct path. That means any version of this hunt built on proxy or TLS-inspection logs has a blind spot on precisely the compromised machines, and a clean proxy-side result should be read as a collection gap rather than an all-clear. Endpoint DNS and network-connection telemetry is what closes it.
