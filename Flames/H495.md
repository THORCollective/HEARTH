false_positive_notes: |
  Enabling SSH on a VCSA is a legitimate and reasonably common administrative action, usually during vendor support cases, upgrades and troubleshooting. Legitimate use differs on every axis this hunt measures: it is ticketed, it is performed by a named administrator from a management host or privileged access workstation, the session that follows runs for the length of the task rather than a few minutes, and SSH is frequently left enabled afterwards because the administrator forgets rather than because they are covering tracks. The suspicious shape is specifically the tight enable-use-disable cycle with no change record.

  Automation and configuration-management tooling toggles appliance services on a schedule in some estates. Register those service accounts and source addresses explicitly, so they can be excluded by identity rather than by behaviour, and alert on a toggle from anything outside the register.

  Reading the PostgreSQL password file is something some VMware support procedures legitimately require. Treat the file read as corroborating rather than conclusive, and anchor the finding on the identity and source of the session that read it.

  `vpxuser` authenticating to an ESXi host is normal in the sense that it is the account vCenter itself uses to manage hosts. What Mandiant observed is different - authentication to the ESXi Host Client web interface using that account, which is not how vCenter uses it. Separate interactive Host Client and SSH logins from the API traffic vCenter generates before treating a `vpxuser` event as a finding.

  A clean configuration audit is expected here and is not evidence of absence. Because the actor disables SSH immediately after use, any point-in-time posture check will show the appliance compliant. This is a log-based hunt by necessity, and if VAMI and sshd logs are not being forwarded off the appliance there is no retrospective answer available at all.

  Mandiant does not state how the actor authenticated to the VAMI API to make the PUT request, only that it gained VAMI access and that the hardening guidance treats compromised VAMI or vSphere administrative credentials as the assumed starting point. Do not assert a specific authentication path for the toggle in an investigation write-up without appliance-side evidence.
notes: |
  VAMI API leg (appliance management API access logs) - Core filter: any request whose method is `PUT`, `POST` or `PATCH` against a URI path containing `/rest/appliance/access/ssh`, or the equivalent current-generation path under the appliance access API, where the source address is not in the approved-management register. Mandiant names the `PUT` to `/rest/appliance/access/ssh` specifically. Triage values are `timestamp`, `HTTP method`, `URI path`, `status code`, `authenticated principal`, `source IP`, `user agent` and `request body` where the appliance records it. Correlation that defines the hunt: two state-changing requests to that endpoint from the same source or principal, the second within roughly an hour of the first, with at least one successful SSH authentication to the appliance in between. Strong red flags: the principal is an account created earlier in the intrusion rather than an established administrator; the source address is an internal Linux appliance; the user agent is a generic HTTP client rather than a browser or a known management tool; there is no change ticket covering the window.

  SSH session leg (VCSA sshd logs, flow records) - Core filter: accepted SSH authentications to a vCenter appliance, joined to the VAMI toggle events above with a bounded window so that unrelated days are not correlated. Triage values are `principal`, `authentication method`, `source IP`, `session start and end`, `session duration` and `TTY`. Strong red flags: a session duration measured in minutes that nonetheless touches credential material; the principal is a local account on the appliance rather than a federated administrator; the source address matches the host seen in H493's port-2012 activity.

  File-access leg (auditd watch rules on the appliance) - Core filter: any read of the vCenter internal master crypto key file or the PostgreSQL password file by a process other than the vCenter services that legitimately consume them. These are the two files Mandiant records the actor taking. Watch rules to install ahead of the hunt, pointing at the appliance's own paths for its vCenter version:

      auditctl -w /etc/vmware-vpx/ssl -p r -k vcsa_crypto_material
      auditctl -w /etc/vmware-vpx/vcdb.properties -p r -k vcsa_db_credentials
      auditctl -w /storage/db/vmware-vmdir -p r -k vcsa_vmdir_read

  Confirm the exact paths on the appliance before deploying the rules, because they differ between vCenter generations; the rule set matters more than the specific path, and the key is that reads of credential material are audited at all, which they are not by default.

  ESXi follow-on leg (ESXi host authentication logs) - Core filter: authentication to the ESXi Host Client web interface using the `vpxuser` account, and SSH sessions to ESXi as `root`, in the window after the VCSA credential theft. Mandiant observed both, in that order, after the master symmetric key and database credentials were taken - which is the practical reason the master key matters, since it is what protects the stored host credentials vCenter uses. Triage values are `principal`, `interface` (Host Client, SSH, API), `source IP`, `timestamp` and `session duration`. Strong red flags: `vpxuser` appearing in an interactive Host Client login rather than in vCenter's API traffic; a `root` SSH session from the same internal appliance; an SSH public key appearing in the ESXi `root` account's authorised keys, which is the artefact H496 follows.

  Collection prerequisite, stated plainly - Mandiant's hardening guidance for this campaign is explicit that the native VCSA host-based firewall managed through VAMI "does not generate remote logs for denied connection attempts or shell activity", which "blinds the SOC to active lateral movement and port scanning", and that the VAMI firewall is itself managed on TCP 5480, creating a circular dependency in which an attacker with VAMI access can deactivate the firewall entirely. Their recommended approach enforces policy with `iptables` at the Photon kernel level, independently of the VAMI application, so that the API path used here cannot circumvent the control and so that the attempts are logged remotely. Until something like that is in place, this hunt depends entirely on whichever appliance logs are already being forwarded.

  Scope note: HEARTH covers adjacent toggles on the hypervisor side but not this one. H480 covers vCenter Host Profile remediation turning Tech Support Mode SSH on across ESXi hosts, with the following SSH session arriving from the vCenter appliance address - a different interface, a different target, and a push to many hosts rather than a toggle on one appliance. H458 covers an ESXi root SSH session disabling the `execInstalledOnly` policy, which is a security-control change rather than a service enablement. Neither sees the VCSA's own SSH daemon being enabled and disabled through the appliance management API around a credential read. B070 baselines who may administer the management plane, which is where this hunt's approved-source register comes from.

# H495

Mandiant and Google Threat Intelligence Group's November 19, 2026 analysis of ARMORY CASTLE records a short, deliberate sequence on the vCenter Server appliance after the actor had created a local administrator account. SSH was enabled through the vCenter Server Appliance Management Interface API with a `PUT` request to `/rest/appliance/access/ssh`. The actor connected over SSH with the new account, read the vCenter internal master crypto key file and the PostgreSQL password file, and disabled the SSH service through the same API immediately afterwards.

Mandiant notes it has observed this same TTP during BRICKSTORM intrusions conducted by a different suspected PRC-nexus actor, which makes the VAMI SSH toggle shared tradecraft across PRC-nexus intrusions into virtualisation infrastructure rather than a quirk of one campaign.

What follows in the report is the payoff. With the master symmetric key and the database credentials in hand, the actor authenticated to the ESXi Host Client using the `vpxuser` account — the account vCenter itself uses to manage hosts — and connected to ESXi over SSH as `root`. The appliance was not the objective; it was the key cabinet.

## Why

- A posture check cannot find this. The actor restores the appliance to a compliant state on the way out, so any configuration audit, benchmark scan or drift report will show SSH disabled. The only durable evidence is in logs that, on a default VCSA, are not forwarded anywhere.
- The toggle is a documented administrative API, so there is no exploit to signature and nothing anomalous about the request itself. The signal is entirely in the correlation — two state changes bracketing a short SSH session, from a source that does not administer that appliance, with no change record.
- The files taken are the ones that unlock everything else. The master crypto key protects stored credentials, and the PostgreSQL password file opens the vCenter database. That is why the next events in Mandiant's timeline are ESXi logins rather than further activity on the appliance, and it is why this hunt's ESXi leg belongs in the same hypothesis rather than in a separate one.
- Mandiant's own hardening guidance identifies the structural reason this works: the VAMI firewall is managed through VAMI, so VAMI access is sufficient to remove the control that would otherwise constrain it, and it produces no remote logs for denied connections or shell activity. Enabling kernel-level enforcement and remote syslog is both the mitigation and the collection this hunt needs.
