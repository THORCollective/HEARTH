title: PowerShell run through the Windows Scripted Diagnostics engine, so sdiagnhost.exe owns the Run-key write instead of the implant
hypothesis: >-
  A Rust backdoor avoids being the visible parent of its own PowerShell by driving the Windows
  Scripted Diagnostics framework. It creates the `CScriptedDiag` COM class
  (CLSID `{1F3D8AA5-9EBF-4EE4-85C2-EA40379AEDE8}`, implemented by `sdiageng.dll`), initialises the
  engine with the legitimate Program Compatibility Wizard package at
  `C:\Windows\diagnostics\system\PCW` and a blank Answers XML, and receives back a temporary working
  copy at `C:\Windows\Temp\SDIAG_<GUID>`. It writes its own PowerShell into that directory, then
  resumes the diagnostic workflow - and the Microsoft-signed native host
  `%windir%\SysWOW64\sdiagnhost.exe -Embedding` executes `result.ps1`. The persistence write (an
  `HKCU` Run value) therefore appears to originate from a signed Windows troubleshooting component,
  not from the implant. Two anchors make this huntable regardless of payload - a PowerShell script
  file created under `C:\Windows\Temp\SDIAG_*` by a process that is not the diagnostics stack, and
  `sdiagnhost.exe` as the initiating process for a registry Run-key write or any non-diagnostic
  child.

false_positive_notes: |
  The Scripted Diagnostics framework is a real, shipping Windows feature and it does fire legitimately, so the base rate is not zero - but it is low and, more usefully, its legitimate invocations have a very consistent shape. Genuine troubleshooter runs are USER-INITIATED through Settings, the Control Panel troubleshooters, `msdt.exe`, or an administrator running `Get-TroubleshootingPack`/`Invoke-TroubleshootingPack`. In those cases `sdiagnhost.exe` is launched by `svchost.exe` (the Diagnostic Policy Service) or by `msdt.exe`, the working directory under `C:\Windows\Temp\SDIAG_<GUID>` is populated by the diagnostics stack ITSELF from a package under `C:\Windows\diagnostics\`, and the PowerShell that runs is Microsoft's own troubleshooter script - signed content shipped in the package, with recognisable names like `CL_Utility.ps1`, `TS_*.ps1`, `RS_*.ps1` and `VF_*.ps1`. Enterprise remote-assistance and support tooling occasionally drives troubleshooting packs programmatically too, and some OEM support utilities ship their own packs.
  So do not alert on `sdiagnhost.exe` running, and do not alert on the existence of an `SDIAG_` directory. The discriminators are - WHO WROTE THE SCRIPT, and WHAT THE HOST DID NEXT. A `.ps1` created under `C:\Windows\Temp\SDIAG_*` by a process that is not part of the diagnostics stack is the single highest-fidelity signal in this hunt; in the reported chain the implant wrote the script itself, so the creating process is the backdoor's host executable. A file named `result.ps1` is what the reported implant used, but treat the DIRECTORY and the WRITER as durable and the filename as incidental. On the output side, `sdiagnhost.exe` writing an `HKCU` or `HKLM` Run value is not something a Microsoft troubleshooter does; neither is `sdiagnhost.exe` parenting `cmd.exe`, `rundll32.exe`, `regsvr32.exe`, `curl.exe`, a binary in a user-writable path, or a network connection to a non-Microsoft host.
  Two scoping cautions. First, `SDIAG_` directories are cleaned up, so file-creation telemetry and script-block logs matter more than disk forensics - a host that was used this way may have no `SDIAG_` directory left. Second, the reported execution was observed as `%windir%\SysWOW64\sdiagnhost.exe`, i.e. the 32-bit host on a 64-bit system. Do not scope the hunt to `System32` only; a `SysWOW64` diagnostics host invoked by a 32-bit implant is both legitimate-looking and easy to miss if the query assumes the native path.

notes: |
  Platform: Windows. Driven by Cisco Talos, "China-nexus UAT-11587 targets government and policy organizations across Asia with Antino backdoor" (September 30, 2026).
  What Antino is, for context - a Rust-compiled Windows backdoor seen in 32-bit and 64-bit builds, named by Talos after the `AntinoApp` application manifest and repeated `antino` directory names in PDB and Rust source paths. It supports host reconnaissance, shell and PowerShell execution, file transfer, in-memory shellcode loading and persistence, and runs its command-and-control exclusively through Microsoft 365 - see [[M053]] for that channel. UAT-11587 targeted government and policy organisations across Asia; Talos identified at least 16 affected or targeted institutional environments across eight countries by July 2026 and assesses with high confidence that the actor is China-nexus. Antino arrives at the end of a five-stage chain - HTA or WSF stager via Cloudflare Pages, HTA-hosted JScript downloader, a .NET `BinaryFormatter` deserialization gadget chain executed inside `mshta.exe`, a `TestAssembly.dll` downloader, and finally DLL sideloading of `slc.dll` by the Microsoft-signed ADK binary `GatherOsState.exe`.
  The reported technique, exactly as published - Talos describes Antino abusing "the Windows Scripted Diagnostics framework to execute attacker-controlled PowerShell through legitimate Windows components", and notes that "both the `execute_program` and `add_to_run` commands use this technique". The three components named are the Scripted Diagnostics Execution Engine (`sdiageng.dll`), the Program Compatibility Wizard troubleshooting package (`C:\Windows\diagnostics\system\PCW`), and the Scripted Diagnostics Native Host process (`sdiagnhost.exe`). The sequence - Antino initialises COM and creates an instance of CLSID `{1F3D8AA5-9EBF-4EE4-85C2-EA40379AEDE8}`, the `CScriptedDiag` class implemented by `sdiageng.dll`; initialises the engine with the legitimate PCW package and a blank diagnostic Answers XML document; receives the engine's temporary working copy directory, "such as `C:\Windows\Temp\SDIAG_<GUID>`"; writes an attacker-controlled PowerShell script into that directory (for `add_to_run`, "a script that creates an HKCU Run key value"); and resumes the diagnostic workflow, at which point "the Scripted Diagnostics engine delegates execution to the native host, observed in runtime traces as `%windir%\SysWOW64\sdiagnhost.exe -Embedding`", and "the host subsequently executes `result.ps1`". The resulting Run key entry launches the selected Antino executable at next sign-in.
  Why the indirection is worth a dedicated hunt - Talos is explicit about both the benefit and its limit. The technique "allows Antino to proxy PowerShell execution and the persistence-related registry modification through a Microsoft-signed diagnostic workflow", which "can complicate behavioral attribution to the original implant, although it does not eliminate observable PowerShell, file-creation or registry telemetry". That is precisely the hunting opportunity. Detections built on process lineage - "which process wrote the Run key", "what is the parent of this PowerShell" - return a signed Microsoft component and are liable to be tuned out. Detections built on the two anchors in this hunt do not care who the implant is.
  Anchor 1, the script write - the engine creates `C:\Windows\Temp\SDIAG_<GUID>` and hands the path back to its caller. In a legitimate run, the diagnostics stack populates that directory from a package under `C:\Windows\diagnostics\`. Here the IMPLANT writes into it. So a `.ps1` created under `C:\Windows\Temp\SDIAG_*` whose creating process is not `sdiagnhost.exe`, `msdt.exe` or `svchost.exe` is close to a pure signal, and it fires before the payload executes.
  Anchor 2, the output - `sdiagnhost.exe` writing an autostart value. Microsoft's troubleshooters diagnose and repair; they do not install Run-key persistence. `DeviceRegistryEvents` filtered to the Run keys with `InitiatingProcessFileName =~ "sdiagnhost.exe"` should be empty in a healthy estate, which makes it a standing query rather than a one-off sweep.
  Anchor 3, the COM activation - `sdiageng.dll` loading into a process outside the diagnostics stack is the earliest observable moment, available via Sysmon Event ID 7 before any file or registry event. It is noisier to maintain than the other two because the legitimate loader set varies by Windows build, so treat it as a supplementary pivot rather than the primary.
  Script Block Logging is the compensating control that matters here - the `SDIAG_` directory is cleaned up, and the script file is transient, so a host used this way may retain no on-disk trace. PowerShell Event ID 4104 captures the script body regardless, and because the script was written by the attacker rather than shipped by Microsoft, its contents will not match the known troubleshooter corpus. Where Script Block Logging is enabled, search 4104 for Run-key writes (`New-ItemProperty`, `Set-ItemProperty`, `reg add`, `HKCU:\Software\Microsoft\Windows\CurrentVersion\Run`) in events whose host process is `sdiagnhost.exe`.
  Related tooling-level markers from the same report, useful for scoping but not part of this hunt's logic - all recovered `TestAssembly.dll` downloader builds share the AssemblyAttribute GUID `b2b3adb0-1669-4b94-86cb-6dd682ddbea3`, which Talos calls out as "a useful tooling-level detection marker". The signed sideloading host is `GatherOsState.exe` loading `slc.dll` via its `SLOpen` export, with a calculator decoy PE named `OsGather.dat`. Antino's persistent copy stages under `%LOCALAPPDATA%\Windows GatherOSStateKit\`. Delivery used randomised nonstandard extensions (`.luy`, `.pzs`, `.syk`) on Cloudflare R2 objects to remove executable filename signaling.
  Detection breadth beyond what the report attests - Talos documented the chain and the `result.ps1` filename but published no detection queries. The three anchors above, the `SysWOW64`-inclusive scoping, and the Script Block Logging fallback are this hunt's inference from the described mechanics; they were not stated as detections by Talos. The CLSID, the component names, the `SDIAG_<GUID>` path shape, the `-Embedding` invocation and `result.ps1` are the attested artifacts.

# H354

Talos documented a Rust backdoor, Antino, used by the China-nexus actor UAT-11587 against government and policy organisations across Asia. Most of the report covers delivery and a Microsoft 365 command channel, but one capability is unusual enough to hunt on its own: Antino does not run its PowerShell directly, and it does not write its own persistence.

Windows ships a troubleshooting framework — the Scripted Diagnostics engine. Antino initialises COM, instantiates `CScriptedDiag` (CLSID `{1F3D8AA5-9EBF-4EE4-85C2-EA40379AEDE8}`, implemented by `sdiageng.dll`), and points the engine at the legitimate Program Compatibility Wizard package with a blank Answers XML. The engine does what it always does: it makes a temporary working copy of the package at `C:\Windows\Temp\SDIAG_<GUID>` and hands the path back. Antino writes its own PowerShell into that directory and resumes the workflow. The engine delegates to the Microsoft-signed native host — observed as `%windir%\SysWOW64\sdiagnhost.exe -Embedding` — and the host runs `result.ps1`.

For the `add_to_run` command, that script writes an `HKCU` Run value. So the autostart entry that persists the backdoor was created by a signed Windows troubleshooting component. Any detection that asks "which process wrote this Run key" gets an answer that looks entirely normal, and is a strong candidate for being tuned out.

Talos is careful to say the indirection "does not eliminate observable PowerShell, file-creation or registry telemetry" — it just moves it. That is the opening. Two questions catch this without knowing anything about Antino: who wrote a `.ps1` into an `SDIAG_` directory, and has `sdiagnhost.exe` ever written an autostart value. In a legitimate troubleshooter run the diagnostics stack populates that directory itself, from Microsoft's own signed package content, and it never installs persistence.

## Why

- The technique is designed to defeat lineage-based detection, which is what most persistence rules are built on. Attributing a Run-key write to a signed Microsoft troubleshooting host inverts the usual signal — the more a SOC trusts process provenance, the better this works. Hunting the inputs and outputs of the engine instead of the identity of the caller sidesteps that inversion entirely.
- The script-write anchor is close to a pure signal with no tuning. In a genuine run the diagnostics stack populates `C:\Windows\Temp\SDIAG_<GUID>` from a package under `C:\Windows\diagnostics\`; here the implant writes into it. A `.ps1` in that directory created by anything outside the diagnostics stack is the technique, and it fires before the payload runs.
- `sdiagnhost.exe` writing an autostart value should be an empty result set forever. Troubleshooters diagnose and repair — they do not install Run keys. That makes it a cheap standing query rather than a sweep, and an immediately legible finding when it returns a row.
- The artifacts are transient, so this hunt forces the right telemetry decision. `SDIAG_` directories get cleaned up and the script file does not survive, meaning disk forensics on a compromised host can come back empty. Recognising that pushes Script Block Logging (4104) and file-creation telemetry from "nice to have" to load-bearing, which is a durable improvement beyond this one actor.
- The observed host was the 32-bit `SysWOW64` binary, which is exactly the detail a hand-written query gets wrong. Scoping to `System32` would have missed the reported activity outright — a reminder that WOW64 paths need to be explicit in LOLBin hunts rather than assumed.
- Nothing here requires the implant to be Antino. Any tool that can create a COM object can drive the same workflow, so the hunt covers a reusable execution-proxy primitive rather than one malware family.
