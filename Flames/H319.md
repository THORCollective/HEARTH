hypothesis: >-
  Post-exploitation implants on a compromised Linux web server masquerade as system components at
  two levels at once. On disk they are dropped into `/usr/local/bin/` under the names of real
  system binaries - `systemd-udevd`, `rsync-tsl`, `tcp-tsl`, `snapd-ext`, `fsck-disk`,
  `nftables-init`, `xtables-addons` - where the tell is the PATH, not the name, because the real
  `systemd-udevd` lives in `/lib/systemd/` or `/usr/lib/systemd/` and never in `/usr/local/bin/`.
  Without root they fall back to `/tmp/php_sess_<32 hex>` and `/tmp/private-tmp-<5 alnum>`.
  At runtime they rename themselves to BRACKETED KERNEL THREAD names - `[kworker/1:2]`,
  `[ksoftirqd/0]`, `[watchdog/0]`, `[systemd]`, `[dbus-daemon]`, `[journald]`, `[migration/0]`,
  `[ksmd]` - and to `sshd: root@pts/0`. A bracketed name is only legitimate when the process is a
  real kernel thread, and a real kernel thread has PPID 2 (`kthreadd`) and NO mapped executable in
  `/proc/<pid>/exe`. So a bracketed process with a userspace parent, or with a readable
  `/proc/<pid>/exe`, is self-evidently fake - that is the invariant, and it holds for every actor
  who has ever tried this trick. Execution is wrapped in `/bin/sh -c` with `HISTFILE=/dev/null`
  prepended, files are timestomped after drop, and the oRAT agent registers its GUID by APPENDING
  A COMMENT LINE TO `/etc/protocols`, a package-managed file that is otherwise never modified.

false_positive_notes: |
  The bracketed-name check is the closest thing to a zero-false-positive query on Linux, but only if it is written correctly. Real kernel threads are children of PID 2 (`kthreadd`) - the tool shows their names in brackets precisely BECAUSE the kernel reports no command line for them, which is also why `/proc/<pid>/exe` is unreadable for them. The failure mode is not a benign process that looks fake; it is a query that only matches the name and therefore matches every genuine `kworker` on the host, drowning you. Write the condition as "name starts with `[` AND PPid != 2 AND PPid != 0", or equivalently "name starts with `[` AND `/proc/<pid>/exe` resolves to a real file", and the result set on a clean host is empty. Two caveats worth knowing before you call an empty result a true negative - inside containers and in some namespaced views the PID of `kthreadd` may not be 2, so run the check on the host PID namespace; and a rootkit that hides PIDs from `/proc` will hide them from this check too, which is why the kernel-taint and module checks belong in the same hunt rather than a separate one. Some monitoring agents and process supervisors do rewrite `argv[0]` for cosmetic reasons, but essentially none of them write a bracketed kernel-thread name, and none write `[kworker/1:2]`. The `/usr/local/bin/` collision check has a genuine benign population and needs judgement - `/usr/local/bin/` is the correct, FHS-blessed home for locally installed software, and a shop that builds `rsync`, `python`, `node` or `curl` from source will legitimately have a `/usr/local/bin/` binary shadowing a packaged one. The discriminator is that legitimate shadowing is deliberate, consistent across the fleet, explainable by someone on the team, and usually accompanied by the rest of a `/usr/local` install tree (`lib`, `share`, `include`); a lone unowned binary named after a systemd or kernel component - `systemd-udevd`, `fsck-disk`, `nftables-init` - has no such story, because nobody builds systemd into `/usr/local/bin`. `/etc/protocols` modification is about as low-noise as FIM gets: the file is package-owned, changes only on package upgrade, and is not something administrators or configuration management edit - so a modification outside a package transaction window is the finding, and the few benign hits come from `dpkg`/`rpm` upgrades that you can confirm from `/var/log/dpkg.log` or `rpm -q --last`. The ctime-versus-mtime timestomp check has a real benign population that must be understood or it will be noisy: ctime legitimately exceeds mtime after a `chmod`, `chown`, a hard-link change or an SELinux relabel, all of which touch the inode without touching contents. The signal is not the inequality by itself but the inequality on an EXECUTABLE whose mtime has been backdated to match its neighbours, in a directory where nothing else was relabelled. An empty result across all four checks is meaningful ONLY if `/proc` was enumerated on live hosts; a hunt run purely against shipped logs cannot answer the bracketed-name question at all, and should say so rather than reporting a clean bill.
notes: |
  ATT&CK mapping provenance - the Check Point report contains NO detection queries and NO ATT&CK mapping table. T1036.005, T1014, T1070.006 and T1070.003 are ANALYST-MAPPED from the described behavior. Use them for pivoting, not as vendor-asserted ground truth.
  Core check 1, the centrepiece - bracketed process name with a userspace parent. A real kernel thread is a child of PID 2 (`kthreadd`) and has no mapped executable. Shell version - `ps -eo pid,ppid,comm,args | awk '$3 ~ /^\[/ && $2 != 2 && $2 != 0'`. Stronger version, because it does not trust the name at all - for every PID whose `comm` starts with `[`, test whether `readlink /proc/<pid>/exe` resolves; if it does, the process has a real backing binary and is NOT a kernel thread. `for p in /proc/[0-9]*; do n=$(cat $p/comm 2>/dev/null); case "$n" in \[*) e=$(readlink $p/exe 2>/dev/null); [ -n "$e" ] && echo "$p $n -> $e";; esac; done`. Reported spoofed names, verbatim - `[kworker/1:2]`, `[ksoftirqd/0]`, `[watchdog/0]`, `[systemd]`, `[dbus-daemon]`, `[journald]`, `[migration/0]`, `[ksmd]`, and the non-bracketed `sshd: root@pts/0`. Note the last one is a different trick on the same idea - it imitates the `argv[0]` rewrite that real sshd performs for its per-connection children, so compare it against the actual sshd process tree rather than against a name list.
  Core check 2, path-versus-name collision under /usr/local/bin - for every executable in `/usr/local/bin/`, ask whether a binary of the same NAME exists elsewhere in the filesystem under package ownership. `for f in /usr/local/bin/*; do b=$(basename $f); dpkg -S "*/$b" 2>/dev/null | head -1; done` on Debian family, `rpm -qf $(which -a <name>)` on RHEL family. Reported paths, verbatim - `/usr/local/bin/systemd-udevd`, `/usr/local/bin/rsync-tsl`, `/usr/local/bin/tcp-tsl`, `/usr/local/bin/snapd-ext`, `/usr/local/bin/fsck-disk`, `/usr/local/bin/nftables-init`, `/usr/local/bin/xtables-addons` (the oRAT agent). The real `systemd-udevd` ships in `/lib/systemd/` or `/usr/lib/systemd/`; a copy in `/usr/local/bin/` is wrong by construction regardless of what it contains.
  Core check 3, the /etc/protocols tripwire - oRAT persists its GUID by APPENDING A COMMENT LINE to `/etc/protocols`. That file is package-managed, is read by `getprotobyname()`, and changes only on package upgrade - which makes it one of the best low-noise FIM targets on a Linux host. `rpm -V setup` / `dpkg -V netbase` will flag the content change directly; `tail -20 /etc/protocols` will show the appended comment; `stat /etc/protocols` gives you the modification time to pivot on. Extend the same watch to the sibling files nobody edits - `/etc/services`, `/etc/networks`, `/etc/rpc`, `/etc/nsswitch.conf`, `/etc/ld.so.preload` (an empty-or-absent file whose mere existence is a rootkit indicator). auditd - `-w /etc/protocols -p wa -k etc_static`, surfaced with `ausearch -k etc_static -i`.
  Core check 4, timestomp detection via ctime - the toolset timestomps after drop. `touch -r` and `touch -t` reset mtime and atime but CANNOT reset the inode change time, because ctime updates on any inode write including the timestamp write itself. So `ctime` newer than `mtime` on an executable is the residue of the timestomp. `find /usr/local/bin /tmp /usr/sbin /usr/bin -type f -printf '%T@ %C@ %p\n' | awk '$2 > $1 + 60'`, or per-file with `stat -c '%y %z %n'`. Pair it with the Elastic cross-platform `touch`-argument rule (`-r`, `-t`, `-a`, `-m` by a non-root user) for the execution side of the same behavior.
  Core check 5, the non-root fallback paths - when the implant does not have root it writes to `/tmp` instead. Reported patterns, verbatim - `/tmp/php_sess_<32 hex chars>` and `/tmp/private-tmp-<5 alphanumeric chars>`. `ls -la /tmp /dev/shm` and `find /tmp -maxdepth 1 -regextype posix-extended -regex '.*/php_sess_[0-9a-f]{32}'`. The `php_sess_` name is deliberately chosen to blend with PHP session files, but real PHP sessions are named `sess_<id>` and live in the configured `session.save_path` (commonly `/var/lib/php/sessions`), so the `php_` prefix and the `/tmp` location are both wrong for a genuine session file. oRAT additionally drops a lock file at `/tmp/.lock` and uses `/tmp/asset-scan` as its default log directory - both are worth their own one-line check.
  Core check 6, the systemd unit and the execution wrapper - oRAT registers a systemd service named `xtables-addons`. `systemctl list-unit-files --type=service | grep -i xtables` and, more generally, `grep -rl 'ExecStart=.*\(/usr/local/bin\|/tmp/\)' /etc/systemd/system/ /usr/lib/systemd/system/` - a unit whose `ExecStart` points into `/tmp` is anomalous on any production host. Execution is wrapped as `/bin/sh -c` with `HISTFILE=/dev/null` PREPENDED to the command, which is directly greppable in auditd `execve` argument vectors and in EDR command lines - `HISTFILE=/dev/null` in a command line has essentially no benign enterprise population and is worth a standing rule of its own independent of this campaign. It also tells you shell history on that host is deliberately incomplete, so do not treat a clean `.bash_history` as evidence of anything.
  Rootkit branch - AlphaAgent exposes an `-r` flag that installs a rootkit. If any of the checks above hit, immediately capture kernel taint state (`cat /proc/sys/kernel/tainted`, and syslog `kernel` messages about module verification failure), the loaded module list (`lsmod`, `/proc/modules`), and compare module names against `modinfo` and the package database. A tainted kernel or an out-of-tree module on a web server that has never had a third-party driver installed is corroboration, and it also changes your confidence in every other check on this hunt, since a kernel-resident rootkit can lie to `/proc`.
  Cross-references - the initial access and the web-server-resident implant this cleans up after are in [[H318]]; the credential theft the same toolset performs with ptrace and a setuid backdoor is in [[H320]]. A hit on any one of the three should trigger all three.

# H319

The post-exploitation toolset Check Point attributes to "Gambling Goblin" (linked to Earth Berberoka) spends most of its evasion budget on looking like part of the operating system. On disk, implants go into `/usr/local/bin/` under names lifted from real system components — `systemd-udevd`, `snapd-ext`, `fsck-disk`, `nftables-init`, `rsync-tsl`, `tcp-tsl`, and `xtables-addons` for the oRAT agent — which is effective against anyone reading a process list, because the names are familiar and nobody checks the path. Without root, the same binaries land in `/tmp` as `php_sess_<32 hex>` or `private-tmp-<5 alnum>`, borrowing the look of PHP session files. At runtime they go further and rename themselves to bracketed kernel-thread names: `[kworker/1:2]`, `[ksoftirqd/0]`, `[watchdog/0]`, `[systemd]`, `[journald]`, `[migration/0]`, `[ksmd]`, plus the `sshd: root@pts/0` form that imitates a live SSH session. Everything is launched through `/bin/sh -c` with `HISTFILE=/dev/null` prepended, and files are timestomped after they are dropped. The one piece of housekeeping that betrays the whole set is small: oRAT stores its GUID by appending a comment line to `/etc/protocols` — a package-managed file that, on a normal system, changes only when the package that owns it is upgraded.

## Why

- **The bracketed-name check is one of the few genuinely near-zero-false-positive queries available on Linux, and it generalises far past this actor.** Brackets in a process listing are not a naming convention an attacker can safely imitate; they are what the tool prints when the kernel reports no command line, which happens exactly when the process is a kernel thread. Kernel threads are children of `kthreadd` (PID 2) and have no mapped executable. So the pair of conditions — bracketed name, userspace parent — describes a state that cannot occur legitimately. Any actor who has ever hidden a process this way fails this check, which makes it worth building into standing collection rather than running once against this campaign.
- **Masquerading is a path problem, not a name problem, and treating it as a name problem is why it works.** A defender who reads `systemd-udevd` in a process list recognises it and moves on; the lie is entirely in the directory. Reframing the check as "does a binary in `/usr/local/bin/` share a name with a package-owned binary somewhere else" converts an unwinnable recognition task into a mechanical comparison against the package database — and the package database is authoritative, complete, and already on the host.
- **`/etc/protocols` is a near-perfect tripwire precisely because it is boring.** Choosing FIM targets is normally an exercise in trading coverage against noise, and `/etc` as a whole is noisy. But a handful of files in `/etc` — `protocols`, `services`, `networks`, `rpc` — are package-owned reference data that nothing in normal operation writes to. Watching them costs nothing, alerts essentially never, and here catches the RAT storing its own identity. The actor picked that file because it looked inert; that is exactly what makes it a good watch.
- **Timestomping is self-defeating on Linux, and the residue outlives the campaign.** `touch` can rewrite mtime and atime, but ctime records the moment the inode itself was last changed and is not settable through any ordinary interface — so the act of backdating a file leaves a ctime newer than the mtime it just wrote. Any dropped-and-timestomped file therefore carries a permanent marker of having been tampered with, and a single `find -printf '%T@ %C@ %p\n'` sweep surfaces it. The benign population (chmod, chown, relabels) is real but is not made of freshly dropped executables.
- **`HISTFILE=/dev/null` in a command line is both an indicator and a scoping fact.** As a detection it is cheap and nearly unique — no legitimate automation prepends it. As an investigative fact it is more important: it tells you that shell history on this host was deliberately suppressed, so an empty or unremarkable `.bash_history` during triage means nothing at all. Analysts routinely read a clean history as reassurance; on a host where this string appears, that inference is invalid and the writeup should say so.
