false_positive_notes: |
  The burst leg alone is noisy: scheduled backup and mirroring tools (gickup, GitHub-to-GitLab mirrors, enterprise migration importers), security scanners and SCA tooling running under OAuth apps such as Dependabot or Renovate, monorepo CI cache warming, and a new hire or rebuilt laptop cloning the whole org all produce legitimate read-only bulk access. Control them by allowlisting known automation `hashed_token` values and OAuth app names, baselining per-identity distinct-repo rates over 30 days, and confirming bulk reads against change tickets. The decisive control is the conjunction: require the dormant-identity leg (no interactive IdP sign-in in the trailing window) before alerting, since sanctioned bulk readers are either service identities on an allowlist or active humans with live SSO sessions. notes: |
  GitHub organization audit log (enable Git events; they are off by default) - Core filter: `action` equal to `git.clone` or `git.fetch` against private repositories, aggregated per actor over a rolling 10-minute window; flag when the distinct `repo` count exceeds roughly 3x that identity's 30-day daily maximum (CrowdSec lost ~170 repositories in nine minutes). Triage values: `actor`, `actor_ip`, `user_agent`, `repo`, `hashed_token`, `programmatic_access_type`. Strong red flags: the burst walks the repository list in near-alphabetical or API-enumeration order, the `user_agent` is a bare `git/2.x` or generic HTTP client instead of the actor's usual IDE and CLI mix, and the `actor_ip` sits in a hosting ASN or geography never before associated with that identity.
  GitHub token and app telemetry - Core filter: audit events where `programmatic_access_type` is `OAuth access token` or `personal access token`. Pivot: group all audit activity by `hashed_token` to reconstruct the complete token session; a single `hashed_token` touching tens of private repositories with zero writes is the chokepoint signal, regardless of which IP or token value the attacker used. Correlation: sweep `GET /orgs/{org}/credential-authorizations` (SAML-enforced orgs) and the fine-grained PAT inventory for grants whose owning user is deprovisioned in HR or the IdP — every hit is a standing exposure worth revoking even absent replay.
  IdP sign-in logs (Okta/Entra/GitHub SSO) - Correlation: join the GitHub `actor` login to the IdP user and require a successful interactive sign-in within the trailing 14-30 days; API token activity from an identity with none is the dormant-identity leg of the conjunction. Strong red flags: HR termination date precedes the token activity, or the SAML session was revoked at offboarding while API reads continue — proof that deprovisioning killed the session but not the grant.
  Read-only session shape - Core filter: for the flagged `actor` and window, absence of `git.push`, pull-request, issue, or workflow-run activity; pure enumerate-and-clone with no contribution is collection, not development. False positive: migration and backup tooling produces the same read-only burst — separate it by service-account allowlist, change tickets, recurring schedule, and a `user_agent` matching the sanctioned mirror tool.
  Developer endpoint precursor (optional companion) - Core filter: package-manager lifecycle execution such as `npm` spawning `node` to run a `postinstall` script that reads developer credential stores or opens connections to non-registry infrastructure; Shai-Hulud harvested the CrowdSec token this way from a former employee's endpoint, so this telemetry provides the left-of-boom edge of the same intrusion chain.

# H334

On May 11, 2026, the TanStack npm project was compromised and 42 packages were backdoored with the Shai-Hulud credential-harvesting worm, which specializes in stealing developer tokens and secrets. One harvested credential was a GitHub OAuth token taken from a former CrowdSec employee's machine — a token that still held read access to CrowdSec's private organization repositories long after the employee departed. On May 22, 2026, between 05:52 and 06:01 UTC, that token was replayed from an IP address in Toronto to download roughly 170 private repositories in about nine minutes. CrowdSec only learned of the breach on September 16, 2026, when the stolen source code surfaced on an underground leak forum; the token itself no longer appeared in their own audit records, and reconstruction required GitHub's assistance. The generalizable exposure is systemic, not CrowdSec-specific: OAuth apps and PATs granted to human users routinely outlive both the user's employment and their SSO session, because SAML/SCIM offboarding revokes sessions, not token grants. The replay, however, cannot avoid producing a distinctive shape in first-party telemetry — one token, tens of private repositories, minutes, read-only, and an owning identity that is otherwise silent. This hunt targets that conjunction and pairs it with a proactive sweep for standing token grants owned by deprovisioned users, which are actionable findings even before any replay occurs.

## Why

- The Shai-Hulud/TanStack npm wave mass-harvested developer tokens at ecosystem scale, and CrowdSec's loss of ~170 private repositories took nine minutes in May but went undiscovered until the code hit a leak forum in September — the GitHub audit log was the only place the theft was visible in the intervening four months, making this a hunt, not an alert you already have.
- Attacker IPs, token values, and trojanized package names rotate per victim, but monetizing a stolen repo-read token forces an invariant chokepoint: the adversary must enumerate and clone many private repositories quickly through the same API surface, producing the human-token/burst-read/dormant-owner conjunction no matter what infrastructure they use.
- Every leg of the conjunction is first-party and queryable: org audit logs expose `git.clone`/`git.fetch` per repository with `hashed_token`, `actor_ip`, and `user_agent` once Git events are enabled, credential-authorization APIs enumerate standing grants, and IdP logs establish dormancy — no third-party sensor is required.
- False positives collapse under the joint condition because legitimate bulk readers are either allowlisted service identities or active users with contemporaneous SSO sessions; what remains after the dormancy filter is either an incident or a deprovisioning gap, and both are worth a ticket.
