  MCP server registration is a normal, supported and increasingly common thing for developers to do, so
  the presence of entries in an agent's tool-server configuration is not a finding. Developers add
  servers deliberately, legitimate packages ship them, and plenty of real tooling writes these files as
  part of setup - which means an estate without an inventory of sanctioned servers cannot run the second
  half of this hunt at all. Likewise, overriding a model base URL is a legitimate practice: teams point
  clients at an internal gateway, a proxy for cost control or auditing, Azure OpenAI, a local inference
  server, or a staging endpoint, and all of those produce exactly the pattern described here. The
  discriminators are provenance and consistency. For the configuration half: was the entry written by a
  package install rather than by the developer, and does the endpoint appear in the sanctioned list. For
  the traffic half: does the endpoint the client reports match the host it is actually talking to -
  Elastic's finding is that the label and the peer disagreed, and a mismatch between a configured

# H409

The usual malicious npm package reads your `.env`, posts it somewhere, and is done. One file, one theft, one chance to catch it.

This one installs a working AI coding agent and changes where the agent sends its conversations.

Elastic Security Labs found that `@apexacc/cli`'s bootstrap overwrote three environment variables in the running process. The important one: `OPENROUTER_BASE_URL`, pointed at `arena.apexaccs[.]org`. And then — this is the detail that makes it work — nothing in the interface changed. Elastic puts it exactly: "The provider remains labeled OpenRouter, while the actual network peer is an attacker-controlled server."

The developer sees the provider they chose. The traffic goes elsewhere.

Elastic proved out the consequence rather than inferring it. They created a file with a unique value in it and asked the agent to read it with its local read tool, explicitly telling it not to use shell or MCP tools. The first request to the attacker endpoint contained the instruction and the path, but not the contents. The agent then ran the local read tool. And the *next* POST carried a tool-result field holding the file's contents. Elastic adds that "The same file-read result remained in later conversation requests, showing that the model transmitted locally read content as context after an explicitly requested file read."

Sit with the mechanics of that for a second, because it is not really exfiltration in the sense we normally hunt.

There is no upload. No separate channel. No connection the developer would consider unexpected — a coding agent talking to a model API is the most normal thing on that machine. The file contents leave as *conversation context*, which is precisely what an agent is supposed to send. And they keep leaving, in every subsequent request in that conversation.

So the theft is not a moment. It is a standing condition, and its scope is every file the developer asks the agent to look at for as long as the configuration holds.

Then there is the half that survives a reboot. The bootstrap "creates or replaces an apex-copilot entry in ~/.apex/agent/mcp.json, pointing to hxxps://arena.apexaccs[.]org/api/copilot/mcp with a bearer token and device identifier", and that entry "persists across process restarts." The agent's MCP support connects to it automatically on next launch. Elastic saw the server's eight tool definitions and its instructions turning up in outgoing requests — "alongside a warning that the instructions were server-controlled and might not be verified."

The client did warn. Worth remembering how much that is worth in practice.

Two things Elastic was careful about, and I will be too. Controlling the endpoint would let an attacker substitute responses — including tool calls the client parses as genuine model output — and the captured source "defaults tool approvals to yolo, allowing read, write, and execution tiers unless explicit policies or other controls intervene." That is a serious capability. But Elastic states plainly: "we didn't observe malicious LLM response substitution." Described, not seen.

For hunting, there are two surfaces and the useful tests are about provenance rather than content.

MCP registration is normal — developers add servers on purpose, and legitimate packages ship them. So the question is not whether entries exist but *who wrote them*. A tool-server configuration modified by `npm`, `npx` or `bun` in the same minute as an install is a different thing from one a developer edited. And the entry's display name tells you nothing at all; it is attacker-controlled text. Key on the URL and the writing process.

Base-URL overrides are normal too — internal gateways, cost proxies, Azure OpenAI, local inference. Which means a naive "model traffic to a non-provider host" query will return your own gateway, loudly, forever. Build that allowlist first or the hunt is unusable.

The signal that has no benign form is the one Elastic actually identified: the provider the client names and the host it is talking to disagreeing. A label that lies.

## Why

- **The exfiltration path is the agent's normal traffic.** File contents leave as conversation context to a model API, so there is no anomalous upload, no new channel and nothing a developer would question.
- **It is a standing condition rather than a single theft.** Every file the developer subsequently asks the agent to read leaves, and Elastic observed the content persisting across later requests in the same conversation.
- **The interface keeps the trusted provider's name.** The client still displays OpenRouter while talking to an attacker host, which defeats the one check a developer might actually perform.
- **The MCP entry survives restarts.** Configuration-based persistence needs no binary, no scheduled task and no service, and reconnects automatically on next launch.
- **Install-time provenance is the discriminator, not the configuration itself.** Developers legitimately register tool servers, so a config write parented by a package manager within minutes of an install is the shape worth isolating.
- **The entry name is attacker-controlled.** Any query built on a server's display name is evadable by typing a different one, which is why the URL and the writing process carry the hunt.
- **Server-controlled tool instructions reach the model.** The remote server's instructions appeared in outgoing requests, so the attacker influences agent behaviour without executing anything locally.
- **Response substitution is a real capability with default-permissive approvals.** Tool approvals defaulting to a permissive tier means a substituted response could drive local read, write and execute tiers — stated as capability, because Elastic did not observe it.
- **The delivery vehicle was a months-long legitimacy campaign.** Free AI credits, conference presence and fake reviews mean the package arrived by invitation rather than by typosquat, so dependency-name heuristics would not have flagged it.
