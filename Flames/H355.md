false_positive_notes: |
  This is one of the rare hunts where the expected result is genuinely nothing, and a single hit deserves immediate incident handling rather than triage. `HideExclusionsFromLocalAdmins` is not part of any Microsoft security baseline, not set by the Windows Security Baselines in the Security Compliance Toolkit, not set by Defender for Endpoint onboarding, and not something a hardening guide recommends - because its only effect is to conceal security configuration from the administrators and tooling responsible for auditing it. Treat the registry write as the finding.
  There is one category of legitimate use that must be ruled out before declaring an incident, and it is worth checking first precisely because it is defensible. Some organisations deliberately restrict what endpoint users - including users who hold local administrator rights on their own machines - can see about centrally managed security policy, for example on shared or kiosk builds, in high-assurance environments, or where local admin is granted to developers who should not be able to enumerate the estate's exclusion design. If a Group Policy Object or an Intune configuration profile sets this value, it will be set identically across a large, policy-defined population of hosts, the writing process will be the policy application path (`svchost.exe -k netsvcs -p -s gpsvc` for GPO, or the Intune management extension), and there will be a corresponding policy object you can name and an owner who can explain it. Confirm that before anything else - and if it turns out to be deliberate, record it in the exclusion register built by [[B056]] and re-scope this hunt to "set by anything other than the sanctioned policy", which keeps the detection useful instead of retiring it.
  The malicious shape is the opposite in every respect - a single host or a small cluster, set by `reg.exe`, `powershell.exe`, an MSI, a script host, or a binary running from a user-writable path, with no corresponding policy object, and almost always accompanied in time by exclusion additions to the policy `Exclusions\Paths` key. Microsoft Defender locks down direct writes to `HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions`, so an operator who wants registry-level control works against the POLICY hive instead, which is also where this hiding value lives. That co-location is useful - the same key path carries both the carve-out and the concealment, so one Sysmon filter covers both.
  One important caveat about interpreting a NEGATIVE result. Because this value defeats API-based enumeration for SYSTEM too, any inventory you have built by calling `Get-MpPreference` or the Defender WMI class may already be wrong on an affected host, and the affected host will not announce itself. Do not conclude "we have no unexpected exclusions" from an API-sourced inventory. The only sound method is to collect both views - the API list and the raw hive contents - and diff them per host; a disagreement is itself a detection, independent of whether you caught the registry write.

  - platform: PowerShell (the API-versus-registry diff)
    description: Collect both views on the same host. A disagreement means the API view is being suppressed, which is a detection in its own right and does not depend on having caught the write.
    query: |
      $api = (Get-MpPreference).ExclusionPath
      $mdav = Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows Defender\Exclusions\Paths' -EA SilentlyContinue
      $pol  = Get-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions\Paths' -EA SilentlyContinue
      $hide = (Get-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows Defender' -EA SilentlyContinue).HideExclusionsFromLocalAdmins
      [pscustomobject]@{
        Host=$env:COMPUTERNAME; HideFlag=$hide
        ApiCount=@($api).Count
        RegistryPaths=@(($mdav.PSObject.Properties.Name + $pol.PSObject.Properties.Name) -notmatch '^PS')
      }

notes: |
  Platform: Windows. Driven by Huntress (Jonathan Johnson), "You Can Run, but You Can't Hide: Defender Exclusions" (last updated September 30, 2026).
  How Defender exclusions work, which is what makes this hiding value matter - Microsoft supports four exclusion types. `Process` disables real-time scanning on files opened by a specified source process; `Path` excludes entire file paths from real-time and scheduled scans; `Extension` disables real-time, scheduled and custom scans for given file extensions; `IpAddress` disables network packet inspection from a given IP. Huntress notes that `Path` and `Extension` are the two most used and most valuable to an attacker, because when set, "the path/process that matches that exclusion is removed from scheduled scans, on-demand scans, and always-on, real-time protection and monitoring".
  The four write paths, and why they all converge on the registry - exclusions can be set via PowerShell (`Set-MpPreference`/`Add-MpPreference`), via WMI (the `MSFT_MpPreference` class), via Group Policy, or by direct registry modification. Huntress traced the PowerShell path through `MSFT_MpPreference`, then COM and RPC, into `MsMpEng.exe`, which performs the actual registry write to `HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions`. The GPO path goes through the Group Policy `svchost` (`C:\Windows\system32\svchost.exe -k netsvcs -p -s gpsvc`) and writes to a DIFFERENT key - `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions`. Querying exclusions reads both. Huntress's engineering conclusion is the useful one for defenders - "no matter how someone sets an exclusion, it needs to be set in the registry", so registry-operation telemetry sees PowerShell, WMI, GPO and manual methods alike, which is why that is the collection point this hunt specifies.
  Direct registry modification, and the hive that is actually writable - Huntress found that "due to MDAV locking down the ability to directly write to the `HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows Defender\Exclusions` registry key, it isn't feasible to directly modify it". The policy hive is a different matter - an attacker can modify the `Paths` value under `HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions`, for example with `reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions\Paths" /v "C:\Temp" /t REG_SZ`. Huntress notes one caveat on this path - "this policy requires a reboot to take place".
  The concealment value, exactly as reported - Huntress found that "attackers can set the following registry key value to 'hide' exclusions from administrators when they try to query them - `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\HideExclusionsFromLocalAdmins`". Their figures show a successful `Get-MpPreference`-style query before the value is set and an unsuccessful one after. Critically - "although this registry value says 'HideExclusionsFromLocalAdmins,' it also stops SYSTEM users from querying this data". Huntress spell out the consequence - "this is obviously problematic because, depending on how products are querying the exclusions list, it allows attackers to potentially hide the exclusions they're setting. However, administrators and SYSTEM users can still query this data. They just need to do it through the registry directly."
  That last sentence is the whole hunt. The attacker's hiding mechanism defeats the API, not the registry. So the detection is to stop trusting the API as the source of truth for exclusion inventory, read the hives, and diff the two views - a disagreement is a finding even on a host where the registry write itself was never captured.
  Prior adversary use, for prevalence context - Huntress cite GootKit (2019) creating an MDAV path exclusion via the `MSFT_MpPreference` WMI class, WhisperGate (2022) creating a path exclusion for the entire `C:\` drive via `Set-MpPreference`, and Muddled Libra (2024). Their framing is that this is older tradecraft still working - "we identified that MDAV exclusions are used more than we originally thought". Huntress's own response was to collect telemetry on exclusions set via registry operations regardless of the setting method, collect telemetry on `HideExclusionsFromLocalAdmins` specifically, and build detections both for suspicious exclusions (known-bad binaries and suspicious directories such as `C:\`, `Temp`, `Downloads`) and for the hiding setting.
  Pair this with the baseline - a single registry write is a clean detection, but the question it raises immediately is "what was being hidden, and is any of it still there". That is an inventory problem, not a detection problem, and it is what [[B056]] is for. Run both - this hunt as a standing high-severity rule, the baseline as a periodic census with a diffable snapshot.
  Detection breadth beyond what the report attests - Huntress documented the registry value, its effect on local administrators and SYSTEM, the four setting methods and the two hives. The API-versus-registry diff as a standalone detection, the legitimate-GPO ruling-out procedure, the Sigma logic and the KQL above are this hunt's construction from those facts; Huntress published no detection rules or queries. The registry paths, the `reg add` example, the setting methods and the SYSTEM-level effect are the attested artifacts.

# H355

Adding a Microsoft Defender exclusion is well-trodden attacker tradecraft — Huntress cite GootKit in 2019, WhisperGate excluding the entire `C:\` drive in 2022, and Muddled Libra in 2024. What their September 2026 research adds is the step after that, and it is considerably more interesting than the exclusion itself.

`HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\HideExclusionsFromLocalAdmins`, when set, stops the exclusion list being returned to queries. Huntress demonstrated it against `Get-MpPreference` before and after, and then established the part that actually matters: despite the name, it does not only affect local administrators. It blocks SYSTEM too. So an EDR agent, an inventory script, or a compliance check that enumerates exclusions through the Defender API gets an incomplete or empty answer from a host that has been carved wide open — and nothing about the response indicates that it is being suppressed.

Huntress also traced where exclusions physically live, which is what makes this tractable. Whichever interface is used — PowerShell's `Set-MpPreference`/`Add-MpPreference`, the `MSFT_MpPreference` WMI class, Group Policy, or direct registry editing — the setting ends up in the registry. PowerShell and WMI route through COM and RPC into `MsMpEng.exe`, which writes to `HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions`. Group Policy writes to a different key, `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions`. Defender locks down direct writes to the first; the second is writable, which is why an operator working at the registry level uses the policy hive — the same hive that carries the hiding value.

Huntress end on the sentence that defines the hunt: administrators and SYSTEM can still read this data, they just have to go to the registry directly. The concealment defeats the API, not the hives. So there are two detections here — catch the registry write, and stop treating `Get-MpPreference` as the source of truth for exclusion inventory. Collect both views and diff them; a host where they disagree is a finding even if the write was never captured.

## Why

- The value has no legitimate security purpose, so the base rate should be zero. It is absent from Microsoft's security baselines and from Defender onboarding, and its only effect is to hide security configuration from the people accountable for auditing it. That makes a single hit an incident rather than a triage queue item — a rare property for a registry-based detection.
- It silently invalidates inventory you may already rely on. Because enumeration fails for SYSTEM as well, any exclusion inventory built by calling the Defender API can be wrong without raising an error. Recognising that converts "we audit our exclusions" from a reassurance into a question about collection method, which is a finding in itself for most organisations.
- The API-versus-registry diff is a detection that does not depend on catching the write. Registry auditing on the Defender policy key is off by default and Sysmon coverage is uneven, so the write is often missed. Comparing the two views recovers the detection after the fact, from configuration state alone.
- All four setting methods converge on one observable. Huntress's tracing establishes that PowerShell, WMI, GPO and manual editing all terminate in a registry write, so a single registry-operation filter covers every interface — including methods that have not been used yet.
- The concealment and the carve-out share a key path. Both `HideExclusionsFromLocalAdmins` and the writable `Exclusions\Paths` live under the same policy branch, so one filter catches the hiding and the thing being hidden, and the two events correlate in time to give a complete picture of what the operator protected.
- The legitimate-use case is narrow and nameable, which keeps the rule alive rather than retired. If a GPO or Intune profile sets this deliberately for a high-assurance build, it will be uniform across a policy-defined population with an identifiable owner — easy to record once and then re-scope the detection to "set by anything other than the sanctioned policy".
