  Rather than drop an unsigned loader, an adversary takes a legitimate, validly signed executable from one software vendor, renames it to the filename of a different product's component-management binary, and writes it into that product's component directory alongside a malicious DLL the renamed binary will side-load. false_positive_notes: |
  Signer mismatch inside an application directory is common enough that the hunt only works with the vendor-to-path mapping in place.
  - Redistributable runtimes are everywhere and are legitimately Microsoft-signed inside third-party trees: Visual C++ runtimes, .NET assemblies, `vcruntime*.dll`, `msvcp*.dll`, WebView2 and Edge components. Exclude Microsoft-signed modules in third-party directories by signer, then narrow further by requiring the mismatch on an `.exe` rather than a `.dll` for the first pass.
  - Embedded frameworks ship signed by their own vendor. Chromium Embedded Framework binaries, Electron, Qt, Java runtimes and installer frameworks such as Inno Setup or NSIS all produce signer-versus-path mismatches that are entirely normal. Allowlist by the pair of signer plus module name plus directory, never by signer alone.
  - OEM and ISV bundling produces genuine cross-vendor binaries in one tree, especially on consumer-grade endpoints and vendor-imaged laptops. Baseline the mismatch set per hardware model before alerting.
  - Legitimate licensing, telemetry and crash-reporting helpers are frequently third-party signed and installed into the host product's folder. The discriminator is that the renamed file takes the name of an existing first-party component, so compare `OriginalFileName` from the version resource against the on-disk filename rather than comparing signers only.
  - A renamed signed binary is not inherently malicious, so a hit is a lead. Confirmation comes from the DLL loaded next to it: a module in the same directory that is unsigned, signed by no one the product uses, or has an `OriginalFileName` unrelated to its on-disk name.
notes: |
  The report behind this hunt is ESET's analysis of SlippyNunchucks delivering the DarkVigil implant through Sogou Input Method. The configuration delivered to victims named two files: the legitimate and signed Adobe Licensing WF Helper, renamed to `biz_helper.exe` (SHA-1 79188C8DE2378B437D39E867475C5B4714A0D7C9), and the DarkVigil implant as `libcef.dll` (SHA-1 8A60A8E90E1F5F08F28FE5A6DD57BD686C20DC23). The destination paths were chosen so execution happened through workflows the product already runs - see [[H454]] for the delivery half of the same intrusion.
  Signer versus owning directory - Core filter: processes executing from a third-party application tree whose certificate signer is not the vendor that owns that tree. `DeviceProcessEvents` carries `SHA1` and `FolderPath` but no signature fields, so the signer has to come from `DeviceFileCertificateInfo` via a join on `SHA1`. Sample Defender XDR query:
  ```kql
  let lookback = 30d;
  let certs = DeviceFileCertificateInfo
      | summarize arg_max(Timestamp, Signer, Issuer, IsSigned, IsTrusted) by SHA1
      | project SHA1, Signer, Issuer, IsSigned, IsTrusted;
  let ownedPaths = dynamic([@"\SogouInput\", @"\Tencent\"]);
  let ownedSigners = dynamic(["Sogou", "Tencent", "Beijing Sogou"]);
  DeviceProcessEvents
  | where Timestamp > ago(lookback)
  | where isnotempty(SHA1)
  | where FolderPath has_any (ownedPaths)
  | join kind=inner certs on SHA1
  | where IsSigned == true
  | where not(Signer has_any (ownedSigners))
  | project Timestamp, DeviceId, DeviceName, FileName, FolderPath, SHA1,
            Signer, Issuer, IsTrusted, ProcessCommandLine,
            InitiatingProcessFileName, InitiatingProcessCommandLine
  | order by Timestamp desc
  ```
  One product is one run of this query, with its own `ownedPaths` and `ownedSigners` pair - that is deliberate, because the comparison is only meaningful per product and a single combined query would mark every vendor's binaries as foreign to every other vendor's directory. Fill both lists from software inventory for the products you actually run; the Sogou and Tencent values are a worked example, not a detection. Keep `ago(30d)` as the ceiling, since Defender XDR advanced hunting retains 30 days and silently truncates longer windows. Triage values are `FileName`, `FolderPath`, `SHA1`, `Signer`, `Issuer`, `ProcessCommandLine` and the parent command line.
  Version resource versus on-disk name - Core filter: Sysmon Event ID 1 where `OriginalFileName` differs from the leaf of `Image`, and `Company` or `Product` names a vendor other than the one owning the directory. This is the cheapest high-signal cut available on Windows, because a renamed signed binary keeps its version resource. In the reported case the on-disk name was a Sogou component-manager filename while the version resource still described an Adobe licensing helper. Triage values are `Image`, `OriginalFileName`, `Company`, `Product`, `Description`, `Signature`, `SignatureStatus`, `Hashes` and `ParentImage`. Strong red flags are an `OriginalFileName` from a software category unrelated to the host product (licensing, updater, installer helper), and a `Signature` that is valid but from a vendor whose software is not otherwise installed on that host.
  The side-loaded module - Core filter: Sysmon Event ID 7, or `DeviceImageLoadEvents` joined to `DeviceFileCertificateInfo` on `SHA1`, for modules loaded out of an application component directory where the loading process is the mismatched binary found above. `DeviceImageLoadEvents` has no signature columns of its own, so the join is mandatory rather than optional. Watch for module names drawn from common embedded frameworks, because those names are rarely questioned - the reported implant used `libcef.dll`, which is the Chromium Embedded Framework library name and therefore unremarkable in a directory that already contains a browser framework, and conspicuous in one that does not. Correlation: compare the module's `OriginalFileName` and `Company` against the real framework's values, and compare the module's SHA-256 against the vendor's published distribution. Strong red flags are an unsigned module beside a validly signed renamed executable, and a module that exports the small handful of entry points the host binary imports and nothing else.
  Resilience of the planted pair - Core filter: file-create telemetry for the same filename being re-written after a product update. ESET describes two mutually exclusive variants of this placement: overwriting the component manager so the application runs the planted binary whenever it installs or loads a component, or placing the pair under a versioned component subdirectory so the application loads it through its normal bundle invocation. The second is sensitive to updates that introduce a new version directory, the first is undone by an update that replaces the overwritten file. Either way a product update is a natural remediation and a natural re-infection moment, so look for the same hash reappearing at the same path after an update, which separates a one-off from a maintained foothold. Correlation: pair any hit with the DNS and plaintext-configuration evidence in [[H454]], because that is where the instruction to write these files came from.

# H455

The usual shape of DLL side-loading is an unsigned or stolen-certificate loader placed next to a vulnerable application. This variant inverts the trust question. The executable is genuinely signed, by a real vendor, with a valid certificate - it is simply not the file it claims to be, because it has been renamed to the filename of a completely different product's component.

In ESET's SlippyNunchucks case the planted executable was Adobe Licensing WF Helper, renamed to `biz_helper.exe` and written over Sogou Input Method's own `SogouComMgr.exe`. Whenever the input method's dispatcher tried to install or load a component - something it does routinely - it executed the Adobe binary instead, which side-loaded the DarkVigil implant from `libcef.dll` in the same directory.

Signature verification does not catch this, because nothing about the signature is wrong. Application allowlisting by publisher does not catch it either, since Adobe is a publisher most environments trust. What is wrong is the relationship between three facts that are rarely compared: the signer of the file, the version resource inside the file, and the vendor who owns the directory the file runs from.

That comparison is cheap. Sysmon records `Company`, `Product` and `OriginalFileName` on every process creation; Defender XDR records SHA1 on process events and signer data in a separate table that joins on it. The hunt is the join.

## Why

- The technique defeats the two controls most environments rely on for delivery. The binary is validly signed so reputation and publisher allowlisting pass it, and it executes from inside a legitimate product directory under that product's own parent process, so lineage-based detections see application maintenance.
- The discriminating evidence survives renaming. An adversary can change a file's name and its location, but the Authenticode signer and the version resource travel with the bytes. A process whose `OriginalFileName` describes a licensing helper while its on-disk name is another vendor's component manager is a one-line finding once the comparison exists.
- Module names borrowed from embedded frameworks are the quiet part. `libcef.dll` sitting in a directory that already hosts a Chromium Embedded Framework build is invisible; the same name in a product that embeds no browser is a strong lead. This needs the per-product baseline, which is why the hunt is built on the vendor-to-path map rather than on names.
- The placement is deliberately parasitic on the host application's own workflow, so there is no scheduled task, service or Run key to find. Hunting for the absent persistence artefact returns nothing, which is exactly why the hunt has to key on the pair of files instead.
- Product updates both remediate and expose it. One variant is overwritten by an update, the other is orphaned by a new version directory, and both cause the application failures ESET observed - so update telemetry and application-crash tickets become corroboration rather than noise.
