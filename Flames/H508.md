false_positive_notes: |
  `%APPDATA%\Microsoft\SystemCertificates` is a real Windows directory and software writes to it legitimately, which is the entire point of the choice. The discriminators are the filename and the subdirectory - a `Cache\logs.dat` that grows steadily while a user types, written by a process that is not a Microsoft component, is the finding. Reconcile the writing process first; a path match alone is not evidence.

  `logs.dat` is a generic filename used by plenty of real software elsewhere on the filesystem, so search it only in combination with this path. Several existing HEARTH hunts reference a `logs.dat` belonging to unrelated tooling, which is a reminder that the name travels.

  `log.lock` is a better indicator than it looks, because it is a zero-content control file in a directory where lock files are not conventional, but it is still a short generic name. Check content and size - this one exists to be present or absent, not to hold data.

  Low-level keyboard and mouse hooks are used legitimately by accessibility software, input-method editors, screen readers, remote-support agents, macro tools and some enterprise DLP products. Hook installation on its own is not actionable on a typical estate; hook installation by a process with no user interface, running from a system directory, is.

  The named object is the strongest discriminator here and also the one most estates cannot query. `OneDriveStandaloneUpdater` is a genuine Windows scheduled task name, chosen so the string reads as legitimate if anyone greps for it, but the real OneDrive updater does not create an object whose name is prefixed with `keylogger###`. Where object names are not logged, this leg becomes a live-response check rather than a hunt.

  The 32-byte marker and the hard-coded masking key are byte sequences, not strings, so they will not appear in text-based searches. They are inputs for a YARA scan or a forensic parse of a recovered file, not for log queries.

  Absence of `log.lock` does not mean the keylogger is absent - it means it is not currently enabled. The plug-in and the hooks can be resident with logging switched off, which is precisely why the operator built a gate file.
notes: |
  Leg one, the gate file and the log file (DeviceFileEvents or Sysmon 11) - Core filter: creation of either named artefact under any user profile.

      DeviceFileEvents
      | where Timestamp > ago(30d)
      | where (FileName =~ "log.lock" and FolderPath has @"\AppData\Roaming")
           or (FileName =~ "logs.dat" and FolderPath has @"\Microsoft\SystemCertificates\Cache")
      | project Timestamp, DeviceName, ActionType, FolderPath, FileName, FileSize,
                InitiatingProcessFileName, InitiatingProcessFolderPath,
                InitiatingProcessParentFileName, InitiatingProcessCommandLine
      | order by Timestamp desc

  Thirty days is the whole Defender advanced hunting retention. `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, so this leg sees the file appear and grow and will never see the backdoor checking for it - which is fine, because the check is the behaviour and the file is the evidence. Red flags, heaviest first - the writing process runs from `C:\Windows\System32` or `C:\ProgramData`; it is one of the four signed sideload hosts the report names, javaw.exe, start.exe, pythonw.exe or zoomit.exe; `log.lock` is created and later deleted, which is the operator toggling capture; `logs.dat` grows in increments through a working day.

  Leg two, the sweep for hosts without file history (live response or inventory) - Two file paths per user profile, checked directly. The check is cheap enough to run estate-wide:

      Get-ChildItem 'C:\Users' -Directory | ForEach-Object {
        $lock = Join-Path $_.FullName 'AppData\Roaming\log.lock'
        $log  = Join-Path $_.FullName 'AppData\Roaming\Microsoft\SystemCertificates\Cache\logs.dat'
        foreach ($p in @($lock, $log)) {
          if (Test-Path $p) {
            $f = Get-Item $p
            [pscustomobject]@{ User=$_.Name; Path=$p; Length=$f.Length; Modified=$f.LastWriteTime }
          }
        }
      }

  A `logs.dat` whose last-write time tracks the user's working hours is a capture in progress.

  Leg three, the named object (EDR object telemetry, or live inspection) - Core filter: any kernel object whose name contains `OneDriveStandaloneUpdater` but is not created by the genuine OneDrive updater, and specifically any object name containing the literal `keylogger###`. The report gives the form as `keylogger###Global\OneDriveStandaloneUpdater{%X-%X}`, where the braces hold two hex values. Where object creation is not logged, enumerate the object namespace on a suspect host with Sysinternals WinObj or an equivalent and look under `\BaseNamedObjects`. The same `###` delimiter convention runs through the whole plug-in suite - the process lister emits records prefixed `bof-process###`, the screenshot plug-in prefixes its Base64 JPEG with `bof-screenshot###`, and the keylogger prints `bof-keylogger###` status strings - so `bof-` plus `###` is a usable string for memory scanning across all three.

  Leg four, the hooks and the pipe (Sysmon 7, Sysmon 17) - The plug-in sets low-level keyboard and mouse hooks, which requires a module in the hooking process; an image load from a non-standard path into a process with no window is the correlating signal. Status output does not go to a console in practice - the plug-ins write into the named pipe `\\.\pipe\p<backdoor PID in decimal>` that GraphDoor creates on start, so a Sysmon 17 event for a pipe named `p` followed by the creating process's own decimal PID is the structural tell, and H507 covers it in context.

  Reading a recovered file, for the forensic case - the layout is masked key, then a one-byte checksum equal to the sum of those key bytes reduced to one byte, then a fixed 32-byte marker, then XOR-encrypted records. Recovering the session key means XORing the stored key against the hard-coded 32-byte mask the report publishes. Each record carries the foreground window title, a UTC timestamp formatted year-month-day hour:minute:second, the virtual key code as an unsigned long, and mouse events as a three-letter code plus x and y coordinates - `MLD` and `MLU` for left button down and up, `MRD` and `MRU` for right, `MMD` and `MMU` for middle, and `MWH` for wheel scroll. The window title is the part that matters for scoping impact, because it tells you which application each captured keystroke belonged to.

  Scope note: H128 is the closest existing hunt by technique - credential API hooking with a `logs.dat` artefact belonging to different tooling - and the distinction is that this hunt keys on an operator-controlled gate file, a masquerading path inside the per-user certificate store, and a named event object impersonating the OneDrive updater, none of which appear in H128. H125, H126 and H127 reference the same generic filename for unrelated malware families and are not the same behaviour. The pivots from any hit here are H505 for the loader trio that delivered the plug-in, H507 for the Graph channel that fetched it conditional on `log.lock` existing, and H503 for the GitHub variant where keylogger tasking and output travel in files with the `kmap` extension.

# H508

The keylogger in Operation ShadowCloud is not the most sophisticated part of the toolkit, and that is what makes it worth hunting. It is three small decisions, each of which leaves something a defender can look for.

The first is a gate. The backdoor checks for a file called `log.lock` in the user's Roaming application data directory, and only starts capturing if it is there. The GraphDoor variant goes further and will not even download the keylogger plug-in unless the file exists. Commands named `autoStartUp`, `stopAutoStartUp` and `autoStartUp_status` create it, delete it and report on it — so the operator's on/off switch for keystroke capture is a zero-byte file.

The second is the hiding place. Keystrokes land in `%APPDATA%\Microsoft\SystemCertificates\Cache\logs.dat`, inside the per-user certificate store, where a slowly growing opaque binary file reads as cached certificate data. The contents are XOR-encrypted with a random per-session key, and that key is itself masked with a hard-coded one and written into the file ahead of a fixed 32-byte session marker.

The third is a name. The plug-in creates a kernel object called `keylogger###Global\OneDriveStandaloneUpdater{%X-%X}` and stops logging when it is signalled. `OneDriveStandaloneUpdater` is a real Windows scheduled task; borrowing the name means a casual string search finds something plausible. The `keylogger###` prefix in front of it means a careful one does not.

## Why

- The gate file inverts the usual problem. Instead of hunting a running keylogger, you hunt an operator's switch — and because the file must exist on disk for capture to happen at all, its presence is a direct statement that keystroke collection is enabled right now on that host, for that user.
- The hiding place is a specific path, not a pattern. `Cache\logs.dat` under `Microsoft\SystemCertificates` is two string comparisons away from a finding in any estate with file telemetry, and the directory is obscure enough that almost nobody has baselined what belongs in it.
- Keystroke capture changes the scope of every other finding on the host. Window titles are stored alongside the keys, so a recovered file says which applications were typed into — which is the difference between assuming credentials were taken and knowing which ones.
- The plug-in's own strings give memory scanning a handle. `bof-keylogger###`, `bof-process###` and `bof-screenshot###` are the status prefixes for three plug-ins in the same suite, so one substring finds all of them in process memory on a suspect host.
- Masquerading as the OneDrive updater is a deliberate bet that nobody checks object names. It is a cheap bet to call, and calling it once gives the estate a reusable check — the real updater does not create objects with a `keylogger###` prefix.
