false_positive_notes: |
  Writes to a distribution bucket are the normal output of a release pipeline, so the hunt rests on which identity wrote, from where, and whether it had ever written before.
  - Deployment pipelines overwrite production objects constantly, including manifests and landing pages. Those writes come from a CI role or an OIDC-federated session, from known addresses, in a burst that matches a release record. Allowlist by role and by the presence of a corresponding build, not by bucket.
  - Content and marketing tooling legitimately replaces HTML and assets, sometimes from a vendor's address space. Enumerate those integrations once and record which prefixes each may write to; an integration writing outside its prefix is the finding.
  - Long-lived access keys genuinely used by applications will show application-shaped activity, which is the baseline this hunt compares against. The signal is a change in that shape - a read-only key starting to write, or a key adding permission-discovery calls it has never made.
  - Permission-probing calls occur legitimately during infrastructure-as-code runs and during security assessments. Correlate with change records and with any authorised testing window before escalating; an assessment will usually be attributable to a named role.
  - Bucket enumeration at scale also happens during migrations, inventory jobs and backup runs. The discriminator is the pairing with a write to an existing public object from the same key in the same session.
notes: |
  Source reporting is Check Point Research's November 5, 2026 analysis of ARTEX cybercrime campaigns, which recovered operator-console artefacts from misconfigured agentic hacking platforms. The relevant case is their third attack within the crypto-draining campaign, where agents searching for a specific wallet holder found a different problem instead: Check Point reports that "An unauthenticated web API leaked AWS S3 credentials, which then enabled write access to a bucket holding the iOS apps and landing pages for one crypto service."
  The agent's own reasoning, quoted by Check Point, is a precise statement of what the write accomplished - the bucket "has full overwrite permission, serves text/html directly to the public internet, and contains 714 iOS enterprise-signed IPA landing pages", and "the newest production landing page from 2026-10-15 is still being distributed and is the install entry point real users click". The planned actions were to rewrite the package download URL in the install manifest so it pointed at a controlled application, or to rewrite the landing page's redirect target, or to replace the production landing page with a collection page. Check Point reports the compromise was executed and verified, and that "the original manifest file was restored later by the bucket owners" - so in this instance the restore is part of the evidence rather than part of the remediation.
  Stage one, the credential leak - Core filter: application responses that contain credential material. This is a code and traffic problem rather than a cloud-log problem, so hunt it from both sides. On the application side, grep responses and source for access-key identifier prefixes and for configuration objects returned by unauthenticated routes. On the cloud side, the tell is a key whose first use comes from outside the application's own network. Triage values are the endpoint path, whether authentication is required, the response content type, the key identifier, and the identity the key belongs to. Strong red flags are a configuration or bootstrap endpoint returning a whole settings object, and an access key that appears in a client-side bundle or a mobile application package rather than only in server configuration.
  Stage two, permission discovery - Core filter: CloudTrail management events where one identity makes the small, characteristic set of calls an operator uses to learn what a found key can do. Sample query over a CloudTrail table:
  ```kql
  let lookback = 30d;
  let probeEvents = dynamic(["GetCallerIdentity", "ListBuckets", "GetBucketAcl",
                             "GetBucketPolicy", "GetPublicAccessBlock",
                             "GetBucketVersioning", "ListAttachedUserPolicies",
                             "SimulatePrincipalPolicy"]);
  CloudTrail
  | where TimeGenerated > ago(lookback)
  | where EventName in (probeEvents)
  | extend KeyId = tostring(UserIdentity.accessKeyId)
  | summarize Probes = make_set(EventName, 20), ProbeCount = dcount(EventName),
              SourceIPs = make_set(SourceIpAddress, 10), Agents = make_set(UserAgent, 5),
              FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated)
      by KeyId, Window = bin(TimeGenerated, 1h)
  | where ProbeCount >= 3
  | order by FirstSeen desc
  ```
  Field names depend on how CloudTrail is normalised in your platform, so confirm the access-key and user-identity paths in your own schema before relying on them. Triage values are the key identifier, the source address and its autonomous system, the user agent, and the set of probe calls. Strong red flags are three or more distinct permission-discovery calls by one key inside an hour, and a user agent string that names a generic SDK or command-line client where the application normally presents its own.
  Stage three, enumeration of the distribution bucket - Core filter: `ListObjects` or `ListObjectsV2` at high volume by a key with no enumeration history, followed by `GetObject` on manifest and HTML objects. The reported bucket held 714 landing pages, which is the scale at which an operator stops browsing and starts cataloguing, so a single key producing a complete object listing of a public bucket is both a discovery event and a strong lead. Triage values are the bucket name, the request count, the key identifier, the source address, and the prefixes enumerated. Correlation: compare against the same key's previous thirty days - an application key that has only ever read a handful of fixed object paths and suddenly lists everything has changed behaviour, which is the whole signal.
  Stage four, the overwrite - Core filter: `PutObject`, `CopyObject` or `DeleteObject` against an object key that already existed, where the writing identity is not the deployment role. This requires S3 data events to be enabled on the bucket, which is the single most common reason this hunt cannot run - management events alone will not show it. Sample query for writes to existing public content by a non-pipeline identity:
  ```kql
  let lookback = 30d;
  let pipelineRoles = dynamic(["ci-deploy-role", "release-publisher"]);
  CloudTrail
  | where TimeGenerated > ago(lookback)
  | where EventSource == "s3.amazonaws.com"
  | where EventName in ("PutObject", "CopyObject", "DeleteObject", "PutObjectAcl")
  | extend KeyId = tostring(UserIdentity.accessKeyId),
           Principal = tostring(UserIdentity.arn),
           Bucket = tostring(RequestParameters.bucketName),
           ObjectKey = tostring(RequestParameters.key)
  | where not(Principal has_any (pipelineRoles))
  | where ObjectKey endswith ".plist" or ObjectKey endswith ".html"
        or ObjectKey endswith ".ipa" or ObjectKey endswith ".apk"
        or ObjectKey endswith ".js" or ObjectKey endswith ".json"
  | project TimeGenerated, KeyId, Principal, Bucket, ObjectKey, SourceIpAddress, UserAgent
  | order by TimeGenerated desc
  ```
  Fill `pipelineRoles` from your own deployment identities; two names are a worked example. Triage values are the object key, the content type set on the write, the writing principal, the source address, and whether a prior version of the same object exists. Strong red flags are a write that sets a content type of text/html on an object serving the public internet, a write to an install manifest or a package download path, and a write to an object whose previous version was authored by the pipeline.
  Stage five, the restore - Core filter: object versioning history showing an attacker write followed by a restore of the previous content, with no incident record in between. In the reported case the owners restored the manifest without, on the evidence available, treating it as an intrusion. Correlation: a silent restore is evidence that the overwrite was noticed by someone who read it as corruption rather than compromise, which makes the version history a retrospective hunting surface in its own right. Pivot: for every public distribution bucket, list object versions and look for any version authored by a principal that is not the pipeline, at any point in the retention period.
  What the end users received - Core filter: CloudFront or S3 access logs during the window between the overwrite and the restore, counting requests for the affected objects. This converts a cloud-log finding into an impact statement - how many install attempts were served attacker content - and it is the number that determines whether the event is a configuration incident or a user-notification one.

# H462

Check Point Research found ten ARTEX instances misconfigured badly enough to expose their own databases, which gave an unusual view of agentic hacking from the operator's side: the prompts, the models, and every step the agents took.

One operator ran a crypto-draining campaign that mostly failed. Across 292 campaign objectives, 230 findings and more than 400,000 agent messages, the wallet ended with a zero balance. But along the way the agents found something that had nothing to do with draining wallets.

An unauthenticated web API returned AWS S3 credentials. Those credentials had write access to a bucket that served the iOS applications and install landing pages for a crypto service - 714 enterprise-signed landing pages, serving HTML directly to the public internet, with full overwrite permission. The agent worked out what that meant and wrote it down plainly: the newest production landing page was still being distributed and was the install entry point real users clicked. Rewriting the install manifest's download URL would hand every new installer an attacker-controlled application.

It executed the overwrite and verified the chain. The owners restored the original manifest later. Nothing in the available evidence suggests they recognised it as an intrusion.

That is the hunt. Not the agent, which is interchangeable, but the sequence: a credential leaked by an application, used from somewhere the application does not run, probing its own permissions, cataloguing a public bucket, and overwriting live content that users are about to download.

## Why

- The whole chain runs on legitimate API calls with a valid credential, so nothing in it is malformed, exploitative or signature-bearing. The only thing that is wrong is the pattern - who used the key, from where, and that a read-only application identity started writing - which makes behaviour the only available detection surface.
- Distribution buckets are a supply-chain position dressed up as storage. Overwriting an install manifest reaches every future installer without touching a single endpoint, and the blast radius is the product's user base rather than the cloud account. That asymmetry justifies data-event logging on public buckets even where it is otherwise considered expensive.
- The restore shows how this gets missed. Someone noticed a manifest was wrong and put the old one back, which is the correct engineering response and the wrong security response. A version history that nobody reads is where this class of event goes to be forgotten, which also makes it a cheap retrospective hunt.
- Leaked credentials now get used at machine speed and at machine breadth. Check Point's assessment of what makes agentic tooling dangerous applies directly - "it is not necessarily the complexity of attacks, but the breadth and perseverance at which LLMs can audit a scope and test every endpoint, front end bundle and site, non-stop until an objective is achieved". An endpoint that leaks a key is now found in hours rather than eventually.
- Every stage has a concrete prevention lever next to it. Short-lived federated credentials instead of long-lived keys, public-access blocks and bucket policies that deny overwrite to anything but the pipeline, object versioning with alerting on non-pipeline versions, and a review of which unauthenticated endpoints return configuration. The hunt measures whether those exist.
