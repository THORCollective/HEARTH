false_positive_notes: |
  Shell aliases are the single most customised thing on a Linux host, so the existence of aliases in
  `.bashrc` is meaningless on its own. Developers alias `ls`, `grep`, `git` and dozens more, and plenty
  of legitimate setups wrap privileged commands: `alias sudo='sudo '` is a widely copied idiom that
  makes aliases expand after sudo, `sudo -E` wrappers appear in CI images, and tools like `please`,
  `doas` and corporate privilege-management agents legitimately interpose on sudo. The discriminator is
  not the alias but what it does: a benign sudo alias does not contain a `read` of user input, does not
  write to a file, and does not reference a path outside the user's own tooling. Specifically look for a
  `read` with the terminal echo disabled (`read -s`, or `stty -echo`), a redirection to a file, and a
  trailing call to the real binary. All three together have no benign form. Expect genuine noise from
  dotfile management - chezmoi, yadm, stow and homeshick rewrite these files legitimately and often, and
  shared or templated images may distribute an identical `.bashrc` to every account, so a diff against

# H400

Every Linux user has been trained to do exactly the wrong thing: when something says `[sudo] password for you:`, type your password.

Nothing stops a shell alias from saying that.

The CL-UNK-1211 operators replaced `.bashrc` with a copy that aliased `sudo`. Unit 42 lists what the alias did, in order: it "Displays a prompt for the user to insert their password (mimicking the standard system authentication prompt)", it "Captures the inserted password", and it "Writes it to the attackers' log file". Then — and this is the part that makes it work — the harvested password "is then passed to the legitimate sudo command for execution, leaving the victim unaware of the underlying interception."

So the command succeeds. The user gets the result they wanted. Nothing fails, nothing prompts twice, nothing looks wrong. The only difference is that the password is now also in a file.

Consider what this *doesn't* do. It doesn't open a credential store. It doesn't read process memory. It doesn't attach a debugger to anything. It doesn't call a single API an endpoint agent associates with credential theft. It edits a text file, and later reads a text file. And it waits — collecting on the user's own schedule, the next time they need to do something administrative.

Then there is the filename, which is the detail worth carrying away from this report. The captured passwords went to `Solarwinds.StatusLog.txt`. Unit 42 notes the name was chosen "to mimic legitimate SolarWinds activity in the environment", and is explicit that no SolarWinds compromise was involved — they had "no evidence of SolarWinds systems and infrastructure being compromised during this operation." The name was pure cover.

That name defeats two things at once. Anyone grepping for `creds.txt` or `passwords.log` walks straight past it. And an analyst who *does* trip over it has an explanation ready to hand, which is worse than finding nothing, because it closes the question.

The generalisable version: a plain-text log file attributed to a monitoring product, on a host where that product is not installed, is a finding. Your asset inventory answers that.

For the alias itself, the trick is knowing what to ignore. Aliases are the most customised thing on any Linux box, and wrapping sudo is not inherently suspicious — `alias sudo='sudo '` is a widely copied idiom. What has no benign form is the combination: a `read` with terminal echo turned off, a redirection to a file, and a handoff to the real binary. Benign aliases do not collect input. They certainly do not write it down.

## Why

- **The prompt is indistinguishable because the user is the authentication surface.** No technical control prevents a shell from printing the same string sudo prints, and the user has no way to tell which process asked.
- **It yields the credential that matters most.** A password that works with sudo on the host where it was typed is immediately useful, and unlike a hash it needs no cracking.
- **Nothing about it looks like credential access to an endpoint agent.** A dotfile write and a later file read generate no LSASS-equivalent signal, no debugger attach, no memory read — which is why the detection has to be the file's content.
- **It is self-timing and patient.** The capture happens when the user next escalates privilege, so the attacker spends nothing waiting and the artefact sits dormant and unremarkable in between.
- **Passing the password through is what buys the silence.** Because the real sudo still runs, there is no failed command, no retry and no user-reported oddity to start an investigation.
- **The decoy filename is an anti-triage measure, not just anti-grep.** It survives discovery by supplying a plausible answer, which is why the asset-inventory question — is this product even installed here? — is the one that breaks it.
- **The discriminating content is narrow and enumerable.** Echo-suppressed input plus file redirection plus a call to the wrapped binary is a shape with no legitimate counterpart, so the query can be specific rather than heuristic.
- **The same operators cleaned up afterwards.** Unit 42 describes attempts to delete authentication logs and command history, so the startup file's current state is more reliable evidence than the history of how it got there.
