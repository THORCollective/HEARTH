false_positive_notes: |
  Almost everything this hunt returns is explainable; the work is separating the explainable from the gap.
  - Token lifetime is the expected behaviour, not a defect. A bearer token issued minutes before an account was disabled is supposed to keep working until it expires. A success inside that documented window is a correct observation about your containment timing, not evidence of a second intrusion. Record the expected window per resource first, then rank findings by how far past it they fall.
  - Service-account offboarding produces this pattern constantly. Decommissioning an application generates a credential removal followed by residual traffic from caches, retries and queued jobs for minutes or hours. Scope the hunt to revocations that were performed as a response action rather than as routine lifecycle work; your ticketing system usually knows the difference.
  - Replication and propagation delay is real and documented by the providers. Multi-region control planes acknowledge a change before it is effective everywhere. Treat successes that stop by themselves inside a few minutes as propagation and successes that continue as a gap.
  - Partial revocation is the common case and is easy to misread as an attacker. Deactivating one access key leaves the other, revoking role sessions leaves the long-term keys that can request new ones, and deleting a client secret leaves a certificate credential. These are findings about the response procedure. They belong in the result, labelled as such.
  - An identity with the same display name but a different object ID is not the same identity. Join on the immutable object ID or ARN, never on the name, or a recreated service account will read as a revoked one that came back.
notes: |
  Source reporting is Elastic Security Labs' November 13, 2026 review of five agentic offensive frameworks, which devotes a section to why containment lags the attack. Elastic writes that "AWS and Google each document a propagation delay for access changes, and in Entra ID an access token issued before a user or service principal is deleted or disabled generally stays valid until it expires, typically 60 to 90 minutes, unless the resource and client support continuous access evaluation," and that "an acknowledged revocation may not stop the next request, and an agent operating at machine speed can act within that gap." Its defensive guidance is the hunt in one line: "Combine any block on a source address with revoking the identity's sessions and tokens, because these frameworks return from new addresses, then confirm that the next request fails."
  No existing HEARTH coverage for this behaviour - Grepped the corpus for post-revocation access, revocation windows and continuous access evaluation and found no hunt on any of them. The closest adjacent hunts are [[H445]], which covers one source address holding client secrets for several registered applications, and [[H448]], which covers cloud service accounts created, keyed, used and deleted inside hours. Both are about credential lifecycle on the attacker's side; neither looks at what happens on the defender's side after a revocation is issued. [[B055]] baselines Azure service principal control-plane behaviour and is the natural pairing, because knowing the normal caller set is what makes a post-revocation success legible.
  Core filter 1, the join - The whole hunt. Build a table of revocation moments: for each principal, the timestamp of the Entra audit event that disabled or deleted it or revoked its sessions, or the CloudTrail event that deactivated or deleted its key. Then select every authenticated action by that same principal object ID or ARN with a timestamp after that moment and an outcome of success. Triage values are the elapsed time since revocation, the resource touched, the source address, the application or role used, and which specific credential authenticated the call.
  Core filter 2, separating a stale token from a live credential - A stale bearer token cannot authenticate afresh; it can only be presented. In Entra ID, non-interactive sign-ins and Graph activity logs will show resource access with no corresponding new interactive sign-in, and the token's issue time predates the cutoff. A new sign-in or a new sts:AssumeRole after the cutoff is a different and worse finding: something still holds a credential that can mint access. Elastic notes the AWS case directly - role-session revocation "leaves IAM users' long-term keys alone and does not block sessions requested after its cutoff, so pair it with removing whatever can still assume the role."
  Core filter 3, which resources were never covered - Microsoft documents continuous access evaluation for Exchange, Teams and SharePoint, and for service principals only Microsoft Graph. Everything else falls back to token expiry. Enumerate the resources that appeared in post-revocation successes and sort them into covered and not covered; the not-covered list is the set of places where the next revocation will also fail to take effect, which is the durable output of this hunt.
  Sample KQL for the Entra side, over 30 days of Defender XDR and Entra data, with the join window bounded so a revocation in one week cannot pair with a sign-in in another:
  ```kusto
  let lookback = 30d;
  let revocations =
      AuditLogs
      | where TimeGenerated > ago(lookback)
      | where OperationName in ("Disable account", "Delete user", "Delete service principal",
                                "Revoke sessions", "Update service principal")
      | mv-expand TargetResources
      | extend principal_id = tostring(TargetResources.id)
      | project revoke_time = TimeGenerated, principal_id, OperationName;
  let successes =
      AADNonInteractiveUserSignInLogs
      | where TimeGenerated > ago(lookback)
      | where ResultType == 0
      | project signin_time = TimeGenerated, principal_id = UserId,
                ResourceDisplayName, AppDisplayName, IPAddress;
  revocations
  | join kind=inner successes on principal_id
  | where signin_time between (revoke_time .. revoke_time + 6h)
  | extend minutes_after_revocation = datetime_diff('minute', signin_time, revoke_time)
  | project revoke_time, minutes_after_revocation, OperationName, principal_id,
            ResourceDisplayName, AppDisplayName, IPAddress
  | sort by minutes_after_revocation desc
  ```
  The six-hour bound is deliberately wider than the 60 to 90 minutes Elastic cites, so that a success well past the expected window is visible in the same result as one inside it and the two can be told apart by the elapsed-minutes column rather than by a filter. Run the equivalent against Graph activity logs as well, because an app-only identity can reach a resource without producing a sign-in row.
  Expected, not observed by Elastic - A specific number of minutes at which a post-revocation success stops being propagation and becomes a gap. Elastic reports the documented token lifetimes and the existence of the window but does not publish a threshold, and the right figure depends on which resources an environment uses and whether continuous access evaluation applies to them.
  Scope - Any environment where cloud credential revocation is part of the incident-response runbook. The hunt is worth running retrospectively against past incidents, because it answers a question most post-incident reviews record as closed without evidence: whether the credential actually stopped working when the ticket said it did.

# H475

The revocation goes in. The portal says the account is disabled. The incident channel gets a green tick.

The token issued four minutes earlier is still in memory on a server in another country, and it has another hour to live.

Elastic's write-up of the five agentic frameworks makes this concrete: in Entra ID, a token minted before a user or service principal is disabled generally stays valid until it expires — typically sixty to ninety minutes — unless both the resource and the client support continuous access evaluation, which covers Exchange, Teams and SharePoint, and for service principals only Microsoft Graph. AWS and Google both document propagation delay. AWS role-session revocation leaves an IAM user's long-term keys untouched and does not block sessions requested after its cutoff.

None of that is a vulnerability. It is documented, intended behaviour. It only becomes a problem when the thing on the other end can issue a hundred requests in the time it takes a responder to refresh a page.

So this hunt is not really about the attacker. It is a join between two things your own logs already hold: the moment you revoked something, and every successful call that identity made afterwards. Each row is either a token living out its documented life, a credential you forgot to remove, or a resource that was never covered by the controls you thought you had.

Most teams have never run that join. The answer is usually not zero.

## Why

- **Containment is asserted far more often than it is verified.** The revocation event is logged, the response is closed, and the question of whether the next request failed is almost never asked. This hunt asks it with data the environment already collects, which makes it cheap to run and awkward to argue with.
- **Machine-speed operation turns a documented delay into an exploitable one.** A sixty-minute token window is an administrative footnote when the adversary is a person reading a console. It is a working session when the adversary is a loop issuing requests seconds apart, which is exactly what these frameworks do.
- **Partial revocation is the normal failure, and it is invisible without this check.** An identity usually has more than one credential — two access keys, a secret and a certificate, a refresh token and a session. Removing one and believing the identity is contained is a procedural defect that produces no error and no alert, and only shows up as a success that should not exist.
- **The output is a durable list, not a single finding.** The resources that appeared in post-revocation successes are the resources where your next revocation will also be slow. That list drives Conditional Access and token-lifetime work, so the hunt improves containment even in the common case where nothing malicious is found.
- **It reframes the block-the-address reflex.** These frameworks come back from new addresses by design. Blocking the source and leaving the credential alive is the worst of both outcomes: the activity disappears from the place you were watching and continues from somewhere you are not.
