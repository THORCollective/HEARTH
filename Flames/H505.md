false_positive_notes: |
  The individual files are all legitimate in their proper homes. `winmm.dll`, `version.dll`, `msvcp140.dll`, `vcruntime140.dll`, `snmpapi.dll` and `MSIMG32.dll` are genuine Windows or Visual C++ components and exist under System32 by design, so a filename-only search on those returns noise on every host in the estate. The finding is the combination - a vendor executable that does not belong to Windows, sitting in a Windows system directory, beside one of those DLL names and a `config.ini`. Query the directory, not the file.

  `config.ini` is a generic name and real software uses it constantly. On its own it is close to worthless as an indicator; co-located with a non-Microsoft signed executable in System32 it is close to decisive. A quick triage on any candidate - a real `config.ini` is readable text, and this one is a Base64 blob over RC4-plus-XOR or straight XOR, so a high-entropy `config.ini` that no human could have authored is the tell.

  Software that legitimately ships a portable copy of a Python or Java runtime into an application directory produces the same co-location shape outside System32, which is why the location filter does most of the work. Under `C:\Program Files` and `C:\ProgramData` the pattern needs the signature and parentage checks to be meaningful, and the report has observations in both - a PDF24 directory and a `%ProgramData%\excint` directory.

  The 19-name DLL list is this campaign's current rotation, not a universal sideload list. The operator can add names in the next build, and other actors use different ones. Treat a match on the list as a high-confidence confirmation and keep the structural query - non-Microsoft signed executable plus any DLL plus an opaque data file in a system directory - as the primary hunt.

  Sysinternals tools are legitimately present on administrator workstations and jump hosts. `zoomit.exe` registered as a Windows service is not legitimate anywhere - it is an interactive screen magnifier - so the service angle carries far more weight than the presence of the binary.
notes: |
  Leg one, the co-location query (DeviceFileEvents or Sysmon 11) - Core filter: directories that received both a DLL and a `config.ini` within a short window, restricted to paths where third-party software has no business living. The window bound matters - correlating on folder path alone over a long lookback will pair unrelated installs.

      let loaderNames = dynamic(["python311.dll","sbiedll.dll","jli.dll","libcef.dll","krita.dll",
          "nvdahelperremote.dll","appvisvsubsystems64.dll","winmm.dll","corefoundation.dll",
          "vcruntime140.dll","msvcp140.dll","snmpapi.dll","msimg32.dll","version.dll","sqlite.dll",
          "msedge_elf.dll","python39.dll","python38.dll","python33.dll"]);
      let drops =
          DeviceFileEvents
          | where Timestamp > ago(30d)
          | where ActionType in ("FileCreated", "FileModified")
          | where FolderPath has @"\Windows\System32" or FolderPath has @"\ProgramData"
          | project Timestamp, DeviceId, DeviceName, FolderPath, FileName = tolower(FileName),
                    SHA256, InitiatingProcessFileName, InitiatingProcessCommandLine;
      let dlls  = drops | where FileName in (loaderNames);
      let inis  = drops | where FileName == "config.ini";
      dlls
      | join kind=inner (inis | project IniTime = Timestamp, DeviceId, FolderPath, IniWriter = InitiatingProcessFileName)
          on DeviceId, FolderPath
      | where IniTime between (Timestamp - 1h .. Timestamp + 1h)
      | project Timestamp, DeviceName, FolderPath, FileName, SHA256, InitiatingProcessFileName,
                InitiatingProcessCommandLine, IniTime, IniWriter

  `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, which is why this leg keys on the drop and not on the loader reading its payload. Every `let` above is used; the time bound on the join is what keeps it honest.

  Leg two, the structural sweep (file inventory, no history required) - For hosts with no retained file telemetry, sweep directly. The question is which directories under `C:\Windows\System32`, `C:\ProgramData` and `C:\Program Files` contain a non-Microsoft-signed `.exe` alongside a `.dll` and a small opaque data file. PowerShell will answer it on a single host, and the output is short enough to read:

      Get-ChildItem 'C:\Windows\System32','C:\ProgramData' -Recurse -Include *.exe -ErrorAction SilentlyContinue |
        ForEach-Object {
          $sig = Get-AuthenticodeSignature $_.FullName
          if ($sig.Status -eq 'Valid' -and $sig.SignerCertificate.Subject -notmatch 'Microsoft') {
            $dir = $_.DirectoryName
            $ini = Get-ChildItem $dir -Filter 'config.ini' -ErrorAction SilentlyContinue
            if ($ini) { [pscustomobject]@{ Exe=$_.FullName; Signer=$sig.SignerCertificate.Subject; Ini=$ini.FullName } }
          }
        }

  Note what this finds and what it does not - a validly signed executable from a real vendor in the wrong directory. The report's four observed hosts are all genuinely signed, so signature validation is not the control here; location and company are.

  Leg three, execution and persistence (4688 or Sysmon 1, plus 7045) - Core filter: process creation where the image path is under `C:\Windows\System32` or `C:\ProgramData` and the process name is not a Windows component. Windows Security 4688 uses `New_Process_Name` and `Creator_Process_Name`, not Sysmon's `Image` and `ParentImage` - a query written against the wrong field names silently returns nothing. The report names `javaw.exe`, `start.exe`, `pythonw.exe` and `zoomit.exe` as observed hosts; the service route is the one to alert on, so check System 7045 for any service whose binary path points at a Sysinternals tool or a runtime binary, and specifically for `zoomit.exe`.

  Leg four, confirming the sideload at load time (Sysmon 7 or DeviceImageLoadEvents) - A module whose file path is a system directory but whose signer is not Microsoft, loaded by a process in that same directory. `DeviceImageLoadEvents` has no signature columns, so join `DeviceFileCertificateInfo` on SHA1 to get signer and trust state; Sysmon 7 carries `Signed`, `Signature` and `SignatureStatus` inline and needs no join. Red flags - an unsigned DLL beside a signed host, or a DLL signed by a vendor unrelated to the executable loading it.

  Two observed variants worth folding into the sweep. The FamousSparrow directory `%ProgramData%\excint\` used a renamed Avast component as the host and named the encrypted payload after the host executable rather than `config.ini`, so a payload file whose base name matches the neighbouring `.exe` is the same pattern under a different convention. The CopperTurtle case placed the staging under `C:\Program Files\PDF24\`, a real application directory, which is the harder variant - there the discriminator is a second executable in a legitimate product's folder that the product does not ship.

  What follows a hit - the trio is the delivery mechanism for GitDoor and GraphDoor. H503 covers GitDoor's GitHub control channel, H504 the Ably proxy channels, H507 GraphDoor's app-only Microsoft Graph channel, H508 the keylogger on disk, and H509 the self-relocation and parent-kill routine that moves this same trio and deletes the old copy.

  Scope note: H455 is the closest existing hunt and the distinction is location and composition. H455 keys on a correctly signed binary from an unrelated vendor planted under another product's component filename; this hunt keys on the three-file trio as a unit, inside Windows system directories, against a published 19-name loader list and a specific encrypted-payload convention. H361 covers a sideloaded `config.dll` carrying tunnel configuration, which is the same payload-beside-loader idea for a different toolkit. B038 and B052 are the baselines that make all three cheap - which signed applications load DLLs from user-writable paths, and where each trusted binary name legitimately runs from. Run B052 first if the estate has never answered the question for System32.

# H505

Every ShadowCloud infection Kaspersky examined started the same way on disk: three files in one directory. A legitimate executable with a valid signature, a DLL named so that the executable loads it without being told to, and an encrypted file called `config.ini` that holds the backdoor. The executable is the only thing that runs from disk; the backdoor never touches the filesystem in executable form.

What makes this a hunt rather than an indicator list is where the operator put it. Two of the observed instances went into `C:\windows\system32` — one as Sandboxie's `start.exe` with `sbiedll.dll`, the other under a fabricated `system32\dts\pc\apo4x` path with a Python binary and `python39.dll`. A third ran the Sysinternals screen magnifier `zoomit.exe` as a Windows service. System32 is a directory where almost nothing third-party belongs, which inverts the usual sideloading problem: instead of hunting for a bad DLL among millions of good ones, you hunt for a vendor executable that has no business being there at all.

The campaign also published its own target list. The `moveDir.ts` relocation plug-in, documented in part two, iterates a fixed list of nineteen loader DLL names when it copies the trio to a new path. That list is reproduced in the hypothesis, and it turns the DLL half of the query from a guess into an enumeration.

## Why

- Three files that mean nothing apart mean one thing together. A signed executable, a DLL and an opaque data file are each individually unremarkable; co-located in a Windows system directory they are a staging layout, and co-location is a query any estate with file telemetry can run today.
- The location does the filtering that signature checks cannot. All four observed host binaries are genuinely signed by real vendors, so validity proves nothing. What is anomalous is Sandboxie, OpenJDK, Python and Sysinternals living under System32 — which is a short, readable list on a healthy host.
- The loader name list came from the attacker's own tooling. `moveDir.ts` exists to relocate the trio and therefore has to know every name the trio might use, and the report publishes all nineteen. Hunting a published enumeration is cheaper than hunting a behaviour.
- `zoomit.exe` as a Windows service has no benign explanation. It is an interactive presentation tool. A 7045 event pointing at it is a finding on its own, with no further correlation needed.
- Finding the trio finds the backdoors before the channel opens. Everything else in this campaign — the GitHub dead drop, the Ably SOCKS5 proxy, the Graph uploads, the keylogger, Mimikatz and PetitPotam modules — is downstream of these three files being in place.
