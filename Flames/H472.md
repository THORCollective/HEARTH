title: "A scheduled watcher on a managed endpoint enumerates the installed remote-support clients, copies each one's libraries into its own build directory and compiles a replacement client with the C# compiler, rebuilding whenever the source or those libraries change"
hypothesis: >-
  A component that has to impersonate a specific installed client cannot ship as a binary, because it needs that client's own libraries and connection parameters to be accepted. So it ships as source and builds on the endpoint. A scheduled task starts a watcher that polls on a short interval, enumerates the remote-support client services, reads their executable paths and connection parameters, creates a per-client directory, copies libraries out of each client's installation, and invokes the framework C# compiler to produce an executable - rebuilding when the source or the client libraries change so the impersonation stays current through client upgrades. The resulting binary reuses the endpoint's own client connection details in place of the real client, so it is positioned to act on the support session rather than on the host. The observable chain is the C# compiler running on a workstation with its output directed into a staging directory, library files copied out of a remote-support client installation, a scheduled task that polls every few seconds, and a persistence value under the machine-wide Run key.

false_positive_notes: |
  The compiler is a legitimate part of Windows and runs for legitimate reasons, so the hunt has to key on where its output goes and what it was given to build.
  - The framework C# compiler is invoked by the operating system and by legitimate software. Script hosts, installers, PowerShell add-type calls, XML serialization and several Microsoft products compile at runtime routinely, so the compiler running is not the finding. The output path and the parent process are.
  - Developer workstations compile constantly and legitimately. Treat the developer population separately rather than suppressing the signal estate-wide, and expect the server and general-office populations to be where this check is actually cheap.
  - Management and deployment software copies vendor libraries between directories as part of normal operation, and so do upgrade routines for the remote-support client itself. Correlate library copies against the vendor update process and the deployment agent; the candidate population is a copy into a staging directory with no corresponding product operation.
  - Short-interval scheduled tasks exist legitimately. Monitoring agents, update checkers and some line-of-business software poll every few seconds. Enumerate the approved short-interval tasks once and treat the inventory as the allowlist, because the polling interval alone is not distinguishing.
  - Antivirus path exclusions are legitimately configured by policy and by vendor installers, including for management software whose file activity would otherwise be scanned. The signal is an exclusion written locally for a path that belongs to a staging or temporary directory, by a process that is not the policy agent, not the existence of exclusions.
  - A rebuild-on-change design means the artefacts recur, which cuts both ways. It gives multiple chances to see the behaviour, but it also means a single historical compile event may be the normal update cadence of something legitimate. Look for the combination - compile, library copy, scheduled task, Run value - rather than any one leg.
notes: |
  Source reporting is Microsoft Threat Intelligence November 13, 2026 analysis of SCKit, following ConnectWise reporting from November 11, 2026 of an active campaign against cloud-hosted ConnectWise ScreenConnect instances belonging to managed service providers. This hunt covers RelayTrap and the watcher that builds it. The companion hunt from the same report is [[H471]], which covers theft of the console authentication cookie from the same endpoints. The closest existing hunts are [[H337]], which covers compiling a miner on the victim to avoid shipping a known hash - the same evasion motive but a different build input and a different objective - and [[H306]] and [[B051]], which cover the remote-support platform as a delivery mechanism and the rogue-client baseline respectively. No existing hunt covers building a replacement client from the installed client own libraries.
  Why it compiles instead of shipping a binary - This is the detail that makes the hunt specific. The component has to present itself as the client for a particular installation, so it needs that installation libraries and its connection parameters. Microsoft reports that the watcher "enumerates ScreenConnect client services and reads their executable paths and connection parameters", and that "for each client, its build routine creates a directory under trapbins, copies libraries from that client installation, and uses the .NET C# compiler to build RelayTrap.exe". Microsoft adds that "it checks for changes to the source or client libraries before rebuilding", which means the build is maintained rather than one-off and survives a client upgrade. The consequence for detection is that a file hash is close to useless - Microsoft says so directly, noting that "the watcher compiles RelayTrap against local client libraries, and embedded configuration changes script hashes" and advising defenders to "use file and process behavior to investigate other builds".
  What it is positioned to do - Microsoft reports RelayTrap "is designed to reuse the customer endpoint’s ScreenConnect connection details in place of its normal client", and that "when a technician connects with a vulnerable host client, RelayTrap attempts to deliver the staged batch launcher through that session". So the direction of travel is unusual: this is a managed endpoint aiming at the person who supports it. Microsoft notes that ConnectWise "states that the fix for CVE-2026-84869 blocks the toolkit’s attempted endpoint-to-technician spread", that the fix was released on September 8, 2026, and importantly that technician clients update separately from the console - "a cloud-console update does not automatically update those clients", so client version inventory is a real control here and not a formality. Microsoft also notes the diagram for this path "describes the toolkit’s propagation design, not a confirmed sequence of infections", so the endpoint-to-technician step is a designed capability rather than an observed outcome, and should be described that way in any finding.
  Core filter 1, the compiler with a staging output path - The highest-value single check. Hunt for the framework C# compiler executing on a non-developer endpoint where the output path on the command line is a user or machine temporary directory, a program-data subdirectory, or any staging path rather than a build tree. Microsoft reports the scripts are placed under `C:\ProgramData\RelayTrap` and the build directories under a `trapbins` subdirectory. Sample Defender XDR query:
  ```kql
  let lookback = 30d;
  let stagingHints = dynamic([@"\ProgramData\", @"\AppData\Local\Temp\", @"\Windows\Temp\", "trapbins"]);
  DeviceProcessEvents
  | where Timestamp > ago(lookback)
  | where FileName in~ ("csc.exe", "vbc.exe")
  | where ProcessCommandLine has_any (stagingHints)
  | project Timestamp, DeviceId, DeviceName, AccountName, FileName, FolderPath,
            ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessCommandLine,
            InitiatingProcessParentFileName
  | order by Timestamp desc
  ```
  Keep the lookback at `ago(30d)` or less, because Defender XDR advanced hunting retains 30 days and silently truncates a longer window. Triage values are the output path, the source files named on the command line, the parent process, and the account. A compiler invoked by a script host, with output into a program-data or temporary path, on a machine that is not a developer workstation, is the row to work.
  Core filter 2, the library copy out of the client installation - The input side of the same build, and the leg that ties it to the platform. Hunt for file creates in a staging directory whose source is a remote-support client installation directory, and in particular for managed assemblies belonging to the vendor appearing outside their installed location. Microsoft reports the source file for the component is `RelayTrap.cs` with SHA-256 `3c7a98f0fdb6235b8076319c74dc1085f7b349b6d750416dd0cadb07d7972ec4`, and the watcher as `TrapWatch.ps1` with SHA-256 `d2ed7a7bf4f8ac9c7969e9b3a07ebd4dda0d858f372c876ac0a041611698de9a`. Those hashes are worth a sweep but they are the artefacts the report says will vary, so they are a starting point rather than the hunt.
  Core filter 3, the watcher persistence pair - Microsoft reports two persistence mechanisms placed together: "the RelayTrapLiteAlert value in the machine-wide CurrentVersion\Run key launches an alert script at user logon", and "a scheduled task starts the watcher with a payload filename and lists of client identifiers and relay hosts to exclude", with a `-PollSeconds 10` argument configuring a ten-second poll. Microsoft publishes queries for both, reproduced as published:
  ```kql
  DeviceRegistryEvents
  | where Timestamp > ago(14d)
  | where ActionType == "RegistryValueSet"
  | where RegistryValueName =~ "RelayTrapLiteAlert"
      or RegistryValueData contains "RelayTrap"
  | project Timestamp, DeviceId, DeviceName, RegistryKey,
      RegistryValueName, RegistryValueData,
      InitiatingProcessFileName, ReportId
  ```
  ```kql
  DeviceEvents
  | where Timestamp > ago(14d)
  | where ActionType contains "ScheduledTask"
  | where AdditionalFields contains "RelayTrap"
      or AdditionalFields contains "TrapWatch"
  | project Timestamp, DeviceId, DeviceName, ActionType,
      AdditionalFields, InitiatingProcessFileName, ReportId
  ```
  The named strings are campaign-specific. The durable version of the second query is a scheduled task whose action is a script interpreter, polling on a sub-minute interval, registered by something that is not the deployment agent - which is the shape rather than the name.
  Core filter 4, the exclusions written to make room for the build - Microsoft reports that "registry writes target Microsoft Defender Antivirus path exclusions for staged MSI copies and CWInstall_...\Installer.ps1", and publishes an exclusion-focused query, noting the paths worth attention are those naming Windows Temp, the vendor install directories and the toolkit directory. A locally written exclusion for a temporary or staging path, by a process that is not the policy agent, is a strong corroborating leg - and Microsoft guidance to "review tamper-protection events when investigating exclusion changes" is the right follow-up, because it establishes whether the exclusion actually took effect or was blocked.
  Core filter 5, the whole chain on one endpoint - Microsoft describes the deployment sequence ahead of the build: the platform console directs the installed client to start the command shell, which invokes `curl.exe` to download an installer over HTTP from an attacker-controlled instance with a `c=Exploited<N>` marker, saving it to `C:\Windows\Temp\sc.msi`, which Windows Installer then installs silently with `/i`, `/qn` and `/norestart` so that an additional client connects to infrastructure the organisation does not control. Microsoft is explicit about what that means for remediation: "securing access to the legitimate console does not remove this additional client or its connection", and "removing an unauthorized client alone does not remove the toolkit persistence or invalidate exposed web sessions". The rogue-client side of this is already baselined in [[B051]]; the point for this hunt is that a compile event found on an endpoint should be worked backwards into that chain rather than treated in isolation.
  A note on the cleanup script - Microsoft reports the cleanup script "removes trap-related tasks, services, processes, Run entries, and files, and restores ScreenConnect client services unless client removal was requested", and that after running it the decoder cleanup mode "starts the bundled dropper again unless -NoReArm is set". Two consequences: a host that looks clean may have been cleaned by the toolkit rather than by a responder, and Microsoft warns directly - "do not use a cleanup script recovered from the kit as a remediation tool".
  Scope - Endpoints with a remote-support or remote-monitoring client installed, which in a managed-service context is the whole customer estate, plus the technician workstations that connect to them. The compile-against-installed-libraries pattern generalises to any agent-based management platform where impersonating a specific enrolled client requires that client own files.

# H472

Most malware that compiles on the victim does it to dodge a hash. This compiles on the victim because it has to.

Microsoft Threat Intelligence found that RelayTrap, part of the SCKit toolkit, cannot ship as a binary. To stand in for the remote-support client on a particular machine, it needs that installation's own libraries and its own connection parameters. So it arrives as a C# source file and a watcher script.

A scheduled task starts the watcher, polling every ten seconds. The watcher enumerates the remote-support client services, reads their executable paths and connection parameters, makes a directory per client under `trapbins`, copies the libraries out of that client's installation, and calls the .NET C# compiler to produce an executable. Then it keeps checking: if the source or the client libraries change, it rebuilds. The impersonation survives client upgrades.

Microsoft is blunt about what that does to hash-based detection — the binary is compiled against local libraries and embedded configuration shifts the script hashes, so defenders should work from file and process behaviour instead of indicators.

What the build is for runs against the normal direction of travel. The customer endpoint is aiming at the technician. RelayTrap reuses the endpoint's own client connection details in place of the real client, so when a technician connects with a vulnerable host client, it tries to push a launcher back through that support session. ConnectWise says the fix for CVE-2026-84869 blocks that transfer — released on September 8, 2026 — and the detail that matters operationally is that technician clients update separately from the cloud console. Updating the console does not update them.

Microsoft also notes that this endpoint-to-technician step is the toolkit's propagation design, not a confirmed chain of infections. The build on the endpoint, however, was observed.

## Why

- **Compiling on the host is a requirement here, not a preference, and that makes it reliable to hunt.** The component needs the specific client's libraries to be accepted, so the build cannot be moved off the endpoint. A technique the operator cannot relocate is a technique a defender can count on being there.
- **Hash detection is explicitly off the table, by the vendor's own assessment.** Local libraries plus embedded configuration means every build is different. That removes the easy path and leaves the process behaviour — a compiler invoked by a script host, writing into a staging directory, on a machine with no reason to compile anything.
- **The rebuild-on-change loop is maintenance, which tells you about intent and gives you more chances.** Watching for library changes and rebuilding is the behaviour of an operator planning to be present through the next client upgrade. It also means the artefacts recur rather than appearing once, so retention gaps are less fatal than usual.
- **The attack direction inverts the trust model of managed service delivery.** Customer endpoints are the things being supported, and support sessions are assumed to flow outward from the technician. A payload travelling back up that session breaks an assumption baked into how these platforms are deployed and monitored.
- **Patching the console does not patch the clients that matter.** The fix is in the technician client, which updates on its own schedule. An organisation that has updated its cloud instance and believes itself covered has verified the wrong version number — which makes technician client version inventory a control, not paperwork.
- **A clean-looking host may have been cleaned by the toolkit.** The kit's own cleanup removes tasks, services, Run entries and files, restores the client services, and then re-arms unless told not to. Current state is therefore poor evidence; the compile, copy and task-registration history is what holds. And the recovered cleanup script is not a remediation tool, whatever it appears to do.
