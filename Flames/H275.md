  enumerated first. Expect:
  - IT automation and helpdesk scripting. AutoIt is genuinely popular for GUI automation of installers and
    legacy line-of-business applications, and some organisations run a lot of it. Where it exists, it usually
    runs from a consistent script repository and under a known account.
  - Installers and software packaging. Many commercial installers are AutoIt-compiled, so `AU3!` markers and
    AutoIt-derived binaries appear in vendor software. These run from `Program Files` or from an installer temp
    path under an MSI parent.
  - Game macros, accessibility tooling, and testing frameworks on developer or QA machines.
  - Legitimate AutoIt development on machines with the AutoIt IDE installed, running from
    `C:\Program Files\AutoIt3\` or `C:\Program Files (x86)\AutoIt3\` with SciTE as the parent.
  The separators, in order:
  (1) PATH. `C:\Program Files\AutoIt3\AutoIt3.exe` is a development install. `C:\ProgramData\<something>.exe`

  (2) RENAME. A legitimate AutoIt deployment does not rename the interpreter. `OriginalFileName` =
      `AutoIt3.exe` while `Image` does not contain "autoit" is close to conclusive by itself — this is the

  (3) PARENT. SciTE, an MSI, or a scheduled automation account is normal. `powershell.exe` spawned from an LNK

  (4) DELIVERY PROVENANCE. Mark-of-the-Web on the LNK or the archive it came in, and a `Recent\` entry for it.
  (5) FLEET PREVALENCE. Sanctioned AutoIt automation is deployed to many hosts by the same tooling. This lands

      DeviceProcessEvents

# H275

The LNK arrives by email. Its embedded PowerShell decodes a HEX blob into three files: a document that opens and looks real, a copy of the AutoIt interpreter, and a `.au3` script. The interpreter is the genuine article — correctly signed, unmodified, downloadable from the vendor. Every hostile instruction lives in the text file it is handed on the command line.

That is why this works. Signature checks pass. Reputation checks pass. Script-host detections built around PowerShell, WScript, and MSHTA never fire, because none of those are executing the payload. What the endpoint sees is a legitimate automation tool doing what automation tools do.

What it cannot hide is the shape. Real AutoIt deployments live in `Program Files`, keep the interpreter's own name, and are launched by SciTE or a packaging tool. This one runs out of `C:\ProgramData`, frequently under a different filename, spawned by a PowerShell process that a user's double-click created ninety seconds ago — and then registers a scheduled task claiming to be a OneDrive update.

## Why

- **`OriginalFileName` is the whole hunt and it is one field.** Renaming the interpreter is standard tradecraft in this family — DarkGate did it, these campaigns do it — and it defeats any detection keyed on the filename. It does not defeat the PE version resource, which still says `AutoIt3.exe`, because populating that convincingly is extra work attackers routinely skip. SigmaHQ ships this exact logic as "Renamed AutoIt Execution," it is a single-condition query, and it has almost no benign population. If your pipeline drops `OriginalFileName` at ingest to save space — many do — restoring it is a five-minute change with disproportionate payoff.

- **The malicious logic never becomes a process, so the interpreter pairing is the only observable.** There is no unsigned binary to detect, no injected thread at delivery time, no unusual module load. The `.au3` file is data. That means detection cannot ask "is this process bad" — it has to ask "is this interpreter, at this path, with this parent, normal here." Which is a question process telemetry answers exactly, provided the query is built around the pairing rather than around the binary.

- **`C:\ProgramData` is the tell, and it is used because it is writable by everyone and looks official.** A user-launched chain cannot write to `Program Files` without elevation, and `%APPDATA%` is more heavily watched. `ProgramData` splits the difference: world-writable, rarely inventoried, and visually indistinguishable from legitimate application state. Both this campaign and the unrelated TerminalFix chain in the same week's intel staged there — see [[H277]] and [[B039]], where the general problem of unknown `ProgramData` contents is treated directly.

- **The scheduled task is a second, independent detection opportunity that most teams already collect.** Every campaign type in the source report registers Task Scheduler persistence, disguised as a OneDrive update, a browser update, or a renamed `pythonw.exe`. Event 4698 carries the full TaskContent XML, so the name and the actual command are both in one record — and a task calling itself a OneDrive updater whose `<Exec><Command>` points into `ProgramData` is self-refuting. That gives a hunter two independent chances at the same intrusion, on two different telemetry sources.

- **PubNub as a C2 channel is a gift, if anyone looks for it.** Commands arrive over a PubNub channel with results exfiltrated base64-encoded. PubNub is a legitimate real-time messaging service with real customers, so it has clean reputation and will never appear on a threat feed — and it also has essentially no reason to be contacted by a corporate Windows endpoint. That combination makes it high-signal and low-volume, which is the ideal shape for a hunt, and it is the kind of destination that only gets found when somebody thinks to ask. The general form is scored in [[M036]].

- **HEARTH had no T1059.010 coverage at all,** despite AutoIt and AutoHotKey being a persistent delivery mechanic across both commodity malware (DarkGate) and state-aligned campaigns, and despite the technique existing precisely because these interpreters interact with the Windows graphical subsystem in ways that bypass command-line and API-based detection.

- **The compiled-script variant is one build step away, so cover it now.** Compiling the `.au3` into a standalone EXE removes the script argument this hunt keys on. The fallback is cheap: the `AU3!` marker and `>>>AUTOIT SCRIPT<<<` string sit in the PE overlay of every compiled AutoIt binary, and `AutoItX3.dll` shows up in image-load telemetry. Adding the YARA rule and the module-load query at the same time as the process query closes the gap before it is used, rather than after.
