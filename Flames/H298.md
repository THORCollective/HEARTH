  provenance of the deletion: a legitimate uninstall is driven by `msiexec.exe`, an `unins000.exe`-style
  vendor uninstaller, a package manager, or an RMM or software-deployment agent, and it is typically
  initiated by an interactive administrator session or a scheduled deployment job. A cleanup issued by a
  process that is itself the target of the cleanup, or by a `cmd.exe` child of an application that has no
  business uninstalling anything, is the anomalous case. Second, the self-delete idiom: vendor
  uninstallers do not generally drop a batch file to `%TEMP%` that deletes a signed executable, an
  adjacent DLL, a `.dat` file and then itself, and the trailing `del "%~f0"` combined with a

# H298

There is an asymmetry in how persistence is usually hunted. Enormous effort goes into detecting the
creation of a service, a `Run` value, a scheduled task. Very little goes into detecting their removal,
even though removal is the point at which an intrusion is being deliberately concealed and is therefore
the point at which the defender's interest is highest.

ESET's SparroWocky analysis gives a concrete, current instance. The backdoor supports a command from its
C&C numbered `0x13`, described simply: removes persistence, then terminates by calling `ExitProcess`.
The persistence being removed is whichever of two forms was established — a service named
`ProcAuditManager`, whose description reads "Tracks process creation, termination, and related system
audit events" and which is convincing enough to pass a skim of `services.msc`, or a value named
`SnapCart` under `SOFTWARE\Microsoft\Windows\CurrentVersion\Run` in `HKLM` or `HKCU` depending on the
privilege available.

The file cleanup is more interesting than the registry cleanup, because it is forced by the operating
system. A running Windows executable holds a lock on its own image and cannot delete it. The standard
resolution, unchanged in twenty years, is to write a batch file, launch it, and exit — leaving the batch
script to wait for the process to die and then remove the image. SparroWocky's script deletes four
things: the legitimate executable that was being sideloaded against, the loader DLL, the `.dat` payload
file, and the batch script itself.

Those four deletions are a fingerprint of the delivery method, not just of the cleanup. A signed
executable, a DLL that no package owns, and a same-named non-PE data file, all removed together from one
directory, is the DLL-sideloading triad being dismantled. Ordinary program removal does not have that
shape.

The autonomous trigger deserves separate attention because it inverts what a completed cleanup means.
ESET notes that when a new instance of the implant is launched, the currently running instance stops,
and if the new instance came from a different location, the files and persistence of the old one are
deleted. The implant coordinates this through three named global objects — a mutex `MyMutexName`, an
event `MyEventName`, and a shared memory block `MySharedMemName`. So a host can present a clean,
complete, textbook uninstall sequence precisely because the actor moved the implant somewhere else on
the same machine. Finding this sequence is a reason to hunt harder on that host, not a reason to close.

The query is a correlation over a short window rather than a single match: a delete against a Services
key or an autorun value, then within seconds to minutes a `cmd.exe` process whose command line names a
batch file in a user-writable directory, then file deletions of a signed PE, a DLL and a data file
sharing a directory, and finally the batch file removing itself. Each element on its own is noisy; the
ordering is not. Elastic's prebuilt rule for file creation, execution and self-deletion in a suspicious
directory is the closest shipped analytic to this shape and is a reasonable starting template, and
SigmaHQ's `proc_creation_win_cmd_del_execution` gives the `del`/`erase` leg. Neither correlates the
registry deletion in front of them, which is the part this hunt adds.

Sysmon Event ID 23 with archiving configured is what turns this from a detection into an investigation:
it preserves the loader and payload the script was trying to destroy. That configuration has to exist
before the event, which is the practical argument for running this hunt as a telemetry-readiness check
first.

[[H297]] covers the same implant's other evasion — the rewritten PEB argument block that makes its
command line unreliable — and the two are worth running against the same host set.

## Why

- Persistence removal is the moment of highest defender value and lowest defender coverage. The actor
  only issues the uninstall when the operation is finished or is believed to be observed, so catching it
  is the difference between reconstructing an intrusion and discovering that a host was compromised for
  a period nobody can bound.
- The file cleanup is forced by Windows and therefore cannot be engineered away. An executable cannot
  unlink its own running image, so a helper process must do it, and that helper is a child process with
  a command line, a file creation and a set of deletions — all of it recorded, all of it happening after
  the malware has already decided to disappear.
- The deletion set identifies the delivery method. Removing a signed executable, an unowned adjacent DLL
  and a same-named `.dat` file in one action describes DLL sideloading with a reflectively loaded payload
  specifically, which means the hunt yields attribution of technique and not only evidence of cleanup.
- A successful cleanup does not mean the host is clean. The implant performs the same sequence on its own
  when a copy starts from a new path, so the completed uninstall is frequently a relocation, and the
  telemetry that recorded it is the only remaining pointer to when and where to look next.
