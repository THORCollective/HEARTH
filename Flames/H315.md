false_positive_notes: |
  The benign population here is bounded and largely knowable, because provider sources are declarative and version-controlled rather than ad hoc. Legitimate non-default registry hosts do exist and are the main source of noise in mature organisations: a private provider mirror or network mirror configured in `~/.terraformrc` or `.terraformrc`, an internal Artifactory or Nexus proxy fronting the public registry, and Terraform Enterprise or Terraform Cloud private registries all cause `terraform init` to fetch from something other than `registry.terraform.io`. Every one of those is an organisational decision with an owner, so the correct control is an allowlist of sanctioned registry hosts obtained from platform engineering — not a rule that assumes the public registry is the only legitimate source. Partner and community providers hosted on legitimate third-party infrastructure are a smaller but real population. Developers also routinely run `terraform init` against scratch and learning projects pulled from GitHub, which is exactly the behaviour being abused, so the discriminator cannot be "project came from outside" — it has to be the destination host and the post-fetch behaviour. On the process-lineage side, IDE integrated terminals spawn shells constantly and legitimately; that condition contributes context, never a verdict. The sharpest low-noise discriminator is what happens AFTER the fetch: a Terraform provider plugin is a binary that speaks a gRPC protocol to the Terraform core process, and it has no legitimate reason to spawn `curl`, `bash`, `osascript`, `nohup`, or to write into `~/Library/LaunchAgents/`. Those child-process and file-write conditions carry almost no benign volume and should anchor the hunt, with the non-registry host as the enrichment rather than the other way round.

# H315

SentinelOne tracked TraderTraitor backdoors onto a victim with no cryptocurrency exposure at all, which is itself the notable part — the targeting had widened past the sector everyone associates with this actor. The delivery was a fake job interview carrying a coding project, and the weapon inside it was a `.terraform.lock.hcl` file declaring a custom provider pointed at an attacker-controlled domain. The developer's only action was the ordinary one: open the workspace and run `terraform init`. Terraform dutifully fetched the provider and executed it. SentinelOne's timeline is stark — the workspace opened in Cursor at 05:00:41 UTC, shells spawned from the integrated terminal five seconds later, both implants launched at 05:00:53 as `nohup .../SystemUpdate --type=renderer` and `nohup .../iSync --type=renderer`, and C2 was established at 05:00:55. Fourteen seconds from opening a project to an established backdoor, with no security prompt anywhere in the chain, because every step used a trusted developer tool exactly as documented.

## Why

- **Infrastructure-as-code tooling is an execution primitive that is not policed like one.** Application allowlisting, Gatekeeper, notarisation and macro controls all sit outside this path. `terraform init` fetching and running a plugin is the tool's designed behaviour, so there is no policy violation to detect — only a destination that should not be there, which means the organisation has to know its own sanctioned registry set to have any opinion at all.
- **The provider source is declarative, so the attack is detectable statically before anyone runs anything.** Unlike most initial-access techniques, the malicious intent is written down in a committed text file. Grepping checked-out repositories for `required_providers` blocks naming hosts outside the allowlist finds the plant at rest, which turns this from an incident-response problem into an inventory sweep.
- **Provider plugins have an unusually rigid legitimate behaviour profile, which makes the anchor condition nearly noise-free.** A Terraform provider talks gRPC to Terraform core and does essentially nothing else. It does not spawn shells, call `curl`, invoke `osascript`, run `nohup` or write LaunchAgents. That rigidity is rare and valuable — it supports a detection with almost no benign volume, independent of which domain this particular campaign used.
- **The victim population is the one where compromise compounds fastest.** These are engineers holding cloud credentials, CI/CD access and source-control write permissions. A backdoor here is not one workstation; it is a path into the build pipeline and the cloud estate, which is why SentinelOne recommends treating this group as a distinct monitoring tier and why this hunt should run there first.
