title: "A user-mode process mounting the EFI System Partition and writing .efi files — bootkit installation staged from a two-file package in ProgramData"
hypothesis: >-
  Pre-boot persistence is the most durable foothold on a Windows host and the least watched, because the EFI System Partition is not assigned a drive letter and nothing in normal operation writes to it outside of a servicing operation. An operator who already has administrator rights and wants to survive reimaging mounts that partition deliberately, writes their own EFI binaries into it, and manipulates Secure Boot so those binaries are allowed to load. The installer is deliberately uninteresting on its own: the executable carries no malicious strings, and everything needed for the install sits in an encrypted extensionless companion file whose decryption key is passed on the command line, so a responder who recovers only the binary learns nothing. Hunting the mount and the write — a process assigning a letter to the ESP, or any file creation of a .efi under an EFI path by something that is not a Windows servicing component — catches the installation in the narrow window where it is still a user-mode action.

false_positive_notes: |
  Windows servicing legitimately writes to the ESP. Feature updates, bootloader servicing and BitLocker operations all touch it, and so do backup, imaging and disk-cloning products. Allowlist by the writing process image and signer, not by the path, and expect the legitimate set to be small and stable.
  Dual-boot and Linux installations write EFI binaries by design. Hosts that legitimately multi-boot will have third-party EFI binaries and shim loaders present. Inventory them deliberately rather than treating each as a finding, and scope the hunt to the single-boot managed estate first.
  Administrators do mount the ESP during troubleshooting. mountvol and diskpart against the system partition are legitimate recovery actions. The discriminator is what happens next: a mount followed within minutes by a file write under an EFI path by a non-Microsoft process is the finding, a mount followed by a read or nothing is not.
  Signature state will not clear the driver stage. The kernel driver in this campaign was validly signed at the time of use, by a real certificate issued to a real company, and the certificate was revoked only afterwards. Checking only for unsigned drivers will miss it; checking the signer against a list of publishers expected in your estate will not.
  Once the bootkit is resident, host telemetry becomes untrustworthy for this purpose. The driver disables process, thread and registry callbacks used by security products and tampers with ETW providers, and it intercepts kernel requests to open the bootkit files, returning a handle to calc.exe instead. So a live file-system check of the EFI partition from the running host can come back clean on an infected machine. Confirm from an offline mount or from measured-boot data, never from the host itself.
  Absence of the exploit is not absence of exposure. The Baton Drop patch revokes the certificate that signs the vulnerable components, but the revocation is not applied automatically on patch installation, so a fully patched host can still be exploitable.
notes: |
  ESP mount - Core filter: a process assigning a drive letter to, or otherwise mounting, the EFI System Partition. Triage values: full command line, parent process, account, and the process image path and signer. Defender XDR, 30-day retention:
  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where (FileName =~ "mountvol.exe" and ProcessCommandLine has "/s")
       or (FileName =~ "diskpart.exe")
       or (FileName =~ "powershell.exe" and ProcessCommandLine has_any ("Get-Partition", "Add-PartitionAccessPath", "Set-Partition"))
  | project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine,
            InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessCommandLine
  | order by Timestamp desc
  ```
  `mountvol <letter>: /s` is the documented way to mount the system partition and is the single most direct command-line signal. `diskpart` scripted with `set id` or `assign` against the system partition achieves the same thing without that switch, so review diskpart invocations by hand rather than trying to filter their arguments.
  EFI binary writes - Core filter: creation of a file with a `.efi` extension, or any write under an `\EFI\` path, by a process outside the servicing allowlist:
  ```kql
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("FileCreated", "FileModified")
  | where FileName endswith ".efi" or FolderPath has @"\EFI\"
  | where InitiatingProcessFileName !in~ ("TiWorker.exe", "TrustedInstaller.exe", "poqexec.exe", "bcdboot.exe")
  | project Timestamp, DeviceName, FolderPath, FileName, InitiatingProcessFileName,
            InitiatingProcessFolderPath, InitiatingProcessCommandLine, InitiatingProcessAccountName
  | order by Timestamp desc
  ```
  Build the exclusion list from your own estate; the four names above are a starting point, not a complete servicing set.
  Installer shape - The staging pattern is distinctive and worth a filter of its own: an executable in a vendor-flavoured ProgramData subdirectory invoked with two positional arguments, the first an extensionless file in the same directory and the second a high-entropy string. The observed command line was `C:\ProgramData\Intel\inst.exe PVMDIJGKAX2 Q46F6MDLI3RX2KV1`, where `PVMDIJGKAX2` is "an RC4-encrypted extensionless file containing files and strings required for the installation" and the final argument is the RC4 key. The report notes the installer itself "does not contain any malicious strings or embedded blobs", which is the point: recovering `inst.exe` without the companion file yields nothing, so collect both or neither.
  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where FolderPath startswith @"C:\ProgramData\"
  | where ProcessCommandLine matches regex @"(?i)\.exe""?\s+[A-Z0-9]{8,}\s+[A-Z0-9]{12,}\s*$"
  | project Timestamp, DeviceName, AccountName, FolderPath, FileName, ProcessCommandLine, SHA256,
            InitiatingProcessFileName
  | order by Timestamp desc
  ```
  Kernel driver stage - The UEFI payload injects a driver into the Windows kernel. The driver observed here was signed with a certificate issued to an organisation recorded in the report as 温江区明宇网络技术服务工作室 (Wenjiang District Mingyu Network Technology Service Studio), serial number `0bcdf5e0da32d68900b8b7638459d072`, since revoked by its issuer. Hunt driver loads by signer rather than by signature validity, joining `DeviceImageLoadEvents` to `DeviceFileCertificateInfo` on `SHA1`, and treat any kernel-mode signer that is not on your expected-publisher list as a finding. `DeviceImageLoadEvents` carries no signature columns, which is why the join is required.
  User-mode payloads for scoping - Two second-stage payloads were observed. One is a RAT that uses cloud storage for C2, seen using Google Drive, OneDrive and Yandex.Disk, which iterates the files available there and dispatches on a file suffix (`0X01` through `0X06`, plus `SSSR` for initial system information). The other, OxiDLLRunner, is an OLLVM-obfuscated DLL side-loaded by a binary delivered as `googleupdate.exe` whose original filename is `jcef_helper.exe` (MD5 `AF8A983B9ADA07EAE1259BF2953ABD40`); it decrypts `v8_context_snapshot.bin` from the same folder and jumps to the decrypted content, which is shellcode followed by a Rust payload that communicates with `www[.]archivetj[.]com`. A binary named `googleupdate.exe` whose version information names a different original filename is a cheap corroborating check.
  Exposure check, worth running regardless of any hit - The Baton Drop patch does not take effect on its own. The report's finding is that the patch "is designed to revoke the “Windows Production PCA 2011” certificate used to sign vulnerable UEFI components. However, this revocation does not happen automatically upon patch installation — the user has to trigger it manually." Inventory which hosts have had the revocation applied; the gap between patched and actually-protected is the population this campaign targeted.
  Verification discipline - Because the resident driver hides the bootkit files from the running kernel, confirm findings offline: mount the ESP from a separate boot medium or an image, compare its contents against a known-good baseline, and use measured-boot or TPM attestation data rather than a live directory listing. Reimaging the OS volume alone does not remove pre-boot persistence.

# H421

Kaspersky reported in October 2026 on a UEFI bootkit it names BlackX, used against diplomatic agencies in Tajikistan, Uzbekistan and Turkmenistan in early 2026 and attributed to APT41 with medium confidence. The bootkit is closely modelled on BlackLotus, the Secure Boot bypass that was advertised on a criminal forum in 2022 for $5,000 and confirmed genuine by ESET in 2023. BlackLotus had gone quiet after Microsoft's updates; BlackX revives the approach, and since the BlackLotus source was never published, Kaspersky assesses the actors either reverse-engineered it or bought the source — an unusual case of an APT borrowing from cybercrime tooling.

The installation is a post-compromise step rather than an entry vector. Operators arrive with administrator privileges already and drop two files: an installer, and an RC4-encrypted extensionless blob holding everything the install actually needs. The installer was launched as `C:\ProgramData\Intel\inst.exe PVMDIJGKAX2 Q46F6MDLI3RX2KV1`, with the last argument serving as the decryption key. The design is explicitly anti-forensic — `inst.exe` "does not contain any malicious strings or embedded blobs", so a responder who collects the executable alone recovers nothing of value. From there the package writes files to both the system and UEFI partitions to exploit Baton Drop (CVE-2022-21894), with the goal of installing custom Machine Owner Keys so arbitrary EFI files can be loaded.

What follows is why the installation window matters so much. The UEFI payload injects a kernel driver which disables process, thread and registry callbacks belonging to security products and tampers with ETW providers so their output is unavailable. It also protects its own files: it intercepts kernel requests to open them and returns a handle to `calc.exe` instead. Once that driver is live, the host's own telemetry cannot be trusted to answer whether the host is infected — a live listing of the EFI partition can come back clean.

There is also a patching trap worth acting on independently of any hunt. Kaspersky found the problem was not a missing patch but the patch itself: the Baton Drop fix revokes the certificate that signed the vulnerable components, but "this revocation does not happen automatically upon patch installation — the user has to trigger it manually." Few organisations realised this, which is plausibly why the actor judged a BlackLotus copycat worth building.

## Why

- Pre-boot persistence outlives the responses teams actually perform. Reimaging the OS volume, rotating credentials and rebuilding the domain account all leave a bootkit in place, so detecting the installation is disproportionately valuable compared to detecting most persistence.
- The installation window is the only moment this is a user-mode, well-logged action. Mounting the ESP and writing `.efi` files are ordinary file and process events while they happen; afterwards the observer is running underneath the thing it is trying to observe.
- The ESP is close to silent in normal operation. It has no drive letter, and the set of processes that legitimately write to it is a short servicing list, which makes both the mount and the write high-signal with a small allowlist.
- Signature checks do not catch the driver. It was validly signed by a real certificate issued to a real company, revoked only later, so detection has to key on whether the kernel-mode signer is expected in the estate rather than on whether the signature verifies.
- The two-file installer pattern is itself a durable artefact. Separating the payload from the loader and passing the key on the command line defeats string and blob analysis of the executable, but it produces a command line with an unmistakable shape, and it means the key needed to decrypt the package is sitting in process telemetry.
- The manual-revocation gap is independently actionable. Inventorying which hosts have actually had the Baton Drop revocation applied is a one-off exercise that shrinks the exploitable population, and most teams have never done it because the patch reported as installed.
