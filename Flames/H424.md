title: "A CryptoAPI user agent that POSTs octet-streams — Aokigahara's `/gate` upload session, where the `X-Chunk` header names the data class being stolen"
hypothesis: >-
  Windows certificate validation fetches revocation data over HTTP with the user agent `Microsoft-CryptoAPI/10.0`, which makes that string a comfortable disguise for an implant: it is genuinely common, it is expected on every host, and defenders learn to ignore it. The disguise fails on method and content type. Legitimate CryptoAPI traffic retrieves certificate revocation lists with GET, and the one case where it POSTs is an OCSP request carrying `Content-Type: application/ocsp-request`. Aokigahara uses the same user agent to POST `application/octet-stream` bodies to three fixed paths under `/gate`, carrying a set of custom `X-` headers that identify the build, the session, the host and the data class in flight. The combination of that user agent with that method and that content type should not occur on a healthy host, and when it does, the `X-Chunk` header states in plain text which category of stolen data is being uploaded.

false_positive_notes: |
  The user agent alone is not the finding and must never be alerted on by itself. `Microsoft-CryptoAPI/10.0` is legitimate, ubiquitous and generated by Windows itself for revocation checking. Alerting on it will bury the analyst in certificate traffic on day one.
  Genuine CryptoAPI POSTs exist. OCSP requests are POSTs, so method alone does not separate implant from Windows. The content type does: an OCSP request carries `Content-Type: application/ocsp-request` and is sent to a certificate authority's responder. Keep the content-type term in the query rather than relying on method.
  Any software may copy a Windows user agent. Enterprise agents, scanners and poorly written in-house tooling sometimes borrow this string, and some of them POST. Resolve the initiating process before escalating and allowlist by signed image path; this is normal estate hygiene and shrinks over time.
  Without TLS inspection the HTTP detail is unavailable. The C2 can be HTTPS and the configuration supports certificate pinning, so an estate with no inspection and no proxy will not see headers at all. In that case fall back to the destination, process-attribution and session-shape terms below and accept lower fidelity, rather than concluding the behaviour is absent.
  The `/gate` paths are one build's choice. Build identifiers, tokens and paths rotate, and the report records that the user agent has already changed across versions, so treat the path list as the fast confirmation and the method-plus-content-type pair as the durable part.
  A single handshake with no chunks is not a cleared alert. The handshake registers the session before any data moves, so an interrupted upload leaves only the 32-byte POST. That is an infection that was cut off, not a false positive, and the host still needs investigating.
notes: |
  Platform - Windows hosts, detected at the network boundary. The sensor is a proxy or TLS-inspecting gateway, or Zeek; this is not a Defender advanced-hunting detection, for the reason given below.
  Telemetry limitation worth stating up front - `DeviceNetworkEvents` does not carry HTTP headers, user agents or request content types. It is useful here only for the destination, the initiating process and the timing, and any query claiming to match a user agent in that table cannot work. The header evidence has to come from a proxy, a gateway with inspection, or Zeek.
  The published request structure - Check Point reproduces all three requests. The base path is `/gate`, with three endpoints handling session establishment, uploads and completion. Every request observed carries `Connection: Keep-Alive`, `Content-Type: application/octet-stream` and `User-Agent: Microsoft-CryptoAPI/10.0`, plus `X-Build-ID`, `X-Gate-Token`, `X-Session` and `X-HWID`.
  - `POST /gate/handshake` - "Establishes an upload session by sending the client's raw 32-byte X25519 public key. The malware requires an HTTP `200` response before enabling uploads." It adds `X-KEX: x25519`, and `Content-Length` is exactly 32.
  - `POST /gate/chunk` - "Uploads collected information packaged into ZIP archives and encrypted using AES-256-GCM." It adds `X-Chunk`, naming the module whose data this is, `X-Chunk-Index` for sequence and `X-Total` for the expected count. The body is a 12-byte nonce, the ciphertext and a 16-byte authentication tag, and the upload buffer is the ZIP size plus 28 bytes.
  - `POST /gate/complete` - body is the eight-byte marker `COMPLETE`, so `Content-Length` is exactly 8. The report notes the limit of what this means: "This notification does not independently establish that every upload succeeded."
  Sample header values from the report, for recognition and not for blocking - `X-Build-ID` values of `cae87a25` and `4dbf818f`, `X-Session` of `ca47b44161834cb70a224dbe3d92a383`, `X-HWID` of `69B506A1`, and `X-Gate-Token` of `fc157583cc171c2c82419748390126839a0f8fba317a75f919e785aca3d98f8e`. These are the values in Check Point's captured examples. They are per-build and per-host, so they identify the structure rather than the infrastructure and should not be deployed as indicators.
  Why method and content type are the durable terms - This is the part that is my analysis and not in the report: Windows generates this user agent from the certificate stack to retrieve revocation data, which is a GET against a CRL distribution point, and the one legitimate POST case is an OCSP request with `Content-Type: application/ocsp-request` directed at a responder. Check Point does not discuss legitimate CryptoAPI behaviour at all. The consequence is that `Microsoft-CryptoAPI/10.0` plus POST plus `application/octet-stream` has no benign counterpart to tune against, which is what makes the pair worth keying on even after the paths and the user agent rotate.
  Zeek query - The highest-fidelity version, since Zeek records method, user agent and content type together:
  ```bash
  cat http.log \
    | zeek-cut ts id.orig_h id.resp_h host uri method user_agent request_body_len \
    | awk -F'\t' '$7 == "Microsoft-CryptoAPI/10.0" && $6 == "POST"'
  ```
  Follow up on any hit by pulling the full record for the matching `uid` to read the request content type and the `X-` headers, which `zeek-cut` above does not project.
  Proxy log query, Sentinel or any proxy table - Parentheses are explicit because the terms must bind as one conjunction:
  ```kql
  let gatePaths = dynamic(["/gate/handshake", "/gate/chunk", "/gate/complete"]);
  CommonSecurityLog
  | where TimeGenerated > ago(30d)
  | where RequestMethod =~ "POST"
  | where RequestClientApplication =~ "Microsoft-CryptoAPI/10.0"
  | extend gateMatch = RequestURL has_any (gatePaths)
  | summarize requests = count(), paths = make_set(RequestURL, 20),
              gateHits = countif(gateMatch),
              bytes = sum(tolong(SentBytes)),
              firstSeen = min(TimeGenerated), lastSeen = max(TimeGenerated)
          by SourceIP, DestinationIP, DestinationHostName
  | extend span = lastSeen - firstSeen
  | order by gateHits desc, bytes desc
  ```
  Every row this returns is already anomalous, because the method and user agent alone have no benign counterpart outside OCSP; `gateHits` ranks the confirmed path matches to the top rather than being the filter. Note that CEF proxy records do not reliably carry the request content type, so the OCSP separation here rests on the destination and path rather than on `application/ocsp-request`; where the gateway does log request content type, add it as the stronger term.
  Splunk - The `OR` group is parenthesised so it cannot absorb the following terms, which is the usual way this query goes wrong:
  ```spl
  index=proxy sourcetype=proxy
    http_method=POST
    http_user_agent="Microsoft-CryptoAPI/10.0"
    (uri_path="*/gate/handshake" OR uri_path="*/gate/chunk" OR uri_path="*/gate/complete")
  | stats count AS requests, values(uri_path) AS paths, sum(bytes_out) AS bytes_out,
          min(_time) AS first_seen, max(_time) AS last_seen
          BY src_ip, dest, http_user_agent
  | eval span_s = last_seen - first_seen
  | sort - bytes_out
  ```
  Session-shape query, for estates with no header visibility - The upload has a recognisable silhouette even when the headers are opaque: one very small request, a run of larger ones, then one very small request, all to the same destination within a short window. Build it from proxy byte counts or from `DeviceNetworkEvents` timing, and expect lower fidelity.
  Scope triage, the part that is unusual - The `X-Chunk` header names the module whose archive is being uploaded, with labels Check Point gives as `sysinfo`, `browsers`, `firefox` and `aisessions`, and `X-Total` states how many archives the implant intends to send. Where headers are visible, the proxy log therefore tells an incident responder which categories of data left the host and whether the upload completed, before any host forensics are done. An `aisessions` chunk means the AI and developer credential sweep in [[H422]] succeeded and every token in that set must be treated as compromised; a `browsers` chunk scopes to session-cookie replay. Record the observed labels and the `X-Total` value in the case notes.
  Cryptography, and what it means for recovery - The implant generates an X25519 key pair, computes a shared secret against the server public key from its configuration, and derives the AES-GCM key by SHA-256 over that secret with the fixed string `aokigahara`. The private half never leaves the host and the server's private half is the operator's, so captured traffic cannot be decrypted from the network capture alone. Collect the capture anyway: sizes, labels and sequence numbers are recoverable from the headers and establish scope without any decryption.
  Configuration context for the hunt - The decrypted configuration holds the base URL, a build identifier, a gate token, a module bitmask, TLS certificate pinning settings and "up to three fallback URLs". So a blocked primary destination does not end the session, and a hunt that finds one destination should look for two more. The module bitmask also means absence of a chunk label proves only that the module was disabled in that build, not that the data was safe.
  Adjacent coverage - [[H224]] is the closest existing hunt in shape: a modular C2 identified by a static HTTP protocol fingerprint, in that case a custom `X-User-token` header ending in `00` against three fixed URIs. The distinction here is that the fingerprint is built on a masqueraded Windows user agent contradicted by its own method and content type rather than on a bespoke header, and that this protocol's headers leak the data class and the expected archive count, which gives exfiltration scope from the proxy log alone — something [[H224]] has no analogue for. [[H422]] and [[B066]] cover the collection stage that feeds these uploads, and [[H423]] covers the clipper component deployed on the same hosts.

# H424

Check Point Research's October 2026 analysis of the Aokigahara infostealer documents its command-and-control protocol in full, including complete request captures. The protocol is a three-stage upload session against a fixed base path, and the most interesting thing about it is the user agent it wears.

Every request carries `User-Agent: Microsoft-CryptoAPI/10.0`. That string is not invented: Windows generates it when the certificate stack fetches revocation data, so it appears on essentially every Windows host and in essentially every proxy log. It is a good disguise for the same reason it is a bad one. Legitimate CryptoAPI traffic retrieves certificate revocation lists with GET requests, and the single case where it POSTs is an OCSP request, which carries `Content-Type: application/ocsp-request` and goes to a certificate authority's responder. Aokigahara POSTs `application/octet-stream`. That contradiction is not discussed in the report — it is the analytic observation this hunt is built on — and it means the combination has no benign population to tune against.

The three stages are explicit. `POST /gate/handshake` "Establishes an upload session by sending the client's raw 32-byte X25519 public key. The malware requires an HTTP `200` response before enabling uploads." `POST /gate/chunk` then "Uploads collected information packaged into ZIP archives and encrypted using AES-256-GCM", once per collection module. `POST /gate/complete` sends the eight-byte marker `COMPLETE`, about which the report adds a useful caution: "This notification does not independently establish that every upload succeeded."

The headers are where this becomes unusually valuable to an incident responder. Alongside the build identifier, gate token, session identifier and hardware identifier, each upload carries an `X-Chunk` header naming the module whose archive it contains — `sysinfo`, `browsers`, `firefox`, `aisessions` — and an `X-Total` stating how many archives the implant means to send. Where a proxy can see those headers, the log states which categories of data left the host and whether the set completed, before anyone touches the endpoint. An `aisessions` upload is a direct instruction to revoke AI service and cloud SSO credentials.

The report is also clear that this is a moving target: the stealer "appears to be under active development, with changes to its HTTP User-Agent string observed across versions." The paths, tokens and even the user agent will rotate. What survives rotation is a Windows certificate user agent doing something Windows certificate code does not do.

## Why

- The masquerade contains its own contradiction. A user agent chosen because defenders ignore it becomes high-fidelity the moment the method and content type are considered, and those two fields are present in every proxy log without additional instrumentation.
- The upload headers give exfiltration scope before host forensics. Knowing from the proxy that an `aisessions` archive was uploaded, and how many archives of an expected total arrived, converts a vague stealer alert into a specific revocation list and a specific blast radius.
- Detection at the boundary catches hosts that endpoint telemetry missed. A stealer that evaded or disabled endpoint controls still has to reach its server, and this protocol is distinctive in fields that a forward proxy records by default.
- The handshake requirement creates an early, small, recognisable event. The implant will not upload until it receives an HTTP 200, so the 32-byte POST precedes all data loss and is itself worth catching.
- The fingerprint degrades gracefully. Where TLS inspection is absent the session silhouette, destination set and process attribution still apply, and the configuration's up-to-three fallback URLs tell the hunter to expect more than one destination rather than stopping at the first.
