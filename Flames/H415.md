  Module load by an unexpected process - Core filter: image load of `jscript9.dll` where the loading process is not in the browser and script-host allowlist. Triage values: `InitiatingProcessFileName`, `InitiatingProcessFolderPath`, `InitiatingProcessCommandLine`, `InitiatingProcessParentFileName`, the loaded `FolderPath`, and the loading process integrity level. Defender XDR, 30-day retention:
  ```kql
  let allowed = dynamic(["iexplore.exe","msedge.exe","msedgewebview2.exe","mshta.exe","explorer.exe","wwahost.exe"]);
  DeviceImageLoadEvents
  | where Timestamp > ago(30d)
  | where FileName =~ "jscript9.dll"
  | where InitiatingProcessFileName !in~ (allowed)
  | summarize Loads = count(), FirstSeen = min(Timestamp), LastSeen = max(Timestamp),
              Paths = make_set(InitiatingProcessFolderPath, 10)
            by DeviceName, InitiatingProcessFileName, InitiatingProcessCommandLine
  | order by FirstSeen asc
  ```
  Order ascending rather than descending: the first appearance of a new loader in the estate is the interesting row, and rare-process-first beats most-recent-first for this behaviour.
  Sysmon 7 equivalent - match `ImageLoaded` ending in `\jscript9.dll` and exclude the same process set in the Sysmon config to keep volume down. Sysmon 7 is the highest-volume event in a default config, so filter at the agent, not at the query.
  Why this module - The report states that "Instead of invoking VirtualProtect directly, the malware uses the identified HeapPageAllocator::ProtectPages in jscript9.dll to modify the memory page protection of the MD4Update function." The engine is mapped for one internal routine, not to run script, so there will be no corresponding script activity on the host: no 4104 script-block events, no `DeviceEvents` script telemetry, and no child process from a script host. A module load with no script execution around it is the shape to look for.
  The patch target and the hook - The start of `MD4Update` is overwritten with a fixed opcode sequence that acts as a syscall stub, and the stub is then used to disable a user-mode syscall instrumentation hook before the next stage is reflectively loaded. The report does not say which module exports the `MD4Update` function it patches, and does not name the security product whose instrumentation hook is being disabled, so do not build a filter on either; confirm the patched module from memory during triage instead. Comparing the first bytes of exported functions in a loaded module against the on-disk copy is the direct check once a candidate process is identified.
  Reflective load that follows - The final stage is loaded into memory and never written to disk, so file telemetry will not show it. The corroborating evidence is unbacked executable memory in the process, plus the absence of any image-load event for the stage that is clearly running. Where your EDR exposes region telemetry, look for private executable memory in a process whose module list includes `jscript9.dll` but whose loaded-module set is otherwise minimal.
  Relationship to existing coverage - [[M030]] scores dynamic API resolution and direct syscall invocation across the estate using call-stack and unbacked-memory anomalies. This hunt is the opposite approach for one specific tradecraft: a single discrete artefact, the module load, with no scoring, which is cheap enough to run as a standing query and which fires before the instrumentation hook is removed rather than inferring the removal afterwards. Run both; they fail in different ways.
  Triage sequence - Confirm the loading process has no script-hosting role, pull its module list and compare exported-function prologues against disk, check for unbacked executable regions, then pivot on the parent process and on the service that started it. In this intrusion set the loader is reached from a side-loaded DLL under a service, so see [[H412]] for the service stage that precedes it and [[H124]] for the side-load itself.

# H415

Kaspersky's Operation FlashHole report, published in October 2026, documents an updated version of the Lazarus Group profiler LPEClient. Most of the report concerns its cryptography — the group moved to post-quantum key encapsulation for payload delivery — but the step immediately before the payload is loaded is the more useful one for a hunter.

LPEClient needs to patch code in memory, which means making a page writable. Doing that the normal way means calling `VirtualProtect`, which is among the most heavily watched calls on the platform. The report describes the alternative: "Instead of invoking VirtualProtect directly, the malware uses the identified HeapPageAllocator::ProtectPages in jscript9.dll to modify the memory page protection of the MD4Update function." The Internet Explorer script engine is mapped into the process not to run any script, but because it contains a page-protection routine the implant can reach. The start of `MD4Update` is then overwritten with a hardcoded opcode sequence acting as a syscall stub, and that stub is used to disable a user-mode syscall instrumentation hook. Only then is the next stage — identified in the report as the Cubridge orchestrator — reflectively loaded into memory.

The memory operations themselves are largely invisible to native Windows telemetry. In-module patches and page-protection changes are not recorded by Sysmon or the Defender XDR tables, which is precisely why this technique is attractive. But the module load is recorded, by both Sysmon Event ID 7 and `DeviceImageLoadEvents`, and the module in question has a small and enumerable set of legitimate consumers. A background service or an unsigned binary in a staging directory mapping `jscript9.dll`, with no script activity anywhere near it, is a finding on its own.

## Why

- The hunt fires before the defence is impaired. Once the instrumentation hook is removed, whatever depended on it stops reporting, so detections built on the post-unhook behaviour are looking through the hole the adversary just made. The module load happens while telemetry is still intact.
- Borrowing a primitive from an unrelated signed module is a general evasion pattern, not a quirk of this family. Any implant that wants to avoid calling the obvious API has to map something that already contains an equivalent routine, and that mapping is logged. The specific module will change; the shape of the anomaly will not.
- The legitimate consumer set is small and stable. Browser and script-host processes aside, almost nothing on a managed endpoint has a reason to map the legacy IE script engine, which makes the allowlist short and the resulting queue genuinely triageable rather than nominally so.
- The absence of accompanying script execution sharpens it further. A real script-engine consumer produces script activity; this one produces none, so pairing the module load with the lack of any script-block or script-host telemetry removes most of the remaining legitimate cases.
