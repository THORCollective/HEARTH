false_positive_notes: |
  Nested task folders are normal for software vendors — `\Microsoft\Windows\...`, `\Mozilla\`, `\Google\`, `\Adobe\`, `\Lenovo\` and management agents all register under their own folder trees, and some vendors use product codenames that look odd out of context. The distinction is that every legitimate folder root maps to an installed product and shows up on many hosts with the same name, whereas a generated path like the INC one is likely unique to the victim (not reported by Huntress) and is made of words with no relation to any product. So drive this hunt from fleet prevalence: a task folder root seen on one or two hosts, not matching any installed-software publisher, is the population to review. The second filter is the action — PowerShell running a `.ps1` from a dedicated, freshly-created folder directly under `C:\ProgramData` is uncommon for commercial software, which almost always runs a signed executable from `Program Files`. In-house IT scripts are the main benign source for that pattern, and they are usually registered under a recognisable folder (`\IT\`, `\Company\`) by a known admin account; confirm with the owner and add them to an allowlist.

Huntress also notes the late-August tasks were registered "via the same compromised user account". Huntress published no detection queries; the queries below are derived from the reported artefacts.
  What the names look like, and why that matters - Most tokens are a real English stem with extra suffixes bolted on: "cancellation" + "izing", "illuminate" + "ers", "fictionally" + "es", "vendetta" + "ister". They look like words at a glance and fail a dictionary lookup on close inspection. Generated names of this kind defeat rules that look for high-entropy random strings (they have ordinary letter frequencies) and rules that look for GUID-shaped task names, while still being unlike anything a vendor would ship. [[M051]] turns this into a scoring model; this hunt uses the cheaper structural signals.
  Task-registration leg - Core filter: Event ID 4698 or `DeviceEvents | where ActionType == "ScheduledTaskCreated"` where the task name has two or more folder levels, the top-level folder is not in the host's installed-publisher list, and the action runs `powershell.exe` or `pwsh.exe` with `-File`, or directly references a `.ps1`, under `C:\ProgramData\<single folder>\`. Triage fields: `TaskName`, the `<Description>` element of the task XML, `<Author>`, `<Principal>`, trigger type and repetition interval, and the registering process and account. Strong red flags: the description is a string of unrelated words with no product meaning; the task runs as SYSTEM or as a service account on a server; the ProgramData folder was created within minutes of task registration and contains only the script; and the script's first executions coincide with outbound connections to a newly-registered domain.
  Sample KQL - multi-level task folders running ProgramData PowerShell, ranked by rarity:
  `DeviceEvents | where Timestamp > ago(60d) | where ActionType == "ScheduledTaskCreated" | extend td = parse_json(AdditionalFields) | extend TaskName = tostring(td.TaskName), TaskContent = tostring(td.TaskContent) | extend depth = countof(TaskName, "\\"), root = tostring(split(TaskName, "\\")[1]) | where depth >= 3 and root !in~ ("Microsoft", "Mozilla", "Google", "Adobe", "Apple", "Intel", "Dell", "Lenovo", "HP") | where TaskContent has_any ("powershell", "pwsh", ".ps1") and TaskContent has @"ProgramData\" | join kind=leftouter (DeviceEvents | where Timestamp > ago(60d) | where ActionType == "ScheduledTaskCreated" | extend root = tostring(split(tostring(parse_json(AdditionalFields).TaskName), "\\")[1]) | summarize rootHosts = dcount(DeviceId) by root) on root | where rootHosts <= 3 | project Timestamp, DeviceName, InitiatingProcessAccountName, TaskName, rootHosts, TaskContent`
  On-disk and registry corroboration - The task definition is written to `C:\Windows\System32\Tasks\<folder>\<folder>\<name>` and to `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree\<folder>\...`. Walk both on suspect hosts; a folder path present in one and not the other is a sign of tampering (see [[B050]] for that integrity baseline). Collect the `.ps1` itself; its obfuscation is the other half of this hunt, and PowerShell Event ID 4104 will hold the deobfuscated script blocks if script block logging is on.
  Hunting the dwell window - Because this foothold predated the ransomware stage by 17 days, run the hunt retroactively over at least 60 days, and for every hit pivot to RDP logons (Security Event ID 4624 logon type 10, and TerminalServices-LocalSessionManager Event IDs 21/25) from the same account in the following days, and to DNS lookups of the task's C2 domain across the fleet.

# H349

Huntress's timeline of an INC Ransom intrusion has two distinct halves separated by seventeen quiet days. The second half is loud and fast: AnyDesk, a renamed remote-management agent, a network scanner, a vulnerable-driver kit to kill endpoint protection, Impacket's `atexec.py`, and ransomware on at least 175 endpoints. The first half is quiet, and it is the one to hunt.

In early August someone registered a scheduled task at `\Nonweighise\Cancellationizing\Illuminateers`, gave it the description "nationhood kinestheticization preironish fictionallyes", and pointed it at an obfuscated PowerShell script in `C:\ProgramData\Vendettister\jocularities.ps1` that talked to `throughoutes[.]net`. They moved laterally over RDP and then left. Huntress says the gap suggests two groups, an initial access broker and a ransomware affiliate. If so, that task was the product being sold.

The names are the interesting part. They are not random strings. They are real English stems with suffixes stacked on until they stop being words, so they read naturally at a glance, carry normal letter frequencies, and slip past rules looking for high-entropy or GUID-shaped names. They still stand out in a task inventory, because no software vendor names a folder "Nonweighise", and a two-level folder tree that exists on exactly one host and belongs to no installed product has no benign explanation.

## Why

- It targets the likely initial access broker's artefact, not the affiliate's. The task existed for more than two weeks before any ransomware activity, so finding it moves detection from "during encryption" to "before the access is sold."
- Prevalence does most of the work. Legitimate task folder roots map to installed products and recur across the fleet; a nested folder tree that appears on one or two hosts and matches no publisher is a small, reviewable population.
- The action narrows it further. Commercial software schedules signed executables from `Program Files`; a PowerShell `.ps1` in a freshly-created single-purpose folder directly under `C:\ProgramData` is uncommon enough to combine with rarity for a short list.
- Pseudo-word names defeat the usual name heuristics. Entropy and GUID-pattern rules miss suffix-stacked English stems, so a structural and prevalence-based hunt catches what those rules were never going to see.
- Event ID 4698 carries everything needed. The task XML in the event includes the folder path, description, author, principal and action, so the whole hunt runs from one event type most organisations already collect.
