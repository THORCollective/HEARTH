title: "A WAF block on the WordPress users endpoint followed by successful author harvesting elsewhere — enumeration that pivots to post author fields and author sitemaps, then returns as a username list"
hypothesis: >-
  The usual advice for WordPress user enumeration is to block `/wp-json/wp/v2/users`, and WAF vendors ship rules that do exactly that. The endpoint is not the only place the same data lives. Post objects carry an author field, embedded post responses carry the author object with display name and slug, and core publishes author sitemaps, none of which is a user endpoint and none of which a users-endpoint rule touches. An adversary that is blocked on the obvious path and then retrieves the same roster from the alternatives leaves a two-part signature in the logs that is far more specific than either part alone: a 403 from the WAF on the users endpoint, then successful 200s to author-bearing endpoints from the same source, then a credential-guessing burst against `wp-login.php` whose usernames are the names that were just harvested. The block is the thing that makes it legible, because it establishes intent before the successful requests happen.

false_positive_notes: |
  Search engine crawlers, SEO tools and uptime monitors request sitemaps and post listings constantly, and author sitemaps are published precisely so that they are crawled. Crawler traffic is the dominant population on any public site. Separate it on user agent and reverse DNS, and more reliably on behaviour: a crawler fetches sitemaps on a schedule and does not follow them with authentication attempts.
  The author endpoints are legitimate and widely consumed. Headless front ends, mobile apps, caching layers, aggregators and the site's own theme all read post objects with embedded author data. A site that serves a JSON API to its own front end will show high, steady volume here, which is why the WAF block is the anchor term rather than the author requests.
  A 403 on the users endpoint is itself ordinary. Scanners hit `/wp-json/wp/v2/users` all day and are blocked, and most never come back. The finding is the pivot: the same source returning to author-bearing endpoints and succeeding. Without the second half this is background internet noise.
  Plugin and theme updates can produce bursts resembling enumeration. A newly installed plugin or a cache warm-up can walk every post and author in minutes from the server's own address or a known integration. Allowlist the site's own infrastructure and integration sources before hunting.
  Not every estate records WAF blocks where the hunter can see them. If the CDN blocks at the edge and only forwards allowed traffic, the origin access log contains no 403 and the anchor term is unavailable. In that case the hunt runs on the author-harvesting and login-burst halves alone and loses fidelity; getting edge logs into the same index is the fix.
  A successful login in the window is not necessarily the adversary. Legitimate users log in during any window. Correlate on the specific username, the source address and the preceding failure sequence rather than on the presence of a success.
notes: |
  Platform - Internet-facing WordPress. The whole hunt runs on web, WAF and application logs; no endpoint telemetry is involved.
  What Unit 42 observed - The attack ran in four stages against an Indian university's online education platform. Stage one: "Subdomain enumeration: The actor identified 12 subdomains including the main WordPress site, a learning management system (LMS), student portal and administration dashboard". Stage two is the pivot this hunt is built on: "The actor extracted 13 active user IDs with real names via post author fields and author sitemaps, bypassing the Cloudflare Web Application Firewall (WAF) that blocked direct user endpoint access". Stage three: "A generator script produced a brute force tool with 117 usernames (derived from the enumeration) and 28 common passwords". Stage four: "The actor's tool flagged one WordPress login as valid".
  The 117-usernames-from-13-identities figure is worth holding onto during triage. The generator expanded each harvested real name into candidate account formats, so the login attempts will show many near-miss variants of a small number of genuine staff names — first initial plus surname, dotted and undotted forms, and so on. That pattern is distinctive against both credential stuffing, which uses unrelated addresses from breach corpora, and ordinary user error.
  Which endpoints, and what is inference - Unit 42 names only "post author fields and author sitemaps". The specific paths below are the standard WordPress surfaces that expose those two things and are not covered by a users-endpoint rule; they are my mapping from the report's description to concrete paths, not endpoints the report lists:
  - `/wp-json/wp/v2/posts` with the `author` field in each post object, and `?_embed` or `_fields=author` to pull the author object including name and slug.
  - `/wp-sitemap-users-1.xml`, the author sitemap published by WordPress core, and the sitemap index at `/wp-sitemap.xml` that points to it.
  - `/?author=N` for sequential N, where the author archive redirect discloses the account slug.
  - Legacy and plugin equivalents such as `/wp-json/wp/v2/users` itself where the rule is missing, and XML sitemap files emitted by SEO plugins.
  Confirm which of these the site actually exposes before hunting; a site with author archives disabled and sitemaps suppressed will only show the posts route.
  Anchor query, the pivot - Find sources blocked on the users endpoint that then succeeded against an author-bearing endpoint. Both bindings are used and the join is windowed, which matters because a source address seen weeks apart is not the same session:
  ```kql
  let blocked = CommonSecurityLog
      | where TimeGenerated > ago(30d)
      | where RequestURL has "/wp-json/wp/v2/users"
      | where DeviceAction in~ ("block", "blocked", "deny", "denied")
      | project blockTime = TimeGenerated, SourceIP, blockedPath = RequestURL;
  let harvested = CommonSecurityLog
      | where TimeGenerated > ago(30d)
      | where RequestURL has_any ("/wp-json/wp/v2/posts", "wp-sitemap-users",
                                  "wp-sitemap.xml", "?author=", "&author=")
      | where DeviceAction !in~ ("block", "blocked", "deny", "denied")
      | project hitTime = TimeGenerated, SourceIP, harvestPath = RequestURL,
                ua = RequestClientApplication;
  blocked
  | join kind=inner (harvested) on SourceIP
  | where hitTime between (blockTime .. blockTime + 2h)
  | summarize harvestRequests = count(), paths = make_set(harvestPath, 20),
              agents = make_set(ua, 5),
              firstBlock = min(blockTime), lastHarvest = max(hitTime)
          by SourceIP
  | order by harvestRequests desc
  ```
  The two-hour window is the starting value. Unit 42's actor worked through staged reconnaissance rather than in one burst, so widen it if the estate's logs are sparse, and narrow it if crawler volume dominates.
  Login-burst query - The third stage is the one with consequences, and it is identifiable by username shape rather than by volume alone:
  ```spl
  index=web sourcetype=wordpress_auth action=failure
  | bin _time span=10m
  | stats dc(user) AS distinct_users, count AS attempts, values(user) AS users
          BY _time, src_ip
  | where (distinct_users >= 10 AND attempts >= 25)
  | sort - distinct_users
  ```
  Then compare the `users` values against the real author roster. A set of many variants of a few genuine staff names is the signature of a generated list; a set of unrelated email addresses is ordinary credential stuffing and belongs to a different hunt. Note the explicit parentheses around the `AND` pair in the `where`: Splunk binds `OR` more tightly than the implicit `AND`, so a later addition of an `OR` term to an unparenthesised clause silently changes the logic.
  Retrospective access-log grep - Cheaper than either query above and reaches as far back as log retention, which is usually much further than a SIEM window:
  ```bash
  grep -E 'wp-json/wp/v2/(users|posts)|wp-sitemap-users|[?&]author=[0-9]+' /var/log/nginx/access.log \
    | awk '{print $1}' \
    | sort \
    | uniq -c \
    | sort -rn \
    | head -40
  ```
  Aggregate by source first and investigate the heavy sources, rather than reading individual lines. A single address accounting for hundreds of author-bearing requests is the shape to pull apart.
  Estate scope, not host scope - The actor enumerated 12 subdomains before choosing a target, including an LMS, a student portal and an administration dashboard. Run this across every host in the estate and aggregate by source address, not per site. Enumeration spread thinly across twelve hosts looks like noise on each one and like a campaign in aggregate, and the WordPress site that gets brute-forced may not be the one that was enumerated first.
  Hardening that follows from the finding - Blocking the users endpoint alone is demonstrably insufficient, which is the report's practical lesson. If user disclosure matters for the site, the author object has to be suppressed from post responses, author sitemaps disabled, and author archive redirects turned off; otherwise accept that the roster is public and put the control on authentication instead, with rate limiting and multi-factor enforcement on `wp-login.php`.
  Adjacent coverage - [[H211]] covers a specific vulnerable-plugin REST endpoint on WordPress being used to exfiltrate API keys and configuration, which is a different endpoint and a different objective; this hunt is about core surfaces that are working as designed. [[H071]] and [[H399]] cover other WordPress attack paths and are worth running against any host that produces a hit here. [[M048]] scores web-application request anomalies volumetrically and is the right companion where the WAF block anchor is unavailable.

# H425

Unit 42 published an analysis in October 2026 of an actor operating under the handle BUGSTER, who used a jailbroken AI assistant to plan and execute several unrelated kinds of cybercrime. Most of the report concerns the AI toolchain. The part worth hunting is a four-stage attack on an Indian university's education platform, because stage two is a clean demonstration that the standard WordPress hardening advice protects the wrong thing.

The actor was blocked. The report is specific: they "extracted 13 active user IDs with real names via post author fields and author sitemaps, bypassing the Cloudflare Web Application Firewall (WAF) that blocked direct user endpoint access". The WAF did its job on `/wp-json/wp/v2/users`. The roster was retrieved anyway, from endpoints that are not user endpoints and were never in scope for that rule — post objects carry an author field, embedded post responses carry the author object, and WordPress core publishes author sitemaps so that search engines can read them.

That failure mode is what makes this detectable rather than merely instructive. A source that is blocked on the obvious path and then succeeds on the alternatives has announced its intent before it got what it came for. The 403 is the anchor; the successful author requests, which are indistinguishable from crawler traffic in isolation, become meaningful only because they follow it from the same address.

The consequence arrived two stages later. "A generator script produced a brute force tool with 117 usernames (derived from the enumeration) and 28 common passwords", and then "The actor's tool flagged one WordPress login as valid". The expansion from 13 real identities to 117 candidate usernames is itself a signature: the login log fills with many near-variants of a few genuine staff names, which looks nothing like credential stuffing from a breach corpus.

The scope lesson is in stage one. The actor "identified 12 subdomains including the main WordPress site, a learning management system (LMS), student portal and administration dashboard" before picking a target. Enumeration spread across twelve hosts is invisible on any single one, so this hunt belongs at the estate level, aggregated by source address.

## Why

- The control most sites rely on is incomplete by design, and this is a documented case of it failing in the wild. Any estate that considers user enumeration mitigated because the users endpoint returns 403 has the same gap, and the hunt tests for it directly.
- The WAF block converts ambiguous traffic into a sequence with intent. Author-bearing requests alone are crawler noise; the same requests following a block from the same source within a short window are an adversary working around a control.
- The attack produces a username list that is recognisable in the authentication log. Many formatted variants of a few real staff names is a distinct population from stuffed breach credentials, so the login burst can be attributed to this chain rather than to generic password spraying.
- Every stage lives in logs that are already collected and retained far longer than endpoint telemetry. Web access logs, WAF logs and authentication logs make this one of the cheapest hunts available, and the retrospective grep reaches back as far as retention allows.
- The enumeration preceded a successful credential guess against a platform holding student records. The same report documents a second university where the actor exfiltrated thousands of records including PII, so the stakes of the stage this hunt catches are established rather than hypothetical.
