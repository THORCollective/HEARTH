# H402

A FortiOS administrator cannot run commands on the appliance. That is the design. Unit 42 states it plainly: an administrator, "including a super_admin, operates within a restricted management command line with no shell access and no direct control over the appliance file system or its running processes."

But the daemons underneath that CLI run as root. And one of them will write a file wherever you tell it to.

`system.auto-script` is a legitimate FortiOS feature — scheduled CLI command sets. When you create one, the engine writes the script body to a file named after the object. Unit 42 found that "The auto-script object name is not sanitized, allowing a name containing traversal sequences to place the script body outside the intended directory, at any file system location."

So the object name becomes a file path. Name your auto-script `../../../../setup` and the engine writes your content four directories up, as root.

That is CVE-2025-61624, and it collapses the entire administrator-versus-root boundary. Which matters here because the attackers already *had* administrative credentials — recovered by brute-forcing the reversibly-encrypted passwords in FortiGate configurations they had stolen from a compromised FortiManager months earlier. They did not need to break in again. They needed to get out of the restricted CLI.

They used the primitive twice. `../../../../setup` dropped the loader for the PEERSTITCH implant ([[H403]]). `../../tmp/apache2/conf/md-acme.conf` planted an Apache configuration that turned certificate renewal into a reverse shell ([[H404]]). One vulnerability, two footholds.

Here is what makes this a genuinely good hunt: a path traversal sequence in a configuration object name has no benign form. None. A real auto-script is called `backup-nightly` or `failover-check`. Nothing legitimate puts `../` in one. And on most estates the legitimate set of auto-script objects is empty, which is about as clean a control sample as appliance hunting ever offers.

Unit 42 says the same, recommending defenders "Inspect FortiOS configuration revisions for system.auto-script objects containing path traversal strings (../../)".

Note the word *revisions*. Running `show system auto-script` on a compromised appliance will almost certainly return nothing, because the operators "Automatically deleted rogue administrator accounts, rogue VPN groups and auto-script objects (../../../../setup) shortly after execution." The object is gone. The revision that contained it is not — if you kept it somewhere other than the appliance.

The same applies to everything else here. Before running the malicious auto-scripts they executed `killall -9 miglogd` and `killall -9 syslogd` to stop local and remote logging, and afterwards `diagnose debug crashlog clear` to wipe the segmentation faults their memory injection had produced. Every local record was treated as deletable.

Which turns the absence into evidence. A gap in an appliance's syslog stream, bracketing a configuration change, is corroboration — and it is only visible if the stream was going somewhere else.

## Why

- **It converts an administrator into root, which are not the same thing on an appliance.** The restricted CLI *is* the privilege boundary in FortiOS, so arbitrary root file write is a total escalation rather than an incremental one.
- **A traversal sequence in an object name has no legitimate counterpart.** This is a rare appliance hunt where the signature is unambiguous rather than statistical.
- **The legitimate population is usually empty.** Most estates have no auto-script objects at all, so any object is worth reading and the false-positive surface is dominated by known automation accounts.
- **One primitive delivered two unrelated implants.** Both the memory-resident implant and the ACME reverse shell arrived through this object, making the object name the highest-leverage single observable in the intrusion.
- **The credential came from a prior theft, not a fresh intrusion.** This is the second act of a FortiManager compromise, which is why patching alone does not close it — Unit 42 notes the stolen trust material "remains valid until it is rotated."
- **The attacker deleted the object, so the hunt must read history rather than state.** Off-appliance configuration retention is the precondition; without it this activity leaves no configuration trace at all.
- **The logging gap is corroborating evidence, not merely an obstacle.** Terminating miglogd and syslogd before the change produces a silence that is itself detectable, provided logs are shipped off the device.
- **Edge appliances carry no endpoint agent.** There is no EDR on a FortiGate, so configuration revisions and forwarded logs are the entire available telemetry — which is an argument for treating them as crown-jewel data sources.
