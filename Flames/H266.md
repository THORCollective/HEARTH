false_positive_notes: |
  `reg save` is a real administrative and forensic command, so the naive single-hive query will produce benign
  hits. Expect legitimate volume from:
  - Backup, imaging and migration tooling (USMT, MDT/SCCM task sequences, disaster-recovery agents) that exports
    SYSTEM or SOFTWARE as part of a documented workflow.
  - IR and forensic collection tooling — KAPE, Velociraptor, CyLR — which legitimately grabs SAM, SECURITY and
    SYSTEM together. This is the single most important benign population because it looks *identical* to the
    attack. Attribute by the collection agent's image path, its signer, and the responder who ran it.
  - Vendor support scripts and hardening-baseline tooling exporting SYSTEM or SOFTWARE for offline comparison.
  - Administrators exporting a single hive to troubleshoot a policy or driver problem.
  The separators, in order of strength:
  (1) SECURITY is the tell. `HKLM\SECURITY` has almost no administrative reason to be exported — it exists to
      yield LSA secrets, cached domain credentials, and machine-account passwords. A SECURITY export by anything
      other than an enumerated forensic agent is close to conclusive on its own.
  (2) The *set*. SAM alone is useless without SYSTEM (the boot key). Two or three of the trio within the same
      logon session and a few minutes of each other is the offline-cracking recipe, not troubleshooting.
  (3) Output naming and location. Legitimate tooling writes to a named collection directory with descriptive
      filenames. `C:\Windows\Temp\s.dat` / `sy.dat` / `se.dat` are deliberately short and non-descriptive.
  (4) Parent lineage. reg.exe descended from an interactive `cmd.exe /d /Q /K`, a PowerShell one-liner, or a
      binary compiled on the host minutes earlier is not a backup job. In the source intrusion the same session
      had already used csc.exe to build its own beacon.
  (5) Archive-then-egress. A `Compress-Archive` naming those files, followed by outbound traffic from the same
      lineage, closes the loop.
  Enumerate your backup, imaging and IR collection agents as a named population before treating anything as
  actionable — do not suppress reg.exe or the hive names themselves.

    with the weakest legitimate justification.

  WHY THIS PATH AND NOT LSASS: the report notes no comsvcs.dll, procdump or Mimikatz-style LSASS memory access
  in this intrusion. `reg save` is a signed, in-box Microsoft binary performing a documented operation, it does
  not open a handle to LSASS, and it is unaffected by Credential Guard, PPL, or LSASS-access EDR rules. Estates
  that invested heavily in LSASS protection and never built coverage for the on-disk path have a live gap here.

  STARTING QUERY — Defender XDR:

    DeviceProcessEvents
    | where Timestamp > ago(30d)
    | where FileName =~ "reg.exe"
    | where ProcessCommandLine has_any ("save", "export")
    | where ProcessCommandLine has_any (@"HKLM\SAM", @"HKLM\SECURITY", @"HKLM\SYSTEM",
                                        "HKEY_LOCAL_MACHINE\\SAM", "HKEY_LOCAL_MACHINE\\SECURITY")
    | summarize HiveSet = make_set(ProcessCommandLine), Hives = dcount(ProcessCommandLine),
                FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
              by DeviceName, AccountName, InitiatingProcessFileName, bin(Timestamp, 10m)
    | where Hives >= 2 or HiveSet has "SECURITY"

  Then pivot to DeviceFileEvents for the archive:

    DeviceFileEvents
    | where Timestamp > ago(30d)
    | where FolderPath has @"C:\Windows\Temp"
    | where FileName endswith ".zip" or FileName endswith ".dat" or FileName endswith ".hiv"
    | where InitiatingProcessFileName in~ ("powershell.exe", "pwsh.exe", "cmd.exe", "reg.exe")

# H266

The credential-access phase of this intrusion never touched LSASS. It ran three commands:

```
reg save HKLM\SAM      C:\Windows\Temp\s.dat  /y
reg save HKLM\SYSTEM   C:\Windows\Temp\sy.dat /y
reg save HKLM\SECURITY C:\Windows\Temp\se.dat /y
```

and then packed the results into `C:\Windows\Temp\sy.zip`. That is a signed Microsoft binary performing a documented operation, writing three files to a directory that is written to constantly, with no handle opened against a protected process. Credential Guard does not apply. PPL does not apply. LSASS-access rules do not fire.

The discriminator is not `reg.exe` — it is *which hives* and *how many at once*. SAM without SYSTEM is worthless, so an operator always takes both. And `HKLM\SECURITY` has almost no legitimate administrative purpose: it exists to hold LSA secrets, cached domain credentials, and the machine account password. One SECURITY export from a host that is not running an enumerated forensic agent is worth an investigation on its own.

## Why

- **This is the LSASS-hardening bypass, and it is cheap.** Most estates have spent years building detection and prevention around LSASS memory access — Credential Guard, PPL, EDR handle-access rules, `comsvcs.dll MiniDump` signatures. `reg save` routes around all of it using an in-box signed binary, and the operator in this report chose it over any memory-dumping tool. Coverage built exclusively on the LSASS path leaves this wide open, and the payoff is the same: local NTLM hashes plus LSA secrets, offline, at leisure.

- **The SECURITY hive is the highest-signal, lowest-noise artifact available in credential access.** SAM and SYSTEM both have thin but real administrative justifications; SECURITY effectively does not. It contains cached domain logons, service account plaintexts, and the machine account password. Backup and imaging tooling generally does not need it. That makes a single `reg save HKLM\SECURITY` a near-binary indicator once forensic collection agents are enumerated — which is a rare thing in a technique family that is usually drowning in false positives.

- **Requiring the set turns an ambiguous event into an unambiguous one.** The false-positive problem here is entirely solved by counting rather than matching. An administrator exports one hive. A forensic tool exports all three, but from a named collection agent by an identified responder. An operator exports two or three from an interactive shell into short, non-descriptive filenames in `C:\Windows\Temp` and archives them within minutes. Those three populations separate cleanly on hive-count, output naming, and parent lineage — no volumetric baseline required.

- **The archive step is the exfiltration handle, and it is where you win time.** The hives on disk are not yet a breach; the `.zip` leaving the host is. `Compress-Archive` naming those files, or any new archive in `C:\Windows\Temp` created by a shell process, gives a second independent trigger and a concrete containment action — the credentials are still local at that moment. In the source intrusion the operator moved from these commands to authenticating against the domain controller with recovered domain-admin credentials within hours.

- **It sits mid-chain, so catching it collapses everything downstream.** The report's timeline runs ClickFix → multi-RAT staging → AdaptixC2 hands-on-keyboard → AD discovery → *this* → seeded-credential abuse → SMB and WinRM to the DC → VPN credential stuffing. The credential-access step is the hinge: everything before it is one compromised workstation, everything after it is domain-wide. Detection here is worth far more than detection at the phishing stage, and it is far more reliable than detecting the initial ClickFix paste.

- **HEARTH had no coverage for either hive-based technique.** Neither T1003.002 nor T1003.004 appears in any existing hunt, despite being one of the most durable credential-access paths on Windows and one of the first things a hands-on-keyboard operator reaches for once they hold SYSTEM.
