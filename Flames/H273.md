  Chaining CVE-2026-81578 (improper access control in the PaperCut web management interface) with
  CVE-2026-82078 (unsafe dynamic class loading in the database connection utilities) gives an unauthenticated

false_positive_notes: |
  The benign child-process population under `pc-app.exe` is small but it is not empty. Enumerate it before
  treating a single hit as an incident:
  - PaperCut's own scheduled maintenance, database backup, and log-rotation helpers, and its print-provider
    components communicating with the spooler. These recur on a schedule and have consistent command lines.
  - PaperCut upgrades and patch installers, which legitimately spawn shells and utilities — expect a burst of
    activity in the maintenance window, from an installer parent, on a day you can correlate to a change record.
  - Custom PaperCut integrations: scripted print scripts, external user-lookup and card-lookup programs,
    site-server sync scripts, and customer-written hooks. These are the largest genuine source of shell
    execution under this parent, and they are environment-specific — enumerate yours rather than assuming zero.
  - Backup agents and monitoring tools that happen to be parented under the Java process in some configurations.
  The separators:
  (1) TIME. Legitimate helpers run on a schedule or during a change window. Exploitation is unscheduled and,
      in these cases, completed in under two minutes.
  (2) COMMAND SHAPE. `whoami`, `ver`, `tasklist`, `net`, `ipconfig`, `systeminfo`, `nltest` chained with `&` is
      reconnaissance. A print script invoking a named executable with fixed arguments is not.
  (3) ENCODING. Base64 anywhere in a command line under this parent is not something a print workflow does.
  (4) CORROBORATION IN THE APP LOG. Every real hit here should have a matching Derby `pwn` database entry or a

  "Release 2" patch should be applied even if the first was installed. Fixed Windows v25 builds: PaperCut NG

  DETECTION — PROCESS LINEAGE. This is the core query. Defender XDR:

      DeviceProcessEvents
      | where InitiatingProcessFileName =~ "pc-app.exe"
         or (InitiatingProcessFileName in~ ("java.exe", "javaw.exe")
             and InitiatingProcessCommandLine has_any ("PaperCut", "pc-app", "server\\lib"))
      | where FileName in~ ("cmd.exe", "powershell.exe", "pwsh.exe", "wscript.exe", "cscript.exe",
                            "mshta.exe", "rundll32.exe", "regsvr32.exe", "certutil.exe", "curl.exe",
                            "bitsadmin.exe", "whoami.exe", "net.exe", "net1.exe", "ipconfig.exe",
                            "systeminfo.exe", "tasklist.exe", "nltest.exe", "hostname.exe", "arp.exe",
                            "reg.exe", "sc.exe", "schtasks.exe", "wmic.exe")
      | project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine,
                InitiatingProcessFileName, InitiatingProcessCommandLine, InitiatingProcessParentFileName

  Then widen it: after establishing the normal set, invert to `where FileName !in~ (<your enumerated benign
  helpers>)` so that a novel child process is the alert rather than a listed bad one. On a print server that
  inverted query is realistically runnable, which is not true of the same approach on a general web server.

  DETECTION — GRANDCHILDREN. `whoami` in these intrusions is a grandchild: `pc-app.exe` -> `cmd.exe` ->
  `whoami.exe`. A pure parent-child rule catches the `cmd.exe` hop only. In Sysmon, stitch via ProcessGuid /
  ParentProcessGuid; in Splunk use `parent_process_guid`; in Defender, `InitiatingProcessParentFileName` gives
  the grandparent directly. SigmaHQ's "Whoami.EXE Execution Anomaly" rule is useful here precisely because it is
  built as an inverted allowlist — it filters known-good parents and therefore fires naturally when the ancestry
  is a Java application server.

  DETECTION — APPLICATION LOGS, which is where this hunt is strongest. The payload deletes `server.log`, but it
  does NOT delete `derby.log`. Hunt for:
    - `DB URL: jdbc:derby:memory:pwn` in `server.log` (present if the log survived, immediately after a large
      encoded blob)
    - a second `Booting Derby version` entry in `derby.log` naming a database directory ending in `pwn`,
      timestamped just before command execution — described by Huntress as very high confidence
    - `ERROR No suitable driver found for jdbc:no:x`
    - `ERROR DatabaseUtils - Database error looking up cardID: VALUES CAST`
    - a missing, truncated, or zero-length `server.log`, which is itself the indicator
    - unexpected `.class` files under `[install]\server\lib\` and matching `.cmd`/`.out` files under
      `[install]\server\data\content\`

  useful reminder that the child process need not be a shell at all — the meaningful anomaly is that
  `pc-app.exe` parented anything unexpected.

  WHY THE PRIVILEGE CONTEXT MATTERS: the PaperCut Application Server runs as SYSTEM on Windows. Every command

# H273

Two customer environments, one of them compromised in under two minutes. The payload was not ransomware, not a beacon, not a web shell that stayed. It was `whoami & ver & tasklist`, base64-encoded, executed as SYSTEM inside the PaperCut Application Server, followed by a directory listing and then a careful cleanup of everything it touched.

Getting there took two bugs chained: an authorization check that trusts the page being rendered rather than the component doing the work, and a database utility that will load whatever class you hand it. The result is arbitrary Java bytecode running unauthenticated, at SYSTEM, on a print server that talks to your directory and to every workstation in the building.

The hunt is unusually clean because the host is unusually boring. A general-purpose web server spawns shells all day. `pc-app.exe` does not. On most PaperCut installations the child-process tree is close to empty — which means "anything unexpected under this parent" is a query you can actually run, and read, and act on.

## Why

- **The parent process is a near-empty namespace, and that is rare.** Web-shell hunting on `w3wp.exe` or `java.exe` generally is a tuning exercise, because those parents legitimately spawn things constantly. A dedicated print-management server does not. The realistic benign set is PaperCut's own maintenance helpers, upgrade installers, and whatever custom print scripts or external user-lookup programs the site has configured. That list can be enumerated in a week and then inverted, so the hunt alerts on novelty rather than on a list of bad binaries — which is the version that still works against the next payload.

- **The observed payload is discovery, which means this is an early-stage catch.** Huntress reports no secondary malware, no C2, no persistence recovered from either intrusion. The operator ran `whoami`, `ver`, `tasklist`, and a directory listing, and left. Whatever that reconnaissance was for has not happened yet on those hosts. Finding this lineage in your own telemetry is finding an intrusion at the point where the response is patch, isolate, and rotate — not restore from backup.

- **The application's own logs corroborate the process events, and one of them survives the cleanup.** The payload deletes `server.log`. It does not delete `derby.log`. A second "Booting Derby version" entry naming a database directory ending in `pwn`, timestamped immediately before the execution, is close to conclusive on its own, and it sits in a file the attacker overlooked. Pairing endpoint telemetry with two application log files means the hunt has an answer even when one side has been tampered with — and a missing or truncated `server.log` is itself a finding rather than a dead end.

- **The IOCs published are explicitly disposable, and the report says so.** `Udydn.class` and `Moo97.class` are five random alphanumeric characters. Huntress states plainly that "the observed five-character filenames may vary." A detection built on those two names has a shelf life of one campaign. The durable observables are structural: an unexpected `.class` file appearing under `server\lib` at all, a matching `.cmd`/`.out` pair under `server\data\content`, and `pc-app.exe` parenting a process it has never parented before.

- **SYSTEM privilege on this specific host makes the severity worse than the payload suggests.** The Application Server runs as SYSTEM, holds the configuration for directory integration and external user lookup, and is trusted by the print infrastructure across the estate. A discovery burst here is a foothold with full local privilege on a machine that most environments have never treated as tier-0 and rarely monitor as closely as a domain controller. Configuration tampering on this server — which CVE-2026-81578 permits directly — also reaches the external user-lookup path, which is worth checking independently of any process evidence.

- **Exposure, not just version, decides who is at risk — and nearly half the population cannot patch.** About 47% of tracked PaperCut installations run v23 or older, for which no fix exists. For those sites the only available control is taking the Application Server off the internet, and the only available detection is this one. That makes the hunt a standing control rather than an incident-response exercise, and it is worth scheduling rather than running once.

- **Preserve before you patch.** A restart or an upgrade can overwrite exactly the Derby and server log entries the hunt depends on. Copy `server\logs\` and `server\data\internal\derby.log` with metadata intact before touching the installation, or the answer to "were we already compromised" becomes unavailable at the moment you most want it.
