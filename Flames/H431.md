title: "A portable JavaScript or Java runtime, renamed but still carrying its real version metadata, executing a script out of a KB-prefixed folder created during a remote-support session"
hypothesis: >-
  After a user is talked into granting a remote-support session, the operator does not drop a malware binary — they drop an archive, extract it into a newly created update-themed folder under the user profile such as `%APPDATA%\Roaming\KB5062553\`, and run attacker-supplied script with a *portable, legitimate* language runtime carried in that archive. The executable is renamed, but it keeps the version metadata of the real runtime, so file-name blocklists and script-host controls both miss it: Bun executing a `.js` file is not Windows Script Host, and a renamed `bun.exe` is not on anyone's deny list. The durable observable is the mismatch between `FileName` and `ProcessVersionInfoOriginalFileName` on a process running from a user-writable staging path whose parent is a remote-support tool.

false_positive_notes: |
  Developer workstations run portable runtimes from user-writable paths as a matter of routine — `nvm`, `volta`, `fnm`, `sdkman`, Gradle and Maven wrappers, JetBrains bundled JDKs and `npx` caches all live under the user profile. Scope this hunt by host class first, or the engineering fleet will dominate every result. On non-developer hosts the same query is close to silent.
  The original-filename mismatch has legitimate sources. Installers stage renamed copies of their own payloads, some packagers rewrite the output name without touching the version resource, and self-updating tools run a copy named `*.tmp` or `*.new` mid-upgrade. Resolve the signer and the parent before escalating, and treat an unsigned image with a mismatch as a different finding from a signed one.
  `KB`-prefixed folder names are not inherently malicious. Windows Update and some OEM update tooling create `KB`-named directories, though in `%WINDIR%` and `%PROGRAMDATA%` rather than in `%APPDATA%\Roaming`. Anchor on the location, not the prefix.
  Java running a `.java` source file directly is a real and supported pattern since single-file source execution landed in JDK 11, so it is not odd on a developer host and is odd almost everywhere else.
  A result with no preceding remote session is not automatically clean. Microsoft is explicit that the runtime choice is interchangeable: "The Java variant confirms that runtime choice can change between deployments." Treat the staging shape as the finding and the session as corroboration, rather than requiring the session to be present.
notes: |
  Platform - Windows.
  What the report states - Microsoft Threat Intelligence investigated two human-operated intrusions that began with Teams messages and calls impersonating IT support, leading users to grant a remote session "primarily by guiding the user to open Quick Assist and provide the connection code." The staging step is described directly: commands launched during the session "created a KB-prefixed staging directory under the user’s profile, extracted the archive into that directory, and started the included payload with a portable Python, JavaScript, or Java runtime." On the renamed runtime: "In one JavaScript variant, a renamed executable retained version metadata identifying it as the Bun runtime and launched the staged loader."
  The report states the detection thesis better than a paraphrase can - "File names alone are weak indicators. The actionable pattern is a portable runtime launched from a newly created, user-writable staging directory after an unauthorized remote session, followed by script execution, discovery commands, or connections to identity infrastructure." And on how to establish identity: "Evaluate file identity through signer, original filename, product metadata, path, parent process, and behavior. A renamed executable can retain legitimate version information."
  Why the script-host controls do not help - Microsoft spells out the gap: "Do not assume controls for Windows script hosts automatically cover JavaScript executed through Bun or source files launched through Java." ASR rules and WSH restrictions are built around `wscript.exe`, `cscript.exe` and `mshta.exe`. A JavaScript payload run by Bun never touches any of them.
  Scope boundary - this hunt deliberately stops at the staging and execution step. The AD CS legs of the same incidents are already covered: ESC1 template abuse and certificate-based Kerberos in [[H152]], [[H153]], [[H154]] and [[H155]], the PetitPotam coercion and ESC8 relay in [[H161]], [[H293]] and [[H390]], and the AD CS posture surface in [[B047]]. The Teams-impersonation-to-Quick-Assist entry is covered by [[H118]], [[H182]] and [[M037]], with [[B021]] as the sanctioned-remote-access baseline.
  Primary query - this is Microsoft's published query, which keys on the original-filename metadata and the staging path:
  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(7d)
  | where ProcessVersionInfoOriginalFileName =~ "bun.exe"
      or FileName in~ ("bun.exe", "java.exe", "javaw.exe")
  | where ProcessCommandLine contains ".js"
      or ProcessCommandLine contains ".java"
  | where FolderPath matches regex
      @"(?i)\\AppData\\Roaming\\KB[0-9]+\\"
  | order by Timestamp desc
  ```
  Generalised query - the mismatch, not the names. This is the version that survives the next deployment choosing Deno, a portable Python, or a different folder prefix. `ProcessVersionInfoOriginalFileName` is the runtime's real identity and `FileName` is what the operator called it, so the two disagreeing on a process running from a user-writable path is the whole signal:
  ```kql
  let runtimes = dynamic(["bun.exe", "node.exe", "deno.exe", "java.exe", "javaw.exe",
                          "python.exe", "pythonw.exe", "php.exe", "ruby.exe", "perl.exe"]);
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where ProcessVersionInfoOriginalFileName in~ (runtimes)
  | where FileName !in~ (runtimes)
  | where FolderPath has_any (@"\AppData\", @"\Downloads\", @"\Public\", @"\Temp\", @"\ProgramData\")
  | project Timestamp, DeviceName, AccountName, FileName, FolderPath,
            ProcessVersionInfoOriginalFileName, ProcessVersionInfoProductName,
            ProcessVersionInfoCompanyName, ProcessCommandLine,
            InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessCommandLine
  | order by Timestamp desc
  ```
  Tying the staging directory to a remote session - the session and the extraction are minutes apart, so the join needs a time window; a join on `DeviceId` alone across a thirty-day lookback correlates unrelated days and will manufacture pairs:
  ```kql
  let rmm = DeviceProcessEvents
      | where Timestamp > ago(30d)
      | where FileName in~ ("quickassist.exe", "anydesk.exe", "teamviewer.exe",
                            "screenconnect.clientservice.exe", "atera.exe",
                            "splashtopstreamer.exe", "rustdesk.exe")
      | project SessionTime = Timestamp, DeviceId, DeviceName,
                RmmProcess = FileName, RmmCmd = ProcessCommandLine;
  let staged = DeviceFileEvents
      | where Timestamp > ago(30d)
      | where ActionType in ("FileCreated", "FileRenamed")
      | where FolderPath matches regex @"(?i)\\AppData\\Roaming\\KB[0-9]+\\"
          or (FolderPath has @"\AppData\Roaming\" and FileName endswith ".exe")
      | project StageTime = Timestamp, DeviceId, FolderPath, FileName,
                Writer = InitiatingProcessFileName, WriterCmd = InitiatingProcessCommandLine;
  rmm
  | join kind=inner (staged) on DeviceId
  | where StageTime between (SessionTime .. SessionTime + 60m)
  | project SessionTime, StageTime, DeviceName, RmmProcess, RmmCmd,
            FolderPath, FileName, Writer, WriterCmd
  | order by SessionTime desc
  ```
  Where the runtime goes next - Microsoft's third published query covers the egress leg, and the port list is the informative part because it reaches identity infrastructure rather than a web C2:
  ```kql
  DeviceNetworkEvents
  | where Timestamp > ago(7d)
  | where InitiatingProcessVersionInfoOriginalFileName =~ "bun.exe"
      or InitiatingProcessFileName in~ (
          "bun.exe", "java.exe", "javaw.exe")
  | where RemotePort in (80, 445, 636, 88)
  | where InitiatingProcessFolderPath matches regex
      @"(?i)\\AppData\\Roaming\\KB[0-9]+\\"
  | order by Timestamp desc
  ```
  Ports 445, 636 and 88 are SMB, LDAPS and Kerberos. The report records that "The compromised workstation also connected to domain infrastructure using LDAPS and SMB", and warns against expecting query content from the network layer: "TLS intentionally hides LDAP query content from passive network inspection." Use the network events to find the conversation and endpoint telemetry to establish what the process did.
  Sysmon equivalent - Sysmon Event ID 1 carries `OriginalFileName`, `Product` and `Company` next to `Image` and `ParentImage`, which is everything the generalised query needs, and `Hashes` for the signer lookup. Event ID 11 covers the extraction. If 4688 is the only available source, the fields are `New_Process_Name` and `Creator_Process_Name`, there is no original-filename field at all, and command-line capture must be enabled separately — so on a 4688-only estate this hunt degrades to path-and-parent matching and the mismatch half is unavailable.
  A note on the discovery commands - the staged payload "queried Windows version information, network configuration, and running processes", and Microsoft is clear these are not findings on their own: "These commands are common in administration, but they become high-value signals when it is launched by a renamed runtime from an uncommon location and follow an unexpected remote-support session." Do not build a separate hunt on the commands; use them to confirm one from this hunt.
  Expected, not observed by Microsoft - the report does not name the archive format, the specific `KB` numbers used, or the file names of the staged loaders beyond describing the pattern, and the figures showing the Bun and Java commands are sanitized. The regex above is written from the described shape (`\AppData\Roaming\KB` followed by digits) rather than from a published literal path. Microsoft also does not say the renamed runtime was signed, only that it "retained version metadata" — so treat signer state as something to establish per sample, not as a known.
  Response - preserve the staging directory and the archive before cleanup; the archive is the only artefact that identifies which packaging variant ran, and the extracted runtime's version resource is what confirms the mismatch. Then check whether the session that created it was authorised, because the report's own framing of the whole intrusion turns on that: the remote session "was the decisive transition in the attack."
  Closest existing coverage - [[H264]] and [[H173]] are the nearest hunts by subject and both cover a Bun runtime being fetched and run as a Node-evasion step during an npm install on a developer host or CI runner; the initial access, the parent lineage and the staging location are all different here, and this hunt keys on a renamed-but-metadata-intact binary rather than on a runtime download. [[H382]] covers editor-spawned download-and-execute chains on developer workstations. [[H278]] and [[H274]] key on `java.exe` lineage on application servers rather than on user workstations.

# H431

Both intrusions Microsoft Threat Intelligence describes in this report start the same way — a Teams message impersonating IT support, a Quick Assist session the user approves — and then do something more interesting than dropping malware. The operator places an archive in Downloads, extracts it into a newly created folder under the user profile with an update-themed name like `KB5062553`, and runs the payload with a *portable, legitimate* language runtime shipped inside the archive.

That choice defeats two whole classes of control at once. Application-control and file-name blocklists see an executable with an operator-chosen name. Script-host restrictions see nothing at all, because the JavaScript is not running under Windows Script Host. Microsoft says so outright: "Do not assume controls for Windows script hosts automatically cover JavaScript executed through Bun or source files launched through Java."

What survives is the metadata. A renamed executable still carries the version resource of the runtime it actually is, which is why Microsoft's guidance is to "Evaluate file identity through signer, original filename, product metadata, path, parent process, and behavior." In Defender terms that is `ProcessVersionInfoOriginalFileName` disagreeing with `FileName`; in Sysmon terms it is `OriginalFileName` disagreeing with `Image`. On a non-developer workstation, a process whose real identity is a language runtime, running under a different name, out of `%APPDATA%`, is close to a zero-volume query.

The report is also explicit that none of the specific names matter: "The Java variant confirms that runtime choice can change between deployments," and "File names alone are weak indicators. The actionable pattern is a portable runtime launched from a newly created, user-writable staging directory after an unauthorized remote session, followed by script execution, discovery commands, or connections to identity infrastructure." This hunt covers that pattern and deliberately leaves the certificate-abuse endgame to the AD CS hunts that already exist, because the staging step is the one place both incidents are identical and the one place neither was detected on arrival.

## Why

- The staging step is the common ancestor of both intrusions. One ended in ESC1 certificate abuse and DCSync, the other in PetitPotam and ESC8, but both passed through a portable runtime executing from a user-profile staging folder — so this is the single query that would have surfaced either.
- Version metadata is the one identity field the operator did not change. Renaming the binary is cheap; rebuilding it to strip or forge the version resource is not, and the report confirms the metadata survived intact.
- Script-host controls and ASR rules have a structural blind spot here, not a tuning problem. Bun running `.js` and Java running `.java` bypass `wscript.exe`, `cscript.exe` and `mshta.exe` entirely, so coverage built on those will report clean.
- The folder name is social engineering aimed at the user and at the responder. An `%APPDATA%\Roaming\KB`-prefixed directory reads as a Windows update to anyone glancing at a path list, while Windows Update itself never stages there.
- The next deployment will use a different runtime. Writing the hunt on the mismatch and the path class rather than on `bun.exe` means it keeps working when the archive ships Deno, a portable Python, or a JDK nobody has seen yet.
