  When an operator overwrites a system daemon in place — `crond`, `atd`, `agetty`, `polkitd`, `sshd` —

  `/usr/bin` and `/usr/sbin`. So they fix it: `touch -r /usr/bin/ssh /usr/bin/crond`, or the programmatic

  benign explanation on a file that a package manager also reports as checksum-mismatched. Hunt for
  `ctime` significantly newer than `mtime` on files in system binary directories, cluster the mtimes to
  find replacements sharing a donor timestamp, and confirm against package verification.

false_positive_notes: >-
  The ctime-newer-than-mtime signal is not rare on its own, and treating it as an alert rather than a
  hunting filter will bury you. Every `chmod`, `chown`, SELinux relabel, extended-attribute write,
  hard-link creation and `restorecon` run updates ctime without touching mtime, so a fresh SELinux relabel
  or a configuration-management run that enforces file modes will light up an entire directory at once.
  That mass-update shape is also the discriminator: legitimate metadata churn hits many files with the
  same ctime, while a timestomp hits one binary, or a handful of daemons, in isolation. Rank by rarity
  within the directory, not by the size of the gap. Package installation and upgrade legitimately produce
  both new mtimes and new ctimes together, so an upgraded package is not a hit — the hit is a file whose
  mtime matches the original install epoch while its ctime does not. Restored backups, `rsync -a`,
  `tar -p` extraction and container image layers all deliberately preserve mtime while writing fresh
  ctimes, so hosts recently rebuilt or restored need to be excluded by build date before the results
  are readable. Note also that filesystems differ: ext4 and XFS record a birth time that survives
  `touch`, but many overlay and network filesystems do not expose it, so do not build the hunt on crtime
  alone. Finally, `rpm -Va` reports mode and ownership drift constantly on hardened builds — filter to
  the checksum flag before comparing to timestamps, or the correlation is meaningless.

# H290

Timestomping is usually written up as a detail — a line in the defence-evasion column of an ATT&CK
mapping, noted and moved past. It is worth more attention than that on Linux, because of an asymmetry
the technique cannot escape.

An attacker replacing a system binary has a visible problem. On a host installed two years ago, every
file in `/usr/sbin` carries an mtime from the install or from a known patch window. A daemon that was
modified last Tuesday is conspicuous to anyone who runs `ls -lt`. The fix is trivial and well known:
copy the timestamps from a file that was not touched. Rapid7 observed exactly this in the DPRK campaign
against South Korean media and automotive organizations — the trojanized `/usr/bin/crond` had its
creation timestamp matched to `/usr/bin/ssh`, so a listing showed it as original-vintage.

The asymmetry is that `mtime` and `atime` are attacker-writable and `ctime` is not. `utimensat()` and
its relatives set the modification and access times to whatever the caller asks for, and in doing so
they perform a metadata write — which the kernel records by setting `ctime` to now. There is no portable
user-space call to move ctime backwards. So a successful timestomp always leaves behind the thing that
proves it happened. The forgery and the evidence of forgery are produced by the same syscall.

That gives the hunt a specific and unusually clean shape, which is worth stating precisely because it
is easy to get backwards. The finding is **not** a file with a recent mtime. It is a file whose mtime
sits back with its neighbours in the install epoch while its ctime sits alone in the recent past. Run
against package verification, it sharpens further: `rpm -Va` reports mtime drift with a `T` flag and
content drift with a `5` flag, so a binary flagged `5` but **not** `T` is a file whose contents changed
while its modification time did not — which is the definition of a completed timestomp, expressed in
the package manager output rather than inferred.

There is a second, cheaper pivot in this campaign that generalizes well. The operators trojanized several
daemons on the same host — `crond`, `atd`, `agetty`, `polkitd`, `sshd` — and a donor timestamp gets
reused. Clustering system binaries by identical mtime and then looking for clusters whose members have
scattered, recent ctimes finds the whole set from any one member. That is a better use of the artifact
than checking a single suspicious file, because it turns one hit into the full list of what was replaced.

The noise here is real and needs naming up front, because ctime moves for many innocent reasons — SELinux
relabels, `chmod` sweeps, configuration-management enforcement. All of those touch many files at once.
A timestomp touches one binary, or a small handful of daemons. Rarity within the directory is the
discriminator, not the size of the mtime-to-ctime gap.

[[H289]] covers the trojanized `sshd` from the same intrusion, and depends on this hunt in a direct way:
if the replaced binary was timestomped, the mtime on it will lie, so the integrity finding there has to
be read against the ctime evidence here. [[H291]] covers the selective log erasure the same operators
used, which is the other half of the anti-forensic work. [[B044]] covers the load-time variant, where
nothing on disk is replaced at all.

## Why

- **The forgery cannot be completed, and the gap it leaves is deterministic.** Every other anti-forensic
  technique in this campaign — log erasure, encrypted configs, counter scrubbing — genuinely destroys
  data. Timestomping does not. The syscall that backdates mtime necessarily advances ctime, so the act
  of hiding produces the artifact that reveals it. Detections built on a structural property of the
  kernel rather than on a tool signature do not decay, which makes this worth building once and running
  indefinitely.
- **It is the pivot that turns one compromised binary into the full inventory.** Operators reuse a donor
  timestamp. Clustering system binaries by identical mtime and inspecting clusters with scattered ctimes
  found `crond`, `atd`, `agetty`, `polkitd` and `sshd` together in the source campaign. During an
  incident this is the difference between remediating the daemon you happened to find and remediating
  the set, and it costs one query.
- **It directly undermines the timeline the rest of the investigation is built on.** Responders anchor
  on file modification times constantly — first-seen, dwell time, patient zero. A successful timestomp
  does not merely hide a file, it inserts a false anchor that pulls the reconstructed timeline years off.
  Establishing early whether mtimes on a host are trustworthy is prerequisite work for every other
  question, not an optional extra.
- **Linux estates usually have no file-integrity control, but they do ship the tooling.** `rpm -Va` and
  `debsums` already know every vendor checksum and are installed by default. The reason this is not
  routinely hunted is not capability, it is that nobody enumerated the legitimate exceptions — source
  builds, appliances, third-party repositories — so the output looks unreadable. That enumeration is a
  one-time cost, and afterwards the `5`-without-`T` correlation is close to a free high-fidelity signal.
- **The mass-update shape cleanly separates the benign explanations.** The standard objection to this
  hunt is that ctime moves all the time, and it does — for relabels, mode enforcement and attribute
  writes. But those hit directories, not individual daemons. Ranking by rarity within the directory
  converts the technique from something with an unmanageable false-positive rate into something with a
  handful of results per fleet sweep.
- **It corroborates findings that are otherwise arguable in isolation.** A single package-verification
  mismatch invites a shrug about a source build. A package-verification mismatch on a binary whose
  mtime was restored to match an unrelated system file does not. This hunt is most valuable not standing
  alone but as the second signal that makes [[H289]] and any other integrity finding actionable.
