title: An extra device added to an existing Entra MFA method after vishing-led AiTM session theft, with nothing removed and nothing broken
hypothesis: >-
  After voice or SMS vishing steers a user to a passkey-themed AiTM phishing page and the stolen
  session is replayed from an unmanaged device, the attacker does not remove the victim's MFA. They
  ADD an additional device to an EXISTING strong-authentication method — a phone number, an
  authenticator app or a software OTP — so the victim's own factor keeps working, no prompt fails,
  nothing appears broken and the user never calls the help desk. The observable is not a

  `StrongAuthenticationUserDetails`, where the count of `"Id"` occurrences is higher in `NewValue`
  than in `OldValue`. The invariant is additive registration with no corresponding deletion,
  performed inside a session that originated on a device the tenant does not manage.

false_positive_notes: |
  Be honest about the benign population here, because it is large and it is not going away. Users genuinely enrol new phones - every hardware refresh, every upgrade cycle, every lost-device replacement and every new-starter onboarding produces exactly this event, and in a mid-sized tenant that is a steady daily rate rather than a rarity. Help-desk-assisted re-registration is routine and produces the same audit record with the same shape. A user who adds the Authenticator app to a tablet alongside their phone, or who registers a second number for travel, is indistinguishable at the level of the audit event alone. The event therefore has real volume and low standalone fidelity, and any attempt to alert on it unqualified will fail. What makes it tractable is that the discriminator is not the registration but its CONTEXT, and the context is cheap to fetch. First, the sign-in in the hour preceding the registration - was it from a device the tenant manages and considers compliant, from a familiar ISP and location, and was it a fresh interactive authentication or a replayed session token? Legitimate enrolments overwhelmingly happen from a managed corporate device or from the user's habitual network; AiTM replay happens from an unmanaged host, frequently behind a hosting provider, VPN or anonymous proxy whose autonomous system never appears in that user's history. Second, the absence of a corresponding help-desk ticket within a sensible window, which converts a volume problem into a short list wherever ITSM data is joinable. Two specific traps. Do NOT hunt for a FIDO2 or passkey registration - "passkey" is the social-engineering pretext on the phishing page only, and Microsoft's reporting contains no actual FIDO2 credential registration, so a filter keyed on passkey registration will return a clean and entirely false negative. And do not mistake this for [[H163]] - that hunt keys on a deletion, and here there is no deletion to find, so [[H163]]'s correlation logic will not fire. On ambiguity of an empty result - if `RawEventData` is not being retained in full, or if your `CloudAppEvents` ingestion drops `ModifiedProperties`, the query returns zero rows for a collection reason rather than a behavioural one. Verify by deliberately adding a second device to a test account and confirming the record appears with both `OldValue` and `NewValue` populated before you trust a clean result.
notes: |
  NOVELTY - what makes this different from [[H163]]. HEARTH already covers self-service password reset followed by REMOVING the user's legitimate MFA methods and registering an attacker one. This is the opposite manoeuvre. The attacker ADDS a device to an EXISTING method and removes nothing, so the victim's own authenticator keeps prompting normally, no sign-in fails, no factor disappears from the user's security info page, and the user has no reason to contact support. Every detection built on `User deleted security info` or on a delete-then-add correlation is blind to it. The detection logic here is a DEVICE-COUNT COMPARISON inside a single `Update user.` record, not an event pairing across records.
  Core filter - Microsoft's own advanced-hunting KQL, reproduce verbatim - `CloudAppEvents | where ActionType == "Update user." | where tostring(RawEventData.ResultStatus) == "Success" | where RawEventData has_any ("StrongAuthenticationPhoneAppDetail", "StrongAuthenticationUserDetails") | extend AccountObjectId = extract(@"User_([a-f0-9\-]+)", 1, tostring(RawEventData.Target)) | where isnotempty(AccountObjectId) | mvexpand ModifiedProp = RawEventData.ModifiedProperties | where tostring(ModifiedProp.Name) in ("StrongAuthenticationPhoneAppDetail", "StrongAuthenticationUserDetails") | extend OldValue = tostring(ModifiedProp.OldValue), NewValue = tostring(ModifiedProp.NewValue) | extend OldDeviceCount = countof(OldValue, @"""Id"""), NewDeviceCount = countof(NewValue, @"""Id""") | where NewDeviceCount > OldDeviceCount`
  What that query actually does, step by step - it takes Entra ID directory audit activity as it lands in `CloudAppEvents` (Entra audit arrives under `ApplicationId` 11161), restricts to the `Update user.` action (note the TRAILING PERIOD in the action name, which is easy to lose), keeps only successful operations, and keeps only records whose raw payload mentions one of the two strong-authentication attributes. It pulls the target account object ID out of `RawEventData.Target` with a regex on the `User_<guid>` form, expands the `ModifiedProperties` array so each changed attribute becomes its own row, and then compares the number of `"Id"` occurrences in `NewValue` against `OldValue`. More `"Id"` entries after the change than before means a DEVICE WAS ADDED to the method rather than the method being replaced or removed. That count comparison is the entire novelty of the detection and is what makes it fire where a deletion-based rule does not.
  Audit-log fields named by the source - `StrongAuthenticationPhoneAppDetail`, `StrongAuthenticationUserDetails`, `DeviceToken`, `DeviceTag`, `AuthenticationType`. Pull `DeviceToken`, `DeviceTag` and `AuthenticationType` out of the `NewValue` blob for the added entry - they describe the device and factor type that was just enrolled and are the first thing to show the user when you contact them.
  Do NOT hunt for a passkey - "passkey" is the phishing LURE, not the artefact. The pretext page is passkey/SSO-themed and the vishing script talks about passkey enrolment, but what the attacker actually registers is a phone number, an authenticator app or a software OTP. Microsoft's reporting explicitly contains NO FIDO2 credential registration, NO Temporary Access Pass issuance, NO `Add member to role`, NO Conditional Access policy modification and NO mailbox-rule creation. Building the hunt on any of those returns nothing.
  Initial access, for scoping - voice and SMS vishing rather than email, directing the target to a passkey/SSO-themed adversary-in-the-middle phishing page. This matters for scoping because there will be no malicious email to find in the mail gateway, and the usual "pivot from the phish" reflex has nothing to pivot from.
  Phishing domains, verbatim - registered through Nicenic, frequently within hours of use, and often presented as a `companyname[.]maliciousdomain[.]com` subdomain so the target sees their own employer's name first - `passkeyhelpdesk[.]com`, `secure-passkey[.]com`, `setupmypasskey[.]com`, `add-passkey[.]com`, `integratedsso[.]com`, `oktasession[.]com`, `keysyncos[.]com`, `oskeysync[.]com`, `oskeysetup[.]com`, `oskeyregister[.]com`, `syncmykey[.]com`, `myconnectkey[.]com`, `validationsetupac[.]com`, `portalsetuphub[.]com`. Treat these as expired by the time you read this and hunt the PATTERN - a freshly registered domain bearing your own organisation's name as a subdomain label, resolved by a user shortly before an MFA device addition.
  Post-replay behaviour to correlate - the stolen session is replayed from an UNMANAGED device, after which the attacker signs into OfficeHome and performs reconnaissance through LEGITIMATE FIRST-PARTY APPLICATIONS - My Apps, My Sign-Ins, My Profile and Microsoft Approval Management. Observed session length is about one hour. None of those applications is inherently suspicious, which is the point - the discriminator is that they are being driven from an unmanaged device in a session that also produced an MFA device addition.
  Enrichment that turns a hit into an incident - for every hit, join back to `SigninLogs` on the account and the hour preceding the registration and answer four questions. (1) Was the originating device managed and compliant, or unmanaged? (2) Is the ISP or autonomous system one this user has ever used, or is it a hosting provider, VPN or anonymous proxy? (3) Did the same session subsequently touch My Sign-Ins or My Profile? (4) Is there a help-desk ticket for this user within a sensible window? Then check what followed - Microsoft Graph reconnaissance pivots to [[H169]], bulk file or SharePoint access pivots to [[M046]].
  Actors, for context not for filtering - Storm-3121, linked to ShinyHunters and to the Falcon extortion brand, and Storm-3032, splintered from BlackFile and operating under the Helix extortion banner. Activity tracked since May 2026. Do not build the hunt on actor attribution - the tradecraft here is generic enough that it is already being copied.
  Mitigations that are OUTPUTS of this hunt, not preconditions - restrict device code flow and authentication transfer flow through Conditional Access; block security-info registration when sign-in risk is high, using the `Register security information` user action; require a managed or compliant device for security-info registration; and enforce phishing-resistant MFA so that a replayed session cannot be used to enrol a weaker additional factor in the first place. A hunt that finds nothing but shows these controls are absent has still produced the right finding.
  Triage values - target user principal name and object ID, `AccountObjectId`, timestamp, `OldDeviceCount` and `NewDeviceCount`, the `DeviceToken` / `DeviceTag` / `AuthenticationType` of the added entry, the initiating IP and user agent, the preceding sign-in's `IPAddress`, ISP, `Location`, `DeviceDetail.isCompliant`, `RiskLevelDuringSignIn` and `CorrelationId`, the applications touched in the same session, and the presence or absence of a matching help-desk ticket.

# H329

Microsoft documented two extortion-motivated clusters — Storm-3121, linked to ShinyHunters and the Falcon brand, and Storm-3032, splintered from BlackFile and operating as Helix — running a passkey-themed social-engineering campaign against Entra ID tenants since May 2026. Initial access is voice and SMS vishing rather than email: the target is called, walked through a "passkey enrolment" pretext, and steered to an adversary-in-the-middle page on a domain registered hours earlier through Nicenic, often dressed as a subdomain carrying the victim's own company name. The stolen session is replayed from a device the tenant does not manage, and the attacker then does something quietly clever.

Rather than seizing the account by tearing down the victim's MFA, they leave it completely intact and add one more device to a method the user already has. The victim's authenticator keeps prompting. Nothing fails. No factor vanishes from their security info page. There is no reason to call the help desk, and therefore no early report. "Passkey" turns out to be only the story told on the phone — what actually gets registered is a phone number, an authenticator app or a software OTP, never a FIDO2 credential. The single audit artefact is a successful `Update user.` record in which the strong-authentication blob contains one more device than it did a moment earlier.

## Why

- **Additive persistence is quiet in a way that removal never is.** Every user-facing signal an organisation relies on for MFA tampering — a failed prompt, a missing factor, a confused user ringing the service desk — depends on the victim's own authentication breaking. Here it does not break, so the entire human detection layer is bypassed by design and the audit log is the only witness left.
- **The detection is a count comparison, which is why existing rules miss it.** [[H163]] and most published MFA-tampering content key on a deletion, or on a delete-then-register pairing within one session. Neither exists in this pattern. Comparing `"Id"` occurrences between `OldValue` and `NewValue` inside a single `ModifiedProperties` entry is a different query shape, and an organisation can have complete, well-tuned coverage of the removal case and zero coverage of this one.
- **The lure and the artefact are deliberately different things, and conflating them produces a false negative.** The whole campaign is branded around passkeys, so the instinctive filter is a passkey or FIDO2 registration event — which never occurs. A hunter who writes that query gets an empty result and a warm feeling. Naming the gap between pretext and artefact explicitly is the difference between a hunt that works and one that quietly does not.
- **The benign population is real, but the discriminators are cheap and external to the event.** Users genuinely enrol new phones constantly, so the registration record alone can never carry the alert. Both discriminators that do work — the management and network context of the preceding sign-in, and the presence of a help-desk ticket — live in data most tenants already have and can be joined in one step, which turns a high-volume event into a short list without any tuning of the event itself.
- **Recon through first-party applications defeats app-based scoping.** My Apps, My Sign-Ins, My Profile and Microsoft Approval Management are Microsoft's own, are used by everybody, and cannot be blocked or treated as suspicious. That leaves the originating device and session as the only usable frame — which is precisely the frame this hunt builds, and precisely why the mitigations it points at are all device- and risk-conditioned rather than application-conditioned.
