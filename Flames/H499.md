title: "The camouflage is the indicator — a non-Chrome process writing and deleting HKCU Chrome BrowserCrashRecovery, firing ten random-path requests at popular sites, and churning named temp files"
hypothesis: >-
  KUKURAT does not only hide its own activity, it manufactures other activity to hide inside. Unit 42
  describes a heuristic camouflage engine operating across three system axes - network, registry and
  files - whose purpose is to generate dummy, legitimate-looking activity on the endpoint so that the
  threat actor establishes a false baseline, and which the operator can toggle per axis at runtime
  with a C2 command. The engine's output is meant to be unremarkable in aggregate, and it is. What it
  is not is unremarkable in attribution, because all three streams of synthetic noise come from the
  implant's own process, and each stream has a shape no genuine application produces. On the registry
  axis the engine mimics Chrome crash recovery - it writes random data to
  HKCU\Software\Google\Chrome\BrowserCrashRecovery, reads the data back, then deletes the key, and
  afterwards opens and enumerates HKCU\Software\Google\Update\ClientState. Whatever Chrome itself
  does, a process that is not Chrome and not Google Update performing that exact write-read-delete
  sequence against Chrome''s own hive is the single highest-confidence observation in this hunt. On
  the network axis the engine emits 10 decoy HTTP requests per operational cycle to randomly selected
  domains drawn from a hard-coded list of 15 popular websites, using randomly generated URL paths -
  so look for small fixed-size bursts of requests to well-known sites whose paths are high-entropy
  and overwhelmingly fail, from a process that is not a browser. On the file axis it continuously
  creates temporary files with random names and randomised content in the %temp% directory and
  immediately deletes them, which produces a create-to-delete ratio near one and a lifetime measured
  in milliseconds, per process, that nothing legitimate matches. Hunt the noise, and the signal is
  underneath it.

false_positive_notes: |
  Chrome, Chromium-derived browsers and Google Update legitimately write across `HKCU\Software\Google\`, so the registry leg must be conditioned on the initiating process. Exclude the real browser and updater by full path and signer rather than by process name, because masquerading on the name is exactly what this family does elsewhere. A process that is genuinely Chrome, running from its installed location and correctly signed, is not this.

  Enterprise software inventory tools, browser-management agents and some endpoint products read `HKCU\Software\Google\Update\ClientState` to determine installed browser versions. Reading that key alone is therefore common and is not the finding; the finding is the write-read-delete cycle against `BrowserCrashRecovery` by the same process, with the `ClientState` enumeration following it.

  Temporary-file churn in `%temp%` is produced legitimately by installers, Office applications, build tooling, antivirus scanners and backup agents. The discriminators are the create-to-delete ratio, the file lifetime and the per-process concentration: legitimate tools create temporary files that live for the duration of a task and are cleaned up in batches, whereas this engine creates and immediately deletes each file in a continuous loop. Rank by lifetime percentile rather than by raw count or the top of the list will be a build server.

  Requests to popular websites are the background radiation of any estate, and the decoy traffic is designed to look like them. The usable features are the burst size, the path entropy, the response status distribution and the initiating process - not the destination, which is deliberately innocuous. Where a proxy records only destinations and not paths, this leg degrades sharply, and the registry leg should carry the hunt.

  Unit 42 notes that elements of this evasion technique have been documented across various malware families before, and that what distinguishes KUKURAT is coordinating camouflage across three vectors while enabling or disabling each at runtime. Two consequences for the hunt: a single-axis hit does not identify this family on its own, and an operator who has switched the engine off produces none of these artefacts, so a negative result is weak evidence. The default configuration Unit 42 recovered has all three axes set to zero, meaning off, and the operator enables them with a C2 command.

  The claim that random URL paths against popular sites will overwhelmingly return errors is inference about how those sites behave, not something Unit 42 measures. Validate the expected status distribution against the organisation's own proxy data before setting a threshold on it.
notes: |
  Registry leg (Sysmon Event IDs 12, 13 and 14; DeviceRegistryEvents) - Core filter: any registry operation under `HKCU\Software\Google\Chrome\BrowserCrashRecovery` where the initiating process is not the installed Chrome or Chromium-derived browser and not Google Update, and separately any enumeration of `HKCU\Software\Google\Update\ClientState` by the same process within the following minute. Triage values are `registry key path`, `registry value name`, `registry value data`, `operation type`, `initiating process path, command line and SHA256`, `signer`, `user` and `timestamp`.

      DeviceRegistryEvents
      | where Timestamp > ago(30d)
      | where RegistryKey has @"\Software\Google\Chrome\BrowserCrashRecovery"
      | where not (InitiatingProcessFolderPath has_any (@"\Google\Chrome\Application\", @"\Google\Update\", @"\Microsoft\EdgeUpdate\"))
      | summarize Ops = make_set(ActionType, 10), OpCount = count(), FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
          by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessSHA256, RegistryKey
      | order by OpCount desc

  Strong red flags: the same process shows a value write, a value read and a key delete against that path in sequence; the process folder path is under `AppData`, `ProgramData`, `Users\Public` or `Windows\Temp`; the process is unsigned; the write-read-delete cycle repeats on a regular cadence rather than once. Note that Sysmon Event IDs 12 and 13 do not record registry reads, so the read step of the cycle will not appear in Sysmon telemetry - look for the write and the delete and treat the pair as the observable, and use `DeviceRegistryEvents` or a product that records key-open operations for the enumeration step.

  File-churn leg (Sysmon Event IDs 11 and 23; DeviceFileEvents) - Core filter: per initiating process, the count of file creations in the per-user temporary directory and the count of deletions of those same paths, with the file lifetime computed as the gap between them. `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, so the create-and-delete pair is exactly what this table can answer. Rank processes by median lifetime ascending and by create-to-delete ratio near one.

      let creates =
          DeviceFileEvents
          | where Timestamp > ago(30d)
          | where ActionType == "FileCreated"
          | where FolderPath has @"\AppData\Local\Temp"
          | project CreateTime = Timestamp, DeviceId, DeviceName, FolderPath, FileName, InitiatingProcessFileName, InitiatingProcessFolderPath;
      let deletes =
          DeviceFileEvents
          | where Timestamp > ago(30d)
          | where ActionType == "FileDeleted"
          | where FolderPath has @"\AppData\Local\Temp"
          | project DeleteTime = Timestamp, DeviceId, FolderPath, FileName, InitiatingProcessFileName;
      creates
      | join kind=inner deletes on DeviceId, FolderPath, FileName, InitiatingProcessFileName
      | where DeleteTime between (CreateTime .. CreateTime + 5m)
      | extend Lifetime = DeleteTime - CreateTime
      | summarize Files = count(), MedianLifetime = percentile(Lifetime, 50), P90Lifetime = percentile(Lifetime, 90)
          by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath
      | where Files >= 50
      | order by MedianLifetime asc

  The bounded five-minute join window is required - joining creates to deletes on path alone over a 30-day lookback will pair unrelated files that happened to reuse a name. Strong red flags: a median lifetime under a second across hundreds of files; the filenames are high-entropy with no extension or a random extension; the same process also appears in the registry leg.

  Decoy-traffic leg (proxy logs, DNS logs, connection telemetry) - Core filter: per initiating process and per 10-minute bucket, request bursts whose size is a small fixed number, whose destinations are drawn repeatedly from the same small set of popular domains, whose URI paths have high character entropy, and whose HTTP status codes are predominantly 4xx. Unit 42 states the engine emits 10 decoy requests per operational cycle to randomly selected domains from a hard-coded list of 15 popular websites with randomly generated URL paths, so the measurable features are the burst cardinality, the small destination set and the path randomness - not the domains themselves, which are chosen precisely because they are above suspicion. Triage values are `source host`, `initiating process`, `destination domain`, `URI path`, `status code`, `bytes received`, `user agent` and `request count per bucket`. Strong red flags: a non-browser process generating requests to popular consumer websites at all; a user agent string that does not match any browser in the estate; a near-constant burst size across many cycles; the same process also holding a long-lived session to an unpopular destination, which is the real C2 that the noise exists to obscure.

  Pivoting from camouflage to implant - All three legs attribute to one process, so a hit on any of them yields the binary. Once identified, Unit 42's description of the family gives several corroborating checks. KUKURAT is C++ and almost entirely modular - nearly every post-exploitation capability is a separate DLL loaded dynamically at runtime directly from the C2, with at least 12 distinct named modules supported, which means the static binary deliberately contains no feature code and will look thin under analysis. It registers by posting hostname, username and integrity level, OS type and architecture, host IP address and a randomly generated agent instance ID to a `/register` node, then polls a `/heartbeat` node. Its recovered default configuration carries a 300000 millisecond heartbeat timeout, five command worker threads and a 600000 millisecond module execution timeout, alongside the three camouflage toggles. The HTTP/3 variant adds a natively coded `exec` command that spawns a subprocess with `CreateProcessA` and pipes terminal output back, which Unit 42 reads as a built-in survival option when no module DLL can be fetched. H498 covers the transport this process uses and H500 covers the watchdog and service components deployed alongside it.

  Scope note: HEARTH has hunts that touch decoy and noise behaviour in other contexts, and several that cover registry persistence under `HKCU`, but none that treat an implant's own camouflage output as the detection surface, and none that key on the Chrome crash-recovery mimicry or on per-process temporary-file lifetime. Searching the hunt corpus for the registry path and for this behaviour returned nothing before this hunt was written.

# H499

Unit 42's November 16, 2026 analysis of TGR-STA-0049 documents a capability in the KUKURAT backdoor that inverts the usual relationship between an implant and its telemetry. Rather than minimising what it leaves behind, KUKURAT ships a heuristic camouflage engine that deliberately generates additional, benign-looking activity across three axes — network, registry and files — so that the implant's real operations are buried inside a volume of artificial noise. Unit 42's assessment is that by manipulating the behavioural baseline of the endpoint it can obscure indicators of compromise, affecting automated detection and forensic effort alike. Each axis is independently switchable at runtime through a C2 command, and the default configuration Unit 42 recovered has all three off.

Unit 42 is careful to note that decoy activity is not itself new; what distinguishes this family is the coordination across three vectors with runtime control of each. For a hunter, that coordination is also the weakness. All three noise streams originate from the implant's process, and each has a distribution that no real application reproduces: a fixed burst of ten requests with random paths against a small set of popular sites, a write-read-delete cycle against Chrome's registry hive performed by something that is not Chrome, and temporary files created and destroyed in the same breath.

This hunt treats the camouflage as the indicator rather than as an obstacle.

## Why

- The registry leg is close to unambiguous and costs nothing to run. One key path, one process-exclusion list, and the result is a short list of processes impersonating Chrome's crash-recovery behaviour. There is no benign reason for an unsigned binary in a user-writable directory to be writing and deleting values under Chrome's own hive.
- Synthetic noise has to be cheap to generate, which is what makes it statistically distinctive. A fixed count of ten requests per cycle, randomly generated paths, and immediate deletion of every temporary file are all artefacts of a simple loop. Real applications have reasons for what they request and how long their files live, and those reasons produce ragged distributions.
- Attribution survives the noise even when the content does not. Every leg here is conditioned on the initiating process, so the engine's volume works against it: more noise means more events attributed to the same binary, which raises its rank rather than lowering it.
- The engine's existence is itself a scoping signal. An actor who built a runtime-switchable, three-axis camouflage system is expecting behavioural and baseline-driven detection, which is a reason to prioritise the host-side legs of this hunt over network inspection — particularly since Unit 42 reports both this family and its predecessor use HTTP/3 precisely to avoid being inspected.
