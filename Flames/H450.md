false_positive_notes: |
  `curl` is ubiquitous on servers and an allowlist built on the binary name alone is useless. The usable constraints are the *parent* and the *destination*:
  - Application code that legitimately fetches over HTTP. Many applications shell out to `curl` for webhooks, health checks, license checks or package metadata. These have stable destinations, appear on every host running that application, and are visible in the application's own source or configuration. Baseline the set of destinations each service account fetches over 30 days; the finding is a first-ever destination, especially a raw IP.
  - Deploy and configuration-management runs. Ansible, Chef, cloud-init, container entrypoints and `apt`/`yum` wrappers all fetch and execute. These run as root or as a deploy user, not as the web application's service account, and they coincide with a change window. Requiring the parent to be the *application* service account removes nearly all of them.
  - Monitoring agents and sidecars fetching their own configuration or updates. Allowlist by binary path and signature where available, and by the destination domain.
  - `nc` is the sharper indicator because modern distributions often do not install it. A `nc` or `ncat` execution under a web service account is worth a look even without the download chain; on hosts where it is genuinely used for port checks in start-up scripts, allowlist the specific script path.
  Chaining the stages is what makes the queue short. A fetch alone is noisy; a fetch to a new destination, followed by a `chmod` and an execution of the fetched file by the same service account, is not. Note also that many web servers run as root in containers, so the UID filter must be derived from the running configuration rather than assumed.
notes: |
  Linux process telemetry - Core filter: `execve` of `curl`, `wget`, `nc`, `ncat`, `socat`, `python3 -c`, or `perl -e` whose effective UID is the web application's service account (`www-data`, `nginx`, `apache`, `tomcat`, `httpd`, or the container's app user) and whose parent is the web server or application runtime (`nginx`, `httpd`, `apache2`, `php-fpm`, `java`, `node`, `python`, `uwsgi`, `gunicorn`). Triage values: full command line, parent command line, effective and real UID, working directory, container ID, `auid` (the login UID, which is `4294967295`/unset for a process descended from a daemon rather than from a login session). Strong red flags: a destination that is a bare IP address or a host with no DNS history on the box; `-o`/`-O` writing into the document root, `/tmp`, `/dev/shm` or `/var/tmp`; `nc` with `-e`, or a `nc` invocation piped into `sh`/`bash`; the command line being base64 or URL-encoded.
  Sample auditd-based reconstruction of the chain (run on the host, or over shipped `execve` records):
  ```bash
  ausearch -m EXECVE -ts recent --raw |
    aureport -i --executable |
    grep -Ei '(^|/)(curl|wget|nc|ncat|socat)$'
  ```
  Then, for each hit, confirm the lineage and the follow-on stages rather than treating the fetch as the finding. Use the PID from the `execve` record to pull the subsequent `chmod`/`fchmodat` and `execve` of the written path from the same session.
  File-write and permission telemetry - Core filter: a file created by the fetching process, followed within 60 seconds by a `chmod`, `fchmodat` or `chown` making it executable, followed by an `execve` of that exact path. Triage values: file path, file mode before and after, creating process command line, SHA-256 of the written file. Correlation: the path is the join key - a fetch, a mode change and an execution that all name the same path by one service account is a complete ingress-and-run chain in three events. Strong red flags: the written filename mimics a system binary or a dotfile; the path is inside the web document root (which also makes it a webshell candidate); the file is deleted immediately after execution.
  Network telemetry for the implant - Core filter: an outbound connection whose initiating process is the newly executed file, to a destination with no prior history on the host, persisting or reconnecting on an interval. Microsoft reports that "Storm-3358 has used the WISP, vshell, and AdaptixC2 RATs for persistence and lateral movement", all of which are open-source and whose network behaviour is configuration-dependent rather than fixed - so hunt the lineage and the novelty of the destination, not a fixed port or a known beacon interval. Triage values: destination IP and port, bytes in and out, connection duration, initiating process path and command line. Pivot: Microsoft's indicator list for this activity names several ARTEX server and RAT C2 addresses; check them, but treat them as perishable. Microsoft's own note is that "Threat actors regularly use proxies and virtual private networks (VPNs) to change the source IP address of malicious traffic and bypass static detections."
  Web log correlation, to recover the entry point - Core filter: for the application that owns the flagged service account, pull access and error log entries from the 15 minutes before the fetch. Microsoft reports Storm-3358 exploiting "security flaws including anonymous file upload and server-side request forgery (SSRF)". Look for unauthenticated POST or PUT requests to upload handlers returning 200 or 201, especially with a body size that does not match the application's normal uploads, and for requests whose parameters contain URLs or internal addresses (the SSRF shape). Triage values: method, path, status, body size, source IP, user agent, response time. Strong red flags: a successful upload immediately followed by a GET of a path under the upload directory (webshell first-touch); a burst of varied requests from one source before the successful one - Microsoft notes that agentic frameworks "send a wide variety of requests in a brief time and retry variations on the same technique or move on to next-stage actions at machine speed."
  Persistence to check once the host is confirmed - Core filter: Microsoft's Defender coverage table for this activity lists "Suspicious cron job creation" and "Possible Web Server compromise activity" among the detections. Enumerate `crontab -l` per user, `/etc/cron.*`, systemd user and system units created in the window, and new or modified files under every document root, comparing against the deployment artifact. Microsoft reports web shells used "for persistence on compromised web servers" in this activity.
  Expected, not observed by Microsoft: the Windows equivalent of this chain - `w3wp.exe` or a Java/Tomcat process spawning `curl.exe` or `certutil.exe` under an application pool identity - is the same tradecraft on a different platform and should be hunted with 4688 `New_Process_Name`/`Creator_Process_Name` or Sysmon Event ID 1. Microsoft's report describes this activity against internet-facing systems without naming the server operating system, and the utilities it names (netcat, curl) are quoted here in their Linux form.

# H450

Microsoft Threat Intelligence reports that "In October 2026, the financially motivated threat actor Storm-3358 began targeting organizations in the financial sector using the agentic AI offensive framework ARTEX." Storm-3358 is described as "a Cambodia-based intrusion cluster that primarily targets financial organizations in Southeast Asia, in addition to a smaller number of large financial organizations globally."

The tradecraft Microsoft describes is ordinary; the speed is not. "Microsoft has observed Storm-3358 use ARTEX in combination with conventional automated tools to scan systems connected to the public internet, exploit security flaws including anonymous file upload and server-side request forgery (SSRF), and install open-source remote access trojans (RATs)." The RATs are WISP, vshell and AdaptixC2, and the delivery mechanism is whatever the server already has: "Microsoft has observed ARTEX agents using utilities like netcat and curl to download these RATs to compromised systems."

That last point is the reason this hunt is built on process lineage rather than on indicators. An agent framework does not need to bring a loader, evade a signature or write a dropper - it reads the host, finds `curl`, and uses it. The resulting artefact is a legitimate, signed, expected binary doing something slightly out of place: being invoked by the web application's own service account, against a destination the host has never contacted, writing a file into a path the application can write to.

The chain is three events long and each one is cheap to collect on Linux: a fetch by a service account that should not fetch, a mode change making the result executable, and an execution of that same path. The web access log in front of it supplies the entry point - an anonymous upload or an SSRF-shaped request minutes earlier - which turns a suspicious process tree into an incident with a root cause.

HEARTH already hunts ARTEX by the residue the framework leaves in its own artefact names (H439, built on CrowdStrike's recovery of an exposed controller). That hunt depends on operators not renaming defaults. This one does not care what the framework is called: it hunts the shape the framework's actions take on a web server, which an operator cannot rename away.

## Why

- Agentic frameworks make living-off-the-land the default rather than a choice. There is no payload-development step to skip - the agent enumerates the host and composes a command from what it finds. That pushes detection value away from file artefacts and onto the question of which account invoked which existing binary.
- The service account is the constraint that makes `curl` huntable. A web application's identity exists to serve requests; it has no legitimate reason to fetch an executable from a new destination and run it. Anchoring on the parent and UID turns the noisiest binary on the server into a workable filter.
- Microsoft names the exploitation classes, and both are self-logging. Anonymous file upload leaves a successful unauthenticated POST with an anomalous body size, and SSRF leaves a request whose parameters carry a URL - both already in the access log of every application that was attacked this way, including for the attempts that failed.
- The RATs are open-source and therefore configuration-defined. WISP, vshell and AdaptixC2 have no fixed port, interval or protocol to pin a rule to, so the durable signal is the lineage that produced the implant and the novelty of the destination it calls, not the implant itself.
