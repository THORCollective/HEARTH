  The last collection step before encryption is not file shares or databases - it is the desktop
  messaging client's session directory, taken from every reachable machine at once. A script executed on
  a domain controller creates a single staging folder whose name is the plural of the messenger's session
  directory, walks the systems it can reach, and archives each user's session data with 7-Zip into that
  folder under a name composed of the host, the date and the username. Those directories hold

  password reset and no multi-factor prompt interrupts. The archives then leave through a browser to an
  external web service. The observables are a staging directory of per-host archives on a domain
  controller, remote reads of a user profile path that a domain controller has no reason to touch, and a
  browser uploading from a server account minutes before the locker runs.

false_positive_notes: |
  Archiving and remote profile access are both routine, so the hunt turns on where it happened, what the names look like, and what ran shortly afterwards.
  - Backup and migration tooling archives user profile directories legitimately and at scale, and some of it does so with per-host naming. Enumerate the backup and profile-migration products in use and the accounts they run as; the remaining population on a domain controller is usually empty.
  - Help desk staff legitimately collect application data from user profiles during troubleshooting, including messaging client folders. The discriminators are breadth and location: one profile collected to a technician workstation is support, many profiles collected into one folder on a domain controller is not.
  - 7-Zip is installed and used everywhere, including by administrators and by software packaging processes. Do not hunt the utility; hunt archives created on a domain controller, which is a host class where almost nothing should be producing them.
  - The script name in the reported case suggests Kerberos ticket theft rather than messaging data, and name-based hunting would have mapped it to the wrong behaviour entirely. Treat script names as leads to pivot on, never as the basis for the detection, and prefer the artefacts the script produced.
  - Legitimate browser use on a server is rare but not nonexistent - some administrators do download updates or open a console from a server desktop. The combination to escalate is a browser upload, from a server, with a large payload, correlated to archive creation in the same window.
  - Where the endpoint sensor was not deployed to domain controllers, none of the event-based filters will return anything and the USN journal is the only surviving record. Establishing which of your domain controllers have process and file telemetry is a prerequisite and frequently the first finding.
notes: |
  Source reporting is Kaspersky's November 11, 2026 analysis of Citrus Ransomware, which reaches victims through compromised contractors and encrypts with the Go-based Sn00py family, appending a `.citrus` extension. The escalation stage of the same intrusion is covered in [[H476]] and the policy-based deployment of the locker in [[H483]]; this hunt covers the collection step immediately before impact.
  What Kaspersky observed - "Right before encrypting the data, the attackers connected to one of the domain controllers and ran the PowerShell script steal_tgs.ps1, which created the tdatas directory. According to the NTFS USN journal, while the script ran, 7-Zip created archives in this directory with telltale names hinting at their contents", with the naming convention recorded as `<system_name>_<date>_<username>_tdata.zip`. Kaspersky's reading of the target is that "the directory name tdatas and the substring tdata may refer to the C:\Users\<username>\AppData\Roaming\Telegram Desktop\tdata directory. The Telegram messaging app uses this directory to store authorization keys, session data, app settings, and other session information." Its conclusion on the operation: "so the attackers were harvesting messaging app data from remote systems they could reach, packing it with 7-Zip and uploading it to an external web service through Google Chrome."
  Why the session directory is the prize - These directories hold authorization material rather than passwords. An archive of one is an authenticated session that a password reset does not revoke and a multi-factor prompt does not challenge, which puts it in the same class as a stolen browser session but against a channel where staff discuss incidents, share credentials in plain text, and coordinate recovery. In a ransomware operation, taking the messaging sessions of the people who will run the response is a direct attack on the response itself - though note that this is a reading of the value, not something Kaspersky states as the actors' intent.
  No existing HEARTH coverage - Grepped the corpus for the session-directory name and for messaging-client session theft and found nothing. [[H247]] covers a RAT keylogger plugin with financial keyword triggers alongside browser credential and wallet-extension theft, which is endpoint-local stealer behaviour rather than a domain-wide sweep. Nothing in the corpus covers desktop messaging session directories, and nothing covers a collection script staged and executed from a domain controller.
  Core filter 1, archives on a host that should not make them - The highest-value check. Hunt archive creation - any extension your estate uses, not only the one reported - on domain controllers and member servers, and group by directory. A single directory accumulating many archives whose names each contain a different hostname is the finding, and it is nearly self-explaining: no legitimate process names a file after another machine and drops it on a domain controller. Triage values are the staging directory, the number of distinct hostnames in the file names, the total size, the creating process and its parent, and the account.
  Core filter 2, the naming convention generalised - The reported convention is host, date, username and a target marker. Rather than matching that string, hunt for archives whose names contain a hostname that is not the host they sit on. That single comparison is cheap, needs no campaign knowledge, and catches any collection script that labels its output by source - which most of them do, because the operator needs to know which archive came from where.
  Core filter 3, the remote reads - On member systems, hunt Event ID 5145 for share access whose relative path includes a user profile application-data path, where the accessing account is a server or domain-controller account rather than the profile owner or a backup account. This is the collection seen from the other end and it survives even when the staging host has no file telemetry. Pair with Event ID 4624 logon type 3 to establish the source.
  Core filter 4, the script itself - Hunt PowerShell Event ID 4104 on domain controllers for script blocks that reference a user profile application-data path together with an archiving utility or a loop over computer names. Kaspersky recovered the script's name but notes it did not see the commands behind some of the group's scheduled tasks, so the content-level view here comes from script block logging rather than from the file, which the operators delete - the report records that they "delete their tools and output files and clear the command history."
  Core filter 5, the egress, and the clock - Hunt browser network activity originating on servers and domain controllers. A browser uploading a large payload from a domain controller is close to zero-noise in most estates. The timing matters for the response rather than the detection: Kaspersky places this step "right before encrypting the data", so a hit on this hunt against live activity is an indicator that encryption is minutes away, not hours, and should be treated as an in-progress intrusion rather than a collection finding.
  Sample Defender XDR query for archives naming other hosts, within the 30-day advanced hunting retention:
  ```kusto
  let lookback = 30d;
  let archives =
      DeviceFileEvents
      | where Timestamp > ago(lookback)
      | where ActionType == "FileCreated"
      | where FileName endswith ".zip" or FileName endswith ".7z" or FileName endswith ".rar"
      | project Timestamp, DeviceId, DeviceName, FileName, FolderPath,
                InitiatingProcessFileName, InitiatingProcessCommandLine,
                InitiatingProcessAccountName, FileSize;
  let hostnames =
      DeviceInfo
      | where Timestamp > ago(lookback)
      | distinct other_host = tolower(tostring(split(DeviceName, ".")[0]));
  archives
  | extend name_lower = tolower(FileName)
  | join kind=inner hostnames on $left.name_lower contains $right.other_host
  | where other_host != tolower(tostring(split(DeviceName, ".")[0]))
  | where strlen(other_host) > 4
  | summarize distinct_hosts_named = dcount(other_host),
              hosts_named = make_set(other_host, 20),
              archive_count = dcount(FileName),
              total_bytes = sum(FileSize),
              creators = make_set(InitiatingProcessFileName, 5),
              accounts = make_set(InitiatingProcessAccountName, 5)
            by DeviceName, FolderPath
  | where distinct_hosts_named >= 3
  | sort by distinct_hosts_named desc
  ```
  The `strlen` guard is there because short hostnames produce substring collisions against ordinary file names and would flood the result; set it from the shortest hostname in your estate. Requiring three distinct named hosts in one folder keeps single-host support collections out of the result while still catching a sweep early, and the account and creator columns are what separate a backup product from a script.
  Expected, not observed by Kaspersky - Which external web service received the archives, and how many systems the script reached. Kaspersky reports the upload went out "to an external web service through Google Chrome" and that the collection covered "remote systems they could reach", but does not name the service or give a count, so filter 5 above is written against the pattern rather than against a destination.
  Scope - Any Windows domain where staff run desktop messaging clients, which is most of them. The structural check - archives on a domain controller, archives named after other hosts - generalises to any pre-encryption collection sweep and is worth standing up as a permanent detection regardless of which application the next operator targets.

# H486

The script was called `steal_tgs.ps1`, which reads like Kerberos ticket theft.

It was not. It created a folder called `tdatas` on a domain controller and filled it with 7-Zip archives named `<host>_<date>_<user>_tdata.zip` — one per user, per machine, pulled from every system the operators could reach. Kaspersky reconstructed the whole thing from the NTFS USN journal.

`tdata` is the Telegram Desktop session directory. It holds authorization keys and session state.

So what left the building was not passwords. It was live, authenticated sessions. A password reset does not revoke them. A multi-factor prompt never fires, because nobody is logging in — the session already exists. And the archives went out through Chrome to an external web service.

Then the locker ran. Kaspersky places the collection "right before encrypting the data", which makes this hunt something closer to an alarm than an audit: finding it live means you have minutes, not hours.

The naming convention is the gift here, and not because of the specific string. The operators had to label the output by source — otherwise they would not know which archive came from where. That means there are archives on a domain controller whose file names contain other machines' hostnames.

No legitimate process does that. A domain controller does not produce zip files named after the workstations in accounting.

One lesson about the script name, too. Anyone hunting on `steal_tgs` would have gone looking for Kerberos tickets and found nothing, because the name describes the wrong thing. Pivot on names; detect on artefacts.

## Why

- **Session material bypasses the whole credential-response playbook.** Resetting passwords and enforcing MFA does nothing to an exported session directory. If messaging sessions were taken, the remediation is revoking sessions in the application itself — which means the finding has to be recognised as session theft and not filed as "some zip files".
- **The archives name their sources, which makes the hunt almost self-proving.** A comparison between the hostnames in a file name and the host the file sits on is one join over data most estates already collect, and the expected result is empty. That shape — cheap, generalisable, near-zero baseline — survives every rename the operators might make.
- **A domain controller is the wrong place for archives, full stop.** Scoping the check to domain controllers and member servers removes nearly all the benign archiving population in one step, without needing to know which utility or extension was used.
- **It lands at the point of maximum urgency.** This is the last step before encryption, so a live hit is an in-progress ransomware operation. That changes who gets called and how fast, and it is the reason the egress filter belongs in the hunt even though it is the noisiest one.
- **It attacks the response, not just the data.** Incident coordination happens in exactly these applications — credentials get pasted, recovery plans get discussed, vendors get contacted. Taking the responders' sessions on the way out is a sensible move for an operator, and worth considering when deciding where to run the recovery from. That reading is ours, not something the report asserts.
- **The USN journal saved the reconstruction.** The tools and output files were deleted and the command history cleared. A change journal recorded the file creations anyway, which is a reminder that it is a first-class forensic source on servers and not merely a filesystem implementation detail.
