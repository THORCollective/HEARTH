# H388

Editing `/etc/sudoers` on an appliance is pointless. The appliance rebuilds that file from a template, so the edit disappears at the next upgrade or configuration reset.

ARMORY CASTLE edited the template.

They created `/home/bomgar/sbin/post_boot.d` — a directory whose contents run automatically at startup — and dropped in a script called `zz-root-persist`. It checks whether the site service account already has a NOPASSWD sudo entry in `/ns/config/sudoers.template`, appends one if not, and then runs `'/ns/sbin/bt-sysconfig' --no-restart misc`, which makes the appliance reparse the template and rebuild the live `/etc/sudoers` immediately.

The consequence is the inversion that makes this worth its own hunt. Normally persistence has to survive remediation. This persistence is *applied by* remediation. Reset the appliance's configuration and it rebuilds `/etc/sudoers` from the template — including the attacker's line. Mandiant states it directly: the strategy "ensures the threat actor's privilege escalation survives system reboots and configuration resets, which would normally overwrite manual changes made directly to /etc/sudoers."

Three things about that script are the hunter's handholds.

The `zz-` prefix sorts it last in a directory executed in order, so it runs after everything else has settled. Vendor scripts are not named like that.

The `grep -qF` guard makes it idempotent — it can run at every single boot without ever duplicating its own line. That is how you write something intended to live on a box indefinitely, not how you write a one-off.

And the grant goes to the *web service account*. Not to a human administrator, not to a documented integration account. A web service account with `ALL=(ALL) NOPASSWD: ALL` has no legitimate reason to exist, and it is the thread back to the webshell foothold and the setuid shell in [[H387]].

Startup directories and templates are real vendor mechanisms, which means a new file in one is a question rather than a verdict. Upgrades rewrite templates. Support engineers occasionally add boot-time workarounds during a case. Some documented integrations genuinely want a sudo grant. All of that is resolved by a change record and a per-build baseline, not by broadening the query.

But there is one test that cuts through all of it, and it is worth building the hunt around: **check again after a reset.** A sudo grant that an administrator removed, or that a configuration reset should have cleared, and which is simply there again afterwards, is template-based persistence by definition. Nothing benign reinstalls itself.

Which leads to the remediation trap worth passing on with any finding. Mandiant recommends rebuilding rather than cleaning, and restoring "only a configuration backup dated before the exposure window." Restore a backup taken after the compromise and you restore the template — and the backdoor with it. Rotate credentials only after the rebuild, because rotating while the actor still controls the appliance just hands them the new ones.

## Why

- **Remediation re-applies this persistence instead of removing it.** The grant lives in the file the appliance rebuilds `/etc/sudoers` from, so a configuration reset — the natural response — restores it.
- **Surviving a reset is a test with no benign answer.** A NOPASSWD grant that reappears after being removed, or after a reset that should have cleared it, is template persistence. That makes the strongest query a temporal comparison rather than a static scan.
- **The grant recipient is the discriminator.** `ALL=(ALL) NOPASSWD: ALL` for a web service account is not something any documented integration requires, and it ties the persistence to the webshell foothold.
- **The script is written to be idempotent, which is a deliberate design tell.** A `grep -qF` guard before an append means it is expected to run at every boot forever without corrupting its own entry.
- **The `zz-` prefix is a scheduling choice, not a naming accident.** It sorts last in a directory whose scripts execute in order, so the change lands after the appliance has finished its own startup work.
- **Appliance config templates are an unwatched file class.** They are not in any software inventory, carry no file integrity monitoring, and a firmware upgrade legitimately rewrites them — which is exactly why a stale or absent baseline leaves them invisible.
- **The vendor utility that rebuilds the config is itself a high-signal command.** `bt-sysconfig` being invoked outside a maintenance window, from a web service account, is a narrow and queryable event.
- **The actor deleted logs throughout, so file state outranks command history.** Hunting the artefacts that remain — template content, startup directory contents, live sudoers — is more reliable than hoping the invocation was recorded.
- **It is a distinct mechanism from existing HEARTH sudo coverage.** [[H352]] abuses the PAM stack via a symlinked `/etc/pam.d/sudo`; this abuses a vendor configuration template and a vendor boot-script directory, with different telemetry and a different remediation failure mode.
