  A macOS stealer that writes a LaunchAgent now has to survive Ventura's Background Task Management, which tells

false_positive_notes: |
  Shell configuration files are modified legitimately and constantly, so the write event alone is not a finding — the responsible process is what carries the signal. Expect heavy benign volume from package managers and version managers that append to ~/.zshrc by design: Homebrew (brew shellenv), nvm, rbenv, pyenv, jenv, conda and mise all write initialisation lines, as do the installers for Docker Desktop, iTerm2 shell integration, Rosetta-era toolchains, the Google Cloud SDK and many JetBrains and VS Code shell-integration features. Editors (vim, nano, code, subl, emacs), the shells themselves, and git are the expected writers in Elastic's own rule exclusions. Filter on responsible process rather than on path: an unsigned or ad-hoc-signed Mach-O in /tmp, ~/Library/Application Support/ or a mounted DMG appending to ~/.zshrc is the case of interest, while brew doing it is not. Global git hooks are the quieter leg and the better discriminator — legitimate use of core.hooksPath does exist (Husky and Lefthook set per-repository hooks, and some enterprises deploy a managed global hooks directory), so baseline your developer population's hooks paths once and alert on new ones, and note that MacSync targets pre-commit and post-checkout specifically because they fire during normal work. The killall leg has almost no benign form: legitimate software does not terminate BTMNotificationAgent or BackgroundTaskManagementAgent, so treat any such signal as high-confidence regardless of what else is present. Apple-style reverse-domain LaunchAgent labels are the third discriminator — com.apple.* plist names in ~/Library/LaunchAgents/ are suspicious by construction, because Apple's own agents live in /System/Library/ and do not install per-user there.
notes: |
  Shell configuration writes (primary leg) - Core filter: ESF ES_EVENT_TYPE_NOTIFY_WRITE, _CREATE, _RENAME or _CLOSE where the target path is ~/.zshrc, ~/.zshenv, ~/.zprofile, ~/.zlogin, /etc/zshrc or /etc/zprofile, and the responsible process is NOT in the expected-writer set (zsh, bash, vim, nano, emacs, code, subl, git, brew, defaults, softwareupdate). Triage fields: responsible process path and team ID, code-signing flags (unsigned or ad-hoc is the strong case), the writing process's parent, and the appended content. Strong red flags: the appended line references a dot-prefixed path so it is hidden from Finder and plain ls (MacSync uses .repair-run), or it sources a file under ~/Library/Application Support/, ~/Library/Logs/ or /tmp. Practical triage commands: tail -20 ~/.zshrc, then grep -nE '^[^#]*(source|\.|eval|curl|base64|osascript)' ~/.zshrc ~/.zshenv ~/.zprofile, and ls -la ~ to surface dot-prefixed helpers.
  Global git hooks (the quiet leg) - Core filter: process execution of git config with --global and core.hooksPath, or ESF file writes creating or modifying files named pre-commit, post-checkout, post-merge, pre-push or post-commit under any hooks directory, including .git/hooks/ inside repositories and the directory named by core.hooksPath. Triage: git config --global --get core.hooksPath, then ls -la on the result and on ~/.git-templates/hooks/ (git init templates propagate hooks into every newly cloned repository, which is a broader blast radius than a single repo). Strong red flag: an executable hook whose contents are base64, curl-piped, or reference a path under ~/Library/Application Support/System — that directory name is deliberately chosen to read as an Apple component in a casual listing.
  Background Task Management suppression (highest-confidence leg) - Core filter: any process invoking killall or kill against BTMNotificationAgent, BackgroundTaskManagementAgent or NotificationCenter, visible as ESF ES_EVENT_TYPE_NOTIFY_SIGNAL or as a killall execution with those arguments. Corroborate in the Unified Log: log show --predicate 'subsystem == "com.apple.backgroundtaskmanagement"' --last 24h, and compare the BTM database state per host with sfltool dumpbtm to find agents registered without a corresponding user notification. This leg is what makes the campaign's persistence survivable, and it is the cleanest single query in the hunt.
  LaunchAgent masquerade - Core filter: new plists in ~/Library/LaunchAgents/ whose Label or filename uses an Apple reverse-domain prefix; MacSync registers com.apple.finder.agent, which is not an Apple agent. Triage: launchctl list | grep -i apple cross-referenced against the plists actually present in ~/Library/LaunchAgents/, then codesign -dvvv and spctl -a -vv against each ProgramArguments target. Apple's own launch agents ship in /System/Library/LaunchAgents/, so a com.apple.* label in a user LaunchAgents directory is a masquerade rather than an ambiguity. For the broader Launch Agent and Launch Daemon persistence pattern this pairs with, see [[H316]] and [[H284]].
  Supporting MacSync artefacts for scoping and retro-hunt - Staging directories /tmp/.sys- followed by a 16-digit random string; a self-copy under $HOME/Library/Application Support/System; a log or data file at $HOME/Library/Logs/.sysnotif-agent.log; Gatekeeper quarantine stripping with xattr -cr against the delivered app bundle; keychain access attempts using security set-generic-password-partition-list; anti-analysis via sysctl kern.hv_vmm_present and machdep.cpu.brand_string plus ptrace with PT_DENY_ATTACH; delivery from DMGs impersonating applications (a fake Toria crypto wallet) and installer.sh scripts retrieved from lookalike hosts including streamyard.appstore[.]com[.]mx and slack.apple03cloudstore[.]com, with iCloud Calendar published paths under caldav.icloud[.]com/published/2/ used as an intermediate delivery stage and a custom X-Upload-Token HTTP header on C2 uploads. The current payload is compiled Swift and Objective-C in fat Mach-O binaries for ARM64 and x86_64, replacing the earlier AppleScript and shell-script droppers, so hunting for osascript alone will miss this generation.
  Platform note - This hunt is macOS-only. The ATT&CK mapping for zsh and git-hook persistence is T1546.004 (Unix Shell Configuration Modification), which covers Linux and macOS; the source report's own mapping to T1547.013 (XDG Autostart Entries) is a Linux-only technique and does not apply to macOS. The Linux shell-profile equivalent of this behaviour is already covered by [[H005]], which hunts .bash_profile, .bashrc and .bash_login on Linux hosts; this hunt is the macOS counterpart and adds the git hooks, Apple-label masquerade and BTM-suppression legs that have no Linux analogue.

# H338

Kaspersky's 24 September 2026 analysis of MacSync is mostly a story about the payload growing up — AppleScript droppers replaced by compiled Swift and Objective-C, XOR replaced by Curve25519 key exchange, iCloud Calendar pressed into service as a delivery stage. The persistence, though, went in the opposite direction: it got simpler and lower to the ground. Instead of fighting for a LaunchDaemon or a TCC grant, MacSync appends a line to the user's own `~/.zshrc` pointing at a dot-prefixed `.repair-run` helper, sets a global git hooks path so `pre-commit` and `post-checkout` execute attacker code the next time a developer does ordinary work, and keeps a spare copy of itself in a directory named `~/Library/Application Support/System` — a name chosen to read as an Apple component in a casual listing. None of that needs elevation, a signed installer, or user consent. The interesting move is what it does about the one control designed to catch this: macOS Background Task Management notifies the user when a login item is registered, so the malware runs `killall` against `BTMNotificationAgent`, `BackgroundTaskManagementAgent` and `NotificationCenter`. That is the hunt's centre of gravity, because legitimate software has no reason to silence those agents, while the shell-configuration write it is protecting is something Homebrew does every day.

## Why

- Persistence here lands entirely inside user-owned files, so it needs no root, no signed installer and no TCC prompt, which means the controls organisations rely on for macOS malware — Gatekeeper, notarisation checks and consent dialogs — are never consulted and produce no evidence either way.
- The one macOS control purpose-built to surface this, Background Task Management's login-item notification, is actively defeated by terminating its agents, and that defeat is itself the cleanest signal in the chain: nothing benign kills `BTMNotificationAgent`, so the evasion is more detectable than the persistence it hides.
- The git hooks leg quietly widens the blast radius on exactly the hosts that matter most: a global `core.hooksPath` or a populated git template directory re-arms execution on every clone and every commit across all repositories a developer touches, turning one infection into repeated execution driven by the victim's normal workflow.
- Both writes sit in telemetry that macOS gives up readily — ESF file events on a short, well-known path list, and a `killall` execution — and the discriminator is the responsible process rather than the path, so a hunt that keys on unsigned or ad-hoc-signed writers filters out Homebrew, nvm and the editors while keeping the DMG-delivered Mach-O that matters.
