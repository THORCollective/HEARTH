false_positive_notes: |
  `dllhost.exe` is a normal and high-volume Windows process, and its usual parent is the service host that runs DcomLaunch. Parent-process anomaly is therefore the wrong filter for this hunt - the legitimate lineage is exactly what the activated instance also has. Filter on destination and lifetime instead.
  Plenty of legitimate COM servers run out-of-process and make network connections, including shell extensions, imaging and scanning components, Office integrations and management agents. Build the allowlist on the CLSID in the `/Processid` argument, because that identifies which COM server is actually hosted, and treat an unresolvable or unregistered CLSID as the signal rather than the connection itself.

  What the report states - Kaspersky describes the transition: RPC is used to create a remote COM object, which is then exploited through a binary object deserialization flaw and the TypeConfuseDelegate technique, and on success the payload "is loaded into the remote host process dllhost.exe". The report names this a "covert method for initiating a new process that loads the malicious payload" and explains the purpose in its own words: "This technique effectively separates the infection chain from its initial process, allowing it to bypass behavioral monitoring by security solutions such as EDR." Kaspersky also records that the implant calls `CoLockObjectExternal` to lock the object in memory, "ensuring that the dllhost.exe process created by RPC is not released by the system" - which is what turns a transient surrogate into a resident implant.
  Why ancestry is the wrong filter, stated plainly - most hunts for an implant in a signed Windows binary look for an implausible parent. Here the parent is the service host that legitimately launches COM surrogates, because the surrogate genuinely was launched by the COM infrastructure. The lineage is authentic. Only the reason for the activation is not. That is why the two usable discriminators are the hosted CLSID and the behaviour of the process after it starts.
  The single most specific artifact - the CLSID is on the command line. Windows starts a COM surrogate as `dllhost.exe /Processid:{GUID}`, so the GUID identifying which COM server is hosted is recorded in ordinary process-creation telemetry. Resolve every observed GUID against the registry on a known-good host of the same build: a GUID that resolves to nothing, or to a class whose registered server path does not exist, is wrong by construction.
  Check 1 - inventory the hosted CLSIDs and find the ones nothing claims:
  ```kusto
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where FileName =~ "dllhost.exe"
  | extend Clsid = extract(@"/[Pp]rocessid:\{?([0-9A-Fa-f-]{36})\}?", 1, ProcessCommandLine)
  | where isnotempty(Clsid)
  | summarize Hosts = dcount(DeviceId), Starts = count(),
              FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
            by Clsid
  | order by Hosts asc, Starts asc
  ```
  Sorting ascending is deliberate: a CLSID seen on one host a handful of times is the interesting tail, and a CLSID seen fleet-wide thousands of times is the Windows baseline. Resolve the rare ones under `HKLM\SOFTWARE\Classes\CLSID\{GUID}` before triaging further.
  Check 2 - a COM surrogate with an outbound session. This is the behaviour that does not depend on knowing any GUID in advance:
  ```kusto
  let window = 2m;
  let surrogates =
      DeviceProcessEvents
      | where Timestamp > ago(30d)
      | where FileName =~ "dllhost.exe"
      | project StartTime = Timestamp, DeviceId, DeviceName, ProcessId = ProcessId,
                Clsid = extract(@"/[Pp]rocessid:\{?([0-9A-Fa-f-]{36})\}?", 1, ProcessCommandLine);
  let egress =
      DeviceNetworkEvents
      | where Timestamp > ago(30d)
      | where InitiatingProcessFileName =~ "dllhost.exe"
      | where RemoteIPType == "Public"
      | project ConnTime = Timestamp, DeviceId, RemoteUrl, RemoteIP, RemotePort,
                InitiatingProcessId;
  surrogates
  | join kind=inner egress on DeviceId
  | where ConnTime between (StartTime .. StartTime + window)
  | where InitiatingProcessId == ProcessId
  | summarize Connections = count(), Destinations = dcount(RemoteIP),
              SampleUrl = any(RemoteUrl) by DeviceName, Clsid
  | order by Connections desc
  ```
  The join is bounded to a two-minute window and matched on process identifier as well as device, because a join on `DeviceId` alone over a 30-day lookback would pair a surrogate that started in week one with a connection from week four. Treat the window as the tie between a specific activation and its first beacon, not as the full beacon history - the implant Kaspersky describes waits before its first request, which is covered in the paired hunt below.
  Check 3 - the registry state keys. The implant keeps an exception-state record in GUID subkeys under the AppID hive, and derives those GUIDs from its C2 URL, so Kaspersky notes that "each C2 server has its own distinct set of bound GUIDs". That has a useful consequence: the GUID set is infrastructure-specific and will not match a published indicator list from a different victim. Hunt the shape instead - Sysmon Event ID 12 records for key create and delete under `HKLM\SOFTWARE\Classes\AppID`, clustered in time, for GUIDs that no installed product registers. Kaspersky describes the cleanup step as deleting nine such keys "one at a time, along with all of their child subkeys", so the deletion burst is as good a signal as the creation.
  Check 4 - the pinned TLS session, as a corroborator rather than a detection. The implant registers a server certificate validation callback and checks the certificate against a value from its own configuration, which means it does not care about the system trust store and will fail against an inspecting proxy in a characteristic way. If TLS interception is deployed, a process that consistently refuses the inspected certificate while every other process on the host accepts it is worth pulling. This is corroboration: on its own it is also what well-behaved pinned software looks like.
  Inference, not stated by Kaspersky - all four queries, the ascending-rarity ranking, the two-minute join windows, the process-identifier match and the TLS-interception heuristic are mine. Kaspersky published the mechanism and the artifacts, not detection logic. Kaspersky also states that the deserialization flaw in the remotely activated COM object is unknown, so this hunt does not assume a particular vulnerability or a patch that would prevent it; and the single CLSID named in the report should be treated as one observed instance rather than as the technique's fingerprint.
  Pairing - [[H437]] covers the loader stage that precedes this one, where the payload is reached through a second configuration file and a .resx resource beside a signed patch-management binary. [[M066]] covers the beacon behaviour of this same implant, whose polling interval is long enough that conventional beacon detection does not see it. A hit on any one of the three should be triaged against the other two, because they are stages of one chain.
  Closest existing coverage - no existing hunt covers COM surrogate activation as a process-tree evasion. Several hunts reference `dllhost.exe` in passing as an injection target or a masquerade host, which is a different proposition: there the implant is placed into an existing process, and here the COM infrastructure is induced to create the process legitimately, so there is no injection event to find and the lineage is genuinely correct.

# H438

Behavioral detection leans on process ancestry. An implant that gets itself created by the operating system's own COM infrastructure does not need to defeat that; it simply is not in the tree anyone is following.

That is what the last stage of NetamLoader does. Kaspersky describes the loader using RPC to activate a COM object, exploiting a deserialization flaw in it, and thereby landing the payload inside a newly created `dllhost.exe` — a "covert method for initiating a new process that loads the malicious payload." The report states the purpose without hedging: "This technique effectively separates the infection chain from its initial process, allowing it to bypass behavioral monitoring by security solutions such as EDR." A call to `CoLockObjectExternal` then keeps the object alive, "ensuring that the dllhost.exe process created by RPC is not released by the system," which converts a momentary surrogate into a resident implant.

So the usual filter is useless here. A hunt that looks for `dllhost.exe` with a suspicious parent finds nothing, because the parent is the service host that legitimately launches COM surrogates, and it genuinely did launch this one. The path is right, the signature is Microsoft's, the lineage is authentic. Only the reason for the activation is false.

Two things do separate it. The first is on the command line: Windows starts a surrogate as `dllhost.exe /Processid:{GUID}`, so ordinary process-creation telemetry already records which COM server is being hosted. Inventory those GUIDs across the fleet, sort by rarity rather than volume, and resolve the tail against the registry — a GUID that resolves to no registered class, or to a server path that does not exist, is wrong independent of any threat intelligence. The second is behavior after start: a COM surrogate with a public outbound session, kept alive far longer than its registered class warrants, and no COM client to account for it.

The registry artifact is worth collecting even though it will not match anyone else's indicator list. The implant stores exception state in GUID subkeys under the AppID hive and derives those GUIDs from its C2 URL, so, as Kaspersky notes, "each C2 server has its own distinct set of bound GUIDs." Published GUIDs from one victim are therefore useless at another. The shape — a cluster of AppID subkeys that no installed product claims, created and later deleted nine at a time — travels fine.

## Why

- The evasion targets the detection logic rather than the telemetry: the process tree is genuinely correct, so ancestry-based analytics return nothing while the implant runs in plain sight.
- `dllhost.exe` is signed by Microsoft, lives in System32 and starts thousands of times in a normal fleet, which makes it one of the cheapest places to hide and one of the most commonly tuned-down images.
- The hosted CLSID is already in standard process-creation telemetry, so the most specific discriminator in this hunt needs no new collection — only the discipline to rank by rarity instead of volume.
- The registry state keys are derived from the C2 URL, which means indicator sharing cannot carry this one between victims and a structural hunt is the only portable approach.
- The implant validates its server certificate against its own configured value, so TLS interception does not yield plaintext and the usual network-content detections do not apply.
