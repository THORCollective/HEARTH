false_positive_notes: |
  Every one of these three surfaces has a large, legitimate, actively-used population on exactly the hosts being hunted, which is why the hunt is built on reconciliation rather than on presence. Developers install many legitimate VS Code extensions, and a lot of them ship activation events that run at startup — presence of an extension, or even a startup activation, proves nothing on its own. The discriminator is that "GitHub Copilot Helper" is not a Marketplace extension; a real Copilot install is publisher `GitHub`, extension IDs `github.copilot` and `github.copilot-chat`, and it is resolvable in the Marketplace with a matching publisher signature. An extension directory present on disk that has no Marketplace-resolvable publisher/ID pair is the exception worth pulling, and that check is mechanical once you have the per-host extension inventory. Git hooks are similarly a real, common, legitimate tool - Husky, pre-commit, lint-staged and lefthook all install genuine executable hooks into `.git/hooks/`, and in a JavaScript shop Husky in particular will be near-universal. The reconciliation there is cheap because those tools declare themselves - Husky hooks carry a Husky header and the repo has `husky` in `devDependencies` and usually a `.husky/` directory; pre-commit hooks carry a `pre-commit` generated banner and the repo has `.pre-commit-config.yaml`; lefthook hooks reference `lefthook.yml`. A hook file whose content maps to no declared tool in that repository is the anomaly, and the `# shepherd-persist;` marker settles it outright where it survives. The strongest structural point in favour of hunting this surface at all is that the default hook set git creates is entirely `.sample`-suffixed and therefore inert, so ANY non-sample hook file is already an exception - the volume problem is bounded by the number of repos with a hook framework, not by the number of repos. For the dependency angle, bundled `node_modules` directories committed into a repository are not unheard of in older projects and in vendored builds, so the discriminator is not "bundled" alone - it is a package present in `node_modules` with no corresponding entry in `package-lock.json` / `yarn.lock` / `pnpm-lock.yaml`, and a name-version pair (`colorized_terminal@2.1.0`, `pretty-log@2.1.0`) that does not resolve on the public registry. An empty result here is ambiguous for a very specific reason - most EDR deployments do not retain file-create events for user-profile paths at this depth, and almost none enumerate git working trees at all, so a clean sweep is far more likely to mean the collection does not exist than that the estate is clean. Confirm Event ID 11 retention covers `%USERPROFILE%\.vscode\extensions\` before recording a true negative, and treat the repo-tree enumeration as a separate, actively-run inventory rather than as a query over existing logs.

# H326

The same Securelist reporting on Mirage Kitten that describes the macOS LaunchAgent branch also documents a Windows branch that persists somewhere most detection programs never look — inside the developer's own toolchain. The RAT installs a VS Code extension named "GitHub Copilot Helper" with the activation event `StartupFinished`, so it runs every time the IDE launches, and it exposes explicit `persist:vscode` and `persist:vscode:remove` operator commands, meaning this is managed, first-class persistence rather than an incidental artefact. It injects code into `.git/hooks/post-merge` and `.git/hooks/post-checkout` tagged `# shepherd-persist;`, so the implant re-executes as a side effect of an ordinary `git pull` or `git checkout` — no scheduled task, no registry key, and nothing that appears in the repository's tracked contents, because git hooks are never committed or cloned. And it delivers trojanized `colorized_terminal` v2.1.0 and `pretty-log` v2.1.0 by bundling them straight into `node_modules` rather than publishing them, which means `npm audit`, lockfile review and registry-side supply-chain monitoring all return clean. Supporting it are a renamed `nodew.exe`, an `HKCU` Run key, payloads under `%APPDATA%\Microsoft\` and `%LOCALAPPDATA%\Intel\`, and a loopback listener whose port falls in a narrow derived band.

## Why

- **Developer workstations are a distinct asset class with a distinct telemetry surface, and most programs cover neither.** The persistence here is not in the registry, the service table, WMI or the Task Scheduler — it is in `.vscode\extensions\` and `.git\hooks\`, two directories that endpoint file telemetry frequently does not retain and that no standard persistence sweep enumerates. The hunt's first practical output is not a detection but a fact about the estate: whether you can see writes to those paths at all.
- **Git hooks are invisible to every control the repository itself provides.** Hooks live in `.git/hooks/`, which is not tracked, not committed, not cloned and not pushed. Code review, branch protection, required reviewers, signed commits and CI pipelines therefore all see nothing, by design rather than by oversight. Combine that with a trigger fired by `git pull` and `git checkout` and the operator gets high-frequency re-execution with no scheduled task and no registry key to find.
- **The default hook set is entirely `.sample`-suffixed, which bounds the problem.** Git writes a dozen example hooks at `git init` and every one of them is inert because of the suffix. That means any executable hook file at all is already an exception — the hunt does not have to define "suspicious hook content", only "hook that is not a sample". The legitimate populations that remain (Husky, pre-commit, lint-staged, lefthook) all declare themselves in the repository, so reconciling a hook against a declared tool is a mechanical check rather than a judgement call.
- **Bundling into `node_modules` defeats the entire supply-chain control stack at once.** `npm audit`, lockfile review, registry-side monitoring, dependency-confusion alerting and SBOM generation from the manifest all operate on what the project *declares*. A package that was never published and is simply present on disk is declared nowhere, so every one of those controls reports clean. The only check that works is a filesystem one — reconcile what is physically in `node_modules` against the lockfile's resolved set.
- **The loopback port band is a free, content-free check.** V1 binds `127.0.0.1:48739` and V2 derives a port in the range 41984–46983 from the agent ID. Listening-port inventory is cheap, it is available from `Get-NetTCPConnection` without any EDR at all, and a `node` process bound to loopback in that narrow band on a developer host is specific enough to be worth running as a standing sweep alongside the file-based work.
