false_positive_notes: |
  WinPTY is legitimate open-source software and is bundled widely. Git for Windows ships it, several terminal emulators and editors use it, and Python and Node packages wrap it, so `winpty.dll` and `winpty-agent.exe` exist legitimately on a large share of developer workstations. The discriminators are the location and the host - a copy inside a Git installation directory or a package's site-packages tree is expected; a copy written into `%TEMP%` by a process that is not an installer, on a file server or a non-developer workstation, is not.

  Note also that the library is nearly obsolete in its original role. WinPTY existed because Windows had no pseudo-console API; ConPTY has shipped since Windows 10 version 1809 and modern tooling targets it instead. That makes a fresh WinPTY drop on a current Windows build an odd choice for legitimate software and a reasonable one for a self-contained implant that does not want to depend on the host.

  `MyInputPipe` is a literal name, not a pattern, and an operator can change it in the next build - the report publishes it because it is what this module compiles with. Keep the named-pipe leg broad as well as specific - a pipe created by a process that then spawns `cmd.exe`, whatever the pipe is called, is the structural version of the same finding. Legitimate software creates named pipes constantly, so pipe creation alone is noise; pipe creation plus a `cmd.exe` child plus a non-console parent is not.

  Pseudo-console use by legitimate remote-administration tools produces a similar process shape, including a `cmd.exe` with no visible window and piped handles. Reconcile against the estate's sanctioned remote-support inventory first - the question is whether an approved tool explains the parent process, not whether the shape is unusual.

  The exit string `hklnwqxaa123` is an arbitrary token and will not appear in telemetry unless command content is captured, which it usually is not. Treat it as forensic confirmation on a recovered sample rather than a hunting input.

  The 80 by 25 terminal size is the module's hard-coded configuration and is not visible in standard endpoint telemetry at all. It is included because it is a recognisable constant in memory on a host already being examined, not because it is queryable.
notes: |
  Leg one, the binary drop (DeviceFileEvents or Sysmon 11) - Core filter: either WinPTY file created anywhere under a temporary or user-writable path, with the writing process captured.

      DeviceFileEvents
      | where Timestamp > ago(30d)
      | where ActionType in ("FileCreated", "FileModified")
      | where FileName in~ ("winpty.dll", "winpty-agent.exe")
      | where FolderPath has @"\Temp" or FolderPath has @"\AppData" or FolderPath has @"\ProgramData"
      | project Timestamp, DeviceName, FolderPath, FileName, SHA256,
                InitiatingProcessFileName, InitiatingProcessFolderPath,
                InitiatingProcessParentFileName, InitiatingProcessCommandLine
      | order by Timestamp desc

  Thirty days is the whole Defender advanced hunting retention. Triage values are the writing process and its own path. Red flags in weight order - the writer is a signed vendor binary running from `C:\Windows\System32` or `C:\ProgramData`, which is the ShadowCloud staging shape that H505 hunts; the writer is not an installer, a package manager, or a development tool; both files appear within seconds of each other, because the module decodes and drops them together; the host has no developer tooling installed at all, in which case the drop has no innocent explanation.

  Leg two, the pipe (Sysmon 17 and 18) - Core filter: pipe creation where `PipeName` is `\MyInputPipe`, and more broadly any pipe created by a process that goes on to spawn a command interpreter.

      Sysmon Event ID 17 where PipeName contains "MyInputPipe"
      Sysmon Event ID 18 where PipeName contains "MyInputPipe"

  Event 17 gives the creating process and Event 18 the connecting one, which matters here because the report describes two separate modules on the two ends - the WinPTY shell creates the pipe and the command-forwarder module connects to it to inject commands. Both ends inside the same process tree, or both inside the same backdoor process, is the expected picture. The structural version of this query, for when the name changes, is a pipe-creating process that within the same minute becomes the parent of `cmd.exe`.

  Leg three, the shell itself (Sysmon 1, or 4688) - Core filter: `cmd.exe` whose parent is neither a console host, a script host, a terminal application, nor a legitimate remote-support agent. Note the field names - Sysmon exposes `Image`, `ParentImage` and `IntegrityLevel`; Windows Security 4688 exposes `New_Process_Name` and `Creator_Process_Name` and has no Sysmon-style integrity field, so a 4688 query written with Sysmon field names returns nothing silently. Red flags - a `cmd.exe` parented by `javaw.exe`, `start.exe`, `pythonw.exe` or `zoomit.exe`, the four sideload hosts the report names; a `cmd.exe` with no window and a long-lived session; `winpty-agent.exe` present anywhere in the tree.

  Note on what the module actually does, because it changes the triage question. This is not a `cmd.exe /c` one-shot. A pseudo-console gives the operator a real terminal - prompts, interactive programs, line editing, anything that needs a console to work. Commands arriving through `MyInputPipe` are not individually visible as process creations at all; they are keystrokes into an existing shell. So an estate relying on command-line logging to see what an operator did will see the `cmd.exe` and none of the session. The pipe and the shell's lifetime are therefore the evidence, and full process-tree capture or ETW console telemetry is what recovers the content.

  Leg four, image loads from temporary paths (Sysmon 7 or DeviceImageLoadEvents) - `winpty.dll` loaded from `%TEMP%` by a process whose on-disk image lives elsewhere. `DeviceImageLoadEvents` carries no signature columns, so join `DeviceFileCertificateInfo` on SHA1 if signer state is needed; Sysmon 7 has it inline.

  Related modules in the same toolkit, worth sweeping on any hit - the report enumerates COFF modules for Mimikatz invoked as `imzimzgo 2.2.0 x64` with `sekurlsa::logonpasswords full` and `lsadump::sam`, browser cookie theft via CookieKatz against Chrome, Edge and Msedgewebview2 process memory, PetitPotam EFSRPC coercion, service and scheduled-task creation and enumeration, process memory dumping, and firewall rule manipulation. An interactive shell is usually not the first module an operator loads.

  Scope note: no existing HEARTH hunt names WinPTY, ConPTY or `MyInputPipe` - a grep of all hunt bodies for those strings returns nothing, and the closest matches by shape are about different mechanisms. H014 covers named pipes as a covert command-and-control transport, which is the same primitive used for a different purpose - this hunt uses the pipe as a local input channel into a shell, not as the C2 channel itself. H298 covers operator-commanded cleanup of a loader and its host, which is the end of the same session this hunt catches the start of. H505 covers the loader trio that delivers the backdoor hosting this module, and is the strongest pivot from any hit here.

# H506

Somewhere in the middle of Kaspersky's catalogue of ShadowCloud shellcode modules — between the service-control modules and the registry CLI — is one that does something the others do not. Instead of running a command and returning output, it builds the operator a terminal.

The module carries two files as hard-coded Base64 strings: `winpty.dll`, the core WinPTY library, and `winpty-agent.exe`, the helper that manages the terminal. It decodes both, writes them to `%TEMP%`, loads the library, creates a terminal configuration sized 80 by 25, and spawns `cmd.exe` with its handles wired into the pseudo-console. Two threads then run — a reader that ships output back, and a writer that listens on a named pipe called `\\.\pipe\MyInputPipe` for whatever the operator types. A separate `command-forwarder` module exists purely to open that pipe and write commands into it, appending a carriage return and a null terminator. The session ends when the string `hklnwqxaa123` arrives.

WinPTY is an unusual choice in 2026. It exists because Windows had no pseudo-console API before ConPTY shipped in Windows 10 version 1809, and modern software has moved on. Carrying it anyway is the choice of an implant that does not want to depend on anything the host provides — and it is exactly that self-sufficiency that leaves two named binaries in a temporary directory.

## Why

- Two specific filenames landing in `%TEMP%` is as concrete as a hunt gets, and the drop happens before the shell opens. The window between the files appearing and an operator typing into them is the cheapest moment to intervene in the whole intrusion.
- An interactive shell defeats command-line logging by design. Commands typed into a pseudo-console are not process creations, so an estate that watches 4688 and nothing else sees one `cmd.exe` and none of the session. Hunting the pipe and the shell's existence is the only way to see it at all.
- WinPTY on a non-developer host has almost no innocent explanation. It is bundled with Git for Windows and development tooling, so it is common on engineering workstations and genuinely rare everywhere else — which makes host role do most of the filtering for free.
- The pipe has two named ends in the report, which gives the hunt a structure rather than a string. One module creates `MyInputPipe`, another connects to it to inject commands, and Sysmon records both sides with Event IDs 17 and 18.
- It is a late-stage module, so finding it means the earlier ones already ran. The same toolkit carries Mimikatz, browser cookie theft from process memory, and PetitPotam coercion. An interactive shell is what an operator reaches for once credentials are already in hand.
