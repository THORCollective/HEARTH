false_positive_notes: |
  ptrace does have a legitimate population and it is worth naming precisely, because the value of this hunt comes from how small and how well-separated that population is. The real users of ptrace are interactive debuggers (`gdb`, `lldb`), tracers (`strace`, `ltrace`), crash handlers and core-dump collectors (`abrt`, `apport`, `systemd-coredump`), profilers and APM agents (`perf` in some modes, Datadog, Dynatrace, New Relic, Instana, Pyroscope), some memory-leak and heap tools, container and sandbox runtimes that use ptrace-based seccomp supervision (`gVisor`, some `runsc` and `proot` configurations), and checkpoint/restore tooling (`criu`). Every one of those attaches to APPLICATION processes - the JVM, the Python worker, the crashed service - and none of them attaches to `sshd`, `sudo`, `su`, `doas`, `passwd`, `kinit` or `login`. So the filter is not "ptrace happened", which on a developer workstation is common; it is "ptrace happened AND the tracee is an authentication binary", which is close to empty. Scope the hunt to servers rather than developer laptops and the benign volume collapses further - production web servers and application servers have no interactive debugging population at all, and a `gdb` or `strace` execution on one of them is itself worth a look. Two genuine ambiguities remain. First, `systemd-coredump` and `abrt` legitimately touch a crashing `sudo` or `sshd`, so correlate against the crash record and the core file before escalating; a crash handler arrives AFTER a signal and leaves a core, while a harvester attaches to a healthy long-lived process and stays attached. Second, container platforms with `SYS_PTRACE` granted will produce ptrace events whose tracee is inside the container - check the namespace before treating it as host-level credential theft. The setuid axis has a different and larger benign population. A stock Linux host legitimately carries roughly two dozen setuid-root binaries - `sudo`, `su`, `passwd`, `chsh`, `chfn`, `gpasswd`, `newgrp`, `mount`, `umount`, `ping` on older distros, `pkexec`, `fusermount`, `ssh-keysign`, `dbus-daemon-launch-helper`, `Xorg.wrap`, `snap-confine` - and all of them are OWNED BY A PACKAGE. The discriminator is ownership, not the count: an unowned setuid-root binary is the finding, and there should be zero of them. Locally compiled admin helpers are the one recurring benign case and, like legitimate `/usr/local/bin` software, they are consistent across the fleet and someone can explain them. Note the third possibility that the ownership query alone misses - a setuid bit ADDED to a legitimate packaged binary; `rpm -Va` flags that with `M` in the mode column and `dpkg -V` reports the permission delta, so run both. On `yama.ptrace_scope`, be explicit that a value of 0 is a HARDENING FINDING rather than evidence of compromise - it means any process can ptrace any other process of the same user without a parent relationship, so the technique is unobstructed on that host. Report it as an output of the hunt regardless of whether anything was found. Finally, an empty result needs a caveat: if `ptrace` was never in your auditd rules, you have no historical ptrace telemetry at all and cannot conclude anything about the past - only about the live `TracerPid` state at the moment you looked. Say which of the two you are reporting.

The first `a0` argument to the syscall is the ptrace REQUEST - `PTRACE_ATTACH` is 16 (`0x10`) and `PTRACE_SEIZE` is 0x4206; a harvester that wants to stay attached to a long-lived `sshd` will use one of those rather than `PTRACE_TRACEME`. Triage every record by resolving the target PID to a binary and asking whether it is an authentication binary.
  Core check 2, live TracerPid - `/proc/<pid>/status` carries a `TracerPid` field that is 0 for an untraced process and otherwise names the PID doing the tracing. `grep -H '^TracerPid' /proc/[0-9]*/status | grep -v ':\s*TracerPid:\s*0$'` returns, on a clean production host, nothing. Then for each hit resolve BOTH ends - the tracee via `readlink /proc/<tracee>/exe` and the tracer via `readlink /proc/<TracerPid>/exe`. A tracer whose executable is `/usr/sbin/unix_updates`, or anything in `/usr/local/bin/` or `/tmp/`, against a tracee of `/usr/sbin/sshd` or `/usr/bin/sudo`, is the finding. This check needs no agent, no prior instrumentation and about one second per host, which makes it the right thing to run first across an estate.
  Core check 3, the ptrace_scope hardening inventory - `sysctl kernel.yama.ptrace_scope`. Value 0 means classic permissive ptrace (any process may attach to any same-uid process); 1 restricts attaching to descendants; 2 restricts to root with `CAP_SYS_PTRACE`; 3 disables ptrace attach entirely until reboot. Most server distributions ship 1, but hardened images, container hosts and anything with a debugging or APM requirement are frequently set to 0. # H320

The credential-access half of the "Gambling Goblin" toolset Check Point documented is unusually direct. A component installed at `/usr/sbin/unix_updates`, which Check Point calls PasswordHarvester, attaches to the host's authentication binaries with ptrace and reads credentials as the user types them — `sshd`, `sudo`, `su`, `doas`, `ssh`, `ssh-add`, `passwd`, `kinit` and `login` are all targets. It will not run unless invoked with `-v FuckMe#988`, validated by a CRC32 check, so an analyst who executes the binary to see what it does will observe nothing. Next to it sits a setuid-root backdoor at `/usr/bin/chuser`, which accepts `-c <command>` to execute something as root, `-x <version>` to perform an HTTP check that expects the literal response `chuser no version`, and `-s <secret>` validated as an MD5 hash salted with `FuCkMe#`. A shell script, `info.sh`, with Chinese-language comments, sweeps `.ssh` directories and `.bash_history`, and the SSH private keys it collects become the lateral-movement path onward. DownPro pulls the payloads down using `-u`, `-id` and `-up` flags.

## Why

- **ptrace against an authentication binary has effectively no legitimate enterprise population, and that is rare enough to build on.** Most Linux detections require separating a signal from a large benign baseline. This one does not. Debuggers, tracers, profilers, APM agents, crash handlers and sandbox runtimes are the real ptrace users, and every one of them attaches to application processes — not to `sshd`, not to `sudo`, not to `su`. Adding the tracee identity to the filter takes a query that is noisy on developer machines and makes it silent on production servers, which is where the campaign operates.
- **`TracerPid` gives you an agentless, instant version of the same question.** Every Linux process advertises whether it is being traced, and by whom, in `/proc/<pid>/status`. A single grep across `/proc` answers "is anything attached to my authentication binaries right now" on a host with no EDR, no auditd rules and no log shipping — which describes a great many of the internet-facing Linux web servers this campaign targeted. It only sees the present moment, and the writeup must say so, but it can be run everywhere today.
- **The hunt produces a hardening deliverable whether or not it finds anything.** Collecting `kernel.yama.ptrace_scope` fleet-wide answers a question most organisations have never asked: on how many production hosts can any process attach a debugger to any other process of the same user? A value of 0 is not compromise, but it is an unobstructed path for precisely this technique, and it is fixable with one sysctl. Designing the hunt so the null result is still worth the collection effort is what keeps it from being a one-off.
- **"Every setuid-root binary should be owned by a package" is a rule with no exceptions worth arguing about.** A stock host carries roughly two dozen setuid binaries and all of them ship in packages. That makes the reconciliation a join, not a judgement call, and it makes the expected result exactly zero. `/usr/bin/chuser` fails it. So does every other unowned setuid implant, past and future. Running `rpm -Va` / `dpkg -V` in the same pass closes the other half of the gap, where the attacker adds a setuid bit to a binary that is legitimately present.
- **A hit here is a lateral-movement incident, not a host incident, and the scoping decision has to be made immediately.** Harvested SSH private keys are used to move on, so the blast radius is every system those keys reach — which is usually not knowable from the compromised host alone. Rotating passwords is the instinctive first response and it is insufficient by itself; the keys have to be rotated too, and `Accepted publickey` events sourced from the compromised host are the fastest way to bound the problem. Building that pivot into the hunt rather than leaving it to the responder is what stops the investigation from stopping at the wrong boundary.
