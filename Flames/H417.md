false_positive_notes: |
  Scheduled tasks that run PowerShell are routine. Patch tooling, inventory agents, log rotation and in-house automation all do it, usually from a fixed script path under Program Files or a software distribution directory. The discriminator is the payload location and extension, not the use of PowerShell: a task that runs a .ps1 from a managed path is normal, one that reads script text out of a .txt in a user temp directory is not.
  Software deployment creates tasks in bulk. SCCM, Intune, and third-party deployment tools register and remove tasks constantly, and will dominate 4698 volume. Exclude by the author or principal recorded in the task registration, and by the task folder, rather than trying to filter on the action.
  Document-themed task names are not inherently malicious. Adobe, Office and several PDF utilities register tasks with names referencing documents or updates. Allowlist the specific names your estate produces; the finding is a document-themed name whose action does not point at the vendor's own binary.
  Temp directories legitimately hold intermediate files, and some installers do drop script content there during a run. The combination that matters is a temp path AND a non-script extension AND execution via a task, rather than any one of the three.
  Non-script extensions are sometimes used honestly. Configuration read with Get-Content from a .txt or .json is extremely common and benign. Require that the content be executed — piped to Invoke-Expression, passed through the script-block parser, or dot-sourced — rather than merely read. Script Block Logging is what separates these two cases, and without it this hunt loses most of its precision.
  Task Scheduler is not always the parent. A task action can be configured to run cmd.exe or wscript.exe which then launches PowerShell, so the direct parent may be a shell rather than svchost.exe. Pivot through the grandparent when the immediate lineage looks ordinary.
notes: |
  Task-launched PowerShell with a non-script payload - Core filter: a `powershell.exe` or `pwsh.exe` process whose parent is `svchost.exe` (the Task Scheduler service runs in the netsvcs group) and whose command line references a file under a temp path with an extension other than `.ps1` or `.psm1`. Triage values: full `ProcessCommandLine`, `InitiatingProcessCommandLine` for the svchost instance, the account, and the integrity level. Defender XDR, 30-day retention:
  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where FileName in~ ("powershell.exe", "pwsh.exe")
  | where InitiatingProcessFileName =~ "svchost.exe"
  | where ProcessCommandLine matches regex @"(?i)(\\Temp\\|%temp%|\\AppData\\Local\\Temp\\)"
  | where ProcessCommandLine matches regex @"(?i)\.(txt|log|dat|tmp|cfg|ini|jpg|png)\b"
  | project Timestamp, DeviceName, AccountName, ProcessCommandLine,
            InitiatingProcessCommandLine, ProcessIntegrityLevel, InitiatingProcessParentFileName
  | order by Timestamp desc
  ```
  In the activity ESET documented, a task named `pdfopentask` executed at 06:59 on July 16th, 2025 and "executed a PowerShell payload from %temp%\temporarydoc.txt". Both the task name and the payload filename are lure-themed rather than system-themed, which is the pattern to look for in the task inventory.
  Task registration - Core filter: 4698, or Task Scheduler Operational 106, where the task action is a script interpreter and the arguments reference a temp path. Triage values: task name, task path (the folder it was registered into), the author, the principal it runs as, the trigger, and the full action command line. 4698 carries the XML of the task definition, which is the most complete single record of what was registered and by whom. Compare the author against your deployment tooling's service accounts: a task authored by an interactive user account whose action reads from that user's own temp directory is the shape of a phishing-delivered launcher.
  Script content - With Script Block Logging enabled, 4104 records the script text actually compiled, which is where the payload read out of the .txt becomes visible. Note that `DeviceEvents` with `ActionType == "PowerShellCommand"` records cmdlet names only, never script text or comments, so it cannot substitute for 4104 here; to use it at all, aggregate the cmdlets observed per process with `make_set` and look for the combination of a content-reading cmdlet and an execution cmdlet in one process.
  ```kql
  DeviceEvents
  | where Timestamp > ago(30d) and ActionType == "PowerShellCommand"
  | summarize Cmdlets = make_set(AdditionalFields, 100) by DeviceName, InitiatingProcessId, bin(Timestamp, 5m)
  | where tostring(Cmdlets) has "Get-Content" and tostring(Cmdlets) has_any ("Invoke-Expression", "Invoke-Command")
  ```
  4688 field names - If process creation comes from the Security log rather than Sysmon, the fields are `New_Process_Name` and `Creator_Process_Name`, not Sysmon's `Image` and `ParentImage`, and 4688 carries no integrity level. Build the lineage filter accordingly.
  Payload file on disk - Pivot to `DeviceFileEvents` or Sysmon 11 for the creation of the referenced file. The writer is the more interesting half: a file written into `%temp%` by an Office application, a mail client or an archive utility, and then executed as script by a task registered minutes later, connects the delivery to the execution. `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, so the write will be there and the read by PowerShell will not.
  Adjacent persistence in the same intrusion - The downloader in this activity also persists its backdoor by adding the registry value `UpdateMonitor` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\` pointing at the dropped payload path. Check Run and RunOnce for the affected user while scoping, and see [[H416]] for the mesh-network backdoor that followed one day after this initial execution.

# H417

ESET's October 2026 MythicRatatoskr report traces a UAC-0099 intrusion at a Ukrainian grain logistics company from initial access through to a Sandworm data-wiping attack two months later. The first observable event in that chain is small and ordinary: according to ESET telemetry, "at 06:59 on July 16th, 2025, a scheduled task named pdfopentask was executed on one machine in the target organization. It executed a PowerShell payload from %temp%\temporarydoc.txt."

Both halves of that sentence are worth a hunt. The task name, `pdfopentask`, is built to pass a glance at the task list — it reads like something a PDF handler registered. And the payload is not a script file. It is a `.txt` in the user's temp directory, read in and executed as script text, so nothing with a script extension is ever written to disk and no file-extension-based control has anything to act on.

Using a scheduled task as the launcher also breaks the lineage a responder would normally follow. Initial access here was a spearphishing email with a malicious attachment; had the attachment's handler spawned PowerShell directly, the parent-child chain would have pointed straight back at the mail client or the document. Routed through the Task Scheduler, the PowerShell process is parented by `svchost.exe` instead, and the connection to the lure survives only in the task definition and in the timestamps.

That makes the task registration record the most valuable artefact in the chain. Event 4698 captures the full task XML — name, folder, author, principal, trigger and action — and it names the account that registered it, which is the account the phishing landed on.

## Why

- This is the earliest point in the intrusion that produces durable, structured evidence. The access gained here was handed to a second actor and used for destruction two months later, so the task registration marks the start of the dwell time that mattered.
- Routing execution through the Task Scheduler is specifically an attempt to break attribution of the execution to its delivery. Hunting the task restores the link, because the task definition records the author and the trigger even when the process lineage no longer shows the document.
- A script interpreter reading executable content out of a non-script file in a temp directory is a narrow and describable anomaly. Legitimate scheduled PowerShell runs from managed script paths; configuration read from a .txt is common but is not executed. Requiring both the temp path and the execution of the content keeps the queue short.
- Every artefact is in telemetry that is already enabled or cheap to enable: task registration is audited in the Security log, Task Scheduler has its own operational channel, process creation shows the svchost parent, and Script Block Logging exposes the content that the file extension was chosen to hide.
- The lure-themed naming generalises past this actor. Task names that imitate document handlers and payloads parked under innocuous extensions are a durable phishing-to-execution pattern, so a standing inventory of task names and their actions pays off well beyond this campaign.
