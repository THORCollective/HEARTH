hypothesis: >-
  An operator who wants to read mail in transit has an obvious option and a quiet one. The obvious option is registering a transport agent, which is a supported extensibility point and which leaves a visible entry in the mail server configuration that any administrator can enumerate. The quiet option is to inject into the transport process, locate the transport agents that are already loaded, and wrap their handlers so the implant's logic runs first and then hands control back. Mail continues to flow, no new agent appears anywhere in configuration, and every configuration-enumeration check a defender runs returns a clean result. Selected messages are compressed, encrypted and written to files on disk for later retrieval. The observable chain is a module loaded into the transport process that no installed product owns, a configuration enumeration that lists fewer agents than are actually loaded in memory, and opaque files written under the mail server directories by the transport process itself.

false_positive_notes: |
  Mail servers run third-party code inside the transport pipeline by design, so the hunt cannot treat extra modules as inherently hostile.
  - Security and compliance products legitimately load into the transport process. Anti-spam, data-loss-prevention, encryption gateways, archiving and journaling products all do exactly this, some of them without registering a visible agent. Build the approved-module inventory per server first; without it this hunt produces a list of the organisation's own security stack.
  - Registered agents are normal and expected. A default Exchange install ships several, and products add more. The finding is not that agents exist, it is loaded code with no corresponding registration and no owning package.
  - Process-access events against the transport process are not rare. Monitoring agents, backup software, memory scanners and the endpoint protection product itself open handles to it constantly. Filter on the granted-access mask for write and thread-creation rights rather than on access alone, and allowlist the known monitoring processes.
  - Encrypted or opaque files under the mail directories have legitimate sources. Queue databases, transaction logs, journaling output, archiving spools and content-filter caches are all binary and all live near the transport directories. Characterise the normal file population before treating an unrecognised file as staged collection.
  - The absence of a registered agent is the expected state in a real compromise, so a clean configuration enumeration must not be read as a clean result. This inverts the usual triage reflex and is the single most important false-negative risk in the hunt.
  - A live loaded-module capture is a point-in-time check and the implant may not be resident. ESET describes delivery through a chain of nested components, so a server that is between stages can show nothing. One clean capture does not clear the host; the file-system and image-load history do more work here than the live snapshot.
notes: |
  Source reporting is ESET Research's November 13, 2026 analysis of the Cereal toolset, attributed to Turla and observed in two national governmental organizations. This hunt covers CerealBox, the component ESET singles out as the most novel in the toolset. The companion hunts from the same intrusion are [[H466]], which covers the loader placements that start the chain, and [[H468]], which covers the passive backdoor used to retrieve what this component stages. The closest existing coverage is for Exchange transport-agent abuse as a registered extensibility point; no existing hunt covers hooking agents already loaded in memory, and nothing in the corpus references EdgeTransport.exe.
  Why the usual check fails here - ESET makes the distinction explicit. Turla has abused transport agents before, and ESET notes that "Installed transport agents, however, leave visible traces in Exchange’s configuration". CerealBox does not install one: ESET reports that "instead of registering itself, it is injected directly into EdgeTransport.exe, the Exchange process that handles email flow", and summarises the result in one line - "CerealBox doesn't add a new agent; it hijacks existing ones loaded in memory." ESET assesses that "injecting into the Exchange transport service and hooking mail flow from within is a novel technique, not previously documented for any malware family". The operational consequence is that `Get-TransportAgent` is the first thing a defender runs and it will come back clean, so the hunt has to compare configuration against memory rather than reading configuration alone.
  Core filter 1, the configuration-versus-memory comparison - The defining check, and it exists nowhere in a log. On each Exchange server, capture the registered agent list and the transport process's loaded modules in the same session, then reconcile them. A triage capture:
  ```powershell
  $p = Get-Process -Name EdgeTransport -ErrorAction SilentlyContinue
  if ($null -eq $p) { 'EdgeTransport.exe is not running on this host'; return }
  '=== Registered transport agents ==='
  Get-TransportAgent | Format-Table Identity, Enabled, Priority, TransportAgentFactory -AutoSize
  '=== Modules loaded in EdgeTransport.exe with no valid signature ==='
  $p.Modules |
    ForEach-Object {
      $sig = Get-AuthenticodeSignature -FilePath $_.FileName
      [pscustomobject]@{
        Module    = $_.ModuleName
        Path      = $_.FileName
        SigStatus = $sig.Status
        Signer    = $sig.SignerCertificate.Subject
      }
    } |
    Where-Object { $_.SigStatus -ne 'Valid' } |
    Format-Table -AutoSize
  ```
  Run `Get-TransportAgent` from the Exchange Management Shell so the cmdlet is available. Triage values are every loaded module whose signature does not validate or whose signer is not an approved vendor, the module path, and whether an installed package owns it. A module implementing transport logic with no corresponding registered agent is the finding. Expected, not observed by ESET: the module name and on-disk path of CerealBox itself - the report describes the injection and the hooking but does not publish a file name for the injected component, so a hunt keyed on a specific module name would be keyed on an invention.
  Core filter 2, the injection into the transport process - ESET reports that CerealIron is "an injector that allows operators to load and run .NET assemblies from non .NET processes", and that CerealBox reaches the transport process through a chain of nested components. Hunt Sysmon Event ID 10 for process-access events targeting `EdgeTransport.exe` where the granted-access mask includes write or thread-creation rights, and Sysmon Event ID 8 for remote thread creation into it, excluding the approved monitoring and protection processes. Note that Sysmon Event ID 5 records process termination but does not say who terminated a process, so it is not a substitute here; the access and thread-creation events are the ones that carry the caller.
  Core filter 3, the modules the transport process maps - Hunt Sysmon Event ID 7 for modules loaded by `EdgeTransport.exe` where the signature is absent or the signer is outside the approved vendor list, and where the module path is not under the Exchange or vendor installation directories. In a Defender-only environment the equivalent requires a join, because `DeviceImageLoadEvents` has no signature columns:
  ```kql
  let lookback = 30d;
  let loads =
      DeviceImageLoadEvents
      | where Timestamp > ago(lookback)
      | where InitiatingProcessFileName =~ "EdgeTransport.exe"
      | project Timestamp, DeviceId, DeviceName, FileName, FolderPath, SHA1, InitiatingProcessId;
  let certs =
      DeviceFileCertificateInfo
      | project SHA1, IsTrusted, IsSigned, Signer, SignerHash;
  loads
  | join kind=leftouter certs on SHA1
  | where isempty(Signer) or IsTrusted == false
  | project Timestamp, DeviceName, FileName, FolderPath, SHA1, IsSigned, IsTrusted, Signer
  | order by Timestamp desc
  ```
  Keep the lookback at `ago(30d)` or less, because Defender XDR advanced hunting retains 30 days and silently truncates a longer window.
  Core filter 4, the staged output - The collection has to land somewhere, and that is file-system evidence that survives a reboot and a process restart. ESET reports that qualifying messages are "compressed, encrypted, and staged in files on disk", and that operators later "use ordinary CerealNeuron commands to exfiltrate and delete these files". Hunt for file creates under the Exchange installation and queue directory trees where the writing process is `EdgeTransport.exe` and the file is not part of the known queue, log or journaling population. The write-then-delete pattern is useful in itself: a file created by the transport process and deleted shortly afterwards, repeatedly, is the staging cycle.
  Core filter 5, the selection criteria, which tell you what to go and read - ESET reports that a message qualifies if it has a .doc, .docx, or .pdf attachment and matches at least one of several hardcoded lists of sender addresses, recipient addresses, subject substrings, or attachment names, while avoiding matching ignore lists. ESET also reports that in the Romanian case CerealBox "was configured to collect messages involving NATO and EU institutional addresses". For a responder this is the scoping question for the incident rather than a detection filter: recovering the hardcoded lists from a sample tells you exactly whose mail was taken, and Exchange message tracking logs can then establish which matching messages transited during the window. Treat the attachment-type filter as a narrowing hint when reviewing tracking logs for a confirmed case.
  Core filter 6, the fallback that leaves no network trace - ESET reports a second variant, CerealHermit, as "a variant of CerealNeuron with the network parts removed" that "reads encrypted command files from disk and writes encrypted results back", and notes that in some intrusions both backdoors were deployed together. For this hunt the consequence is that encrypted-file read-and-write cycles on an Exchange server are a tasking channel in their own right. Note that `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, so the read half of that exchange is not visible there; the modify-and-delete cadence is what is observable.
  Scope - Exchange servers, specifically the Mailbox and Edge Transport roles where `EdgeTransport.exe` runs. The configuration-versus-memory reconciliation is worth running as a periodic control rather than only during an investigation, because it costs one command per server and it is the only check that sees this class of technique at all.

# H467

A defender who suspects mail interception on an Exchange server runs `Get-TransportAgent`. It is the right command. Transport agents are the supported way to hook mail flow, Turla has abused them before, and a registered agent shows up in configuration where anyone can see it.

On these servers that command returned a clean list.

ESET Research found that CerealBox never registers an agent. It is injected into `EdgeTransport.exe` — the process that moves mail — then reaches into Exchange's own internal structures, finds the transport agents that are already loaded, and wraps their handlers. The implant's code runs first and then hands control back to the original. Mail keeps flowing. Nothing appears in configuration, because nothing was added to configuration.

ESET calls this novel, and not previously documented for any malware family. It requires knowing how Exchange's mail pipeline is assembled internally, which is not knowledge that comes cheap.

What it collects is narrow. A message qualifies if it carries a `.doc`, `.docx` or `.pdf` attachment and matches one of several hardcoded lists — senders, recipients, subject substrings, attachment names — while dodging a set of ignore lists. In the Romanian case, the lists were configured around NATO and EU institutional addresses. Matching messages are compressed, encrypted and written to disk, and collected later through ordinary backdoor commands.

So the hunt is not a configuration query. It is a comparison: what does Exchange say is loaded, versus what is actually in the process. The gap between those two answers is the whole technique.

## Why

- **The first check a defender runs is the one check this defeats.** Enumerating registered agents is correct practice, it is in every Exchange hardening guide, and against this implant it returns a clean result. Any hunt built on configuration state will confirm the server is fine, which makes the configuration-versus-memory reconciliation the only query that sees it.
- **Hooking existing handlers inherits their legitimacy.** The implant does not need to be in the pipeline — it needs the pipeline's existing members to call it, which they do, because their handlers were rewritten in place. There is no new participant to enumerate and no ordering change to notice.
- **The collection is deliberately small, which defeats volume-based detection.** Three attachment types and a hardcoded recipient list produce a trickle, not a dump. Nothing will trip an exfiltration threshold, and the staged files are deleted after retrieval. This is a long-horizon espionage posture, not a smash-and-grab.
- **The staged files are the durable evidence, and they are on disk.** Everything else about this toolset is in memory by design. Opaque files written by the transport process into the mail directories, created and then deleted on a cadence, survive the process restart that clears the rest.
- **Recovering the hardcoded lists answers the question that actually matters.** For a confirmed case, the senders, recipients and subject substrings compiled into the module define the scope of the breach precisely. Paired with message tracking logs, that turns an unanswerable question — whose mail was read — into a finite list.
- **This generalises to any mail-adjacent extensibility point.** The lesson is not about one process name. It is that an extensibility framework's registration list is a statement of intent, not an inventory of loaded code, and anywhere that gap exists it can be occupied.
