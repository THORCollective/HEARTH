false_positive_notes: |
  `/bin/sh` is not setuid on a stock NetScaler appliance, and no Citrix maintenance procedure makes it so — this is effectively a zero-baseline check, which is why it belongs near the top of any appliance triage. Legitimate setuid binaries do exist on the appliance (the usual Unix set plus vendor utilities), so the hunt must compare against the permission set shipped with the exact firmware build rather than flagging every setuid bit on the box. The realistic confounder is prior incident response and vendor support activity - a support engineer or a previous responder may have left a modified shell or a staged script behind, and a few consultancies' triage scripts touch permissions. Confirm with change records rather than assuming, because an attacker's bit and a support engineer's bit look identical. Note also that the surrounding evidence is actively destroyed - Mandiant observed access-log scrubbing for the staging paths - so clean logs around a setuid shell should raise the finding's priority rather than lower it.
notes: |
  Platform: Citrix NetScaler ADC and Gateway appliances. The appliance management plane is FreeBSD-based; T1548.001 is documented by ATT&CK for Linux and macOS, and the setuid semantics are identical on FreeBSD, so the mapping is by behaviour — noted explicitly here because the technique's platform list does not name the appliance OS. Driven by Google Threat Intelligence Group / Mandiant, "Defending Against Active Exploitation of Citrix NetScaler ADC and Gateway Appliances" (29 September 2026), covering CVE-2026-88772 and CVE-2026-88771. Mandiant publishes the commands verbatim - `chmod u+s /bin/sh`; `/bin/httpd -k restart -f /etc/httpd.conf && chmod u+s /bin/sh`; the same chain invoked from PHP as `system('/bin/httpd -k restart -f /etc/httpd.conf && chmod u+s /bin/sh');`; and `/netscaler/nsshutdown -R`. Mandiant's published verification command is simply `ls -l /bin/sh`. Their YARA rule `G_Hunting_Script_NetScaler_Persistence_1` keys on `chmod u+s /bin/sh` together with `/netscaler/nsshutdown`, `/bin/httpd -k restart` and the access-log scrubbing regex, which is the signature of the staging and clean-up script rather than of the shell itself. Mandiant published no ATT&CK IDs; the mappings here are assigned.
  Why the chain matters as much as the chmod - The restart is not incidental. The web server must be restarted for the attacker's modified `httpd.conf` (see [[H358]]) to take effect, and the `&& chmod u+s /bin/sh` rides along on the same command so the privilege path is established in the same action that activates the webshell. That makes the conjunction a much stronger artefact than either half - a lone `chmod u+s` could be argued as administrative, but a web server restart against an explicitly specified configuration file, immediately followed by making the shell setuid, is a deployment step.
  Permission leg (primary, and the fastest check on the box) - `ls -l /bin/sh` and look for the `s` in the owner execute position. Extend it to the full set rather than one path - `find / -xdev -type f -perm -4000 -user root -exec ls -l {} \;` and compare the result against the same command run on a known-good appliance of the identical firmware build. Triage fields - mtime and ctime of the binary (ctime changes when permissions change even if mtime is forged), and whether `/bin/sh`, `/bin/csh`, `/bin/tcsh` or a copied shell elsewhere on the filesystem carries the bit. A copy of a shell at an unusual path with the setuid bit is the quieter variant of the same idea and is missed by checking `/bin/sh` alone.
  History and script leg - `grep -E "chmod +u\+s|nsshutdown|httpd -k restart" /var/log/sh.log` for the commands as typed, and search the filesystem for scripts carrying the same chain. Mandiant's YARA logic is directly reusable here as a grep set - the appliance restart commands (`/netscaler/nsshutdown`, `nsshutdown -R`), the SUID creation (`chmod u+s /bin/sh`), the web server reload (`/bin/httpd -k restart -f /etc/httpd.conf`), the Apache configuration strings (`AddHandler application/x-httpd-php`, `php_flag engine on`, `AliasMatch`, `SetEnvIf`), and the access-log scrubbing regex `#^.*/vpn(s)?/(scripts|media|theme|themes|help|logon)`. Two or more of those in one file is a staging script, not an administrative one.
  Anti-forensic leg - The scrubbing regex above is itself the artefact worth hunting. It removes `/vpn/scripts/`, `/vpn/media/` and `/vpn/theme/` request lines from the access log, which produces a detectable negative - a period in which the portal served authentications but logged no requests to its own static asset paths. Where appliance logs are forwarded off-box, compare the forwarded copy against the on-box copy - the attacker edits what is on the appliance, and the forwarded stream is what proves lines were removed. That gap, not the shell, is often the first thing a SIEM can see without appliance access.
  Why this is separate from the existing Linux SUID hunts - HEARTH already covers setuid abuse on Linux endpoints and servers from two angles - [[H299]] hunts a SUID helper invoked with almost no arguments by an interpreter or a binary in a writable path, crossing to root in one step, and [[M041]] ranks every setuid and setgid binary in the Linux estate by fleet prevalence so a first-ever privileged execution scores as rare. Both assume an agent or a fleet-wide inventory feed. Neither reaches a NetScaler, because no EDR agent runs on the appliance and it does not appear in the Linux estate inventory those hunts draw from. This hunt is the appliance-telemetry form of the same behaviour - run from the appliance shell, verified against firmware-matched baselines, and tied to the specific deployment chain Mandiant observed.
  Scope and response - Run this on every internet-facing NetScaler regardless of whether it was patched, because patching does not remove a permission bit or a configuration edit. A confirmed setuid shell means assume full appliance compromise - rotate appliance credentials and certificates, invalidate active sessions, treat saved configurations as untrusted, and check `/nsconfig/` and `/flash/nsconfig/` copies before restoring any backup. Pair with [[H358]] for the webshell that uses this privilege path and with [[H360]] for the tunneler that follows it.

# H359

Among all the artefacts in Mandiant's September 2026 NetScaler report, the smallest one is the most consequential: `chmod u+s /bin/sh`.

Exploitation of CVE-2026-88772 gives unauthenticated root by bypassing authentication and crashing the NetScaler Packet Processing Engine. Root obtained that way is fragile — it depends on an exploit that will be patched. Making the appliance's shell setuid root converts it into something durable. After that, any code execution at any privilege level on the appliance, including through a PHP webshell running as the web server user, becomes root by invoking a shell.

Mandiant observed it chained onto the web server restart that activates the attacker's modified configuration: `/bin/httpd -k restart -f /etc/httpd.conf && chmod u+s /bin/sh`, including issued from PHP via `system()`. One command activates the webshell and establishes the privilege path.

The check is a single command — `ls -l /bin/sh` — and on a stock appliance the answer is never setuid. The reason to run it anyway is that patching does not undo it, firmware upgrades preserve the configuration files it travels with, and nothing on the appliance will tell you it happened.

## Why

- **It outlives the vulnerability.** Patching CVE-2026-88772 removes the way in; it does not remove a permission bit. An appliance that was exploited, then patched, then declared clean can still be rooted by anyone who can execute a single command on it.
- **Zero baseline makes it decisive.** No Citrix procedure makes `/bin/sh` setuid. Unlike most hunts, a single match is a confirmed compromise rather than a lead, and the check costs one command per appliance.
- **It pairs with the webshell by design.** The restart is required to load the attacker's `httpd.conf`; the chmod rides the same command line. Finding either one should immediately drive a check for the other ([[H358]]).
- **Existing SUID hunts cannot see it.** [[H299]] and [[M041]] both depend on endpoint agents or fleet inventory, and appliances have neither. The behaviour is in HEARTH; the appliance is not — this closes that gap specifically.
- **The anti-forensics leaves its own trace.** Scrubbing access-log lines for the portal's static asset paths produces a window where the portal served users but logged none of those requests — a negative signal visible in forwarded logs even without appliance access.
- **Edge appliances sit in front of everything.** A rooted NetScaler sees VPN sessions, credentials and internal routing, so the cost of missing this is not limited to the device.
