hypothesis: >-
  A compromised dependency no longer needs the developer to run anything. Unit 42 describes the
  PolinRider campaign, spanning npm, Go modules and Packagist, which "rather than relying strictly on

# H382

The careful thing to do with an unfamiliar repository is to look at the code before you install anything. PolinRider makes looking at it the execution event.

Unit 42's description is specific. Rather than relying on package installation scripts, the campaign hides its loaders in "repository configuration files, web resources and developer IDE workspace automation" — and when the developer loads the workspace, the payload runs in the background and starts collecting developer credentials, cloud session tokens and environment secrets.

That is a trigger relocation, and it steps around essentially the whole defensive apparatus built for malicious packages. `--ignore-scripts` applies to lifecycle hooks. Install-time sandboxing applies to lifecycle hooks. CI scanning for `preinstall` and `postinstall` applies to lifecycle hooks. The cautious developer who clones a repository, declines to run `npm install`, and opens it in an editor to read it first has performed the one action that was not defended.

The mechanics are mundane, which is the problem. Visual Studio Code will run a task when a folder opens if the task says `"runOptions": {"runOn": "folderOpen"}`. Dev containers have six lifecycle command hooks. JetBrains run configurations commit to `.idea/`. direnv reads `.envrc`. `NODE_OPTIONS` with `--require` runs code before the entry point of every Node process on the machine. None of these are vulnerabilities. All of them are documented features that exist because developers asked for them, and all of them will be present, legitimately, across any healthy engineering organisation.

So the construct cannot be the finding. Three things separate the signal.

**Provenance.** A `folderOpen` task a teammate committed deliberately is a different object from one that arrived inside `node_modules`, or that appears in a commit nobody on the team authored. The commit-author and lockfile-attribution queries are where the precision actually lives.

**The action.** Legitimate workspace tasks start watchers, builders, servers and type-checkers, and their command lines name the project's own tooling. A task that pipes a download into a shell, decodes base64, fetches a non-standard language runtime, or opens `~/.aws/credentials` is not building anything.

**What happens next.** A dev server listens locally. This payload exfiltrates. An editor-parented process making an outbound connection to somewhere unfamiliar within a minute of workspace open is the shape worth waking up for.

Two details from the companion worm are worth carrying. ChainDrop — Shai-Hulud family, 400-plus npm packages including `keyv` and `cacheable-request` — pulls down a custom Bun runtime from a `preinstall` hook to run its harvester, so a non-standard language runtime arriving mid-install is a flag by itself. And it does not only read credential files from disk: it searches *memory inside running build processes* for ephemeral IAM keys, worker tokens and short-lived OIDC credentials, then lets the runner terminate. Short-lived credentials are not a mitigation against something running inside the build, and the ephemeral host takes the evidence with it.

One last implication, and it is the uncomfortable one. Unit 42 says the trigger fires when a developer opens a project *or starts an AI coding session*. Agentic coding tools open workspaces, read configuration and run tasks programmatically, across many repositories, usually with live developer credentials. That makes an automated agent a better trigger for this technique than a human is. The population of editor-spawned processes on a developer endpoint is growing fast — baseline it while it is still small enough to read.

## Why

- **It relocates the trigger off dependency installation, where every existing control lives.** `--ignore-scripts`, install sandboxing and lifecycle-hook scanning all protect an event this technique does not use.
- **The cautious behaviour becomes the vulnerable one.** Cloning and opening a repository to read it before installing is good practice, and it is the execution event.
- **The constructs are legitimate features, so provenance has to carry the hunt.** `folderOpen` tasks and devcontainer hooks are everywhere and intentional. Who committed the file, and whether it came with a dependency, is the discriminator.
- **Legitimate tasks build things and this one does not.** Watchers, servers and compilers name project tooling in their command lines. Downloads piped to shells and reads of cloud credential paths do not build software.
- **`NODE_OPTIONS` with `--require` is the widest version of the same idea.** It executes before the entry point of every Node process on the host, not just the one in that workspace, and it is a single environment variable.
- **A non-standard language runtime arriving mid-install is a signal on its own.** ChainDrop fetches a custom Bun runtime from a `preinstall` hook, and nothing legitimate needs a new interpreter during dependency resolution.
- **Memory harvesting defeats short-lived credentials.** Reading IAM keys and OIDC tokens out of running build processes means rotation and expiry provide no protection, and the runner's termination erases the host-side evidence.
- **AI coding agents make the trigger more efficient, not less.** Programmatic workspace opening across many repositories with live credentials is a better delivery condition than a human developer, and it is becoming the normal case.
- **The C2 side is already covered, so this hunt stays on the trigger.** Web3 resolution is hunted in [[H270]] and baselined in [[B060]]; duplicating it here would blur the one behaviour that has no coverage.
