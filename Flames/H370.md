false_positive_notes: |
  Extension-versus-content mismatch is less noisy than it sounds, but it is not free. Legitimate sources - minified and bundled JavaScript with embedded base64 or source maps can score high on naive entropy tests, as can already-compressed or encrypted assets served deliberately, web fonts, WebAssembly, sprite sheets and some SVG; CMS and framework caches write opaque serialized blobs under arbitrary names; `.js` files that are actually JSON, and `.png` files that are genuinely optimised PNGs with high-entropy IDAT streams, will both appear in a poorly-tuned entropy sweep. The fix is to test leading bytes against the claimed type rather than entropy alone - a real PNG starts `89 50 4E 47`, a real GIF starts `GIF87a` or `GIF89a`, a real JPEG starts `FF D8 FF`, and a `.js` file that begins with no printable ASCII at all is not JavaScript regardless of its entropy. Use entropy only as a secondary ranking feature on files that already failed the magic-byte test. The second benign class is real `.gz` archives in application paths - backup and log-rotation output legitimately lands in writeable directories, so `All_scanner_vXX.pl.gz` style names need the directory and the writing process to carry the signal rather than the extension. Third, developer and deployment churn writes a lot of files into web roots; scope by writing process, because the interesting case is content written by the web server's own user (`www-data`, `apache`, `nginx`, `php-fpm`) rather than by a deployment account or package manager. Finally, note that the encryption is optional in the observed tradecraft - CISA says the bot encrypted "in some instances," so a compressed-but-unencrypted dump is the same behaviour with a weaker entropy signal, and the magic-byte mismatch remains the reliable test in both cases.

The bot was built from a PHP script named `Curlc4.txt`, "specifically designed to interface with the Microsoft EWS API, which allows the threat actors to access email and content items, such as calendars and contacts [T1114.002]." It "uploaded emails to a remote server [T1020], obfuscating many of the directories and files it created, and changed the name of the child process to `crypto`." Before exfiltration the bot compressed emails, and "in some instances, the threat actor also used a password to encrypt emails using RC4 or AES-128-CBC [T1560.003]." The script took up to two command-line arguments - if the first (a root directory) was not supplied, "the script searched for a writeable directory [T1074.001] to use as its directory." Infrastructure - the original file was downloaded from `https://upl.natcloudservice[.]com` at IP `149.28.132[.]137`; the main C2 domain was `natcloudservice[.]com`, communicating with `https://natcloudservice[.]com/ews` and `upl.natcloudservice[.]com/ews`. The advisory notes the script "appears to be stand-alone rather than installed on a compromised device."
  Why T1560.003 rather than T1560.001. The distinction is load-bearing for detection. T1560.001 is archiving via a utility - `zip`, `rar`, `7z`, `tar` - which produces a process-execution event and a file with a recognisable container header, and is well covered by existing detection content. T1560.003 is the adversary implementing compression and encryption in their own code. Nothing executes, nothing is installed, and the output has no header any file-type classifier recognises. The process-centric detections that catch `rar.exe a -hp` are structurally blind to a PHP script calling `openssl_encrypt` with `aes-128-cbc`. That is why the artefact has to be the file on disk and the mismatch between what it claims to be and what it is.
  Core filter, the staging leg. Over web-accessible and application-writable paths, read the first bytes of every file and compare against the type its extension claims. Flag - `.gif` not starting `GIF87a` or `GIF89a`; `.png` not starting `89 50 4E 47 0D 0A 1A 0A`; `.jpg`/`.jpeg` not starting `FF D8 FF`; `.js`/`.css` whose first 64 bytes contain no printable ASCII; `.gz` not starting `1F 8B`. Rank survivors by Shannon entropy over the first 4 KB (an RC4 or AES-CBC ciphertext sits near 8.0 bits per byte), then by size, then by whether the writing process was the web server's own user. Triage fields - full path, size, mtime and ctime, writing process and UID where available, and whether the file is reachable over HTTP.
  Sample sweep command. `find /var/www /srv/www /usr/share/nginx -type f \( -name '*.gif' -o -name '*.png' -o -name '*.jpg' -o -name '*.js' -o -name '*.css' \) -size +100k -printf '%s %T@ %p\n' | while read -r sz ts p; do hdr=$(head -c 8 "$p" | xxd -p); case "$p" in *.gif) echo "$hdr" | grep -q '^4749463' || echo "MISMATCH gif $sz $p";; *.png) echo "$hdr" | grep -q '^89504e47' || echo "MISMATCH png $sz $p";; *.jpg|*.jpeg) echo "$hdr" | grep -q '^ffd8ff' || echo "MISMATCH jpg $sz $p";; *.js|*.css) head -c 64 "$p" | LC_ALL=C grep -qP '^[\x09\x0a\x0d\x20-\x7e]+$' || echo "MISMATCH text $sz $p";; esac; done`. The size floor matters - a mailbox dump is large, and setting it at 100 KB removes most of the legitimate small-asset noise in one step.
  Core filter, the writeable-directory search. The bot's fallback behaviour is itself detectable. A PHP process that `stat`s or test-writes its way through a list of candidate directories in rapid succession, before settling on one and writing a large file there, is a distinctive sequence in auditd. The advisory reproduces the searched-directory list as its Table 1. Pair this with the process-name change to `crypto`, which is a free pivot - a child process of the web server named `crypto` has no legitimate explanation.
  Core filter, the collection side. The bot speaks to the EWS API, so the mailbox access leaves telemetry on the Microsoft side independent of the web server. Look for EWS requests from the web server's egress IP or from any non-user source, `natcloudservice[.]com` and `upl.natcloudservice[.]com` in DNS and proxy logs, and the `/ews` paths the advisory names. Because the script is stand-alone rather than installed, the Microsoft-side evidence may be the only durable record.
  Core filter, the retrieval side. The staged file has to be collected, which means an HTTP GET for a large `.gif` or `.js` from an unusual client. Rank web access-log rows by bytes-sent for static-asset extensions, and compare each path's response size against the file actually on disk - a 40 MB `001.gif` retrieved once by a single IP is the exfiltration event itself. This is the same reasoning [[M054]] applies to webshell response sizes, and the two should be run together on any server where both are plausible.
  Pivots. The credential access that opened the mailboxes is hunted in [[H369]]. A confirmed hit should also be walked to SoftEther or other unexpected VPN client installations on the same estate - the advisory describes installers named `conhost.exe` or `dllhost.exe` configured to reconnect on startup - and to the MySQL email database the dump was drawn from.

# H370

`001.gif` is a forty-megabyte file. That is the whole finding.

CISA's October 2026 advisory on Integrity Technology Group-enabled activity describes a PHP bot, built from a script the FBI recovered as `Curlc4.txt`, that pulls mail through the Microsoft EWS API, compresses it, encrypts it with RC4 or AES-128-CBC under an operator-supplied password, and writes the result into a web-writable directory. The names the FBI observed are the interesting part: `001.gif`, `Include.png`, `Css.js`, `M2k.js`, `M2k_list.js`, `M2k_ui_adm.js`, `All_scanner_vXX.pl.gz`.

Every one of those reads as web furniture. Look at a directory listing and you see an image, a stylesheet, some JavaScript with a vaguely administrative name. Nothing in the listing says "mailbox dump."

What makes this worth a separate hunt from ordinary data staging is the *custom method* part of the ATT&CK mapping. T1560.001 — archive via utility — means `zip` or `rar` or `7z` ran, which means there is a process-execution event with a command line, and the output has a container header any file-type classifier recognises. A great deal of detection content exists for exactly that. T1560.003 means the adversary wrote the compression and encryption themselves. A PHP script calling `openssl_encrypt` with `aes-128-cbc` spawns no process, installs nothing, and produces a file with no header at all. Every process-centric archive detection is blind to it by construction.

So the artefact is the file, and the signal is disagreement. A real GIF begins `GIF89a`. A real PNG begins with those eight bytes everyone can recite. A real JavaScript file begins with printable ASCII. An AES-CBC ciphertext begins with none of those things, and sits near eight bits of entropy per byte all the way through.

Reading the first eight bytes of every large static asset in a web root is a cheap sweep, and the size floor does most of the tuning work for free — mailbox dumps are big, and setting the threshold at a hundred kilobytes drops almost all the legitimate small-file noise.

Two free pivots come with it. The bot searches for a writeable directory when it is not given one, which is a distinctive burst of directory probing from a web-server process. And CISA notes it "changed the name of the child process to `crypto`" — a child of `php-fpm` called `crypto` needs no further analysis.

## Why

- **Rolling your own crypto removes the process event, so the file is all that is left.** No `zip`, no `rar`, no `7z`, no container header. Detections built on archive-utility execution cannot see this, which is precisely the gap the technique exists to exploit.
- **Magic-byte mismatch is a structural test, not a signature.** It survives the operator changing every filename, because the disagreement is between the extension and the bytes rather than between the name and a list.
- **Entropy alone is a trap; entropy as a tiebreaker is useful.** Minified JavaScript, web fonts, WebAssembly and optimised PNGs all score high. Testing leading bytes first and ranking the failures by entropy keeps the false-positive rate manageable.
- **The size floor is free tuning.** A mail dump is large and a sprite is not. Filtering above a hundred kilobytes removes most benign web-root churn before any other test runs.
- **The writing process is the sharpest scope available.** Content written into a web root by `www-data` or `php-fpm`, rather than by a deployment account or the package manager, is a small and meaningful set on most servers.
- **The retrieval is a second, independent chance.** The staged file has to be fetched. A single client pulling one enormous `.gif` shows up by ranking access-log rows on bytes-sent — the same reasoning [[M054]] applies to webshell responses.
- **The Microsoft side may be the only durable record.** CISA assesses the script as stand-alone rather than installed, so the web server may retain little. EWS request telemetry, the `/ews` paths and the `natcloudservice[.]com` infrastructure persist independently.
- **The process rename is an unforced error.** Changing a child process name to `crypto` was meant to look innocuous and instead created a string with no legitimate occurrence under a web server.
