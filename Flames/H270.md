id: H270
category: Flames
title: JSON-RPC eth_call to public blockchain RPC endpoints resolving the real C2 address from a smart contract
hypothesis: >-
  An implant that stores its C2 address on a public blockchain cannot have that address taken down, sinkholed, or
  blocked — the operator updates a smart contract's storage for a few cents of gas and every implant picks up the
  new address on its next poll. To read it, the implant issues an HTTP POST carrying a read-only JSON-RPC call to
  a public RPC endpoint. On EVM chains that is `eth_call` against `polygon-rpc.com`, `eth.llamarpc.com`,
  `ethereum-rpc.publicnode.com` and dozens of equivalents, with the contract address in `to` and a four-byte
  method selector in `data`. On Solana it is `getAccountInfo` against `api.mainnet.solana.com`, with the account
  address as the first parameter. Hunt for that request shape from any enterprise endpoint or server: an HTTP
  POST to a blockchain RPC host whose body contains a read-only chain-state method — `eth_call`,
  `eth_getTransactionByHash` or `getAccountInfo` — issued by a process that is not a browser and not a
  developer's Web3 tooling.

required_data_sources:
  - Web proxy / TLS-inspecting gateway logs — full request URL, HTTP method, request body where inspected, Host/SNI, response size, and the authenticated user or source host. The POST body is where eth_call and the method selector live
  - Zeek ssl.log and http.log, or equivalent NSM — server_name (SNI), method, uri, request_body_len, response_body_len, and connection duration for the RPC hosts
  - Sysmon Event ID 22 (DNSQuery) and Defender XDR DeviceEvents ActionType DnsQueryResponse — resolution of blockchain RPC hostnames, attributed to the querying process
  - Sysmon Event ID 3 (NetworkConnect) and Defender XDR DeviceNetworkEvents — RemoteUrl, RemoteIP, InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessCommandLine for every connection to those hosts
  - Sysmon Event ID 1 / Windows Security 4688 — the full process lineage of whatever issued the request, including custom user-agent strings visible in command lines
  - HTTP user-agent from proxy logs — non-browser agents such as cpp-httplib/*, python-requests, Go-http-client, curl, or a bespoke string, against a blockchain RPC destination
  - Sysmon Event ID 11 / DeviceFileEvents — staging and persistence artifacts written by the same lineage (%AppData%\Local\, %ProgramData%\Startup\*.lnk)
  - DNS server logs or Umbrella/Cloudflare Gateway logs — estate-wide resolution counts per blockchain RPC domain, to establish which hosts have ever done this
  - Asset inventory / CMDB role data — which hosts legitimately belong to a blockchain, Web3, or crypto-treasury function. Without this the hunt has no denominator
false_positive_notes: |
  In most enterprises the true baseline for this traffic is zero, which makes the hunt unusually clean — but
  "most" is not "all." Enumerate these populations first:
  - Developer and engineering workstations running Web3 tooling — MetaMask and other browser wallet extensions,
    Hardhat, Foundry/Anvil, Truffle, ethers.js/web3.py projects, Remix. These generate exactly this traffic and
    are the dominant benign source where they exist. Note the browser-extension case is legitimate but is also
    the vector EtherHiding-style attacks use, so "it came from Chrome" is not automatically exculpatory.
  - Any crypto, treasury, payments, or blockchain-analytics business function, and the servers supporting it.
  - Security and IR tooling that resolves on-chain indicators as part of enrichment.
  - Node/CLI package managers and CI jobs pulling Web3 dependencies that phone RPC endpoints during tests.
  - Blockchain-adjacent SaaS agents and browser telemetry.
  The separators, in order of strength:
  (1) THE HOST HAS NO BUSINESS REASON. This is the whole hunt. A domain controller, file server, finance
      workstation, or conferencing server issuing eth_call has no legitimate explanation. Join against asset
      role and the result set collapses to something an analyst can read line by line.
  (2) THE PROCESS IS NOT A BROWSER OR KNOWN WEB3 TOOL. Aeternum used a bespoke C++ client with user-agent
      cpp-httplib/0.18.3; Kimwolf used a statically-linked ELF with BoringSSL. Attribute every request to a
      process image and signer and the legitimate set is small and nameable.
  (3) THE REQUEST IS READ-ONLY AND REPETITIVE. A dead-drop resolver only ever reads: eth_call against the same
      contract, same method selector, on an interval. It never sends transactions, never signs, never queries
      balances across many addresses. Real wallet and developer traffic is varied and bursty.
  (4) ENDPOINT ROTATION. The implants shuffle a hardcoded list of RPC providers per attempt for resilience. A
      single host contacting five or six different RPC providers with structurally identical requests is doing
      failover, not development.
  (5) WHAT FOLLOWS. A short RPC response immediately followed by a first-ever connection to a newly resolved
      domain from the same process is the resolver working. That sequence is the confirmation step.
  Score against asset role and process identity. Do not blocklist the RPC domains as a substitute for the hunt —
  there are dozens of public providers, the lists in these reports are already incomplete, and operators can and
  do stand up their own (Kimwolf's eth.rpcuniverse.com).
notes: |
  PLATFORM: Windows (enterprise endpoints and servers). The same technique appears on Linux/IoT — Kimwolf v7 is
  an ARM ELF on Android TV boxes — and the network-layer logic here transfers directly; the process-attribution

  CATEGORY: Flames, and this was the closest call in the batch. Alchemy was seriously considered — the RPC
  endpoint lists rotate and grow, operators stand up their own providers, and "static lists won't generalise" is
  an explicit Alchemy trigger. It was rejected because the durable indicator is not the destination at all: it
  is the REQUEST SHAPE (a read-only JSON-RPC eth_call, on an interval, from a non-browser process), which is
  concrete, matchable, and does not require scoring. Embers rejected because in the overwhelming majority of
  enterprises the baseline for this traffic is genuinely zero — there is nothing to baseline, only an asset-role
  join to perform, and spending 30 days establishing "no host here talks to Polygon" would delay a hunt that is
  actionable on day one. The one place that reasoning inverts is an estate with a real Web3 or crypto-treasury
  function; there, the initiator inventory becomes a genuine baseline and this should be paired with an Ember.

  CAUTION ON SOLANA METHOD COVERAGE: `getAccountInfo` is the only RPC method the MovieReaper report documents.
  `getSignaturesForAddress` and `getProgramAccounts` are NOT observed in that report — they are included in the
  queries below because they are the other read-only Solana methods a dead-drop resolver would plausibly use
  (transaction history for an account, and enumeration of a program's accounts), and the point of this hunt is
  to match the shape rather than one family's indicators. Treat a hit on `getAccountInfo` as matching published
  tradecraft, and a hit on the other two as an unproven-but-sensible extension. Do not cite them as IOCs.

  WHY SOLANA CHANGES THE QUERIES: the EVM request shape and the Solana one share nothing at the string level.
  There is no `eth_call`, no `to`/`data` pair, and no four-byte selector — Solana takes the account address as a
  plain base58 string parameter and returns base64 account data. A body-inspection rule written only against
  `eth_call` misses this entirely, which is exactly the failure mode this hunt was written to avoid.

  THE REQUEST SHAPE, which is the durable indicator:

    POST / HTTP/1.1
    Host: polygon-rpc.com
    Content-Type: application/json

    {"jsonrpc":"2.0","id":1,"method":"eth_call",
     "params":[{"to":"0x8EF7c3e531d871D3B9D559722DE77EB1dEc19dAe","data":"0x933a9ce8"},"latest"]}

  And the Solana equivalent, which shares the intent and none of the strings:

    POST / HTTP/1.1
    Host: api.mainnet.solana.com
    Content-Type: application/json

    {"jsonrpc":"2.0","id":1,"method":"getAccountInfo",
     "params":["6pnDGAiHgyPdmckM5Qt1YbanGzrX43WLEU159nRaNLDm",{"encoding":"base64"}]}

  The RPC provider is interchangeable. The contract or account address is one edit. The selector changes per
  family, and on a non-EVM chain there is no selector at all. What does not change is that a non-browser process
  on a corporate host is making a read-only JSON-RPC call to a public blockchain node and then connecting
  somewhere new. Match on that, not on any one chain's method names.

  STARTING QUERY — proxy/Zeek, the request-shape path:

    (http.method == "POST")
    and (http.request_body contains "eth_call"
         or http.request_body contains "eth_getTransactionByHash"
         or http.request_body contains "eth_getLogs"
         or http.request_body contains "getAccountInfo"          // Solana — attested (MovieReaper)
         or http.request_body contains "getSignaturesForAddress" // Solana — plausible, not observed
         or http.request_body contains "getProgramAccounts")     // Solana — plausible, not observed
    and (ssl.server_name matches "(rpc|infura|alchemy|llamarpc|publicnode|drpc|nodies|merkle|quicknode|ankr|solana)")

  Note `getAccountInfo` is a generic-sounding name; unlike `eth_call` it can collide with unrelated APIs. Pair it
  with the destination condition rather than matching it on body content alone.

  STARTING QUERY — Defender XDR, the host-attribution path (works without body inspection):

    let RpcHosts = dynamic(["polygon-rpc.com","polygon.drpc.org","polygon-bor-rpc.publicnode.com",
                            "polygon-pokt.nodies.app","1rpc.io","polygon.meowrpc.com",
                            "0xrpc.io","eth.llamarpc.com","ethereum-rpc.publicnode.com",
                            "eth-protect.rpc.blxrbdn.com","eth.merkle.io","polygon.rpc.hypersync.xyz",
                            "eth.rpcuniverse.com",
                            // Solana public clusters (solana.com/docs/references/clusters).
                            // api.mainnet.solana.com is the MovieReaper destination; the other two are
                            // included because a test/dev cluster is an equally valid dead drop.
                            "api.mainnet.solana.com","api.devnet.solana.com","api.testnet.solana.com"]);
    DeviceNetworkEvents
    | where Timestamp > ago(90d)
    | where RemoteUrl has_any (RpcHosts)
          or RemoteUrl matches regex @"^(eth|polygon|matic|bsc|arb|sol|solana)[-.].*rpc"
          or RemoteUrl matches regex @"solana\.com$"
    | where InitiatingProcessFileName !in~ ("chrome.exe","msedge.exe","firefox.exe","brave.exe")
    | summarize Requests = count(), Providers = dcount(RemoteUrl), ProviderList = make_set(RemoteUrl, 10),
                FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
              by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath
    | where Providers >= 2

  Then join `DeviceName` against asset role and discard anything with a legitimate Web3 function. In most
  estates that leaves a very short list, and every entry on it is worth a look.

  THE CONFIRMATION PIVOT: take the timestamp of the RPC response and look for the first-ever outbound connection
  from the same process to a domain it has never contacted before, within the following minute. That is the
  resolver doing its job, and it is the sequence that distinguishes C2 resolution from a developer reading chain
  state.

  ALSO SWEEP THE HTTP EQUIVALENTS, per Armored Likho: raw.githubusercontent.com, gist.github.com, pastebin and
  paste-service raw endpoints, and Telegram bot API URLs, fetched by non-browser processes on servers. Same
  technique, cheaper substrate, and it is where an operator goes when blockchain egress is blocked.

# H270

Four reports in one week, four unrelated actors, one idea: put the C2 address somewhere nobody can take it down.

DeadLock ransomware stores its negotiation-proxy URL in a Polygon smart contract. Aeternum stores its C2 domain in one. Kimwolf v7 resolves its C2 through Ethereum Name Service, with Tor as a backup. Armored Likho does the same thing more cheaply, with a Blowfish-encrypted JSON blob in a GitHub raw URL that only activates after three days of primary C2 silence.

A month later MovieReaper did the same thing on Solana — `getAccountInfo` against `api.mainnet.solana.com`, returning a base64 blob holding an XOR-encrypted second-stage C2 address. That one matters out of proportion to its novelty, because it shares no strings with the other four: no `eth_call`, no `to`/`data` pair, no method selector. Any rule written against the Ethereum request shape misses it completely, which is the precise failure this hunt was supposed to prevent.

Microsoft's write-up states the design goal plainly: the operator can update the proxy URL "without changing…victim-facing infrastructure, and no domain registration or DNS infrastructure is required." There is no domain to seize, no registrar to serve, no host to sinkhole. Updating the address costs a few cents of gas, and every implant picks it up on its next poll.

What that buys the defender is a request that stands out. To read the contract, the implant has to POST a JSON-RPC `eth_call` to a public blockchain node. In a bank, a hospital, a manufacturer, or a law firm, the number of hosts with a legitimate reason to do that is zero.

## Why

- **The baseline is genuinely zero in most estates, and that almost never happens.** Nearly every C2 hunt is a fight against a noisy legitimate population — DNS, HTTPS, cloud services, admin tooling. This one is not. Outside developer workstations running Web3 tooling and any actual crypto business function, there is no reason for a domain controller, a finance laptop, or a conferencing server to make a JSON-RPC call to a Polygon node. Joining the traffic against asset role turns the entire hunt into a list short enough to read line by line, which is a rare and valuable property.

- **Blocklisting the RPC providers is the obvious response and it does not work.** There are dozens of public providers, the lists in these four reports are already incomplete, and operators stand up their own — Kimwolf's `eth.rpcuniverse.com` is a single-tenant VPS behind a Let's Encrypt certificate that no feed will ever flag. The durable artifact is not the destination hostname, it is the request: a read-only `eth_call`, on an interval, from a process that is not a browser. Hunting the shape survives the provider list changing; blocking the list does not.

- **Takedown resistance shifts the entire cost of the response onto detection.** For conventional C2, a detection that arrives late is still useful — the infrastructure can be blocked, the domain seized, the IP sinkholed, and every other victim benefits. Here none of that is available to anyone. The contract is immutable and the chain is public. The only remaining lever is finding the implants on your own hosts, which means the value of this specific detection is higher than the equivalent detection against a normal C2 family, not equal to it.

- **The families converged independently, which makes this a technique hunt rather than a campaign hunt.** A ransomware crew, a commodity stealer, an IoT botnet, and an espionage toolkit arriving at the same design in the same week is the signal that the pattern has crossed into general tradecraft. Writing this against the mechanism — read-only JSON-RPC from an unexpected host — means it covers all of them today and the next one without an update, which is the opposite of the per-family IOC lists these reports otherwise hand you.

- **MovieReaper proves the "write it against the mechanism" claim, and partly falsifies the first version of it.** The original hunt claimed to cover the technique, but its queries were EVM-specific: a Solana resolver produces no `eth_call`, no contract/selector pair, and no matching string anywhere in the body. The *reasoning* generalised and the *detection* did not. The fix is to match on the combination of a blockchain RPC destination and a read-only chain-state method, with the method list treated as per-chain vocabulary that will keep growing — Bitcoin inscriptions, TON, and Tron all support the same pattern and none of them will look like either query above.

- **Endpoint rotation is a self-inflicted indicator.** These implants deliberately contact several RPC providers, shuffled, for resilience — Kimwolf PRNG-shuffles five endpoints per attempt; DeadLock carries six; Aeternum over twenty. A developer using Hardhat points at one provider, or at a local node. A single host issuing structurally identical requests to four different blockchain RPC providers is performing failover, and the very resilience the operator built is what makes the host stand out from the legitimate population.

- **The confirmation pivot is unambiguous and takes one query.** A dead-drop resolver is only useful if the resolved address is then used. Take the RPC response timestamp and look for a first-ever connection from the same process to a previously unseen domain within the next sixty seconds. Chain read followed immediately by novel egress is the resolver working; a developer querying chain state produces no such follow-through. That sequence turns a suspicious observation into a confirmed one without needing to decrypt anything.

- **The cheap HTTP variant belongs in the same sweep, and it is what an operator falls back to.** Armored Likho's dead drop is a GitHub raw URL with a Blowfish-encrypted JSON payload, dormant until the primary C2 has been unreachable for three days. Same technique, no blockchain, no gas, and it works from any host that can reach `raw.githubusercontent.com` — which is all of them. If blockchain RPC egress gets blocked in response to this hunt, that is the next stop, so sweep both substrates from the start.

- **HEARTH has eight hunts touching T1102 but none for T1102.001,** the dead-drop resolver sub-technique itself — the layer *underneath* C2 that determines whether takedown is even possible. This is the gap this week's intel pointed at from four directions at once.
