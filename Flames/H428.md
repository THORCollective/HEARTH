false_positive_notes: |
  Backup, archiving, eDiscovery, API-based email security, and DLP/CASB integrations legitimately hold tenant-wide Mail.Read or Files.Read.All application permissions and read every mailbox on a schedule. Read breadth alone is therefore not a signal. Measure breadth only after an (app ID, source IP/ASN) pair has failed the egress baseline. Vendors do change egress (new cloud regions, new IPv6 ranges, a move to a different hosting provider). Before escalating, check an off-baseline address against the vendor's published egress list or a vendor support ticket. In this campaign Huntress reported activity from Azure IPv6 space as well as a hosting-provider address, so a major-cloud ASN lowers suspicion but does not clear a sign-in. Apps that rotate their own credentials produce `Add service principal credentials` events where initiator and target are the same object. Exclude only that self-rotation case, never writes to a different object. MSP and partner management platforms may legitimately provision or update their own companion apps; check those writes against the partner's documented onboarding behavior and change records. Graph activity logs and mailbox auditing must be enabled before the hunt window.   Entra ID service principal sign-in logs - Core filter: successful app-only sign-ins (`client credential type` of `clientSecret` or `certificate`) where the app's owner tenant is neither your own tenant nor a Microsoft first-party tenant (`f8cdef31-a31e-4b4a-93e4-5f571e91255a`, `72f988bf-86f1-41af-91ab-2d7cd011db47`), and the resource is Microsoft Graph `00000003-0000-0000-c000-000000000000` or Exchange Online `00000002-0000-0ff1-ce00-000000000000`. For each `app ID`, build a baseline of the source IP addresses and ASNs it used over the prior 30-90 days, add any vendor-published egress list, and keep only sign-ins outside that set. Triage values: `app ID`, `service principal ID`, `source IP address`, `ASN`, `location`, `service principal credential key ID`, `unique token identifier`, `resource ID`. Correlation: group by `source IP address` across all third-party app IDs. One address signing in as several unrelated vendor apps is not vendor behavior. Strong red flags: an app that has only ever signed in from one cloud provider suddenly signing in from a hosting/VPS ASN it has never used; a credential key ID or credential type absent from the baseline window; sign-ins that continue after the vendor announces it has disabled the integration.
  Microsoft Graph activity logs - Core filter: requests with no signed-in user (app-only token) whose `app ID` and `source IP address` match an off-baseline sign-in from the step above, and whose request URI matches `/users/{id}/messages`, `/users/{id}/mailFolders`, `/users/{id}/drive`, `/drives/{id}/root/children`, `/sites/{id}/drives`, or tenant-wide `/users` enumeration. Triage values: `request URI`, `request method`, `response status code`, `response size in bytes`, `user agent`, `sign-in activity ID`. Correlation: join each request to its sign-in where `sign-in activity ID` equals the sign-in's `unique token identifier`. Then count distinct target user IDs parsed from the request URI, per token per hour, and compare with the same app's tokens issued from baseline egress. Strong red flags: one off-baseline token touching dozens of mailboxes within minutes; `$search` or `$filter` queries over message content from an app whose baseline traffic is incremental `delta` paging; scripting user agents such as `python-requests/2.31` or `Python-urllib/3.12` (these rotate, so use them for triage only, never as the filter); any write call from a read-oriented integration, such as `POST /servicePrincipals/{id}/addPassword` or `POST /roleManagement/directory/roleAssignments`.
  Microsoft 365 unified audit log (Exchange mailbox audit and SharePoint/OneDrive) - Core filter: `MailItemsAccessed` records whose `client app ID` is the flagged app and whose `client IP address` is the off-baseline address, plus `FileAccessed` and `FileDownloaded` records for the same app ID and IP. Triage values: `mailbox owner`, `mail access type` (`Bind` versus `Sync`), `folder path`, `internet message ID`, `site URL`, `file path`. Pivot: list every mailbox owner and site reached from the off-baseline IP and rank them by role (executives, finance, IT and security administrators). Use this as the scoping set if Graph activity logs were not enabled before the incident. Strong red flags: `Sync` access across many mailboxes from one IP in a short window; file reads concentrated on finance, legal, or credential-adjacent sites rather than the whole-tenant sweep a backup job produces.
  Entra ID audit logs (persistence pivot) - Core filter: `Add service principal credentials`, any activity containing `Certificates and secrets management`, `Add member to role`, or `Add app role assignment to service principal`, where the initiating actor is an application rather than a user and the initiating app ID is one flagged above. Exclude only self-rotation (initiator equals target). Triage values: `initiating app ID`, `target object ID`, `target display name`, new `key ID`, `credential end date`, `user agent`, `result`. Pivot: take each new `key ID` and target app ID back to the service principal sign-in logs and search forward for sign-ins using that key from any IP. This access outlives disabling or re-securing the vendor integration. Strong red flags: credential end dates set years out; a target app that belongs to a different vendor; the target app's first sign-ins with the new key coming from the same off-baseline infrastructure.

# H428

On October 15, 2026, an adversary began using a compromised Microsoft 365 application credential belonging to ConnectWise Cloud Backup (formerly SkyKick) to sign in directly to customer tenants as the backup app's service principal. Huntress confirmed unauthorized sign-ins across 162 tenants by 19:00 UTC on October 16. It later counted nearly 1,000 Entra tenants with sign-in activity from the attacker's address, more than 300 of them successful. On October 17, ConnectWise revoked certificates and disabled seven application identities. Microsoft later attributed the activity to Storm-0940 and said the actor likely relied on broad application permissions such as Directory.ReadWrite.All. Mitiga's analysis of the incident describes the defender's problem. The access is app-only, so there is no user sign-in, no MFA prompt, and no user-targeted Conditional Access. The events also sit in the service principal sign-in view, which many teams never review. Read volume is a weak signal because a legitimate backup app reads every mailbox. What separates abuse is where the token was issued from and what that specific token did. This hunt starts from a third-party app signing in from outside its own historical and published egress. It then joins that token to Graph and mailbox audit activity to scope cross-user mail and file reads. The campaign's follow-on persistence step, where the compromised app writes a new credential onto a different application, is used here only as a scoping pivot, because that planted credential keeps working after the vendor integration is disabled.

## Why

- Vendor app credentials are now a proven multi-tenant entry point. One ConnectWise Cloud Backup credential produced confirmed sign-ins in 162 tenants within about a day and sign-in activity against nearly 1,000. Every MSP-installed integration holding tenant-wide Graph application permissions has the same single point of failure.
- The chokepoint survives IOC rotation. Whatever address, user agent, or secret the actor rotates, a stolen app credential still has to be exchanged for a token from infrastructure the actor controls, and the data still has to be pulled under that app ID. An (app ID, source IP/ASN) pair missing from the app's own history is the invariant; the published attacker IP is not.
- The chain is observable end to end when logging is in place. Service principal sign-ins record the source address and credential key for each token. Graph activity logs record the app ID, source IP, request URI, and sign-in identifier for each request. Mailbox audit records app-only `MailItemsAccessed`. Together, one suspicious token can be followed to the exact mailboxes and files it reached.
- False positives stay controllable because breadth is measured second. Backup and email-security apps legitimately read every mailbox, but they do it from a stable, vendor-owned egress set. Filtering on off-baseline egress first, then counting distinct mailboxes per token, leaves a handful of tokens per app for analyst review.
