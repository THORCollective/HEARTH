false_positive_notes: |
  Confluence legitimately executes external processes in a small number of cases - some plug-ins shell out, backup and index maintenance jobs run helpers, and administrators occasionally trigger exports that spawn child processes. The discriminators are which binary and which parent. A Java application process becoming the parent of `bash`, `sh` or `curl` is the finding; a Java process spawning its own bundled helper is not. Build the short list of expected children once and the leg becomes close to noise-free, which is the point of B075.

  Monitoring and configuration management agents run commands as service accounts constantly, and on some estates they do so through the application account. Attribute by parent - an agent's commands are parented by the agent, not by the application's JVM.

  The access-log leg will return scanning noise, and a lot of it, because a Metasploit module exists and the CVE is in the KEV catalog. Volume of requests to the vulnerable endpoint is therefore not evidence of compromise on its own. The correlation with process execution on the same host, within seconds, is what separates a scan from a hit.

  Do not use response status as a filter. The observed exploitation returned HTTP 500 on every request while still executing commands, so a query that excludes 5xx responses, or that looks for 200s, will miss this entirely. This is the single most important false-negative trap in the hunt.

  A clean access log does not clear a host. Log rotation on busy Confluence instances is often aggressive, and the exploitation window observed here spanned roughly twelve hours from first request to Microsoft 365 sign-in, so the relevant entries may already be gone. Treat process-lineage telemetry as the primary evidence and the access log as corroboration.

  The published IP addresses are a snapshot of one intrusion. Rapid7 states plainly that the absence of those addresses does not confirm an environment was unaffected, so they belong in a retrospective search and not in a detection rule.
notes: |
  Leg one, the exposure question (configuration inventory) - Run this first, because it is finite and it scopes everything else. For Confluence Data Center, versions 1.x through 9.x are affected when Remote API, covering XML-RPC and SOAP, is enabled; the setting has been off by default for new installations since version 3.0, so an enabled instance usually means a long-lived deployment or a deliberate integration. Confluence 9.2.28 is the fixed release, 10.x and later removed the feature entirely, and Atlassian Cloud is unaffected. The administrative path is General Configuration, then Further Configuration, where clearing Remote API takes effect without a Confluence restart - and will break integrations that use the API, which is why the inventory needs to record who uses it. For N-central, on-premises administrators should confirm Legacy API is disabled even on 2026.4 HF2; 2026.4 HF3, numbered 2026.4.1.39, disables the exposed surface and addresses seventeen further CVEs. Prioritise internet-facing instances and then check internal ones, because the vulnerability is unauthenticated and an internal attacker is the common case for this product class.

  Leg two, the web log (access logs from every instance) - Core filter: requests whose path contains `soap-axis1` or the servlet path `/plugins/servlet/soap-axis1/confluenceservice-v2`, with no status filter at all. Collect source IP, user agent, body length and timestamp. The same search should cover any path containing `axis`, `/services/`, or `.jws`, since Axis 1.x exposes service endpoints under several conventional prefixes and the observed one is this product's mapping rather than the library's only shape. For N-central, search the Legacy API paths named in the vendor's advisory.

  Leg three, the process lineage (auditd, Sysmon for Linux, or EDR) - Core filter, and the one that would have caught this without any knowledge of the CVE: a shell or download tool whose parent is the application's Java process.

      # auditd: shells and download tools executed on the Confluence host
      auditctl -a always,exit -F arch=b64 -S execve -F path=/usr/bin/curl -k conf_exec
      ausearch -k conf_exec -i | grep -E 'ppid=|comm='

      # Sysmon for Linux / EDR equivalent, expressed as a filter:
      #   ParentImage ends with /java  AND  Image in (/bin/bash, /bin/sh, /usr/bin/curl, /usr/bin/wget,
      #                                               /usr/bin/python3, /usr/bin/perl, /usr/bin/nc)
      #   AND the effective user is the Confluence service account

  Triage values are the parent command line, which identifies the Confluence installation and its configuration directory; the child command line in full; the executing user, which should be the dedicated service account rather than root; and the time delta to the nearest access-log entry from leg two. In the observed intrusion that delta was seconds. Red flags beyond the lineage itself - the child is `curl` fetching from a hostname under `trycloudflare.com` or `pinggy.net`, or from `webhook.site`; the command line is hex-encoded rather than readable, which H511 covers in detail; the same process tree goes on to execute a MySQL client.

  Leg four, egress from the application host (network telemetry and DNS) - Core filter: outbound HTTP or HTTPS from the Confluence or N-central host to a destination that is not a vendor update endpoint, an internal service, or a sanctioned integration. Server egress inventories are usually short, which makes this leg cheap. Red flags - any resolution or connection to an ephemeral tunnel provider, because those exist to give a short-lived public hostname to a service that has no business having one, and because the observed exploitation fetched hundreds of commands and scripts from Pinggy and Cloudflare Tunnel domains.

  Retrospective indicator search, scoped to the published intrusion - the Confluence addresses are 192.238.253[.]176, 5.133.47[.]243, 163.182.68[.]109 and 104.13.106[.]166, with the tunnel hostname wpefh-192-238-253-176.free.pinggy[.]net, any subdomain of trycloudflare[.]com, and webhook[.]site. For N-central, N-able's 13 November update lists 157.20.241[.]16, 139.99.69[.]109 and 79.76.51[.]56. Note the first Confluence address is worth more than the others - the same address appears in the Pinggy tunnel hostname, in exploit requests, and roughly twelve hours later in a Microsoft 365 sign-in, which is the thread H512 follows.

  What follows a hit - the observed intrusion moved fast. Just over three minutes after the first execution the attacker was authenticating to MySQL with Confluence's own database credentials; within about four hours they held a service account credential and were querying a production cloud data warehouse; within about twelve hours they signed into Microsoft 365. So a confirmed hit on this hunt is not an endpoint incident, and scoping it as one will understate it. H511 covers the post-exploitation tooling signature and H512 the identity pivot out of the Confluence secret store.

  Scope note: H161 and H162 are the closest existing hunts and both begin where this one ends - H161 covers NTLM relay coercion launched from a compromised Confluence or F5 host, and H162 covers payload staging in `/dev/shm` or `/tmp` by a compromised Confluence or F5 Java service. Neither covers initial access, and neither keys on the Axis SOAP endpoint, the HTTP 500 response, or the Java-parents-a-shell lineage that is this hunt's core filter. B017 and B025 baseline legitimate access to Confluence credential material and information repositories, which is the data the attacker went after next rather than the exploitation itself. No existing hunt names Apache Axis, XML-RPC, Pinggy or `webhook.site`.

# H510

The detail worth remembering from Rapid7's write-up is that every exploit request returned an error.

On 13 November 2026, Rapid7's MDR team responded to a surge of alerts about abnormal child processes on a customer's Atlassian Confluence server. The access logs showed unauthenticated POST requests to `/plugins/servlet/soap-axis1/confluenceservice-v2`, each one answered with HTTP 500. Endpoint telemetry showed the opposite story: within seconds of those same requests, Confluence's Java process was launching Bash and curl as the dedicated Confluence service account.

CVE-2026-90436 is an unsafe reflection flaw — CWE-470 — in Apache Axis 1.x, disclosed by the Apache Software Foundation on 6 November 2026 and scored 9.8 by CISA. Axis 1.x is end of life and Apache does not plan to publish a fixed release for it. What made the CVE matter beyond Axis itself is that Atlassian Confluence Data Center and N-able N-central both bundle the affected library, and both expose it when a non-default setting is on: Remote API in Confluence, Legacy API in N-central. A Metasploit module for the Confluence path arrived on 17 November, a public proof of concept targeting N-central on 12 November, and CISA added the CVE to the Known Exploited Vulnerabilities catalog on 18 November.

So this hunt has a cheap half and an important half. The cheap half is a configuration question with a definite answer. The important half is a process-lineage query that would have found this with no knowledge of the CVE at all.

## Why

- The response status lies. Exploitation succeeded while returning HTTP 500 on every request, so any triage that filters for 200s, or that treats 5xx as failure, produces a false all-clear. Knowing this one fact changes how the access log is read.
- The lineage is the detection that does not expire. A Java application process becoming the parent of `bash` or `curl` is anomalous regardless of which CVE put it there, which makes this leg worth standing up permanently rather than for this vulnerability — the next Axis-class flaw in a Java product will look identical at the host.
- Exposure is a finite, answerable question. Both products need a non-default feature enabled, and in Confluence it has been off by default since version 3.0. The set of enabled instances is usually small and the mitigation does not require a restart, so the hunt converts directly into remediation.
- The window to act is hours, not days. In the observed intrusion, database credentials were in use three minutes after first execution, a cloud data warehouse was being queried four hours in, and Microsoft 365 was reached at twelve hours. Detection latency here is the whole game.
- A public exploit plus KEV status means the scanning volume will bury the signal unless the hunt correlates. Requests to the vulnerable endpoint are now background noise; requests followed seconds later by a shell on that host are not.
