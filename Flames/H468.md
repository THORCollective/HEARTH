title: "A passive backdoor on an internet-facing Exchange server takes its tasking from inbound requests to Exchange-shaped URL paths and answers a malformed request with a legitimate-looking error page, so there is no outbound beacon and no attacker infrastructure to block"
hypothesis: >-
  An implant that never calls out cannot be found by looking for where it calls. Instead of beaconing, this backdoor waits on the mail server's existing HTTPS listener for requests to paths that read like ordinary Outlook Web Access, Autodiscover and ActiveSync traffic. A properly encrypted request that passes its integrity checks is decrypted and executed as a command; a request that does not pass is answered with a plausible error page, so probing it looks like probing a mail server. The victim's own internet-facing server is the control point, which means there is no domain, no address and no hosting provider to discover or take down, and the malicious traffic is indistinguishable at the flow level from the mail traffic nobody can block. The observable chain is successful responses on Exchange URL paths that the product does not actually implement, requests to those paths with no corresponding authentication or mailbox activity, and an HTTP listener or server-side component on the host that no installed product owns.

false_positive_notes: |
  Internet-facing mail servers are among the noisiest logging surfaces in any estate, and most of what hits them is hostile but unrelated.
  - Scanners and vulnerability research generate enormous volumes of requests to Exchange paths, including invented and malformed ones. The vast majority produce 404s and authentication failures. The candidate population is requests that received a success status on a path the product does not implement, not requests that merely look odd.
  - Exchange genuinely serves a sprawling and poorly documented set of paths. Virtual directories differ by version, cumulative update, role and third-party add-in, so a path being unfamiliar to the analyst is not evidence that the product does not serve it. Build the reference list from the actual installed version before treating any path as unimplemented.
  - Mobile clients, Autodiscover and ActiveSync produce long, unusual, deeply nested URLs as a matter of routine, and legitimate clients retry aggressively against paths that do not exist. Volume and shape alone will not separate this.
  - Monitoring and load-balancer health probes hit synthetic paths on a fixed cadence and get success responses by design. These are easy to allowlist by source address and user agent, and they must be, or they dominate the result.
  - Third-party products add IIS modules and handlers legitimately. Archiving, security, mobile-device-management and backup products all extend the mail server web stack. Establish the approved module inventory per server; without it, the module check reports the organisation’s own software stack.
  - A clean result from the usual outbound checks is expected, not reassuring. There is no beacon, no C2 domain, and no outbound flow to find, so a network-centric review of this host will come back empty while the backdoor is resident. Treating that as an all-clear is the main false-negative risk.
notes: |
  Source reporting is ESET Research's November 13, 2026 analysis of the Cereal toolset, attributed to Turla and observed in two national governmental organizations. This hunt covers CerealNeuron and its offline variant CerealHermit. The companion hunts from the same intrusion are [[H466]], which covers the loader placements that start the chain, and [[H467]], which covers the mail-collection component whose staged files are retrieved through this channel. The closest existing coverage in the corpus is for web shells and IIS component abuse generally; nothing covers a passive backdoor using the victim mail server as the operator-accessible control point, and nothing names these paths.
  Why the usual network-centric approach finds nothing - ESET is direct about what was absent: "The most notable aspect of this campaign is what we did not find: an attacker-controlled server." CerealNeuron does not initiate outbound connections, so it produces none of the artefacts a defender normally pivots on - no domains, no addresses, no hosting providers, no beacon timing. ESET records the practical consequence for the investigation itself: "We were unable to identify the ingress IP addresses used by the operators." Three things follow. The victim server is the control point. Network-based tracking is severely limited. And the malicious traffic coexists with legitimate Exchange web services, which ESET notes is "exactly the kind of traffic defenders are least likely to block".
  Core filter 1, the reported paths - ESET lists paths observed in use, reproduced here with the casing as published:
  ```
  https://*:443/owa/sdds/
  HTTPS://*:443/AUTODISCOVER/PROXYSERVICE/
  HTTPS://*:443/MICROSOFT-SERVER-ACTIVESYNC/INTEGRATED/API/
  ```
  Search IIS logs across every Exchange server for these stems. Treat them as a starting point rather than as the detection, because the operators choose the paths and a different intrusion will use different ones - which is why core filter 2 matters more.
  Core filter 2, success on a path the product does not serve - The generalisable version, and the one that survives a path change. Reconcile the set of URL stems that received a 200 response against the set of stems the installed Exchange version actually implements, and work the difference. A path that answers successfully but corresponds to no virtual directory, no handler and no documented endpoint is the finding regardless of what it is named. Sample log query, adjust the field names to the log format in use:
  ```kql
  let lookback = 30d;
  let knownProbeAgents = dynamic(["ELB-HealthChecker", "kube-probe", "Zabbix", "Pingdom"]);
  W3CIISLog
  | where TimeGenerated > ago(lookback)
  | where scStatus == 200
  | where csUriStem has_any ("/owa/", "/autodiscover/", "/Microsoft-Server-ActiveSync/", "/ecp/", "/mapi/")
  | where not(csUserAgent has_any (knownProbeAgents))
  | summarize requests = count(),
              bytesOut = sum(scBytes),
              bytesIn  = sum(csBytes),
              clients  = dcount(cIP),
              agents   = make_set(csUserAgent, 10),
              firstSeen = min(TimeGenerated),
              lastSeen  = max(TimeGenerated)
      by Computer, csUriStem, csMethod
  | order by requests asc
  ```
  Order ascending on purpose: the interesting rows are the rare stems, not the busy ones. Triage values are the stem, the method, the client address, the user agent, and the byte counts in both directions. Strong red flags are a stem with a handful of requests from one or two addresses over a long period, a POST to a path that should only ever be read, and a response body size far larger than any error page would be.
  Core filter 3, requests with no matching authentication or mailbox activity - A request that reaches an authenticated Exchange path and succeeds should have a corresponding sign-in and, usually, a corresponding mailbox operation. Correlate the candidate requests against authentication and mailbox-access records for the same second. A successful response with no authentication behind it is the clean discriminator, and it does not depend on knowing the path in advance. Use a bounded time window on the join - a join on server and client address alone over a 30-day lookback correlates unrelated days.
  Core filter 4, the error page that is not an error - ESET reports that "if a request looks wrong, CerealNeuron redirects the client to a legitimate-looking Exchange error page". This is the behaviour that makes the backdoor safe to probe and it is also a usable tell: a path that answers every malformed request with a redirect or an error page, consistently, from a stem that is not a real endpoint, is behaving like a gate rather than like a mail server. For an operational check, requesting a candidate path from a controlled host and comparing the response against what the same server returns for a genuinely nonexistent path is a fast discriminator - a real 404 and a synthesised error page rarely match in headers, timing or body length.
  Core filter 5, the listener and the module - The component has to be registered somewhere to receive requests at all. Capture the HTTP URL reservations and the loaded IIS modules per server and reconcile both against the approved inventory:
  ```powershell
  '=== HTTP URL reservations ==='
  netsh http show urlacl
  '=== HTTP server service state ==='
  netsh http show servicestate
  Import-Module WebAdministration -ErrorAction SilentlyContinue
  '=== Global IIS modules ==='
  Get-WebGlobalModule | Sort-Object Name | Format-Table Name, Image -AutoSize
  ```
  Triage values are any URL reservation naming a path that is not a product endpoint, and any global module whose image path is outside the approved product directories or whose signature does not validate. Pair this with the signature-aware image-load check in [[H466]], noting again that `DeviceImageLoadEvents` has no signature columns and requires a join to `DeviceFileCertificateInfo` on SHA1.
  Core filter 6, the offline sibling - ESET reports CerealHermit as "a variant of CerealNeuron with the network parts removed" which "reads encrypted command files from disk and writes encrypted results back", and that in some intrusions both were deployed together "giving operators two independent ways to reach their goals". A server cleared on the network side may still be tasked entirely through files, so a confirmed or suspected case needs the file-cadence check from [[H467]] as well. Note that `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, so only half of a file-based exchange is directly observable; the repeated modify-and-delete rhythm is the visible part.
  What the operators do once tasked - Useful for scoping a confirmed case. ESET reports that commands arrive as individual compiled programs rather than as a built-in command set, and that observed tasks included retrieving mailboxes or specific messages through Exchange Web Services, querying Active Directory for computers, users, groups and DNS records, running WMI queries such as listing processes or active TCP connections, extracting LSA Secrets, listing volume snapshots, and listing, reading and deleting files - often the staged email dumps. Each of those leaves its own telemetry on the server and in the directory, so a confirmed case should be worked outward along those lines rather than stopping at the web logs.
  Scope - Internet-facing Exchange servers, including those behind a reverse proxy, where the proxy logs are often the better record of the original client. The pattern generalises to any internet-facing application server with a sprawling URL surface and a pluggable web stack, where a self-registered path is indistinguishable from the product’s own endpoints without a reference list.

# H468

ESET set out to map Turla's infrastructure for this campaign and found that there wasn't any.

CerealNeuron, the main backdoor in the Cereal toolset, does not call home. It sits on the compromised Exchange server and waits for someone to call it, on paths that look like the mail server's own:

```
https://*:443/owa/sdds/
HTTPS://*:443/AUTODISCOVER/PROXYSERVICE/
HTTPS://*:443/MICROSOFT-SERVER-ACTIVESYNC/INTEGRATED/API/
```

To a firewall log, that is Outlook Web Access, Autodiscover and ActiveSync. If an inbound request is properly encrypted and passes the integrity checks, the contents are decrypted and run as a command. If it is not, the client gets a legitimate-looking Exchange error page — so anyone poking at the path, including a defender, sees a mail server behaving like a mail server.

The consequences stack up quickly. There is no C2 domain to block, no address to sinkhole, no hosting provider to notify. ESET could not even determine the ingress addresses the operators used. And the traffic carrying the tasking is mail traffic, which is the one category nobody is willing to drop.

There is a second variant, CerealHermit, with the network code removed entirely — it reads encrypted command files from disk and writes encrypted answers back. In some intrusions both were deployed, so a server cleared on the network side could still be under tasking through the file system.

The way in is not the network. It is the web logs, and one question: which of these paths does this Exchange version actually implement?

## Why

- **Every outbound-centric detection returns nothing, correctly.** No beacon, no C2 domain, no periodic egress. A network review of this host is clean while the backdoor is live, and that clean result is the most dangerous artefact in the case because it reads as an all-clear.
- **The victim's server is the infrastructure, so there is nothing to take down.** Blocklists, sinkholing, provider abuse reports and infrastructure pivoting — the standard toolkit for a backdoor — all assume the operator owns something. Here the operator owns a secret and a URL path on a machine the organisation cannot turn off.
- **The paths are chosen to sit inside the one traffic class that cannot be blocked.** An organisation can live without most protocols egressing. It cannot live without inbound HTTPS to its mail server, which is why these particular paths were picked and why flow-level analysis will not separate the tasking from the mail.
- **The error-page fallback makes the backdoor safe to probe, including by the operator.** A malformed request gets a believable Exchange error, so a mistake costs nothing and a scan reveals nothing. That same behaviour is a usable tell, because a synthesised error page and a genuine 404 rarely agree on headers, timing or body length.
- **The generalisable check does not depend on knowing the paths.** The published stems will change in the next intrusion. What does not change is the invariant: a request that got a success response on a path the installed product does not implement, with no authentication behind it. That query is reusable against any internet-facing application with a pluggable web stack.
- **Two independent tasking channels means one clean check is not enough.** With a file-based sibling deployed alongside the network one, clearing the web logs clears half the problem. The file-cadence check and the loaded-module reconciliation have to run too.
