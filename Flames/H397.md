false_positive_notes: |
  POST-heavy endpoints are normal. File upload handlers, API endpoints, SOAP and gRPC-over-HTTP
  services, and long-polling or streaming endpoints all produce sustained POSTs with large bodies, and
  some legitimately run for minutes at a time. Volume alone is not the finding.
  The narrowing that works is the combination of volume with provenance. Ask when the handler file was
  created. A legitimate API endpoint was deployed by a release process, exists in source control, and
  has a creation timestamp matching a deployment. A tunnel handler appeared outside any deployment
  window, often with a name chosen to blend into its directory, and has no counterpart in the
  repository. ASEC's example was renamed to look like an image-handling script, which is exactly the
  pattern — the filename will not look suspicious and should not be expected to.
  The second discriminator is directionality. An ordinary web application receives connections. A
  tunnel makes the web worker process originate them, to internal hosts, on ports that have nothing to
  do with HTTP. `w3wp.exe` connecting outbound to RDP, SMB, WinRM or database ports on internal systems
  is difficult to explain benignly, and in most environments that query alone returns a very short list.
  Do not rely on a missing child process. This tunneling mode may spawn nothing at all, so the usual
  web-shell heuristic of `w3wp.exe` parenting `cmd.exe` or `powershell.exe` will not fire. Its absence
  is not evidence of absence.
  The Temporary ASP.NET Files artefacts are corroboration, not a primary signal. Every ASP.NET page
  compiles on first request, so the directory is full of legitimate assemblies. What matters is a
  compiled artefact corresponding to a source file that should not exist, which means the directory is
  useful for confirming and timing an upload rather than for finding one.
  User-Agent filtering is weak here by design. ASEC notes the tool "allows for the adjustment of HTTP
  methods, headers, and User-Agent strings", so any specific string is operator-chosen and trivially
  changed. Rarity of a User-Agent against the server's own history is worth ranking on; a named value is
  not worth matching.

  Core filter. Over IIS logs, aggregate POST requests per URI stem and rank by request count, total
  bytes and distinct client addresses. A tunnel shows high volume concentrated on ONE URI from FEW
  clients, which is the inverse of a popular legitimate endpoint. Then check the handler file's creation
  time against deployment records, and query the web worker process for outbound internal connections.
  Sample Splunk SPL over IIS logs, ranking candidate URIs. The low client count is as important as the
  high request count — it is what distinguishes a tunnel from a busy API.
  `index=iis cs_method=POST | stats count AS requests, dc(c_ip) AS clients, sum(cs_bytes) AS bytes_in, sum(sc_bytes) AS bytes_out, avg(time_taken) AS avg_ms, values(cs_User_Agent) AS agents, min(_time) AS first, max(_time) AS last BY s_ip, cs_uri_stem | where requests > 100 AND clients < 5 | eval total_mb=round((bytes_in+bytes_out)/1024/1024,2) | sort - total_mb`
  Sample Splunk SPL for the off-hours element ASEC calls out, which is a useful secondary ranking on a
  server whose legitimate traffic follows business hours.
  `index=iis cs_method=POST | eval hour=strftime(_time,"%H") | eval shift=if(hour>=8 AND hour<=19,"business","offhours") | stats count BY cs_uri_stem, shift | xyseries cs_uri_stem shift count | fillnull value=0 | eval ratio=round(offhours/(business+1),2) | where offhours > 50 | sort - ratio`
  Sample KQL over Defender XDR for the pivot leg, which is the strongest single signal because it
  inverts the expected direction of traffic for a web server. The 30-day bound is the advanced hunting
  retention limit.
  `DeviceNetworkEvents | where Timestamp > ago(30d) | where InitiatingProcessFileName =~ "w3wp.exe" | where ActionType == "ConnectionSuccess" | where ipv4_is_private(RemoteIP) | where RemotePort !in (80, 443, 1433, 3306, 5432, 11211, 6379) | summarize Connections = count(), Targets = dcount(RemoteIP), Ports = make_set(RemotePort, 20), First = min(Timestamp), Last = max(Timestamp) by DeviceName, InitiatingProcessFileName | order by Targets desc`
  Sample KQL for the compiled-artefact and web-root file evidence, which dates the upload even after the
  source file is removed.
  `DeviceFileEvents | where Timestamp > ago(30d) | where FolderPath has_any (@"\Temporary ASP.NET Files\", @"\inetpub\wwwroot\", @"\inetpub\") | where ActionType in ("FileCreated", "FileModified", "FileRenamed") | where FileName endswith ".aspx" or FileName endswith ".ashx" or FileName endswith ".asmx" or FileName endswith ".dll" or FileName endswith ".compiled" | project Timestamp, DeviceName, ActionType, FileName, FolderPath, SHA256, InitiatingProcessFileName, InitiatingProcessAccountName | order by Timestamp asc`

  `index=sysmon EventCode=3 Image="*\\w3wp.exe" (DestinationIp=10.0.0.0/8 OR DestinationIp=172.16.0.0/12 OR DestinationIp=192.168.0.0/16) NOT (DestinationPort=80 OR DestinationPort=443) | stats count AS connections, dc(DestinationIp) AS targets, values(DestinationPort) AS ports BY Computer | sort - targets`

# H397

The web shell was not answering commands. It was carrying traffic.

That distinction decides whether you find this. ASEC describes an attacker who exploited a file upload flaw on an internet-facing IIS server, dropped Suo5 — an HTTP tunneling tool that exposes a SOCKS5 proxy — and renamed it from its tool name to `FilesImages.Aspx`, a name that looks entirely at home next to an image handler. From there they relayed TCP into the internal network.

A web shell and a tunnel produce completely different log signatures, and most web-shell hunting looks for the wrong one.

A web shell takes a command and returns output: short requests, small responses, bursty. A SOCKS5 proxy tunnelled over HTTP is relaying entire TCP sessions, so one URI absorbs sustained POST traffic for long stretches, with real volume in both directions and long per-request durations in full-duplex mode. You can measure every part of that from ordinary IIS logging — method, URI, byte counts, time-taken — with no content inspection at all.

The shape to query is high request volume concentrated on a *single* URI from a *small* number of clients. That is the inverse of a popular legitimate endpoint, which gets high volume from many clients. The low client count is doing as much work in that query as the high request count.

Two things not to build the hunt on.

Not the filename. It was chosen to blend into its directory and the next one will be too. Not the User-Agent either — ASEC notes the tool "allows for the adjustment of HTTP methods, headers, and User-Agent strings", so any specific value is an operator preference. Rarity against the server's own history is worth ranking on; a named string is worth nothing.

And not a suspicious child process. This mode may spawn nothing whatsoever, so the familiar `w3wp.exe` parenting `cmd.exe` heuristic never fires. Its silence proves nothing.

The strongest corroborating signal is directional. A web server receives connections; it does not make them. When `w3wp.exe` starts originating connections to internal hosts on RDP, SMB, WinRM or database ports, that is the pivot itself, and in most environments the query returns a list short enough to read.

One forensic detail worth keeping. ASEC notes that ASP.NET's dynamic compilation left DLL and compiled files in the Temporary ASP.NET Files directory. Those artefacts outlive deletion of the uploaded source, so when a handler has already been cleaned up they can still date the intrusion. The directory is full of legitimate assemblies, so this is for confirming and timing — not for finding.

## Why

- **Tunnels and web shells look nothing alike in logs.** Sustained high-volume POSTs with large bidirectional bodies and long durations is a different profile from command-and-response, and hunts written for the latter miss it entirely.
- **The volumetric shape needs no content inspection.** Standard IIS fields — method, URI, byte counts, time-taken, client IP — are enough, so the hunt works over logs already being collected.
- **Few clients plus high volume inverts the normal endpoint profile.** A legitimate busy endpoint serves many clients; a tunnel serves one operator.
- **The filename is deliberately unremarkable.** The sample was renamed to blend into its directory, so name-based and signature-based approaches start from behind.
- **Header-based detection is explicitly defeated.** The tool adjusts HTTP methods, headers and User-Agent strings, so only rarity against the server's own baseline is useful.
- **Direction of travel is the clearest corroboration.** A web worker process originating internal connections on non-HTTP ports inverts what a web server is supposed to do.
- **The absence of a child process is expected.** This mode may spawn nothing, which defeats the standard `w3wp.exe` spawning a shell heuristic and makes its absence uninformative.
- **Compilation artefacts outlive cleanup.** DLL and compiled files in the Temporary ASP.NET Files directory can date an upload whose source file has already been deleted.
