false_positive_notes: |
  Reflective assembly loading is not inherently malicious. Plenty of legitimate .NET software uses
  `Assembly.Load` over a byte array — plugin hosts, obfuscation and licensing products, ORMs that emit
  dynamic proxies, serialisers that generate code at runtime, and most commercial .NET packers. A hunt
  built on `Assembly.Load` alone will return a great deal of ordinary software.
  The discriminators are contextual rather than technical. Signature state is the strongest: legitimate
  software that loads assemblies reflectively is almost always signed by its publisher, and the binaries
  here are not. Location is next: a managed process doing this from `%APPDATA%` or a user Downloads path,
  rather than from Program Files, is a much shorter list. Provenance matters too — a binary extracted
  from an emailed archive carries Mark-of-the-Web, and a legitimate installed application does not.
  Metadata that contradicts the file is a reliable signal in this chain and worth querying on its own.
  The second stage labels its product information as "Kingsoft security software" and the third sets its
  assembly title to "Microsoft PC Manager", its product name to "PC Manager" and its company name to
  "Microsoft Corporation". A binary claiming Microsoft Corporation as its company while carrying no valid
  Microsoft signature is anomalous regardless of what else it does, and the query for that stands alone.
  Bitmap resources are not suspicious. Essentially every GUI application ships images, and resource size
  is a poor filter — the report describes a 471x471 region being read from one of them, which is an
  unremarkable size for a legitimate asset. Do not attempt to hunt this by image dimensions or resource
  entropy; hunt the loads and the context instead.
  FTP egress is the cleanest single signal in most modern environments, because almost nothing
  legitimate still uses it from a user endpoint. Where FTP is genuinely in use — some finance, logistics
  and manufacturing workflows retain it — enumerate the legitimate client processes and destinations
  once, and treat egress from any other process as the finding.

# H396

The malware was a picture of itself.

ASEC's write-up describes a phishing attachment — `{Company Name} LIST.ZIP`, posing as a product list awaiting pricing feedback — containing an executable rather than a document. The executable is a .NET application that presents itself as café management software, complete with Chinese-language assembly metadata and working UI code for managing menus and orders.

Its first act is to read the RGB values of every pixel in a bitmap resource called `Fee`, reassemble them into a byte array, and hand that array to `Assembly.Load`.

The DLL that comes out claims to be "Kingsoft security software". It reads the top-left 471×471 pixels of a second bitmap named `HATA`, XOR-decrypts the result with a key derived from the string `yjw`, and loads *that* through `AppDomain.Load`. The third stage sets its company name to "Microsoft Corporation" and its product name to "PC Manager", copies the original file to `%APPDATA%\AH.exe`, then decrypts a resource called `8VXmw2w` with the UTF-8 key `ZIyStAzSE`, strips the last byte, and produces AgentTesla.

Three reflective loads, two images, and nothing decrypted ever touches the disk.

That last point is what should shape the hunt. A file scanner looking at this sees a GUI application with some bitmaps in it. There is no dropped DLL, no staged payload, no unpacked executable to find — stages two and three exist only in process memory, reconstructed from pixel data. And the final payload is AgentTesla, a commodity stealer with thousands of builds and no hash worth chasing.

So hunt the structure instead, which is far more stable than any of the content.

Four observables, none of which depend on the payload. A managed process performing repeated runtime assembly loads. A binary running from `%APPDATA%` or Downloads that is unsigned. Metadata claiming Microsoft Corporation on a file carrying no Microsoft signature. And FTP credentials leaving the host.

A warning about the first of those: `Assembly.Load` over a byte array is thoroughly legitimate. Plugin hosts do it, licensing and obfuscation products do it, ORMs and serialisers emit code at runtime, and most commercial .NET packers are built on it. Querying reflective loading alone will bury you. What separates this is context — unsigned, user-writable path, Mark-of-the-Web from an emailed archive. Legitimate software that loads assemblies reflectively is almost always signed and almost always lives in Program Files.

The metadata contradiction is worth a query entirely of its own, because it needs no .NET knowledge at all. A binary that declares Microsoft Corporation as its company and carries no valid Microsoft signature is anomalous whatever else it is doing. In this chain it catches stage three directly.

Do not try to hunt this by image size or resource entropy. 471×471 is a perfectly ordinary dimension for a legitimate asset, every GUI application ships bitmaps, and that path leads only to false positives.

FTP is the cleanest signal left. Almost nothing on a modern user endpoint still speaks it, and this chain ends with credentials going to `server356.web-hosting.com` over port 21.

## Why

- **No decrypted payload ever reaches disk.** Two of the three stages exist only in memory, reconstructed from bitmap pixels, so file-based scanning and retrospective disk sweeps have nothing to match.
- **The final payload has no stable hash.** AgentTesla is commodity malware with thousands of builds, which makes structural detection the only durable option.
- **Steganography in a managed resource defeats carrier-file hunting.** There is no separate image file to inspect — the carrier is inside the executable, so the usual approach of finding anomalous standalone files does not apply.
- **The metadata contradicts itself in a queryable way.** "Microsoft Corporation" as company name with no valid Microsoft signature is a standalone anomaly requiring no knowledge of this chain.
- **The self-copy is a fixed, narrow artefact.** A copy of the running binary landing in `%APPDATA%` within minutes of extraction from an emailed archive is a tight, time-boundable join.
- **FTP egress from a user endpoint is nearly extinct.** Where it is not in legitimate use, a single port-21 connection from a user process is enough to open an investigation.
- **The lure targets a reply, not a click.** A request to review a product list and respond on pricing invites engagement from exactly the staff who handle supplier mail, so the recipient pool is predictable and worth scoping.
- **The chain is reusable beyond this actor.** Pixel-carried payloads with layered reflective loads is a packer pattern, so the structural hunt keeps paying off against unrelated families using the same construction.
