# H281

Storing implant configuration in an alternate data stream is not new. Choosing the hosts file to hang it
on is the part worth studying, because it is a small decision that quietly defeats several defensive
assumptions at once.

The hosts file is one of the most-watched files on Windows — plenty of organizations monitor it because
malware has historically modified it to hijack name resolution. But that monitoring almost always hashes
or diffs the file's *contents*: the unnamed stream. SPECTRE never touches the contents. It attaches a
named stream, `hosts:cache`, and stores the C2 endpoint there. The file's size, timestamps and hash as
reported by conventional tooling are unchanged. A directory listing shows nothing. A file-integrity
check passes.

The operational value to the attacker is infrastructure agility. The implant ships with a hardcoded C2
domain, but the ADS overrides it. That means rotating infrastructure across a fleet of compromised hosts
is a config rewrite, not a rebuild-and-redeploy — and because the new endpoint never has to appear in a
DNS query for the original domain, it sidesteps blocklists built from the initial IOC set. Defenders who
blocked the domain from the report have not disturbed the channel.

The detection is correspondingly narrow and durable. Not "look for alternate data streams," which drowns
in `Zone.Identifier`, but: does any host in the estate have a named stream on its hosts file? The
expected answer is zero, everywhere, always.

## Why

- **The expected value is exactly zero, which is the rarest and most useful property a hunt can have.**
  Most hunts trade false positives against coverage. This one does not: no legitimate software attaches
  a named stream to the hosts file. A sweep that returns any result at all is worth investigating, which
  makes it deployable estate-wide without a tuning phase.
- **It defeats file-integrity monitoring by construction, and FIM is the control most teams believe
  covers this file.** Because the unnamed stream is untouched, hash-based FIM reports the hosts file as
  unmodified — accurately. The organization's existing control fires no alert and, worse, provides
  positive assurance that nothing happened. This is a blind spot created by a reasonable control being
  applied at the wrong granularity.
- **The Sysmon gap is a configuration problem, not a capability problem, and it is cheap to close.**
  Sysmon can capture this today via Event ID 15, but the widely-used community configurations scope
  `FileCreateStreamHash` to Downloads, Temp and script extensions. Adding a
  `<TargetFilename condition="contains">drivers\etc</TargetFilename>` include rule costs nothing in
  volume — the directory is nearly static — and turns an invisible technique into a logged one.
- **Catching the config write is worth more than catching the beacon.** The whole point of the ADS is
  that the C2 endpoint is mutable and unknown to you. Network detections built from the reported domain
  expire the moment the operator rewrites the stream. The write itself is the stable observable, and it
  happens before the new channel is used.
- **It sits alongside kernel-level EDR blinding in the same implant, so the window is short.** The same
  intrusion set drops RTCore64.sys or DBUtil_2_3.sys to `%TEMP%`, loads them through the service control
  manager, and uses IOCTL-driven kernel read/write to clear `PspCreateProcessNotifyRoutine`,
  `PspCreateThreadNotifyRoutine` and `PspLoadImageNotifyRoutine`. Once those callback arrays are
  cleared, callback-dependent EDR is blind for the rest of the session — including to the file events
  this hunt relies on. Detection has to land early.
- **HEARTH had no T1564.004 coverage at all**, and ADS abuse is a long-standing, still-effective
  defense-evasion primitive that resurfaces in current tradecraft.
