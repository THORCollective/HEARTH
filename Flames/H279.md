  managed estates do install private root CAs for internal PKI. Three things separate this from a real
  deployment, and you should require at least two. (1) STAGING PATH: a genuine deployment runs from
  SCCM/Intune cache, a software-distribution share, or an admin session — not from

# H279

An adversary lands on a workstation, sits quietly for four and a half hours, and then does something
more durable than dropping a second implant: they enroll the host into a commercial endpoint-management
platform that they own. The enrollment is a silent `msiexec` install of a genuine, Zoho-signed
ManageEngine UEMS agent, and the command line carries two extra properties — `SERVER_ROOT_CRT=` and
`DS_ROOT_CRT=` — pointing at `.crt` files the attacker authored and staged in
`C:\Users\Public\Documents\work\`. Those become trusted root CAs, which is the whole point: once the
endpoint trusts the attacker's CA, the agent will happily accept the attacker's Endpoint Central server
as its legitimate management authority.

Everything after that is vendor-signed. Domain enumeration over SAMR/LSAD, patch and misconfiguration
scanning, USB control, interactive remote control, even a kernel file-filter driver
(`DCFAFilter.inf`, installed via `driversetup64.exe`) — all of it executed by binaries that carry a
valid Zoho signature and appear in EDR as a normal management agent doing its job. The report's own
removal guidance is the tell of how deep this goes: getting rid of it "requires uninstalling the full
UEMS agent, not just killing the RAT."

The certificate install is the narrowest, most durable place to catch this. A RAT can be rewritten; the
trust relationship cannot be established without writing a root CA and pointing the agent at a server.

## Why

- **The trust anchor is the beachhead, and it is a single observable write.** Everything the attacker
  gains downstream depends on the endpoint accepting their management server. That acceptance requires a
  root CA in the machine trust store. Unlike the RAT, the loader, or the C2 domain — all of which are
  disposable — the certificate install is structurally required and lands in a registry location that is
  small, slow-changing, and easy to inventory.
- **Post-enrollment, the attacker stops generating malware telemetry entirely.** The source report is
  blunt that after the agent is installed there was "no further malware, no LOLBin tricks." Detection
  stacks tuned to unsigned binaries, suspicious script hosts, and anomalous process trees go quiet
  precisely when the adversary gains the most capability. If you do not catch the enrollment, the next
  opportunity may be an outbound connection to an IP that looks like ordinary agent check-in traffic.
- **The property names are far more specific than the binary.** `msiexec.exe` is one of the noisiest
  binaries on Windows and `TRANSFORMS=` alone is a normal enterprise pattern. But `SERVER_ROOT_CRT=` and
  `DS_ROOT_CRT=` are product-specific properties whose entire function is to seed trust at install time.
  Requiring them together with a user-writable MSI path collapses a very noisy binary into a query that
  should return single digits per year in most estates.
- **A kernel file-filter driver arrives as a legitimate feature, not an exploit.** After reboot,
  `meaap.exe -c StartUp` pulled DeviceControl, BitLockerMgmt and an "EDR" component from the attacker's
  server, and `driversetup64.exe -install ...\DCFAFilter.inf` loaded a signed kernel filter driver. The
  attacker did not need BYOVD or a vulnerable driver — they inherited kernel-level file filtering as a
  supported product capability of the platform they now control.
- **Persistence survives every response action aimed at the malware.** Killing the hollowed svchost,
  deleting the `NvSvc` scheduled task and removing `Tax_Notice_10029.exe` leaves a fully functional,
  attacker-controlled management agent with interactive remote control. Responders who scope to "the
  RAT" will close the incident with the adversary still holding the host.
- **HEARTH had no T1553.004 coverage at all**, despite root-certificate installation being the enabling
  step for TLS interception, code-signing abuse, and — as here — rogue management-platform enrollment.
