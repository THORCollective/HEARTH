# H399

A web shell you have to ask for by name can be found by walking the web root. This one does not need to be asked for.

`auto_prepend_file` tells the PHP interpreter to load a file before every script it runs. Set it, and your code executes on requests to completely ordinary URLs — the site's own login page, its homepage, anything. The shell itself can sit outside the web root, where no web-root scan will ever look at it.

That is what the CL-UNK-1211 operators did. Unit 42 reports they "modified the auto_prepend_file value across all PHP configurations under the directories /etc/php/ and /opt/plesk/php/" — not one vhost, every PHP configuration on the box. On a Plesk host that is every site at once.

The file they pointed it at was `/usr/lib/php/plesk_sys_driver.php`. Read that path again: a real directory that genuinely holds PHP support files, and a name that sounds like something Plesk shipped. Unit 42 says it was deployed "to appear legitimate", and it is hard to argue. Nothing about it looks out of place in a directory listing, and it is nowhere near the document root.

So the usual instincts fail here. Scanning the web root finds nothing. Looking for strange paths in access logs finds nothing, because the requests are to real pages. Hunting for odd PHP files finds this one only if you happen to look in `/usr/lib/php/`.

What does work is reading the directive itself.

`auto_prepend_file` is legitimate and genuinely used — New Relic, Datadog, Blackfire, Xdebug, some WAF products and a few WordPress hardening plugins all prepend a bootstrap file. So its presence is never the finding. The value is. And there is a test that cuts through almost all of the noise: take the file the directive names, and ask the package manager who owns it. Vendor agents are installed by packages. `plesk_sys_driver.php` was not.

Two things to anticipate before running this. PHP version upgrades rewrite ini files wholesale, so a baseline needs versioning per PHP minor release or every patch cycle reads as a wall of findings. And the shape Unit 42 describes — the same directive changed across *every* ini file in the tree in one window — is itself the signal. No profiler installer does that.

## Why

- **It executes without being requested.** A prepended file loads before every PHP script on the host, so the attacker never needs a reachable URL and the defender never gets an anomalous path in an access log.
- **It lives outside the web root.** `/usr/lib/php/` is not covered by the web-root walks and document-root integrity checks that most teams point at PHP compromise.
- **One write covers every site on the host.** Unit 42 notes the targeted directories hold all default PHP and Plesk configuration, so modifying them is a single action with host-wide effect — efficient for the attacker and, usefully, a distinctive multi-file write pattern for the hunter.
- **The directive is enumerable and nearly static.** Unlike most persistence surfaces, the full set of values on a host fits in one grep, and on a stable host it does not change between PHP upgrades.
- **Package ownership is a cheap, decisive discriminator.** Legitimate prepended bootstraps ship in packages. A PHP file that no package owns, named by a directive that changed last week, has a short list of explanations.
- **The name was built to pass human review.** `plesk_sys_driver.php` reads as vendor plumbing, which is exactly why the hunt is keyed on the directive and the package database rather than on filename intuition.
- **The same operators deleted logs as routine practice.** Unit 42 describes attempts to delete authentication, command history, web server and OS logs, which argues for hunting the configuration state that remains over the command that created it.
