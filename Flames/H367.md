# H367

The dropper in this chain does nothing in a sandbox. That is by design, and it is the reason the behaviour has to be hunted rather than detonated.

Rapid7's October 2026 research on BPFDoor and AVERAT describes a small x86-64 ELF with no networking at all — `fopen`, `fwrite`, `chmod`, `system`, `sleep`, `access`, and little else. It is a local installer, run after access is already established. Before it does anything it checks for `/tmp/flag`. If that file is absent, it exits. Nothing in a normal appliance build creates `/tmp/flag`, and the dropper never writes it either — the operator does, by hand, which means an analyst who runs the sample in isolation observes no malicious behaviour whatsoever.

When the gate passes, the dropper writes a shell script to the appliance's bulk-storage mount under the name `updIptable.php` — a `.php` extension on a file that begins `#!/bin/sh` — chmods it, and hands it to `system()`. The script is nine lines and does the same thing twice:

```
/bin/cp -f /addpkg/sbin/update /sbin/ntpdate
chmod 755 /sbin/ntpdate
/sbin/ntpdate &
sleep 10
rm -rf /sbin/ntpdate
```

Ten seconds after each payload starts, its file is gone. Both processes keep running. `/proc/<pid>/exe` resolves to `(deleted)`, there is nothing to hash or quarantine, and a responder who greps `/sbin` finds an empty result.

The part worth admiring is that `/sbin/ntpdate` is the dropper re-executing itself. The second instance finds the `.php` file already present, fails its own gate, and settles into a two-second watchdog that rewrites the script and recreates a marker file whenever either disappears. That is also why the chain contains no persistence code at all: `/addpkg/sbin/` is the appliance's own add-on package directory, so the firmware relaunches it at boot as a matter of course.

Two things survive all of this. The ordered process sequence, and the unlinked executable.

## Why

- **The guardrail defeats detonation, so behaviour is the only reliable signal.** A sample that no-ops without `/tmp/flag` produces a clean dynamic-analysis verdict. The ordered `sh -c` → `cp` → `chmod` → execute → `rm` sequence is what actually distinguishes the chain, and Rapid7 assesses it as high-fidelity on its own.
- **Ten seconds is the discriminator.** Package installers copy and `chmod` into `/sbin` all the time. None of them delete a binary that is still running. The window is what turns a common administrative pattern into a specific one.
- **A `.php` file that starts `#!/bin/sh` has no benign explanation.** It is a one-line retrospective sweep across an estate and it does not depend on the operator reusing any filename, because the mismatch is structural rather than nominal.
- **The unlinked executable is the residue the design cannot avoid.** The payload has to be running to be useful, and a running process the kernel can account for is a process the kernel will tell you about. `ls -l /proc/*/exe | grep '(deleted)'` is the entire sweep.
- **`/tmp/flag` is anomalous by its own absence from the build.** The dropper checks it and never writes it. Finding it on an appliance means someone placed it there, which makes it a cheap indicator of operator presence independent of whether the payload is still resident.
- **The mount options are both triage and mitigation.** `system()` runs `sh -c` against a real shebang, so `/HDD` has to be writable *and* exec-capable. A `noexec` bulk-storage mount returns `EACCES` and the shell offers no interpreter fallback — this specific chain simply fails.
- **Evidence does not survive the reboot, and the implant knows it.** AVERAT's reboot handler calls `sync()` before forcing a restart through the kernel rather than through init. Flushing buffers before destroying volatile state is the behaviour of an operator who knows precisely which artefacts persist — so collect memory, argv and socket metadata before anyone power-cycles the device.
