title: A servlet filter that exists only in heap — Jenkins Script Console used to register a tunnel on the pre-auth login path, with nothing written to disk
hypothesis: >-
  A Jenkins administrator can execute arbitrary Groovy inside the running JVM, and anything registered
  that way lives in heap rather than on disk. ASEC describes an attacker who did exactly this: "After
  gaining administrator privileges on a Java-based Jenkins server, the attacker exploited the Script
  Console, a feature for executing Groovy scripts. Using a Groovy script, the attacker registered the
  Suo5 functionality in runtime memory as a Servlet and Filter, thereby establishing a Path to internal
  systems without requiring a separate file." The tunnel then rode an endpoint that is reachable before
  authentication — web logs "recorded requests for /login.Php or /login". So file integrity monitoring
  sees nothing, web-root scanning sees nothing, and the request path is one every scanner already
  ignores. Hunt the Script Console invocation, the JVM-side evidence ASEC names, and sustained POSTs to
  an authentication endpoint that produce no authentication events.

false_positive_notes: |
  The Script Console is a legitimate administrative feature, and in some organisations it is used
  routinely for diagnostics, bulk job edits and plugin troubleshooting. Its use is not by itself the
  finding — but it should be a short, attributable list, and every invocation should map to a known
  administrator and ideally to a change record. In an environment where Script Console use is genuinely
  frequent, the per-user and per-source-address profile is what to rank on.
  The login-path traffic needs care, because sustained POSTs to an authentication endpoint is also
  exactly what credential stuffing looks like. The discriminator is the outcome: a brute-force campaign
  generates a large volume of authentication FAILURES, and a tunnel generates almost none, because the
  injected filter intercepts the request before the authentication logic ever runs. POST volume high and
  authentication-event volume near zero is the combination that matters, and either number alone is
  misleading.
  Byte counts help separate the two further. Credential attempts are small and uniform. Relayed TCP
  sessions are large and variable, in both directions.
  Do not expect filesystem evidence. ASEC is explicit that "no actual files were left on disk". File
  integrity monitoring over the web root, web-shell scanners and scheduled filesystem sweeps will all
  return clean, and a hunt that treats a clean filesystem as reassurance will close this incident as a
  false positive.
  Stack traces are strong but inconsistent evidence. ASEC observed a ClassFormatError, which suggests a
  class-loading problem during injection, and that is the kind of error that appears when something goes
  wrong rather than when everything works. A clean injection may leave no exception at all, so treat
  trace evidence as high-value when present and uninformative when absent.
  Restarting the JVM removes the filter entirely. That is worth knowing before any remediation step,
  because a restart destroys the only copy of the evidence — capture a heap dump or thread listing from
  the live process first.

  What Suo5 is. ASEC describes an HTTP/HTTPS-based tunneling tool that "uses HTTP/HTTPS communication to

  through a system that has already been compromised".
  The incident. The entry condition was administrative access to Jenkins; ASEC does not say how it was
  obtained. The attacker then used the Script Console to register the tunnel as a servlet and filter in
  runtime memory, "thereby establishing a Path to internal systems without requiring a separate file".
  Not stated in the report: how the administrator credentials were acquired, the Groovy source itself,

  web logs recorded requests for /login.Php or /login. Java logs revealed the PluginServletFilter chain,
  a doFilter() call in Script1.Groovy, and an error stack trace related to ClassFormatError." Those are
  four distinct evidence sources: the absence of filesystem artefacts, the request path, the filter
  chain visible in JVM logging, and a class-loading exception.
  Why a servlet filter is a well-chosen place to hide. A filter sits in front of request handling, so it
  can claim a request before the application's own routing or authentication logic sees it. Registering
  one in the running JVM means there is no deployed artefact, no WAR change, no file in the web root and
  nothing for file integrity monitoring to compare against a known-good state. It also means the tunnel
  disappears on restart — which is an evidence-handling problem as much as a persistence limitation.
  Why the login path is the clever part. An authentication endpoint is reachable before authentication,
  by definition. It is excluded from the access controls protecting everything else, it is expected to
  receive POST requests, and its traffic is routinely dismissed as noise or as a brute-force attempt
  already handled by lockout. A filter bound there inherits all of that cover. Not stated in the report:
  whether the filter was bound specifically to intercept the login path or whether it answered on any
  path and the login path was simply what the operator used.
  Core filter. Three independent queries, any of which can start the investigation. First, every Script
  Console invocation, attributed to a user and a source address. Second, POST volume to the login path
  compared against the count of authentication events it produced. Third, outbound connections from the
  JVM process to internal hosts on ports unrelated to its function.
  Sample Splunk SPL for Script Console invocations in the Jenkins access log. These endpoints should be
  rare and fully attributable in any environment.
  `index=jenkins sourcetype=jenkins:access (uri_path="/script" OR uri_path="/scriptText" OR uri_path="*/scriptText" OR uri_path="*/script") method=POST | stats count AS invocations, values(user) AS users, values(clientip) AS sources, min(_time) AS first, max(_time) AS last BY uri_path | sort - invocations`
  Sample Splunk SPL for the login-path tunnel, comparing request volume against authentication outcomes.
  A tunnel produces the first without the second, which is what separates it from credential stuffing.
  `index=jenkins sourcetype=jenkins:access uri_path="/login" method=POST | stats count AS posts, dc(clientip) AS clients, sum(bytes_in) AS bytes_in, sum(bytes_out) AS bytes_out, avg(duration) AS avg_ms BY clientip | where posts > 100 | eval total_mb=round((bytes_in+bytes_out)/1024/1024,2) | join type=left clientip [ search index=jenkins sourcetype=jenkins:security "Failed to authenticate" | stats count AS auth_failures BY clientip ] | fillnull value=0 auth_failures | eval ratio=round(auth_failures/posts,3) | where ratio < 0.05 | sort - total_mb`

# H398

There was no file. There was never going to be a file.

ASEC describes an attacker who reached administrator on a Jenkins server and opened the Script Console — the built-in feature that executes Groovy inside the running JVM. They used it to register Suo5's tunnel as a servlet and filter directly in runtime memory. No WAR deployment, no web-root write, no plugin install. The tunnel existed in heap and nowhere else.

Then it answered on `/login`.

Both halves of that are worth pulling apart, because each defeats a different control.

The in-memory half defeats everything that looks at disk. File integrity monitoring compares the filesystem against a known-good state and finds it unchanged, because it is unchanged. Web-shell scanners sweep the web root and find nothing. Scheduled filesystem baselines come back clean. ASEC states it flatly: "no actual files were left on disk." A hunt that treats a clean filesystem as reassurance will close this as a false positive, which is precisely the risk.

The login-path half defeats everything that looks at access control. An authentication endpoint is, necessarily, reachable before authentication. It is excluded from the policies protecting every other path, it is supposed to receive POSTs, and its traffic gets dismissed as noise or as brute force that lockout already handles. A filter bound there inherits all of that cover for free — and because a filter runs *in front of* request handling, it claims the request before Jenkins' own authentication logic ever sees it.

Which hands you the cleanest discriminator in this hunt.

Credential stuffing against `/login` produces a flood of authentication *failures*. A tunnel on `/login` produces almost none, because authentication never runs. High POST volume with near-zero authentication events is the combination; either figure alone tells you the wrong story. Byte counts corroborate — credential attempts are small and uniform, relayed TCP sessions are large and variable in both directions.

The other two starting points are simpler. Script Console invocations should be a short, fully attributable list in any organisation, mapping to named administrators and ideally to change records. And a CI server that begins originating connections to arbitrary internal hosts and ports is doing something no build job asks for.

ASEC also found JVM-side wreckage: the servlet filter chain visible in Java logs, a `doFilter()` call from a Groovy script, and a `ClassFormatError`. Treat that kind of trace as high-value when present and meaningless when absent — a class-loading exception appears when injection goes *wrong*, and a clean injection may throw nothing at all.

One operational warning. Restarting the JVM removes the filter, which sounds like remediation and is actually evidence destruction. The filter exists only in memory, so capture a thread dump or heap dump from the live process before anyone bounces the service.

## Why

- **Filesystem-based detection cannot see this.** No file is written, so FIM, web-shell scanners and filesystem baselines all return clean — and that clean result is actively misleading.
- **A servlet filter intercepts before the application decides anything.** It claims requests ahead of routing and authentication, so application-level access controls never apply to it.
- **The login path is pre-authentication by design.** Binding there inherits an endpoint that is reachable without credentials, expected to receive POSTs, and routinely dismissed as noise.
- **POSTs without authentication failures is the discriminator.** Credential stuffing generates failures in bulk; a tunnel generates none, because the authentication logic never executes.
- **The Script Console is a short, attributable list.** Legitimate use maps to named administrators and change records, so invocation review is cheap even where the feature is used routinely.
- **A CI server originating internal sessions is hard to explain.** Build infrastructure pulls from source control and pushes to artefact stores; arbitrary internal hosts and ports are not part of that pattern.
- **Stack-trace evidence is asymmetric.** A `ClassFormatError` or filter-chain reference is strong proof when present, and its absence means only that injection went smoothly.
- **Remediation destroys the evidence.** The filter lives only in heap, so a restart removes both the attacker and every trace of what they installed.
