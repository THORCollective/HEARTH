hypothesis: >-
  After reaching root on a remote-access gateway, the operator installs a two-part implant whose names are
  chosen to read as product components. The standalone half is launched from a temporary directory under
  nohup with its output sent to a dot-prefixed log, then relocates itself into the appliance's boot
  persistence directory under a near-identical name so it survives reboot. The second half is a shared
  object the first one carries and writes into the system library directory, with a name shaped like an
  existing firewall library; the implant then loads it into selected appliance processes, where it hooks
  networking functions so that specially marked operator connections are handled while ordinary traffic
  continues to the real service. Both halves authenticate and encrypt over one fixed TCP port and one
  fixed Unix socket, and the standalone half can tamper with binary firewall logs, so the appliance's
  own record of the connection is not trustworthy.

false_positive_notes: |
  Appliance library and boot directories are tightly controlled by the vendor package, which makes the provenance check unusually clean, but the naming is deliberately close to legitimate components.
  - The names are the point of the trick, so matching on them loosely will produce confusion rather than false positives. A genuine appliance has a config daemon and genuine firewall libraries with similar names. Compare against the vendor manifest and the package database, not against a name pattern, and record the legitimate names for the running version before hunting so the near-miss is obvious.
  - Vendor hotfixes and support-supplied debug builds do add and replace files in these directories. Reconcile every unowned file against change records and support cases; the distinguishing feature is that a vendor file arrives with a package transaction and a support case number, and this one arrives with neither.
  - Legitimate interposer libraries exist on appliances. Vendor instrumentation, debug tooling and some monitoring agents hook networking functions on purpose. Establish which are approved and treat that inventory as the allowlist, the same way the GPU-library case in [[H464]] is handled.
  - Dot-prefixed files in temporary directories are created by ordinary software. A hidden log is corroboration for an unowned binary, never a finding on its own.
  - A listener on a non-product port may be a support tunnel or a monitoring probe. The combination that matters is a listener on all interfaces, on a port no package claims, owned by a process whose binary is not package-owned - any one of those three alone is weak.
  - If the appliance has already been rebuilt, this hunt returns nothing from the live host. Check whether the rebuild restored a configuration backup or a snapshot, because the implant's reported capability set includes backup and snapshot persistence, and a clean rebuild that restores a tainted backup is not clean.

  Source reporting is Check Point Research's November 12, 2026 analysis of exploitation against unpatched Check Point Security Gateways. The access chain that precedes this implant is covered in [[H477]]; this hunt covers what the operators installed once they had root. CPR reports that the attackers "moved from web-based access to a standalone passive backdoor, launching the TSGA malware (/tmp/CPconfigdaemon) in the background and redirecting its output to a hidden temporary log", recording the command verbatim as `nohup /tmp/CPconfigdaemon >/tmp/.bd.log 2>&1 & printf started`.
  Closest existing HEARTH coverage - [[H403]] covers an implant with no file, port or connection of its own, injected by ptrace into logging and VPN daemons and speaking through their existing traffic; that is a more extreme version of the same idea and the nearest neighbour in the corpus. [[H366]] covers a raw packet socket with a classic BPF filter on a Linux appliance. The distinction here is a two-part implant with a package-ownable footprint: a file in the boot persistence directory and a shared object in the system library directory, both of which a provenance check can settle, plus a fixed port and socket. [[H464]] covers the same provenance logic applied to a replaced library on a GPU host, and [[H479]] covers the Windows equivalent of the marked-connection idea on a shared service port.
  Core filter 1, the boot persistence directory - The highest-value check. CPR reports that "when executed as root, the malware relocates itself and relaunches under the name slot_CPconfigdaemon in the boot persistence directory." Inventory that directory, hash everything in it, and reconcile against the vendor package manifest. A binary that no package owns is the finding. The reported name is one character class away from a real product daemon, which is why the check is ownership and not naming: CPR's IOC table gives SHA-256 4171b521fa6441382aa2fa014a08e18ff9a6e0ab6096c9144072bf46b37a2ec8 for `slot_CPconfigdaemon` and d7549671c7189979f0624ec52dad9ea6a707d23146e3585ab8f8c4720eca0c63 for the staged `CPconfigdaemon`.
  Core filter 2, the shared object - CPR reports that the executable "carries a second component, TSProxy: an embedded shared library that it writes to /lib/libcpfwcommon.so", and that "its injection code loads this library into selected appliance processes, where it intercepts networking functions to handle specially marked attacker connections while allowing ordinary traffic to continue." Two checks follow. First, provenance on that path: a shared object in the system library directory that no package claims, with a name shaped like an existing firewall library. Second, which processes have it mapped: read `/proc/<pid>/maps` for the appliance daemons and look for a library that the binary does not link at build time. The second check is the one that survives a renamed file.
  Core filter 3, the fixed port and socket - CPR reports that TSGA and the related PhiliKit implant "both implement authenticated, encrypted communications through TCP port 11072 and the Unix socket /tmp/.p_sock", and that where "the analyzed PhiliKit build restricts its TCP listener to loopback, TSGA listens on all IPv4 interfaces." That difference is the useful part: a loopback listener needs local access to reach, and an all-interfaces listener on a gateway is reachable from the network. Inventory listening sockets by interface and check for a Unix socket at that path. Collect the inbound-connection evidence from a sensor in front of the appliance rather than from the appliance, for the reason in filter 5.
  Core filter 4, the capability set as a triage guide - CPR describes TSGA as providing "encrypted remote access, configuration theft, backup and snapshot persistence, process injection, and binary firewall-log tampering", and notes that operators "can execute arbitrary shell commands and Python or Perl scripts, retrieve their output, transfer files using operator-selected paths, and collect selected or full appliance configurations over the encrypted channel." Two of those shape the response rather than the detection: configuration theft means the gateway's full configuration, including any credentials stored in it, should be treated as disclosed, and backup and snapshot persistence means a restore is not a remediation until the backup is checked.
  Core filter 5, why the appliance cannot be the witness - Binary firewall-log tampering is in the reported capability set. Any conclusion drawn from the gateway's own connection logs about whether the implant was reached is therefore weaker than the same conclusion drawn from a device in front of it. Where a span, upstream firewall or flow record exists, prefer it. Where it does not, say so in the finding rather than reporting the appliance's silence as absence.
  Sample out-of-band triage, read-only, run from expert mode with results compared against the vendor manifest off the box:
  ```bash
  set -u
  echo "== unowned files in library and boot persistence directories"
  for p in /lib/libcpfwcommon.so; do
    if [ -e "$p" ]; then ls -la "$p"; sha256sum "$p"; fi
  done
  echo "== staged binary and hidden log"
  ls -la /tmp/CPconfigdaemon /tmp/.bd.log /tmp/.p_sock 2>/dev/null || echo "none of the staged paths present"
  echo "== listeners, by interface"
  netstat -lnp 2>/dev/null | grep -E ':11072|LISTEN' | head -40
  echo "== unix domain sockets"
  netstat -lxp 2>/dev/null | head -40
  echo "== which processes have the library mapped"
  for pid in $(ls /proc | grep -E '^[0-9]+$'); do
    if grep -qs 'libcpfwcommon' "/proc/$pid/maps" 2>/dev/null; then
      printf 'pid %s cmd %s\n' "$pid" "$(tr '\0' ' ' < /proc/$pid/cmdline)"
    fi
  done
  ```
  The last loop is the durable check. A renamed binary and a renamed library defeat every path above it; a shared object mapped into a daemon that does not link it is a structural consequence of the injection and cannot be renamed away.
  Lineage, for scoping other appliances - CPR reports that "TSGA and TSProxy are Check Point-specific components linked to the previously reported PhiliKit-associated toolset", that PhiliKit "is a passive backdoor and installer targeting Ivanti VPN appliances", and that both families have "roots in Tiny SHell". TSProxy "shares distinctive configuration with libdssafe.so, the networking component embedded in PhiliKit package: identical operator credentials, transport secrets, three matching activation-selector digests, and the same TLS certificate and private key" - SHA-256 fb1a6235eb6bce8c9ec8cd8bb85f17c9c2bde8ecb45b7a243a30ceadf26654da. The practical reading is that an estate with more than one appliance vendor should run the equivalent provenance check on each, because the same toolset has been retargeted at least once.
  Attribution caution, stated as the report states it - CPR notes the PhiliKit association with China-nexus UNC5221 but writes that "the evidence does not allow us to assess with high confidence the true nature of this operation", listing an initial-access-broker role and a false-flag operation among the plausible scenarios.
  Expected, not observed by Check Point - How the marked connections are selected and what the marker is. CPR describes TSProxy as handling "specially marked attacker connections" and names "three matching activation-selector digests" shared with libdssafe.so, but does not publish the selector values or the on-wire shape, so there is no network signature to build here and the hunt stays on the host and the provenance.

# H478

`CPconfigdaemon`, then `slot_CPconfigdaemon`. And a shared library called `libcpfwcommon.so`.

If you administer a Check Point gateway, those names do not make you look twice. That is the entire design.

Check Point Research found this pair on gateways compromised through the Mobile Access portal in late October 2026. The first half starts from `/tmp` under `nohup`, with its output redirected into a dot-prefixed log so nothing appears on a console. Once it has root it moves itself into the boot persistence directory under a slightly different name and comes back after every reboot.

The second half is carried inside the first. It gets written into the system library directory and then injected into appliance processes, where it hooks the networking functions. Connections carrying the operator's marker get handled by the implant. Everything else continues to the real service and nobody notices anything.

Both halves listen on TCP 11072 and talk over a Unix socket at `/tmp/.p_sock`. The related PhiliKit build on Ivanti appliances bound that listener to loopback; this one binds to every IPv4 interface, which means it is reachable from the network rather than only from the box.

And there is one more item in the capability list that changes how you read everything else: binary firewall-log tampering. The appliance can rewrite its own record of who connected to it.

So do not ask the gateway whether it was reached. Ask the package manager what it owns, ask `/proc` which daemons have a library mapped that they never linked, and ask the device in front of the gateway what arrived.

## Why

- **Package ownership is the one question the implant cannot answer for itself.** The names are chosen to defeat recognition, so matching names is a losing game. A file in a library or boot directory that no installed package claims is a structural anomaly on an appliance, where essentially every file comes from a vendor package — and the check is cheap enough to run across an entire estate.
- **An injected library shows up in `/proc`, and renaming does not help.** The operator can call the shared object anything. They cannot make a daemon's memory map stop listing a library the binary does not link. That makes the mapped-module check the durable version of this hunt, and it is the one to automate.
- **The listener binds to every interface, not loopback.** The sibling family on Ivanti appliances restricted itself to local access. This one does not, which turns a post-exploitation convenience into a reachable service on an internet-facing device — and makes an inbound-connection record from an upstream sensor directly meaningful.
- **Log tampering inverts the usual evidence hierarchy.** On most hosts the local log is the primary source. Here it is in the implant's reported capability set, so the appliance is the least reliable witness to its own compromise. Any hunt on this family has to be designed to be answerable from off the box.
- **Backup and snapshot persistence means remediation can reinstall it.** Rebuilding a gateway and restoring its configuration is the standard recovery path, and the reported capability set specifically includes riding a backup. A clean rebuild from a tainted backup produces an appliance that is trusted again and still compromised, which is why this belongs in the finding and not only in the detection.
