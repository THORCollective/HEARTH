title: Native curl.exe copied into %TEMP% and executed under a different name to fetch the next stage
hypothesis: >-
  Two of the seven LNK campaign types observed against South Korean targets in July 2026 use Windows' own
  `curl.exe` as the downloader — one invoking it directly from the LNK to pull an HTA into `%TEMP%`, the other
  copying `curl.exe` into `%TEMP%` first and then using it to fetch a decoy PDF and a BAT downloader. Copying an
  in-box utility out of `System32` before use is a deliberate move: it defeats detections scoped to the
  System32 path, and renaming the copy defeats detections scoped to the filename. What it does not change is the
  PE version resource, which still reports `OriginalFileName` of `curl.exe`. Hunt for any process whose
  `OriginalFileName` is `curl.exe` executing from outside `System32`/`SysWOW64` — and for `curl.exe` being
  written into `%TEMP%`, `%APPDATA%` or `C:\ProgramData\` by a shell, regardless of the name it is given.

required_data_sources:
  - Sysmon Event ID 1 / Windows Security 4688 — Image, **OriginalFileName**, CommandLine, ParentImage, ParentCommandLine, User, Hashes. OriginalFileName is mandatory for the rename half of this hunt and is absent from raw 4688, so Sysmon or an EDR surfacing PE metadata is a prerequisite
  - Defender XDR DeviceProcessEvents — ProcessVersionInfoOriginalFileName, ProcessVersionInfoFileDescription ("The curl executable"), FolderPath, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessCommandLine
  - Sysmon Event ID 11 (FileCreate) / DeviceFileEvents — the copy operation itself, i.e. an `.exe` written into `%TEMP%`, `%APPDATA%` or `C:\ProgramData\` whose SHA256 matches the in-box `System32\curl.exe` for that OS build. Hash-matching the copy catches the rename before any execution happens
  - Sysmon Event ID 3 / DeviceNetworkEvents — the resulting egress, carrying RemoteUrl, RemoteIP, RemotePort, InitiatingProcessFileName, InitiatingProcessFolderPath. A curl-metadata process connecting outbound from `%TEMP%` is the pairing that makes this conclusive
  - PowerShell Script Block Logging (EID 4104) and cmd.exe command lines — the LNK's embedded `copy`/`Copy-Item` of `curl.exe`, and the download command with its `-o`/`--output` target

  - Sysmon Event ID 15 (FileCreateStreamHash) — MOTW on the downloaded HTA/BAT/PDF, showing internet provenance of the second stage
  - Web proxy / TLS-inspecting gateway logs — user-agent and destination for the fetch. Windows `curl.exe` sends a default `curl/x.y.z` user-agent unless overridden, which is itself uncommon from an endpoint
  - Windows Security 4698 / TaskScheduler Operational — the persistence registered after the download completes, in every one of these campaign types
false_positive_notes: |
  `curl.exe` has shipped in Windows since 1803 and is used legitimately, but the specific behaviours this hunt
  targets — a copy out of System32, or execution under a different name — have a much narrower benign
  population. Enumerate:
  - Developer tooling and SDKs that bundle their own curl build. These have their own version metadata and
    usually their own filename containing "curl", and they live under `Program Files`, a language runtime
    directory, or a project workspace — not `%TEMP%`.
  - Git for Windows, MSYS2, Cygwin, WSL interop shims, and vendored CI runners, which ship curl in their own
    install trees.
  - Software packaging, imaging, and build systems that stage tooling into a temp working directory. These run
    under a build or deployment account, from a consistent path, on a schedule or a pipeline trigger.
  - Container and Kubernetes tooling, and vendor agents that use curl for health checks.
  - Legitimate administrative use of `curl.exe` from `System32` — extremely common and explicitly NOT what this
    hunt looks for. Do not widen it to "curl executed"; that returns everything and is the reason this hunt is
    scoped to path and rename.
  The separators:
  (1) HASH IDENTITY. If the binary in `%TEMP%` hashes identically to `C:\Windows\System32\curl.exe` on that OS
      build, it is a copy of the in-box utility, not a vendored one. This is exact, not heuristic.
  (2) NAME MISMATCH. `OriginalFileName` = `curl.exe` while the image path contains no "curl" — the published
      SigmaHQ condition. A vendored curl keeps its name.
  (3) PARENT. `cmd.exe` or `powershell.exe` descended from `explorer.exe` opening an LNK is not a build system.
  (4) WHAT IT FETCHED. An `.hta`, `.bat`, `.vbs`, `.ps1`, or `.exe` written to `%TEMP%` seconds later, with
      Mark-of-the-Web, followed by that file executing.

  PLATFORM: Windows. T1036.003 also covers Linux and macOS, but this hunt is Windows-specific: it targets the
  in-box `C:\Windows\System32\curl.exe` shipped since Windows 10 1803 and the `%TEMP%` staging convention.

  Kimsuky. The report cites no ATT&CK IDs; this mapping is derived from described behaviour. Type B: "LNK
  invokes native `curl.exe` to drop an HTA into `%TEMP%`", staged from an actor-run GitHub repository or Google
  Drive, leading to a downloader named `sys.dll` and memory-loaded infostealer, keylogger and backdoor
  components. Type F: an LNK with CMD plus PowerShell that "copies `curl.exe` to `%TEMP%`", downloads a decoy
  PDF and a BAT downloader, and the BAT then "installs a Python package and registers `pythonw.exe` under a
  disguised name in the Task Scheduler." (The source page renders these as `curl.Exe`, `sys.Dll`, `pythonw.Exe`
  — a rendering artifact of the site, not real filenames. Hunt the conventional lowercase forms.)

  WHY COPY IT AT ALL? Because a large amount of published detection content is scoped to
  `C:\Windows\System32\curl.exe`, and because AppLocker and WDAC policies are frequently written as path rules.
  Copying the binary to `%TEMP%` sidesteps path-scoped detection; renaming it sidesteps name-scoped detection;
  and doing both leaves an adversary with a fully functional, Microsoft-shipped downloader that no reputation
  system will ever flag. MITRE describes exactly this variant of T1036.003: "copying/moving a legitimate utility
  to a different directory and renaming it to defeat detections based on execution from non-standard paths."

  DETECTION — RENAME (highest value, one condition). Defender XDR:

      DeviceProcessEvents
      | where ProcessVersionInfoOriginalFileName =~ "curl.exe"
             or ProcessVersionInfoFileDescription =~ "The curl executable"
      | where not(FolderPath has "curl")
      | project Timestamp, DeviceName, AccountName, FileName, FolderPath, ProcessCommandLine,
                InitiatingProcessFileName, InitiatingProcessCommandLine, SHA256

  This is the SigmaHQ "Renamed CURL.EXE Execution" logic (id `7530cd3d-7671-43e3-b209-976966f6ea48`). Add a
  path condition for `\Temp\`, `\AppData\`, `\ProgramData\`, `\Users\Public\` to target the staging case
  specifically, and keep the unrestricted version as a lower-volume standing query.

  DETECTION — THE COPY, BEFORE EXECUTION:

      DeviceFileEvents
      | where ActionType == "FileCreated"
      | where FolderPath has_any (@"\Temp\", @"\AppData\", @"\ProgramData\", @"\Users\Public\")
      | where FileName endswith ".exe"
      | where SHA256 in (<SHA256 of System32\curl.exe for each OS build in the estate>)
      | project Timestamp, DeviceName, FolderPath, FileName, SHA256,
                InitiatingProcessFileName, InitiatingProcessCommandLine

  Building that hash list is a one-off task per OS build and it makes the detection exact rather than
  heuristic — the copied binary is byte-identical to the system one by definition.

  DETECTION — COMMAND-LINE ARGUMENTS. MITRE's guidance on this technique is to key on distinctive arguments
  rather than on filenames, which for curl means `-o` / `--output`, `-O`, `-T` / `--upload-file`,
  `--data-binary`, `-k` / `--insecure`, `--proxy`, `-A` (custom user-agent), and `-H` with unusual headers.
  A command line containing `-o` with a `%TEMP%` destination and an `http` URL is the download step regardless
  of what the binary is called. Note the TerminalFix chain in the same week's intel used a custom User-Agent on
  its initial ZIP fetch too — custom UA on an endpoint download is a recurring shape.

  DETECTION — THE PAIRING THAT CLOSES IT. One query joining three events inside a few minutes: (1) an `.exe`
  written to `%TEMP%` matching the System32 curl hash, or a process with curl metadata running from `%TEMP%`;
  (2) an outbound connection from that process; (3) an `.hta`, `.bat`, `.vbs`, `.ps1` or `.exe` created in the
  same directory immediately afterwards, carrying Mark-of-the-Web, and then executed. Each event alone has a
  benign population; the sequence does not.

  WHAT FOLLOWS, and is worth pivoting to on any hit: `mshta.exe` executing the downloaded HTA (T1218.005);
  a downloader named `sys.dll`; memory-only loading of the infostealer/keylogger/backdoor stages, meaning no
  further on-disk payload exists to find; scheduled-task persistence registered under a disguised name — see
  [[B040]]; and C2 staged through GitHub or Google Drive rather than actor-owned infrastructure — see [[M036]].

# H276

`copy C:\Windows\System32\curl.exe %TEMP%\update.exe` is not an exploit. It is two seconds of work that quietly invalidates a category of detection: anything scoped to the System32 path, anything scoped to the filename, and any AppLocker path rule that assumed in-box utilities stay where Microsoft put them. The attacker keeps a fully functional, Microsoft-signed downloader and loses nothing.

Two of the seven LNK campaign types AhnLab tracked in July did exactly this — one calling `curl.exe` in place to drop an HTA into `%TEMP%`, the other copying it there first and using it to pull a decoy PDF and a BAT downloader that ends in `pythonw.exe` registered under a false name in Task Scheduler.

The copy is also the mistake. A byte-identical duplicate of a known system binary sitting in `%TEMP%` is one hash comparison away from certain, and the PE version resource still says `curl.exe` no matter what the file is called.

## Why

- **The binary is byte-identical to a file you already know the hash of.** This is unusually rare in detection. Most "is this file bad" questions are probabilistic; this one is not. Compute the SHA256 of `System32\curl.exe` for each OS build in the estate — a one-off task — and any `.exe` created in `%TEMP%`, `%APPDATA%`, or `ProgramData` matching that hash is a copy of the in-box utility, full stop. Legitimate vendored curl builds are different binaries with different hashes. The check is exact, cheap, and fires before the download even happens.

- **`OriginalFileName` survives the rename, and renaming is the entire point of the technique.** MITRE describes this variant explicitly: move a legitimate utility elsewhere and rename it to defeat path-based detection. The PE version resource is not updated in the process, because doing so would require rebuilding the binary and would break its signature. SigmaHQ ships the one-condition rule for it. The only prerequisite is that your pipeline retains `OriginalFileName` — a field that is routinely dropped at ingest for volume and is the difference between this hunt working and not existing.

- **Scoping to the rename and the copy keeps the hunt usable, where scoping to "curl ran" does not.** Windows has shipped `curl.exe` since 1803 and administrators, scripts, and monitoring use it constantly. A hunt for curl execution returns the estate. A hunt for curl executing from outside System32, or under another name, returns a handful of hits — mostly developer tooling with its own hash — and that is a list a person can work through. The discipline of not widening this query is what makes it survivable.

- **Living off an in-box binary means there is no malware to find at this stage.** No dropped implant, no unsigned DLL, no injected process. The chain uses Microsoft's downloader to fetch Microsoft's script host to run a stage that loads entirely into memory — the source report notes that after the downloader, "everything is loaded into memory (no on-disk payload)." Once that happens, the on-disk evidence is a decoy document and a temp directory. The copy of `curl.exe` is one of the last durable artifacts in the chain, which makes it the right place to hunt rather than the least interesting.

- **The three-event sequence has essentially no benign population.** A System32-identical `.exe` appears in `%TEMP%`; it makes an outbound connection; an `.hta` or `.bat` carrying Mark-of-the-Web lands in the same directory and executes. Each event in isolation has legitimate analogues — build systems stage tooling, applications download things. The ordered sequence inside a few minutes, descended from `explorer.exe` opening a shortcut, does not. Writing this as one joined query rather than three separate rules is what converts a noisy signal into a precise one.

- **Custom user-agents and curl-specific arguments are a second, independent angle.** MITRE's own advice is to hunt distinctive arguments rather than filenames — `-o`, `-T`, `--data-binary`, `-k`, `-A`, `--proxy`. On an endpoint these are uncommon, and a custom `-A` string is uncommon enough to be interesting on its own. Notably the unrelated TerminalFix campaign from the same week also set a custom User-Agent on its initial download, which suggests the shape generalises well past this actor.

- **HEARTH had no T1036.003 coverage,** despite renamed system utilities being one of the cheapest and most widely used evasions available, and one that directly undermines path-based application-control policies that many organisations rely on as a preventive control.
