  WWAHost.exe is a legitimate inbox component and runs constantly on healthy machines to host built-in and Store web apps, so its mere execution is not a finding and any hunt keyed on the process name alone will drown. The discriminators are the package's provenance and the traffic's destination, not the binary. Expect genuine volume from three places. First, real developer machines: anyone building UWP, WinJS, PWA or MSIX-packaged applications will legitimately enable Developer Mode and call Add-AppxPackage -Register against a loose manifest in a project directory all day, so scope the hunt to non-developer populations or baseline your developer hosts explicitly rather than trying to write the exception into the rule. Second, sanctioned enterprise sideloading: LOB app distribution through Intune, Company Portal or a management agent also registers packages outside C:\Program Files\WindowsApps, so allowlist by publisher certificate and deploying agent. Third, vendor web apps hosted in AppX containers may legitimately reach their own cloud, which is why the proxy leg filters on Microsoft-owned destinations rather than on any external destination — a third-party AppX reaching its own vendor domain needs an allowlist entry, and building that allowlist is exactly what the paired baseline [[B054]] delivers. The strongest single signal with the fewest false positives is an AppxManifest.xml under a user-writable path that combines WindowsRuntimeAccess="all" with a ContentUriRule pointing at a host you do not own; that combination has essentially no benign enterprise use outside active development.

# H336

Huntress published this chain on 23 September 2026, and its significance is that every component is legitimate. WWAHost.exe is a signed Microsoft binary whose job is to render web content for packaged applications. Microsoft Office's client ID is a genuine first-party application identifier. The sign-in dialog is served by login.microsoftonline.com and rendered by that signed binary, so the user is looking at a real Microsoft prompt and completing real multi-factor authentication. The only attacker-supplied element is an AppX manifest that pairs `ContentUriRules` with `WindowsRuntimeAccess="all"`, which promotes remote JavaScript from sandboxed web content to holder of the full Windows Runtime API surface — including `WebAuthenticationBroker`, the system component that drives OAuth flows. The JavaScript asks the broker for tokens using Office's identity and the out-of-band redirect URI, and the authorization code comes back into attacker code. Because there is no fake domain, no harvested password and no unsigned executable, signature-based detection and identity-based detection both fail: the resulting Entra sign-in is a successful Office sign-in with no risk flags. The chain is still detectable, but only on the endpoint and at the proxy — package registration from a user-writable path, a manifest granting full runtime access to a foreign URL, and an AppX host talking to a host Microsoft does not own.

## Why

- Every conventional control on this path fails by design: the process is signed and inbox, the client ID is first-party, the login page is authentic, MFA is genuinely satisfied, and the Entra record shows success with no risk detection — so if this is happening, nothing in the identity stack will tell you, and only a hunt over endpoint and proxy telemetry will.
- The privilege bar is low enough to matter for the whole fleet rather than a few admins: registering a sideloaded package with `Add-AppxPackage -Register` needs no administrative rights once Developer Mode is enabled, and enabling Developer Mode is itself a user-writable registry flip, so the technique is available to any standard user session an adversary lands in.
- The tokens obtained are not session-scoped: the broker returns a refresh token alongside the access token with scopes including `Mail.ReadWrite`, `Mail.Send`, `Files.ReadWrite.All` and `Directory.Read.All`, which converts one user's click into durable mailbox and file access that survives password resets and outlives the endpoint foothold.
- The decisive artefacts are cheap to query and nearly unambiguous: an `AppxManifest.xml` in a user-writable path combining `WindowsRuntimeAccess="all"` with an external `ContentUriRule` has no benign enterprise use outside active development, and `MSAppHost/3.0` traffic to a non-Microsoft destination is a fingerprint that only appears when a sideloaded package is reaching infrastructure Microsoft does not own.
