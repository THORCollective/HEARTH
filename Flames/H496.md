false_positive_notes: |
  Legitimate Dropbear installations exist, particularly on embedded devices, network appliances and minimal container images, and they do answer with a Dropbear banner. They differ in that they run from a package-owned path, store host keys under `/etc/dropbear`, and are in the approved service register for that device class. A Dropbear-derived binary running out of `/tmp` with host keys beside it is not a deployment choice anyone makes.

  TCP 53 is legitimately a listening port on real name servers, which use it for zone transfers and for responses too large for UDP. The discriminator is the process - a name server daemon rather than an ELF in `/tmp` - and the protocol seen on the wire. Check the DNS infrastructure register before treating a TCP 53 listener as suspicious.

  High non-standard ports are also used legitimately by management agents, monitoring software and application servers. This is why the hunt pairs the port with the binary path and the banner rather than alerting on the port alone, and why the approved listening-port register is a listed prerequisite rather than a nicety.

  Real Pulse Secure and Ivanti appliances present their own SSH banners, and an estate may contain them. Mandiant's finding is that the string appeared on hosts that were compromised third-party firewalls and routers, so the test is whether the device presenting the banner is actually that product, not whether the banner exists anywhere. Reconcile every hit against the asset inventory.

  Mandiant reports the actor first attempted a listener on TCP 53 and later used TCP 33992, which implies the first attempt did not succeed, though Mandiant does not say why. Do not assume the specific ports generalise - treat them as this intrusion's values and hunt the shape, since the port is a command-line argument the operator chooses per host.

  Note also that BEARBONES logs plaintext credentials. If this backdoor is found, every credential used against that host during its lifetime must be treated as disclosed, including those of legitimate users and automation that connected to the appliance believing they were talking to the real service.
notes: |
  Listening-socket leg (scheduled socket inventory, EDR, `ss` or `netstat` collection) - Core filter: any listening TCP socket whose owning process path is under `/tmp/`, `/var/tmp/`, `/dev/shm/` or another world-writable directory, and separately any listening socket on a port not in the approved register for that host role. A per-host enumeration, output written for collection rather than read interactively:

      ss -ltnp > /var/log/listener-inventory-$(date +%F).txt

  Triage values are `local port`, `local address`, `process path`, `PID`, `effective UID`, `process start time`, `command line` and `hostname`. Strong red flags: the process path is a short name in `/tmp` such as a three-letter binary; the command line carries a port flag and an inetd-style flag, which is the invocation form Mandiant recorded for both executions; the binary is an ELF with no package ownership, which `rpm -qf` or `dpkg -S` will confirm in one command.

  Host-key leg (auditd watch rules, file inventory) - Core filter: creation or presence of a file named `rsa_host_key`, `ecdsa_host_key` or `dss_host_key` anywhere outside `/etc/dropbear` and `/etc/ssh`. Mandiant's published BEARBONES YARA rule keys on exactly those three paths under `/tmp` alongside the banner prefix, which is a direct statement that the backdoor relocates its host keys there. This is the single highest-ratio check in the hunt - a one-line filesystem sweep, essentially zero legitimate hits, and it survives the binary being renamed:

      find /tmp /var/tmp /dev/shm -xdev -maxdepth 3 -type f \( -name 'rsa_host_key' -o -name 'ecdsa_host_key' -o -name 'dss_host_key' \) -printf '%T+ %u %p\n' 2>/dev/null

  An auditd rule to catch the write prospectively rather than finding it later:

      auditctl -w /tmp -p wa -k tmp_write_watch

  Banner leg (internal and external SSH banner scan) - Core filter: any SSH service whose session identification string begins `SSH-2.0-pulsesecure_`, and in particular the full string `SSH-2.0-pulsesecure_23345` that Mandiant recorded, on any host that is not genuinely that appliance product. Mandiant's rule treats the prefix as the indicator rather than the full version, which is the right level - the trailing number is the backdoor's internal version string and will change. Scan all ports, not 22, because the whole point of the backdoor is that it is not on 22. A banner sweep across the internal estate, with the port list scoped to what the organisation can scan responsibly:

      nmap -sS -p 22,53,2222,8022,33992,30000-40000 --script ssh2-enum-algos,banner --open -oA ssh-banner-sweep 10.0.0.0/8

  Treat the address range and ports above as placeholders to be replaced with the organisation's own ranges and an agreed scan window. Triage values are `IP address`, `port`, `banner string`, `asset owner`, `asset class` and `expected product`. Strong red flags: the banner claims a VPN appliance product but the asset inventory says the host is a Linux server or a vCenter appliance; the same banner appears on third-party network devices at the edge, which is the obfuscation-network pattern Mandiant describes; the port is a high non-standard one.

  Authentication-bypass confirmation (host analysis, not a query) - If a candidate binary is recovered, two facts distinguish BEARBONES from a stock Dropbear build without full reversing. First, the password-authentication handler grants access on a hash comparison against a hardcoded SHA-256 value rather than validating against `/etc/shadow`, and the comparison covers only the first 14 bytes of the supplied password. Mandiant's YARA rule includes a byte pattern for the length constant used in that comparison, in which the immediate operand is 14 - consistent with the 14-byte figure stated in the report text. Second, plaintext credentials are written to the backdoor's log output. Preserve that log before containment; it records what the actor collected, and it is the fastest way to scope credential rotation.

  Correlation with the rest of the intrusion - Mandiant records that after BEARBONES opened its listener on the high port, the actor moved laterally to the vCenter appliance as Administrator, created a local administrator account there, and then enabled SSH through the VAMI API. Pull flow records for the appliance either side of the listener's start time rather than treating the backdoor as an isolated finding; the listener is an inbound channel, so the useful question is which external or internal addresses reached it. H495 covers the vCenter leg that follows, H493 the exploitation that precedes it.

  Scope note: HEARTH's existing SSH persistence hunts look at the stock daemon and at key material - H320 covers `ptrace` attaching to `sshd`, `sudo` and `su` for credential capture alongside a setuid-root backdoor binary, and several hunts cover `authorized_keys` additions. None of them cover a second, rogue SSH server running in parallel with its own host keys and a masquerading banner, which is a different artefact set entirely - a listening socket and three misplaced key files rather than a modification to the real service.

# H496

Mandiant and Google Threat Intelligence Group's November 19, 2026 report on ARMORY CASTLE describes five newly identified malware families deployed on internal Linux appliances the actor had chosen specifically because they lacked EDR tooling. BEARBONES is the one that provided durable interactive access: a C backdoor based on the open-source Dropbear SSH Server, staged as `/tmp/dbr` and executed twice — first attempting a listener on TCP 53, then on TCP 33992.

Three modifications to the upstream project make it a backdoor rather than a second SSH service. The password-authentication handler for the user-auth request packet was changed to bypass `/etc/shadow` validation entirely and grant access when the SHA-256 digest of the first 14 bytes of the client's password matches a hardcoded hash, logging the plaintext credential in the process. The server host keys are loaded or generated from `/tmp` instead of `/etc/dropbear`. And the internal version and session identification strings were rewritten to present as a VPN appliance product, `SSH-2.0-pulsesecure_23345`.

That last change turned out to be the most consequential for defenders. Mandiant pivoted on the banner and identified a suspected obfuscation network of compromised third-party firewalls and routers exposing the same string on non-standard high TCP ports — infrastructure that is detectable with nothing more than a banner scan.

## Why

- The host-key relocation is a free, near-zero-false-positive check. Nothing legitimate writes `rsa_host_key`, `ecdsa_host_key` or `dss_host_key` into `/tmp`, and Mandiant's own hunting rule treats those three paths as indicators. One `find` command covers an estate's appliances.
- The banner is both a detection and a map. Because the actor reused the same identification string across its obfuscation infrastructure, a single scan signature finds the backdoor on the appliance and the relay network in front of it. Mandiant's rule keys on the prefix rather than the version number, which is the level that survives the actor incrementing it.
- The credential consequences are broader than the host. The backdoor logs plaintext passwords supplied to it, so every account that authenticated to that appliance while it was running — including legitimate administrators and automation that could not tell which SSH service answered — must be treated as compromised. That changes the response from removing a file to rotating credentials.
- This is persistence that configuration review will not find. The real `sshd` configuration is untouched, no package is modified, and nothing is written to `/etc`. The evidence is a listening socket, three files in `/tmp` and a string on the wire, none of which appear in a hardening benchmark.
