false_positive_notes: >-
  The `IPC$` plus named-pipe filter is far quieter than it first appears, but it is not empty, and the
  benign population differs sharply by pipe. `lsarpc`, `samr` and `netlogon` are used by legitimate
  administrative tooling and by domain-joined machines during normal operation — expect hits from
  identity and directory management consoles, vulnerability scanners doing authenticated checks, backup
  agents, and anything running `Get-ADUser` style enumeration at scale. `srvsvc` is noisy enough that
  including it will hurt more than it helps in most estates. By contrast `efsrpc` has almost no
  legitimate use from a workstation to a domain controller: the Encrypting File System Remote Protocol
  exists for a narrow purpose that ordinary endpoints do not exercise against DCs, so scoping the hunt
  to `efsrpc` first and widening only if it comes back clean is the right order of work. `netdfs` is
  similar and should be treated the same way. The interpreter half has its own noise: developer
  workstations, data-science environments, vendor agents that bundle a private Python, and packaged
  applications that ship an embedded interpreter all place `python.exe` outside the standard paths, so
  enumerate those once by path and signing certificate rather than triaging them repeatedly. What none
  of them do is originate outbound TCP/445 to dozens of internal hosts — the combination of a
  non-standard interpreter and an SMB fan-out is where the false-positive rate collapses to near zero,
  and it is worth building the query as the conjunction rather than as two separate alerts.
  Two operational warnings. First, Event ID 5145 is genuinely high-volume once enabled on a busy file
  server, so enable it on domain controllers and Tier 0 systems first and size the collection before
  turning it on estate-wide. Second, do not treat a 4624 Type 3 NTLM machine-account logon as a finding
  on its own — legacy applications, appliances and non-Kerberos-capable services generate these
  constantly. It is corroboration for a coercion event, not a standalone signal.

# H293

The interesting part of Unit 42's Spring Ring reporting is how short the distance is between a Teams
message and domain-level escalation, and how little of that distance involves anything a credential
control would notice.

The entry is social. An external `.onmicrosoft.com` tenant, created by the operator, chats a target
employee using the Teams "chat with anyone" capability under a display name like "IT assistance" or
"help desk". The chat becomes an unsolicited voice call within minutes — Unit 42 recorded the operators
cycling through five or six identities in that window, and calls ranging from a few seconds to a full
quarter-hour. Over the call, the victim is guided to run something. In one campaign that is Quick Assist
or a third-party RMM tool. In the other it is a tailored executable fetched from an S3 URL constructed
from the target organization's name and the victim's own name.

What that payload then does is the part worth hunting, because it does not attempt to steal a password
at all.

It drops a Python interpreter at `C:\ProgramData\IntegrityData\python.exe` — not a script run by a
system interpreter, a private interpreter placed in a data directory — and uses it to sweep internal
servers on TCP/445. That sweep is target selection: it is looking for hosts that will accept a relayed
authentication, which in practice means hosts without SMB signing enforced. Then it runs PetitPotam
against the domain controller.

PetitPotam is worth stating precisely, because the detection depends on the mechanism. It makes an
`EfsRpcOpenFileRaw` call over the `\PIPE\lsarpc` named pipe on the DC's `IPC$` share, passing a UNC path
pointing at a machine the operator controls. The DC, doing what it was asked, connects out to that path
over SMB and authenticates with its own machine account. The operator never learns a password. They
receive an NTLM authentication from a domain controller and relay it onward — classically to Active
Directory Certificate Services — and that is domain escalation.

The reason this makes a good hunt rather than a good rule is the shape of the observable. There is no
malware signature, no credential-dumping API call, and no failed authentication anywhere in the chain.
Every individual step is a supported protocol operation performed successfully. But a domain controller
being asked by a user workstation to open a file over the Encrypting File System Remote Protocol is
semantically absurd. EFSRPC exists for a narrow purpose that ordinary endpoints simply do not exercise
against DCs. That semantic emptiness is what makes Event ID 5145 filtered to `IPC$` and `efsrpc` such a
quiet, high-value query — and it is off by default, which is why most estates cannot currently run it.

There is a practical ordering point here worth acting on. The named pipes usually listed together in
coercion detections are not equally valuable. `lsarpc`, `samr`, `netlogon` and especially `srvsvc` carry
real administrative traffic. `efsrpc` and `netdfs` carry almost none. Scoping to those two first gives a
result set small enough to read on the first day, and widening later is a choice rather than a
prerequisite.

The second half of the hunt is cheaper still and needs no audit policy change. A private Python
interpreter under `C:\ProgramData` is unusual. A process opening SMB connections to dozens of internal
hosts is unusual. A single process doing both is, in practice, the tool. Building that as a conjunction
rather than as two alerts is what keeps it usable on estates full of developer workstations.

Unit 42 note that both campaigns were blocked before completion, which is worth reading as a caution
rather than reassurance: the technique reached the coercion stage against a domain controller from a
starting point of one employee answering a chat request. [[M035]] covers the authentication-graph
analytic that surfaces the relayed movement itself, and is the natural companion when the coercion event
was not captured because auditing was off. [[H288]] covers the Teams and Graph collection surface from
the identity side of the same platform.

## Why

- **Nothing in the chain looks like credential theft, because no credential is stolen.** The operator
  never reads a hash, never touches LSASS, never triggers a failed logon. They ask a domain controller
  to authenticate, and it does, correctly. Every detection built around credential access or
  authentication failure is blind to this, which is why the coercion call itself has to be the
  detection point.
- **The coercion has no semantic justification, which is rare and worth exploiting.** Most Windows
  hunting fights protocols with large legitimate populations. A workstation invoking EFSRPC against a
  domain controller has essentially none — the protocol exists for a purpose that endpoints do not
  exercise against DCs. Filtering 5145 to `IPC$` and `efsrpc` produces a result set small enough to read
  by hand, which is an unusually good position to be in for a domain-escalation technique.
- **The audit policy this depends on is off by default, and that gap is the finding.** Event ID 5145
  requires Advanced Audit Policy `Audit Detailed File Share` to be enabled, and most estates have not
  enabled it. Running this hunt therefore either detects coercion or discovers that coercion would be
  undetectable — and the second outcome is the more common and more important one. Enabling it on
  domain controllers and Tier 0 first is a small, bounded change with a large payoff.
- **The interpreter-plus-SMB-fanout conjunction is a strong signal available to everyone right now.**
  It needs no audit policy change and no domain controller instrumentation. Developer machines have
  Python in odd places, and plenty of processes talk to a file server, but a private interpreter under
  `C:\ProgramData` opening SMB to dozens of internal hosts is the relay-target sweep and very little
  else. Expressing it as a conjunction rather than two alerts is what makes it deployable.
- **The relay target selection reveals a systemic weakness worth fixing while you are in there.** The
  sweep is looking for hosts that accept relayed authentication, which is to say hosts without SMB
  signing enforced. Running the same enumeration defensively — which of our servers would accept a relay
  — converts a detection exercise into a hardening backlog, and SMB signing enforcement plus Extended
  Protection for Authentication on ADCS removes the escalation path rather than merely observing it.
- **Initial access here bypasses email entirely, so the usual gate never sees it.** The lure arrives as
  a Teams chat from an external tenant and escalates to a voice call within minutes. No attachment, no
  link in mail, no secure email gateway involvement. Organizations that measure phishing exposure through
  mail flow have no visibility into this path at all, which makes the external-federation and
  external-chat telemetry a genuinely new surface to be watching rather than an incremental one.
