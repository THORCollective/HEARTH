title: "LiteLLM 1.107.0 startup-hook collector: a routine Python or pip process runs host discovery, encrypts a staged bundle with openssl, and POSTs it out"
hypothesis: >-
  An adversary who has poisoned a Python package with an interpreter startup hook (a single-line `.pth` import or a `sitecustomize.py` at the site-packages root) steals credentials the first time any Python or pip process starts in that environment. Nothing has to import the package. On the endpoint this shows up as one interpreter process, often started for unrelated work like `pip install`, `pytest`, or a notebook kernel. Within seconds of starting, that process runs host and network discovery binaries, reads credential material from several unrelated stores (cloud CLIs, SSH, browsers, package registries, Kubernetes, coding-assistant tools), and calls openssl twice from a short-lived hidden temp directory: once for AES-256-CBC packaging and once for RSA public-key wrapping. It then sends one HTTP POST of an octet-stream body to a lookalike domain on a harmless-sounding path. Afterwards, the exposed cloud keys appear in cloud audit logs doing identity checks, creating new keys, or invoking models from infrastructure that identity has never used.

false_positive_notes: |
  Python calling openssl: legitimate build, test, and provisioning scripts mostly run certificate subcommands (`req`, `x509`, `genrsa`, `rand`) rather than `enc -aes-256-cbc` and `pkeyutl -encrypt -pubin` back to back. Most Python crypto goes through the `cryptography` library without spawning a child process. Teams that do seal secrets to a public key from Python (backup or secret-escrow scripts) should be baselined by parent script path and repository, not by allowlisting the openssl binary. Discovery fan-out: Python inventory and config-management agents (Ansible fact gathering, Salt minions, psutil-based monitoring wrappers) can run `ipconfig`/`netstat`-style commands. They do it on a schedule under a known service account and rarely pair it with openssl encryption and a one-off POST, so require at least two of the three runtime stages (discovery burst, paired `enc`/`pkeyutl`, octet-stream POST to a newly seen domain) under one parent before escalating. Credential file reads: the AWS CLI v1, gcloud SDK, Azure CLI, and kubectl wrappers are Python or call Python, and they read their own stores all the time. A single-store read by the matching tool is expected. Escalate only when one interpreter touches three or more unrelated stores (for example cloud plus browser plus SSH plus coding-assistant files). Startup-hook files: many legitimate `.pth` files exist (`distutils-precedence.pth`, `_virtualenv.pth`, `__editable__.*.pth`, `easy-install.pth`, coverage hooks), and some distributions and conda/pyenv builds ship a `sitecustomize.py`. Baseline by owning package and `RECORD` entry, and focus on hooks whose owning package name does not match the module they import, or that arrived in a version bump with no matching source-repository change. Network: `/healthcheck` endpoints are everywhere. The discriminator is a POST with a binary body from an interpreter to a domain first seen recently, not the path name. Cloud: `sts:GetCallerIdentity` is called constantly by SDKs, Terraform, and CI. The signal is a known key appearing from a new source IP or region after the exposure window, not the call itself.
notes: |
  EDR process creation (Windows, macOS, Linux) - Core filter: child image `openssl` or `openssl.exe` with a parent image of `python`, `python3`, `python.exe`, `pythonw.exe`, or `pip`, where the command line contains either `enc` with `-aes-256-cbc`, or `pkeyutl` (or `rsautl`) with `-encrypt` and `-pubin`. Triage values: `process command line`, `parent process command line`, `parent process start time`, `process current directory`, `file path` of the `-in`/`-out` arguments, `user`. Correlation: group by host, parent process ID, and parent start time. The strongest form is one parent producing an `enc` child and a `pkeyutl` child within 60 seconds, with both input and output files in a hidden, short-lived temp directory that the same parent created. The 1.107.0 collector used a `.pc_e_` prefix; expect the prefix to change. Strong red flags: the parent command line is routine work such as `pip install` of an unrelated package, `pytest`, or a notebook kernel launch, or the parent python has working directory `/` or has been re-parented to PID 1 / launchd.
  
  EDR process creation, discovery fan-out - Core filter: one python or pip process launching three or more of `systeminfo`, `ipconfig`, `route`, `arp`, `netstat` within 120 seconds of its own start. Microsoft observed this sequence on Windows from a single Python process. On macOS and Linux, baseline the equivalents (`uname`, `ifconfig`, `ip`, `netstat`, `arp`) from the same kind of parent. Triage values: `process command line`, `parent process command line`, `parent process start time`, `child process count`. Pivot: take the same host and parent process ID into the openssl filter above and into that parent's outbound connections. Strong red flags: discovery children under an interpreter whose own command line has nothing to do with inventory, and a burst that happens once per host instead of on a schedule.
  
  EDR file telemetry - Core filter: file creation at the root of a `site-packages` or `dist-packages` directory of a `.pth` whose body is a single `import <module>` line, or of `sitecustomize.py` / `usercustomize.py`, written by `pip`, `uv`, `poetry`, or a container image layer. Use this to scope which environments to examine for the runtime chain; it is not the alert. Triage values: `file path`, `file size`, `initiating process command line`, and the owning package's `RECORD` entry under `*.dist-info`. For the 1.107.0 wave, look for `cook.pth`, `cook.py`, and `sitecustomize.py` together, plus the marker `/tmp/.pc_once_*`. The marker is written only after a successful upload, so its absence does not prove a host is clean. Where file-open telemetry exists, flag one python process opening three or more unrelated stores: `~/.aws/credentials`, `~/.azure/`, `~/.config/gcloud/`, `~/.kube/config`, `~/.docker/config.json`, `~/.ssh/`, `~/.git-credentials`, `~/.npmrc`, `~/.pypirc`, Chromium `Login Data` / `Cookies`, Firefox `logins.json`, `/var/run/secrets/kubernetes.io/serviceaccount/token`, and coding-assistant credential files under the home directory. Do not start Python or pip inside a suspect environment to check it; inventory the files from disk or from the image layer.
  
  Proxy, DNS, and EDR network telemetry - Core filter: an HTTP `POST` with `Content-Type: application/octet-stream` from a python process, or from the same host within 60 seconds of the openssl children exiting, to a domain first seen in your environment in the last 30 days, especially a lookalike of the package's real project domain. For the 1.107.0 wave, sweep history for `www.litellm[.]dev`, path `/healthcheck`, request header `X-Token` plus a second custom `X-` request header named after the SHA-256 hash algorithm, and an outdated `MSIE 7.0` user agent. Also flag python requests to `169.254.169.254` from hosts or pods where Python does not normally use the instance role. Triage values: `destination domain`, `domain first-seen date`, `URL path`, `user agent`, `bytes sent`, `response code`, `initiating process ID`. Correlation: join on host, initiating process ID, and time window back to the openssl and discovery hits. Strong red flags: POST retries that stop after the first HTTP `200`, and an upload size that looks like a compressed archive rather than a health probe.
  
  AWS CloudTrail and cloud audit - Core filter: for every access key ID and role session an affected host could reach (credential files, instance or task role, provider keys stored in the gateway's proxy database), find `sts:GetCallerIdentity` from a `source IP address` outside known egress ranges, followed by `bedrock:ListFoundationModels`, `bedrock:InvokeModel`, `bedrock:InvokeModelWithResponseStream`, `iam:CreateAccessKey`, `iam:CreateUser`, or `iam:CreateLoginProfile`. Triage values: `access key ID`, `user identity ARN`, `source IP address`, `user agent`, `event name`, `error code`, `AWS region`. Pivot: compare each key's source IPs and regions before and after the host's exposure window. Repeat for Azure activity logs, GCP audit logs, Kubernetes audit (service account token used from a new IP), and model-provider usage dashboards for keys the gateway held. Strong red flags: instance-role session credentials used from outside the account's NAT addresses, model invocation in regions the account never uses, and a new access key created for an existing user within hours of exposure.

# H427

On October 21, 2026, a compromised LiteLLM 1.107.0 release was published to PyPI and to the project's official container image tags. The wheels put three files at the site-packages root: `cook.pth` (12 bytes, just an import line), `cook.py` (a collector that reports call `privcollect`), and `sitecustomize.py` (a Unix-oriented loader). Python's site module runs `.pth` import lines and `sitecustomize` every time the interpreter starts. That means pip, pytest, a Jupyter kernel, or an unrelated script in the same environment all run the payload, and the application never has to import LiteLLM. Microsoft Security Research analyzed the wheels and correlated them with endpoint observations on Windows and macOS. In one Windows case, a routine Python call to install an unrelated dependency set off the collector. In an observed Windows sequence, Python launched `systeminfo`, then `ipconfig`, `route`, `arp`, and `netstat` from the same process. Each run creates a 32-byte AES key and a 16-byte IV, encrypts the collection with AES-256-CBC, and wraps the key with an embedded 4,096-bit RSA public key using OAEP. When it uses the OpenSSL backend, it stages input and output files in temp directories that start with `.pc_e_` and deletes them after use. Before starting, the collector checks an inherited `PRIVCOLLECT_ACTIVE` environment variable, which prevents repeat runs in child processes. The upload retries until it gets HTTP 200, and only then writes a run-once marker under `/tmp/.pc_once_`. Public analyses list about sixteen collection modules: browser passwords and cookies, SSH/GPG/TLS keys, shell history, AWS/Azure/gcloud/Kubernetes/Docker credentials, package-registry and CI secrets, coding-assistant credential files, environment variables of running processes, cloud instance metadata, and the LiteLLM proxy database (provider keys and model configuration). The bundle went by POST to `www.litellm[.]dev/healthcheck`, a lookalike of the project's real domain. The `sitecustomize.py` loader polls a GitHub-hosted file every hour for a domain and runs Python fetched from it; reports say it fails on Windows while the collector still works. This is the second LiteLLM startup-hook compromise of 2026. The March 1.82.8 release used `litellm_init.pth`, and that release and other PyPI compromises showed the same Python-to-openssl `enc` plus `pkeyutl` lineage. Microsoft and the LiteLLM maintainers both stress two things. Removing the package or tag is not enough to recover: affected environments, surviving processes, and every credential the identity could reach all have to be dealt with. And responders should not start Python or pip inside a suspect environment to check whether it is affected, because that runs the hook again.

## Why

- It matters now: Microsoft saw this collector run on Windows and macOS within two days of the October 21 release, once from a pip install of an unrelated dependency. Hunts that rely on package inventory or on LiteLLM being imported miss hosts that never used the gateway, and this is the second startup-hook compromise of the same project in 2026.
- It survives IOC rotation: between the March and October waves the domain, upload token, hook filename (`litellm_init.pth` versus `cook.pth`), and marker hash all changed. A startup hook still has to run inside whatever interpreter starts, so it inherits a pip, pytest, or kernel parent, and hybrid encryption through system openssl forces a paired `enc` and `pkeyutl` child from that parent before anything leaves the host.
- The telemetry is observable: parent/child process lineage with command lines is standard EDR data on all three operating systems and is where Microsoft's observations came from. CloudTrail and other cloud audit logs record the follow-on key use even for containers and CI runners where endpoint coverage is thin.
- False positives are controllable: legitimate Python-to-openssl use is mostly certificate subcommands, and legitimate credential reads come from the matching CLI touching only its own store. Requiring two of the three runtime stages under one parent process, plus a key appearing from a new IP in the cloud, cuts the noise to a reviewable set.
