  A purchase-order lure arrives as a DOCX rather than an RTF, because the DOCX is only a wrapper: Word's

false_positive_notes: |
  The individual registry locations are legitimately used, so the discriminators are the writer and the shape of the Run command rather than the paths themselves.
  - HKCU\Environment is a normal place to set user environment variables, and software and login scripts write there. The anomaly is a value there holding an interpreter path, written by a script host, and then referenced from a Run entry.
  - HKCU\SOFTWARE\AppDataLow is a real location used by Internet Explorer-era low-integrity components and by some installers, so it is not empty on every host. A value there containing a large block of script text is the finding; baseline the value names and sizes present in the estate before hunting, because the size distribution is what separates a setting from a stored script.
  - Run keys are the busiest autorun location on Windows and most entries are legitimate. The specific shape to hunt is a Run command line that contains no file path at all - only an environment variable expansion plus a Get-ItemProperty read - which is a pattern almost no legitimate software produces.
  - cscript and wscript run legitimately from logon scripts, management tooling and some line-of-business applications. The parent is what matters: a script host whose parent is winword.exe, excel.exe or the Equation Editor is the condition, not script hosts generally.
  - Files with unexpected extensions in the temporary directory are common; installers and updaters produce them constantly. Treat a non-script extension holding base64 as corroboration once a script host wrote it, not as a standalone lead.
  - Script block logging is frequently not enabled, and without it the content of the registry-resident script is invisible at runtime. If 4104 is unavailable, the registry-write filter still works and should be relied on; establishing that the logging gap exists is part of the result.
notes: |
  Source reporting is AhnLab ASEC's November 12, 2026 write-up of phishing emails disguised as purchase order confirmation requests, which deliver XLoader - version 8.9 per the report, a family ASEC also tags as Formbook. The chain is unusually well documented at the registry level, and that is the part this hunt is built on.
  The delivery, as ASEC describes it - The attachment is a DOCX. ASEC reports that when the user opens it, "a malicious RTF document embedded within the Word file is executed by exploiting" the Word feature for importing content from another document, which the report names as altChunk. While Word processes that RTF, ASEC reports that "a malicious VBS file contained within an OLE object inside the document is created at the path" `%TMP%\724812.vbs`, and that a second OLE object exploiting CVE-2017-11882, the Equation Editor vulnerability, then "performs command execution on the VBS file." The recorded execution command is `CmD.exe/Ccscript %tmp%\724812.vbs`, with its mixed case and absent space preserved as the report presents it.
  The staging - ASEC reports the VBS "contains Base64-encoded data, which it saves as a file at the path %TMP%\Quisque.Dal", and publishes the decoded layout of that file: a loader at offset 0x0 for 0x285 bytes, the payload at 0x285 for 0x577F8 bytes, and a secondary PowerShell script at 0x57A7D for 0x4F1B bytes. The loader decrypts the payload with XOR key 0X6B506102 and runs it in memory. Note that the file carries a `.Dal` extension, which is not a script or executable extension and will not be caught by a hunt keyed on extensions.
  The persistence, which is the durable part - ASEC reports that the primary PowerShell script "stores the PowerShell execution path and the script itself in the TORO and Laboris registry values", and "then ensures persistence by registering the Cupidatat value under the Run key, causing the stored PowerShell script to execute automatically when the user logs in." Its table gives three entries: `HKCU\Environment` value `TORO` holding the PowerShell.exe path; `HKCU\SOFTWARE\AppDataLow` value `Laboris` holding the primary PowerShell script; and `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run` value `Cupidatat` holding a command that expands `%TORO%` with `-w 1`, reads the `Laboris` property from the AppDataLow key into a variable, and expands `%TORO%` again to run it. The report renders the quotation marks around the registry path as typographic characters, so the command is reproduced here in a normalised form rather than quoted verbatim.
  No existing HEARTH coverage for either half - Grepped the corpus for altChunk, Equation Editor and CVE-2017-11882 and found nothing, and the same for AppDataLow. The closest neighbour on the staging side is [[H451]], which covers a SQL Server process writing a payload one base64 fragment at a time and certutil reassembling it; that is a server-side staging pattern with a different parent and a different persistence outcome. Nothing in the corpus covers a Run entry whose command line resolves its interpreter through an environment variable stored in another registry value.
  Core filter 1, the Run entry with no path in it - The highest-value check, and the one that finds this host after every file in the chain has been deleted. Enumerate `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run` across the estate and select values whose data contains an environment-variable expansion and a `Get-ItemProperty` call and no filesystem path. Triage values are the value name, the full data, the registry key it reads from, and the creation time of the referenced value. The indirection is the signal: legitimate autorun entries name a binary.
  Core filter 2, the stored script - Enumerate values under `HKCU\SOFTWARE\AppDataLow` and `HKCU\Environment` and rank by data length. A value of several kilobytes under either key is not a configuration setting. Where the sensor captures registry write data, Sysmon Event ID 13 on those paths is the live version of the same check; where it does not, a periodic inventory of value names and sizes is sufficient and cheap.
  Core filter 3, the Office lineage - Hunt for `cscript.exe` or `wscript.exe` whose parent is an Office application or the Equation Editor, with a command line naming a file in the user temporary directory. The reported command line is `CmD.exe/Ccscript %tmp%\724812.vbs`, so match on the script host and the temporary path rather than on the specific numeric file name, which is a per-campaign value. Separately, hunt for the Equation Editor binary executing at all: on a patched estate it should not run, so any execution is worth a look regardless of what followed it.
  Sample Defender XDR query for the autorun indirection, within the 30-day advanced hunting window:
  ```kusto
  DeviceRegistryEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("RegistryValueSet", "RegistryKeyCreated")
  | where RegistryKey has @"CurrentVersion\Run"
        or RegistryKey has @"SOFTWARE\AppDataLow"
        or RegistryKey endswith @"\Environment"
  | extend data_length = strlen(tostring(RegistryValueData))
  | where (RegistryKey has @"CurrentVersion\Run"
              and RegistryValueData has "Get-ItemProperty"
              and RegistryValueData has "%")
        or (RegistryKey has @"SOFTWARE\AppDataLow" and data_length > 2000)
        or (RegistryKey endswith @"\Environment"
              and RegistryValueData has_any ("powershell.exe", "pwsh.exe"))
  | project Timestamp, DeviceName, RegistryKey, RegistryValueName, data_length,
            InitiatingProcessFileName, InitiatingProcessParentFileName,
            InitiatingProcessCommandLine
  | sort by Timestamp desc
  ```
  The length test on the AppDataLow branch is the part to tune per environment: 2000 characters is well above any setting and well below the script ASEC reports, which decodes to roughly twenty kilobytes, so it should be adjusted once the local size distribution is known rather than adopted as published.
  Script content at execution, where logging allows - Because the Run command carries only a variable and a registry read, the only runtime view of what executes is PowerShell Event ID 4104. Hunt 4104 for script blocks containing a `Get-ItemProperty` read of an `AppDataLow` path, which catches the execution even on a host where the registry writes predate the lookback.
  Indicators from the report, for retrospective scoping only - The C2 is reported as the defanged `http[:]//www[.]dumbsplash[.]com/ilto/`, and ASEC lists MD5 hashes 5bd3c5f273ba5ae4c4ae745c6943a4f7, 8b3542531d98a47524c0f468d0158996 and e0d7a34bc9f4590bc073d08b50c854d1. XLoader is a commodity family sold to many operators, so these rotate quickly; the registry structure is the part worth building a detection on.
  Expected, not observed by AhnLab - Whether the altChunk route meaningfully changes gateway detection outcomes in practice. ASEC documents that the RTF is embedded in the DOCX and loaded through that feature, but does not report testing it against mail filtering, so the inference that the wrapper exists to keep the RTF out of the attachment extension and leading bytes is a reading of the design, not something the report states.
  Scope - Windows endpoints with Office installed, and in particular any estate where the Equation Editor component has not been removed or the relevant update not applied. The persistence half of this hunt is worth running regardless of patch level, because the registry-resident Run pattern is reusable by any loader and is not specific to this delivery chain.

# H481

The autorun entry contains no program name.

Not an obfuscated path, not a renamed binary — nothing. Just an environment variable, a registry read, and the same environment variable again. Something like: expand `%TORO%`, pull the `Laboris` property out of a key under `AppDataLow`, feed it to `%TORO%`.

`%TORO%` is a user environment variable that the malware set, and it holds the path to `powershell.exe`. `Laboris` is a registry value that holds about twenty kilobytes of PowerShell script. Neither name means anything; they look like they came out of a lorem ipsum generator, which is probably where they came from.

So you can delete every file this campaign dropped and the persistence still works. There is no file. There are three registry values, two of which are in places nobody enumerates.

AhnLab traced the whole chain from a purchase-order phish. The attachment is a DOCX, which is itself a bit of a trick: the DOCX is a wrapper, and Word's import-content-from-another-document feature pulls a malicious RTF out of it. Keeping the RTF inside means the attachment's extension and leading bytes are an ordinary Word document. While Word processes the embedded RTF, one OLE object drops a VBS into `%TMP%` with a numeric name, and a second OLE object exploits the 2017 Equation Editor flaw to run it via `cscript`. The VBS writes a base64 blob to a file called `Quisque.Dal` — note the extension, which no extension-based hunt will look twice at — and from there the loader, an XOR key, and the payload all live in memory.

XLoader at the end of it. Commodity infostealer, version 8.9, and the C2 will be dead by the time you read this.

The registry triple will not be.

## Why

- **The persistence has no file to find and no path to block.** Application allowlisting sees `powershell.exe`, which is allowed. A command-line hunt sees a variable and a registry read, with no script text and no path. Only an enumeration of the Run key's actual data, or script block logging, shows what is happening — which makes this a hunt rather than something a rule catches on its own.
- **A Run entry that names no program is a near-unique shape.** Legitimate autorun entries point at a binary. An entry whose data is entirely indirection — variable expansion plus a registry property read — is something almost no vendor ships, so the false-positive population is small enough to work through by hand.
- **The storage locations are chosen for being unenumerated, not for being hidden.** `HKCU\Environment` and `HKCU\SOFTWARE\AppDataLow` are both real, both documented, and both absent from almost every autorun inventory and forensic triage checklist. A size check over their values is a one-time piece of work that pays off against any loader using this idiom, not just this one.
- **The DOCX wrapper moves the dangerous format behind the extension.** The thing that triggers the vulnerability is RTF, and RTF attachments attract attention. Delivering the RTF inside a DOCX through a legitimate import feature means the file that arrives, and the bytes a gateway reads first, are an ordinary Word document.
- **The Equation Editor still running is a finding all by itself.** The vulnerability is from 2017 and the component was removed from supported Office years ago. On a correctly patched estate it should never execute, which makes "did this binary run anywhere this month" one of the cheapest and most decisive estate-wide questions in this hunt.
