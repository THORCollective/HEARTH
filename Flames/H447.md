false_positive_notes: |
  Single-token requests are not inherently malicious, and several legitimate patterns produce them. Each is separable:
  - Health checks and readiness probes. Platform teams routinely ping an inference endpoint with a one-token request on a timer. These are perfectly periodic, use one key, come from a fixed internal source, and never produce authentication failures. Allowlist by key plus source plus the period; a probe whose interval suddenly becomes irregular is worth a look.
  - Token-counting and cost-estimation tooling. Some libraries issue a minimal request to resolve a model's tokeniser or confirm a model name. These are low-count, tied to a deploy or a notebook session, and use a key that has other, larger traffic.
  - Classification and scoring workloads that genuinely want one token. A yes/no classifier or a logit-based scorer legitimately sets a one-token cap at high volume. This is the hardest benign case and the reason this hunt requires *credential breadth* rather than request shape alone - a classifier uses one key or a small fixed set, while validation sweeps across many unrelated keys. Record which keys run one-token workloads so the exception is explicit.
  - Provider-side or SDK retries after a timeout can duplicate a minimal request. These share a request ID or trace ID with the original.
  Where payload logging is disabled - the common case, since it carries its own cost and data-handling burden - the `max_tokens` value is not visible. Fall back to the derived form: output tokens equal to 1 (or response size at the floor) across a high request count, which is available from usage metering without logging prompts.
notes: |
  The request-shape filter - Core filter: inference invocations where the output cap is one token. Field names differ by provider: `max_tokens` (Anthropic Messages API, OpenAI-compatible endpoints, LiteLLM), `maxOutputTokens` (Vertex AI `generateContent`), `max_tokens_to_sample` (legacy Anthropic completions), `maxTokenCount` (Amazon Titan `textGenerationConfig`). In a Bedrock model invocation log, the value sits inside `input.inputBodyJson` for the model's own schema, so the extraction is model-specific - parse per `modelId` rather than with one path. Triage values: `identity.arn` or `principalEmail` or virtual-key ID, `sourceIPAddress`, `userAgent`, `modelId`, `awsRegion`/location, input token count, output token count, response status.
  The credential-breadth filter, which is what makes this a finding - Core filter: group one-token invocations by source address (and by user agent, which validation tooling usually leaves at a default) over a 1-hour window, and keep groups spanning 3 or more distinct keys, access key IDs, service accounts or virtual keys. Then require a mix of outcomes in the group: at least one success and at least one authentication or authorisation failure. A sweep over harvested keys of unknown quality cannot avoid the failures, in the same way a password spray cannot. Strong red flags: keys belonging to different projects or even different organisations appearing behind one address; a key's first-ever invocation being a one-token request; the same tiny prompt string repeated verbatim across keys.
  Sample AWS Athena / CloudTrail Lake query over Bedrock invocation logs staged in S3 (adjust the JSON path per `modelId`):
  ```sql
  SELECT   identity_arn,
           source_ip,
           user_agent,
           COUNT(*)                                   AS calls,
           COUNT(DISTINCT access_key_id)              AS distinct_keys,
           SUM(CASE WHEN error_code IS NOT NULL THEN 1 ELSE 0 END) AS failures,
           SUM(output_tokens)                         AS total_output_tokens
  FROM     bedrock_invocation_logs
  WHERE    event_time >= current_timestamp - INTERVAL '30' DAY
    AND    output_tokens <= 1
  GROUP BY identity_arn, source_ip, user_agent
  HAVING   COUNT(*) >= 20
    AND    COUNT(DISTINCT access_key_id) >= 3
    AND    SUM(CASE WHEN error_code IS NOT NULL THEN 1 ELSE 0 END) > 0
  ORDER BY calls DESC
  ```
  Why cost monitoring cannot find this - a validation sweep is engineered to be cheap. A thousand one-token completions against a premium model bill a fraction of a cent in output and a trivial amount in input, which is why GTIG describes the technique as letting the actor "stealthily confirm the viability of the stolen keys while remaining undetected by the victim’s endpoint detection and response (EDR) and SIEM volume anomaly alerts." Any detection keyed on spend, token volume or request-rate anomaly is being actively evaded here. The usable signal is the *ratio*: request count high, output tokens at the floor, and credential count high.
  Self-hosted gateways - Core filter: where inference is fronted by LiteLLM or an OpenAI-compatible proxy, the gateway access log holds both the virtual-key identifier and the request body size, which makes the one-token filter and the key-breadth filter available in one place. Look for a run of sub-200-byte POSTs to `/v1/chat/completions` or `/v1/messages` cycling through virtual keys, with HTTP 401 and 200 interleaved. GTIG reports actors acquiring "pre-validated Virtual Keys" from an access broker, which means a validation sweep against a victim's own gateway is a precursor to resale as well as to use.
  What to do once confirmed - Core filter: every key that returned a success in the sweep is compromised and in the hands of an operator or already sold on. Pivot each one into its own subsequent invocation history and into GTIG's downstream monetisation shapes: new API keys minted from the validated key, premium model selection, and sustained high-volume streams. HEARTH's H446 covers the service-enablement and key-minting step that often follows, and M040 scores the sustained invocation.
  Expected, not observed by GTIG: the same minimal-request validation shape should appear against embedding and image endpoints, where the analogous floor is a single-token input or a minimum-dimension request, and against self-hosted `/v1/models` listings used as a cheaper liveness check. GTIG describes the technique specifically as "automated credential validation sweeps using minimal single-token requests" against LLM APIs, capped with `max_tokens=1`.

# H447

Google Threat Intelligence Group's LLMJacking reporting contains one detail that reads as a direct instruction to defenders about where their monitoring fails. Describing an actor that "opportunistically harvested exposed corporate LLM API keys from public GitHub repositories", GTIG writes: "Demonstrating advanced evasion tradecraft, the group conducted automated credential validation sweeps using minimal single-token requests" with the output capped at one token (`max_tokens=1`). GTIG continues: "This allowed the threat actor to stealthily confirm the viability of the stolen keys while remaining undetected by the victim’s endpoint detection and response (EDR) and SIEM volume anomaly alerts."

The economics explain the tradecraft. An operator who scrapes a thousand API keys needs to know which ones are live before investing in infrastructure or offering them for resale, and the cheapest live-or-dead test is a real inference call with the output capped at one token. The call is well-formed, authorised, indistinguishable in structure from legitimate traffic, and costs essentially nothing - so every control an organisation is likely to have deployed around AI spend, token volume and request rate is specifically and deliberately beneath the threshold.

What the technique cannot hide is its purpose. Validating a bag of harvested keys means attempting keys that have been rotated, keys that were never valid, and keys from projects that no longer exist, so the run produces authentication failures mixed with successes. It also means touching many distinct credentials from one place, which no single legitimate one-token workload does - a health probe uses its own key, a classifier uses the key of the application it serves. The combination of request shape (output at the floor), credential breadth (many keys from one source), and mixed outcomes is narrow enough to hunt directly.

This sits deliberately before the monetisation stage. HEARTH's M040 scores sustained inference abuse per principal on burst shape and region novelty, and H446 fires on the service enablement and key minting that follow a successful compromise. Both begin after the operator knows which keys work. This hunt is the step where they find out - and it is the last point at which a key can be rotated before it is used or sold.

## Why

- The evasion is stated by the reporting vendor, not inferred. GTIG says the sweep stayed "undetected by the victim’s endpoint detection and response (EDR) and SIEM volume anomaly alerts". Any organisation whose AI monitoring is a spend or volume threshold has a documented blind spot here, and closing it needs a different feature, not a lower threshold.
- A validated key is a tradeable good. GTIG describes a division of labour in which one cluster establishes access and another monetises it, and documents a follow-on cluster that acquired "pre-validated Virtual Keys" from the actor that established initial access. The validation step is where a leaked key becomes inventory, so it is the highest-leverage moment to rotate.
- The failure responses are free intelligence. Exactly as with a password spray, the keys that fail tell an organisation which of its credentials have leaked even when none of the attempts succeed. A tenant that only reviews successful inference calls throws that away.
- The signal is a ratio, not a count, so it survives the operator slowing down. Spreading the sweep over days reduces rate but does not change the fact that output tokens sit at the floor across many distinct credentials from one source.
