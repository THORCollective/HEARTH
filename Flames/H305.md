  An attacker installing a malicious Chrome extension without the Web Store cannot simply drop files on
  disk, because Chrome validates its own preferences with a keyed MAC and disables anything it did not

false_positive_notes: |
  Chrome writes `Secure Preferences` constantly during normal operation, so the raw file-modification event is pure noise and must never be the detection on its own — the entire signal is carried by the initiating process. Legitimate non-browser writers do exist and should be enumerated once: enterprise browser management and configuration tooling; profile migration, roaming-profile and user-state migration utilities; some backup, imaging and VDI profile products; browser cleanup and privacy utilities that users install themselves; and developer tooling such as Puppeteer, Selenium and Playwright, which legitimately create profiles and load unpacked extensions and are best excluded by host role rather than by process name. Developer workstations are the dominant false-positive population for the `developer_mode` and `--load-extension` conditions specifically, and the correct handling is to scope the hunt to non-developer estate first, then profile the developer hosts separately rather than suppressing globally. Note that `extensions.ui.developer_mode` being enabled is also a legitimate user action — a curious user can toggle it in the UI — so it is corroborating evidence rather than a finding, and the version written BY ANOTHER PROCESS while Chrome is closed is the anomalous one. Finally, some endpoint security and DLP products deliberately inject or force-install their own extensions and will trip parts of this hunt; identify them early, because they are also the products most likely to be impersonated.
notes: |
  The core detection, who wrote the file - Core filter: a write to `Secure Preferences`, `Preferences` or `Local State` under the browser user-data directory where the initiating process is not the browser itself or its updater. Paths - `%LOCALAPPDATA%\Google\Chrome\User Data\<Profile>\Secure Preferences`, `%LOCALAPPDATA%\Google\Chrome\User Data\Local State`, and the Edge equivalents under `%LOCALAPPDATA%\Microsoft\Edge\User Data\`. Defender XDR KQL - `DeviceFileEvents | where FolderPath has_any (@"\Google\Chrome\User Data", @"\Microsoft\Edge\User Data") | where FileName in~ ("Secure Preferences","Preferences","Local State") | where ActionType in ("FileModified","FileCreated") | where InitiatingProcessFileName !in~ ("chrome.exe","msedge.exe","setup.exe","MicrosoftEdgeUpdate.exe","GoogleUpdate.exe","elevation_service.exe") | project Timestamp, DeviceName, FileName, FolderPath, InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessCommandLine, InitiatingProcessAccountName`. Triage values - `InitiatingProcessFolderPath` (a writer running from `%TEMP%`, `%APPDATA%` or a user download path is a strong finding), signer status of the initiating process, and whether `chrome.exe` was running at the time. Strong red flag - the rewrite happens while the browser is CLOSED, which is required for the forgery to survive since Chrome rewrites the MACs from memory on exit.
  What changed inside the file - Core filter: after any hit above, diff the JSON. The fields that matter are `protection.macs.extensions.settings.<extension-id>` (the per-extension keyed MAC), `protection.super_mac` (the MAC over the MAC set), `extensions.settings.<extension-id>` (the extension entry itself), and `extensions.ui.developer_mode`. The Volexity-documented LONGTALE loader removed `_encrypted_hash` and `super_encrypted_hash` values and wrote forged legacy HMACs in their place — so the ABSENCE of the newer encrypted-hash fields on a profile that should have them is itself an artefact worth querying across the estate. Collect `Secure Preferences` centrally and alert on profiles whose protection structure differs from the fleet norm.
  The new extension itself - Core filter: an extension ID appearing under `%LOCALAPPDATA%\Google\Chrome\User Data\<Profile>\Extensions\<extension-id>\` with no corresponding Web Store installation. Triage - read the extension `manifest.json` and score on permissions: the observed families requested `tabs`, `cookies`, `storage` and `webRequest`, which together are sufficient to read every page, steal every cookie and rewrite every request. Strong red flags - a display name impersonating a security or system product (KREMLIN used `AVSync System Inc` and `FrameSync Driver System V16.9.7`; LONGTALE masqueraded as a Google Gemini extension), and an ID absent from the enterprise allowlist. Observed IDs, useful as retro-hunt seeds but NOT as the detection - `ndpbidppejfanjbhfgjlohfanbfbklff`, `cdgcjghdeinagopbaobhmaefigoafaaa`, `djodclnjknbpambeaaapadmdfhmbpeog`, `ckiknalbeplpcpofpnabcnhjcegckfei`.
  Encryption-key theft, the enabling step - Core filter: reads of `Local State` (which holds the OSCrypt key, DPAPI-protected) by a non-browser process, and Sysmon event 10 `ProcessAccess` against `chrome.exe` with debug or memory-read access rights. KREMLIN recovered the App-Bound Encryption key by launching Chrome under a debugger and scanning the `.rdata` section for the string `OSCrypt.AppBoundProvider.Decrypt.ResultCode`, then following a RIP-relative LEA to the key buffer. Practical detection - any process opening `chrome.exe` with `PROCESS_VM_READ` that is not a known EDR or crash-reporting component, and any launch of Chrome with `--remote-debugging-port`, `--load-extension`, `--disable-extensions-file-access-check` or `--user-data-dir` pointing outside the normal profile location. Those command-line flags are a cheap, high-value standalone query. Because this same key unlocks saved credentials and cookies, treat any hit as a credential-access incident as well as a persistence one.
  Runtime behaviour of the extension - Core filter: browser-originated network activity that does not match user browsing. The observed extensions polled a WebSocket route (`/google_ws/`) once per second and pulled configuration from paths disguised as stylesheets (`/google_api/81d47cb6.css`, `/google_api/a98cb43d.css`), exfiltrating LZ-string-compressed, RC4-encrypted data. Detection angle - a `.css` request that returns non-CSS content, and a persistent WebSocket from the browser to a domain that is not in the user's browsing history, are both queryable in proxy logs. LONGTALE beaconed roughly every 30 seconds, so regular sub-minute periodicity from a browser process to a single host is the volumetric tell.
  Accompanying side-load - Core filter: Sysmon event 7 where a legitimately named executable loads an unsigned DLL from its own directory. KREMLIN paired the extension with `SentinelMemoryScanner.exe` side-loading a malicious `SentinelAgentCore.dll`, and cleared `LdrpWorkInProgress` to start a thread from `DllMain` during loader lock. A security-product-branded binary running from a user-writable path is the anomaly, not the name.
  Hardening note that changes the hunt - `ExtensionInstallForcelist` and `ExtensionInstallAllowlist` applied via enterprise policy make unapproved extensions unloadable regardless of preference forgery, which converts this from a detection problem into a configuration check. Part of the hunt's value is confirming whether those policies exist and are actually applied on every host, because an estate that enforces an allowlist has largely eliminated the technique.

# H305

Chrome anticipated this attack. Extension state lives in `Secure Preferences`, and each entry is protected by a keyed MAC — with a `super_mac` covering the set — specifically so that an attacker who writes extension files to disk cannot make the browser load them. Chrome checks the MACs at startup and disables anything whose entry it did not write itself.

Two independent 2026 campaigns responded the same way, which is what makes this worth hunting as a behaviour rather than as an indicator. Elastic's KREMLIN analysis and Volexity's LONGTALE analysis describe unrelated actors, different payloads, different targets — and an identical technique: read the OSCrypt key out of Chrome's `Local State`, write the extension entry into `Secure Preferences`, and recompute the protection MACs so the forgery validates. KREMLIN went further and recovered the App-Bound Encryption key by launching Chrome under a debugger and scanning `.rdata` for the string `OSCrypt.AppBoundProvider.Decrypt.ResultCode`. LONGTALE stripped the `_encrypted_hash` and `super_encrypted_hash` fields and substituted forged legacy HMACs. When two unconnected groups converge on the same method, the method is the durable thing.

The detection follows directly from what the technique requires. `Secure Preferences` changes constantly during normal browsing, so the file event carries no signal at all — but the *writer* does. Chrome holds the key material and rewrites the MACs from memory, which means a forging process must be a separate process, and it must generally act while the browser is closed or its work will be overwritten. "A non-browser process wrote `Secure Preferences` while Chrome was not running" is a narrow condition with a small, enumerable legitimate population, and it sits upstream of every payload those extensions carried. The same query also catches the credential-access half of the problem, because the key that unlocks `Secure Preferences` is the key that unlocks saved passwords and cookies — a hit here is both a persistence finding and a credential incident. H304 covers the browser exploit chain that delivered the LONGTALE loader in the first place.

## Why

- Two unrelated actors independently converged on forging Chrome's integrity MACs, which establishes the technique as a stable method rather than one crew's tradecraft, and makes a behavioural hunt against it durable in a way that extension IDs and C2 domains are not.
- The technique's own requirements create the detection. Chrome recomputes the MACs from memory on exit, so a forgery has to be performed by an external process, generally while the browser is closed — a condition that is queryable and that the attacker cannot design around without abandoning the approach.
- The noisy part and the signal are cleanly separable. `Secure Preferences` is written continuously by Chrome itself, so attribution to the initiating process is what converts an unusable event stream into a low-volume, high-value query.
- A browser extension with `tabs`, `cookies`, `webRequest` and `storage` is a full-coverage implant that most endpoint tooling does not inspect at all. It reads every page after TLS termination, which makes it immune to network inspection, and it survives reimaging of nothing else but persists through browser profile sync.
- The enabling step is a credential compromise in its own right. The OSCrypt and App-Bound keys that make the forgery possible also decrypt saved passwords and session cookies, so any true positive immediately widens the incident scope beyond browser persistence.
- Part of the hunt's output is a configuration answer rather than a finding. Verifying whether `ExtensionInstallAllowlist` or `ExtensionInstallForcelist` is genuinely applied across the estate tells the organisation whether it is exposed to this entire technique class, which is a more valuable result than any single detection.
