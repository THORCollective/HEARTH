false_positive_notes: |
  A browser spawning a command interpreter is rare but not unheard of, and the legitimate population is small enough to enumerate once and then suppress by specific path and command line. Known benign producers: Chrome and Edge update and installer flows (`setup.exe`, `MicrosoftEdgeUpdate.exe`), which spawn shells but from signed binaries in `Program Files` paths; enterprise browser management and policy tooling; developer workflows where a browser-registered custom URI protocol handler launches a local script, which is legitimate but is also exactly the shape of the attack and should be inventoried explicitly rather than blanket-allowed; browser extensions using native messaging hosts, which spawn a registered host process rather than a shell — a native messaging host that is itself `cmd.exe` or `powershell.exe` is a finding, not a false positive; and automated testing frameworks such as Selenium or Puppeteer on developer and CI hosts, which are best excluded by host role rather than by process name. The `curl.exe` term specifically produces noise on developer workstations, where curl is used constantly — but almost never as a CHILD OF THE BROWSER, which is why the lineage condition rather than the utility name is doing the work. Be aware of two collection artefacts that mimic this: some EDR products re-parent orphaned processes to an incorrect ancestor when the true parent exits quickly, and Chrome's own multi-process architecture can cause renderer PIDs to be reused, so verify the parent by PID plus process start time rather than by PID alone before escalating.
notes: |
  The core lineage detection - Core filter: a process whose parent is `chrome.exe`, `msedge.exe`, `brave.exe` or another Chromium binary, and whose own image is `cmd.exe`, `powershell.exe`, `pwsh.exe`, `wscript.exe`, `cscript.exe`, `mshta.exe`, `rundll32.exe`, `regsvr32.exe` or `msiexec.exe`. Defender XDR KQL - `DeviceProcessEvents | where InitiatingProcessFileName in~ ("chrome.exe","msedge.exe","brave.exe") | where FileName in~ ("cmd.exe","powershell.exe","pwsh.exe","wscript.exe","cscript.exe","mshta.exe","rundll32.exe","regsvr32.exe","msiexec.exe") | project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine, InitiatingProcessCommandLine, InitiatingProcessFileName, FolderPath`. Sysmon/EQL equivalent - `process where event.type == "start" and process.parent.name : ("chrome.exe","msedge.exe") and process.name : ("cmd.exe","powershell.exe","mshta.exe","rundll32.exe","regsvr32.exe","msiexec.exe")`. Triage values - `ProcessCommandLine`, `InitiatingProcessCommandLine` (the renderer command line identifies the sandbox type and the site isolation context), `AccountName`, `FolderPath`. Strong red flags - the command line contains a download utility (`curl`, `certutil -urlcache`, `bitsadmin`, `Invoke-WebRequest`, `iwr`, `wget`) together with a URL and an output path in a writable directory; the parent renderer command line includes `--type=renderer`, which means the spawn came from the sandboxed content process rather than from the browser process that legitimately handles updates.
  The staged second stage - Core filter: executable or MSI writes into `%TEMP%` and `%LOCALAPPDATA%\Temp` within seconds of the shell spawn, via Sysmon event 11 or `DeviceFileEvents`. In the observed chains the first stage landed as `msgbox.exe`. Strong red flags - a file written with a non-executable extension that is then executed as one: the UTA0560 chain downloaded an MSI to `%TEMP%\Temp.txt` and ran it with `msiexec /i "%TEMP%\Temp.txt"`, which defeats any control keyed on the `.msi` extension. Hunt `msiexec` command lines whose installer argument does not end in `.msi` as a standalone high-value query — it is cheap, generalises far beyond this campaign, and has almost no legitimate population.
  DLL side-loading stage - Core filter: Sysmon event 7 where a signed, legitimate executable loads an unsigned or differently-signed DLL from the same user-writable directory it was launched from. The chain extracted a legitimate EXE plus a malicious `wsc.dll` from the dropper resources and relied on search-order resolution. Triage values - `ImageLoaded`, `Signed`, `SignatureStatus`, `Company` compared against the loading image. Note ATT&CK has merged the side-loading sub-technique into T1574.001 (DLL Hijacking), so rules and references tagged with the retired T1574.002 still apply here.
  Persistence stage - Core filter: Security event 4698 or `schtasks.exe` execution creating a task whose name imitates a Windows component. The observed task was `Windows Scheduled System`, running on a five-minute interval. Detection guidance - do not chase the literal name; hunt tasks whose names are not present in a golden-image task inventory, and specifically tasks with sub-hourly repetition intervals, which are rare among legitimate Windows tasks and common among beacons. Registry corroboration - Sysmon event 12/13 under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tasks`.
  C2 and beaconing corroboration - Core filter: outbound HTTPS where the URI path is derived from host identity. The observed beacon fetched `https://<c2>/<path>/%COMPUTERNAME%.txt`, so hunt web-proxy and DNS logs for requests whose URI contains the requesting host's own name — a pattern with essentially no legitimate equivalent and one that is trivially queryable if proxy logs carry both the hostname field and the URI. The second-stage backdoor communicated from within `msiexec.exe`, so a long-lived `msiexec` process holding an outbound connection is itself anomalous: `msiexec` should be short-lived and should not beacon.
  Scoping and retro-hunt - The chain exploited CVE-2026-85046 (V8 type confusion), CVE-2026-87491 (WebAssembly sandbox escape) and CVE-2026-85880 (Windows `RtlpCreateServerAcl` kernel privilege escalation), with the kernel bug affecting Windows 10 1809 through 22H2, Server 2022, and Windows 11 builds below 22000. Patching closes the door but does not evict anything already installed, so scope the retro-hunt by browser build inventory across the full exposure window rather than by current patch state.

# H304

Volexity's September 2026 analysis describes multiple Chinese threat actors chaining three zero-days — a V8 type confusion, a WebAssembly sandbox escape, and a Windows kernel privilege escalation — to move from a visited web page to SYSTEM on the host. Almost all of that chain is invisible to endpoint telemetry. The renderer exploit runs as pre-staged Base64 shellcode inside a Web Worker thread, isolated from the visible tab. The sandbox escape achieves arbitrary read and write without touching disk. The kernel exploit is a reflectively loaded, position-independent DLL. Up to this point there is no file, no registry key, and no process to detect.

Then the chain does something completely ordinary. It calls `CreateProcessA` to run `cmd.exe /c curl`, downloading `msgbox.exe` into the temp directory. That single step is the whole hunt, and it is worth being precise about why. The exploit is what the attacker invests in and what they replace when it burns; the process creation is what the operating system forces on them. Three zero-days can be rotated, but if the objective is persistent access rather than a one-shot in-memory action, something has to survive the browser process, and on Windows that means creating a process or writing a file. `chrome.exe` as the parent of a command interpreter is a lineage that normal browsing simply does not produce, and it stays true regardless of which CVEs the next chain uses.

The stages that follow are worth folding into the same hunt because each has an independently durable property. The second stage was delivered as an MSI written to `%TEMP%\Temp.txt` and executed with `msiexec /i "%TEMP%\Temp.txt"` — an extension mismatch that defeats extension-based controls and that is cheap to query on its own. Persistence was a scheduled task named `Windows Scheduled System` running every five minutes, where the generalisable signal is the sub-hourly repetition interval rather than the name. The backdoor then beaconed to a URI containing the host's own `%COMPUTERNAME%`, which is a pattern with no legitimate equivalent and is directly visible in proxy logs. The parallel JungleBamboo chain from the same report took a different route after execution — installing a malicious Chrome extension by forging the browser's own integrity checks — which is covered separately in H305.

## Why

- The exploit chain is deliberately file-less until the moment it needs persistence, so detection built on payload artefacts has nothing to match until after the attacker has already succeeded. The process-creation boundary is the earliest point at which the host produces evidence.
- The lineage is invariant to the vulnerabilities. Three separate zero-days were chained here and all three will eventually be patched, but any successor chain that wants durable access still has to create a process or write a file from the browser's context, so the hunt does not expire with the CVEs.
- The legitimate population is small and enumerable. Browsers spawning shells happens almost exclusively during update flows and a handful of developer workflows, which can be inventoried once and suppressed by path — leaving a query that runs at very low volume in a normal environment.
- The renderer command line distinguishes the dangerous case for free. A spawn whose parent carries `--type=renderer` came from the sandboxed content process, which is where exploitation happens, rather than from the browser process that legitimately performs updates.
- Several follow-on stages generalise well beyond this campaign and cost almost nothing to add: `msiexec` invoked against a file that is not an `.msi`, scheduled tasks with sub-hourly repetition intervals, and beacon URIs containing the requesting host's own name are each independently useful hunts with very small legitimate populations.
- Patching does not evict an established foothold. Because the exploited builds are known, the browser version inventory turns this into a bounded retro-hunt over a specific exposure window rather than an open-ended search.
