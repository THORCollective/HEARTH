false_positive_notes: |
  The file-write leg is close to zero-baseline when scoped correctly. A user-content upload directory should never receive a file with an executable or server-parsed extension — `.aspx`, `.asp`, `.ashx`, `.asmx`, `.aspx.cs`, `.php`, `.jsp` — and a correctly configured application stores uploads outside the web root or with execution disabled. Deployment activity is the main confounder for the process leg - application releases and configuration changes legitimately write `.aspx` files into web roots, but they do so from a deployment agent, MSDeploy or a release pipeline account, in bursts, across many files at once, with predictable paths — not one file at a time into a member documents folder with a GUID name. `w3wp.exe` spawning a child process is genuinely rare in most applications but not universal - some applications shell out for PDF generation, image conversion, antivirus scanning or report rendering. Those are enumerable, repetitive and launch the same few binaries with the same argument shapes, so a short per-application allowlist of expected children resolves them permanently. `cmd.exe /c whoami` from a web worker is not on anybody's list.

Commands run through the shells, published verbatim - `cmd.exe /c whoami`, `cmd.exe /c ipconfig`, `cmd.exe /c netstat -ano | findstr LISTENING`, `powershell -NoProfile -Command "Import-Module WebAdministration -ErrorAction SilentlyContinue; Get-Website | Format-List *; Get-WebBinding | Format-Table -AutoSize"`, `findstr /i /c:"connectionString" /c:"password" /c:"Data Source" E:\Content\info\web.config`, and `findstr /s /i /c:"CVV" /c:"CardNumber" /c:"CreditCard" E:\Content\info\*.aspx`. Later activity staged `C:\Windows\Temp\plant_ccrtc_mousewheel.ps1`, `plant_ccrtc_fast.ps1.ps1` and `ccrtc_sdk_init.js`, each alongside a `.b64` copy. The environment included payment integrations with Fortis and mxmerchant, an authentication page at `/auth/default.aspx`, and a jQuery path `*\includes\jquery\jquery.mousewheel-3.0.6.pack.js`. Huntress published no detection queries and no ATT&CK IDs; the queries and mappings below are derived from those artefacts.
  The two naming strategies, and why both are catchable - The attacker used the upload directory for initial access, where the application's own naming convention supplied the filename, and then wrote a second set of shells into the web root under names chosen to blend with real site assets - `css_bundle.aspx`, `jquery.validate.min.aspx`, `webresource.aspx`. The second set is the more durable persistence and is the more interesting detection, because the names are plausible but the extensions are wrong for what they imitate - a jQuery validation plugin is `.js`, a CSS bundle is `.css`, and neither is ever an `.aspx`. That mismatch between the implied asset type and the server-parsed extension is a general rule, not an IOC.
  File-write leg (primary) - Core filter - creation of a file with a server-parsed extension (`.aspx`, `.asp`, `.ashx`, `.asmx`, `.ascx`, `.cshtml`) anywhere under a user-upload directory, or anywhere in the web root where the writing process is `w3wp.exe` rather than a deployment agent. Triage fields - full path, writing process and its parent, account, file size, and the IIS log entry for the request that immediately preceded the write. Strong red flags - the file name imitates a static asset type (`*.min.aspx`, `*css*.aspx`, `*jquery*.aspx`); the file is written into `Images\`, `includes\`, `master\` or `css\`; the writing process is the IIS worker itself.
  Sample KQL - server-parsed file written by the IIS worker process.
  `DeviceFileEvents | where Timestamp > ago(30d) | where InitiatingProcessFileName =~ "w3wp.exe" | where FileName endswith ".aspx" or FileName endswith ".ashx" or FileName endswith ".asmx" or FileName endswith ".asp" | project Timestamp, DeviceName, FolderPath, FileName, SHA256, InitiatingProcessCommandLine, InitiatingProcessAccountName | order by Timestamp desc`
  Process-lineage leg (independent, and the strongest single query) - Core filter - any process whose parent is `w3wp.exe`. Triage - the child image, full command line, the application pool identity, and the IIS log line correlated by timestamp, which yields the requesting client IP and the URL of the shell. Strong red flags - `cmd.exe`, `powershell.exe`, `net.exe`, `whoami.exe`, `ipconfig.exe`, `netstat.exe`, `findstr.exe`, `certutil.exe` or `bitsadmin.exe` as a child of the web worker. The observed sequence here is a textbook post-exploitation triad - identity (`whoami`), network position (`ipconfig`, `netstat -ano | findstr LISTENING`), and application context (the `Get-Website`/`Get-WebBinding` PowerShell) — so a single hit should be expanded to all children of that worker across the preceding and following days rather than triaged in isolation.
  `DeviceProcessEvents | where Timestamp > ago(30d) | where InitiatingProcessFileName =~ "w3wp.exe" | summarize count(), commands = make_set(ProcessCommandLine, 50) by DeviceName, FileName, InitiatingProcessCommandLine | order by count_ desc`
  Credential and card-search leg (what the intrusion was for) - Core filter - `findstr.exe` or `Select-String` with arguments naming `connectionString`, `password`, `Data Source`, or payment field names such as `CVV`, `CardNumber`, `CreditCard`, especially with `/s` for recursion against a web root. This is a high-value standalone detection regardless of how the attacker got there, and it is also the clearest statement of intent in the whole intrusion - a recursive search for card-number field names across application source is not reconnaissance, it is target selection. Where the application has payment integrations (Fortis and mxmerchant here), a hit should trigger payment-data incident procedures immediately, not after the technical investigation completes.
  Staging leg - Files written to `C:\Windows\Temp` in matched pairs, one with a `.b64` extension and one without, indicate base64 transfer through a shell with no binary upload capability followed by local decode. A generic query for a file and its `<name>.b64` twin in the same directory within a short window catches that transfer pattern independently of the file names chosen, and the doubled extension in `plant_ccrtc_fast.ps1.ps1` is a reminder to match on substring rather than on exact suffix.
  Relationship to existing coverage - HEARTH's IIS and web-application intrusion hunts cover specific products and specific exploitation routes — [[H311]] for an Exchange backdoor launched from a forged VIEWSTATE and commanded through the `x-owa-urlpostdata` header, [[H278]] for PaperCut's application server spawning shells as SYSTEM, [[H317]] for Cisco Secure FMC. This hunt is the generic municipal-SaaS case - no CVE, no product-specific exploit, just an application that accepts member file uploads into a web-reachable directory. That makes it portable to any IIS application with an upload feature, which is most of them.

# H364

Huntress's September 2026 investigation into a parks and recreation management platform describes an intrusion with no exploit in it.

The attacker registered a member account and used the application's own document upload feature. The uploaded files were `.aspx` webshells, and the application dutifully stored them under its generated naming convention — `/documents/MemberFiles/12345_67890_<guid>.aspx` — in a directory served over the normal site URL. Six of them.

From there the shells wrote a second generation into the web roots under names picked to disappear into a real site: `css_bundle.aspx`, `jquery.validate.min.aspx`, `webresource.aspx`, placed in `includes\`, `master\` and `Images\`. Each one imitates a static asset type while carrying a server-parsed extension, which is the tell — a jQuery validation plugin is a `.js` file and never an `.aspx`.

What ran through them is a tidy post-exploitation sequence: `whoami`, `ipconfig`, `netstat -ano | findstr LISTENING`, a PowerShell enumeration of every IIS site and binding, then `findstr` against `web.config` for connection strings and passwords, and finally a recursive search across the application source for `CVV`, `CardNumber` and `CreditCard`. The platform had Fortis and mxmerchant payment integrations.

Every stage of that is visible as a child process of `w3wp.exe`, which is a parent that should have almost no children at all.

## Why

- **No vulnerability is required, so patching does not help.** The entry point is a feature working as designed. The control is where uploads are stored and whether they can execute — and the detection is whether a server-parsed extension ever lands in a user-content directory.
- **`w3wp.exe` spawning a command interpreter is near-zero baseline.** Most applications never shell out; those that do use a short, repetitive, enumerable set of children. `cmd.exe /c whoami` from a web worker is unambiguous.
- **The second-generation names teach a reusable rule.** "Implied asset type does not match the executable extension" catches `jquery.validate.min.aspx` and everything like it, without knowing any of these filenames in advance.
- **The upload directory gives the shells camouflage the attacker did not have to build.** The application generated the filenames, the directory legitimately receives new files constantly, and the files are reachable over the normal site URL — so nothing about their presence or their retrieval looks unusual.
- **The card-field search states the objective out loud.** A recursive `findstr` for `CVV` and `CardNumber` across application source is target selection, and on a platform with live payment integrations it should start payment-incident procedures on its own.
- **The `.b64` pairs expose the transfer method.** A file and its base64 twin appearing together in `C:\Windows\Temp` is a generic signature of moving binaries through a text-only shell, independent of what the files are called.
- **It generalises to a very large population.** Municipal, education and small-vendor IIS applications with member upload features are everywhere, are rarely covered by an application security programme, and frequently hold payment data.
