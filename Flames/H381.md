# H381

`ARPSYSTEMCOMPONENT=1`. One installer property, and the thing you just installed is no longer in Programs and Features.

Huntress found it in `ISOSimple.msi`, the payload of a ClickFix chain that started on a counterfeit ChatGPT Custom GPT. The package introduces itself as "Advanced Printer Configuration Reader" from a publisher called "Softplicity", installs silently with `msiexec /qn /norestart` into `%LOCALAPPDATA%\Programs\`, and sets that property so — in Huntress's words — a user who goes looking for whatever they just installed won't find it.

The user-facing effect is the obvious one. The defender-facing effect is worse, and it is the reason this is worth a hunt rather than a footnote.

`ARPSYSTEMCOMPONENT` sets the `SystemComponent` registry value under the product's Uninstall key. A great deal of software inventory tooling enumerates those same keys and honours that same value. So the installed product can be missing from the estate inventory too — not hidden from the user, hidden from asset management. Which turns the most useful version of this hunt into something that needs no new telemetry at all: enumerate the Uninstall keys *including* `SystemComponent` entries, difference against what inventory reports, and read whatever only one of them knows about.

The property has a legitimate purpose and it matters to say so, because alerting on it alone will not survive a week. Microsoft intends it for things that are not independently removable — runtime redistributables, shared language packs, driver support packages, the constituent MSIs of a suite whose parent entry is the one you are supposed to uninstall. Microsoft's own products use it. Large commercial suites use it. That is all correct behaviour.

What has no legitimate form is the conjunction. The property is set, *and* the package was installed fully silently from a user-writable path by a script host rather than by a deployment system, *and* a custom action launches a process the instant the install finishes. A real component MSI is installed by its parent or by a management platform, from a staging location, and it does not immediately execute something out of `%LOCALAPPDATA%`.

That custom action deserves its own note. It means the initial execution does not wait for a reboot or a logon — so the window where only the MSI exists on disk and nothing has run yet is effectively zero. Huntress recorded exactly what that costs: in one incident Defender quarantined the MSI as `Trojan:Script/Wacatac.H!ml`, and it did not matter, because the installer had already run and the Run key and the scheduled task it planted carried the chain forward. A quarantine verdict on the dropper is not remediation.

Underneath, the package is mostly camouflage — 177 files, including an entire legitimately signed .NET runtime and, genuinely, a DOS 6.22 floppy image as set dressing. Eight files do the work: a Canon-signed `COTFileReadApp.exe` as the host process, a real Canon DLL patched to load a malicious one with its signature stripped, two more unsigned DLLs (one borrowing the name of a real open-source library), and the loader itself encrypted inside a `.wav` file.

`Softplicity` and `Advanced Printer Configuration Reader` will be different next month. The property and the path shape will not.

## Why

- **The property hides the product from asset inventory, not just from the user.** Inventory tooling reads the same Uninstall keys and honours the same `SystemComponent` value, so the install can be invisible to the system of record.
- **That makes inventory differencing the highest-yield leg and it needs no new telemetry.** Registry enumeration against the management platform's view, with anything present in one and absent from the other getting read.
- **The property alone is legitimate, and the conjunction is not.** Runtime redistributables and suite components set it correctly. None of them are installed silently from `%TEMP%` by PowerShell and then immediately execute from `%LOCALAPPDATA%`.
- **The launch-on-completion custom action removes the detection window.** No reboot, no logon, no Run key needed for first execution — so there is no interval in which the MSI sits on disk inert.
- **Quarantining the dropper did not stop it, and that is the lesson to carry.** Defender caught the MSI after it had already run; the Run key and scheduled task continued regardless. An AV verdict on the installer is not a closed incident.
- **The persistence pair shares one literal name across two mechanisms.** A Run-key value and a scheduled task with identical names is a cheap, high-precision pivot that survives the specific name changing.
- **A `.wav` read by a DLL rather than by a media player is independently anomalous.** The generic query — a non-media process reading audio from a program directory — has a small benign population and needs no campaign knowledge.
- **The identifying strings rotate and the structure does not.** Publisher and product name are per-campaign. `ARPSYSTEMCOMPONENT`, a silent install from a user path, and a signed vendor binary beside unsigned DLLs in `%LOCALAPPDATA%\Programs\` are the durable parts.
