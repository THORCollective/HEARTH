hypothesis: >-
  An Office document exploiting CVE-2017-0199 fetches and runs an HTA, and that HTA does not spawn its
  payload directly. AhnLab observed a project-material-purchase phishing chain where the malicious HTA
  "uses the Win32_Process.Create() method of WMI to execute an obfuscated PowerShell script in the
  background." That choice has a specific forensic consequence: when a process is created through WMI,
  the parent recorded on the new process is `WmiPrvSE.exe`, not the caller. So the lineage a responder

  parent-child pair mshta-to-powershell sees nothing. Hunt the break instead: a `powershell.exe` whose

  either COM-activated with `-Embedding` or launched from an Office application - plus, where it is
  enabled, the WMI-Activity trace channel that records which client process issued the

  WMI-launched processes are legitimate and routine, so the `WmiPrvSE.exe` parent on its own selects a

  `Invoke-CimMethod`, vulnerability scanners with authenticated checks, and backup and patch tooling all

# H378

The responder pivots on children of `mshta.exe` and finds nothing. The conclusion is that the HTA failed. The conclusion is wrong.

AhnLab's project-material-purchase chain starts conventionally enough: a phishing email impersonating staff at a specific company in Korea, an XLS attachment that displays a complete and entirely plausible purchase request form, and CVE-2017-0199 — the nine-year-old OLE2Link flaw — firing on open to pull an HTA down from `172.245.209[.]133`. The decoy is good. The user sees what they were promised, so there is no report, no ticket, and no suspicious-attachment escalation.

Then the HTA does something slightly unusual. Instead of spawning PowerShell, it calls `Win32_Process.Create()`.

The payload still runs. But the process-creation record for that PowerShell names `WmiPrvSE.exe` as its parent, because that is the process that actually created it. The HTA is nowhere in the lineage. What a responder reconstructs ends at `mshta.exe`, full stop, plus a separate PowerShell hanging off the WMI provider host somewhere nearby looking like inventory tooling.

Nearly every triage playbook and most published detection content for this class of attack keys on the parent-child pair. The exploit starts `mshta.exe`; `mshta.exe` spawns a shell. Routing through WMI cuts the second link cleanly, and it costs the attacker one line of code.

So the hunt has to be the break, not the pair. A shell parented to `WmiPrvSE.exe` is far too common on its own — SCCM alone will drown you, along with inventory agents, `Invoke-CimMethod`, authenticated scanners and patch tooling. What has no benign form is that shell appearing on the same host within seconds of an `mshta.exe` that the exploit started. With CVE-2017-0199 that `mshta.exe` usually runs as `mshta.exe -Embedding` under `svchost.exe` rather than under Excel, so match on that as well as on an Office parent. Legitimate WMI process creation comes from a management service or a remote administrator. It does not come from a spreadsheet.

The rest of the chain is largely covered ground in HEARTH and is worth knowing but not worth a second hunt. The PowerShell pulled a steganographic PNG from a `*.workers.dev` subdomain, carved Base64 out of it between the markers `IN-` and `-inl`, loaded a .NET loader in memory, and used it to fetch Remcos — served, incidentally, from the same `172.245.209[.]133/70/` path as the HTA, with a `.png` extension and, very likely, no image inside it. [[H246]] already covers payloads hidden in PNGs. [[H120]] hunts unexpected `wmiprvse.exe` children too, but for remote WMI execution; this hunt is the local, document-started version.

Two pivots pay off immediately, though. The reused infrastructure is sloppy — one host, one path, both stages — so a single hit should pull every request to it. And a `.png` download whose magic bytes are not an image is detectable without knowing anything about this campaign at all.

## Why

- **The WMI call exists to break lineage, and it succeeds.** The payload's recorded parent is `WmiPrvSE.exe`, so the HTA never appears in the process tree that a responder or a rule reconstructs.
- **Detection content for this attack class is built on the pair this technique removes.** Office to `mshta.exe` to shell is the canonical chain. One `Win32_Process.Create()` call deletes the second hop for one line of code.
- **"PowerShell under WMI" alone is unusable, and the correlation makes it precise.** SCCM, inventory agents, authenticated scanners and remote administration all produce it constantly. An exploit-started HTA seconds earlier does not.
- **The decoy guarantees no user report.** The XLS renders the exact document the email promised. There is no moment where the victim suspects anything, so endpoint telemetry is the first and only signal.
- **WMI-Activity tracing names the caller directly, where it is available.** It closes the gap the lineage break opens — but the Trace channel is off by default and the Operational channel does not record the call, so silence is a telemetry gap, not an all-clear.
- **The infrastructure reuse is the cheapest high-yield pivot.** One IP and one URL path served both the HTA and the final RAT. A single confirmed hit on that host justifies pulling every connection to it.
- **A `.png` that is not an image is detectable without any campaign knowledge.** Magic-byte and content-type mismatch on image downloads generalises past this intrusion entirely.
- **The steganography is already covered and the WMI hunt that exists is remote.** [[H246]] covers PNG-hidden payloads and [[H120]] covers `wmiprvse.exe` children from remote WMI; scoping this hunt to the local, document-started lineage break keeps it distinct from both.
