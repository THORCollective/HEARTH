false_positive_notes: |
  Legitimate ScreenConnect self-updates and reinstalls through the same instance keep the instance ID and relay host, so they fail the different-instance condition. Confirm by comparing the `ScreenConnect Client (<id>)` service name before and after the event.
  
  Planned MSP platform migrations or instance consolidations do install a new instance ID through the old client. They differ from this activity in several ways: they are change-ticketed, roll out in waves rather than across unrelated customers within minutes, point to the MSP's documented relay, and remove the old client through its MSI uninstall rather than stopping its service. They also do not add Defender exclusions for Temp or ProgramData staging paths or create new Run values.
  
  Co-managed estates, such as internal IT plus an MSP or two MSPs, legitimately carry two ScreenConnect instances, but the first instance did not install the second. Reconcile both instance IDs against the authorized RMM register. Treat an unknown but benign instance as a governance finding to document and authorize, not something to suppress.
  
  MSPs routinely push other software through ScreenConnect commands with curl and msiexec, for example EDR agents, patch tools and line-of-business installers. The discriminator is that the MSI creates a `ScreenConnect Client (...)` service with a foreign relay.
  
  Defender exclusions for RMM install folders pushed by GPO, Intune or the antivirus console originate outside the ScreenConnect process tree and target Program Files paths, not Temp or ProgramData script paths.
  
  Collection caveats: you may need to request cloud-hosted panel audit exports from ConnectWise or the MSP. Endpoints whose original client was stopped may also drop out of RMM-based inventory, so rely on EDR and native Windows event telemetry for the host stage.

# H489

On November 11, 2026, ConnectWise reported unauthorized access to cloud-hosted ScreenConnect instances belonging to managed service providers. Huntress saw an operator use the panels' Run Command feature to reach at least 288 managed endpoints across 48 organizations in about 90 minutes, roughly a third of them in the first 10 minutes. Huntress attributes initial access to the third-party RMM+ extension (versions 1.0.31 and 1.0.32). If an administrator never set its shared access key, it accepted a blank one, so commands ran with no ScreenConnect login, role check, or MFA. ConnectWise had not independently confirmed that vector. Microsoft Threat Intelligence confirmed the activity and analyzed the follow-on toolkit, SCKit. The broadcast command checks for an existing client, pulls an attacker-controlled ScreenConnect MSI into C:\Windows\Temp, and installs it silently. A batch launcher then retrieves a PowerShell decoder that unpacks a package keyed to each device. SCKit persists through scheduled tasks, including a TrapWatch watchdog, and registry Run entries, and sets ScreenConnect services to start at boot. It writes Defender path exclusions for staged MSI copies and for a CWInstall_<8 hex>-c1\Installer.ps1 script, which installs a further attacker-controlled client. It also stops and displaces the legitimate client. Its RelayTrap component (C:\ProgramData\RelayTrap) replaces the guest process and waits for a technician to connect. It tries a patched guest-to-host file-execution flaw (CVE-2026-84869, blocked from client 26.6.5) and then aims to reuse the technician's panel session cookie to push payloads to other sessions through the Shared Toolbox. Huntress and Blackpoint report that this technician-to-fleet stage did not succeed in any observed case. The affected panels ran current ScreenConnect releases, so patching the core product would not have stopped the endpoint stage. Removing the rogue client alone leaves the persistence and exposed web sessions in place. This hunt targets the step every victim host goes through: a trusted remote-support client installing a second copy of the same product that reports to a different relay. It complements H306, which covers script-interpreter children of ScreenConnect, and H307, which reconciles management agents against tenants the organisation owns.

## Why

- In the November 11, 2026 campaign, one operator reached at least 288 endpoints across 48 organizations in about 90 minutes through MSP panels running current ScreenConnect releases, so patch status is not a control. Microsoft notes that removing the rogue client alone leaves SCKit's scheduled-task and Run-key persistence and the exposed technician sessions in place.
- The actor cannot avoid this step: to keep access independent of the MSP's own instance, it must land a client that reports to its own relay. Whatever the MSI hash, download URL or per-device decoder key, that client carries a different instance ID in its service name and a different `h=` relay host in its ImagePath. It is also installed by the trusted client running as SYSTEM, so the lineage survives indicator rotation.
- Every stage shows up in standard telemetry. The parent-child lineage, the Event ID 7045 service name, the ImagePath registry value and the Defender exclusion write (Event ID 5007) are recorded by stock Windows logging and any EDR, and the panel audit supplies the cross-customer fan-out count. The hunt therefore does not depend on SCKit-specific file names.
- False positives are easy to rule out. Legitimate updates keep the instance ID. Migrations are planned, point to documented relays, and do not write Temp-path Defender exclusions, add Run values or stop the original service. An authorized instance register reduces the remaining cases to a simple reconciliation.
