false_positive_notes: |
  GPU hosts are a heavily customised population and the library path is legitimately rewritten more often than on a general-purpose server, so the hunt has to key on provenance rather than on modification.
  - Driver installation and upgrade rewrite this exact path by design. The NVIDIA installer, dpkg and rpm all replace libnvidia-ml.so.1 and may leave backups behind. Correlate every write against package-manager transaction history for the same minute; a write with no corresponding transaction is the candidate population, a write inside one is routine maintenance.
  - Container runtimes and the NVIDIA container toolkit mount and symlink driver libraries into container filesystems constantly. Scope the hunt to the host mount namespace and to the resolved host library directory, and exclude the per-container bind-mount paths, or the result is thousands of legitimate events a day.
  - Compilers running on a GPU host are not suspicious on their own. These machines exist to build and run CUDA and machine-learning code, and `make` is in the normal working day of every researcher with an account. The discriminator is what the build writes, not that a build happened - a build whose install step lands on a driver library path is the finding.
  - Legitimate interposer libraries exist. Profilers, schedulers, MIG and MPS tooling, cgroup-based GPU limiters and some commercial monitoring agents all wrap NVML deliberately, and a site may have installed one on purpose. Establish which wrappers are approved before hunting, and treat the inventory as the allowlist.
  - A dot-prefixed backup is weak on its own. Administrators make hidden backups by hand, and so do install scripts. It is corroboration for an unowned library file, not a finding by itself.
  - Low reported utilization is normal most of the time. Idle GPUs are the common state in any environment that is not saturated, which is why the telemetry check in [[M070]] is framed as a divergence between two independent measurements rather than as a threshold on the reported figure.
notes: |
  Source reporting is Elastic Security Labs' November 12, 2026 analysis of REF3364, a Linux cryptomining intrusion in which the actor abused an exposed Ray job agent to obtain root on three Linux GPU hosts and deployed a toolkit staged under `/opt/vadi_`. The component this hunt targets is the modified NVIDIA Management Library wrapper. The closest existing hunts are [[H280]], which covers a loadable kernel module impersonating a stock kernel component and persisted by a masquerading systemd unit - the same intrusion pattern and the same need for provenance, but a kernel module rather than a userspace shared object - and [[H337]], which covers compiling a miner on the victim to avoid shipping a known hash. Neither covers falsifying the output of a hardware monitoring interface, and no existing hunt references NVML or nvidia-smi.
  Why this is worth a hunt of its own - A miner is loud in exactly one dimension, which is utilization, and this component removes that dimension. Elastic reports that the wrapper "forwards queries to the genuine NVIDIA library, then alters selected results", that "GPU utilization is reported as 0%", and that temperature and power "are replaced with random readings of 36 to 46 degrees Celsius and 100 to 200 watts". The randomised plausible band is the detail that matters: a constant value would stand out in a time series, so the readings are made to look like a lightly loaded card rather than a dead one. Every consumer of that library - `nvidia-smi` on the console, a Prometheus exporter, a scheduler's capacity view, a cloud-cost dashboard - receives the same fabricated numbers, because they all read through the same interface.
  Core filter 1, the install itself - The highest-value single check. Elastic reports that the recovered `/opt/vadi_/nvml-hook/` directory contains `nvml_hook.c` and a Makefile, that the Makefile "uses ldconfig to locate the NVIDIA library directory and replaces its libnvidia-ml.so.1 with the wrapper", and that it "leaves the genuine versioned library in place for backend calls". Hunt for a write, rename or replace of `libnvidia-ml.so.1` at the `ldconfig`-resolved path where no package-manager transaction covers the same window. Triage values are the writing process and its full command line, its parent, the account, the resulting file hash, and whether any installed package claims ownership of the path. On a Debian-family host `dpkg -S` and on a RHEL-family host `rpm -qf` answer the ownership question directly, and `rpm -V` on the owning package reports a changed file; an unowned file at a driver library path is the strong finding.
  Core filter 2, the preserved original - Elastic reports the Makefile "creates /usr/lib/.libnvidia-ml.so.1.backup if no backup exists". Hunt for dot-prefixed siblings of driver libraries anywhere in the linker search path. The shim needs the genuine library because it forwards real calls to it, so the original is not deleted - which is useful twice over, because the backup is both an indicator and the artefact that lets a responder compare the two files and recover the real one. Note that the reported path is `/usr/lib/`; resolve the actual directory with `ldconfig -p | grep libnvidia-ml` on the host rather than assuming it, because the library directory differs across distributions and driver packaging.
  Core filter 3, the build on the host - Elastic reports that the toolkit's "maintenance task locates this source directory and can run make followed by make install to build and install the wrapper", which means the compile is repeated rather than one-off and the staging source tree persists on disk. Hunt for `make` or a C compiler whose working directory or arguments name a directory containing a file like `nvml_hook.c`, and for any `make install` whose effect reaches a library path. Pair this with [[H465]], which covers the initial access route in the same intrusion, and with the kernel-module angle in [[H280]]: the same host also built `acpi_thermal_mgr` through DKMS, so a GPU host compiling more than one out-of-tree component in a short window is worth working as a unit.
  Sample host check, run under a shell so the finding is reproducible during triage:
  ```bash
  set -u
  libdir=$(ldconfig -p | awk '/libnvidia-ml\.so\.1/ {print $NF; exit}')
  libdir=${libdir%/*}
  echo "resolved NVIDIA library directory: $libdir"
  ls -la "$libdir" | grep -i nvidia-ml
  ls -la "$libdir"/.*nvidia-ml* 2>/dev/null
  sha256sum "$libdir"/libnvidia-ml.so.1
  if command -v dpkg >/dev/null 2>&1; then
    dpkg -S "$libdir/libnvidia-ml.so.1" || echo "NO PACKAGE OWNS THIS PATH"
  elif command -v rpm >/dev/null 2>&1; then
    rpm -qf "$libdir/libnvidia-ml.so.1" || echo "NO PACKAGE OWNS THIS PATH"
  fi
  find / -xdev -name 'nvml_hook.c' -o -xdev -name 'nvml-hook' -type d 2>/dev/null
  ```
  The ownership line is the one that decides the case. A driver library that no package claims, on a host where the driver was installed from a package, is not a configuration variant.
  Core filter 4, the contradiction - Core concept: compare the library's answer against a measurement that does not pass through it. The reported behaviour fabricates utilization, temperature and power at the NVML boundary, so any reading taken below or beside that boundary disagrees. A BMC or IPMI power sensor, a rack PDU, an inlet-temperature reading, or a fan-speed curve are all outside the library. A card reporting 0% utilization and 100 to 200 watts while the chassis draws a load consistent with a saturated GPU is the contradiction to chase. Expected, not observed by Elastic: a specific numeric divergence threshold - the report describes the falsified values but does not publish a detection threshold, and the band that works is environment-specific, which is why the statistical form of this check is [[M070]] rather than a fixed rule here.
  Core filter 5, what the shim was hiding - The reported toolkit ran two miners, `kurt` (XMRig 6.25.0) and `tilki` (SRBMiner-MULTI 3.6.9), selected by SANSAR's CPU and GPU branches, with the GPU miner started from `/opt/vadi_/tilki`. Elastic notes that the collected `tilki` "has the same SHA-256 hash as the executable in the official SRBMiner-MULTI 3.6.9 Linux release", so a hash hunt for the GPU miner finds a legitimately published file and will not distinguish the intrusion on its own. The process names were also hidden at the kernel level by the rootkit in the same toolkit, which is why the library check and the out-of-band telemetry check matter more here than a process-name hunt: on this host, process listings were not trustworthy.
  Scope - GPU hosts, build servers with cards, and AI or machine-learning infrastructure. Elastic's own closing recommendation is that organizations expanding GPU infrastructure "should check who can submit jobs and whether GPU monitoring libraries have been modified", which is precisely the pair of hunts in [[H465]] and this one.

# H464

A cryptominer has exactly one loud symptom. The card gets busy, and anyone who looks sees it.

Elastic Security Labs found an intrusion where the operator closed that window. On three Linux GPU hosts, the toolkit built a small shared object from C source sitting on the host, used `ldconfig` to find where the NVIDIA management library lives, and dropped the shim in its place. The real library was kept — renamed to a hidden file beside it — because the shim needs it. Every call is forwarded to the genuine library, and then the answer is edited on the way back.

Utilization comes back as 0%. Temperature comes back as a random number between 36 and 46 degrees. Power comes back as a random number between 100 and 200 watts. Not zeroes, not constants: a plausible, slightly-busy card.

Everything that reads GPU load reads it through this interface. `nvidia-smi` on the console, the metrics exporter, the scheduler's capacity view, the finance team's cost dashboard. They were all told the same thing, and they all agreed, because they were all asking the same compromised library.

What does not go through that library is the chassis. The power supply draws what the GPU actually draws, the inlet temperature rises with real heat, and the BMC reports what its own sensors read. That is the gap this hunt lives in — and the artefact that makes it findable is on disk: a driver library that no installed package owns, with the original hidden next to it.

## Why

- **The shim converts a detectable behaviour into an undetectable one.** Compute hijacking is normally found by noticing load, so a component that fabricates load at the interface every tool reads removes the primary detection rather than evading a particular rule. Nothing downstream of the library can tell the difference, which is why the hunt has to look at the library itself.
- **It leaves provenance evidence that is hard to fake.** The library path belongs to a package on any normally-built host. A file at that path that no package owns, with a hidden copy of the real one beside it, is a cheap and near-unambiguous check — and unlike the process listings on this host, package ownership was not something the toolkit tampered with.
- **The randomised plausible values tell you the operator expected a time series to be read.** Reporting a constant would stand out in any graph. Choosing a narrow believable band for temperature and power is a deliberate accommodation to monitoring, and it says the operator expected to be looked at and planned for it.
- **GPU estates are the worst place to lose telemetry trust.** These hosts are expensive, shared, and often administered outside the central IT estate by the researchers using them. Cryptojacking there is not only compute theft — it quietly degrades the throughput of workloads whose owners will attribute the slowdown to their own code.
- **The same intrusion also hid the processes in the kernel.** With an ftrace-based rootkit filtering `/proc` listings and a userspace library filtering GPU telemetry, the two sources a responder reaches for first were both answering to the operator. Out-of-band measurement is not a nice-to-have on a host like this; it is the only reading that was ever true.
