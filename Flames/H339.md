false_positive_notes: |
  `listKeys` is a legitimate and common operation: Terraform and Bicep deployments read keys to wire up connection strings, Azure Functions and App Service resolve storage keys at deploy time, backup and monitoring agents call it on a schedule, and AKS/Data Factory linked services re-read keys on every run. Key Vault secret reads are similarly routine for any application that stores its config there. Control this by baselining per-principal `listKeys` behaviour over 30 days (see [[B055]]): the sanctioned callers are a small, stable set of deployment and platform identities, each touching a predictable set of storage accounts from a predictable IP range with a recognizable user agent. The decisive discriminator is breadth plus provenance, not the operation itself — a CI/CD principal reads keys for the three accounts in its own resource group from the pipeline's egress range, whereas a compromised principal walks every account it can reach from an address that identity has never used. Treat a principal whose `listKeys` fan-out exceeds its 30-day distinct-account maximum, from a new ASN, as reportable even when the calls succeed and look authorized — RBAC permitting the call is precisely why this is a hunt and not an alert.

  Azure Activity Log (AzureActivity) - Core filter: `OperationNameValue` in the credential-bearing set, principally `MICROSOFT.STORAGE/STORAGEACCOUNTS/LISTKEYS/ACTION`, with `ActivityStatusValue` equal to `Success` and the caller identity resolving to a service principal rather than a user. Aggregate distinct `_ResourceId` per `Caller` over a rolling 1-hour window and flag when the distinct storage-account count exceeds roughly 3x that principal's 30-day hourly maximum. Triage fields: `Caller` (the SP object ID or appId), `CallerIpAddress`, `OperationNameValue`, `ResourceGroup`, `SubscriptionId`, `Authorization_d` (the role assignment that permitted it), `Claims_d` (carries `appid`, `idtyp`, and the audience). Strong red flags: `CallerIpAddress` in a hosting or VPS ASN rather than a known CI/CD or corporate egress range, the same `Caller` appearing against multiple subscriptions within minutes, and `listKeys` calls with no preceding or following deployment operation (`MICROSOFT.RESOURCES/DEPLOYMENTS/WRITE`) — a real deployment reads keys in the middle of a deployment, a thief reads them alone.
  Sample KQL — ListKeys fan-out per service principal:
  `AzureActivity | where TimeGenerated > ago(30d) | where OperationNameValue =~ "MICROSOFT.STORAGE/STORAGEACCOUNTS/LISTKEYS/ACTION" | where ActivityStatusValue == "Success" | extend appid = tostring(parse_json(Claims_d).appid) | summarize keyCalls = count(), distinctAccounts = dcount(_ResourceId), accounts = make_set(_ResourceId, 50), ips = make_set(CallerIpAddress, 20), subs = dcount(SubscriptionId), firstSeen = min(TimeGenerated), lastSeen = max(TimeGenerated) by Caller, appid, bin(TimeGenerated, 1h) | where distinctAccounts >= 5 or subs > 1 | order by distinctAccounts desc`
  Entra service principal sign-in logs - Correlation: join `AADServicePrincipalSignInLogs` on `ServicePrincipalId` to establish where the token came from. Core filter: `ResourceDisplayName` equal to `Windows Azure Service Management API`, then compare `IPAddress` and its ASN against that principal's historical set. Strong red flags: multiple tokens issued to one principal inside a short window with overlapping validity (Microsoft explicitly called out "overlapping token streams" and division of work across principals as the agentic tell), authentication with a client secret where the principal is documented as certificate-based, and `ServicePrincipalCredentialKeyId` changing without a corresponding credential-rotation change ticket.
  User-agent provenance - Core filter: Storm-3168's ARM traffic carried `python-requests/2.34.2`. Hunt `AzureActivity` and the sign-in logs for SDK-shaped or bare HTTP-client user agents on principals whose sanctioned tooling is the Azure CLI, Terraform or an Azure DevOps agent. This is a soft signal on its own — plenty of legitimate automation uses raw SDKs — but it is a strong corroborator once fan-out has already flagged the principal.
  Key Vault audit logs - Core filter: `AzureDiagnostics` where `ResourceType` is `VAULTS` and `OperationName` in (`SecretGet`, `SecretList`, `KeyGet`, `CertificateGet`), grouped by `identity_claim_appid_g`. Strong red flag: a principal enumerating secrets (`SecretList`) and then reading many of them, which is inventory-then-harvest behaviour rather than an application resolving the one secret it needs by name.
  Left-of-boom: leaked-credential provenance - The initial exposure was an edited GitHub issue, so the secret never appeared in a commit and repository secret scanning did not see it. Sweep your organization's GitHub issue and pull-request *edit histories* and comment bodies for `client_secret`, tenant GUIDs and `login.microsoftonline.com` strings via the Issues API `since` parameter, and cross-check any recovered `appid` against the principals in this hunt.
  Close the loop on the data plane - Once a key is stolen, subsequent access authenticates with the shared key and shows up only in `StorageBlobLogs` with `AuthenticationType` equal to `AccountKey`, not in Entra at all. For any storage account named in a flagged `listKeys` burst, pivot to `StorageBlobLogs | where AuthenticationType == "AccountKey"` and compare `CallerIpAddress` against the application's expected ranges — this is where the exfiltration becomes visible, and it is invisible to identity-centric monitoring.

# H339

On September 25, 2026, Microsoft Threat Intelligence published its analysis of Storm-3168, an actor that obtained Azure service principal credentials — client ID, client secret and tenant ID — from the edit history of a public GitHub issue, where they had been pasted and then removed. Because the secret never landed in a commit, repository secret scanning never fired on it. The actor authenticated that principal straight against Azure Resource Manager and, over roughly 15.5 hours, ran more than 300 successful read operations enumerating subscriptions, virtual machines, resource groups, storage accounts, web apps, App Service plans, resource locks and Recovery Services vaults. Inside that activity it made 30+ successful `ListKeys` requests, retrieving storage account access keys, and read Key Vault material, before pivoting into a seven-minute destructive phase.

The credential harvesting is the part worth hunting separately from the destruction, because it is the part that outlives the incident. A storage account access key retrieved via `listKeys` is a bearer credential for the data plane: it does not expire with the token that fetched it, it does not appear in Entra ID sign-in logs when used, and revoking the compromised service principal does not invalidate it. Rotating the key is a separate, easily forgotten action. So an actor who reads keys broadly and quietly retains access to the data long after the identity that stole them is disabled — which is why the `listKeys` fan-out, not the later deletions, is the event that determines how much of the tenant is still exposed.

## Why

- The operation is fully authorized, which is exactly why it needs hunting rather than alerting: RBAC permitted every one of Storm-3168's `listKeys` calls, so no policy violation, no failed authorization and no Defender alert on the call itself marks the theft. Only the shape — one principal, many accounts, one short window, unfamiliar provenance — separates it from the deployment automation that makes the same call all day.
- Stolen storage keys create a persistence path that survives identity remediation. Data-plane access authenticated with `AccountKey` bypasses Entra entirely and appears only in storage diagnostic logs, so an incident response that disables the service principal and rotates its secret, without rotating every key it read, leaves the adversary's access intact and unmonitored.
- The exposure vector generalizes past this actor and defeats the control most teams assume covers it. Secrets pasted into an issue, comment or pull-request description and then edited out remain retrievable through the GitHub API's edit history while being invisible to commit-oriented secret scanning, so the same class of leak is very likely present and unflagged in most organizations.
- Every leg is first-party and queryable without additional sensors: `AzureActivity` records the operation, caller, source IP and the specific role assignment that authorized it; `AADServicePrincipalSignInLogs` establishes token provenance and reveals the overlapping-token pattern Microsoft attributed to automated execution; and `StorageBlobLogs` closes the loop on whether the harvested keys were actually used.
