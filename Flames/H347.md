false_positive_notes: |
  Mark-of-the-Web removal is a legitimate operation with real benign volume, so this hunt lives or dies on lineage and timing rather than on the removal itself. Archive utilities routinely do not propagate the stream when extracting (7-Zip historically did not, which is why it was a favoured delivery wrapper), and `Unblock-File`, the Explorer "Unblock" checkbox, and `streams.exe -d` are all sanctioned administrative actions. Build and deployment tooling strips the stream at scale by design, and developers unblock downloaded DLLs and scripts constantly. Browsers themselves also delete `Zone.Identifier` streams during normal download handling (overwriting, cancelling, finalizing a partial download) — SigmaHQ's "ADS Zone.Identifier Deleted By Uncommon Application" rule filters Chrome, Edge and Firefox out as benign deleters for exactly that reason, which means that rule would suppress this case. So a browser deleting a stream is not enough on its own. The discriminator is the conjunction: a PE written by a browser process, its zone marking gone within seconds, and that same path executed within seconds more, parented by `explorer.exe`, `dllhost.exe`, `sihost.exe` or `svchost.exe` (shell/COM launch) with no user interaction in between. A user who downloads an installer and double-clicks it at once produces the same parent, so require the fast timing plus either the missing zone marking or renderer-side context (a renderer crash or respawn, or a download with no navigation from the user). Expect near-zero hits on the full conjunction; if you see steady volume, check whether a browser-hosted deployment or virtualization product performs downloads on the user's behalf and allowlist it explicitly.

  Platform: Windows. Volexity does not report how the Mark of the Web was removed, and published no detection queries; the queries below are derived from the reported chain.
  Why this sequence matters - The three steps each remove a different detection anchor. Downloading in-process means no `curl`, `bitsadmin` or `certutil` child. Removing Mark-of-the-Web means SmartScreen, the unverified-publisher prompt and every rule keyed on "MotW-marked file executed from a user-writable path" see a locally-created file. Launching via the shell over COM (for example `ShellExecute`-style activation through a shell COM object, not observed in detail in the report) means the new process is created by the shell or a COM surrogate, so its parent is `explorer.exe`, `dllhost.exe`, `sihost.exe` or `svchost.exe` rather than the browser, and the replaced `cmd.exe`/`curl` command line never exists. Process-lineage rules that look for a browser spawning a child see nothing.
  Removal method - not reported. Possible in-process routes include deleting the `:Zone.Identifier` stream directly or using the documented `IZoneIdentifier` interface (`IZoneIdentifier::Remove`, persisted with `IPersistFile::Save`), which is in-process COM, so the file system write is attributed to the calling (browser) process, not to the shell. Hunt the effect, the stream disappearing, rather than any one API.
  What MotW removal actually buys, and why it is worth a dedicated hunt - The `Zone.Identifier` stream is the input to a whole family of downstream controls: SmartScreen reputation prompts, Office Protected View and macro blocking, the "publisher could not be verified" execution warning, and a large number of detection rules that treat "file with MotW executed from a user-writable path" as their trigger. Strip the stream and the file is indistinguishable from one created locally.
  Sysmon leg (Event ID 15 then 23/26) — stream created, then deleted, then the file executed - Core filter: an Event ID 15 (`FileCreateStreamHash`) recording a `Zone.Identifier` stream on a file, followed within seconds by an Event ID 23 or 26 (`FileDelete` / `FileDeleteDetected`) whose `TargetFilename` ends in `:Zone.Identifier` for the same file, and then an Event ID 1 for that path. Triage fields: `TargetFilename`, `Image`, `Hashes`, `User`. Strong red flags: the deleting `Image` is a browser; the file is a PE in `%LOCALAPPDATA%`, `%TEMP%` or `%USERPROFILE%\Downloads`; and execution follows within seconds. Confirm your Sysmon configuration keeps `:Zone.Identifier` targets for Event IDs 15, 23 and 26 — many configurations filter them for volume.
  Sample KQL (Microsoft Sentinel, Sysmon via the `Event` table) — zone marking created then deleted on the same file:
  `Event | where TimeGenerated > ago(30d) | where Source == "Microsoft-Windows-Sysmon" and EventID in (15, 23, 26) | extend TargetFilename = extract(@"<Data Name=""TargetFilename"">([^<]*)<", 1, EventData), Image = extract(@"<Data Name=""Image"">([^<]*)<", 1, EventData) | where TargetFilename endswith ":Zone.Identifier" | extend baseFile = replace_string(TargetFilename, ":Zone.Identifier", "") | summarize created = minif(TimeGenerated, EventID == 15), removed = minif(TimeGenerated, EventID in (23, 26)), creators = make_set_if(Image, EventID == 15), removers = make_set_if(Image, EventID in (23, 26)) by Computer, baseFile | where isnotnull(created) and isnotnull(removed) and removed between (created .. (created + 5m)) | order by removed desc`
  Defender XDR leg — browser writes a PE, then the shell launches it within seconds - Core filter: a PE created or renamed into place by `chrome.exe` or `msedge.exe`, followed within 60 seconds by a process created from that exact path whose parent is a shell or COM host rather than the browser. Triage: `writerCmd` containing `--type=renderer` is a strong flag (normal downloads are written by the browser process, not a renderer); an empty `FileOriginUrl` on a browser-written PE is worth noting, since the origin is normally recorded from the zone marking. Strong red flags: the executed path is under `%LOCALAPPDATA%` rather than `Downloads`; a renderer crash or respawn immediately beforehand; and the executed binary then copying itself to a new path and registering a scheduled task.
  Sample KQL — browser-written PE executed within seconds by a shell or COM host:
  `let writes = DeviceFileEvents | where Timestamp > ago(30d) | where ActionType in ("FileCreated", "FileRenamed") | where InitiatingProcessFileName in~ ("chrome.exe", "msedge.exe") | where FileName endswith ".exe" or FileName endswith ".scr" or FileName endswith ".com" | project DeviceId, DeviceName, writeTime = Timestamp, FolderPath, SHA256, FileOriginUrl, writerCmd = InitiatingProcessCommandLine; let launches = DeviceProcessEvents | where Timestamp > ago(30d) | where InitiatingProcessFileName in~ ("explorer.exe", "dllhost.exe", "sihost.exe", "svchost.exe") | project DeviceId, execTime = Timestamp, FolderPath, ProcessCommandLine, parent = InitiatingProcessFileName, parentCmd = InitiatingProcessCommandLine, AccountName; writes | join kind=inner launches on DeviceId, FolderPath | where execTime between (writeTime .. (writeTime + 60s)) | extend fromRenderer = writerCmd has "--type=renderer", noOrigin = isempty(FileOriginUrl) | project writeTime, execTime, DeviceName, AccountName, FolderPath, SHA256, FileOriginUrl, noOrigin, fromRenderer, parent, parentCmd, ProcessCommandLine | order by execTime desc`

# H347

Volexity's September 21, 2026 report on UTA0565 documents a Chinese threat actor running Chrome and Windows zero-days from fake websites. A phishing email sent to Asian government entities linked to typosquatted news and think-tank domains — `thecovnresation[.]com` for The Conversation, `americanprgoress[.]top` for American Progress — whose landing pages rendered legitimate content while loading the exploit from a hidden, zero-sized iframe marked `aria-hidden`. Two Chrome zero-days were chained with a Windows privilege-escalation zero-day, and the payload, `chrome_cleanup.exe`, ended up installed as `%LOCALAPPDATA%\Microsoft\IME\MicrosoftIME.exe` under a scheduled task named `MicrosoftIME`.

One short passage in the report describes how the payload got from the exploit to a running process: "Download chrome_cleanup.exe in-process. Remove its Mark of the Web. Launch it via the Windows shell using COM, replacing the cmd.exe/curl command". Each of those three steps removes something defenders routinely rely on.

Windows tags files that arrive from the internet with a `Zone.Identifier` alternate data stream, and a surprising amount depends on it: SmartScreen reputation checks, Office Protected View and macro blocking, the unverified-publisher execution prompt — and a whole class of detection rules whose trigger is "a file carrying Mark-of-the-Web executed from a user-writable directory." Volexity does not say how the marking was removed, and it does not need to for this hunt: whatever the method, the stream is created and then disappears within seconds, and that is observable where ADS events are logged.

The launch step matters as much. Replacing a `cmd.exe`/`curl` command with a shell launch over COM means the payload's parent is the shell or a COM host rather than the browser, and there is no command line connecting the two. A detection looking for a browser spawning a child sees nothing. What remains is timing and provenance: a PE written by a browser process and, seconds later, executed from that same path by the shell.

## Why

- One step disables both a user-facing control and a detection assumption. Stripping `Zone.Identifier` suppresses SmartScreen and Protected View while blinding every rule whose trigger is "MotW-marked file executed from a user-writable path," so its impact is far larger than its footprint.
- The shell-over-COM launch deliberately breaks browser-parent lineage. Rules built around a browser spawning `cmd.exe`, `curl` or the payload directly see nothing, because the new process is created by `explorer.exe`, `dllhost.exe` or another shell or COM host — which is why this hunt joins on file path and time instead of parentage.
- The conjunction is narrow even though each part is common. Browsers write files, browsers sometimes delete zone streams, and the shell launches programs all day; a browser-written PE that loses its marking and is launched by the shell within seconds, with no user interaction, is rare enough to enumerate.
- This is post-exploitation telemetry for an intrusion whose initial access is unstoppable by design. Against chained Chrome and Windows zero-days there is no patch to have applied and no user decision to have made differently, so the file-system and process steps that follow are the realistic detection surface.
- Running the hunt audits the telemetry as well as the environment. Zone.Identifier streams are filtered out of many Sysmon configurations for volume, and SigmaHQ's own deletion rule excludes browsers, so a clean result is only meaningful once Event ID 15 and 23/26 coverage for `:Zone.Identifier` is confirmed.
