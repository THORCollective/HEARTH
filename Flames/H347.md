false_positive_notes: |
  Mark-of-the-Web removal is a legitimate operation with real benign volume, so this hunt lives or dies on lineage rather than on the removal itself. Archive utilities routinely do not propagate the stream when extracting (7-Zip historically did not, which is why it was a favoured delivery wrapper), and `Unblock-File`, the Explorer "Unblock" checkbox, and `streams.exe -d` are all sanctioned administrative actions. Build and deployment tooling strips the stream at scale by design — MSBuild, installers, software distribution agents, and CI workspaces all produce large volumes of internet-sourced files whose zone marking is legitimately removed. Developers unblock downloaded DLLs and scripts constantly. None of that resembles the pattern here. The discriminator is that the removal is performed by, or immediately downstream of, a *browser renderer process* on a file the renderer itself just wrote, with no user interaction in between — a browser has no legitimate reason to remove the zone marking from its own download, since applying it is precisely the browser's job. Scope the hunt to that lineage first: `chrome.exe`, `msedge.exe`, `firefox.exe` and their child processes as the actor, within a short window of the file create. Then treat the timing as a second filter: a legitimate unblock happens minutes to days later by a user or a tool, while an exploit chain does it within seconds and then executes the file. Expect near-zero hits on that conjunction; if you see steady volume, check whether a browser-hosted deployment or virtualization product in your estate performs downloads on the user's behalf and allowlist it explicitly.

Driven by Volexity, "Mind the (Patch) Gap, Part 2: Fake Websites Used to Deploy Chrome & Windows 0-Day Exploits" (September 21, 2026), attributed to the Chinese APT group UTA0565. The chain: spearphishing links to typosquatted news and think-tank domains whose landing pages loaded legitimate content in a visible frame and the exploit in a hidden iframe (`<iframe src="/config.html" style="display:none;visibility:hidden;width:0;height:0;border:0;overflow:hidden" tabindex="-1" aria-hidden="true" title="site-config">`); Chrome renderer exploitation via CVE-2026-85046 and CVE-2026-87491; a Windows privilege-escalation 0-day, CVE-2026-85880; in-process download and execution of `chrome_cleanup.exe`; and, as Volexity explicitly records, "Mark of the Web removal via Windows shell COM execution." Volexity published no detection queries; the queries below are derived from the reported chain.
  Why shell COM rather than deleting the stream - The obvious way to clear Mark-of-the-Web is to delete the `:Zone.Identifier` stream or overwrite it, and that is what most tooling does — which is why most detections watch for stream deletion. Going through shell COM (`IZoneIdentifier`, `IPersistFile`, or `IAttachmentExecute::SetClientGuid`/`Save`, reached via `CoCreateInstance` on the relevant shell classes) has the file system operation performed by the shell on the caller's behalf, inside the exploited process, using documented interfaces that thousands of legitimate applications also use. There is no `streams.exe`, no `Unblock-File`, no PowerShell, no `cmd` — nothing on a command line to key on. The resulting file system event may be attributed to the shell rather than to the malicious code, and no new process is created at all, so process-creation-centric detection sees the exploit chain as a single browser process doing browser things.
  What MotW removal actually buys, and why it is worth a dedicated hunt - The `Zone.Identifier` stream is the input to a whole family of downstream controls: SmartScreen reputation prompts, Office Protected View and macro blocking, the "publisher could not be verified" execution warning, and — importantly for hunters — a large number of detection rules that treat "file with MotW executed from a user-writable path" as their trigger. Strip the stream and the file is indistinguishable from one created locally. So this single step silently disables both a user-facing control and a detection assumption, which is why it is worth hunting as its own behaviour rather than as an attribute of the payload.
  Sysmon Event ID 15 then deletion — the core sequence - Core filter: an Event ID 15 (`FileCreateStreamHash`) recording a `Zone.Identifier` stream on a file, followed within a short window (seconds to a couple of minutes) by that stream disappearing — captured as Event ID 23/26 where your configuration logs alternate data streams, or inferred where the file is later executed with no zone marking present. Triage fields: `TargetFilename` (including the `:Zone.Identifier` suffix), `Image` of the creating process, `Hashes`, `User`. Strong red flags: the creating process is a browser renderer and the same or a child process performs the removal; the file is a PE in `%LOCALAPPDATA%`, `%TEMP%` or `%USERPROFILE%\Downloads`; and execution of that file follows within seconds. Confirm Sysmon is configured to log alternate data streams for Event IDs 23 and 26 — many configurations filter them out for volume, which removes the most direct leg of this hunt, so verify before concluding the environment is clean.
  Sample KQL — zone marking created then absent, with browser lineage:
  `let zoneCreated = DeviceFileEvents | where Timestamp > ago(30d) | where ActionType == "FileCreated" and FileName endswith ":Zone.Identifier" | extend baseFile = replace_string(FolderPath, ":Zone.Identifier", "") | project DeviceId, DeviceName, zoneTime = Timestamp, baseFile, creator = InitiatingProcessFileName; let zoneRemoved = DeviceFileEvents | where Timestamp > ago(30d) | where ActionType == "FileDeleted" and FileName endswith ":Zone.Identifier" | extend baseFile = replace_string(FolderPath, ":Zone.Identifier", "") | project DeviceId, removeTime = Timestamp, baseFile, remover = InitiatingProcessFileName, removerCmd = InitiatingProcessCommandLine; zoneCreated | join kind=inner zoneRemoved on DeviceId, baseFile | where removeTime between (zoneTime .. (zoneTime + 5m)) | where creator has_any ("chrome.exe", "msedge.exe", "firefox.exe", "iexplore.exe") | project zoneTime, removeTime, DeviceName, baseFile, creator, remover, removerCmd`
  Renderer-lineage leg (works even without ADS logging) - Core filter: a browser renderer process writing a PE to disk and a process being created from that path within the same minute, with no intervening user-initiated download dialog. Triage: compare against `DeviceEvents` `ActionType == "BrowserLaunchedToOpenFile"`, whose absence alongside a PE written by the renderer is itself the anomaly — a normal download is user-mediated and leaves that event. Strong red flags: `chrome.exe` or `msedge.exe` as the direct parent of a new PE in `%LOCALAPPDATA%`; a renderer process spawning any child at all beyond the expected utility and GPU processes; and a crashed-then-respawned renderer immediately beforehand, which is the usual artifact of an exploitation attempt. See [[H304]] for the adjacent case of a Chrome renderer spawning a command shell after a zero-day chain — run both, since the payload-write path and the shell-spawn path are separate detection opportunities on the same exploit.
  Follow-on artifacts from this specific campaign - `chrome_cleanup.exe` (893 KB, SHA256 `8858ea412dc306b3558885af18006c5ca24689e8875733b5e13b3c2692e603cb`) installed to `%LOCALAPPDATA%\Microsoft\IME\MicrosoftIME.exe` with a scheduled task named `MicrosoftIME`; HTTP-only C2 to `thecovnresation[.]com` with `POST /beacon/pre-register` and `Content-Type: application/octet-stream`; typosquatted delivery domains `chinadigitaltimes[.]top`, `americanprgoress[.]top`, `thecovnresation[.]com`, `thecovnresation[.]net`, `halal-navi[.]net`, `borneobulletins[.]top`, several hosted on `96.9.125[.]52`. Use these for retro-hunting and scoping, not as the hunt's anchor — the MotW-removal behaviour is what generalises.
  Hidden-iframe delivery leg - Core filter: proxy or web-gateway records where a page load is immediately followed by a request for a secondary HTML path (`/config.html`-style) from the same host with no user-visible navigation, particularly on a recently-registered domain that typosquats a news or policy site. Strong red flag: the same client fetching both a legitimate-looking article path and a short, generically-named HTML path within the same page load.

# H347

Volexity's September 21, 2026 report on UTA0565 documents a Chinese APT group running Chrome and Windows zero-days from fake websites. Targets in Asian government entities received spearphishing links to typosquatted news and think-tank domains — `thecovnresation[.]com` for The Conversation, `americanprgoress[.]top` for American Progress — whose landing pages rendered the real site's content while loading the exploit from a hidden iframe sized to zero pixels and marked `aria-hidden`. Two Chrome vulnerabilities got code execution in the renderer, a Windows privilege-escalation zero-day escaped the sandbox, and the chain downloaded and executed `chrome_cleanup.exe` in-process before installing it as `%LOCALAPPDATA%\Microsoft\IME\MicrosoftIME.exe` under a scheduled task named `MicrosoftIME`.

One line in that chain deserves separating out: Mark-of-the-Web removal via Windows shell COM.

Windows tags files that arrive from the internet with a `Zone.Identifier` alternate data stream, and a surprising amount depends on it. SmartScreen reputation checks, Office Protected View and macro blocking, the unverified-publisher execution prompt — and, for defenders, a whole class of detection rules whose trigger is "a file carrying Mark-of-the-Web executed from a user-writable directory." Remove the stream and a file downloaded moments ago becomes indistinguishable from one that has always been local.

Most tooling that clears the marking does so bluntly, by deleting or overwriting the stream, and most detections are written to catch exactly that. Doing it through shell COM instead means the exploited process asks documented Windows interfaces to update the zone information, and the shell performs the file system change. No new process is created. No command line exists. The file system event may be attributed to the shell rather than to the attacker's code. An exploit chain that never leaves the browser process has removed a user-facing security control and quietly invalidated a detection assumption, in one step, without giving process-creation monitoring anything to see.

## Why

- One step disables both a user-facing control and a detection assumption. Stripping `Zone.Identifier` suppresses SmartScreen and Protected View while simultaneously blinding every rule whose trigger is "MotW-marked file executed from a user-writable path," so its impact is far larger than its footprint.
- Shell COM specifically evades the common implementation of MotW-removal detection. Rules built around `Unblock-File`, `streams.exe -d`, or explicit stream deletion see nothing, because the removal is performed by the shell through documented interfaces on behalf of code running inside an already-legitimate process, with no new process and no command line.
- The browser-renderer lineage makes the conjunction nearly false-positive-free. Archive tools, `Unblock-File`, developers and deployment systems all legitimately remove the marking, but a browser has no reason to remove zone information from a file it just downloaded — applying that marking is the browser's own job — so scoping to renderer lineage inside a seconds-long window cuts the benign volume to essentially nothing.
- This is post-exploitation telemetry for an intrusion whose initial access is unstoppable by design. Against a Chrome renderer zero-day chained to a Windows privilege-escalation zero-day, there is no patch to have applied and no user decision to have made differently, so the file-system and persistence steps that follow are the only realistic detection surface.
- Running the hunt audits the telemetry as well as the environment. Alternate data streams are filtered out of many Sysmon configurations for volume reasons, so a clean result is only meaningful once Event ID 15 and Event ID 23/26 ADS logging is confirmed — and discovering that gap is itself a worthwhile outcome.
