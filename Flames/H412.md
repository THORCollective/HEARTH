hypothesis: >-
  An operator who wants a service to survive a reviewer's glance does not invent a service name, they borrow one. On a compromised host, an installer reads the list of service names registered under the netsvcs svchost group from the registry, picks one at random, and appends two random letters to produce a name that reads as a legitimate Windows service in any service listing. The service it registers does not point at a Microsoft-signed binary in its normal place: it points at a copy of a legitimate Windows executable that has been dropped into a newly created subdirectory of System32, with an attacker DLL beside it and a description of "Microsoft Service". Hunting for registered services whose name is an existing netsvcs entry extended by exactly two alphabetic characters, or whose ImagePath resolves to a System32 subdirectory that is not a standard Windows directory, finds this persistence at install time rather than after the loader has run.

false_positive_notes: |
  Legitimate software does create services from subdirectories of System32. Driver and management agents from hardware vendors are the usual case. Build the allowlist from the directory name and the signer of the ImagePath binary, not from the service name, because the service name is the field the adversary controls.
  Two-letter suffixes occur naturally. Service names such as `WinHttpAutoProxySvc` or vendor names ending in two letters will match a naive suffix rule. The discriminator is that the name with the last two characters removed must match an entry in the netsvcs list exactly, and the resulting service must not itself be a real svchost-hosted service (a genuine netsvcs service has an ImagePath of `%SystemRoot%\system32\svchost.exe -k netsvcs` and a ServiceDll under its Parameters subkey; this one has a direct ImagePath to an EXE).
  Microsoft-signed binaries in unusual places are expected during servicing. Windows Update and component servicing stage signed binaries under `C:\Windows\WinSxS`, `C:\Windows\SoftwareDistribution` and `C:\Windows\servicing`. Exclude those trees and keep newly created directories directly under `System32`.
  A file copy of a legitimate binary keeps its valid Microsoft signature, so signature state alone will not clear it. Treat the combination of a Microsoft-signed EXE at a non-Microsoft path plus a non-Microsoft DLL in the same directory as the finding.
notes: |
  Service installation (4697 / 7045) - Core filter: new service where `ImagePath` matches `C:\Windows\System32\<dir>\*.exe` with `<dir>` not in the standard System32 directory set, or where the service name minus its last two characters equals an entry in the netsvcs `REG_MULTI_SZ` value. Triage values: `ServiceName`, `ImagePath`, `ServiceType`, `StartType`, `AccountName`, and the service description. Kaspersky recorded the description `Microsoft Service` and the command line `C:\Windows\System32\RasConv\ImeBroker.exe -TimeBroker`, where `ImeBroker.exe` was a copy of `C:\Windows\System32\printfilterpipelinesvc.exe`. 4697 carries the account that installed the service, which 7045 does not; prefer 4697 where Audit Security System Extension is enabled.
  Resolving the netsvcs list - Read `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Svchost` value `netsvcs` on a representative build and hold it as a lookup. The report says the installer collects "up to 100 legitimate service names" from this group, "randomly selects one of these names, appends two random alphabetic characters to form a new service name". So the hunt is a string operation against that list, not a static IOC list: strip two trailing alphabetic characters from each observed service name and test for an exact match.
  Defender XDR - new service via registry (30-day retention):
  ```kql
  let netsvcs = dynamic(["AeLookupSvc","CertPropSvc","gpsvc","IKEEXT","iphlpsvc","PolicyAgent","ProfSvc","SCPolicySvc","SENS","SessionEnv","ShellHWDetection","Themes","TrkWks","Winmgmt","wuauserv","BITS","lanmanserver","Schedule"]);
  DeviceRegistryEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("RegistryValueSet","RegistryKeyCreated")
  | where RegistryKey startswith @"HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\"
  | extend SvcName = tostring(split(substring(RegistryKey, strlen(@"HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\")), @"\")[0])
  | where strlen(SvcName) > 2
  | extend Stem = substring(SvcName, 0, strlen(SvcName) - 2), Suffix = substring(SvcName, strlen(SvcName) - 2, 2)
  | where Suffix matches regex @"^[A-Za-z]{2}$" and Stem in~ (netsvcs) and SvcName !in~ (netsvcs)
  | project Timestamp, DeviceName, SvcName, Stem, RegistryKey, RegistryValueName, RegistryValueData, InitiatingProcessFileName, InitiatingProcessCommandLine
  ```
  Replace the `netsvcs` literal with the list read from your own build; the hardcoded set above is a representative subset, not the whole group.
  Defender XDR - binary and DLL staged into a System32 subdirectory:
  ```kql
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where ActionType == "FileCreated"
  | where FolderPath matches regex @"(?i)^C:\\Windows\\System32\\[^\\]+\\$"
  | where FolderPath !has "WinSxS" and FolderPath !has "DriverStore" and FolderPath !has "catroot"
  | summarize Files = make_set(FileName, 50), Writers = make_set(InitiatingProcessFileName, 20), FirstSeen = min(Timestamp) by DeviceName, FolderPath
  | where array_length(Files) >= 2
  ```
  Kaspersky lists `mscoree.dll` and `ActivationStore.dat` as the two files written beside the copied EXE, and the paths `C:\Windows\System32\RasConv\` and `C:\Windows\System32\DrvConh\`. Both directory names are plausible-looking but are not Windows directories.
  Process execution - Core filter: `DeviceProcessEvents` or Sysmon 1 where the process image sits under a System32 subdirectory and the parent is `services.exe`. A service-launched process parented by `services.exe` running from a non-standard directory is the execution half of the same event. Pivot on the `-TimeBroker` style switch: a copied binary is usually invoked with an argument the original never takes, because the argument is the loader's key material.
  Image load - `DeviceImageLoadEvents` or Sysmon 7 where `FileName == "mscoree.dll"` and the folder path is not under `C:\Windows\Microsoft.NET\` or `C:\Windows\System32\`. `DeviceImageLoadEvents` has no signature columns, so join `DeviceFileCertificateInfo` on `SHA1` if signer state is needed. A side-loaded runtime shim is materially larger than the genuine file on the same build and exports a function the real shim does not, which makes a single candidate file quick to resolve. See [[H124]] for the broader side-loading hunt this feeds.
  Scoping - Once one host is confirmed, sweep the estate for the directory name and for services whose stem matches the netsvcs list. The directory name is per-intrusion, not per-sample, so it makes a good short-lived pivot.

# H412

Kaspersky's Operation FlashHole report, published October 2026, describes a Lazarus Group intrusion set against South Korean targets in which a previously unknown installer they named TouchHub establishes the persistence for the rest of the chain. Its method is worth hunting on its own because every step is an ordinary Windows administrative action performed with an unusual choice of names.

TouchHub "copies the legitimate `printfilterpipelinesvc.exe` to `C:\Windows\System32\RasConv\ImeBroker.exe`, registers it as a service, and places an embedded TouchShift payload named `mscoree.dll` in the same directory". The service name is not hardcoded. The installer reads the service names registered under the netsvcs svchost group from `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Svchost`, then "randomly selects one of these names, appends two random alphabetic characters to form a new service name", and registers it with the description `Microsoft Service` running `C:\Windows\System32\RasConv\ImeBroker.exe -TimeBroker`. The report notes the resulting service launches TouchShift with SYSTEM privileges, and that TouchHub also writes `ActivationStore.dat` as the configuration file for the next stage.

That name-generation step is what makes this findable at scale. A hardcoded malicious service name is an IOC that dies with the sample. A name derived from the victim's own netsvcs list is a *relationship* between two registry values, and it holds across samples and across intrusions: the service name will always be an existing netsvcs entry plus two letters, and it will never be a real svchost-hosted service. The same applies to the file layout. Copying a Microsoft-signed binary preserves its signature, so the signature tells you nothing, but the path does: a new directory directly under `System32` holding a signed Microsoft EXE and an unsigned DLL is not something Windows servicing produces.

## Why

- The persistence is the narrowest point in this chain. Kaspersky describes everything downstream of this service as running in memory, with "only minimal traces of these files were found on disk" — the service registration and the three files TouchHub writes are the durable, on-disk evidence.
- The detection is a derived relationship rather than a static indicator. Stripping two alphabetic characters and testing against the netsvcs list generalises to any sample using this routine, and it does not decay when the actor rotates directory names, service names or binary names.
- Every artefact lands in telemetry that is already collected for other reasons: service installation is audited in the Security and System logs, the registry writes appear in Sysmon 12/13 and `DeviceRegistryEvents`, and the file writes appear in Sysmon 11 and `DeviceFileEvents`. No new sensor is required.
- Volume is low. New service installations on a managed endpoint are rare events outside of software deployment windows, and new directories directly under `System32` are rarer still, so the combination is a short triage queue rather than a scored alert.
