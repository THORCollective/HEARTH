false_positive_notes: |
  Legitimate SAML configuration and troubleshooting does involve PEM files. The distinguishing facts are where they are and what they are called together. A vCenter administrator replacing a signing certificate works through the vSphere Client or the certificate-manager utility against the appliance's own certificate store, not by writing a loose `idp_key.pem` beside a `domain.txt` in a temporary directory on a different host. An export directory holding exactly those three filenames is the tool's documented output, not an administrative byproduct.

  Penetration tests and red-team exercises use the public Python vCenter SAML login tool and will produce very similar artefacts. Reconcile against authorised-testing records before escalating; a matching hit during an unannounced window is the finding.

  Backup software holds copies of `data.mdb`. It stores them in a backup repository under a backup service account, not in an operator-chosen export directory on an appliance, and it does not parse the database for signing keys or write them out as PEM.

  The sequencing claim in this hunt - that the forged assertion arrives with no preceding primary authentication and no MFA challenge - is the expected consequence of offline assertion signing rather than something Mandiant timestamps. Mandiant states that SAWSNAKE forges and signs SAML assertions for the Administrator account and authenticates to obtain administrative session cookies, and that this allows MFA bypass and impersonation. Confirm the absence of a matching authentication event in your own SSO audit trail rather than assuming it.

  Mandiant identified a second, likely updated SAWSNAKE sample that added verbose debug logging across TLS, HTTP, SAML initiation, XML signing and login routines, and expanded redirect handling for up to ten HTTP 302 redirects to support multi-hop authentication. A detection that depends on a single-hop login flow may miss that variant; follow redirect chains when reconstructing the session.

  Because the actor deletes the tool and its output, a clean filesystem is not evidence of absence. Treat the file-creation events, the remote syslog record and the web access log as the primary sources and the disk as the least reliable of the three.
notes: |
  File-artefact leg (auditd file writes, Linux EDR, DeviceFileEvents where a sensor exists) - Core filter: creation of a file named `idp_key.pem`, `trusted_cert_2.pem` or `domain.txt` anywhere on an appliance or management host, and in particular any directory that gains two or three of them within the same minute. Mandiant lists those three names as the files SAWSNAKE creates. Also filter on the BONESAW-stage artefacts this leg usually follows - a directory whose name begins `extracted_tenant_signer_`, a copied database whose filename begins `anon_` and ends `_data.mdb`, and paired `.key.pem` and `.key.der` files alongside `.leaf.pem`, `.chain.pem` and `.context.json`. Triage values are `file path`, `file name`, `size`, `creating process path and full command line`, `effective UID`, `creation time` and `deletion time` where a later unlink is recorded.

  An auditd rule set to capture the writes and the follow-up deletion, installed ahead of the hunt:

      auditctl -w /tmp -p wa -k saml_export_artifacts
      auditctl -a always,exit -F arch=b64 -S unlink,unlinkat -F dir=/tmp -k tmp_cleanup

  Process leg - Core filter: any binary invoked with an argument ending `data.mdb`, or with flag patterns matching the tool's documented interface - a path flag for the database, a target flag for the vCenter address, a key flag for an IdP private key PEM, repeatable certificate flags, and an export-directory flag that writes the PEM files and exits. Mandiant records the staged copy at `/tmp/sss`, but the filename is incidental; the argument shape is the durable part. Strong red flags: an ELF binary in `/tmp` executed within minutes of a `data.mdb` appearing on the same host; the same process then opening an outbound TLS session to a vCenter address; `rm` removing both the binary and its export directory shortly afterwards.

  Where YARA can be run over staged files or memory, Mandiant publishes a hunting rule for the utility that keys on its Go source-path strings - `saml_login/mdb.go`, `saml_login/saml.go` and `saml_login/c14n.go` - and on operational strings including the SAML web single sign-on URL template `https://%s/ui/saml/websso/sso` and a success message confirming Administrator cookies were obtained. That rule is the fastest way to confirm a suspect ELF without reversing it.

  Network and session leg (vCenter web access logs, SSO audit events) - Core filter: requests to a URI path under `/ui/saml/websso/` that result in a session for an administrative principal, where the source address is not in the approved-management register. Correlate each such session against the SSO primary-authentication record for the same principal within a tight window - a join on principal alone over a long lookback will pair unrelated logins, so bound it, for example to the two minutes before the assertion was consumed. A session with an assertion but no primary authentication in that window is the Golden SAML signature. Triage values are `source IP`, `URI path`, `HTTP method`, `status code`, `user agent`, `principal`, `session identifier`, `assertion identifier` and `issuer`. Strong red flags: the assertion's issuer is the appliance's own STS but the signing event has no corresponding activity on the appliance; a chain of 302 redirects ending in an administrative session; the source address is the same internal appliance seen in H493's port-2012 leg.

  Pre-emptive controls that produce the telemetry - Mandiant's hardening guidance for this campaign notes that an inbound DROP policy on TCP 443 to the vSphere Web Client and API from untrusted sources means that even if the signing key is extracted over port 2012, the forged administrative cookies cannot be used from the compromised appliance, because it is not in the trusted-web allowlist. Enforcing that at the kernel level with `iptables` rather than through the VAMI interface also means the dropped attempts are logged and forwardable, which turns this leg from an absence of evidence into an event.

  Containment note: rotating the compromised credential here is not a password reset. The stolen material is the identity provider's signing key and trusted certificates for the SSO domain, so every assertion that key can sign remains valid until the STS signing credential is replaced and the old certificate distrusted. Treat key rotation, not account disablement, as the remediation, and expect to revoke existing sessions.

  Scope note: H223 covers the same attack class on a different platform and with different telemetry - active AD FS token-signing key theft from the machine DPAPI MachineKeys store, producing federated Entra ID sign-ins with no correlating AD FS primary-authentication event. This hunt is the vCenter STS equivalent, where the key is parsed out of a stolen LMDB directory file on a Photon Linux appliance and the artefacts are named PEM files rather than DPAPI blobs. H493 covers the step that supplies the database, and B070 holds the management-plane register this hunt's source filter depends on.

# H494

Mandiant and Google Threat Intelligence Group's November 19, 2026 analysis of ARMORY CASTLE describes a two-utility chain against VMware vCenter. BONESAW exploits CVE-2026-123890 to pull the vmdir database off the appliance. SAWSNAKE, deployed minutes later and staged at `/tmp/sss`, turns that database into a working identity: it extracts the identity provider signing key and trusted certificates, exports them as PEM files, forges and signs a SAML 2.0 assertion for the Administrator account, and authenticates to the target vCenter to obtain administrative session cookies.

This is a Golden SAML attack against the virtualisation control plane rather than against a cloud identity provider, and the consequence is the same: Mandiant notes it lets the actor forge authentication tokens, bypass MFA, and impersonate any user. Mandiant identified a second, likely updated sample with verbose debug logging and support for up to ten HTTP 302 redirects, which suggests the tool was being maintained against real environments rather than used once.

The artefact set is unusually clean. In extract mode the utility writes three specific files — `idp_key.pem`, `trusted_cert_2.pem` and `domain.txt` — and the actor then deletes the tool and its output with `rm`. That deletion is what makes the file-creation events, rather than the files themselves, the thing worth hunting.

## Why

- The three output filenames appearing together have no benign reading. A private key, a trusted certificate and a plain text file naming an SSO domain, co-located in a temporary directory on an appliance, are precisely the inputs required to sign an assertion offline, and no vCenter process or administrative workflow produces that trio in that place.
- The attack defeats the controls most organisations rely on for the management plane. Once the signing key is held, MFA and password policy are irrelevant, because the appliance is being shown a correctly signed assertion rather than a credential. The detection has to look for a session without an authentication, not for a failed or anomalous login.
- The actor cleans up, and Mandiant says so explicitly — consistent with earlier activity, SAWSNAKE and its output files were deleted from disk using `rm`. Any hunt that depends on finding the files at rest will come back empty on a real intrusion. File-write auditing and remote syslog forwarding are the collection prerequisites, which is why both are listed as required rather than optional.
- Remediation is different from the usual answer, and getting it wrong leaves the actor in place. Disabling the created accounts does not invalidate anything the stolen signing key can sign. The STS signing credential has to be rotated and the previous certificate distrusted, and existing sessions revoked.
