# H280

The rootkit that ships with the SPECTRE implant does not hide by being clever about one thing; it hides
by being unremarkable about several. It is named `acpi_pad.ko`, which is a real Linux kernel module, so
a name-based check waves it through. It persists as `hardware-monitor.service` described as "Hardware
Performance Monitor," which reads like something a hardware vendor would install. And it hooks kernel
functions through ftrace with `FTRACE_OPS_FL_IPMODIFY` rather than patching the syscall table, which
means the classic integrity check — compare the syscall table against a known-good copy — comes back
clean.

The ordering is the detail worth dwelling on. The systemd unit specifies `Before=sysinit.target`, so the
rootkit initializes before basic system initialization completes, which in practice means before the
security tooling that might have observed it. By the time an EDR agent's kernel component starts asking
questions, the thing answering them is already compromised.

Its control channel is unusual enough to be a detection opportunity in its own right. There is no socket
and no file — userland talks to the kernel component by sending real-time signals to a magic PID,
`0x7A69` (31337). Signal 62 unlinks a target `task_struct` from the PID list so `/proc/<pid>`
disappears; signal 36 unlinks `THIS_MODULE` from the module list so `lsmod` goes blind; signal 37
overwrites the calling process's credentials to UID 0; signal 35 is a load acknowledgement.

Self-hiding is also where it becomes catchable. Unlinking from the module list defeats `lsmod` and
`/proc/modules`, but the kernel still holds a `/sys/module/` directory for the module. The cross-view
diff is the standard answer and it works here.

## Why

- **Module loading is a narrow, high-signal syscall boundary that most Linux estates never watch.** A
  server loads kernel modules at boot and then, in a healthy environment, essentially never again. An
  `init_module`/`finit_module` call at 3am parented by a web application or a post-exploitation implant
  is close to a standalone verdict. The auditd rule is two lines and the volume is negligible — this is
  among the best effort-to-yield ratios available on Linux.
- **Self-hiding is imperfect and the residue is the detection.** Unlinking `THIS_MODULE` from the module
  list is what defeats `lsmod`, but the kernel still maintains `/sys/module/<name>/`. Comparing the two
  views catches every rootkit that uses this standard trick, including ones that have nothing else in
  common with SPECTRE. The same logic applies to ftrace: `touched_functions` retains evidence of hooked
  functions even after the hook is removed, so the artifact outlives the attacker's cleanup.
- **Ftrace hooking defeats the integrity check most teams actually run.** Syscall-table comparison is the
  textbook LKM rootkit detection and it returns clean here by design. Teams who believe they cover
  kernel-level persistence because they check the syscall table have a gap precisely where the modern
  technique lives — ftrace-based hooking is now the dominant approach, used by PUMAKIT and others.
- **`Before=sysinit.target` is a genuinely rare and semantically loud property.** Very little legitimate
  software needs to start before basic system initialization. Grepping every unit file in the estate for
  that ordering directive is a one-off sweep that produces a short, reviewable list, and anything on it
  that is not core OS or a known early-boot dependency deserves an explanation.
- **Once the rootkit is resident, the telemetry this hunt depends on is the telemetry it suppresses.**
  Process hiding via `task_struct` unlinking means `/proc/<pid>` vanishes for the attacker's processes;
  agents that enumerate `/proc` will simply not see them. Detection latency here is not a matter of
  degrees — it decides whether you are investigating a module load or negotiating with a host that is
  lying to you.
- **HEARTH had no T1547.006 and no T1014 coverage at all**, despite Linux kernel rootkits appearing in
  targeted intrusions with increasing regularity and this particular one being deployed alongside a
  cross-platform implant with BYOVD capability on the Windows side.
