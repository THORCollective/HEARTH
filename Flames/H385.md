  `IdentityLogonEvents | where Timestamp > ago(30d) | where Protocol == "Ldap" | where DeviceName has "ics" or IPAddress in ("10.10.20.5") | summarize Binds = count(), Targets = dcount(DestinationDeviceName), First = min(Timestamp), Last = max(Timestamp) by AccountUpn, IPAddress, DestinationDeviceName | order by Binds desc`
  Sample KQL - directory queries recorded by Defender for Identity, projecting the query string so the
  attribute names requested are visible.
  `IdentityDirectoryEvents | where Timestamp > ago(30d) | where ActionType in ("LDAP query", "Directory Services replication") | where AdditionalFields has_any ("ms-Mcs-AdmPwd", "msLAPS-Password", "msLAPS-EncryptedPassword", "msFVE-RecoveryPassword", "msFVE-KeyPackage", "userPassword", "unixUserPassword", "scriptPath") | project Timestamp, AccountUpn, IPAddress, DeviceName, DestinationDeviceName, ActionType, AdditionalFields | order by Timestamp asc`

  only fires for searches the DC considers expensive or inefficient, so treat an empty result as a
  collection problem rather than an answer.

  Sample Splunk SPL over event 4662, for estates that have put SACLs on the secret-bearing attributes.
  The attribute is identified by schema GUID in this event, so the lookup below assumes a GUID-to-name
  lookup table has been populated - without the SACL and the lookup, this query cannot work.
  `index=wineventlog EventCode=4662 Object_Type="*" | lookup ad_schema_guids guid AS Properties OUTPUT attribute_name | search attribute_name IN ("ms-Mcs-AdmPwd","msLAPS-Password","msFVE-RecoveryPassword") | stats count BY Account_Name, Client_Address, attribute_name | sort - count`

  1644 needs the Field Engineering diagnostic level and the 15 LDAP Interface Events setting raised.
  Event 4662 needs an audit ACL on the specific attributes - a read of `ms-Mcs-AdmPwd` with no SACL
  generates nothing at all. Defender for Identity needs a sensor on the domain controller. If none of
  these are in place, the honest first output of this hunt is a collection gap, not a clean result.
  Remediation note worth carrying to the asset owner. The appliance account in the reported case could
  read LAPS passwords and BitLocker keys because the directory let it. The durable fix is scoping that
  account's read rights to what VPN authentication actually needs, which is a question this hunt answers
  as a by-product.

  not LAPS or BitLocker attributes). [[B061]] is the baseline this hunt depends on, and [[M025]] covers the

# H385

The appliance had a domain account because it needed one. That is how a VPN checks whether you are a real user with a real password.

The account could also read LAPS passwords and BitLocker recovery keys, because nobody had scoped it, and nothing in Active Directory stops an account from asking for attributes it has rights to read. UTA0576 wrote a custom LDAPv3 tool to `/tmp/ml.py`, bound to a domain controller as the appliance's own service account, and asked for exactly the things worth having: LAPS local administrator credentials, BitLocker recovery information, `userPassword` and `unixUserPassword` values, logon script paths. The answers came back as zlib-compressed, Base64-encoded JSON in `/tmp/`, and left through the exploit channel.

This is the leg of the intrusion worth building a hunt on, and the reason is about where the evidence lives rather than about which step was cleverest.

The appliance side of this intrusion is nearly unhuntable with ordinary telemetry. The exploit chain patched a library in memory, restored the configuration store afterwards, and left Ivanti's Integrity Checker Tool reporting a clean device. The operator then truncated the ICS debug log and the Linux audit log. There is no EDR agent on the box. Volexity needed memory images and core dumps.

The directory hop is the opposite. It lands in domain controller logs, in Defender for Identity, in LDAP bind records — telemetry that is centrally collected, retained for months, and sits on a machine the attacker had not compromised. They could edit the appliance's logs. They could not edit the DC's.

So the question becomes small: which accounts ask a domain controller for stored secrets, and do any of them live on an appliance?

A directory-integration account has a narrow and repetitive job. It looks up users, checks group membership, validates a bind. It does not ask for `ms-Mcs-AdmPwd`. When it does, either someone repurposed the account for helpdesk automation — worth knowing on its own terms — or something else is using it.

One honest caveat about collection, because all three query paths here fail quietly. Event 1644 only records searches the DC judges expensive or inefficient, so a well-aimed query against an indexed attribute may simply never appear. Event 4662 needs a SACL on the specific attribute, and without one a LAPS password read generates no event whatsoever. Defender for Identity needs a sensor on the DC. Run this hunt and get nothing, and the first thing to establish is which of those three was actually collecting.

The spray that came next — `sp_run.py`, `sp_out.txt`, `spray_hits.json` — belongs to [[M025]] rather than here. And `mk.py`, the Python Kerberos implementation, contained Kerberoast functionality that the report says the operator's script did not use; capability present, not exercised.

## Why

- **The second hop lands in telemetry the attacker could not reach.** The appliance was log-tampered and agentless; the domain controller was neither. Hunting the LDAP query instead of the exploit moves the detection onto ground the operator did not control.
- **The attributes requested are specific, nameable, and rarely queried.** `ms-Mcs-AdmPwd`, `msLAPS-Password`, `msFVE-RecoveryPassword`, `userPassword`, `unixUserPassword`, `scriptPath` — a short list that turns a vague question about enumeration into a string match.
- **The source and the account together are the discriminator.** Helpdesk tools and PAM platforms read LAPS legitimately, but they do not run on a VPN appliance under its directory-integration account.
- **These attributes are the keys to the next stage, not just data.** LAPS gives local administrator access to workstations; BitLocker recovery keys unlock disks. Volexity assesses the activity "signaled preparation for lateral movement and a broader compromise of the victim network".
- **The appliance account's rights are usually far wider than its function.** It needs to validate authentications. It was able to read stored secrets for the whole domain, which makes this hunt double as a least-privilege audit.
- **Exfiltration rode the exploit channel, so network C2 detection would not have caught it.** No backdoor and no separate C2 connection — results were returned inside the HTTPS requests that carried the commands. The directory query is the observable, not the egress.
- **The collection prerequisites are themselves a finding.** 1644 needs diagnostic levels raised, 4662 needs attribute SACLs, Defender for Identity needs a sensor. Discovering which are missing is a real outcome of running this.
- **Volexity names the behaviour as cross-actor, not one-off.** The same report notes a different actor, UTA0533, using an analogous credential-harvesting approach against SonicWall SMA appliances after zero-day root access, which suggests the appliance-to-directory pivot is a pattern rather than a quirk.
