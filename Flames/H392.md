title: A service principal that promotes itself — an application, not a person, appearing in the actor field of an Entra directory-role assignment
hypothesis: >-
  When a vendor's application credential is stolen, the attacker does not need to phish anyone. They
  authenticate as the application and inherit every permission it already holds, and if those permissions
  include the ability to assign directory roles, the application can promote itself. Huntress observed
  exactly this during the October 2026 ConnectWise Cloud Backup incident: in roughly 50 tenants,
  "service principals for ConnectWise's Cloud Management apps (Exchange Online, Microsoft Teams, and
  Microsoft Graph) assigned themselves directory roles, mostly Exchange Administrator", and in one tenant
  the Microsoft Teams application "added itself to the Global Administrator role". The observable is a
  role-assignment audit record whose INITIATING actor is a service principal rather than a user, and
  whose target is that same service principal. Hunt Entra audit records for `Add member to role` where
  the initiator is an application and no human is in the loop.

false_positive_notes: |
  Applications do legitimately hold directory roles, and some privileged access management and identity
  governance tooling assigns roles programmatically as its core function — so the finding is not
  "an application assigned a role". Three narrowings make this hunt operational.
  First, scope to SELF-assignment: the initiating service principal and the target principal are the
  same object. Governance tooling assigns roles to other principals, usually to users; an application
  granting a role to itself is a materially different shape and is rare in most tenants.
  Second, weight toward the high-impact roles. Huntress names Exchange Administrator as the role most
  commonly taken, with Global Administrator in one tenant. Global Administrator, Privileged
  Authentication Administrator, Application Administrator and Cloud Application Administrator all let the
  holder create further access, so a self-assignment of any of them deserves investigation regardless of
  which application did it.
  Third, remember what the log does not hold. Huntress is explicit that for app-only actions the Entra
  audit log "carries no source IP, and it does not record the details of the credential that was added or
  what an application read through Microsoft Graph". So the audit record will tell you that a role was
  taken and by which application, but not from where. Correlating to a source address means pivoting to
  the service principal sign-in log, which is a separate tab in the Entra admin center and is not shown by
  the default user sign-in view.
  Expect legitimate noise from tenants that recently onboarded a backup, migration, eDiscovery or
  security product, since consent and setup flows can produce role grants in a burst. The distinction is
  that onboarding is accompanied by a user-initiated consent record and happens once; this activity has no
  user anywhere in the chain and recurs across tenants.
  Note also that a clean result does not mean the tenant is unaffected. Huntress advises acting
  regardless, because a tenant can hold stolen tokens without any role change having occurred.

# H392

An application gave itself Global Administrator, and no human was involved at any point.

That is the whole finding, and it is worth sitting with for a second, because it inverts how most tenants think about privilege escalation. There is no phished user, no stolen session cookie, no MFA fatigue. A backup vendor's credential leaked, somebody authenticated as the application, and the application already had enough permission to promote itself.

Huntress saw it in roughly 50 tenants from 01:58 UTC on 15 October 2026: ConnectWise Cloud Management service principals "assigned themselves directory roles, mostly Exchange Administrator". In one tenant it went further — the Microsoft Teams application added itself to Global Administrator at 03:44, again at 03:48, and had modified two other applications by 03:49. Five minutes, start to finish.

What makes this hunt clean is that the discriminator sits in a single field.

Entra's audit log records who initiated each change. For a role assignment made by a person, that field holds a user. For these, it held an application. The query is not "did a role get assigned" — roles get assigned constantly — it is "was the thing that assigned the role an application, and was the thing that received it the same application". Self-assignment by a non-human actor is rare in almost any tenant, and it is trivially expressible as a filter.

Two caveats that decide whether you get a usable answer.

The audit log will not tell you where the action came from. Huntress is explicit: for app-only actions the log "carries no source IP, and it does not record the details of the credential that was added or what an application read through Microsoft Graph". You get the acting application and the target. To get an address you have to pivot to the service principal sign-in log, which lives on a different tab in the Entra admin center and is not what the default view shows you.

And attribution of this particular phase is genuinely unresolved. The role assignments carried the `kiota-dotnet` user agent, which is what ConnectWise's own applications use — Huntress says it "points to vendor automation, but we have not confirmed that with ConnectWise." The role changes also preceded the known-attacker sign-ins by about two and a half hours, with no source address available for the earlier activity. Huntress has not tied the two phases to the same operator, and neither should you. Hunt the behaviour; the indicator may belong to someone else.

The reason to care even if your tenant looks clean: app-only access does not behave like user access. No user, no device, no MFA prompt. Conditional Access policies written for people do not touch it, password resets do not revoke it, and a role taken this way outlives the rotation of the credential that took it.

## Why

- **The actor field is the detection.** A directory role assigned by an application rather than a person is a narrow, queryable shape that does not require knowing the vendor, the application or the attacker in advance.
- **Self-assignment narrows it further.** Governance and PIM tooling assigns roles to other principals; an application granting a role to itself is a different shape, and it is rare enough in most tenants to review by hand.
- **App-only access escapes the controls built for users.** No user, no device, no MFA prompt — so Conditional Access, password resets and MFA enrolment all fail to constrain it.
- **The role outlives the credential.** Rotating the vendor's stolen secret does not remove a role the application granted itself, which is why Huntress treats credential rotation as necessary but not sufficient.
- **It is the hinge of the whole intrusion chain.** Global Administrator is what made the next step possible; the credentials grafted onto two other applications minutes later are hunted in [[H393]].
- **The blast radius is every tenant the application is consented in.** A client assertion lives in the vendor's tenant, so no customer action produced it and no customer action alone contains it.
- **It is quiet by construction.** Directory reads through Graph leave no audit trail at all, so a tenant can be fully accessed with only the role change to show for it.
- **MSP environments compound it.** Management applications are consented across many customer tenants, so one foothold becomes a path outward — the reason Huntress asks partners to review their management and security tooling first.
