false_positive_notes: |
  Windows marks several of its own processes critical as designed, and that set changes between builds. `wininit.exe`, `csrss.exe`, `services.exe`, `smss.exe` and `lsass.exe` are the usual members, with variation by Windows version and configuration. The hunt is only meaningful against an enumerated per-build baseline; without one, every legitimate critical process reads as a finding.

  `CRITICAL_PROCESS_DIED` has mundane causes and is not by itself evidence of this technique. Failing storage, bad memory, driver faults, aggressive third-party security software terminating a system process, and corrupted system files all produce the same stop code. The report's technique is one explanation among several, and the discriminator is which process died, not the stop code.

  Some legitimate security and availability software marks its own processes critical or otherwise resists termination, as an anti-tamper feature. Several EDR agents, anti-cheat drivers and high-availability agents behave this way deliberately. Enumerate the estate's own tooling and exclude by signer and image path before treating a non-Microsoft critical process as hostile.

  `SeDebugPrivilege` is held and used legitimately by a great deal of software. Debuggers, profilers, crash handlers, backup agents and most EDR products enable it routinely, and it is granted to administrators by default. On its own it is background noise; its value here is as a corroborating event close in time to a process that subsequently appears critical.

  There is no standard Windows event that fires when `ProcessBreakOnTermination` is set. The call is a direct native API invocation, which Talos notes bypasses the documented Win32 API layer entirely, so it leaves no audit record. This means the flag has to be observed as live process state rather than caught as an event, and a historical hunt over existing logs will not find the moment it was set. Absence of evidence here is close to meaningless.

  Talos does not state why the RAT acquires `SeDebugPrivilege` specifically, only that it does so before the native call. Setting the critical flag on the caller's own process does not obviously require it, so the privilege may serve other functions in the implant - the report does not say, and this hunt does not assume a causal link beyond the sequence as reported.

  Leg one, enumerate the critical flag as live state. This is the only direct observation of the technique, and it requires a live sweep rather than a log query, because setting the flag generates no event. For each running process, read the `ProcessBreakOnTermination` information class and compare the resulting set against a per-build baseline of processes Windows legitimately marks critical. Any member of the set that is not in the baseline, not signed by Microsoft, and not an enumerated security agent is the finding. Practically this means an endpoint agent query, a WMI or PowerShell sweep driving the native call, or a live-response script run across the estate - pick whichever your tooling supports and schedule it, since the flag only exists while the process does.

  Triage the output on three axes. Image path - a critical process running from `AppData`, `ProgramData` or a temporary directory has no legitimate reading. Signer - unsigned, or signed by an unexpected authority. Parent and age - a critical process created recently by a user-context parent, rather than by `wininit.exe` or `services.exe` at boot.

  Leg two, the bugcheck as retrospective evidence. Where this technique has already been triggered, the host crashed. Pull Windows System event log Event ID 1001 from the `BugCheck` source and Event ID 41 from `Kernel-Power`, and correlate stop code `CRITICAL_PROCESS_DIED`, bugcheck `0x000000EF`, against the host's own history. The question that separates this from hardware trouble is which process the dump names as the dying one. Open the memory dump and identify it - a core Windows process points at instability; a randomly-named binary from a user profile points at an implant that was killed. Worth noting the asymmetry for responders: every attempt to kill this process produces exactly one crash and one dump, and that dump contains the implant's own memory. The anti-removal control is also a forensic gift, provided the crash is investigated rather than written off.

  Leg three, the privilege sequence (Security 4672 and 4703). Event ID 4703 records token privilege adjustment and will show `SeDebugPrivilege` being enabled; Event ID 4672 records special privileges assigned at logon. Neither is rare, so use them only as corroboration anchored in time against legs one and two. The useful query is privilege enablement by a process whose image path is unusual, within a short window of that process starting - not privilege enablement in general.

  Leg four, the response implication, which is the real reason to run this hunt. Talos's phrasing is that the process is effectively unremovable without triggering a full system crash. So the standard containment reflex - kill the process, then investigate - is precisely what the implant is built to punish, and on a production server it converts a contained incident into an outage. Where leg one identifies a non-baseline critical process, the correct sequence is to clear the flag first and then terminate, or to isolate the host at the network layer and reboot in a controlled way, rather than issuing a kill. Document that explicitly in the playbook, because the failure mode here is self-inflicted downtime during business hours.

  Leg five, the other anti-analysis behaviour in the same RAT, for scoping. Talos states the defence evasion and anti-analysis techniques implemented include the detection of in-memory execution to suppress forensic artifacts when running in sandboxes, alongside the kill-flag mechanism. The report does not describe how that in-memory detection is implemented, so treat it as a reason to expect reduced artefacts in sandbox analysis rather than as something to hunt directly.

A host with this flag set should be treated as having an interactive operator with network pivot capability, not as a commodity infection.

# H520

There is a feature in the Windows kernel that lets a process declare itself load-bearing. Set `ProcessBreakOnTermination` on a process handle and the kernel will treat that process the way it treats `csrss.exe` or `wininit.exe` — as something the operating system cannot continue without. Kill it anyway and the kernel does not let it exit. It stops the whole machine and writes `CRITICAL_PROCESS_DIED` on the blue screen.

The Overlord RAT variant Talos attributes to UAT-12643 sets that flag on itself.

The sequence is short and deliberate. Check for administrative privilege. Acquire `SeDebugPrivilege`. Then call `NtSetInformationProcess` directly — bypassing, as Talos notes, the documented Win32 API layer entirely — and set the information class to 1. From that moment the implant is, in Talos's words, effectively unremovable without triggering a full system crash.

What makes this worth a hunt is less the cleverness than the operational trap. An analyst sees a suspicious process, right-clicks, ends task, and takes down a production server in the middle of the day. The second time, on the next host, they hesitate. That hesitation is the actual payload.

There is no event for it. The native call leaves no audit record, so the flag is only observable as live process state — which means this is a sweep you schedule, not a query you run over last month's logs.

## Why

- It turns incident response into self-inflicted downtime. The reflexive containment step — terminate the process — is the one action guaranteed to crash the host. Knowing which processes carry the flag before touching them is the difference between a contained incident and an outage review.
- The flag is directly observable, and almost nothing legitimate should be wearing it. The set of genuinely critical processes on a given Windows build is small, enumerable and stable, so a sweep comparing live state against that baseline is a tight, low-noise check.
- No event fires when it is set, which inverts the usual hunting assumption. There is no log to search and no detection to write at the moment of the call. That makes a scheduled live-state sweep the only mechanism that can find it, and makes an empty log search worthless as evidence.
- Every crash it causes leaves a dump containing the implant. The anti-removal control is also an artefact generator: one `CRITICAL_PROCESS_DIED` bugcheck means one memory image of a process someone tried to kill. Estates that triage crash dumps rather than discarding them get the sample for free.
- The stop code is a retrospective tripwire that most organisations already have. Bugcheck events are collected by default and kept for a long time, so asking which process died in past `CRITICAL_PROCESS_DIED` crashes is a historical hunt that costs nothing and occasionally finds something.
- A hit means an interactive operator with a network tunnel. The same RAT carries a reverse SOCKS proxy that routes operator traffic through the victim network to internal hosts unreachable from the internet, in-memory plugin loading, and recovery-environment persistence. The flag is the cheapest thing to find and the least of the problem.
