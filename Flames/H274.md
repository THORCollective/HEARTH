hypothesis: >-
  The Java class dropped into the PaperCut Application Server during the CVE-2026-81578 / CVE-2026-82078 chain
  cleans up after itself: it deletes its own output file (`Udydn.out`), deletes `server.log`, and then removes
  itself from disk. Total intrusion time under two minutes. The deletions are the durable observable — the
  filenames are five random characters and will change, but a process deleting the application log of the
  service it is running inside, seconds after that service spawned an unexpected child, will not. Hunt for file

  `[install]\server\data\content\*.out|*.cmd` where the deleting process is `pc-app.exe` or a PaperCut-parented
  `java.exe` — and treat a `server.log` that is missing, truncated, or zero-length on a running installation as
  the finding in its own right.

EID 23 additionally ARCHIVES the deleted file, which on this hunt means recovering the attacker's `.class` file after it removed itself. That is the difference between knowing you were hit and knowing what ran
  - Defender XDR DeviceFileEvents with ActionType `FileDeleted` — FolderPath, FileName, InitiatingProcessFileName, InitiatingProcessCommandLine, SHA256. The Defender-native equivalent, without the archive capability
  - Sysmon Event ID 11 (FileCreate) / DeviceFileEvents `FileCreated` on `[install]\server\lib\` and `[install]\server\data\content\` — the create half of the pair. A create and a delete of the same path within seconds, by the same process, is the whole signature
  - PaperCut `[install]\server\logs\server.log` — its own existence, size, and modification time. Absence is evidence. Collect file metadata (size, MAC times, and whether the file handle is held by a running `pc-app.exe`) rather than only the contents

  - Sysmon Event ID 1 / Windows Security 4688 — the process lineage that produced the deletions, joined by ProcessGuid to the file events
  - USN journal / `$J` and MFT from the app server volume — recovers deleted filenames and timestamps when the endpoint agent was not watching that path. Frequently the only surviving source in an estate without file-delete telemetry on servers
  - Backup and volume shadow copies of the PaperCut install tree — an older `server.log` from a snapshot predating the deletion may contain the encoded request blob in full
false_positive_notes: |
  File deletion is the highest-volume event class on any server, so this hunt is only viable because it is
  tightly scoped to one application's directory tree. Even scoped, expect:
  - PaperCut's own log rotation. `server.log` is rotated normally and archived copies are aged out — this is
    routine and it is the dominant benign population. The separators are (a) rotation produces a NEW
    `server.log` immediately, deletion does not, and (b) rotation happens on a size or date boundary that is
    consistent and predictable, whereas this deletion happens within seconds of an unexpected child process.
  - PaperCut upgrades and patch installation, which legitimately remove and replace `.class` and `.jar` files
    under `server\lib\`. These correlate to a change record, run from an installer parent, and touch many files
    at once rather than one five-character class file.
  - Temporary print job and document-content files under `server\data\content\`, which are created and removed
    constantly by normal operation. Scope this hunt's `content\` component to `.out` and `.cmd` extensions
    specifically, not to the directory as a whole, or it will be unusable.
  - Antivirus quarantine removing a detected file — which looks like deletion but is attributed to the AV
    process, and should be treated as a detection, not a false positive.
  - Backup agents and disk-cleanup tooling.
  The separators that matter:
  (1) THE DELETING PROCESS. Rotation and upgrades are done by PaperCut's own service or an installer. A
      deletion whose Image is `pc-app.exe` immediately after that process spawned `cmd.exe` is a different
      event with the same file path.
  (2) CREATE-THEN-DELETE WITHIN SECONDS. A `.class` file that appeared minutes ago and is gone again is not
      part of any legitimate lifecycle.
  (3) NO REPLACEMENT. Rotation leaves a fresh `server.log`. Deletion leaves an absence, or a file whose
      creation time is later than the service start time.
  (4) CORROBORATION IN `derby.log`, which survives.

  WHY THIS IS A SEPARATE HUNT FROM [[H273]]. H273 hunts the execution — `pc-app.exe` parenting a shell or a
  discovery utility. This hunt exists because the payload's entire purpose after executing is to remove the
  evidence that H273 depends on, and because it deletes an APPLICATION log rather than a Windows event log,
  which most anti-forensics detection does not cover. Estates watch `wevtutil cl`, `Clear-EventLog`, and 1102
  religiously and watch application log deletion not at all. Running both hunts together answers the question
  from two directions: H273 finds the intrusion, H274 finds the shape of the intrusion where the process
  telemetry was cleaned up or never collected.

  DETECTION — FILE DELETION. Defender XDR:

      DeviceFileEvents
      | where ActionType == "FileDeleted"
      | where FolderPath has_any (@"\PaperCut MF\server\", @"\PaperCut NG\server\")
      | where FileName endswith ".class" or FileName endswith ".out" or FileName endswith ".cmd"
             or FileName =~ "server.log"
      | where InitiatingProcessFileName in~ ("pc-app.exe", "java.exe", "javaw.exe", "cmd.exe", "powershell.exe")
      | project Timestamp, DeviceName, FolderPath, FileName, InitiatingProcessFileName,
                InitiatingProcessCommandLine, InitiatingProcessParentFileName, SHA256

  Sysmon equivalent: EID 23 or 26 with `TargetFilename` contains `\PaperCut` and the same extension set. Prefer
  EID 23 (archived) for this specific path even though EID 26 is the general recommendation for volume reasons —
  the install tree is small, the deletion volume is low, and archiving is what recovers the attacker's class
  file after self-deletion. Configure the Sysmon `ArchiveDirectory` and add a narrow `FileDelete` include rule
  for the PaperCut path rather than enabling archival globally, which Microsoft warns will grow `C:\Sysmon` to
  an unreasonable size.

  DETECTION — CREATE/DELETE PAIRING. The strongest single query is a self-join: a file created under
  `server\lib\` or `server\data\content\` and deleted again within, say, 300 seconds, by a process in the
  PaperCut tree. Legitimate `.class` files are written by installers and stay. This pairing needs no filename
  IOC at all, which is the point — Huntress explicitly warns the "observed five-character filenames may vary."

  DETECTION — ABSENCE AS EVIDENCE. Run a fleet sweep across every PaperCut Application Server for:
    - `server.log` missing entirely, zero-length, or with a creation time later than the `pc-app` service start
    - `server.log` present but with a gap in its timestamp sequence
    - `derby.log` containing more than one `Booting Derby version` entry, and any such entry whose database
      directory ends in `pwn`
    - `.class` files under `server\lib\` whose names are five alphanumeric characters and which are not part of
      the vendor's shipped file manifest — compare against a clean installation of the same version
    - orphaned `.out` or `.cmd` files under `server\data\content\`
  This sweep requires no historical telemetry, which matters because most estates do not have file-delete
  events on print servers, and it is runnable today.

  OBSERVED ARTIFACTS: `Udydn.class`, `Moo97.class`, `Udydn.out`, `Udydn.cmd` under
  `C:\Program Files\PaperCut MF\server\lib\` and `...\server\data\content\`. Log strings that survive or
  precede the deletion: `DB URL: jdbc:derby:memory:pwn`;
  `Booting Derby version ... memory:C:\Program Files\PaperCut MF\server\data\internal\pwn`;
  `ERROR No suitable driver found for jdbc:no:x`;
  `ERROR DatabaseUtils - Database error looking up cardID: VALUES CAST`.

  RESPONSE NOTE: preserve `server\logs\` in full, with file metadata, before upgrading or restarting. A restart
  can overwrite the surviving artifacts. Pull volume shadow copies and the USN journal at the same time — an
  older `server.log` from a snapshot may still contain the encoded request blob that identifies what was
  executed, which is exactly how the payload was recovered in the source report.

  CATEGORY: Flames. Embers rejected — the benign deletion population within one application's install tree is

# H274

The intrusion lasted under two minutes. In that time the payload profiled the system, listed a directory, wrote its output to `Udydn.out`, deleted `Udydn.out`, deleted `server.log`, and deleted itself.

Huntress recovered the class file anyway — a hex-encoded copy of it was still inside log content they had, and Fernflower did the rest. That is a lucky break, not a repeatable method. In the general case, an attacker who removes their tooling, their output, and the application log of the service they exploited leaves a defender with an absence and a two-minute hole.

Which is the hunt. Not "find the malicious file" — it deleted itself. Find the deletion. Find the `.class` that was created and gone again inside the same minute. Find the `server.log` that a running service should be writing to and isn't. And find the Derby log, which the payload did not think to remove, still recording that a database called `pwn` was booted seconds before the gap.

## Why

- **Application log deletion is a genuine blind spot in most detection programs.** Every estate watches `wevtutil cl`, `Clear-EventLog`, and Security event 1102. Very few watch a service deleting its own log file. There is no Windows event for it, no built-in alert, and the file lives in a vendor directory nobody has instrumented. An attacker who understands this — and this one clearly did, deleting `server.log` rather than attempting to clear the Windows event log — operates entirely outside the anti-forensics coverage that has been built.

- **The deletions are structural where the filenames are disposable.** `Udydn` and `Moo97` are five random alphanumeric characters, and the source report says outright that they will vary. Any detection keyed on those names expires immediately. What does not vary: a payload delivered through a dynamic class-loading vulnerability must write a `.class` file somewhere the loader will find it, must write its command output somewhere retrievable, and — if it wants to stay quiet — must remove both. The create-then-delete pair inside the install tree is the invariant.

- **Sysmon Event ID 23 turns this from detection into recovery.** The archived-delete variant preserves a copy of every deleted file to a protected directory. Applied globally that is a storage problem Microsoft explicitly warns about; applied to one small application install tree with a narrow include rule, it costs almost nothing and it means the next time a payload self-deletes off a PaperCut server, you have the payload. In the source incident that artifact had to be reconstructed from a hex blob in a log by luck. It should not require luck.

- **Absence is evidence, and it is checkable right now with no telemetry at all.** A running PaperCut service should have a `server.log` that it is actively writing. Missing, zero-length, or created after the service started are all anomalous, and a fleet sweep for that condition needs no historical events, no Sysmon deployment, and no EDR coverage on print servers — which is fortunate, because print servers are exactly the class of host that tends to have none of those. This is the version of the hunt that a team can run this afternoon.

- **The attacker cleaned up incompletely, and the leftover is dated.** `derby.log` is not deleted. It records a second "Booting Derby version" entry with a database directory ending in `pwn`, timestamped immediately before the execution. That gives the deletion a time anchor even when the deleted log is unrecoverable, and it makes the whole sequence reconstructable: Derby boots the attacker's in-memory database at T, `pc-app.exe` spawns a child at T+seconds, files appear and vanish under `server\lib`, `server.log` ends. Anti-forensics is rarely complete, and the surviving artifact is usually the one that was never part of the plan.

- **Centralised log forwarding defeats this entire step, and most sites do not forward application logs.** If `server.log` is shipped off-box as it is written, deleting the local copy accomplishes nothing. Whether that forwarding exists is the single largest factor in whether a PaperCut compromise is reconstructable, and it is a cheap thing to fix. The hunt is worth running for what it reveals about that gap as much as for what it finds.

- **The deletion is the last cheap moment.** Huntress observed no secondary malware, no C2, and no persistence from the recovered payload — this was reconnaissance and cleanup. The value of catching it is that it is early. Once the operator returns to a host they have already profiled, with SYSTEM-level access on a server that holds directory integration credentials, the deletions stop being the interesting artifact.
