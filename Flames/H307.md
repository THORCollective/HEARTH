false_positive_notes: |
  Endpoint management agents running PowerShell as SYSTEM is the definition of normal in any managed estate, so the behaviour is not the signal and treating it as one will bury the analyst. The discriminator is tenancy: which deployment tenant the agent reports to. That reframes the hunt from behavioural detection to inventory reconciliation, and the false positives change character accordingly. Expect legitimate findings that look alarming at first: an MSP or outsourced IT provider operating a tenant the internal security team was never told about — very common, and worth resolving as a governance gap rather than dismissing; vendor support tools installed temporarily during a support engagement and never removed; shadow IT where a business unit procured its own management platform; software trials and proof-of-concept deployments; and acquired subsidiaries still enrolled in a parent organisation's tenant during integration. Every one of those is a real endpoint-management channel into the estate that security does not control, so the correct disposition is to document and authorise it, not to suppress it — an unmanaged-but-benign tenant is exactly the thing an attacker would otherwise blend into. On the script-source condition, note that fetching scripts from `raw.githubusercontent.com` is genuinely common in legitimate IT automation, particularly among smaller teams and MSPs, so it should raise confidence rather than stand alone. Two collection caveats: proxy logs that record only the hostname and not the full URI will not show the tenant identifier at all, which silently removes the hunt's best field; and TLS interception may be required to see it, so verify what the environment actually captures before concluding the estate is clean.
notes: |
  The core detection, tenant reconciliation - Core filter: outbound requests from endpoints to endpoint-management vendor cloud endpoints, grouped by the tenant or customer identifier carried in the URI. For Faronics Deploy the configuration call is `https://deploy.faronics[.]com/api/GetConfigSettings?ck=<GUID>`, where `ck` is the deployment identifier; the Huntress-documented campaign clustered on `ck=6D70CDEF-CFF4-48A7-8092-24E5B9C3FA1D`. Hunt approach - enumerate every distinct identifier observed across the estate and reconcile against the authorised register. ANY unrecognised value is a finding with no further behavioural condition required, and a single unexpected identifier typically reveals the full set of affected hosts in one query. Generalise the same method to the other platforms in this class by identifying the tenant field each one carries in its check-in: ScreenConnect instance identifier, Atera and NinjaOne tenant identifiers, Action1 organisation identifier, and the site or company identifier used by N-able and ConnectWise agents.
  The agent's own log as primary evidence - Core filter: read `C:\ProgramData\Faronics\Logs\ScriptRunner.log` and grep for script-retrieval entries, which appear as `Entered GetScriptNameUsingURL URL=<url>`. This log is unusually valuable because it PERSISTS the remote script URL after the PowerShell process has exited and after the command line has aged out of process telemetry, which makes it the reliable artefact during late incident response. Strong red flags - a script URL on `raw.githubusercontent.com`, a paste service, a URL shortener, or any domain that is not the vendor's own. Equivalent evidence exists for most products in this class; locating and centrally collecting each vendor's script-execution log is a durable improvement that outlasts this specific campaign.
  Installer masquerade at the point of entry - Core filter: file creation of an executable in a download, mail-attachment or temp path whose name imitates a document, followed by service installation. The campaign delivered the genuine signed Faronics installer under names such as `Adobe.exe`, `DocuSignView.exe` and `Invoice_*.exe`. Detection guidance - the binary is legitimately signed by the real vendor, so signature and reputation checks pass; the anomaly is entirely in the NAME-VERSUS-PUBLISHER mismatch. A useful standalone query is any executable whose filename suggests a document or a different vendor's product while its Authenticode subject names an endpoint-management vendor. Corroborate with Security event 7045 for the resulting service and with Mark-of-the-Web on the downloaded file.
  The execution that follows - Core filter: `powershell.exe` whose parent is the deployment agent process, particularly with `-ExecutionPolicy Bypass`, `-EncodedCommand`, `-w hidden`, `-nop`, or an inline download expression. Defender XDR KQL - `DeviceProcessEvents | where InitiatingProcessFolderPath has_any (@"\Faronics\", @"\ScreenConnect\", @"\Atera", @"\N-able", @"\Action1") | where FileName in~ ("powershell.exe","pwsh.exe","cmd.exe","msiexec.exe","curl.exe","bitsadmin.exe") | project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessFolderPath`. Triage values - `AccountName` (SYSTEM context is the point of the technique), `ProcessCommandLine`, and the downloaded-from domain within it.
  The daisy-chain, and why finding one tool is never the end - Core filter: installation of a SECOND remote-access or management product shortly after the first. In this campaign the sequence ran phishing to a fake document, to a genuine Faronics Deploy agent enrolled in the attacker's tenant, to remote PowerShell, to a ScreenConnect installation for durable interactive access. Each hop is independently trusted, and each provides fallback if the previous is removed. Practical consequence for response - remediation must enumerate ALL remote-access and management agents on the host, not just the one that triggered the alert, because removing the second tool while leaving the first re-establishes access within one polling interval. Pivot directly to H306 for the ScreenConnect stage and to M043 for estate-wide scoping.
  A standing control worth checking during the hunt - Whether unapproved endpoint-management agents can install at all. Application control policy, or a simple blocklist of known RMM and deployment installers where allowlisting is impractical, converts this entire technique class from a detection problem into a prevention one. Enumerating which of these products are currently installable is a concrete output of the hunt regardless of findings.

# H307

The Faronics Deploy abuse Huntress documented in 2026 is a clean illustration of a pattern that keeps recurring and that traditional controls are structurally poor at catching. The attacker did not compromise the victim's deployment server. They did not exploit the product. They phished a user into running a genuine, correctly signed Faronics Deploy installer named something like `Adobe.exe` or `DocuSignView.exe`, and enrolled the machine into a deployment tenant that they owned. From that point they had a vendor-supported, vendor-hosted channel for executing SYSTEM-level PowerShell on the host — and they used it to pull scripts from GitHub and install ScreenConnect for durable interactive access.

Every layer of that chain is legitimately trusted. The installer is signed by the real vendor, so reputation and signature checks pass. The service is a real service. The network traffic goes to the vendor's own cloud over HTTPS, so domain reputation passes. The scripts come from `raw.githubusercontent.com`, which is on almost every organisation's allowlist. Huntress called this daisy-chaining trust, and the name is apt: at no point does the attacker have to defeat a control, because each hop borrows credibility from a relationship the organisation already has.

Which means the hunt cannot be behavioural. "Deployment agent runs PowerShell as SYSTEM" describes the product working correctly and will bury an analyst in any managed estate. The question that actually separates the populations is *whose tenant is this machine enrolled in*, and that is answerable because the agent has to say so on every check-in. Faronics Deploy carries it as the `ck` parameter on its configuration call; the campaign clustered on a single GUID. ScreenConnect carries an instance identifier, Atera and NinjaOne carry tenant identifiers, N-able and ConnectWise carry site identifiers. Enumerating every distinct value seen across the estate and reconciling it against an authorised register turns this from detection into inventory — and it usually finds something even when there is no intrusion, because shadow IT, forgotten vendor support tools and undocumented MSP tenants are all real management channels that security does not control. One more artefact deserves specific attention: `C:\ProgramData\Faronics\Logs\ScriptRunner.log` retains the URL of every remotely executed script long after the PowerShell process and its command line have aged out of telemetry, which makes it the evidence that survives to late incident response.

## Why

- Every control in the path is defeated by design rather than by evasion. A correctly signed vendor installer, a legitimate service, HTTPS to the vendor's own cloud and scripts from an allowlisted code host mean signature checking, reputation and domain filtering all pass the activity through without the attacker doing anything clever.
- The behavioural framing does not work, and recognising that is the hunt's main contribution. A deployment agent executing SYSTEM-level PowerShell is the product functioning correctly, so the only viable discriminator is tenancy — which the agent must transmit on every check-in and therefore cannot conceal.
- Reconciling tenant identifiers is cheap, fast and reliably productive. It requires no behavioural baseline, a single unrecognised value typically reveals every affected host at once, and the same method generalises across every product in this class once each one's identifier field is known.
- The hunt finds governance problems as well as intrusions. Undocumented MSP tenants, lingering vendor support agents and shadow-IT management platforms are all uncontrolled SYSTEM-level channels into the estate, and each one is cover an attacker can hide behind — so documenting them is a genuine security outcome, not noise.
- The vendor's own script log preserves evidence that process telemetry loses. Retaining the remote script URL after the executing process is gone makes it the artefact that still answers "what was actually run" during an investigation that starts days late.
- The daisy-chain makes single-tool remediation actively unsafe. Because the deployment agent installed a second remote-access product, removing only the tool that triggered the alert leaves a channel that re-establishes access within one polling interval — so a confirmed hit must trigger a full agent inventory on the host and across the estate.
