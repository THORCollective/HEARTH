title: "A hidden PowerShell loop restarting an SSH reverse forward, kept alive by a scheduled task and a Startup-folder batch file both named after SysMon"
hypothesis: >-
  On a Windows developer workstation, a tampered code-editor extension loaded a JavaScript loader that reaches for persistence twice: first a scheduled task named after SysMon requesting SYSTEM execution, and if that is refused, a batch file dropped into the user's Startup folder as `sysmon.cmd`. Either path launches a hidden PowerShell loop that re-runs `ssh` with a reverse forward back to port 22 on the workstation, sleeping sixty seconds between attempts. The task-creation event, the Startup-folder write and the `-R` argument are three independent observables for the same chain, and because the loader degrades from SYSTEM to user-level persistence, a hunt that only watches scheduled tasks will miss the hosts where the elevation was denied.

false_positive_notes: |
  Genuine Sysmon deployments are the obvious collision and the reason this hunt has to read the task action. Sysmon installs as a *service*, not as a scheduled task, so a scheduled task whose name contains SysMon is already anomalous on a host that runs the real thing. Resolve the `Actions` element of the task XML, not the task name.
  OpenSSH on Windows is legitimate and widely used by developers. Outbound `ssh.exe` to internal Git and jump hosts is normal; so are local forwards (`-L`) and dynamic forwards (`-D`) to lab and staging systems. The remote forward (`-R`) with a target of `localhost:22` is the shape with no ordinary explanation, because it exposes the workstation's own SSH service rather than reaching a service elsewhere.
  Per-user Startup folder writes come from a long tail of legitimate installers, OEM tooling and user shortcuts, so the raw volume of that query is high on a first run. Filter on the writer: a `.cmd` or `.bat` file written into Startup by a code editor, `node.exe`, `bun.exe` or a shell is a far smaller population than Startup writes generally.
  Hidden-window PowerShell is used by legitimate management tooling and by some installers, so `-WindowStyle Hidden` alone is a tuning exercise rather than a finding. Pair it with the `ssh` invocation or the retry sleep in the script block.
  A clean scheduled-task result does not clear a host. Microsoft records the Windows task as an *attempt*: "Attempted SysMon scheduled task requesting SYSTEM execution", with a documented fallback of "Batch file in the user's Startup folder". Cursor reports that "errors and administrator-permission requirements blocked SSH access on most macOS and Windows hosts", so the hosts where elevation failed are precisely the ones that will only show the user-level artefacts.

  What the report states - Microsoft Threat Intelligence analysed the injected JavaScript in a tampered `anthropic.claude-code` package (versions 2.1.313 and 2.1.312) served from the Cursor extension marketplace on October 29, 2026. The report's platform table gives the Windows row as "Attempted SysMon scheduled task requesting SYSTEM execution" with key artifacts `%USERPROFILE%\.config\smt.cmd` and `%USERPROFILE%\.config\smtk`, and a separate Windows fallback row: "Batch file in the user's Startup folder", at `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\sysmon.cmd`.
  The retry mechanism, verbatim - "On Unix-like systems it prefers autossh, falling back to ssh; on Windows it uses a hidden PowerShell loop. The loops wait sixty seconds after SSH exits before retrying." The tunnel arguments are given as "-N -R '*:0:localhost:22'", and the report pre-empts the misreading: "The remote port value 0 asks the server to allocate a port; it does not change the local target from port 22."
  How Windows differs from the Unix path - on macOS and Linux the `.smt` script rebuilds the tunnel identity when it runs. The report says the Windows case is simpler: "On Windows, the loader writes the identity and batch script directly." So on Windows both `smt.cmd` and `smtk` should be present from the start, where on Unix-like hosts `.smtk` may be absent between runs.
  The masquerade is aimed at the responder - "The startup objects use names such as SysMon and com.apple.sysmond, which resemble monitoring components. Behind these names, their configured actions invoke the generated scripts that maintain reverse SSH forwarding." Microsoft's remediation guidance says the same thing operationally: "Inspect each startup object's configured action before removal; names alone are not sufficient to distinguish malicious objects from legitimate monitoring software."
  Scheduled-task query - this is Microsoft's published query, and it is the right starting point because `AdditionalFields` is where the task action lands in Defender:
  ```kql
  DeviceEvents
  | where Timestamp > ago(30d)
  | where ActionType == "ScheduledTaskCreated"
  | where AdditionalFields has "SysMon"
      and AdditionalFields has "smt"
  | project Timestamp, DeviceName, AccountName, AdditionalFields,
            InitiatingProcessFileName, InitiatingProcessCommandLine
  ```
  Generalised version - the name will change, the lineage will not. A scheduled task registered by a code editor, a JavaScript runtime or a shell spawned from one is the durable observation:
  ```kql
  DeviceEvents
  | where Timestamp > ago(30d)
  | where ActionType == "ScheduledTaskCreated"
  | where InitiatingProcessFileName in~ ("cursor.exe", "code.exe", "code - insiders.exe",
                                         "windsurf.exe", "node.exe", "bun.exe",
                                         "cmd.exe", "powershell.exe", "pwsh.exe")
  | project Timestamp, DeviceName, AccountName, AdditionalFields,
            InitiatingProcessFileName, InitiatingProcessFolderPath,
            InitiatingProcessCommandLine, InitiatingProcessParentFileName
  | order by Timestamp desc
  ```
  Startup-folder fallback - this is the half that catches hosts where SYSTEM was refused. Note that a `.cmd` file is never a process `FileName`, so this has to be a *file* query plus a `cmd.exe` command-line query, never a process-name query on `sysmon.cmd`:
  ```kql
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("FileCreated", "FileRenamed", "FileModified")
  | where FolderPath has @"\Start Menu\Programs\Startup"
      or FolderPath has @"\.config\"
  | where FileName in~ ("sysmon.cmd", "smt.cmd", "smtk")
      or (FileName endswith ".cmd" and InitiatingProcessFileName
          in~ ("cursor.exe", "code.exe", "node.exe", "bun.exe", "cmd.exe", "powershell.exe"))
  | project Timestamp, DeviceName, ActionType, FolderPath, FileName, SHA256,
            InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessCommandLine
  | order by Timestamp desc
  ```

  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where FileName in~ ("ssh.exe", "autossh.exe")
  | where ProcessCommandLine has "-R"
  | where ProcessCommandLine has_any ("localhost:22", "127.0.0.1:22", ":0:localhost:22")
  ```

  ```kql
  let loops = DeviceProcessEvents
      | where Timestamp > ago(30d)
      | where FileName in~ ("powershell.exe", "pwsh.exe")
      | where ProcessCommandLine has_any ("-w hidden", "-WindowStyle Hidden", "-windowstyle hidden")
      | project LoopTime = Timestamp, DeviceId, DeviceName,
                LoopCmd = ProcessCommandLine, LoopPid = ProcessId;
  let tunnels = DeviceProcessEvents
      | where Timestamp > ago(30d)
      | where FileName in~ ("ssh.exe", "autossh.exe")
      | where ProcessCommandLine has "-R"
      | project SshTime = Timestamp, DeviceId, SshCmd = ProcessCommandLine,
                InitiatingProcessId;
  loops
  | join kind=inner (tunnels) on DeviceId
  | where SshTime between (LoopTime .. LoopTime + 5m)
  | project LoopTime, SshTime, DeviceName, LoopCmd, SshCmd
  | order by LoopTime desc
  ```

  On-premises equivalents - Security Event ID 4698 carries the task XML, and the `Actions` element is where the script path lives; where 4698 auditing is off, Microsoft-Windows-TaskScheduler/Operational 106 records the registration. Sysmon 1 gives the `ssh.exe` command line with `ParentImage`, and Sysmon 11 gives the Startup-folder and `.config` writes. If 4688 is the only process source available, the fields are `New_Process_Name` and `Creator_Process_Name` rather than Sysmon's `Image` and `ParentImage`, and command-line capture has to be enabled separately or the `-R` argument will not be there to match on.
  Reading the PowerShell loop - `DeviceEvents` with `ActionType == "PowerShellCommand"` holds cmdlet *names* such as `Start-Sleep` or `Invoke-Expression`, never script text, so it cannot be used to search for the loop body or the ssh invocation. For the content, use Event ID 4104 `ScriptBlockText`. To get anything out of the cmdlet telemetry, aggregate per process instead:
  ```kql
  DeviceEvents
  | where Timestamp > ago(30d)
  | where ActionType == "PowerShellCommand"
  | summarize cmdlets = make_set(AdditionalFields, 25)
          by DeviceId, DeviceName, InitiatingProcessId, bin(Timestamp, 1h)
  | where tostring(cmdlets) has "Start-Sleep"
  ```

# H430

The Windows side of the Cursor marketplace incident is a good illustration of why a persistence hunt should never key on a single mechanism. Microsoft Threat Intelligence analysed the JavaScript injected into the tampered `anthropic.claude-code` extension and found that the loader tries for the stronger option first — the report calls it an "Attempted SysMon scheduled task requesting SYSTEM execution" — and has a documented fallback when that fails: a "Batch file in the user's Startup folder", written as `sysmon.cmd`.

That design means the two populations you care about look completely different in telemetry. On a host where the user had local administrator rights, there is a scheduled task. On a host where they did not, there is a `.cmd` file in `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\` and no task at all. Cursor reports that "errors and administrator-permission requirements blocked SSH access on most macOS and Windows hosts", which makes the second population the larger one — and the one a scheduled-task query silently skips.

Whichever path runs, the payload is the same: a hidden PowerShell loop that re-invokes `ssh` with a reverse forward. The arguments are "-N -R '*:0:localhost:22'", which asks the remote server to allocate a listening port and forward anything arriving there to port 22 on the victim's own loopback interface. The loops "wait sixty seconds after SSH exits before retrying", so a single failed connection is invisible against a day of telemetry unless you are looking for the cadence.

The names were chosen for whoever reads the alert. Microsoft: "The startup objects use names such as SysMon and com.apple.sysmond, which resemble monitoring components. Behind these names, their configured actions invoke the generated scripts that maintain reverse SSH forwarding." On a host that genuinely runs Sysmon this is doubly effective, because the responder has a real reason to expect that string — and no reason to expect it attached to a *scheduled task*, since Sysmon installs as a service.

## Why

- The fallback is where the hosts are. Elevation was refused on most affected machines, so the Startup-folder write — not the scheduled task — is the artefact most affected Windows hosts will actually have.
- Three independent observables cover the same chain. Task registration, the Startup-folder file write, and the `-R localhost:22` argument each survive the other two being missed, which matters when auditing coverage is uneven across a developer fleet.
- A reverse forward to the workstation's own SSH port needs no inbound firewall change and no listening service exposed to the network, so perimeter controls and external scans will not show it.
- The task name is an anti-response measure rather than an anti-detection one. It is designed to survive a human scanning a list of startup objects, which is why resolving the configured action is part of the hunt and not part of the cleanup.
- Code-editor lineage is the part that outlasts the campaign. A scheduled task or Startup-folder script created by an editor, a JavaScript runtime, or a shell spawned from one has no legitimate explanation on a managed workstation, and that query will still be correct for the next tampered extension.
