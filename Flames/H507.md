false_positive_notes: |
  `login.microsoftonline.com` and `graph.microsoft.com` are among the most-contacted hosts on any Windows estate and are allowlisted everywhere, so destination alone is meaningless. The anomaly is narrower and much rarer - an endpoint performing an OAuth client-credentials grant. Workstations authenticate users through interactive and refresh-token flows; application-only authentication belongs to servers, service accounts and automation. A `grant_type=client_credentials` POST originating from a user workstation is the finding.

  There are real exceptions and they are enumerable. Some management agents, backup clients, monitoring tools and line-of-business integrations do hold application credentials and run on servers; a few run on workstations. Build that list once - it is short - and the leg becomes high-signal rather than noisy.

  The tenant-mismatch leg depends on knowing your own tenant GUIDs, including those of acquisitions, subsidiaries and partner tenants the organisation legitimately federates with. Cross-tenant collaboration through SharePoint and Teams is normal in many estates, so a foreign tenant GUID is not automatically malicious. It is, however, always worth attributing - the question "which tenant is this endpoint uploading to, and who approved it?" has a correct answer.

  Without TLS interception, neither the grant type nor the request path is visible, and the hunt degrades to process attribution against the two hostnames. That is still useful on hosts where the initiating process is a sideload host rather than a browser or a Microsoft component, but it will not distinguish an app-only token request from ordinary sign-in traffic.

  The specific site and list GUIDs in the report are the operator's infrastructure at time of analysis, not durable indicators. Treat `buildersemp.sharepoint.com` and the list identifiers as evidence of what the shape looks like; hunt the shape.

  Tenant-side Entra sign-in logs will not show any of this, because the authentication happens against the attacker's tenant, not the victim's. This is an endpoint and egress hunt even though the behaviour is cloud-shaped - looking for it in your own sign-in logs will produce a clean result that means nothing.
notes: |
  Leg one, the client-credentials request from an endpoint (web proxy, TLS-terminated) - Core filter: `POST` to `login.microsoftonline.com` whose path matches `/<GUID>/oauth2/v2.0/token` and whose form body contains `grant_type=client_credentials`, where the source is a workstation or any host not on the approved application-credential list. Two additional body fields sharpen it - `scope=https://graph.microsoft.com/.default`, which is the app-only scope pattern, and the presence of `client_secret` rather than a client assertion, since well-configured legitimate integrations increasingly use certificate-based assertions. The `X-CSRF-TOKEN` header described in the report is a header the Microsoft identity platform does not use, and is the same free discriminator its GitHub sibling leaves on `api.github.com`.

  Leg two, the tenant mismatch (web proxy, TLS-terminated) - Core filter: requests to `graph.microsoft.com` whose path contains a `sharepoint.com` hostname or a tenant GUID that is not one of yours. The Graph site-addressing form the report records is `/v1.0/sites/<host>,<site GUID>,<web GUID>/drives/<drive ID>/root:/<filename>:/content`, so the foreign hostname sits in the path in clear text. Searches worth saving:

  - `PUT` requests to a Graph `drives/.../root:/` path where the filename matches `main\.[A-Za-z0-9]{8}\.js\.map`.
  - `GET` requests to `/v1.0/sites/.../lists/<GUID>/items` carrying `$filter=startswith(fields/Title,'main.` - tasking retrieval, and a filter expression no first-party client emits.
  - the same list query filtered on `'scr.ts'`, `'pr.ts'` or `'kl.ts'` - plug-in retrieval by title prefix.
  - any request body containing `commit from INSOMNIA`, which catches this backdoor and GitDoor in one search.

  Leg three, process attribution (Defender XDR DeviceNetworkEvents, or Sysmon 3 joined to 1) - For estates without TLS interception this is the primary leg. Aggregate per device and process rather than per connection, so a single sign-in does not read the same as a resident channel:

      let expected = dynamic(["msedge.exe","chrome.exe","firefox.exe","outlook.exe","teams.exe",
                              "onedrive.exe","svchost.exe","officeclicktorun.exe","ms-teams.exe"]);
      DeviceNetworkEvents
      | where Timestamp > ago(30d)
      | where RemoteUrl has "graph.microsoft.com" or RemoteUrl has "login.microsoftonline.com"
      | where InitiatingProcessFileName !in~ (expected)
      | summarize Connections = count(), FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
          by DeviceId, DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath,
             InitiatingProcessParentFileName
      | where Connections >= 10
      | order by Connections desc

  Thirty days is the maximum Defender advanced hunting retains. Red flags, heaviest first - the initiating process runs from `C:\Windows\System32` or `C:\ProgramData`; it is one of the four legitimate sideload hosts the report names, javaw.exe, start.exe, pythonw.exe or zoomit.exe; its parent is services.exe; the same device also shows up in H503's `api.github.com` query or H504's Ably query.

  Leg four, host-side confirmation (file and pipe telemetry) - GraphDoor leaves three artefacts worth checking on any candidate. It creates `C:\ProgramData\Intel_Log\<random GUID>` as a working directory - a directory named for a hardware vendor under ProgramData, containing a GUID-named subdirectory, is a cheap and specific file-telemetry query. It opens a named pipe `\\.\pipe\p<its own PID in decimal>`, which every plug-in then writes status into, so Sysmon 17 showing a pipe whose name is the letter p followed by the creating process's own PID is the convention to look for. And the keylogger gate file `log.lock` under the user's Roaming AppData decides whether the keylogger plug-in is fetched at all, which H508 covers.

  Two behaviours in this backdoor that defeat common detection assumptions, worth knowing before writing a rule. API resolution is by DJB2 hash of DLL and function names, so there are no import-table strings to match. And calls are issued from inside a vectored exception handler - the backdoor installs a handler containing a stub for the call it wants, deliberately raises an exception, and lets the handler make the call - so call-stack-based detection sees the exception dispatcher rather than the caller. Neither changes the network evidence, which is why this hunt is built on it.

  Scope note: M053 is the closest existing hunt and the distinction is which side of the connection you stand on. M053 models a Graph-based command-and-control channel over Outlook and OneDrive volumetrically from cloud telemetry; this hunt keys on the endpoint-side artefacts - a client-credentials grant initiated by a local process, a foreign tenant GUID in the request path, and a specific filename and list-filter grammar. H248 covers an Entra application reading command attachments from far-future Outlook calendar events, which is the same app-only Graph primitive against a different dead-drop store and is read from tenant-side logs. H339 covers a leaked service-principal secret used against Azure Resource Manager, which is app-only authentication into your own tenant rather than out to someone else's. B074 is the baseline that makes leg one answerable in one row rather than a week of triage.

# H507

GraphDoor is GitDoor's sibling — same campaign, same loader trio, same filename grammar, same `commit from INSOMNIA` commit message. What changed is the cloud service underneath. Instead of GitHub issues, it uses a SharePoint document library and SharePoint lists, reached through the Microsoft Graph API.

The interesting part is how it gets in. The backdoor carries three AES-encrypted strings: a tenant UUID, an application client ID, and a client secret. It decrypts them, POSTs them to `login.microsoftonline.com` with `grant_type=client_credentials` and the `.default` Graph scope, and gets back an access token. Kaspersky states plainly what that means — the call authenticates the malicious application, not a user. There is no phished account, no stolen session, no consent grant in anyone's tenant. The operator registered an app in a tenant they control, and the implant signs in as that app from inside the victim's network.

The consequence for defenders is that none of this appears in your own Entra sign-in logs. The authentication is against a tenant you do not own, over TLS, to a hostname every estate allowlists. What you have instead is an endpoint doing something endpoints never do — asking for an app-only token — and Graph requests whose paths contain somebody else's SharePoint hostname in clear text.

## Why

- Workstations do not perform client-credentials grants. Interactive and refresh-token flows belong to users; application-only authentication belongs to servers and automation. The set of endpoints that legitimately hold app credentials is small and enumerable, which makes an unexpected one a genuine anomaly rather than a threshold.
- The tenant GUID is in the request path. Graph's site addressing carries the full SharePoint hostname and site identifiers in the URL, so "which tenant is this host uploading to" is answerable by string comparison against a list you already have — provided someone maintains the list.
- Looking in the wrong place returns a reassuring nothing. Because the authentication terminates in the attacker's tenant, a defender who checks their own sign-in logs will find no evidence and conclude correctly that nothing happened in their tenant, while the channel keeps running. Knowing this is an egress hunt is most of the work.
- Two of the backdoor's evasions are aimed at exactly the detections people reach for first. DJB2-hashed API resolution removes import strings, and issuing calls from inside a deliberately raised vectored exception handler hides the real caller from stack-based inspection. Network and file artefacts survive both.
- One string spans both backdoors. `commit from INSOMNIA` appears in GitDoor's GitHub `PUT` body and GraphDoor's Graph `PUT` body, so a single search over logged request payloads covers both halves of the campaign.
