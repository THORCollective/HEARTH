false_positive_notes: |
  Wide file enumeration by one process is the normal behaviour of several product categories, and this hunt is unusable without allowlisting them by signed publisher and path rather than by process name:
  - Backup and sync agents. Whole-profile backup (Windows Backup, Veeam Agent, Acronis, Backblaze, CrashPlan) and cloud sync clients (OneDrive, Dropbox, Google Drive, Box) read Desktop, Documents and Downloads continuously and touch removable volumes. These run persistently, not as a single burst, and they do not read browser credential stores.
  - Search indexing. `SearchIndexer.exe` and third-party desktop search read vast numbers of files by extension. Allowlist by signed path; note that the indexer does not read `Login Data` or `cookies.sqlite` for their contents.
  - Security and DLP products. AV scans, DLP content inspection and eDiscovery collection agents do exactly this by design, including on removable media, and some legitimately read browser stores. These are the hardest exclusions and the ones most worth writing down precisely, with publisher, path and schedule.
  - Migration and profile tools. USMT, profile-migration utilities and IT onboarding scripts sweep user folders and sometimes export browser data. These coincide with a change window and run under an administrative or SYSTEM context from a known share.
  - Password managers and browser-import features. A browser importing from another browser, or a password manager's import wizard, legitimately reads `Login Data` and `cookies.sqlite`. These are user-initiated, interactive, read one or two stores, and do not then enumerate mapped drives.
  The three constraints that make the queue short are: multiple *different vendors'* browser stores read by one process; a credential-container extension (`.ovpn`, `.kdbx`, `.jks`, `.zs2`, `.pfx`) among the collected files; and the whole sequence completing inside a short window followed by an archive write and an outbound send. No benign tool in the list above does all three.
notes: |
  Browser credential-store reads - Core filter: a single process reading two or more of these within minutes, where the process is not the owning browser: Chromium-family `Cookies`, `Login Data`, `Local State` and `Web Data` under `%LOCALAPPDATA%\Google\Chrome\User Data\<profile>\`, `%LOCALAPPDATA%\Microsoft\Edge\User Data\<profile>\` and the Opera profile directory; and Firefox `cookies.sqlite`, `logins.json` and `key4.db` under `%APPDATA%\Mozilla\Firefox\Profiles\<profile>\`. ESET reports BeautyStealer targeting "cookies, stored passwords, and local state from the Chrome, Edge, Opera, and Firefox browsers". Triage values: file path, reading process image, command line, parent process, SHA-256, user, integrity level. Correlation: `Local State` holds the DPAPI-wrapped key that decrypts Chromium cookies and passwords, so a process reading `Local State` *and* `Cookies` is collecting a decryptable set, not browsing history. Strong red flags: stores from two different browser vendors read by one non-browser process; the reads completing in seconds rather than spread over a session.
  Sample Defender XDR query - a non-browser process touching several browser credential stores (note that `DeviceFileEvents` has no read events, so this approximates via the copy/stage side and must be paired with EDR read telemetry where available):
  ```kql
  let lookback = 30d;
  let stores = dynamic(["Login Data", "Cookies", "Local State", "Web Data",
                        "logins.json", "key4.db", "cookies.sqlite"]);
  DeviceFileEvents
  | where Timestamp > ago(lookback)
  | where ActionType in ("FileCreated", "FileModified", "FileRenamed")
  | where FolderPath has_any ("\\Google\\Chrome\\User Data\\", "\\Microsoft\\Edge\\User Data\\",
                             "\\Opera Software\\", "\\Mozilla\\Firefox\\Profiles\\")
      or FileName has_any (stores)
  | where InitiatingProcessFileName !in~ ("chrome.exe", "msedge.exe", "opera.exe", "firefox.exe",
                                          "MsMpEng.exe", "SearchIndexer.exe", "OneDrive.exe")
  | summarize Stores = make_set(FileName, 20),
              StoreCount = dcount(FileName),
              Paths = make_set(FolderPath, 20),
              FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
        by DeviceId, DeviceName, InitiatingProcessFileName, InitiatingProcessId,
           InitiatingProcessCommandLine, InitiatingProcessSHA256
  | where StoreCount >= 2
  | extend WindowSeconds = datetime_diff('second', LastSeen, FirstSeen)
  | order by StoreCount desc, WindowSeconds asc
  ```
  `DeviceFileEvents` retains 30 days in Defender XDR advanced hunting, so `ago(30d)` is the ceiling there. The exclusion list above is a starting point only - derive it from your own fleet's top writers to these paths, and exclude by `InitiatingProcessSHA256` or signer where you can, because process name alone is trivially spoofed.
  VPN and private-key material - Core filter: reads or copies of OpenVPN configuration directories in both locations ESET names - the per-user configuration path and the system-wide `C:\Program Files\OpenVPN\config\` - and of files with the credential-container extensions. ESET reports collection of "OpenVPN configurations from both user and system directories", and that files with certain extensions "are targeted specifically for credentials and private keys", listing `.ovpn` (OpenVPN), `.kdbx` (KeePass), `.jks` (Java KeyStore), `.zs2` (private key), `.rdp` (Remote Desktop) and `.pfx` (Personal Information Exchange). ESET adds a note with real triage value for Ukrainian organisations: "The .zs2 file extension is particularly noteworthy: it is used for files that store a secret electronic signature key issued by a Ukrainian accredited key certification center." Triage values: file path, extension, process, volume type (fixed, removable, remote), file size. Strong red flags: a `.kdbx` or `.pfx` read by a process that is not the owning application; any `.zs2` access at all outside its normal application.
  The sweep's breadth is the signal - Core filter: one process touching files on a fixed disk, a removable volume and a mapped network drive within the same short window. ESET describes the targets as "located in the victim's Desktop, Documents, and Downloads folders, as well as on removable media and mapped network drives". That cross-volume reach inside one burst is what separates a harvester from an application doing its job. Triage values: distinct volume roots touched, distinct extensions collected, total bytes read, elapsed time from first to last file. Correlation: count distinct extensions - ESET's combined list across versions runs to more than forty, so a process selecting across dozens of unrelated extensions is enumerating by extension rather than opening documents.
  Staging, exfiltration and self-delete - Core filter: an archive written shortly after the sweep, an outbound connection from the same process, then deletion of the process's own image. ESET reports that "Stolen data is compressed into an archive and exfiltrated either to an attacker-controlled Telegram chat via the Telegram sendDocument API, or, from version 1.2 onward, to a custom C&C server that implements FastAPI." Triage values: archive path and size, destination host and IP, bytes sent, the deleted file path. Correlation: `api.telegram.org` contacted by a process that is not a known Telegram client is worth investigating on its own; a POST carrying a multi-megabyte body to it is conclusive. Note that the self-delete changes shape by version - ESET reports that version 2.0 brought "an updated self-delete mechanism that uses Windows API calls directly rather than the BAT scripts used in earlier versions", so a hunt keyed only on a `.bat` self-deletion misses current samples. Look for Sysmon Event ID 23/26 naming the executing image's own path.
  Why the single-pass shape matters operationally - Core filter: ESET assesses that "The operational focus is on one-time information harvesting rather than long-term access, which may indicate a role as an initial access broker for other Russia-aligned threat actors", and that "Browser credentials, VPN configurations, and selected documents are gathered in a single pass before the deployed malware attempts to remove itself." A hunt built on persistence, beaconing or dwell will find nothing here, because there is none. The entire intrusion may be one process lifetime, which is the argument for retaining file-access telemetry long enough to look backwards.
  Pivot into what the stolen material unlocks - Core filter: for every confirmed host, treat the OpenVPN configurations, `.rdp` files and browser-stored passwords as compromised and look for their use. The follow-on actor is not the one who stole them, so the relevant window may be weeks later: VPN authentications from new addresses or new client fingerprints, RDP sessions originating outside normal ranges, and sign-ins using credentials that only ever lived in a browser store.
  Expected, not observed by ESET: the same single-pass shape should appear on macOS and Linux variants of access-broker tooling, where the analogous targets are Keychain items, `~/.ssh`, `.ovpn` files and browser profiles under `~/Library` or `~/.config`. ESET's report describes a Windows C++ stealer only.

# H453

ESET Research documents Gorbag, a Russia-aligned actor it has tracked since February 2025 against Ukrainian targets: law enforcement and justice entities, city councils in frontline areas, defence organisations, and an entity publicly documented as a major transportation hub for foreign military aid.

The tooling is the interesting part, because it is built for a job most hunting programmes are not configured to catch. ESET writes: "Gorbag uses a small toolset built for rapid intelligence collection. Browser credentials, VPN configurations, and selected documents are gathered in a single pass before the deployed malware attempts to remove itself." Its assessment is that "The operational focus is on one-time information harvesting rather than long-term access, which may indicate a role as an initial access broker for other Russia-aligned threat actors."

That inverts the usual detection economics. There is no persistence to find, no beacon interval to profile, no lateral movement, and no dwell time - the malware runs, collects, sends and erases itself. Every detection strategy that waits for a second stage has nothing to wait for. What there *is*, for a few minutes, is a single process doing something no legitimate program does: reading four different browser vendors' credential stores, then selecting files by extension across Desktop, Documents, Downloads, any plugged-in volume and every mapped network drive.

The extension list is also a statement of intent. Alongside documents and archives, BeautyStealer specifically collects `.ovpn`, `.kdbx`, `.jks`, `.rdp` and `.pfx` - the containers that hold the next actor's access. ESET singles out one more: "The .zs2 file extension is particularly noteworthy: it is used for files that store a secret electronic signature key issued by a Ukrainian accredited key certification center." That is not document theft; it is the theft of a legal signing identity.

HEARTH's nearest existing coverage is H340, which hunts a ransomware affiliate running `s5cmd` with extension filters to exfiltrate to S3 from a file server. The telemetry overlaps - extension-filtered collection - but the behaviour does not: that hunt is a server-side, operator-driven bulk copy to cloud storage with a plaintext credentials file, while this one is a workstation-side, self-contained, single-pass harvester whose distinguishing act is reading multiple browsers' credential stores and then deleting itself.

## Why

- The whole intrusion may be one process lifetime, so the hunt has to be built on the burst rather than on anything that follows it. That makes the collection decision - keeping file-access telemetry long enough to look backwards - as important as the query, and it is the reason this hunt names a 30-day retention ceiling explicitly.
- Reading several unrelated browser vendors' credential stores from one process is close to a unique behaviour. A browser reads its own store; a password manager reads one on import; only a harvester reads Chrome, Edge, Opera and Firefox. Pairing that with a `Local State` read - the DPAPI-wrapped key that makes the Chromium data decryptable - narrows it further.
- Cross-volume reach inside a single window is a second near-unique constraint. Backup and indexing agents touch fixed disks continuously and removable media occasionally; a process that touches a fixed disk, a removable volume and a mapped drive in the same few minutes while selecting by extension is enumerating, not working.
- The stolen material is somebody else's initial access, which changes the response. If Gorbag brokers what it collects, the organisation's exposure is not the compromised workstation - it is every VPN profile, RDP file, signing key and browser-stored password that left it, used by a different actor on a different timeline. The remediation list is a credential inventory, not a reimage.
