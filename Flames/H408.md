false_positive_notes: |
  Heap dumps are a legitimate and important diagnostic artefact, so their existence is not a finding and
  a hunt that treats every `.hprof` as malicious will be switched off within a day. Three entirely
  normal sources produce them in volume. `-XX:+HeapDumpOnOutOfMemoryError` is a recommended production
  setting and writes a dump automatically whenever the JVM exhausts its heap, which on a struggling
  application can mean several a week with no human involved. Performance engineers and on-call staff
  legitimately run `jmap -dump` and `jcmd GC.heap_dump` during incidents, and APM vendors and
  memory-analysis tooling (Eclipse MAT, YourKit, JProfiler, VisualVM) both create and consume them.
  And some platforms collect dumps centrally for crash analysis, which looks exactly like exfiltration.
  The discriminators that survive, in order of strength: who ran the command - the application service
  account and a named engineer are expected, a web service account or a shell user is not; whether an
  incident or ticket exists in the same window, which is the question that resolves most candidates;
  whether an out-of-memory condition actually occurred, because an automatic dump should be preceded by
  one in the application log and a dump with no such event was deliberate; and what happened to the file
  afterwards, since troubleshooting reads a dump in place with an analysis tool while collection
  compresses it and moves it. Expect to need a per-application allowlist of legitimate dump paths
  (`HeapDumpPath` values) because a dump in its configured location is far less interesting than one in
  `/tmp` or a web-accessible directory.

# H408

A JVM heap dump is a complete copy of an application's memory, written to disk by the application itself, in a documented format, readable with free tools.

Everything the application was holding is in it. Database passwords loaded from configuration. API keys. Session tokens. Connection strings. Secrets a vault client just decrypted. Credentials users typed, still in flight.

None of it encrypted, because the application was *using* it.

AhnLab found tooling for exactly this while tracing internet-exposed ARTEX instances. In one of two open directories they recovered — 51 files in total, covering "internal network reconnaissance and access, pivoting, and the deployment of follow-up payloads" — there was a Python file written to search for credential-related strings in JVM heap dumps. Next to it: scan results listing 85 active systems in a Kubernetes Pod network and 8 more in a separate internal network.

Let me be precise about what that is and is not, because it changes how much weight the hunt can carry. This is recovered attacker tooling, not an observed intrusion. AhnLab is careful about it — the files "do not consist solely of ARTEX's default toolkit", ARTEX "allows for the addition of custom tools", and their assessment is only that "it is presumed that some of the hosts where ARTEX was detected were used for attack-related activities or their preparation." No victim is described in which heap-dump harvesting was carried out.

The technique is worth hunting anyway, and here is why.

Consider the Windows equivalent. Dumping a process that holds secrets — LSASS being the famous case — is one of the most heavily monitored actions in the entire detection stack. Handle access, memory read, debug privilege: all watched.

Now the JVM version. `jmap -dump`. The dump is written by the JVM through a supported diagnostic interface. Nothing injects. Nothing attaches a debugger. There is no `ptrace`, no `/proc/pid/mem` read, no handle to a protected process. An endpoint agent sees a Java process writing a large file, which Java processes do.

The artefact is enormous and completely ordinary.

So the hunt cannot be "a heap dump exists" — dumps are legitimate and a query that flags all of them dies on first contact. `-XX:+HeapDumpOnOutOfMemoryError` is *recommended* production configuration and fires automatically. On-call engineers run `jmap` during incidents. Eclipse MAT and YourKit exist to consume these files.

Four questions separate the cases, in rough order of strength.

**Who ran it.** The application service account and a named engineer are expected. A web service account or an interactive shell user is not.

**Was there a ticket.** This resolves most candidates, and it is a question rather than a query.

**Did the JVM actually run out of memory.** An automatic dump should have an `OutOfMemoryError` in the application log immediately before it. A dump with no such event was asked for by someone.

**What happened to the file next.** Troubleshooting reads a dump in place with an analysis tool. Collection compresses it and moves it. That sequence — dump, then `tar` or `scp` within a few minutes — is the clearest shape in the whole hunt.

One blind spot to close deliberately. In a containerised estate, and those scan results suggest a large one, the dump is both easier to take and harder to see. A `kubectl exec` into a pod lands in the Kubernetes audit log, not in host process telemetry. The dump writes to an ephemeral filesystem nothing is monitoring. And the pod is likely holding a service-account token and mounted secrets in memory alongside the application's own credentials.

A hunt that watches only nodes will not see any of it.

## Why

- **The credentials are in cleartext because the application was using them.** No decryption, no cracking, no key material needed — reading the file is the whole attack.
- **The dump is created through a supported diagnostic path.** The JVM writes its own memory, so there is no injection, no debugger attach and no protected-process handle for an endpoint agent to flag.
- **It is dramatically quieter than the Windows equivalent.** Dumping a secret-holding process on Windows is among the most monitored actions available; the JVM version is a routine file write.
- **The blast radius is everything the application touches.** A single application server dump can yield database credentials, API keys, vault-issued secrets and live session tokens at once.
- **Existence is not the signal, so the hunt must be contextual.** Automatic out-of-memory dumps are recommended practice, which forces the discriminators onto identity, ticket, OOM corroboration and post-creation handling.
- **The absence of an OutOfMemoryError is a strong, cheap test.** An automatic dump has a cause recorded in the application log; one without a cause was requested deliberately.
- **Dump-then-compress is the behaviour that distinguishes theft from troubleshooting.** Analysis tools read dumps in place, so archiving and moving one within minutes is the sequence worth alerting on.
- **Containerised JVMs are the gap.** Pod exec leaves no host process trace, ephemeral filesystems are unmonitored, and mounted secrets and service-account tokens are in the same memory image.
- **The source is a toolkit, not an incident, and the hunt should say so.** Treating recovered tooling as evidence of local compromise would overstate what AhnLab reported, while still justifying the detection.
