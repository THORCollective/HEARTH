false_positive_notes: |
  Console access is a legitimate and frequent administrative action, so the hunt depends on the account, the source and the fan-out rather than on the request itself.
  - Administrators open consoles constantly during patching, troubleshooting and guest installation work. A single `vncwebsocket` request is routine. The shape that is not routine is one session touching consoles on several distinct nodes within a few minutes, which is a sweep rather than a task.
  - Legitimate maintenance windows produce exactly that sweep. Compare every candidate burst against the change calendar first, and against the identity - planned work is normally done by a named administrator account, not by the realm root account.
  - Some estates genuinely administer Proxmox as `root@pam` because that is the default and no additional realm or named accounts were ever configured. In those environments the account provides no signal and the hunt has to lean entirely on source address, time of day and fan-out, so fixing the identity model is a precondition for making this detection cheap.
  - Backup and monitoring integrations authenticate to the API frequently and can appear as high-volume users. Those use API tokens or dedicated service accounts and request inventory and status paths, not console sockets, so splitting by API path separates them cleanly.
  - A compromised administrator workstation is a plausible source for legitimate traffic too, since that is where administrators work. The discriminator is the absence of the administrator's own interactive pattern around the burst - no preceding browser session, no related tasks, activity outside their working hours.
notes: |
  Source reporting is Kaspersky GERT's analysis of two ransomware cases in virtualized environments. This hunt covers the second case, a The Gentlemen intrusion against Proxmox; the ESXi case is hunted in [[H458]] and the shared credential-exposure precondition is baselined in [[B070]]. Kaspersky reports that the actor gained access to Proxmox using information collected during the dwell time between initial access and visible impact, that on a compromised system administrator workstation the actor discovered administrative credentials and access details stored in notes in plain text, and that these records provided what was needed to log in to Proxmox using the root account.
  The console sweep - Core filter: `pveproxy` access-log entries where the authenticated user is the realm root account and the path requests a node console socket. The reported log records take the form:
  ```text
  root@pam [01/08/2026:00:28:36 -0400] "GET /api2/json/nodes/******/vncwebsocket?port=5900&vncticket=****
  ```
  with five such requests between 00:28:36 and 00:44:49 against node names Kaspersky redacted. Triage values are the authenticated user string including its realm, the node name in the path, the request timestamp, the source address if your log format records it, the `port` parameter, and the response code. Group by user and session and count distinct node names per fifteen-minute window - the sweep shape is several distinct nodes, not one node several times, and that distinction is what separates it from an administrator working on a single guest. A sample shell aggregation over a forwarded access log:
  ```sh
  # count distinct nodes consoled per user per hour; a sweep is many nodes in one hour
  grep 'vncwebsocket' /var/log/pveproxy/access.log \
    | sed -E 's#^([^ ]+) \[([0-9]{2}/[0-9]{2}/[0-9]{4}:[0-9]{2}).*/nodes/([^/]+)/vncwebsocket.*#\1 \2 \3#' \
    | sort -u \
    | awk '{print $1, $2}' \
    | uniq -c \
    | sort -rn \
    | head -40
  ```
  Strong red flags are a burst that spans every node in the cluster, requests outside the administrator's working hours, and console access with no corresponding task-log entry for any work on those guests.
  The authentication that preceded it - Core filter: a successful web-interface login for the realm root account, with the source address and user agent. Correlation: compare that source address to the set of hosts that normally administer the cluster. The reported case had the credential arriving from a compromised administrator workstation, so the source will often be a legitimate administrative endpoint, which is why the hunt cannot rest on source reputation alone. Pivot: a single login followed immediately by a multi-node console sweep and then by guest or storage activity is one session doing reconnaissance and staging in one pass. Strong red flags are a login with no matching browser session on the workstation's own endpoint telemetry, and a login from a workstation whose user was not working at that hour.
  What the console access was for - Core filter: ransomware delivery and execution inside the cluster after the sweep. Kaspersky reports the access was used to download and execute ransomware within the cluster, which encrypted the entire virtual environment. Console access is attractive precisely because it needs no guest credentials and leaves no guest authentication record - the operator types into the guest as though at its keyboard. Correlation: look for guest-side evidence that starts without any preceding guest logon event, which is the signature of keyboard-level access rather than network access. Pivot: storage write-rate metrics across the cluster date the encryption window even when node logs are unavailable.
  The source of the credential - Core filter: on administrator workstations, process and file telemetry for reads of note-taking and password-adjacent data stores by anything other than the owning application. The practical target list is the data files of note applications, plain `.txt` and `.md` files under the user profile and desktop, connection-manager profiles, spreadsheet files whose names reference infrastructure, and browser-saved credentials. Correlation: this is the step that makes the hypervisor compromise possible, and it is the only step that happens somewhere a modern EDR is actually installed - hypervisor nodes generally have no endpoint agent, administrator laptops do. Kaspersky's conclusion is the operative one for scoping: because the credentials belonged to a highly privileged root account, one poor credential-handling practice significantly increased the scope and impact of the attack. Strong red flags are a bulk read of user-profile text and note files by a scripting interpreter or a newly installed utility, and any process reading those files shortly before a management-plane login from the same host.
  Hardening the hunt reads as a control test - Core filter: the identity model itself. Enumerate which accounts can authenticate to the management plane, in which realm, whether multifactor authentication is enforced for the realm root account, and which source networks can reach TCP 8006. An estate where console access is only reachable from a jump host by named accounts with multifactor authentication turns this entire hunt into a one-line exception report; an estate administered as realm root from laptops cannot distinguish the sweep from a working day. Measuring which of the two you have is part of running the hunt.

# H459

Kaspersky's Global Emergency Response Team responded to a ransomware incident by The Gentlemen group that encrypted an entire Proxmox virtual environment. The interesting part is how little exploitation was involved.

The actor compromised a system administrator's workstation and spent the dwell time looking around. On that workstation they found administrative credentials and access details written in plaintext notes - the kind of file that exists on a lot of administrator machines, holding the things that are tedious to look up. Among them was what was needed to log in to Proxmox as root.

From there they did not pivot to SSH or deploy tooling. They used the management interface the way an administrator would. The access log shows the root realm account requesting a VNC websocket console on one node after another, five requests across sixteen minutes. Console access through the hypervisor means typing directly at each guest's virtual keyboard: no guest credentials needed, no guest authentication logged, no lateral movement in the network sense at all. Then they downloaded and executed ransomware inside the cluster and encrypted everything.

This hunt looks for that sweep. One management-plane identity opening consoles across several distinct nodes in a few minutes is not how maintenance looks, and the Proxmox proxy access log records every one of those requests with the user, the node and the timestamp already in it.

## Why

- The management plane is the highest-leverage surface in a virtualized estate and the least instrumented. Hypervisor nodes rarely carry an endpoint agent, so the API access log is often the only record that exists - and it is a plain text file that already contains the authenticated user, the node and the full request path.
- Console access defeats guest-side detection by design. An operator at a virtual keyboard produces no network logon, no remote-session event and no credential use inside the guest, so a detection strategy built on guest authentication telemetry sees nothing at all until files start changing.
- The sweep shape is distinguishable from administration. One node repeatedly is a task; several distinct nodes inside a few minutes is reconnaissance of the whole cluster, and counting distinct node names per short window separates the two without needing any threat intelligence.
- The precondition is widespread and testable today. Plaintext credential notes on administrator workstations are common, and so is administering Proxmox as the realm root account because that is the default. Both can be inventoried before any intrusion, which turns this hunt into a control test as much as a detection.
- Impact scales with the identity, not with the intrusion. The actor never escalated beyond what the stolen credential already allowed, and because that credential was cluster root the result was total. The response scope is therefore every secret on the compromised workstation, not only the one that was obviously used.
