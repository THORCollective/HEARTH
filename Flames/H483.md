title: "A new Group Policy Object named after the installed antivirus distributes the locker, while a second policy writes the Defender-disabling registry settings - both created by a PowerShell script that leaves its own deployment log on disk"
hypothesis: >-
  Ransomware reaches the estate through the mechanism built to reach the estate. A PowerShell script
  creates a Group Policy Object whose display name impersonates the security product the organisation
  actually runs, and that policy distributes a self-extracting archive - also named after the security
  product - containing the locker, scheduled on each host under a task name that reads like the vendor's
  own agent installer. A policy in the same operation writes the registry settings that switch Windows
  Defender off, so nothing responds when the archive runs. The naming is the defence-evasion strategy: an
  administrator auditing Group Policy, a scheduled-task inventory, or a list of executables in SYSVOL sees
  the name of a product that belongs there. The observables are a GPO created outside change control whose
  name matches a security vendor, an executable staged in SYSVOL, a scheduled task deployed by policy
  rather than locally, and the script's own log file left behind on the host where it ran.

false_positive_notes: |
  Group Policy is the legitimate software-distribution mechanism in most Windows estates, so none of the individual actions is unusual and the hunt turns on naming, provenance and change control.
  - Software deployment by GPO is normal, including deployment of security agents. Many organisations genuinely distribute their antivirus or EDR installer through a policy named after the product. That is the benign population this technique hides inside, which is why the first pass must be an inventory comparison - a policy that exists today and did not exist at the last snapshot, with no change record - rather than a name match.
  - Administrators do name policies after vendors. A policy called after the installed security product is not suspicious; a policy with that name created last Tuesday by an account that has never created a policy before, linked to every OU, is. Carry the creator and the creation date, not just the name.
  - Executables in SYSVOL are a legitimate if unloved pattern. Logon scripts, startup scripts and software-installation policies all put binaries there. Hash everything in SYSVOL and reconcile against the known deployment set; the point of the check is that SYSVOL should contain a short, stable list of files and almost nobody has ever read it.
  - Defender policy registry values are set deliberately in environments that run a different endpoint product, and that configuration is permanent and legitimate. The finding is a change to those values, correlated to a new policy, not their presence.
  - Scheduled tasks named after vendor installers are created by real vendor installers. The discriminator is whether the task arrived through Group Policy Preferences on hosts that have no corresponding software-install record, and whether its action points at an archive in SYSVOL or in a staging path rather than at an installed program directory.
  - Directory service change auditing for GPO objects is commonly not enabled, and without it Event ID 5136 will not exist. If the only record of policy creation is the policy itself, this hunt runs as a periodic inventory diff instead, which still works but loses attribution. Determining which of the two situations applies is part of the result.
notes: |
  Source reporting is Kaspersky's November 11, 2026 analysis of Citrus Ransomware, which reaches victims through compromised contractors and encrypts with the Go-based Sn00py family using RSA-2048 and ChaCha20, appending a `.citrus` extension. The escalation that precedes this stage is covered in [[H476]]; this hunt covers the deployment and the defence impairment that made it work.
  The named artefacts, as Kaspersky lists them - The report sets out the masquerading set in full. `KasperskyGPO_Deploy_64.exe` and `KasperskyGPO_Deploy_64_FIXED.exe` are self-extracting archives that "contain the Deploy-KasperskyGPO.ps1 script, a directory with a malicious Group Policy Object, and one of two archives, KasperskyAgent.exe or agent.exe." `KasperskyAgentInstaller.exe`, `KasperskyAgent.exe` and `agent.exe` are "self-extracting archives containing the ransomware Trojan executable and auxiliary files." Kaspersky GPO "is the name of the Group Policy Object that distributes the ransomware Trojan in the victim's infrastructure." `KasperskyAgentInstallTask` and `Sysvc` "are names used for the scheduled task that runs the self-extracting ransomware archive files." `Deploy-KasperskyGPO.ps1` "is the PowerShell script that creates the malicious Kaspersky GPO", and `Kaspersky_GPO_Deployment.log` "is the log of the Deploy-KasperskyGPO.ps1 script." Kaspersky adds, reasonably, that "using the Kaspersky name in malicious file names doesn't help the attackers avoid detection. Kaspersky solutions successfully detect and block these malicious files" - the masquerade is aimed at the human reading an inventory, not at the product.
  Why the vendor name is interchangeable and the structure is not - The specific vendor here is an artefact of which product the victims ran. The technique is to name the policy, the archive and the task after whatever security product the target has installed, so hunt the structure - a new policy distributing an executable, with a Defender-disabling policy alongside it - and use the names of your own installed products as the local name list. An organisation running a different vendor should expect that vendor's name.
  Closest existing HEARTH coverage - Grepped the corpus for malicious GPO deployment and for security-vendor masquerading and found no hunt covering policy-based locker distribution. [[H431]] covers a renamed portable runtime executing a script from a KB-prefixed folder created during a remote-support session, which is a different masquerade. [[H476]] is the escalation half of this same intrusion. Nothing in the corpus covers SYSVOL as a staging location.
  Core filter 1, the policy inventory diff - The highest-value check and the one that needs no knowledge of this group. Snapshot every GPO - display name, GUID, creator, creation and modification time, links - on a schedule, and diff. A policy that appeared without a change record is the finding, and a policy that appeared without a change record and is named after a security product is the reported case. Triage values are the creating account, whether that account has ever created a policy before, the scope of the links, and whether the policy contains a software-installation, startup-script or Group Policy Preferences element.
  Core filter 2, what is in SYSVOL - Hash every file under the Policies directory on each domain controller and reconcile against the known deployment set. Kaspersky's chain puts the locker archive there for distribution, so an executable or self-extracting archive in SYSVOL that no deployment record explains is a direct finding. This check is cheap, is almost never run, and is useful against any policy-based deployment abuse rather than only this one.
  Core filter 3, the two policies together - Kaspersky reports that "at the impact stage, the attackers also use a Group Policy Object that modifies Windows Defender settings in the registry to switch it off. As a result, the antivirus did not respond when the ransomware was launched." Hunt registry writes to the Defender policy keys and establish whether they arrived by policy or locally; a policy-sourced Defender disable appearing within the same window as a new software-distribution policy is the pair that matters. In a domain where a different product is installed and Defender is legitimately off by policy, the equivalent check is a change to that product's own policy state.
  Core filter 4, the script's own log - The simplest check in the hunt. The deployment script writes a log file, so search for a deployment log matching the script's name on domain controllers and administrative workstations. A file a tool leaves behind about itself is the cheapest possible artefact and it survives deletion of the script more often than it should.
  Core filter 5, the task that runs it - Hunt Event ID 4698 for scheduled tasks whose action points at a self-extracting archive in SYSVOL or a staging directory, with particular attention to tasks that arrived identically across many hosts in a short window, which is the signature of policy-based deployment rather than of local installation. The reported names are `KasperskyAgentInstallTask` and `Sysvc`, and the second one is the more durable lead because it is short, generic and does not depend on which vendor the target runs.
  Sample read-only GPO and SYSVOL triage, run from a domain-joined administrative workstation:
  ```powershell
  Import-Module GroupPolicy
  # policies created or changed in the last 30 days, newest first
  Get-GPO -All |
    Where-Object { $_.CreationTime -gt (Get-Date).AddDays(-30) -or
                   $_.ModificationTime -gt (Get-Date).AddDays(-30) } |
    Select-Object DisplayName, Id, Owner, CreationTime, ModificationTime |
    Sort-Object CreationTime -Descending |
    Format-Table -AutoSize

  # executables, archives and preference files staged under SYSVOL
  $domain = (Get-ADDomain).DNSRoot
  Get-ChildItem "\\$domain\SYSVOL\$domain\Policies" -Recurse -File -ErrorAction SilentlyContinue |
    Where-Object { $_.Extension -in '.exe','.dll','.ps1','.bat','.cmd','.msi','.zip','.7z' } |
    Select-Object FullName, Length, CreationTimeUtc,
                  @{n='SHA256';e={ (Get-FileHash $_.FullName -Algorithm SHA256).Hash }} |
    Sort-Object CreationTimeUtc -Descending |
    Format-Table -AutoSize
  ```
  Both commands are read-only and run in seconds on a normal estate. The second one is worth running today regardless of whether this group is a concern, because the expected output on a healthy domain is a short list that somebody can account for, and a long list nobody recognises is a finding about the domain rather than about an intrusion.
  Surrounding defence impairment, for scoping - Kaspersky reports that the group clears "event logs on some systems using the built-in wevtutil utility", disables antivirus protection on hosts once privileged, goes "after the centralized management consoles for security solutions, which they then use to disable protection en masse", and "manually add their malicious tools to the antivirus exclusion list" where privileges allow. The console is the one to check first after a hit here, because a console-driven mass disable leaves its record in the console rather than on the endpoints.
  Expected, not observed by Kaspersky - Which account created the policy, and whether the policy was linked at the domain root or to selected organisational units. Kaspersky documents the artefacts and their purpose but does not report the policy's link scope or its creator, so the inventory-diff filter above is written to surface both rather than to match a reported value.
  Scope - Any Active Directory domain, and in particular domains reachable by contractor or third-party accounts, which is this group's access shape. The inventory and SYSVOL checks are worth standing up permanently; they are the two cheapest controls against the entire class of policy-based deployment abuse, and most domains have neither.

# H483

The Group Policy Object was called "Kaspersky GPO". The archive it deployed was called `KasperskyAgent.exe`. The scheduled task that ran it was called `KasperskyAgentInstallTask`. The script that created the whole thing was `Deploy-KasperskyGPO.ps1`.

The organisation ran Kaspersky.

None of that was aimed at the antivirus — Kaspersky notes drily in its own report that the naming did not help the attackers and the products blocked the files anyway. It was aimed at the person. At the administrator scrolling a list of Group Policy Objects, the analyst reading a scheduled-task inventory, the responder looking at what is staged in SYSVOL. Every one of those readers sees the name of software that is supposed to be there and moves on.

And the locker was delivered through the mechanism the domain exists to provide. Not lateral movement, not a tool pushed host by host — a policy, linked, applied, and executed on schedule across the estate, exactly as software deployment is designed to work.

A second policy in the same operation wrote the registry settings that turn Defender off, so nothing answered when the archive ran.

The vendor name is a detail. If the victim had run a different product, the policy would have been named after that one. What does not change is the structure, and the structure is checkable with two read-only commands: which policies appeared without a change record, and what executables are sitting in SYSVOL.

Most domains have never had the second question asked. The expected answer is a short list somebody can account for.

## Why

- **The masquerade targets the reviewer, not the product.** Detection engines never see a display name. Humans do, and a name matching the installed security product short-circuits exactly the moment of attention this technique needs to survive. That is why the hunt is an inventory diff with provenance rather than a name match.
- **Policy-based delivery reaches the whole estate at once and looks like administration while doing it.** There is no per-host lateral movement to detect, no remote execution tool, no credential use on each target. The locker arrives the same way a patch does, which collapses the window between first impact and full impact.
- **The two policies together are the finding; either alone is ordinary.** A software-distribution policy is routine, and Defender policy settings are legitimately changed in estates running other products. A new distribution policy and a protection-disabling policy inside the same window is a combination with no benign explanation.
- **SYSVOL is a staging location nobody inventories.** It is world-readable to domain members, it legitimately holds scripts and occasionally binaries, and its contents on a healthy domain are short and stable. Hashing it and reconciling against known deployments is a one-command check that works against this technique and every variation of it.
- **The script leaves a log about itself.** `Kaspersky_GPO_Deployment.log` is the kind of artefact that outlives the tool, because operators clean up executables and forget output files. Searching for a deployment log named after a deployment script costs nothing and sometimes answers the question on its own.
