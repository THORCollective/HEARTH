hypothesis: >-
  A PowerShell payload running at medium integrity elevates itself without producing a consent prompt
  by borrowing an already-elevated process rather than by hijacking a registry handler. AhnLab observed
  this in a quote-request phishing chain: the secondary PowerShell payload "creates a ShellWindows COM
  object to bypass UAC. It then indirectly uses the ShellExecute Path of explorer.Exe to launch a new
  PowerShell process and execute subsequent commands with privilege escalation." The mechanism is the
  ShellWindows CLSID `{9BA05972-F6A8-11CF-A442-00A0C90A8F39}`, instantiated out-of-process, which hands
  the caller a window object belonging to the running `explorer.exe`; calling `Document.Application.ShellExecute`
  on it causes `explorer.exe` to create the new process, so the child inherits explorer's token and
  integrity level instead of the caller's. The forensic signature is distinctive and it is a lineage
  anomaly rather than a registry write: a `powershell.exe` whose parent is `explorer.exe`, running at
  high integrity, in a session where the user was not interactively driving the shell - and crucially
  with no corresponding UAC consent event. Hunt that parent-child pair alongside instantiation of the
  ShellWindows CLSID.

false_positive_notes: |
  The core pair - `explorer.exe` as parent of `powershell.exe` - is extremely common and entirely benign in
  the ordinary case, because that is exactly what happens every time a user double-clicks a script, opens
  PowerShell from a Start-menu entry, pins it to the taskbar, or runs it from the File Explorer address bar.
  Running the parent-child pair alone will return the whole estate and teach nobody anything. Three
  additional conditions make it usable, and all three are needed. First, integrity level - interactive
  launches by a standard user produce a medium-integrity child, and a legitimate elevated launch produces a
  consent event. The hunt wants high integrity WITHOUT consent. Second, the absence of a UAC consent
  artefact is the load-bearing negative: a user who right-clicks Run as administrator generates
  `consent.exe` and an audit trail, and this technique generates neither, which is the entire point of it.
  Third, session context - a human-driven launch sits inside a burst of interactive shell activity, while
  this one appears as an isolated elevated child in a session whose foreground activity was something else
  entirely, often seconds after a script host ran. Genuine exceptions remain. Administrators who are already
  running an elevated Explorer session - which happens on servers, in some RDP and jump-host configurations,
  and wherever someone has launched Explorer elevated deliberately - will produce high-integrity children of
  explorer with no consent event, legitimately. Scope those hosts explicitly rather than tuning the query.
  Some installer and updater frameworks also use shell execution through COM for their elevation step, so a
  signed vendor binary appearing in the chain deserves a look before it is called an attack. The CLSID leg is
  much cleaner: scripted instantiation of ShellWindows by a script host has almost no legitimate population,
  though a small amount of legitimate automation does enumerate open Explorer windows to find a current
  directory, and some RPA and desktop-automation tooling does it routinely.

  cover different mechanisms with different artefacts. [[H243]] targets per-user handler hijack - a payload
  command written to `HKCU\Software\Classes\ms-settings\Shell\Open\command` with a `DelegateExecute` value,

  the AppInfo service RPC interface over `ncalrpc`, explicitly chosen because it never touches those
  registry keys. ShellWindows touches neither: there is no registry write and no RPC call to AppInfo from

  and child command lines, integrity level, logon session, user, and the preceding process-creation events in
  that session.
  Sample KQL over Defender XDR.
  `DeviceProcessEvents | where Timestamp > ago(90d) | where InitiatingProcessFileName =~ "explorer.exe" | where FileName in~ ("powershell.exe","pwsh.exe","cmd.exe","wscript.exe","cscript.exe","mshta.exe") | where ProcessIntegrityLevel in ("High","System") | join kind=leftanti ( DeviceProcessEvents | where Timestamp > ago(90d) | where FileName =~ "consent.exe" | project DeviceId, ConsentTime = Timestamp ) on DeviceId | project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine, ProcessIntegrityLevel, InitiatingProcessCommandLine`

  `index=windows (EventCode=4688 OR source="*Sysmon*" EventCode=1) ParentImage="*\\explorer.exe" (Image="*\\powershell.exe" OR Image="*\\pwsh.exe" OR Image="*\\cmd.exe") | search IntegrityLevel="High" OR IntegrityLevel="System" | table _time host User ParentImage Image CommandLine IntegrityLevel`

  consent prompting turned off, there is no consent event for anything and the negative filter silently
  passes everything. Record the UAC configuration of the population before trusting the result, and treat

# H377

Every published UAC bypass detection worth having is built on an artefact the attacker leaves behind. Write to `HKCU\Software\Classes\ms-settings\Shell\Open\command` and the registry write is the detection. Talk to the AppInfo service over `ncalrpc` and the RPC call is the detection.

The ShellWindows method leaves neither, because it does not elevate anything. It asks a process that is already elevated to do the work.

AhnLab found it in the middle of a quote-request phishing chain against Korean targets. The secondary PowerShell stage instantiates the ShellWindows COM object — CLSID `{9BA05972-F6A8-11CF-A442-00A0C90A8F39}` — which returns a collection of the open Explorer windows belonging to the running `explorer.exe`. From any one of those windows the caller can reach `Document.Application.ShellExecute`, and when that call creates a process, the process is created *by explorer*. It inherits explorer's token. It inherits explorer's integrity level. The medium-integrity script that asked for it never elevated, never wrote to the registry, and never produced a consent prompt, because from the operating system's point of view nothing was elevated at all.

What is left on the host is a lineage anomaly: a `powershell.exe` whose parent is `explorer.exe`, running at high integrity, with no UAC consent event anywhere near it.

That pair, on its own, is useless. `explorer.exe` is the parent of `powershell.exe` every single time a human double-clicks a script or opens a shell from the Start menu, which is constantly. Three things have to be true together before it means anything: the child is high integrity, there is no consent event, and the session's foreground activity was something other than a person driving a shell.

The third condition is where the chain context helps. This elevated child appears seconds after a script host ran — a VBScript extracted from a RAR attachment that built the string `powershell` out of bytes it read from `notepad.exe`, which is its own problem and is modelled in [[M058]]. It is not sitting in a burst of interactive administration. It is sitting alone.

One warning about the negative indicator, because it is the part most likely to be built wrong. "No consent event" is only meaningful where UAC is actually prompting. On a host with UAC disabled there is no consent event for anything, the filter passes everything, and the hunt returns silence that looks like a clean result. Check the UAC configuration of the population first — and treat the hosts where it is off as a larger problem than this one.

## Why

- **It produces no registry write, so the two detections HEARTH already has do not see it.** [[H243]] is built on `ms-settings` handler hijack and [[H321]] on AppInfo RPC. This mechanism touches neither, by design.
- **Nothing is actually elevated, which is why there is no consent event.** `explorer.exe` creates the process with the token it already holds. The absence of a UAC artefact is not evasion of the logging; it is a consequence of the mechanism.
- **The only host artefact is process lineage, and lineage is cheap to query.** Parent, child, integrity level and session are all fields that standard process-creation telemetry already carries.
- **The high-volume benign population has a clean discriminator.** Interactive launches are medium integrity, or they are high integrity with a consent event. High integrity with no consent is the narrow slice.
- **Scripted ShellWindows instantiation has almost no legitimate population.** The CLSID appearing in a PowerShell script block alongside `ShellExecute` is a much tighter signal than the lineage pair, where script logging is available.
- **The surrounding chain gives independent confirmation.** An extensionless staging blob in `%APPDATA%` read twice by the same process tree, and `MicrosoftEdgeUpdate.exe` reaching a non-Microsoft destination, both corroborate without depending on the elevation leg at all.
- **Legitimate elevated Explorer sessions are real and must be scoped by host, not tuned away.** Servers, jump hosts and deliberately elevated Explorer sessions produce the same pair honestly. Naming those hosts keeps the query sharp instead of broadening it until it is useless.
- **The negative indicator fails silently where UAC is off.** A hunt that depends on the absence of consent events returns an empty, reassuring result on exactly the hosts that are least protected. Verify the UAC posture before believing the output.
