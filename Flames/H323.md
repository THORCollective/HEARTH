hypothesis: >-
  Rather than killing a security product, this implant disables the network inspection path. A scheduled
  task named `INetHealth` runs PowerShell that clears three values under
  `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` — `ProxyEnable` to `0`,
  `ProxyServer` to an empty string and `AutoConfigURL` to an empty string — and then calls
  `InternetSetOption(0, 39, 0, 0)` (INTERNET_OPTION_SETTINGS_CHANGED) and `InternetSetOption(0, 37, 0, 0)`
  (INTERNET_OPTION_REFRESH) so WinINet picks the change up immediately without a logoff. Because the task
  is scheduled, any remediation or GPO/Intune re-push is silently undone within the hour. A second task,
  `ExdBackupTool`, relaunches `%APPDATA%\ExdBackupTool\Exodus.exe` hourly at 42 minutes past the hour.
  Both tasks are registered through the Task Scheduler COM API, not `schtasks.exe`, so there is no
  process command line to catch. The invariant is repetition - a one-off proxy clear is a user or a
  support script, but the same three values cleared on a schedule by a process outside the management
  set is the implant announcing itself in the registry after it has blinded the proxy logs.

false_positive_notes: |
  Proxy registry values are not inert in a managed enterprise - they are written routinely, and the naive query returns thousands of rows. The recurring benign writers are a short and enumerable list: Group Policy processing (`svchost.exe` hosting the GP client, `gpscript.exe`), Intune and other MDM agents, VPN clients that swap proxy configuration on connect and restore it on disconnect, proxy-management and SSL-inspection agents from your web-gateway vendor, browser installers, and support scripts run by the help desk. Users themselves toggle these values through Internet Options and the Settings app, which surfaces as `SystemSettings.exe`, `rundll32.exe` hosting `inetcpl.cpl` or `explorer.exe`. Three discriminators survive all of that and should be applied together. First, the writing process - anything outside your enumerated management set is the interesting population, and in most estates that reduces to a handful of hosts. Second, the direction of the change - legitimate management writes populate proxy values or swap them for a different proxy, whereas this behavior clears them, so filter to `ProxyEnable` set to `0` alongside `ProxyServer` and `AutoConfigURL` set to empty. Third and most important, repetition - a single clear is a person or a script, but the same three values cleared on a fixed schedule, hour after hour, is not something a human or a well-behaved agent does. Group Policy refresh will fight the implant, so on a compromised host you will see the values oscillate, and that oscillation is itself the tell. Note also that the tasks were registered through the Task Scheduler COM API and never through `schtasks.exe`, so any query built on process creation for `schtasks.exe` will return a genuine-looking empty result while the tasks sit on disk. An empty result is therefore ambiguous unless you can confirm three things - that Sysmon Event ID 13 is enabled with the `Internet Settings` key actually in scope (the default Sysmon configurations do not all include it), that the Object Access - Audit Other Object Access Events subcategory is on so 4698 fires at all, and that Microsoft-Windows-TaskScheduler/Operational is enabled and forwarded. Missing any one of those makes a clean result a collection gap rather than a true negative. Finally, do not fall back to proxy logs to validate this hunt - the entire point of the behavior is that the affected hosts stop appearing in them.
notes: |
  Core filter, the registry - Sysmon Event ID 13 where `TargetObject` ends with `\Software\Microsoft\Windows\CurrentVersion\Internet Settings\ProxyEnable` and `Details` is `DWORD (0x00000000)`, or ends with `\Internet Settings\ProxyServer` or `\Internet Settings\AutoConfigURL` with empty `Details`. Exclude your management set by `Image` - the GP client under `svchost.exe`, `gpscript.exe`, the Intune management extension, your VPN client and your web-gateway agent. Also cover the policy-scoped twins where they apply in your estate - `HKCU\Software\Policies\Microsoft\Windows\CurrentVersion\Internet Settings`, `HKLM\Software\Policies\Microsoft\Windows\CurrentVersion\Internet Settings` and `HKLM\Software\Microsoft\Windows\CurrentVersion\Internet Settings` - and the `Internet Settings\Connections\DefaultConnectionSettings` binary value, which is what WinINet actually consumes.
  Core filter, the repetition - this is the discriminator that matters more than any single value. Aggregate Event ID 13 hits on those three values by host and by writing process over a 7 to 30 day window and count them. One or two is benign. Twenty-four a day, at a fixed offset within the hour, is the implant. Where Group Policy is re-pushing proxy settings, expect to see the values oscillate between the policy value and empty; that oscillation, visible only in the registry timeline, is a strong standalone lead.
  Defender XDR equivalent - `DeviceRegistryEvents` where `RegistryKey` contains `Internet Settings` and `RegistryValueName` is in (`ProxyEnable`, `ProxyServer`, `AutoConfigURL`), with `InitiatingProcessFileName` not in your management set, summarised by `DeviceId` and `InitiatingProcessFolderPath` and ordered by event count descending. The top of that list is the hunt result.
  The tasks, verbatim - `INetHealth` is the proxy-stripping task; `ExdBackupTool` launches `%APPDATA%\ExdBackupTool\Exodus.exe` hourly at 42 minutes past the hour. Hunt the shape as well as the names - a task whose action path sits under `%APPDATA%` and whose trigger repeats hourly is the pattern, and SigmaHQ's `win_security_susp_scheduled_task_creation.yml` already keys 4698 on `TaskContent` containing `\AppData\Roaming\` and `\AppData\Local\Temp\`, which matches this directly.
  The COM collection lesson - both tasks were registered through the Task Scheduler COM API (`ITaskFolder::RegisterTaskDefinition`), not through `schtasks.exe`. There is no `schtasks` command line anywhere in this chain, so every detection keyed on process creation for `schtasks.exe` misses it silently. Registration is still recorded, because the events are emitted by the Task Scheduler service rather than by the caller - use Security 4698 (which carries the full task XML) and Microsoft-Windows-TaskScheduler/Operational 106 (which records the registration but not the XML). Pivot on the creating process in the 4698 record rather than looking for a scheduler binary; a 4698 whose creator is an unsigned binary under a user profile is the finding. For hosts where neither channel was on, the task XML under `C:\Windows\System32\Tasks\` is the fallback artifact.
  The API calls that make it immediate - `InternetSetOption(0, 39, 0, 0)` is INTERNET_OPTION_SETTINGS_CHANGED and `InternetSetOption(0, 37, 0, 0)` is INTERNET_OPTION_REFRESH. Both take a NULL handle and a NULL buffer, which is the documented idiom for pushing a system-wide WinINet proxy change without a logoff. Their presence is why the operator does not need to wait for a reboot, and why remediating by re-pushing policy without removing the task buys you at most sixty minutes.
  Re-parenting, and why the ancestry looks clean - the MSI custom action is `LaunchExodus: [WindowsFolder]explorer.exe "[INSTALLDIR]Exodus.exe"`. Launching through `explorer.exe` severs the installer ancestry, so `Exodus.exe` appears as an ordinary `explorer.exe` child with no visible link to `msiexec.exe`. Do not expect a clean process tree back to the MSI; pivot on file-create and MsiInstaller timestamps instead.
  Installer artifacts to sweep for - `%TEMP%\jn0101.msi`, 210,767,872 bytes, SHA256 `c513a7346484ee69a2931c4a89956ee50aa63e4366ef989315e669d8f10d7485`, 0 of 76 detections on VirusTotal at time of reporting. Deliberately false metadata - Manufacturer `Apple Inc`, ProductName `Background Service`, ProductVersion `43.4.30`, ProductCode `{4046AD2B-3831-4011-AEAD-D98C5C9FD1EF}`, UpgradeCode `{C4A1D8F2-3E5B-4C72-9A6D-1B8F0E27A3C9}`, built with WiX Toolset 6.0. The UpgradeCode survives the MSI being deleted, as `HKLM\SOFTWARE\Classes\Installer\UpgradeCodes\{C4A1D8F2-3E5B-4C72-9A6D-1B8F0E27A3C9}` - that registry key is the cheapest fleet-wide sweep in this whole hunt and it costs one query. A 200 MB MSI claiming to be published by `Apple Inc` with ProductName `Background Service` is also a standing anomaly worth its own rule.
  Other host artifacts - mutex `ExodusHelper`, which is a fast live-triage check. Recon children observed under the implant - `conhost.exe --headless powershell -e <Base64>` and `cmd.exe /c chcp 65001 >nul 2>&1 & systeminfo`. Treat `conhost.exe --headless` as its own filter; it is a window-hiding technique with a very small legitimate population, and pairing it with `powershell -e` and a Base64 blob is close to self-evident.

# H323

The same Huntress-reported Exodus installer intrusion that carries the Azure Table Storage C2 in [[H322]] also ships an unusual defense-evasion primitive. Instead of killing an EDR agent, it disables the *network inspection path*. A scheduled task called `INetHealth` runs PowerShell that clears `ProxyEnable`, `ProxyServer` and `AutoConfigURL` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings`, then calls `InternetSetOption` with INTERNET_OPTION_SETTINGS_CHANGED (39) and INTERNET_OPTION_REFRESH (37) so WinINet honours the change immediately rather than at next logon. Because it is a *task*, not a one-shot, any remediation or policy re-push is undone within the hour. A second task, `ExdBackupTool`, relaunches `%APPDATA%\ExdBackupTool\Exodus.exe` hourly at 42 minutes past. Both are registered through the Task Scheduler COM API rather than `schtasks.exe`, so there is no command line to catch — and the RAT itself is launched via an MSI custom action that goes through `explorer.exe`, severing its installer ancestry. The net effect is a host that has quietly removed itself from your proxy logs and keeps removing itself, on a timer.

## Why

- **Disabling the inspection path is strategically different from disabling the product.** Killing an EDR agent generates a loud, well-instrumented event that most organisations already alert on. Clearing a user's proxy settings generates a registry write that almost nobody watches, achieves a comparable result for network-side visibility, and looks exactly like an IT support action if you only ever see one of them. Hunting it requires deciding in advance that proxy configuration is security-relevant telemetry, which is the part most detection programmes skip.
- **Repetition is what converts noise into a finding, and it costs nothing to compute.** Every field in this query has a large benign population when evaluated one event at a time. Counted per host per process over a week, the distribution separates cleanly: legitimate writers appear a handful of times around logon, policy refresh or VPN connect, and the implant appears twenty-four times a day at a fixed minute. The aggregation is a single `summarize` and it is the difference between an unworkable query and a short list.
- **The COM registration path is a collection lesson that generalises well past this campaign.** A large amount of published detection content for T1053.005 keys on `schtasks.exe` command lines, and all of it returns nothing here. The events that do fire — Security 4698 and TaskScheduler Operational 106 — are emitted by the Task Scheduler service itself, so they are agnostic to how the task was registered, but 4698 depends on an audit subcategory that is off by default and the Operational channel is frequently not forwarded. Verifying those two collection settings is worth more than any rule you could write on top of them.
- **This hunt exists specifically to close the blind spot the behavior creates.** Any detection built on proxy or web-gateway logs has, by design, the least data about the hosts that most need attention: once `INetHealth` runs, the compromised machine's traffic no longer traverses the inspection point. Registry telemetry is the one place where the act of going dark is itself recorded, which makes hunting the registry the only reliable way to find hosts that have vanished from your network visibility. That is also why [[H322]]'s process-attributed DNS and network-connection telemetry should be run alongside this rather than instead of it.
- **The MSI metadata and the re-parenting both reward hunting for shape rather than for names.** A 210 MB installer claiming `Apple Inc` as its manufacturer with the ProductName `Background Service`, zero detections, and a WiX-built custom action that launches its payload through `explorer.exe`, is an artefact profile that will recur under different filenames and hashes. The UpgradeCode registry key it leaves behind outlives the deleted MSI, which makes it a cheap retrospective sweep across an entire fleet long after the file is gone.
