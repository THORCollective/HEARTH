  The shortest path from a web service account to root on an appliance is a copy of the shell that
  remembers it was owned by root. During an incident response engagement, Mandiant observed ARMORY CASTLE
  do precisely this on a BeyondTrust Remote Support appliance after exploiting CVE-2026-102764 as a

  the file `/usr/bin/dbus-authd`, then "modified the file's ownership to root and enabled Set User ID

  it sits in `/usr/bin` among hundreds of genuine daemons. Hunt for setuid-root files whose content is a
  copy of a system shell, for setuid bits appearing on files outside the small and stable set a given
  firmware build ships with, and for the chmod and chown pair that creates one.

false_positive_notes: |
  Setuid-root binaries are a normal and necessary part of Linux, so the bare existence of one is never
  the finding. A stock system legitimately ships a few dozen - `sudo`, `su`, `passwd`, `mount`, `umount`,
  `ping`, `chsh`, `chfn`, `newgrp`, `gpasswd`, `pkexec`, `fusermount`, `at`, `crontab`, `ssh-agent` and
  friends - and appliances add their own vendor utilities on top. That set is the baseline, it is stable
  for a given firmware build, and the finding is a file that is not in it. Three benign sources of change
  are worth anticipating. Firmware upgrades and patches legitimately add, remove and replace setuid
  binaries, so a baseline must be versioned per build or every upgrade will produce a wall of findings -
  this is the same versioning problem [[B057]] exists to solve. Package installation on appliances that
  permit it can introduce new setuid files with legitimate provenance. And administrator or vendor-support
  troubleshooting occasionally creates a privileged helper by hand, which is exactly the shape being
  hunted and must be resolved by asking rather than by widening the query. The content test is what makes
  this cheap to triage regardless: a legitimate setuid binary is a purpose-built program, while
  `/usr/bin/dbus-authd` was a byte-for-byte copy of `/bin/sh`. A setuid-root file whose hash matches the
  system shell has no benign explanation, because no distribution ships one and no administrator needs
  one. Hash-matching the shell set is therefore a stronger first filter than path or name heuristics.

# H387

`/usr/bin/dbus-authd` is not a real program. It just looks like one.

ARMORY CASTLE copied `/bin/sh` to that path, made root the owner, and set the SUID bit. From then on the unprivileged web service account could run a root shell on demand. Mandiant's description of the consequence is worth keeping, because it explains why this tiny change matters so much: it gave them "access to every credential the appliance stored or brokered and the ability to modify files that survive reboot and configuration reset."

The name is doing real work. `/usr/bin` holds hundreds of daemons, a good number of them with `dbus-` prefixes, and `dbus-authd` sounds like authentication plumbing for a message bus. An analyst reading a directory listing has no reason to stop on it. A path like `/tmp/rootsh` would have been found in an afternoon.

How they got there is the now-public CVE-2026-102764, a file-upload vulnerability in BeyondTrust Remote Support that ARMORY CASTLE used as a zero-day in late August 2026. POST requests to `/app_84304470%2Ephp`, and eleven minutes later the SAWFLY webshell appeared in the Laravel public directory. SAWFLY is careful too — if the POST does not carry its parameter `_c94mfe`, it returns a 404 and exits, so crawlers and vulnerability scanners see nothing. But it ran as the site service account, unprivileged. The setuid shell is what closed that gap.

Which makes the hunt pleasantly concrete, because there is a test that does not depend on guessing which names look suspicious.

Setuid-root binaries are normal. A stock Linux ships a few dozen, appliances add vendor utilities, and the set is stable for a given firmware build. So the first question is which setuid files are not in that baseline. The second question is the better one: hash every setuid-root file and compare it against the shipped shells. A setuid-root file whose content *is* `/bin/sh` has no benign explanation at all. No distribution ships one. No administrator needs one. That single test would have found `dbus-authd` regardless of what it was called.

Two practical constraints are worth knowing before anyone runs this.

The baseline has to be versioned per firmware build, because upgrades legitimately add and replace setuid binaries. An unversioned baseline produces a wall of findings after every patch and gets switched off. That is precisely the problem [[B057]] exists to solve, and this hunt is the Flames counterpart to it — B057 answers "is this permission bit supposed to be here", H387 is the specific behaviour that answer makes visible.

And on a managed appliance you may not be able to look. Mandiant notes the relevant logs sit on a LUKS-encrypted partition and that customers "cannot audit the appliance host file system." Their recommendation for a confirmed or unknown-status appliance is not to clean it but to rebuild it, because host-level persistence survives reboot and configuration reset. Snapshot with memory and export the disk *before* any change or reboot — the evidence is destroyed by the obvious first response.

## Why

- **A setuid-root copy of the system shell has no legitimate counterpart.** Hash-matching setuid files against the shipped shells is a content test with essentially no false-positive surface, independent of filename or path.
- **The filename was chosen to survive human review, not machine review.** `dbus-authd` in `/usr/bin` reads as system plumbing. Name-based intuition is exactly the wrong detection strategy here, which is why the hunt is built on permission bits and hashes.
- **The setuid set is small, enumerable and stable per firmware build.** That makes the anomalous-file question tractable in a way most appliance questions are not.
- **It converted a webshell into root, which is what made everything after it possible.** Mandiant ties root directly to access to every credential the appliance stored or brokered, and to files that survive reboot and configuration reset.
- **The webshell above it is built to defeat scanning.** SAWFLY answers anything without its `_c94mfe` parameter with a 404 and exits, so crawler-based and scanner-based discovery will not find it. The privilege artefact on disk is the more reliable observable.
- **Appliances are the blind spot this exploits.** No EDR agent, no software inventory entry, no file integrity monitoring, and in this case a log set the actor deleted throughout the intrusion.
- **Catching the creation needs rules set in advance, and saying so is part of the hunt.** The chmod and chown syscalls are auditable, but only if the rules were already loaded — so the state check is the retrospective half and the audit rules are the forward-looking half.
- **The actor deleted logs as routine practice, so state beats history here.** Mandiant observed systematic deletion of system, web server and application logs, which argues for hunting the artefact that remains rather than the command that created it.
- **The fix is rebuild, not removal, and the hunt should hand over that recommendation.** Deleting the setuid file leaves the sudoers and boot-script persistence in [[H388]] and the tunnel in [[H389]] untouched.
