false_positive_notes: |
  Trusted Publishing Domain export is a real administrative operation with real legitimate uses, and they are infrequent enough that reviewing each one by hand is tractable — which is what makes this hunt viable despite the technique having no dedicated log source. Genuine occasions: migrating an RMS cluster to new hardware or a new forest; establishing a trust relationship with another organisation's RMS deployment or with Azure Information Protection; backing up the cluster key as part of a documented disaster-recovery procedure, which is explicitly recommended practice and is therefore expected to appear; and vendor-assisted troubleshooting during a support engagement. Each of these is planned, attributable to a named administrator, performed from a management host, and accompanied by a change record — so the tuning approach is to reconcile every observed export against change management rather than to build behavioural exclusions. The higher-value false-positive concern runs the other way: a legitimate TPD export produces a key file that then has to be stored somewhere, and an exported TPD sitting on a file share, in a backup, in a documentation repository or in an engineer's mailbox is the same compromise by a slower route. Hunting for those files is a worthwhile companion exercise. Note also that reading `/_wmcs/admin/` POSTs will surface other admin operations besides export, since the SOAP body rather than the URI carries the operation name — so expect the initial query to return legitimate administrative traffic that must be triaged by body inspection or by correlation with the acting identity, and size the hunt accordingly. Finally, HSM-backed clusters cannot have the key extracted this way at all, and Azure Information Protection is not affected; confirming which deployment model is in use is the first triage step and may close the hunt immediately.
notes: |
  The primary detection, IIS logs - Core filter: `POST` requests to `/_wmcs/admin/` on any AD RMS cluster node. The SOAP operation name lives in the request BODY, which IIS does not log, so the URI alone cannot distinguish `ExportTrustedPublishingDomain` from benign administration — which is precisely why every POST to this path needs triage rather than alerting. Triage values - `cs-username`, `c-ip`, `cs(User-Agent)`, `sc-status`, `time-taken`. Strong red flags - `c-ip` is a WORKSTATION rather than an RMS server or a sanctioned management station; the user agent is a scripting library or a custom string rather than an RMS or Microsoft management client; the request occurs outside a change window; `time-taken` and the response size are materially larger than for routine admin calls, since the response carries a key blob. Practical first query - enumerate every distinct `cs-username` and `c-ip` pair that has ever issued a POST to `/_wmcs/admin/` in the retained logs and review the list; this is small in almost every environment and is the fastest path to a finding.
  The detection gap that defines this hunt - `ExportTrustedPublishingDomain` does NOT appear in the DRMS logging database, which records only `GetLicensorCertificate`, `Certification.Certify`, `Certification.Precertify`, `TemplateDistribution` and `GroupExpansion`. No Windows Event ID fires by default. An environment relying on RMS's own logging for coverage of its own root key is blind to the single most damaging operation the product supports, and confirming whether IIS logs from the RMS nodes are collected and retained at all is the first and most valuable output of this hunt.
  Precondition worth checking before hunting - the `keyprotection` admin operation returns `IsServicePrivateKeySoftwareBased`. If it is `true`, the key is software-protected and extractable by this path. If the cluster is HSM-backed, the hardware prevents extraction and the hunt can be de-prioritised. Determining this once, per cluster, correctly scopes the entire effort.
  The export format, for recognising the artefact - The default TPD export produces a password-protected blob using a SHA-256 key derived from the supplied password with a HARDCODED initialisation vector `01-02-03-04-05-06-07-08-09-0A-0B-0C-0D-0E-0F-10` under AES-128-CBC, yielding a 1172-byte CAPI `PRIVATEKEYBLOB` in little-endian form. The hardcoded IV means the protection is only as strong as the password chosen at export time, so a stolen TPD file with a weak password is equivalent to a stolen key. Hunt for exported TPD files by extension and structure on file shares, in backups, in documentation repositories and in mail, and treat any found outside a controlled key store as a compromise of the cluster.
  Alternative extraction path, the database - Core filter: direct reads of the RMS configuration database tables holding the encrypted SLC material by an identity that is not the RMS service account. This path needs integrated-security access to SQL rather than Service Group membership, so it is a different privilege and a different detection: SQL Server audit or Extended Events on the configuration database, correlated against the small expected set of service identities. Include the SQL host in scope when investigating, because an attacker with database access does not need to touch the admin SOAP surface at all.
  Post-theft activity, forged Rights Account Certificates - Core filter: the stolen SLC key can sign a forged RAC, letting the attacker request use licenses from the LIVE server as a forged identity. That activity DOES appear in the RMS logging database, as certification and licensing requests. Look for licensing requests for identities that do not correspond to real directory principals, requests for a given user arriving from an unexpected source, and a single source requesting licenses across an unusually broad set of protected content. Note the server still evaluates authorisation against AD, so this path is constrained by what the forged identity is permitted to open — which is why offline decryption is the more attractive option for an attacker and the one that leaves no trace at all.
  Why the impact justifies the hunt cost - The SLC is not a credential that can be rotated. Replacing it invalidates every document ever protected by the cluster, so most organisations cannot realistically rotate it after a suspected compromise. A leaked key therefore grants permanent, silent, offline access to all historically protected content — including documents protected before the intrusion and documents protected after it — with no server contact and no rights evaluation. This is the rare case where the absence of evidence must be treated as a reason to hunt harder rather than as reassurance, because the technique's defining property is that it does not generate any.

# H308

Huntress's two-part analysis of Active Directory Rights Management Services describes something more uncomfortable than a vulnerability. AD RMS protects documents by sealing them to a cluster key — the Server Licensor Certificate. Anyone holding the SLC private key can decrypt any document the cluster has ever protected, entirely offline, with no server contact, no credentials, and no rights evaluation. The key cannot meaningfully be rotated, because rotating it invalidates every document ever sealed to it. And the supported administrative operation that hands it over, `ExportTrustedPublishingDomain`, writes nothing to the Windows event log and nothing to the RMS logging database.

That last point is the whole reason this is a hunt rather than a detection. The DRMS logging database records `GetLicensorCertificate`, `Certification.Certify`, `Certification.Precertify`, `TemplateDistribution` and `GroupExpansion` — a reasonable set, and one that conspicuously omits the export of the cluster's root key. The only record is an IIS W3SVC line for a POST to `/_wmcs/admin/`, and because the SOAP operation name lives in the request body rather than the URI, even that line does not say what was done. An environment that does not collect and retain IIS logs from its RMS servers has no evidence that this operation ever occurred, and most environments do not collect them, because AD RMS is typically a decade-old deployment nobody has looked at since it was installed.

The practical consequence is that the hunt's first and most valuable output is usually not a finding but an answer to a prerequisite question: are these logs being kept at all, and is this cluster software-key or HSM-backed? The `keyprotection` admin operation returns `IsServicePrivateKeySoftwareBased`, and if the cluster is hardware-backed the technique does not work and the effort can be redirected. If it is software-backed, the working query is small enough to run by hand — enumerate every username and source IP that has ever POSTed to the admin endpoint and review the list. Legitimate TPD export is infrequent and planned, which makes reconciliation against change management a realistic tuning strategy. It is also worth hunting the *output* rather than only the act: a legitimate export still produces a key blob, protected by a password under a hardcoded IV, and an exported TPD sitting in a backup or a documentation share is the same compromise arriving by a slower route. B047 builds the standing baseline that makes all of this answerable in seconds rather than in an afternoon of archaeology.

## Why

- The operation that steals the root of trust generates no Windows event and no application log entry, so an organisation relying on AD RMS's own auditing is blind to the single most damaging thing the product can be made to do. Establishing whether IIS logs from the cluster are retained is a finding in its own right.
- The stolen key is effectively unrotatable. Replacing the SLC invalidates every document the cluster has ever protected, so most organisations cannot rotate after a suspected compromise — which means the loss is permanent and applies retroactively to content sealed long before the intrusion.
- Offline decryption leaves no trace on the server at all. Once the key is out, the attacker never touches the infrastructure again, so post-theft detection is impossible and the entire defensive opportunity sits in the narrow window of the export itself.
- The legitimate population is small and planned, which makes an otherwise low-fidelity signal workable. TPD export happens during migrations, federation setup and documented backups, all of which are attributable and change-managed, so reconciliation rather than behavioural tuning is a realistic strategy.
- The exported artefact is protected by a scheme with a hardcoded initialisation vector, so its security reduces entirely to the password chosen at export time. That makes hunting for stray TPD files on shares, in backups and in mail a high-value companion exercise with a concrete remediation.
- AD RMS deployments are typically old, lightly monitored and outside the scope of modern identity tooling, while still protecting the documents an organisation considered sensitive enough to encrypt. The combination of high value and low visibility is exactly what makes it worth a deliberate hunt rather than waiting for an alert that cannot fire.
