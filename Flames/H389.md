false_positive_notes: |
  Reverse proxies on appliances legitimately route to loopback services - that is the normal architecture,
  and the appliance ships with several such backends. The finding is not the existence of a
  loopback-bound backend but the presence of one that is not in the build baseline, which is why this
  hunt is a diff and not a pattern match. Expect legitimate change from three directions. Firmware
  upgrades rewrite `haproxy.conf` and will change the ACL and backend set wholesale, so an unversioned
  baseline produces a false wall after every patch - version per build, as [[B057]] does. Vendor support
  engineers occasionally add a temporary route or a debug backend during a case, which looks identical and
  is resolved by asking the case owner rather than by widening the query. And some customer-side
  integrations documented by the vendor do add routes. WebSocket traffic is likewise normal here: remote
  support products use WebSockets for session transport, so an HTTP 101 upgrade to the appliance is
  expected and only an upgrade to an UNDOCUMENTED path is interesting. Long-lived connections are also

# H389

The backdoor listened on `127.0.0.1`. That is normally the sentence that ends an investigation, because nothing outside the host can reach a loopback port.

ARMORY CASTLE picked loopback deliberately, and then edited the appliance's reverse proxy to publish it.

BARECLAW — a SOCKS5 proxy carried over WebSocket, written in C with an embedded CivetWeb server — ran as `/tmp/ingredi_ws --listen 19800 --token %REDACTED% --obfs -q --ws-path /uidchanarge`. Listening on 19800, serving a WebSocket endpoint at `/uidchanarge`, requiring a token, obfuscating traffic with an XOR routine derived from that token, and `-q` to log nothing at all.

Then two stanzas went into `/ns/config/haproxy.conf`: an ACL matching the path `/uidchanarge`, and a backend sending those requests to `127.0.0.1:19800`.

HAProxy is the appliance's own reverse proxy — it already terminates TLS on 443 with a valid certificate and routes requests to the appliance's local services. The attacker added one more route. No new port opened. No firewall rule changed. No certificate needed. The appliance's legitimate front door now serves a SOCKS5 tunnel into the internal network, and Mandiant spells out why the loopback binding was the right choice: it "ensures that the backdoor listener remains completely hidden from external network scans, as it can only be reached internally via HAProxy's local redirection."

So every instinct about where to look is wrong here. An external port scan sees 443, exactly as it did last week. A listening-socket inventory on the box shows a loopback listener, which reads as benign in isolation — plenty of legitimate appliance services bind to loopback. Neither half is suspicious alone. The conjunction is the finding.

Of the two halves, the proxy configuration is the one worth building a hunt on, because it is a file with a known-good version. The appliance ships `haproxy.conf` per firmware build. Diff it. An ACL and a backend that are not in the baseline are a question with an owner, and the answer is a change record or an incident.

The traffic side has a signal too, and it is Mandiant's own guidance: watch for request paths outside the known Remote Support path set, including unknown `.php` paths and WebSocket upgrades. The nuance is that WebSocket upgrades to this appliance are *normal* — remote support products use them for session transport — so the query cannot be "a 101 response" and has to be "a 101 response to a path nobody documented." Likewise, long-lived connections are normal for an appliance whose job is hour-long support sessions, and the actor set `timeout tunnel 5h` to blend into exactly that. Duration is a weak signal here. The path is a strong one.

One caution against dismissing a finding: the actor left TLS and authentication off on the inner hop, because BARECLAW disables them by default and they never supplied `--ssl-cert`. An unencrypted loopback hop is not evidence of something harmless.

## Why

- **Loopback binding is the stealth mechanism, not a mitigating factor.** The report states the local-only binding hides the listener from external network scans, which inverts the usual reasoning about `127.0.0.1` listeners.
- **The appliance's own TLS listener and certificate carry the tunnel.** Nothing new was exposed, so perimeter scanning, firewall review and certificate inventory all look unchanged.
- **The proxy configuration has a known-good version per firmware build.** That makes the detection a diff against a baseline rather than a judgement call, which is the cheapest reliable test available on an appliance.
- **Neither half of the mechanism is suspicious alone; the pair is.** A loopback listener is ordinary and a proxy backend is ordinary. A proxy backend pointing at a loopback port that is not in the vendor set is not.
- **The URI path is the durable network signal, and WebSocket upgrades alone are not.** This product legitimately uses WebSockets for session transport, so the query must exclude the documented path set rather than match on upgrades.
- **The tunnel is configured to imitate a long support session.** `timeout tunnel 5h` means connection duration will not separate it from legitimate traffic on this appliance.
- **The tunneler suppresses its own logging.** `-q` means the appliance has no record of it, so the observable has to be the configuration file, the socket inventory, or traffic seen in front of the device.
- **It provides general-purpose internal network access, so the blast radius is every reachable host.** A SOCKS5 relay on an appliance that sits between the internet and the internal estate is an arbitrary pivot, and Mandiant notes every endpoint touched is in scope for downstream hunting.
- **A configuration backup taken after the compromise reinstalls it.** Restoring the wrong backup restores the malicious stanzas, which is why the report's guidance is to restore only a backup predating the exposure window.
- **It is the inverse of HEARTH's existing tunnel coverage.** Existing hunts cover outbound, client-initiated channels from endpoints; this is an inbound listener published through a vendor reverse proxy, with different telemetry entirely.
