  - C:\Windows\System32\inetsrv\ is a legitimate Microsoft directory containing IIS native modules, all signed
    by Microsoft. On a real IIS web server, DLL writes there occur during IIS feature installation, .NET
    servicing updates, and third-party IIS module installs (URL Rewrite, ARR, WebDeploy, APM agents).
  The separators, in order of strength:
  (1) PATH plus SIGNER plus ROLE. An UNSIGNED, non-Microsoft DLL in System32\inetsrv on a host that does not run
      IIS is the finding. The directory was chosen precisely because it looks systemic; on a non-web-server it
      has no reason to gain new files at all. Inventory which hosts actually serve IIS first — that list is
      short, and everything off it becomes high-fidelity.
  (2) SERVICE REGISTRATION SHAPE. Event 7045 with an ImagePath pointing at a DLL in inetsrv, installed by an
      -EncodedCommand PowerShell process rather than by an MSI or Windows Update. Legitimate IIS modules are
      installed by trusted installers, not by base64 blobs.
  (3) PROCESS ATTRIBUTION ON THE NETWORK SIDE. Enumerate the processes that legitimately talk to
      graph.microsoft.com in your estate — it is a bounded, nameable list. A svchost.exe instance hosting a
      service whose DLL lives in inetsrv, or any unsigned binary, reaching that hostname is outside it.
  (4) CADENCE. Legitimate Graph clients are bursty and event-driven. A C2 poll is regular. Beacon-interval
      analysis on the SNI, grouped by source process, separates them without needing to decrypt anything.
  (5) IDENTITY SIDE. The token in use belongs to an attacker-controlled tenant, not yours. Non-interactive
      sign-in logs and Graph Activity Logs for your own tenant will NOT show this traffic — its absence from your
      tenant logs while the host is demonstrably talking to Graph is itself a discriminator.
  Enumerate your IIS hosts and your legitimate Graph-calling processes as named populations before scoring.

  STARTING QUERY — the host anchor (Defender XDR):

    DeviceFileEvents
    | where Timestamp > ago(90d)
    | where FolderPath has @"C:\Windows\System32\inetsrv"
    | where FileName endswith ".dll"
    | where ActionType in ("FileCreated", "FileModified")
    | where InitiatingProcessFileName !in~ ("TiWorker.exe", "TrustedInstaller.exe", "msiexec.exe")
    | project Timestamp, DeviceName, FileName, FolderPath, SHA256,
              InitiatingProcessFileName, InitiatingProcessCommandLine, InitiatingProcessAccountName

  Join that against your IIS inventory and keep only the non-IIS hosts. Then pivot to service creation:

    DeviceEvents
    | where Timestamp > ago(90d)
    | where ActionType == "ServiceInstalled"
    | where AdditionalFields has "inetsrv"

  and to the network side, attributed by process:

    DeviceNetworkEvents
    | where Timestamp > ago(30d)
    | where RemoteUrl in~ ("graph.microsoft.com", "login.microsoftonline.com")
    | summarize Connections = count(), Days = dcount(bin(Timestamp, 1d)),
                IntervalStdDev = stdev(datetime_diff('second', Timestamp, prev(Timestamp)))
              by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath
    | where InitiatingProcessFolderPath !has @"\Program Files"

  A low interval standard deviation on a long-running series is the beacon; enumerate and name your legitimate
  Graph clients first so the query returns the unnamed ones.

# H269

PhantomGraph's command-and-control channel is a OneDrive account.

Not a OneDrive-themed domain. Not a lookalike. The two service DLLs authenticate against `login.microsoftonline.com` and then read and write task files under `https://graph.microsoft.com/v1.0/me/drive/root:/` on an attacker-controlled tenant. Every byte goes to a genuine Microsoft endpoint, over a genuine Microsoft certificate, to a hostname that is on your proxy allowlist and — in most estates, for performance and privacy reasons — explicitly exempted from TLS inspection.

There is nothing to block and nothing to sinkhole. Threat intelligence does not help: the indicator would be "graph.microsoft.com."

So hunt the other end. The backdoor still had to land somewhere, and it chose `C:\Windows\System32\inetsrv\` — the IIS native modules directory — for `SysExcSvc.dll` and `SysReadSvc.dll`, registered as services by a base64-encoded PowerShell command. That path is systemic-looking camouflage, and it is also the mistake: on a host that does not run IIS, that directory has no reason to ever gain a new file.

## Why

- **The network side is unwinnable and the host side is nearly free — so invert the hunt.** Every detection instinct says "find the C2 traffic." Here that instinct produces a query returning every Office application, the OneDrive client, Teams, Intune, Defender, and half the management agents in the estate. Meanwhile the host-side anchor — an unsigned, non-Microsoft DLL appearing in `System32\inetsrv` on a machine with no IIS role — has a natural false-positive rate close to zero once you have an IIS inventory, and that inventory is a one-time, small piece of work. This is a case where the cheap detection is the one nobody builds because it does not look like C2 detection.

- **Choosing a Microsoft endpoint defeats an entire category of controls at once.** Domain blocklists, newly-registered-domain scoring, certificate-reputation checks, JA3 fingerprinting against known C2 profiles, DNS sinkholing, and every IOC feed all key on infrastructure the adversary owns. Here they own none of it. The only attacker-controlled asset is a tenant account you cannot see, and the only attacker-controlled string is a OneDrive folder name inside an encrypted session. Estates that measure their C2 coverage by "how many bad domains do we block" have no coverage of this at all and no way to notice.

- **The service-installation event is the highest-fidelity moment in the whole chain.** Event 7045 firing for a service whose `ImagePath` sits in `inetsrv`, installed by a PowerShell process running `-EncodedCommand`, is not something any legitimate IIS module deployment does — real modules arrive via MSI, Windows Update, or the Web Platform Installer, all of which are named, signed, and attributable. One event, one host, no baseline required. It is also durable: the operator can rename the DLLs and change the service names freely, but they cannot make base64 PowerShell service installation look like `TrustedInstaller.exe`.

- **Beacon cadence still works even when the destination does not.** You cannot use the hostname to distinguish the backdoor from Teams, but you can use the *shape* of the conversation. Legitimate Graph clients are event-driven and bursty — a user opens a file, a sync kicks off, a policy refreshes. A backdoor polling for tasks is regular. Grouping connections to `graph.microsoft.com` by initiating process and scoring interval regularity separates them without decrypting anything, and it requires only the network telemetry you already have. Enumerating the legitimate Graph-calling processes first is a bounded, nameable job; anything left over is the question.

- **Absence from your own tenant logs is a discriminator, not a gap.** Defenders reasonably reach for Entra ID sign-in logs and Graph Activity Logs when they see Graph traffic — and find nothing, because the token belongs to the attacker's tenant. That mismatch is diagnostically useful in itself: a host demonstrably establishing sustained sessions to `graph.microsoft.com` with no corresponding activity in your own tenant's Graph logs is either an unmanaged personal account or something worse, and both are worth knowing about.

- **This intrusion turned a conferencing server into a distribution channel, so the blast radius is not the server.** Head Mare used the web shell on the TrueConf server to swap the legitimate client installer for a trojanised one, then served it to conference participants — a supply-chain step that pushes PhantomCore onto every endpoint that installed the client. Detecting the backdoor on the server is therefore not a single-host finding; it defines the population that needs to be checked next. The report's `unsigned_trueconf_installer` rule exists for precisely that reason.

- **HEARTH has eight hunts touching T1102 broadly, but none for T1102.002 specifically** — bidirectional C2 over a legitimate web service, where the adversary reads *and* writes through infrastructure you cannot block. That is the pattern most likely to be underserved by an IOC-driven programme, and it is the one this week's intel showed twice.
