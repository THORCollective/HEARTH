false_positive_notes: |
  Password prompts during installation are normal on macOS, and that is exactly why the lure works, so the
  benign population has to be separated carefully rather than excluded by keyword. Legitimate installers
  prompt constantly - any package needing administrative rights triggers the real system authorization
  dialog, and VPN clients, backup agents, virtualisation products, printer drivers and developer tooling all
  do it routinely. The critical distinction is architectural, not textual: a legitimate installer requests
  authorization through the Security framework and the system presents the dialog, so the credential is
  handled by the operating system and never reaches the installer. A malicious script draws its own dialog -
  typically through `osascript` with `display dialog` and `with hidden answer` - so the plaintext password is
  returned to the script as a string. Those two cases look identical to the user and look completely
  different in ESF exec telemetry, which is the whole basis of the hunt. Three legitimate patterns do
  approach it and should be named rather than tuned away. Some enterprise tooling and MDM scripts genuinely
  prompt with AppleScript for a password, and some help-desk automation does the same; both are
  identifiable, both should be inventoried, and both are worth questioning on their own merits because they
  are a bad practice independent of this campaign. Legitimate scripts also call `dscl` for directory reads
  all the time - user enumeration, group membership, home-directory lookups - so the `dscl` leg must be
  scoped to the `-authonly` verb specifically, which is authentication rather than lookup. Finally, cleanup
  of temporary files by installers is completely standard, so the deletion leg is corroboration only and
  carries no weight by itself.

# H379

Anyone can put up a dialog asking for a password. What makes this one worth a hunt is that it checks the answer.

AhnLab tracked roughly 1,500 JSCEAL infections across Korea in August and September 2026, delivered through Facebook ads impersonating a cryptocurrency exchange. The landing page mimics the real exchange — logo, colours, live prices — and fingerprints the visitor's OS before assembling an installer for them in the browser. Windows users get a BAT file. macOS users get a PKG, named to look like a versioned release.

The PKG's `postinstall` script pulls a second shell script from a remote server, runs it, and deletes the temporary files behind it. That script draws a password prompt localised to the system language. And then it verifies the password against the actual account before writing it to a file.

That verification step changes what the attacker walks away with. An unverified harvest is a pile of strings, some of them typos, some of them deliberate garbage from a suspicious user. A verified harvest is a list of credentials that are known to work, on hosts the operator knows are real. It also tells them immediately which victims are worth coming back to.

It is also the step that cannot be done quietly. Checking a macOS password locally means `dscl . -authonly`, or a Security-framework authorization call, or an Open Directory authentication — and every one of those leaves a trace. The attacker has traded silence for certainty.

The dialog itself is the harder half to detect, because password prompts during installation are completely normal. That is the entire basis of the lure. But there is a clean architectural line between the two cases, and it shows up in exec telemetry even though it is invisible to the user. A legitimate installer asks the *system* to authorize, the system draws the dialog, and the credential never reaches the installer at all. A malicious script draws its own dialog — `osascript`, `display dialog`, `with hidden answer` — and gets the plaintext password back as a string. Same picture on screen. Completely different argv.

Two scoping notes that matter for making this work. `dscl` is called by legitimate scripts constantly, for user lookups and group membership and home directories, so the query has to be anchored on `-authonly` specifically — that verb is authentication, not lookup. And if the hunt turns up enterprise MDM or help-desk scripts prompting for passwords with AppleScript, those are real findings of a different kind: inventory them, because that is a bad practice whether or not anyone is attacking you.

One thing deliberately left out. The Windows half of this same campaign is real and is in the report, but its Node.js-runtime leg is substantially what [[H343]] already hunts and its Defender-exclusion leg is covered several times over. The Windows indicators are recorded in the notes for pivoting — the `Binance.lnk` shortcut planted on the public desktop is the most distinctive — and the hunt is scoped to macOS, where the credential-validation behaviour has no coverage at all.

## Why

- **Verification turns a guess into an asset.** A password confirmed against the local directory service is known-good, which makes the whole collection more valuable and tells the operator which hosts to revisit.
- **The verification is the one step that cannot be silent.** Checking the credential locally requires `dscl . -authonly`, a Security-framework call, or an Open Directory authentication, all of which are observable. The attacker bought certainty with telemetry.
- **The user cannot tell the real prompt from the fake one, and exec telemetry can.** A legitimate installer delegates to the system and never touches the password. A malicious script draws its own dialog and receives plaintext. Identical on screen, unmistakable in argv.
- **`-authonly` is the discriminator that keeps the `dscl` leg usable.** Directory reads are everywhere; a password check inside an installer process tree is not.
- **There is no stable hash or URL to block.** The PKG is generated client-side from server-supplied configuration, so it is different every time. Behavioural detection is not a preference here, it is the only option.
- **Clipboard access by an installer-spawned script is independently anomalous.** `pbpaste` in the argv of a script descending from `installd` is a cheap additional query with its own signal.
- **The LaunchAgent is attacker-configured per victim, so hunt its shape not its name.** Label and path come from the server. What generalises is an agent created during an install that runs a scripting runtime against a user-writable path with `RunAtLoad` set.
- **Legitimate AppleScript password prompts found along the way are their own finding.** Enterprise tooling that harvests passwords through a dialog is handing attackers a credible template, and it should be inventoried regardless of this campaign.
