false_positive_notes: |
  Legacy authentication by service accounts is common and usually benign in origin - it is the residue of integrations written before modern authentication, and most tenants carry some. That is precisely why it is useful here and also why it cannot be alerted on alone. The query is not "which principals use legacy authentication" but "which legacy-authentication sign-in came from an address that also appears in a web exploitation log". The second condition is what makes the first actionable.

  Shared egress addresses will create spurious joins. A corporate NAT address, a cloud provider range, or a SaaS integration's published egress range may legitimately appear in both web logs and identity logs, and matching on it proves nothing. Exclude known corporate and vendor ranges before correlating, and weight residential, hosting and tunnel-provider ASNs heavily - the observed address is also embedded in a Pinggy tunnel hostname, which is about as clear a provenance signal as an address carries.

  Retention is the most common reason this hunt returns nothing. The correlation spans about twelve hours in the observed case but the useful search window is days, and web access logs on busy application servers often rotate faster than identity logs are reviewed. A clean result from a host whose logs cover six hours is not a clean result.

  Service accounts querying a data warehouse is their job, so the warehouse leg needs the principal-and-source pairing to mean anything. A service account appearing from a new source address, or querying object sets it has never touched, is the signal; query volume alone is noise.

  Kerberos pre-authentication failures occur legitimately in volume - misconfigured clients, expired credentials, scanning tools - so Event ID 4768 and 4625 patterns are a weak standalone signal. In this intrusion the AS-REP roasting attempt failed, which means the only reliable evidence of it is the attempt pattern from the application server's address, not a successful ticket.

  A failed technique still establishes intent and position. The Impacket run and the Crowd API enumeration did not succeed in the observed case, and a hunt that only looks for successful credential access will score this intrusion as less severe than it was.
notes: |
  Leg one, forward correlation, web to identity (access logs joined to sign-in logs) - Core filter, and the primary hunt: collect every distinct source address that appears in internet-facing application access logs in a suspicious role - requests to the Axis SOAP endpoint H510 covers, or to any recently disclosed exploitation path - and search Microsoft 365 and Entra ID sign-in logs for successful authentications from those addresses over the following seven days. Exclude corporate egress and vendor ranges first. Red flags on a match, heaviest first - the principal is a non-human integration or service account; the authentication used legacy protocols rather than modern authentication; the address belongs to a hosting, residential-proxy or tunnel-provider ASN; the sign-in is the first ever from that address for that principal.

  Leg two, reverse correlation, identity to web (sign-in logs joined to access logs) - Core filter: enumerate every legacy-authentication sign-in by a non-human principal in the last 30 days, extract the source addresses, and search web and application access logs for each. This direction is the cheaper one to automate because the input set is small - most tenants have a short list of principals still using legacy authentication, and it should be a shrinking list. The output is either empty or an incident.

  Disabling the protocol is better than detecting its abuse, and the two should be run together. An inventory of principals still permitted legacy authentication, with an owner and a retirement date each, converts this leg from a recurring hunt into a closed gap.

  Leg three, the credential store itself (application database and file telemetry) - The reason this chain worked is that the wiki held the credentials. In the observed intrusion the attacker authenticated to MySQL with Confluence's own database credentials just over three minutes after first execution, and queried page bodies, application links, and attachments whose names were associated with credentials, tokens, VPN configurations and private keys. Two practical consequences. First, database query logs are evidence - a local MySQL authentication by the application's own credentials from a shell rather than the JVM, followed by reads of page body and attachment metadata tables, is the collection step. Second, the inventory question is worth answering before any incident - which credentials, tokens, VPN configurations and private keys currently live in wiki pages and attachments? That list is the blast radius of any compromise of this host, and B017 and B025 are the baselines for it.

  Leg four, the Active Directory attempt (domain controller telemetry) - The attacker used a Confluence application credential against the internal Atlassian Crowd API to enumerate users and group memberships, then ran Impacket's `GetNPUsers.py` against a domain controller to attempt AS-REP roasting. Both legs are hunt-able. For Crowd, look for API authentication from the application host to the Crowd service enumerating users and groups outside the application's normal pattern. For the roasting attempt, look at Kerberos pre-authentication requests from the application server's own address:

      Windows Security Event ID 4768 where the source address is an application server
        and PreAuthType is 0 (pre-authentication not used)
      Windows Security Event ID 4625 clustered from the same source address

  The decisive condition is the source - a Linux application server has no reason to request Kerberos tickets for accounts at all, let alone for accounts that do not require pre-authentication. Pair this with the standing hygiene check for accounts configured with Kerberos pre-authentication disabled, which is the population AS-REP roasting targets; that list should be empty or justified.

  Leg five, the data warehouse (warehouse authentication and query logs) - Core filter: a service account authenticating to the production cloud data warehouse from a source address not on its expected list, or querying object sets it has no history of touching. Roughly four hours elapsed between first exploitation and warehouse access in the observed case, which makes this the leg where an intrusion that started on one Linux host becomes a data-exposure question.

  Scope note: H161 is the closest existing hunt for the Active Directory half - it covers NTLM relay coercion launched from a compromised Confluence or F5 host, which is the same adversary position attacking the same target, by a different mechanism; this hunt covers Kerberos pre-authentication harvesting and Crowd API enumeration from that position, and neither appears in H161. H369 and M034 touch legacy authentication and cloud service-account abuse respectively, but neither correlates an identity event back to a web exploitation source address, which is this hunt's core filter. B017 and B025 baseline legitimate access to Confluence credential material and to information repositories, and they are what makes leg three answerable. H510 covers the exploitation that opened this chain and H511 the automated enumeration that found the credentials.

# H512

Twelve hours and two consoles apart, the same IP address shows up twice.

In Rapid7's account of the CVE-2026-90436 Confluence intrusion, `192.238.253[.]176` appears first in exploit requests against the Confluence server, and again in the hostname of the Pinggy tunnel that delivered the attacker's tasking. Then, about twelve hours after the first exploit request, it appears a third time — as the source of a successful Microsoft 365 sign-in, by an integration service account, using legacy authentication.

What connected the two was the wiki's contents. Rapid7 states that the access they observed relied on credentials stored in Confluence. The attacker read page bodies, application links, and attachments whose names suggested credentials, tokens, VPN configurations and private keys; roughly four hours in they had a service account credential and were querying a production cloud data warehouse. Along the way they used a Confluence application credential against the internal Atlassian Crowd API to enumerate users and groups, and ran Impacket's `GetNPUsers.py` at a domain controller to try AS-REP roasting. That last part failed. The rest did not.

Each half of this looks like something tolerable in its own tool. A legacy-authentication service account is a hygiene backlog item. An unauthenticated POST to a Java servlet is scanning noise. The join is the incident, and nothing joins them automatically.

## Why

- The correlation is free and almost nobody runs it. Both logs are already collected; the only missing ingredient is a query that treats a web server source address as an identity indicator. It needs no new telemetry, no agent and no vendor.
- Legacy authentication is the attacker's preferred door precisely because it is everyone's open hygiene item. It bypasses the conditional-access and MFA controls that protect modern authentication, and the population using it is small enough to enumerate — which makes the reverse direction of this hunt a short, repeatable list rather than an open-ended search.
- A wiki is a credential store whether or not anyone intended it to be. The exposure is not the server; it is every secret anyone ever pasted into a page or attached to one. That inventory is worth having before an incident, because it is the only thing that converts "a Confluence host was compromised" into a scoped response.
- The chain crosses boundaries that usually correspond to different teams. Linux application server, application database, Active Directory, a cloud data warehouse, and a Microsoft 365 tenant — five owners, four consoles, one intrusion. The hunt is built the way it is because the handoffs are where this kind of activity survives.
- The failed steps matter for scoping. The AS-REP roasting attempt and the Crowd enumeration did not succeed, and an investigation that only records successes will understate both the attacker's intent and their position inside the network.
