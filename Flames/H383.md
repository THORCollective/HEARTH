title: Windows service whose binary lives in a developer-toolchain root - C:\msys64 as a persistence path
hypothesis: >-
  A service binary is hiding in a directory that every service-path baseline ignores and every developer
  recognises. AhnLab tracked a SEO-poisoned fake KakaoTalk installer campaign in which, in the latest
  variant, "the malicious file was created in the C:\msys64 Path, registered as a Service, and executed;
  the final payload was identified as Ghost." `C:\msys64` is the default installation root of MSYS2, the
  Unix-like build toolchain for Windows. It sits at the root of the system drive rather than under
  `Program Files`, it is routinely user-writable, it legitimately contains several thousand executables
  and DLLs with Unix names, and it appears in no standard allowlist, no Microsoft-signed inventory and
  almost no organisation service-path baseline. A service pointed into it is therefore both plausible to
  a human reviewer and invisible to the usual query, which looks for service binaries in `%APPDATA%`,
  `%TEMP%`, `%ProgramData%` or `C:\Users\Public`. Hunt service creation where the resolved image path
  falls inside a developer-toolchain root on the system drive, and treat the same paths as a gap in the
  existing service baseline rather than as a new indicator.

false_positive_notes: |
  MSYS2 is real software with a real user base, and on a developer estate `C:\msys64` will be present and
  busy. It ships thousands of binaries with Unix names, its package manager writes into the tree
  constantly, and `pacman` updates will generate large bursts of file creation under it that look like
  staging activity if nobody knows what the directory is. The same applies to `C:\cygwin64`, `C:\mingw64`,
  `C:\tools` (the Chocolatey convention), `C:\msys32` and `C:\Strawberry`. None of that is the finding.
  The finding is narrow and specific: a WINDOWS SERVICE whose image path resolves inside one of those
  trees. Legitimate MSYS2 does not install a Windows service. Cygwin can, for `sshd` and `cron` through
  `cygrunsrv`, and that is a genuine exception that exists on some hosts and must be scoped by name
  rather than by broadening the query - note that a legitimate `cygrunsrv` service has a recognisable
  binary and a recognisable service name, so the exception is cheap to write. The other benign pattern to
  expect is developer-built services: an engineer testing a service they compiled in an MSYS2 or MinGW
  environment, which happens on build and test machines and is identifiable by host role and by the
  binary being a project artefact. Beyond that, two scoping cautions. First, do not invert this into a
  broad allowlist-everything-under-Program-Files rule - the point is that the toolchain roots are a gap,
  and filling the gap means adding them to the baseline, not replacing it. Second, on hosts with no
  MSYS2 installation at all, the existence of `C:\msys64` is itself the anomaly and should be treated as
  such before anyone looks at services, because the attacker gains the camouflage of the path without
  needing the product.

# H383

The service binary was in `C:\msys64`.

That is the whole trick, and it is a good one. Every service-anomaly query in existence asks whether the image path sits somewhere a user can write, and almost every one of them implements that as a list: `%APPDATA%`, `%TEMP%`, `%LOCALAPPDATA%`, `%ProgramData%`, `C:\Users\Public`, maybe `C:\Windows\Temp`. `C:\msys64` is user-writable, sits at the root of the system drive, and is on none of those lists.

It also has something none of those paths have, which is plausibility. An analyst who sees a service running out of `C:\Users\Public` knows instantly that something is wrong. An analyst who sees one running out of `C:\msys64` on an engineer's machine thinks: MSYS2, build toolchain, probably something somebody compiled. The directory legitimately contains several thousand Unix-named executables and DLLs. It is a very comfortable place to stand.

AhnLab found it at the end of a long, patient SEO-poisoning campaign against Korean users searching for KakaoTalk. The installer rotated packaging — NSIS, then Advanced Installer, then Inno Setup — and each package carried the real KakaoTalk files alongside the malicious ones, so the victim ends up with working software and no reason to look twice. The shellcode loader evolved across variants too: sRDI, then Donut, then added XOR, then a move from `CreateFile` to `VirtualAlloc`, then code virtualisation, and finally the shellcode hidden encrypted inside a PNG. Filenames were randomised — and, in a detail worth pausing on, the random strings were sometimes fetched from an external web service at `www.qmsjmfb[.]com`, because the operator wanted names no signature could anticipate.

The final payload in the `C:\msys64` variant was Ghost. The domain it reached, `damaix9k[.]com`, matched infrastructure previously reported as a Ghost C2 that had delivered MODBEACON. AhnLab raises SilverFox / UTG-Q-1000 as a possibility and then explicitly declines to attribute on C2 similarity alone — worth preserving if anything built on this hunt gets written up.

Most of this chain is already hunted in HEARTH. DLL side-loading has broad coverage, and `javacpl.exe` loading `deploy.dll` is one more instance of it. The steganographic PNG shellcode is close to [[H246]]. So this hunt is scoped deliberately to the part that has no coverage, and the honest framing is that it is less an indicator than a hole in an existing baseline.

Which suggests running the better version of the query. Rather than adding `C:\msys64` to a list and moving on, rank every service on the estate by whether its image path sits outside both `Program Files` trees and `System32`, and read the tail. That finds the toolchain roots and everything else nobody thought to contemplate.

Two scoping notes. Cygwin genuinely does install services through `cygrunsrv` — `sshd` and `cron` — so that exception is real and needs writing down by name. And on a host with no MSYS2 installation at all, the existence of `C:\msys64` is the anomaly, before anyone looks at services: the attacker gets the camouflage of the path without needing the product.

## Why

- **The path is user-writable and absent from every standard service-anomaly list.** The usual query enumerates `%APPDATA%`, `%TEMP%`, `%ProgramData%` and `C:\Users\Public`. A toolchain root at `C:\` is none of those.
- **It is semantically camouflaged in a way those paths are not.** A human reviewer reads `C:\msys64` as a build environment and moves on. That combination — invisible to the query, plausible to the analyst — is what makes it worth naming.
- **MSYS2 does not install a Windows service, so the conjunction is narrow.** The directory being busy is normal. A service pointed into it is not, with one nameable exception in `cygrunsrv`.
- **The gap-closing query is worth more than the indicator.** Ranking every service by whether its image lies outside `Program Files` and `System32` finds this path and whatever else the baseline never contemplated.
- **Nothing else in the chain is stable enough to detect on.** Packaging rotated through three installers, the loader rotated through five techniques, and filenames were randomised from a remote service. The persistence path is the part that held still.
- **The installer ships working software, so there is no user suspicion and no report.** The victim gets a functioning KakaoTalk. The endpoint is the only place this campaign is visible.
- **Fetching random filenames from a web service is a distinctive and queryable habit.** A non-browser process pulling a short response from an unclassified domain immediately before creating a randomly-named file is unusual on its own terms.
- **`C:\msys64` on a host that never installed MSYS2 is the finding before services are even considered.** The camouflage does not require the product, so the directory's bare existence is the cheaper question.
- **The one gap-flagged technique was not huntable, and saying so is part of the result.** T1608.006 describes the actor staging content on their own infrastructure. No victim telemetry exists for it, which is why this hunt targets the service path instead.
