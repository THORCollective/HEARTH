title: A systemd unit named like a Zimbra logging component, installed outside the application tree and timestomped to match sshd
hypothesis: >-
  An operator who already has root on a mail server establishes host persistence with a systemd unit
  called `zimlog.service` - a name that reads as a legitimate Zimbra logging component. The unit is
  not where Zimbra's own units live - it was staged in `/tmp`, moved into `/etc/systemd/system/` with

  `/etc/systemd/system/` by mtime sees nothing recent. The unit was enabled with `systemctl enable`

  name - a unit file in `/etc/systemd/system/` whose mtime is implausibly identical to a distro
  package's unit, a unit owned by a non-root service account, and a unit whose name implies a vendor
  application while living outside that vendor's own directory.

false_positive_notes: |
  Units in `/etc/systemd/system/` are legitimately created all the time - that directory is precisely where a local administrator or a configuration-management agent is SUPPOSED to put units, so the presence of a non-package unit there is normal and not by itself a finding. Expect to see units for monitoring agents, backup software, container runtimes, custom application services, and anything an engineer wrote by hand. Do not hunt "unit file exists".
  The discriminators are narrower and much better behaved. First, PACKAGE OWNERSHIP combined with NAME IMPLICATION - a unit whose name claims a vendor application (`zimlog`, `zimbra-*`, `nginx-*`, `mysql-*`) but which belongs to no package AND lives outside that vendor's own directory tree is the shape to chase. Zimbra's genuine components live under `/opt/zimbra/`, so a "Zimbra logging" unit installed to `/etc/systemd/system/` and owned by the `zimbra` account is not how Zimbra ships anything. Second, OWNERSHIP - unit files are normally `root:root`. A unit file owned by a service account is unusual enough to enumerate exhaustively, and Microsoft specifically observed the unit "assigned to the Zimbra service account". Third, TIMESTAMP IMPLAUSIBILITY - this is the strongest and least intuitive axis. Legitimate units acquire their mtime from the package transaction or from the moment an engineer wrote them. A unit whose mtime matches `sshd.service` or `rsync.service` TO THE SECOND, while belonging to no package, is not a coincidence; distro packages for unrelated components are not installed in the same second by different transactions. Build the check as "group unit files by exact mtime and flag any group that mixes package-owned and non-package-owned files".
  Two caveats that will produce noise if ignored. Container and orchestration tooling (Docker, Podman, Kubernetes, systemd-nspawn) generates transient and templated units programmatically, sometimes in bursts with near-identical timestamps - scope those out by path and by generator rather than tuning thresholds. And image-based or golden-image deployments can give MANY files an identical mtime because they were all laid down by the imaging process, which defeats the timestamp axis on freshly provisioned hosts; check the host's provisioning date before treating a timestamp cluster as timestomping, and prefer `ctime` (which `utimensat` does not forge) against `mtime` as the internal consistency check - an mtime older than its own ctime is the tell that the mtime was set deliberately.
detection_queries:
  - platform: Microsoft Defender XDR (KQL)
    description: Microsoft's published Zimbra persistence and privilege-escalation query, verbatim from the source report - the file-evidence half, which covers the named units.
    query: |
      let lookback = 30d;
      DeviceFileEvents
      | where Timestamp > ago(lookback)
      | where FileName in~
        ("zimlog.service", "chronyd-helper.service", "syslog_init.service", "81_metric")
         or FolderPath == "/etc/pam.d"
         or FolderPath == "/etc/sudoers.d"
      | project Timestamp, DeviceId, DeviceName, EvidenceType="File",
                ActionType, FileName, FolderPath,
                ProcessCommandLine=InitiatingProcessCommandLine,
                InitiatingProcessFileName, InitiatingProcessCommandLine, ReportId
      | order by Timestamp desc
  - platform: Shell (triage census)
    description: Enumerate unit files in /etc/systemd/system that belong to no package, with owner and both timestamps. The ctime-vs-mtime comparison is what exposes a forged mtime.
    query: |
      for f in /etc/systemd/system/*.service; do
        pkg=$(rpm -qf "$f" 2>/dev/null || dpkg -S "$f" 2>/dev/null || echo NO_PACKAGE)
        case "$pkg" in NO_PACKAGE*) stat -c '%n owner=%U mtime=%y ctime=%z' "$f";; esac
      done
  - platform: Shell (triage census)
    description: Group unit files by exact mtime; a group mixing package-owned and unowned files is the timestomp signal.
    query: |
      find /etc/systemd/system /usr/lib/systemd/system -maxdepth 1 -name '*.service' \
        -printf '%T@ %u %p\n' | sort -n | awk '{print $1}' | uniq -d
  - platform: auditd rules
    description: Watches that make the install and the timestamp forgery attributable after the fact.
    query: |
      -w /etc/systemd/system/ -p wa -k systemd_unit
      -a always,exit -F arch=b64 -S utimensat,utimes,futimesat -F auid>=1000 -F auid!=4294967295 -k timestomp
notes: |
  Platform: Linux (Zimbra Collaboration Suite on a mail server; the unit-masquerading pattern is product-agnostic). Driven by Microsoft Threat Intelligence, "Unauthenticated command injection on internet-facing mail servers: tracking CVE-2026-73570" (September 30, 2026).
  Where this sits in the campaign - CVE-2026-73570 is an unauthenticated OS command-injection flaw in Zimbra's SNMP notification path; a crafted SMTP request causes `swatchdog` to fold attacker input into an `snmptrap` shell invocation, executing commands as the `zimbra` service account. [[H352]] covers the escalation from that service account to root via PAM and sudoers. This hunt covers what the operator does with root - establishing boot persistence that does not look new.
  The reported artifact, exactly as published - Microsoft describes "a second persistence mechanism established through a systemd service named `zimlog.service`". The name "was consistent with a Zimbra logging component, but the payload was manually installed in `/etc/systemd/system/`, outside the Zimbra application directories". The unit file "was moved from `/tmp` into the system-wide systemd directory using `sudo` and assigned to the Zimbra service account". Its "timestamps were then modified to match existing systemd services, including `rsync.service` and `sshd.service`". It "was enabled with `systemctl enable`, establishing execution at system boot, and its status was subsequently checked". Microsoft's remediation guidance asks defenders to "review systemd units for unexpected ownership, enablement, or timestamp changes, including units that resemble Zimbra or operating-system logging components".
  A second unit name from the same report - Microsoft's ATT&CK table notes that alongside `zimlog.service`, "a separate payload installed `chronyd-helper.service` as a root service". The Defender query above also carries `syslog_init.service`. All three follow the same naming logic - impersonate a logging, time-sync or OS housekeeping component, because those are the units a responder is least likely to question and least likely to be able to recall the legitimate name of. Retro-hunt all three strings, and treat the NAMING PATTERN as the durable property.
  Why timestomping is the most useful axis here - it is the only step in the chain that the operator could not accomplish without leaving an internal inconsistency. `utimensat` sets `mtime` and `atime` but NOT `ctime`; the kernel updates `ctime` on the metadata change itself. So a unit file whose `mtime` predates its own `ctime` has had its mtime set deliberately, and that comparison requires no baseline, no allowlist and no knowledge of the campaign. It is a single `stat` away on any Linux host. Pair it with package attribution - matching `sshd.service`'s timestamp while belonging to no package is the specific shape Microsoft observed.
  Why the ownership axis is worth collecting separately - unit files are conventionally `root:root`, and systemd does not require otherwise. A unit owned by `zimbra`, `postfix`, `apache`, `www-data` or `mysql` is both unusual and, where it exists, a direct pointer at which service account was compromised. This is a cheap estate-wide census with a very short expected result list.
  Triage path on a hit - resolve the unit's `ExecStart` target and hash it; check `systemctl is-enabled` and `systemctl cat` for drop-ins that may override a benign-looking `ExecStart`; look for the staging copy or its removal in `/tmp` and `/var/tmp`; and pivot on the invoking account to [[H352]] and the service-account baseline in [[B056]], since a root-installed unit on a mail server implies the escalation already succeeded. Microsoft also observed broader persistence redundancy in the same campaign - OpenRC scripts under `/etc/init.d/` with `rc-update`, cron entries in `/etc/cron.d/` and `@reboot`, shell startup files (`/etc/profile`, `/etc/bashrc`, `.bash_profile`, `.zprofile`), `.ssh/authorized_keys` modification, and local account creation via `useradd`/`adduser` - so a single unit found is a reason to enumerate all of those, not to close the case.
  Detection breadth beyond what the report attests - Microsoft documented the three unit names above and the `rsync.service`/`sshd.service` timestamp match. The mtime-versus-ctime consistency check, the package-attribution census and the non-root-owner census are this hunt's generalisation of that behaviour and were NOT described in the report; they are offered because they detect the technique without depending on the observed strings. The unit names, the staging path and the account assignment are the attested artifacts.

# H353

Microsoft's September 2026 report on CVE-2026-73570 exploitation describes an operator who, having reached root on a Zimbra mail server, wanted persistence that would survive a reboot and not attract attention. They wrote a systemd unit called `zimlog.service`.

The name is the whole trick. It reads as a Zimbra logging component, and a responder scanning `/etc/systemd/system/` has no particular reason to doubt it — most people cannot recite the legitimate unit names of a mail suite they did not install. But Zimbra's own components live under `/opt/zimbra/`; this unit was staged in `/tmp`, moved into the system-wide directory with `sudo`, assigned to the `zimbra` service account, and enabled for boot. Microsoft observed a companion payload do the same thing under the name `chronyd-helper.service`, and their hunting query carries a third, `syslog_init.service`. Logging, time sync, OS housekeeping — the three categories nobody questions.

The operator then modified the unit's timestamps to match `rsync.service` and `sshd.service`, so sorting the directory by modification time surfaces nothing recent.

That last step is the one worth building a hunt on, because it cannot be done cleanly. Setting `mtime` through `utimensat` leaves `ctime` untouched by the caller — the kernel updates it on the metadata write. A unit file whose `mtime` is older than its own `ctime` has had its timestamp forged, and that check needs no allowlist, no baseline, and no knowledge of this campaign. Combine it with package attribution and file ownership and you have three independent census questions, each with a very short expected answer, that together catch the technique without depending on the three names above.

## Why

- Timestomping is self-incriminating at the filesystem level. `utimensat` forges `mtime` but the kernel still bumps `ctime`, so `mtime < ctime` on a unit file is direct evidence of deliberate timestamp manipulation. That single comparison is available via `stat` on any host, requires no prior baseline, and generalises to every file-based persistence location — which makes it unusually durable for a hunt derived from one campaign.
- The masquerade targets the exact gap in responder knowledge. Impersonating a logging or time-sync component works because defenders can rarely recall the legitimate unit inventory of a third-party application. Reframing the question as "which units belong to no package" replaces recall with an authoritative check that the package database already answers.
- Unit-file ownership is a near-empty census with high diagnostic value. Units are conventionally `root:root`; one owned by `zimbra`, `postfix` or `www-data` is both anomalous and a direct pointer at which service account was compromised, letting a single query identify both the persistence and the initial foothold.
- The attacker needed root to install it, so a hit upgrades the incident immediately. Finding a non-package unit owned by a service account on a mail server implies the privilege escalation in [[H352]] already succeeded, which changes containment urgency and credential-rotation scope before any payload is even analysed.
- The campaign deliberately built redundant persistence, so one finding is a starting point rather than a conclusion. Microsoft observed the same operation also using OpenRC scripts, `/etc/cron.d/` and `@reboot` entries, shell startup files, `authorized_keys` modification and local account creation — enumerating all of them on a hit is the difference between eviction and reinfection at next boot.
- Boot-time persistence on an internet-facing mail server is worth auditing regardless of this actor. The census this hunt asks for — non-package units, non-root owners, forged timestamps — is cheap, runs estate-wide, and leaves behind a reusable inventory.
