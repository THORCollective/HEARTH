false_positive_notes: |
  A single address legitimately serving many service principals is normal in several shapes, and each needs an allowlist entry rather than a tuning rule:
  - A NAT or secure-web-gateway egress IP in front of a CI/CD estate, a Kubernetes cluster or an integration platform can front dozens of app identities. Allowlist by the egress range plus the set of application IDs that normally appear behind it, not by the IP alone - the point of the hunt is a *new* application ID appearing behind a known address.
  - A managed service provider or ISV operating a multitenant application authenticates to many tenants from its own infrastructure. Microsoft reports a case where "a multitenant application credential was compromised at the source (vendor-owned application) and used to access multiple downstream tenants", so an MSP address is a reason to call the MSP, not a reason to suppress.
  - Secret rotation genuinely produces AADSTS7000222 (expired secret) followed by a success from the same address. Separate rotation from credential testing by checking the Entra audit log for a matching `Update application - Certificates and secrets management` event in the same window, and by the count of distinct application IDs: rotation touches the apps one team owns, testing touches apps with no common owner.
  - Developers debugging locally produce failures from a residential address against one or two apps they own. Require three or more unrelated application IDs before the fan-out criterion is met.
  Multi-resource token requests are also normal for a deliberately broad integration (a backup product, a CSPM scanner, a migration tool). Those have a stable audience set; keep 30 days of audiences per application ID so a first-ever audience is visible.
notes: |
  Entra ID service principal sign-in logs - Core filter: group service principal sign-ins by `IPAddress` over a 1-hour window and keep addresses with 3 or more distinct `ApplicationId` values that have no common owner in your app inventory. Within each group, keep the addresses that show both a success and a failure. Triage values: `Timestamp`, `IPAddress`, `ApplicationId`, `ServicePrincipalId`, `ServicePrincipalName`, `ResourceDisplayName`, `ResourceTenantId`, `ErrorCode`, `UserAgent`, `CorrelationId`, `RequestId`. The two error codes Microsoft calls out are `7000215` (invalid client secret) and `7000222` (expired client secret); Microsoft's guidance is that these "indicate someone holds a credential for your app; a failure followed by a success is urgent." Keep failures - a tenant that only looks at successful sign-ins cannot see which of its applications an operator is holding a secret for.
  Sample Defender XDR query - fan-out and the failure-then-success pair:
  ```kql
  let window = 1h;
  let signins = EntraIdSpnSignInEvents
      | where Timestamp > ago(30d)
      | where isnotempty(ApplicationId);
  signins
  | summarize Apps = make_set(ApplicationId, 100),
              AppCount = dcount(ApplicationId),
              Failures = countif(ErrorCode != 0),
              Successes = countif(ErrorCode == 0),
              CredErrors = make_set_if(ErrorCode, ErrorCode in (7000215, 7000222)),
              UserAgents = make_set(UserAgent, 20),
              Resources = make_set(ResourceDisplayName, 20)
        by IPAddress, bin(Timestamp, window)
  | where AppCount >= 3 and Failures > 0 and Successes > 0
  | order by AppCount desc
  ```
  `EntraIdSpnSignInEvents` retains 30 days in Defender XDR advanced hunting, so `ago(30d)` is the widest useful lookback there; run the same logic over the `AADServicePrincipalSignInLogs` diagnostic table in Log Analytics for anything longer. The failure-then-success ordering is not expressible in the summarize above - confirm it per application ID by ordering that app's sign-ins by `Timestamp` and checking that a `7000215`/`7000222` row precedes an `ErrorCode == 0` row.
  Sample Defender XDR query - per-application resource fan-out in the minutes after a first success:
  ```kql
  let firstSuccess = EntraIdSpnSignInEvents
      | where Timestamp > ago(30d)
      | where ErrorCode == 0
      | summarize FirstSuccess = min(Timestamp) by ApplicationId, IPAddress;
  EntraIdSpnSignInEvents
  | where Timestamp > ago(30d)
  | where ErrorCode == 0
  | join kind=inner firstSuccess on ApplicationId, IPAddress
  | where Timestamp between (FirstSuccess .. FirstSuccess + 30m)
  | summarize Audiences = make_set(ResourceDisplayName, 20),
              AudienceCount = dcount(ResourceDisplayName)
        by ApplicationId, IPAddress, FirstSuccess
  | where AudienceCount >= 3
  ```
  The `between` bound is what makes this a correlation rather than a coincidence - a join on `ApplicationId` alone over 30 days groups unrelated days together. Microsoft's behavioural guidance is to look for "one address authenticating to three or more service principals with mixed success, or one app requesting tokens across Azure Resource Manager, Key Vault, Storage and Graph in a short window." Treat `Azure Key Vault`, `Azure Storage`, `Windows Azure Service Management API` and `Microsoft Graph` appearing together for one application ID as the strong form.
  Entra audit log correlation - Core filter: for every application ID that appears in the fan-out, pull `Add service principal credentials`, `Update application - Certificates and secrets management` and `Add owner to application` events for the surrounding 7 days. A credential added by an identity that does not own the app, or added shortly before the first successful sign-in from the flagged address, converts the finding from "a leaked secret is being tested" to "the operator has planted their own". Microsoft's containment guidance is to remove *all* client secrets, certificates and federated credentials from an affected application, "including those added by the threat actor", because already-issued tokens stay valid until they expire.
  Follow-on activity to pivot into - Core filter: for each confirmed application ID, query `CloudAuditEvents` and `CloudAppEvents` for the same window. Microsoft reports that "The threat actor targeted operations that return credentials, including storage account keys, App Service settings, connection strings and publishing credentials, AI and machine learning (ML) connections and datastores, and Azure Kubernetes Service (AKS) user credentials." It also reports that "The compromised applications subsequently accessed SharePoint and OneDrive in the targeted organization tenants, including file downloads and mailbox-item access", and that "The agents once authenticated have also searched Azure DevOps for secrets." Strong red flags: a storage `listKeys` or Key Vault `secrets/list` call by an application ID that has never made one; a Microsoft Graph search by an application whose business function does not involve content search; an Azure DevOps audit entry for PAT creation or a new federated service connection attributed to the same identity.
  Expected, not observed by Microsoft: the same fan-out shape should appear for federated-credential and certificate-based applications, not only secret-based ones, because the distinguishing signal is the spread of application IDs behind one address rather than the credential type. Microsoft's reported cases involve client secrets stored in code.

# H445

Microsoft Threat Intelligence reports that threat actors are using an agentic AI offensive framework to search public GitHub repositories for exposed secrets - credentials, application credentials, and AI inference API keys - and then using those secrets against the organizations they belong to. The queries the framework submitted to GitHub "often included the name of a target organization, keywords for secrets, a keyword linked to cloud services, or a keyword linked to another AI service provider."

What makes this worth a dedicated identity-side hunt is the speed and the breadth. Microsoft writes that "In at least one case, Microsoft observed an AI agent advance from scanning GitHub for secrets to exfiltrating data from Azure Key Vault in just five minutes." From as early as October 28, 2026, Microsoft observed successful service principal sign-ins from a single address "involving multiple application IDs across some impacted customers", and the agent "successfully conducted service principal sign-ins on dozens of associated applications across multiple tenants."

Harvesting secrets in bulk means an operator ends up holding a bag of credentials of unknown quality: some valid, some rotated, some never valid. Using them produces a signature that a single legitimate integration does not - one address, many unrelated application IDs, and a mix of outcomes. Microsoft states it plainly in its hunting guidance: the two sign-in errors "indicate someone holds a credential for your app; a failure followed by a success is urgent."

This hunt deliberately sits on the identity plane rather than the resource plane. HEARTH already covers the resource-side sweep that follows - H339 hunts a single service principal with a leaked secret calling storage `listKeys` and reading Key Vault secrets across its subscriptions, and M016 models per-identity Key Vault operation volume. Neither can see the shape that tells a tenant *how many of its applications are compromised*, because both start from one identity that is already known to be bad. This hunt starts from the address and the error codes, and it answers a question no resource-side hunt can: which other application IDs is the operator holding a secret for.

## Why

- Exposed secrets stay usable until they are rotated. Microsoft is explicit that "Publicly exposed credentials remain usable until revoked or rotated; removing the original disclosure alone does not remediate the exposure" - so a secret deleted from a repository six months ago is still a live credential, and the sign-in log is the only place its use shows up.
- The credential-test fan-out is a structural consequence of bulk harvesting and cannot be tuned away by the operator. Microsoft notes that actors "can and do change the source IP address, user agent strings, and other fingerprints", but an operator holding twelve secrets of unknown validity still has to try twelve secrets, and the failures are logged whether or not the address is new.
- Failed sign-ins are the highest-value rows and the ones most often discarded. AADSTS7000215 against an application ID is positive evidence that someone outside the tenant holds a string that was once that app's secret, even when every attempt fails - it is an exposure report the tenant gets for free.
- Scoping blast radius is the part of this incident class that goes wrong. An application-by-application investigation finds the app that was used; grouping by source address finds the apps the operator *has*, which is what rotation has to cover. Microsoft's containment guidance - remove every secret, certificate and federated credential, and treat issued tokens as valid until expiry - only works if the list of affected applications is complete.
