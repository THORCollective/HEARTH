title: A mail service account owns /etc/pam.d/sudo by symlink, then grants itself NOPASSWD via a pam_exec session hook
hypothesis: >-
  An operator holding only the unprivileged `zimbra` service account reaches root without an exploit
  and without touching a setuid binary. They exploit the fact that a sudo-authorized Zimbra helper,
  `zmmailboxdmgr`, writes to its own log file as root - so they delete `zmmailboxd.out` and replace it
  with a SYMLINK to `/etc/pam.d/sudo`, invoke the privileged helper, and let it chown the PAM

  delete the staging artifacts, keeping only the sudoers entry. The durable, huntable moment is a
  non-root account causing a write or an ownership change inside `/etc/pam.d/`, and a `pam_exec`
  directive appearing in a PAM stack that has never legitimately contained one.

false_positive_notes: |
  The strength of this hunt is that almost none of its component events have a legitimate counterpart. Writes to `/etc/pam.d/` are a configuration-management action - they come from a package manager (`rpm`, `dpkg`, `apt`, `yum`, `dnf`), from `authselect` or `pam-auth-update`, or from a configuration-management agent (Ansible, Puppet, Chef, Salt). In every one of those cases the acting process runs as root with a root `auid`, and the change is correlated with a change window and a package transaction. A write to `/etc/pam.d/` attributable to a MAIL SERVICE ACCOUNT has no benign explanation, and neither does an ownership change on a file in that directory to a non-root owner. That is the finding, and it should be treated as a confirmed compromise rather than triaged.
  Three sources of genuine noise to resolve first. Package upgrades of `zimbra-*`, `pam`, `openssh-server` or `sudo` will rewrite PAM files and sudoers drop-ins legitimately, sometimes leaving `.rpmnew`, `.rpmsave`, `.dpkg-dist` or `.pacnew` siblings - correlate every hit against the package transaction log (`/var/log/dnf.rpm.log`, `/var/log/yum.log`, `/var/log/dpkg.log`) before escalating, and expect a cluster of PAM writes immediately after any patch window. Second, `pam_exec` is not inherently malicious and does have real uses - some commercial MFA/SSO products, mandatory-access-control integrations and home-directory provisioning scripts install a `pam_exec` line deliberately. Inventory the legitimate `pam_exec` population across the estate on day one; in most environments it is empty, and where it is not, the legitimate instances are identical across many hosts and point at a vendor-owned script path under `/usr/libexec/` or `/opt/<vendor>/`, not at `/tmp`, `/var/tmp`, `/dev/shm` or a path under `/opt/zimbra/`. Third, Zimbra's own helpers legitimately write to `/opt/zimbra/log/zmmailboxd.out` constantly, so the file being written is not the signal - the signal is that file being REPLACED BY A SYMLINK, which is why the `symlink`/`symlinkat` syscall axis matters more than the file-write axis.
  One caution on scoping. Because the operator restored the original PAM content and removed the temporary files, a point-in-time integrity scan of `/etc/pam.d/sudo` will come back CLEAN on a host that was successfully escalated. The surviving artifact is the sudoers entry, not the PAM file. Do not read a clean PAM diff as absence of compromise - enumerate `/etc/sudoers.d/` and the `NOPASSWD` population independently, and treat the auditd record of the transient change as the authoritative evidence if it exists.
detection_queries:
  - platform: Microsoft Defender XDR (KQL)

    query: |
      DeviceFileEvents
      | where Timestamp > ago(30d)
      | where FolderPath has_any ("/etc/pam.d", "/etc/sudoers.d") or FileName == "sudoers"

      | project Timestamp, DeviceName, ActionType, FolderPath, FileName,
                InitiatingProcessAccountName, InitiatingProcessFileName,
                InitiatingProcessCommandLine, ReportId
      | order by Timestamp desc
  - platform: Microsoft Defender XDR (KQL)
    description: Microsoft's published Zimbra persistence and privilege-escalation query, verbatim from the source report - process-side half, keyed on the pam_exec and zmstat-fd strings.
    query: |
      let lookback = 30d;
      DeviceProcessEvents
      | where Timestamp > ago(lookback)
      | where ProcessCommandLine contains "zimlog.service"
         or ProcessCommandLine contains "chronyd-helper.service"
         or ProcessCommandLine contains "syslog_init.service"
         or ProcessCommandLine contains "zimbraPreAuthKey"

         or ProcessCommandLine contains "/etc/sudoers.d/81_metric"

                ActionType, FileName, FolderPath, ProcessCommandLine,

  - platform: auditd rules
    description: Minimum watch set that makes this hunt answerable. Without these rules the transient PAM change leaves no trace once the operator restores the file.
    query: |
      -w /etc/pam.d/ -p wa -k pam_config
      -w /etc/sudoers -p wa -k sudoers_change
      -w /etc/sudoers.d/ -p wa -k sudoers_change
      -a always,exit -F arch=b64 -S symlink,symlinkat -F auid>=1000 -F auid!=4294967295 -k symlink_nonroot
  - platform: Shell (triage)
    description: Point-in-time enumeration of the surviving artifacts - the NOPASSWD population and any pam_exec directive.
    query: |
      grep -rn "pam_exec" /etc/pam.d/

      find /etc/pam.d -maxdepth 1 ! -user root -o -maxdepth 1 -type l
notes: |
  Platform: Linux (Zimbra Collaboration Suite on a mail server; the primitive generalises to any product that ships sudo-authorized helpers that write logs as root). Driven by Microsoft Threat Intelligence, "Unauthenticated command injection on internet-facing mail servers: tracking CVE-2026-73570" (September 30, 2026).
  Where this sits in the campaign - CVE-2026-73570 is an unauthenticated OS command-injection flaw in the Zimbra SNMP notification path. A crafted SMTP request introduces attacker-controlled input into SNMP notification processing; when a service-state change triggers health monitoring, `swatchdog` folds that value into an `snmptrap` shell invocation and the embedded commands execute AS THE `zimbra` SERVICE ACCOUNT. That is where this hunt begins - the attacker already has command execution, but only as an unprivileged service account, and needs root. See [[B056]] for the baseline that makes the rest of the service account's behaviour legible, and [[H353]] for the collection and exfiltration stage that follows.
  The escalation chain exactly as reported - Microsoft describes the sequence as abusing "Zimbra's legitimate, sudo-authorized service helpers and the interaction between `zmmailboxdmgr`, its writable log directory, the sudo PAM configuration, `pam_exec`, and `zmstat-fd`". The steps - (1) verify the server exposes the required Zimbra helpers and that the mailbox manager's log directory is writable; (2) back up `/etc/pam.d/sudo`; (3) replace the legitimate `zmmailboxd.out` log with a SYMLINK to the PAM configuration; (4) invoke the privileged `zmmailboxdmgr` process, which causes the PAM file to become OWNED BY the `zimbra` service account; (5) with ownership obtained, add a `pam_exec` session hook invoking a local script; (6) trigger a sudo session through the legitimate `zmstat-fd` helper, so the hook executes AS ROOT and creates a `NOPASSWD: ALL` entry for `zimbra`; (7) restore the original PAM content and remove temporary files and staging artifacts, RETAINING the sudoers entry. Microsoft confirmed the resulting root access through subsequent passwordless sudo operations. Microsoft also notes the controller contained FALLBACK paths involving Postfix, a Java agent, `zmstat-fd` and nginx, but that the observed child processes indicate the mailbox-manager/PAM path was the one successfully exercised on that server - so do not treat the specific helper names as the whole technique.
  Why this is a hunt and not a patch - nothing here is a software vulnerability. Every component is working as designed - the helper is supposed to be sudo-authorized, it is supposed to write its log as root, PAM is supposed to honour `pam_exec`, and `sudo` is supposed to read `/etc/sudoers.d/`. The flaw is the composition - a root-writing process pointed at an attacker-chosen path via a symlink is a classic privileged-file-write primitive, and `pam_exec` turns a one-shot file write into arbitrary root code execution. Patching Zimbra to 10.1.20 closes the INITIAL ACCESS but does not remove this primitive, which is why it deserves standing detection rather than a one-time remediation.
  Detection anchor 1, ownership and writes in /etc/pam.d - this is the primary signal and it is close to zero-base-rate for non-root actors. Collect `auid` (the original login UID), not just `uid`, so a change made through a helper is still attributable to the account that triggered it. In Defender for Endpoint on Linux the equivalent is `DeviceFileEvents` filtered on `FolderPath has_any ("/etc/pam.d", "/etc/sudoers.d")` with `InitiatingProcessAccountName != "root"`.
  Detection anchor 2, the symlink creation - `symlink`/`symlinkat` from a non-root `auid` where the target is under `/etc/` is the step that cannot be undone retroactively, because the operator's cleanup restores file CONTENT but the syscall record persists. This is the reason the auditd rule set above is listed as a required data source rather than an optional nicety.
  Detection anchor 3, pam_exec in a sudo stack - enumerate `grep -rn "pam_exec" /etc/pam.d/` across the Linux estate as a one-off census. In most environments the result is empty. A `pam_exec` line in `/etc/pam.d/sudo` specifically, pointing at a script outside a vendor directory, is the technique.
  Detection anchor 4, the surviving sudoers entry - Microsoft's query names `/etc/sudoers.d/81_metric` as an observed drop-in path. Retro-hunt that exact filename, but hunt the SHAPE as the durable property - any `NOPASSWD: ALL` grant to a service account that should never hold interactive privilege (`zimbra`, `postfix`, `apache`, `www-data`, `nginx`, `mysql`). Build that list from the baseline in [[B056]] rather than from intuition.
  Hardening that shrinks the primitive - Microsoft's own guidance is to "limit the blast radius of mail-server service accounts" by confining them with namespace, seccomp or AppArmor controls. Concretely - audit which Zimbra helpers are sudo-authorized and remove any that are not required; make the helper log directory non-writable by the service account, or have the helper refuse to write through a symlink (`O_NOFOLLOW`); and add the `/etc/pam.d/` and `/etc/sudoers.d/` auditd watches permanently, because they are cheap and this is not the last privileged-file-write primitive that will be found in a mail stack.
  Detection breadth beyond what the report attests - the source report documents this chain only on Zimbra, via `zmmailboxdmgr` and `zmstat-fd`. The hunt logic above deliberately widens to ANY non-root write or chown inside `/etc/pam.d/` and to the general `pam_exec` census, because the primitive is not Zimbra-specific and the same composition exists wherever a vendor ships sudo-authorized log-writing helpers. That widening is this hunt's inference and was NOT observed by Microsoft - the Zimbra-specific strings (`zmmailboxdmgr`, `zmstat-fd`, `zmmailboxd.out`, `/etc/sudoers.d/81_metric`) are the attested artifacts, and the IOCs and references below are confined to what the report actually published.

# H352

CVE-2026-73570 gets an attacker command execution on an internet-facing Zimbra server, but only as the unprivileged `zimbra` service account. Microsoft's September 2026 report on the campaign documents how operators crossed from that account to root without a second exploit, and the method is worth hunting on its own because every moving part is a legitimate, supported feature.

Zimbra ships a set of sudo-authorized helper binaries. One of them, `zmmailboxdmgr`, writes to its own log file — `/opt/zimbra/log/zmmailboxd.out` — while running as root. The attacker first confirmed the helper existed and that its log directory was writable by the service account. Then they deleted the log file and put a symlink in its place, pointing at `/etc/pam.d/sudo`. Invoking the helper made the root-privileged process write through that symlink, and the PAM configuration file ended up owned by `zimbra`.

Ownership of a PAM file is arbitrary root code execution, because PAM will run whatever `pam_exec` tells it to. The operator added a `pam_exec` session hook invoking a local script, then triggered a sudo session through a second legitimate helper, `zmstat-fd`. The hook ran as root and wrote a `NOPASSWD: ALL` sudoers entry for the `zimbra` account. With root secured, they restored the original PAM content and deleted the staging files — keeping only the sudoers entry, which is the one artifact that had to survive.

That cleanup is why this is a hunt and not an integrity check. A scan of `/etc/pam.d/sudo` on a successfully escalated host comes back clean. The evidence lives in the audit record of the transient change, in the `symlink` syscall, and in the sudoers drop-in the operator left behind.

## Why

- A non-root account writing inside `/etc/pam.d/` has no legitimate counterpart. PAM configuration is changed by package managers, `authselect`, and configuration-management agents — all of which act as root with a root `auid` and correlate to a change window. The same event attributed to a mail service account is a confirmed compromise, not a triage item, which makes this one of the rare Linux hunts with an essentially zero base rate.
- The primitive survives the patch. Upgrading Zimbra to 10.1.20 closes the SNMP command injection but leaves the symlink-through-a-root-writer composition entirely intact. Anything else that gets command execution as the service account — a future mail-stack bug, a stolen key, a webshell — inherits the same path to root, so this deserves standing detection rather than one-off remediation.
- The attacker's own cleanup dictates the telemetry you need. Because the PAM file was restored, content-based integrity monitoring produces a false negative. Only syscall-level auditing of the directory and of `symlink`/`symlinkat` records the step that actually happened, which turns an abstract "collect audit logs" recommendation into a specific, testable rule set.
- `pam_exec` is a near-empty population in most estates, so a census answers the question cheaply. One `grep -rn "pam_exec" /etc/pam.d/` across the Linux fleet either returns nothing — establishing a hard allowlist for free — or returns a handful of identical vendor-owned entries. Either outcome makes every future occurrence immediately legible.
- It generalises past the reported product. The composition is "a root process writes to a path an unprivileged account controls", and sudo-authorized log-writing helpers are common in commercial Linux appliances and mail stacks. Hunting the PAM and sudoers write surface catches the class, not just the Zimbra instance.
- The surviving sudoers entry is a durable, high-value question for any environment. `NOPASSWD: ALL` granted to a service account that should never hold interactive privilege is worth enumerating whether or not this campaign ever touched the estate.
