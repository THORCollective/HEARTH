false_positive_notes: |
  Same-length renames happen legitimately, just not randomly. Many applications write to a temporary name and rename on commit, and backup and sync clients rename constantly. The discriminator is that both names are the same length AND the new name has no structure: no extension carried over, no shared prefix with the old name, and high character entropy. Require all three before triage.
  Office and editor save patterns look superficially similar. Word, Excel and several editors create a temp file, rename the original, write the new content and delete the old name, all within a second. Exclude by initiating process for your known editor and sync-client set, and keep the hunt focused on processes with no business writing to the directory in question.
  Named streams are normal in small numbers. Zone.Identifier is the common case and should be excluded outright. The :EFS routine is distinctive precisely because streams with that name are not something ordinary software creates, but confirm against your own estate before treating one as malicious.
  Secure-delete utilities produce the overwrite pattern honestly. sdelete.exe, cipher /w and vendor data-sanitisation tools all generate repeated writes before a delete. Allowlist them by binary and signer, and treat the same pattern from an unsigned binary in a staging directory as the finding.
  Sysmon 23 archives a copy of every deleted file it matches and will fill a disk quickly if scoped broadly. Scope the FileDelete rule to the directories and extensions you care about, or use Event ID 26 and accept the loss of the archived content.
notes: |
  Rename-then-delete with preserved length - Core filter: a `FileRenamed` event where the previous and new filenames are the same character length, followed by a `FileDeleted` on the new name by the same process within a short window. Triage values: `PreviousFileName`, `FileName`, `FolderPath`, `InitiatingProcessFileName`, `InitiatingProcessCommandLine`, `InitiatingProcessId`. Defender XDR, 30-day retention:
  ```kql
  let lookback = 30d;
  let renames = DeviceFileEvents
    | where Timestamp > ago(lookback) and ActionType == "FileRenamed"
    | project RenameTime = Timestamp, DeviceId, DeviceName, FolderPath,
              OldName = PreviousFileName, NewName = FileName,
              InitiatingProcessId, InitiatingProcessFileName, InitiatingProcessCommandLine;
  let deletes = DeviceFileEvents
    | where Timestamp > ago(lookback) and ActionType == "FileDeleted"
    | project DeleteTime = Timestamp, DeviceId, DeletedName = FileName, InitiatingProcessId;
  renames
  | where strlen(OldName) == strlen(NewName) and OldName != NewName
  | where not(NewName has_any (".tmp", ".partial", ".crdownload"))
  | join kind=inner (deletes) on $left.DeviceId == $right.DeviceId,
        $left.InitiatingProcessId == $right.InitiatingProcessId,
        $left.NewName == $right.DeletedName
  | where DeleteTime between (RenameTime .. RenameTime + 2m)
  | extend Gap = DeleteTime - RenameTime
  | project RenameTime, DeleteTime, Gap, DeviceName, FolderPath, OldName, NewName,
            InitiatingProcessFileName, InitiatingProcessCommandLine
  | order by RenameTime desc
  ```
  The time window on the join is required. Joining on device and process alone over a 30-day lookback correlates renames and deletes from unrelated days.
  Scoring the new name - Add a structure test rather than relying on length alone. A generated name has no extension inherited from the original and no shared prefix. In KQL, `extend Entropy = ...` is not available, so approximate: require `NewName !has "."` where `OldName has "."`, and require that the first three characters of the two names differ. Both are cheap and remove most commit-rename noise.
  Named stream creation - Core filter: Sysmon Event ID 15 where `TargetFilename` ends in `:EFS`. The cleanup routine documented here will "Rename the provided file to :EFS (the alternate data stream area) and delete it using the native API SetFileInformationByHandle". Exclude `:Zone.Identifier` and your own known stream users. Whether `DeviceFileEvents` surfaces the stream suffix in `FileName` varies by sensor version, so validate on a test host before relying on the Defender XDR path for this half; Sysmon 15 is the dependable sensor.
  Multi-pass overwrite before delete - Core filter: three or more `FileModified` events on one path by one process within a few seconds, immediately followed by `FileDeleted`. The orchestrator command in this toolset overwrites a file's entire contents with a fixed five-stage sequence of zero bytes, one bytes, random bytes, one bytes and zero bytes before removing it (five passes as described in the report). A separate plugin "Overwrites the provided file with NULL bytes, renames it to a randomly generated filename of the same length, and then deletes it", which is the same hunt joined to the rename above.
  ```kql
  DeviceFileEvents
  | where Timestamp > ago(30d) and ActionType == "FileModified"
  | summarize Writes = count(), FirstWrite = min(Timestamp), LastWrite = max(Timestamp)
            by DeviceName, FolderPath, FileName, InitiatingProcessId, InitiatingProcessFileName
  | where Writes >= 3 and LastWrite - FirstWrite < 10s
  | order by Writes desc
  ```
  `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, so the overwrite passes are visible while the preceding read of the file is not.
  Timestamp manipulation alongside - The same toolset synchronises the modified, accessed and created times of files it writes to those of an unrelated system driver, and has a dedicated command to copy one file's MAC times onto another. Sysmon Event ID 2 covers the creation-time half. Treat a creation time that predates the directory it sits in as corroboration during triage.
  Scoping after a hit - Pivot on the initiating process to everything else it touched, then on the directory to recover the names of files deleted around the same time from `$LogFile` and the MFT if an image is available. The point of the same-length rename is to make that recovery fail, so take the image before the host is reimaged.

# H414

Kaspersky's October 2026 Operation FlashHole report documents the plugin and module set that a Lazarus Group framework deploys after it has collection in place. Two of its cleanup routines are specific enough to hunt directly, and both target the forensic record rather than the file content alone.

The first is a rename before the delete. A ClientHub plugin "Overwrites the provided file with NULL bytes, renames it to a randomly generated filename of the same length, and then deletes it", and when pointed at a directory it does the same to every file matching a pattern. The detail that matters is *same length*. Overwriting the content destroys the data, but the filename survives in the MFT and in `$LogFile` long after the delete; replacing it with a random string of identical length first means the residue carries no indication of what the file was called, and the entry looks like any other reused slot.

The second routine is unusual enough that it functions as a near-signature. The framework's action module can "Rename the provided file to :EFS (the alternate data stream area) and delete it using the native API `SetFileInformationByHandle`". Renaming a file into a named stream and then removing it through a handle-based information call, rather than through an ordinary delete, avoids the path that most monitoring watches. Streams named `:EFS` are not something ordinary software creates, which makes Sysmon's named-stream event a short and high-value queue.

Alongside both, the orchestrator carries a command that overwrites a file's entire contents in five passes — zero bytes, one bytes, random bytes, one bytes, zero bytes — before deleting it, and a command that copies one file's modified, accessed and created times onto another. Taken together these describe an operator who expects the host to be examined and is deliberately degrading what an examiner will find.

## Why

- This is the behaviour that destroys the rest of the investigation. Staging directories, archived collections and the tools themselves all go through this cleanup, so catching it early is often the difference between scoping an intrusion and guessing at it.
- The same-length rename is a stronger signal than a delete on its own. Deletes are constant on any endpoint and unhuntable in bulk; a rename that preserves length exactly while discarding all name structure, performed by a process that then deletes the result, is rare and describable in one query.
- The `:EFS` stream routine needs no scoring at all. It is a specific stream name created by a specific API pattern, Sysmon Event ID 15 reports it directly, and legitimate creators of that stream name can be enumerated in an afternoon.
- The overwrite pattern is visible in telemetry most teams already have. Three or more content writes to one path by one process inside a few seconds, immediately before a delete, separates deliberate destruction from ordinary file churn without needing file content or memory access.
