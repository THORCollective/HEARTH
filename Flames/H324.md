title: "Wiper staged into SYSVOL and launched by a new GPO startup script — the domain distributing its own destruction"
hypothesis: >-
  Rather than pushing a destructive payload host by host, the actor writes it into the SYSVOL policies
  tree on a domain controller and creates a Group Policy Object with a startup script that launches it,
  so the domain's own software-distribution channel delivers the wiper to every joined machine at once.
  No lateral-movement tooling runs against the endpoints, no remote service is created, no PsExec
  crosses the wire — the endpoints fetch and execute the payload themselves, as SYSTEM, from a path
  Windows trusts by design. The detectable asymmetry is that GPO administration is low-volume,
  highly privileged and fully audited, while the destruction that follows is loud but far too late.
  Hunt Windows domain controllers for Security event 5137 (groupPolicyContainer created) and 5136
  (modified, especially `gPCMachineExtensionNames` and `gPLink`), correlated with an EXECUTABLE or
  SCRIPT file written under `\\<domain>\SYSVOL\<domain>\Policies\{GUID}\Machine\Scripts\Startup\` or a
  change to `scripts.ini` / `psscripts.ini`. An `.exe`, `.dll`, `.ps1` or `.bat` appearing in a SYSVOL
  Startup directory is rare enough in most estates to stand as a permanent detection on its own.

false_positive_notes: |
  GPO administration is genuinely low-volume in almost every organisation, which is what makes this hunt tractable, but the benign populations are specific and worth naming. Domain controller promotion, domain functional level upgrades and Group Policy Preferences client-side extension registration all generate legitimate 5136 events against `gPCMachineExtensionNames`, and creating any new GPO through GPMC produces a 5137 followed immediately by 5136 events for `displayName` and `gPCFileSysPath` — Splunk's published rule for this explicitly filters the `New Group Policy Object` placeholder value for exactly that reason. Inter-DC replication and DFSR convergence will produce SYSVOL file activity that is not an operator writing a payload; scope Sysmon Event ID 11 to the writing process and user, and expect the DFSR service account to dominate. Software distribution done properly through GPO is the largest legitimate population of files in SYSVOL, but note WHERE it lives: MSI packages are referenced from `\Machine\Applications\`, and GPP files live under `\Machine\Preferences\`. Legitimate content in `\Machine\Scripts\Startup\` is overwhelmingly `.bat`, `.cmd` or `.ps1` written once, years ago, by a named administrator, and still present unchanged — the discriminators are RECENCY and AUTHOR, not existence. A brand-new file in a Startup directory, or a `.exe`/`.dll` in one at all, is the finding. Legitimate exceptions that will surface: printer-mapping scripts, drive-mapping scripts that predate GPP, antivirus deployment wrappers and a handful of vendor agents that ship a startup batch file. Each is stable, attributable and allowlistable by path plus hash. The strongest single discriminator is the ACTOR: GPO creation by an account that has never created one before, or a GPO change made outside a change window, separates operator activity from administration more cleanly than any file-content rule. Two ambiguity traps. First, an empty 5136 result usually means the Directory Service Changes audit subcategory was never enabled rather than that nothing changed — this is off by default and is one of the most commonly missing audit settings in the field, so verify it by making a benign GPO edit and confirming the event appears. Second, and more dangerous, SYSVOL contents CAN change without a 5136 at all when the policy files are edited directly on disk rather than through the GPMC path — tooling that writes to the share does not necessarily touch the directory object. That is why the independent recursive SYSVOL inventory is listed as a required source and not an optional one: the absence of a 5136 for an observed SYSVOL change is itself a high-signal finding, not a reason to close the lead.
notes: |
  Core filter, the directory side - Security 5137 where `ObjectClass` is `groupPolicyContainer`, and Security 5136 where `ObjectClass` is `groupPolicyContainer` and `AttributeLDAPDisplayName` is one of `gPCMachineExtensionNames`, `gPCFileSysPath`, `gPCUserExtensionNames`, `versionNumber` or `displayName`; plus 5136 on `gPLink` against a domain or OU object, which is how a new policy is attached to a scope. A `gPLink` modification at the DOMAIN ROOT by an account outside the known GPO administrator set is the single strongest event in this hunt. Security 5141 catches the cleanup afterwards. Correlate the `SubjectUserName` across all of them.
  Core filter, the file side - Sysmon Event ID 11 on domain controllers where `TargetFilename` matches `\SYSVOL\*\Policies\{*}\Machine\Scripts\Startup\*` or `\Machine\Scripts\Shutdown\*`, and the extension is `.exe`, `.dll`, `.ps1`, `.bat`, `.cmd`, `.vbs` or `.js`. Also alert on any write to `scripts.ini` or `psscripts.ini` under those policy paths - those are the two files that bind a script to the startup trigger, and modifying one is how an EXISTING, already-linked, already-trusted GPO gets a new payload without creating a new object at all. Where SACLs are in place, Security 4663 (write access) and 4670 (permissions changed) on the same paths corroborate.
  The standing detection worth building regardless of this actor - an executable or script written into ANY SYSVOL `Scripts\Startup` or `Scripts\Shutdown` directory. In most estates the legitimate population of those directories is a handful of files that have not changed in years. A recursive sweep is a one-liner and produces an allowlist that stays valid, which makes this one of the cheapest permanent detections available on a domain controller.
  How this differs from the existing GPO hunts - [[H300]] is about a GPO used to change a SETTING estate-wide, specifically the Registry client-side extension writing `EnableFirewall = 0`, where the point is that no endpoint process ever runs. [[H301]] is about non-policy FILE TYPES appearing anywhere in the SYSVOL policies tree and is found by a file-type inventory alone. [[B046]] baselines GPO administration provenance. This hunt is the third shape - a policy object created specifically to EXECUTE a staged binary at boot, which means the discriminating evidence is the pairing of a Scripts\Startup write with a `gPCMachineExtensionNames` change registering the Scripts CSE, and the outcome is destruction rather than configuration drift. Run all four; they overlap on data source and not on logic.
  Endpoint-side confirmation - Microsoft-Windows-GroupPolicy/Operational records which policies applied and which client-side extensions ran, and `gpscript.exe` is the process that executes startup and shutdown scripts. A `gpscript.exe` process with an unusual child, running as SYSTEM at boot across many hosts within the same short window, is the detonation itself. A sudden domain-wide change in the applied policy set is the coarser version of the same signal and is visible in the Group Policy History registry keys.
  Prior stages in the same intrusions, for scoping backwards - Zerologon (CVE-2020-1472) and MS17-010 for initial access and escalation; `secretsdump.py` against `ntds.dit` with output written to `ntds.txt` and SAM/SYSTEM hives to `SAM.txt`; RustHound and BloodHound for AD mapping; NetExec for SMB share enumeration; Responder with impacket-partial-mic for NTLM relay; Ligolo-ng and chisel for tunnelling; AnyDesk for persistence; rclone for exfiltration to Wasabi object storage; AdaptixC2 for command and control. Those output filenames (`ntds.txt`, `SAM.txt`) are cheap retro-hunt strings on domain controllers.
  Companion scripts named in the report - `veeam_kill.py` targeting Veeam backup infrastructure and `deploy_locker.py` distributing the encryptor. The Veeam angle matters for the T1490 half of this hunt - backup infrastructure is attacked before the encryptor runs, so Veeam service stops, Veeam SQL database access and Veeam repository deletions belong in the same timeline.
  Caveat on fidelity - Talos described the GPO staging only at comment level in the actor tooling - `# Stage wipe payload to SYSVOL`, `# Stage startup script`, `# Create GPO via PowerShell on DC`. There are no full command lines, no GPO names, no hashes and no C2 addresses for this stage in the published report. This hunt is therefore written against the MECHANISM and its audit trail, which is fully documented by Microsoft, rather than against actor strings. Do not expect to match on a GPO name.
  Actor context - The Gentlemen, active since approximately July 2025, double extortion. Talos' review of Japanese incidents in the first half of 2026 also names Qilin, SafePay, NightSpire, LockBit 5.0 and RansomEXX operating in the same set; GPO-based mass deployment is a shared playbook item across that group rather than one crew's signature, which is an argument for building this as a standing detection rather than an actor hunt.
  Triage values - `SubjectUserName` and `SubjectLogonId` from 5136/5137, the GPO GUID and `displayName`, the modified attribute and its old and new values, the SYSVOL file path, extension, hash and write time, the writing process and account from Sysmon Event ID 11, the linked scope from the `gPLink` change, and on endpoints the `gpscript.exe` lineage and the applied-policy list from Microsoft-Windows-GroupPolicy/Operational.

# H324

Cisco Talos' review of ransomware incidents in Japan in the first half of 2026 describes an intrusion by The Gentlemen — a double-extortion crew active since roughly July 2025 — that ends in a way worth separating from the rest of the ransomware corpus. Instead of pushing the destructive payload host by host, the actor stages a wiper into SYSVOL on a domain controller and creates a Group Policy Object with a startup script that launches it. The domain's own software-distribution channel does the delivery. Every joined machine fetches the payload itself, at boot, as SYSTEM, from a path Windows is built to trust — so none of the lateral-movement telemetry that ransomware detection is usually tuned around ever fires.

The asymmetry this creates is the hunt. The destruction is loud but terminal; the step that enables it is quiet, extremely low-volume, highly privileged, and — if the Directory Service Changes audit subcategory is enabled — completely recorded. Security event 5137 marks the creation of the `groupPolicyContainer`, 5136 records the attribute changes that register the Scripts client-side extension and link the policy to a scope, and Sysmon Event ID 11 on the domain controller records the payload landing in `\Policies\{GUID}\Machine\Scripts\Startup\`. An executable or script written into a SYSVOL Startup directory is rare enough in most estates to stand as a permanent detection with no tuning at all. Talos described this stage only at comment level — `# Stage wipe payload to SYSVOL`, `# Create GPO via PowerShell on DC` — so this hunt is written against the mechanism and its audit trail rather than against actor strings.

## Why

- **The privileged step is the quiet one, and it is fully audited.** Everything about the encryption and wiping phase is designed to be irreversible by the time it is visible. The GPO creation that precedes it is a handful of events per month in a typical domain, carries the responsible account in `SubjectUserName`, and is generated by Windows itself on the domain controller. Hunting a low-volume, high-privilege, well-instrumented step in order to catch a high-volume, low-latency, uninstrumented one is the correct trade.
- **A SYSVOL Startup directory has a tiny, stable legitimate population.** Most organisations have a few drive-mapping or printer scripts there, written once and untouched for years. That makes "an `.exe`, `.dll`, `.ps1` or `.bat` newly written into `Machine\Scripts\Startup\`" a detection you can stand up permanently, with an allowlist you build in an afternoon and revisit annually. Very few high-impact techniques have a benign baseline this small.
- **Modifying `scripts.ini` is the version that creates no new object at all.** The obvious form of this attack creates a GPO and gets a 5137. The subtler form adds a script to a policy that already exists, is already linked and is already trusted, by editing `scripts.ini` or `psscripts.ini` in place. Building the hunt on the file side as well as the directory side is what covers both, and it is also why an independent SYSVOL inventory is a required source: SYSVOL contents can change without producing a 5136, and that mismatch is a finding rather than a gap.
- **It differs from the GPO hunts already in the corpus on logic, not just on source.** [[H300]] covers a GPO changing a setting estate-wide with no endpoint process; [[H301]] covers anomalous file TYPES anywhere in the policies tree; [[B046]] baselines who legitimately administers policy. This one covers a policy created to EXECUTE a staged binary at boot, whose distinguishing evidence is a Startup-directory write paired with a `gPCMachineExtensionNames` change registering the Scripts CSE. They share telemetry and answer different questions.
- **The discriminator that survives everything is the actor and the window.** File names, GPO names, payload hashes and C2 all rotate, and Talos published none of them for this stage anyway. What does not rotate is that a GPO created by an account with no GPO history, or changed outside a change window, is anomalous in a way that is a fact about the organisation rather than about the malware — which is exactly the property that makes a hunt survive the next campaign.
