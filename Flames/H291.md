false_positive_notes: >-
  The single biggest source of noise is log rotation, and it produces exactly the shape this hunt looks
  for: the file shrinks to zero or near zero, the inode changes, and a non-logging process — logrotate —
  is the one that touched it. Suppress by correlating against the rotation schedule and against the
  appearance of the corresponding `.1`, `.gz` or dated archive; a size decrease WITHOUT a matching
  archive file is the real signal, and that distinction does almost all the tuning work on its own.
  Beyond rotation, expect legitimate hits from journald vacuuming (`journalctl --vacuum-size` and

  incident, and from configuration-management runs that reset log permissions. Application logs under

  append — should be enumerated once and scoped out, leaving the authentication and system logs where

# H291

The mental model most detections encode is that attackers delete logs. The better operators do not,
because deletion is loud in the one way that matters: it tells the responder which host to look at
first. An empty `/var/log/secure` on a live server is not evidence that is gone, it is a flare.

What Rapid7 documented in the DPRK activity against South Korean media and automotive organizations is
the disciplined version. The operators ran a selective filter across `/root/.bash_history`,
`/var/log/messages`, `/var/log/audit/audit.log`, `/var/log/cmd.log`, `/var/log/secure`, `/var/log/syslog`
and `/var/log/auth.log`, staging the result through `/tmp/jasper-log` before writing it back. The filter
matched on keywords — `tmp`, `wget`, `cron`, `crond` — chosen to name their own tooling rather than their
identity. Everything else in the file survived. The logs kept their normal size profile, kept being
appended to, and would pass any check that asks whether logging is working.

The keyword choice is worth pausing on, because it is the part that generalizes. Filtering on the
attacker's source IP is the obvious approach and it is also fragile — it misses every line where the IP
does not appear. Filtering on the tooling keywords removes the download, the cron persistence and the
staging directory references in one pass, across all seven files, regardless of which account or address
was in use. It is a more thorough erasure than IP filtering and it requires no knowledge of what the
logging configuration happens to record.

The technique has one structural weakness, and it is not subtle once named. These are append-only files.
`sshd`, `sudo` and the kernel add to them; nothing in normal operation removes from them. A selective
rewrite is a whole-file replacement — read, filter, write back — so the file gets *smaller*, and either
its inode changes or its ctime advances without any corresponding authentication event. Log rotation
produces the same shape, which is why the discriminator is not the shrink itself but the absence of a
matching archive: a `/var/log/secure` that lost bytes with no `secure.1` or `secure-YYYYMMDD.gz`
appearing alongside it has been rewritten, not rotated.

The other weakness is more important and it is architectural rather than forensic. All of this happens
on the host. If the lines were forwarded to a central collector as they were written, the erasure removes
the local copy of evidence that already left. Replaying the central stream against the on-disk file
turns the entire technique into a diff, and the diff is the attacker's own activity, reconstructed
precisely — including the keywords they thought worth removing, which is itself intelligence about their
tooling. Where forwarding is not in place, this hunt degrades to metadata inference that a careful
operator can also clean up, and finding that out is a legitimate outcome of running it.

Note also that `audit.log` was in the target list. An operator who can filter auditd's own log has
already dealt with auditd, so the watches this hunt recommends need companion watches on the auditd
service unit and binary — otherwise the control that would record the tampering was stopped before the
tampering happened.

This is one of four uncovered behaviours from the same intrusion. [[H289]] covers the trojanized `sshd`
that harvested credentials on the same hosts — and `auth.log` is precisely where its restarts would have
been recorded. [[H290]] covers the timestomping of the replaced daemons, the other half of the same
anti-forensic effort, and it matters here because a rewritten log can also have its mtime restored.
[[B044]] covers the load-time implant variant. On the Windows side, [[H268]] covers the equivalent
PowerShell console-history removal and [[H274]] covers an application deleting its own server log.

## Why

- **It defeats every check that asks whether logging is working.** Monitoring for absent, empty or
  stalled logs is common and catches the crude version of this technique. Selective filtering passes all
  of it: the file exists, has a normal size, has a recent timestamp, and is still being written to. The
  only way to see it is to compare what the file contains against what it should contain, which is a
  different question from whether it exists.
- **The append-only invariant is a real structural property, not a heuristic.** Authentication and system
  logs are only ever added to during normal operation. Any decrease in size is therefore anomalous by
  construction, and the single benign cause — rotation — announces itself by creating an archive file.
  Detections resting on an invariant rather than a pattern hold up against tool changes, which is what
  makes this worth building rather than signaturing.
- **Log forwarding converts the technique from an evidence-destruction problem into a diff.** This is the
  highest-value point in the hunt and it is an architecture decision, not a detection one. Lines shipped
  the moment they were written cannot be recalled. Replaying the central copy against the host copy does
  not just detect the tampering, it recovers the exact content the operator judged worth removing —
  which names their tooling, their staging paths and often their source address.
- **What they chose to filter is intelligence about how they work.** The source campaign matched on
  `tmp`, `wget`, `cron` and `crond` — a tooling-shaped keyword set, not an identity-shaped one. That is
  a deliberate choice for completeness over precision, it tells you the operator expected their download
  and persistence steps to be logged, and it points directly at the artifacts to hunt next on the same
  host.
- **`audit.log` being in the target list reorders the detection dependency.** If the auditd log is
  something the operator edits, then auditd cannot be the sole witness to its own tampering. This forces
  the same conclusion the rest of the hunt reaches from a different direction: the evidence has to live
  somewhere the operator does not control, and watches on the auditd unit and binary have to exist
  alongside the watches on the logs.
- **Shell history is the cheapest and most commonly skipped half.** `/root/.bash_history` on a jump host
  is a plaintext record of hands-on-keyboard activity, and it was first in the source campaign target
  list. It is also the file least likely to be forwarded anywhere. Shipping shell history off-host, or at
  minimum recording its size over time, costs almost nothing and closes the gap where the most
  investigation-relevant content lives.
