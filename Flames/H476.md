hypothesis: >-
  A low-privileged contractor account escalates to domain-controller identity by abusing a certification
  authority verification callback rather than a permissive template. The public exploit script creates a
  machine account with a fixed prefix and eight random uppercase letters, then requests a certificate on
  the stock Machine template on the newly created account's behalf. The request's Attributes field carries
  three things at once: the template name, a Subject Alternative Name naming a domain controller, and a
  `cdc` value pointing at a host the operator controls, which the certification authority then contacts to
  verify the request and which answers with forged data. If the certificate issues, the DC name in its
  SubjectAlternativeName is an authentication primitive for the domain controller account. The observable
  is the request, not the use: a certificate request on the Machine template whose SAN does not belong to
  the requesting principal and whose attributes point the CA at an address that is not a domain member.

false_positive_notes: |
  Machine-template enrolment is one of the highest-volume activities on any Enterprise CA, so none of the individual fields discriminates and the hunt has to key on the combination.
  - Every domain join enrols on the Machine template and every autoenrolment refresh does it again. The benign population is the entire Windows estate. The discriminator is the SAN: a normal machine certificate names the requesting computer, so a request whose SAN names a different host, and specifically a domain controller, is the finding. Filter on SAN-versus-requester mismatch first and the volume collapses.
  - Legitimate computer-account creation by users is normal in environments that have not set ms-DS-MachineAccountQuota to zero. Help desk staff, imaging processes and some software deployment tools create computer objects under their own credentials. Correlate against whether a real host ever authenticated as that account; a machine account that never produces a logon, never populates dNSHostName and never registers an SPN is hollow regardless of who made it.
  - The GHOST prefix is a property of one published script, not of the technique. Kaspersky observed it because the operators used an exploit from GitHub unmodified. A renamed fork produces a different prefix tomorrow, so treat the prefix as a cheap first pass and the SAN mismatch and the hollow-account check as the durable filters.
  - Outbound connections from a CA host are not all malicious. CRL and OCSP publication, AIA retrieval, time sync, patching and management agents all talk outward. Build the CA egress allowlist deliberately - it should be short, because a CA has few legitimate reasons to initiate a connection - and alert on anything outside it rather than on volume.
  - Enabling CA auditing changes the event volume substantially and is frequently switched off for that reason. If 4886 and 4887 are absent, this hunt cannot run, and establishing that is itself the first finding. [[H154]] covers the tampering case where the audit filter was deliberately silenced.
notes: |
  Source reporting is Kaspersky's November 11, 2026 analysis of Citrus Ransomware, a previously undocumented group that reaches victims through compromised contractors and encrypts with the Go-based Sn00py family. Kaspersky reports that initial access used "credentials stolen from these contractors' employees to connect to corporate VPNs or directly to internet-facing terminal servers over RDP," that "in every case we know of, the contractor domain account used for initial access had very limited privileges, so the attackers tried to escalate them," and that to do so "they attempted to exploit the authentication bypass vulnerability CVE-2026-54121 (Certighost); these attempts created machine accounts with telltale names in Active Directory." The observed names were `GHOSTAUFTAFGS`, `GHOSTCZYQVAZS` and `GHOSTIVPRLDZA`, which Kaspersky generalises as `GHOST{8 random letters}` and attributes to "scripts making use of an exploit published on GitHub."
  How the mechanism differs from the AD CS hunts already in HEARTH - [[H153]] covers ESC1, where the template itself permits the enrollee to supply the subject. [[H155]] covers the downstream PKINIT authentication with a forged or stolen certificate. [[H152]] covers shadow credentials written to msDS-KeyCredentialLink, and [[H154]] covers silencing the CA audit filter beforehand. This path is none of those: the template is the stock Machine template, the requester is a machine account the operator just created, and the forged element is the data returned to the CA by a host the operator nominated in the request. Kaspersky explains the `cdc` field precisely - it "specifies the IP address or name of the system that the certification authority must contact to verify the data. The attackers specify the address of a system they control (in this case, 91.210.109[.]118) and send forged data from it." The pairing to run alongside this hunt is [[H155]], because it covers the use of whatever certificate this hunt catches being requested.
  Core filter 1, the SAN that does not match the requester - The highest-value single check, and the one that survives a renamed exploit. On each Enterprise CA, read Event ID 4886 and 4887 and compare the `SubjectAlternativeName` DNS entry against the requesting principal in `Requester`. Kaspersky records the observed request fields verbatim: the `Attributes` field held `CertificateTemplate:Machine\nSAN:dns=dc01.victim.domain\ncdc:91.210.109[.]118\nrmd:dc01.victim.domain`, the `Subject` held `CN=GHOSTABUIEFAD.victim.domain`, and the `SubjectAlternativeName` held `DNS name =dc01.victim.domain`. A request from `GHOSTABUIEFAD$` for a certificate whose SAN is the domain controller is the whole finding in one row. Triage values are the template, requester, SAN, RequestID, and whether 4887 followed 4886.
  Core filter 2, the attributes themselves - Search the `Attributes` field of every 4886 for a `cdc` or `rmd` key, and for any address literal. These are not fields a domain join populates. Where the CA database is reachable, `certutil -view -restrict "RequestID=<id>" -out "RequestAttributes,RequestorName,CertificateTemplate,SubjectAltName"` returns the same information for historical requests after the Security log has rolled.
  Core filter 3, the hollow machine account - Join Event ID 4741 against the computer objects that exist today. Kaspersky's prefix gives a free first pass, but the structural check is better: a computer object created by an interactive user account, holding no `dNSHostName`, no `servicePrincipalName` and no corresponding host logon, is a machine account that exists only to make a request. Pull `mS-DS-CreatorSID` on each one; if the creator is a contractor or third-party account rather than a join service, that is the escalation attempt with its author attached.
  Core filter 4, the CA calling out - The only place the forged verification is visible. The CA host must initiate a connection to the address in the `cdc` attribute. Hunt egress from CA hosts for connections to addresses outside the domain and outside the CA egress allowlist, correlated to the minute of a 4886. In the reported case the address was 91.210.109[.]118, which Kaspersky also records as the destination for the group's keylogger output - so the same address answers two different questions in one environment.
  Sample host-side reconciliation on a CA, to list machine-template requests whose SAN does not look like the requester, run from an elevated prompt on the CA:
  ```powershell
  $rows = certutil -view -restrict "Disposition=20,CertificateTemplate=Machine" `
                   -out "RequestID,RequestorName,CertificateTemplate,SubjectAltName,NotBefore" csv |
          ConvertFrom-Csv
  foreach ($r in $rows) {
    $requester = ($r.'Requestor Name' -split '\\')[-1].TrimEnd('$')
    $san       = $r.'Subject Alternative Name'
    if ($san -and $requester -and ($san -notmatch [regex]::Escape($requester))) {
      [pscustomobject]@{
        RequestID = $r.'Request ID'
        Requester = $r.'Requestor Name'
        SAN       = $san
        Issued    = $r.'Certificate Effective Date'
      }
    }
  }
  ```
  Disposition 20 is the issued state, so this returns requests that succeeded; rerun with `Disposition=30` for failed and `Disposition=31` for denied to see attempts the CA refused, which are equally interesting and much less likely to have been noticed.
  What follows, for scoping the rest of the intrusion - Kaspersky reports that once privileged, the group ran mimikatz from `C:\ProgramData\x64\`, deployed a modified peeping-tom keylogger as `C:\ProgramData\Oracle\Java\jhost.exe` logging to `C:\Users\<username>\AppData\Roaming\Microsoft\CLR\ErrorLog.txt`, used Snaffler against network shares, ran ADRecon on domain controllers and SharpHound on a workstation, and created scheduled tasks through Impacket atexec with eight-character random names whose actions carry a doubled path such as `C:\Windows\System32\..\System32\cmd.exe`. Any of those corroborates a hit here.
  Expected, not observed by Kaspersky - Whether the certificate issued in the reported environment and whether the domain-controller authentication succeeded. Kaspersky describes the exploit mechanism and states what a successful issuance would permit, but reports the activity as attempts; it does not say the escalation completed.
  Scope - Any Active Directory forest running an Enterprise CA, and in particular forests reachable by third-party or contractor accounts, which is the access shape this group uses. Environments where ms-DS-MachineAccountQuota is still at its default of 10 are the ones where the first step of this chain needs no privilege at all.

# H476

The account was called `GHOSTAUFTAFGS`. Then `GHOSTCZYQVAZS`. Then `GHOSTIVPRLDZA`.

Eight random uppercase letters after a fixed prefix, because whoever wrote the exploit script on GitHub needed a name and did not care what it was. Kaspersky found these machine accounts sitting in Active Directory at victims of Citrus Ransomware, a group that gets in through contractors' stolen credentials and arrives with almost no privilege at all.

The escalation is the interesting part, and it is not the AD CS abuse most people have read about. There is no permissive template here. The template is `Machine` — the stock one, the one every domain join uses. What is forged is not the subject the requester supplies; it is the answer the certification authority receives when it checks.

The request's `Attributes` field carries a `cdc` value, and `cdc` tells the CA which system to contact to verify the data. The operators put their own address there. The CA dutifully asked, their host dutifully lied, and the certificate came back with a domain controller's name in its Subject Alternative Name. From there, the DC name in that field is enough to authenticate as the domain controller account.

So the finding lives in one row of one log: a certificate request on the Machine template, from a machine account created minutes earlier by a contractor's user account, asking for a certificate that names the domain controller.

And there is a second, stranger observable. For this to work, your certification authority has to make an outbound connection to an address on the internet. A CA should almost never do that.

## Why

- **The forgery happens outside the request, so request-side template review misses it.** Hardening templates against enrollee-supplied subjects — the ESC1 posture work most teams have done — does not address a path where the CA is pointed at an attacker-controlled verifier. A template audit returns a clean bill of health for this.
- **The SAN mismatch is a near-free discriminator in a very noisy event stream.** Machine-template enrolment is constant, but a machine certificate naming a host other than its requester is not a thing a domain join produces. One comparison between two fields in Event ID 4886 reduces the entire estate's enrolment traffic to a workable list.
- **The hollow machine account outlives the exploit's naming convention.** The `GHOST` prefix is one script's choice and will change. A computer object created by a human account, with no DNS host name, no service principal name, and no host that ever logged on as it, is a structural artefact of the technique rather than of the tool.
- **It catches an escalation reached from the lowest-privilege access there is.** This group arrives as a contractor with "very limited privileges", and in a default forest any authenticated user can create ten computer objects. The hunt sits exactly where a third-party credential turns into domain-controller identity, which is the step that decides whether the rest of the intrusion happens.
- **The CA's own egress is a detection surface nobody watches.** Certification authorities are monitored for what is issued and rarely for what they connect to. A short, deliberate allowlist for outbound traffic from a CA host turns a subtle protocol abuse into an obvious one, and the same control helps against other verification-callback bugs that have not been published yet.
