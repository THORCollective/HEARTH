false_positive_notes: |
  Two conditions that are individually common produce most of the noise. A mismatch between file name and `OriginalFileName` — or an empty `OriginalFileName` — happens legitimately with installers and self-extractors, with vendors who never populate the version resource, and with in-house tools. Executables in another product's folder happen legitimately with plugins, shell extensions and bundled runtimes. The conjunction is the signal: an executable in vendor B's install directory that vendor B did not ship, running under an updater-style name. For the 7-Zip case specifically, the benign file set is small and stable (`7z.exe`, `7zFM.exe`, `7zG.exe`, `7z.dll`, `7-zip.dll`, `7-zip32.dll`, `Uninstall.exe`, plus language and help files), so any other executable in that folder is worth a look regardless of what it claims to be.   Why this disguise is worth hunting - Vulnerability-remediation platforms like vRx are built to deploy changes and run remediation actions on endpoints, so they can give an operator remote execution (a product capability; Huntress did not report how this instance was used). Renaming it to `HealthUpdater.exe` removes the vendor name from the process list, and placing it in `C:\Program Files\7-Zip\` puts it in an admin-writable, protected path that path-based rules treat as trusted. The operators also installed AnyDesk, so the renamed agent may have been a quieter backup channel (inference, not stated by Huntress).
  Foreign-executable-in-product-folder leg - Core filter: processes running from a `C:\Program Files\<product>\` folder whose file name is not in that product's shipped file set, prioritised where `ProcessVersionInfoOriginalFileName` is empty or differs from the running file name, or where `ProcessVersionInfoCompanyName` names a different vendor than the folder's owner. Note that the INC binary's version information did not contain an original file name, so a rule requiring a populated `OriginalFileName` would have missed it. Triage fields: `FolderPath`, `FileName`, `ProcessVersionInfoOriginalFileName`, `ProcessVersionInfoCompanyName`, signer, `SHA256`, the launching process, and whether a scheduled task or service points at the file. Strong red flags: an updater-style name (`HealthUpdater`, `UpdateService`, `AgentHelper`) with no updater in the owning product; a scheduled task created by an ordinary user account pointing at a path under `Program Files`; and outbound connections to a vendor cloud tenant your organisation does not own.
  Sample KQL - executables in the 7-Zip folder that are not 7-Zip, and generalised version-info anomalies under Program Files:
  `DeviceProcessEvents | where Timestamp > ago(60d) | where FolderPath has @"\Program Files\7-Zip\" or FolderPath has @"\Program Files (x86)\7-Zip\" | where FileName !in~ ("7z.exe", "7zFM.exe", "7zG.exe", "Uninstall.exe") | project Timestamp, DeviceName, FolderPath, FileName, ProcessVersionInfoOriginalFileName, ProcessVersionInfoCompanyName, ProcessVersionInfoProductName, SHA256, InitiatingProcessFileName, AccountName`
  `DeviceProcessEvents | where Timestamp > ago(30d) | where FolderPath startswith @"C:\Program Files" | where isempty(ProcessVersionInfoOriginalFileName) or FileName !~ ProcessVersionInfoOriginalFileName | extend productFolder = tostring(split(FolderPath, @"\")[2]) | where not(ProcessVersionInfoCompanyName has productFolder or ProcessVersionInfoProductName has productFolder) | summarize hosts = dcount(DeviceId), firstSeen = min(Timestamp), names = make_set(FileName, 5) by productFolder, ProcessVersionInfoOriginalFileName, ProcessVersionInfoCompanyName | where hosts <= 5 | order by firstSeen desc`
  Scheduled-task leg - Core filter: `DeviceEvents | where ActionType == "ScheduledTaskCreated"` (or Security Event ID 4698) where the task action points at an executable under `C:\Program Files\` and the registering account is an ordinary user rather than SYSTEM or an installer. This is how Huntress found the INC binary launched. Correlate with the same account's task registrations on other hosts in the same window, since Huntress reports the late-August tasks were registered on several endpoints.
  File-arrival leg (not observed by Huntress; the writing process was not reported) - a new `.exe` created under `C:\Program Files\7-Zip\` (or any product folder) by a process other than that product's installer or updater — `DeviceFileEvents` with `ActionType == "FileCreated"`, grouped by the writing process.

# H350

In the late-August phase of the INC Ransom intrusion Huntress reconstructed, the same compromised user account registered scheduled tasks on several endpoints. On one of them, the task pointed to `C:\Program Files\7-Zip\HealthUpdater.exe`. That file was not part of 7-Zip. It was a renamed executable from Vicarius vRx, a commercial vulnerability-remediation platform. AnyDesk, a network scanner and a vulnerable-driver kit arrived in the same wave.

Each choice defeats a different control. vRx is a legitimate product built to push fixes and run remediation actions on endpoints, which is capability an operator can use; Huntress did not report how this instance was used. RMM allowlists and inventories are usually built around remote-support products like AnyDesk, ScreenConnect and MeshAgent, and a patching agent rarely appears on either the approved or the blocked list. The rename removes the vendor from the process list. The 7-Zip folder is an admin-only, trusted path that most rules ignore, inside a product nobody expects to run a background agent.

Huntress adds a detail that shapes the hunt: the file's version information did not contain the original file name. A rule that looks for a mismatch between the running name and a populated `OriginalFileName` would pass straight over this binary. What does stand out is simpler — an executable in 7-Zip's folder that 7-Zip never shipped, launched by a scheduled task that an ordinary user registered.

## Why

- It targets a quieter channel alongside a noisy one. The same wave installed AnyDesk, which most environments would flag; a renamed remediation agent in another product's folder is the kind of access that survives after the obvious tool is removed.
- "Foreign file in a product folder" is cheap and robust. It does not depend on the version resource at all, which matters here because the INC binary's version information carried no original file name. Some product folders — 7-Zip is one — ship so few files that any other executable is close to a zero-noise signal.
- The version resource still helps when it is present. An empty `OriginalFileName`, or a `CompanyName` that names a different vendor than the folder's owner, sharpens the ranking of what the product-folder leg finds.
- The launcher is itself a signal. A scheduled task registered by an ordinary user account that runs an executable under `Program Files` is unusual, and the same account registering tasks on several hosts in one window is how the late-August wave looked.
- It widens RMM hunting beyond remote-support brands. Treating patching, remediation and software-deployment agents as remote access tools closes a blind spot in inventories that only list the familiar remote-support products.
