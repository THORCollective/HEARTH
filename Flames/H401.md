# H401

On a Linux mail server, a mailbox is a directory. Not an API, not a database with an audit log — a tree of files with one message per file.

Which means collecting someone's mail needs no credential, no OAuth grant, no mail client and no token. It needs read access and `zip`.

The CL-UNK-1211 operators did it in three steps, and the first one is the interesting one. Before taking anything, they counted. Unit 42 reports they "enumerated the /var/qmail/mailnames/ directories for several domains and counted the number of emails stored in specific users" Maildir folders "to identify targets". They were triaging — working out which mailboxes were worth the effort.

Then they searched. A PHP script called `search_social.php` looked for keywords in email headers and returned, per Unit 42, "the exact file path, social media account email sender, recipient and subject."

Read that again, because it explains the whole operation. They were not after the email. They were after what the email could unlock. Unit 42 says the attackers "targeted official government mail servers to steal emails and facilitate access to external social media accounts" — mailboxes "tied to government email addresses." The mail server was a route to password-reset messages for accounts that live somewhere else entirely, on platforms the organisation does not own and cannot monitor.

The third step was `zip_mails.sh`, intended to walk user directories and compress mailboxes into ZIP archives.

It didn't work. Unit 42 notes the script "contained syntax errors, such as a broken variable assignment user=\;) and would fail upon execution."

That failure is the most instructive thing in this section, because of what it implies for detection. Steps one and two ran. Step three — the one that writes an archive to disk, the one most detections are built around — did not. A hunt keyed solely on the appearance of a large archive on a mail server would have seen nothing here, on an intrusion where mailbox enumeration and targeted header searching had already succeeded.

So this hunt has to reach for the read side, and the read side is the awkward telemetry. Nothing is modified when someone walks a Maildir. There is no file-write event, no process touching a credential store, nothing that a tool built around change detection will surface. On Linux that means audit rules on read access, loaded before the fact.

The saving grace is that the *identity* is wrong in an obvious way. Mail storage is traversed constantly — by backup agents, by antivirus, by quota enforcement, by indexers — and all of it runs as a dedicated service account or as root, from a scheduled job, with a stable command line, writing to a known destination. What ran here was a PHP script on a mail host and an interactive shell user. And no backup agent counts messages per user to decide who is worth copying, because backups take everything.

That last point is the cheapest filter available: counting is a targeting behaviour, and legitimate tooling does not target.

## Why

- **The mailbox is the route to identities outside the organisation.** Unit 42 ties this collection directly to gaining access to social media accounts registered to government addresses, so the impact does not stop at the mail server or at anything the organisation controls.
- **Collection needs no authentication at all.** Maildir is a filesystem, so file read access is the entire access-control story — no mailbox permission, no OAuth grant, no API log entry.
- **The enumeration step is a targeting signal with no benign twin.** Counting messages per user to rank mailboxes is something only an attacker does; backup and scanning tooling reads everything indiscriminately.
- **The step that writes to disk is the step that failed.** Because `zip_mails.sh` was broken, archive-centric detection would have missed this entirely — which is the argument for collecting read-side telemetry despite its cost.
- **A PHP script reading mail storage is an identity mismatch, not a subtle anomaly.** `search_social.php` would execute as the web service account, which has no legitimate reason to traverse Maildir folders on any host.
- **Header-keyword searching reveals intent that bulk theft hides.** Searching for specific senders tells the defender what the operation was for, which changes the incident response — notify the external platforms, not just reset mail passwords.
- **Mail servers are often outside the EDR estate.** Appliance-like Unix mail hosts frequently carry no endpoint agent and no file integrity monitoring, which is the visibility gap this activity depends on.
- **The same operators deleted mail-activity logs.** Unit 42 lists email activity among the log categories targeted for deletion, so the filesystem state and forwarded audit records outlast the local evidence.
