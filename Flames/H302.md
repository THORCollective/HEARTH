false_positive_notes: |
  Non-browser user agents in OAuth flows are not inherently malicious and this is the axis that generates almost all of the noise. Legitimate producers: Azure CLI, Azure PowerShell and the Microsoft Graph PowerShell SDK; Terraform and other IaC providers; CI/CD pipelines using user-delegated permissions; backup, DLP, eDiscovery, archiving and security vendors that authenticate as a user rather than as an application; custom internal scripts written against Graph with `python-requests`, `httpx`, `curl` or `Go-http-client`; and monitoring agents. The correct tuning approach is NOT to allowlist the user-agent string, because the attacker chooses it — allowlist the IDENTITY plus the source. Legitimate automation authenticates as a small, stable set of service or admin accounts, from predictable IP space (corporate egress, cloud provider ranges you own, CI runner ranges), on a predictable cadence, against a stable set of resource applications. Malicious replay shows the opposite on every axis: a normal human end-user account, a residential or hosting-provider IP with no prior history for that user, an irregular burst, and often a resource application the user has never touched. Expect genuine false positives from developers testing Graph scripts against their own accounts — these are real and are best handled by identifying those users and profiling them explicitly rather than suppressing the detection. Device registration also has a legitimate high-volume equivalent during Autopilot enrolment, Intune onboarding waves and hardware refresh cycles; scope those by time window and by the enrolling account, and note that a genuine enrolment is normally preceded by an INTERACTIVE sign-in from the device itself, which the attacker path lacks.

  Entra ID non-interactive sign-ins, the replay engine itself - Core filter: `AADNonInteractiveUserSignInLogs` where `UserAgent` matches a scripted HTTP client rather than a browser. The Knight Office kit used the literal string `python-requests/2.34.2, OAuth2:Token`, but hunt the CLASS, not the string: `python-requests*`, `curl/*`, `httpx*`, `aiohttp*`, `Go-http-client*`, `Java/*`, `okhttp*`, `*Headless*`, and empty or absent user agents. KQL starting point - `AADNonInteractiveUserSignInLogs | where ResultType == 0 | where UserAgent has_any ("python-requests","curl/","httpx","aiohttp","Go-http-client","okhttp","Java/") | summarize Requests = count(), Apps = make_set(AppDisplayName, 10), IPs = make_set(IPAddress, 10), ASNs = make_set(AutonomousSystemNumber, 10) by UserPrincipalName, UserAgent | where Requests > 1`. Triage values - `UserPrincipalName`, `IPAddress`, `AutonomousSystemNumber`, `AppDisplayName`, `ResourceDisplayName`, `AuthenticationProtocol`, `IncomingTokenType`, `ConditionalAccessStatus`. Strong red flags - the account is a normal human end user rather than a service identity; `IncomingTokenType` indicates a refresh or primary refresh token rather than a fresh credential; `ConditionalAccessStatus` is `success` while the IP has no prior history for that user.
  The zero-failed-password tell - Core filter: for any account under suspicion, confirm the ABSENCE of `ResultType` 50126 (invalid username or password) and 50053 (account locked / smart lockout) across the whole compromise window. Knight Office and AiTM kits generally never guess a password — they relay the real one and steal the resulting session — so the account shows a clean authentication history. This inverts the usual triage instinct and matters because "no failed logons" is frequently treated as evidence AGAINST compromise. Use it as a corroborating condition, not as a filter that removes the account from scope.
  Device registration and WHfB binding, the persistence step - Core filter: `SigninLogs` or `AADNonInteractiveUserSignInLogs` where `UserAgent startswith "Dsreg/"` (the kit produced `Dsreg/10.0 (Windows 10.0.19044.1826)`), joined to `AuditLogs` where `OperationName` is `Add device`, `Add registered owner to device`, `Add registered users to device`, or a key-credential / WHfB provisioning operation. KQL starting point - `AuditLogs | where OperationName has_any ("Add device","Add registered owner to device","Register device") | extend Actor = tostring(InitiatedBy.user.userPrincipalName) | join kind=inner (AADNonInteractiveUserSignInLogs | where UserAgent has_any ("python-requests","curl/","httpx") | project UserPrincipalName, ReplayTime = TimeGenerated, IPAddress) on $left.Actor == $right.UserPrincipalName | where TimeGenerated between (ReplayTime .. ReplayTime + 2h)`. Strong red flags - the registering IP differs from every prior sign-in IP for that user; the device is registered by an account that already has compliant managed devices (a second, unmanaged registration is redundant for a legitimate user); the registration is NOT preceded by an interactive sign-in from the new device; and the account subsequently authenticates passwordlessly from a new location. Note `Microsoft Authentication Broker` and `OfficeHome` as the resource applications the kit used to carry the device-join and MFA-push steps.
  Session and infrastructure pivots - Core filter: the same `SessionId` or correlation identifier appearing from more than one IP address, or more than one ASN, inside a short window. Post-MFA activity arriving from a residential-proxy or resale operator range while the user's genuine traffic arrives from corporate egress is the geometric signature of a relay, and it is the pivot M042 models statistically. The kit fronted its callbacks through Comcast residential space in the `73.125.13.0/24` region flagged by Spur as a resale operator, and replayed tokens from Tencent Cloud ranges including `43.0.0.0/8`, `170.106.0.0/16`, `162.62.0.0/16` and `49.51.0.0/16` — treat these as illustrative of the SHAPE (consumer ISP for callback, cheap cloud for replay), not as blocklist entries.
  Post-compromise confirmation in M365 - Core filter: `CloudAppEvents` for `MailItemsAccessed`, `New-InboxRule`, `Set-InboxRule`, `Add-MailboxPermission`, `Set-Mailbox` with forwarding, and `Add OAuth2PermissionGrant`, scoped to the session window identified above. Correlation - inbox-rule creation within minutes of a non-browser token request against a normal user account is a near-definitive business email compromise sequence, and is often the first stage that produces a user-visible impact.
  A control note on mitigation - Conditional Access alone does not stop this, because the replayed token already carries the MFA claim and CA evaluates the initial authentication. The control that breaks the technique is token protection (binding the token to the device that obtained it), together with phishing-resistant FIDO2 or passkey authentication for high-value accounts. Detection engineering here should assume replay will succeed and concentrate on the shape of what happens next.

# H302

The Knight Office phishing kit that Huntress documented in 2026 is interesting less for how it steals a Microsoft 365 session than for what it does with one afterwards. The front end is a familiar adversary-in-the-middle reverse proxy: a Flask application behind a Cloudflare Turnstile challenge, fronted by twenty-five `.vu` domains, relaying the victim's credentials to the real Microsoft login and harvesting the resulting session. The part that matters for hunting is the back end. The captured cookie is passed to an automated replay engine that requests fresh tokens over the default OAuth 2.0 flows, and that engine identified itself in the logs as `python-requests/2.34.2, OAuth2:Token`.

That is a much better signal than any of the infrastructure. Domains rotate, IP ranges rotate, TLS certificates rotate — but an operator running replay at scale is running a script, and a script announces itself in the user-agent field of the non-interactive sign-in log. The generalisable hunt is therefore not "look for this string" but "look for a scripted HTTP client presenting an already-MFA-satisfied token on behalf of a normal human end-user account." Legitimate automation does use these libraries constantly, which is why the discriminator has to be the identity and the source rather than the agent string: real automation runs as a stable service identity from predictable egress on a predictable cadence, and a compromised end user's mailbox being accessed by `python-requests` from a residential proxy is the opposite on every axis.

Two further properties of this campaign are worth building into the query. First, the account shows zero failed password attempts for the entire compromise, because the kit relays the real credential rather than guessing it — which inverts a triage instinct that treats a clean authentication history as exculpatory. Second, the operators converted the borrowed session into something durable by enrolling a device into Entra ID and binding a Windows Hello for Business key credential to it, visible as a `Dsreg/10.0` user agent on the same account. That step is what survives a password reset, and it is the reason a response that only revokes sessions leaves the intruder in place. H303 covers the self-spoofed lure that delivered the phish, and M042 models the proxy-geometry anomaly statistically for environments where user-agent hunting is too noisy on its own.

## Why

- Token replay is invisible to the control most organisations believe is stopping it. The replayed session already carries the MFA claim, so Conditional Access admits it as compliant, and neither the IP change nor the device change is reflected in the token request — the sign-in looks clean on exactly the fields an analyst checks first.
- The detection surface the attacker cannot easily discard is the client library itself. Running replay at operational scale means running a script, and the non-interactive sign-in log records its user agent; changing that requires the operator to maintain browser-fidelity impersonation, which is real engineering cost rather than a configuration change.
- The primary telemetry is frequently not ingested at all. Replay produces non-interactive sign-in events almost exclusively, and many environments collect only `SigninLogs`, so this hunt commonly finds a data-collection gap before it finds an intrusion — which is itself a valuable result.
- The zero-failed-password property corrects a dangerous triage heuristic. AiTM compromise produces a spotless authentication history, so "no failed logons" must be read as corroboration rather than as grounds for closing the case.
- The persistence step has a distinct, high-fidelity artefact. A `Dsreg/` device registration binding a WHfB credential, arriving without a preceding interactive sign-in from that device, is both rare and specific, and it is what determines whether incident response needs to go beyond revoking tokens and resetting the password.
- The sequence is natively joinable. Non-browser token request, device registration, then inbox-rule creation within one short window is a three-event chain across tables that most Microsoft 365 environments already have, and it produces a defensible high-confidence finding without depending on any indicator that rotates.
