false_positive_notes: |
  IMDS requests are entirely normal on Azure virtual machines - the Azure CLI, the Azure SDKs, Kubernetes workloads using pod identity, agent bootstrap code and monitoring agents all query it, and many request tokens. Volume alone is not the signal. Two things separate this activity from legitimate use: the breadth of audiences requested in one burst, and the requesting process. A workload needs tokens for the one or two services it actually talks to; requesting twelve unrelated resource audiences in sequence is a credential sweep, not an application.

  OIDC token requests inside a pipeline are the documented, intended way for a job to obtain federated credentials, so their presence is expected in any estate using workload identity federation. The discriminators are that the observed requests omit the `serviceConnectionId` parameter Microsoft's flow uses, and that the requesting process is a Python interpreter started as a side effect of package installation rather than an Azure task. Elastic is explicit that it is unclear whether the malformed requests return a usable token, so treat an observed attempt as attempted escalation and investigate accordingly, without assuming either success or failure.

  Azure tasks legitimately expose `SYSTEM_ACCESSTOKEN` to a job when the pipeline author opts in, which means a job that has it is not compromised by virtue of having it. The question is which process read it, and whether the job definition declares that it should be available at all.

  Link-local traffic is frequently excluded from network telemetry by default as noise, and the same is often true of host-local identity endpoints. A hunt that returns nothing may be a collection gap rather than an absence - verify that `169.254.169.254` appears somewhere in the data before concluding the estate is clean.

  Containerised build agents complicate process attribution because the interpreter may be short-lived and the agent may be recycled between jobs. Capture the job identifier alongside the process and pivot through pipeline logs; the ephemeral host is often gone by the time the hunt runs.

  The twelve-audience figure is Elastic's count for this stealer and will differ in other samples. Use it to calibrate what breadth looks like, not as a threshold.
notes: |
  Leg one, the audience sweep (host network telemetry plus process attribution) - Core filter: requests from a build agent or developer host to `169.254.169.254` or to the local identity endpoint, grouped by requesting process and counted by distinct resource audience within a short window. Breadth is the signal:

      # Linux, retrospective: which processes have talked to IMDS
      ausearch -i -k net_imds | grep -E 'exe=|comm='
      # Live, on a suspect agent: current connections to the metadata service
      ss -tnp | grep '169.254.169.254'

      # Expressed as a detection, whatever the platform:
      #   destination == 169.254.169.254  (or $IDENTITY_ENDPOINT / $MSI_ENDPOINT)
      #   AND path contains "/metadata/identity/oauth2/token"
      #   AND count(distinct resource audience) >= 4 within 5 minutes
      #   GROUP BY host, requesting process

      The audiences this stealer requested are worth recording as a set, because any subset appearing
      together is more suspicious than any one of them alone: Azure Resource Manager, Microsoft Graph,
      Key Vault, Storage, Azure AI Foundry, Azure Machine Learning, Container Registry and Azure
      DevOps, the last identified by application ID 499b84ac-1321-427f-aa17-267ca6975798.

  Also look for the instance-metadata read that accompanies the token requests - the stealer pulls subscription ID, resource group and VM name, which is how the operator learns what the tokens are for. An IMDS instance-metadata read followed within seconds by multiple token requests from the same process is the sequence.

  Leg two, the pipeline OIDC calls (CI/CD logs, host network telemetry) - Core filter: a `POST` to the URI held in `SYSTEM_OIDCREQUESTURI`, carrying a bearer token in the Authorization header, where the requesting process is an interpreter rather than an Azure task, or where the request body omits `serviceConnectionId`. The observed attempt pattern is two requests in sequence - the first with a body requesting the `api://AzureADTokenExchange` scope, the second with an empty body, which reads as a tool trying both shapes rather than a client following documentation.

  For GitHub Actions, the equivalent is a request to the URL in `ACTIONS_ID_TOKEN_REQUEST_URL` authenticated with `ACTIONS_ID_TOKEN_REQUEST_TOKEN` or `ACTIONS_RUNTIME_TOKEN`, with an `audience` query parameter appended. The observed audiences were `api://AzureADTokenExchange` and the Azure management endpoint. A workflow that requests an ID token it never uses in a declared step is the anomaly worth surfacing, and the cross-check is cheap - compare token requests against the workflow definitions that are supposed to make them.

  Leg three, what the tokens then did (Entra sign-in logs, Activity Log, data-plane logs) - This is the leg that establishes impact, and it is the one that survives after the host is gone. For every managed identity and federated service connection on a potentially affected agent, review sign-ins and resource access in the window after the package ran. Red flags - the identity authenticating from a source address outside the build infrastructure's egress range; the identity touching a resource type it has never used, especially Key Vault secret reads, Storage data-plane access or Container Registry pulls; any role assignment or credential addition made by that identity. Short-lived tokens cannot be revoked, which is why this review is the response rather than an optional extra - Elastic's guidance is to rotate long-lived secrets and review activity for short-lived tokens that cannot be revoked.

  Leg four, confirming the package and the exfil (file and network telemetry) - The package legs are useful for scoping which hosts to review, and Elastic publishes them directly. `agent-framework` 1.26.1 went live at 20:35 UTC on 17 November 2026 and was flagged malicious at 20:41 UTC; 1.26.2 followed at 21:08 UTC with the same stealer under new filenames; PyPI removed both within the hour. The artefacts to search for in `site-packages` are `agent_framework_meta.pth` and `_telemetry.py` for 1.26.1, and `af_runtime_diag.pth` and `af_runtime_diag.py` for 1.26.2. Elastic's own ES|QL hunting queries are:

      FROM logs-endpoint.events.file-*
      | WHERE event.action == "creation"
      | WHERE file.name IN (
          "agent_framework_meta.pth",
          "_telemetry.py",
          "af_runtime_diag.pth",
          "af_runtime_diag.py"
        )

      FROM logs-endpoint.events.network-*
      | WHERE dns.question.name == "webhook[.]site"

  Exfiltration went to a single `webhook.site` endpoint, zlib-compressed and Base64-encoded, with the user agent `af-runtime-diagnostics/1` in 1.26.1 and `runtime-diagnostics/1` in 1.26.2 - both worth a proxy search. The clean version to pin back to is 1.26.0.

  Why the minting leg is the durable hunt - stolen stored secrets can be rotated, and a defender who finds a credential file read knows exactly which secret to change. A minted token is different: it is valid, correctly issued, and carries whatever role assignments the identity holds, which may be a single resource group or an entire subscription depending on how the service connection was configured. Nothing about its later use looks anomalous in the resource's logs. So the identity inventory - which managed identities and federated service connections exist on build infrastructure, and what can each one reach - is the control that bounds this, and it has to exist before the incident.

  Scope note: H351 and H427 already cover the delivery half of this compromise and should not be duplicated - H351 covers a `.pth` path-configuration file left for persistence after a poisoned PyPI package, and H427 covers an interpreter startup hook, either a single-line `.pth` import or a `sitecustomize.py`, stealing credentials the first time Python starts. This hunt deliberately begins after that point, at the escalation from host secrets to freshly minted cloud tokens, which neither covers. M033 covers a sweep of stored credential families in a build environment, and H444 the same on macOS; both read secrets at rest rather than requesting new ones. B043 and B055 reference managed identities from the cloud side and are the closest baselines for leg three. No existing hunt names IMDS, `169.254.169.254`, OIDC token exchange, `SYSTEM_ACCESSTOKEN` or `ACTIONS_ID_TOKEN_REQUEST_URL` - a grep for each returns nothing.

# H513

The agent-framework compromise is a good supply-chain story and a better cloud-identity story.

Microsoft's Agent Framework is an open-source framework for building and orchestrating AI agents in the Azure ecosystem, and the compromised package was its meta-package — a thin wrapper that pulls in the framework's dependencies, averaging around 196,000 downloads a month across all versions. Version 1.26.1 went live on PyPI at 20:35 UTC on 17 November 2026. Elastic's supply-chain monitor flagged it as malicious six minutes later. Version 1.26.2 arrived at 21:08 UTC with the same stealer under new filenames, and PyPI removed both within the hour.

The delivery mechanism — a `.pth` startup hook that runs on every Python launch, no import required — is already well covered as a technique. What is less covered, and what this hunt is about, is what the stealer did once it was running.

It did not stop at reading secrets. It called the Azure DevOps pipeline OIDC endpoint using the pipeline's own access token. It called the GitHub Actions OIDC endpoint for the `api://AzureADTokenExchange` audience. And on any Azure resource with a managed identity, it asked the Instance Metadata Service for a separate token for each of twelve resources — Resource Manager, Graph, Key Vault, Storage, AI Foundry, Machine Learning, Container Registry, Azure DevOps and more — then read the instance metadata so the operator would know which subscription those tokens unlocked.

## Why

- Minted tokens are not revocable and not anomalous. A stolen file can be rotated and its use looks out of place; a token issued by the platform to a legitimate identity is correctly signed, correctly scoped, and invisible in the resource's own logs. The only reliable place to catch it is at the moment of issuance.
- Breadth is the discriminator that works. A real workload asks for tokens for the one or two services it talks to. Twelve unrelated audiences in one burst from one process is a sweep, and that comparison needs no indicators and no knowledge of this package.
- The escalation path leads out of the build and into the subscription. Elastic is clear that a usable federated token could be exchanged for Entra ID access as the identity behind the service connection, inheriting its role assignments — which may be one resource group or an entire subscription, depending on configuration nobody revisits.
- Link-local telemetry is commonly discarded, which makes this a collection question before it is a hunting one. `169.254.169.254` is filtered as noise in many pipelines, and an estate that cannot see IMDS traffic cannot run this hunt at all — finding that out deliberately is better than finding it out during an incident.
- The window was minutes and the response window is hours. Six minutes from publication to detection, under an hour to removal — and yet any build that ran in between has to be treated as fully exposed. The identity inventory that bounds the damage is the one artefact that has to pre-exist.
