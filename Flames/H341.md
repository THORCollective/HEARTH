false_positive_notes: |
  MeshCentral is legitimate, free and genuinely popular with small IT shops, MSPs, homelab operators and OT/ICS support teams, so MeshAgent on an endpoint is not by itself malicious — and if your organization or one of its MSPs runs MeshCentral, you will find a large legitimate population. Resolve this against inventory rather than by reputation: the controller address is the discriminator. A sanctioned deployment points every agent at a named, DNS-resolvable management host inside your estate or at your MSP's published endpoint, is installed by a known deployment mechanism, appears on the expected device population, and uses the vendor-default binary name. The malicious deployments in the Settra incidents pointed at bare IPv4 addresses (`45.13.122[.]7`, `193.5.65[.]114`) and, in July, used a renamed binary; neither report states which host roles the agents landed on, but a server or domain controller is where no MSP endpoint-support workflow belongs (not observed in the reports). On a domain controller, tier-0 server or backup host, treat any MeshAgent as reportable regardless of naming.

  Why that query alone is insufficient, and what to add - Microsoft's query keys on the strings `meshagent`, `meshagent64` and `meshcentral`, which catches the `meshagent64-<org>.exe` pattern but by construction misses the Settra `mvtcs.exe` rename entirely, since no MeshCentral-derived string appears in that name. Run Microsoft's query for the naming pattern, then run the name-independent legs below for everything it cannot see.
  Name-independent leg 1 — service installation shape (Event ID 7045 / 4697 / DeviceRegistryEvents) - Core filter: new service whose `ImagePath` points outside `%ProgramFiles%` and `%ProgramFiles(x86)%` — MeshAgent's own installer typically lands in `C:\Program Files\Mesh Agent\` or `%ProgramData%\mesh*`, so a service binary under `C:\Users\Public`, `%TEMP%`, `C:\PerfLogs`, `C:\ProgramData\<random>` or a user profile is the anomaly. Triage fields: service name, display name, `ImagePath`, account (`LocalSystem`), and the account that created it. Strong red flags: service display name mimicking a Windows or vendor component while the image path is unmanaged; the service installed within minutes of a PsExec, WMI or RDP session from another host; and the same service name appearing on a handful of servers but on no workstations, which is the inverse of a real RMM rollout's device distribution.
  Name-independent leg 2 — MeshAgent's own filesystem and registry footprint - Core filter (Sysmon Event ID 11 / DeviceFileEvents): creation of MeshAgent's companion artifacts in the binary's directory regardless of the executable's name — `*.msh` (the agent configuration file carrying the controller URL and server ID), `meshagent.db` or a sibling `*.db` agent state database, and `*.log`. Core filter (Sysmon Event ID 13 / DeviceRegistryEvents): writes under `HKLM\SOFTWARE\Open Source\MeshAgent2` or `HKLM\SYSTEM\CurrentControlSet\Services\<servicename>` where the service is new. The `.msh` file is the highest-value artifact in the whole hunt: it is plaintext and contains `MeshServer=` and `MeshID=`, so recovering it names the controller directly and settles sanctioned-versus-rogue without reverse engineering.
  Name-independent leg 3 — controller provenance, the decisive discriminator - Core filter (Sysmon Event ID 3 / DeviceNetworkEvents / firewall): long-lived outbound sessions from the flagged service binary, typically WebSocket-over-TLS on 443 but frequently on operator-chosen ports (4433, 8080, 8443). Correlation: extract the destination and compare it against your sanctioned controller list from [[B041]]. Strong red flags: the destination is a bare IPv4 literal with no DNS name and no SNI, which is how both Settra incidents presented; the destination ASN is a hosting or bulletproof provider; the TLS certificate is self-signed with an IP address in its subject or SAN — Huntress specifically noted the September agent's certificate carried `193.5.65[.]114`, so certificate inspection alone identifies the controller even when the agent binary is pristine and unrenamed; and a persistent session maintained for days with low-volume keepalive traffic punctuated by short high-volume bursts, which is interactive remote control rather than telemetry.
  Hunt the stacking, not just the agent - Both reports describe redundant remote access: Storm-2570 layered Atera, MeshAgent, ScreenConnect, Splashtop, Remotely_Agent and NinjaRMM across intrusions. Not observed in either report, but common in RMM-driven intrusions: a second RMM deployed as a backup path and left dormant. So on any hit, enumerate *all* remote-access agents on the affected host and its neighbours rather than remediating the one you found. A host carrying two or more distinct RMM families, only one of which is in inventory, is a near-certain compromise even if the second agent has never beaconed.
  Pivot artifacts from the source reports - Huntress has associated the workstation name `WIN-LIVFRVQFMKO` with incidents going back to December 2024, and with `193.5.65[.]114` since November 2025; and Settra's ransomware executables were named after the victim organization's domain with a `_win64.exe` suffix. Both are useful retro-hunt pivots against historical EDR and file telemetry.
  Cross-technique: pair with [[B041]] for the sanctioned agent-to-controller inventory this hunt depends on and [[B051]] for the security-exclusion side, and with [[M043]] which graphs enrolment spread to separate an IT rollout from a self-propagating installation. [[H340]] covers the s5cmd exfiltration that followed this access in the Storm-2570 intrusions, and [[H348]] the anti-recovery commands that followed it in the Settra intrusions.

# H341

Two reports published within days of each other in late September 2026 put MeshAgent at the centre of unrelated ransomware operations. Microsoft's analysis of Storm-2570 lists MeshAgent among six RMM families the affiliate deploys, with binaries renamed to `meshagent64-[organization name].exe` — the victim's own name embedded in the filename so that an administrator glancing at a process list reads it as something their own IT team packaged. Huntress's analysis of a new Settra ransomware variant found MeshAgent renamed to `mvtcs.exe` in a July incident, and then, in a September incident, an entirely unmodified MeshAgent whose only distinguishing feature was the controller IP address embedded in its certificate.

MeshCentral is a legitimate open-source remote-management platform, and that is precisely why it is attractive: the agent is freely available, cross-platform, signed by nobody in particular, installs cleanly as a `LocalSystem` service, and gives full interactive control including file transfer and shell. Unlike a commercial RMM there is no vendor tenant to subpoena, no licensing trail, and no cloud console the victim can be locked out of — the operator runs their own controller on a VPS.

The detection problem this creates is that the two most obvious anchors each fail against one of the two observed variants. A filename or string-based rule keyed on "meshagent" catches Storm-2570's pattern and completely misses `mvtcs.exe`; a hash or reputation check catches a modified binary and completely misses September's unmodified one. What holds across both is the controller address. An agent must call home, its configuration says where, and in both Settra incidents home was a bare IP address rather than a named management server — which is a question inventory can answer definitively.

## Why

- Remote-management agents are the access layer that ransomware is deployed through, so a hit here is a pre-encryption finding. In the Settra incidents MeshAgent provided the persistent access from which recovery destruction and encryption followed, and in the Storm-2570 intrusions it sat alongside the credential theft and exfiltration that preceded payload deployment.
- The two reported variants defeat opposite detection strategies, which is the practical argument for hunting the controller rather than the binary. Microsoft's own published query — reproduced in this hunt's notes — is keyed on MeshCentral-derived strings and structurally cannot see the `mvtcs.exe` rename, so a defender who adopts it verbatim is covered against one campaign and blind to the other.
- The agent carries its own attribution in plaintext. MeshAgent's `.msh` configuration file contains `MeshServer=` and `MeshID=`, and the agent certificate carried the controller IP in the September Settra incident, so a single file read or certificate inspection resolves sanctioned-versus-rogue without reverse engineering or vendor assistance.
- Device distribution is a strong independent signal that requires no atomic indicator. A genuine RMM rollout reaches a broad, growing population weighted toward workstations; an adversary's deployment appears on a handful of servers and domain controllers and stops, because it follows privileged access rather than an asset list.
- Redundancy changes remediation as well as detection. Storm-2570 layered six RMM families across its intrusions, and (not observed in these reports) operators commonly keep a second RMM as a dormant backup path, so finding one agent obliges enumerating all of them — and a dormant second agent that has never beaconed is invisible to every network-based detection.
