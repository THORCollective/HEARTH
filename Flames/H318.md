id: H318
category: Flames
title: Apache module loaded from no package, gated on /wps /bmw /card path prefixes and rewriting Content-Security-Policy to allow injected SEO content
hypothesis: >-
  An attacker compromises a Linux web server, fingerprints the distribution as Debian/Ubuntu or
  CentOS/RedHat, and COMPILES a malicious Apache module on the host from a source file named
  `opsproxy.c`. The resulting `.so` is added to the Apache configuration with a `LoadModule`
  directive, so it is loaded into every httpd worker and never appears as a separate process.
  The module stays dormant for ordinary traffic and activates only on requests whose URL begins
  with one of three prefixes - `/wps`, `/bmw` or `/card` - which is why anyone browsing the site
  normally sees nothing wrong. Its configuration is RC4-encrypted inside the binary (`rule1`
  matches on path, referrer and User-Agent; `rule3` filters the response). The durable, remotely
  observable artefact is that the module REWRITES the Content-Security-Policy response header on
  the requests it handles, relaxing it to permit inline scripts, third-party assets and
  `data:`/`blob:` sources so the injected SEO and gambling content can execute. The invariant is
  not the filename and not the prefixes - it is a loaded Apache module that no package owns, and
  a CSP that differs between two URL paths on the same vhost.

false_positive_notes: |
  The benign population for "an Apache module that no package owns" is real but small, well-defined, and enumerable once. Modules installed from PECL, PEAR, `apxs`-built site modules, vendor agents (New Relic, Datadog, AppDynamics, Dynatrace, ModSecurity builds compiled locally, commercial WAFs, Passenger, mod_wsgi installed via pip) and anything a configuration-management system compiles on the host will all show up as unowned `.so` files loaded by `LoadModule`. Every one of those has three properties the malicious module does not: it was installed by a known mechanism that left a trace somewhere else (a Puppet/Ansible/Chef run, a `pip`/`pecl` log, a vendor installer), it is present on EVERY host of the same role rather than on one or two, and its mtime lines up with a change window you can name. So the discriminator is not "unowned" alone - it is unowned AND singleton across the fleet AND with an mtime that matches no change record. Diffing the module set across identically-built web servers collapses this in one query; a module present on three of forty identically-provisioned hosts is the finding. Compilers on a web server have their own benign population - some shops genuinely build in place, and some container images run `gcc` during `pip install` of a source distribution - so treat `gcc`/`apxs` on a production web host as a lead rather than a verdict, and pivot on WHAT was compiled. The path prefixes deserve care in the other direction - `/card` and `/bmw` are perfectly ordinary strings on an e-commerce or dealership site, and `/jogos` (Portuguese for "games") is entirely legitimate on a Brazilian site, so do not key an alert on the literal prefixes outside the context of the CSP and module findings. CSP differences between paths can also be legitimate where an application sets per-route policies in code. An EMPTY result is genuinely ambiguous here and you should say so in the writeup - if you never collected Apache config files, never ran the package verification, and have no response-header capture, a clean result means you did not look, not that the host is clean. Only a completed `apachectl -M` versus package-database reconciliation on every web server licenses a true negative.
notes: |
  ATT&CK mapping provenance - the Check Point report contains NO detection queries and NO ATT&CK mapping table. Every technique ID on this hunt is ANALYST-MAPPED from the described behavior - T1505/T1505.003 for the server software component compiled into Apache, T1685 for the CSP weakening (a security control being modified rather than a tool being killed), T1071.001 for the web-protocol channel the module both serves and controls. Treat the IDs as an aid to pivoting, not as vendor-asserted ground truth.
  Core check 1, the reconciliation - list every module Apache actually loads with `apachectl -M` (Debian/Ubuntu) or `httpd -M` (RHEL family), resolve each to a file path from the `LoadModule` directives, then ask the package database who owns that file - `dpkg -S /usr/lib/apache2/modules/<name>.so` or `rpm -qf /etc/httpd/modules/<name>.so`. Any `.so` that returns "no path found" / "not owned by any package" is the hunt result. This is cheap, runs in seconds, needs no agent, and is decisive. Run `dpkg -V apache2` and `rpm -V httpd` alongside it to catch a legitimate module file that was REPLACED in place rather than added - a `5` in the `rpm -V` output column is an MD5 mismatch on a package-owned file.
  Core check 2, mtime and ctime on the module directory - `find /usr/lib/apache2/modules /etc/httpd/modules /usr/lib64/httpd/modules -name '*.so' -printf '%T@ %C@ %p\n' | sort -n`. Package-installed modules cluster tightly around the install or last-patch date; the odd one out is the lead. Because the same toolset timestomps (see [[H319]]), compare inode change time (`ctime`, `%C@`) against modification time (`%T@`) - `touch` does not reset `ctime`, so `ctime` newer than `mtime` on a module file is itself the tell.
  Core check 3, the LoadModule line - grep the whole Apache config tree, not just the main file - `grep -rn 'LoadModule' /etc/apache2/ /etc/httpd/`. On Debian/Ubuntu a legitimately enabled module is a SYMLINK in `mods-enabled/` pointing at `mods-available/`; a `LoadModule` directive written directly into `apache2.conf` or into a vhost file, or a `mods-enabled` entry that is a regular file rather than a symlink, is anomalous by construction. Compare the config tree against the same tree on a known-good peer host.
  Core check 4, the CSP divergence - request two paths on the SAME vhost and diff the response headers, for example `/` versus `/wps/`, `/bmw/` and `/card/`. `curl -sS -D - -o /dev/null https://<host>/` against `curl -sS -D - -o /dev/null https://<host>/wps/`. A `Content-Security-Policy` that is present and strict on one path and RELAXED on another - gaining `'unsafe-inline'`, wildcard or third-party `script-src`/`img-src` hosts, or `data:` and `blob:` sources - on a server whose application sets one global policy is the finding. This is observable from outside the host entirely, which makes it the one check you can run against an estate you do not have agents on. Reported behavior, verbatim in substance - the module rewrites CSP response headers to permit inline scripts, third-party assets and `data:`/`blob:` sources.
  Core check 5, the activation prefixes and the payload paths - count access-log hits per vhost for paths beginning `/wps`, `/bmw` and `/card` (the three module activation prefixes) and for `/jogos` and `/nova` (where the SEO payload is served). `awk '{print $7}' /var/log/apache2/access.log | grep -E '^/(wps|bmw|card|jogos|nova)' | sort | uniq -c | sort -rn`. On a site that has no such routes, ANY volume here is unexplained by the application. Reported payload content, useful for confirmation once you have a candidate URL - pages impersonating Google Play, Microsoft Store and Amazon, `lang="pt-BR"`, CSS comments in Chinese, Open Graph and Twitter card metadata citing `@GooglePlay` and `@microsoftstore`, and thumbnail images sourced from `tse-mm.bing.com`.
  Build-on-host artefacts - the toolset fingerprints the distro (Debian/Ubuntu versus CentOS/RedHat) and then compiles the module FROM SOURCE on the victim. Hunt for the source file and the toolchain - `find / -name 'opsproxy*' 2>/dev/null`, and auditd `execve` records for `gcc`, `cc`, `apxs`, `apxs2`, `make` or `a2enmod` with a parent in the web-server process tree (`apache2`, `httpd`, `php-fpm`, `www-data`). An auditd rule scoped to that - `-a always,exit -F arch=b64 -S execve -F auid>=1000 -F path=/usr/bin/gcc -k webserver_compile` plus a `www-data`-scoped variant - is a low-volume, high-value standing rule on a production web server. A compiler invocation whose parent is the web server is also strong corroboration for a preceding webshell (T1505.003).
  Why the module form matters for triage - because the code runs INSIDE httpd worker processes, there is no extra process, no extra listening socket and no unusual child process to find. Process-centric hunting will return nothing here, which is exactly why this hunt is built on file-and-config reconciliation and on the response headers rather than on process telemetry. Say this explicitly when reporting a clean result.
  Fleet-scale version - do not do this host by host. Collect `apachectl -M` output plus the SHA-256 of every loaded `.so` from every web server, then group by hash. Modules present on all hosts of a role are the baseline; a hash present on one or two hosts is the answer. This same collection doubles as the baseline artefact for future runs.
  Triage values to carry forward - the unowned `.so` full path, its SHA-256, its mtime AND ctime, the exact `LoadModule` line and which file it lives in, the owning package query result, the differing CSP header values per path, per-path hit counts for `/wps` `/bmw` `/card` `/jogos` `/nova`, and any `gcc`/`apxs` execution with its parent process and working directory.

# H318

Check Point Research documented a Chinese-speaking actor it tracks as "Gambling Goblin", linked to Earth Berberoka, running a campaign against Brazilian `.gov.br`, education and commercial Linux web servers since mid-2025. The goal is SEO abuse: borrow the search-engine reputation of trusted government and university domains to rank gambling and phishing content. The delivery mechanism is what makes it a hunting problem. Rather than dropping a PHP webshell where a file-based scan would find it, the actor fingerprints the distribution, compiles an Apache module on the victim from a source file called `opsproxy.c`, and wires it into the server with a `LoadModule` directive. The module then runs inside every httpd worker — no new process, no new socket, nothing for process-centric detection to grab — and it stays completely inert unless the request path begins with `/wps`, `/bmw` or `/card`. Its configuration is RC4-encrypted inside the binary, with a `rule1` that matches on path, referrer and User-Agent and a `rule3` that filters the response. The one thing it cannot hide is what it does to the response: it rewrites Content-Security-Policy headers to permit inline scripts, third-party assets and `data:`/`blob:` sources, because the injected SEO and phishing content at `/jogos` and `/nova` cannot run under a policy that forbids them. That CSP weakening is durable, server-side, and visible from outside the host.

## Why

- **A loaded module that no package owns is a near-binary answer, and it costs one command.** Every legitimate Apache module on a managed server came from somewhere with a receipt — a distro package, a vendor installer, a configuration-management run. Reconciling `apachectl -M` against `dpkg -S` or `rpm -qf` turns "is there a malicious module here" into a list that is usually empty and always short. That asymmetry — seconds to run, decisive when it hits — is what makes this worth standardising across an estate rather than running once during an incident.
- **The CSP rewrite is the rarest kind of artefact: server-side, durable, and observable without access to the server.** Most web-server implants are visible only if you already have telemetry on the host. This one advertises itself in the response headers, so a scan that fetches two paths on the same vhost and diffs the CSP will find it on hosts you have no agent on, no log shipping from, and possibly no inventory record of. For an estate that includes third-party-hosted and forgotten sites — which is exactly the population this campaign targeted — that is often the only check that can actually run.
- **Path-prefix gating defeats browsing, scanning and casual review by design.** The module ignores every request that does not start with `/wps`, `/bmw` or `/card`. A person looking at the site sees a normal site. A vulnerability scanner crawling links sees a normal site. The injected content only exists for requests the operator or a search-engine crawler makes. Any hunt built on "look at the website" fails here, and understanding why is what forces the hunt onto the config, the package database and the headers.
- **Compiling on the victim is a deliberate portability choice that leaves its own evidence.** Apache's module ABI is tied to the build, so shipping one prebuilt `.so` would not work across Debian and RHEL families — hence the distro fingerprinting and the on-host build. That decision hands defenders a second, independent detection surface: a compiler running on a production web server, with a parent in the web-server process tree. Most production web servers have no reason to invoke `gcc` or `apxs` at all, so an auditd rule scoped to that is close to free to run.
- **The filenames will change and the prefixes will change; the shape will not.** `opsproxy.c`, `/wps`, `/bmw`, `/card`, `/jogos`, `/nova` are this campaign's current values and are worth searching for today. But an actor who rotates them still has to get a module loaded, still has to leave a `LoadModule` line, still owns a file no package claims, and still has to relax CSP for the injected content to execute. Writing the hunt against those invariants is what keeps it useful after the indicators go stale.
