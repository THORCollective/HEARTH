hypothesis: >-
  A Linux-based embedded device on the network - a media player, set-top box, digital signage panel, karaoke unit or clinical kiosk - runs a vendor-planted backdoor that bootstraps in two stages. It first makes HTTP POST requests to a small set of fixed configuration paths on a non-standard port, carrying an encrypted JSON object of hardware telemetry, and receives broker details, geolocation endpoints and module flags in return. It then opens a long-lived MQTT session to the named broker and keeps it open, receiving instructions for silent application installation, arbitrary shell execution, screen capture and network reconnaissance. The hunt is that two-stage shape in network telemetry, because the device itself carries no endpoint agent and never will.

false_positive_notes: |
  MQTT is a normal protocol for exactly this class of device, so the protocol alone is never the finding.
  - Legitimate IoT platforms use MQTT heavily. Building management, environmental sensors, badge readers, smart displays, UPS telemetry and many industrial gateways all maintain persistent broker sessions by design. The discriminator is which broker, resolved through which name, in which hosting provider - and whether that broker appears in the asset inventory for that device class.
  - Vendor cloud management for media and signage devices genuinely involves configuration polling and firmware retrieval, which produces the same two-stage shape. Build the allowlist on the vendor's own documented endpoints, obtained from the vendor rather than inferred from observed traffic, because observed traffic is what is in question.
  - Non-standard ports are not themselves suspicious on embedded devices, where port 8000 and port 8080 are ordinary choices for vendor services. Treat the port as a grouping attribute, not as a signal.
  - Code-hosting release downloads are legitimate on developer workstations and build servers, so the retrieval signal only carries weight when the client is a device with no business fetching binaries at all. Scope that half of the hunt to unmanaged device VLANs.
  - Geolocation and STUN lookups are standard for consumer media devices doing NAT traversal for streaming and conferencing. They are context for a case, not a case on their own.
notes: |
  Source reporting is Google Threat Intelligence Group's November 2, 2026 account of the dismantling of the XCPE backdoor, which enrolled more than 1.3 million set-top boxes into a botnet. Google assesses with high confidence that the backdoor was intentionally developed, deployed and operated for financial gain by an Android OEM and ODM, which sold access to criminal affiliates and loaded those affiliates' modules onto infected devices. The monetization half of the same activity is modelled in [[M069]]. The enterprise relevance is in Google's own scoping note - while the overwhelming majority of infected devices were Android TV set-top boxes, they also observed other infected Android-based devices including telehealth devices, karaoke machines and digital signage devices, all of which do appear on corporate and clinical networks.
  Stage one, the configuration bootstrap - Core filter: HTTP POST requests from an unmanaged device to a small set of fixed configuration paths on a non-standard port. The reported paths are `/router/config/mqtt`, which returns broker hostname, TCP port, authentication tokens or passwords and the topic structure; `/router/config/acs`, which returns a geolocation URL, a STUN server, a file-upload URL and flags that enable or disable modules; and `/router/config/app`, which returns module-level configuration. The request body is an AES-encrypted JSON object containing hardware telemetry - serial number, MAC address, model and firmware version. Triage values are the host, the URI path, the server port, the request method and body length, and the client MAC and switch port. The reported bootstrap hostnames were derived at runtime: a fixed default of `http://mcstb.anyevonline[.]com:8000` when a particular Android system property was set, and otherwise a generated name of the form `http://stb[AndroidVersion][Type].anyevonline[.]com:8000`. A Zeek-side filter for the path shape:
  ```zeek
  event http_request(c: connection, method: string, original_URI: string,
                     unescaped_URI: string, version: string)
      {
      if ( method != "POST" )
          return;
      if ( /^\/router\/config\/(mqtt|acs|app)/ !in original_URI )
          return;
      print fmt("config bootstrap %s -> %s:%s%s", c$id$orig_h, c$id$resp_h,
                port_to_count(c$id$resp_p), original_URI);
      }
  ```
  Strong red flags are a generated hostname pattern where the subdomain encodes device attributes, and three distinct configuration paths requested in one short burst by a device that has no management console in the asset inventory.
  Stage two, the persistent broker session - Core filter: a long-lived TCP session from an unmanaged device to an external MQTT broker, identified either by Zeek's MQTT analyzer or by session duration and byte profile in conn.log. All samples Google analysed used a single broker hostname, `mqtt.szbboys[.]com`. The topic structure the configuration hands back is `/device/{model}/{chipId}/{action}`, so where MQTT is parsed the topic strings themselves name the device model and chip identifier, which is unusually good evidence for attributing a session to a physical unit. Triage values are the broker hostname and address, the port, the session duration, the subscribed topics, the publish and subscribe byte counts, and the client identifier. Correlation: the broker session should begin within seconds of the stage-one response, so joining the two on client address inside a short window gives a far stronger case than either alone. Strong red flags are a session that persists for days with small periodic keep-alives and occasional larger bursts, and a broker whose hostname shares a registered domain with a file-upload endpoint the same device also contacts - the reported upload URL was `http://ott.szbboys[.]com:8000/cpe/file/upload`, on the same registered domain as the broker.
  What the tasking does - Core context for triage: the reported MQTT actions include silent application installation by fetching remote packages to a temporary directory; disabling the platform's application verification by writing a global setting to a disabled value; arbitrary shell execution at system privilege with results published back to the broker; downloading and executing shell scripts; continuous screen capture compressed to JPEG and published over the broker, with key events injected to drive the interface; and network reconnaissance using an embedded traceroute binary plus ping and routing lookups. The screen-capture capability is why a clinical or signage device matters beyond its own compromise - whatever is on the panel is being published to an external broker. Correlation: sustained upstream volume on the broker session, or to the file-upload endpoint, is consistent with screen capture and log exfiltration rather than with configuration polling.
  Stage three, module retrieval from code hosting - Core filter: binary downloads by unmanaged devices from a code-hosting release path. Google reports that a significant majority of staged files were hosted as releases on operator-owned pages of a public code-hosting service, with the configuration naming a download address per CPU architecture together with an MD5 and a relative priority weight. Triage values are the client address, the full download URL, the response size and content type, and the architecture string in the path. Strong red flags are a device fetching an architecture-specific native binary with no file extension, and the same URL fetched by several devices of the same model across different VLANs.
  Attribution and persistence context - Core context: the backdoor runs at system privilege as a firmware preload and reinstalls itself from the read-only vendor partition after a reboot if a user removes it, so remediation on the device is not available to a defender. Later variants masquerade as platform system applications, restart the debug daemon as root through a native helper, remount the system partition read-write, copy themselves into a privileged application directory, write a permissions file granting package-installation and reboot rights, and timestomp their own installation time to match neighbouring system packages. Correlation: none of that is visible without host telemetry the device does not provide, which is the argument for treating these units as untrusted network participants and placing the control at the network boundary. Practical outcome of a hit: isolate the device class, not the device, since infection is a property of the firmware build rather than of one unit.

# H461

Google and industry partners dismantled the XCPE backdoor in late October 2026. It had enrolled more than 1.3 million set-top boxes into a botnet, and Google assesses with high confidence that it was built, shipped and operated for profit by the device manufacturer itself - an Android OEM and ODM that sold backdoor access to criminal affiliates and loaded their modules onto devices it had already sold.

The reason this belongs in an enterprise hunt rather than a consumer advisory is in Google's own device census. Most infected units were Android TV boxes, but they also found telehealth devices, karaoke machines and digital signage panels. Those appear on corporate, retail and clinical networks routinely, bought by facilities or marketing or a clinical team, racked, given an address, and never looked at again.

The backdoor cannot be removed by the owner. It is preloaded in the firmware partition at system privilege and reinstalls itself from the vendor partition on reboot. There is no endpoint agent for it and never will be. Everything a defender can observe is on the wire.

Fortunately the wire is enough. The device bootstraps by posting an encrypted hardware inventory to three fixed configuration paths on a non-standard port, gets back broker details and module flags, and then holds a persistent MQTT session that carries the real tasking: silent installs, shell commands, screen capture, network reconnaissance. Two stages, both in ordinary flow and HTTP telemetry, with the second one lasting for days.

## Why

- These devices are unmanageable by design and invisible by default. No agent can be installed, the vendor is the adversary, and reimaging does not help because the backdoor lives in the firmware. Network telemetry is not the convenient option here, it is the only option, which makes a network-shaped hunt the entire control.
- The two-stage bootstrap is a narrow and durable shape. Three specific configuration paths requested in one burst, followed within seconds by a long-lived broker session, is a sequence that legitimate vendor management does produce but that an asset inventory can account for - and anything the inventory cannot account for is a finding.
- MQTT is an excellent hiding place precisely because it is normal for this device class. A persistent publish-subscribe session looks like exactly what a smart display should be doing, which is why the hunt has to be built on broker identity and inventory rather than on protocol anomaly.
- The capability set reaches past the device. Screen capture published to an external broker means whatever a clinical kiosk or signage panel displays is leaving the building, and arbitrary shell execution at system privilege on a device sitting inside a trusted VLAN is a pivot point with no local logging.
- A hit scopes to a product line, not a host. Because the infection is a property of the firmware build, finding one unit tells you every unit of that model on every site is in the same state - which is operationally useful in a way single-host detections rarely are.
