hypothesis: >-
  An operator who lands on one managed endpoint wants the console that manages all of them, and the way in is not a password but the technician's live web session. The toolkit goes after the remote-support platform's authentication cookie by two routes in sequence: it locates and copies the browser cookie databases and their supporting files, using a volume shadow copy when the database is locked, and decrypts the values with the browser master key through the data-protection interface in the current user context; and when no candidate is found there, it scans the memory of the browser process responsible for network handling, looking for cookie strings and nearby host strings. With that cookie plus the anti-forgery and access tokens, the console's session enumerates every device the account can reach. The observable chain is a non-browser process reading or copying browser cookie databases, a shadow copy created on a workstation outside a backup window, and a process opening the browser network-service process for memory read.

false_positive_notes: |
  Browser credential stores are touched legitimately by a surprising amount of ordinary software, and shadow copies are routine on servers.
  - Backup, migration, profile-roaming and endpoint-management products read and copy browser profile data by design, including the cookie databases. Build the approved-software list first; without it the file-copy check reports the organisation’s own tooling.
  - Browser processes open handles to each other constantly. The browser multi-process architecture means the parent process legitimately accesses its own children, including the network service, so the calling process identity matters more than the access itself. Exclude same-browser-family access before anything else.
  - Endpoint protection products scan process memory as their core function, and so do some performance monitoring and application-compatibility tools. Allowlist them explicitly, by signer rather than by name.
  - Shadow copies are created legitimately and often - by backup agents, by system restore, by installer rollback points and by some update processes. On servers this is constant. The signal here is a shadow copy on a workstation outside any backup window, created by a process that is not the backup agent, which is a much smaller population.
  - Browser sessions are legitimately long-lived and consoles are legitimately used from technician workstations all day. Console audit records will show enumeration performed by real technicians doing real work, so the console-side checks need the technician roster and the shift pattern to be useful.
  - The database route failing is not required for the memory route to run, so absence of file-copy evidence does not clear a host. The two routes are sequential by design, which means either one alone can be the whole case.
notes: |
  Source reporting is Microsoft Threat Intelligence November 13, 2026 analysis of SCKit, following ConnectWise reporting from November 11, 2026 of an active campaign against cloud-hosted ConnectWise ScreenConnect instances belonging to managed service providers. This hunt covers the browser-access component. The companion hunt from the same report is [[H472]], which covers the component compiled on the endpoint to target a connecting technician. The closest existing coverage is the rogue-client baseline in [[B051]] and the console-as-delivery-mechanism hunt in [[H306]], both of which address the platform rather than the credential; [[H284]] and [[H302]] cover session-cookie theft in other contexts. No existing hunt references the platform authentication cookie or browser network-service memory scanning.
  Why the cookie is the objective - The architecture of these platforms makes a technician web session unusually valuable. Microsoft describes three parts: a management instance providing the web console and relay, a technician workstation where support staff sign in through a browser, and customer endpoints running an installed client that executes commands delivered through the platform. A console session therefore reaches every managed device, and Microsoft notes that the console-distribution component "targets the technician’s management-console access, rather than only the original customer device", with "the account permissions determine which additional sessions and devices the distribution workflow can reach". That is why this is filed as credential access with a lateral-movement consequence: the cookie is the pivot from one endpoint to the estate.
  Core filter 1, the cookie names and the target browsers - Microsoft reports the browser-access code "searches Chrome, Edge, Opera, and Opera GX profiles for cookies named .ASPXAUTH", and that its "database route identifies associated hosts and queries encrypted cookie values". The cookie name is the platform standard forms-authentication cookie, so it is a durable string rather than a campaign artefact. Microsoft publishes a command-line hunt that includes it, reproduced here as published:
  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(14d)
  | where ProcessCommandLine contains "/EadF.php"
      or ProcessCommandLine contains "SCKit"
      or ProcessCommandLine contains "RelayTrap"
      or ProcessCommandLine contains "Panel-Lateral"
      or ProcessCommandLine contains "ToolboxRelayUploader"
      or ProcessCommandLine contains ".ASPXAUTH"
      or ProcessCommandLine contains "c=Exploited"
  | project Timestamp, DeviceId, DeviceName, FileName,
      ProcessCommandLine, InitiatingProcessFileName, ReportId
  ```
  Keep the lookback at `ago(30d)` or less in any variant, because Defender XDR advanced hunting retains 30 days and silently truncates a longer window; the 14-day window above is Microsoft published figure. Treat the campaign-specific strings as perishable and the cookie name as the durable one.
  Core filter 2, the database copy - Microsoft reports the component "copies cookie databases and their supporting files, with a volume-shadow-copy fallback for locked databases", and that the decryption code "uses the Chromium master key and the Windows Data Protection API (DPAPI) in the current user context, with AES-GCM routines for v10 and v11 cookie values". Two detection notes follow. First, `DeviceFileEvents` records no reads, so the copy is detectable as the write at the destination, not as the read of the cookie database - hunt for file creates whose name matches the cookie database or the local-state file, in a location that is not a browser profile directory. Second, the supporting files matter: the master key lives in the browser local-state file, so a copy of the cookie database alone is insufficient for the operator and the pair appearing together is the stronger signal.
  Core filter 3, the shadow copy on a workstation - The fallback route leaves a loud, infrequent artefact on an endpoint. Microsoft describes it as a fallback for locked databases, which is what a running browser produces. Hunt for shadow-copy creation on workstations where the creating process is not the backup agent, correlated with activity in browser profile directories in the same window. Triage values are the creating process and its parent, the account, the volume, and what was read from the snapshot afterwards. A shadow copy created on a user workstation, outside a backup window, minutes before a cookie-database-shaped file appears somewhere unusual, is close to a complete case on its own.
  Core filter 4, the memory route - The more novel of the two and the one with the cleanest telemetry, because it requires opening another process for read. Microsoft reports the memory-scanning route "first examines browser network-service processes identified by network.mojom.NetworkService in their command lines", that "an embedded C# scanner uses OpenProcess, VirtualQueryEx, and ReadProcessMemory to inspect readable committed memory regions for cookie strings and nearby host strings", and that "if the initial scan finds no candidates, it scans other browser processes". The target is specific: in the Chromium multi-process model the network service is the process that holds cookies in memory, and its command line carries that service-name switch. Hunt Sysmon Event ID 10 for process-access events where the target process command line contains the network-service switch and the calling process is not part of the same browser installation or an allowlisted security product, filtering on a granted-access mask that includes memory read rather than on access alone. Note that Sysmon Event ID 5 records termination but not who terminated a process, so it is not an alternative source here.
  Core filter 5, the uploader and what the session did next - Microsoft reports the console-distribution component is designed to combine an authentication cookie with the required anti-forgery and access tokens, enumerate accessible sessions, upload a payload using a named uploader binary, and queue execution through the platform shared toolbox, including removing the uploaded item after distribution. Microsoft publishes the uploader as `ToolboxRelayUploader.exe` with SHA-256 `8cb5f48bbe70b5248db7f327f3d1ad6649df5c767d2a7e0711ee147fd92e06af`, and detects it as a hacktool. For a confirmed case the console audit records are where the damage is scoped, and Microsoft remediation guidance is specific about one thing that is easy to miss: "Review Toolbox history for tools removed after use", because the distribution workflow deletes its own artefact. Microsoft also notes that password changes alone do not address every existing session, so session invalidation has to be explicit and performed from a clean device.
  A note on the SQLite utility - Microsoft reports the toolkit retrieves `sqlite3.exe` for browser-cookie queries if a suitable copy is absent, and states that "the toolkit also uses the legitimate SQLite utility; investigate its use alongside the browser-cookie queries described above". That is a dual-use binary with plenty of legitimate presence, so it is a corroborating artefact rather than a detection - the pairing with a browser profile path in the same process tree is what makes it meaningful.
  Scope - Technician workstations and administrative endpoints for any remote-support, remote-monitoring or endpoint-management platform whose console authenticates with a browser cookie, plus the managed endpoints those consoles reach. Microsoft guidance is to "investigate technician workstations and downstream affected endpoints", which is the right scoping instinct here: the cookie theft happens on the endpoint but the consequence lands on the console.

# H471

The operator already had code running on a managed endpoint. What they wanted was the console that manages all the others.

Microsoft Threat Intelligence found that SCKit goes after that console the way an attacker goes after any web application they cannot brute-force: it takes the live session. The target is a cookie named `.ASPXAUTH` — the standard forms-authentication cookie for the remote-support platform — in Chrome, Edge, Opera and Opera GX profiles.

There are two routes, tried in order.

The first is the database. Copy the cookie database and the supporting files, fall back to a volume shadow copy when the database is locked because the browser is running, then decrypt the values with the browser master key through DPAPI in the user's own context. On a workstation, a shadow copy appearing outside any backup window is a conspicuous thing.

The second route runs when the first finds nothing, and it is the more interesting one. The scanner looks for the browser process that handles networking — identified by `network.mojom.NetworkService` on its command line, because in the Chromium process model that is the one holding cookies in memory — opens it, and walks its readable committed regions looking for cookie strings and nearby host strings. If that finds nothing either, it scans the other browser processes.

With the cookie, plus the anti-forgery and access tokens, the console session enumerates every device the account can reach, uploads a payload through the shared toolbox, queues it, and then deletes the toolbox item.

Microsoft's remediation note is the one to read twice: changing the password does not end the session.

## Why

- **One endpoint becomes the whole estate, and the hinge is a cookie.** These platforms are built so one console reaches every managed device. A technician's browser session is therefore not a workstation-scoped credential — it is estate-scoped, and the permissions on the account decide how far it goes.
- **Two independent routes means one clean check is not a clean result.** The memory scan runs when the database route finds nothing, so a host with no cookie-database copies and no shadow copy can still have been harvested. The access-mask check on the network-service process has to run alongside the file checks, not instead of them.
- **The memory route names its target precisely, which is a gift for detection.** `network.mojom.NetworkService` is not a string an operator chose — it is how Chromium identifies the process that holds cookies. That makes "who opened the network-service process for read, and were they part of the browser" a narrow, durable query that survives a rebuild of the toolkit.
- **A shadow copy on a user workstation is rare and loud.** On servers it is background noise. On a laptop, created by something that is not the backup agent, minutes before a cookie-database-shaped file turns up somewhere odd, it is close to a finished case by itself.
- **The cookie name outlives the campaign.** The domains, hashes and staging paths in this report will be dead within weeks. `.ASPXAUTH` is the platform's own cookie and will still be the target in the next intrusion against it, which is why the hunt is built on the cookie and the process model rather than on the indicators.
- **The console cleans up after itself, so the audit trail needs reading deliberately.** The distribution workflow removes the uploaded toolbox item once it has been used. A current, tidy-looking toolbox is not evidence that nothing was distributed through it — the history is, and only if someone looks for items that were removed.
