false_positive_notes: |
  This hunt is deliberately narrow because the general form of it is not. Parent PID spoofing as a category is close to undetectable from process-creation logs alone — the spoofed PPID is a real, live, legitimate process, and the record Windows writes is indistinguishable from an honest one, which is why SigmaHQ's only T1134.004 rule is a tool-name signature for SelectMyParent rather than a behavioural rule. What makes THIS instance huntable is the specific parent the operator chose. `ComputerDefaults.exe` is the Default Apps settings shim; it opens a Settings page and exits. It does not spawn `sc.exe`. It does not spawn `powershell.exe`. In a normal estate the count of process-creation events with `ParentImage` ending in `\ComputerDefaults.exe` and a child of any kind other than the Settings host is effectively zero, so this is one of the rare hunts where a single event is the finding. The same holds, with a little more care, for `fodhelper.exe`, `sdclt.exe`, `slui.exe` and `wsreset.exe` — each has a small, enumerable set of legitimate children, and none of those sets includes a shell or a service-control binary. `eventvwr.exe` is the one to watch: it legitimately spawns `mmc.exe`, and administrators do launch it interactively all day, so scope it to non-`mmc.exe` children only. The benign population that WILL show up is your own red team and any endpoint-security product that performs UAC-bypass simulation; both are enumerable once and stable. Two things make an empty result ambiguous rather than reassuring. First, if `ParentImage` is not being collected — and a surprising number of estates ship process-creation events with the child fields only, or have 4688 enabled without `Include command line` and without parent data — this query returns nothing on a fully compromised host. Verify collection by checking that ORDINARY parent-child pairs are present before concluding anything. Second, the operator is free to pick a different spoof parent tomorrow; a clean result means this campaign's chosen parent is absent, not that PPID spoofing is absent. The Sysmon Event ID 10 condition is the one that generalises, and it is also the noisier one — `GrantedAccess` values carrying 0x0040/0x0080 against a non-security product are worth ranking, not alerting.

# H321

AhnLab ASEC documented a MoiClient backdoor intrusion whose privilege-escalation step is worth separating from the UAC-bypass literature it superficially resembles. The loader does not hijack a per-user handler. It connects to the AppInfo service RPC interface over the `ncalrpc` protocol sequence, launches `winver.exe` as a debug target, launches the legitimate auto-elevating `ComputerDefaults.exe`, clones that process's handle, and then uses the cloned handle as the parent process for `sc.exe` and `powershell.exe`. Both children inherit high integrity by inheritance — no consent prompt, no registry write, nothing for the standard fodhelper-family detections to match on. What it does leave is a lineage that cannot occur naturally: the Default Apps settings shim recorded as the parent of a service-control binary and a shell.

That lineage is the hunt. `ComputerDefaults.exe` opens a Settings page and exits; it has no legitimate reason to spawn anything, least of all `sc.exe`. The condition is close to zero-false-positive and it is directly readable from `ParentImage` in Sysmon Event ID 1 and Security 4688 — telemetry most estates already collect, provided they collect the parent fields and not only the child's. Generalised, the durable form is an auto-elevating Windows binary appearing as the PARENT of a scripting or administrative process. Everything else in the report is behavioural too, by necessity: AhnLab published the full chain but gated every hash, domain and IP behind AhnLab TIP, so there is no indicator list to fall back on.

## Why

- **T1134.004 has no coverage in this corpus at all, and almost none anywhere else.** Parent PID spoofing is generally considered near-undetectable from process-creation logs, because the spoofed parent is a real running process and the event Windows writes is honest-looking. SigmaHQ's only rule for the technique is a filename signature for Didier Stevens' SelectMyParent — a tool indicator, not a behaviour. This hunt is behavioural, and it works precisely because the operator chose a spoof parent with an empty legitimate-child set.
- **The existing UAC hunts are silent against this chain, and it matters that we say so.** [[H243]] keys on the `HKCU\Software\Classes\ms-settings\Shell\Open\command` write; this loader makes no such write, because it drives AppInfo over RPC and steals a handle instead. Framing this as "another UAC bypass hunt" would produce a near-duplicate of coverage that does not actually fire. The novelty is the PPID-spoofing lineage, and building the hypothesis around it is what makes the file worth having.
- **An impossible parent is a stronger primitive than a suspicious child.** Nearly all endpoint detection is written about what a process does — its command line, its network connections, its file writes. This chain's children are `sc.exe` and `powershell.exe` doing ordinary administrative things, at high integrity, which is unremarkable on its own. The anomaly lives entirely in one field that many pipelines drop. That is also the reason to check the field is present before trusting an empty result.
- **The handle clone is the part that survives the operator changing its mind.** If tomorrow's build spoofs off `slui.exe` instead, the `ParentImage` allowlist has to be extended — but the Sysmon Event ID 10 access with PROCESS_DUP_HANDLE or PROCESS_CREATE_PROCESS against an auto-elevating binary still has to happen, because handle inheritance is how the technique works. Running both conditions gives one narrow high-fidelity query and one broad rankable one.
- **No IOCs is a feature of this hunt, not a limitation of it.** AhnLab withheld every hash, domain and IP. An organisation that consumes this report through an indicator feed gets nothing at all. The lineage, the suspended extra `explorer.exe`, the sideloaded `uxtheme.dll` next to a signed SumatraPDF binary and the `%PUBLIC%` kernel driver are all still there, and all still cost the operator something real to change.
