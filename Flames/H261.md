  The Chrome profile directory is touched constantly, so the naive "file read" event is unusable. Expect
  legitimate access from:
  - `chrome.exe` itself, and Chrome's own updater/crashpad helpers, all signed by Google LLC.
  - Enterprise backup, DLP, EDR, and profile-roaming/USMT tooling that walks the entire user profile. These are

  KEY PATHS AND APIS (from the report):
    %LocalAppData%\Google\Chrome\User Data\<Profile>\Sync Data\LevelDB   (WebauthnCredentialSpecifics records)
    passkey_enclave_state                                                (wrapped identity private key)
    chrome://device-log/FIDO                                             (Security Domain Secret leaked in plaintext)
    NCryptOpenStorageProvider / NCryptImportKey / NCryptSignHash         (TPM-backed signing via Windows CNG)

  THE THREE VARIANTS:
  - Pass-ta-Key (device identity impersonation): read the wrapped identity private key, use CNG to sign the
    cloud-authenticator WebSocket handshake and assertion request, receive a valid assertion, forward it to the
    relying party. Unit 42: the signature is obtained "silently, without user consent, biometrics, device unlock
    or elevated privileges."
  - Silver Pass-ta-Key (UV key manipulation): delete `passkey_enclave_state` or issue a device/forget command to
    force re-onboarding; during the `uv_key_pending` window send `device/add_uv_key` registering an
    ATTACKER-controlled public key. The cloud authenticator does not validate attestation on new UV keys, so the
    attacker can thereafter sign any request with UV=1 — even with the victim device offline.
  - Golden Pass-ta-Key (master key extraction): force re-onboarding, watch for `passkey_enclave_state` to be
    recreated, dump Chrome process memory, recover the Security Domain Secret in plaintext, and use it to decrypt
    the private key material in the sync records. Unit 42 notes the SDS cannot be revoked.

  WHY THE CLOUD SIDE WON'T SAVE YOU: synced passkeys carry a CONSTANT `signCount`, so the classic FIDO clone-
  detection signal is absent. Unit 42 states relying parties "have limited visibility into unauthorized use of
  synced credentials, including scenarios where passkeys are extracted or reused from unexpected environments."
  That is precisely why this must be hunted on the ENDPOINT — the authentication that follows looks correct.

  HUNT LOGIC (Windows):
  1. PRIMARY / HIGHEST FIDELITY — file DELETE or MODIFY of `passkey_enclave_state` where the initiating process is
     not chrome.exe signed by Google LLC:
       DeviceFileEvents
       | where FileName == "passkey_enclave_state"
       | where ActionType in ("FileDeleted","FileModified","FileRenamed")
       | where InitiatingProcessFileName !~ "chrome.exe"
       | project Timestamp, DeviceName, AccountName, FolderPath, ActionType,
                 InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessCommandLine
  2. SYNC DB ACCESS — any non-Google-signed process opening files under
     `\Google\Chrome\User Data\*\Sync Data\LevelDB\`. Sysmon EID 11 covers writes/copies; for reads, use EDR file
     telemetry or an audit ACL (Windows Security 4663) on the directory. Prioritise processes that read only
     these files rather than sweeping the whole profile.
  3. THE GOLDEN CHAIN (sequence hunt, strongest composite) — `passkey_enclave_state` deleted, then within 60
     minutes a cross-process memory read of chrome.exe by the same process:
       Sysmon EID 10 where TargetImage endswith \chrome.exe AND GrantedAccess has PROCESS_VM_READ (0x0010)
         AND SourceImage is not Google-signed
       DeviceEvents | where ActionType == "OpenProcessApiCall" | where FileName =~ "chrome.exe"
     Legitimate software does deletion OR memory reads; the pair is the tell.
  4. CNG / TPM SIGNING FROM AN UNEXPECTED PROCESS — imports of `NCryptOpenStorageProvider`, `NCryptImportKey`,
     `NCryptSignHash` (ncrypt.dll) in a process that has also touched the Chrome profile. Sysmon EID 7 (Image
     Load) on ncrypt.dll plus EID 1 lineage; where available, ETW `Microsoft-Windows-Crypto-NCrypt`. Also flag
     Microsoft Platform Crypto Provider key-usage events attributed to a non-browser process.
  5. EGRESS — the accessing process establishing a WebSocket/HTTPS session to a Google cloud-authenticator
     endpoint. A non-browser process speaking the authenticator protocol is anomalous on its own.
  6. BREADTH PIVOT — check whether the same process also read `Login Data`, `Local State`, `Web Data`, or cookie
     stores. Most real-world implementations of this will be bolted into a commodity infostealer, so the passkey
     read will be one branch of a broader credential sweep ([[H249]], [[H247]]).
  7. IDENTITY-SIDE CORROBORATION — for hosts with a hit, pull relying-party/IdP WebAuthn records and look for
     assertions with UV flag 0 where userVerification was required, unexpected re-onboarding/recovery prompts, and
     authentications from environments inconsistent with the registered device.

  RESPONSE NOTE: because the Security Domain Secret is not revocable, a confirmed Golden Pass-ta-Key on a host
  means the synced passkeys for that Google account must be treated as compromised and re-enrolled, not merely
  re-authenticated. Scope by account, not by host.

  CROSS-REF: T1111 (Multi-Factor Authentication Interception — the practical effect is a silent MFA bypass),

# H261

Unit 42 published three attacks against Google Password Manager's synced passkeys in August 2026, and the part that should change how you hunt is what they *don't* require: no password, no fingerprint, no device unlock, no administrator rights. Malware running as the ordinary logged-in user reads two files and asks the TPM to sign something.

```
%LocalAppData%\Google\Chrome\User Data\<Profile>\Sync Data\LevelDB   ← WebauthnCredentialSpecifics
passkey_enclave_state                                                ← wrapped identity private key
NCryptOpenStorageProvider → NCryptImportKey → NCryptSignHash         ← TPM signs as the "trusted device"
```

HEARTH had zero coverage of passkeys or WebAuthn — not one hunt mentioned either word. That gap matters more than a typical one, because the entire organisational case for passwordless is that stolen credentials stop working. These attacks do not break that promise cryptographically; they sidestep it by stealing the device's identity instead of the user's.

The worst variant is the quietest to describe and the loudest to hunt. Delete `passkey_enclave_state`, wait for Chrome to re-onboard, and dump the browser's memory while the Security Domain Secret — the passkey master key — sits there in plaintext. Unit 42 notes it cannot be revoked.

## Why

- **The cloud side cannot see this, by design.** Synced passkeys report a constant `signCount`, so the standard FIDO clone-detection heuristic never fires. Unit 42 states outright that relying parties have limited visibility into passkeys extracted and reused from unexpected environments. The authentication that follows a successful theft is a *correct* authentication. If you are not hunting the endpoint, there is nothing to find anywhere else.
- **Deletion of `passkey_enclave_state` by a non-Chrome process is a near-zero-false-positive event.** Most of this hunt requires filtering; this one line does not. Chrome does not routinely delete its own enclave state, and an attacker has a specific reason to: it forces the re-onboarding window that both the Silver and Golden variants depend on. It is one file name, one action type, one signer check.
- **The attack requires no privilege escalation, which removes the step most detection stacks are tuned for.** No UAC prompt, no token manipulation, no LSASS handle. A great deal of credential-access detection is anchored on privilege boundaries being crossed, and this crosses none. The observable is mundane file and memory access by an unprivileged process — which is exactly why it needs to be written down as a hunt rather than left to a rule someone else wrote.
- **The blast radius is unusual and asymmetric.** A stolen browser password affects one site. A stolen Security Domain Secret decrypts the private key material for every passkey in the synced set — and unlike a password, it cannot be rotated. That turns a single unprivileged infection on one laptop into a full re-enrolment exercise for that identity, which is an incident-response decision worth being able to make from evidence rather than assumption.
- **This will not stay research for long.** The pattern — read two profile files, call CNG, forward an assertion — is a small amount of code and slots naturally into commodity stealers that already parse Chrome's `Login Data` and cookie stores. Hunting it as a branch of existing infostealer behaviour now is much cheaper than retrofitting after the first mass campaign.
