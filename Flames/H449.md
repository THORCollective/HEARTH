false_positive_notes: |
  Key regeneration is a legitimate and encouraged operation, so the endpoint alone is not the finding:
  - Routine rotation. Platform teams and users rotate their own keys on a schedule or after an exposure. These calls name the caller's own `user_id` (or omit it), come from the expected admin tooling or from the user's own session, and leave the key's owning user unchanged. The finding requires the owning user to *change*.
  - Legitimate administrative reassignment. A real administrator moving a key between users - during an offboarding, a team transfer or a project migration - produces the same database change. Separate these by whether the calling credential already held administrative scope before the call. An escalation is a call made by a key that did not have admin scope and did after.
  - Automation that provisions keys on behalf of users. A self-service portal creating or rotating keys for many users is normal and will name other users' IDs constantly. Allowlist that automation by its credential, and alert on any *other* credential doing the same thing.
  - Upgrade and migration scripts can rewrite key rows in bulk, changing timestamps without any API call. Correlate database changes to request logs; a row change with no corresponding request is a migration, not an exploit.
  Many deployments run LiteLLM with minimal logging and no audit trail, in which case none of the above is separable and the practical answer is to patch and then rotate every key, rather than to hunt. Treat the inventory question - where are our gateways, what version, who can reach them - as the prerequisite.
notes: |
  Gateway request telemetry - Core filter: HTTP POST to `/key/regenerate` (and the `/key/update` and `/key/generate` siblings) where the request body carries a `user_id`, `user_email` or equivalent that differs from the identity bound to the presenting credential. Triage values: request path, method, status code, source IP, user agent, the presenting key's hash or ID, the `user_id` named in the body, response body key ID. Correlation: within the following minutes, calls to administrative routes from the same source or the same new key - `/key/list`, `/key/info` for keys the caller does not own, `/user/new`, `/team/new`, `/model/new`, budget or spend-limit updates, and anything under the proxy's admin UI paths. Strong red flags: a single source cycling `user_id` values across several regeneration calls; a successful regeneration from a source address that has only ever made inference calls; administrative routes returning HTTP 200 to a credential that received HTTP 401 on the same routes earlier the same day.
  Database state as the ground truth - Core filter: in the LiteLLM backing store, compare each virtual key's owning user and role against the last known-good inventory. The exploit's effect, as GTIG describes it, is to "elevate standard Virtual Keys into full PROXY_ADMIN master administrative credentials". Triage values: key ID, owning user, assigned role or scope, budget and spend caps, created-at and updated-at timestamps. Correlation: any key whose role became an administrative one, or whose owning user changed, with no matching administrator request in the gateway logs. Strong red flags: more than one key holding master administrative scope when the deployment is documented to have one; an administrative key whose created-at predates its role change by weeks (an ordinary key that was promoted, rather than a new admin key).
  Where the gateway sits in the intrusion - Core filter: GTIG reports this used by a follow-on cluster that had already, in GTIG's words, come "after acquiring pre-validated Virtual Keys from the threat actor that established initial access", then "executed targeted application logic exploitation against the victim's LiteLLM gateway." So the exploitation is not initial access - the keys arrived first. Pivot backwards into how a virtual key leaked (committed configuration, a `.env` file, an exposed CI variable, a developer workstation) and forwards into what the administrative key then reached. GTIG notes the result was "establishing deep, persistent control over the compromised environment", and that actors also "hosted LiteLLM gateways on external servers to manage and route API traffic" - so an administrative key on your gateway may be routing your upstream quota through someone else's proxy.
  Host and container telemetry for the gateway itself - Core filter: on the pod or VM running the gateway, look for process execution that is not the proxy's own runtime (a shell, `curl`, `wget`, a package manager), writes to the proxy's configuration YAML or `.env`, and outbound connections to destinations that are not the configured upstream model providers. Triage values: process command line, parent process, file path written, destination address and port, container image and digest. Strong red flags: an outbound connection from the gateway to a new upstream endpoint; a configuration write adding a model provider or changing the master key; the proxy restarting shortly after a configuration write.
  Exposure triage, worth doing regardless of whether the hunt finds anything - Core filter: enumerate every LiteLLM, vLLM, Ollama and OpenAI-compatible proxy in the estate, record its version and whether its management routes are reachable from outside the cluster, and confirm CVE-2026-40217 is patched. Check the upstream project's own advisory for the fixed version rather than relying on a version number quoted in a blog post. GTIG separately reports actors scanning for and testing publicly exposed inference endpoints, so an unauthenticated or internet-reachable management plane is an exposure independent of this specific flaw.
  Expected, not observed by GTIG: the same class of identity-rebind flaw should be hunted for in any multi-tenant AI gateway or model-routing middleware that issues per-user keys, not only LiteLLM - the pattern is an endpoint that accepts a user identifier from the request body and trusts it. GTIG's report names the LiteLLM `/key/regenerate` endpoint and CVE-2026-40217 specifically, and does not describe equivalent flaws in other gateways.

# H449

Most AI security attention sits on the model and on the cloud provider's IAM. Google Threat Intelligence Group's LLMJacking reporting documents an intrusion that went through neither: the privilege boundary that actually mattered was a piece of open-source routing middleware the victim ran themselves.

GTIG describes it directly. "In one case, after acquiring pre-validated Virtual Keys from the threat actor that established initial access, a follow-on cluster executed targeted application logic exploitation against the victim's LiteLLM gateway. The actor exploited a user ID rebind vulnerability in the /key/regenerate endpoint (CVE-2026-40217) to elevate standard Virtual Keys into full PROXY_ADMIN master administrative credentials, establishing deep, persistent control over the compromised environment."

LiteLLM is a widely deployed proxy that gives an organisation one OpenAI-compatible endpoint in front of many providers, with per-user virtual keys, budgets and spend tracking. That makes it both a chokepoint for every model call in the environment and a credential store in its own right. An ordinary virtual key promoted to the proxy's master administrative role does not just get more quota - it gets the ability to mint keys for anyone, change budgets, add upstream providers, and read what everyone else is spending. None of that generates a single event in the cloud provider's audit log, because none of it happens at the cloud provider.

HEARTH has no coverage of AI gateway middleware at all. The AI-related hunts in the corpus look at inference usage, at stolen provider keys, and at agentic frameworks driving cloud APIs. This is the layer in between - the thing an organisation installed to govern model access, which is now a target because it governs model access.

## Why

- Self-hosted AI middleware has become infrastructure without becoming inventory. Gateways get stood up by platform or ML teams to control cost and route traffic, they hold every provider credential and every user's key, and they are frequently absent from the asset list, the patch cycle and the log pipeline. That combination is what makes an application-logic flaw in one worth this much.
- The escalation is invisible to cloud-native monitoring. Because the rebind happens inside the gateway's own database, the cloud provider sees only well-formed inference traffic from the gateway's service identity, exactly as before. Detection has to come from the gateway's request log and its key table, which means the hunt is also an argument for collecting both.
- An administrative key is durable in a way a stolen virtual key is not. Rotating the leaked key that got the operator in does nothing if they minted their own administrative credential on the way through - the same shape as any identity-provider compromise, and the same reason the remediation has to start from the key table rather than from the incident's first indicator.
- The access was bought, not earned, which means the technique scales. GTIG describes a specialised ecosystem in which one cluster sells validated keys and another monetises them. A gateway flaw that turns a cheap commodity credential into administrative control over an organisation's entire model estate is exactly the kind of capability that ecosystem rewards.
