false_positive_notes: |
  A handful of cross-platform developer tools do create dotfiles on Windows. Git writes .gitignore and .gitattributes, Node tooling writes .npmrc and .eslintrc, Python tooling writes .python-version, and several SDKs write dot-prefixed caches. These appear in repository working directories, user profile roots and package caches — not in System32. Scoping the hunt to Windows system and temp directories removes essentially all of them.
  Some agents and installers do use C:\Windows\Temp as scratch space, occasionally with unusual names. Confirm the writing process and its signer rather than treating the directory alone as the finding.
  Content is the second filter and it is decisive. A legitimate dotfile is text that a human could have written. An encrypted configuration is high-entropy binary with no readable structure. Sampling the first few hundred bytes separates the two immediately.
  Do not expect the file attributes to be set. The leading dot does not mark a file hidden on Windows, so the hidden and system attributes will usually be absent, and a hunt that filters on those attributes will miss this entirely. The report is explicit on the point: "This is not the case on Windows, where these files are not hidden."
  Forward slashes in a configured path are a clue, not an error in your tooling. One sample's configuration path is recorded as %LocalAppData%/Temp/.crond with forward separators, which ESET annotates as the attackers' typo. A path that mixes separators is worth noting during triage rather than normalising away.
  The file may legitimately be absent on an infected host. The implant carries an embedded default configuration and works without the file, writing it only during initialisation, so absence of a dotfile does not clear a host.
notes: |
  Core filter - file creation in a Windows system or temp directory where the filename begins with a dot. Triage values: full path, `InitiatingProcessFileName`, `InitiatingProcessFolderPath`, `InitiatingProcessCommandLine`, the writing process signer, and file size. Defender XDR, 30-day retention:
  ```kql
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("FileCreated", "FileModified")
  | where FileName startswith "."
  | where FolderPath has_any (@"\Windows\System32", @"\Windows\Temp", @"\AppData\Local\Temp")
  | where FileName !in~ (".gitignore", ".gitattributes", ".npmrc", ".DS_Store")
  | project Timestamp, DeviceName, FolderPath, FileName, FileSize,
            InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessCommandLine,
            InitiatingProcessAccountName
  | order by Timestamp desc
  ```
  Sysmon 11 equivalent - match `TargetFilename` containing `\.` as the final path component. Expressing "the basename starts with a dot" varies by backend: in Splunk, `| rex field=TargetFilename "\\\\(?<base>[^\\\\]+)$" | search base="." ` style extraction then a prefix match is more reliable than a raw wildcard, because a naive `*\.*` matches every file with an extension.
  Known paths from the reporting - `C:\Windows\Temp\.updatecache`, `C:\Windows\system32\.updatecache`, and `%LocalAppData%/Temp/.crond`. One sample also carries an unused configuration path `/tmp/.test_config`, which ESET assesses was left over from testing. Use these to confirm a match, not as the hunt itself; the leading-dot-in-a-system-directory shape is what generalises, including to future samples and to the Linux variant the report suggests exists.
  Triaging the content - The configuration is a JSON document encrypted with AES-256-CFB, where the first 16 bytes of the file are the IV, under a key embedded in the binary. For triage that means two things: the file will be small, and it will be uniformly high-entropy binary with no printable JSON structure despite being a configuration file. A quick entropy estimate or a hexdump of the first 64 bytes is enough to separate it from a legitimate text dotfile.
  Tying the file to a process - The implant writes this file itself during initialisation, so the writer in `DeviceFileEvents` is the implant, not an installer or a package manager. Pivot straight from the write to that process: its image path, whether it runs as a service, and its network behaviour. ESET records this family running as a Windows service under the name `ieupdate`, from paths including `C:\windows\system32\updater.exe`, `C:\Windows\system32\krbtman.exe` and `C:\windows\system32\windowsdefendersvc.exe`. A Go-built binary in System32 writing a dot-prefixed encrypted blob next to itself is the complete finding.
  Retrospective sweep - Because this is a path-and-name pattern rather than a hash, a one-off filesystem sweep across the estate for leading-dot filenames under System32 and Windows\Temp covers hosts whose file telemetry predates your retention window. Run it once alongside the live query.
  Related stages - The network side of this implant, including the mesh-overlay C2 that the configuration points at, is covered in [[H416]]. The service-naming and binary-masquerading patterns seen across this and other intrusion sets are covered in [[H412]].

# H418

ESET's October 2026 report on MythicRatatoskr documents a Go backdoor used against a Ukrainian grain logistics company in a UAC-0099 intrusion that was later handed to Sandworm. Among the host artefacts is one that only exists because of how the malware was written rather than how it was deployed.

The backdoor stores its configuration in a file at a hardcoded path, and across samples those paths are `C:\Windows\Temp\.updatecache`, `C:\Windows\system32\.updatecache` and `%LocalAppData%/Temp/.crond`. ESET draws the obvious conclusion: "All of the configuration filenames start with a dot. On Unix-like systems, programs used for listing files, such as ls, typically exclude these entries by default, effectively hiding them. This is not the case on Windows, where these files are not hidden. This further suggests the existence of a Linux variant." One sample carries an unused `/tmp/.test_config` path as well, and the `.crond` path uses forward slashes, which the report annotates as the attackers' typo.

So a concealment convention has been carried onto a platform where it conceals nothing. The file is fully visible in Explorer and in `dir`, and the hidden and system attributes are not set. More usefully, the convention is not merely ineffective on Windows — it is *unnatural*. Windows and its components do not create dot-prefixed files in `System32` or `Windows\Temp`. The cross-platform developer tools that do write dotfiles write them in repositories and profile directories, nowhere near a system directory.

The content closes the triage. This is not a readable settings file: it is a JSON document encrypted with AES-256-CFB, with the first 16 bytes serving as the IV, under a key embedded in the binary. A small, uniformly high-entropy file whose name begins with a dot, written into `System32` by a Go binary that runs as a service called `ieupdate`, is not an ambiguous artefact.

## Why

- The query is close to noise-free in the one place it matters. Scoped to Windows system and temp directories, leading-dot filenames are not something the platform or ordinary software produces, so this runs as a standing detection rather than a scored hunt.
- It keys on an authorial habit, which is more durable than any individual indicator. The paths differ between samples and the encryption key is per-build, but a codebase shared with a Linux target will keep naming its configuration this way. The report's own inference that a Linux variant exists rests on exactly this artefact.
- It survives the usual evasions. Renaming the binary, changing the service name, rotating the C2 address and rebuilding to change every hash all leave the configuration filename convention intact, because the convention is in the source, not the packaging.
- Attribute-based hiding detections will not cover it. Because the dot does nothing on Windows, the hidden and system attributes are typically unset, so hunts looking for concealed files by attribute pass over these entirely — a gap worth closing explicitly rather than assuming existing coverage applies.
- The write identifies the implant directly. The file is written by the backdoor during initialisation, not by an installer, so the writing process in file telemetry is the thing you are looking for, with no intermediate step to untangle.
