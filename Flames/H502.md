false_positive_notes: |
  Users legitimately enrol new passkeys and MFA devices constantly - new phones, replaced laptops, added hardware keys, service-desk-assisted recovery. The enrolment leg is therefore conditioned on the preceding challenge pattern and on the device model being new to the tenant, not on the enrolment itself. A user who approves one prompt and enrols a device model the tenant already knows is ordinary; a user who approves after a flood of prompts and the enrolment comes from an unfamiliar model and a residential ASN is not.

  Service-desk-assisted recovery produces a very similar shape to the attack, because the user may approve repeatedly, backup codes are often generated, and the source address may be unusual. Reconcile against service-desk tickets first; in practice the ticket either exists or the finding stands.

  Backup-code authentication is legitimate for users who have lost a device, but it should be rare and ticketed. Mandiant's detection guidance treats it as worth alerting on, particularly when originating from a non-corporate ASN or a known residential proxy network. A tenant where backup-code use is routine has a hygiene problem that will also hide this activity.

  Distance and impossible-travel heuristics will not fire on this activity and should not be relied on. Mandiant records COLD RELIC selecting residential proxies that geolocate to the same approximate location as the victim user, specifically to avoid impossible travel and other heuristic-based alerting, and recommends enriching authentication logs with residential proxy and VPN reputation and alerting on sudden residential ASN shifts for privileged accounts instead.

  The survival leg will produce apparent findings for every user who kept their own authenticators through a routine password change, which is the normal case - a password reset is not supposed to invalidate a passkey. That is precisely why the leg is scoped to accounts that went through an incident-driven reset rather than any reset, and why the output is a reconciliation question for the account owner rather than an alert.

  The specific claim that an enrolment follows an accepted push within minutes is a triage window, not a measured interval. Mandiant states the registration occurred after the victim accepted an MFA request but does not publish the delay. Calibrate the window against the tenant's own data.
notes: |
  Enrolment leg (identity-provider authentication and authenticator lifecycle logs) - Core filter, as a bounded three-stage correlation per principal. Stage one, three or more MFA challenge or failed-authentication events for one principal within 15 minutes. Stage two, a successful authentication for that principal from the same source address. Stage three, within 30 minutes of stage two, any of a passkey enrolment, an MFA device registration, or a backup-code generation event, by that principal. The window bounds matter - correlating authenticator enrolments to challenge bursts on principal alone over a long lookback will pair unrelated weeks.

  Triage values are `principal`, `event type`, `login challenge type`, `source IP`, `ASN`, `ASN type`, `device identifier`, `device model`, `user agent`, `result` and `timestamp`. Strong red flags, in rough order of weight: the registered device model has never appeared in the tenant before, which is the signal Mandiant names explicitly; the source ASN is a consumer ISP or a known residential proxy network; the principal holds administrative privilege, and Mandiant's case study begins with a Super Admin; backup codes are generated rather than used; more than one authenticator type is added in the same session, which matches the reported use of passkeys, backup codes and rogue MFA devices together.

  A device-model difference query, expressed against whichever identity log holds registration events:

      -- pseudo-query: device models new to the tenant in the last 7 days
      WITH known AS (
        SELECT DISTINCT device_model
        FROM device_registration
        WHERE registered_at < NOW() - INTERVAL '7 days'
      )
      SELECT r.principal, r.device_model, r.registered_at, r.source_ip, r.asn
      FROM device_registration r
      LEFT JOIN known k ON r.device_model = k.device_model
      WHERE r.registered_at >= NOW() - INTERVAL '7 days'
        AND k.device_model IS NULL
      ORDER BY r.registered_at DESC;

  In most tenants the result is a short list dominated by genuinely new hardware generations, which is a list worth reading weekly regardless of this actor.

  Survival leg (credential-reset records joined to authenticator inventory and session events) - Core filter: for every account that went through an incident-driven password reset or forced sign-out in the last 90 days, enumerate the authenticators registered before the reset that are still registered after it, and enumerate every successful authentication after the reset whose login challenge type was a backup code or a passkey registered before the reset. This is the leg that answers whether a past remediation actually worked, and Mandiant's report contains two separate instances where it did not - reauthentication using unrevoked attacker-enrolled passkeys that persisted across password and session resets and bypassed device registration controls, and a victim organisation whose password-only remediation left hijacked sessions intact.

  Also check whether sessions were in fact revoked. A reset event with no corresponding bulk session-revocation or refresh-token-invalidation event in the same window is a remediation that left the actor logged in. Mandiant's recommendation is unambiguous: when remediating suspected account compromise, password changes alone are insufficient, and administrators must revoke all active browser sessions, refresh tokens and authorised third-party OAuth app permissions across both cloud estates, and remove any unauthorised passkeys, backup codes or MFA devices.

  Cross-cloud leg (federation configuration joined to authentication logs) - Core filter: for each rogue authenticator found, enumerate every downstream service the issuing identity provider authenticates. Mandiant's second case study is a tenant using Entra ID as its federated single sign-on identity provider for Google Workspace, where the actor compromised the Entra ID account and registered a new MFA device in the SSO solution to retain access. The consequence for scoping is that an authenticator added at the identity provider is not one tenant's problem - it unlocks everything federated to it, and a response that cleans one cloud and not the other leaves the access intact. Build the federation map before the hunt, not during the response.

  Hardening that removes the technique rather than detecting it - Mandiant's guidance is to enforce phishing-resistant MFA using FIDO2 or WebAuthn hardware keys in place of SMS, voice and push, because hardware keys are bound to the origin URL and cannot be intercepted by adversary-in-the-middle reverse proxies or approved through fatigue attacks; to monitor identity logs for passkey registrations and rogue device enrolments, particularly on administrative accounts; and to require an existing administrator or out-of-band identity verification to approve any new MFA device or secondary authenticator. The last of those is what would have broken this intrusion at stage three.

  Scope note: H329 is the closest existing hunt - an extra device added to an existing Entra MFA method after vishing-led adversary-in-the-middle session theft, with nothing removed and nothing broken. The overlap is real and the distinctions are the point of this hunt: H329 is single-cloud Entra and keys on the device-addition event itself, whereas this hunt adds the push-fatigue precondition, the previously-unseen device model as discriminator, backup-code generation and use as a parallel authenticator path, the cross-cloud federation scoping, and the survival leg that checks whether a past reset actually removed the actor. H302 covers a stolen Entra session cookie being converted into a Windows Hello for Business credential, which is a different conversion path, and H262 covers local passkey state access on an endpoint rather than enrolment at the provider. H501 covers what this access was used for in the same intrusion.

# H502

Mandiant's November 18, 2026 report on COLD RELIC — the Russian state-sponsored group formerly tracked as COLDRIVER and UNC4057, also known as Star Blizzard, Callisto and Gossamer Bear — documents two linked cloud intrusions at US organisations. The initial access in the first was a stolen Super Admin credential plus an MFA push-notification fatigue attack, from a residential proxy network located close to the victim. What the actor did immediately after the victim accepted a prompt is the subject of this hunt: it registered a device model previously unseen within the tenant, and went on to use passkeys, MFA backup codes and rogue MFA devices to hold that access for months.

Mandiant then records the consequence twice over. In one case, the actor reauthenticated using attacker-enrolled passkeys that had never been revoked, which survived both password and session resets and bypassed device registration controls. In another, the victim organisation detected the intrusion and reset passwords for the affected accounts but did not revoke existing sessions, and the actor retained access.

That makes this a hunt with two halves. One looks forward for the enrolment as it happens. The other looks backward and asks a question most organisations have never asked: of the accounts we have already remediated, which still carry an authenticator the attacker put there?

## Why

- Enrolling an authenticator converts a stolen password into durable access, and the two events are only minutes apart in the log. The push-fatigue burst, the acceptance, and the enrolment are each individually ordinary and collectively a takeover, which is exactly the shape a correlated hunt is for.
- The previously-unseen device model is a strong, cheap discriminator that most tenants already have the data for and almost none use. It separates a user re-enrolling hardware they own from an operator enrolling hardware the organisation has never encountered, without needing to know anything about the user's habits.
- The survival leg finds damage that has already happened. Because a password reset is not meant to invalidate a passkey, the standard remediation leaves attacker-enrolled authenticators in place by design, and Mandiant has two observed instances of exactly that. Any organisation that has run a credential-reset response in the last quarter can run this check today.
- Federation turns one rogue authenticator into estate-wide access. Mandiant's second case study runs from a compromised Entra ID account into Google Workspace through federated SSO, which means scoping has to follow the federation map rather than the tenant boundary — and a response that cleans one cloud leaves the other open.
- Geographic heuristics are specifically defeated here, so the hunt does not depend on them. COLD RELIC chooses proxies that geolocate near the victim to avoid impossible-travel alerting, which makes ASN type and proxy reputation the enrichment that still works.
