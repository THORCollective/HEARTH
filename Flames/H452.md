false_positive_notes: |
  Each indicator here is a default rather than tradecraft, so each has a benign shadow:
  - Update-flavoured scheduled task names are everywhere. Genuine Microsoft and third-party updaters create tasks with names of exactly this shape, so the task *name* is a weak signal on its own. The discriminators are the action path (a legitimate updater does not run from `C:\Windows\Temp` or `C:\Temp`), the absence of a signed publisher on the action binary, and the creating principal - a task created by a process that is itself a child of a database engine, a web server or a shell is the finding.
  - Custom HTTP headers are common in legitimate software: telemetry agents, SaaS SDKs, API gateways and licence checks all add them. The constraint is that this one has a *fixed* value across every request from a host, is not present in any documented product, and accompanies a destination with no business relationship. Build the header inventory before hunting, or the queue is unworkable.
  - Self-signed TLS certificates on the public internet are routine - development servers, appliances, internal services exposed by accident. The finding is a self-signed certificate whose issuer or subject carries a known offensive-framework name, which is a much narrower population.
  - Go binaries with version-control metadata are normal; most compiled Go software carries it. The `vcs.modified` flag indicating uncommitted local changes is a weaker statement than it sounds, since plenty of legitimate software is built from dirty trees. Treat build metadata as a clustering aid for samples already known to be bad, which is how Kaspersky used it, not as a detection.
  - Renaming a binary to resemble a system process is caught by the mismatch between the file name and the file's own version resources and signature, not by the name alone; some legitimate software ships binaries with confusing names.
notes: |
  Scheduled-task persistence - Core filter: Security Event ID 4698 where the task's action command path falls under `C:\Windows\Temp\`, `C:\Temp\`, `C:\ProgramData\` or `C:\Windows\` and the action binary is unsigned or signed by an unexpected publisher. Kaspersky reports that on delivery "the agent created a scheduled task named" SystemUpdate, "which specified the path to the implant as the action to be performed", and that the framework’s source reveals an alternative method of persistence "by adding a value to the registry key" HKCU\Software\Microsoft\Windows\CurrentVersion\Run, "where the name of the created value matches the task name". Triage values: task name, task path, action command and arguments, the principal the task runs as, the trigger, `SubjectUserName` (who created it) and the creating process where your EDR links them. Strong red flags: the task runs as SYSTEM but was created by a non-administrative service identity; the same task name appears on several hosts within minutes; a `Run` key value under HKCU whose name matches a scheduled task name on the same host.
  Note on remote task creation - Kaspersky reports that with administrative rights "the agent on remote hosts often created scheduled tasks so that the malicious payload would run with SYSTEM privileges", and that an alternative avoids `schtasks` entirely by creating the task "via the `Schedule.Service` COM object". A COM-created task still produces 4698, so the Security log catches both; a filter written only against `schtasks.exe` command lines catches only one. For the COM path, look additionally at Sysmon Event ID 1 for the process that instantiated it and at WMI/COM activity on the source host.
  Implant file and process characteristics - Core filter: an executable in the four default directories above whose name resembles a Windows system process but which is not in `%SystemRoot%\System32`. Kaspersky notes the deployment paths were deducible from the attackers' own presence check, and that "the attacker can disguise the agent's name as that of a legitimate system process. In the example below, it mimics svchost.exe (svchosts.exe)". Triage values: file path, SHA-256, signature status, original file name from the PE version resource, parent process, `CommandLine`. Correlation: compare the PE's internal original-file-name against the on-disk name; a one-character variation on a system binary name with no matching version resource is decisive. Strong red flags: the binary is a Go executable (recognisable from its section layout and embedded runtime strings) living in a temp directory; Kaspersky reports that build metadata from `go version -m` "contains a path to the main package, which includes data pointing to the built-in CyberStrikeAI generator - a temporary directory with the build identifier. This path is identical for all payloads, making it a reliable signature", so retain the binary and extract its build info for clustering even after remediation.
  The HTTP header, which is the sharpest network signal - Core filter: outbound HTTP or HTTPS requests carrying an `X-Implant-Token` header. Kaspersky states that "When communicating with the server, the implant sends an" X-Implant-Token "header with a fixed value in the HTTP request. The token is unique to each C2 server and is embedded into the malicious payload during the build phase; therefore, it serves as both a network indicator and a sign that the samples belong to the same server." Triage values: the header name and value, destination host and port, requesting process, request interval, request and response sizes, user agent. Correlation: because the value is per-controller, every host presenting the same value is talking to the same controller - which turns one detection into the full victim list inside the environment in a single query. Note that this is only visible where TLS is terminated or inspected at the egress, or in plaintext HTTP; the implant also supports TCP and WebSocket transports, in which case the header is unavailable and the lineage and persistence halves of this hunt are the only route in.
  Controller discovery by certificate - Core filter: self-signed server certificates whose issuer or subject common name or organisation contains the framework's name. Kaspersky reports that "Upon launch, a self-signed TLS certificate is generated, with the framework's name appearing in the issuer and subject fields", and makes a further point worth acting on: "The certificate is created in memory at each startup, so the `not_before` field effectively records the time the process was launched. Accordingly, as with Cobalt Strike, the chronology of restarts can be reconstructed from the scan history." Triage values: issuer and subject fields, `not_before` and `not_after`, serial number, public-key fingerprint, the IP and port it was served on. Use this both prospectively in egress TLS metadata and retrospectively against internet-wide scan data, where the certificate's validity start times build a restart timeline for the controller.
  Pivot once a host is confirmed - Core filter: the post-exploitation set Kaspersky observed is conventional and well covered elsewhere in HEARTH, so use it as confirmation rather than as the entry point - `reg.exe` hive dumps, an LSASS MiniDump via `comsvcs.dll` where "the target process's PID was used instead of its name to make static detection based on the command line more difficult", DCSync and Golden Ticket via a renamed mimikatz, and lateral movement over SMB admin shares, Impacket's `wmiexec` and `Invoke-CimMethod`. Kaspersky's timeline is the reason to work quickly: "the entire attack - from agent deployment to the compromise of domain administrators - was completed within 3-4 days", with lateral movement, mass credential dumping and database export "taking no more than one hour".
  Expected, not observed by Kaspersky: the Linux persistence variant is documented in the same report as a crontab `@reboot` entry pointing at the beacon, which is the same idea on a different platform and needs its own hunt against cron and systemd telemetry rather than being folded in here. This hunt is scoped to Windows, where the scheduled task, Run key and masqueraded binary were observed.
  Expected, not observed by Kaspersky: an operator who rebuilds the framework can trivially change the header name, the task name and the certificate fields, since all three are build-time or source-level defaults. Kaspersky observed a single agent version throughout each incident and does not report any operator customising them, but the durable half of this hunt is the persistence shape and the implant's location, not the strings.

# H452

Kaspersky's Cyber Threat Intelligence team documents what it assesses to be one of the first public descriptions of a compromise involving an LLM in the wild. The framework is CyberStrikeAI, an open-source Go platform in which an LLM orchestrator on the C2 server plans the operation, picks tools and generates commands, while the implant on the victim stays deliberately dumb. Kaspersky is precise about this split: the implant is "a classic C2 agent with no AI functionality – no API keys, no calls to AI service APIs, and no autonomous logic", and "To the victim, this activity looks like a typical remote-control session, where a server-side LLM orchestrator queues tasks instead of a live operator."

That architecture is good news for defenders, and Kaspersky says so: "the introduction of AI into the attack chain does not yet present fundamentally new challenges for detection." In the same passage it adds that all the “intelligent” work remains on the attacker’s side, "while the compromised host is subjected to familiar actions." The novelty is speed - key phases took hours, and the whole intrusion from implant to domain-administrator compromise took three to four days - not capability.

It also means the implant can be hunted the way any beacon is hunted, by its defaults. And this one has unusually good defaults to hunt. Every request carries a custom header: "the implant sends an X-Implant-Token header with a fixed value in the HTTP request. The token is unique to each C2 server and is embedded into the malicious payload during the build phase; therefore, it serves as both a network indicator and a sign that the samples belong to the same server." Persistence is a scheduled task Kaspersky observed named `SystemUpdate` pointing at the implant, with a `Run` key alternative using the same name. The controller's listener generates a self-signed certificate "with the framework's name appearing in the issuer and subject fields."

Because the header value is per-controller rather than per-host, one detection answers the scoping question immediately: every machine in the environment sending the same value is talking to the same operator. That is a rarer property than it sounds, and it is worth building a query around before the defaults change.

## Why

- Framework defaults are the cheapest detection in any intrusion and the first thing to use before they are customised. CyberStrikeAI is publicly available and, as Kaspersky observes, that openness means different operators deploy it independently - so the defaults are likely to persist across unrelated campaigns rather than being hardened by one group.
- The per-controller header value turns detection into scoping. Most beacon indicators are per-sample or per-host; a value fixed at build time and shared by every implant from one server means a single matching request yields the complete internal victim list in one query, and the same value can be searched back through retained proxy logs.
- The persistence half survives what the network half does not. If the implant is configured for TCP or WebSocket transport, or egress TLS is not inspected, the header is invisible - but the scheduled task pointing at an unsigned binary in `C:\Windows\Temp`, created by a process descended from a database engine or web server, is still there in Event ID 4698.
- The certificate gives a retrospective and external view. Because the controller regenerates its certificate in memory at every start, the `not_before` values recorded in internet-wide scan history reconstruct the controller's uptime, which supports dating the intrusion and finding sibling infrastructure - the same analytic that has worked on Cobalt Strike team servers for years.
- Kaspersky's own framing argues for hunting the host behaviours rather than building something new for AI-driven intrusions. The orchestrator left no local artefacts at all - no local model calls, no anomalous resource consumption - because it ran entirely on the attacker's server. The only thing that changed is how fast familiar techniques arrived.
