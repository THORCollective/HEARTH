false_positive_notes: |
  Ably is a legitimate commercial service with real customers, and some organisations genuinely use it - live dashboards, chat features, collaborative editing, IoT telemetry. The question is not whether the service is legitimate but whether this estate uses it, and that is a one-row answer. Where the answer is no, any connection to rest.ably.io, realtime.ably.io or main.pusher.ably.net is worth a look on its own. Where the answer is yes, pivot immediately to which process is connecting - a browser or the one application that embeds the SDK is expected, a Java host process or the Sysinternals screen magnifier is not.

  The Pusher-compatible endpoint complicates the inventory question, because an estate that uses Pusher itself, or a product that bundles a Pusher client, will produce similar-looking WebSocket upgrades to different hostnames. Scope on the hostname, not the protocol version.

  The client parameter is a strong discriminator but not a stable one. `client=cpp-socks5` is this plug-in naming itself, and the operator can change that string in the next build. The channel-name pattern `private-socks5-<instance>-request` and `-response` is similarly a configuration choice. Treat both as high-confidence confirmations when present and never as the only query.

  Software-development hosts and container build agents sometimes reach a long tail of SaaS APIs as part of dependency resolution or integration tests, which can place a single Ably connection on a developer workstation legitimately. A single short-lived connection is weak; a resident connection with a steady message rate is not.

  The Go-runtime signal has real false positives on any host that legitimately runs Go software, which is common on servers. It is only meaningful as a secondary observation about a process whose on-disk image contains no Go code - a reflectively loaded Go binary inside javaw.exe or start.exe is the finding, not Go on the host.

  Leg one, destination inventory (DNS and endpoint network telemetry) - Core filter, and the cheapest high-yield query in this hunt. Resolve the one-row question first - does any sanctioned application in this estate use Ably? - then run:

      DeviceNetworkEvents
      | where Timestamp > ago(30d)
      | where RemoteUrl has "ably.io" or RemoteUrl has "ably.net" or RemoteUrl has "pusher.ably"
      | summarize Connections = count(), FirstSeen = min(Timestamp), LastSeen = max(Timestamp),
                  Urls = make_set(RemoteUrl, 20)
          by DeviceId, DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath,
             InitiatingProcessParentFileName
      | order by Connections desc

  Thirty days is the full Defender advanced hunting retention; a longer window is truncated silently. The equivalent on Sysmon is Event ID 22 filtered on `QueryName` ending in `ably.io` or `ably.net`, joined to Event ID 1 on `ProcessGuid` for the command line and parent, because Event ID 3 alone gives an IP that tells you nothing.

  Triage values are the initiating process, its folder path, its parent, and whether the host is a server. Red flags, heaviest first - the process image sits in `C:\Windows\System32` or under `C:\ProgramData`, which is where the report observed this campaign staging; the process is one of the four legitimate sideload hosts the report names, javaw.exe, start.exe, pythonw.exe or zoomit.exe; the parent is services.exe; the same device also appears in H503's GitHub query, because GitDoor runs both channels at once.

  Leg two, the HTTP shapes (web proxy records) - Three specific request families, each worth its own saved search:

  - `POST /messages` to `rest.ably.io` with an `Authorization: Basic` header, where the request body is a JSON array containing a `channels` value beginning with `data:main.` - the channel name is the dead-drop filename.
  - `GET /channels/comm/messages?limit=50` and `POST /channels/data/messages` against the same host. The literal channel names `comm` and `data` and the fixed `limit=50` are what the report observed; the first is the implant's status check and the second its retry path.
  - A WebSocket upgrade to `main.pusher.ably.net` with path `/app/<key>` and a query string containing `protocol=7` and `client=cpp-socks5`. The `client` parameter is the SOCKS5 plug-in announcing itself. Subscriptions to channels matching `private-socks5-.*-(request|response)` confirm it.

  Where message bodies are available, the delimiter `###!!###` and the terminator `###EOF###` are the abchannel.ts framing, and `socks5:connect`, `socks5:data` and `socks5:close` are the ab2channel.ts message names. The SOCKS5 plug-in reads from the remote socket in 0x8400-byte blocks, which is 33,792 bytes decimal - a fixed, unusual chunk size that shows up as a tight cluster in a distribution of outbound message sizes if the proxy records them.

  Leg three, the host-side plumbing (Sysmon 17/18, section objects, image loads) - The proxy plug-ins do not read a configuration file. Both read a shared-memory section whose name is built from the hosting process ID - `Local\pc<PID>` for the modified Erfrp client and `Local\pcs<PID>` for the Ably client - and the shellcode loader uses `Local\sm<PID>` for its arguments. A section object whose name is a prefix plus the creating process's own decimal PID is an unusual naming convention and a good hunt in its own right on hosts already under suspicion.

  Two further host artefacts worth checking on any hit. The Erfrp-derived proxy is a Go binary whose build path survives in the image - the report publishes it as `C:/Users/user/Desktop/pythonrat/proxytest/Erfrp-0.1/frpc.go`, with the Ably client carrying `C:/Users/user/Desktop/armon/server.go`. A string search for `Erfrp` or those paths across process memory on a suspect host is decisive. And because both plug-ins are reflectively loaded rather than written to disk, image-load telemetry will show the Go runtime inside a process whose on-disk file contains none - which is the reflective-loading signal, not a Go-on-host signal.

  Hardening that removes the technique - realtime-messaging SaaS is a small, enumerable category. An estate that egress-filters to an allowlist of sanctioned SaaS hostnames removes this channel outright, and the inventory needed to do that is the same inventory leg one asks for. B074 builds it.

  Scope note: no existing HEARTH hunt names Ably, Pusher or Erfrp - a grep of every hunt body for those strings returns nothing. The nearest neighbours are by shape rather than by service. H503 is the same implant's other channel and should be run alongside this one. M036 covers command and control routed through consumer cloud services at the campaign level, including PubNub, which is the closest conceptual match - a realtime message bus as tasking channel - but it models multi-service routing volumetrically rather than hunting one service's request signatures. H062 covers legitimate tunnelling services generally. The Erfrp proxy and the SOCKS5-over-WebSocket plug-in are tunnelling, so H062's baseline questions apply, but neither the destination nor the artefacts here are in it.

# H504

Part one of Kaspersky's Operation ShadowCloud report describes a backdoor that talks to GitHub. Part two describes its plug-ins, and that is where the more interesting choice shows up: for proxying, the operator did not stand up a listener. It rented a message bus.

Ably is a commercial realtime-messaging platform — publish/subscribe channels, a REST endpoint, a WebSocket endpoint, and a Pusher-compatible protocol for clients written against that older API. Operation ShadowCloud uses all three faces of it. The GitDoor backdoor publishes its victim survey through the REST endpoint and polls a channel named `comm` for status. One plug-in, `abchannel.ts`, is a Go program built on Ably's own SDK that forwards TCP through a channel. Another, `ab2channel.ts`, is a complete SOCKS5 proxy riding Ably's Pusher-compatible WebSocket, announcing itself in the query string as `cpp-socks5` and splitting socket reads into 33,792-byte blocks.

Neither plug-in carries a C2 address. The report is explicit that the backdoor embeds no hard-coded C2 domain and retrieves the hostname and port at runtime through the proxy plug-in or the Ably channel — which means capturing the implant does not hand you the infrastructure. What it hands you is a protocol, and that is what this hunt is built on.

## Why

- Most estates have a one-row answer to whether they use Ably at all, and it is usually no. That makes a destination query the whole hunt for the majority of organisations — a rare case where a modern SaaS-hosted channel is cheap to find rather than expensive, provided someone asks the question before the incident.
- Choosing a message bus removes every indicator a hunter would normally start from. There is no attacker domain to block, no self-signed certificate, no unusual port, and no hard-coded C2 to recover from the binary. The tradeoff the operator accepted is that the protocol itself is distinctive, and it is logged by any proxy that records query strings.
- SOCKS5 over a commercial WebSocket is lateral movement infrastructure, not just exfiltration. Once `ab2channel.ts` is running, the operator can open arbitrary TCP sessions to anything the host can reach, through a connection that reads as a SaaS integration.
- The shared-memory configuration channel is a reusable hunt. Both proxies read their settings from a section named with a fixed prefix plus the host process's own PID, which is an unusual convention and a good discriminator on any host already under suspicion.
- A reflectively loaded Go binary inside a Java or Python host process is an internal contradiction that image-load telemetry can see. The on-disk file contains no Go runtime; the running process does.
