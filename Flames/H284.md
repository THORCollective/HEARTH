# H284

Most macOS stealer tradecraft ends with a LaunchAgent. This chain's final stage does something quieter:
it stops adding persistence and starts inheriting it.

Stage 6 copies, rewrites and replaces applications that are already installed and already trusted —
desktop cryptocurrency wallets, and three trojanized hardware-wallet companion apps. There is no plist
to find, no new binary in a suspicious directory, no autostart entry. As the source describes it, there
is "no separate persistence, only malicious code patiently waits inside wallet apps." The user launches
the wallet themselves, from the Dock, on purpose. Execution is granted by the victim's own routine.

The targeting explains the effort. The chain covers 60 wallet browser extensions, 21 desktop wallet
applications, and the three companion apps, and what it wants from the desktop ones is the recovery seed
phrase. That distinction matters for how you prioritize this: stolen cookies and session tokens expire,
and stolen passwords can be rotated. A seed phrase cannot be revoked or reset. A successful theft is
permanent and immediately monetizable, which is why the operators are willing to spend a whole stage on
in-place application rewriting rather than settling for the credentials they already had.

Earlier stages of the same chain are already covered by [[H147]], which hunts the ClickFix Terminal-paste
delivery and the in-memory `osascript` stage. This hunt deliberately picks up where that one stops — at
the point where the malware stops behaving like a stealer and starts behaving like a supply-chain
implant on software that is already on the host.

There is a useful accident of macOS design here: rewriting a bundle breaks its seal. `codesign -v` will
report "a sealed resource is missing or invalid," usually followed by `file added:` and a path. That is
a deterministic, scriptable verdict available on any host, with no prior telemetry required.

## Why

- **Substitution persistence is invisible to every persistence-focused control on the platform.** Tools
  and hunts built around LaunchAgents, LaunchDaemons, login items, cron and `.zshrc` — which is most of
  the macOS persistence detection literature, and most of what BlockBlock-style utilities watch — see
  nothing here, because nothing is added. The autostart inventory is unchanged. Detection has to come
  from bundle integrity instead, which is a different data source than most macOS hunting programs
  currently collect.
- **macOS gives you a deterministic integrity oracle, and almost nobody queries it.** Every signed
  application carries a seal over its own resources. `codesign -v` on a rewritten bundle fails with a
  specific, parseable error. Sweeping installed applications for signature validation failures is a
  point-in-time check that needs no historical telemetry, runs in seconds per host, and can be pushed
  through existing MDM — an unusually cheap way to cover a technique this consequential.
- **The write event and the signature check are stronger together than either alone.** Writes into
  application bundles do happen legitimately, constantly, via self-updaters — so the write alone is
  noisy. Signature failures also occur benignly, on developer builds and mid-update. But a write from a
  non-updater process *followed by* a broken seal or a changed team ID is a conjunction with no routine
  explanation, and it is computable automatically at the moment of the write.
- **The protection people assume covers this has real gaps and a recent bypass.** macOS 13 added
  Gatekeeper protection against unauthorized app tampering, and it does make casual bundle modification
  harder. But researchers demonstrated in July 2026 that an app or script running with the current
  user's privileges can silently replace a bundle's main executable and launch the modified app without
  a signature warning — it does not defeat Gatekeeper or TCC outright, but it is exactly the primitive
  this stage needs. Assuming the OS handles it is not currently safe.
- **Notarization is not a clean bill of health for this family.** Jamf's analysis of MacSync found
  samples that were code signed *and* notarized under a valid team ID whose code directory hashes had
  not been revoked at the time of analysis, with some detected by only a single VirusTotal engine. That
  makes first-seen-team-ID and signing-identity-drift analytics as important as validity checks — the
  question is not only "is this signed" but "is this signed by whoever signed it last week."
- **The value at risk is irreversible in a way that changes triage priority.** Cookie and session theft
  is recoverable with rotation and revocation. A seed phrase harvested from a trojanized wallet is a
  permanent, immediately liquid loss with no remediation path, so a hit on this hunt should escalate
  ahead of a generic infostealer detection on the same host.
