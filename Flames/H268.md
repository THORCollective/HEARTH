title: PowerShell console history file deleted, truncated, or disabled via Set-PSReadLineOption on a server
hypothesis: >-
  A hands-on-keyboard operator who has been typing into PowerShell leaves a complete, plaintext, per-user
  transcript of every command behind in `%APPDATA%\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt`.
  Before leaving the host they remove it — `Remove-Item` on the file, truncation to zero bytes, `Clear-History`
  for the live session, or the quieter option, `Set-PSReadLineOption -HistorySaveStyle SaveNothing`, which stops
  the file being written at all and leaves no deletion event to find. Hunt for deletion or truncation of
  ConsoleHost_history.txt by any process, for `SaveNothing` in script-block telemetry, and for the file simply
  ceasing to grow on a host where PowerShell is still being used.

required_data_sources:
  - Sysmon Event ID 23 (FileDelete, archived) and Event ID 26 (FileDeleteDetected) — deletions of ConsoleHost_history.txt, with the Image of the deleting process. EID 23 is preferred because it archives the file content for recovery
  - Sysmon Event ID 11 (FileCreate) and Defender XDR DeviceFileEvents — ActionType FileDeleted / FileModified / FileRenamed on the PSReadLine path, plus FileSize where available to catch truncation
  - PowerShell Script Block Logging (Microsoft-Windows-PowerShell/Operational Event ID 4104) — the literal text Clear-History, Set-PSReadLineOption, HistorySaveStyle, SaveNothing, and Remove-Item paths naming PSReadLine
  - PowerShell Module Logging (Event ID 4103) and Engine Lifecycle (Event ID 400/403) — session start/stop bracketing, to establish that PowerShell was in use across a window where history stopped growing
  - Sysmon Event ID 1 / Windows Security 4688 with command-line auditing — del, Remove-Item, and Clear-Content invocations naming the history path
  - Windows Security 4663 (object access) on the PSReadLine directory with a SACL for DELETE and WRITE_DATA — the audit-side view for estates without Sysmon
  - Windows Security 1102 (audit log cleared) and Event ID 104 — co-occurring event-log clearing, which is the same operator intent one layer up
  - Windows Security 4624/4625 — LogonId, LogonType and source IP for the session that owned the deleted history, to scope what was hidden
false_positive_notes: |
  The PSReadLine history file is a user-profile artifact and does get removed legitimately. Expect volume from:
  - Profile cleanup and roaming — USMT, folder redirection, FSLogix, Citrix/UPM profile management, and
    "delete local profile on logoff" policies. On VDI and RDS this is constant and will dominate the results.
    These are the population to enumerate first.
  - Disk cleanup utilities, privacy tools (CCleaner, BleachBit) and endpoint hygiene scripts.
  - Developers and administrators who genuinely clear history after pasting a secret at a prompt. This is a real
    and reasonable behaviour, and on a developer workstation it is common.
  - Antivirus quarantine or remediation removing the file as part of a broader cleanup.
  - Users with `HistorySaveStyle` set to `SaveNothing` deliberately as a personal preference, or org-wide via
    profile script — check whether it is set centrally before treating any instance as a finding.
  The separators, in order of strength:
  (1) WHERE. This is a server-and-DC hunt first. On a domain controller, file server, or hypervisor host,
      almost nobody has a legitimate reason to be removing PowerShell history — the benign populations above
      are overwhelmingly workstation and VDI phenomena. Scope to servers and the noise mostly disappears.
  (2) WHO DELETED IT. Profile management tooling and cleanup utilities delete the file from a named, signed
      agent, usually at logoff and usually alongside hundreds of other profile files. An operator deletes it from
      `powershell.exe`, `cmd.exe`, or a beacon process, on its own, mid-session.
  (3) SELECTIVITY. One file out of a profile tree is not cleanup. Count how many other files under the same
      profile were touched in the same window — a profile wipe touches thousands, an operator touches one.
  (4) CO-OCCURRENCE with other indicator removal. `wevtutil cl`, `Clear-EventLog`, Security 1102, deletion of
      `.bash_history` on adjacent Linux hosts, or removal of staged tooling in the same window. Gunra performs
      log deletion and history clearing together; either alone is ambiguous, both together is not.
  (5) THE SILENT VARIANT. `Set-PSReadLineOption -HistorySaveStyle SaveNothing` produces no file event at all.
      The only way to catch it is script-block logging on the literal string, or the negative-space check: a host
      where 4104/400 events show active PowerShell use but the history file's last-write timestamp has stopped
      advancing. Build both — the string match is cheap, and the negative-space check is what catches an operator
      who knows to avoid the deletion.
  Enumerate profile-management and cleanup agents as a named population and scope the primary hunt to servers.
  Do not suppress the path.
notes: |
  PLATFORM: Windows — prioritise servers, domain controllers, jump hosts, and hypervisor management hosts over
  workstations, for the scoping reason in the false-positive notes.

  CATEGORY: Flames. Embers rejected — the benign population is real but it is bounded and nameable (profile
  management, cleanup utilities, AV remediation), and the far cheaper fix is scoping to servers, where that
  population barely exists. A 30-day baseline of "who normally deletes PowerShell history on a domain
  controller" would return an empty set, which is the answer without the exercise. Alchemy rejected — there is
  no volume, rate, or distribution to model here; the event is a single file operation on a named path, and the
  question is binary. The negative-space check (history stopped growing while PowerShell kept running) is a
  scheduled comparison of two timestamps, not a statistical model.

  SOURCE: CISA / FBI joint advisory AA26-222A, "#StopRansomware: Gunra Ransomware". The advisory states that
  while active in victim networks Gunra actors "typically attempt to mask their presence by deleting
  system/network access logs [T1685] and clearing command history [T1070.003]", and that they concentrate
  activity in the 22:00-06:00 window to reduce the chance of an administrator noticing. The same intrusions used
  Impacket `secretsdump.py` against domain controllers, OpenSSH tunnels for persistence, and exfiltrated up to
  tens of terabytes before encrypting.

  WHY THE ARTIFACT IS WORTH SO MUCH: `ConsoleHost_history.txt` is not a security log. It is a usability feature —
  PSReadLine writes every line the user types at an interactive PowerShell prompt to a plaintext file, per user,
  with no size cap by default and no rotation. It is not cleared at session end. On a host where an operator has
  been working hands-on-keyboard it contains, verbatim and in order, their entire session: the discovery
  commands, the credential paths, the internal hostnames, the tooling URLs, and frequently plaintext passwords
  passed as arguments. It survives reboots. Very few artifacts on Windows give an incident responder that much.
  That is precisely why a competent operator removes it, and why its absence is itself evidence.

  DEFAULT PATH:

    %APPDATA%\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt
    C:\Users\<user>\AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt

  Note the path is per-host-application: `ConsoleHost_history.txt` for powershell.exe, and a separate file for
  the ISE and for VS Code's integrated terminal. Check the whole PSReadLine directory, not just the one filename.

  THE FOUR VARIANTS, AND WHAT EACH LEAVES BEHIND:

    Clear-History                                        -> clears the LIVE session buffer only. Does NOT touch
                                                            the file. Often used by operators who believe it
                                                            does. Visible in 4104. Weakest of the four, and the
                                                            one most likely to leave the file intact — always
                                                            check for the file before assuming it is gone.
    Remove-Item / del <path>                             -> Sysmon EID 23/26, DeviceFileEvents FileDeleted.
                                                            Loudest. EID 23 archives the content, so the history
                                                            is recoverable from the Sysmon archive directory.
    Set-Content / Clear-Content <path>                   -> file size drops to 0. No delete event. Catch via
                                                            FileModified plus a size check, or FileCreated
                                                            overwriting an existing path.
    Set-PSReadLineOption -HistorySaveStyle SaveNothing   -> NO file event of any kind. Nothing is ever written
                                                            again for that session. Only script-block logging or
                                                            the negative-space check will find it.

  STARTING QUERY — Defender XDR, the file-event path:

    DeviceFileEvents
    | where Timestamp > ago(30d)
    | where FolderPath has @"\PowerShell\PSReadLine"
    | where ActionType in ("FileDeleted", "FileModified", "FileRenamed")
    | where InitiatingProcessFileName !in~ ("explorer.exe")   // then subtract your enumerated profile agents
    | project Timestamp, DeviceName, InitiatingProcessAccountName, InitiatingProcessFileName,
              InitiatingProcessCommandLine, FolderPath, FileName, ActionType
    | join kind=leftouter (DeviceInfo | distinct DeviceName, DeviceType) on DeviceName
    | where DeviceType == "Server"

  STARTING QUERY — the silent variant, script-block logging:

    event.code:4104 and powershell.file.script_block_text:(
        "HistorySaveStyle" or "SaveNothing" or "Clear-History"
        or ("Remove-Item" and "ConsoleHost_history")
        or ("Set-PSReadLineOption" and "SaveNothing"))

  THE NEGATIVE-SPACE CHECK, which is the one an operator cannot design around: for each server, compare the
  last-write timestamp of ConsoleHost_history.txt against the most recent PowerShell engine-lifecycle event
  (400/403) or script-block event (4104) for the same user. A host where PowerShell has been running
  interactively for days but the history file has not grown since last Tuesday has either had SaveNothing set or
  had the file replaced. Run this as a periodic sweep, not a real-time rule.

  CROSS-REF: T1685.005 (Clear Windows Event Logs — Gunra does both; Security 1102 and 104 in the same window
  raises confidence sharply. Note ATT&CK has retired T1070.001 and moved this behaviour under the T1685
  "Disable or Modify Tools" family — use the current ID), T1685 (the advisory's own mapping for deleting
  system/network access logs, and the right parent for SaveNothing, which is functionally telemetry
  disablement rather than deletion),
  T1059.001 (PowerShell — what generated the history in the first place). Note that on Linux and ESXi hosts in
  the same estate the equivalent artifacts are `~/.bash_history`, `~/.zsh_history`, `HISTFILE`, and
  `unset HISTFILE` / `HISTSIZE=0`; Gunra operates across both, so sweep them together. [[H266]] covers the
  credential-access step that typically appears in the history being deleted.

# H268

`ConsoleHost_history.txt` is not a security control. It is a convenience feature — PSReadLine writes every line you type at a PowerShell prompt to a plaintext file, per user, uncapped, unrotated, and not cleared when the session ends.

Which means that on a domain controller where someone has been working hands-on-keyboard, there is a file sitting in a user profile containing their entire session in order: the discovery commands, the internal hostnames they found, the paths they went looking for credentials in, the URLs they pulled tooling from, and — routinely — passwords passed as command-line arguments. It survives reboots. There are very few artifacts on Windows that hand an incident responder that much for free.

Gunra's operators delete it. CISA's advisory lists clearing command history alongside deleting access logs as standard practice for the group, performed while they are still resident, in the same 22:00–06:00 window they do everything else in. The deletion is not the attack — it is the tell that something worth hiding was typed on that host.

## Why

- **The absence of the file is itself evidence, which is unusual and useful.** Most anti-forensic actions leave you with less to work with. This one leaves you with a specific, timestamped, attributable event: a named process deleted a named file in a named user's profile at a known moment. You lose the commands but you gain the certainty that an interactive session on that host was worth concealing — and on a domain controller or file server, that is enough to justify a full investigation on its own. Deletion converts an unknown into a scoped question.

- **Scoping to servers turns an unusable detection into a clean one.** The benign population for this technique — profile roaming, VDI cleanup, FSLogix, privacy utilities, developers clearing a pasted secret — lives almost entirely on workstations. Domain controllers, file servers, jump hosts and hypervisor management hosts have essentially none of it. The same query that would drown an analyst across a laptop fleet produces a handful of results a month when pointed at the server estate, and every one of those results is worth reading. This is a case where the right filter is not a suppression list but a change of where you look.

- **`SaveNothing` is the variant that beats every file-based detection, and almost nobody hunts for it.** `Set-PSReadLineOption -HistorySaveStyle SaveNothing` produces no deletion, no modification, no truncation — nothing is ever written again. An operator who sets it at the start of their session never generates the artifact in the first place, so a detection built purely on Sysmon EID 23 sees a clean host. Catching it needs script-block logging on the literal string, or the negative-space check: PowerShell is demonstrably running interactively, and the history file has stopped growing. Building only the deletion rule means building the half an informed adversary will step around.

- **Co-occurrence with event-log clearing raises this from suspicious to conclusive.** Gunra clears command history *and* deletes system and network access logs. A profile agent deleting a history file is common; a process deleting a history file in the same window as Security 1102, a `wevtutil cl`, or the removal of staged tooling is not. Correlating the two indicator-removal families collapses the false-positive rate to near zero without needing any baseline at all, and it is cheap because both event sources are almost certainly already collected.

- **Timing is a free discriminator here, and the advisory hands it to you.** CISA notes Gunra deliberately works between 22:00 and 06:00 to avoid administrator attention. Profile cleanup fires at logoff, which correlates with the working day; an operator's cleanup fires at 03:00. Overlaying the deletion timestamps against each host's own activity profile costs nothing and separates the populations further — and unlike most timing heuristics, this one is documented adversary tradecraft rather than an assumption.

- **Recovery is often possible and rarely attempted.** Sysmon Event ID 23 archives the deleted file's contents to the configured archive directory before the deletion completes. If EID 23 with `ArchiveDirectory` is configured, the operator's entire typed session is sitting on disk after they thought they removed it. That should be the first pivot on any finding, and it is a strong argument for enabling EID 23 with archiving on servers specifically — the volume is manageable when scoped, and the forensic payoff is disproportionate.

- **HEARTH had no coverage for T1070.003 in any form** — not on Windows, not on Linux — despite it being a routine step for every hands-on-keyboard intrusion that touches a shell, and despite the artifact being one of the highest-value forensic sources available on a compromised Windows server.
