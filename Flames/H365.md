false_positive_notes: |
  Dot-prefixed directories are a Unix convention, not a Windows one, and that asymmetry is what makes this worth hunting. On Windows they do occur legitimately — cross-platform developer tooling creates `.git`, `.vscode`, `.gradle`, `.m2`, `.nuget`, `.cache` and similar under user profiles, and some Java middleware genuinely uses dot-named working directories. Those cluster in predictable places: user profile roots, source trees, build agent workspaces. What is not normal is a dot-prefixed directory appearing under `C:\Windows\Temp` on a production application server, created by a web or application process rather than by a developer tool. Scope the hunt by path and by creating process and the noise largely disappears. The EDR-script half has its own caveat - legitimate administrative scripts that stop or reconfigure security agents do exist, for troubleshooting, imaging and vendor-directed workarounds, and they are usually named plainly for exactly that reason. The discriminator is provenance - a sanctioned script runs from a management share or software distribution path under a deployment account, is identical across many hosts, and is accompanied by a change record. One copy, in a hidden folder, on one server, is not that. Note also that legitimate names may be imitated - `.bea-cache` is plausible precisely because BEA WebLogic is the lineage of the Oracle middleware PeopleSoft runs on.

# H365

Sekoia's October 2026 retrospective on ShinyHunters covers years of identity and SaaS intrusions, but one detail from its PeopleSoft campaign is worth a hunt on its own: `C:\Windows\Temp\.bea-cache\cs_disable.cmd`.

Read the path slowly. `cs_disable.cmd` is a script to turn off CrowdStrike. It is sitting in a directory called `.bea-cache` — BEA being the company behind WebLogic, the middleware lineage that Oracle PeopleSoft runs on. An administrator glancing at a compromised PeopleSoft server sees what looks like middleware scratch space. The leading dot means directory listings and tools that follow Unix conventions skip it. And `C:\Windows\Temp` is a path many organisations exclude from scanning outright.

The rest of the campaign fits around it. Initial access came from CVE-2026-35273, a 9.8-rated flaw in PeopleSoft Environment Management, followed by JSP webshells named `orau.jsp` and `webpack.jsp` — names picked to read as application and front-end build artefacts. Persistence ran through a scheduled task called `MeshFwFix` and a MeshAgent binary at `C:\Windows\Temp\ma.exe`, with C2 at `azurenetfiles.net` and agents labelled as "Microsoft Azure services". Chisel tunnelled, Rclone exfiltrated, and PowerShell monitoring was switched off before the obfuscated scripts ran.

Sekoia published exact-match detection content for all of it, which is worth running today and worthless next quarter. The durable question is simpler: why is there a dot-prefixed directory on a Windows server at all?

## Why

- **Dot-prefixed directories are a Unix convention on a non-Unix system.** On Windows they appear in predictable places — user profiles, source trees, build workspaces — and essentially never under `C:\Windows\Temp` on a production application server. That asymmetry is a cheap, structural filter.
- **The name is chosen to pass a human review.** `.bea-cache` is plausible to anyone who knows what PeopleSoft runs on, which is exactly the person most likely to be looking. Detection has to come from path and provenance, not from whether the name sounds reasonable.
- **Disabling EDR is both the goal and the evidence.** Even if the script is never found, the sensor's own telemetry shows the outcome — and a host that goes sensor-silent while still producing Windows event logs is a strong standalone detection.
- **The webshell names imitate build output.** `webpack.jsp` reads as a front-end artefact; `orau.jsp` reads as an Oracle component. Hunting by extension, directory and writing process survives the operator renaming both.
- **Sekoia's SOL content is immediately runnable.** The published file paths, task name, domain and IP give a free retrospective sweep across the estate today, which is the right use of IOCs — scoping, not detection.
- **It targets the half of ShinyHunters that HEARTH did not cover.** The OAuth consent and MFA-addition legs are already hunted in [[H234]] and [[H329]]. The PeopleSoft on-premises leg, with real host artefacts, was not.
- **Scanning exclusions are the attacker's planning assumption.** `C:\Windows\Temp` is excluded on a great many servers for performance reasons. A hunt that looks specifically where scanning does not is checking the assumption the operator is relying on.
