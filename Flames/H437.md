false_positive_notes: |
  Legitimate third-party patch management genuinely runs from the Windows update download tree, and Kaspersky is explicit that in the archive they examined "most executables were legitimate components of the third-party patch management tool Patch My PC". The presence of that product, running from that path, is not the finding. The finding is a `fabric.config` or a `.resx` beside it.
  `.NET` applications legitimately ship `.exe.config` files, and plenty of them legitimately set an AppDomainManager. Scope the file-creation check to configuration files written outside a vendor installation directory, and to configuration files whose write time is long after the binary beside them was installed.
  `fabric.config` is a legitimate Windows Server AppFabric Cache Client artifact. On a host that genuinely runs AppFabric this file is expected in the application directory. Confirm whether AppFabric is installed at all before treating the file name as suspicious; on a workstation or a server with no AppFabric role, it has no business being there.
  Software deployment windows will generate bursts of file writes under the update tree that look like staging. Correlate against the change calendar, and prefer the content checks over the file-name checks during a patch cycle.
  `dllhost.exe` is a normal, high-volume COM surrogate process. Its mere presence means nothing; only an instance with no plausible COM client, or one making outbound connections, is interesting. Baseline before relying on it.
notes: |
  Platform - Windows. Kaspersky states the malware was designed to target a customized, government-only build of Windows used by government entities in Asia, and identified a single victim; the loading mechanism itself, however, depends only on the .NET Framework and is not specific to that build.
  Why this is not the same hunt as the standard AppDomainManager case - the established detection for this technique is: a planted `.exe.config` sets an AppDomainManager, and a non-Microsoft-signed DLL then loads into a Microsoft-signed .NET host before `Main()` runs. That logic keys on the unsigned load. This chain has no unsigned load. Kaspersky found that "even the .NET assemblies used for the injection were Microsoft-signed", and the assembly the `.config` names is a real Microsoft one. The abuse is a legitimate class reading a second configuration file: it has a "design flaw that can be abused to load arbitrary assemblies", and "its instance first attempts to find and read the default configuration file, fabric.config, located in the same directory". Everything attacker-controlled is in `fabric.config` and in the resource it points at, so the signature-based filter that catches the common case returns nothing here. This is the gap this hunt covers; see the coverage note at the end.
  The chain, as the report describes it - a CAB archive is placed in the directory that stores Windows operating system update packages; Kaspersky records the archive name as a 40-character hexadecimal string, `e4537a1762fcafd2fd96bfc825bad34f9db9a24d`. Kaspersky did not observe delivery: "we only saw the process PatchMyPC-ScriptRunner.exe running with the following arguments". That process loads its `.config`, which names a Microsoft-signed assembly and type; the type reads `fabric.config`; `fabric.config` names `System.Resources.ResXResourceSet`, which parses `Resources.resx`; and "Parsing this .resx file with ResXResourceSet causes the embedded Base64" payload "to invoke BinaryFormatter.Deserialize(), triggering a deserialization vulnerability that enables a TypeConfuseDelegate attack", which in turn reaches a XAML payload. Kaspersky notes that of the files in the archive, apart from the resource, "none of the files contain malicious code".
  Why the resource file is the best single artifact - the binary payload is not a PE on disk. It is a Base64 blob inside a human-readable XML resource file, which means file-reputation and PE-based scanning have nothing to grade, while a content search for the resource schema plus a long Base64 run is cheap and specific.
  Check 1 - the second configuration file, by name and by location. This is the highest-value check because the file is the hinge of the whole chain:
  ```shell
  dir /s /b "%WINDIR%\SoftwareDistribution\fabric.config" 2>nul
  dir /s /b "%WINDIR%\SoftwareDistribution\*.exe.config" 2>nul
  dir /s /b "%WINDIR%\SoftwareDistribution\*.resx" 2>nul
  ```
  Any hit in this tree is worth triage on its own. A `.resx` file in the Windows update download tree has no legitimate reason to exist there.
  Check 2 - the same question in Defender XDR, over the retained window. Advanced hunting keeps 30 days, so the lookback is capped at that:
  ```kusto
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where FileName =~ "fabric.config"
     or FileName endswith ".resx"
     or (FileName endswith ".exe.config" and FolderPath has @"\SoftwareDistribution\")
  | project Timestamp, DeviceName, FileName, FolderPath, ActionType,
            InitiatingProcessFileName, InitiatingProcessCommandLine, SHA256
  | order by Timestamp desc
  ```
  `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, so this finds the staging of these files and never the act of loading them. The load has to come from image-load telemetry, which is check 3.
  Check 3 - the rare assembly load, with the signature joined in. `DeviceImageLoadEvents` has no signature columns of its own, so the certificate state has to be joined from `DeviceFileCertificateInfo` on SHA1:
  ```kusto
  let window = 2m;
  let loads =
      DeviceImageLoadEvents
      | where Timestamp > ago(30d)
      | where FileName in~ ("Microsoft.HostIntegration.Connectors.dll")
      | project LoadTime = Timestamp, DeviceId, DeviceName, FileName, FolderPath, SHA1,
                InitiatingProcessFileName, InitiatingProcessFolderPath;
  let starts =
      DeviceProcessEvents
      | where Timestamp > ago(30d)
      | where FolderPath has @"\SoftwareDistribution\"
      | project StartTime = Timestamp, DeviceId, HostProcess = FileName, HostPath = FolderPath,
                HostCommandLine = ProcessCommandLine;
  loads
  | join kind=inner starts on DeviceId
  | where LoadTime between (StartTime .. StartTime + window)
  | join kind=leftouter (DeviceFileCertificateInfo | project SHA1, IsSigned, Signer, IsTrusted) on SHA1
  | project LoadTime, DeviceName, HostProcess, HostPath, HostCommandLine,
            FileName, FolderPath, IsSigned, Signer, IsTrusted
  | order by LoadTime desc
  ```
  The join is bounded to a two-minute window because an AppDomainManager assembly loads before the host process reaches `Main()`; a join on `DeviceId` alone across a 30-day lookback would correlate unrelated days. Note what the signature columns will say here: signed, Microsoft, trusted. That is the point - the result is interesting because of *which* assembly loaded into *which* host, not because the signature is bad.
  Check 4 - the configuration file content, which is where the attacker-controlled type name actually sits. The file names in checks 1 and 2 can be changed by the operator; the XML structure is load-bearing and cannot. Content-search any `.config` written outside a vendor installation directory for an `appDomainManagerAssembly` attribute, for a `customType` element carrying a `className` attribute, and for `System.Resources.ResXResourceSet`. Kaspersky describes the crafted file plainly: "The fabric.config file is meticulously crafted."
  Check 5 - the log edit, which is a second independent artifact. The same chain does not clear logs wholesale; it rewrites them selectively, to "filter out any lines containing the exact substring GetExtendedUpdateInfoHandler, and write the filtered content back to the log files", for files matching a six-character date pattern under a `CmitUpdateAgent` log path. A log file whose modification time is recent but whose newest entry is old, in that tree, is the artifact. This only works against logs collected off-host, because the tampering happens in place.
  Where the next stage runs - Kaspersky describes a later stage reached through RPC and a remote COM object, giving a "covert method for initiating a new process that loads the malicious payload", and notes that "This technique effectively separates the infection chain from its initial process, allowing it to bypass behavioral monitoring by security solutions such as EDR." That stage executes in `dllhost.exe` and is hunted separately; see the pairing note.
  Inference, not stated by Kaspersky - the Defender queries, the two-minute join window, the content-search attributes and the modification-time-versus-newest-entry heuristic in check 5 are all mine. Kaspersky published the chain and the artifacts, not detection logic, and did not state how the CAB archive reached the host. Nothing here should be read as a vendor-published detection.
  Closest existing coverage - [[H165]] is the nearest existing hunt and covers the common form of this technique: an attacker-planted `.exe.config` that sets `appDomainManagerAssembly` to a malicious DLL, with ETW suppression directives, detected by watching for a non-Microsoft-signed DLL loading into a signed .NET host. The distinction is the signature state of the loaded code: H165's core filter assumes an unsigned or untrusted image, and this chain never produces one, because the arbitrary-assembly load is reached through a flaw in a legitimate Microsoft class and a second configuration file. Run both; H165 catches the planted-DLL variant and this one catches the fully-signed variant. [[H356]] and [[H357]] also touch `.exe.config` abuse but on different chains and different hosts.
  Pairing - [[H438]] covers the stage that follows in this same intrusion, where the payload is executed inside `dllhost.exe` through a remotely activated COM object so that the process tree no longer connects to the loader.

# H437

The standard way to hunt AppDomainManager injection is to watch for an unsigned DLL loading into a Microsoft-signed .NET host process before `Main()` runs. It works because the usual version of this technique plants a `.config` file that points directly at attacker code. NetamLoader never loads attacker code that way, and that is the reason it needs its own hunt.

Kaspersky's analysis starts from a detection alert on a `.config` file inside a CAB archive sitting in the directory that stores Windows operating system update packages. The initial read of the archive found nothing: "most executables were legitimate components of the third-party patch management tool Patch My PC, and even the .NET assemblies used for the injection were Microsoft-signed." The `.config` names a real Microsoft assembly and a real Microsoft type. The type is the AppFabric cache client configuration class, and it has a "design flaw that can be abused to load arbitrary assemblies" — when it loads, "its instance first attempts to find and read the default configuration file, fabric.config, located in the same directory."

So the attacker-controlled content is one file further down than anyone is looking. `fabric.config` names `System.Resources.ResXResourceSet`, which parses `Resources.resx`, and "Parsing this .resx file with ResXResourceSet causes the embedded Base64" payload "to invoke BinaryFormatter.Deserialize(), triggering a deserialization vulnerability that enables a TypeConfuseDelegate attack." Every signature check along that path passes, because every assembly in it genuinely is Microsoft's.

That shifts the hunt from signatures to files. The artifacts are a second configuration file and an XML resource, both in a directory where neither belongs, and the payload is a Base64 string inside human-readable XML rather than a PE on disk — so there is nothing for file reputation to grade. The file names can be changed by the operator; the XML structure cannot, which is why the content check matters more than the name check.

One more artifact is worth collecting at the same time, because it is independent of all of the above: this chain does not clear logs, it edits them. It rewrites specific log files to "filter out any lines containing the exact substring GetExtendedUpdateInfoHandler, and write the filtered content back to the log files." A log file in that tree with a recent modification time and a stale last entry is evidence on its own — but only if the logs were collected off the host, since the rewrite happens in place.

## Why

- The detection that catches the common form of this technique keys on an unsigned or untrusted image load, and this chain produces neither, so it passes cleanly through the established check.
- The payload is a Base64 blob inside an XML resource file rather than an executable on disk, which removes PE-based scanning and file reputation from the picture entirely.
- The artifacts are specific and cheap to look for: a `fabric.config` and a `.resx` in the Windows update download tree are both wrong by location, independent of any hash.
- Staging inside the operating system update package directory borrows that directory's legitimacy, and it is a path that most file-creation monitoring treats as noisy and tunes down.
- The selective log rewrite leaves a detectable inconsistency that wholesale log clearing would not, and it is the one artifact here that survives the operator changing every file name.
