category: Flames
title: "A legitimate packet-filter driver is loaded to steal one source address off a production 443 listener and reroute it to a high local port, forwarding everyone else to the real service on loopback"
hypothesis: >-
  A Windows backdoor on an internet-facing server stops owning a port and starts borrowing one. It loads
  a legitimate kernel packet-capture and manipulation driver, carried inside itself as a resource for both
  architectures, and installs a filter narrow enough to be invisible: inbound TCP to the port a real
  service already listens on, but only from one source address. Those packets have their destination port
  rewritten to the backdoor's own high local port, and the backdoor's replies have their source port
  rewritten back, so responses appear to come from the production service. Traffic that does not carry the
  expected magic value is forwarded to the real service on loopback and works normally. The result is a
  backdoor with no exposed port, no outbound beacon, and no service disruption - and the observables are
  a signed filter driver on a host that has no tunnelling product, a listener on a high port owned by a
  process that is not the web stack, and loopback traffic to a port the host also serves externally.

false_positive_notes: |
  The driver is a real signed utility driver with legitimate users, so the whole hunt rests on host role rather than on the driver being bad.
  - Legitimate software ships this class of driver. VPN clients, personal firewalls, parental-control and traffic-shaping tools, some proxy and tunnelling utilities, and a range of network diagnostic products all install packet-interception drivers. The report says so directly. The discriminator is the host: a driver like this on an internet-facing web or application server, which runs none of those products, is the finding. Build the allowlist from the software inventory before running the hunt.
  - Developer and analyst workstations are a large benign population. Anyone who runs a local proxy, a packet manipulation tool, or a network emulator will load one of these. Scope the hunt to servers and to internet-facing roles rather than running it estate-wide, or the signal is buried.
  - High-port listeners are abundant on Windows. RPC, WinRM-adjacent services, application frameworks and ephemeral listeners all appear. The combination is what matters: a high-port listener whose owning process is not part of the application stack, on a host that also loaded a filter driver, on a host that serves a public port.
  - Loopback forwarding is a normal reverse-proxy pattern. IIS ARR, nginx on Windows, a sidecar agent and many application architectures forward to 127.0.0.1 by design. Where such a design exists, document it; the anomaly is loopback forwarding to the externally served port by a process that is not the documented proxy.
  - Driver load events are frequently not collected. Sysmon Event ID 6 is excluded from a number of default configurations and the Windows System log rolls quickly. If neither is available this hunt cannot run on the host, and determining that is the first result.
  - A single source address in a filter means almost nothing is visible until that address connects. An idle implant of this design produces a driver and a listener and no traffic at all, so the host-side checks have to be able to stand alone.
notes: |
  Source reporting is Check Point Research's November 10, 2026 report on CopperDragon, which it assesses as a possible digital quartermaster supplying the Sparrow malware framework to several China-nexus actors including FamousSparrow, Earth Estries, TropicTrooper and UAT-9244, across three clusters named SilentDelivery, OceanGate and DarkWire. CPR reports that "some observed versions of the Windows backdoor SparrowDoor include kernel-level packet interception capabilities, with WinDivert drivers embedded as resources for x86 and x64", noting that "WinDivert is a legitimate driver for network packet capture and manipulation, and is commonly used by utilities such as VPNs, firewalls, and tunneling applications."
  What the design achieves, in CPR's words - The actor "abused the driver to convert SparrowDoor into a passive backdoor that intercepts and manipulates packets at the kernel level, making its traffic less visible. This allows the backdoor to listen internally on one port while receiving connections through an externally accessible port, such as 443, that is already used by a legitimate service." The filter is narrow: "the backdoor applies a strict filter to intercept connections from a specific source IP address to the legitimate service's port. It manipulates the packet and rewrites the destination port to the backdoor's internal listening port, typically a high port such as 49628. For response traffic, it rewrites the source port back to the external service port, making the responses appear to originate from the legitimate service." CPR publishes the filter expression itself, in which the inbound clause matches a destination port and a single source address and the outbound clause matches the backdoor's internal source port. Selection is by marker: "incoming connections are checked for the magic value 0x11223344. Matching requests are queued for backdoor command processing, while nonmatching traffic is forwarded to the legitimate service at 127.0.0.1:<external_port>, allowing normal connections to continue functioning."
  Closest existing HEARTH coverage, and why this is a separate hunt - [[H468]] covers a passive backdoor on an internet-facing Exchange server that takes tasking from inbound requests to Exchange-shaped URL paths and answers a malformed request with a legitimate-looking error page. Both hunts are passive backdoors on a shared service port with no outbound beacon, and that overlap is real and worth naming. The mechanisms and the telemetry are different: H468 lives in the application - an HTTP handler reading paths, found in web server logs and module inventories - while this one lives below it, in a kernel driver rewriting port numbers, found in driver-load events, a socket inventory that disagrees with observed traffic, and loopback forwarding. A host can carry either without the other, and the checks that find one do not find the other. [[H478]] is the Linux appliance equivalent of the marked-connection idea, and [[H366]] covers a raw packet socket with a BPF filter on an appliance.
  Core filter 1, the driver on the wrong host - The highest-value check and the only one that works while the implant is idle. Hunt Sysmon Event ID 6 and System Event ID 7045 for packet-interception driver loads, then subtract every host whose software inventory explains it. On an internet-facing IIS, Exchange or application server with no VPN or tunnelling product, one such load is the entire finding. Triage values are the driver path, its signer, its hash, the installing process and its parent, and whether the host's role explains any of it. Note that the signature will be valid - this is a legitimately signed driver - so a signature check is not a triage step here, and that is the point of choosing it.
  Core filter 2, the socket inventory that does not match the traffic - A passive backdoor of this design produces a specific inconsistency. The host's TCP table shows a high-port listener owned by a process that is not part of the application stack, and external sessions arrive on the production port rather than on that high port, because the rewrite happens in the kernel before the TCP stack sees it. Capture `Get-NetTCPConnection` with owning process periodically and compare the listener set against the documented application stack. CPR gives 49628 as a typical value, but the port is configurable, so the check is role-based rather than port-based.
  Core filter 3, loopback forwarding to the port the host serves externally - Non-matching traffic is forwarded to `127.0.0.1:<external_port>`. On a host with no documented reverse-proxy design, a loopback connection to the externally served port, originating from a process that is not the web stack, is a strong corroborator. This requires loopback to be present in network telemetry; many Sysmon configurations exclude 127.0.0.1 for volume reasons, and a one-line configuration change on the relevant servers makes this filter available.
  Sample Defender XDR query, within the 30-day advanced hunting retention, pairing a filter-driver load with a high-port listener and bounding the join so events on different days cannot pair:
  ```kusto
  let lookback = 30d;
  let driver_loads =
      DeviceEvents
      | where Timestamp > ago(lookback)
      | where ActionType == "DriverLoad"
      | where FolderPath has_any ("windivert", "WinDivert")
            or FileName has_any ("WinDivert64.sys", "WinDivert32.sys", "WinDivert.sys")
      | project load_time = Timestamp, DeviceId, DeviceName, FolderPath, SHA256,
                InitiatingProcessFileName, InitiatingProcessCommandLine;
  let loopback_forwards =
      DeviceNetworkEvents
      | where Timestamp > ago(lookback)
      | where RemoteIP in ("127.0.0.1", "::1")
      | where RemotePort in (443, 80, 8080)
      | project fwd_time = Timestamp, DeviceId, InitiatingProcessFileName,
                InitiatingProcessId, RemotePort;
  driver_loads
  | join kind=leftouter loopback_forwards on DeviceId
  | where isnull(fwd_time) or fwd_time between (load_time .. load_time + 7d)
  | summarize loopback_forward_count = countif(isnotnull(fwd_time)),
              forwarding_processes = make_set(InitiatingProcessFileName1, 20)
            by DeviceName, FolderPath, SHA256, InitiatingProcessFileName,
               InitiatingProcessCommandLine, load_time
  | sort by load_time desc
  ```
  The join is a `leftouter` on purpose: a host that loaded the driver and has produced no loopback forwarding yet still has to appear in the result, because an idle implant is the normal state between operator sessions. Run the corresponding `Get-NetTCPConnection` collection separately rather than trying to reconstruct a listener inventory from event data, because a listener that was already open before the lookback began generates no event to find.
  Expected, not observed by Check Point - The service name used to install the driver, the on-disk path the driver is written to, and how the operator reaches the host to trigger the first interception. CPR describes the capability, publishes the filter expression and the magic value, and gives a typical internal port, but does not document the installation artefacts, so filter 1 above is written against the driver class rather than against a named service.
  Scope - Internet-facing Windows servers, and in particular mail, web and application servers in telecommunications and government environments, which is the victim profile CPR reports across the DarkWire and OceanGate clusters. The hunt is also worth running against any Windows host where an inbound session on a production port has been observed to last far longer than the service's normal transaction, because that is what an operator session through this design looks like from the network.

# H479

The backdoor does not have a port. It has your port.

Check Point Research found versions of SparrowDoor that carry a legitimate, signed kernel packet-interception driver inside themselves as a resource — one for x86, one for x64. WinDivert, the kind of driver a VPN client or a personal firewall installs. There is nothing wrong with it. That is why it was chosen.

Once loaded, the implant installs a filter narrow enough that nothing else in the environment notices. Inbound TCP to 443, from one specific source address. Those packets get their destination port rewritten to the implant's own high local port — 49628 in the reported case. The implant's replies get their source port rewritten back to 443, so the answers look like they came from the web server.

Anything arriving on 443 without the expected magic value gets forwarded to the real service on `127.0.0.1:443` and works exactly as it should. The site stays up. Monitoring stays green. Nobody's TLS handshake fails.

So what is actually left to find?

Not an exposed port — there isn't one. Not an outbound beacon — there isn't one. Not an invalid signature — the driver is properly signed and will pass every check you point at it.

What is left is a question about the host's job. A packet-interception driver belongs on a laptop running a VPN. It does not belong on an internet-facing IIS server. One driver-load event on a machine whose software inventory cannot explain it is the whole finding, and it is findable while the implant is sitting idle waiting for its operator — which is most of the time.

## Why

- **It defeats the three things most teams detect C2 with.** There is no new listening port to inventory, no outbound connection to a suspicious destination, and no unsigned binary in the kernel. A programme built on those three signals has no purchase on this design, which is exactly why it needs a hunt keyed on host role instead.
- **Choosing a legitimate signed driver is a deliberate trade.** The operator gives up stealth-by-rarity — a driver load is loggable — in exchange for passing every integrity and signature control. That trade only pays off if nobody asks whether the driver makes sense on that machine, so asking is cheap and high-yield.
- **The single-source-address filter is what makes it survive.** A port that answers to anyone gets found by the first internet-wide scan. A port that answers to one address and silently proxies everyone else to the real service will not appear in any external scan, any vulnerability report, or any uptime check.
- **The inconsistency between the socket table and the wire is structural.** The rewrite happens before the TCP stack sees the packet, so the host believes it is serving a high port while the network believes it is talking to 443. Two inventories that should agree and do not is a durable artefact of the technique, independent of which port numbers were configured.
- **A shared toolkit means the design will show up under other names.** CPR assesses CopperDragon as a quartermaster supplying several China-nexus actors, and tracks the same Sparrow lineage into Melofee and the Linux SparrowShell. A hunt written against the mechanism rather than against SparrowDoor keeps working when the implant is renamed, which — given the number of actors reported using this toolset — it will be.
