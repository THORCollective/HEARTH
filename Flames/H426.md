hypothesis: >-
  Applications that fetch user-supplied URLs are normally protected by validating the destination before the request is made. That check runs once, against the URL the user supplied, and an HTTP redirect happens after it. An attacker who controls a host that passes validation can therefore answer the application's request with a 302 whose `Location` points at `169.254.169.254`, `127.0.0.1` or an internal RFC 1918 address, and a fetcher that follows redirects without re-validating will make that second request itself, from inside the perimeter, with whatever credentials the workload carries. The signature is a pair of events in the right order: an outbound fetch from an application process to an external host that returns a 3xx with a private-address `Location`, followed closely by a request from the same process to that private address. Neither event is remarkable alone, and the sequence has no legitimate reason to occur.

false_positive_notes: |
  Redirects to private addresses occur legitimately in split-horizon and hybrid estates. An internal service published under an external name may redirect clients to its internal address, and some load balancers and SSO flows do the same. Build the allowlist from the destination pairs, external host to internal target, rather than from either side alone.
  Link-preview, webhook, feed-reader and document-import features fetch arbitrary URLs by design and will dominate the volume. These are exactly the components the hunt is about, so do not exclude them; exclude instead the specific redirect destinations they legitimately reach.
  Content delivery and URL-shortening chains produce long redirect sequences with no malice. The term that matters is not the presence of a redirect but the address family of the target: only a `Location` resolving to link-local, loopback or RFC 1918 space is interesting.
  A 3xx into private space that the application did not follow is a blocked attempt, not a false positive. The second half of the sequence is the compromise; the first half alone is attempt evidence worth recording and aggregating by source, since it indicates someone is probing the endpoint.
  Without egress inspection or a proxy the Location header is invisible. For HTTPS egress with no inspection, the hunt degrades to the second half only: an application process connecting to the metadata address or to an internal address it has never contacted before. That is weaker but still worth running, and it is where existing metadata coverage picks up.
  DNS rebinding produces the same outcome with no redirect at all. A hostname that passes validation and then resolves to a private address on the second lookup defeats the same check without any 3xx, so a clean result here does not mean the endpoint is safe. Pair this hunt with short-TTL resolution monitoring for names resolving into private space.

  Platform - Linux application servers and the API tier, detected from egress and application telemetry. Equally applicable to Windows-hosted application servers; the queries are written against the network and application layers rather than against host-specific sensors.
  What JPCERT/CC observed - The October 2026 report investigates attack servers behind a series of unauthorized-access incidents involving personal-information leakage at multiple organizations in Japan. On one server the team found evidence of API vulnerability testing, and the tool itself is the detail this hunt is built on: "The script functions as an HTTPS server and returns an HTTP 302 redirect response to specific requests." That is a purpose-built SSRF bypass harness. It answers the target application's fetch with a redirect, which is how a destination check that ran before the request is evaded.
  The report's own mitigation makes the mechanism explicit, and it is the sentence that defines the detection: "Prevent SSRF: For APIs that retrieve content from external URLs, restrict the destinations they can access and validate redirect destinations as well." The second clause is the one most implementations miss.
  How the attackers found the endpoints - The same campaign reached these APIs by reverse-engineering mobile applications: "One notable characteristic of these attacks was that the attackers analyzed Android application packages (APK files) to identify APIs and exploit them". So the vulnerable URL-fetching endpoints were not necessarily documented or linked from a web front end, which matters for scoping: an inventory built from the public site will miss them, and an inventory built from the mobile app's API surface will not. That enumeration path is modelled in [[M063]].
  Primary query, the sequence - Find an external fetch that returned a private-address redirect, then a request from the same source to that address. Both bindings are used and the join is windowed, because a redirect and an unrelated internal connection hours apart are not the same event:
  ```kql
  let redirects = CommonSecurityLog
      | where TimeGenerated > ago(30d)
      | where toint(EventOutcome) between (300 .. 399)
      | where AdditionalExtensions has_any ("169.254.169.254", "metadata.google.internal",
                                            "127.0.0.1", "localhost")
             or AdditionalExtensions matches regex @"//(10|127|192\.168|172\.(1[6-9]|2[0-9]|3[01]))\."
      | project redirectTime = TimeGenerated, SourceIP, externalHost = DestinationHostName,
                locationHint = AdditionalExtensions;
  let followed = CommonSecurityLog
      | where TimeGenerated > ago(30d)
      | where ipv4_is_private(DestinationIP)
             or ipv4_is_in_range(DestinationIP, "169.254.0.0/16")
             or ipv4_is_in_range(DestinationIP, "127.0.0.0/8")
      | project followTime = TimeGenerated, SourceIP, internalTarget = DestinationIP,
                internalPath = RequestURL;
  redirects
  | join kind=inner (followed) on SourceIP
  | where followTime between (redirectTime .. redirectTime + 2m)
  | project redirectTime, followTime, SourceIP, externalHost, internalTarget,
            internalPath, locationHint
  | order by redirectTime desc
  ```
  The two-minute window is deliberate and tight: a fetcher following a redirect does so immediately, within the same request handler. Widening it past a few minutes reintroduces unrelated internal traffic and destroys the fidelity of the join.
  Zeek query, where the Location header is directly available - Zeek records both the response status and the redirect target, which makes the first half of the sequence a single-pass filter rather than a join:
  ```bash
  cat http.log \
    | zeek-cut ts id.orig_h id.resp_h host uri status_code \
    | awk -F'\t' '$6 ~ /^3/'
  ```
  Then pull the full records for the matching connections to read the `Location` response header, which the projection above omits, and keep only those whose target is link-local, loopback or RFC 1918. Zeek's `http.log` carries response headers only when configured to do so, so confirm the local policy before relying on a negative result.
  Attempt-evidence query, cheaper and longer-reaching - The first half alone is probing evidence and it survives in proxy logs well past most SIEM windows. Aggregate by the external host that issued the redirect rather than by the application, since one attacker host will target many endpoints:
  ```spl
  index=proxy sourcetype=proxy
    (status>=300 AND status<400)
    (location="*169.254.169.254*" OR location="*metadata.google.internal*"
     OR location="*127.0.0.1*" OR location="*://10." OR location="*://192.168.")
  | stats count AS redirects, dc(src_ip) AS targets_probed, values(location) AS locations
          BY dest
  | sort - redirects
  ```
  The status range and the `location` group are parenthesised separately on purpose. Splunk binds `OR` more tightly than the implicit `AND`, so an unparenthesised mixture of the two groups would not mean what it reads as.
  Which private targets matter most - A redirect into loopback reaches anything bound to localhost on the application server, which on a typical deployment includes admin interfaces, debug endpoints and unauthenticated service ports that were never meant to be reachable. A redirect to `169.254.169.254` or `metadata.google.internal` reaches the cloud instance metadata service and, on an unprotected configuration, the workload's credentials. A redirect into RFC 1918 space reaches whatever the application server can route to, which is usually a great deal more than the application needs.
  Hardening that follows - The fix is in the report's own wording: validate redirect destinations, not just supplied URLs. Practically that means disabling redirect-following in the fetcher where the feature allows it, or re-running the destination check on every hop and on the resolved address rather than the hostname. Requiring the metadata service's session-token flow removes the credential outcome specifically, and egressing all server-initiated fetches through a proxy that enforces the allowlist independently removes the entire class regardless of application-level checks.
  Cross-technique note - Where the redirect target is a cloud instance metadata service, the credential outcome is T1552.005 (Cloud Instance Metadata API), which is the technique [[H137]] is filed under. This hunt is filed under T1046 instead because the redirect reaches whatever internal service the application server can route to, and the metadata service is only the most valuable case rather than the defining one.
  Adjacent coverage - [[H137]] covers the outcome rather than the bypass: an SSRF chained to the GCP instance metadata service, keyed on an IMDS token request originating from a workload process rather than from the metadata SDK. It fires when the target is IMDS and the credential is reached. This hunt fires on the redirect pivot itself, so it also catches redirects into loopback and RFC 1918 space where no metadata service is involved and no credential is taken, and it catches attempts the application refused to follow. Run both; they cover different halves of the same chain. [[H190]] covers an SSRF reached through a specific product vulnerability. [[M063]] models the mobile-app API enumeration that located these endpoints in the first place.

# H426

JPCERT/CC published an investigation in October 2026 into the attack infrastructure behind a series of unauthorized-access incidents in Japan involving leakage of personal information. The team examined several attacker-controlled servers, and on one of them found API vulnerability testing tooling. The description of one script is the whole reason this hunt exists: "The script functions as an HTTPS server and returns an HTTP 302 redirect response to specific requests."

That is not a web server. It is a purpose-built server-side request forgery harness. Applications that fetch user-supplied URLs usually defend themselves by validating the destination before making the request, and that validation runs exactly once, against the string the user supplied. A redirect happens afterwards. An attacker whose host passes the check can answer the application's fetch with a 302 pointing wherever they like, and a fetcher that follows redirects without re-validating will make that second request itself — from inside the network, as the workload, with the workload's credentials.

JPCERT/CC's own mitigation names the gap precisely: "Prevent SSRF: For APIs that retrieve content from external URLs, restrict the destinations they can access and validate redirect destinations as well." The second half of that sentence is the half most implementations skip, because the first half feels like it covers the problem.

The detectable shape is a sequence rather than an event. An application process fetches an external host; the response is a 3xx whose `Location` resolves into link-local, loopback or RFC 1918 space; and within seconds the same process requests that address. Each half is unremarkable on its own — servers fetch external URLs constantly, and application servers talk to internal addresses constantly — and the ordered pair has no legitimate cause.

The campaign context explains why the vulnerable endpoints were obscure ones. The same report notes that "the attackers analyzed Android application packages (APK files) to identify APIs and exploit them", so the URL-fetching endpoints under test were reached through a mobile application's API surface rather than through a public web front end. An endpoint inventory built from the website will not contain them.

## Why

- The bypass defeats the control most teams believe closes SSRF. Destination allowlisting is the standard remediation, and it is evaluated before the redirect exists, so an estate can be fully remediated on paper and fully exploitable in practice.
- The ordered pair is specific in a way neither half is. This is what makes the hunt worth running against components whose entire purpose is fetching arbitrary URLs — link previews, webhooks, feed readers, document importers — where no filter on the fetch itself could ever be selective.
- The reachable targets are the worst ones available. Loopback exposes admin and debug interfaces that were never meant to be routable, the link-local metadata address exposes workload credentials, and RFC 1918 space exposes whatever the application server can route to, which is almost always more than it needs.
- The first half alone is useful intelligence. A proxy log full of 3xx responses redirecting into private space tells you someone is probing the endpoint, aggregates neatly by attacker host, and survives in proxy retention long after endpoint telemetry has rolled over.
- The endpoints at risk may not be in any inventory the defender holds. Attackers located them by decompiling mobile applications, which means the authoritative list of URL-fetching endpoints is the mobile API surface, not the documented web one.
