# H410

IRC. In 2026. On a Magento server.

That is the whole detection, really — and it is a good one, because almost nothing legitimate on a commerce server has any reason to speak a protocol from 1988.

AhnLab found the artefacts while examining an exposed environment belonging to an operator running a rebranded ARTEX build. Among them: a working copy of the public proof of concept for CVE-2026-75650, which AhnLab describes as "a Magento/Adobe Commerce remote code execution vulnerability exploitable without authentication", a deployment message announcing an IRC bot, a generated PHP payload, and a PHP implant that "operates as a persistence-based IRC C2 (remote control channel) implant that connects to the password-protected #mg_master".

Worth being clear about what that is. These are the *operator's* files, recovered from their own exposed infrastructure — AhnLab's assessment is that "source code, credentials, development artifacts, runtime logs, and attack tools are widely exposed on the internet, indicating poor OPSEC practices." They report "signs that the same steps as in the public PoC had been performed," not a confirmed merchant compromise. No victim is described. The tradecraft is what we are hunting, not an incident.

So why would anyone choose IRC?

Because for a botnet operator it is still remarkably well suited. One channel gives you a live roster of every implant that has joined. Nickname addressing lets you talk to one host; the channel lets you broadcast to all of them — AhnLab notes the implant accepted both a targeted and an all-hosts command form. Server-side relay means you never connect to the victims; they connect to you. There is a channel password for access control. And all of it fits in a few dozen lines of PHP with no libraries.

Against content inspection it is also, ironically, quite good — very few security stacks still parse IRC.

Against egress monitoring it is terrible. Which is our opening.

The persistence is the other half, and it is chosen for a specific reason. The implant installs an `@reboot` cron entry, which runs at boot. Think about what that defeats: rebooting the server is the single most likely thing an administrator does to a machine behaving strangely. Combined with copying itself into hidden paths outside the application tree, redeploying Magento does not remove it either.

Two collection details decide whether this hunt actually works.

**Crontabs are per-user.** A check that reads root's crontab finds nothing, because this entry would live under the web service account. Enumerate every account.

**`@reboot` is legitimate** and Magento deployments lean on cron heavily. The directive is not the finding. The *pairing* is: an `@reboot` entry owned by the web service account invoking a PHP file that is not in the application's deployed tree. Magento's own entries call its documented scripts from the application root and are stable across deploys, so a diff against the deployment manifest resolves nearly everything.

On the exploitation side, be realistic about the web logs. AhnLab lists the sequence as "creating a Guest Cart, manipulating billing information, triggering the vulnerable checkout flow, and extracting the Magento Report Identifier." The first three are also a description of someone buying shoes. The report identifier extraction is the step with no shopping equivalent — that is where to look.

## Why

- **IRC from a commerce server has no benign explanation.** Scoped to server roles, the egress query is close to signature-grade, which is rare for a C2 hunt.
- **The protocol gives the operator fleet management for free.** Channel membership is an implant roster, and nickname plus channel addressing provides both targeted and broadcast tasking with no custom infrastructure.
- **Victims connect outward, so there is nothing to scan for.** No listening port and no inbound session means external discovery finds nothing and egress telemetry is the only view.
- **Very little tooling inspects IRC content.** Protocol obscurity buys evasion at the content layer even while it costs the attacker at the connection layer.
- **`@reboot` defeats the administrator's instinctive response.** Restarting a misbehaving server is what re-establishes the implant rather than removing it.
- **Hidden out-of-tree copies survive application redeployment.** Reinstalling or redeploying Magento does not touch a PHP file living in a dotfile directory outside the document root.
- **Per-user crontabs are the collection trap.** The entry belongs to the web service account, so a root-only crontab check returns clean on a compromised host.
- **The directive is common, so the pairing is the discriminator.** `@reboot` plus a PHP file absent from the deployment manifest is the specific shape; either half alone is noise.
- **Exploitation hides in ordinary commerce traffic.** Cart creation, billing changes and checkout calls are normal customer behaviour, which pushes the web-log detection onto the report-identifier step.
- **The source is attacker-side tooling, which the hunt should state.** AhnLab recovered an operator's artefacts rather than documenting a victim, so this justifies the detection without implying a known compromise.
