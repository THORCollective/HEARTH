false_positive_notes: |
  The hard part of this hunt is that in a managed-service environment, an RMM client running scripts IS the business process — that is literally what the product is for, and a help desk pushing a remediation script produces the same lineage as an intruder pushing a loader. Three things separate them, and all three should be applied together rather than individually. First, INSTANCE IDENTITY: legitimate activity comes from the organisation's own ScreenConnect instance with its known relay hostnames and its known instance identifier, and a second instance on the same host is the finding regardless of what it runs. Second, INTERPRETER CHOICE: most modern help desks push PowerShell or MSI packages; a chain of numbered `.vbs` files executed by `wscript.exe` is old tradecraft and is now much more common in intrusions than in legitimate IT operations, though it does still appear in long-lived legacy automation. Third, SCRIPT PROVENANCE: legitimate scripts come from the vendor or from an internal repository, not from `raw.githubusercontent.com` or a paste site. Expect genuine false positives from: MSP onboarding and remediation workflows; legacy VBScript automation in older environments, particularly around printer, drive-mapping and Office configuration; software deployment performed deliberately through the RMM; and security vendors whose own agents are installed via RMM push. Environments that legitimately run several RMM products (an MSP plus an internal IT team plus a vendor support tool) need the authorised-instance inventory built first — without it, this hunt produces noise proportional to how well-managed the estate is, which is the wrong incentive. Note also that ScreenConnect binaries are frequently renamed by the operator at build time, so name-based filtering alone will miss instances; pivot on the service description, the installation path and the code-signature subject as well.
notes: |
  The core lineage detection - Core filter: a script interpreter whose parent is a ScreenConnect client process. Defender XDR KQL - `DeviceProcessEvents | where InitiatingProcessFileName has "ScreenConnect" | where FileName in~ ("wscript.exe","cscript.exe","powershell.exe","pwsh.exe","cmd.exe","mshta.exe","rundll32.exe","regsvr32.exe","curl.exe","bitsadmin.exe") | project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessCommandLine, FolderPath`. Because operators rename the binaries, widen the parent condition to match on code-signature subject and on the installation path as well as on the filename. Triage values - `ProcessCommandLine`, `AccountName` (the client service runs as SYSTEM, so a SYSTEM-context script is higher impact), `FolderPath` of the script. Strong red flags - sequentially numbered scripts (`1.vbs` through `4.vbs` in the Huntress-documented campaign), execution from `%TEMP%` or the public profile, and `powershell.exe` with `-ExecutionPolicy Bypass`, `-EncodedCommand`, `-w hidden` or `-nop` in the same chain.
  Unauthorised instance identification, the highest-value single check - Core filter: enumerate every ScreenConnect installation across the estate and group by instance identifier and relay hostname. The identifier appears in the service name, in the installation directory name, and in the client configuration; the campaign's malicious instance was `7a4d7d66502d4260`. Any instance whose identifier or relay is not on the organisation's authorised list is a finding on its own, with no behavioural condition required. This is an inventory query rather than a detection, it can be answered in minutes, and it is the check most likely to produce a true positive in an environment that has not looked before. Relay endpoints observed in the campaign, useful as seeds rather than as the detection - `tele-sync.opik[.]net`, `homehub.opik[.]net:443`, `borertors92.anondns[.]net`, `45.13.237[.]190`, `131.123.40[.]98:8041`, `15.204.185[.]204`.
  Staging artefacts of the script chain - Core filter: file creation in `%TEMP%` of the working files the loader used — `value.txt` (state), `map.txt` (payload catalogue), `out.enc` (encrypted payload) and `runner.ps1` (decryptor). The generalisable pattern is an encrypted blob plus a small PowerShell decryptor written to the same directory within seconds of each other, then the decryptor executing and the blob being deleted. Hunt the CO-OCCURRENCE and the short lifetime rather than the filenames.
  Persistence - Core filter: creation of a value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` pointing at a `.vbs` in an AppData path. The campaign used the value name `WindowsServiceHost` referencing `WindowsServiceHost.vbs`. Detection guidance - a Run key entry whose data ends in `.vbs`, `.js`, `.hta` or `.bat` rather than `.exe` is a narrow and durable query with a small legitimate population; do not chase the specific value name.
  Masqueraded follow-on payloads - Core filter: executables with Windows-component names running from non-system paths. Observed - `Themes.exe` (a wstunnel tunnelling client), `SearchIndex.exe` (XMRig miner), `svcdrv64.sys` (the WinRing0 driver, a well-known bring-your-own-vulnerable-driver component) and `PyTorchFix.ps1`. Highest-value of these is the driver: hunt Sysmon event 6 (driver load) for WinRing0 by hash and signature, since it appears in cryptomining and privilege-escalation chains far beyond this campaign. A miner is also a useful triage accelerator — sustained full CPU on a host with an unexplained RMM instance is an easy confirmation.
  RMM-native audit evidence - Core filter: ScreenConnect's own logs record file transfers and command execution. Look for `RunFiles` / `RanFiles` entries naming the script files, and for entries where the executing process context is the guest session. Where the organisation runs its own ScreenConnect server, the server audit log attributes each command to a technician account — which is the fastest way to distinguish "our help desk did this" from "someone else's instance did this", and should be the first pivot after a lineage hit.
  Secondary tooling - Core filter: a second remote-access product installed shortly after the first. The campaign followed ScreenConnect with UltraViewer connecting to `146.59.55[.]107` and `45.32.192[.]150`. Stacking remote-access tools is a deliberate redundancy pattern; finding one should always trigger an inventory sweep for the others rather than a single-host remediation.

# H306

Huntress reported rogue ScreenConnect installations appearing across hosts with no business relationship to one another, behaving in a way that looked worm-like. The execution mechanism is worth stating plainly because it is not an exploit: once an operator controls a ScreenConnect instance, the product's own file-transfer and command features run code on every machine connected to it, with the client service's privileges. There is no vulnerability in the chain. The remote access tool is doing exactly what it was built to do, for someone who should not have it.

That is what makes the lineage the detection. `ScreenConnect.WindowsClient.exe` is a signed binary from a legitimate vendor, installed through a legitimate installer, running as a legitimate service — so application control, publisher reputation and binary allowlisting all pass it through by design. What does not look right is `wscript.exe` as its child, executing `1.vbs`, `2.vbs`, `3.vbs` and `4.vbs` in sequence from a writable directory, followed by PowerShell with an execution-policy bypass. The campaign then wrote a `HKCU` Run key named `WindowsServiceHost` pointing at a `.vbs` in AppData, dropped a wstunnel client disguised as `Themes.exe`, an XMRig miner as `SearchIndex.exe`, and the WinRing0 vulnerable driver as `svcdrv64.sys`.

There is a caveat this hunt has to be honest about: in a managed environment, an RMM client running scripts *is* the business process, and a help desk pushing a remediation script produces a very similar lineage. The separator that carries the most weight is not behavioural at all — it is instance identity. Legitimate activity originates from the organisation's own instance, with its known relay hostnames and its known instance identifier. The campaign's instance was `7a4d7d66502d4260`, and it was not anyone's IT department. Enumerating every ScreenConnect installation across the estate and grouping by instance identifier is an inventory question answerable in minutes, it needs no behavioural condition, and in an environment that has never checked, it is the query most likely to return something real. M043 models the cross-host spread pattern that made this campaign look worm-like, and H307 covers the same trust-abuse pattern in a software deployment platform rather than a remote-support tool.

## Why

- Nothing in the chain is exploited, so vulnerability-centric defences have no purchase. The remote access tool is signed, legitimately installed and doing its documented job, which means publisher reputation and application allowlisting actively help the attacker rather than hindering them.
- The signal is entirely in the parent-child relationship. A signed RMM binary is unremarkable and a script interpreter is unremarkable, but the RMM client as the direct parent of `wscript.exe` running numbered scripts from a temp path is a shape ordinary support work rarely produces — and it is visible in process telemetry every environment already collects.
- The unauthorised-instance check is cheap, needs no behavioural analysis, and has a high base rate of finding something. Grouping installations by instance identifier and relay hostname against an authorised list turns the hunt's hardest judgement call into a lookup, and it catches dormant installations that have not yet run anything.
- The follow-on payloads carry their own durable detections. A Run-key value whose data ends in `.vbs` rather than `.exe`, and a load of the WinRing0 driver, are both narrow queries with small legitimate populations that generalise well past this campaign.
- Stacked remote-access tooling makes single-host remediation unreliable. The operators layered UltraViewer behind ScreenConnect and tunnelled with wstunnel, so a confirmed hit should always escalate to an estate-wide inventory rather than a cleanup of the affected machine.
- The product's own audit trail resolves the ambiguity that the process telemetry cannot. ScreenConnect logs file transfers and command execution, and a self-hosted server attributes each command to a technician account — which converts "is this our help desk?" from a judgement into a record lookup.
