# H299

Elastic Security Labs published a Linux local-privilege-escalation detection framework in September 2026
whose central claim is worth stating on its own, because it changes what a hunt for this should look
like. There are a great many Linux privesc bugs and there will be more next quarter, but they nearly all
converge on one observable: a process with an effective user or group ID of 0 whose real user or group ID
is not 0. That is the moment the boundary was crossed, and it is visible regardless of whether the route
was a sudo misconfiguration, a polkit bug, a kernel page-cache exploit, or a SUID binary that should
never have had the bit set.

The condition on its own is useless as an alert. It fires on every `sudo` an administrator runs. What
Elastic's framework does is layer three independent facts around it — the outcome (root transition), the
precursor (execution from a writable path, or a recently compiled binary), and the relationship
(parent-child lineage) — and treat the conjunction as the signal. That layering is what this hunt
implements.

Three distinct patterns come out of it, and they are genuinely separate queries rather than one query
with options.

The first is the known-helper pattern. `sudo`, `su`, `pkexec`, `passwd` and their relatives are SUID by
design, and an exploit invokes them differently from a human. Elastic's logic pairs the credential
condition with helper names and a low `args_count` — `sudo` with a single argument, `su` with two or
fewer — and with a parent that is an interpreter, a shell running `-c`, or a binary in a writable path.
The reasoning is behavioural: an administrator types a command with a verb and an object, while
programmatic exploitation supplies the minimum the helper will accept.

The second is the uncommon-helper pattern, and it is the most interesting because it explicitly refuses
to use an allowlist. Elastic matches `stringcontains(process.executable, process.command_line)` — the
executable path appearing inside its own command line, which is what a direct invocation by absolute
path with no arguments looks like. That expression catches a SUID binary nobody has ever heard of,
including one an actor just created, without anybody having to enumerate the legitimate set in advance.
The fleet-wide rarity question that sits behind this pattern — which SUID binaries exist across the
estate at all, and which of them are rare enough that a single execution is notable — is a different kind
of problem and is handled separately in [[M041]].

The third is proxy execution, and it exists because the first two are name-aware. Passing `/usr/bin/pkexec`
as an argument to some other binary executes the helper without the helper's name ever appearing in the
`process.name` field. The detection inverts accordingly: look for SUID helper paths inside `process.args`
of an unrelated process with `args_count` of two or fewer.

What makes all three workable in practice is the confirmation step. A SUID helper whose child is an
interactive shell launched with the privilege-preserving flag — `/bin/sh -p`, `bash -p` — is not an
ambiguous result. Elastic's triage guidance for the shipped rule points at the same set of confirmations:
a TTY or SSH session behind the execution, a matching successful authentication in `journald`, the
sudo and polkit policy outcome, and root-owned droppers appearing in `/tmp` or `/usr/local/bin`.

There is a hardening finding that falls out of running this hunt regardless of whether it catches
anything. Collecting mount options for `/tmp`, `/var/tmp`, `/dev/shm` and home directories tells you
which hosts permit SUID execution from writable storage at all. Mounting those `nosuid,nodev,noexec`
removes a whole branch of this technique, as does stripping the setuid bit from rarely used binaries
such as `chfn`, `chsh`, `newgrp` and `ssh-keysign`, and constraining `pkexec` through polkit rules to
specific callers.

## Why

- The detection target is the destination rather than the route. Elastic's framework is built on the
  observation that privilege escalation methods proliferate but the privilege transition does not
  change, so a hunt anchored to effective-versus-real credential divergence keeps working against
  exploits that did not exist when it was written.
- The distinguishing context is cheap and already collected. Argument count, parent executable path and
  writable-directory membership are fields any competent Linux process sensor already emits — Elastic
  Defend, auditd `execve` records, or eBPF — so this requires interpretation of existing telemetry
  rather than new instrumentation.
- The three query shapes close each other's gaps deliberately. Name-based helper matching misses unknown
  SUID binaries, self-referential matching misses helpers passed as arguments, and proxy-execution
  matching misses the ordinary case; running all three is what makes the coverage hold against an actor
  who knows the first one exists.
- It produces hardening output even on a clean estate. The inventory of `nosuid` mount coverage,
  unnecessary setuid bits, and unconstrained `pkexec` callers is a durable reduction in attack surface,
  which is a better outcome than a hunt that returns nothing and leaves nothing behind.
