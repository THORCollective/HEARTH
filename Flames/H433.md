title: "An SSL_read hook inside an SD-WAN controller daemon harvesting data-plane key material, staged RSA-encrypted in /var/tmp with its own config deleted after it is read"
hypothesis: >-
  The collection half of KeyDrift never reads a packet off the wire. It hooks `SSL_read` inside the controller daemon so that control messages are inspected *after* TLS has already decrypted them, filters for a specific buffer length and leading byte, parses three marker patterns to locate vEdge transport IPs, OMP system-IPs and 32-byte data-plane keys, then RSA-encrypts the extracted records and writes them to a fixed path under `/var/tmp`. Its endpoint configuration is read once and deleted. So a controller that has been collected from shows a staging file with high-entropy contents, a UDP flow that looks like DTLS application data to an address no controller should be talking to, and a configuration file that existed for only moments. The staging file is the durable observable, because exfiltration is a separate step from collection and the two may be days apart.

false_positive_notes: |
  `/var/tmp` is a legitimate scratch directory on these appliances and vendor tooling writes there. Support-bundle generation, upgrade staging and crash handling all produce files. The discriminating properties are the specific name, the absence of a vendor process holding the descriptor, and content that is high-entropy without being a recognised archive or image format.
  High entropy alone is not the finding. Compressed support bundles, encrypted backups and signed upgrade images are all high-entropy and all legitimate. Check whether a vendor process created the file and whether the format is identifiable before treating entropy as evidence.
  UDP flows that resemble DTLS application data are the normal control-plane traffic on an SD-WAN fabric, which is exactly the cover this uses. The anomaly is the *destination*, not the protocol shape, so this half of the hunt is unusable without the approved peer list and will produce nothing but noise until that exists.
  A missing configuration file is the expected steady state, not a negative result. The module deletes its own endpoint configuration after reading it, and Talos never recovered a copy — so an absent file is consistent with both a clean controller and a collected one.
  Mapped-object comparison needs the same role and the same software version on both sides. vSmart, vBond and vManage load different library sets, and a cross-role comparison will report dozens of differences that are all legitimate.
notes: |
  Platform - Linux-based Cisco SD-WAN controller appliances; the report attributes this component to evidence from a vSmart process. As with [[H432]], there is no endpoint agent here, so the hunt is on-box inventory plus off-box flow records.
  What the report states - Talos describes the module as "a control-session interception module positioned to collect data-plane keying material from control sessions visible to the injected vSmart process." The mechanism: "LittleFilch installs an SSL_read hook inside vdaemon. The hook calls the original SSL_read, then processes returned buffers only when the returned size is greater than 0x18F, the first decrypted byte is 0x07, and three marker patterns are checked for presence."
  0x18F is 399 bytes. That threshold and the leading byte value are filters the module applies to decrypted control messages, which is a useful detail for a reverse engineer and a dead end for a network sensor — by the time the hook sees the buffer, decryption has already happened inside the process.
  What it extracts - the report gives a marker table: `40 03 06` precedes a 4-byte vEdge public or transport IP, `40 0C 04` precedes a 4-byte vEdge OMP system-IP, and `05 01 0C 06 40` precedes a 32-byte binary key field that Talos assesses to be OMP-distributed AES-256 IPsec data-plane key material. The qualifier matters: Talos labels this field as assessed rather than confirmed, so a hunt note should not assert that the operator holds working data-plane keys, only that the fields carrying them were targeted.
  Staging and configuration - the extracted records are RSA-encrypted before being written to a fixed staging path under `/var/tmp`, and the module can then "send the encrypted content over UDP in a DTLS 1.2 application-data style record." Its runtime configuration is expected to carry "two host port lines: one local bind IP/port and one remote destination IP/port", and it deletes that configuration after reading it. Talos records that it was never able to recover the configuration file.
  Why the staging file is the anchor - collection and exfiltration are separate operations in this design. The module writes locally first and transmits on configuration, which means a controller can hold a staging file with no corresponding egress flow, and an egress flow can occur long after the writes that filled the file. Hunting the file catches the window that hunting the flow misses.
  Check 1 - the staging path and the entropy of what is in it:
  ```shell
  ls -la --time-style=full-iso /var/tmp/
  for f in /var/tmp/*; do
    [ -f "$f" ] || continue
    printf '=== %s  %s bytes\n' "$f" "$(stat -c %s "$f")"
    file "$f"
    head -c 32 "$f" | od -An -tx1
  done
  ```
  `file` reporting `data` on a file that is neither an archive nor an image, with no recognisable header, is the shape to pull out. Record sizes: a staging file that grows between two collections is accumulating records.
  Check 2 - who holds the descriptor. A staging file written by an injected module is held open by the daemon, not by a vendor utility, and that attribution is the difference between a support artefact and a finding:
  ```shell
  for pid in $(pgrep -x vdaemon); do
    printf '=== pid %s\n' "$pid"
    ls -l /proc/$pid/fd 2>/dev/null | grep -E '/var/tmp|/tmp'
    awk '$6 ~ /\.so/ {print $6}' /proc/$pid/maps | sort -u
  done
  ```
  The mapped-object list is the same check as in [[H432]] and is included here deliberately: the collection module and the residence module were deployed together, so a controller that shows one should be examined for the other. The name Talos recovered for this component is `libcommon.so`, but compare the whole set against a known-good controller rather than matching the name.
  Check 3 - the hooked symbol. The interposition is what makes the decrypted buffers reachable, so the symbol binding is worth resolving directly where the platform has the tooling:
  ```shell
  for pid in $(pgrep -x vdaemon); do
    cat /proc/$pid/maps | awk '$2 ~ /rwx/ {print "RWX: " $0}'
    grep -l 'SSL_read' /proc/$pid/maps 2>/dev/null
  done
  ```
  An anonymous read-write-execute mapping in a daemon that should have none is the generic form of this finding and does not depend on the module keeping its name. Resolving which object currently provides `SSL_read` is the specific form, and is the stronger evidence when it can be obtained.
  Check 4 - the egress, from flow records rather than from the box. The report describes a DTLS 1.2 application-data style record over UDP, which on an SD-WAN fabric is indistinguishable in shape from legitimate control traffic. The destination is the only usable discriminator:
  ```
  # Pseudo-query against the flow collector, not a device CLI command.
  # src_ip IN (controller addresses)
  #   AND protocol = UDP
  #   AND dst_ip NOT IN (approved control-plane peers, management, NTP, DNS, syslog)
  # GROUP BY src_ip, dst_ip, dst_port
  # ORDER BY bytes DESC
  ```
  This is where the approved peer list from an appliance baseline earns its keep. Without it, every controller flow looks like every other controller flow.
  Check 5 - the deletion, where auditd is available on the platform. The configuration file is read once and removed, so the deletion is the event:
  ```shell
  auditctl -w /var/tmp -p wa -k keydrift_stage
  ausearch -k keydrift_stage -i 2>/dev/null | tail -50
  ```
  As with the ptrace rule in [[H432]], this is forward-looking: if the watch was not in place before the intrusion, an empty result carries no information and should be reported as "not instrumented" rather than as "not found."
  Expected, not observed by Talos - the report does not state the RSA key size or padding used for the staging records, does not resolve the transmission cadence (there is no polling interval in the recovered samples), and never recovered the configuration file, so neither the bind address nor the destination is known. The entropy test, the descriptor attribution and the auditd watch above are my additions rather than vendor-published detections. Talos also does not say whether the staging file is truncated or removed after a successful send, which is why the hunt treats both a present file and an absent one as inconclusive on their own and relies on comparison across collections.
  Scope note - the report names a predefined target list: the module "extracts keying material for a list of predefined edge nodes." That is a collection-targeting detail rather than a hunt input, but it is worth recording in an incident note, because it implies the operator had prior knowledge of the fabric topology and the exposure may be narrower than the full edge inventory.
  Coverage already published by the vendor - Snort SIDs for the artefacts in the blog are given as "Snort v2: 67387 through 67416" and "Snort v3: 7:44 through 7:73", with 65938 and 65958 for CVE-2026-20127 itself. Those address the exploitation and known artefacts; they do not address in-process collection on an already-compromised controller.
  Pairing - [[H432]] covers the residence half: the trojanized runit launcher and the ptrace injection that put the module inside `vdaemon` in the first place. Run both against any controller that produces a hit on either.
  Closest existing coverage - [[B057]] is the prerequisite baseline for this entire class of hunt and inventories edge appliances that have no agent, no inventory and no file integrity monitoring; it is what supplies the approved-peer and known-good-file lists this hunt needs. [[H360]] is the nearest hunt by behaviour — a compromised Citrix NetScaler used as a pivot by a two-part tunneler — but it covers traffic *forwarding* through an appliance rather than in-process harvesting of key material from decrypted control messages, and its telemetry is HTTP header inspection rather than process memory mapping. [[H389]] covers a loopback-bound listener on a compromised BeyondTrust appliance, again a tunnelling rather than a collection behaviour.

# H433

The collection component of KeyDrift is a good argument for why "we decrypt and inspect at the perimeter" is not a detection strategy against something living inside the process. Talos describes it as "a control-session interception module positioned to collect data-plane keying material from control sessions visible to the injected vSmart process", and the mechanism is a hook on `SSL_read`: the module calls the real function, then examines the buffer that TLS has already decrypted on its way back to the application.

The filter is narrow and specific. The report records that the hook "processes returned buffers only when the returned size is greater than 0x18F, the first decrypted byte is 0x07, and three marker patterns are checked for presence." 0x18F is 399 bytes. Those three markers locate a vEdge transport IP, an OMP system-IP, and a 32-byte key field that Talos assesses to be OMP-distributed AES-256 IPsec data-plane key material — assessed, not confirmed, which is a distinction worth preserving in any incident note.

What makes this hunt different from the residence hunt is the time dimension. Collection and exfiltration are separate steps: the extracted records are RSA-encrypted and written to a fixed staging path under `/var/tmp`, and transmission happens on configuration, over UDP, shaped like a DTLS 1.2 application-data record. So the staging file can sit on a controller with no matching egress flow, and the flow can happen long after the writes that filled it. A hunt that watches only the network catches one phase of a two-phase operation.

The configuration is the part that is designed to be unrecoverable. It is expected to hold "two host port lines: one local bind IP/port and one remote destination IP/port", and it is deleted after being read — Talos never recovered a copy. That means the destination is unknown, the bind address is unknown, and an absent configuration file is consistent with a clean controller *and* with a collected one. Do not read its absence as a clear.

Which leaves three things that are actually checkable on the box: a file in `/var/tmp` whose contents are high-entropy and whose format `file` cannot name, held open by the daemon rather than by a vendor utility; a mapped-object set in `vdaemon` that differs from a known-good controller of the same role and version; and, from flow records rather than from the appliance, UDP to a destination that is not on the approved peer list.

## Why

- The interception happens after decryption, inside the process, so TLS inspection, packet capture and IPS all see ciphertext and nothing else no matter where they sit on the path.
- Local staging decouples collection from exfiltration, which means the file on disk is the only observable that covers the period between the two — and that period may be the whole investigation window.
- The targeted fields are data-plane key material and fabric identity, so the consequence of a hit is not just controller compromise: it is potential exposure of the keys protecting edge-to-edge traffic across the fabric.
- The configuration is self-deleting and was never recovered by the vendor, so the destination cannot be blocklisted and the hunt has to rest on the staging artefact and on a peer allowlist rather than on indicators.
- The egress deliberately imitates the fabric's own control traffic, which makes protocol-shape detection useless and makes the approved-destination list the only part of the network half that can work.
- Collection and residence shipped together, so the mapped-object check appears in both this hunt and its pair — a controller that fails one is very likely failing the other, and the two halves have different remediation.
