# H406

The most durable thing you can be inside a tenant is not an administrator. It is an application.

Microsoft's write-up of the Storm-3119 pipeline captures the moment precisely. With a compromised Global Administrator account in hand, the actor "self-provisions the PnP Management Shell service principal, which represents the actor's application inside the compromised tenant", and then "grants themselves broad Microsoft Graph permissions, including read and write access to directory data and AppCatalog.ReadWrite.All, along with full control over the SharePoint API".

Two moves, a minute apart. After that, the stolen administrator password is optional.

Microsoft spells out why, in the context of the admin panels built on this access: "Leveraging the compromised environment's client secret through an application-only authentication flow, the panel performs full directory control: it resets passwords silently (without forcing a change at next sign-in), assigns education licenses, and grants privileged attributes that the actor can later monetize." And the assessment that follows is the sentence worth pinning above the desk — "Because this access is application-level rather than tied to a single user session, the resulting persistence is more durable, more scalable, and harder to detect."

Work through what that means for the usual response. Reset the compromised admin's password: the app token is unaffected. Require MFA: applications do not prompt. Review interactive sign-ins: the app is not there. Revoke the user's sessions: unrelated.

Then there is the name, which is the part I find genuinely clever. PnP Management Shell is real. It is a widely used, community-maintained administration toolset, and a SharePoint administrator provisioning it is an entirely ordinary Tuesday. An analyst scrolling the enterprise applications list has no reason to stop on it — and arguably should not, because in most tenants it is exactly what it appears to be.

So a name-based query is the wrong instinct twice over: it will flag legitimate installations, and it is trivially evaded, because a service principal's display name is whatever the attacker types.

What is harder to disguise is the shape.

Legitimate provisioning has an owner, a purpose and usually a change record. It is scoped — consent to the one or two permissions a project needs. The pattern here is provisioning *and* a sweeping application-permission grant inside a single session, by an account that does not normally do app administration, with nothing on the change calendar to match.

`AppCatalog.ReadWrite.All` together with full control of the SharePoint API is a particularly loud pairing, and it is loud because of what it is for. Microsoft continues: "The actor then abuses the compromised tenant's SharePoint and OneDrive as bulk hosting and converts the hijacked storage into a sellable product." The grant is the enabling step; the storage abuse is the business. That downstream half is [[M061]], and these two hunts are meant to be run together.

One more framing shift this report earns. Storm-3119 is an access broker — it "hijacks Microsoft 365 and Azure for Education tenants and resells the stolen accounts, licenses, and storage as a service." Your tenant is not the target of a data theft. It is inventory. Which means the post-compromise behaviour to expect is provisioning, licensing and storage activity, not exfiltration — and those are not the queries most teams have written.

## Why

- **An application-only token survives the response that usually works.** Password resets, MFA enforcement and session revocation are all user-scoped, and none of them touches a service principal holding its own credential.
- **It is largely invisible in the logs people watch.** App-only authentication does not appear in interactive sign-in review, so the provisioning event in the audit log is the main chance to see it.
- **The tool it impersonates is genuinely popular.** PnP Management Shell appears legitimately in many tenants, which defeats name-based review and is precisely why the hunt keys on the permission grant.
- **The display name is attacker-controlled, so the permissions are the durable signal.** Any query built on the name alone is evadable by typing a different one.
- **The permission pair explains the intent.** App catalog write plus SharePoint full control is the combination needed to turn tenant storage into hosting, which is what Microsoft reports happening next.
- **The motive is resale, not theft, which changes what to look for.** An access broker provisions, licenses and hosts rather than exfiltrating, so detections tuned for data loss will not fire.
- **Sequence is what separates attack from administration.** Creation followed by a broad grant in one session, by an account with no app-administration history and no change record, is the discriminator that survives contact with a real tenant.
- **Silent password resets leave an application in the actor field.** An app rather than a person resetting user passwords is a shape with no benign explanation, and it is queryable directly.
- **Ownership is the triage question, not permission breadth.** Migration and backup vendors request near-identical permissions, so "who asked for this application" resolves candidates that no amount of query narrowing will.
