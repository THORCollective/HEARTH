false_positive_notes: |
  Browsers do DoH by default, so the raw signal of "a process queried a DoH endpoint" is dominated by legitimate traffic. The discriminator is the process, not the destination: scope to processes that are not browsers and not the operating system resolver, and expect to allowlist a security product or two that performs its own resolution deliberately.
  Some enterprise software legitimately performs DNS resolution over HTTPS to bypass local resolver problems, and some installers and updaters embed their own resolver libraries. These are real and they look identical. Build the allowlist from the inventory named in the data sources rather than discovering it from alert volume.
  Dynamic-DNS zones have legitimate users. Home lab access, field devices, small-vendor remote support and some conferencing tools all resolve hostnames under zones of this kind. The four-token hyphenated pattern is what narrows it; the zone alone is far too broad.
  The hyphenated-dictionary-hostname pattern collides with legitimate naming. Container platforms, ephemeral preview environments and some cloud services generate adjective-noun style names deliberately, and release or build hostnames often carry a trailing digit. Confirm the parent zone as well as the pattern before treating a match as a finding.
  Telegram is in legitimate use in many organisations, and fetching a channel avatar is indistinguishable from any other image fetch at the network layer. Telegram contact on its own is not a finding - only its conjunction with a DoH TXT lookup from the same process shortly afterwards is.
  The DNS-less-connection check produces false positives wherever caching, hosts files, long-lived connections or a resolver that is not logged are in play. A host that resolved a name before the log window opened will look like it never resolved it at all. Treat the result as a candidate list requiring the window to be checked, not as evidence.
notes: |
  Platform - Windows. Check Point tracks the campaign as Yoba and describes delivery through fake GitHub projects impersonating AI desktop applications, with the malicious component placed beside legitimate signed executables so it loads indirectly.
  Why there is nothing to blocklist - this is the central point of the hunt. The loader carries no C2 domain. The address is derived at runtime from the bytes of an image hosted on a service the organisation probably permits, and the tasking arrives inside a DNS TXT record fetched through a public resolver's HTTPS API. Check Point states the intent: "By relying on a DoH service and common file-hosting platforms, the actor aims to bypass passive DNS monitoring and some gateway-based security protections, making their command-and-control traffic harder to distinguish from regular user activity." Three standard controls are neutralised at once - domain reputation has no domain, passive DNS sees no query, and the egress destination is a reputable resolver.
  The seed is replaceable, which defeats indicator sharing - "By changing the image of the Telegram channel, a new domain can be generated." Any generated hostname published in a report is therefore valid only until the operator uploads a new avatar. This is why the hunt targets the pattern and the behaviour rather than the names, and why the pattern below is worth more than any list of observed domains.
  Why the loader is worth hunting even though the observed payload was a miner - Check Point is explicit: "Although we observed an XMRig cryptominer as the final payload in this campaign, the YobaLoader is a generic loader. The operator can supply any PE or PowerShell payload via the signed DNS TXT tasking, so future waves may deliver different malware families." A cryptominer finding here should be triaged as an access problem rather than a nuisance, because the same channel delivers anything.
  Check 1 - the primary signal: a non-browser process using DoH. This is the strongest single query in the hunt because it inverts the usual relationship between a suspicious destination and a benign one:
  ```kusto
  let lookback = 30d;
  let browsers = dynamic(["msedge.exe","chrome.exe","firefox.exe","brave.exe","opera.exe","iexplore.exe","msedgewebview2.exe"]);
  let doh_hosts = dynamic(["dns.google","cloudflare-dns.com","one.one.one.one","dns.quad9.net","doh.opendns.com"]);
  DeviceNetworkEvents
  | where Timestamp > ago(lookback)
  | where RemoteUrl has_any (doh_hosts) or RemoteIP in ("8.8.8.8","8.8.4.4","1.1.1.1","1.0.0.1","9.9.9.9")
  | where InitiatingProcessFileName !in~ (browsers)
  | summarize Requests = count(), FirstSeen = min(Timestamp), LastSeen = max(Timestamp),
              Destinations = make_set(RemoteUrl, 8)
            by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath,
               InitiatingProcessCommandLine
  | order by Requests desc
  ```
  Every `let` is used. Review the process list that comes back by hand on first run: in most environments it is short, and the legitimate members of it are stable enough to allowlist permanently.
  Check 2 - the generated-hostname pattern, where DNS data actually lives. Note that resolved DNS queries are a `DeviceEvents` ActionType and not a `DeviceNetworkEvents` one, which is the usual mistake here:
  ```kusto
  DeviceEvents
  | where Timestamp > ago(30d)
  | where ActionType == "DnsQueryResponse"
  | extend Query = tostring(parse_json(AdditionalFields).DnsQueryString)
  | where isnotempty(Query)
  | where Query matches regex @"(?i)^[a-z]+-[a-z]+-[a-z]+-[0-9]+\."
  | project Timestamp, DeviceName, Query, InitiatingProcessFileName, InitiatingProcessCommandLine
  | order by Timestamp desc
  ```
  The regex is anchored on the four-token structure Check Point documented - three dictionary words and a digit group, hyphen-separated, as the leftmost label. It deliberately does not hard-code the parent zone, so a variant that moves to another dynamic-DNS provider still matches; filter to the observed zone only if the result volume demands it. This check will only ever fire if the loader resolves through the local resolver as well, which it is not designed to do - so a negative result is expected and check 3 is the one that covers the designed behaviour.
  Check 3 - connections to addresses the host never resolved. This is the structural consequence of resolving over DoH: the connection exists with no matching query. Take outbound public connections per host over a window, take resolved DNS queries for the same host and window, and list destination addresses that appear in the first set and in no answer in the second. Rank by how rare the destination is across the fleet. The caveats in the false-positive notes apply heavily; this is a candidate generator.
  Check 4 - the delivery and persistence artefacts, which are cheap to add once a host is a candidate. Check Point records that the dropper "maintains persistence by leveraging the legitimate executable, which will sideload the malicious payload" using scheduled tasks, and that "To make the task appear legitimate, it sets the author to" a chosen value - so Security Event ID 4698 task-creation records, triaged on the author field against the binary the task actually runs, are a direct check. The same report notes that before running its payload the downloader "removes the Zone.Identifier alternate data stream, which is hidden metadata used by Windows to track the origin of downloaded files", so an executable in a user temporary directory that has no mark-of-the-web despite having arrived from the internet is a second artifact. Check Point also describes the final payload as running under a copied host binary with "a hidden command line targeting a TLS-enabled onion mining endpoint through a local Tor SOCKS5 proxy", which means a local SOCKS listener and Tor bridge traffic are corroborating host-level evidence.
  Inference, not stated by Check Point - all four checks, the queries, the regular expression, the browser and resolver lists, and the DNS-less-connection method are mine. Check Point published the chain and its design rationale, not detection logic. The DoH endpoint list above is a general one rather than the specific endpoint in the report, because scoping the hunt to a single provider would miss a trivially changed variant. The Tor bridge addresses and file hashes in the report are deliberately not reproduced here as hunting inputs, since the hunt is built not to depend on them.
  Closest existing coverage - [[M006]] is the nearest existing work and is deliberately a different instrument: it applies a trained model to lexical features of deduplicated domain lists to find dictionary-based generated domains in general. This hunt is a specific chain with a known structure, hunted by pattern and by process behaviour, and it would still fire where a model has no useful training data for this family. Run M006 as the broad net and this as the targeted check. [[M002]] covers beaconing inside encrypted DNS traffic by modelling cadence, which is the timing question rather than the resolution question and does not address where the address came from. [[H185]] involves an implant using an encrypted transport on edge appliances, which is a different platform and a different resolution mechanism.

# H440

The useful thing about this loader is what it does not have. There is no command-and-control domain in the binary, because there is no command-and-control infrastructure. Check Point describes the design as showing "strong operational security (OPSEC) by avoiding dedicated command-and-control (C2) infrastructure and instead relying on Telegram, Tor, Catbox, and DNS over HTTPS (DoH)."

The address is assembled at runtime. The loader fetches the profile image of a Telegram channel and "uses the last 50 bytes as a seed to generate a domain based on three lists of dictionary words," yielding a hostname shaped like `$adjective-$noun-$verb-$digit.dedyn[.]io`. Then it does not ask the local resolver about it — it queries a public DNS-over-HTTPS API for a TXT record containing the encrypted command.

Each leg of that removes a control. Domain reputation has nothing to grade, because the domain did not exist until an avatar was uploaded. Passive DNS sees no query, because the resolution happened inside an HTTPS session. Egress filtering sees a connection to a major public resolver, which is the last destination anyone blocks. Check Point names the goal: to "bypass passive DNS monitoring and some gateway-based security protections, making their command-and-control traffic harder to distinguish from regular user activity."

Indicator sharing fails here too, and the report says why in one sentence: "By changing the image of the Telegram channel, a new domain can be generated." Any hostname published from this campaign is valid until the operator changes a picture. So the hunt has to key on shape instead — and there are three usable shapes. A process that is not a browser talking to a DoH endpoint is the strongest, because browsers are the only thing that should be doing that, and the surviving process list in most environments is short enough to read by hand. A four-token hyphenated hostname as the leftmost label is a precise pattern that does not depend on the parent zone. And a connection to an address the host never asked a DNS server about is the structural footprint that resolving over DoH cannot avoid leaving.

One framing note for whoever triages a hit. The payload observed in this campaign was a cryptominer, which is the kind of finding that gets closed as a nuisance. That would be a mistake: "the YobaLoader is a generic loader. The operator can supply any PE or PowerShell payload via the signed DNS TXT tasking, so future waves may deliver different malware families." The miner is what arrived, not what the access is worth.

## Why

- There is no domain, address or hash stable enough to blocklist, because the C2 address is derived at runtime from a file the operator can replace at will.
- Resolution over a public DoH API moves the DNS lookup inside TLS to a reputable destination, which defeats passive DNS collection, DNS sinkholing and resolver-based blocking simultaneously.
- A non-browser process performing its own DoH resolution is a narrow and highly reviewable signal, because the legitimate population is small and stable.
- The DNS-less connection is a structural consequence of the design rather than an implementation slip, so it survives the operator changing infrastructure, seeds and payloads.
- Tasking rides in a DNS TXT record, so there is no HTTP request body, no distinctive URI and nothing for content inspection to match.
- The delivery lure is a fake AI desktop application on real GitHub infrastructure, which places the first artifact on a developer workstation where the onward access is worth more than the observed miner.
