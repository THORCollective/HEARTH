false_positive_notes: |
  Dynamic loading is ordinary and this hunt will drown if it is not scoped by path. Every process on Linux maps shared objects; the question is only ever *which* ones and *from where*. Legitimate `dlopen` from non-standard paths is common for language runtimes loading native extensions - Python `.so` modules under `site-packages`, Node native addons, Java JNI libraries, PHP and Perl extensions - and for application servers, database engines with pluggable storage or authentication modules, PAM and NSS modules, GPU and vendor driver userspace components, and anything shipped as a self-contained bundle with a private `lib/` directory. Browser and media stacks load codecs on demand. On appliances specifically, the vendor's own add-on package mechanism exists precisely to drop code outside the base image, so `/addpkg` and its equivalents are legitimate by design for vendor modules. The discriminators that survive all of this - package ownership, since a `.so` that no package manager claims and that is not part of a known application bundle is the interesting set; the loading process, since a `.so` appearing inside a daemon that has no plugin architecture at all is far more suspicious than one inside a web or database server; write recency, since a library written minutes before it was mapped is not how software ships; and the executable's own state, because a shared object loaded by a process whose `/proc/<pid>/exe` reads `(deleted)` has essentially no benign explanation. # H368

Most backdoor command sets are a fixed menu. AVERAT's is not.

Among the command codes Rapid7 recovered from the implant's dispatcher — a `uint16` space grouped into bands by subsystem — code `1010` loads or unloads a shared-object module. The implant's capabilities are therefore not settled at deployment. An operator who decides they want a new collection routine, a different tunnel, or a credential scraper does not need to re-run the dropper, restage into `/sbin`, or send another magic packet through the BPF filter. They push a `.so` down the channel they already have and load it into the resident process.

That changes what the artefact looks like. There is no new process, no new parent-child relationship, no new binary in a system directory — the things most Linux detection logic is built around. What there *is* is a new entry in `/proc/<pid>/maps`.

And that entry is unusually durable. A mapping survives the file being deleted from disk. On a host where the implant's own executable has already been unlinked — which is precisely the state [[H367]]'s staging chain leaves it in — the mapped library path is sometimes the only remaining record of what was loaded, pointing at a file that no longer exists.

The hunt is therefore a scoping exercise rather than a signature. Every Linux process maps shared objects; the useful question is which long-running daemons on an appliance are mapping executable code from paths no package owns, and whether the daemon doing it has a plugin architecture at all. A mail filter or a DVR recorder has a short, knowable answer. That is what makes this tractable on devices that will never run an EDR agent.

## Why

- **Runtime module loading decouples capability from deployment.** The operator can add functionality without re-touching the staging chain, which means detections aimed at the install sequence see nothing on the second and every subsequent capability change.
- **The mapping outlives the file.** `/proc/<pid>/maps` records the backing path for executable regions, and that record persists after the `.so` is unlinked. On a host where the implant's own image is already `(deleted)`, this is frequently the only artefact left.
- **Package ownership is a cheap, structural filter.** An appliance's library directories are inventoried by its package manager. A shared object mapped into a daemon that no package claims, from a bulk-storage mount or `/tmp`, is a small set and a meaningful one.
- **The loading process narrows it further.** Application servers, language runtimes and database engines load plugins by design. A mail-filtering daemon or a recorder process does not. Asking whether the loader even *has* a plugin mechanism removes most of the remaining noise.
- **A `.so` loaded by a deleted executable has no benign story.** Legitimate `(deleted)` executables happen after package upgrades. A deleted executable that is also pulling in unowned modules from a writable mount is not that.
- **Code `842` makes static config untrustworthy.** The same command set lets the operator overwrite the C2 host and port tables at runtime, so a configuration extracted from a recovered sample may not reflect where the live process is actually connecting. Live socket metadata wins.
- **The dispatcher punishes probing, which argues for passive hunting.** Rapid7 notes the implant terminates on any unrecognised command code. Interactively poking a suspected implant destroys the volatile evidence that matters most here — enumerate `/proc` instead.
