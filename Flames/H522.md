false_positive_notes: |
  OpenGL is loaded by an enormous amount of ordinary software. `opengl32.dll` is pulled in by browsers, media players, office applications, remote-desktop clients, games, CAD and design tools, and plenty of frameworks that render anything at all. On a workstation this load event is close to meaningless on its own, and a rule written against the module name alone will match most of the estate.

  OpenCL and GPU compute are likewise legitimate in many places. Machine learning workloads, video transcoding, scientific computing, cryptocurrency mining that the organisation sanctions, and some database and analytics engines all use GPU compute properly. Host role does the heavy lifting here - the anomaly is GPU compute on a host whose job involves no graphics and no computation, such as a domain controller, a file server or a finance workstation.

  `rundll32.exe` loading a DLL is routine and heavily used by Windows itself and by installers. The discriminator in this hunt is not `rundll32.exe` but the combination of a DLL named after a well-known library sitting outside that product's installation directory, loaded from a temporary or user-writable path.

  7-Zip is extremely widely deployed and ships a genuine `7z.dll`. A legitimate copy lives inside the 7-Zip program directory and is loaded by `7zFM.exe`, `7zG.exe` or software that bundles the library. The finding is a `7z.dll` in `%TEMP%`, `%PROGRAMDATA%` or `%LOCALAPPDATA%`, especially one loaded by `rundll32.exe` with an exported function name on the command line. Several legitimate applications do bundle their own copy of the library, so confirm against the host software inventory before concluding.

  The GLSL shader source and the specific XOR construction are recovered from sample analysis, not from endpoint telemetry. No standard Windows event records shader compilation or shader source, so those details are for malware analysts confirming a sample rather than for hunters querying logs. Treat them as corroboration on a recovered file.

  Kaspersky describes the packer change as OpenCL to OpenGL between variants, which means both runtimes are in scope and neither is a stable indicator. The durable framing is GPU compute in a process that has no graphics or compute purpose, not a specific library name.

  Thirty days is the whole Defender advanced hunting retention. Note that `DeviceImageLoadEvents` carries no signature columns, so if signer state is needed, join `DeviceFileCertificateInfo` on SHA1 rather than expecting it inline; Sysmon Event ID 7 has signature fields present. The process list in the `InitiatingProcessFileName` clause is drawn from the injection targets Kaspersky names for this family - `dllhost.exe`, `WerFault.exe`, `svchost.exe`, `OpenWith.exe` and `AtBroker.exe` - plus the two obvious proxy binaries; `svchost.exe` is deliberately omitted from the filter because its volume would swamp the result, and should be run as a separate narrower query against unusual service hosts. Treat the list as a ranking aid, not a boundary.

  The reasoning behind this leg, which is what makes it worth running despite OpenGL's ubiquity. A graphics library has no business in a process that draws nothing. `rundll32.exe` loading `opengl32.dll` is the cleanest version of that contradiction, and it is cheap to check. On servers the query is tighter still, since a headless host loading a graphics runtime at all deserves a look.

  Leg two, the patched library (Sysmon 7 and 11, plus Sysmon 1). Core filter: a module named `7z.dll` whose path is not inside a 7-Zip installation. Two events matter - the file being written into a temporary directory by an NSIS-style installer, and `rundll32.exe` subsequently loading it. Kaspersky states the installer dropped `7z.dll` into a temporary directory and ran it through `rundll32.exe`, so the command line should carry the DLL path and an export name. Hash any `7z.dll` found outside a 7-Zip directory and compare against the genuine library - this is a patched legitimate file, so it will carry real 7-Zip version metadata while differing in content, which defeats metadata-based triage and rewards hashing.

  Why a patched real library rather than a purpose-built DLL: the file reads as a known-good component by name, publisher string and version, and part of its code has simply been replaced with self-decrypting shellcode. Static triage that stops at file properties will clear it.

  Leg three, the download of the main body (Sysmon 3, DeviceNetworkEvents, proxy logs). Kaspersky publishes the request shape precisely. The downloader fetches the Trojan's main body over HTTPS using the `/payload?md5=` path, with the `md5` parameter set to zeros on the first request and the hash of the previously downloaded payload on subsequent requests - which is an unusual and quite distinctive update-check idiom. The published example request uses the host `api.internet-speed-check.com` and a Firefox 152 user-agent string. The response carries two custom headers, `X-Signature` and `X-Content-MD5`, the first a signature over the downloaded data verified against a public key embedded in the Trojan and the second the MD5 of the decrypted payload. Where response headers are retained, `x-content-md5` alongside `x-signature` on an `application/octet-stream` response is a strong network-side indicator. Where they are not, the `/payload?md5=` URI pattern and the all-zero initial parameter are still queryable.

  Leg four, the protocol constants, for analyst confirmation. Kaspersky records that the new version uses keys `A21251838432306F2CD2540593656B9E` and `2026F751079659CF71C7BA64B345C12A` for C2 request encryption and response decryption, that certificate validation during the connection to the C2 has been replaced with signature verification of C2 responses using an embedded public key, and that the binary protocol magic constant has changed from `0xC0FFEE42` - which gave the malware its name - to the far less telling value `0xD1D57871`. The magic-constant change matters for anyone carrying older network signatures: a rule keyed on `0xC0FFEE42` will no longer fire on this variant.

  Delivery context, which is the unusual part of this report. Kaspersky states these CoffeeLoader infections come from the Retadup worm, first discovered in 2017 and written in AutoIt and AutoHotkey, which copied itself to all connected USB flash drives and external drives as hidden files and shortcuts. French law enforcement took over its C2 servers in July 2019 and instructed checked-in hosts to wipe the worm, disinfecting more than 850,000 machines. Kaspersky then records that someone began re-registering the domain names Retadup had used as C2 servers two years ago and using them to issue commands to download third-party malware - SmokeLoader at first, packed with the 32-bit Armoury variant, then CoffeeLoader from early 2025. The report is explicit that we don't know whether it was the worm's author or someone else that decided to revive the C2 servers. The practical consequence for a hunter is that long-dormant infections are still beaconing: Kaspersky shows traffic from a 2017 Retadup variant still communicating successfully with its C2 in 2026, using a plaintext Base64-then-hex command protocol, to the host `noobminer.newblackage.com`. Any host still reaching a historical Retadup C2 domain is a nine-year-old infection with a new payload, so the USB-propagation leg and the removable-media hunts in the corpus are the right place to look for peers.

  Scope note on existing coverage. A grep of every hunt body for `OpenGL`, `OpenCL`, `compute shader` and `opengl32` returns three files, none of them about GPU-based unpacking - H092 and H094 concern AI agent API and skill-package abuse and matched on unrelated substrings, and H247 concerns a keylogging plugin. `GPU` appears in 13 files, overwhelmingly in the context of GPU compute as a resource being hijacked for mining or inference rather than as an execution surface for decryption. No existing hunt covers a packer that offloads its unpacking loop to the graphics card. H523 covers the persistence and autorun-locking behaviour of the same downloader and is the natural pivot from a hit here.

# H522

Unpacking is the one thing a packed sample cannot avoid doing, and it is where most of them get caught. The decryption loop runs, the plaintext payload appears in memory, and anything watching the CPU has its moment.

The Armoury packer runs that loop on the graphics card instead.

Kaspersky's earlier analysis found it using OpenCL — a reasonable choice, since OpenCL exists precisely for general-purpose computation on a GPU. The August 2026 variant switched to OpenGL, which exists for drawing things. The shader is unremarkable in itself: a local size of 256, three shader storage buffers for data, key and result, and a single XOR per element. A first-year exercise, executed somewhere no endpoint product is looking.

Getting there is equally economical. An NSIS installer drops a file called `7z.dll` into a temporary directory and runs it through `rundll32.exe`. The DLL is genuine 7-Zip — real publisher strings, real version metadata — with part of its code replaced by self-decrypting shellcode. Static triage reads a known-good archiving library.

Which leaves a contradiction worth hunting. `opengl32.dll` is loaded by half the software on a workstation, so the module name proves nothing. But `rundll32.exe` has nothing to render, and a file server has nothing to render, and a process that exists for four seconds has nothing to render. GPU runtimes in processes with no graphics purpose is a small, reviewable set in almost any estate.

## Why

- The decryption happens where no security product watches. EDR instruments CPU execution, API calls and memory writes; shader execution on a discrete GPU is outside that model entirely. Moving the unpacking loop there removes the single most reliable detection opportunity a packer offers.
- The contradiction is cheap to query and genuinely rare. OpenGL is ubiquitous but `rundll32.exe` loading it is not, and on a headless server any graphics runtime load is odd. Filtering a noisy module by an implausible loader turns a useless indicator into a short list.
- A patched legitimate DLL defeats metadata triage, so the hunt has to be path-based. The file carries authentic 7-Zip version information while differing in content, which means file properties clear it and only location, loader and hash do not.
- Both GPU runtimes are in play, which tells you how to frame the rule. The packer moved from OpenCL to OpenGL between variants, so a library-specific signature has already expired once. GPU compute by a process with no compute purpose survives the next switch.
- Old network signatures have quietly stopped working on this family. The protocol magic constant that gave CoffeeLoader its name, `0xC0FFEE42`, is now `0xD1D57871`, and certificate validation has been replaced by response signature verification. Anyone relying on a 2025 rule is getting a clean result for the wrong reason.
- The delivery route means the infected population is much older than the malware. These infections arrive via Retadup, a 2017 USB worm that law enforcement dismantled in 2019 and that someone revived by re-registering its old C2 domains. Kaspersky shows a 2017 variant still reaching its C2 in 2026 — so a host hitting a historical Retadup domain is a nine-year-old foothold with a current payload on it.
