id: H434
category: Flames
title: "A stealer replaying the stolen session from the victim's own machine — searching the mailbox for delivery receipts and calling food-delivery and chat APIs to confirm a home address"
hypothesis: >-
  A stealer that has taken browser cookies and OAuth tokens does not have to wait for an operator to use them. VOLTA uses them on the spot, from the victim host: it searches the mailbox for purchase receipts to corroborate a home address, calls food-delivery services for order history, re-queries the chat platform with the stolen token to enrich the account profile, and looks up a gaming inventory valuation on a public site. Every one of those requests is authenticated, successful, and originates from the legitimate user's own IP — so identity-side anomaly detection sees nothing wrong. What is wrong is the client: a short-lived unsigned process, not a browser, making authenticated API calls to consumer services it has no business talking to, in a burst, minutes after reading the credential stores.

false_positive_notes: |
  Browsers legitimately talk to every destination in this hunt, constantly. The hunt is only meaningful when scoped to a non-browser initiating process, so the browser exclusion is load-bearing rather than cosmetic — without it this query returns the entire fleet.
  Native desktop and packaged apps for chat and delivery services exist and make authenticated calls to the same APIs. Those are signed, installed in `Program Files` or a packaged-app path, long-lived, and present on the host for weeks. An unsigned image in a user-writable path that lives for two minutes is a different population entirely.
  On a corporate fleet, personal consumer services may be blocked or simply unused, in which case this hunt produces almost nothing — and that is the correct outcome rather than a sign the hunt is broken. On a BYOD or contractor fleet, expect legitimate volume and scope by host class.
  Email clients, backup utilities, calendar sync tools and some security products access mailbox APIs programmatically with stored tokens. Allowlist them on the triple of signer, image path and destination, not on the image name, which is the field an operator controls.
  A burst to only one or two of these destinations is weak on its own. The strength of the signal is the *diversity* of consumer services reached by a single non-browser process in one short window, which is what the aggregation below measures.
  Absence of mailbox audit records does not clear a host. The search happens through the stolen session against the provider, so it is the provider's audit log that holds it — if that log is not collected, the endpoint half of this hunt is the only evidence available.
notes: |
  Platform - Windows. The enrichment traffic also reaches cloud services, and the provider-side half of this hunt is noted below, but the hunt is anchored on endpoint telemetry because that is where the client identity is visible.
  What the report states - Cisco Talos describes a stage that sets VOLTA apart from commodity stealers: after collection, "There is a live enrichment pass that leverages stolen sessions to deep dive the victim's data." The specifics, verbatim: the malware "then uses stolen session access to enrich that bundle further: searching the victim's Gmail for purchase receipts to corroborate a home address, pulling UberEats and DoorDash order history, and enriching Discord accounts via the stolen token."
  The report expands on the mailbox step: "using the victim's own authenticated Gmail tokens, it queries their inbox for receipts from Amazon, DoorDash, Uber Eats, Grubhub, Walmart, and PayPal, then review those receipts to establish a confirmed home address." The gaming valuation is a public lookup rather than an authenticated one: "Roblox inventory is valued via a live" lookup against `Rolimons[.]com`.
  Why this is worth its own hunt rather than a line in a stealer write-up - a stolen cookie or token is normally a *future* risk: the operator exfiltrates it and uses it later, from their own infrastructure, which is where impossible-travel and unfamiliar-IP detection gets a chance. Here the session is replayed from the victim host, over the victim network, in the same minute it was stolen. From the provider's side the request is authenticated, from the usual device and the usual IP, and it is a search rather than a destructive action. There is nothing for identity-side anomaly detection to flag.
  Which means the only distinguishing evidence is the client. Browsers talk to these services; a two-minute-old unsigned binary in `%APPDATA%` does not.
  Primary query - a non-browser process reaching consumer identity-bearing APIs. The strength of a result is the number of *distinct* services one process touched:
  ```kql
  let browsers = dynamic(["chrome.exe", "msedge.exe", "firefox.exe", "brave.exe",
                          "opera.exe", "iexplore.exe", "msedgewebview2.exe",
                          "safari.exe", "vivaldi.exe"]);
  let enrichment = dynamic(["gmail.googleapis.com", "www.googleapis.com", "mail.google.com",
                            "discord.com", "discordapp.com",
                            "ubereats.com", "www.ubereats.com",
                            "doordash.com", "www.doordash.com",
                            "grubhub.com", "rolimons.com", "www.rolimons.com"]);
  DeviceNetworkEvents
  | where Timestamp > ago(30d)
  | where isnotempty(RemoteUrl)
  | extend Host = tostring(parse_url(RemoteUrl).Host)
  | where Host in~ (enrichment)
  | where InitiatingProcessFileName !in~ (browsers)
  | summarize services = dcount(Host), serviceSet = make_set(Host, 12),
              calls = count(), firstCall = min(Timestamp), lastCall = max(Timestamp)
          by DeviceId, DeviceName, InitiatingProcessId, InitiatingProcessFileName,
             InitiatingProcessFolderPath, InitiatingProcessAccountName
  | extend burstSeconds = datetime_diff('second', lastCall, firstCall)
  | where services >= 2
  | order by services desc, burstSeconds asc
  ```
  Two services from one non-browser process is the floor; three or more in under a few minutes is the shape the report describes. `DeviceNetworkEvents` carries no User-Agent and no request body, so the HTTP-level evidence has to come from a proxy — which matters here because the report records the request format for the inference call as a hand-assembled request with a browser User-Agent, and the enrichment calls plausibly share that code path.
  Pairing the enrichment with the credential reads that preceded it. `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, so the usable file-side signal is the *copy* a stealer makes of a locked database before decrypting it, not a read of the original:
  ```kql
  let stores = dynamic(["Login Data", "Cookies", "Web Data", "Local State",
                        "key4.db", "logins.json", "leveldb"]);
  let copies = DeviceFileEvents
      | where Timestamp > ago(30d)
      | where ActionType in ("FileCreated", "FileRenamed", "FileModified")
      | where FileName in~ (stores) or FolderPath has "leveldb"
      | where InitiatingProcessFileName !in~ ("chrome.exe", "msedge.exe", "firefox.exe",
                                              "brave.exe", "opera.exe")
      | project CopyTime = Timestamp, DeviceId, DeviceName, FileName, FolderPath,
                InitiatingProcessId, InitiatingProcessFileName;
  let enrich = DeviceNetworkEvents
      | where Timestamp > ago(30d)
      | where isnotempty(RemoteUrl)
      | extend Host = tostring(parse_url(RemoteUrl).Host)
      | where Host has_any ("gmail.googleapis.com", "discord.com", "ubereats.com",
                            "doordash.com", "grubhub.com", "rolimons.com")
      | project CallTime = Timestamp, DeviceId, InitiatingProcessId, Host, RemoteUrl;
  copies
  | join kind=inner (enrich) on DeviceId, InitiatingProcessId
  | where CallTime between (CopyTime .. CopyTime + 15m)
  | summarize hosts = make_set(Host, 10), calls = count(), lag = min(CallTime) - min(CopyTime)
          by DeviceName, InitiatingProcessFileName, FileName, FolderPath
  | order by calls desc
  ```
  The join is on both `DeviceId` and `InitiatingProcessId` and is bounded to fifteen minutes after the copy. A join on `DeviceId` alone across a thirty-day lookback correlates unrelated days, and both `let` bindings are used.
  Sysmon equivalent - Event ID 3 gives the initiating image for each connection, which is the whole basis of the hunt, and Event ID 1 gives lifetime, signer and parent. Event ID 22 (DNS query) is a useful cheap pre-filter where Event ID 3 volume is unmanageable, since the destination set here is small and distinctive. If 4688 is the only process source, note that it has no network events at all and the hunt cannot be run from it.
  The provider-side half - where mailbox audit telemetry is collected, the same incident should appear as a search or message-read burst from the user's usual device in the same minute. In Google Workspace that is the Gmail and Login audit activity; in Microsoft 365 it is the mailbox audit `SearchQueryInitiated` and `MailItemsAccessed` operations with the corresponding `CloudAppEvents` records. Worth noting as a caveat on scoping: the Workspace login audit has no user-agent or device-ID fields, so the provider log will confirm *that* a search happened and not *what* made it. The client identification has to come from the endpoint.
  Named artefacts from the report - the locally assembled bundle is `Identity_Report.txt`, the model response is received as `AI_Analysis.txt`, both leave in `volta_dox.zip`, and a third archive `volta_doxnet.zip` is produced "if the network enrichment produces anything" — which makes that third archive the single best confirmation that this stage ran and succeeded. The harvest log in `%APPDATA%` is the artefact to preserve first: "This is a timestamped harvest log and contains a record of exactly what was collected and whether the LLM call succeeded." The sample hash is `57ef4242666d78c50df145b34023df564f0fad38812d6a580e66433d427e2279`.
  Response - scope by what the enrichment reached, not by what the stealer collected. A host that produces a hit here has had its mailbox searched with a live session, so token and session revocation is the first action and password rotation is the second; revoking the password does not invalidate an already-issued session. Then treat the home-address corroboration as a real outcome rather than a theoretical one: the output of this stage is a dossier about a person, and the duty-of-care conversation with that person is part of the response.
  Expected, not observed by Talos - the report does not state the HTTP client, headers or User-Agent used for the *enrichment* calls specifically; the hand-assembled request with a browser User-Agent is documented for the inference call, and treating the enrichment calls as sharing that code path is an inference. The report does not give the mailbox search syntax, the number of requests per service, or the interval between them, so the `services >= 2` floor and the fifteen-minute join window above are starting points to tune rather than values from the report. Talos also does not say whether the enrichment runs before or after the appraisal call on every execution; the staged-archive description implies enrichment can produce its own later archive.
  Scope boundary - the collection legs are already covered and are not restated here. Browser credential and cookie theft including the App-Bound Encryption bypass is covered by [[H346]], [[H372]], [[H216]] and [[H247]]; wallet and seed-phrase collection by [[H284]], [[H322]] and [[M014]]. The appraisal call that follows this stage is [[M064]], and a host hitting either should be checked against the other, since the two stages run minutes apart in the same execution.
  Closest existing coverage - [[H247]] is the nearest hunt by subject and covers the theft of the cookies and tokens this stage consumes, stopping at the point of collection. Nothing in the corpus currently covers a stealer *using* the stolen session from the victim host during the same execution, which is the leg this adds and the leg that provider-side anomaly detection is structurally blind to. [[H409]] and [[M064]] cover the AI-egress behaviour of this family rather than the session replay.

# H434

The part of VOLTA that should change how a responder scopes a stealer incident is not the theft. It is that the stolen session gets used immediately, on the victim's own machine, before anything leaves.

Cisco Talos describes the stage plainly: the malware "then uses stolen session access to enrich that bundle further: searching the victim's Gmail for purchase receipts to corroborate a home address, pulling UberEats and DoorDash order history, and enriching Discord accounts via the stolen token." The mailbox step is specific about the goal — "using the victim's own authenticated Gmail tokens, it queries their inbox for receipts from Amazon, DoorDash, Uber Eats, Grubhub, Walmart, and PayPal, then review those receipts to establish a confirmed home address."

Normally a stolen cookie is a deferred risk. The operator exfiltrates it, uses it later from their own infrastructure, and that is where unfamiliar-device and impossible-travel detection earns its place. None of that applies here. The requests are authenticated, successful, from the user's usual device and usual IP, and they are searches rather than changes. On the provider side there is nothing anomalous to see.

Which leaves exactly one distinguishing fact: the client. Browsers and signed desktop apps talk to these services; a two-minute-old unsigned binary running from `%APPDATA%` does not. So the hunt is a non-browser process reaching several consumer identity-bearing APIs in one short burst, ideally joined back to the copies it made of the browser cookie and credential databases minutes earlier.

One practical note on what a hit means. The outcome of this stage is not a credential dump — it is a dossier. The report describes the local report file as being assembled from geolocation and home address, employer and employer domain, inferred birth year, card last-4 digits, Slack workspaces and document authorship metadata, with a separate archive produced only "if the network enrichment produces anything." That third archive is both the best confirmation the stage succeeded and the clearest statement of what was lost: a confirmed home address for a named person, corroborated from their own receipts.

## Why

- Session replay from the victim host defeats the controls built for stolen sessions. Unfamiliar IP, unfamiliar device, impossible travel and new-geography detections all key on the operator using the token from somewhere else, and here the operator never does.
- The client is the only anomaly in the transaction, so an endpoint hunt is not just one option among several — it is the only vantage point that can distinguish this from the user checking their own email.
- Diversity of destinations is what makes the signal strong. One non-browser process touching a mailbox API, two food-delivery services, a chat platform and a public valuation site inside a few minutes has no benign explanation on a managed host.
- The copies give a second anchor. A stealer must duplicate locked cookie and credential databases before decrypting them, and those copies are visible in file telemetry even though the reads are not — which supplies the join that turns a destination list into a behavioural chain.
- A hit changes the response, not just the ticket. Revoking the password does not invalidate a session already in use, so token and session revocation come first; and the person whose home address was corroborated needs to be told.
- Provider logs will confirm the search and not the searcher. The Workspace login audit has no user-agent or device-ID fields, so without endpoint telemetry the mailbox burst looks exactly like the user reading their own receipts.
