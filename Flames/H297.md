false_positive_notes: >-
  Cross-process memory writes are not rare, and a rule built on Sysmon EID 10 alone will drown. The
  legitimate population is large and well-defined - EDR and DLP agents, application performance
  monitoring and tracing libraries, debuggers and profilers, installers applying runtime patches,
  crash-reporting frameworks, accessibility software, game anti-cheat, and the Windows Error Reporting
  and shell components that routinely open other processes with broad access masks. The narrowing that
  makes this hunt workable is the parent-child constraint plus timing: restrict to cases where the
  writing process is the same process that created the target, and where the write lands inside the first
  few hundred milliseconds of the child's life and before it was resumed. That combination is
  uncommon outside injection tooling, because a legitimate monitoring agent has no reason to write into a
  process it just spawned before letting it run. The second half of the hunt - behavioural contradiction
  - carries its own trap in the opposite direction: a benign process legitimately does things its command
  line does not describe, because the command line names a script or a configuration file and the
  behaviour comes from the contents. Scope the contradiction test to processes whose logged arguments are
  empty or trivially short while the process performs external network connections, rather than trying to
  reason about whether any given argument "explains" any given action. Three further cautions. First,
  argument length is itself a signal worth stacking - the Process Hacker truncation bypass works by
  setting `UNICODE_STRING.Length` shorter than the buffer, so an unusually short or empty command line on
  a process that clearly received input is suspicious in its own right. Second, do not expect the
  sideloaded DLL to be unsigned in every case; the signed-executable-plus-malicious-DLL pattern means the
  parent will look entirely legitimate, and the module rather than the process is where the anomaly sits.
  Third, if the actor has forged the `LDR_DATA_TABLE_ENTRY` as SparroWocky does, a module inventory taken
  from the process itself will not list the payload at all - which is why Sysmon EID 7 collected at load
  time, not an on-demand module listing, is the data source specified above.

# H297

ESET's September 2026 analysis of SparroWocky, a backdoor used by the China-aligned FamousSparrow group
(overlapping with Earth Estries), is worth reading for one structural reason rather than for its
indicators. The implant does not try to make its command line look benign. It makes the command line a
value it controls. Launched with the `c` argument, it hooks `GetCommandLineA` and `GetCommandLineW`,
`__getmainargs` and `__wgetmainargs`, `__p___argc` and `__p__argv`/`__p__wargv` — the complete set of
entry points through which anything in usermode can ask what arguments a process received — and points
all of them at a command line of its choosing. The arguments it actually acts on are read from stdin.

That is a different proposition from obfuscating a command line. An encoded PowerShell one-liner is still
present in the telemetry and can be decoded. Here the telemetry is simply wrong, and it is wrong in the
field that a very large fraction of published Windows detection logic depends on. NVISO's demonstration of
the same class of trick put it plainly: Sysmon is completely fooled, because the process is started
suspended with benign arguments, Sysmon reads and logs them at creation, and only then are the arguments
overwritten and the thread resumed.

SparroWocky extends the same idea to module visibility. It builds a fake `LDR_DATA_TABLE_ENTRY` and links
it into the doubly-linked list in `PEB_LDR_DATA`, so a reflectively-loaded PE does not appear where a
tool enumerating loaded modules would look for it. Both tricks share one property: they corrupt what the
process reports about itself. Neither touches what the process does.

That is the seam this hunt works. There are two independent observables, and they should be run as
separate queries rather than one.

The first is mechanical and specific. Process argument spoofing requires the parent to write into the
child's memory after the PEB is initialised and before the thread resumes. That produces a Sysmon EID 10
ProcessAccess event whose source process is the target's own parent, whose GrantedAccess mask includes
`PROCESS_VM_WRITE`, and whose timestamp falls within the child's first moments. Legitimate software
writes into other processes constantly; it very rarely writes into a process it created before allowing
it to run. The parent-child identity and the sub-second window are what make this tractable.

The second is behavioural and general, and it is the one that survives a variant technique. Whatever the
logged command line says, the process still has to resolve a domain, open a socket, write a file, or set
a registry value to be useful. Join process creation to the network, file and registry events attributed
to the same process and look for processes whose arguments are empty or near-empty while the process
reaches out to an external host. MITRE's own detection strategy for this technique, DET0045, is built on
exactly this correlation rather than on any argument string, and that is the right instinct: the field is
adversary-controlled, the behaviour is not.

Both queries are more productive when anchored to the delivery chain rather than run across the estate
cold. SparroWocky arrived through DLL sideloading — a legitimate signed executable in a directory
alongside a malicious `winfsp-x64.dll` or `DukeQt.dll`, with the payload held in a `.dat` file of the
same name as the executable, and persistence established either as a service called `ProcAuditManager`
carrying a plausible audit-themed description or as a `SnapCart` value under the `Run` key. Starting from
Sysmon EID 7 image loads of unsigned or signer-mismatched DLLs adjacent to signed binaries gives a much
smaller candidate set to apply the two contradiction queries against.

[[H298]] covers the other end of the same intrusion: what SparroWocky does on command `0x13`, when it
deletes the service or Run value, drops a batch file to erase the loader, the payload and the legitimate
host executable, and exits.

## Why

- The technique defeats the single most widely used Windows detection field. A very large share of
  published hunting logic, Sigma rules and EDR analytics match on `ProcessCommandLine`; against an
  implant that hooks every argument-retrieval API, all of it returns a clean result on a compromised
  host. A hunt that does not depend on that field is not an incremental improvement, it is the only
  thing that works.
- It is used by a state-aligned actor against government targets right now. ESET attributes SparroWocky
  to FamousSparrow and reports roughly 90% of observed targets in Latin America from mid-2025 into 2026
  — Argentina, Ecuador, Guatemala, Honduras, Panama, Peru, Puerto Rico and Venezuela — including a
  Panamanian entity connected to the Canal ports dispute. This is current tradecraft, not a research
  curiosity.
- The evasion has a mandatory mechanical footprint that the evasion itself cannot hide. To rewrite the
  PEB the parent must obtain a handle with write access and call `WriteProcessMemory` against a child it
  has not yet resumed. That cross-process write is logged by the kernel callback Sysmon EID 10 is built
  on, not by the process, so spoofing the process's own view of itself does nothing to suppress it.
- The behavioural half generalises past this specific implant. Argument spoofing, parent PID spoofing
  and hollowing all produce the same downstream shape: a process doing more than its recorded provenance
  accounts for. Building the contradiction join once gives coverage against the variant that appears
  after this one.
