title: "A relay client staged in a hidden memory-backed directory on a compromised Linux web server, made executable, back-dated to match system files, then deleted from disk while its outbound session to a public relay network keeps running"
hypothesis: >-
  A web-application compromise normally ends when the application is patched. An operator who installs a relay client instead keeps access that outlives the fix, and does it without owning any infrastructure: the client and the operator each connect outbound to a shared public relay network which pairs them on a secret, so there is no attacker address or domain to block, no inbound listener on the host, and no payload-embedded destination. The deployment leaves a short, ordered sequence on disk - retrieve a script with the system HTTP client, stage an architecture-matched client binary in a dot-prefixed directory under a memory-backed filesystem, make it executable, back-date it to blend with system files, then remove the staging files - and persists across reboot through several mechanisms at once. The observable chain is a web-service account executing the system HTTP client, an executable created under a hidden directory in a memory-backed mount, a permissions change and a timestamp change on the same path, and the staged file deleted while its process keeps a session open.

false_positive_notes: |
  Memory-backed directories and the system HTTP client are both load-bearing parts of ordinary Linux operation, so neither can carry the hunt alone.
  - Memory-backed mounts are used heavily and legitimately. Application servers, session handlers, PHP opcache, container runtimes, systemd and several databases write there constantly, and some legitimate software uses dot-prefixed paths. The finding is an executable file created there and then run, not activity in the directory.
  - Retrieving a script with the system HTTP client and piping it to a shell is, unfortunately, a mainstream software installation pattern. Legitimate vendor install instructions do exactly this. The discriminator is the account - a web-service account doing it, rather than an administrator or a deployment agent.
  - Permissions changes on freshly written files are routine for deployment tooling, build processes and package managers. On its own a permissions change is uninteresting; on a file in a hidden memory-backed directory, immediately before execution, it is part of the sequence.
  - Timestamp manipulation has legitimate uses. Archive extraction preserves original times, build reproducibility tooling sets them deliberately, and rsync and some package operations adjust them. The signal is a timestamp set to match unrelated system files on a binary that was just written and executed.
  - Deleting an installer after installation is normal hygiene. Plenty of legitimate software cleans up its staging files. It becomes a finding when the deleted file is still running and holding a network session, which is the combination to query rather than the deletion.
  - Relay and tunnelling services have legitimate users. Developers and administrators use remote-access relay tools deliberately, including for support and for reaching machines behind network address translation. Decide whether the organisation permits them before hunting, and treat an approved-use inventory as the allowlist - otherwise the result is a list of the engineering team.
notes: |
  Source reporting is Microsoft Threat Intelligence November 11, 2026 analysis of GSocket deployment on compromised Linux servers across multiple incidents. The companion hunt is [[B071]], which baselines the outbound-session and persistence surface this behaviour hides inside. The closest existing hunts are [[H450]], which covers a web-application service account using already-installed tooling after a web flaw becomes command execution - the same account and the same stage, but the living-off-the-land case rather than a staged relay client - [[H319]], which covers Linux implants masquerading as system components including bracketed kernel-thread names, and [[H283]], which covers dot-prefixed staging under a temporary directory after an exposed gateway is exploited. No existing hunt in the corpus references GSocket, gs-netcat or a shared public relay network.
  Why patching does not end this, which is the whole point of the report - Microsoft frames the problem as a single compromise outlasting its own remediation: the relay client "runs independently of the exploited application", so "patching the vulnerability does not remove the relay client or its persistence". Microsoft states the defender consequence directly - treat application patching as incomplete remediation, and investigate the host as well as the vulnerability. Microsoft reports devices with related detections increased 356.2% from March through August 2026, that web applications and hosting accounted for 87.1% of attributable incidents, that PHP web applications and cPanel hosting represented 63.9% of incidents within that group and Apache 24.3%, and that education and research accounted for the largest share of affected organizations at 30.7%, followed by technology and telecommunications at 22.9%. Microsoft is careful that these figures reflect the share of affected organizations rather than deliberate sector selection, and attributes the distribution to exposure.
  Why there is nothing to block - The design choice that makes this attractive to unrelated actors. Microsoft reports that traffic "passes through the Global Socket Relay Network, a public relay service", that "the threat actor does not register or host any infrastructure, so there is no threat actor-owned IP address or domain to block", and that both the compromised host and the operator connect outbound, so "the host needs no inbound listener or public IP address, and network address translation does not prevent the connection". Microsoft notes the control that does remain available: "inbound firewall rules do not see this traffic, although egress filtering and outbound monitoring can". Endpoints are identified by a shared secret rather than an address - Microsoft reports the deployment script typically generates a random secret and writes it to standard output, with the operator able to read it from the console, redirect it to a temporary file, or have it delivered through a notification channel such as Telegram, configured with `GS_TG_TOKEN` and `GS_TG_CHATID`, Discord, or a webhook. Hunting for those environment-variable names in process telemetry and in persistence artefacts is a narrow, high-signal check.
  Core filter 1, the staging sequence - The ordered, observable core of the hunt. Microsoft reports the script "profiled the host, selected a GSocket client matching the system architecture, staged it in writable or memory-backed paths such as /dev/shm", with payloads staged under the dot-prefixed `/dev/shm/.gs-0` directory and a detected file also observed at `/tmp/.gsn_ora`. The published paths and hashes are:
  ```
  /dev/shm/.gs-0/gs-netcat_mini-linux-x86_64
  d94f75a70b5cabaf786ac57177ed841732e62bdcc9a29e06e5b41d9be567bcfa
  /dev/shm/.gs-0/gs-netcat_mini-linux-aarch64
  f95c4d029e6784e3849b4d1e2e2ae1a661187236ef7c5d487c71158a290a03b5
  /tmp/systemd-remount-d
  ```
  Microsoft publishes two further hashes in the same indicator set, `55d141bb2f62c527c3fea3413b8429fed7d52633d0b123b5e611bfa42165229f` and `12450bafc7a4398040e1ad3a16dbf4dbc79b6a8f83ef306c4f0f73f59886f06c`, and reports the distribution endpoints as `gsocket[.]io`, `cdn[.]gsocket[.]io` and `gsgg[.]b-cdn[.]net`. These are tool distribution endpoints rather than operator-owned command and control, which matters for how a hit is triaged - a connection there means the tool was fetched, not that the operator lives there. The durable form of the check is behavioural: an executable created under a dot-prefixed directory in a memory-backed mount, chmod-ed, executed, then deleted.
  Core filter 2, the chmod and the timestomp on the same path - Microsoft reports `chmod` changed permissions on the renamed payload, "including chmod 700 /usr/bin/defunct", and that `touch` commands "applied older timestamps to /usr/bin/defunct and defunct.service", with timestamp copy operations targeting the service-like payload name. Hunt for a permissions change and a timestamp change applied to the same path within a short window of that path being written, which is a three-event sequence that legitimate deployment tooling rarely produces in that order on a memory-backed mount. A back-dated binary in a system binary directory is independently checkable during triage by comparing its modification time against the package-owned files around it and against the package database.
  Core filter 3, the file that is gone while its process runs - The strongest single artefact, and one that needs no indicator at all. Microsoft reports `rm` removed the staged client from the memory-backed directory and a separate `rmdir` removed the staging directory. A process whose executable path has been unlinked still shows the deleted state in its process entry, so this is directly observable on a live host:
  ```bash
  set -u
  ls -la /proc/*/exe 2>/dev/null | grep -i 'deleted' || echo "no running process with a deleted executable"
  for p in /proc/[0-9]*; do
    [ -r "$p/exe" ] || continue
    tgt=$(readlink "$p/exe" 2>/dev/null) || continue
    case "$tgt" in
      *" (deleted)"|/dev/shm/*|/tmp/*)
        echo "PID ${p#/proc/}  exe=$tgt"
        tr '\0' ' ' < "$p/cmdline" 2>/dev/null; echo
        awk '/^Uid:|^PPid:/' "$p/status" 2>/dev/null
        ls -l "$p/fd" 2>/dev/null | awk '/socket/ {c++} END {print "  sockets: " c+0}'
        echo "---"
        ;;
    esac
  done
  ```
  A process running from a deleted executable, or from a path in a memory-backed or temporary mount, while holding open sockets, is the case. Triage values are the command line, the effective user, the parent, and the destinations of its open sockets.
  Core filter 4, the layered persistence - Microsoft reports operators "persisted through cron, systemd, shell profiles, watchdogs, and redundant copies", and warns that "persistence is often layered across several mechanisms, so stopping the running process alone does not remove access". Observed artefacts include a client executed under the service-like filename `systemd-remount-d`, a `defunct.service` unit with a `multi-user.target.wants` link, and a renamed payload at `/usr/bin/defunct`. Hunt cron tables for every account including the web-service accounts, systemd units whose names resemble a system component but which no package owns, and additions to shell startup files - then enumerate all of them rather than stopping at the first. Note that [[H319]] already covers the bracketed kernel-thread naming that the same deployment uses at runtime, so the two hunts are complementary on the masquerade leg.
  Core filter 5, the escalation that sometimes follows - Microsoft reports that after gaining execution as the web-service account, "in few observed incidents, threat actors attempted to exploit CVE-2026-43284, one of the recent Linux kernel vulnerabilities also known as Dirty Frag, to elevate privileges to root". Microsoft recommendation is to prioritise local privilege-escalation patching on internet-facing servers specifically, which is a prioritisation most estates do the other way around. For a confirmed case, kernel patch state on the affected host determines whether the finding is a web-service-account compromise or a root compromise. Expected, not observed by Microsoft: whether the escalation attempts succeeded - the report says attempted, so a finding should not assert root.
  Core filter 6, the initial access and the first commands - Microsoft reports operators "exploited internet-facing web applications and used curl to download and execute a remote script", with follow-on commands launched as children of web server and application runtime processes. The highest-value generalisable query here is the system HTTP client executed by a web-service account with a parent in the web server or runtime process tree, which is the first observable moment in the whole chain and the one that precedes every artefact above.
  Scope - Internet-facing Linux web and application servers, hosting environments, and content-management platforms. Microsoft telemetry concentration on PHP applications, cPanel hosting and Apache is a prioritisation hint rather than a boundary, and the sector distribution points at decentralised web estates maintained outside central IT as the population to inventory first.

# H473

You patch the web application. The access stays.

Microsoft Threat Intelligence described multiple incidents where that is exactly what happened. A threat actor exploits an internet-facing application, gets command execution as the web-service account, and installs a relay client. The client runs independently of the application that let them in, so the patch that closes the vulnerability does not touch it.

The reason multiple unrelated actors have adopted this particular tool is worth understanding, because it is about infrastructure the operator does not have to own. Traffic goes through the Global Socket Relay Network, a public relay service. The compromised host connects outbound. The operator connects outbound. The relay pairs them. There is no actor-registered domain and no actor-owned address, so there is nothing to blocklist. The host needs no inbound listener and no public address, and network address translation is irrelevant. Inbound firewall rules never see any of it.

Endpoints are matched on a shared secret rather than an address. The install script generates one and prints it, and the operator can have it delivered over Telegram, Discord or a webhook. With that secret, they reconnect from anywhere, later, without knowing the victim's address or hostname.

What is left on the host is a short sequence. `curl` fetches a script. The script picks a client matching the architecture and stages it under `/dev/shm/.gs-0`. `chmod` makes it executable. `touch` back-dates it to look like a system file. Then `rm` removes the staged file and `rmdir` removes the directory — while the process keeps running and keeps its session open.

That last part is the gift. A process running from an executable that no longer exists, holding open sockets, is not a thing a legitimate service does.

Microsoft's own closing control is the one that still works: inbound rules cannot see this, but egress filtering and outbound monitoring can.

## Why

- **This turns one web compromise into persistent access, and the remediation most teams perform does not address it.** Patching the application is the correct fix for the vulnerability and is not a fix for the host. An estate that patched and moved on has closed the door and left the tenant inside.
- **There is nothing to blocklist, which breaks the normal containment reflex.** Blocking an address, sinkholing a domain or filing an abuse report all presume the operator owns something. Here they own a secret. That pushes the response toward egress policy and host remediation rather than indicator blocking.
- **The staging sequence is short, ordered and unusual as a sequence.** Any one of create, chmod, touch, execute, delete is ordinary. All five against the same path in a hidden memory-backed directory, in that order, within seconds, is not — and it needs no indicator to find.
- **A deleted executable with live sockets is close to a zero-false-positive check.** It is directly readable from the process table on a live host, it survives the operator's own cleanup, and no legitimate service runs that way. On a host where disk artefacts have been removed, this is what is left.
- **The persistence is layered on purpose, so partial remediation leaves access.** Cron, systemd, shell profiles, watchdogs and redundant copies, all at once. Killing the process or removing one unit is the mistake the report specifically warns about, and it means the remediation task is an enumeration task.
- **The affected population skews toward estates nobody owns.** Education and research led the distribution, which fits large, decentralised web estates maintained outside central IT — the servers least likely to appear in an inventory, be patched promptly, or have egress monitoring at all.
