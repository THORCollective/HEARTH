false_positive_notes: >-
  Interactive administrators and configuration management legitimately write authorized_keys —
  Ansible, Puppet, Chef, Salt, cloud-init and Terraform provisioners all do it, and will be the bulk of
  your results. Enumerate and exclude those parents explicitly by process ancestry, not by user, since
  config management often runs as root. The discriminator that carries this hunt is PROCESS ANCESTRY:
  a key written by a process descending from an AI gateway, a web server, a Java worker, or any
  network-facing daemon has no legitimate explanation, whereas one written by an SSH session or a
  config-management agent usually does. A critical piece of tuning context: in cloud fleets using OS
  Login, EC2 Instance Connect, or equivalent, authorized_keys is abstracted away and engineers
  essentially never touch it by hand — in those environments ANY manual write is anomalous and this
  becomes a very high-signal, very low-volume detection. Two collection caveats. First, auditd watches
  inodes, so the file must exist when auditd starts; you cannot watch `*/.ssh/authorized_keys` by
  pattern, and a key dropped into a home directory that had no .ssh at boot will be missed by a naive
  file watch — back it with directory watches and process telemetry. Second, `chattr +i` is not
  supported on tmpfs, so the immutability signal will not appear for payloads staged in /tmp or /run on
  a default systemd host.

# H282

Exposed AI infrastructure has become a category of internet-facing application with the security posture
of an internal tool. Inference gateways, orchestration platforms and RAG frameworks — LiteLLM, RAGFlow,
Kestra — sit at a control point where model credentials, provider API keys and database connection
strings all converge, and a meaningful number of them are reachable from the internet.

What the operators do after exploiting one is unglamorous and effective. Having read `/proc/1/environ`
for master keys and API tokens, and having dumped `LiteLLM_ProxyModelTable` and
`LiteLLM_VerificationToken` from the backing PostgreSQL, they need to survive a container restart. So
they append a key to `authorized_keys` and add a cron entry. Microsoft maps the LiteLLM case explicitly
as "service-account SSH key and cron entries for durable access."

The mechanics are worth being precise about, because they define the query. The write is an append
redirect — `>>` — not an editor session. It is executed non-interactively: Microsoft notes the RAGFlow
chain was "fully automated with no interactive shell." And its parent is the gateway itself, or a
Python or shell child of the gateway. That lineage is the entire detection. The file being written is
ordinary; who is writing it is not.

The durability varies with deployment, and Microsoft is careful to qualify it: for the RAGFlow case,
persistence "depends on container privileges, filesystem persistence, and host-container boundary
configuration." A key written into an ephemeral container layer dies with the container. One written to
a mounted host volume does not — which is exactly why your triage needs the container context.

## Why

- **Process ancestry converts a noisy file into a precise detection.** `authorized_keys` is written
  legitimately every day by administrators and configuration management, which is why file-only
  monitoring on it tends to get tuned into oblivion. The parent process is what carries the signal: a
  network-facing inference gateway has no reason to add an SSH key, ever. Requiring that lineage turns a
  high-volume file event into a query that should return nothing in a healthy environment.
- **This is the step that converts an exploit into an incident.** Everything before it — the gateway
  vulnerability, the `/proc/1/environ` read, the credential dump — is recoverable by patching and
  rotating keys. The SSH key is what survives the patch. Catching the persistence write is the
  difference between "we rotated some API keys" and "we found the backdoor six weeks later."
- **In cloud fleets this is nearly false-positive-free.** Where OS Login, EC2 Instance Connect or
  equivalent are in use, key distribution is handled by the platform and engineers do not touch
  `authorized_keys` at all. Any manual write is anomalous by definition, and inserted keys tend to
  persist for a long time precisely because nobody looks at the file.
- **The credentials at stake are not just host credentials.** These gateways broker provider API keys —
  OpenAI, Azure, Anthropic, Gemini — and RAGFlow was backdoored by monkey-patching `TenantLLM.insert()`
  so every subsequent config event leaked keys, with errors suppressed so the application kept working.
  Persistent host access on a gateway is persistent access to an organization's model spend and to
  whatever data flows through it.
- **The published detection guidance is genuinely good, and reusable beyond this campaign.** Microsoft's
  persistence query ORs four conditions — hidden `/tmp/.` execution, `crontab` piped through `grep -v`
  to strip rival entries, `chattr`, and `authorized_keys` with `>>`. Each maps to a different ATT&CK
  technique and each is independently useful, which makes it a good template rather than a set of IOCs.
- **HEARTH had no T1098.004 coverage at all**, despite SSH key persistence being one of the most common
  and longest-dwelling Linux persistence mechanisms in cloud environments.
