title: A ScreenConnect client uninstalled by a script that a sibling instance delivered - the rogue RMM that removes its own delivery chain
hypothesis: >-
  An operator deploying rogue remote-management software installs a second client of the same product
  and then removes the first - the copy that is attached to the phishing delivery. Huntress observed a
  Power BI-delivered ScreenConnect installer plant a first client (`2b302081e9e777d0`, relay
  `instance-g01s1n-relay[.]screenconnect[.]com`) that in every instance established a second client
  (`43773b3da4ccb17b`, controller `onthegotree[.]site`). In one incident the first client executed a CMD
  file that deployed `SCAutoFix.ps1` from the temp directory; that script installed the second instance

  likely effort to evade detection." Hunt for the removal of one remote-access client instance -

false_positive_notes: |
  A host having more than one remote-management product on it is extremely common and is not what this hunt is about - managed service providers, acquisitions, migrations between RMM vendors, co-managed estates and help-desk escalation paths all leave two or three different products installed side by side, often for years. That is messy, not malicious. What this hunt targets is narrower - one client instance of a product removed shortly after a *second instance of the same product*, with a different instance identifier or controller address, arrived on the same host. In a legitimately managed estate there is one tenant and one relay, so a second instance ID is a second owner. Real exceptions do exist - a genuine vendor migration between two ScreenConnect tenants, a managed service provider onboarding or offboarding a client, and lab or test instances on engineering machines will all produce a transient second instance, so scope by whether the second controller address is an approved one, which is exactly what the baselines [[B041]] and [[B051]] exist to answer. The uninstall leg has its own benign cases - uninstalling an old agent after a migration is the correct procedure, and software-deployment tooling does it routinely. The discriminator is *who performed it* - a scripted uninstall executed by a PowerShell script that a client of the same product delivered from `%TEMP%`, rather than by a deployment system under a management account, has no legitimate form. Note also that short-interval scheduled tasks named like repair jobs are a real pattern in some vendor tooling, so the task name alone is weak; it is the two-minute interval combined with a script in a user-writable path that carries the signal. Finally, legitimate ScreenConnect guest-access installer URLs do carry `?e=Access&y=Guest&t=` tokens, so the URL shape is not itself suspicious - the tenant hostname is the field that matters.

The page showed a blurred form and a "Download Reference" prompt; clicking it opened a new tab to `hxxps[://]dailylifeproject[.]site/S/`.

It "performed browser and environment fingerprinting, checking the operating system, browser and version, mobile/desktop status, user-agent, automation indicators, screen size, iframe context, and cloud-provider-associated cookies. It also embedded a Telegram Bot API credential and chat identifier to report victims' IP addresses, geolocation, browser, operating system, and download activity." Visitors failing the checks were redirected to `check.vykyn[.]click/E/`. Other variants - `burnsworth[.]site/S/main.html` (which restricted access to Windows desktop systems and filtered Microsoft or unknown ISPs, reusing the same hardcoded Telegram bot credential), `essaywritingservice[.]site/S/main[.]html`, `openpediatrics[.]site/S/main.html`. In one incident the first client executed `LyN03DvVjUKPrun.cmd`, which deployed `SCAutoFix.ps1` from the temp directory; that script downloaded `C:\Temp\ScreenConnect.ClientSetup.msi` (saved as `C:\Users\ScreenConnect.ClientSetup (6).exe`) from `hxxps[://]onthegotree[.]site/Bin/ScreenConnect.ClientSetup.msi?e=Access&y=Guest`, installed the second instance, and - the key detail - "also resulted in the uninstallation of the first ScreenConnect instance, in a likely effort to evade detection." After the rogue RMMs were deployed they executed `HideUL_x64.exe`, which Huntress assessed as a defense evasion tool, and in one incident created a scheduled task `SCAutoRepairEvery2Min` running `SCAutoFix.ps1` every two minutes. The SOC shut the attack down at that point. A retroactive hunt found the unique client and configuration from one of these RMMs on 22 other endpoints across separate incidents.
  Why the removal is the hunt and the pair is not. HEARTH already covers a good deal of rogue-RMM ground - [[H306]] for a ScreenConnect client spawning a staged script chain as its own child, [[H279]] for an RMM MSI installed from a user-writable path with attacker-supplied root CA properties, [[H307]] for an endpoint enrolled into an attacker-controlled deployment tenant, [[M043]] for graphing agent enrolment to separate a rollout from self-propagation, and [[B041]] and [[B051]] for the sanctioned-instance and exclusions baselines. The *pair* itself is already covered - [[B041]] flags a second instance of an RMM product on a host that already has one, especially with a different configured server, [[B051]] flags a second client of the same product on one host, and [[H306]] groups ScreenConnect activity by instance. What is new here is the *removal* - one instance uninstalled by a script its sibling delivered. Inference, not stated by Huntress: that removal is an attack on incident reconstruction, because the surviving agent's own install event points only at a local script and a local MSI. Process lineage still connects them (first client to `cmd.exe` to `powershell.exe` to the installer), and the browser download still exists in history, so the chain is weakened rather than erased - which is why the deletion is worth catching as it happens.
  Context filter, the pair. ScreenConnect installs each client under a path and service name carrying its 16-hex instance ID - `ScreenConnect Client (<id>)` - so instances can be counted per host without relying on network destinations (a single legitimate cloud instance already talks to both a web host and a relay, so counting destinations over-fires). Advanced hunting keeps 30 days; for longer history use the [[B041]] inventory.
  Sample KQL - hosts that have run more than one ScreenConnect instance.
  `DeviceProcessEvents | where Timestamp > ago(30d) | extend Inst = extract(@"ScreenConnect Client \(([0-9a-f]{16})\)", 1, FolderPath) | where isnotempty(Inst) | summarize Instances = make_set(Inst), FirstSeen = min(Timestamp), LastSeen = max(Timestamp) by DeviceName | where array_length(Instances) > 1`
  Core filter, the removal. The uninstall is visible as deletion of the instance's service key and install directory. A process-command-line filter on product names is not enough - `msiexec /x {GUID}` names no product, and an in-process uninstall (WMI or `Uninstall-Package`) spawns no child at all - so key on the deletion itself and then walk back to what launched the uninstaller. The deleting process will usually be `msiexec.exe` running as a service; the useful pivot is the `cmd.exe` or `powershell.exe` that started the uninstall, and whether its own ancestry leads back to the other instance's client process.
  Sample KQL - a ScreenConnect instance's service key deleted.
  `DeviceRegistryEvents | where Timestamp > ago(30d) | where ActionType == "RegistryKeyDeleted" | where RegistryKey has @"\Services\ScreenConnect Client (" | extend Inst = extract(@"ScreenConnect Client \(([0-9a-f]{16})\)", 1, RegistryKey) | project Timestamp, DeviceName, Inst, RegistryKey, InitiatingProcessFileName, InitiatingProcessCommandLine, InitiatingProcessParentFileName`
  Sample KQL - files under a ScreenConnect instance directory deleted, grouped per instance.
  `DeviceFileEvents | where Timestamp > ago(30d) | where ActionType == "FileDeleted" | where FolderPath has "ScreenConnect Client (" | extend Inst = extract(@"ScreenConnect Client \(([0-9a-f]{16})\)", 1, FolderPath) | summarize Deleted = count(), First = min(Timestamp) by DeviceName, Inst, InitiatingProcessFileName, InitiatingProcessCommandLine`
  Promote a removal when a different instance ID first appeared on the same host within the preceding hours, and when a script under `%TEMP%` or `C:\Temp\` sits between the two. Triage fields - both instance IDs, both controller addresses, install and removal timestamps, the process chain that ran the uninstall, and whether either controller is on the approved list.
  Corroborating legs worth the same sweep. A scheduled task with a repetition interval under five minutes whose action is a `.ps1` in a user-writable path (`SCAutoRepairEvery2Min` running `SCAutoFix.ps1`) is a tight query against Event ID 4698 and survives renaming, since the interval and the path carry the signal. `HideUL_x64.exe` is worth a retrospective hash and name sweep. On the delivery side, the generalisable pattern is a browser navigation to a trusted cloud-application domain followed within seconds by a navigation to an unrelated newly-registered host and then an executable or MSI download - the trusted domain is the reason the mail got through, so email-gateway telemetry will show nothing wrong with the link.
  Scoping note on the delivery page. The landing page's checks - automation indicators, iframe context, screen size, cloud-provider cookies, and in one variant an explicit filter on Microsoft or unknown ISPs - are designed to keep scanners and researchers from ever seeing the payload. Two practical consequences - detonating the URL from a security vendor's or cloud provider's address space will return the benign redirect rather than the installer, so a clean sandbox verdict on one of these URLs means very little; and the victim-side download is the first reliable artefact in the chain.

# H374

The interesting move in this campaign is not that the operators installed remote-management software. It is that the first rogue client brought in a second one, and in one incident the first copy was then uninstalled.

Huntress traced the chain in October 2026. A phishing email carried a link to a real Microsoft Power BI page. Huntress notes that Power BI has been abused this way before - real dashboards created under compromised or throwaway accounts, set to public sharing, with a malicious link embedded. Because the URL points at `app.powerbi.com`, it passes mail filters and gateways that trust the domain outright. The dashboard displayed a blurred form and a "Download Reference" button. Clicking it opened a new tab to an attacker-controlled site that fingerprinted the visitor — operating system, browser, mobile or desktop, user agent, automation indicators, screen size, iframe context, cloud-provider cookies — reported all of it to a hardcoded Telegram bot, and only then, after a deliberate few-second delay, programmatically clicked a hidden link to start the download. Visitors who failed the checks were redirected to `check.vykyn[.]click/E/` instead. One variant explicitly filtered out Microsoft and unknown ISPs.

The payload was a ScreenConnect client. Then came the part worth hunting.

In every instance the first client — `2b302081e9e777d0`, talking to a ScreenConnect relay — established a *second* client, `43773b3da4ccb17b`, pointed at a completely different controller at `onthegotree[.]site`. In one incident Huntress saw how: the first client ran a CMD file that deployed `SCAutoFix.ps1` from the temp directory, and that script downloaded and installed the second instance — which also uninstalled the first one.

Read that from the responder's chair (this is inference, not something Huntress states). You find a rogue ScreenConnect agent on the host. Its own install event points at a local MSI, installed from a local path, by a local script. The phishing email, the Power BI link and the browser download all attach to the instance that no longer exists. Process lineage and browser history still connect the two if you go looking, but the obvious pivot from the surviving agent leads somewhere boring.

Finding the rogue RMM is already covered several ways, and so is finding a host with *two* instances of one product — [[B041]] and [[B051]] both flag it. The new piece is the removal: one instance's service key and directory deleted, by an uninstall that a script delivered by the other instance started from `%TEMP%`. That is the signature of the cleanup rather than of a migration, which is performed by a deployment system under a management account.

The operators left two other things behind: `HideUL_x64.exe`, which Huntress assessed as a defense-evasion tool, and a scheduled task called `SCAutoRepairEvery2Min` configured to run `SCAutoFix.ps1` every two minutes. The SOC caught it there. A retroactive hunt found the same unique client configuration on 22 other endpoints across separate incidents.

## Why

- **The removal is the new behaviour.** The pair of instances is already flagged by [[B041]] and [[B051]]; one instance being uninstalled by a script its sibling delivered is not covered elsewhere.
- **Key on the deletion, not the uninstall command line.** `msiexec /x {GUID}` names no product and an in-process uninstall spawns nothing, but the instance's service key and directory still get deleted.
- **Historical state matters more than current state here.** By design, only one client survives. Advanced hunting keeps 30 days, so a removal older than that has to be found in the [[B041]] inventory history rather than in event telemetry.
- **Provenance separates cleanup from migration.** Uninstalling an old agent after a vendor change is correct procedure performed by a deployment system under a management account. A scripted uninstall driven from `%TEMP%` by a same-product agent is not that.
- **The trusted domain is why the mail got through, so the mail gateway is the wrong place to look.** `app.powerbi.com` is a legitimate Microsoft domain with legitimate public sharing. There is nothing wrong with the link, which makes the endpoint the first place the campaign is visible.
- **A clean sandbox verdict on the URL is close to meaningless.** The landing page filters automation indicators, iframe context and — in one variant — Microsoft and unknown ISPs. Detonating from vendor or cloud address space returns the benign redirect, so absence of a payload proves nothing.
- **The two-minute repair task is the most durable artefact.** A scheduled task whose action is a `.ps1` in a user-writable path with a sub-five-minute repetition interval survives every rename, and it means the host keeps reaching out.
- **One configuration reached 22 other endpoints.** Huntress's retroactive hunt found the same unique client and configuration across separate incidents — so a confirmed instance ID or controller address is worth an immediate estate-wide sweep, not just a single-host remediation.
