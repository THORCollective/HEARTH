false_positive_notes: |
  A host having more than one remote-management product on it is extremely common and is not what this hunt is about - managed service providers, acquisitions, migrations between RMM vendors, co-managed estates and help-desk escalation paths all leave two or three different products installed side by side, often for years. That is messy, not malicious. What this hunt targets is narrower - *two client instances of the same product*, carrying different instance identifiers or pointed at different controller addresses, on one host. In a legitimately managed estate there is one tenant and one relay, so a second instance ID is a second owner. Real exceptions do exist - a genuine vendor migration between two ScreenConnect tenants, a managed service provider onboarding or offboarding a client, and lab or test instances on engineering machines will all produce a transient second instance, so scope by whether the second controller address is an approved one, which is exactly what the baselines [[B041]] and [[B051]] exist to answer. The uninstall leg has its own benign cases - uninstalling an old agent after a migration is the correct procedure, and software-deployment tooling does it routinely. The discriminator is *who performed it* - a scripted uninstall executed by a PowerShell script that a client of the same product delivered from `%TEMP%`, rather than by a deployment system under a management account, has no legitimate form. Note also that short-interval scheduled tasks named like repair jobs are a real pattern in some vendor tooling, so the task name alone is weak; it is the two-minute interval combined with a script in a user-writable path that carries the signal. Finally, legitimate ScreenConnect guest-access installer URLs do carry `?e=Access&y=Guest&t=` tokens, so the URL shape is not itself suspicious - the tenant hostname is the field that matters.

# H374

The interesting move in this campaign is not that the operators installed remote-management software. It is that they installed it twice and then deleted the first copy.

Huntress traced the chain in October 2026. A phishing email carried a link to a real Microsoft Power BI dashboard — created under a compromised or throwaway account, set to public sharing, with a malicious link embedded in it. Because the URL points at `app.powerbi.com`, it passes mail filters and gateways that trust the domain outright. The dashboard displayed a blurred form and a "Download Reference" button. Clicking it opened a new tab to an attacker-controlled site that fingerprinted the visitor — operating system, browser, mobile or desktop, user agent, automation indicators, screen size, iframe context, cloud-provider cookies — reported all of it to a hardcoded Telegram bot, and only then, after a deliberate few-second delay, programmatically clicked a hidden link to start the download. Visitors who failed the checks got a harmless redirect instead. One variant explicitly filtered out Microsoft and unknown ISPs.

The payload was a ScreenConnect client. Then came the part worth hunting.

The first client — instance `2b302081e9e777d0`, talking to a ScreenConnect relay — ran a CMD file that dropped `SCAutoFix.ps1` into the temp directory. That script downloaded a *second* ScreenConnect installer, pointed at a completely different controller at `onthegotree[.]site`, installed it as instance `43773b3da4ccb17b` — and uninstalled the first one.

Read that from the responder's chair. You find a rogue ScreenConnect agent on the host. You trace it backwards to establish how it got there. What you find is a local MSI, installed from a local path, by a local script. No phishing email. No Power BI link. No fingerprinting landing page. No browser download event. The entire delivery chain was attached to the instance that no longer exists, and the agent you are looking at has a clean, boring, unhelpful provenance.

So the hunt cannot be "find the rogue RMM" — HEARTH already does that several ways. It has to be "find the host that has held *two*." Two client instances of the same product, with different instance IDs or different controller addresses, is a second owner, because a legitimately managed estate has one tenant and one relay. And the uninstall, when it was performed by a PowerShell script that an agent of the same product delivered from `%TEMP%`, is the signature of the cleanup rather than of a migration.

The operators left two other things behind: `HideUL_x64.exe`, which Huntress assessed as a defense-evasion tool, and a scheduled task called `SCAutoRepairEvery2Min` configured to run `SCAutoFix.ps1` every two minutes. The SOC caught it there. A retroactive hunt found the same unique client configuration on 22 other endpoints across unrelated incidents.

## Why

- **The uninstall is an attack on reconstruction, not on detection.** Removing the first client severs the surviving agent from the phishing email, the Power BI link and the browser download. The forensic chain is deliberately broken, which is why the *pair* has to be the unit of analysis.
- **Two instances of one product means two owners.** A managed estate has one tenant and one relay. Multiple different RMM *products* is ordinary estate mess; multiple instance IDs of the same product on one host is not, and it is a far tighter filter than "an RMM is present."
- **Historical state matters more than current state here.** By design, only one client survives. The hunt has to read registry writes, service installations and MSI product GUIDs over time rather than inventorying what is installed now.
- **Provenance separates cleanup from migration.** Uninstalling an old agent after a vendor change is correct procedure performed by a deployment system under a management account. A scripted uninstall driven from `%TEMP%` by a same-product agent is not that.
- **The trusted domain is why the mail got through, so the mail gateway is the wrong place to look.** `app.powerbi.com` is a legitimate Microsoft domain with legitimate public sharing. There is nothing wrong with the link, which makes the endpoint the first place the campaign is visible.
- **A clean sandbox verdict on the URL is close to meaningless.** The landing page filters automation indicators, iframe context and — in one variant — Microsoft and unknown ISPs. Detonating from vendor or cloud address space returns the benign redirect, so absence of a payload proves nothing.
- **The two-minute repair task is the most durable artefact.** A scheduled task whose action is a `.ps1` in a user-writable path with a sub-five-minute repetition interval survives every rename, and it means the host keeps reaching out.
- **One configuration reached 22 other endpoints.** Huntress's retroactive hunt found the same unique client and configuration across separate incidents — so a confirmed instance ID or controller address is worth an immediate estate-wide sweep, not just a single-host remediation.
