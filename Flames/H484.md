hypothesis: >-
  After guessing an administrator password over RDP, the operator does not install an implant - it
  reconfigures the host into a reusable administrative entry point and then leaves. One tool performs the
  whole sequence with built-in utilities: it creates a local account whose name ends in a dollar sign so
  it reads as a machine account, sets a hardcoded password that never expires, adds it to the local
  Administrators group, and writes the registry value that hides it from the Windows logon interface. It
  then sets LocalAccountTokenFilterPolicy to 1 so that remote connections authenticating with a local
  administrator account keep full privileges, forces the LanmanServer and LanmanWorkstation services to
  automatic and starts them, and adds an inbound firewall rule permitting TCP 445 on every profile - under
  a rule name borrowed from a Windows application so it survives a glance at the firewall list. Every step
  is a one-line command, so the detection is the sequence on one host inside a few minutes, and the
  durable artefacts are the hidden account, the token-filter value, and the oddly-named firewall rule.

false_positive_notes: |
  Every command here is a legitimate administrative action, and several of the end states exist deliberately in real environments, so the hunt keys on the combination, the naming, and the absence of a change record.
  - Local administrator accounts are created legitimately by imaging, by break-glass processes and by some management tooling. The discriminators are the dollar-suffixed name, the group addition in the same minute, and the registry hide; an account created by a provisioning process does not also get hidden from the logon screen.
  - A dollar suffix on an account name is not exclusively malicious. Service and application accounts occasionally use it, and genuine computer accounts end in a dollar sign by design. The check is for a dollar-suffixed entry in the local SAM that is a user account and a member of local Administrators, which is a much narrower population.
  - LocalAccountTokenFilterPolicy is set to 1 deliberately in environments that need remote administration with local accounts - some backup products, some management frameworks and many lab environments require it. Where it is set by policy or by a documented build, record that; the finding is a change to the value on a host where the build does not set it.
  - LanmanServer and LanmanWorkstation are running on most Windows hosts already, so the service commands will be no-ops in the majority of cases and will not generate a start-type change. Treat the service element as corroboration only, and do not build the hunt on it.
  - Firewall rules permitting 445 inbound are normal on file servers and domain controllers. The anomaly is a rule with a plausible-but-wrong name on a host that has no file-sharing role, added outside change control, with the profile set to every profile including public.
  - Administrators do all of this during genuine troubleshooting, particularly on a host that has lost domain trust. Correlate against change records and against whether an RDP session from an unexpected source preceded the sequence; the tool runs the whole set in seconds, where a human doing the same work leaves minutes of unrelated activity between steps.
notes: |
  Source reporting is Check Point Research's November 10, 2026 report on CopperDragon, which it assesses as a possible digital quartermaster supplying the Sparrow framework to several China-nexus actors. This tool belongs to the OceanGate cluster, which CPR reports targeting government organizations and critical infrastructure primarily in Asia during 2025 and 2026. The access route into Windows is reported plainly: after harvesting credentials on the Linux side, "the actor attempted to log in to several Windows machines over RDP, trying different passwords until it successfully authenticated with an administrator account." The passive Windows implant from the same report is covered in [[H479]].
  What the tool does, as CPR describes it - "CopperAdu is a post-exploitation tool that configures a compromised Windows host for remote administrative access, preparing it for further attacker activity. It creates a local account with hardcoded credentials, disables password expiration, and adds the account to the local Administrators group. It also modifies the registry to hide the account from the standard Windows logon interface. The tool sets LocalAccountTokenFilterPolicy to 1, allowing remote connections using local administrator accounts to retain full administrative privileges and facilitating lateral movement. Finally, CopperAdu enables the LanmanServer and LanmanWorkstation services and configures an inbound Windows Firewall rule to allow SMB traffic on TCP port 445."
  The commands, as published - CPR gives the full set. The account work is `net user admin$ "Admin@123456" /add /expires:never /passwordchg:no`, then `wmic useraccount where "Name='admin$'" set PasswordExpires=false`, then `net localgroup administrators admin$ /add`. The services are set with `sc config LanmanServer start= auto` and `sc start LanmanServer`, repeated for `LanmanWorkstation`. The firewall work is two commands: `netsh advfirewall firewall delete rule name = "RasiUwpApp"` followed by `netsh advfirewall firewall add rule name="RasiUwpApp" dir=in action=allow protocol=TCP localport=445 profile=any`. The delete-then-add is how the tool stays idempotent across repeated runs on the same host, and it means a failed delete in the log is as useful as a successful add.
  Closest existing HEARTH coverage - Grepped the corpus for LocalAccountTokenFilterPolicy and found no hunt referencing it at all. [[H479]] is the implant from the same report and the same clusters. [[B037]] baselines WinRM and winrs remote execution, which is the adjacent remote-administration baseline and a useful pairing because this configuration exists to make remote local-admin authentication work. Nothing in the corpus covers a hidden local administrator account or a masquerading firewall rule name.
  Core filter 1, the hidden account - The highest-value check and the one that persists after every process has exited. Two artefacts, and both are inventory questions rather than event questions. First, local accounts whose name ends in a dollar sign that are members of the local Administrators group. Second, any value under the Winlogon SpecialAccounts UserList key, which is the registry location that removes an account from the logon screen; on a normal host this key either does not exist or contains nothing an administrator put there deliberately. Collect both across the estate on a schedule. Triage values are the account name, its creation time, its group memberships, whether its password is set never to expire, and its last logon time and source.
  Core filter 2, the token-filter value - Hunt registry writes setting `LocalAccountTokenFilterPolicy` to 1 under the Policies System key, and separately inventory its current value on every host. CPR explains the purpose exactly: it allows "remote connections using local administrator accounts to retain full administrative privileges". Without it, remote authentication with a local administrator account is stripped to a filtered token and the account is much less useful, so this value is what converts the created account from a nuisance into a working lateral-movement credential. A host where the value is 1 and the build does not set it is a strong finding on its own.
  Core filter 3, the firewall rule name - The cheapest high-signal check in the hunt. Inventory inbound firewall rules permitting TCP 445 and compare the rule names against the set your build and your management tooling create. CPR reports the name `RasiUwpApp`, which is close enough to a real Windows component name to pass a glance and specific enough to search for directly. The durable version of the check is name-based reconciliation rather than that one string: a rule name that matches nothing in your build, on a host with no file-sharing role, with `profile=any`.
  Core filter 4, the sequence - Where process telemetry exists, the whole tool is visible as a short burst of built-in utilities on one host. Hunt for `net user` with `/add` and `/expires:never`, `net localgroup administrators` with `/add`, `netsh advfirewall firewall add rule` naming port 445, and `sc config` against the Lanman services, grouped by host within a few minutes. The grouping is what makes this specific: any one of those commands is a Tuesday, and all four inside two minutes is a tool.
  Sample Defender XDR query for the sequence, within the 30-day advanced hunting retention, with the window bounded so commands from different days cannot group:
  ```kusto
  let lookback = 30d;
  let window = 10m;
  DeviceProcessEvents
  | where Timestamp > ago(lookback)
  | where FileName in~ ("net.exe", "net1.exe", "netsh.exe", "sc.exe", "wmic.exe")
  | extend step = case(
        ProcessCommandLine has "user" and ProcessCommandLine has "/add",            "account_create",
        ProcessCommandLine has "localgroup" and ProcessCommandLine has "administ",  "admin_add",
        ProcessCommandLine has "advfirewall" and ProcessCommandLine has "445",      "firewall_445",
        ProcessCommandLine has "config" and ProcessCommandLine has_any ("LanmanServer", "LanmanWorkstation"), "smb_service",
        ProcessCommandLine has "PasswordExpires",                                   "password_never_expires",
        "other")
  | where step != "other"
  | summarize steps = make_set(step, 10),
              step_count = dcount(step),
              commands = make_list(ProcessCommandLine, 20),
              first_seen = min(Timestamp), last_seen = max(Timestamp)
            by DeviceName, bin(Timestamp, window)
  | where step_count >= 3
  | extend span_seconds = datetime_diff('second', last_seen, first_seen)
  | project first_seen, DeviceName, step_count, steps, span_seconds, commands
  | sort by step_count desc, first_seen desc
  ```
  Requiring three of the five steps rather than all five is deliberate: the Lanman service commands are frequently no-ops because the services are already running, and `wmic` is deprecated and may be absent on a current build, so a tool run can legitimately produce only three observable steps. Pair this with the inventory checks in filters 1 to 3, which do not depend on having had process telemetry on the host at the time.
  What the configuration was for, in this intrusion - CPR reports that after CopperAdu the actor deployed CopperList to collect a recursive file inventory staged for exfiltration, CopperLogger - a Raw Input keylogger registering a hidden window and capturing keystrokes, active window titles, process names and clipboard activity regardless of focus - and CopperLsa, which "collects credentials directly through the Windows authentication flow" by installing a custom LSA security package inside LSASS. Any hit on this hunt should be followed by a check of registered LSA security packages on the same host.
  Expected, not observed by Check Point - Whether the created account was ever used for an interactive or network logon in the reported environments, and from where. CPR documents the configuration the tool applies and its stated purpose, but does not report the subsequent authentications, so the last-logon element of filter 1 is a triage field rather than a reported observable.
  Scope - Windows servers and workstations reachable over RDP, and in particular any host where RDP is exposed to a network segment that an internet-facing Linux server can reach, which is the path CPR reports for this cluster. The three inventory checks - dollar-suffixed local admins, the SpecialAccounts UserList key, and inbound 445 rule names - are worth running estate-wide as a standing control rather than only in response to this report.

# H484

The account is called `admin$`.

That trailing dollar sign is doing real work. Computer accounts end in a dollar sign, so the name reads as machine rather than person, and it slides past a tired eye in an account list. Then a registry value under Winlogon's `SpecialAccounts\UserList` key removes it from the logon screen entirely, so it is not visible where most people would ever look.

It is in the local Administrators group. Its password is hardcoded and set never to expire.

Check Point found this in the OceanGate cluster of the CopperDragon ecosystem — a tool they call CopperAdu, run after the actor guessed its way into a Windows box over RDP. There is no implant in this part of the story. There is no malware on disk to hash. The whole thing is seven or eight commands using `net`, `wmic`, `sc` and `netsh`, and then the operator closes the session and goes away.

What they leave behind is a host that has been quietly converted into an entry point.

`LocalAccountTokenFilterPolicy` set to 1 is the piece that makes it useful. Without it, authenticating remotely as a local administrator gets you a filtered token and not much else. With it, the new account works over the network with full privileges. Then `LanmanServer` and `LanmanWorkstation` forced to automatic and started, and an inbound firewall rule opening TCP 445 on every profile.

That rule is named `RasiUwpApp`. Which sounds like something Windows ships. It is not.

So there are three things sitting on that host right now, and all three are inventory questions, not alert questions: a dollar-suffixed local admin, a registry value hiding it, and a firewall rule whose name matches nothing in your build.

## Why

- **Nothing here is malware, so there is nothing for the endpoint product to decide about.** Built-in utilities, legitimate registry values, a standard firewall rule. The operator traded capability for a configuration that persists on its own and needs no process running, which means the detection has to be a state check rather than a behavioural one.
- **The three artefacts outlive the session, and two of them are a single query each.** Dollar-suffixed local administrators and non-empty `SpecialAccounts\UserList` are both estate-wide questions with near-empty expected answers. That combination — cheap to ask, almost always zero — is the most valuable shape a hunt can have.
- **`LocalAccountTokenFilterPolicy` is the load-bearing step and nobody inventories it.** It is the difference between an account that exists and an account that works remotely with full rights. A grep across HEARTH finds no hunt that mentions it, and in most estates nobody can say which hosts have it set or why.
- **The firewall rule name is a masquerade aimed at a human reading a list.** It is plausible enough to skip over and distinctive enough to search for, and the general check — rule names that match nothing your build creates — keeps working after the name changes.
- **Hidden from the logon screen is not hidden from the API.** The registry hide defeats the interactive view and nothing else. `net localgroup administrators`, PowerShell's local-account cmdlets, and any management agent all still report the account, so the asymmetry favours whoever decides to look programmatically — which is the entire argument for doing it on a schedule.
