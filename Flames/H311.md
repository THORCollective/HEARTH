false_positive_notes: |
  The core conditions here are close to zero-noise, but each needs scoping so it is not dismissed on first run. The `x-owa-urlpostdata` header is genuinely non-standard for browser-driven OWA traffic, and a legitimate client has no reason to emit it — the practical caveat is that this header cannot be seen at all in default IIS logging, so an empty result is far more likely to mean the field is not being captured than that the header is absent. Confirm collection before concluding anything. On `__VIEWSTATE`, ordinary OWA and ECP do use ViewState, so volume alone is meaningless; the discriminators are size and validity. Legitimate ViewState on Exchange endpoints is bounded and MAC-valid, while a forged payload carrying a serialised object graph is substantially larger and, if machine keys have since been rotated, fails validation and produces a burst of HTTP 500 responses with ASP.NET ViewState MAC errors in the application event log. That failure burst is itself a finding, not noise. Genuine benign MAC failures do occur in two situations worth knowing in advance: a load-balanced farm whose members hold mismatched machineKey values, and clients resuming a stale session after an application pool recycle — both produce failures spread across many users and source addresses, where an attack produces them from one or a few addresses against a narrow set of endpoints. Finally, unexpected assembly loads into `w3wp.exe` are common on Exchange during normal patching and compilation, so scope that signal to assemblies backed by no file on disk or by a file outside the ASP.NET temporary directories, rather than to novelty alone.
notes: |
  Core filter, the header - search IIS request logs, WAF logs or reverse-proxy logs for requests carrying the header name `x-owa-urlpostdata`. This is the single highest-fidelity artefact in the chain and the one to stand up as a permanent detection. Note the prerequisite - stock IIS W3C logging records a fixed field set and does NOT capture arbitrary request headers, so this requires IIS Advanced Logging, a custom field configuration, or capture at the WAF/reverse proxy. If no telemetry records request header names on the Exchange path, treat closing that gap as the first output of this hunt.
  Core filter, the response marker - each command execution returns an XML-formatted response whose value element begins with the hardcoded string `/wEPDwUKLTcyODc4`. This string is inherited from the public `ExchangeCmdPy.py` CVE-2020-0688 tooling. Where response bodies are retained or inspectable, grep for it directly; it is a literal, fixed, high-confidence indicator.
  Core filter, the VIEWSTATE submission - in IIS logs, look for `POST` requests to OWA/ECP endpoints with unusually large `cs-bytes` relative to that endpoint's own baseline, especially where `cs-uri-query` or the body carries `__VIEWSTATE`. Pair with ASP.NET application event log entries for ViewState MAC validation failure (Event ID 1316 / `System.Web.HttpException` "Validation of viewstate MAC failed"), which is what a forged ViewState produces once keys no longer match. Cluster failures by `c-ip` - attack traffic concentrates on one or a few source addresses against a narrow endpoint set, while benign farm-mismatch failures spread across many users.
  In-memory loading and evasion - Sysmon Event ID 7 / `DeviceImageLoadEvents` for .NET assemblies loaded into `w3wp.exe` that are not backed by a file on disk or that sit outside the ASP.NET temporary compilation directories. The reported implant was cloaked under the assembly name `App_Web_Container_1.dll`, with internal classes `Stub`, `App_Web_843e75cf5b63` (virtual path redirection) and `App_Web_8c9b251fb5b3` (traffic proxying). The `Stub` class patches `amsi.dll` and `ntdll.dll` in memory to blind AMSI and the Windows Event Log, so a sudden cessation of ETW/event-log output from `w3wp.exe` on a server that is still serving traffic is a corroborating anomaly in its own right - hunt for the SILENCE, not only for the write.
  Impersonation behaviour - the implant checks whether it is running as a system account and, if not, impersonates a user via a token held in the application domain's data store. Correlate Security event 4624 logon type 9 (NewCredentials) and 4648 (explicit credential logon) originating from `w3wp.exe` on Exchange hosts.
  Remediation pivot that doubles as scoping - because the entry point is the stolen `machineKey`, patching does not evict the actor. Inventory `validationKey` and `decryptionKey` across every Exchange server and record the last rotation date; any server whose keys predate a suspected compromise is still exposed regardless of patch level, and rotating them is what actually closes the door.
  Triage values - `c-ip`, `cs-username`, `cs-uri-stem`, `cs-bytes`, `sc-status`, `cs(User-Agent)`, request header names, and the loading module list for `w3wp.exe`.

# H311

Kaspersky first documented GhostContainer as a .NET backdoor on Exchange servers in Asia, then tracked the same implant into a campaign against Russian organisations attributed to NightEagle. Its delivery is what makes it worth a dedicated hunt: rather than dropping a web shell, the operators extract the ASP.NET cryptographic keys from Exchange's own configuration, forge a `__VIEWSTATE` parameter containing a serialised payload, and let ASP.NET deserialise the backdoor into memory for them. From that point the implant is entirely passive — it holds no outbound connection and contacts no C2 server. Commands arrive on the `x-owa-urlpostdata` header of ordinary-looking requests, Base64-encoded and AES-encrypted under a key derived from the same stolen validation key, and it answers in-band. Kaspersky found no external C2 infrastructure to attribute, because there is none. The implant is assembled from public parts — Neo-reGeorg for proxying, a CVE-2020-0688 exploit, `ysoserial`'s GhostWebShell — and it patches `amsi.dll` and `ntdll.dll` in memory to blind AMSI and the Windows Event Log on the way in.

## Why

- **Passive backdoors invert the usual detection strategy and most stacks are not configured for it.** Every control premised on finding outbound C2 — beacon analysis, DNS reputation, egress anomaly detection — has nothing to score against an implant that only ever answers inbound requests. The evidence exists only in inbound web telemetry, which is exactly the telemetry most Exchange deployments log least carefully.
- **The header name is a literal, durable, zero-ambiguity indicator, and hunting for it audits the logging gap.** Legitimate OWA clients never send `x-owa-urlpostdata`. The catch is that default IIS W3C logging cannot record arbitrary header names at all, so a clean result is usually a statement about collection rather than about compromise — which makes this hunt valuable even when it finds nothing, because it forces that gap into the open.
- **Stolen machine keys survive patching, so the exposure window is defined by key rotation, not by update status.** An organisation that patched Exchange but never rotated `validationKey`/`decryptionKey` after a suspected intrusion remains trivially re-exploitable by anyone holding the old keys. Inventorying key age across the Exchange estate converts an unanswerable question into a list.
- **Deliberate blinding leaves its own signature.** The implant patches AMSI and the event log in-process, so the absence of expected ETW and Defender telemetry from a `w3wp.exe` that is demonstrably still serving requests is itself anomalous. Hunting for the silence catches the technique even when every positive indicator has been rotated away.
