  Remove the malware from a malware delivery chain and most of the detection stack has nothing to say.
  Huntress investigated an incident beginning with a lookalike WatchGuard VPN download site,
  `watchguard-vpn[.]net`, reached from a search for "watchguard vpn sll download". The page presented a
  pop-up asking for Server, Login and Password - the same three values the real client asks for - and

  for the pairing rather than for either half: a browser navigation chain through a lookalike vendor
  domain, an outbound POST to a second unrelated domain, and a download of a legitimately signed vendor
  installer from the real vendor CDN with the lookalike as the referring site.

false_positive_notes: |
  Every component of this chain is individually benign, which is the point and also the difficulty.
  Employees legitimately search for VPN client downloads, legitimately download signed vendor
  installers, and legitimately type VPN server addresses and credentials into clients - so neither the
  download nor the credential entry is a finding. The signed installer in particular will pass every
  check applied to it, because it genuinely is the vendor's file: Huntress recomputed the Authenticode
  digest and confirmed "the binary has not been modified since WatchGuard signed it". Hash reputation,
  signature validation and sandbox detonation all return clean, correctly. The discriminator is
  therefore the navigation and POST context around the download, not the file. Expect benign noise from
  three places. Software download portals and mirrors legitimately sit between a search and a vendor
  CDN, so a referrer that is not the vendor's own site is suspicious rather than conclusive - build the
  allowlist of sanctioned internal and reseller download paths first. Vendor marketing and tracking
  domains generate POSTs to hosts unrelated to the download, which look structurally similar to a
  credential submission; filter on the browser process and the proximity to a credential-shaped form
  rather than on the POST alone. And typo-prone searching is extremely common, so arriving at a
  misspelled domain is not itself evidence of compromise. The strongest low-noise signal available is
  domain novelty paired with the vendor's brand in the hostname, which is cheap to compute and rarely
  wrong.

  delivers a fake client that harvests credentials and often sideloads a malicious DLL - Huntress notes
  Microsoft attributed a wider iteration of this campaign to Storm-2561 and describes that chain as
  "delivering a signed, fake MSI that sideloads malicious DLLs, harvesting credentials typed into a fake

  captured in the browser, and the only file that reaches the endpoint is the vendor's own. Huntress's
  summary of the consequence is the operative one: "there is no malicious file for endpoint security
  tools to flag".
  The lure, and why it is classified as search poisoning rather than advertising. An administrator
  searched Bing for "watchguard vpn sll download" - a typo - and, per the report, "Eight seconds later,
  they clicked through to www.watchguard-vpn[.]net, a page titled "WatchGuard Firebox VPN Client"". The
  click went through the standard Bing result redirect with the destination in the `u=` parameter;
  decoding that parameter gives exactly the lookalike URL, which is consistent with an organic search
  result rather than an ad. Huntress states this "supports classifying the lure as SEO poisoning rather
  than malvertising", and notes Secplicity and Microsoft describe related activity the same way.
  The capture, which is ordinary JavaScript. Huntress describes the logic as living in "a single file,
  popup.js, about 150 lines of plain, unobfuscated JavaScript", presenting a prompt reading "To install
  WatchGuard SSL VPN, please enter your connection details" and asking for Server, Login and Password.
  The Server field is the detail worth noting: it hands the operator the address to authenticate
  against, so the stolen credential arrives with its target attached. Submissions are posted as JSON to
  `watchguard-ssl[.]online` with a tag marking whether it is the first or second attempt, and the fetch
  is wrapped so that a failure logs only a console warning - the user sees nothing either way.
  The double submission, which is a deliberate yield optimisation. The script rejects the first attempt
  and replaces the header with red text reading "Incorrect data, please enter again to start
  installation", then sets the attempt counter to 2. Huntress explains the reasoning: "Anyone who
  mistyped their passwords will now type more carefully, and anyone unsure which of their passwords
  applies is likely to try the other one, so the attacker gets a second set of credentials to validate
  against". For a defender with proxy visibility this is useful, because it produces two POSTs to the
  same endpoint seconds apart from one browser session - a shape ordinary form submission rarely has.
  The payload, and what makes it unflaggable. After the second submission the script creates a hidden
  link to `https://cdn.watchguard.com/SoftwareCenter/Files/MUVPN_SSL/12_11_5/WG-MVPN-SSL_12_11_5.exe`

  client, version 12.11.5, carrying "an Authenticode signature from WatchGuard Technologies, Inc.,
  issued by Sectigo Public Code Signing CA R36, with a countersignature timestamp of 4 November 2025",
  and confirms the recomputed digest matches the signature. The report gives the digest only in
  truncated form, so it is not reproduced here as an indicator.

  "the browser history actually recorded no download from cdn.watchguard.com for the timeframe in
  question", which suggests the user did not complete both rounds "although they may have entered their
  credentials in the first round". Huntress Managed Defender flagged the incident 21 seconds after the
  malicious domain loaded. So the download leg is documented from the script rather than from observed
  endpoint activity in this victim - a hunt relying solely on the CDN download would not have caught
  this instance, which is an argument for keying on the navigation and POST legs.

  `let vendorBrands = dynamic(["watchguard", "fortinet", "sonicwall", "sophos", "globalprotect", "pulsesecure", "ivanti", "citrix"]); DeviceNetworkEvents | where Timestamp > ago(30d) | where InitiatingProcessFileName in~ ("chrome.exe", "msedge.exe", "firefox.exe", "brave.exe") | where isnotempty(RemoteUrl) | extend Host = tostring(parse_url(RemoteUrl).Host) | where Host has_any (vendorBrands) | where not(Host endswith ".watchguard.com" or Host endswith ".fortinet.com" or Host endswith ".sonicwall.com" or Host endswith ".sophos.com" or Host endswith ".ivanti.com" or Host endswith ".citrix.com") | summarize Hits = count(), FirstSeen = min(Timestamp), Urls = make_set(RemoteUrl, 10) by DeviceName, Host, InitiatingProcessFileName | order by FirstSeen desc`

# H407

Take the malware out of a malware delivery chain, and most of a security stack has nothing left to look at.

An administrator searched Bing for "watchguard vpn sll download" — note the typo — and eight seconds later landed on `watchguard-vpn[.]net`, a page titled "WatchGuard Firebox VPN Client." Clicking download produced a pop-up: "To install WatchGuard SSL VPN, please enter your connection details." Server, Login, Password.

Which is exactly what the real client asks for. That is why it works.

The three fields went as JSON to a second domain, `watchguard-ssl[.]online`. And then the interesting part, in Huntress's words: "the site then downloads the genuine, validly signed WatchGuard installer directly from WatchGuard's own content delivery network (CDN), meaning there is no malicious file for endpoint security tools to flag."

Not a trojanised installer. Not a signed-but-fake MSI sideloading a DLL. The actual file, from `cdn.watchguard.com`, which Huntress verified by recomputing the Authenticode digest — "the binary has not been modified since WatchGuard signed it."

So the victim installs a working VPN client. Everything behaves correctly. Hash reputation: clean. Signature validation: valid, WatchGuard Technologies, Sectigo CA. Sandbox detonation: a VPN client installs. All of those answers are *correct*, and all of them are useless, because the theft already happened in the browser.

There is a detail in the credential prompt worth pausing on. The **Server** field. The operator does not just get a username and password — they get the address to use them against. The credential arrives with its target attached.

And the script deliberately rejects the first submission. It clears the fields and turns the header red: "Incorrect data, please enter again to start installation". Huntress explains the thinking: "Anyone who mistyped their passwords will now type more carefully, and anyone unsure which of their passwords applies is likely to try the other one, so the attacker gets a second set of credentials to validate against."

A yield optimisation. It is also a gift to anyone with proxy visibility, because it produces two POSTs to the same endpoint seconds apart in one browser session — a shape ordinary form submission rarely has.

Now, how should this actually be hunted? Not on the file, which is genuine. Not on the credential entry, which is normal. On the *pairing*: a navigation through a brand-lookalike domain, a POST to a different domain, and a vendor-CDN download sitting between them.

One honest caveat about scope, because it changes which query matters. In the incident Huntress investigated, "the browser history actually recorded no download from cdn.watchguard.com for the timeframe in question" — the user probably never completed the second round, though they may have submitted the first. Managed Defender flagged it 21 seconds after the domain loaded. So the download leg is documented from reading the script, not from observed activity on this victim. A hunt keyed only on the CDN download would have missed this case entirely. Key on the navigation and the POST.

The cheapest high-yield query here needs no correlation at all: browser connections to hostnames that carry a vendor's brand but are not that vendor's domains. `watchguard-vpn[.]net` fails that test instantly, as would the F5, Fortinet, SonicWall and Sophos lookalikes from the same broader campaign. Pair it with domain-age enrichment — both domains here were registered weeks before use, and Huntress notes detection was thin: "Only seven VirusTotal vendors flagged the lure domain, and two flagged the collector, with no AbuseIPDB reports against either IP."

Then remember what the credential is for. It is a VPN credential with its server address. The next event is an authentication to your appliance from infrastructure you do not use. Huntress's guidance is to "Monitor for SSL VPN logins from hosting providers, unfamiliar ASNs, or countries where the account has never connected from", and to treat that VPN endpoint as known to the attacker. Knowing which sources each account legitimately uses is [[B021]]'s job — run it alongside this.

## Why

- **There is no malicious file at any point.** The delivered installer is the vendor's own signed binary, so hash reputation, signature validation and detonation all return clean and correct answers while the credentials are already gone.
- **The theft happens in the browser, before anything touches disk.** Endpoint controls positioned around file execution are structurally on the wrong side of this chain.
- **The credential arrives with its target.** Capturing the Server field alongside the username and password hands the operator a specific appliance to authenticate against, with no discovery required.
- **The victim experience is indistinguishable from success.** A real client installs and works, which removes the user-reported oddity that normally starts an investigation.
- **The forced retry is both a yield tactic and a detectable artefact.** Two submissions seconds apart from one session is a shape legitimate forms rarely produce, and it is visible in proxy logs.
- **Brand-in-hostname plus domain novelty is cheap and rarely wrong.** It needs no correlation, no payload and no prior knowledge of the campaign, and it would have flagged this domain and its F5, Fortinet, SonicWall and Sophos siblings.
- **The download leg was not observed on the victim.** A detection built solely on the vendor-CDN fetch would have missed this incident, which is why the navigation and POST legs carry the hunt.
- **Search results are the delivery vehicle, so email controls never engage.** A typo in a search box replaced the phishing email entirely, bypassing every mail-layer defence.
- **The impact lands on the appliance, not the endpoint.** Remediation is credential reset plus treating the VPN endpoint as compromised, and the follow-on authentication is where this becomes an intrusion.
