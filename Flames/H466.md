title: "A managed loader planted in the .NET native image cache and in the WMI provider directory runs native code inside a signed non-.NET service before any managed code executes, then forwards calls so the host process keeps working"
hypothesis: >-
  An operator who wants code running inside a trusted Windows service does not inject into it. They put a file where that service's own loader will fetch it: a forwarding DLL in the WMI provider directory under the name of a real provider library, and a precompiled-assembly file in the framework's native image cache under the name of a library the target application requests. Both files are managed assemblies, but their entry point is reached through a rarely used specification feature that runs unmanaged code before the runtime executes anything a decompiler will show. The payload has already run by the time managed execution begins, and because the file forwards or falls back to the genuine implementation, the host service continues to operate normally and nothing visibly fails. The observable chain is a write to the WMI provider directory or the native image cache by a process that is not the installer or the framework's own compiler, a file at those paths that no installed package owns, and a signed service process loading an unsigned module from one of them.

false_positive_notes: |
  Both directories are legitimately written by the operating system and by application installers, so the hunt turns entirely on provenance rather than on the fact of a write.
  - The native image cache exists to be written to. The framework's own ahead-of-time compiler populates it during installation, servicing and scheduled maintenance, and a monthly patch cycle produces large bursts of writes across the whole cache. Correlate against the compiler process and against patch windows; the candidate population is a write by something that is not the framework compiler or an installer.
  - The WMI provider directory is a normal install target. Products legitimately drop provider libraries there, and the directory contains dozens of Microsoft-signed files on a default build. The discriminator is signature status and package ownership, not presence.
  - Signed does not mean trusted here and unsigned does not mean malicious. Legitimate third-party providers are sometimes unsigned on older builds, and some in-house management tooling drops unsigned libraries deliberately. Build the per-host inventory first and treat deviation from it as the finding.
  - Forwarding DLLs are a legitimate engineering pattern. Shims, compatibility layers and some instrumentation products export forwarders on purpose. On its own a forwarder is uninteresting; a forwarder at one of these two specific paths, unowned by any package, is the finding.
  - Image-load volume in these directories is large on a busy server. An Exchange or WMI-heavy host loads from them continuously, so a query returning every load will return thousands of rows. Filter to unsigned or unexpected-signer modules before anything else, which cuts the population to something a human can read.
  - A decompiler showing nothing is not evidence of innocence, and it is also not evidence of guilt. Plenty of legitimate assemblies have trivial entry points. The check that matters during triage is whether the file carries a Vtable Fixups directory at all, which is rare enough in benign software to be decisive.
notes: |
  Source reporting is ESET Research's November 13, 2026 analysis of the Cereal toolset, attributed to Turla, observed in two national governmental organizations. This hunt covers CerealLoader, the only component ESET found written to disk in unencrypted form. The companion hunts from the same intrusion are [[H467]], which covers the in-memory hooking of the Exchange transport pipeline, and [[H468]], which covers the passive backdoor that uses the victim Exchange server as the control point. No existing hunt references the native image cache or the WMI provider directory by name; the nearest in mechanism are [[H375]] and [[H266]], which cover on-host compilation rather than loader placement.
  Why the loader is the detectable component - ESET describes the toolset's design principles as keeping payloads encrypted, keeping execution in memory, reusing the compromised Exchange server, and delivering commands as separate .NET assemblies. CerealLoader is the exception: ESET states it "is the only component in the toolset that is written to disk as a recognizable .NET file", because something has to start the chain. That makes it the one place where file-system telemetry has anything to work with, and it is why this hunt targets placement rather than behaviour.
  The mechanism, and why static analysis misses it - ESET reports that in a .NET decompiler "the entry point code does essentially nothing, and a breakpoint set on the malicious method is never triggered", because the loader "abuses a rarely used feature of the .NET specification, Vtable Fixups, to build a hidden bridge from native code back into a .NET method that no other part of the program appears to call". The consequence for triage is specific: a reviewer who opens the file in a managed decompiler and sees an empty entry point has not cleared it. The check that answers the question is whether the PE carries a Vtable Fixups directory, which is the 10th data directory in the COR20 header and is almost never present in ordinary managed assemblies. Any PE-parsing tool that prints the CLR header directories will show it.
  Core filter 1, the WMI provider directory - ESET reports that "in one execution chain, CerealLoader was placed as ncobjapi.dll inside C:\Windows\System32\wbem\, where the Windows Management Instrumentation service loaded it automatically", and that "in another, it impersonated wbemcomn.dll in the same folder". Both names are real library names, which is the point of placing them there. Note that `wbemcomn.dll` hijacking in this directory is a publicly documented technique with existing detection coverage; the addition here is the second name and the loader's managed-with-native-entry construction. Hunt for creates, modifies and renames in the provider directory where the writing process is not an installer or servicing process, and for any file there that no installed package claims.
  Core filter 2, the native image cache - The more novel of the two placements. ESET reports the operators "placed malicious CerealLoader files in this cache, using names such as Microsoft.Exchange.Search.Mdb.ni.dll", and explains the fallback behaviour that keeps the host working: "Because the malicious file contains no real replacement code, .NET quietly falls back to the genuine library for actual functionality". ESET adds that "in one sample, the malicious code only activates when the parent process is Exchange's search service", which is a conditional-execution check worth knowing during analysis, because the sample will look inert when run anywhere else. Hunt the cache for assembly names belonging to applications on the host, written by something other than the framework compiler, and unowned by any package. Sample Defender XDR query:
  ```kql
  let lookback = 30d;
  let frameworkWriters = dynamic(["ngen.exe", "mscorsvw.exe", "crossgen.exe", "crossgen2.exe",
                                  "trustedinstaller.exe", "tiworker.exe", "msiexec.exe"]);
  DeviceFileEvents
  | where Timestamp > ago(lookback)
  | where ActionType in ("FileCreated", "FileModified", "FileRenamed")
  | where FolderPath has @"\assembly\NativeImages" or FolderPath has @"\System32\wbem"
  | where not(InitiatingProcessFileName in~ (frameworkWriters))
  | project Timestamp, DeviceId, DeviceName, FileName, FolderPath, SHA256,
            InitiatingProcessFileName, InitiatingProcessCommandLine,
            InitiatingProcessParentFileName, InitiatingProcessAccountName
  | order by Timestamp desc
  ```
  Keep the lookback at `ago(30d)` or less, because Defender XDR advanced hunting retains 30 days and silently truncates a longer window. Fill the writer allowlist from the host build rather than from this example. Triage values are the written path, the file hash, the writing process and its parent, and the account.
  Core filter 3, what the service loaded - The write may predate the retention window, so check the load as well as the create. Hunt Sysmon Event ID 7 for modules loaded by the WMI service and by the target application services where the module path is the provider directory or the native image cache and the signature is absent or the signer is unexpected. Note that `DeviceImageLoadEvents` carries no signature columns, so a Defender-only environment must join `DeviceFileCertificateInfo` on SHA1 to get signer and signature status - a query that filters on a signature field in the image-load table will silently return nothing.
  Core filter 4, the host-side inventory check - The cheapest reliable discriminator, and the one that settles a case. Both directories should contain only files owned by an installed product. A shell check for triage, run under an elevated prompt:
  ```powershell
  $paths = @("$env:SystemRoot\System32\wbem", "$env:SystemRoot\assembly\NativeImages_v4.0.30319_64")
  foreach ($p in $paths) {
    if (-not (Test-Path $p)) { continue }
    Get-ChildItem -Path $p -Recurse -Include *.dll -ErrorAction SilentlyContinue |
      ForEach-Object {
        $sig = Get-AuthenticodeSignature -FilePath $_.FullName
        [pscustomobject]@{
          Path       = $_.FullName
          Written    = $_.LastWriteTime
          SizeBytes  = $_.Length
          SigStatus  = $sig.Status
          Signer     = $sig.SignerCertificate.Subject
        }
      } | Where-Object { $_.SigStatus -ne 'Valid' } | Format-Table -AutoSize
  }
  ```
  The native image cache directory name carries the framework version and architecture, so enumerate the actual directories under the assembly path on the host rather than relying on the one named here. A file in either location whose signature does not validate is the row to pull for analysis.
  Triage of a candidate file - Three questions in order. Does an installed package own the path. Does the PE carry a Vtable Fixups directory. Does the assembly export or forward the functions the host process expects, which is what let the service keep running. ESET notes of the provider-directory case that "the malicious DLL forwards legitimate function calls, so the affected process continues to operate normally" - so the absence of any application error or crash is expected and is not reassurance.
  Scope - Exchange servers first, because that is where this toolset was found and because the cache entry was named for an Exchange library, but the two placements are not Exchange-specific. The WMI provider directory exists on every Windows host, and the native image cache exists wherever the framework is installed, so the inventory check is worth running estate-wide on servers once the Exchange population is clear.

# H466

Everything else in this toolset was encrypted. This one file was not, because something has to go first.

ESET found CerealLoader, the only Cereal component written to disk as a recognisable .NET file. Open it in a decompiler and the entry point does essentially nothing. Set a breakpoint on the malicious method and it never fires.

The reason is a corner of the .NET specification almost nobody uses. Vtable Fixups let a managed assembly run unmanaged code and call back into a managed method that nothing in the program appears to reference. By the time the runtime starts executing the instructions an analyst can read, the payload has already run.

That capability is what makes the file placement interesting, because a .NET assembly that bootstraps from native code can be dropped anywhere a non-.NET process will load it. The operators used two such places.

The first is `C:\Windows\System32\wbem\`, under the name `ncobjapi.dll` in one chain and `wbemcomn.dll` in another. The WMI service loads from that directory automatically. The malicious DLL forwards the real function calls, so WMI keeps working and nothing breaks.

The second is the .NET native image cache — the folder of precompiled assemblies the runtime checks before compiling anything itself. The operators put files there named for libraries Exchange asks for, such as `Microsoft.Exchange.Search.Mdb.ni.dll`. When Exchange requested the library, the runtime handed over the malicious version. It contains no replacement code, so .NET quietly falls back to the genuine library for the actual work — but only after the native entry point has run. One sample would not even activate unless its parent process was the Exchange search service.

No injection. No crash. No error. Just a file in a directory that a trusted service was always going to read.

## Why

- **Static review of the file clears it, incorrectly.** An empty managed entry point is exactly what an analyst expects from a benign stub, and a decompiler will not show the native bridge. That inverts the normal triage intuition, and it means the question to ask about a candidate file is structural — does it carry a Vtable Fixups directory — rather than behavioural.
- **Both directories are read by processes that are signed, long-running and above suspicion.** The WMI service and Exchange are not going to be flagged for loading a library from a path they are supposed to load libraries from. The trust being abused belongs to the loader, not to the payload, which is why image-load telemetry with signer information matters more here than process telemetry.
- **The forwarding and fallback behaviour removes the usual tell.** Most DLL hijacks break something eventually, and a broken service is how they get noticed. Here the genuine implementation still services every call, so the host process behaves correctly indefinitely. Absence of errors is not evidence of absence.
- **The native image cache is a persistence surface almost nobody inventories.** Administrators know about Run keys, services, scheduled tasks and the WMI directory. A folder of precompiled assemblies is widely treated as a performance implementation detail, and a file planted there is both durable and invisible to every persistence-enumeration tool that does not know to look.
- **Provenance is a cheap and near-decisive check, which is the practical takeaway.** Both of these directories should contain only files that an installed product put there. Listing them and testing each signature takes a minute per host and converts an exotic .NET technique into an ordinary inventory question.
