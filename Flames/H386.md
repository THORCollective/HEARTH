# H386

Nobody cleared the log. That is the point.

The payload Volexity recovered from the compromised Ivanti appliance reads `/home/runtime/dlogs/debuglog` and `/var/log/audit/audit.log`, filters out the entries that fall inside a chosen time window, and writes the file back with everything else intact. Months of history survive. The size looks right. The most recent entries are recent. Only the operator's own window is missing.

Every check that asks "was this log cleared?" returns no, correctly. An integrity checker that hashes the file sees a change, but log files change every second, so that tells you nothing. The log looks like a log.

What is left to find is the hole. A period with no entries, bounded on both sides by normal density, in a file that is otherwise continuous. And, more usefully, a disagreement: entries that reached the SIEM before the edit and are no longer in the file on the box. The attacker had root and could rewrite anything on the appliance. They could not rewrite what had already left it.

That asymmetry is the hunt. Mandiant, writing about a different appliance compromise the same month, reached the same conclusion from the other direction — forward appliance syslog to a SIEM over TLS with multi-month retention, because an attacker with host access can delete on-appliance logs. The forwarded copy is the control sample.

Rotation is the thing that will waste your time, and it deserves to be designed out rather than explained away. Rotation shrinks files to nothing, changes inodes, and leaves gaps in the live file. So does a firmware upgrade. So does an appliance truncating its own logs under disk pressure. On the SIEM side, a collector restart or an expired TLS certificate leaves a hole that looks identical to tampering. A gap that appears across many appliances at the same moment is infrastructure, not an intrusion. Check the rotation schedule, the rotated siblings and the collector's connection state first — then what remains is narrow and genuinely interesting.

Two more things from the report are worth carrying into any investigation that starts here.

The cleanup was broad but not necessarily complete. Volexity says so explicitly: the capabilities are confirmed in the recovered code, but how much of it actually succeeded on the appliance "has not been fully established." Partial cleanup is where evidence lives. Look for the artefacts the payload *tried* to remove — `/home/runtime/tmp/ics-root-run-inband-*.pl`, `/home/runtime/tmp/ics-root-result-inband-*`, `/tmp/rq5.py`, `/tmp/rr.py`.

And the disk was never the place to look. The privilege escalation patched a library in memory and restored the byte afterwards through `/proc/self/mem`, leaving the on-disk library untouched. Volexity found the sniffer, its capture files and the exploit components in memory, after the disk had been curated. So a confirmed gap in a log should lead to memory acquisition before anyone reboots the device — not to a clean Integrity Checker result, which this chain produces by design.

## Why

- **Selective rewriting defeats every "was the log cleared" check, by construction.** The file retains its history, a plausible size and recent entries. Absence of a cleared-log alert is not evidence of an untampered log.
- **The forwarded copy is the one version the attacker could not edit.** Comparing what reached the SIEM against what remains on the appliance turns an anti-forensics problem into a set difference.
- **A gap bounded by normal density is a distinctive shape.** Wholesale deletion removes everything; this removes a window. The signature is continuity on both sides of silence, which rotation and upgrades do not reproduce.
- **The appliance is the one host with no EDR and attacker-controlled logs.** That combination is exactly why the detection has to be built on forwarded telemetry and scheduled metadata snapshots rather than on anything the box says about itself.
- **Cleanup was probably incomplete, and the report says so.** Volexity declines to claim every operation succeeded, which means the named temporary files and helper scripts are worth hunting for directly on an image.
- **Ivanti's Integrity Checker Tool cannot answer this.** The chain patched memory only and restored the configuration store, so on-disk integrity verification reports no modifications on a compromised appliance.
- **Benign explanations are enumerable, which makes the hunt tractable.** Rotation, upgrade, disk-pressure truncation, collector outage and genuine quiet hours are a short and checkable list, and ruling them out leaves a small residue.
- **Capture rotation destroyed evidence as a side effect.** The attacker's own eight rotating packet-capture files overwrote earlier traffic, so time matters: the longer the delay before acquisition, the less there is to recover.
- **The same gap signal scales to the whole estate.** Per-appliance silence modelling in [[M059]] finds candidates across every forwarded log source, and this hunt is what confirms one.
