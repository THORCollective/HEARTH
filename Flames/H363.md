false_positive_notes: |
  `HKCU\Software\Classes` is one of the busiest parts of the registry. Every application install, every per-user file association, every "open with" choice and every Office or browser update writes there, and a typical user hive holds hundreds of `.ext` subkeys. Flagging writes to the hive is useless. Three narrowings make this tractable. First, fleet rarity - a file extension that appears on one host in the estate and nowhere else is anomalous regardless of what it contains, and the inventory needed to compute that is a single registry enumeration per host. Second, structural correctness - a legitimate extension key's default value is a ProgID string (`txtfile`, `Word.Document.12`, `AcroExch.Document.DC`), short, printable, and matched by a corresponding ProgID key elsewhere in the hive. A value that is long, high-entropy, base64 or binary, or a default value that points at no existing ProgID, is malformed by the operating system's own schema. Third, correspondence to reality - a registered extension with no matching application and no file of that type anywhere on the host is a registration for nothing. Genuine confounders exist - some line-of-business and engineering applications register obscure extensions, and a few installers write orphaned keys and never clean them up. Those are identifiable because the extension recurs across the hosts running that application. A one-host, one-key, high-entropy value is not that.
notes: |
  Platform: Windows. Driven by Microsoft Threat Intelligence, "Star Blizzard refines phishing and malware delivery with the RedFlick technique" (29 September 2026), which lists `HKEY_CURRENT_USER\Software\Classes\.mollis` among the campaign's artefacts, used for encrypted AES key storage. The campaign's chain also includes the scheduled-task and Control Panel applet persistence hunted in [[H362]], the `ssh.exe PermitLocalCommand` delivery step covered by [[H257]], and the CosmicPulse Python backdoor that retrieves encrypted payloads executed through a Python bootstrapper. The key material is what ties those stages together - the backdoor's downloaded payloads are encrypted, so the key has to live somewhere the operator can rely on finding again across reboots without leaving a file on disk. Microsoft published no ATT&CK mapping for this artefact; the mappings here are assigned. Microsoft published hunting queries for the scheduled-task names and ASIM queries for the network indicators, but none for this registry artefact; the queries below are derived.
  Why this hiding place works - A file-extension class key is an unusually good container for a secret. It is writable by a standard user with no elevation. It is in a hive so densely populated that one more key is invisible to inspection by eye. It survives reboots and user logoff. It has no association with malware in any analyst's mental model, because the key type exists to tell Explorer which icon to draw. And critically, the value's presence does not require the malware to be running or installed - the payload binary can be deleted entirely and the key remains, which means a responder who removes the executable and declares the host clean leaves the operator's key in place.
  Fleet-rarity leg (primary, and the most durable form) - Enumerate `HKCU\Software\Classes\.*` and `HKCU\Software\Classes\` ProgIDs across the estate, then rank each extension by how many hosts carry it. The result is overwhelmingly a long tail of legitimate, widely-shared extensions and a short head of genuine one-offs. Triage the one-offs by - does any file with that extension exist on the host; does the default value name a ProgID that exists; is the value data printable and short; and which process wrote it. `.mollis` is this campaign's choice and is a Latin word rather than a plausible file type, which is itself a weak tell, but the hunt must not depend on the string - the operator picks a new one per campaign.
  Sample KQL - registry writes under the per-user Classes hive carrying value data far longer than a ProgID.
  `DeviceRegistryEvents | where Timestamp > ago(30d) | where ActionType in ("RegistryValueSet","RegistryKeyCreated") | where RegistryKey has @"\Software\Classes\." | where isnotempty(RegistryValueData) | extend dataLen = strlen(RegistryValueData) | where dataLen > 64 | project Timestamp, DeviceName, RegistryKey, RegistryValueName, dataLen, RegistryValueData = substring(RegistryValueData, 0, 120), InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessCommandLine, AccountName | order by dataLen desc`
  Writing-process leg (independent of value shape) - Core filter - any write to `HKCU\Software\Classes\.<ext>` whose initiating process is not an installer, a package manager, Explorer, a browser or a known application. Legitimate associations are written by `msiexec.exe`, setup executables, `explorer.exe` (user choice), and applications registering themselves at first run. A write from `python.exe`, `powershell.exe`, `rundll32.exe`, `control.exe`, `mshta.exe`, or an unsigned binary in a user-writable path is out of pattern regardless of what the value contains. In this campaign the writer would be the CosmicPulse backdoor or its bootstrapper, so a Python process writing a file association is the shape to look for.
  Structural-validity leg (offline, works on collected hives) - For each `.ext` key, check that the default value names a ProgID that exists under `Software\Classes\`, and that the value is printable ASCII under about 64 characters. Flag any key failing either test. This runs on NTUSER.DAT and UsrClass.dat collected during IR without needing live access, and it is schema-based rather than content-based, so it catches arbitrary data stashed in the hive whatever its encoding. A high-entropy or base64 value in this position is, by the registry's own rules, malformed.
  Response note - If a hit is confirmed, preserve the value before deleting it. It is encrypted key material, and with the payload sample in hand it may decrypt the backdoor's downloaded stages, which is how a responder gets from "a backdoor was present" to "here is what it fetched and did". Deleting the key first destroys that. Pair with [[H362]] for the persistence and delivery stages of the same chain, and check for the campaign's scheduled task names on the same host.

# H363

Buried in Microsoft's September 2026 Star Blizzard report, among the scheduled tasks and the Control Panel applet downloader, is a single registry path: `HKEY_CURRENT_USER\Software\Classes\.mollis`, used to store an encrypted AES key.

That key is normally the registry's way of saying "files ending in `.mollis` open with this program". There is no such program, and there are no such files. The key exists purely as a place to keep a secret.

It is a well-chosen place. A standard user can write it without elevation. It sits in a hive holding hundreds of structurally identical siblings, so nothing about it stands out to someone scrolling through. It survives reboots. And it is not a file, so every search for a dropped key blob comes up empty, while analysis of the payload binary yields no embedded key — the key was never in the binary.

The practical consequence for incident response is worse than the evasion. A responder who finds the backdoor, deletes it, and closes the case leaves the key sitting in the user's hive with nothing to indicate it is there.

What gives it away is that the registry has a schema and the malware does not follow it. A file-extension key's default value is supposed to be a short ProgID string naming a key that exists. An encrypted AES key is long, high-entropy and names nothing.

## Why

- **It is malformed by the operating system's own rules.** The detection does not need to know the extension, the campaign or the encoding — only that a value in a ProgID position is long, high-entropy and resolves to no ProgID. That holds for whatever string the next campaign picks.
- **Fleet rarity is cheap to compute and hard to evade.** Enumerating per-user file associations across the estate takes one registry read per host, and a one-host extension stands out immediately against a long tail of extensions shared by thousands.
- **No elevation, no file, no scan surface.** A standard-user registry write leaves nothing for file-based AV, file integrity monitoring or disk forensics keyed on dropped artefacts.
- **The key outlives the malware.** Removing the executable does not remove the key, so this is specifically a hunt for residue that standard remediation leaves behind — including on hosts believed to be already cleaned.
- **The writing process is itself out of pattern.** File associations are written by installers, Explorer and applications at first run. A Python or PowerShell process writing one is anomalous without reference to the value at all, giving the hunt a second independent leg.
- **It is worth money to the investigation.** Captured key material plus a payload sample can decrypt what the backdoor downloaded, turning an unknown-scope incident into a known one — provided the responder preserves the value instead of deleting it.
