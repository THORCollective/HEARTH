false_positive_notes: |
  Custom URL protocol handlers are a normal Windows feature and applications register them constantly — `slack:`, `zoommtg:`, `msteams:`, `vscode:`, `spotify:`, `discord:`, `steam:`, `notion:`, `ms-officeapp:` and hundreds of others. Registration under `HKCU\Software\Classes` specifically is also legitimate, since per-user application installs (anything in `%LOCALAPPDATA%\Programs`, which is how Slack, VS Code, Teams and most Electron apps install) have no other option. So neither the handler nor its hive is suspicious by itself. The anomaly is the *pairing*: a Run key or startup entry that invokes a protocol scheme rather than an executable. Real applications register a handler so the browser can launch them from a web link, and they persist themselves with a Run value pointing at their own `.exe` — they do not route their own autostart through their own URI scheme, because there is no reason to add the indirection. Baseline the environment's Run and RunOnce values over 30 days; legitimate ones are overwhelmingly direct paths to executables, and a `<scheme>://` argument in an autorun value should be a handful of entries or none. Then resolve each observed scheme's `shell\open\command` and judge the target: a signed binary in `%ProgramFiles%` or `%LOCALAPPDATA%\Programs\<vendor>` is fine, while `rundll32.exe /sta {GUID}`, `mshta.exe`, a script interpreter, or any path under `%AppData%\<random>` is not. Note that a scheme name chosen to look mundane (DarkMe used `Locked`) will not stand out by name, so enumerate by structure rather than by scheme reputation.

  Platform: Windows. Driven by Huntress, "DarkMe RAT: A VB6 APT Trojan Turned Conventional Infostealer" (September 22, 2026). The observed chain: `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` value `Locked` set to `explorer.exe "Locked://Newest"`; `HKCU\Software\Classes\Locked` registered with a `(Default)` of `URL:Locked Protocol`, an empty `URL Protocol` value, and `shell\open\command` set to `rundll32.exe /sta {CFDC57BA-1705-45AF-BA10-EFC3D592982B}`; and that CLSID registered under `HKCU\Software\Classes\CLSID\{...}\InprocServer32` pointing at `%AppData%\ComponentsFolder\Coconout.dll`. The CLSID registration was written by `reg.exe import` of a generated `.reg` template (`filetext2.txt`) by the staging script `prnfig.wsf`; the `Locked` handler and the Run value were written by the stage-2 loader `Use.dll`, both in one function.
  What the indirection buys the adversary - Three things, each defeating a different standard practice. First, autorun triage: the Run value reads `explorer.exe "Locked://Newest"`, so a responder reviewing autoruns sees a signed Microsoft binary and a string that looks like an application deep-link, and the actual payload command is one registry key away in a location that autorun tooling has historically not enumerated. Second, parentage: because `explorer.exe` performs the protocol dispatch, the payload's parent process is `explorer.exe` — the same lineage as a user double-clicking a file — so the payload is not the direct autorun child and the autorun command line never names it. Third, resilience: the two halves are independent registry locations (DarkMe wrote both in one function, but they need not be written together), so neither write alone looks like complete persistence, and removing only the Run key leaves a working handler that any browser or document link can still trigger.
  Sysmon Event ID 13 / DeviceRegistryEvents — leg 1, the autorun value - Core filter: `Set` on `HKU\*\Software\Microsoft\Windows\CurrentVersion\Run\*` (also `RunOnce`, and the machine-wide equivalents) where `Details`/`RegistryValueData` matches a URI scheme pattern — `^[A-Za-z][A-Za-z0-9+.\-]*://` — rather than a filesystem path. Strong red flags: the value data invokes `explorer.exe`, `cmd /c start`, or `rundll32 url.dll,FileProtocolHandler` with a scheme argument; the scheme is not one your software inventory accounts for; and the value name matches the scheme name, which is a generator artifact.
  Sample KQL — autorun values that launch a URI scheme instead of an executable:
  `DeviceRegistryEvents | where Timestamp > ago(30d) | where ActionType == "RegistryValueSet" | where RegistryKey has_any (@"\CurrentVersion\Run", @"\CurrentVersion\RunOnce") | where RegistryValueData matches regex @"(?i)[a-z][a-z0-9+.\-]*://" | where not(RegistryValueData has_any ("http://", "https://")) | project Timestamp, DeviceName, InitiatingProcessAccountName, RegistryKey, RegistryValueName, RegistryValueData, InitiatingProcessFileName, InitiatingProcessCommandLine | order by Timestamp desc`
  Sysmon Event ID 13 / DeviceRegistryEvents — leg 2, the handler registration - Core filter: `Set` on `HKU\*\Software\Classes\*\shell\open\command\(Default)` where the sibling key carries a `URL Protocol` value — that empty-valued `URL Protocol` entry is what marks a class as a protocol handler and is the cheapest structural anchor in the whole hunt. SigmaHQ's "Potential Persistence Via Custom Protocol Handler" rule keys on a `TargetObject` starting `HKCR\` with data starting `URL:`; per-user registrations like DarkMe's are logged under `HKU\<SID>\Software\Classes` (or `HKU\<SID>_Classes`), so check that rule matches your per-user writes before relying on it. Strong red flags: the command targets `rundll32.exe` with a bare CLSID (see [[H344]]), `mshta.exe`, `wscript.exe`, `cscript.exe`, `powershell.exe`, `conhost.exe --headless`, or any unsigned binary under `%AppData%`, `%LOCALAPPDATA%`, `%TEMP%` or `%ProgramData%`; and the registration being written by `reg.exe import`, a `.wsf`/`.vbs` script host, or a process that is not an installer.
  Sample KQL — protocol handler command pointing at an interpreter or user-writable path:
  `DeviceRegistryEvents | where Timestamp > ago(30d) | where ActionType == "RegistryValueSet" | where RegistryKey has @"\Software\Classes\" and RegistryKey has @"\shell\open\command" | where RegistryValueData has_any ("rundll32", "mshta", "wscript", "cscript", "powershell", "conhost", @"\AppData\", @"\Temp\", @"\ProgramData\") | extend scheme = tostring(split(tostring(split(RegistryKey, @"\Classes\")[1]), @"\")[0]) | project Timestamp, DeviceName, InitiatingProcessAccountName, scheme, RegistryKey, RegistryValueData, InitiatingProcessFileName, InitiatingProcessCommandLine | order by Timestamp desc`
  The join that makes this high-confidence - Correlate the two legs on the scheme string: a scheme that appears both as the argument of a Run value and as a `HKCU\Software\Classes` registration whose command is an interpreter is effectively conclusive. Either leg alone is worth triage; together they are a finding. Keep the legs as separate queries as well as a join, because the writes may be separated in time and because a handler registered without a Run key is still a live execution path reachable from a browser, a chat client or an Office document link.
  Sysmon Event ID 1 / 4688 — runtime confirmation - Core filter: `explorer.exe` spawning `rundll32.exe`, `mshta.exe` or a script host, where `explorer.exe`'s own command line contains a `<scheme>://` argument. Note that when the protocol is dispatched by an already-running `explorer.exe` the argument may not appear on a new `explorer.exe` process at all, so treat `explorer.exe` as the parent of an interpreter shortly after logon as the signal, and expect the payload to run within seconds of Event ID 4624 for that user.
  `reg.exe import` as a collection anchor - DarkMe wrote its COM registration by importing a generated `.reg` template rather than calling `reg add` per value, which leaves a single process event and a recoverable file. Core filter: `reg.exe` with `import` where the argument path is under `%AppData%`, `%LOCALAPPDATA%`, `%TEMP%` or `%ProgramData%`, or whose parent is `wscript.exe`/`cscript.exe`. The imported file often survives on disk and contains the COM registration, including the DLL path, in plaintext, making it the highest-value artifact to collect during triage. An EQL sketch (derived from the report's hunting guidance; Huntress did not publish detection rules): `process where process_name == "reg.exe" and command_line like~ "*import*%appdata%*" and (command_line like~ "*.reg" or parent_process_name in ("wscript.exe", "cscript.exe"))`.
  Remediation note - Both halves must be removed. Deleting the Run value stops the automatic launch but leaves `HKCU\Software\Classes\<scheme>` registered, and any link with that scheme — in a browser, an email, a chat message or a document — will still execute the payload. Remove the scheme key tree, the `CLSID` key tree, and the Run value together, then hunt the fleet for the scheme name.
  Cross-technique: [[H344]] covers the `rundll32 /sta {CLSID}` command this handler invokes, and [[H346]] the `.pif` delivery that begins the chain. Compare [[H151]] for a conventional Run-key-plus-scheduled-task persistence pair, which is what this technique is designed to look less like.

# H345

Huntress's September 2026 DarkMe analysis documents a persistence design worth separating from the malware that used it. The Run key value reads:

`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` → `Locked` = `explorer.exe "Locked://Newest"`

There is no payload in that value. `Locked` is a custom URL protocol the loader registered for itself under `HKCU\Software\Classes\Locked`, complete with the empty `URL Protocol` value that marks a class as a scheme handler, and its `shell\open\command` runs `rundll32.exe /sta {CFDC57BA-1705-45AF-BA10-EFC3D592982B}` — which in turn resolves, through a third registry key, to a DLL in `%AppData%\ComponentsFolder\`.

The indirection is doing real work. A responder pulling autoruns sees `explorer.exe` and a URI that looks like an ordinary application deep-link, of the kind Slack, Teams and VS Code all register; nothing in that value is unsigned, nothing points at a suspicious path, and the payload command is in a registry location that autorun tooling has not traditionally enumerated. When the payload does run, `explorer.exe` dispatched it, so its parent is the shell — indistinguishable from a user clicking a link, and the payload is not the direct autorun child, so the autorun command line never names it. And because the two halves are independent, removing the Run value leaves a fully functional execution path that any browser or document link can still trigger.

None of this requires elevation. `HKCU\Software\Classes` is writable by the user and takes precedence over the machine-wide registration, so an unprivileged loader can define a scheme that the shell will honour.

## Why

- The technique specifically defeats autorun triage, which is the first thing most responders and most persistence-detection tooling look at. The Run value contains a signed Microsoft binary and an opaque URI, so an analyst scanning a list of autoruns for suspicious paths finds nothing, and the malicious command is one key away in a location that list does not cover.
- Parent-process laundering is a real consequence, not a side effect. Because the shell performs protocol dispatch, the payload looks like user-initiated activity, and the autorun command line never names the payload, which breaks detections that match the Run value's data to the process it launches.
- The structural anchor is cheap, specific, and needs no indicator. An autorun value whose data is a `<scheme>://` URI rather than a filesystem path is rare enough to enumerate exhaustively, and it describes the technique rather than this family — it will catch the next loader that reuses the pattern with a different scheme name and a different payload.
- Splitting persistence across two registry locations also splits the remediation, which is how reinfection happens. Removing only the Run key leaves a live, browser-reachable execution path registered on the host, so a hunt that surfaces only one leg produces an incomplete cleanup and a host that quietly re-executes later.
- Everything needed is already collected in most environments. `HKCU\Software\Classes` and Run-key writes both land in Sysmon Event ID 13 and `DeviceRegistryEvents`, and the `reg.exe import` step frequently leaves the COM registration on disk as a readable `.reg` template — a useful artifact to recover during triage.
