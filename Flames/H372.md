title: A downloader that reads three Event ID 6013 records to prove the machine has been up for two hours before it will run
hypothesis: >-
  A .NET downloader is deciding whether to execute by asking how long the machine has been alive. Late
  MATCHBOIL builds query the Windows System event log for `*[System/EventID=6013]` through
  `EventLogReader`, regular-expression the uptime value out of each record, and proceed only if at
  least three events report uptime of 7,200 seconds or more — then check `Debugger.IsAttached`, and
  only then start a two-minute timer that drives C&C communication. A sandbox is fresh and has neither
  the boot history nor the patience; a real desktop has months of both. Hunt for processes reading the
  System event log with an EventID-6013 query, for .NET downloaders that gate execution on a required
  command-line switch and show a decoy GUI without it, and for the short-interval timer and scheduled
  task that replace one-shot execution with a standing retry.

false_positive_notes: |
  Reading the Windows System event log is a normal administrative and monitoring act, so the hunt has to be scoped by *who* is reading it and *what they ask for*. Legitimate readers are numerous - monitoring and observability agents, inventory and asset-management tooling, SIEM forwarders, patch and compliance scanners, backup software, vendor support-bundle collectors, and uptime-reporting scripts all read `System.evtx`, and some genuinely do look at boot and shutdown events. Event ID 6013 in particular is the canonical way to report system uptime, so capacity and availability reporting tools query it by design. The discriminators - the reading process, because an established monitoring agent running from `Program Files` under a service account is not the same as a short-lived unsigned .NET binary in `%LOCALAPPDATA%`; signature and path, since nearly every legitimate reader is signed and installed; lifetime, because a monitoring agent reads the log continuously over months while this reads it once, within seconds of starting, and then makes network connections; and sequence, since the combination of an uptime query immediately followed by a debugger check and then outbound HTTPS to a newly-seen host has no administrative equivalent. Also note that `Debugger.IsAttached` is used legitimately in real software, usually to branch logging or assertion behaviour in debug builds, so it carries no signal alone. Finally, the decoy-GUI leg will match ordinary small utilities - a program that shows a window when run without arguments is just a program - so that leg is only useful as corroboration on a binary already flagged by path, signature or the event-log query, never as a filter on its own.

Three HTTPS requests follow - the first returns a numeric value echoed in a second request's header (named `Count`, later `Answer`); the second returns HTML with a hex-encoded payload extracted by a sample-specific regex, "most contain an HTML tag format, for example `<script>(.*?)</script>`"; the payload is hex-decoded and installed.
  The uptime gate (ESET, verbatim). In late-2025 samples, MATCHBOIL "determines whether it is running in a sandboxed or other dedicated analysis environment by using the query `*[System/EventID=6013]` via the .NET class `EventLogReader` to obtain Windows event logs. The events logged under ID 6013 report how long the system has been running since the last boot." Two regular expressions iterate the records to extract the uptime value. "If MATCHBOIL detects that there are at least three events with an uptime value at least of 7,200 seconds, which is equal to two hours, then MATCHBOIL assumes that it is not running in a sandbox or other dedicated analysis machine." It then checks `Debugger.IsAttached`, and if not attached, "creates a timer that runs MATCHBOIL's C&C communication logic every two minutes."
  Why T1678 Delay Execution is the right anchor. This is not a sleep call to outlast a sandbox timeout, which is the familiar form. It is a *historical* check - the malware is not waiting, it is auditing whether the machine has a past. Event ID 6013 is written once per day by the Windows Event Log service recording uptime since boot, so requiring three records above 7,200 seconds is a demand that the host have at least several days of ordinary operating history. A freshly-provisioned analysis VM cannot satisfy that no matter how long the sample is allowed to run, and a sandbox that fast-forwards its clock does not retroactively acquire 6013 records. The design consequence for defenders is that dynamic-analysis verdicts on these samples are unreliable, which is the same conclusion [[H367]] reaches about a different guardrail - and it is why the behaviour has to be hunted on real endpoints.
  Version-specific gating, useful for scoping. 2024 samples - one-shot downloader, payload path `%LOCALAPPDATA%\DeviceMonitor`, persistence via a `DeviceMonitor` value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` *and* a scheduled task named `Updates\CheckTask`. July 2025 - Run key only; payload executed by creating a `Win32_Process` object via `ManagementClass`. Late 2025 - Eziriz .NET Reactor obfuscation replaces Unicode-symbol renaming and string encryption; requires the `-auto` switch or it displays a decoy daily-planner GUI; mutex `Global\PlannerAssistant`; payload installed to `%LOCALAPPDATA%\MeowCheck\MeowMeowProgramm.exe`; payload staged first to `C:\Users\<username>\Pictures\WallpappersSet.jpg`; some samples move the C&C and persistence logic into `AdditionalLib.dll` beside the main binary (e.g. SHA-1 `F886B615CB9E23EAD2718FF2A61155ACFB04CE9E`); persistence via scheduled task `UpdateCheckers\DailyPlanner` running every seven minutes. February 2026 - switch becomes `-plans` alongside `-auto` (SHA-1 `1E2C4AAC30EDFF86CD9A30BD08B199BCD3D0CCCE`), then `-renew` with a text-search-utility decoy GUI (SHA-1 `C85D28F7D272CE2BBBFB9DAE71D21BF25B8D00FC`).   Core filter, the uptime-query leg. Hunt for a process reading `C:\Windows\System32\winevt\Logs\System.evtx` or opening the System channel via the EventLog API, where the reader is a .NET assembly running from a user-writable path and is not an installed monitoring agent.   Core filter, the switch-gated decoy leg. A .NET binary that exits or shows a window unless invoked with a specific switch (`-auto`, `-plans`, `-renew`) is a structural pattern worth hunting on its own - the switch is a cheap guardrail that also means the malicious path never executes during naive analysis. The generalisable form - a process in a user-writable path whose only observed invocations carry an unusual single-dash switch, with a WinForms or WPF assembly load, created by `wscript.exe` or `cscript.exe`. ESET notes the decoy's weaknesses - two text fields both titled `Today` and a typo in the window name - but a hunt should not depend on the decoy's quality.
  Core filter, the retry cadence. The shift from one-shot downloader to a two-minute timer plus a seven-minute scheduled task is itself the signal, because it means the host will keep reaching out. A scheduled task with a repetition interval under ten minutes whose action points at a binary under `%LOCALAPPDATA%` is a narrow and productive query against Event ID 4698, and it is what makes this detectable long after the initial execution. Task names observed - `Updates\CheckTask`, `UpdateCheckers\DailyPlanner`.
  Pivots. The three-request C&C sequence is distinctive - a custom `SN` header carrying hardware identifiers, a 25-character `User-Agent`, and a second request echoing a numeric value in a `Count` or `Answer` header. On the WMI side, `ManagementObjectSearcher` queries for `Win32_BIOS`, `Win32_Processor`, `Win32_ComputerSystem` and `Win32_NetworkAdapterConfiguration` from a short-lived user-path process are a corroborating cluster. # H372

Most sandbox evasion asks "am I being watched right now?" MATCHBOIL asks something smarter: "has this computer had a life?"

ESET's October 2026 catalogue of the UAC-0099 downloader's evolution describes the check in late-2025 builds. MATCHBOIL uses the .NET `EventLogReader` class to run the query `*[System/EventID=6013]` against the Windows System log. Event ID 6013 is the record the Event Log service writes to report how long the system has been running since its last boot — one per day, on an ordinary machine, going back as far as the log retains. MATCHBOIL pulls those records, regular-expressions the uptime value out of each one, and requires at least three of them reporting 7,200 seconds or more before it will do anything.

Two hours of uptime, three separate times. That is not a test for a virtual machine, and it is not a timeout to outlast. It is a demand that the host have *history* — several days of being a computer that someone actually used.

A freshly-provisioned analysis VM cannot pass that check however long you let the sample run, because the records simply do not exist. Fast-forwarding the clock does not help either; 6013 entries are written retrospectively by a service that was not running. The gate is therefore much harder to defeat than a `Sleep(300000)`, and the practical consequence for defenders is the same one [[H367]]'s `/tmp/flag` guardrail produces on Linux: the dynamic-analysis verdict on these samples is not trustworthy, so the behaviour has to be found on real endpoints.

Only after the uptime gate does MATCHBOIL check `Debugger.IsAttached`, and only then does it start a two-minute timer driving its C&C logic. That timer is the other half of the story. Earlier builds were one-shot downloaders that fired once and relied on persistence to run again. From late 2025 the malware keeps asking — every two minutes in-process, backed by a scheduled task named `UpdateCheckers\DailyPlanner` that runs every seven. The operator traded stealth for reliability, and in doing so gave defenders a host that will keep reaching out until someone notices.

There is also a decoy. Run the late-2025 sample without `-auto` and it shows a daily-planner GUI; the February 2026 builds want `-plans`, then `-renew`, the latter presenting a text-search utility instead. ESET is politely scathing about the planner — two fields both labelled `Today`, and a typo in the window title suggesting it was for planning one's milk intake. The quality of the decoy is not the point. The switch is: no switch, no malicious path, no analysis.

## Why

- **Checking boot history defeats sandboxes structurally, not by waiting them out.** Three Event ID 6013 records above two hours require days of real operating history. No analysis timeout extension produces them, which is why this gate works and why host hunting is the only reliable answer.
- **The query string is unusually specific for something so cheap to look for.** `*[System/EventID=6013]` via `EventLogReader` is a narrow thing to ask for. Pair it with an unsigned .NET binary in `%LOCALAPPDATA%` and the benign set is empty.
- **The reading process is the whole scope.** Monitoring agents, inventory tools and SIEM forwarders read `System.evtx` constantly and legitimately. A short-lived, unsigned, user-path .NET assembly that reads it once and then makes outbound HTTPS is a different animal.
- **The retry cadence is a gift.** A two-minute in-process timer plus a seven-minute scheduled task means the compromise keeps announcing itself. A task with a sub-ten-minute repetition interval pointing at `%LOCALAPPDATA%` is a tight query against Event ID 4698.
- **Switch gating generalises past this family.** A binary whose malicious branch requires `-auto`, `-plans` or `-renew` and otherwise shows a window is a reusable pattern — and it is specifically designed to produce a clean verdict when someone double-clicks it in a lab.
- **Persistence moved repeatedly, so hunt all three locations.** Run key plus scheduled task in 2024, Run key only in July 2025, scheduled task in late 2025. A hunt that checks one of them tracks one build.
- **The staging path is an odd and durable artefact.** A payload written to `C:\Users\<user>\Pictures\WallpappersSet.jpg` by a non-browser process is strange enough to query for directly, and image-extension staging survives obfuscator changes.
- **Obfuscation changed; behaviour did not.** Unicode-symbol renaming gave way to Eziriz .NET Reactor with control-flow virtualisation, which raises static-analysis cost considerably. The uptime query, the timer and the task are unaffected.
