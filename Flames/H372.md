category: Flames
title: A downloader that reads three Event ID 6013 records to prove the machine has been up for two hours before it will run
hypothesis: >-
  A .NET downloader is deciding whether to execute by asking how long the machine has been alive. Late
  MATCHBOIL builds query the Windows System event log for `*[System/EventID=6013]` through
  `EventLogReader`, regular-expression the uptime value out of each record, and proceed only if at
  least three events report uptime of 7,200 seconds or more — then check `Debugger.IsAttached`, and
  only then start a two-minute timer that drives C&C communication. A freshly provisioned sandbox
  usually has no such history; an ordinary desktop does. Hunt for user-path .NET processes loading the
  Windows Event Log API (`wevtapi.dll`) and then reaching out to the network, for .NET downloaders that
  gate execution on a required command-line switch and show a decoy GUI without it, and for the
  two-minute C&C timer and the short-interval scheduled tasks that keep the payload running.

false_positive_notes: |
  Reading the Windows System event log is a normal administrative and monitoring act, so the hunt has to be scoped by *who* is reading it. Loading `wevtapi.dll` is common too - many installed applications and management agents load it - so the image-load leg is a scoping filter on path and signature, not a detection on its own. Legitimate readers are numerous - monitoring and observability agents, inventory and asset-management tooling, SIEM forwarders, patch and compliance scanners, backup software, vendor support-bundle collectors, and uptime-reporting scripts all read `System.evtx`, and some genuinely do look at boot and shutdown events. Event ID 6013 in particular is the canonical way to report system uptime, so capacity and availability reporting tools query it by design. The discriminators - the reading process, because an established monitoring agent running from `Program Files` under a service account is not the same as a short-lived unsigned .NET binary in `%LOCALAPPDATA%`; signature and path, since nearly every legitimate reader is signed and installed; lifetime, because a monitoring agent reads the log continuously over months while this reads it once, within seconds of starting, and then makes network connections; and sequence, since the combination of an uptime query immediately followed by a debugger check and then outbound HTTPS to a newly-seen host has no administrative equivalent. Also note that `Debugger.IsAttached` is used legitimately in real software, usually to branch logging or assertion behaviour in debug builds, so it carries no signal alone. Finally, the decoy-GUI leg will match ordinary small utilities - a program that shows a window when run without arguments is just a program - so that leg is only useful as corroboration on a binary already flagged by path, signature or the event-log query, never as a filter on its own.

MATCHBOIL was first documented by CERT-UA in August 2025.   Published artefacts (ESET, verbatim). Delivery - "malicious links in spearphishing emails. Clicking the link downloads an archive file with a VBScript file payload that downloads and executes MATCHBOIL on the victim machine," and "the victim is misled into executing the script manually." MATCHBOIL's own persistence is established by that VBScript; the downloaded payload - usually the C# backdoor MATCHWOK - is persisted by MATCHBOIL itself. At runtime it checks for a sample-specific directory under `%LOCALAPPDATA%` and terminates if it already exists. It gathers CPUID, BIOS serial number, computer model and manufacturer, username and the first network interface's MAC via `ManagementObjectSearcher` WMI queries, and sends them in a custom `SN` HTTP header alongside a 25-character `User-Agent`. Three HTTPS requests follow - the first returns a numeric value echoed in a second request's header (named `Count`, later `Answer`); the second returns HTML with a hex-encoded payload extracted by a sample-specific regex, "most contain an HTML tag format, for example `<script>(.*?)</script>`"; the payload is hex-decoded and installed.
  The uptime gate (ESET, verbatim). In late-2025 samples, MATCHBOIL "determines whether it is running in a sandboxed or other dedicated analysis environment by using the query `*[System/EventID=6013]` via the .NET class `EventLogReader` to obtain Windows event logs. The events logged under ID 6013 report how long the system has been running since the last boot." Two regular expressions iterate the records to extract the uptime value. "If MATCHBOIL detects that there are at least three events with an uptime value at least of 7,200 seconds, which is equal to two hours, then MATCHBOIL assumes that it is not running in a sandbox or other dedicated analysis machine." It then checks `Debugger.IsAttached`, and if not attached, "creates a timer that runs MATCHBOIL's C&C communication logic every two minutes."
  Mapping. ESET maps T1497.001 System Checks to the event-log query and T1678 Delay Execution to MATCHBOIL's use of the Sleep API. This hunt anchors on T1497.003 Time Based Checks, an analyst mapping, because the gate is an uptime test and ATT&CK describes T1497.003 as covering checks of system uptime. T1678 is carried for ESET's Sleep-API mapping, not for the uptime gate. It is not a sleep call to outlast a sandbox timeout - the malware is not waiting, it is checking whether the machine has a past. Event ID 6013 is written by the Event Log service about once a day (by default around noon) recording uptime since boot, so requiring three records above 7,200 seconds needs roughly two to three days of operating history in the retained log. A freshly provisioned analysis VM usually cannot satisfy that however long the sample runs, because the records were never written. A sandbox image built from a previously used machine that kept its old 6013 records can pass it, so the gate is strong against fresh sandboxes rather than absolute. The design consequence for defenders is that dynamic-analysis verdicts on these samples are unreliable, which is the same conclusion [[H367]] reaches about a different guardrail, and [[H134]] covers the wider family of Windows pre-execution environment checks (WMI hardware enumeration and timing gates) - this hunt is the event-log-history variant.

  Core filter, the uptime-query leg. `EventLogReader` queries go through the Windows Event Log service, so the reading process never opens `System.evtx` itself and file telemetry cannot see the read. What the process does show is a load of `wevtapi.dll`, the Event Log API that `EventLogReader` calls. Hunt for `wevtapi.dll` loaded by a process running from a user-writable path that is not an installed monitoring agent, followed within minutes by outbound HTTPS. Triage fields - the loading process path, signature status, parent process, whether it made outbound HTTPS shortly after the load, and whether it created a scheduled task or Run value afterwards. Defender advanced hunting keeps 30 days, and DeviceImageLoadEvents may not record every load of a common DLL, so treat an empty result as weak evidence.

  Core filter, the switch-gated decoy leg. A .NET binary that exits or shows a window unless invoked with a specific switch (`-auto`, `-plans`, `-renew`) is a structural pattern worth hunting on its own - the switch is a cheap guardrail that also means the malicious path never executes during naive analysis. The generalisable form - a process in a user-writable path whose only observed invocations carry an unusual single-dash switch, with a WinForms or WPF assembly load, created by `wscript.exe` or `cscript.exe`. ESET notes the decoy's weaknesses - two text fields both titled `Today` and a typo in the window name - but a hunt should not depend on the decoy's quality.
  Core filter, the retry cadence. The shift from one-shot downloader to a two-minute timer plus a seven-minute scheduled task is itself the signal, because it means the host will keep reaching out. A scheduled task with a repetition interval under ten minutes whose action points at a binary under `%LOCALAPPDATA%` is a narrow and productive query against Event ID 4698, and it is what makes this detectable long after the initial execution. Task names observed - `Updates\CheckTask`, `UpdateCheckers\DailyPlanner`, `MailClient\Checker`.
  Pivots. The three-request C&C sequence is distinctive - a custom `SN` header carrying hardware identifiers, a 25-character `User-Agent`, and a second request echoing a numeric value in a `Count` or `Answer` header. On the WMI side, ESET says the hardware details are gathered through `ManagementObjectSearcher` queries; the specific classes are not named in the text, but CPUID, BIOS serial, model and MAC would normally come from `Win32_Processor`, `Win32_BIOS`, `Win32_ComputerSystem` and `Win32_NetworkAdapterConfiguration` (inferred). Successful WMI queries are not written to WMI-Activity/Operational, so this leg needs the WMI-Activity Trace ETW provider or EDR WMI telemetry. UAC-0099 also deploys LONEPAGE, a PowerShell downloader named for the word `page` in its C&C URLs, which is worth a separate search across the same estate.

# H372

Most sandbox evasion asks "am I being watched right now?" MATCHBOIL asks something smarter: "has this computer had a life?"

ESET's October 2026 catalogue of the UAC-0099 downloader's evolution describes the check in late-2025 builds. MATCHBOIL uses the .NET `EventLogReader` class to run the query `*[System/EventID=6013]` against the Windows System log. Event ID 6013 is the record the Event Log service writes to report how long the system has been running since its last boot — about one per day (by default around noon) on a machine that is switched on, going back as far as the log retains. MATCHBOIL pulls those records, regular-expressions the uptime value out of each one, and requires at least three of them reporting 7,200 seconds or more before it will do anything.

Two hours of uptime, three separate times. That is not a test for a virtual machine, and it is not a timeout to outlast. It is a demand that the host have *history* — roughly two to three days of retained operating time, since the records come about once a day.

A freshly provisioned analysis VM usually cannot pass that check however long you let the sample run, because the records were never written. Fast-forwarding the clock does not help either; the Event Log service only writes 6013 records as time actually passes, and does not backfill the days the image never ran. A sandbox image built from a previously used machine that kept its old records can pass, so the gate is strong rather than absolute — but it is still much harder to defeat than a `Sleep(300000)`, and the practical consequence for defenders is the same one [[H367]]'s `/tmp/flag` guardrail produces on Linux: the dynamic-analysis verdict on these samples is not trustworthy, so the behaviour has to be found on real endpoints.

Only after the uptime gate does MATCHBOIL check `Debugger.IsAttached`, and only then does it start a two-minute timer driving its C&C logic. That timer is the other half of the story. Earlier builds were one-shot downloaders that fired once and relied on persistence to run again. From late 2025 the malware keeps asking — every two minutes in-process, with its payload persisted by a scheduled task named `UpdateCheckers\DailyPlanner` that runs every seven. The operator traded stealth for reliability, and in doing so gave defenders a host that will keep reaching out until someone notices.

There is also a decoy. Run the late-2025 sample without `-auto` and it shows a daily-planner GUI; the February 2026 builds want `-plans`, then `-renew`, the latter presenting a text-search utility instead. ESET is politely scathing about the planner — two fields both labelled `Today`, and a typo in the window title suggesting it was for planning one's milk intake. The quality of the decoy is not the point. The switch is: no switch, no malicious path, no analysis.

## Why

- **Checking boot history defeats fresh sandboxes structurally, not by waiting them out.** Three Event ID 6013 records above two hours need a few days of retained operating history. No analysis timeout extension produces them on a fresh image, which is why this gate works and why host hunting is the reliable answer.
- **The read itself is invisible to file telemetry, so hunt the API load.** `EventLogReader` goes through the Event Log service, so no process opens `System.evtx`. A user-path process loading `wevtapi.dll` and then making outbound HTTPS is the observable form.
- **The reading process is the whole scope.** Monitoring agents, inventory tools and SIEM forwarders read the event log constantly and legitimately. A short-lived, unsigned, user-path .NET assembly that loads the Event Log API and then makes outbound HTTPS is a different animal.
- **The retry cadence is a gift.** A two-minute in-process timer plus a payload task running every seven minutes means the compromise keeps announcing itself. A task with a sub-ten-minute repetition interval pointing at `%LOCALAPPDATA%` is a tight query against Event ID 4698.
- **Switch gating generalises past this family.** A binary whose malicious branch requires `-auto`, `-plans` or `-renew` and otherwise shows a window is a reusable pattern — and it is specifically designed to produce a clean verdict when someone double-clicks it in a lab.
- **Persistence moved repeatedly, so hunt all of the locations.** Run key plus scheduled task in 2024, Run key only in July 2025, `UpdateCheckers\DailyPlanner` in late 2025, `MailClient\Checker` in April 2026. A hunt that checks one of them tracks one build.
- **The staging path is an odd and durable artefact.** A payload written to `C:\Users\<user>\Pictures\WallpappersSet.jpg` by a non-browser process is strange enough to query for directly, and image-extension staging survives obfuscator changes.
- **Obfuscation changed; behaviour did not.** Unicode-symbol renaming gave way to Eziriz .NET Reactor with control-flow virtualisation, which raises static-analysis cost considerably. The uptime query, the timer and the task are unaffected.
