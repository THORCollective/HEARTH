false_positive_notes: |
  A number of legitimate products inject into or read from explorer.exe. Shell extension hosts, accessibility software, input-method editors, clipboard managers, backup agents and some endpoint-security products all do. Build the allowlist on the source image path and signer, and expect it to be short and stable; the identity of the injector is the discriminator, not the fact of injection.
  Sysmon Event ID 10 against explorer.exe is high volume by default and will swamp the hunt if left unfiltered. Filter on the access mask before anything else: an injector needs write and thread-creation rights, so require the combination that permits writing memory and creating a thread rather than any open handle. Read-only opens for window enumeration are the bulk of the noise.
  GrantedAccess values vary with how the injector opens the handle. PROCESS_ALL_ACCESS is common but not required, so matching only 0x1F0FFF will miss narrower opens. Match on the presence of the write and create-thread bits instead of on a fixed total.
  Explorer does make some network connections legitimately. Shell integration, Office and OneDrive components, online folder providers and thumbnail or metadata fetching produce traffic to Microsoft and CDN endpoints. Baseline Explorer destinations per estate and treat non-Microsoft, non-CDN destinations as the finding rather than any connection at all.
  Expect no image-load event for the payload. The DLL is decrypted in memory and injected, so there is no file on disk and Sysmon 7 will not name it. A hunt that requires a matching image load, or that pivots on a DLL path, will find nothing.
  Sandbox-aware samples will not reproduce on demand. The family terminates without stealing anything when it believes it is being analysed, so a detonation that produces no injection does not mean a sample is benign. Treat a clean dynamic run as inconclusive.
notes: |
  Cross-process access into Explorer - Core filter: a process opening `explorer.exe` with rights sufficient to write memory and create a thread, where the source image is not in the allowlist. Triage values: `SourceImage` path and signer, `SourceCommandLine`, `GrantedAccess`, `CallTrace` (Sysmon 10 only), and the source process parent. Sysmon 10 is the richer sensor here because `CallTrace` shows whether the call came from a legitimate module or from unbacked memory. Defender XDR equivalent, 30-day retention:
  ```kql
  DeviceEvents
  | where Timestamp > ago(30d)
  | where ActionType == "CreateRemoteThreadApiCall"
  | where FileName =~ "explorer.exe"
  | where InitiatingProcessFileName !~ "explorer.exe"
  | project Timestamp, DeviceName, TargetProcess = FileName,
            InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessCommandLine,
            InitiatingProcessParentFileName, InitiatingProcessAccountName
  | order by Timestamp desc
  ```
  Validate the `ActionType` spelling against your own tenant before relying on it; the API-call action types are present in `DeviceEvents` but their coverage depends on sensor version, which is why Sysmon 8 and 10 are listed as required rather than optional.
  Injector provenance - The source process is the half that makes this triageable. Filter for an unsigned image running from an archive-extraction or download path: `%USERPROFILE%\Downloads\`, `%TEMP%\Rar$*`, `%TEMP%\7z*`, `%TEMP%\Temp1_*`, or a directory created minutes earlier by an archive utility. ASEC's own guidance is to "check whether there is a history of downloading large ZIP files from untrusted sources, decompressing them, and then running the executable files contained within", and to look for "abnormal code injection behavior related to AutoIt.Exe or explorer.Exe".
  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where InitiatingProcessFileName in~ ("explorer.exe", "7zFM.exe", "WinRAR.exe", "Bandizip.exe")
  | where FolderPath matches regex @"(?i)\\(Downloads|Temp)\\"
  | where isempty(ProcessVersionInfoCompanyName)
  | project Timestamp, DeviceName, FileName, FolderPath, ProcessCommandLine, SHA256,
            InitiatingProcessFileName, AccountName
  | order by Timestamp desc
  ```
  Egress from Explorer - Core filter: outbound connections where the initiating process is `explorer.exe` and the destination is outside your baselined Microsoft and CDN set. This is the post-injection signal and often the first one a team notices. Triage values: `RemoteUrl`, `RemoteIP`, `RemotePort`, and the timing relative to the injection event. The C2 protocol here is custom rather than recognisable: "Data transmitted to the C2 server is first encrypted using the XOR encryption method and then compressed using the LZNT1 algorithm", with the XOR key differing per sample specifically to defeat traffic-pattern detection, so content inspection will not classify it and the destination and the initiating process are what you have.
  What the payload collects first - On execution it sends a host profile consisting of "a list of installed programs, the CPU name, graphics driver information, data from the CPUID instruction, and the Windows operating system version", then receives configuration from the C2 that determines what else it takes. The theft targets are therefore not fixed per sample, which is why the breadth-based approach in [[M062]] complements this hunt: this one catches the injection, that one catches the collection regardless of which targets the operator enabled.
  Anti-analysis context for triage - The family is Rust-built and uses "anti-disassembly using dynamic JMPs, anti-sandbox techniques leveraging CPU memory cache lookups, and DLL injection". If it concludes it is being analysed "it terminates without performing any Information Theft", displaying the message `I love stealing cookies, but not on this machine. Sorry!`. Strings are stored encrypted and decrypted immediately before use with a per-sample modified index table, so string-based triage of a recovered binary will come back empty.
  Dropper capability beyond theft - Configuration observed in the wild had the download-and-execute feature enabled, so treat any confirmed infection as a potential foothold for a second payload rather than as credential theft alone. Scope for child processes and new persistence on the host, not just for the stolen data.
  Delivery variant - Earlier, smaller distributions used the AutoIt interpreter as the launcher before the shift to injection and standalone execution. [[H275]] covers the AutoIt interpreter executing a script from a staging directory; use it alongside this hunt when triaging a host where the injector itself cannot be found.

# H419

AhnLab ASEC published an analysis in October 2026 of a Rust-written infostealer distributed as cracked software, first seen in mid-August and spreading widely from September after its execution method changed. The change is the interesting part. Early, small-scale distributions used AutoIt as the launcher; later ones moved to injection, and ASEC records that "In some recently distributed samples, a technique was used where a DLL file stored internally in an encrypted state was decrypted and then injected into the Explorer process."

Explorer is a deliberate choice rather than a convenient one. It is always running, it runs as the logged-on user, it legitimately reads and writes across the whole user profile, and it is a signed Microsoft binary. Credential-store access and C2 traffic performed from inside it look like the shell doing shell things. And because the DLL is decrypted in memory and injected, there is no file on disk, no image-load event naming the payload, and nothing for a hash or path indicator to match.

What remains is the injection itself and its consequences. The cross-process open against Explorer, with rights to write memory and create a thread, is recorded by Sysmon Events 8 and 10. The source of that access is an unsigned binary sitting in a Downloads folder or an archive-extraction directory, which is exactly the provenance ASEC tells defenders to look for: check for "a history of downloading large ZIP files from untrusted sources, decompressing them, and then running the executable files contained within", and for "abnormal code injection behavior related to AutoIt.Exe or explorer.Exe". After injection, Explorer starts making outbound connections to destinations it has no business reaching.

Two details shape how this hunt should be used. The C2 protocol is XOR-encrypted then LZNT1-compressed with a per-sample key, chosen so that network content analysis finds no stable pattern — so the destination and the initiating process are the usable network facts. And the sample is sandbox-aware: it "terminates without performing any Information Theft" when it believes it is being analysed, printing `I love stealing cookies, but not on this machine. Sorry!`. A quiet detonation proves nothing.

## Why

- Injecting into Explorer converts an attributable process into an unattributable one. Every subsequent action belongs, in telemetry, to a signed Microsoft binary running as the user, which is why catching the injection matters more than catching the theft.
- The payload leaves no file-based artefact at all. Decryption in memory means no DLL on disk and no image load, so file and hash-based detection has nothing to work with and cross-process telemetry is the only place the event appears.
- The injector's provenance is a strong, cheap filter. An unsigned executable running from an archive-extraction directory or Downloads, opening Explorer with write and thread-creation rights, is a combination with very few legitimate analogues, and it can be expressed in one query.
- Network egress from Explorer is an independent second chance at the same intrusion. Teams that miss the injection often still see Explorer connecting somewhere unusual, and a baselined Explorer destination list turns that into a usable signal rather than a curiosity.
- The theft scope is operator-controlled, so behavioural detection has to anchor on the mechanism. Configuration arrives from the C2 and decides what gets stolen, meaning no fixed set of target paths will characterise every infection — but every infection has to get into Explorer first.
