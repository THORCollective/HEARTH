  `takeown` and `icacls` are legitimate administrative tools and appear constantly in software
  installers, in deployment and imaging scripts, in remediation runbooks, and in the vast body of
  copy-pasted advice for fixing broken permissions. Treating either binary as a signal on its own will
  generate more noise than it is worth. Three things narrow it sharply. First, the target path: routine
  administrative use overwhelmingly touches application directories, user profiles and data shares, not
  `C:\Windows\System32`. Second, the SID: `*S-1-1-0` grants Everyone full control, which is not something
  a competent administrative script does to a system directory, and searching the command line for that
  literal is both cheap and high-yield. Third, the pairing: `takeown` followed within seconds by `icacls`
  followed by a rename of the same file is a three-step sequence with a specific shape, and the sequence
  is far rarer than any of its parts. Expect genuine hits from a small number of legitimate sources —
  in-place OS upgrade and servicing-stack repair, some antivirus and backup product installers, PC
  vendor bloatware cleanup utilities, and the well-meaning "disable Windows Update permanently" scripts
  circulated on forums, which perform an essentially identical sequence. That last category deserves a
  note: it is not a false positive so much as a policy violation with the same fingerprint, and finding

# H292

There is a common failure mode in hunting for defence tampering, which is that the hunt stops at the
service layer. Stopping `wuauserv` gets caught. Disabling it gets caught. Both are also, from the
operator's point of view, unsatisfying, because Windows will undo them: Windows Update Medic Service
(`WaaSMedicSvc`) exists precisely to detect and repair a sabotaged update stack, and it is reasonably
good at it.

Microsoft's write-up of the counterfeit software download campaign attributed to Silver Fox shows the
answer to that problem, and it is a level lower than most detections look. Rather than fighting the
repair service through configuration, the operators removed its file:

```
for %i in (WaaSMedicSvc wuauserv) do (
  takeown /f C:\Windows\System32\%i.dll &
  icacls C:\Windows\System32\%i.dll /grant *S-1-1-0:F &
  rename C:\Windows\System32\%i.dll %i_BAK.dll &
  icacls C:\Windows\System32\%i_BAK.dll /setowner "NT SERVICE\TrustedInstaller" &
  icacls C:\Windows\System32\%i_BAK.dll /remove *S-1-1-0
)
```

Read that sequence in order, because the shape of it is the detection. Seize ownership from
TrustedInstaller. Grant Everyone full control so the file becomes movable. Rename it so the service
host can no longer find it. Then — and this is the part worth noticing — hand ownership back to
TrustedInstaller and strip the Everyone grant off the renamed file.

Those last two steps do nothing for the attack. The DLL is already gone from its path; the service is
already broken. They exist to clean up after the first two, so that anyone who later inspects the file
sees an ordinary TrustedInstaller-owned object with an ordinary ACL. That is a deliberate defeat of the
obvious detection, and it has a direct consequence for how this is hunted: **the current ACL state is
not the artifact**. Auditing System32 for weak permissions returns clean on a host this has been run
against. What remains is the absence of the DLL from its expected path, the presence of a `_BAK`
sibling, and the command-line and 4670 records from the moment it happened.

Two of those three are durable, and one is not. Filenames rotate; `_BAK` is this campaign's choice and
not a law of nature. The version that generalizes is the *absence*: a service host DLL that Windows
servicing says should exist at a packaged path and does not. That check needs no knowledge of the
attacker's naming convention, holds against every variant of this technique, and can be run as an
inventory across the estate rather than as an event query.

The command line does offer one unusually clean pivot in the meantime. `*S-1-1-0` is the well-known SID
for Everyone, and granting Everyone full control over a file in `C:\Windows\System32` is not something
legitimate administrative tooling does. Searching process command lines for that literal string costs
nothing and has a very small benign population.

It is also worth situating this in the wider sequence, because the file work does not happen alone.
Microsoft observed it running alongside `sc config ... start= disabled` against `wuauserv`, `UsoSvc`,
`uhssvc` and `WaaSMedicSvc`; a `NoAutoUpdate` policy write; `Start = 4` on the WaaSMedicSvc service key;
deletion of `C:\Windows\SoftwareDistribution`; Defender exclusion writes via `Add-MpPreference`; and
`vssadmin delete shadows /all /quiet`. Any single element is arguable. The cluster, inside one process
tree, descending from an executable in `C:\Users\Public\<random>\<random>.exe`, is not.

The consequence is what makes this worth prioritising over other tamper hunts. Defender exclusions can
be removed and services can be re-enabled, but a host whose update stack has been dismantled at the file
layer stays unpatched indefinitely, reports no update failures because the machinery that would report
them is gone, and quietly ages into every subsequent vulnerability. [[H172]] covers an unrelated
intrusion where `icacls.exe` appears as a post-exploitation child of `w3wp.exe`, which is a useful
contrast: same binary, entirely different meaning, and the parent is what separates them.

## Why

- **It defeats the self-healing that most defenders are implicitly relying on.** Detections for update
  tampering usually watch service state, and service state is exactly what Windows Update Medic Service
  restores. Removing the Medic service's own DLL from disk takes the repair mechanism out of the loop
  entirely, which turns a temporary evasion into a permanent one and makes the file layer, not the
  service layer, the place this has to be caught.
- **The cleanup steps mean the obvious detection returns clean.** Restoring TrustedInstaller ownership
  and stripping the Everyone grant after the rename serves no operational purpose except to defeat a
  later permissions review. Any hunt built on "find System32 files with weak ACLs" reports nothing on a
  compromised host. Recognising that the ACL is transient — and pivoting to file absence and to the
  historical 4670 and command-line records — is the difference between this hunt working and quietly
  failing.
- **Absence is the version of this that survives the next campaign.** `_BAK` is a naming choice, `WaaSMedicSvc`
  is one target among several, and both will change. A servicing-derived inventory question — which
  packaged system DLLs are not present at their expected paths — needs no attacker knowledge at all,
  runs as a fleet sweep rather than an event query, and catches every variant including ones that
  delete rather than rename.
- **`*S-1-1-0` on a System32 path is close to a free high-fidelity signal.** Granting Everyone full
  control over a Windows system binary is not a thing competent administrative tooling does. It is one
  string, it is cheap to search across process command lines, and its benign population is small enough
  to enumerate. Even where the rest of this hunt is out of reach, that single query is worth deploying.
- **The damage is cumulative, silent, and gets attributed to something else.** An unpatched host is not
  an incident anyone opens. It reports no update errors, because the component that would report them
  has been removed, so patch-compliance dashboards show a stale timestamp rather than a failure. Months
  later the host is exploited through a vulnerability that was patched long ago, and the root cause looks
  like a compliance gap rather than the deliberate act it was.
- **The cluster is what makes it conclusive, and the cluster is free once you have the process tree.**
  Individually, `takeown` is administrative, `sc config` is administrative, a registry policy write is
  administrative. Together, inside one process tree, within seconds, descending from a randomly-named
  executable in a world-writable directory, they form a sequence with no legitimate analogue. Hunting the
  tree rather than the tool is what separates this from the deployment scripts that share its binaries.
