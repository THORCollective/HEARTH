  An adversary who has bypassed authentication on an internet-reachable Cisco Secure Firewall

false_positive_notes: |
  An FMC is a purpose-built appliance running a narrow, vendor-defined workload, which makes its legitimate behaviour far more constrained than a general-purpose server — and that is the main reason these conditions are low-noise. `package_info.pl` is a genuine Cisco utility and it does run legitimately during package installation, upgrade and patching, so the discriminator is never the utility itself. It is the target: legitimate invocations operate on vendor-supplied packages in the appliance's own update directories, whereas the attack invokes it against a file the actor staged in `/var/tmp`. Expect real matches around scheduled maintenance windows, and correlate against the organisation's own change records — an invocation during an approved upgrade with a vendor-named package is routine, the same invocation at 03:00 on a file called `license.tmp` is not. Files legitimately appear in `/var/tmp` during upgrades and troubleshooting, and Cisco TAC procedures occasionally direct administrators to place files there, so `/var/tmp` occupancy alone is weak; the pairing with `package_info.pl` execution is what matters. The Tomcat webroot has a fixed, vendor-defined file inventory that changes only at upgrade, so any `.jsp` outside that inventory is close to self-evidently malicious — this is one of the cleanest conditions available on an appliance. `OmniQuery.pl` is likewise a real internal tool, but a query selecting `name, auth_data` from the users table is a credential-dumping operation regardless of which binary issues it, and has no legitimate administrative equivalent. The most important caveat is not false positives but false NEGATIVES: once the actor has root they can edit or delete on-box logs, so an absence of findings in appliance-local logging is not evidence of absence, and off-box forwarding is the only trustworthy source.

# H317

Cisco Talos reported active, multi-cluster exploitation of Secure Firewall Management Center, chaining CVE-2026-20079 — an unauthenticated authentication bypass scoring CVSS 10.0 that yields root — with CVE-2026-20316, which lets a remote attacker log in as a low-privileged user and is used to escalate. What makes the post-exploitation worth a dedicated hunt is that three separate clusters converged on the same living-off-the-appliance primitive: write a Makeself self-extracting archive to `/var/tmp/license.tmp`, then invoke the appliance's own `/usr/local/sf/bin/package_info.pl` against it with `--lsm` and let Cisco's signed management utility unpack and execute it as root. Alongside it, `home.jsp` is dropped into the Tomcat webroot and the bundled JRE runs a `cmd.jar` command executor that queries the FMC's own user table for `auth_data`. The outcomes ranged from Cyclops Blink persistence in `/etc/init.d/` and SOCKS5/reverse-SSH tunnels forwarding Active Directory ports, to harvested configurations for every managed firewall, to Qilin ransomware.

## Why

- **Compromising the management plane compromises everything it manages.** An FMC holds credentials for, and configuration of, every firewall in its scope. Talos observed exactly that being harvested. This is not one appliance's worth of exposure — it is the security control plane, which makes the blast radius categorically different from an ordinary server compromise and justifies hunting it specifically rather than as part of a general server sweep.
- **Appliances have a narrow, vendor-defined normal, which makes weak-looking conditions strong.** On a general-purpose server, "an unexpected file in the webroot" or "an outbound connection" would be hopeless signals. On an FMC the legitimate webroot inventory is fixed between upgrades and the set of destinations the appliance should ever contact is short and enumerable, so a diff and a destination allowlist do work here that would be impractical anywhere else.
- **Living off the appliance's own tooling defeats binary-centric detection entirely.** There is no malicious executable to catch in the root-execution step — `package_info.pl` is Cisco's, it is signed, and it is doing its documented job. Detection has to key on the pairing of a legitimate utility with an illegitimate target, which is a genuinely different query shape from the one most detection content is built around.
- **Three independent clusters reached for the same primitive, so it will outlast this campaign.** When separate actors converge on one technique, that technique is a property of the platform rather than of a toolkit, and a detection built on it keeps paying after the current IOCs are dead. The port list they tunnelled — 389, 636, 88, 445, 135, 5985 — also tells you where they were going next, which is where the follow-on hunt belongs.
