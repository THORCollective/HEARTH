false_positive_notes: |
  Each command on its own has legitimate use, which is why this hunt keys on the conjunction rather than on any single binary. `reagentc /disable` is run by imaging and deployment workflows (MDT, SCCM task sequences, OEM provisioning) immediately before `reagentc /setreimage` and `/enable` to re-point WinRE at a new image, and by administrators resizing the recovery partition to fix the well-known WinRE servicing failures — both of which are followed within minutes by `reagentc /enable`, so a `/disable` with no subsequent `/enable` is the first discriminator. `diskpart /s` is used by build scripts to partition new disks and by the same recovery-partition resize procedure; `cipher /w` is used by decommissioning and data-sanitisation runbooks. What legitimate activity does not do is disable WinRE, wipe free space, and clear event logs from one parent within a short window on a production server or user endpoint outside a documented rebuild. Scope out imaging and provisioning hosts explicitly, and treat any hit on a domain controller or file server as high priority.

[[H026]] hunts `cipher /w` on its own as an anti-forensics step; this hunt differs by keying on the conjunction of free-space wiping with WinRE disablement, recovery-partition removal and a log-clearing burst, which is what places it in the pre-encryption window rather than in general anti-forensics. # H348

Huntress's September 2026 write-up of two Settra ransomware intrusions is mostly about access: MeshAgent installed for persistence, renamed `mvtcs.exe` in one case and left unmodified in the other, talking to operator infrastructure for days before anything was encrypted. The last few minutes before encryption are the part worth hunting, though, because the operators did not use the recovery-impairment commands most detections are built around.

There was no `vssadmin delete shadows`, no `bcdedit /set recoveryenabled no`, no `wbadmin delete catalog`. Instead the operators ran `reagentc /disable` to take the Windows Recovery Environment out of the boot path, invoked `diskpart` with a script file, and ran `cipher /w:D:\ >nul 2>&1` against each volume. That last command is a data-sanitisation feature: it overwrites all free space on the volume so that previously deleted files cannot be recovered by carving. The ransomware then tried to clear twelve event log channels, including Sysmon, PowerShell, WinRM and Task Scheduler.

It got one wrong. The embedded list names `Microsoft-Windows-Windows-Defender/Operational`, a channel that does not exist, so the real Defender operational log survived. That is a useful detail for responders and a reminder that the anti-forensic stage is itself a detection opportunity. Every one of these commands runs in a tight window, from the same parent, just before encryption starts.

## Why

- It closes a gap in the most commonly deployed ransomware analytics. Detections for pre-encryption recovery impairment overwhelmingly key on `vssadmin`, `bcdedit` and `wbadmin`, and Settra's operators used none of them — `reagentc` and scripted `diskpart` achieve the same outcome through commands those rules do not cover, and `cipher /w` is usually hunted only as a standalone anti-forensics step.
- The conjunction is rare and the individual commands are not. `reagentc /disable`, `diskpart /s` and `cipher /w` each have legitimate imaging or sanitisation uses, but a WinRE disable with no follow-up `/enable`, a free-space wipe of every volume, and an event log clearing burst from one parent within minutes is not an administrative workflow.
- `cipher /w` specifically targets the responder, not just the victim. Shadow-copy deletion prevents restoration; free-space wiping prevents forensic recovery of deleted tooling and staging files, so catching it early preserves evidence the investigation will need.
- It fires before encryption finishes. On a host where these commands appear, encryption is usually minutes away, so the hunt converts into an isolation decision that can still limit how many hosts are encrypted.
- The file-system side effects make it robust to missing command-line logging. `ReAgent.xml` changes and the `EFSTMPWP` working directory that `cipher /w` creates are visible in file telemetry alone, so the hunt still works in environments where process command lines are not collected.
