false_positive_notes: |
  Each command on its own has legitimate use, which is why this hunt keys on the parent and the conjunction rather than on any single binary. `reagentc /disable` is run by imaging and deployment workflows (MDT, SCCM task sequences, OEM provisioning) immediately before `reagentc /setreimage` and `/enable` to re-point WinRE at a new image, and by administrators resizing the recovery partition to fix WinRE servicing failures — both of which are followed within minutes by `reagentc /enable`, so a `/disable` with no subsequent `/enable` is the first discriminator. `diskpart /s` is used by build scripts to partition new disks and by the same recovery-partition resize procedure; `cipher /w` is used by decommissioning and data-sanitisation runbooks. Those workflows launch these tools from `cmd.exe`, `powershell.exe`, a task-sequence engine or a management agent. What legitimate activity does not do is launch `reagentc /disable` and `diskpart /s` directly from an unrecognised executable in `C:\PerfLogs\` or a user profile. Scope out imaging and provisioning hosts explicitly.

# H348

Huntress's September 2026 write-up of two Settra ransomware intrusions is mostly about access: MeshAgent installed for persistence, renamed `mvtcs.exe` in one case and left unmodified in the other. The part worth hunting is what the ransomware executable does once it runs, because it does not use the recovery-impairment commands most detections are built around.

There was no `vssadmin delete shadows`, no `bcdedit /set recoveryenabled no`, no `wbadmin delete catalog`. In both intrusions the ransomware ran `reagentc /disable` to take the Windows Recovery Environment out of the boot path and invoked `diskpart` with a script file that Huntress assesses was used to remove the recovery partition. In September Huntress confirmed these commands "were embedded in the ransomware executable, and launched as a child process of that executable image." In the July intrusion there was also `cmd.exe /c cipher /w:D:\ >nul 2>&1` across multiple volumes, a data-sanitisation feature that overwrites free space so previously deleted files cannot be carved back, and an attempt to clear twelve event log channels, including Sysmon, PowerShell, WinRM and Task Scheduler.

One of those channel names was wrong. Huntress notes the Defender entry is misspelled, so the Defender operational log survived — a useful detail for responders. More useful for hunters is the structure: two built-in Windows recovery tools launched directly by an unrecognised executable named after the victim's own domain, which is not how any imaging or maintenance workflow runs them.

## Why

- It closes a gap in the most commonly deployed ransomware analytics. Detections for recovery impairment overwhelmingly key on `vssadmin`, `bcdedit` and `wbadmin`, and Settra used none of them — `reagentc` and scripted `diskpart` achieve the same outcome through commands those rules do not cover.
- The parent is the discriminator. Imaging, provisioning and repair workflows run `reagentc` and `diskpart` from shells, task-sequence engines or management agents, and re-enable WinRE afterwards. Both tools spawned directly by an unknown executable, with no re-enable, is not an administrative pattern.
- It fires while encryption is running. On a host where these commands appear the ransomware is already executing, so the hunt converts into an immediate isolation decision that can still limit how many hosts are encrypted, and into a fleet-wide sweep for the same parent hash.
- `cipher /w`, where present, targets the responder. Shadow-copy deletion prevents restoration; free-space wiping prevents forensic recovery of deleted tooling and staging files, so catching it early preserves evidence the investigation will need.
- The file-system side effects make it robust to missing command-line logging. `ReAgent.xml` changes and the `EFSTMPWP` working directory that `cipher /w` creates are visible in file telemetry alone, so parts of the hunt still work where process command lines are not collected.
