false_positive_notes: |
  Each stage of this chain has a benign population, which is why the chain and not any single stage is the hunt:
  - `certutil -decode` is used legitimately by installers, certificate tooling and some administrative scripts. It is also a long-known LOLBin and most environments already have a rule for it. The discriminator here is the *producer* of the input file: a file assembled by several appends from a PowerShell process whose ancestor is a database engine.
  - `sqlservr.exe` legitimately spawns processes in a few shapes: SQL Agent jobs (via `sqlagent.exe`, usually with `cmd.exe` or `powershell.exe` children running known job steps), SSIS package execution (`DTExec.exe`, `ISServerExec.exe`), external script execution for R/Python (`launchpad.exe`, `rterm.exe`, `python.exe` under `MSSQLLaunchpad`), and CLR assemblies. Enumerate the SQL Agent job steps on each instance so a legitimate child can be matched to a job definition by command line; anything not in that list is the finding.
  - Backup, monitoring and patching agents write to `C:\ProgramData` constantly, and some write base64. The constraint that removes them is the append pattern combined with the subsequent decode and execute of the same path.
  - Reading `rsreportserver.config` is normal for the Reporting Services service account and for configuration tooling (`rsconfig.exe`, the Reporting Services Configuration Manager). Alert on reads by any other identity, especially by a PowerShell process.

  Process lineage - Core filter: any process whose ancestry includes `sqlservr.exe` and which is `powershell.exe`, `pwsh.exe`, `cmd.exe`, `certutil.exe`, `wscript.exe` or `cscript.exe`, excluding the SQL Agent and SSIS and external-script shapes listed in the false-positive notes. Triage values: `ParentImage`, `ParentCommandLine`, `Image`, `CommandLine`, `User`, `IntegrityLevel`, `ProcessGuid`, `CurrentDirectory`. Kaspersky states that "The first malicious commands on the victims' systems in the campaign under investigation originated from the sqlservr.exe process, indicating the likely initial access vector and the context in which the attackers gained the ability to execute code." Strong red flags: the child runs as the SQL service account and writes outside the instance's data and log directories; `-EncodedCommand` or a long base64 argument - Kaspersky notes that "When a request is received from the operator, the commands to be executed are additionally encoded in Base64 to bypass keyword-based detection."
  Sample Defender XDR query - a SQL Server-rooted shell that leads to a certutil decode:
  ```kql
  let lookback = 30d;
  let sqlChildren = DeviceProcessEvents
      | where Timestamp > ago(lookback)
      | where InitiatingProcessFileName =~ "sqlservr.exe"
      | where FileName in~ ("powershell.exe", "pwsh.exe", "cmd.exe", "certutil.exe", "wscript.exe", "cscript.exe")
      | project SqlTime = Timestamp, DeviceId, DeviceName, SqlChildPid = ProcessId,
                SqlChildCmd = ProcessCommandLine, SqlChildFile = FileName, AccountName;
  let decodes = DeviceProcessEvents
      | where Timestamp > ago(lookback)
      | where FileName =~ "certutil.exe"
      | where ProcessCommandLine has_any ("-decode", "/decode", "-decodehex", "/decodehex")
      | project DecodeTime = Timestamp, DeviceId, DecodeCmd = ProcessCommandLine,
                DecodeParent = InitiatingProcessFileName;
  sqlChildren
  | join kind=inner decodes on DeviceId
  | where DecodeTime between (SqlTime .. SqlTime + 30m)
  | project SqlTime, DecodeTime, DeviceName, AccountName, SqlChildFile, SqlChildCmd, DecodeParent, DecodeCmd
  | order by SqlTime desc
  ```
  The `between (SqlTime .. SqlTime + 30m)` bound is required: joining on `DeviceId` alone over a 30-day lookback pairs a SQL Server child process on one day with an unrelated certutil decode on another. `DeviceProcessEvents` retains 30 days in Defender XDR advanced hunting, so `ago(30d)` is the maximum useful lookback there - a longer value is silently truncated.
  The fragment-append pattern - Core filter: in Sysmon Event ID 11, a single file path receiving multiple create/modify events from one PowerShell process within a short window, with a `.b64`, `.txt` or extensionless name under `C:\ProgramData`, `C:\Windows\Temp`, `C:\Temp` or `C:\Windows`. Kaspersky reports that the attackers "split the malicious payload into multiple files" and that "Below is a sequential record of several script fragments written to the file d3.b64." Note that Sysmon Event ID 11 fires on file creation and on some modifications depending on configuration, so the repeated-append shape may appear as one create followed by nothing - in that case fall back to script block logging, where each `Add-Content`/`Out-File -Append` call is visible in `ScriptBlockText`, or to the file's size growing across successive EDR snapshots. `d3.b64` and `dsn_line.txt` are names from one incident; hunt the shape, and use the names only as a quick grep over existing telemetry. Triage values: `TargetFilename`, `Image`, `ProcessGuid`, `User`, file size at each event, `Hashes`.
  PowerShell script block logging - Core filter: 4104 `ScriptBlockText` containing DPAPI unprotect calls (`CryptUnprotectData`, `[System.Security.Cryptography.ProtectedData]::Unprotect`, `ProtectedData` with `DataProtectionScope`), or the SSRS configuration path. This is the only telemetry that shows the decoded intent; `DeviceEvents` with `ActionType == "PowerShellCommand"` records cmdlet *names* only, never script text, so it cannot be used for this and aggregating it per process with `make_set` is the most it can offer. Correlation: the same script that unprotects the blob usually also reads the staging file created in the previous stage. Strong red flags: a `ScriptBlockText` referencing `rsreportserver.config` from a non-SSRS identity; Chinese-language comments in the script body, which Kaspersky observed - "some of the scripts delivered and executed as described above contain comments in Chinese".
  The credential target - Core filter: reads of the SSRS configuration file (`rsreportserver.config`, under the Reporting Services `ReportServer` directory) by any process other than the Reporting Services service, and creation of a plaintext staging file holding its DSN. Kaspersky describes a command that "searches for a DSN string containing connection settings in the SQL Server Reporting Services configuration file rsreportserver.config and copies its contents to dsn_line.txt", and a decoded script that "is a tool for decrypting DPAPI secrets from the file C:\ProgramData\dsn_line.txt." Triage values: file path read, reading process image and command line, identity, subsequent file writes. Note that Sysmon does not record file reads; use EDR file-access telemetry, an audit SACL on the file, or infer the read from the script block that performs it. Strong red flags: the staging file being deleted shortly after the decode; a new SQL login or a successful SQL authentication from a new host using the recovered credentials in the following hours.
  Hardening and follow-on - Core filter: once confirmed, check whether `xp_cmdshell` or `Ole Automation Procedures` were enabled on the instance and when, and confirm the SQL Server service account is not a local administrator or a domain account with broad rights. Kaspersky reports the initial access was "a compromised SQL Server (version 16.0.1000)". The DSN credentials recovered here are the pivot, so audit what that account can reach.
  Expected, not observed by Kaspersky: the same fragment-and-decode pattern works with `expand.exe`, PowerShell's own `FromBase64String`, or `bitsadmin` in place of `certutil`, and the same DPAPI-protected-configuration target exists in other Microsoft server products that store connection strings machine-encrypted. Kaspersky's report names `certutil` and the Reporting Services configuration file specifically.

# H451

Kaspersky's investigation of a campaign using CyberStrikeAI - an open-source Go framework that puts an LLM orchestrator on the command-and-control server, where it plans actions, selects tools and generates the commands an ordinary C2 implant then executes - contains a sequence worth hunting on its own merits, independently of anything AI-related about the intrusion.

The entry point was a database server. Kaspersky writes that "The first malicious commands on the victims' systems in the campaign under investigation originated from the sqlservr.exe process, indicating the likely initial access vector and the context in which the attackers gained the ability to execute code."

What happened next is a defence-evasion pattern that defeats both static detection and casual review. Rather than writing one script, "the attackers split the malicious payload into multiple files" - Kaspersky shows "a sequential record of several script fragments written to the file d3.b64" - and then "the attackers used the certutil utility to decode the resulting file and executed it." Any single write is a short base64 string with no detectable content. Only the assembled file is a program, and it exists as a program for the moments between the decode and the execution.

The decoded program's purpose is the part that makes this worth a hunt rather than a signature. It is, in Kaspersky's words, "a tool for decrypting DPAPI secrets from the file C:\ProgramData\dsn_line.txt" - a file populated by a command that "searches for a DSN string containing connection settings in the SQL Server Reporting Services configuration file rsreportserver.config and copies its contents to dsn_line.txt." SQL Server Reporting Services stores its connection string DPAPI-encrypted under the machine's context, so an operator already running as the service can simply ask Windows to decrypt it. No exploit, no credential dumping, no LSASS access - just a configuration file and an API call.

Kaspersky's own assessment of this campaign is that "the introduction of AI into the attack chain does not yet present fundamentally new challenges for detection", and this chain is the proof: every stage is a well-understood Windows behaviour. What the orchestrator changed is how quickly they were composed - "establishing persistence and conducting local reconnaissance within 2 minutes" - and that argues for hunting the chain rather than alerting on its stages one at a time.

## Why

- Fragmented staging is specifically designed to beat the controls most environments rely on. A rule on PowerShell command-line length, on base64 entropy, or on a script file's content sees four innocuous appends. The chain - several writes to one path, then a decode of that path, then an execution of the decoded path - is detectable in three ordinary Sysmon events and does not depend on the fragment size or the file name.
- `sqlservr.exe` has a small, enumerable set of legitimate children. Unlike a browser or a mail client, a database engine's process tree is defined by its SQL Agent job steps, its SSIS packages and its external-script configuration. That makes the parent filter unusually precise, and it makes the exception list something a DBA can produce in an afternoon.
- DPAPI-protected configuration is a credential source that leaves no credential-access telemetry. Nothing touches LSASS, no hive is dumped, no ticket is requested. The only evidence is the script that calls the unprotect API, which is why this hunt treats PowerShell script block logging as a prerequisite rather than an optional enrichment.
- The recovered credential is a database connection string, which is rarely scoped as tightly as its blast radius deserves. A Reporting Services DSN typically reaches a database holding business data and frequently uses an account with rights beyond that one database - so the value of catching this stage is much higher than the value of catching the generic `certutil` decode that sits inside it.
