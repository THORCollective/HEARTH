false_positive_notes: |
  Firewall profile changes delivered by Group Policy are a completely normal administrative act, so the technique alone is not the signal — the provenance of the policy is. Established firewall GPOs are long-lived, carry a stable GUID that appears in months of Group Policy History, are linked at an OU rather than the domain root, and are edited by a small and knowable set of accounts. Tune by building that inventory first (see B046) and alerting on deviation from it rather than on the firewall setting itself. Expect legitimate noise from: a genuine security-baseline rollout or a migration to a third-party firewall or EDR-managed firewall, which will be accompanied by a change record and will typically disable only one profile or set `EnableFirewall` on a scoped OU; lab, imaging and VDI gold-image OUs where the firewall is intentionally off; and Microsoft Security Compliance Toolkit or LGPO imports during a baseline refresh. The combination that is genuinely rare and should be treated as high-signal is a GPO created and linked at the DOMAIN ROOT within the same short window, disabling ALL THREE profiles, by an account that has never previously created a GPO. Also note that a newly created GPO with no links at all is not benign-by-default — linking is the second half of the operation and may simply not have happened yet, so a fresh `groupPolicyContainer` from an unusual creator still deserves review.

  Domain controller, GPO creation and linking (authoritative evidence) - Core filter: Security event 5137 where `Object Class` is `groupPolicyContainer`, followed within minutes by Security event 5136 where `Attribute LDAP Display Name` is `gPLink` and the `Object DN` is the domain naming context itself (for example `DC=contoso,DC=local`) rather than a child OU. Triage values: `Subject Account Name`, `Subject Logon ID`, `Object DN`, `Object GUID`, `Attribute Value`, `Correlation ID`. Strong red flags: the creating account has no prior 5137 history; creation and domain-root link occur inside the same logon session; the operation runs outside a change window. In the Kaspersky PAYLOAD intrusion two GPOs were created and linked at the domain root on the same day, `{C897F2C7-C2AC-4E6F-BF48-58036FF29E79}` (PAYLOAD) and `{22099AD2-E062-4F56-B574-5099BBA4E7A6}` (Win Firewall Off), the second of which existed only to turn the firewall off.
  Domain controller, which client-side extension will execute - Core filter: Security event 5136 where `Attribute LDAP Display Name` is `gPCMachineExtensionNames` and `Attribute Value` contains the Registry CSE GUID `{35378EAC-683F-11D2-A89A-00C04FBBCFA2}`. This attribute is what tells every domain member to actually process the registry settings in the policy, so a change to it is the commit point of the attack. Pivot: also watch `gPCFileSysPath` (points the GPO at its SYSVOL content) and `versionNumber` (increments on every edit). Note the Elastic prebuilt rule for GPO privilege addition keys on this same attribute with the SECURITY CSE GUID `{827D319E-6EAC-11D2-A4EA-00C04F79F83A}` — that rule will NOT fire on this campaign, because a registry-policy GPO carries a different CSE.
  SYSVOL content, what the policy actually sets - Core filter: file writes under `\\<domain>\SYSVOL\<domain>\Policies\{GPO-GUID}\Machine\` via Security event 4663 or Sysmon event 11. The firewall values land in `Machine\Registry.pol`, which is a binary file — parse it with `Parse-PolFile` (PolicyFileEditor module) or `LGPO.exe /parse` rather than grepping it. Strong red flags: any non-policy file type staged in the policy directory (the same intrusion staged `payload.jpg` and `hello.txt` in SYSVOL for use as wallpaper and lock screen) and any `.ps1`, `.bat`, `.vbs` or `.exe` under `Machine\Scripts\`.
  Endpoint registry, where the firewall is actually turned off - Core filter: a write of `EnableFirewall = 0 (DWORD)` under `HKLM\SYSTEM\CurrentControlSet\Services\SharedAccess\Parameters\FirewallPolicy\DomainProfile`, `\StandardProfile` and `\PublicProfile`. The policy-delivered variant also writes the mirrored keys under `HKLM\SOFTWARE\Policies\Microsoft\WindowsFirewall\<Profile>\EnableFirewall`, and it is the `SOFTWARE\Policies` path that proves the change came from Group Policy rather than a local administrator. Defender XDR: `DeviceRegistryEvents | where RegistryKey has "FirewallPolicy" or RegistryKey has @"Policies\Microsoft\WindowsFirewall" | where RegistryValueName == "EnableFirewall" and RegistryValueData == "0" | summarize DeviceCount = dcount(DeviceName), make_set(InitiatingProcessFileName) by bin(Timestamp, 1h)`. Strong red flag: the writing process is `svchost.exe` (the Group Policy client, `gpsvc`) rather than `netsh.exe`, `mmc.exe` or `powershell.exe` — that is the tell that this arrived as policy. The estate-wide fan-out is the other tell: hunt on DEVICE COUNT per hour, not on the single event. Dozens or hundreds of hosts writing the same value inside one Group Policy refresh interval (90 minutes plus up to 30 minutes of jitter by default) is not something a local administrator can produce.
  Endpoint firewall audit, the policy-aware events - Core filter: Security event 4954 (Group Policy settings for Windows Firewall changed) and 4950 (a Windows Firewall setting changed), with `Profile Changed` and `New Setting`. These fire specifically on the policy path and are the cleanest single corroboration that the change was pushed rather than local. Correlation: 4954 arriving on many hosts within one refresh window and matching the GPO GUID seen in 5137 on the DC closes the loop from directory object to endpoint effect.
  Negative control, why the usual rules miss this - Core filter: confirm the ABSENCE of Security event 4688 / Sysmon event 1 for `netsh.exe advfirewall set * state off`, `netsh firewall set opmode disable` and `Set-NetFirewallProfile -Enabled False` on the affected hosts during the window. Every widely deployed Sigma, Elastic and Splunk detection for this technique is process-creation based. If the firewall is off across the fleet and none of those rules fired, the delivery mechanism was Group Policy and the investigation belongs on the domain controller, not the endpoint.

# H300

In April 2026 Kaspersky documented a PAYLOAD ransomware intrusion that reached its objective almost entirely through Active Directory. The operators authenticated to a FortiGate SSL VPN with a compromised domain credential that held GPO creation and linking rights, then created two Group Policy Objects and linked them at the domain root. One delivered the ransom note, wallpaper and logon banner. The other, named "Win Firewall Off", did nothing but disable the Windows Firewall on every domain-joined machine in the environment. No firewall command ever ran on an endpoint. No ransomware binary was needed for that stage at all.

This is the part worth hunting, because it is a detection-coverage inversion rather than a novel capability. Search any public rule corpus for this technique and you get `netsh.exe` — the SigmaHQ process-creation rules, the Elastic EQL rule, the Atomic Red Team tests, the Splunk analytics. All of them watch a command line. Group Policy never produces one. The firewall is disabled by the Group Policy client service writing a registry value under `HKLM\SOFTWARE\Policies\Microsoft\WindowsFirewall\`, which on the endpoint looks like `svchost.exe` doing exactly what it is supposed to do. The defensive leverage sits in two places instead: the directory service change events on the domain controller that recorded the GPO being created and linked, and the fan-out shape on the endpoint, where the same registry write appears across hundreds of hosts inside a single Group Policy refresh interval — a distribution no local administrator and no single compromised endpoint can produce.

The hunt is deliberately scoped to the firewall-disable outcome rather than to GPO abuse in general. GPO modification is a broad technique with a wide legitimate surface; "all three firewall profiles turned off by a policy object that was created and linked at the domain root in the same logon session" is narrow enough to query directly and rare enough to review by hand. B046 builds the baseline of normal GPO administration that makes the provenance half of this hunt precise, and H301 covers the defacement payload the same two GPOs delivered.

## Why

- The technique has near-total public detection coverage against the wrong delivery mechanism. Every mainstream rule for disabling the Windows Firewall keys on `netsh.exe` or `Set-NetFirewallProfile` process creation, and a GPO-delivered change generates neither, so an environment can be fully "covered" on paper and completely blind in practice.
- Disabling the firewall estate-wide is a precondition, not an endpoint. In the source intrusion it preceded lateral movement, service stops and encryption; catching it buys time inside the intrusion rather than after it, and it fires while the operator still has to come back and use the access they just opened.
- Every stage is natively observable with telemetry most environments already license: 5137 and 5136 on the DC, Sysmon 13 or `DeviceRegistryEvents` on the endpoint, and firewall audit events 4950 and 4954 that exist specifically to distinguish a policy-driven change from a local one. The common failure is not missing data sources but the DS Access audit subcategory being off by default on domain controllers.
- The fan-out is the discriminator that makes this high-precision without any IOC. One host writing `EnableFirewall = 0` is an administrator. Two hundred hosts writing it within one Group Policy refresh window is a policy object, and a policy object linked at the domain root that did not exist yesterday is an intrusion.
- Group Policy is a late-stage technique, so a true positive is also a reliable indicator that a privileged account is already fully compromised — the finding scopes the incident upward immediately rather than producing an isolated endpoint alert.
