  Most shellcode injection hunts rest on a remote thread being created, and this one deliberately
  does not create any. Kaspersky documents that OpsAgent, the implant AuditTeam uses, offers two

false_positive_notes: |
  Debuggers legitimately do every single thing this hunt looks for. WinDbg, Visual Studio, x64dbg, dnSpy, OllyDbg and gdb variants all create processes with debug flags, attach to running processes and set hardware breakpoints, because that is their function. Host role is the primary filter - a debug relationship on a developer workstation is the tool working; the same relationship on a file server or a finance workstation is the finding.

  Crash-reporting and telemetry agents hold debug-adjacent handles routinely. `WerFault.exe` is the obvious one, and several commercial crash handlers, application performance monitors and anti-cheat systems attach to processes they supervise. Enumerate these per estate and exclude by image path and signer rather than trying to separate them behaviourally.

  Security products themselves are heavy users of process-access handles with broad masks. An EDR agent opening every process on the box with `PROCESS_VM_READ` is normal and will dominate Sysmon Event ID 10 volume. Exclude the estate's own agents explicitly first, or this hunt returns nothing but its own tooling.

  Hardware debug registers are genuinely rare in telemetry, but mostly because nothing records them. Standard Windows auditing does not log `SetThreadContext` or `Dr0` through `Dr7` manipulation at all, so the absence of hits is much more likely to mean the absence of visibility than the absence of the technique. Treat a silent result here as an instrumentation gap to close, not as a clean estate.

  Kaspersky names `FileTimeToSystemTime` as the function this implant breakpoints, and that specific choice will not survive a rebuild - it is an arbitrary, frequently-called, harmless API chosen because it is reliably hit soon after process start. Any similarly common function serves the same purpose. The structure, a breakpoint on an innocuous API used as an execution trigger, is the durable part; the function name is this build's choice.

  Kaspersky also states that by default these commands use `msiexec.exe` as a host process, but the path can be changed, and that the `monitor` command uses `notepad.exe` instead. So an image-name allowlist will be bypassed by configuration. H518 covers the host-process and named-pipe side of the same job mechanism.
notes: |
  Leg one, the debug relationship (Sysmon Event ID 10, plus Event ID 1) - Core filter: a process opening another with debug-capable access, where the opener is not on the approved debugger and crash-handler list. This is the highest-value query in the hunt because the debug relationship is structurally required by the technique and cannot be configured away.

      Sysmon Event ID 10 where
        GrantedAccess has any of 0x1F0FFF, 0x1F1FFF, 0x1FFFFF
        and SourceImage not in (approved debuggers, crash handlers, EDR agents)
        and TargetImage ends with "\msiexec.exe" or "\notepad.exe"

  `0x1F0FFF` is `PROCESS_ALL_ACCESS` on older builds and the masks above are the full-access variants; a debugger attaching needs broad rights, so a wide mask on a non-debugger opener is the signal. Keep the `TargetImage` clause as a ranking input rather than a filter, since Kaspersky states the host path is configurable. The `CallTrace` field is where this query earns its keep - a call stack passing through `ntdll.dll` debug or context functions, with no corresponding thread-creation event anywhere in the tree, is the DbgInjector shape rather than the Legacy one.

  Leg two, the absence that defines it. Run the two modes side by side so the contrast is visible, because the point of this hunt is the negative. Legacy mode, per Kaspersky, uses `CreateProcessA` and `NtCreateThreadEx`, which produces a Sysmon Event ID 8 `CreateRemoteThread` record or a thread-creation event in EDR telemetry. DbgInjector produces none, because RIP is redirected on an existing thread. So the triage question on any suspicious `msiexec.exe` or `notepad.exe` is not "did a remote thread get created" but "is there a process-access handle and a parent that has no reason to hold one". An analyst who checks only for remote-thread events will clear this cleanly and wrongly.

  Leg three, the process shape (Sysmon 1 or 4688). The host processes Kaspersky names are `msiexec.exe` for most job commands and `notepad.exe` for the `monitor` keylogging command. Field names matter - Sysmon exposes `Image`, `ParentImage` and `IntegrityLevel`; Windows Security 4688 exposes `New_Process_Name` and `Creator_Process_Name` and has no Sysmon-style integrity field, so a 4688 query written with Sysmon field names returns nothing silently. Red flags in weight order - an `msiexec.exe` with no installer package on its command line at all, which is the strongest single indicator because legitimate `msiexec.exe` almost always names an MSI or a product code; a `notepad.exe` with no file argument that is nonetheless doing work; either process parented by something that is not `services.exe`, `explorer.exe` or a known installer; either process alive far longer than an install or an editing session would last.

  Leg four, the jobs that use it, for scoping a hit. Kaspersky states that `mimikatz_spawn`, `execute_assembly`, `pth_spawn`, `runpe`, `monitor start` and `screenshot_service start` run background jobs in a separate process, that each creates a process and a named pipe and receives shellcode from the C2 server, and that no command contains embedded mimikatz or PTH binaries - all payloads arrive remotely through the pipe, XOR-encrypted with key `604902af7b70b271`. The design consequence stated in the report is that this keeps the implant small and lets operators deliver custom payloads remotely. For a hunter that means the on-disk implant will not match a Mimikatz signature and a memory scan of the *host* process is where the credential tooling actually lives. A DbgInjector hit should therefore be followed by an LSASS access review and a credential-reset decision, not just an injection write-up.

  Leg five, the loaders upstream. Kaspersky describes three, which give three different first-stage shapes - a C loader found in April 2026 that injects shellcode into `msiexec.exe` using `CreateProcessA`, `VirtualAllocEx`, `WriteProcessMemory` and `CreateRemoteThread`; a .NET loader found in June 2026 that uses `NtQueueApcThread` instead of direct process creation and contains the strings `DApc`, `DProtect`, `DResume` and `msiexec.exe`; and a Rust loader found in September 2026 that retrieves an encrypted payload from the C2, decrypts it, parses the PE header and runs the `Execute` export within its own process rather than injecting into another. Kaspersky notes the C and .NET loaders are protected by OLLVM obfuscation with control-flow flattening enabled. Only the first two produce remote-thread or APC artefacts; the Rust loader produces neither, which is the same visibility problem as DbgInjector one stage earlier.

  Implant context for triage. Kaspersky assesses the implant, version 5.2.8, as rivalling Cobalt Strike in functionality, with a worker-thread architecture in which the main thread monitors connection health and a worker thread processes commands from a queue. Its C2 protocol runs over WebSocket with TLS, and protocol frame types act as an extra command set enabling SOCKS proxy establishment, chunked file uploads and inter-agent data forwarding. On infrastructure, the implant optionally obtains its C2 address by reading a public GitHub repository, with the address AES-CBC encrypted using the SHA-256 hash of `f4bb8c7e15d8b98d535eb20b09176b3d` as the key and a zero initialisation vector, wrapped with the markers `GetConfig` and `EndConfig` and base64-encoded. Note for scoping that Kaspersky reports the GitHub repository was removed in November 2026, but that this does not mean the campaign is over, as the latest Rust implants found contained a configuration with the GitHub feature disabled.

  Kaspersky also observes that several code patterns suggest LLM-assisted development - WinAPI functions resolved dynamically by hash with the plaintext name sometimes remaining in memory before hashing, and all injection commands sharing near-identical code structures differing only in argument count and target process selection, which it describes as matching LLM-generated scaffolding. That is an assessment about how the tool was built, not a detection input, and is recorded here only because it explains why the injection modes are so uniform.

  Scope note on existing coverage. A grep of every hunt body for `hardware breakpoint`, for `DEBUG_PROCESS` and `DEBUG_ONLY_THIS_PROCESS`, and for `debug state` returns nothing - no existing HEARTH hunt covers injection via a debug relationship or debug-register manipulation. The injection hunts in the corpus key on the mechanisms this one deliberately avoids: remote thread creation, APC queuing, process hollowing and reflective loading. The closest neighbour by family rather than mechanism is H518, which covers the named-pipe job host used by the same implant and is the natural pivot from a hit here.

# H517

Nearly every process injection hunt in existence has the same load-bearing assumption: somewhere, a thread gets created. `CreateRemoteThread`, `NtCreateThreadEx`, a queued APC — something has to start running. Sysmon has an event ID for it. Every EDR watches it.

OpsAgent, the implant Kaspersky attributes to AuditTeam, ships two injection modes. The first, Legacy, does exactly that — `CreateProcessA` and `NtCreateThreadEx`, fully visible. The second is called DbgInjector, and Kaspersky's description of it is four steps long: it creates a process in DEBUG state, allocates shared memory, sets a hardware breakpoint on `FileTimeToSystemTime`, then redirects RIP to the shellcode without creating a new thread.

Read that last clause again. No thread is created. A thread that already exists, inside a process the operator just launched, hits a debug register on a mundane time-conversion API, and the debugger — the implant — changes where that thread is pointing. Execution begins. Sysmon Event ID 8 has nothing to say, because nothing it watches for happened.

What is left is the debugger relationship. To set a debug register on another process's thread and rewrite its instruction pointer, you must be its debugger, with a handle broad enough to do it. That is a structural requirement of the technique, not a configuration choice, and `msiexec.exe` has no business being debugged by anything.

## Why

- It is built specifically to be absent from the event everyone watches. A hunt keyed on remote thread creation will clear this host as clean, which makes the negative result actively misleading. The only way to see it is to hunt the debug relationship instead.
- The debugger handle cannot be configured away. Kaspersky notes the host process path is changeable and the breakpointed function is arbitrary, but redirecting a thread's RIP requires debug-level access to the target. That requirement is the hunt's anchor and survives rebuilds.
- `msiexec.exe` being debugged is close to self-evidently wrong. The Windows Installer is not a debug target in any normal workflow, and legitimate `msiexec.exe` almost always carries a package or product code on its command line. A debug handle plus an empty command line is two independent anomalies on one process.
- Finding it means credential tooling is already resident, because of how the jobs work. The implant embeds no Mimikatz and no pass-the-hash binary — Kaspersky states all payloads arrive remotely through the pipe, XOR-encrypted. So the sensitive code lives only in the injected host process's memory, and a hit implies `mimikatz_spawn` or `pth_spawn` may already have run.
- The silence is probably an instrumentation gap rather than good news. Standard Windows auditing does not record `SetThreadContext` or debug-register writes at all. Running this hunt and finding nothing is a reason to check whether Sysmon Event ID 10 and call-stack capture are even enabled before concluding anything.
- A ransomware crew built this, which is the part worth escalating. Kaspersky's closing assessment is that custom malware frameworks are typically developed and maintained by APT groups with dedicated engineering resources, and that AuditTeam shows a ransomware crew can build comparable tooling — so injection tradecraft at this level should no longer be scoped to espionage threat models.
