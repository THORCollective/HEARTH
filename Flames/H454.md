title: "A trusted desktop application retrieves its own configuration over plaintext HTTP, a hijacked DNS answer substitutes an attacker configuration, and the application downloads the named payloads into its own component directory"
hypothesis: >-
  A widely deployed desktop application fetches a configuration blob from a vendor hostname over unencrypted HTTP. An adversary who controls DNS resolution for that hostname inside the victim environment answers with a staging server, which returns a configuration in the vendor's own format carrying attacker download URLs, attacker file hashes and destination paths inside the application's own installation tree. The application validates the hashes against the values supplied in the same configuration, so integrity checking passes, writes the payloads where the configuration tells it to, and executes them through its normal component-loading workflow. The observable chain is a plaintext HTTP request to a vendor configuration endpoint whose DNS answer resolves outside the vendor's own address space, followed within minutes by the application's updater process writing a new executable and a new DLL into its component directory.

false_positive_notes: |
  Plaintext HTTP to a vendor hostname is not by itself suspicious, because that is exactly the weakness being abused. The finding is the answer, not the request.
  - CDN and anycast answers change constantly. A vendor configuration host can legitimately resolve to many addresses across Akamai, Cloudflare, Alibaba Cloud, Tencent Cloud and regional CDNs, and the set rotates. Build the comparison on the vendor's published or observed answer set and on hosting organisation, not on a single address, and re-baseline weekly.
  - Split-horizon DNS, internal resolvers, DNS-based content filters and sinkholes all rewrite answers for legitimate reasons. A security product that NXDOMAINs or sinkholes a vendor domain will look like hijacking. Enumerate the sinkhole and filter ranges first and exclude them explicitly, since they are a small, stable list.
  - Applications write into their own installation directories during every update, so the file-write half of the chain fires on normal patching. The discriminators are a file whose name belongs to one component but whose Authenticode signer is a different vendor (see [[H455]]), and a write that is not preceded by the vendor's usual signed-update traffic.
  - Hotel, airport, captive-portal and some ISP resolvers return redirection answers for arbitrary names. Scope the hunt to managed devices on managed networks, or require the destination to serve an attacker-controlled hostname rather than a portal.
notes: |
  The report this hunt is built on is ESET's analysis of SlippyNunchucks hijacking the brand promotion mechanism of Sogou Input Method to deliver the DarkVigil implant. ESET found "20 request endpoints on this host that the application accesses over unencrypted HTTP rather than HTTPS", among them the configuration endpoint that was hijacked, and states that "The point at which the DNS manipulation occurs remains unknown" - so this hunt deliberately does not assume a mechanism for the DNS control, and looks only at its effect. Tencent moved the affected requests to HTTPS with certificate pinning in version 16.10, released October 30, 2026, which means the specific instance is closed and the pattern is the thing worth hunting.
  DNS answer deviation - Core filter: Sysmon Event ID 22 events, or resolver logs, where the queried name is a configuration, update or telemetry host for an installed desktop application, and the answers in QueryResults fall outside the hosting organisation that normally serves that name. Triage values are the queried name, the full answer list, the querying Image and process GUID, the user, and the ASN and hosting organisation of each answer. In the reported case the hijacked name was `config.pinyin.sogou[.]com`, an official Sogou back-end host that ESET confirmed serves a valid Tencent Technology (Shenzhen) Company Limited certificate over HTTPS, and victim resolution pointed instead at 47.239.250[.]102 or 47.237.122[.]175, both serving the attacker domain `sogou-cdn[.]com`. Correlation: the same device should show the application's other requests to the same hostname resolving normally, so a single name resolving to two unrelated hosting organisations within one day on one host is the shape to pull. Strong red flags are an answer in a cloud provider range that the vendor does not use for its production back end, and an answer that is also serving a lookalike CDN hostname.
  Plaintext configuration fetch - Core filter: in Zeek http.log or proxy logs, GET requests from managed endpoints to a vendor configuration path over port 80. Triage values are host, uri, server address, response body length, response content type, and user agent. Zeek expression for the reported endpoint shape, generalised to any PHP configuration handler on a vendor host:
  ```zeek
  event http_request(c: connection, method: string, original_URI: string,
                     unescaped_URI: string, version: string)
      {
      if ( c$id$resp_p != 80/tcp )
          return;
      if ( method != "GET" )
          return;
      if ( /\/api\/.*[Cc]onfig.*\.php/ !in original_URI )
          return;
      print fmt("plaintext config fetch %s -> %s%s (server %s)",
                c$id$orig_h, c$http?$host ? c$http$host : "", original_URI,
                c$id$resp_h);
      }
  ```
  Pivot: for every hostname this surfaces, record the answer set and compare it across the fleet. A hostname that resolves consistently everywhere except on a handful of hosts is the case to work. ESET notes the malicious configuration was encrypted the same way as the legitimate one - AES-256-CBC with the key and IV embedded in the application binary - so the response body will not look anomalous and body inspection is not the discriminator.
  Payload landing in the application's own tree - Core filter: DeviceFileEvents or Sysmon Event ID 11 showing a `.exe` or `.dll` created or modified under a user-facing application's component directory by that application's own updater or dispatcher process. In the reported chain the dispatcher `SGTool.exe` ran with `--appid=scdreg -update`, and the configuration directed it to write a renamed but legitimately signed Adobe Licensing WF Helper binary (`biz_helper.exe`) over `\Components\SogouComMgr.exe`, plus the DarkVigil implant as `\Components\libcef.dll`. Sample Defender XDR query, restricted to writes into a component path by the product's own binaries:
  ```kql
  let lookback = 30d;
  let appRoots = dynamic([@"\SogouInput\Components", @"\AppData\Roaming\SogouInput"]);
  DeviceFileEvents
  | where Timestamp > ago(lookback)
  | where ActionType in ("FileCreated", "FileModified", "FileRenamed")
  | where FileName endswith ".exe" or FileName endswith ".dll"
  | where FolderPath has_any (appRoots)
  | project Timestamp, DeviceId, DeviceName, FileName, FolderPath, SHA1,
            InitiatingProcessFileName, InitiatingProcessCommandLine, InitiatingProcessAccountName
  | order by Timestamp desc
  ```
  `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, which is all this stage needs. Keep the lookback at `ago(30d)` or less, because Defender XDR advanced hunting retains 30 days and a longer window is silently truncated. Generalise `appRoots` to the component, plugin or update directories of whichever applications your plaintext-HTTP inventory flagged; the Sogou paths are one instance, not the hunt. Strong red flags are a write of two files in one burst where one replaces an existing component-manager executable, and a new DLL whose name matches a common embedded-framework library (`libcef.dll`, `libglesv2.dll`, `chrome_elf.dll`) appearing in a directory where that framework was not previously present.
  Execution through the borrowed workflow - Core filter: Sysmon Event ID 1 where the parent is the application's own dispatcher and the child is a binary inside the component tree. The reported dispatcher launched the component manager with arguments of the form `-installdoall <component_path>`, `-invoke <bundle> <component>` and `-remove <component>`, and the observed invocation was `-invoke BizCenterComBundle BizCenterCom`. ESET's point about why this is quiet is worth keeping in view when deciding severity - "By borrowing an existing workflow, this technique provides persistence without requiring a separate persistence mechanism" - so there is no new service, task or Run key to find, and absence of a persistence artefact is expected rather than exculpatory. Correlation: pair any hit with [[H455]], which hunts the signer mismatch directly, and with a review of the application's own update history on that host. ESET also observes that "both methods are highly destructive and likely to cause software failures", so helpdesk tickets about the application crashing or failing to update on the same host are corroborating evidence.
  Scoping the hunt beyond this one product - Core filter: the inventory itself. Run a capture on a representative sample of managed endpoints, extract every distinct HTTP (not HTTPS) request made by installed desktop software, and keep the hostname plus path of anything that returns configuration, update manifests, or download instructions. That list is the hunt's real target set, and it is stable for months. Input method editors, media players, driver updaters, regional messaging clients and OEM utilities are over-represented in it. Strong red flags are a configuration response that names a download URL on a different registered domain than the requesting hostname, and a response carrying its own hash values for the files it tells the client to fetch, which lets an adversary who controls the response control integrity validation at the same time.

# H454

Sogou Input Method is one of the most widely deployed Chinese input method editors, launched in 2006 and owned by Tencent since 2021. One of its components, `SGTool.exe`, is a multipurpose task dispatcher: it parses a command ID from an `--appid=` argument and routes to a handler. ESET identified at least 30 such command IDs covering installation, skin management, dictionary updates and framework downloads.

One of those handlers supports the Startup Brand Support Program, introduced in 2016, which lets startups have their brand names appear in the candidate list with a small green sprout icon. The handler fetches a configuration describing which icons to download. That request went out over plaintext HTTP.

Beginning July 1, 2026, ESET observed victims in Hong Kong, Thailand, Japan, Vietnam, Sri Lanka and Oman receiving the DarkVigil implant while using the IME. The volume and geographic spread initially suggested an exploit. It was not one. DNS resolution for the vendor's configuration host was under attacker control inside victim environments, the plaintext request went to a staging server, and the response was a validly formatted, correctly encrypted configuration that told the application to download two files and where to put them.

The attacker also set the hash fields in that configuration to match the payloads, so the application's own integrity check confirmed the attacker's files. Nothing about the application was exploited or patched. Its trust in an unauthenticated channel was simply used as designed.

This hunt looks for that shape in any product, because the ingredients are common: a desktop application with a privileged updater, a configuration channel without TLS, and a configuration format expressive enough to name a URL, a hash and a destination path.

## Why

- The payload arrives through the application's own signed, expected, scheduled behaviour. There is no exploit, no dropper, no new persistence mechanism and no user interaction, so the detections that normally catch delivery have nothing to fire on. ESET's own framing is that the technique borrows an existing workflow and therefore needs no separate persistence.
- Integrity validation does not help when the same response supplies both the payload URL and its hash. Any hunt that assumes hash checking is a control has to be rewritten for this case, and the only remaining distinguishing evidence is upstream in DNS and in the plaintext HTTP exchange.
- Both halves of the chain are in ordinary telemetry. Sysmon Event ID 22 records the DNS answers, Zeek and proxy logs still see cleartext HTTP in full, and file-create telemetry shows a new executable and DLL appearing in a component directory with a signer that does not belong to the product.
- The exposure is wide and quantifiable before any incident. ESET found 20 plaintext endpoints on one host of one product. An inventory of which installed applications still fetch configuration over HTTP turns this hunt from a single-vendor exercise into a standing control, and that inventory is cheap to build and stable over time.
- The specific case is closed and the pattern is not. Tencent shipped HTTPS with certificate pinning on October 30, 2026 after ESET's disclosure, and ESET's CNA issued CVE-2026-120422. The next product with a plaintext configuration channel has not been disclosed yet.
