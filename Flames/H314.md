false_positive_notes: |
  Root store writes have a real benign population and it must be enumerated before this hunt is run in anger, which is what [[B048]] exists to provide. Windows itself adds roots automatically: when a user reaches an HTTPS site or opens signed content chaining to a root not yet present locally, Windows consults the Microsoft Certificate Trust List, verifies the root is listed and installs it — so roots appearing with a corresponding CTL auto-update trail (CAPI2 records the successful download) are routine, and a root appearing WITHOUT that trail is the anomaly. Enterprises legitimately install their own internal CA and, very commonly, the CA of a corporate TLS-inspection proxy, endpoint DLP product or secure web gateway; those are deployed by GPO, Intune or an installer running with a known parent process, they appear estate-wide rather than on one host, and they are by far the largest legitimate population. That estate-wide versus single-host distinction does most of the triage work here: a corporate inspection CA lands on thousands of machines from a management channel, while this campaign's CA lands on one machine from a hollowed `MsBuild.exe`. Developers also install local development roots (`mkcert`, IIS Express, Docker Desktop, Fiddler, Burp, Charles) and these are genuine recurring matches on engineering workstations — resolvable by the installing process, the user context, and a conversation rather than a suppression rule. Note explicitly that a Fiddler or Burp root is functionally identical to this attack in mechanism, so the discriminator is authorisation, not technique. Hosts-file modification has a thinner benign population — occasional legitimate administrative or developer use, and some VPN and endpoint products — but a hosts entry pointing a MAJOR PUBLIC DOMAIN at loopback is not part of any of those. Firewall rule creation is common during software installation; the discriminator is a rule whose program path is an unexpected binary and whose name does not correspond to any installed product.
notes: |
  Core filter, the root CA - Sysmon Event ID 12/13 writing under `HKLM\SOFTWARE\Microsoft\SystemCertificates\ROOT\Certificates\<thumbprint>`, where the writing process is not a known management agent (`gpsvc`/`svchost` for GPO, the Intune management extension, or your software-deployment agent). Then inspect the certificate itself. Reported values - Subject presented as Google Trust Services with `CN=WR3`, self-signed, with a leaf issued for `www.virustotal.com` whose SAN covers both the legitimate domain and `localhost`. Two structural tells that generalise past this campaign - a root whose subject impersonates a well-known public CA but whose ISSUER CHAIN terminates in itself, and a leaf for a public domain carrying `localhost` in its SAN, which is only ever useful for intercepting traffic that has been redirected to loopback. Enumerate current state with `Get-ChildItem Cert:\LocalMachine\Root` and diff against the [[B048]] register, and with `certutil -store Root` for detail.
  Core filter, the hosts file - Sysmon Event ID 11/2 on `%SystemRoot%\System32\drivers\etc\hosts`, followed by content inspection for any entry mapping a public domain to `127.0.0.1` or `::1`. Combined with a matching leaf certificate for that same domain, this pair is conclusive - the redirect sends the client to the local listener and the forged leaf makes the TLS handshake succeed. Neither artefact alone proves interception; together they are the mechanism.
  Core filter, the firewall rule - Windows Firewall event 2004 for a rule added with the name `LocalProxy` (reported) or any rule permitting inbound traffic to a binary in a user-writable or unexpected path. Enumerate with `Get-NetFirewallRule | Get-NetFirewallApplicationFilter` and reconcile every rule against an installed product.
  Execution chain to pivot on - the dropper masqueraded as a Lenovo driver package (`localcertificate.zip`, with a sibling `asusdriverld.zip` in the same campaign), signed with a STOLEN LENOVO certificate, and executed via hollowed `MsBuild.exe` that imported only `kernel32`. Hunt `MsBuild.exe` running outside a developer context, with no `.csproj`/`.sln`/project argument on its command line, and correlate Sysmon Event ID 8/25 and Defender `DeviceEvents` process-tampering signals. `MsBuild.exe` on a non-developer workstation is itself worth a standing query. The delivery chain reached the host through a fake "Google API Connector" ClickOnce application and an encoded PowerShell command pulling three encrypted payloads from `eu03hub[.]com/get_file`; the sibling payload in the same set persisted as a `Run` key named "Ledger Wallet Installer" pointing at a bare `msbuild` invocation.
  Stolen-certificate angle - three different stolen code-signing certificates were used across this campaign (a Norwegian company's, Lenovo's, and Discord Inc.'s). Hunt for binaries whose signature is VALID but whose signer has no relationship to the file's apparent purpose or install path, and for signatures that fail validation while still carrying a recognisable corporate signer name.
  Why this outlives the incident - of every artefact here, the root CA is the one most likely to survive cleanup. Killing the process and deleting the binary leaves the machine trusting an attacker CA indefinitely. Any remediation that does not explicitly enumerate and remove the root, the hosts entry and the firewall rule leaves the interception capability intact, which is why this hunt should be run against MACHINE TRUST STATE rather than against running processes.
  Triage values - certificate thumbprint, subject, issuer, validity dates, SAN list, the writing process and its parent, hosts-file contents, firewall rule name and program path, and `MsBuild.exe` command line and parent.

# H314

Huntress documented a campaign that begins in a Google Doc — a container-bound Apps Script sidebar that profiles the viewer client-side without an OAuth prompt — and forks by operating system. The Windows branch delivers three payloads, and the second is the one worth a dedicated hunt: a TLS interception proxy disguised as a Lenovo driver package, signed with a stolen Lenovo certificate, executing through a hollowed `MsBuild.exe` that imports only `kernel32`. Once running it builds its own PKI on the victim. It installs a self-signed root CA into the machine trust store presenting itself as "Google Trust Services" with `CN=WR3`, mints a leaf certificate for `www.virustotal.com` whose SAN covers both the real domain and `localhost`, writes a hosts-file entry redirecting that domain to loopback, and adds a Windows Firewall rule named `LocalProxy` to let its listener receive the redirected traffic. The result is a machine that will transparently trust an attacker-terminated TLS session. As Huntress put it, the rogue CA is the artefact most likely to survive cleanup — reimaging removes it, killing the process does not.

## Why

- **Trust-store persistence is configuration, not code, so process-centric response misses it entirely.** Every standard containment step — terminate the process, quarantine the binary, block the C2 — leaves the root CA, the hosts entry and the firewall rule in place. A host that has been "cleaned" still trusts the adversary's certificate authority, which means the capability to intercept and to sign survives the incident unless someone hunts trust state explicitly.
- **Impersonating a real public CA defeats human review at exactly the moment it matters.** An analyst scrolling the root store sees "Google Trust Services" and moves on. The structural tell is not the name but the chain: a genuine public root is cross-signed and widely deployed, while this one is self-signed and present on exactly one machine. That comparison is only cheap if the estate-wide register from [[B048]] already exists.
- **The three artefacts only make sense together, which makes the combination near-unambiguous.** A root CA alone could be a developer tool; a hosts entry alone could be a workaround; a firewall rule alone could be an installer. All three, naming the same domain, with a leaf whose SAN pairs a public site with `localhost`, is an interception rig and admits no innocent reading.
- **Stolen code-signing certificates break the assumption that signature equals provenance.** This campaign used three separate stolen certificates, and a payload signed by Lenovo installing into a user-writable path is trusted by controls keyed on valid signatures. Hunting for the mismatch between a valid signer and the file's actual purpose and location is what recovers signal once signing has stopped being evidence of legitimacy.
