false_positive_notes: |
  Design-time builds are constant and noisy on a developer workstation, so the hunt cannot key on `devenv.exe` spawning processes by itself — compilers, analysers, NuGet restore, source generators, test adapters and language servers all run that way all day. Three things narrow it. First, destination: legitimate build activity writes into the solution tree, `%TEMP%`, the NuGet package cache and `obj\`/`bin\`, not into a freshly created `%LOCALAPPDATA%\Microsoft\<name>\` folder. Second, image identity: the children of a normal design-time build are a known toolchain set (`csc.exe`, `VBCSCompiler.exe`, `MSBuild.exe`, `dotnet.exe`, `nuget.exe`, `vstest.console.exe`, analyser hosts), not an arbitrary EXE that was copied out of the project moments earlier. Third, provenance: the project arrived as a downloaded archive and carries Mark-of-the-Web, which internal repository clones do not. Teams that legitimately vendor build tooling inside a repository and copy it out during restore will generate recurring, identical hits — allowlist those by path and hash rather than by parent.

Unit 42 reports the lure as an archive named `DubaiAirport_Carrers_IT_Test.zip`, presented as a hiring assessment from a Dubai Airports IT department and containing a `Readme.md` with personalised instructions plus an intentional bug, so the candidate is motivated to open and debug the project. The weaponised file is `FlightManager.csproj`, which Unit 42 states hijacks the `GetFrameworkPaths` target so the payload copy and launch happen during Visual Studio's design-time build. The staged files are copied from the project's `Resources` folder to `%LOCALAPPDATA%\Microsoft\RuntimeBrokers\`, and `RuntimeBroker.exe` — a renamed copy of the legitimate Microsoft-signed `vshost.exe` — is launched in the background. Unit 42 explicitly maps this leg to T1127. No detection queries were published with the report; the queries below are derived from the reported artefacts.
  What makes this worth a hunt of its own - HEARTH already covers MSBuild abuse launched from a shell or from `%TEMP%` (see [[H238]], where a RenPy loader drops `*.csproj`, `*.props` and `*.targets` into a `%TEMP%\tmp-*` directory and runs them through `MSBuild.exe`). That is a command-line execution chain and it is caught by watching `MSBuild.exe` invocations. This is the opposite shape: no one invokes MSBuild, there is no command line to inspect, and the trigger is the IDE's own automatic project evaluation on load. The target population is also different — software developers, who are the one population where compiler and build activity is expected and therefore least scrutinised.
  Process-lineage leg (primary) - Core filter: a process whose `ParentImage` is `devenv.exe`, `MSBuild.exe`, `VBCSCompiler.exe` or `ServiceHub.*`, where the child image is NOT in the organisation's known toolchain allowlist, and the child's image path is outside the solution directory, `%TEMP%`, the NuGet cache and the Visual Studio install tree. Triage fields - child image path and SHA256, signer, the solution path from the parent command line, `User`, and the time delta from project open. Strong red flags - the child image was created on disk by the same parent within the preceding 60 seconds; the child is a signed Microsoft binary running from a non-Microsoft path (Unit 42's `RuntimeBroker.exe` is a renamed `vshost.exe`, so it is validly signed and will pass signature checks); the parent directory under `%LOCALAPPDATA%\Microsoft\` did not exist before today.
  Sample KQL - a non-toolchain child of the Visual Studio build chain, where the image was written by that same chain minutes earlier.
  `let toolchain = dynamic(["csc.exe","vbcscompiler.exe","msbuild.exe","dotnet.exe","nuget.exe","vstest.console.exe","testhost.exe","conhost.exe","cmd.exe","git.exe","node.exe","powershell.exe"]); let staged = DeviceFileEvents | where Timestamp > ago(30d) | where InitiatingProcessFileName in~ ("devenv.exe","msbuild.exe") | where FolderPath has @"\AppData\Local\" | project DeviceId, stagedPath = FolderPath, stagedName = FileName, writeTime = Timestamp; DeviceProcessEvents | where Timestamp > ago(30d) | where InitiatingProcessFileName in~ ("devenv.exe","msbuild.exe","vbcscompiler.exe") | where FileName !in~ (toolchain) | join kind=inner staged on DeviceId | where FolderPath =~ stagedPath and datetime_diff("second", Timestamp, writeTime) between (0 .. 300) | project Timestamp, DeviceName, AccountName, FileName, FolderPath, SHA256, InitiatingProcessFileName, InitiatingProcessCommandLine`
  File-staging leg (independent) - Core filter - Sysmon Event ID 11 where `Image` is `devenv.exe` or `MSBuild.exe` and `TargetFilename` begins `%LOCALAPPDATA%\Microsoft\` but is not one of the directories Visual Studio itself uses (`\Microsoft\VisualStudio\`, `\Microsoft\VSApplicationInsights\`, `\Microsoft\MSBuild\`, `\Microsoft\dotnet\`). The campaign's folder, `RuntimeBrokers`, is plural where the real Windows binary is singular — that one-character difference is exactly what a name-similarity check over new `%LOCALAPPDATA%\Microsoft\*` subdirectories surfaces, and it generalises past this campaign's specific folder name.
  Project-content leg (preventive, scales to repositories) - Grep incoming and newly cloned projects for build-file constructs that execute during evaluation rather than compilation. In an MSBuild project file, the suspicious constructs are a `<Target>` whose `Name` or `BeforeTargets`/`AfterTargets` references an internal target such as `GetFrameworkPaths`, `CollectPackageReferences` or `ResolveReferences`, combined with an `<Exec>`, `<Copy>` or `<WriteLinesToFile>` task that touches a path outside the project. The same check applies to `.props`, `.targets`, `Directory.Build.props` and `nuget.config` shipped inside an untrusted archive. Scope this hunt to any workstation that opened a project from a download, an email attachment or an external repository — Unit 42's lure makes job applicants and anyone doing external code review the highest-value population.
  Follow-on behaviour to pivot on - Per Unit 42, the staged `RuntimeBroker.exe` then performs AppDomainManager hijacking via a planted `.exe.config` with `<etwEnable enabled="false"/>` — already hunted in HEARTH as [[H165]] — and establishes GitHub-based C2, hunted here as [[H357]]. A hit on this hunt should be pivoted into both, and into a check for `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run\MicrosoftRuntime`, the Run-key value Unit 42 reports for persistence.

# H356

Unit 42's October 2026 Blinder Tunnel report describes an initial access path that does not need the victim to run anything. The lure is a Visual Studio project, delivered as `DubaiAirport_Carrers_IT_Test.zip` and framed as a technical assessment from a Dubai Airports IT department, complete with a `Readme.md` giving personalised instructions and an intentional bug for the candidate to find. Opening the solution is sufficient.

The weaponisation sits in `FlightManager.csproj`. Visual Studio runs a design-time build automatically when it loads a project — that is how IntelliSense knows what the references are — and the attacker hijacked the `GetFrameworkPaths` target so that evaluation copies a payload out of the project's `Resources` folder into `%LOCALAPPDATA%\Microsoft\RuntimeBrokers\` and launches `RuntimeBroker.exe` in the background. `RuntimeBroker.exe` is a renamed copy of Microsoft's legitimate `vshost.exe`, so it is validly signed.

Two details make this hard for existing detection. The payload runs with no attacker-controlled command line, because the IDE supplies the invocation. And the victim is a developer, the one user population where unexplained compiler activity is the baseline rather than the anomaly. What is left to hunt is the mismatch between where the build toolchain should write and where it actually wrote.

## Why

- **The only user action is opening a file.** There is no macro prompt, no SmartScreen decision, no "enable content" banner and no script execution for the user to refuse. Awareness training does not cover this, so detection has to.
- **It inverts the usual MSBuild hunt.** Existing MSBuild detections, [[H238]] included, watch for `MSBuild.exe` being invoked with a staged project file. Here nobody invokes MSBuild — the IDE evaluates the project on load — so command-line-based rules never fire.
- **Developer workstations are high-value and weakly instrumented for this.** They hold source code, signing material, cloud credentials and CI tokens, and their build noise is routinely excluded from analytics precisely because it is so loud.
- **The write destination is a reliable discriminator.** Legitimate design-time builds write to the solution tree, `obj\`, `bin\`, `%TEMP%` and the package cache. A build process creating a new folder under `%LOCALAPPDATA%\Microsoft\` and executing from it has no benign equivalent.
- **The staged binary will pass signature checks.** Because the launched executable is a renamed, legitimately signed Microsoft file, signer-based allowlisting and "unsigned binary" heuristics are blind to it — path and parentage are what remain.
- **The check extends past this campaign.** The same inspection applied to `.csproj`, `.props`, `.targets` and `Directory.Build.props` in any externally sourced repository covers build-file execution generally, which is a live supply-chain problem well beyond one Iraqi-infrastructure campaign.
