title: "IIS resolves an .aspx path that has no file behind it and builds no file-change monitor for it, because a registered VirtualPathProvider is serving the page out of the worker process"
hypothesis: >-
  After reaching code execution inside an IIS worker process, an operator registers a custom VirtualPathProvider with the ASP.NET compilation system instead of writing a web shell to disk. The application then serves and dynamically compiles a virtual page as though it were an ordinary file, entirely inside its own trust boundary, with no persistent artefact to find on the filesystem. The detectable contradiction is in IIS configuration telemetry - the path resolves to a physical location where no file exists, and the file-change monitoring chain that IIS always builds for a disk-backed page is missing for that same path.

false_positive_notes: |
  VirtualPathProvider is a documented, supported ASP.NET feature with real legitimate users, so this hunt is unworkable without the inventory step first.
  - Content management systems, portal products and plugin frameworks register virtual-path providers as a matter of design, to serve pages out of a database or an archive. SharePoint itself is one of them. Build the allowlist of legitimate implementations per application before any alerting, which is the defensive model Kaspersky recommends.
  - Precompiled applications, deployment packages and some publishing workflows produce path resolution events whose on-disk state lags the configuration state, so a transient mismatch during a deployment is expected. Require the mismatch to persist beyond the deployment window, and correlate with release records.
  - Temporary compilation artefacts exist and will tempt you into using them as evidence. Kaspersky is explicit that during the compilation process temporary files may be generated but cannot be treated as reliable forensic artefacts, so do not build the detection on the ASP.NET temporary folder.
  - The second half of the pattern is an absence, which makes it fragile to collection gaps. A missing file-change monitoring chain can mean a virtual path, or it can mean the ETW events were dropped. Verify that events 17, 18, 19 and 21 are present in volume for ordinary pages on the same server before concluding that their absence for one path is meaningful.
  - Child-process and outbound-connection telemetry from the worker process is noisy in environments where applications legitimately shell out or call APIs. Baseline per application pool rather than per server.
notes: |
  Source reporting is Kaspersky's SOC Files analysis of a fileless SharePoint breach attributed to Storm-2603, following exploitation of the ToolShell vulnerabilities CVE-2025-53770 and CVE-2025-53771 in on-premises SharePoint. Kaspersky describes the actor using the IIS worker process as an in-memory bridge into the infrastructure, keeping the access and control layer within `w3wp.exe`. The nearest existing hunt is [[H311]], which covers a forged `__VIEWSTATE` payload loading an in-memory backdoor on Exchange - same fileless objective and the same worker-process host, but a different mechanism and a different telemetry source. H311 keys on stolen `machineKey` values and a non-standard request header; this hunt keys on the ASP.NET compilation system itself, which is the part no request-level inspection can see.
  Why there is nothing on disk - Core concept: in ASP.NET, `HostingEnvironment.RegisterVirtualPathProvider` registers a new virtual-path provider in the application's compilation system. Once registered, the application can serve virtual paths during dynamic compilation as though they were ordinary on-disk pages. Kaspersky's characterisation is the reason this needs its own hunt rather than a web shell rule - "A mechanism based on VirtualPathProvider should be treated as a separate class of runtime implant (no files involved)" - and dynamic compilation does not require the payload to exist as a file in the filesystem, operating entirely within the trust boundary of the application itself.
  The positive half of the pattern - Core filter: Microsoft-Windows-IIS-Configuration events 25 and 47. Event 25 records the mapping of `ConfigPath` to `PhysicalPath`, and event 47 records the mapping of the configuration path to a directory. Triage values are the configuration path, the physical path, the site and application pool, the timestamp, and the process. The decisive step is a filesystem check at triage time: for each resolved path, confirm whether a file exists there. Kaspersky's lab example shows the virtual resource `googlecheck.aspx` mapped to a physical path where no real file is present, and states that "This discrepancy between configuration resolution and filesystem reality is the primary indicator of virtual content."
  The negative half of the pattern - Core filter: the absence of the file-change monitoring chain for the same path. For disk-backed files, IIS normally creates a `FileChangeNotificationMonitor` chain, reflected in events 17, 18, 19 and 21. For virtual paths served by a custom provider that chain is absent or does not match the normal profile of an ordinary file, because there is no physical object and no on-disk change lifecycle. Kaspersky states the combined rule directly: "the presence of positive events 25 and 47 combined with the absence of the expected events 17, 18, 19, and 21 for the same path forms a reliable detection pattern". Correlation: build the comparison per path per server over a window long enough to contain a request to that path, and treat the chain as present if any of the four events reference the path.
  Running the comparison - Core filter: a set-difference over the collected ETW events. The shape, expressed against a generic event store where the provider has been forwarded into a table, is a left anti join of resolved paths against monitored paths:
  ```kql
  let lookback = 7d;
  let resolved = IISConfigurationEvents
      | where TimeGenerated > ago(lookback)
      | where EventID in (25, 47)
      | where ConfigPath endswith ".aspx" or ConfigPath endswith ".ashx" or ConfigPath endswith ".asmx"
      | distinct Computer, SiteName, ConfigPath, PhysicalPath;
  let monitored = IISConfigurationEvents
      | where TimeGenerated > ago(lookback)
      | where EventID in (17, 18, 19, 21)
      | distinct Computer, ConfigPath;
  resolved
  | join kind=leftanti monitored on Computer, ConfigPath
  | order by Computer asc, ConfigPath asc
  ```
  The table and column names depend on how the provider is collected in your environment, so treat this as the logic rather than as a drop-in query, and confirm the field that carries the path in your own collector before relying on it. The seven-day lookback is deliberate: a path only produces events when it is requested, so a short window risks a false absence while a long window increases the chance that a deployment has changed the on-disk state in between. Strong red flags are a resolved path whose leaf name is innocuous and unfamiliar to the application owner, and a path that appears in IIS access logs with successful responses while being absent from both the filesystem and the application's source control.
  What else was in the worker process - Core filter: children of `w3wp.exe` and its outbound connections, bounded to the window the virtual path first appeared. In the reported incident the webshell injected into the worker-process runtime was a multi-module in-memory framework orchestrated through a main component and extended across several namespaces, with one module enumerating logged-on users and their session types (interactive, service, remote) and holding the results in memory for retrieval over the framework's own proxy and tunnelling capabilities. Shortly after injection the infected worker process spawned `msiexec.exe` to install a remote MSI payload hosted in Supabase cloud storage, which turned out to be a vulnerable version of the open-source Velociraptor forensics tool, used as a post-compromise execution framework. Correlation: `msiexec.exe` parented by `w3wp.exe` is a high-value standalone filter regardless of this hunt, and the MSI source being a cloud object-storage URL rather than an internal distribution point is the second half of it.
  The redundancy that follows - Core filter: multiple independent remote-access and tunnelling mechanisms installed in one window. Kaspersky reports the actor using Velociraptor to deploy several at once, including an unattended remote-support agent, a code-editor CLI tunnel, a tunnelling client fetched from its vendor's own release URL, and a lightweight reverse proxy. Correlation: HEARTH already covers several of these individually, so the pivot here is the count - one host acquiring three or more distinct remote-access channels inside a day is the pattern, and it is what makes eviction fail when only one is removed. An EDR-terminating vulnerable driver was also dropped in the same intrusion, and a ransomware launch attempt followed, so a confirmed hit on this chain should be treated as pre-impact rather than as an isolated web shell finding.
  Scoping guidance from the reporting - Core filter: the inventory. Because virtual-path providers can also be used for legitimate purposes, the defensive model should begin with an inventory of the legitimate implementations, and in all other cases the registration or use of a new provider should be considered anomalous. Kaspersky's closing instruction is the triage procedure for anything that survives the allowlist: "Anything else should be treated as a potential runtime implant and examined using ETW, filesystem verification, and memory inspection of the w3wp.exe process."

# H460

Kaspersky's retrospective analysis found Storm-2603 activity consistent with the actor's known tradecraft in a SharePoint intrusion that left nothing useful on disk. Initial probing came first, then on Christmas Eve - when security staffing at many companies is reduced - the full remote code execution chain ran through the IIS worker process on the same endpoint, from a crafted request to an internet-facing SharePoint server.

What the actor did next is the part worth a dedicated hunt. Instead of writing a web shell file, they used ASP.NET's own compilation system against the application. Registering a `VirtualPathProvider` tells IIS that a path exists and can be compiled and served, without that path corresponding to anything on the filesystem. The page is real to the application and absent from the disk.

That removes nearly every artefact a web shell hunt depends on. There is no file to hash, no file-creation event, no suspicious write into the web root, and the temporary files produced during compilation are not dependable evidence.

What it cannot remove is the inconsistency it creates inside IIS's own configuration telemetry. IIS records that it resolved a configuration path to a physical path - and for a real file it also builds a file-change monitoring chain so it can recompile when the file changes. A virtual path gets the first record and not the second, because there is no file to watch. Positive resolution events with no monitoring chain for the same path is the signature, and Kaspersky published both the event IDs and a lab to reproduce it.

## Why

- This is a distinct class of implant rather than a stealthier web shell, and most web shell detection does not apply to it. Rules keyed on file writes into the web root, on handler mappings, or on new files with script extensions all return nothing, which means an environment can be confident in coverage it does not have.
- The detection is a logical contradiction rather than a signature, so it does not depend on the implant's code, its name, its obfuscation or its command channel. Any provider serving content that is not on disk produces the same inconsistency, which is why the pattern survives a rewrite of the implant.
- The required telemetry is a single ETW provider and the required preparation is an application inventory. Both are cheap compared with the alternative of memory inspection across every IIS server, and the inventory has independent value because it documents which applications legitimately serve virtual content.
- The absence half of the pattern makes collection health part of the hunt. If the monitoring chain events are not arriving in volume for ordinary pages, the detection silently returns false findings, so running this hunt verifies the pipeline that several other IIS hunts also depend on.
- A hit here sits early in a ransomware chain, not at the end of an espionage one. The same intrusion went on to install a remote forensics framework from cloud storage, stand up several independent tunnels, drop an EDR-terminating driver, and attempt ransomware. Finding the runtime implant is the cheapest place to intervene, and the point at which eviction is still a single-host problem.
