false_positive_notes: |
  The two invocation primitives are not attacker inventions and both appear in legitimate code, so the hunt cannot alert on the API names alone. `$ExecutionContext.InvokeCommand.InvokeScript()` is used inside real modules, in DSC resources, in build and deployment tooling, and in any framework that composes script text dynamically; `[System.Management.Automation.Language.Parser]::ParseInput()` is the documented way to build an AST and is used by PSScriptAnalyzer, by editor tooling and linters, by module authors doing static analysis, and by any code that formats or validates PowerShell. On a developer or platform-engineering workstation both will appear with some regularity, and an estate running PSScriptAnalyzer in CI will generate `ParseInput` calls constantly.
  What separates them is what the parsed text CAME FROM. The malicious pattern is a single short block in which the text is retrieved from the network and compiled in the same expression - `irm`, `iwr`, `Invoke-RestMethod`, `Invoke-WebRequest`, `DownloadString`, `DownloadData`, `Net.WebClient`, `System.Net.Http.HttpClient` - with a remote URL present in the same script block. Legitimate `ParseInput` use overwhelmingly parses a FILE or a local string literal and then INSPECTS the AST rather than executing it; the tell is the pairing of `GetScriptBlock()` with the call operator `&` or with `.Invoke()` immediately afterwards. A `ParseInput` that is never executed is almost always tooling, and a `ParseInput` whose source is `irm` is almost always not.
  Three supporting discriminators are worth applying before triage. First, the LAUNCH CONTEXT - `powershell.exe` whose parent is `explorer.exe` with `-w hidden`/`-w h`, `-ep bypass`, `-nop`, `-wi mi` or `-WindowStyle Hidden` on the command line is the ClickFix shape and has essentially no benign analogue in a managed estate, whereas legitimate tooling runs from a console host, a scheduler, a CI agent or a management platform. Second, BREVITY - both observed samples are one-liners of a few hundred characters; real code that uses the parser is embedded in modules hundreds of lines long. Third, the RunMRU corroboration - if the Run dialog history on the host contains the same command, a human pasted it, and the question is answered.
  One coverage caution that decides whether an empty result means anything. Script Block Logging must actually be enabled, and event 4104 splits long blocks across multiple records keyed by `ScriptBlockId` with `MessageNumber` of `MessageTotal`. A query that matches against individual records will miss any string that happens to straddle a boundary, and obfuscation that inserts length is a cheap way to force that split deliberately. Reassemble by `ScriptBlockId` first, then match. Also note that older PowerShell v2 remains installable on some estates and does not produce 4104 at all - a downgrade invocation (`powershell -version 2`) is both an evasion of this hunt and a finding in its own right.

# H332

Detection content for malicious PowerShell has spent a decade converging on a small set of strings — `IEX`, `Invoke-Expression`, `DownloadString`, `.Invoke()` — and adversaries have noticed. In the same few weeks, two campaigns with no relationship to each other shipped ClickFix one-liners that download a script and run it while using none of them. AhnLab's LegionLoader passes the fetched text to the PowerShell language parser and invokes the resulting script block; Sekoia's Exvicy uses `$ExecutionContext.InvokeCommand.InvokeScript()`. Neither is obfuscation. Both are documented, ordinary, entirely supported API surface, and both do precisely what `IEX` does.

What makes this hunt work is that the evasion targets the wrong layer. These primitives hide the intent from anything reading a command line, but PowerShell's Script Block Logging records the script text at the moment it is compiled, irrespective of which API asked for the compilation. Event 4104 sees the downloaded stage in full. The detection therefore does not need to enumerate invocation methods at all — it needs to be looking at the right data source, reassembled correctly.

## Why

- **The evasion is aimed at command lines, and the answer is to stop hunting command lines.** A rule that matches `iex` is a string comparison against attacker-controlled text, and there are at least five interchangeable ways to compile a string in PowerShell. Event 4104 is generated by the engine after the text is assembled, so it sees the same thing no matter which of the five was used. Moving the hunt one layer down converts an arms race into a stable detection.
- **Two independent campaigns in one month means this is a technique, not a quirk.** LegionLoader and Exvicy share no code, no operator and no target set, and both abandoned `IEX` in the same window. That is the signal that published detection content has become predictable enough to be routed around deliberately, and that the alternatives are now in the commodity toolkit rather than in research papers.
- **Flag abbreviation quietly defeats a lot of existing rules, and both samples use it.** `-w h` is not `-WindowStyle Hidden` and `-wi mi` is not `-WindowStyle Minimized`, but PowerShell resolves all of them. Any rule written against full parameter names has a silent gap that costs the adversary nothing to exploit. Enumerating the abbreviations is a small, one-time piece of work with immediate return across every PowerShell hunt in the estate, not just this one.
- **The benign population separates on provenance rather than on API, and that distinction is sharp.** Legitimate `ParseInput` callers — linters, analysers, editor tooling, module authors — parse a file or a literal and then examine the resulting AST. They do not fetch it from a URL, and they do not immediately execute it with `&`. The malicious shape is a short one-liner in which retrieval and compilation happen in the same expression, which is both easy to express as a query and hard for an operator to avoid without abandoning the one-liner entirely.
- **An empty result here is a coverage question before it is a security conclusion.** This hunt depends entirely on Script Block Logging being enabled and on multi-part 4104 records being reassembled by `ScriptBlockId`. Both are commonly wrong, and a query that matches individual records can be defeated by padding the script until the interesting string straddles a record boundary. Running the hunt therefore audits the estate's PowerShell visibility as a side effect — and that audit is worth having whether or not anything is found.
