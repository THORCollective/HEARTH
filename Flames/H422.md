title: "The AI coding-agent credential set read in one sweep — `.claude\\credentials.json`, `.codex\\auth.json`, `state.vscdb` and the Gemini CLI token touched together by one process"
hypothesis: >-
  Every AI coding agent on a developer workstation keeps a long-lived credential or session artefact on disk in a predictable place, and each one is read by exactly one program: its own client. Claude Code reads `.claude\credentials.json`. Codex reads `.codex\auth.json`. Cursor, Windsurf and VS Code each read their own `globalStorage\state.vscdb`. The Gemini CLI reads its workspace token. No legitimate process has a reason to open the credential stores of three different AI tools inside the same minute, because nothing is a client of three different AI tools at once. Aokigahara's `aisessions` handler does exactly that, and the resulting signature is a narrow, named set of small files that are almost never read by anything other than their owner. Unlike the broad credential families a stealer also sweeps, this set is small enough to put a read audit directly on, which makes the collection step visible without a volumetric model.

false_positive_notes: |
  Endpoint security products, backup agents and DLP scanners read broadly by design and will touch these paths. Resolve the initiating process image and signer first; an allowlist of the estate's EDR, backup and indexing agents removes most of the volume permanently. Keep the allowlist keyed on the signed image path, not on the file name.
  Each tool's own updater and the tools themselves are the expected readers. The finding is never a single store being read, it is one process reaching across stores belonging to different vendors. A rule that fires on any read of credentials.json will fire constantly on a developer workstation.
  File-sync clients are a genuine source of multi-store access. OneDrive, Dropbox and roaming-profile tooling will enumerate and copy anything under the user profile including these paths, and they legitimately produce copies outside the original directory, which is the second half of this hunt. Confirm the sync client's scope before treating a copy as collection.
  Developer-environment provisioning crosses tools legitimately. Dev-container bootstrap, dotfile managers and new-machine setup scripts can write several of these files in one run. These cluster around onboarding and device replacement, so correlate against joiner and refresh activity. Note the direction: provisioning tends to write these files, collection reads them.
  SACL volume has to be measured before estate-wide deployment. These are small files read a handful of times a day by their own client, which is why a read audit is affordable here, but a misapplied SACL on the parent directory rather than the named files will generate far more 4663 volume than intended. Apply to the files, pilot it, then expand.
  Absence of the paths is not absence of risk. A host with none of these tools installed produces nothing, which is correct. Scope the hunt to hosts where the tools exist, and treat the sudden first-ever appearance of one of these paths on a host that has no such tool installed as its own finding.

  Check Point is careful about what these files contain and the hunt should be too: "Depending on the application, these files may contain tokens, credentials, session data, or settings; not every targeted file necessarily contains authentication secrets." A hit is evidence of collection, not proof that a usable token left the host.
  The handler also reaches the Windows credential store - "It also queries Windows Credential Manager." Pair this hunt with Credential Manager access telemetry on the same process; the vault lives under the roaming `Microsoft\Vault` and `Microsoft\Credentials` directories, and `vaultcmd.exe` execution by a non-administrative process is a cheap companion signal.   Primary sensor, read auditing - Reads are the behaviour, and no file-creation sensor records a read. `DeviceFileEvents` covers creates, modifies, renames and deletes but not reads, and Sysmon has no read event, so the direct detection needs Windows object-access auditing with a SACL on the named files. This is affordable precisely because the set is small; the breadth model in [[M062]] exists for the opposite case, where the target list is operator-supplied and too broad to audit. Sentinel or any 4663 collection:
  ```kql
  let aiStores = dynamic([
      @"\.claude\credentials.json", @"\.claude.json",
      @"\.codex\auth.json", @"\.codex\config.toml", @"\.codex\.env",
      @"\Cursor\User\globalStorage\state.vscdb",
      @"\Windsurf\User\globalStorage\state.vscdb",
      @"\Code\User\globalStorage\state.vscdb",
      @"\.aws\credentials", @"\.aws\config", @"\.aws\sso\cache",
      @"\amazon-q\data.sqlite3",
      @"\.copilot\config.json", @"\.copilot\hosts.json",
      @"\.codeium\config.json",
      @"\gemini-cli-workspace-token.json", @"\.gemini-cli-workspace-master-key",
      @"\.gemini\.env", @"\.gemini\config.json",
      @"\options\AIAssistantQuotaManager2.xml"]);
  SecurityEvent
  | where TimeGenerated > ago(30d)
  | where EventID == 4663
  | where ObjectName has_any (aiStores)
  | summarize stores = dcount(ObjectName), storeList = make_set(ObjectName, 30),
              firstSeen = min(TimeGenerated), lastSeen = max(TimeGenerated)
          by Computer, SubjectUserName, ProcessName
  | extend span = lastSeen - firstSeen
  | where stores >= 3 and span < 10m
  | order by stores desc
  ```
  Three distinct stores inside ten minutes is the threshold to start with, not a tuned value; raise `stores` and shorten `span` if the estate's provisioning tooling sits in the result set. Both the vendor spread and the speed matter, so keep the span term rather than alerting on count alone.
  Second sensor, copies - `state.vscdb` and `data.sqlite3` are SQLite databases. A collector that wants a consistent read of a database the owning application holds open will usually copy it first, and a copy is a file create, which Defender and Sysmon both see. This copy behaviour is an expectation about how SQLite collection generally works and is not something Check Point states about this sample, so treat it as a second net rather than a confirmation of the family.
  ```kql
  let aiArtifacts = dynamic(["state.vscdb", "credentials.json", "auth.json", "hosts.json",
                             "kiro-auth-token.json", "data.sqlite3",
                             "gemini-cli-workspace-token.json",
                             "AIAssistantQuotaManager2.xml"]);
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("FileCreated", "FileRenamed", "FileModified")
  | where FileName in~ (aiArtifacts)
  | where FolderPath !has @"\globalStorage\"
  | where FolderPath !has @"\.claude" and FolderPath !has @"\.codex"
  | where FolderPath !has @"\.copilot" and FolderPath !has @"\.gemini"
  | where FolderPath !has @"\.aws\sso\cache" and FolderPath !has @"\amazon-q"
  | summarize artefacts = make_set(FileName, 20), landingPaths = make_set(FolderPath, 20),
              lastSeen = max(Timestamp)
          by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath,
             InitiatingProcessSHA256
  | where array_length(artefacts) >= 2
  | order by lastSeen desc
  ```
  The exclusions are what make this query usable: they remove each artefact appearing in the directory where it belongs, leaving only copies that landed somewhere else. Keep them aligned with the path list above when a new tool is added.
  Scoping query, run first - Before hunting, establish which hosts have these tools at all. A simple inventory of the parent directories across the estate turns an un-scoped estate-wide hunt into a hunt over the few hundred engineering hosts where these paths can legitimately exist, and gives the baseline that [[B066]] formalises.
  Egress pairing - The upload stage labels its own contents. The collection modules each upload a separate archive with an `X-Chunk` header naming the module, and `aisessions` is one of the labels Check Point lists. A host that produces a collection hit here and a matching upload is a confirmed theft rather than a suspicious read, and the upload fingerprint is the subject of [[H424]].
  Response - Treat every token and key in the collected set as compromised on a confirmed hit, and revoke rather than rotate where the provider supports it. Session tokens for AI services are bearer credentials that commonly survive a password change, which is why Check Point frames the value of the set the way it does. Cloud credentials in the same sweep, `.aws\credentials` and the SSO cache in particular, give onward access well beyond the workstation, so scope to cloud control-plane activity from new locations after the collection window.
  Closest existing coverage, and why this is not it - [[H259]] is the nearest hunt in the library: an adversary with execution inside an AI coding agent session on macOS harvesting that agent's own OAuth token out of the login keychain with `security find-generic-password`. Three things separate them. It is macOS and keychain-based, where this is Windows and file-based, which is the platform split the library already treats as legitimate. Its sensor is keychain access by a process inside an agent session; this one's is a read audit over files on disk. And its scope is one agent's own credential taken from inside that agent, where this is an unrelated stealer process sweeping several vendors' stores in one pass - the cross-vendor breadth is the entire signal here and has no analogue there. [[H081]] and [[M014]] cover malicious npm packages that harvest LLM API keys, SSH keys and cloud credentials from developer environments; those are supply-chain execution vectors whose credential theft is incidental, and neither enumerates the AI agent session stores this handler targets.
  Adjacent coverage - [[M062]] scores credential-store breadth volumetrically across coarse families and is the right tool when the target list is unknown; its family map does not enumerate AI-agent stores, and adding them as a family there is worth doing alongside this hunt. [[H409]] covers the other direction of AI-agent compromise, where the agent's own configuration is repointed so that what it reads leaves with the conversation, rather than its stored credential being stolen. [[H419]] covers a stealer hosting its collection inside `explorer.exe`, which is a reminder that the initiating process here may be a signed Microsoft binary rather than an unsigned dropper.

# H422

Check Point Research published an analysis in October 2026 of Aokigahara, a newly observed infostealer, noting that "An earlier version may have been known as Kamidere or Stygian." Most of what it does is unremarkable: browsers, wallets, VPN clients, FTP clients, password managers, messaging apps, gaming platforms. The part that is new is a dedicated handler for AI tooling.

The report is direct about it: "The stealer collects authentication files, session data, and configuration files associated with Claude, ChatGPT Desktop, Codex, Cursor, Windsurf, GitHub Copilot, Gemini CLI, and other tools." A companion `ide` handler widens that to the surrounding development environment, where "Notable targets include Git credential files, files under .ssh that may contain private keys, AWS/Azure/Google Cloud credential and configuration files, and GitHub Copilot storage." The handler also reaches the OS credential store directly: "It also queries Windows Credential Manager."

What makes this huntable rather than merely alarming is the shape of the target set. Each of these artefacts has exactly one legitimate reader, and the readers are different vendors' products. A single process opening Claude Code's credential file, Codex's auth file and Cursor's state database in the same minute is not a plausible legitimate event, because no legitimate program is a client of all three. That is a much narrower and cheaper signal than credential theft usually offers, and it is narrow enough to put a read audit directly on the files rather than needing a volumetric model to find the collection burst.

The reason to care about the collection set beyond the workstation is what the credentials are. These are session tokens and API keys for services that hold conversation histories, uploaded files and source code, alongside cloud credentials and SSO caches that reach the estate's cloud control plane. Check Point's own framing of the finding is the line worth carrying into triage: AI application credentials and session data "should be treated as sensitive assets alongside browser sessions, cloud credentials, and developer keys."

Check Point does not claim to know what the operators do with the stolen material, and this hunt makes no such claim either: "the analysis does not confirm how its operators monetize the stolen data."

## Why

- The target set has a one-to-one relationship between file and legitimate reader, which is rare in credential hunting. The detection does not need to know which tool is in use or what the file contains; it needs only to notice one process crossing between vendors, so it survives new tools being added to the collection list.
- The set is small enough to audit reads directly. Credential theft is normally invisible to file-creation telemetry because reading is not creating, and the usual workaround is a volumetric model over broad families. Here the named set is a few dozen small, rarely-read files, so a narrow SACL makes the actual behaviour visible rather than its side effects.
- The credentials are bearer tokens with blast radius past the endpoint. A stolen session token for a cloud AI service can expose conversation history and uploaded source code without any password being used, and the same sweep takes `.aws\credentials` and the SSO cache, so a workstation infection becomes a cloud identity incident.
- Developer workstations are where these paths live, which concentrates the hunt on the hosts with the most onward access in the estate. The same machines hold Git credentials and SSH private keys, and the `ide` handler takes those too, so a hit scopes directly to source control and production access.
- Existing credential-theft coverage keys on families this set does not belong to. Browser profiles, password-manager vaults and wallet files are well covered; AI agent stores are a new family that path-based hunts have no entry for and breadth models score as a single coarse bucket at best.
