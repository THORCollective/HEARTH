false_positive_notes: |
  Host Profiles exist to change host configuration, and remediation is a routine operation, so every element of this sequence is legitimate in isolation and the hunt is about combination and context.
  - Scheduled compliance remediation is the normal use of the feature. Clusters are checked and remediated on a cadence, and that generates exactly the read-then-push pattern. Compare against the change calendar; a remediation outside an approved window is the population worth working, and a remediation inside one that changed a service state nobody asked for is the rarer and more interesting case.
  - Administrators legitimately enable SSH on ESXi hosts, frequently, and often through vCenter. Troubleshooting, vendor support cases, patching and storage work all do it. The sequence here is more specific than SSH being enabled: it is SSH being enabled through the Host Profile desired-state mechanism rather than through the host services panel or an esxcli call, which is an unusual path for a human doing a one-off job.
  - Deliberate policy change produces a permanent version of this. A site that decides SSH should be on across a cluster will push it through a Host Profile once and the profile will then enforce it forever. Capture the intended desired state of each profile as data; a profile whose stored desired state includes a running TSM-SSH is a posture finding to raise separately, and it will otherwise mask this hunt entirely.
  - SSH from the vCenter appliance address can be legitimate. Some automation, backup integrations and VMware tooling connect from the appliance or from management jump hosts. Enumerate what is allowed to connect from there; the report's point is that the address is trusted by default, not that it is always wrong.
  - If vpxa.log and vobd.log are not forwarded off the hosts, this hunt cannot run, and on a host that has been encrypted they are gone. Establishing whether these logs are centralised is the first pass and is worth reporting on its own, because it is also the difference between reconstructing an incident at this layer and not.
  - The thirty-three second interval and the eleven minute total are observations from one incident, not thresholds. A slower push on a larger cluster will stretch both. Use them to rank, not to filter.
notes: |
  Source reporting is Kaspersky GERT's November 13, 2026 account of an engagement in which an adversary destroyed an organization's virtualization estate over ten days, covering four ESXi hosts, every virtual machine on them, both vCenter Server Appliances and all connected backup infrastructure, with ransom notes identifying BlackNevas. The framing matters for this hunt: Kaspersky reports that "no virtualization layer vulnerabilities were exploited: no guest-to-host escapes, no hypervisor memory corruption. Every action taken against ESXi was executed through legitimate VMware management interfaces."
  The reported sequence, verbatim from the evidence table - At T+0, vCenter performed a "Host configuration read through Host Profile workflow", recorded in vpxa.log. At T+10m18s, a "Configuration change pushed to enable SSH", recorded in vpxa.log. At T+10m51s, the "TSM-SSH service reached RUNNING state, indicating that SSH has been enabled on the host and it is accessible from a remote device", recorded in vpxa.log and vobd.log. Kaspersky observes that "the 33-second interval between the configuration push and TSM-SSH reaching RUNNING state is short enough for us to be able to quickly correlate these events by comparing logs from different sources", that "overall, it took the attacker eleven minutes after the initial configuration read to reconfigure the host from policy-disabled SSH to direct remote access support", and that "subsequently, direct SSH access to the target ESXi hosts originated from the vCenter appliance IP, a source that would normally be considered highly trusted on the management network."
  Kaspersky's own detection recommendation is this hunt - "An alert should be generated when Host Profile compliance (or remediation in VMware terms) changes TSM or TSM-SSH configuration outside an approved window, particularly when followed by a new SSH session from vCenter or another management appliance. This sequence is more precise than alerting on SSH alone because each step is legitimate in isolation but dangerous in combination."
  Closest existing HEARTH coverage - [[H458]] covers an ESXi root SSH session disabling the execInstalledOnly policy after a blocked execution and then running the now-permitted binary against the datastore tree. That is the same intrusion shape one step later: it begins with a root SSH session already in hand. This hunt covers how the SSH session came to exist, through the management plane rather than on the host, and its telemetry is vCenter task records and vpxa or vobd logs rather than ESXi shell activity. The two are a pair and should be run together. [[H074]] covers temporary virtual NICs created on ESXi-hosted virtual machines for pivoting, which is a different management-plane abuse.
  Core filter 1, the ordered triple - The hunt itself. For each ESXi host, select Host Profile configuration reads and pushes from vpxa.log, then look for a TSM or TSM-SSH service transition to a running state in vpxa.log or vobd.log within a few minutes of the push. Triage values are the initiating vCenter account from the task record, the target scope - a single host, a cluster, or everything attached to the profile - the timestamp against the change calendar, and the direction of the change. Kaspersky's trust-boundary point is the triage question in one line: "the distinguishing context becomes authorization, the timing, the source account, the change window, and whether the desired state itself weakens security."
  Core filter 2, the session that uses it - Join the service transition to ESXi auth.log for a new SSH session within the following minutes, and record its source address. A session from the vCenter appliance address is the reported case and is also the hardest to notice, because management-network traffic from vCenter to a host is what the architecture is made of. Where a management-network sensor exists, take the session record from there as well, so the finding does not rest on the host alone.
  Core filter 3, which client connected - Kaspersky reports that the payload "was delivered to ESXi via SFTP" and that "the auth.log authentication log file exposed a client identifier associated with FlowSsh, Bitvise's SSH client library for C, C++ and .NET." An SSH client identifier that is not the one your administrators and tooling use is a cheap, high-signal field that almost nobody inventories. Build the list of expected client identifiers for your estate - it is short - and treat anything else as a finding. Kaspersky is careful that "the library identification should rest primarily on the recorded client identifier rather than on behavioral inference alone", so use the string, not the behaviour, to name the client.
  Core filter 4, the behaviour in the session, as corroboration - From shell.log, Kaspersky reconstructed a repeating pattern: a session executing only `true`, then a session running `chmod +x /tmp/esx64`, then another `true`, then `./tmp/esx64 /selftest`, with the self-test running about sixteen seconds roughly three hours before detonation. Kaspersky explicitly declines to treat this as a signature - "the sequence should therefore be hunted as a behavioral fingerprint, not treated as a unique signature for FlowSsh. Its value increases when combined with an unusual SSH client identifier, SFTP staging to /tmp, chmod, and a subsequent self-test or payload execution." Use it that way: as a reason to escalate a session found by filters 1 to 3, not as a detection of its own. The generic and more durable version of the same check is Kaspersky's pre-impact guidance to "treat unexpected executable staging under /tmp, followed by execution and subsequent access to /vmfs, as a critical pre-impact sequence."
  Sample correlation, expressed against forwarded ESXi logs in a generic SIEM idiom, with both windows bounded so events from different days cannot pair:
  ```sql
  WITH pushes AS (
    SELECT host, event_time AS push_time, raw_message
    FROM esxi_vpxa
    WHERE raw_message LIKE '%HostProfile%'
      AND (raw_message LIKE '%TSM-SSH%' OR raw_message LIKE '%TSM%')
      AND event_time > now() - interval '90' day
  ),
  running AS (
    SELECT host, event_time AS running_time
    FROM esxi_vobd
    WHERE raw_message LIKE '%TSM-SSH%'
      AND raw_message LIKE '%RUNNING%'
      AND event_time > now() - interval '90' day
  ),
  sessions AS (
    SELECT host, event_time AS ssh_time, source_address, client_identifier
    FROM esxi_authlog
    WHERE event_type = 'ssh_session_opened'
      AND event_time > now() - interval '90' day
  )
  SELECT p.host, p.push_time, r.running_time, s.ssh_time,
         s.source_address, s.client_identifier
  FROM pushes p
  JOIN running r
    ON p.host = r.host
   AND r.running_time BETWEEN p.push_time AND p.push_time + interval '10' minute
  LEFT JOIN sessions s
    ON p.host = s.host
   AND s.ssh_time BETWEEN r.running_time AND r.running_time + interval '60' minute
  ORDER BY p.push_time DESC
  ```
  The session join is a left join deliberately: a Host Profile that enabled SSH and was never used still needs to appear, because an enabled TSM-SSH across a cluster is a standing exposure whether or not this particular operator came back for it.
  What follows, for scoping - Kaspersky reports that on the disaster-recovery host "all VMs stopping within 23 seconds, while vmksummary.log, which stores the number of running VMs each hour, showed it dropping from normal VM counts to zero", and records the detonation command as `./tmp/esx64 /p /vmfs/ /depth 5 /wipe /allsys /detach /-showvolumes`. The running-VM count in vmksummary.log is an hourly figure, which makes it a coarse but extremely reliable retrospective check across an estate: a host whose count drops to zero outside a maintenance window is worth investigating immediately, and the file is small enough to collect everywhere.
  Expected, not observed by Kaspersky - How the attacker obtained the vCenter privilege that made the Host Profile workflow available, in this specific engagement. Kaspersky lists four recurring routes into the virtualization layer - vulnerability exploitation, credential reuse from the Windows estate, Active Directory integration abuse, and backup infrastructure as a credential bridge - and states that in this incident there was "no evidence pointing to an ESXi vulnerability as the initial access path", but does not attribute the management-plane access to one of the remaining three.
  Scope - Any environment running vCenter with Host Profiles available, which is most VMware estates above a few hosts. Kaspersky's architectural conclusion is the reason this hunt is worth standing up permanently rather than running once: "centrally administered controls should not be considered independent once the central management tool is compromised", which is why it recommends treating vCenter as a Tier 0 asset and comparing vCenter-to-ESXi traffic against a behavioural baseline rather than trusting it implicitly.

# H480

No exploit. No guest escape. No hypervisor memory corruption.

Kaspersky's emergency response team walked a ten-day intrusion that ended with four ESXi hosts, every VM on them, both vCenter appliances and all the backup infrastructure destroyed — and found that every single action taken against ESXi went through a legitimate VMware management interface.

The step worth stealing from that report is how SSH got turned on.

Host Profiles are a compliance feature. Their job is to capture a known-good configuration and enforce it across hosts, so that drift gets corrected automatically. Among the things a profile can enforce is the state of Tech Support Mode SSH.

So the attacker read the host configuration through the Host Profile workflow. Ten minutes later, pushed a change. Thirty-three seconds after that, TSM-SSH was running on the target hosts and reachable from the network. Eleven minutes, start to finish, from policy-disabled SSH to direct remote access — and every event in that chain is the compliance system doing precisely what compliance systems do.

Then the SSH session arrived from the vCenter appliance's own address. On a management network, that is about the most trusted source there is.

That is the part to sit with. Host hardening is real, but it is not independent of the thing that administers it. If vCenter can change host state, then owning vCenter means owning host state, and the malicious version of that change looks structurally identical to the legitimate one: read configuration, apply desired state, observe the result.

What separates them is not the action. It is who, when, and in which direction — toward a stronger configuration, or a weaker one.

## Why

- **It is a trust-boundary failure, not a vulnerability, so patching does not touch it.** There is nothing to fix in ESXi or vCenter here. The feature worked as designed. That makes detection the only available control, and it makes the detection a question about authorization and timing rather than about a signature.
- **Each step is individually unremarkable and the combination is not.** Host Profile remediation happens on a schedule. Administrators enable SSH on hosts all the time. vCenter talks to its hosts constantly. Alerting on any one of those is unworkable; the ordered triple of read, push, and service-running, outside a change window, is specific enough to act on.
- **The direction of the enforced change is the cheapest triage question there is.** A compliance system that enforces a weaker configuration than the one before it is doing the opposite of its job. Capturing each profile's intended desired state as data turns "was this remediation legitimate?" into a comparison instead of a judgement call.
- **The SSH client identifier is free signal that almost nobody collects.** ESXi records what connected. The list of clients your administrators and tooling actually use is short and stable, so an unfamiliar identifier in `auth.log` is high-confidence and needs no baseline period to become useful.
- **The hypervisor is where EDR is not.** Guest agents cannot see an ESXi-side process touching a VMDK; they record the consequences — I/O failures, an abrupt shutdown — after the fact. Management-plane and host-native telemetry are the only sources that explain what happened, which means forwarding `vpxa.log`, `vobd.log`, `auth.log`, `shell.log` and `vmksummary.log` off the hosts is a prerequisite, not a refinement. On an encrypted host, they are gone.
