false_positive_notes: |
  `defaults` is a completely normal administrative tool and runs constantly. MDM (Jamf, Kandji, Intune, Workspace
  ONE), configuration-management (Ansible, Chef, Munki), developer dotfiles, onboarding scripts and countless
  "macOS setup" gists all call `defaults write` in volume — a rule on the binary alone is unusable. Legitimate
  domains are also sometimes written by scripts rather than by the owning app, so "written by a shell" is not by
  itself suspicious. The discriminators that hold up:
  (1) the DOMAIN does not correspond to an installed application bundle identifier and does not follow reverse-DNS
      form, or is a random-looking string;
  (2) the KEY is a random-looking token rather than a documented preference name;
  (3) the VALUE is unusually large (kilobytes) and Base64-shaped, where normal preference values are short scalars;
  (4) the same domain is later READ by a shell interpreter whose output feeds `base64 -d`, `gunzip`, `openssl enc`
      or `eval`.
  Legitimate exceptions to expect: some apps do cache encoded blobs (license tokens, window-state, serialised
  settings) in their own domains — those will have a real reverse-DNS domain matching an installed app, which is
  exactly the check that separates them. Also expect noise from security tooling and backup agents that enumerate
  preferences broadly; scope those out by signer.

  - Payload keys observed: `mpirv_eahpi_apm`, `ychax_muwch_ucy` — deliberately random-looking, not preference-like.

  - Prior art the report notes: NetWire and FruitFly also misused `defaults` to store state — this is an

  HUNT LOGIC (macOS):
  1. WRITE side — ESF NOTIFY_EXEC where the executable is /usr/bin/defaults and argv contains `write`; extract the
     domain (argv[2]) and key (argv[3]) and the value length. Flag where:
       - value length > ~512 bytes AND matches ^[A-Za-z0-9+/=]+$ (Base64 shape), and/or
       - domain is not resolvable to an installed bundle ID (compare against `system_profiler SPApplicationsDataType`
         or the /Applications + ~/Applications bundle inventory), and/or
       - key does not match the documented key set for that domain.
  2. READ side — the higher-fidelity half. Flag a shell (`zsh`, `bash`, `sh`) or `osascript` process whose command
     line chains `defaults read` into decoding/execution:
       defaults read <domain> <key> | base64 -d | gunzip | ...
       eval "$(defaults read <domain> <key> | base64 --decode)"
     Any `defaults read` whose output is piped to `base64 -d`, `gunzip`, `zcat`, `openssl enc -d`, `eval`, `sh -c`,
     or `osascript -e` is worth review on its own — that composition has essentially no benign use.
  3. Filesystem corroboration — ESF NOTIFY_WRITE/CREATE against ~/Library/Preferences/<random>.plist; then inspect
     with `plutil -p ~/Library/Preferences/<domain>.plist` looking for multi-kilobyte string values.
  4. Inventory sweep — list ~/Library/Preferences/*.plist and diff domain names against installed bundle IDs. On a
     developer fleet this is a small, tractable list and orphan domains stand out.
  5. Pivot on a hit — check for the co-occurring XCSSET stages: `/tmp/r` and `/tmp/p.app` creation-then-deletion,
     `~/.tr` / `~/.tr_map`, XProtect/telemetry impairment ([[H255]]), and Xcode/git-hook infection ([[H256]]).

# H254

The interesting move in XCSSET v4.0 is not that it persists — it is *where it puts the payload*. Instead of dropping a file that XProtect, a YARA sweep or an EDR file scan could find, it writes a Base64-encoded, gzipped payload into the macOS preferences system using `defaults`, under a domain it generates per host and a key that looks like `mpirv_eahpi_apm`. A zsh loader reads it back, decodes it, and `eval`s it in memory. The staging files it does create — `/tmp/r`, `/tmp/p.app` — are deleted immediately after use.

HEARTH had no coverage of preference-domain payload staging, and no hunt using T1647 at all.

## Why

- **It defeats file-based detection by never being a file.** The payload lives in a plist that looks like application settings. XProtect signatures, file-reputation lookups and disk YARA scans all have nothing to match, and a preferences plist is not something an incident responder pulls first.
- **The per-host domain name kills IOC sharing.** Unit 42 could publish the keys but not the domain, because it differs on every victim. That forces the hunt onto structure — value size, Base64 shape, domain-to-bundle-ID mismatch — which is more work up front and considerably more durable.
- **The read side is where the signal is clean.** `defaults write` is drowning in legitimate use from MDM and setup scripts. But `defaults read` piped into `base64 -d | gunzip | eval` is a composition with no plausible administrative purpose, and it is the step the malware cannot skip if it wants to run.
- **This is an established pattern, not an outlier.** Unit 42 points out NetWire and FruitFly used `defaults` for state storage years ago. Building the detection now covers a technique family rather than one sample, which matters on a developer fleet where the `defaults` baseline is already noisy and nobody has characterised it.
