false_positive_notes: |
  Legitimate PsExec use is common in many estates, and the real Sysinternals PsExec also creates a named pipe and installs a service. The differences are specific and checkable: the genuine tool installs a service named `PSEXESVC` with a Microsoft-signed `PSEXESVC.exe` in `%SystemRoot%`, whereas Unit 42 records this module registering a service named `PsExec` from a standalone executable named `PsExecService.exe`. Reconcile every hit against the approved remote-execution register and against the service name and binary signer, not against the pipe name alone.

  Endpoint security products do write executables into their own directories, including under `C:\ProgramData`, and they update them frequently. The discriminator is ownership rather than location - compare each executable in those directories against the vendor's file inventory or installation manifest, and treat an executable the vendor does not claim as the finding. Expect some legitimate exceptions from support-supplied diagnostic tools, which should be ticketed.

  Watchdog and mutual-restart patterns exist in legitimate software, particularly in monitoring agents, update services and some licence-enforcement components. They differ in being signed, installed under Program Files, registered in the software inventory, and generally restarting a service through the Service Control Manager rather than relaunching an executable from a path handed over a named pipe.

  Services that install and remove themselves inside minutes are produced legitimately by some software installers, patch-management tools and vulnerability scanners with credentialed-scan features. Those appear on a schedule, from a registered scanner source, and with a recognisable service name. Rank candidates by whether the service name is in the approved register first, and by lifetime second.

  Unit 42 recovered `PsExecService.exe` but was not able to retrieve a second executable deployed alongside it, named `SecurityGuard.exe`, so nothing is known about that component's behaviour. Treat the name as a lead for a file-inventory sweep rather than as a described capability, and do not attribute behaviour to it.

  The three-second write cadence and the one-second heartbeat read are Unit 42's description of the recovered components. They are implementation values the author can change trivially, and they are also below the resolution of some telemetry pipelines that deduplicate or sample pipe events. Treat the exact cadence as a confirming measurement on a candidate pair, and the pipe name and the process pairing as the primary filters.
notes: |
  Named-pipe leg (Sysmon Event ID 17 for pipe create, Event ID 18 for pipe connect) - Core filter: any pipe whose name contains `WINDOW_SEC_WATCHDOG`, and separately any pipe whose name contains `PSEXEC` created by a process that is not the signed Sysinternals tool. Triage values are `pipe name`, `initiating process path, command line and SHA256`, `signer`, `user`, `event type` (create versus connect) and `timestamp`. Correlation that identifies the pair: for a given pipe name, one process appearing repeatedly as the writer and a different process appearing repeatedly as the reader, with both processes running from paths outside Program Files. Pipe telemetry is the only place this relationship is visible, because neither component writes to disk or to the registry while it is operating.

      DeviceEvents
      | where Timestamp > ago(30d)
      | where ActionType in ("NamedPipeEvent", "NamedPipeConnectionEvent")
      | extend Pipe = tostring(parse_json(AdditionalFields).PipeName)
      | where Pipe has_any ("WINDOW_SEC_WATCHDOG", "PSEXEC")
      | summarize Events = count(), FirstSeen = min(Timestamp), LastSeen = max(Timestamp), Procs = make_set(InitiatingProcessFolderPath, 10)
          by DeviceName, Pipe, InitiatingProcessFileName, InitiatingProcessSHA256
      | order by Events desc

  Confirm the field name for the pipe in your own tenant before relying on the parsed value, since named-pipe data is carried in `AdditionalFields` rather than in a dedicated column and the key name has varied. Where only Sysmon is available, Event IDs 17 and 18 carry the pipe name directly and are the better source.

  Cadence measurement (on a candidate pair only) - For a pipe identified above, compute the inter-arrival times of the write events from one process and the read or connect events from the other. Unit 42 states the implant writes its path every three seconds and the watchdog pulls a heartbeat every second, with a 15-second silence triggering a relaunch. A near-constant three-second write interval with sub-second variance is machine-generated by construction, and the 15-second threshold means a terminated implant reappears within roughly 15 seconds - which is also the operational tell during response: if a process is killed and an identical process starts from the same path about fifteen seconds later, the watchdog is still running and must be removed first.

  Security-product directory leg (Sysmon Event ID 11, DeviceFileEvents, file inventory) - Core filter: executables, DLLs and scripts present under directories owned by endpoint security products - including `C:\ProgramData\Cyvera\`, which Unit 42 names, and the equivalent directories for whichever products the estate runs - that do not appear in the vendor's own file inventory. Unit 42 observed the watchdog deployed into `C:\ProgramData\Cyvera\Ransomware\` specifically to lower suspicion by hiding within security-product directory structures. Triage values are `file path`, `file name`, `SHA256`, `signer`, `creation time`, `creating process path and command line` and whether the vendor claims the file. Strong red flags: the file is unsigned or signed by an unexpected publisher; the creating process is not the security product's own installer or updater; the file is an executable in a subdirectory whose purpose is data rather than code.

  Build the inverse list as a standing control, not just a hunt: enumerate every executable under each security product's directories, diff against the vendor manifest, and keep the diff at zero. It is a small, slow-changing set in most estates and it closes an entire class of masquerade.

  Self-destructing-service leg (System Event ID 7045, Security Event IDs 4697 and 4699, SCM Event IDs 7036 and 7040, service registry key create and delete) - Core filter: services whose install and removal events fall within the same short window, and in particular any service named `PsExec` whose image is a file named `PsExecService.exe`. Unit 42 records the module registering itself as a local Windows service named `PsExec` and running an internal self-destruct timer that uninstalls the service and cleans up its artifacts after five minutes of inactivity. The practical consequence is that a point-in-time service inventory will not find it, so this leg must be run against event history rather than against current state.

  Compute, per host, the lifetime of every service installed in the lookback window as the gap between its install event and its delete event, and rank ascending. A service whose entire existence is under ten minutes, which executed something in the middle of that window, and whose name is not in the approved register, is the shape to triage. Triage values are `service name`, `display name`, `image path`, `service account`, `start type`, `install time`, `delete time`, `installing process` and `any process created by the service during its lifetime`. Strong red flags: the service created a named pipe during its lifetime; a child process under the service account ran `cmd.exe` or `powershell.exe`; the image path is in a user-writable directory; the same short-lived service name appears on several hosts within hours, which is lateral movement rather than a one-host event.

  Recovered development path, for corroboration only - Unit 42 reports the module's PDB string explicitly classifies it as an external module of the family, reading `d:\proj\KUKURAT\modules\MyPsExec-master\PsExecService\`, which is consistent with the project paths recovered from the predecessor family's variants. A PDB path containing `KUKURAT` or `MyPsExec-master` in a recovered sample is confirmation rather than a hunting filter, since it requires the binary in hand.

  Scope note: H498 covers the HTTP/3 transport this implant uses and H499 covers its heuristic camouflage engine; this hunt covers the components that keep it alive and move it sideways. HEARTH's existing service-persistence and named-pipe hunts key on other families and other pipe names, and none of them cover a mutual-heartbeat watchdog pair, a binary planted inside an endpoint security product's own directory tree, or a service whose design is to remove itself before an inventory can see it.

# H500

Unit 42's November 16, 2026 analysis of TGR-STA-0049 describes two supporting components deployed alongside the KUKURAT backdoor, both of which are considerably easier to detect than the implant they protect.

The first is a watchdog. KUKURAT writes its own active file path to a named pipe called `WINDOW_SEC_WATCHDOG` every three seconds; a companion process reads that path and polls a heartbeat every second, and relaunches the implant from the cached path if fifteen seconds pass in silence. In one incident the watchdog was placed in `C:\ProgramData\Cyvera\Ransomware\` — a folder structure historically associated with Cortex XDR — which Unit 42 reads as an attempt to lower suspicion by hiding inside a security product's own directories.

The second is a lateral-movement module compiled as a standalone executable, `PsExecService.exe`, which Unit 42 assesses may be partially based on the open-source MyPsExec project. It installs a local Windows service named `PsExec`, creates a named pipe called `PSEXEC`, supports shell execution and file transfer in both directions, and uninstalls itself and cleans up its artifacts after five minutes of inactivity.

Both components make a trade that favours the defender: durable access and remote execution, in exchange for a named pipe, a service install event, and a file in a place its supposed owner never put anything.

## Why

- The watchdog turns the implant's silence into a signal. A pipe written on a fixed three-second cadence by one process and read by another is machine-generated by construction, and the fifteen-second relaunch threshold means that killing the implant produces an immediate, observable resurrection — which is both a detection and the reason to find the watchdog before attempting removal.
- Hiding inside a security product's directory is settled by a question the vendor can answer. The product's own file inventory either claims a file or it does not, and maintaining that diff at zero is a cheap standing control that closes the whole technique rather than this one instance of it.
- A service that removes itself after five idle minutes is invisible to every inventory-based control and fully visible to event history. That asymmetry is worth exploiting deliberately: install and delete events for services are recorded by stock Windows logging, so the service's short lifetime is itself the query.
- These components are where the actor's otherwise strong tradecraft breaks down. The implant uses HTTP/3 to avoid inspection, loads its capabilities as memory-only modules to avoid static scanning, and runs a camouflage engine to corrupt the behavioural baseline — but it still needs something to restart it and something to reach the next host, and both of those leave ordinary Windows artefacts.
