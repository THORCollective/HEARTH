title: A request allowed by its URL but dispatched by its header - X-DSCGI-PATH pointing somewhere the URL never did
hypothesis: >-
  One process decides whether a request is allowed and a different process decides where it goes, and
  they read different parts of the request. Volexity found UTA0576 exploiting a fully patched Ivanti
  Connect Secure appliance (22.8R2.4, Build 19097) in the first week of October 2026, and the first link
  in the chain is an authentication bypass of exactly that shape - "An authentication bypass in ICS
  welcome.cgi allowing requests to be routed to arbitrary CGI files, including those protected by
  authentication". The attacker sends the request to a page that is public by design,
  `/dana-na/auth/url_default/welcome.cgi`, and names a different script in a header,
  `X-DSCGI-PATH: /home/webserver/htdocs/dana/fb/smb/wu.cgi`. As Volexity puts it, "The URL is used to
  determine whether the request is allowed, while the header path is used to determine the destination of
  the request." Hunt for requests to the ICS login page carrying an `X-DSCGI-PATH` header whose value
  does not correspond to the requested URL, and for the second use of the same primitive, where the header
  points at a freshly uploaded file under `/home/runtime/tmp/`.

false_positive_notes: |
  The header is a real Ivanti internal mechanism, not an attacker invention, so it will appear in
  legitimate traffic. The appliance routes its own front-end and back-end requests to CGI handlers with
  it, which means a proxy that logs it will see benign values in normal operation - that is the baseline,
  and it is why the finding is a MISMATCH rather than the presence of the header. Before querying,
  collect a few days of header values per URL path and learn which pairs are normal for the firmware
  build in use. Expect legitimate pairings to be stable and few. Two further cautions. First, a firmware
  upgrade can change the legitimate pairing set, so a baseline taken before an upgrade will produce a
  burst of false findings after one - version the baseline by build. Second, any security scanner,
  penetration test or research tool that fuzzes headers against the appliance will generate exactly this
  pattern, so correlate against the scanning schedule and the known source ranges of authorised testing
  before treating a hit as an intrusion. Conversely, do not treat a single malformed request as benign
  just because it looks like a scan - Volexity notes the operator re-ran the entire chain for every
  command executed, so genuine exploitation looks like volume, not a one-off.

# H384

Two pieces of the appliance read the same request and disagree about what it is.

The front end looks at the URL to decide whether the request needs authentication. `welcome.cgi` is the login page, so the answer is no. A different part looks at the `X-DSCGI-PATH` header to decide which CGI script actually handles the request. The attacker puts a public path in the URL and a private one in the header, and the request is admitted by the first check and dispatched by the second. Volexity states it plainly: "The URL is used to determine whether the request is allowed, while the header path is used to determine the destination of the request."

That is the first of three vulnerabilities UTA0576 chained against a **fully patched** Ivanti Connect Secure appliance — 22.8R2.4, Build 19097, the latest version at the time. The second is a file write in `wu.cgi`, and the third is a privilege escalation through the `dsinvoked` broker that gets the operator to root. Ivanti fixed the first two as CVE-2026-104935 on 13 October 2026. The privilege escalation was still open at publication.

The same header primitive gets used twice, which is the part worth building a query on. `wu.cgi` writes an upload to `/home/runtime/tmp/<MD5(filename)>` and only *then* checks whether it is a valid ZIP, deleting it when it is not. UTA0576 uploaded a Perl script named `.zip` and raced that deletion with parallel requests whose header pointed at the file just written. Win the race and the appliance executes your Perl as the `cgi-server` user. Lose it and you try again — which is why the behaviour shows up as a burst rather than a single request.

There was no webshell and no backdoor. Commands and results rode inside the exploit chain's own HTTPS requests, and the whole chain was re-run for every command. For a hunter that is good news: the volume is the signal.

Two practical points decide whether this hunt works at all.

The header is not in any default log format. No proxy records `X-DSCGI-PATH` unless someone adds it, and it travels inside TLS, so a device that cannot see decrypted HTTP cannot see it. Adding the header to the captured set is step one, and a query that returns zero before that step has told you nothing.

And the collection point has to sit *in front of* the appliance. UTA0576 selectively rewrote `/home/runtime/dlogs/debuglog` and `/var/log/audit/audit.log` from root. Anything the appliance logs about its own compromise is written by a process the attacker controls. Mandiant made the same recommendation about a different appliance in the same month — put a reverse proxy or WAF with full URI logging in front, "to keep a record of request paths that the appliance cannot alter."

Finally, do not pin the query to `wu.cgi`. Volexity expects the paths to move: "It is likely that threat actors will identify additional paths that can either be used as the URL or header target for this exploit." The durable question is not which script was named. It is that the URL and the header named different things.

## Why

- **The vulnerability class is a disagreement between two parsers, and the disagreement is directly observable.** One component authorises on the URL, another dispatches on a header. Logging both and comparing them turns an authentication bypass into a string comparison.
- **The appliance was fully patched when it was compromised.** 22.8R2.4 Build 19097 was current. Patch level was not a defence here, and the privilege-escalation link in the chain was still unfixed when Volexity published.
- **Volexity recommends exactly this comparison.** "If possible, monitoring for mismatches between the URL path and X-DSCGI-PATH is advisable" — this hunt implements the vendor's own best available guidance rather than inventing a mechanism.
- **Re-running the chain per command makes the activity loud.** No webshell was deployed, so every single command meant another pass through the authentication bypass, the upload race and the escalation. Exploitation looks like volume.
- **The execution leg has a dispatch target with no legitimate use.** A header pointing into `/home/runtime/tmp/`, the upload staging directory, is not something normal appliance operation produces.
- **The race condition produces a recognisable burst shape.** Several near-identical execution requests in quick succession, against a path that was just written, is a timing pattern a static single-request rule would miss.
- **Appliance-local logs cannot be trusted for this.** The operator truncated the ICS debug log and the Linux audit log, so the detection has to live at a proxy or WAF the attacker never had root on.
- **The integrity checker does not help, and knowing that is part of the result.** The chain patched a library in memory and restored the configuration store afterwards, so Ivanti's Integrity Checker Tool reports no modifications on a compromised device.
- **The header value is a stable, learnable baseline.** Legitimate ICS traffic uses this mechanism with a small, predictable set of URL-to-header pairings per firmware build, which makes the anomalous pairing cheap to define and version.
