false_positive_notes: |
  Windows Script Host has real users and the volume is not zero, so the hunt is built on parent, path and provenance rather than on `wscript.exe` alone. The recurring benign populations are legacy line-of-business applications that ship `.vbs` or `.js` helpers and invoke them from an installer or a scheduled task; enterprise logon and deployment scripts run by Group Policy, SCCM or Intune, which appear with a system or service parent rather than a browser one; Microsoft Office COM automation, which launches script hosts with `/automation` and `-Embedding` on the command line and should be excluded explicitly; vendor installers and updaters that unpack a helper script into `%TEMP%` and run it; and administrator or developer workstations where somebody genuinely keeps utility scripts in their Downloads folder. In estates with old ERP, CAD or manufacturing software the legacy-script population can be surprisingly large and is best enumerated once and allowlisted by script hash and path, not suppressed by process name.
  Three discriminators carry nearly all of the fidelity and should be applied in this order. First, PARENT PROCESS - a script host whose parent is `chrome.exe`, `msedge.exe`, `firefox.exe`, `brave.exe`, `outlook.exe`, `7zFM.exe`, `WinRAR.exe`, `Bandizip.exe` or an `Explorer.exe` handling a freshly downloaded archive has no legitimate analogue; no browser workflow spawns `wscript.exe`. Second, the ARCHIVE-PATH SUBSTRING - a command line containing `.zip\`, `.rar\` or `.7z\` followed by a script name means the file is being executed from inside the archive viewer's extraction directory, which is what happens when a user double-clicks a script without extracting it first, and which essentially never happens in an administrative workflow. Third, the NETWORK CONNECTION that follows within seconds from the same `ProcessGuid` - a legacy business script generally talks to an internal host or to nothing at all, while a dropper reaches the internet immediately.
  Two cautions on interpretation. JScript and JavaScript share the `.js` extension, so extension alone carries no intent and a `.js` file in a Downloads folder is not by itself a finding - a developer's project files will match constantly. And the double-extension case is worth stating explicitly because BengalSEO relies on it: the file the victim sees is named to look like an `.exe` while actually being a script, so `File name extensions` being hidden in Explorer is what makes the lure work. A hunt for `.js.exe` or `.exe.js` style names is a useful adjunct but must not replace the parent-and-path logic, because the operator changes the filename far more readily than the delivery mechanism.

# H330

The DFIR Report's BengalSEO write-up spends most of its length on infrastructure — 84 GitHub accounts, a dozen free hosting platforms, a rotating redirector fleet, captcha gates to keep crawlers out, a self-hosted Matomo instance fingerprinting every visitor, and roughly 1,900 backlinks manufactured for a single lure page. It is a large, patient, professionally run traffic-distribution business. And then it ends, as these operations almost always do, in something completely mundane: a ZIP file, a JavaScript file named to look like an executable, and a user who double-clicks it.

That last step is the only part of the chain a defender can see from the endpoint, and it is also the part the operator has the least room to change. `wscript.exe` is Microsoft-signed, present everywhere, exempt from application control in most estates, and produces no reputation signal of any kind — which is exactly why the dropper is JavaScript rather than a binary. The compensating fact is that the execution leaves an unusually descriptive process-creation event: the parent is a browser or an archive utility, and the command line frequently still contains the path of the archive the script was run from without ever being extracted.

## Why

- **Nothing in this chain is a file the defender gets to scan.** The payload is a text script, the interpreter is a Microsoft binary, and in the execute-in-place case the script never lands as a durable file at all — it exists only in an archive utility's temporary extraction directory. Reputation, signing and hash-based controls have nothing to work with. Process lineage does.
- **`wscript.exe` spawned by a browser has no legitimate analogue, which is rare enough to build on.** Most LOLBIN hunts fight a large benign population. This one does not: no browser workflow launches Windows Script Host, no mail client does, and no archive utility does unless a human just double-clicked a script inside an archive. The benign script-host population in an enterprise overwhelmingly has a system, installer or Office-automation parent, and separates cleanly on that single field.
- **The archive-path substring is a behavioural artefact of the lure itself.** `.zip\` appearing in a command line means the victim opened the archive and ran the contents without extracting — the precise interaction the ZIP-with-a-fake-.exe-name lure is engineered to produce. It is not a property of the malware, which is why it survives repacking, renaming and rewriting of the dropper. It is a property of how a human is tricked into starting it.
- **The captcha gate in front of the payload means sandbox verdicts will be missing, not clean.** Turnstile and hCaptcha exist in this chain to keep automated analysis away from the ZIP, and the payload domain additionally checks an encoded timestamp before deciding whether to serve malware or a benign page. Detonation-based tooling is therefore likely to have seen the benign branch. A hunter who assumes "no sandbox verdict means no payload" will conclude the wrong thing, which is a specific argument for hunting the endpoint behaviour rather than waiting for a verdict on the file.
- **The infrastructure rotates but the terminal step does not.** Redirector domains are rotated by GitHub commits, hosting platforms are interchangeable, and the report already documents a sequential domain series the operator is plainly still incrementing. Hunting the redirectors is a treadmill. The script host, the parent process and the archive path are the same this month as they were two years ago in the SocGholish-era analytics that first described them.
