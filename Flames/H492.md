hypothesis: >-
  An operator who holds a shell on a Linux appliance but not root does not need an exploit if the
  appliance ships a debugger. Mandiant observed ARMORY CASTLE escalate to root on two separate
  appliances using the same two-step sequence. First a gdb command file is written into /tmp by
  decoding a base64 string through a shell redirect, so the privileged instruction never appears on
  a command line that a reviewer would read as dangerous. Then gdb is attached to an already-running
  process by PID with that file supplied as its command script, and the script shells out to set the
  setuid bit on /bin/env. Because gdb is running with the privilege of whatever it attached to, the
  chmod inherits that privilege, and from that point any user on the appliance can execute arbitrary
  commands as root through env. Hunt the mechanism rather than the outcome. Two process events, on a
  Linux appliance, within seconds of each other - a shell decoding base64 into a file under /tmp or
  another world-writable path, followed by gdb or gcore invoked with -p or -pid against a PID it did
  not spawn and with --command, -x or --eval-command pointing at that file. Neither event is normal
  on an appliance. gdb on a production appliance is already unusual, attaching it to a live service
  process is rarer still, and a debugger whose command script was assembled from base64 moments
  earlier has no legitimate reading.

false_positive_notes: |
  Legitimate debugging does happen on appliances, usually during a vendor support case. It differs in several ways: it is ticketed and time-boxed, it is normally performed by a named support engineer over an authenticated session rather than by a web service account, the gdb command file is typically typed interactively rather than decoded from base64, and a support engineer collecting a core dump uses `gcore` or `generate-core-file` rather than issuing `!chmod` from inside the debugger. Reconcile every hit against change management before treating it as an intrusion.

  Developer and build hosts attach debuggers to their own processes constantly. Scope this hunt to appliances and production servers; on a developer estate the `gdb -p` leg alone will be unusable, and the discriminating condition there is the `chmod` or `!`-prefixed shell escape inside the command script, not the attach itself.

  Package installs and upgrades legitimately set the setuid bit on binaries the distribution expects to carry it. Those changes are made by the package manager, with a package-owned path, and they restore a known set rather than adding to it. A setuid bit arriving on `/bin/env` is in no distribution's expected set.

  The explanation of why the chmod inherits privilege - that gdb runs with the privilege of the process it attached to - is the mechanism this hunt assumes, and Mandiant does not spell it out. Mandiant states only that ARMORY CASTLE performed the permission modification using the GNU Debugger and that enabling setuid on `/bin/env` would allow any user to execute commands as root. Treat the attach-privilege reasoning as inference, not as reported fact, and confirm on the appliance in question which account the target PID runs as before concluding how root was reached.

  Mandiant reports this as the same escalation technique used earlier on the Remote Support appliance, so the pattern is not specific to one product. Do not scope the hunt to vCenter or to BeyondTrust alone.
notes: |
  Process execution leg (auditd execve, Linux EDR, DeviceProcessEvents) - Core filter A, the command-file write - a `/bin/sh`, `/bin/bash` or `/bin/dash` process whose command line contains `base64 -d`, `base64 --decode` or `openssl enc -d -base64` and a redirect into a path under `/tmp/`, `/var/tmp/`, `/dev/shm/` or any world-writable directory. Mandiant recorded the exact form on the appliance as a shell invoked with `-c` that echoed a base64 blob into `base64 -d` and redirected the result to `/tmp/gdb_file`. That blob decodes to a two-line gdb script - a `!`-prefixed shell escape running `chmod u+s /bin/env`, then `q` to quit - so the privileged instruction is never visible in the process arguments.

  Core filter B, the attach - `gdb`, `/usr/bin/gdb` or `gcore` with `-p`, `-pid` or `--pid` naming a PID the invoking shell did not create, in combination with `--command=`, `-x` or `--eval-command`. Mandiant recorded this as gdb invoked with `-pid` against a live PID and `--command` pointing at the file written in filter A. Triage values are `process path`, `full command line`, `parent process path and command line`, `effective and real UID`, `working directory`, `session or TTY`, `appliance hostname` and `event time`. Correlation: filters A and B on the same host within 120 seconds, with B's `--command` argument equal to A's redirect target, is the whole hypothesis in two events.

  Strong red flags: the parent of the shell in filter A is a web or application server process - a Java container, `httpd`, `nginx` or an appliance-specific service - which means the shell came from a webshell rather than from a console; the gdb command file is deleted immediately after the attach; the PID attached to belongs to a process running as root.

  Permission-change leg (auditd syscall records) - Core filter: a `chmod`, `fchmod` or `fchmodat` syscall whose target is a binary under `/bin/`, `/usr/bin/`, `/sbin/` or `/usr/sbin/` and whose new mode sets `S_ISUID`, where the calling executable is not the package manager. An audit rule that captures this, to be installed before the hunt rather than after:

      auditctl -a always,exit -F arch=b64 -S chmod,fchmod,fchmodat -F perm=a -F dir=/usr/bin -k suid_change
      auditctl -a always,exit -F arch=b64 -S ptrace -F a0=16 -k ptrace_attach

  The second rule records `PTRACE_ATTACH` specifically - request value 16 - which is the syscall gdb uses to take control of a running process, and it catches the attach even when the debugger has been renamed. Both rules are additive and should be persisted in `/etc/audit/rules.d/` so they survive a reboot.

  Difference leg (setuid inventory) - Core filter: compare the current setuid and setgid set against the recorded set for that appliance class and investigate every addition. On a suspect appliance, the enumeration itself, which finds `/bin/env` if the escalation succeeded:

      find /bin /sbin /usr/bin /usr/sbin /usr/local/bin -xdev -type f -perm -4000 -printf '%M %u %g %p\n' 2>/dev/null | sort -k4

  `/bin/env` carrying `-rwsr-xr-x` is conclusive - no distribution ships it setuid, and a root-owned setuid `env` is a complete, trivially usable root shell for every local account, because `env` exists to execute a command with a modified environment. Treat it as an active compromise rather than a misconfiguration. B057 holds the per-appliance setuid baseline this leg compares against; without that register the difference cannot be computed and this leg degrades to reading the list by eye.

  Follow-on context (what to look for next on the same appliance) - Mandiant observed the escalation immediately followed by staging - `curl` with `-o` and `-k` pulling tooling from another compromised appliance into `/tmp`, a RAR archive extracted with a password, and the resulting binary executed from `/tmp`. Pull the full process tree for the hour either side of the gdb attach rather than triaging the two events alone.

  Scope note: the privilege-escalation space around setuid on Linux is already well covered in HEARTH from other angles, and this hunt is deliberately narrow on the mechanism rather than the state. H299 hunts a setuid helper being invoked with almost no arguments by an interpreter or a binary in a writable path; H387 hunts a copy of `/bin/sh` wearing a daemon name with the bit already set; H359 hunts a setuid-root `/bin/sh` left on a NetScaler by the web server restarting itself; M041 ranks the estate's setuid binaries by fleet prevalence; B057 baselines the appliance setuid set. None of them see a debugger being used as the chmod vehicle, which is this hunt's whole telemetry - `ptrace` attach plus a base64-assembled command script - and none of them would fire on `/bin/env`, which is not a shell and not a helper.

# H492

Mandiant and Google Threat Intelligence Group published analysis on November 19, 2026 of ARMORY CASTLE — the suspected PRC-nexus actor formerly tracked as UNC5221 — pivoting from a compromised BeyondTrust Remote Support appliance into an internal Linux appliance and on to VMware vCenter. The intrusion is notable for two zero-days and three purpose-built malware sets, but the step that made the rest possible is mundane: the actor escalated to root on a Linux appliance by using the GNU Debugger to set the setuid bit on `/bin/env`.

Mandiant records that this was the same escalation technique the actor had already used on the Remote Support appliance, which makes it a repeatable part of the playbook rather than an improvisation. It also illustrates why appliances are attractive: ARMORY CASTLE deliberately moved to internal Linux appliances that lacked EDR tooling, and gdb was available there to be used.

The two-event signature is small and specific. A base64 string is decoded into a command file under `/tmp`, so the `chmod u+s` never appears in process arguments. Then gdb attaches to a running process by PID with that file as its script. The result is a root-equivalent binary that every local account can use, and nothing about `env`'s own behaviour changes to give it away.

## Why

- The actor chose a path that avoids both an exploit and a suspicious command line. Decoding the instruction from base64 means the dangerous string exists only inside a file in `/tmp` and inside the debugger's own session, not in the execve record a reviewer is most likely to read. Hunting the pair of events recovers what the encoding was meant to hide.
- `/bin/env` setuid-root is an unambiguous finding. No distribution ships it that way, and because `env` exists to run a command with a modified environment, the bit alone is a complete local root escalation for any account on the box. There is no benign configuration this is consistent with.
- The telemetry is cheap where it exists and absent where it matters, which is the real finding. ARMORY CASTLE moved specifically to appliances without EDR. The `ptrace` and `chmod` audit rules in this hunt cost almost nothing to install and are the difference between recording this escalation and never seeing it; Mandiant's own hardening guidance for the same campaign leans on remote syslog forwarding of shell activity for exactly this reason, because it survives local `.bash_history` deletion.
- gdb is a legitimate binary with a narrow legitimate audience on production appliances. On a workstation or build host the attach is routine noise; on an appliance it is close to a zero-rate event, so the hunt is cheap to run and cheap to triage in the estate where it matters.
