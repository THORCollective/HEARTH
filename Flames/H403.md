false_positive_notes: |
  Every element of this hunt is rare on an appliance in a way it would not be on a developer
  workstation, which is what makes it tractable. `ptrace` is used legitimately by debuggers, by crash
  reporters, by `strace` and `gdb`, and by some runtime instrumentation and APM agents - but none of

# H403

Most implants give you something to look for. A file to hash. A port to scan. A connection in the netflow.

PEERSTITCH gives you none of those. Unit 42 is unusually direct about it: it "leaves no persistent binary on disk, opens no listening ports and initiates no outbound network connections. Instead, it communicates through traffic generated by legitimate processes on the infected host."

Here is how that works.

The injector — `lldprx` on disk, briefly — finds two FortiOS daemons by walking `/proc/`: `miglogd`, the logging daemon, and `iked`, the IPsec VPN daemon. It attaches with `ptrace(PTRACE_SEIZE, pid)`, freezes each one with `PTRACE_INTERRUPT`, snapshots the ARM64 registers, and builds a small bootstrap that calls `mmap` for 16,384 bytes of read-write-execute memory. Into that buffer goes a 1,344-byte hook payload, written through `/proc/<pid>/mem`. Then the injector deletes itself from disk and kills its own staging process.

No new process exists. The daemons keep their PIDs and their names. Nothing was added to the filesystem.

The target selection is the elegant part. One daemon sees all the logging; the other terminates VPN sessions. Between them they observe the traffic the implant needs and control the decision it wants to influence.

And the channel between them is not a channel in any normal sense. The hooks watch data "already passing through the process without redirecting packets", matching on two strings: the number `8550` and the address `169.254.0.1`. Neither is a network endpoint. The port is never listened on. The address is never connected to. They are just byte patterns that happen to appear in traffic the daemon was already handling — so an operator who can get those bytes in front of the firewall, by any means, can signal the implant without ever communicating with it.

When a hook extracts a tag, it hands it to the other daemon by opening `/proc/<counterpart_pid>/mem` and writing into it directly. Two system daemons writing into each other's memory. Later, when `iked` handles a VPN session carrying a matching tag, its hook "takes an alternate return branch (ADRP return path), bypassing default FortiOS security validations."

That is the payoff: a VPN session that authenticates because the logging daemon told the VPN daemon to let it.

So what is left to hunt? Memory, and only memory.

The strongest test is the one Unit 42 hands over: look in the maps of those two daemons for an anonymous 16,384-byte region with `rwxp` permissions. Writable-and-executable anonymous memory is ordinary in a JIT runtime — the JVM, V8, .NET all do it. It is not ordinary in `miglogd`. These are C daemons that compile nothing at runtime. There is no benign reason for either to hold a writable executable mapping, and that is why naming the two processes matters more than the size does.

Unit 42 also publishes three offsets patched with `0xAA0003E0` (`MOV X0, X0` — a NOP) to suppress tamper detection. Use them, but know what they are: offsets into the specific firmware build they analysed. A different build puts those functions somewhere else and the literal offsets will not match. The durable form of that test is hashing the daemon's text segment against the vendor binary for the build you are actually running.

One artefact survives outside memory, and it is worth checking first because it is cheap: the injection attempts crashed things before they worked. Unit 42 recommends querying `diagnose debug crashlog read` for Signal 11 faults in `miglogd`, `iked` or `syslogd`. The operators knew — they ran `diagnose debug crashlog clear` to wipe exactly those records.

Which leads to the most important operational point in this hunt, and it is not a query.

Everything here is volatile. A reboot destroys it. A failover destroys it. A configuration reset destroys it. Restarting the daemons destroys it. All of those are also the natural first instinct when a firewall is behaving oddly. Capture memory before you touch anything.

## Why

- **It defeats the three detections people actually have.** No file to hash, no listening port to scan, no outbound connection to log — and on an appliance there is no endpoint agent either, so the usual stack has nothing to say.
- **The daemons are chosen for what they can see and decide.** Logging and IKE between them cover traffic observation and VPN session authorisation, which is why the implant needs no network presence of its own.
- **Its signalling uses traffic the daemon already handled.** Matching `8550` and `169.254.0.1` as strings rather than endpoints means there is no connection, no session and no flow record attributable to the implant.
- **Writable-and-executable memory in a C daemon has no benign cause.** `miglogd` and `iked` JIT nothing, so the rwxp mapping is specific in a way it would never be on a workstation or a JVM host.
- **Cross-process `/proc/mem` writes between two daemons are indefensible as normal.** Even on a host with legitimate debugging, two production daemons writing into each other is not a pattern with a benign twin.
- **The published offsets are evidence, not a signature.** They pin the finding for one firmware build; text-segment integrity against the vendor binary is the version that generalises, and saying so prevents a false sense of coverage.
- **The crash log is the one non-volatile trace, and the actor cleared it.** Segmentation faults from failed injection attempts are recoverable if logs ship off the box, which is the argument for off-appliance retention.
- **Standard incident response destroys the evidence.** Reboot, failover and factory reset are the instinctive responses to a misbehaving firewall and each one erases the entire artefact set — so preservation guidance belongs in the hunt, not after it.
- **The access that delivered it came from stolen trust material.** Unit 42 notes that material "remains valid until it is rotated", so patching the appliance does not evict this implant or prevent its redelivery.
