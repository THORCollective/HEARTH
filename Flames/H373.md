false_positive_notes: |
  Everything in this chain is a legitimate capability being used by someone who should not have it, which means the hunt turns almost entirely on identity and provenance rather than on action. Pipelines are created and modified constantly in any healthy engineering organisation; pipelines read secrets by design, because that is how deployments authenticate; pipelines deploy agents into clusters, because that is what a deployment is. None of these is anomalous on its own and a hunt that flags them will be switched off in a week. The real discriminators - *who* authored the change, since a pipeline created or edited by an identity with no prior authoring history in that project is the signal, and a developer editing their own team's pipeline is not; *breadth*, because a single pipeline authorised against fifty-plus resources is unusual even in large estates and worth enumerating regardless of this campaign; *purpose mismatch*, since a pipeline whose jobs collect credentials but produce no build artifact, run no tests and deploy nothing is doing something other than building; and *timing*, because a pipeline change minutes after a password reset or an authentication-method registration on the same identity is a different event from the same change on a Tuesday afternoon. Known benign cases that will match - platform and SRE teams legitimately build credential-distribution and cluster-bootstrap pipelines, and those genuinely do read many kubeconfigs; migration and disaster-recovery tooling enumerates service connections wholesale; and security tooling itself (secret scanners, posture assessment, compliance agents) reads broadly by design. Allowlist these by pipeline identity and definition ID, not by behaviour, and review the allowlist when its owners change. For the commit leg, note that test fixtures and documentation examples legitimately contain credential-shaped strings, so prefer validated secret-scanning results over regex matches, and treat a *real* cluster's kubeconfig in a repo as an incident irrespective of who put it there.

"The intrusion began with Storm-3068 gaining access to a user account through a self-service password reset process and then taking full control of the identity by registering its own authentication methods." The actor then "shifted its focus to Azure DevOps using legitimate administrative tools and automated scripts to enumerate repositories, projects, pipelines, and deployment environments." Next - "the threat actor created a malicious pipeline designed to harvest Kubernetes credentials at scale. The pipeline deployed a kube agent and executed multiple jobs intended to collect kubeconfig files containing cluster connection details and authentication information. Leveraging the permissions of the compromised account, the threat actor deployed the pipeline that was authorized to access more than 50 resources and authenticated to services." Also - "the threat actor modified pipeline scripts to install the Atera remote management agent and download the Chisel tunneling utility. These tools were deployed in an attempt to provide the threat actor with alternative mechanisms for remote access and to expose the Kubernetes API server. Chisel commands were executed to establish a reverse tunnel to an external IP address to enable potential remote interaction with the Kubernetes clusters." And - "using Azure DevOps audit logs and Git version history, investigators reconstructed the next stage of the intrusion. The threat actor added seven stolen kubeconfig files to a repository, providing the credentials needed to access targeted Kubernetes clusters." Microsoft's framing of why DevOps was the target - "Azure DevOps proved to be a high-value target because it sat at the intersection of identity, software development, and cloud operations."
  Why T1072 Software Deployment Tools is the anchor. Microsoft is explicit that there was no malware and no software exploit - "by leveraging legitimate identity and cloud services rather than malware or software exploits, the threat actor established persistent access." The pipeline *is* the tooling. A build system is a deployment mechanism that holds production credentials and is pre-authorised to reach production, which is precisely the profile T1072 describes - and it means the lateral movement produced no process execution on any endpoint a defender was watching. The credential objective maps to T1552.001, since a kubeconfig is a credential in a file, and the fallback access maps to T1219 for Atera.
  Core filter, the pipeline-authoring leg. From the Azure DevOps audit log, list pipeline create and update events joined to the authoring identity's prior authoring history in that project. Triage fields - actor identity and its authentication method history, the pipeline definition diff, the count of authorised resources and service connections, whether the run produced artifacts, and the time delta to the identity's last credential or MFA-method change. A pipeline created by an identity with zero prior pipeline commits in that project is the top of the list.
  Core filter, the breadth leg. Enumerate every pipeline by the number of resources and service connections it is authorised against, and rank descending. This is worth doing once as a standing inventory regardless of any specific intrusion - Microsoft's own recommendation is "controlling pipeline permissions and limiting who can create, modify, or execute build and deployment pipelines," and you cannot control what you have not counted. A pipeline authorised against fifty-plus resources is a single point of compromise for all fifty.
  Core filter, the purpose-mismatch leg. A build pipeline that reads cluster credentials or secrets but emits no build artifact, runs no test task and performs no deployment is doing collection, not building. Query pipeline run logs for jobs whose tasks include credential or kubeconfig retrieval, cluster authentication, or `az`/`kubectl` invocations, and whose run produced no published artifact. This is the most generalisable form of the hunt and survives the operator renaming everything.
  Core filter, the commit leg. Search Git version history across all repositories for files whose content matches a `kubeconfig` structure - `apiVersion: v1`, a `clusters:` block with `server:` and `certificate-authority-data:`, and a `users:` block with `client-certificate-data:` or a token. Microsoft notes the investigators used Git version history to reconstruct this stage, which is a reminder that the commit is durable even if the files were later deleted - search history, not the working tree. Seven kubeconfigs appearing in one commit, or across a short series by one author, is the specific shape.
  Core filter, the fallback-access leg. Atera agent installation and Chisel download, both originating from pipeline script modifications rather than from an endpoint. On build agents and runners, hunt for the Atera installer and the `AteraAgent` service, for Chisel binaries, and for outbound connections from a runner to an external IP on a long-lived session - a reverse tunnel from a build agent has no legitimate form. HEARTH covers RMM abuse broadly; what is new here is the *delivery path*, where the installer arrives as a pipeline task rather than as a phished download.
  Identity-side pivot, and why it is the real root cause. The whole intrusion starts with a self-service password reset followed by the actor "registering its own authentication methods." That sequence - SSPR completion, then new MFA method registration, then unusual administrative enumeration - is the earliest detectable point and the cheapest to query, and it is the same pattern HEARTH hunts in [[H329]] for a different initial vector. Microsoft's mitigation is "strengthening protection for privileged accounts by limiting exposure to self-service password reset workflows and requiring phishing-resistant multifactor authentication." The baseline that makes the pipeline side of this tractable is [[B059]].

# H373

There was no malware in this intrusion. There was no exploit either. Microsoft says so directly: the actor leveraged "legitimate identity and cloud services rather than malware or software exploits."

What Storm-3068 used instead was a build pipeline.

The chain starts somewhere unglamorous — a self-service password reset on a user account, followed by the actor registering its own authentication methods to take durable control of the identity. From there it moved to Azure DevOps and enumerated repositories, projects, pipelines and deployment environments using, in Microsoft's words, "legitimate administrative tools and automated scripts."

Then it created a pipeline. Not a payload, a pipeline. The pipeline deployed a kube agent and ran multiple jobs whose purpose was to collect `kubeconfig` files at scale. Because it ran with the compromised account's permissions, it was authorised to reach more than fifty resources and authenticate to services across them. Seven stolen kubeconfigs were then committed into a repository, and pipeline scripts were modified to install the Atera RMM agent and pull down Chisel, which established a reverse tunnel to expose the Kubernetes API server.

Read that as an attack pattern rather than an incident and it is unsettling for a specific reason: every single step is the build system doing exactly what build systems do. Pipelines are created. Pipelines read secrets — that is how deployments authenticate. Pipelines deploy agents into clusters. Pipelines are pre-authorised to reach production, which is the entire reason they exist. The lateral movement generated no process execution on any endpoint anybody was monitoring, because the lateral movement happened inside the CI system.

Which means the hunt cannot be about actions. It has to be about identity and purpose.

Identity: who authored this pipeline change, and have they ever authored one in this project before? Purpose: did this pipeline produce a build artifact, run a test, deploy anything — or did it only read credentials? A pipeline that collects secrets and emits nothing is not a build.

And one standing inventory question that Microsoft's own recommendation implies: how many resources is each pipeline authorised against? A pipeline with fifty is a single point of compromise for fifty. You cannot limit what you have not counted.

## Why

- **Microsoft's framing is the thesis.** Azure DevOps "sat at the intersection of identity, software development, and cloud operations" — so one account compromise reached code, pipelines, service connections and production clusters without touching a single endpoint.
- **No malware means no endpoint detection, by construction.** Every detection tuned to process execution, file writes and host telemetry was looking in the wrong place. The audit log for the CI system is the primary telemetry here, not a secondary source.
- **Purpose mismatch is the one filter that generalises.** Pipeline creation, secret reads and cluster deployments are all normal. A run that reads credentials and publishes no artifact, runs no test and deploys nothing is doing collection, and renaming things does not change that shape.
- **Authoring history is a sharp, cheap identity filter.** A pipeline created or edited by an identity with no prior authoring record in that project is a short list in any real organisation, and it is where this intrusion would have surfaced first.
- **Resource-authorisation breadth is worth counting whether or not you are compromised.** Fifty resources behind one pipeline is a blast radius, and ranking pipelines by that number is a one-time query that produces a permanent hardening backlog.
- **Git history is durable evidence the operator cannot retract.** Microsoft's investigators reconstructed the credential-theft stage from version history. Deleted files remain in history, so the commit leg should search history rather than the working tree.
- **A reverse tunnel from a build agent has no benign form.** Chisel establishing an outbound long-lived session from a runner to an external IP is unambiguous, and Atera arriving as a pipeline task rather than a phished installer is a delivery path most RMM detections do not watch.
- **The root cause is upstream of all of it.** SSPR completion followed by the actor registering its own authentication methods is the earliest and cheapest signal in the whole chain — the same sequence [[H329]] hunts from a different starting point.
