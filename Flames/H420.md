title: "A shell spawned by the Zimbra Swatchdog Perl process running anything other than snmptrap — command injection reached through a malformed recipient address in the mail log"
hypothesis: >-
  Zimbra's Swatchdog monitoring daemon tails the mail log and, when it sees a service status change, builds an SNMP notification by interpolating the service name into a backticked Perl string. The service name comes from the log line, and Postfix will write an attacker-controlled malformed recipient address into that same log, so a single SMTP transaction with an unclosed angle bracket can place shell metacharacters where Perl will execute them. Code then runs as the zimbra account, which can read every mailbox on the server and send as any local identity. The exploitation is unauthenticated and leaves nothing on disk. What it does leave is a process lineage that cannot occur legitimately: the Swatchdog Perl process spawns a shell to invoke snmptrap, and under normal operation snmptrap is the only thing that shell ever runs. Any other child of that shell is successful exploitation, and the triggering log line is still sitting in the mail log for retrospective hunting.

false_positive_notes: |
  The first stage of the sequence is legitimate activity and will match on any healthy Zimbra host with SNMP notifications enabled. A shell invoked by the Swatchdog Perl process with snmptrap in its arguments is exactly what the monitoring path is supposed to do, so that stage must never alert on its own. The finding is strictly the second stage: a child of that shell which is not snmptrap.
  Local customisation of swatchrc can introduce legitimate extra children. Some operators extend the Swatchdog configuration with their own notification hooks. Check whether /opt/zimbra/conf/swatchrc.in has been modified locally before treating an unexpected child as exploitation, and allowlist the specific command if it is yours.
  Process names for the shell vary by distribution. The shell may appear as sh, bash or dash depending on what /bin/sh links to, so match a set rather than a single name.
  A failed exploitation attempt still writes the log line. Attempts whose payload does not match the Swatchdog pattern leave the malformed-address entry in the mail log without producing any process activity, so log hits substantially outnumber process hits. Treat the log hunt as reconnaissance and attempt evidence, and the process hunt as compromise evidence.
  A negative test does not mean a patched server. Elastic found that "several of the public proofs of concept (PoCs) we tested write a payload that Swatchdog never matches, so a failed test looks like a patched server". Confirm patch state from the Zimbra version, not from a PoC that did not fire.
  Scanning for this will generate large volumes of malformed-address log entries once the technique is public. Rate-limit or aggregate the log hunt by source address rather than reviewing individual lines.
notes: |
  Published detection rule - Elastic ships this as a SIEM rule, Zimbra Swatchdog SNMP Command Injection Execution. The sequence requires both stages and is the authoritative expression of the hunt:
  ```eql
  sequence by host.id with maxspan=30s
    [process where
      host.os.type == "linux" and
      event.type == "start" and
      event.action in ("exec", "exec_event", "start") and
      process.name in ("sh", "bash", "dash", "ash", "zsh", "ksh") and
      process.parent.name like~ "perl*" and
      process.parent.command_line like~ "*.swatchdog_script*" and
      process.command_line like~ "*snmptrap*" and
      process.command_line like~ "*zmservicename*" and
      process.command_line like~ "*zmservicestatus*"
    ] by process.entity_id
    [process where
      host.os.type == "linux" and
      event.type == "start" and
      event.action in ("exec", "exec_event", "start") and
      process.name != "snmptrap"
    ] by process.parent.entity_id
  ```
  The logic rests on a single fact worth restating when tuning: "Since the only process that should run under legitimate circumstances is snmptrap, this is a very strong indicator of successful exploitation."
  Defender XDR equivalent for onboarded Linux servers, 30-day retention:
  ```kql
  let shells = dynamic(["sh","bash","dash","ash","zsh","ksh"]);
  let stage1 = DeviceProcessEvents
    | where Timestamp > ago(30d)
    | where FileName in~ (shells)
    | where InitiatingProcessFileName startswith "perl"
    | where InitiatingProcessCommandLine has ".swatchdog_script"
    | where ProcessCommandLine has "snmptrap"
    | project ShellTime = Timestamp, DeviceId, DeviceName, ShellPid = ProcessId, ShellCmd = ProcessCommandLine;
  let stage2 = DeviceProcessEvents
    | where Timestamp > ago(30d)
    | where FileName !~ "snmptrap"
    | project ChildTime = Timestamp, DeviceId, ParentPid = InitiatingProcessId,
              ChildName = FileName, ChildCmd = ProcessCommandLine, ChildAccount = AccountName;
  stage1
  | join kind=inner (stage2) on $left.DeviceId == $right.DeviceId, $left.ShellPid == $right.ParentPid
  | where ChildTime between (ShellTime .. ShellTime + 30s)
  | project ShellTime, ChildTime, DeviceName, ShellCmd, ChildName, ChildCmd, ChildAccount
  | order by ChildTime desc
  ```
  Both `let` bindings are used, and the 30-second window on the join matters: process IDs are reused on a busy mail server, so a join on PID alone over a long lookback will correlate unrelated processes.
  Retrospective log hunt - This is the cheaper half and it reaches back further than most process telemetry. Postfix records a malformed recipient address verbatim, in the form `warning: Illegal address syntax from mail.lab.test[10.0.2.15] in RCPT command:<address@host.name`, and a payload must additionally match the Swatchdog pattern `Service status change: <host> <service> changed from stopped to running`. So the signature of an attempt is a single log line containing both the illegal-address warning and the service-status phrasing:
  ```bash
  grep -E 'Illegal address syntax' /var/log/zimbra.log | grep -F 'Service status change:'
  ```
  Extract the source address from each hit and aggregate by source; a single source producing many variants is scanning, and a source producing one well-formed payload followed by outbound activity from the host is the one to investigate. Elastic's own test payload used command substitution of the form `$(touch /tmp/manual_test.txt)` and a `curl` callback to an out-of-band listener, so expect `$(` or backticks inside the address field.
  Post-exploitation pivot - Code runs as the `zimbra` service account. That account "reads every mailbox on the server and sends as any local identity", so scope beyond the host: look for mailbox access patterns inconsistent with user activity, messages sent from local identities without a corresponding authenticated session, and any new credential or key material written under the Zimbra tree. Also check outbound connections from the mail server around the shell execution, since an out-of-band callback is the usual confirmation step and leaves no file behind.
  Patch state - The complete fix is Zimbra 10.1.20 or later. Inventory versions first so the hunt can be scoped to hosts that were actually exploitable during the retention window, including hosts patched recently, which still need the retrospective log hunt for pre-patch attempts.
  Adjacent Zimbra coverage - [[H352]] covers a mail service account taking ownership of a PAM configuration by symlink to grant itself passwordless sudo, and [[H353]] covers a systemd unit named like a Zimbra logging component installed outside the application tree. Both are plausible follow-on persistence from this exact foothold, so run them against any host that produces a hit here. [[M029]] scores mail-data egress volume from the webmail tier.

# H420

Elastic Security Labs published an analysis in October 2026 of CVE-2026-73570, reproducing the full exploitation chain while building detections for it. The vulnerability is an unauthenticated command injection in Zimbra, and the report's summary of the trigger is hard to improve on: "CVE-2026-73570 is an unauthenticated command injection vulnerability in Zimbra, and one malformed recipient address is enough to trigger it."

The chain runs through a monitoring component rather than through the mail path. Postfix writes an unparseable recipient address into `/var/log/zimbra.log` as a warning, which is ordinary behaviour. The Swatchdog daemon tails that log looking for service status changes, and when it finds one it builds an SNMP notification in Perl. The notification is assembled by interpolating the service name into a backticked string — so the service name, which came from the log line, is handed to a shell. As the report puts it: "From there, the Swatchdog monitoring daemon matches it against a service status pattern and passes it to /bin/sh inside a backticked Perl string. The result is remote code execution as the zimbra user."

The consequence is larger than one host. The `zimbra` account "reads every mailbox on the server and sends as any local identity, so compromising the mail server compromises the identities it serves" — which makes this an identity compromise as much as a server compromise, and a staging point for onward phishing that originates from genuinely legitimate addresses.

The detection is unusually clean because the legitimate path is so narrow. Swatchdog's Perl process spawns a shell for exactly one purpose: to run `snmptrap`. That means a two-stage sequence — the expected shell, then any child of it that is not `snmptrap` — separates exploitation from normal monitoring without needing to parse the payload. Elastic ships this as a SIEM rule, and the same shape translates to any Linux process telemetry with parent-child fields.

One operational warning from the report deserves repeating in any hunt that follows it. Many public PoCs do not work: they "write a payload that Swatchdog never matches, so a failed test looks like a patched server". Patch state must be confirmed from the Zimbra version, not inferred from a test that did not fire.

## Why

- Unauthenticated RCE on a mail server is an identity compromise. The service account can read every mailbox and send as any local user, so this foothold produces internally-originated phishing and business email compromise that no sender-reputation control will catch.
- The legitimate process lineage is singular, which is rare and valuable. Because `snmptrap` is the only thing that shell should ever execute, the detection needs no payload parsing, no string heuristics and no tuning beyond local customisation of the Swatchdog configuration.
- The attempt evidence persists in the mail log independent of endpoint telemetry. A grep for the illegal-address warning combined with the service-status phrasing finds pre-patch attempts reaching back as far as log retention allows, which is usually much further than process telemetry.
- Exploitation leaves nothing on disk, so file and hash-based approaches have nothing to match. Process lineage and the log line are the two places this is visible, and both are cheap to collect on a mail server.
- Patch verification is actively misleading here. Teams that tested with a public PoC and saw nothing happen may believe they are patched when they are not, which makes the retrospective log hunt worth running even on hosts that have been "confirmed" safe.
