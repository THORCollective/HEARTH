false_positive_notes: |
  The Startup folder is not quiet. Installers legitimately place shortcuts there, users drop their own
  shortcuts, and software updaters rewrite entries. What makes this hunt narrow is not the directory but
  the writer.
  An archive utility should never be the process that creates a file in Startup. A user who extracts an
  archive and then manually copies a shortcut into Startup produces two separate events, and the file
  creation is attributed to explorer.exe, not to WinRAR. A path-traversal write produces one event, with
  the archive utility itself as the creating process. That distinction is the hunt, and it survives
  without any knowledge of the payload.
  A small number of legitimate self-extracting archives and installer packages are built on archive
  engines and may write to Startup during an install. These are worth enumerating once, because they
  tend to be a short and stable list per environment, and they are usually signed. Check the signature
  and the publisher of the writing binary before dismissing a hit.
  Scope both Startup locations. The per-user path under the profile and the all-users path under
  ProgramData are both valid targets and the all-users path requires elevation, which is itself worth
  knowing.
  Do not filter on file extension. The report says the payload placed was PickleShell, but a traversal
  write can place a script, a shortcut or an executable, and restricting to `.exe` would narrow the hunt
  for no benefit.
  WinRAR version state is a useful scoping signal but a poor filter. Patched hosts are not exposed to
  this defect, but the same hunt catches equivalent traversal bugs in other archive utilities, so do not
  restrict the query to a vulnerable version range.

# H394

WinRAR wrote a file to the Startup folder, and nobody asked it to.

That sentence is the entire detection. Talos found a RAR archive in April 2026 that exploited CVE-2025-8088 to place PickleShell — one of UAT-6275's lightweight reverse shells — directly into the Windows Startup folder during extraction. The payload ran at the next sign-in. No macro prompt, no script, no Run key, no scheduled task. Open the archive, and persistence is already installed.

For the defender this turns out to be a gift, because the behaviour has almost nowhere to hide.

The Startup folder is busy. Installers write shortcuts there, users drop their own, updaters rewrite entries. Querying the directory alone produces noise. But querying *who wrote* into it produces a very short list, and an archive utility should never be on it.

Consider what the benign version looks like. A user extracts an archive to Downloads, then decides to copy a shortcut into Startup. That is two events, and the file creation in Startup is attributed to `explorer.exe`. The traversal version is one event, attributed to `winrar.exe`. Same destination, completely different parent, and the parent is the field you filter on.

This is also why the hunt outlives the campaign. There is no command line to obfuscate, no encoded script, no C2 domain to rotate. UAT-6275 could change the payload, the archive name, the lure document and the infrastructure, and the event shape would be identical. Any traversal defect in any archive utility writing to any persistence location produces the same two-field signature.

Worth being honest about one thing: Talos does not explain how the defect achieves the write. The post says the archive exploited CVE-2025-8088 to place the payload in Startup and stops there — the full technical analysis sits in the joint Virus Bulletin white paper. The specific traversal primitive and archive structure are not stated. That does not weaken the hunt, because the detection is built on the file-creation event and its parent process, and neither depends on knowing the mechanism.

A note on scoping. Patch state tells you who is exposed to *this* CVE, but do not filter the query by WinRAR version — the same query catches equivalent bugs in 7-Zip, WinZip and the rest, and those are the ones you do not have a CVE number for yet. For the same reason, leave the file extension unconstrained. A traversal write can land a script, a shortcut or an executable.

Chain D was the first time Talos saw this group use an exploit for delivery at all. Their earlier chains leaned on macro documents, PS2EXE downloaders with scheduled tasks, and LNK-to-PowerShell fetches from GitHub — that last one is hunted in [[H395]].

## Why

- **The parent process is a near-perfect discriminator.** Archive utilities have no legitimate reason to create files in Startup, so one field separates the attack from the directory's ordinary traffic.
- **Benign and malicious produce different event counts and different parents.** Manual extraction-then-copy is two events owned by explorer.exe; a traversal write is one event owned by the archive utility.
- **Persistence is installed without any persistence-looking behaviour.** No Run key, no scheduled task, no service creation, no script execution — the conventional persistence hunts never fire.
- **The signature survives every indicator rotation.** Payload, archive name, lure and infrastructure can all change without altering the two fields the hunt depends on.
- **It generalises past the CVE.** The same query catches traversal defects in other archive utilities, which is why version-based filtering would be a mistake.
- **Execution is confirmable.** A Startup-resident payload appears at the next interactive sign-in as a child of explorer.exe, so the write and the run can be correlated in a time-bounded join.
- **It marks a capability shift for this actor.** Talos notes this was the first vulnerability exploit observed in UAT-6275's delivery, after a year of macro documents and script downloaders.
- **Patch state scopes the exposure but does not close the hunt.** Updating WinRAR removes this specific defect; the detection remains the cheapest way to see the next one.
