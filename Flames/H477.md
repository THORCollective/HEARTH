false_positive_notes: |
  The template directory is a product directory, so additions are rare but not unheard of, and the exploitation markers are specific enough that the main risk is absence of telemetry rather than noise.
  - Vendor hotfixes, upgrades and customisation legitimately add and modify files in the portal template directory. Branded login pages, custom language files and support-supplied patches all land here. Reconcile against the vendor package manifest and against change records; a file that no package owns and no change ticket mentions is the finding, and the two-letter prefix with random characters is not a naming convention any vendor uses.
  - Segmentation faults in web workers occur for mundane reasons - memory pressure, a bad module, a genuine product defect under unusual input. A handful across a week is background. Hundreds inside one window, correlated with portal requests from one address, is the pattern; treat the count and the correlation as the signal rather than the existence of a fault.
  - Security scanners and penetration tests generate portal requests that look like exploitation attempts and can crash workers. Check the source address against authorised testing ranges and the window against scheduled assessments before escalating, and remember that an authorised test will not have written a template file.
  - PHP session files accumulate normally. The marker string is what makes them interesting; a session file is only a finding when it contains content that belongs to an exploitation technique rather than to the portal.
  - Appliances are frequently the least instrumented hosts on the network. If the portal temporary directory has already rotated, the Apache log has already rolled, and no filesystem baseline exists, this hunt returns nothing and that result means the telemetry is missing, not that the appliance is clean. Establishing which of these sources exist is the first pass, and the answer is worth reporting on its own.

The companion hunt for the implant deployed in this same intrusion is [[H478]]. Nothing in the corpus covers webshells filed in an appliance portal's own template directory.
  Core filter 1, the template directory - The highest-value check and the one that needs no exploit knowledge. CPR records the write verbatim as `printf <base64 Webshell> | base64 -d > <templates>/zz<random>.tpl`, and reports that "the attacker used multiple .tpl files with names matching the pattern zz*.tpl". List the portal template directory and diff it against the vendor manifest for the running version. A `.tpl` file no package owns is the finding; a `.tpl` file whose name starts with `zz` followed by random characters is the reported case. CPR also notes that each file "initially received a small command-execution shell, which was then replaced with a more capable version", so a modification timestamp later than the creation timestamp on the same file is corroboration and a reason to look for the earlier version in backups.
  Core filter 2, the second landing spot - CPR reports that the expanded shell "requires the hardcoded key zz2026 and supports operating-system commands, PHP code execution, and file uploads", that "uploaded files are saved to the fixed path /tmp/.up.tpl", and that "the attackers subsequently issued commands to copy that file into the portal's directory as challenge_render.tpl". Those are two fixed names to check directly: a file at `/tmp/.up.tpl` on a gateway, and a `challenge_render.tpl` in the portal directory whose content is not the vendor's. Because the shell accepts "both plain-text and Base64-encoded, XOR-obfuscated commands", portal request bodies will not reliably carry readable commands, which is why the filesystem checks lead and the request-log checks support.
  Core filter 3, the exploitation window - CPR reports that "PHP session artifacts were created under /opt/CPcvpn-R81.20/tmp/, including session files containing the upload_progress_pwn marker associated with the exploitation activity", and that "during the same window, the portal's Apache/PHP workers experienced hundreds of segmentation faults, providing additional evidence of repeated exploitation attempts against the service." Grep the portal temporary directory for the marker string, and count worker segmentation faults per hour across the appliance's logs looking for a burst rather than a trickle. The fault burst is the most likely surviving artefact on an appliance where session files have rotated, because it lands in system logs rather than in a temporary directory, and it is worth hunting retrospectively across every gateway in the estate regardless of whether a compromise is suspected on any one of them.
  Core filter 4, what the escalation touched - The DynamicCLI IPC interface is the privilege-escalation surface. Any audit of privileged command execution on the appliance for the same window, and any evidence of the portal service account running commands it has no reason to run, places the chain between filter 3 and filter 1. CPR does not publish the request shape for CVE-2026-123039, so this filter is scoped to what the appliance records about privileged execution rather than to a signature for the exploit itself.
  Sample on-appliance triage, to be run from expert mode and treated as read-only, with the template directory resolved rather than assumed:
  ```bash
  set -u
  # resolve the portal temp and template directories for the running version
  for d in /opt/CPcvpn-*/tmp; do
    echo "== session dir: $d"
    grep -rl 'upload_progress_pwn' "$d" 2>/dev/null
  done
  echo "== fixed upload path"
  ls -la /tmp/.up.tpl 2>/dev/null || echo "not present"
  echo "== template files, newest last"
  find /opt/CPcvpn-*/ -name '*.tpl' -printf '%T@ %TY-%Tm-%Td %TH:%TM %p\n' 2>/dev/null | sort -n | tail -40
  echo "== zz-prefixed templates and challenge_render"
  find /opt/CPcvpn-*/ \( -name 'zz*.tpl' -o -name 'challenge_render.tpl' \) -exec ls -la {} \; 2>/dev/null
  echo "== worker faults per day"
  grep -ihE 'segfault|segmentation fault' /var/log/messages* 2>/dev/null | awk '{print $1" "$2}' | uniq -c | sort -rn | head -20
  ```
  The last command is the one to run first across the whole gateway estate: it needs no knowledge of the exploit, reads a log that is retained longer than the session directory, and a day with hundreds of faults on a portal that normally has none is a reason to look at everything above it.
  Infrastructure and hashes from the report, for retrospective scoping - CPR records scanning and exploitation from 130.94.19[.]204 and 130.94.19[.]168, hosted on LightNode VPS infrastructure, with scanning concentrated between 00:00 and 09:00 UTC. The `.tpl` webshell has SHA-256 edb3e92eb7bda7413a09edcc4b1ba3cbed4bcdf42808a8abce63b6e4c3fda2b3. Use the addresses to bound a look-back over portal access logs; the filesystem checks are the detection, because the addresses were already two waves old when the report published.
  What came next in the reported intrusion, for scoping - CPR reports the attackers then launched the TSGA backdoor, deployed the gogo scanner on the gateway "to discover internal assets and services across the network", moved laterally to a VMware ESXi host over SSH "authenticating with the vpxuser service account", staged the `destroy_v6` wiper to `/tmp` on that host and executed it, leaving `DREAM_ANNEXATION.txt` notes. A hit on this hunt should immediately be followed by the gateway's egress record and by the authentication logs of any virtualization management account the gateway could reach.
  Attribution caution, stated as the report states it - TSGA and TSProxy belong to the PhiliKit family, which ESET associated with China-nexus UNC5221, but CPR writes that "the evidence does not allow us to assess with high confidence the true nature of this operation" and lists the possibilities, including that the identified actor was an initial access broker, a false-flag operation, or that "the destructive activity served as a smoke screen." Treat the tooling lineage as a lead and not as an actor assignment.

# H477

The webshells were called `zz` plus some random characters, with a `.tpl` extension, and they were sitting in the directory the VPN portal uses to build its login pages.

That is a good place to put them. An appliance does not run an endpoint agent. Its filesystem is not in anyone's EDR console. And a `.tpl` file in a template directory looks exactly like what belongs there — unless someone compares the directory against the vendor's package manifest, which is not a thing most organizations have ever done to a gateway.

Check Point Research reconstructed the whole chain on unpatched Security Gateways from late October 2026. Exploitation of the Mobile Access portal, then a local privilege escalation through the appliance's own management IPC interface to get from the portal service account to root, then `printf` of a base64 blob piped through `base64 -d` straight into the template directory. The first shell was small. It was then replaced with a bigger one that wants a hardcoded key, runs OS commands and PHP, and accepts uploads — which it writes to one fixed path, `/tmp/.up.tpl`, before the operators copy it into the portal directory as `challenge_render.tpl`.

But the loudest artefact is not the webshell. It is the noise the exploitation made getting there.

The portal's PHP workers segfaulted hundreds of times in the same window, because the exploit was tried over and over and most attempts crashed the worker. And the PHP session files left behind in the portal's temp directory contain a marker string — `upload_progress_pwn` — that is not a thing the product writes.

A gateway that normally segfaults never, segfaulting hundreds of times in an afternoon, is a question worth asking across every appliance you own. You do not need to know the CVE to ask it.

## Why

- **The persistence location is invisible to the tooling most organizations actually run.** Appliances do not take agents, so the template directory is outside endpoint telemetry by construction. The only thing that finds a planted `.tpl` is a deliberate comparison against the vendor package, and that comparison costs almost nothing once someone decides to make it.
- **The segfault burst is durable where the other artefacts are not.** Session files in a temporary directory rotate away, and portal access logs roll. Worker crashes land in system logs with longer retention, which makes the fault count the one check that still works weeks after the fact — and the one that can be run estate-wide without any product-specific knowledge.
- **The marker string belongs to the exploit, not to the product.** A session file containing exploitation residue is unambiguous in a way that most web-server artefacts are not. It is a grep, it needs no baseline, and a hit is not something a misconfiguration produces.
- **Two fixed paths make the second half of the chain trivially checkable.** `/tmp/.up.tpl` and `challenge_render.tpl` are specific names the operators reused. Checking for them on every gateway is a one-line test with no false-positive population to speak of, and either one found means the capable shell, not the small one, was in use.
- **The gateway was a stepping stone, not the objective.** In the reported intrusion the operators scanned internally from the appliance and then pivoted over SSH to an ESXi host with a virtualization service account and ran a wiper. A compromised gateway is a credential and connectivity position in the middle of the network, so a hit here is the beginning of the investigation rather than the end of it.
