false_positive_notes: |
  The dominant benign cause of one ASIA key on multiple source IPs is legitimate multi-path egress: workloads behind several NAT gateways, dual-stack IPv4/IPv6 egress, or region failover can rotate among a small fixed set of addresses. Baseline each compute role's egress set (usually 1-3 NAT/EIP addresses per VPC) and require at least one observed address outside both that set and AWS-published ranges before flagging. Administrators occasionally copy instance credentials to a laptop for debugging; this fires the condition legitimately but is itself a policy violation worth a lightweight triage conversation, not suppression. Calls arriving via VPC endpoints or the AWS console session-forwarding path log AWS-internal source values and should be excluded up front. Scheduled security tooling (CSPM scanners, inventory jobs) can generate ListBuckets/List* bursts, but those run under their own roles and sessions — filtering the enumeration pivot to the specific replayed `role session name` removes them. After these controls the benign volume of the core condition approaches zero, which is what makes this viable as a recurring hunt rather than a one-off.
notes: |
  AWS CloudTrail management events - Core filter: temporary credentials (access key beginning `ASIA`) under an assumed compute role where one `access key ID` appears from two or more distinct `source IP address` values inside a single STS token lifetime (typically 1-6 hours), with at least one value outside AWS-owned ranges and outside the workload's known NAT/EIP egress set; exclude `AWS Internal` and VPC endpoint sources. For EC2 instance profiles the `role session name` is the instance ID (`i-...`), so an instance-ID session calling from a non-AWS address is a direct signal; ECS task role sessions carry the task ID and EKS pod identity sessions arrive via `AssumeRoleForPodIdentity`. Triage values: `access key ID`, `role session name`, `source IP address`, `user agent`, `event name`, `AWS region`.
  Enumeration pivot - Pivot: join all subsequent events on `access key ID` plus `role session name` and look for a first-contact burst from the anomalous address of `GetCallerIdentity`, `ListBuckets`, `ListSecrets`, `ListRoles`, `ListUsers`, or `GetAccountAuthorizationDetails` within minutes of the IP split. Correlation: a `user agent` change on the same session — workload SDK string on the in-account events versus a CLI/botocore-style string on the external events — paired with the IP change is a high-confidence combination.
  Impairment and persistence escalation - Strong red flags: the same replayed session issuing `StopLogging`, `DeleteTrail`, or `PutEventSelectors` paired with `CreateAccessKey`, `CreateUser`, or `CreateLoginProfile`; this is the stolen short-lived compute-role credential being converted into durable IAM persistence while blinding the trail, and should be treated as an active incident rather than a hunt lead.
  Gateway edge telemetry - Core filter: in LiteLLM proxy and fronting load balancer logs, internet-source requests to the `/mcp` route on instances not intended to be public, and any pass-through endpoint configuration whose target URL is the link-local metadata address `169.254.169.254`. Correlation: gateway exposure or configuration change shortly before the CloudTrail split-IP event ties initial access to the credential theft. Event ID: a GuardDuty `InstanceCredentialExfiltration.OutsideAWS` finding on the same role confirms the same chokepoint and should be joined into the timeline, but do not depend on it — it can miss replay routed through other cloud providers' AWS-adjacent ranges, which is why the CloudTrail-native split-IP condition is the primary filter.

# H296

Wiz research published 2026-09-09 chained multiple LiteLLM weaknesses into full cloud compromise: an MCP endpoint authentication bypass (CVE-2026-59822), post-auth root-level code execution via custom code guardrails (CVE-2026-59821), unauthenticated-as-admin default behavior, and an unfixed pass-through endpoint feature that forwards requests to arbitrary URLs — including the link-local instance metadata address — turning gateway access into workload IAM credential theft. Wiz found roughly 9.6% of 3,074 internet-facing LiteLLM instances accepted the default master key or required no authentication, observed CVE-2026-59822 exploitation in the wild via honeypots, and CISA added it to the Known Exploited Vulnerabilities catalog. Regardless of which entry vector is used, the payoff step is invariant: the stolen temporary credentials must be used from attacker infrastructure to be worth anything, and every such use lands in CloudTrail with a source IP that legitimate workload traffic can never produce. This hunt targets that chokepoint rather than any exploit-specific indicator, so it also catches credential theft from any other compromised compute workload, not just LiteLLM.

## Why

- The exposed population is real and current: Wiz found ~9.6% of 3,074 internet-facing LiteLLM instances accepted the default master key or no authentication, observed CVE-2026-59822 exploitation in the wild via honeypots, and CISA added it to KEV — LiteLLM is present in roughly a third of cloud environments per Wiz data.
- The hunt sits on an invariant chokepoint that survives IOC and exploit rotation: whichever bypass, payload, or gateway product the actor uses, stolen compute-role credentials only have value when replayed from attacker infrastructure, and a compute role calling AWS APIs from an address outside its host's egress is behaviorally impossible for legitimate workload traffic.
- The telemetry is on by default and the condition is deterministic: CloudTrail management events record every credential use with source IP, the `ASIA` prefix plus `role session name` give exact join keys, and split-IP within one token lifetime is a yes/no test — no anomaly scoring, no per-tenant model training.
- False positives are tightly controllable: each compute role's legitimate egress is a small static NAT/EIP set, AWS publishes its own ranges for exclusion, and the enumeration/impairment pivots are scoped to the exact replayed session, so residual benign matches are rare enough to triage individually.
