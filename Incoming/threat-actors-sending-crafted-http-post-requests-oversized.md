## Why
- This exploitation technique leaves virtually no application-layer footprint: worker processes stay alive, HTTP responses return 200, and application logs show no anomalies, making it exceptionally difficult to detect without targeted web-server error log analysis.
- The only reliable artifact is a specific error log pattern — "Allowed memory size of N bytes exhausted" paired with "in Unknown on line 0" — which indicates a fatal error occurring before any script execution, distinguishing it from benign in-script memory exhaustion events that security teams routinely dismiss as noise.
- Successful exploitation grants unauthenticated remote code execution in the web server's user context, providing adversaries a foothold to deploy web shells, harvest credentials from configuration files, and pivot laterally into internal networks — independent of the hosted application's code quality or patch status.
- This affects every PHP 7.x and 8.x release (a 7+ year exploitable window) wherever `memory_limit < 4 × post_max_size`, a configuration common in production environments tuned to accept large file uploads, making proactive hunting critical while patches are rolled out.
