false_positive_notes: >-
  The defining problem of this baseline is that there is no malicious shape to look for. Loading shared
  objects into daemons is the normal operation of a dynamic linker, and a mature host maps dozens per
  process — security agents, tracing and APM libraries, malloc replacements such as jemalloc and
  tcmalloc, NSS and SSSD modules, GSSAPI and Kerberos plugins, hardware crypto engines, database client
  libraries, and the compatibility shims that ship with commercial software. Several of those
  legitimately use `LD_PRELOAD` themselves, which is precisely why the technique works. The baseline is
  therefore not a filter to be tuned but an inventory to be completed, and the first run will surface
  more unknown-but-legitimate libraries than anything else. That inventory gap IS the initial finding and
  should be worked as one. Four specific traps. First, container images and language runtimes carry their
  own library sets, so profile per image and per service rather than per host, or a fleet comparison will
  be meaningless. Second, expect legitimate churn on a patch cadence — record the cadence during the
  window so that off-cadence change is distinguishable, because the mapping set changing is normal and
  the mapping set changing on a Tuesday night is not. Third, do not scope this to `LD_PRELOAD`: the
  source campaign used a service plugin API and a compiled-in backdoor, and would not have appeared in a
  preload-only inventory. Fourth, read the environment from `/proc/<pid>/environ` rather than from unit
  files, because the running state and the declared state diverge, and the divergence is the interesting
  case rather than a data-quality problem.

# B044

The interesting thing about the Ted backdoor is not what it did but where it lived. Rapid7 found it
compiled into HAProxy 2.8.12 and registered through the service's own filter API, loaded as a shared
library at process start and persisting across restarts through the master-worker environment. There was
no suspicious binary in `/usr/sbin` to find. The load-bearing artifact was not a file that looked wrong,
it was a mapping that nobody had a record of.

That is the general problem this baseline exists to solve, and it is worth separating from the specific
campaign. A Linux daemon is an execution environment with a documented extension mechanism, usually
several. The dynamic linker offers `LD_PRELOAD`, `/etc/ld.so.preload`, `LD_AUDIT` and the search path in
`ld.so.conf.d`. On top of that, HAProxy takes filters, Nginx and Apache take modules, PHP takes
extensions, PAM takes a whole stack, and SSSD and NSS take plugins. Every one of those is a legitimate
route for third-party code to execute inside a privileged, network-facing, long-running process — and
every one is therefore a persistence mechanism that leaves the daemon binary untouched.

This cannot be written as a detection rule, and it is worth being precise about why rather than
asserting it. The malicious event and the benign event are the same event: a shared object is mapped
into a process. There is no command line to inspect, because the load happens inside the linker. There
is no child process. There is no network connection at load time. The path may be entirely ordinary —
Rapid7's implant loaded through a supported API, from a plausible location. The only property that
distinguishes the malicious mapping from the four dozen legitimate ones on the same host is that nobody
expected it, and expectation is exactly what a baseline encodes and a rule cannot.

There is one part of this that is close to a free win and should not wait for the rest. `/etc/ld.so.preload`
does not exist on most production Linux hosts. It is not a file with a small legitimate population; it is
a file with, typically, none. Inventorying its presence across the estate is a single query, needs no
window, and is worth running before the behavioural collection starts. The same is true of world-writable
directories on the linker search path, which are a privilege-escalation primitive whether or not anything
has used one yet.

The scope trap is the one to guard hardest against, because it is the mistake this campaign punishes.
Most published guidance on this technique is about `LD_PRELOAD`, and a baseline built to that scope would
have produced a clean report on a host running the Ted backdoor. Preload variables are one route among
many. What the baseline has to record is the resulting mapping set — everything actually loaded into the
process, however it got there — together with each configured route that could add to it. Recording the
outcome as well as the mechanism is what makes the inventory robust against the next mechanism.

This baseline is the load-time companion to the disk-time hunts from the same intrusion. [[H289]] covers
the trojanized `sshd` that harvested credentials, [[H290]] the timestomping that made the replaced
binaries look original, and [[H291]] the selective log erasure that removed the traces. Those three hunt
files that changed on disk; this one covers the case where nothing did. [[H226]] touches the same
technique from the proxyware angle.

## Baseline data to collect

For every long-running network daemon on every Linux host — at minimum `sshd`, `haproxy`, `nginx`,
`httpd`/`apache2`, `crond`/`cronie`, `atd`, `polkitd`, `systemd-journald`, `rsyslogd`, `named`, `postfix`,
`dovecot`, and every database and application server — collect:

**Mapped objects (the outcome)**
- Every file-backed mapping from `/proc/<pid>/maps`: resolved path, inode, device, mapping permissions
- Whether the mapping is executable, and whether it is file-backed at all — an anonymous executable
  mapping is a separate finding from an unexpected path
- SHA-256 of each mapped shared object
- Owning package for each path, and whether that package verifies
- The subset of mapped objects whose path is not owned by any package

**Preload and search-path configuration (the mechanisms)**
- Presence, contents, size, mtime and ctime of `/etc/ld.so.preload`
- `LD_PRELOAD`, `LD_AUDIT` and `LD_LIBRARY_PATH` per running process, read from `/proc/<pid>/environ`
- `/etc/ld.so.conf` and every file under `/etc/ld.so.conf.d/`, plus resolved `ldconfig -p` output
- Ownership and mode of every directory on the resolved search path, flagging any that is
  group-writable, world-writable, or owned by a non-root account
- systemd `Environment=`, `EnvironmentFile=`, `ExecStartPre=` and wrapper scripts, including drop-ins
  under `/etc/systemd/system/<unit>.d/`

**Service-specific extension points**
- HAProxy: `filter` and Lua directives in `haproxy.cfg`, and the `HAPROXY_MWORKER_PP_READ` /
  `HAPROXY_MWORKER_PP_WRITE` environment on the master and worker processes
- Nginx `load_module`, Apache `LoadModule`, PHP `extension=`
- The PAM stack under `/etc/pam.d/` and the module directory contents
- NSS and SSSD plugin configuration

**Change and timing context**
- Daemon start time and restart history, so that a mapping-set change can be attributed to a restart
  (configuration) or to no restart at all (runtime injection)
- The observed patch and release cadence for each service, so off-cadence change is distinguishable

## Collection window

Thirty days, which spans at least one patch cycle for most estates and captures the routine library
churn that a shorter window would misread as anomalous. Extend to sixty or ninety days for services
patched quarterly. Profile per container image and per service role rather than per host — a
fleet-wide comparison across mixed images produces noise that no amount of tuning will resolve.

## Deliverable

A per-service mapping register, refreshed monthly, with one row per (service role or image, shared
object path) carrying: SHA-256, owning package and verification status, first-seen date, the hosts and
images where it appears, whether the path is on a writable directory, and an owner-confirmed disposition
of expected / expected-with-review / unexplained. Alongside it, a per-host configuration register
covering `/etc/ld.so.preload` presence, preload environment variables in effect, search-path additions,
writable search-path directories, and each service's declared plugin set. The mapping register is the
allowlist that a monthly diff runs against; the unexplained rows are a standing remediation backlog.

## Flag immediately — do not wait for the baseline to complete

- Any host where `/etc/ld.so.preload` **exists at all**, regardless of contents
- `LD_PRELOAD` or `LD_AUDIT` set in the running environment of any privileged daemon, or set anywhere in
  a systemd unit, drop-in or `EnvironmentFile` for a network-facing service
- Any shared object mapped into a privileged daemon that **no package owns**
- Any shared object mapped from a world-writable or user-writable path — `/tmp`, `/var/tmp`, `/dev/shm`,
  a service account home directory
- Any directory on the resolved linker search path that is group-writable, world-writable, or not
  owned by root
- An anonymous executable mapping in a daemon whose other mappings are all file-backed
- A daemon whose mapped-object set changed with **no corresponding process restart** — this is injection
  into a live process, not configuration
- A `filter`, `load_module`, `LoadModule` or `extension=` directive referencing a path outside the
  service's packaged module directory
- Any mapped shared object whose owning package fails checksum verification — cross-check against
  [[H290]], because the file's mtime may have been restored

## Why

- **The persistence lives in the loading, not in a file, so file-centric controls report clean.** Package
  verification, file-integrity monitoring and hash inventories all answer the question "did a binary
  change". In the source campaign nothing in `/usr/sbin` had changed — the backdoor was compiled into a
  legitimately-installed HAProxy and loaded through a supported API. The only place the implant was
  visible was in the process's mapping set, which nothing was recording.
- **There is no rule to write, because the malicious event is the normal event.** A shared object being
  mapped into a daemon has no command line, no child process, no network connection and often no unusual
  path. Every discriminating property is comparative: this object, in this service, was not here before.
  That is the definition of a baseline problem, and attempting it as a rule produces either an alert on
  every library load or an allowlist that was never actually built.
- **`/etc/ld.so.preload` is a near-binary signal and almost nobody inventories it.** The file is absent on
  the great majority of production hosts. Its population is not small, it is usually zero. A single
  fleet-wide query for its existence is cheap enough to run before any of the rest of this work and
  frequently finds either an implant or an undocumented agent that should have been known about.
- **Writable directories on the linker search path are a standing escalation primitive.** Independent of
  any current compromise, a group-writable directory in `ld.so.conf.d` resolution order means any user
  who can write there can execute code inside every process that subsequently loads a library. Enumerating
  search-path directory permissions is a by-product of this baseline and often the most immediately
  actionable thing it produces.
- **Recording restart timing separates two findings that need very different responses.** A mapping set
  that changed at a service restart points at configuration — a unit file, a drop-in, a plugin directive
  — and the fix is a configuration fix. A mapping set that changed with no restart means code was injected
  into a live process, which is a different severity and a different containment path. Only the restart
  timeline distinguishes them, and only a baseline makes the change visible at all.
- **Scoping to the dynamic linker is the mistake this campaign was built to survive.** Published guidance
  concentrates on `LD_PRELOAD` because it is the classic route. The Ted backdoor used a service plugin
  API. A baseline that records the resulting mapping set rather than only the known mechanisms stays
  correct when the next implant picks a route nobody has written up yet — which is the whole reason to
  capture the outcome alongside the configuration.
- **The inventory gap it exposes is itself the first deliverable.** Most teams cannot currently answer
  which shared objects load into their production `sshd`, let alone whether that set changed last month.
  The first run surfaces mostly legitimate but undocumented libraries, and closing that gap is what
  converts every subsequent month's diff from a research project into a one-line question.
