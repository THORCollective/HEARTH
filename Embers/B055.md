false_positive_notes: |
  A baseline has no alerts to be wrong about, but it has two failure modes that make the resulting envelope useless. The first is collecting during an unrepresentative window: month-end and quarter-end deployment freezes, a migration, or a DR test will either inflate or suppress the rate envelope, so record what happened during the collection window and extend past any freeze rather than averaging through it. The second is treating an unattributed principal as benign because it appeared during collection. A compromised identity active throughout the baseline window will be learned as normal — this is the central risk, and the mitigation is that ownership attribution is a required output, not an optional one: any principal that cannot be traced to a named owner and a documented purpose is an open finding regardless of how stable its behaviour looks. Expect a meaningful fraction of principals to be genuinely orphaned, left behind by decommissioned tooling, and to hold live credentials and role assignments; those are the highest-value output of this baseline and should be routed to deprovisioning rather than filtered into an allowlist.
notes: |
  Platform: Azure (IaaS control plane) and Microsoft Entra ID. Driven by Microsoft Threat Intelligence, "Storm-3168: Agentic-driven cloud attacks using compromised service principals" (September 25, 2026), where a client secret recovered from a GitHub issue's edit history let an actor run 300+ authorized read operations and 30+ successful storage-account `ListKeys` calls before a destructive phase. Every call was permitted by an existing role assignment, so the tenant had no envelope against which to judge them. This baseline builds that envelope.
  Collection window - 30 days minimum, 90 days preferred. ARM behaviour is strongly weekly-periodic (nightly scans, weekly compliance sweeps, sprint-boundary deployments) and monthly-periodic (patch cycles, cost reporting), so a 7-day window will misclassify monthly automation as anomalous forever. Record any deployment freeze, migration or DR exercise inside the window alongside the data.
  Fields to collect, per service principal - Identity: `appId`, service principal object ID, display name, registered owner(s), application owner tenant (to separate first-party Microsoft, third-party multi-tenant, and your own registrations), creation date, and whether it is a managed identity, a registered application, or a legacy principal. Credential: credential type (client secret vs certificate vs federated credential/workload identity federation), credential count, each credential's expiry, and `ServicePrincipalCredentialKeyId` as observed in sign-in logs. Authorization: every role assignment with its role definition name and its scope, flagged by scope breadth (management group and subscription scope are materially different risks from resource scope), plus any Entra directory role and any Graph application permission held. Behaviour from AzureActivity: the set of distinct resource providers, resource types and operation names called; the read / write / delete / action operation mix as a ratio; distinct resource groups and subscriptions touched; per-hour and per-day operation counts with median, 95th percentile and observed maximum; and the coefficient of variation of inter-operation latency. Provenance from sign-in logs: the set of `IPAddress` values with their ASN and geography, the set of user agents, `ResourceDisplayName` (which APIs this identity actually authenticates to), and the observed token issuance cadence. Correlation: the CI/CD pipeline, function app, automation account or vendor product that each principal belongs to, and the change-management identifier for its normal run windows.
  Sample KQL — per-principal control-plane profile:
  `AzureActivity | where TimeGenerated > ago(30d) | extend appid = tostring(parse_json(Claims_d).appid), idtyp = tostring(parse_json(Claims_d).idtyp) | where idtyp == "app" | summarize ops = count(), providers = make_set(split(OperationNameValue, "/")[0], 30), distinctTypes = dcount(OperationNameValue), reads = countif(OperationNameValue has "/READ"), writes = countif(OperationNameValue has "/WRITE"), deletes = countif(OperationNameValue has "/DELETE"), listKeys = countif(OperationNameValue has "LISTKEYS"), subs = dcount(SubscriptionId), rgs = dcount(ResourceGroup), ips = make_set(CallerIpAddress, 30), firstSeen = min(TimeGenerated), lastSeen = max(TimeGenerated) by Caller, appid | extend readRatio = todouble(reads) / todouble(ops) | order by ops desc`
  Deliverable format - A per-principal inventory record, one row per service principal, holding: owner and business purpose; credential type and next expiry; role assignments with scopes; the allowlisted set of operation name prefixes it legitimately calls; whether `listKeys` or Key Vault secret reads are in scope for it and against which resources; the allowlisted egress CIDRs and ASNs; the expected user agent; and the rate envelope as median and 95th-percentile operations per hour plus the observed maximum. Publish it as a queryable table (a Log Analytics custom table or watchlist) so detections can join against it rather than hardcoding thresholds — this is what makes [[H339]] and [[M050]] tunable instead of guesswork.
  Immediate flags — do not wait for the 30 days to complete - Any service principal with no identifiable owner, or whose owner has left the organization. Any principal holding Owner or Contributor at management-group or subscription scope, especially one created by a person rather than a pipeline. Any client secret with an expiry beyond 12 months or already expired-but-still-assigned. Any principal authenticating from a hosting, VPS or residential ASN rather than a known corporate or cloud egress range. Any principal whose user agent is a bare HTTP client (`python-requests`, `curl`, `Go-http-client`) where the documented tooling is the Azure CLI, Terraform or an Azure DevOps agent. Any first-ever `listKeys`, Key Vault `SecretList`, `roleAssignments/write`, resource-lock delete, or Recovery Services operation by a principal, since each of those is a step-change in capability rather than a volume change. Any principal authenticating with a client secret where the registration also holds a certificate, which usually means an added credential nobody sanctioned. Any credential added to a principal (`Update application – Certificates and secrets management` in the Entra audit log) without a matching change ticket — this is the single highest-value immediate flag, because it is how both adversaries and forgotten scripts acquire durable access.
  Cross-reference - This baseline is the prerequisite for [[H339]] (bulk storage-account `listKeys` harvesting, whose fan-out threshold is expressed as a multiple of the per-principal maximum recorded here) and for [[M050]] (cadence and parallelism scoring, which consumes the labelled automation inventory and the rate envelope directly). It also complements [[B043]], which baselines Entra service principals holding mail and chat application permissions — B043 covers the Graph data-plane side of workload identity, this record covers the ARM control-plane side.

# B055

Storm-3168's intrusion, published by Microsoft Threat Intelligence on September 25, 2026, contains an uncomfortable detection lesson: not one of the actor's Azure Resource Manager calls was unauthorized. Credentials recovered from the edit history of a public GitHub issue were used to authenticate two service principals whose existing role assignments — a group-granted Storage Account Contributor, direct Contributor and direct SQL DB Contributor — authorized everything that followed. The actor then made 300+ successful read operations over 15.5 hours and 30+ successful `ListKeys` calls, and finally deleted storage accounts, a Key Vault, a Function App and an App Service plan while targeting Site Recovery and Azure Backup protection locks. Azure logged all of it, correctly, as permitted activity by a legitimate identity.

There is no rule that catches this, because the thing that was wrong was not any single operation but the fact that this particular identity had never behaved this way before — and almost no tenant can state what "before" was. Service principals accumulate silently: created for a pipeline that was decommissioned, granted subscription-scope Contributor because scoping it properly was harder, handed a two-year client secret, owned by someone who has since changed teams. The result is a population of workload identities with real privilege, no attribution, and no measured behavioural envelope, which is precisely the condition that makes an authorized-but-adversarial call indistinguishable from automation. This baseline produces that envelope, and produces the attribution as a side effect.

## Why

- Every detection for compromised workload identity is a comparison against normal, and in Azure that comparison has to be per-principal rather than global. A CSPM scanner legitimately makes tens of thousands of reads a day while a deployment identity makes forty; a single tenant-wide threshold is useless against both, so the envelope must be recorded per identity before any threshold means anything.
- The role assignments are the blast radius, and inventorying them is the only way to know what a leaked secret is actually worth. Storm-3168's destructive reach was determined entirely by pre-existing RBAC — Storage Account Contributor permitted the storage deletions, Contributor permitted the Key Vault and Function App deletions — so mapping scope per principal converts an abstract credential-hygiene problem into a ranked list of which secrets must never leak.
- Credential provenance is the cheapest high-fidelity discriminator available and it requires a baseline to use. A service principal's legitimate egress ranges and user agents are narrow and stable, so a token issued to a known identity from an ASN it has never used is a strong signal — but only once the historical set has been recorded, which no tenant gets for free.
- Unattributed and orphaned principals are a finding in their own right, independent of any intrusion. Running this collection reliably surfaces live credentials and standing role assignments belonging to tooling that no longer exists and owners who have left, each of which is an exposure worth closing before it is found by someone else.
- The specific step-change operations are only definable against an inventory. `listKeys`, Key Vault `SecretList`, resource-lock deletion and Recovery Services changes are routine for a small set of platform identities and deeply abnormal for everyone else; the immediate-flag list above is only actionable because this baseline establishes which principals belong in that small set.
