hypothesis: >-
  On a fleet of developer Macs there is no way to tell a malicious `~/Library/LaunchAgents/` plist from a legitimate one by looking at it, and no way to tell whether an `~/.ssh/authorized_keys` append is remote-development tooling or an attacker, because both populations are small, both are written by shells and helper processes, and neither is inventoried anywhere. false_positive_notes: |
  Everything this baseline collects is overwhelmingly legitimate on day one, which is the point of collecting it rather than alerting on it. Expect the first pass to be dominated by updater agents (editors, browsers, Docker, Rancher, Homebrew services), VPN and endpoint-management helpers, and per-user agents installed by developer tooling.
  Remote-development tooling is the main source of SSH-material writes, and it is noisy but directional. VS Code Remote-SSH, JetBrains Gateway and `ssh-copy-id` write `~/.ssh/config`, `known_hosts` and private keys locally; the append to a remote `authorized_keys` happens on the far side. A local `authorized_keys` append on a laptop is rare enough that it should end up as a named exception per host, not an allowlisted pattern.
  Engineers legitimately enable Remote Login for a week to debug something and then forget. Those hosts are not findings, but they belong on the per-host record, because they are the hosts where a reverse forward to `localhost:22` would actually reach a listener.
  Homebrew-installed agents are written by shells, so the writing process is `bash`, `zsh` or `brew` rather than a signed installer. Do not allowlist on writer alone; allowlist on the triple of label, resolved program path and writer, or the exception will cover any future shell-written plist.
  A collection window shorter than thirty days will miss monthly and quarterly tooling, and will miss the agents created only when an engineer onboards a new project. Re-run the collection after any fleet-wide tooling change rather than treating the allowlist as permanent.
notes: |
  Platform - macOS. Windows developer workstations need the equivalent collection against scheduled tasks, the per-user Startup folder and `administrators_authorized_keys`, which is a different data set and a different allowlist; the Flames hunt that needs it is [[H430]].
  Why this baseline, and why now - Microsoft Threat Intelligence's analysis of the tampered `anthropic.claude-code` extension served from the Cursor marketplace on October 29, 2026 describes macOS persistence as a "User LaunchAgent with RunAtLoad and KeepAlive" at `~/Library/LaunchAgents/com.apple.sysmond.plist`, backed by `~/.config/.smt` and `~/.config/.smtk`. The report's own remediation guidance explains why an inventory has to exist first: "Inspect each startup object's configured action before removal; names alone are not sufficient to distinguish malicious objects from legitimate monitoring software." An estate that cannot answer "what user LaunchAgents are supposed to be here" cannot act on that instruction at incident speed.
  The same applies to the key. The loader "appends an embedded public key and attempts to enable the local SSH service", and Microsoft notes that "Cleanup does not replace investigation of device activity during the exposure window." Confirming which key entries were already legitimate is only possible against a prior record.
  What to collect - per host, per agent, for thirty days:
  - Agent label, the full path of the plist, and its creation and last-modification timestamps.
  - The resolved `Program` or first `ProgramArguments` element, as an absolute path, plus the signing identity of that target where it is an executable (`codesign -dvvv <path>`).
  - `RunAtLoad`, `KeepAlive`, `StartInterval` and `WatchPaths` values, since a tunnel keeper and an updater have very different shapes here.
  - The writing process: image name, full path, parent process, account, and whether the image was signed and notarised.
  - Load state from `launchctl list`, and whether launchd actually loaded it per the `com.apple.xpc.launchd` subsystem, rather than inferring load from the file existing.
  - For SSH: every write to `~/.ssh/authorized_keys` with the writing process, and the count and comment field of each entry at collection time (`ssh-keygen -l -f ~/.ssh/authorized_keys`).
  - For SSH: whether Remote Login is enabled, from `systemsetup -getremotelogin` or the `com.openssh.sshd` job state, plus whether a non-default `Port` or `GatewayPorts` is configured.
  - Host class from MDM, and the installed editor and extension set, so an agent written by an editor can be attributed to a specific extension rather than to the editor generically.
  Collection window - thirty days, which is also the Defender advanced hunting retention limit, so the endpoint half of this can be assembled retrospectively on day one and then extended forward.
  Collection query - LaunchAgent writes with their writer:
  ```kql
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("FileCreated", "FileRenamed", "FileModified")
  | where FolderPath has "/Library/LaunchAgents/"
  | summarize writes = count(), firstSeen = min(Timestamp), lastSeen = max(Timestamp),
              writers = make_set(InitiatingProcessFolderPath, 10),
              writerCmds = make_set(InitiatingProcessCommandLine, 5),
              hosts = dcount(DeviceId)
          by FileName
  | order by hosts asc, firstSeen desc
  ```
  Ordering by ascending host count is deliberate: an agent present on one host out of four hundred is the interesting end of the distribution, and an agent present on all of them is the fleet standard.
  Collection query - SSH authorization writers:
  ```kql
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where ActionType in ("FileCreated", "FileRenamed", "FileModified")
  | where FileName == "authorized_keys" or FolderPath endswith "/.ssh"
  | summarize events = count(), firstSeen = min(Timestamp),
              files = make_set(FileName, 10),
              cmds = make_set(InitiatingProcessCommandLine, 5)
          by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath
  | order by firstSeen desc
  ```
  `DeviceFileEvents` records creates, modifies, renames and deletes but no reads, so this sees the append and will never see a key being read for use. That is the right half for a persistence baseline; attributing use needs authentication telemetry instead.
  Per-host listener state - this is the field that decides whether a reverse forward has anything to forward to, and it cannot be collected from file telemetry:
  ```shell
  sudo systemsetup -getremotelogin
  sudo launchctl print-disabled system | grep -i com.openssh.sshd
  ssh-keygen -l -f ~/.ssh/authorized_keys 2>/dev/null
  launchctl list | awk 'NR>1 {print $3}' | sort
  ```
  Deliverable - three artefacts, each small enough to review:
  1. **An approved user-LaunchAgent allowlist**, one row per agent, keyed on the triple of label, resolved absolute program path and writing process. Agents matching all three are expected; a match on label alone is not, because the label is the field an adversary picks.
  2. **A list of processes that legitimately write SSH authorization material**, with the per-host exceptions named rather than generalised. This list should be short, and on most fleets no process on it will be appending to a local `authorized_keys`.
  3. **A per-host inbound-SSH record**: Remote Login state, configured port, and current `authorized_keys` entry count and comments. This is the scoping list for [[H429]] — it tells you which hosts a reverse forward could have reached and which ones already had keys to compare against.
  Immediate flags - do not wait for the thirty days to finish before acting on these:
  - A plist written into `~/Library/LaunchAgents/` by a code editor, its helper processes, `node`, `bun`, `npm`, `npx`, or a shell spawned by any of them. No legitimate editor build does this.
  - An agent whose label begins `com.apple.` but whose plist is in a *user* LaunchAgents directory. Apple's own agents live under `/System/Library/LaunchAgents/` and `/Library/LaunchAgents/`, so the reserved prefix in a user path is a masquerade regardless of what the program path says.
  - An agent whose resolved program is a script under `~/.config/`, `~/.cache`, `/tmp` or `/var/tmp`, or whose program is unsigned.
  - `KeepAlive` set true on an agent whose program invokes `ssh`, `autossh`, `nc`, `socat`, or a shell.
  - Any append to a local `~/.ssh/authorized_keys` on a workstation, and any entry whose comment field matches `svc-telemetry`.
  - Remote Login newly enabled on a host where MDM did not enable it.
  Reading a clean result correctly - Microsoft's caution cuts both ways for a baseline: "the presence of an artifact alone does not establish that the startup mechanism ran successfully", and equally a host with no agent may still hold the key, because Cursor reports that "errors and administrator-permission requirements blocked SSH access on most macOS and Windows hosts" while the loader "could still attempt to plant its SSH key, establish persistence, and report host information." Collect all three artefacts; do not treat any one as a proxy for the others.
  Cross-reference - this baseline enables [[H429]], which hunts the `com.apple.sysmond` LaunchAgent and the `autossh` reverse forward directly, and scopes [[H430]], the Windows half of the same loader, by telling you which developer hosts are in scope for editor-written persistence at all.
  Closest existing coverage - [[B057]] is the nearest baseline by shape, and inventories edge appliances rather than endpoints: its subject is a device class with no EDR agent and no software inventory, where this one is about a host class that has both and still has no record of its own autostart surface. [[B021]] and [[B043]] cover remote-support tooling and identity activity respectively, neither of which includes the LaunchAgent or local SSH authorization surface.

# B067

A hunt that says "look for a malicious LaunchAgent" is not actionable on a developer fleet, because the population of user LaunchAgents on an engineer's Mac is genuinely messy: updaters, Homebrew services, container runtimes, VPN helpers, and whatever the last three projects needed. They are written by shells as often as by signed installers, they are named by whoever wrote them, and nothing inventories them. The same is true of the SSH surface. Some engineers have Remote Login on, some have keys they added themselves years ago, and remote-development tooling writes into `~/.ssh/` constantly.

Microsoft Threat Intelligence's analysis of the tampered `anthropic.claude-code` extension makes the cost of that gap concrete. The macOS persistence is described as a "User LaunchAgent with RunAtLoad and KeepAlive" named `com.apple.sysmond.plist`, and the report's remediation instruction is to "Inspect each startup object's configured action before removal; names alone are not sufficient to distinguish malicious objects from legitimate monitoring software." That is the correct instruction and it is unexecutable at speed without a prior record of what the configured actions are supposed to be.

So this is the baseline that makes the two Flames hunts work. Thirty days of collection, three deliverables: an allowlist of user LaunchAgents keyed on label *and* resolved program path *and* writer; a list of the processes that legitimately touch SSH authorization material, with per-host exceptions named rather than generalised into a pattern; and a per-host record of whether inbound SSH is even listening.

The third deliverable is the one most easily skipped and the most useful. A reverse forward to `localhost:22` only reaches something if `sshd` is running, and Cursor reports that "errors and administrator-permission requirements blocked SSH access on most macOS and Windows hosts." Knowing which of your hosts are in the minority turns a fleet-wide question into a list of named machines.

A handful of patterns do not need the thirty days. A code editor writing into `~/Library/LaunchAgents/`, a `com.apple.`-prefixed label sitting in a user LaunchAgents directory, `KeepAlive` on an agent that invokes `ssh`, or any append to a local `authorized_keys` on a laptop — those are flags on sight, and the immediate-flags list exists so the collection period is not a detection holiday.

## Why

- The decisive field is the resolved program path, and nothing records it. Label and filename are both attacker-chosen, which is exactly why the published remediation guidance says not to trust them — and why an allowlist keyed on the triple is worth building once.
- `com.apple.` in a user LaunchAgents directory is a structural tell, not a heuristic. Apple's agents ship in system paths, so the reserved prefix in a per-user path is always a claim the file is not entitled to make.
- The SSH half inverts normal developer behaviour and so stays quiet. Remote-development tooling writes local config and private keys and appends authorised keys remotely; a local append on a workstation is rare enough to be a named exception per host rather than an allowlisted pattern.
- Listener state scopes the whole problem. The difference between a planted key that grants nothing and one that grants interactive access is whether `sshd` is running, and that single per-host fact converts a fleet-wide alert into a short triage queue.
- Artefacts and access come apart in this class of compromise, so a baseline that collects only one of them will clear hosts it should not. The key, the agent and the beacon are three independent facts and the record has to hold all three.
