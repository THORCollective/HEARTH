# B033

`ctfmon.exe` is the Windows text-services / input host. It runs on effectively every interactive Windows machine, which is precisely why PikaBot's loader creates one to live inside — an analyst scanning a process list has no reason to stop on it. Sekoia's 2026-07-23 teardown shows stage 2 spawning a **new** `ctfmon.exe` solely as an injection host, then rebuilding the payload PE inside it and hijacking its thread.

The detection problem is not that the behaviour is subtle; it is that nobody has written down what normal looks like. This Ember produces that document, so the paired Flames hunt (H245) can make a confident call.

## Why

- **The Flames hunt is unrunnable without it.** "ctfmon.exe with an unusual parent" only means something once the usual parents are enumerated for *your* estate — and they legitimately differ across OS builds, WOW64, and RDS/VDI. Guessing produces either a dead rule or an alert storm.
- **The expected result is a null, and nulls are the most valuable baselines.** Confirming with 30 days of evidence that `ctfmon.exe` never makes an outbound connection converts a noisy-sounding idea into a standing near-zero-false-positive detection. A documented null is a detection asset.
- **Instance count is a free re-infection signal.** Sekoia notes PikaBot uses no mutex, so re-running on the same host yields a second `ctfmon.exe`. That is only visible if the normal per-session count is known — and it differs between workstations and multi-session servers.
- **It generalises past PikaBot.** The technique here is "create a ubiquitous, unremarkable process and inject into it." Once the profile for this host process exists, the same collection template applies to the other perennial injection targets, and the allowlist keeps paying out after this particular loader is gone.
