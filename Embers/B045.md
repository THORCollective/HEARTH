  endpoint is both large and unintuitive - VPN and ZTNA clients checking whether the tunnel is up, RMM
  and monitoring agents reporting location, cloud and container CLIs, software updaters, licence
  checks, telemetry and crash reporters, game launchers, speed-test and network diagnostic tools,
  conferencing clients, and the installers of all of the above. Elastic ships its equivalent logic as a
  building-block rule rather than an alert for precisely this reason, and SigmaHQ''s version is built
  around excluding browsers, which tells you how much of the volume browsers alone account for. Four
  practical consequences. First, the deliverable is an allowlist keyed on signer and full path, never on

# B045

CrowdStrike's PhantomRaven write-up describes an information stealer distributed through typosquatted
npm packages — `transform-jsbi-to-bigint` and `sort-imports-es6-autofix`, published by the accounts
`jpdhellonpm1` and `jpd15` — that executes via npm's `preinstall` lifecycle hook. The packages
themselves contain almost nothing: a `Hello, world!` script. The payload arrives through dependencies
declared as raw HTTP URLs pointing at attacker infrastructure, which npm's web interface does not render,
so a developer inspecting the package page sees a trivial package with no visible dependencies.

Two behaviours from that report are worth baselining, and they are related but separate.

The first is the IP-echo call. Before exfiltrating, PhantomRaven requests
`https://api64.ipify.org?format=json` to learn the host's external address, and CrowdStrike notes it does
this regardless of whether the request succeeds. This is not a distinctive choice — it is close to
universal in commodity stealers, loaders and RATs, which is exactly the problem. The call is a strong
behavioural marker sitting inside an enormous legitimate population, and every published rule for it
ships hedged: Elastic classifies its version as a building block, SigmaHQ's is defined largely by its
browser exclusions, Splunk's is a Sysmon EID 22 stack. All three are telling you the same thing, which is
that the destination is not the signal. The process that made the call is the signal, and knowing which
processes legitimately make it requires a baseline that only your own estate can provide.

The second is what an install is permitted to do. PhantomRaven's entire execution depends on
`preinstall` running attacker code as a side effect of `npm install`, harvesting `GITHUB_ACTIONS`,
`GITLAB_CI`, `JENKINS_URL`, `CIRCLECI` and `npm_config_registry` from the environment along with OS,
architecture, hostname, Node version, time zone and location. Every one of those actions is something a
legitimate package's build script might also do. There is no rule that separates them. What separates
them is knowing which packages in your organisation legitimately run lifecycle scripts, what those
scripts legitimately spawn, and where they legitimately connect.

The baseline is scoped to Windows developer and build endpoints deliberately, and the scoping matters
because HEARTH already covers the other half. [[B020]] profiles what a legitimate dependency install
looks like on self-hosted CI/CD runners — which interpreters and child processes `npm install`, `npm ci`,
`pip`, `yarn` and `pnpm` normally spawn there. This baseline is the developer-workstation counterpart,
and it differs in the two ways that matter: the platform and its telemetry (Sysmon EID 22 DNS attribution
and Authenticode signer data, neither of which a Linux runner provides), and the primary object. B020's
object is the install subtree. This one's object is the IP-echo lookup — which process in the estate
legitimately asks the internet for its own address — with the install profile present as the supporting
half because PhantomRaven arrives through the install and beacons through the lookup, and a register that
covers one without the other cannot connect them. Run both; do not merge them, because the legitimate
process populations on a build runner and a developer laptop have almost nothing in common and a combined
baseline describes neither.

One structural note on why the manifest inventory sits in this baseline rather than in a rule. A
dependency declared as an HTTP URL instead of a registry version range is unusual, checkable, and
strongly associated with this delivery method — but it is not unknown in legitimate use, particularly for
private forks and internal packages pinned to a git or artifact URL. The number of such dependencies in
an organisation is small and finite, which makes it an ideal thing to enumerate once and diff thereafter,
and a poor thing to alert on cold.

[[H297]] is a Windows process-provenance hunt from the same batch and shares the concern that a process's
self-reported identity is not trustworthy; the signer-plus-path allowlist specified below exists for the
same reason.

## Baseline data to collect

**External IP-echo lookups (the behaviour)**
- Every Sysmon EID 22 DNS query and EID 3 network connection whose destination matches the IP-echo domain
  list, with initiating image path, image name, Authenticode signer, signature validity, user, and
  parent process
- Per `(signer, full path, image name)` tuple: number of distinct hosts observed, calls per host per day,
  time-of-day distribution, and whether the calls are periodic or event-driven
- Whether the initiating process is a browser or runs as S-1-5-19 / S-1-5-20, recorded so these can be
  excluded consistently rather than ad hoc per query
- The same tuple observed against hardcoded IP destinations with no preceding DNS query

**Package-manager lifecycle execution (the mechanism)**
- Every execution of `npm.cmd`, `npx.cmd`, `yarn`, `pnpm`, `pip.exe`, `nuget.exe` and `composer`, with
  the full child process tree spawned during install
- Which installs spawn `node.exe`, `powershell.exe`, `cmd.exe`, `curl.exe` or `certutil.exe` as
  descendants, and which packages those installs were for
- Network connections made by any descendant of a package-manager process, with destination and whether
  it is the configured registry
- File creations under `node_modules`, `%APPDATA%\npm-cache` and `%LOCALAPPDATA%\npm-cache`, timestamped
  for correlation against the network activity that followed

**Dependency and registry configuration (the exposure)**
- Every dependency in `package.json` and `package-lock.json` declared as a raw HTTP or HTTPS URL rather
  than a registry version range, per project and per host
- Per-user and per-project `.npmrc` contents, the effective `npm_config_registry` value, and the pip
  index URL, flagging any that is not the organisation's approved registry or proxy
- Which developer and build hosts have `GITHUB_ACTIONS`, `GITLAB_CI`, `JENKINS_URL`, `CIRCLECI` or
  registry credentials present in the process environment, and under which accounts

**Egress context**
- Outbound HTTP user agent strings per process on developer endpoints, so that the bare
  `Mozilla/5.0 (Windows NT 10.0; Win64; x64)` string can be attributed to the small set of processes
  that legitimately emit it

## Collection window

Thirty days, which covers a full sprint and at least one patch and dependency-update cycle on most
teams. Extend to sixty days where release cadence is monthly or slower, since a build toolchain that
runs once a release will otherwise appear novel on its first observation. Profile developer endpoints and
build endpoints as separate populations from general corporate endpoints, and profile per team where
toolchains differ materially — a data-science group and a front-end group do not share a legitimate
process set.

## Deliverable

Two registers, refreshed monthly.

The first is an IP-echo allowlist with one row per `(signer, full path, image name)` carrying: observed
host count, calls per host per day, periodic or event-driven, business justification, and an
owner-confirmed disposition of expected / expected-with-review / unexplained. The monthly diff against
this register is the actual hunt; the register itself is what makes the diff short.

The second is a package-install profile with one row per `(package manager, package, lifecycle script)`
that legitimately runs a script, carrying what it spawns, where it connects, and which projects depend
on it — plus the complete list of HTTP-URL dependencies and non-standard registry configurations in the
estate, each with a named owner.

## Flag immediately — do not wait for the baseline to complete

- Any IP-echo lookup initiated by `node.exe`, `npm.cmd`, `npx.cmd`, `python.exe`, `pip.exe` or any
  descendant of a package-manager process — a dependency install has no legitimate reason to ask what
  your external address is
- Any IP-echo lookup from an unsigned binary, or from a binary whose path is under `%TEMP%`, `%APPDATA%`,
  `%LOCALAPPDATA%\Temp`, `Downloads` or a user profile root
- Any IP-echo lookup from a LOLBin — `curl.exe`, `certutil.exe`, `bitsadmin.exe`, `powershell.exe`,
  `mshta.exe` — on a developer endpoint
- Any dependency in `package.json` or a lockfile declared as a raw HTTP or HTTPS URL to a host that is
  not the organisation's registry, artifact store or approved git remote
- Any `npm_config_registry` or `.npmrc` registry value pointing at a host that is not the approved
  registry or its proxy
- A package-manager install whose descendant process makes an outbound connection to a host that is not
  the configured registry, within the install window
- The bare user agent `Mozilla/5.0 (Windows NT 10.0; Win64; x64)` emitted by any process other than a
  browser on a developer endpoint
- Any process reading `GITHUB_ACTIONS`, `GITLAB_CI`, `JENKINS_URL` or `CIRCLECI` from the environment
  that is not itself part of the CI toolchain
