title: "Baseline of directory queries made by appliance and gateway service accounts: which attributes each integration actually needs, and from where"
hypothesis: >-
  Every VPN concentrator, gateway and appliance that authenticates users against Active Directory holds a
  service account, and almost none of those accounts are scoped to what they do. They were created to
  validate logons; they can usually read whatever the directory will hand an authenticated user, which
  includes the attributes that store secrets. When UTA0576 compromised an Ivanti Connect Secure appliance,
  the pivot was not an exploit - it was using the appliance's own Active Directory service account to ask
  a domain controller for LAPS passwords and BitLocker recovery keys, which it was permitted to answer.
  Volexity describes the tool authenticating "to an internal domain controller via LDAP using the ICS VPN
  appliance's Active Directory service account" and searching "for high-value Active Directory
  attributes". That query is only anomalous if someone knows what the account normally asks for. Build a
  30-day baseline, per integration account, of the LDAP binds and searches it makes - source address, base
  DN, filter shape, attributes requested, volume and timing - so that a request for secret-bearing
  attributes, or a bind from somewhere the appliance is not, becomes a visible deviation rather than a

false_positive_notes: |
  Nothing in this hunt is an alert, so the usual false-positive framing does not apply - the deliverable
  is a baseline and a scoping decision. What does go wrong is mistaking normal integration behaviour for
  a finding, and there is a lot of normal behaviour to learn. These accounts bind constantly, often many
  times a minute, and they legitimately enumerate user objects, group membership and realm information,
  because that is how a VPN decides whether a user may connect and which policy applies. Query volume is
  therefore not a signal on its own. Expect legitimate variation from several directions. Appliance
  clusters and high-availability pairs mean the same account binds from several addresses, so the
  source-address baseline must be a SET per account rather than a single value, and failover will add an
  address legitimately. Firmware upgrades change which attributes an appliance requests, so an upgrade
  can shift the attribute baseline overnight and must be recorded as a change rather than investigated as
  an intrusion. Nested group expansion and large group membership checks produce broad, expensive queries
  that look like enumeration and are not. Some appliances legitimately read extended attributes for
  policy decisions - department, title, group DNs, UPN suffixes - so the attribute set is wider than one
  might expect and has to be measured, not assumed. Two things are worth treating as findings during
  baselining rather than noise. An integration account binding from an address that is not its appliance
  is either an undocumented reuse of the credential or a compromise, and both need resolving. And an
  integration account with rights to read LAPS or BitLocker attributes is a least-privilege finding on the

  asked for before. That is a baseline question by construction, which is why it is filed as an Ember

  account over the window.

  named human owner. Source network address of every bind, and the resolved hostname where available.
  Destination domain controller. Timestamp, with the bind rate aggregated per hour and per day. Logon
  type and authentication package from event 4624, and whether the bind was simple or SASL, signed or
  unsigned, over 389, 636 or a global catalog port. For each search - the base DN, the scope, the filter
  text, and the list of attributes requested. Result size or record count where the telemetry carries it.
  Group memberships and delegated rights held by the account. And, separately, every principal that has
  read rights on `ms-Mcs-AdmPwd`, `msLAPS-Password`, `msLAPS-EncryptedPassword` and
  `msFVE-RecoveryPassword`.
  Deliverable format. One record per integration account containing - the set of source addresses it is
  permitted to bind from, the set of base DNs it searches, the set of attributes it requests, its normal
  bind volume per hour with a tolerance, the domain controllers it talks to, and an explicit list of
  secret-bearing attributes it can read today versus the list it needs. The second half of that is the
  product worth more than the detection: a scoping proposal per account, with the rights to remove. Also
  deliver the inverse index - for each of the LAPS and BitLocker attributes, every account and host that
  read it during the window, which is a short list in a healthy estate and names the legitimate readers
  for every future query.
  Immediate flags, to raise during collection rather than waiting for the 30 days to finish.

  reported behaviour. A bind by an integration account from an address that is not its appliance or a
  known cluster peer. An integration account that authenticates interactively, or to anything other than
  a domain controller. A bind from an appliance subnet under an account that is not in the integration

  `IdentityLogonEvents | where Timestamp > ago(30d) | where Protocol == "Ldap" | where AccountUpn in~ ("svc-ics-ldap@example.com", "svc-vpn-bind@example.com") | summarize Binds = count(), Sources = make_set(IPAddress, 20), DCs = make_set(DestinationDeviceName, 20), FirstSeen = min(Timestamp), LastSeen = max(Timestamp) by AccountUpn | order by Binds desc`
  Sample KQL for the attribute side - which directory queries each integration account makes, with the
  query detail projected so the attribute names are readable.
  `IdentityDirectoryEvents | where Timestamp > ago(30d) | where AccountUpn in~ ("svc-ics-ldap@example.com") | summarize Queries = count(), Actions = make_set(ActionType, 10), Detail = make_set(AdditionalFields, 10) by AccountUpn, DeviceName, IPAddress | order by Queries desc`
  Sample KQL for the inverse index - every reader of the secret-bearing attributes over the window,
  which is the list that makes [[H385]] cheap to triage.
  `IdentityDirectoryEvents | where Timestamp > ago(30d) | where AdditionalFields has_any ("ms-Mcs-AdmPwd", "msLAPS-Password", "msLAPS-EncryptedPassword", "msFVE-RecoveryPassword", "msFVE-KeyPackage") | summarize Reads = count(), Accounts = make_set(AccountUpn, 50), Sources = make_set(IPAddress, 50) by ActionType | order by Reads desc`
  Sample Splunk SPL over event 4624 for the source-address set per integration account, which is the
  cheapest half of this baseline and needs no diagnostic tuning.
  `index=wineventlog EventCode=4624 Account_Name IN ("svc-ics-ldap","svc-vpn-bind") | stats count AS binds, dc(Source_Network_Address) AS distinct_sources, values(Source_Network_Address) AS sources, values(Logon_Type) AS logon_types, values(host) AS domain_controllers BY Account_Name | sort - binds`
  Sample Splunk SPL over event 1644 for the filter and attribute baseline, with the caveat that 1644 only
  records searches the DC considers expensive or inefficient - so this view is a floor on what the account
  asked for, never a complete picture.
  `index=wineventlog source="WinEventLog:Directory Service" EventCode=1644 | stats count AS searches, values(Search_Filter) AS filters, values(Starting_Node) AS base_dns BY Client_IP_and_Port | sort - searches`
  Sample PowerShell for the rights half of the deliverable - who can read LAPS passwords today. This is a
  configuration question rather than a telemetry one, and it is answerable in an afternoon.
  `Get-ADComputer -Filter * -Properties ms-Mcs-AdmPwd | ForEach-Object { (Get-Acl "AD:$($_.DistinguishedName)").Access | Where-Object { $_.ObjectType -eq (Get-ADObject -SearchBase (Get-ADRootDSE).schemaNamingContext -Filter {name -eq 'ms-Mcs-AdmPwd'} -Properties schemaIDGUID).schemaIDGUID } | Select-Object IdentityReference, ActiveDirectoryRights }`

# B061

The appliance had a domain account, and nobody had ever scoped it.

It was created to answer one question — is this a real user with the right password — and it could answer a great many others, because Active Directory hands an authenticated account whatever it has rights to read. In the Ivanti case Volexity investigated, that turned out to include LAPS local administrator passwords and BitLocker recovery keys.

The important thing about that query is how ordinary it was. No exploit, no malformed request, no unusual port. The appliance's own service account bound to a domain controller over LDAP — as it does thousands of times a day — and asked for some attributes. The directory answered, correctly, because the account was permitted to read them.

That is why this is an Ember and not a second Flames hunt. [[H385]] can look for the specific attribute names Volexity reported, and it should. But a hunt built on a list of attribute names only catches the attacker who wants the things on the list. The generalisable question is different: *what does this account normally ask for, and from where?* Answer that once and any deviation becomes visible, including the ones nobody has published yet.

The baseline is cheap because integration accounts are boring. They bind from one or two addresses — their appliance, and its cluster peer. They search a small number of base DNs. They request a predictable attribute set that supports authentication and policy decisions. Their volume is high but stable. Thirty days is enough to know all of it.

Two things fall out of the collection that are worth more than the detection.

The first is the inverse index: for each of the LAPS and BitLocker attributes, every account and host that read it during the window. In a healthy estate that is a short list — helpdesk tooling, a PAM platform, a few named administrators. Having it written down makes every future query of this kind cheap to triage, because the answer to "is this reader legitimate" is already on paper.

The second is a least-privilege finding that needs no telemetry at all. Export the read rights on `ms-Mcs-AdmPwd` and `msFVE-RecoveryPassword` and look at which service accounts appear. An appliance integration account with rights to read LAPS passwords is a finding the moment you see it, whether or not anything has ever used those rights. In the reported case, those rights are what made the pivot possible. Removing them is a better outcome than detecting their use.

A note on expectations, because the queries here fail quietly. Event 1644 only records searches the domain controller judges expensive or inefficient, so a well-aimed query against an indexed attribute may never appear in it — it is a floor on what was asked, not a transcript. Event 4662 records attribute reads only where a SACL was placed on that attribute first; without one, a LAPS password read generates nothing whatsoever. Defender for Identity needs a sensor on each DC. If none of that is configured, the honest first deliverable of this baseline is a collection gap report, and the achievable starting point is 4624 bind coverage plus the read-rights export.

And learn the normal before calling anything abnormal. These accounts bind many times a minute; volume is not a signal. Clusters mean several legitimate source addresses, failover adds more, and firmware upgrades change which attributes an appliance asks for. Record those as changes rather than investigating them as intrusions.

## Why

- **The malicious query is indistinguishable from the legitimate ones except by comparison.** An authorised account performing a normal protocol operation leaves no artefact to signature, which makes a per-account baseline the only reliable discriminator.
- **The baseline generalises past the published attribute list.** [[H385]] catches a request for the attributes Volexity named; this catches a request for anything this account has never asked for.
- **The identity telemetry is the half the attacker could not edit.** UTA0576 rewrote the appliance's debug and audit logs from root, but the domain controller's records were out of reach — so the directory side is where a durable detection has to live.
- **Integration accounts are boring, so the baseline is small and stable.** A short set of source addresses, base DNs and attributes, with high but steady volume, converges well inside 30 days.
- **The read-rights export is a finding available immediately, with no telemetry.** An appliance account that can read LAPS passwords is a least-privilege problem on sight, and in this case it is precisely what enabled the pivot.
- **The inverse index makes every future triage cheap.** Knowing which accounts and hosts legitimately read LAPS and BitLocker attributes turns a future alert from an investigation into a lookup.
- **Appliances are agentless, so the directory is where their behaviour becomes observable.** No EDR, no software inventory and no file integrity monitoring on the appliance means the second hop is the first place with trustworthy evidence.
- **The collection prerequisites are a real deliverable.** Discovering that 1644 is untuned, that no attribute SACLs exist, or that a DC has no sensor is a concrete and fixable outcome of running this.
- **Scoping the account removes the attack path rather than detecting it.** The durable fix is an integration account that can validate authentications and nothing else, which this baseline produces as a by-product.
