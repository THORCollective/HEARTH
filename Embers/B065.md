  Ransomware operators stopped settling for deleting shadow copies on the encrypted host. false_positive_notes: |
  This produces a description rather than a verdict, but several things will distort the collection.
  Appliance firmware updates and genuine maintenance look destructive. Firmware upgrades, disk replacement, pool expansion and controller failover all generate configuration-change and sometimes reset-adjacent events. Collect the maintenance calendar alongside the logs, and record planned-change windows as a documented category rather than filtering the events away.
  Vendor support sessions are a real and recurring pattern. Support engineers authenticate to appliances, often from outside the estate and sometimes with a vendor-held account. Baseline that explicitly, including which accounts exist for it and whether they can be disabled between engagements, because an attacker using one is otherwise invisible.
  Backup software legitimately deletes data constantly. Retention expiry, synthetic full consolidation and grooming all remove restore points on a schedule. The baseline must capture the normal volume and cadence of restore-point removal per policy, or every ordinary retention run will read as a purge.
  The Volume Shadow Copy service is start-on-demand. It starts and stops routinely on healthy servers as backup and application jobs request snapshots, so transitions alone mean nothing. The signal is a change of start type to disabled, or a stop that is not followed by any snapshot activity, so record the normal transition pattern per server role.
  Appliance logging is frequently thin, non-standard and short-lived. Many NAS devices log sparsely by default, roll logs quickly, and will lose everything relevant in a factory reset — the reset destroys its own evidence. Verify forwarding works before relying on it, and treat the forwarded copy as the only copy.
  Some appliances allow administration over paths that bypass the directory entirely, using local accounts over HTTPS, SSH or a vendor cloud portal. Enumerate all of those paths during collection; a baseline covering only domain-authenticated access describes the least likely route.
notes: |
  Collection window - 30 days minimum, and extend to cover at least one full monthly and one quarterly backup cycle. Retention and consolidation operations run on monthly and quarterly rhythms, so a 30-day window alone will characterise weekly activity and mislabel the periodic work.
  Fields to collect:
  - Appliance inventory: hostname, model, firmware version, management IP and interface types exposed (web, SSH, SNMP, vendor cloud), and which backup data each holds.
  - Administrative accounts per appliance: local accounts, directory-integrated accounts, vendor support accounts, and API tokens or keys, each with owner, privilege level and MFA state.
  - Authentication records: timestamp, account, source IP, source hostname where resolvable, interface used, success or failure, and whether the source is a designated admin jump host.
  - Configuration operations: the operation name, the account, the source, and the before and after values. Record which operations the appliance even exposes, specifically factory reset, configuration reset, volume or pool deletion, snapshot deletion, snapshot schedule change, retention change, immutability or WORM toggle, and replication target change.
  - Backup application operations: policy creation and modification, retention changes, repository addition and removal, restore-point deletion, credential changes, and any change to immutable or air-gapped copy settings.
  - Shadow copy service state per server: service state transitions, start-type changes, and the account that initiated them, correlated with the server role.
  - Cadence: operations per week per appliance per account, and the distribution of restore-point removals per policy.
  - Reachability: which hosts and network segments can reach each management interface at all, which is the control you will most want to tighten afterwards.
  Baseline query - privileged logons to appliance management interfaces, Defender XDR, 30-day retention. Replace the appliance device set with your own inventory:
  ```kql
  let appliances = dynamic([]);   // populate from the asset inventory
  DeviceLogonEvents
  | where Timestamp > ago(30d)
  | where RemoteDeviceName in~ (appliances) or DeviceName in~ (appliances)
  | summarize Logons = count(), Sources = make_set(RemoteIP, 20), FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
            by DeviceName, AccountName, LogonType
  | order by Logons desc
  ```
  Shadow copy service state across the server estate - collect the start type and current state so the baseline records what normal looks like per role:
  ```kql
  DeviceProcessEvents
  | where Timestamp > ago(30d)
  | where ProcessCommandLine has_any ("vssadmin", "wbadmin", "bcdedit", "reagentc")
      or (FileName =~ "sc.exe" and ProcessCommandLine has "VSS")
  | project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine,
            InitiatingProcessFileName, InitiatingProcessCommandLine
  | order by Timestamp desc
  ```
  Treat the results as the inventory of who legitimately touches recovery configuration, which on most estates is a very short list of backup service accounts and a handful of named administrators.
  Deliverable - A backup control-plane document containing: (1) the appliance and backup-application inventory with the destructive operations each exposes; (2) the authorised administrator and service-account list per appliance, with owner, privilege level, MFA state and whether the account can be disabled between uses; (3) the authorised source hosts and segments for each management interface, and the much larger set that should have no reachability at all; (4) the normal weekly and monthly cadence of configuration change and restore-point removal per policy; (5) the per-server-role normal pattern for shadow copy service transitions; (6) an explicit statement of which backup copies are immutable or air-gapped and therefore survive an appliance reset, which is the figure your recovery plan actually depends on. Review quarterly and after any appliance or backup software change.
  Flag immediately, without waiting for the collection window to close:
  - Any factory reset, configuration reset, volume deletion or pool deletion on an appliance holding backup data. This is the operation this baseline exists for, and there is no scenario in which it should occur unannounced.
  - A retention reduction, immutability or WORM setting being disabled, or a replication target being removed or repointed. These precede destruction and are reversible only before the next cycle.
  - Appliance administrative authentication from a host that is not a designated admin jump host, particularly from a general-purpose workstation or a file server.
  - A new local administrative account or API token created on an appliance, or a vendor support account being enabled outside a known engagement.
  - The Volume Shadow Copy service start type set to disabled on any server, or stopped on a server whose role requires it, especially across several servers in one window.
  - Bulk restore-point or snapshot deletion that exceeds the policy's normal removal volume, or any deletion performed by an interactive account rather than the backup service account.
  - Appliance management interface access from a host that has recently run remote-execution tooling such as PsExec or WinRM against other hosts.
  Flames hunts this baseline enables - [[H348]] hunts a ransomware executable disabling the recovery environment and wiping free space on the endpoint, and [[H220]] hunts a masquerading binary used immediately before recovery impairment. Both operate on the victim host; neither sees the appliance. This baseline supplies the control-plane half, so that an operator who resets the backup appliance instead of running recovery commands on the servers does not pass through unobserved. [[B051]] baselines remote-access tooling and endpoint-security exclusions, and [[B046]] baselines Group Policy administration; together with this one they cover the three control planes ransomware operators reach for before encrypting.

# B065

The joint advisory on SafePay ransomware, published October 2026, records a pre-encryption sequence that most recovery plans do not anticipate. SafePay operators "halt the Volume Shadow Copy Service and reset Network Attached Storage containing victim backup data to initial factory settings to inhibit system recovery attempts". They reach that point using entirely legitimate tooling — PsExec, WinRM, RMM software and RDP for movement, with 7-Zip, WinRAR, RClone and WinSCP for collection and exfiltration before encryption with a ChaCha20 and RSA hybrid scheme.

The factory reset is the part worth building for. Deleting shadow copies on a file server is well-covered ground, and so is clearing backup catalogues — both are endpoint actions that leave endpoint telemetry. Resetting the appliance is different in kind. It is a supported administrative operation, performed through the appliance's own management interface, by an account with legitimate rights, and it destroys both the backup data and the retention configuration that protected it. It also destroys the appliance's own logs, so the evidence of the reset frequently goes with it unless logging was being forwarded beforehand.

That is a control-plane problem, and it is unobservable without a baseline. Appliance administration is low-volume, infrequent and performed by a small number of people from a small number of hosts — which is exactly the profile that makes a baseline cheap to build and highly discriminating once built. The same applies to the shadow copy service: it starts and stops constantly on healthy servers, so transitions mean nothing, but a start type changed to disabled across several servers in one window means a great deal.

This hunt establishes that baseline: the appliances and the destructive operations they expose, the accounts and source hosts that legitimately reach them, the normal cadence of configuration and retention change, the per-role shadow copy pattern, and — the number the recovery plan actually rests on — which backup copies are immutable or air-gapped and would survive a reset.

## Why

- The backup control plane is usually monitored for success and nothing else. Teams alert on failed jobs and watch capacity, while the operations that destroy the backups are typically unlogged, unforwarded or unreviewed. This closes a gap that only becomes visible during a recovery that does not work.
- A factory reset is a legitimate operation, so only context can classify it. There is no malicious command line to match and no malware to detect; the only thing that separates an attack from maintenance is whether this account, from this host, at this time, was expected. That is precisely what a baseline provides.
- The appliance destroys its own evidence. A reset wipes the local logs, so the forwarded copy is the only record that will exist afterwards. Verifying that forwarding works is itself a deliverable, and it has to happen before the incident rather than during it.
- The population is small and stable, which makes this one of the cheapest baselines available. A handful of appliances, a handful of administrators and a handful of jump hosts produce a short document with a long useful life, and the reachability inventory it produces is directly actionable as a hardening change.
- Precursor operations are reversible while the reset is not. Retention reductions, immutability being switched off and replication targets being repointed all precede destruction and all show up in the same control plane, so the baseline buys warning time rather than just attribution.
- Existing HEARTH coverage for recovery inhibition sits on the victim host. Hunts for shadow-copy deletion, recovery-environment tampering and masquerading binaries before impact are all endpoint-side; an operator who works through the appliance management interface instead bypasses every one of them.
