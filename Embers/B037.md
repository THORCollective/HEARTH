title: Baseline of WinRM and winrs remote execution — who initiates, from where, to what, and with which accounts
hypothesis: >-
  `winrs -r:DC-US-2 -u:<domain>\<domain_admin> -p:<pw> hostname` is indistinguishable from an administrator doing
  their job, unless you already know that this source host has never initiated WinRM before, that this account
  has never used it, and that nobody in the estate normally reaches a domain controller this way. WinRM is
  enabled by default on Windows Server, runs over 5985/5986 alongside legitimate management traffic, and executes
  as a signed in-box binary — so no Flames hunt against it can work without a baseline first. Establish, over 30

required_data_sources:
  - Microsoft-Windows-WinRM/Operational Event ID 91 (creating WSMan shell) and Event ID 6 (WSMan session created) on destination hosts — the canonical server-side record of an incoming WinRM shell
  - Microsoft-Windows-WinRM/Operational Event ID 169 — authentication of a user to the WinRM service, carrying the account name and auth mechanism
  - Sysmon Event ID 1 / Windows Security 4688 on destinations — wsmprovhost.exe process creation, its child processes, and the full command line of what was executed
  - Windows Security 4624 on destinations — LogonType 3 (network), the source IP/workstation, and the LogonId to tie the session to subsequent process creation
  - Sysmon Event ID 1 / Security 4688 on sources — winrs.exe, Enter-PSSession, Invoke-Command, New-PSSession, and wsmprovhost invocations, with full command lines
  - Sysmon Event ID 3 / Defender XDR DeviceNetworkEvents — outbound connections to 5985/TCP and 5986/TCP, giving the source→destination edge even where host logs are missing
  - Microsoft-Windows-PowerShell/Operational Event ID 4103/4104 on destinations — the script blocks actually executed inside the remote session
  - Defender XDR DeviceLogonEvents and DeviceNetworkEvents — RemoteIP, RemotePort, AccountName, DeviceName for the estate-wide graph
  - Asset inventory / CMDB — host role (workstation, member server, domain controller, jump host, tier-0 asset) and owner, without which the graph has no meaning
  - Privileged access management records — which accounts are approved to administer which tiers, to be joined against the observed account usage
notes: |
  COLLECTION WINDOW:
  30 days minimum, and 45 is better. WinRM administration is strongly weekly and monthly in its rhythm — patch
  Tuesdays, month-end jobs, quarterly maintenance windows. A 7-day baseline will misclassify the monthly cycle as
  anomalous and burn the hunt's credibility in its first week. If the estate has a quarterly change calendar,
  note the windows explicitly rather than trying to cover them all.

  DELIVERABLE:
  A four-part artifact, kept as data rather than a document, and re-generated monthly.
  (1) THE EDGE ALLOWLIST — the authoritative set of observed (source host, account, destination host) triples,
      each annotated with observation count, first-seen, last-seen, and whether it is sanctioned. This is the
      core deliverable; everything else supports it.
  (2) THE INITIATOR INVENTORY — the set of hosts that have EVER initiated WinRM, with role and owner. In most
      estates this is startlingly small (jump hosts, a handful of admin workstations, a management server or
      two, and monitoring/config-management agents). Its smallness is the point.
  (3) THE ACCOUNT-TO-TIER MAP — which accounts initiate WinRM to which asset tiers, reconciled against the PAM
      approvals. Any account reaching tier 0 that is not in the PAM record is a finding regardless of whether
      it is malicious.
  (4) THE PAYLOAD PROFILE — the distribution of commands actually executed inside remote sessions per source,
      so that "this jump host runs three known scripts" can be distinguished from "this jump host ran
      `hostname` and then `net use \\DC\C$`."

  IMMEDIATE FLAGS (act on these before the baseline completes):
  Do not wait for the 30 days to finish. Escalate these on sight from day one, because none of them require a
  baseline to interpret:
  (1) A CLEARTEXT PASSWORD ON THE COMMAND LINE. `winrs ... -p:<password>` puts a credential in 4688/EID 1 in
      plaintext. Administrators using WinRM properly use Kerberos and their current context; typing -u and -p is
      what someone does when they are wielding a credential that is not theirs. This is the single strongest
      immediate flag and it was exactly what the source intrusion looked like.
  (2) ANY WinRM SESSION TERMINATING ON A DOMAIN CONTROLLER OR TIER-0 ASSET from a source outside the enumerated
      jump-host set.
  (3) A WORKSTATION INITIATING WinRM. Workstation-to-anything WinRM is almost never legitimate; administration
      flows from jump hosts. Workstation-to-workstation is rarer still.
  (4) wsmprovhost.exe SPAWNING A CHILD IT SHOULD NOT — cmd.exe, powershell.exe with encoded commands, reg.exe,
      rundll32.exe, net.exe, whoami.exe, certutil.exe, bitsadmin.exe, or any binary from %TEMP% or
      C:\Windows\Temp.
  (5) WinRM SERVICE FIRST-ENABLEMENT. Event 7040/7045 or a `winrm quickconfig` / `Enable-PSRemoting` on a host
      where the service was previously disabled. Turning it on is a prerequisite step, and it is loud.
  (6) A NEW LISTENER ON A NON-STANDARD PORT, or `TrustedHosts` being set to `*`.
  (7) WinRM FOLLOWED WITHIN MINUTES BY SMB ADMIN-SHARE ACCESS to the same destination from the same account —
      the two-protocol pattern in the source report.

  PLATFORM: Windows (domain-joined estate; telemetry lives on both source and destination hosts, and the hunt
  is only meaningful when both are collected).

  SOURCE: Deception.Pro, "[Op Report] From ClickFix SpaceX1337 to Hands-on-Keyboard AD Attack" (2026-08-10).
  After recovering seeded service-account and domain-admin credentials from LDAP description/info attributes and
  the GPP trail, the operator moved to the domain controller using two protocols in the same phase:

    net use \\<DC_NAME>\IPC$    /user:<domain>\<domain_admin> <pw>
    net use \\<DC_NAME>\ADMIN$  /user:<domain>\<domain_admin> <pw>
    net use \\<DC_NAME>\C$      /user:<domain>\<domain_admin> <pw>
    net use Z: \\<DC_NAME>\sysvol /user:<domain>\<domain_admin> <pw>

    winrs -r:DC-US-2.<domain> -u:<domain>\<domain_admin> -p:<pw> hostname

  That `winrs` line is the entire technique. A signed in-box Windows binary, a legitimate management protocol
  enabled by default on Windows Server, a valid domain-admin credential, and a benign-looking command
  (`hostname`) used to confirm the credential works before doing anything expensive.

  WHY THIS IS AN EMBER AND NOT A FLAME. Walking the rubric honestly:
  - Flames rejected. There is no distinguishing artifact. The binary is signed and in-box, the port is the
    documented management port, the destination is a server that is supposed to accept WinRM, and the credential
    is valid. `winrs -r:DC hostname` executed by an administrator and by an intruder produce byte-identical
    telemetry. Any Flames hunt written against WinRM alone reduces to "alert on WinRM," which in a managed
    estate means alerting on Configuration Manager, on monitoring agents, and on every administrator, every day.
    The one exception — the cleartext `-p:` argument — is carved out as an immediate flag above precisely
    because it does not need the baseline.
  - Alchemy rejected. This is a graph-membership problem, not a statistical one. The question is binary — has
    this (source, account, destination) triple ever been seen before? — and it is answerable with a set
    difference over a 30-day window. Reaching for anomaly scoring here adds tuning burden and opacity to a
    question that a lookup table answers exactly. If the estate is large enough that the edge set never
    stabilises, revisit; in most estates the initiator inventory is under fifty hosts.
  - Embers selected. Multiple triggers apply at once: the technique abuses a legitimate remote-management
    service (T1021 family) where malicious use is indistinguishable from admin use; the source report's own
    detection guidance amounts to "watch for unusual WinRM"; and the hunt cannot fire on volume, timing, or
    destination without first knowing what normal looks like for each of those.

  THE TELEMETRY, and its awkward parts:
  - Event 91 in Microsoft-Windows-WinRM/Operational is the canonical server-side record of an incoming shell.
    It is NOT collected by default in most estates — the WinRM operational channel is frequently missing from
    the forwarded-events subscription. Confirming collection is step zero of this baseline, and discovering the
    channel is not collected is itself a worthwhile finding.
  - Correlating WinRM Event 6 with Event 91 within a one-minute window is the documented pairing for identifying
    a genuine remote shell rather than a transient WS-Man query.
  - wsmprovhost.exe on the destination is the process that hosts the remote session. Its command line is
    `C:\Windows\system32\wsmprovhost.exe -Embedding` and is uninformative — the value is entirely in its
    CHILDREN and in the 4104 script blocks executed inside it.
  - PowerShell Remoting (Enter-PSSession, Invoke-Command) and winrs both ride WinRM. Baseline them together;
    they are the same edge in the graph even though the source-side artifacts differ.
  - WS-Management can also be driven through COM without touching winrs.exe or the PowerShell cmdlets, which is
    why the destination-side Event 91 and wsmprovhost telemetry matter more than source-side process creation.

  FIELDS TO COLLECT PER OBSERVATION, for the edge allowlist:

    timestamp, source_host, source_ip, initiating_account, initiating_process_image,
    destination_host, destination_role, destination_port (5985/5986), auth_mechanism (Kerberos/NTLM/Negotiate),
    winrm_event_id (6/91/169), destination_logon_id, wsmprovhost_children (image + full command line),
    scriptblock_text_hash, session_duration, bytes_transferred

  AUTH MECHANISM IS WORTH ISOLATING. Legitimate domain WinRM administration uses Kerberos. NTLM over WinRM to a
  domain-joined destination usually means the client connected by IP rather than by SPN — which is what tooling
  does, and what an operator working from a beacon does. It is not conclusive, but it is a cheap axis and it
  belongs in the baseline from the start.

  VALIDATION: once the 30 days are collected, run the set difference for a known-good week and confirm the
  novel-edge count settles into single digits per day. If it does not, the collection window was too short or a
  scheduled job cycle was missed — extend rather than loosening the criteria. Then, with permission, have a
  red-team or an administrator initiate WinRM from a host outside the initiator inventory and confirm it
  surfaces the same day.

  CROSS-REF: this baseline enables [[H266]] (registry-hive credential theft — the credentials the operator was
  carrying over WinRM came from that step) and [[H267]] (the SYSVOL/GPP and LDAP sweep that produced them).
  T1021.002 (SMB/Admin Shares — the `net use` half of the same lateral movement; baseline both together, since
  the source report shows the operator using them minutes apart) and T1047 (WMI) are the alternative lateral
  paths the same operator would reach for if WinRM were closed, and belong in the same graph.
  T1078.002 (Domain Accounts) is what is actually being wielded.

# B037

The lateral movement in this intrusion was one line:

```
winrs -r:DC-US-2.<domain> -u:<domain>\<domain_admin> -p:<pw> hostname
```

A signed, in-box Microsoft binary. The documented Windows management protocol, on its documented port, enabled by default on Windows Server. A valid domain-admin credential. And `hostname` as the payload — because the operator was checking the credential worked before spending it on anything expensive.

There is no artifact in that line that distinguishes it from an administrator. The binary is right, the port is right, the destination is a server that is *supposed* to accept WinRM, and the credential authenticates cleanly. Every detection you could write against it fires on Configuration Manager, on your monitoring agents, and on your own admins, every day.

What makes it visible is not the command. It is that this source host had never initiated a WinRM session before, and that nothing in the estate normally reaches a domain controller this way. That is a statement about your environment, and you cannot make it until you have measured it.

## Why

- **The technique has no signature, only a context — so the baseline *is* the detection.** WinRM is not a tool an adversary brings; it is a service Microsoft ships enabled on every Windows Server. There is no unsigned binary, no anomalous port, no unusual parent process, no encoded payload. The only thing that separates the intruder's session from the administrator's is who initiated it, from where, and to what — and each of those is a comparison against history, not a property of the event. Skipping straight to a Flames hunt here produces a rule that alerts on legitimate administration and gets muted within a week.

- **The initiator set is far smaller than people expect, and its smallness is the whole return on the work.** Most estates assume WinRM is "used everywhere." When actually measured over 30 days, the set of hosts that have ever *initiated* a WinRM session is usually under fifty: a few jump hosts, some admin workstations, a management server, and the config-management and monitoring agents. Once that list exists, "a host not on this list initiated WinRM" becomes a high-fidelity, near-zero-noise trigger — and the source intrusion, where the initiator was a compromised user workstation, fires on it immediately.

- **The cleartext password is available on day one and does not need the baseline at all.** `-u:<domain>\<domain_admin> -p:<pw>` writes a domain-admin credential into 4688 and Sysmon Event ID 1 in plaintext. Administrators using WinRM properly ride their existing Kerberos context; explicitly supplying credentials on the command line is what someone does when wielding a credential that is not theirs. That is worth deploying as a standalone rule the moment this baseline starts, and it costs nothing — which is why it is carved out as an immediate flag rather than buried in the 30-day deliverable.

- **You will probably discover the telemetry is not being collected, and that is a finding in itself.** `Microsoft-Windows-WinRM/Operational` Event 91 is the canonical server-side record of an incoming remote shell, and in a large fraction of estates that channel is simply absent from the forwarded-events subscription. Starting this baseline forces the question "can we even see WinRM sessions?" — and the answer is frequently no. Establishing that collection is a prerequisite for every future WinRM detection anyone in the organisation will ever try to write.

- **`wsmprovhost.exe` is where the baseline pays off twice.** The remote session host process itself is uninformative — its command line is always `-Embedding`. But its *children* are the payload, and a payload profile per source is the second half of the deliverable. Once you know that a given jump host runs three known scripts through WinRM, `wsmprovhost.exe` spawning `reg.exe`, `net.exe`, or a binary from `%TEMP%` on that same host becomes obvious rather than merely present. That is the transition from "WinRM happened" to "something is wrong," and it requires the profile to exist first.

- **The two-protocol pattern in this intrusion argues for baselining SMB alongside it.** The operator used `net use` against `IPC$`, `ADMIN$`, `C$` and `sysvol` *and* `winrs`, against the same domain controller, with the same credential, minutes apart. Treating WinRM and SMB admin-share access as one lateral-movement graph rather than two separate detections roughly doubles the signal for the same collection effort, and it means closing one protocol does not blind the hunt — the operator simply appears on the other edge.

- **This baseline is what makes the rest of the week's Flames hunts operational.** [[H266]] catches the credential theft and [[H267]] catches the credential discovery, but both of those describe how the operator *got* the domain-admin password. This is where they spent it. Without an edge graph, the spending step is invisible — and it is the step that separates one compromised workstation from a compromised domain.
