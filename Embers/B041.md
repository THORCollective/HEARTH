# B041

The attacker in the source intrusion did not evade detection — they arranged to be indistinguishable
from IT. They installed a real, Zoho-signed ManageEngine UEMS agent, supplied their own root CAs at
install time so the endpoint would trust their Endpoint Central server, and from that point forward did
their domain enumeration, patch scanning and interactive remote control entirely through vendor-signed
binaries. There is no malicious file to find. Process telemetry shows a management agent managing a
host, which is what a management agent is for.

That is why this is an Ember rather than a Flames. A rule that fires on "ManageEngine agent installed"
alerts on every legitimate install in a shop that uses ManageEngine, and fires on nothing at all in a
shop that does not — but the technique works with whichever product the attacker chooses. The signal
that survives that freedom of choice is a set-membership question: *does this host run an agent we
deployed, pointed at a server we own, trusting a CA we issued?* Answering it requires the set to exist
first, and building that set is the deliverable.

The single most valuable field is the configured management server. Attackers can match the product,
the path, the service name and the signature — all of that is inherited from the genuine vendor package.
What they cannot do is point the agent at your server. In the source intrusion the value was a bare IP
with the single-label hostname `win-n3u83ajbeeh`, and the agent leaked that name into victim DNS logs.

## Why

- **Product and signature are attacker-controlled; the server value is not.** Every attribute you might
  normally pivot on — publisher, signature validity, install path, service name — comes free with the
  legitimate installer. The management server is the one field that must differ from yours for the
  attack to work at all, which makes it the only durable discriminator and the reason this baseline is
  worth the collection effort.
- **The allowlist is small, slow-changing, and cheap to maintain.** Unlike DLL-load or process baselines
  that must model a long tail of legitimate variation, most organizations have fewer than ten sanctioned
  remote-access products and a handful of management servers. The profile converges in days, not months,
  and a monthly refresh is sufficient. Baselines this bounded are the ones that actually get built.
- **The root-store inventory catches the enabling step even when the agent is unfamiliar.** You cannot
  enumerate every RMM product an attacker might choose, but you can enumerate every trusted root CA on
  every host. An unexplained root CA — especially one installed recently, by a non-administrative
  process, with a subject impersonating a vendor — is a strong signal regardless of which product it was
  installed to support.
- **This baseline directly enables H279 and is what makes its query interpretable.** H279 hunts the
  msiexec install with `SERVER_ROOT_CRT=` / `DS_ROOT_CRT=` properties. That hunt returns a verdict only
  if you can say whether the resulting server value is yours. Without the allowlist, every hit requires a
  manual investigation; with it, the triage is a lookup.
- **It closes the response gap that lets this intrusion survive remediation.** Because the malware and
  the persistence live in different places, an incident scoped to the RAT leaves the agent installed.
  An inventory that flags agents pointed at unapproved servers turns that from a judgement call during a
  stressful investigation into a standing report.
- **The immediate flags return value on day one, before the 30 days elapse.** A baseline hunt that
  delivers nothing for a month is a baseline hunt that gets abandoned in week two. Several of the flags
  below are actionable on sight.

## Notes — collection specification

**COLLECTION WINDOW: 30 days**, refreshed monthly. Shorter than most baselines because the population is
small and slow-changing. Run the first pass as a point-in-time sweep (inventory + registry + root store)
on day one — that alone produces a usable draft allowlist — then use the 30 days to catch agents that
only appear on infrequently-connected hosts and to observe each agent's real network destinations.

**FIELDS TO COLLECT PER AGENT INSTALLATION:** hostname, host role/OU, product name, vendor, version,
install path, install date, installing account, installation method (msiexec command line if available),
service names registered, service binary paths, service account, signature status and signer of each
service binary, configured management server hostname, configured server IP, configured server port,
configuration source (registry key or file path the value came from), observed network destinations for
the agent process, first-seen and last-seen.

**FIELDS TO COLLECT PER TRUSTED ROOT CA:** hostname, certificate subject, issuer, thumbprint, serial,
validity dates, store location (machine vs user, Root vs third-party), install date where obtainable,
and — where the telemetry supports it — the process that wrote the registry value.

**DELIVERABLE — three artifacts, refreshed monthly:**

1. **THE SANCTIONED AGENT REGISTRY.** For each approved product: the service names, expected install
   paths, expected signer, and the specific management servers (hostname, IP, port) it is permitted to
   contact. This is the thing every alert is evaluated against.
2. **THE UNSANCTIONED AGENT REPORT.** Every host running an agent that is not in artifact 1, or running
   a sanctioned agent pointed at a server that is not in artifact 1. In a healthy estate this list should
   be short and every entry should be nameable — MSP-managed subsets, an acquisition, a documented
   exception. Its contents are the standing risk register for the technique.
3. **THE ROOT CA DIFF.** Per-host trusted root CAs minus your known-issued and Microsoft-shipped sets.
   This catches the trust-anchor step even for a product you never thought to inventory.

**IMMEDIATE FLAGS — escalate on sight, no baseline required:**

1. **An `msiexec` command line carrying a root-certificate property** (`SERVER_ROOT_CRT=`,
   `DS_ROOT_CRT=`, or a product equivalent) where the certificate path is user-writable. This is H279's
   core query and needs no history to interpret.
2. **A root CA written to the machine store by a script host or a non-installer process.** `wscript.exe`,
   `powershell.exe` or a hollowed service process writing under
   `HKLM\SOFTWARE\Microsoft\SystemCertificates\Root\Certificates\` has no benign explanation in a
   managed estate.
3. **A sanctioned RMM agent configured to a server that resolves to a raw IP, a single-label hostname, or
   an address outside your netblocks.** The source intrusion's `win-n3u83ajbeeh` leaked straight into
   victim DNS logs.
4. **An RMM/UEM agent installed from `C:\Users\Public\`, `%TEMP%`, `%APPDATA%`, or a mounted
   removable/ISO volume**, rather than from a deployment cache or share.
5. **A second instance of an RMM product on a host that already has one**, especially with a different
   configured server — the daisy-chaining pattern.
6. **An RMM agent installed on a host with no helpdesk ticket, change record, or deployment-tool history
   for it.** Correlating the install timestamp against your change system is the cheapest verdict
   available.

**PLATFORM: Windows** (workstations and servers both — the source intrusion began on a domain-joined
workstation, but rogue enrollment is at least as valuable to an attacker on a server).

**WHY THIS IS AN EMBER AND NOT A FLAME.** Multiple Embers triggers apply simultaneously. The technique
abuses legitimate, signed software where malicious use is structurally identical to administrative use.
The published detection guidance for RMM abuse reduces to "look for unusual remote-access tools," which
is unactionable without knowing which tools are usual. And no rule can fire without first knowing the
environment's approved agent-and-server set — the alerting condition is defined by reference to a
baseline that must already exist. **Alchemy was considered and rejected:** rarity-scoring agent
installations across the fleet is technically feasible, but the question here is cleanly binary — is
this product-and-server pair on the approved list? — and a set-membership lookup is both exact and
explainable to an analyst, where statistical scoring would add tuning surface and opacity without
improving the answer. **Flames was rejected** because the specific IOCs from the source report
(ManageEngine, `DCFAFilter.inf`, `win-n3u83ajbeeh`) have a shelf life measured in weeks — the attacker
picks whichever management platform they like — while H279 already covers the one durable behavioral
artifact, the certificate-bearing install command line.

**CROSS-REF:** [[H279]] is the Flames hunt this baseline enables — it hunts the msiexec install that
plants the root CA, and depends on this baseline to decide whether the resulting server is yours.
