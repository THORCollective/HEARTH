false_positive_notes: |
  Third-party scripts change constantly and legitimately, which is the central difficulty of this baseline. Tag managers deploy new containers, A/B testing platforms serve different variants to different visitors by design, advertising and analytics vendors push updates without notice, and consent-management platforms rewrite what loads based on each visitor choice. A naive content-hash comparison will alert continuously.

  Experimentation platforms are the hardest case and the one OPTIMJACK involved. Their entire function is to inject arbitrary JavaScript that differs per visitor, per variant and per session, so content-based change detection against them is close to meaningless. For these the baseline has to move up a level - who is permitted to edit the custom JavaScript field, what the change-approval path is, and what the vendor audit log says - rather than what the script contained on any given load.

  Legitimate script content is often minified, versioned and cache-busted, so URLs and bodies change on every deploy without anything being wrong. Normalise on origin and vendor identity first and treat content hashes as a signal only for scripts that are genuinely pinned.

  Visitor-side variation means crawls under-represent reality. A headless crawl from one IP in one region with no consent cookies will load a different script set than a real visitor in another jurisdiction. Combine crawl data with Content Security Policy reports from real sessions, or the baseline will describe a page nobody is served.

  Unit 42's article is a short analysis piece and publishes no indicators - no hashes, no attacker domains, no code. There is nothing to sweep for, which is precisely why the deliverable here is an inventory and a segmentation decision rather than a detection rule. Any hunt built on this report that claims specific indicators has invented them.

  Unit 42 also does not describe the vulnerability in the Optimizely platform, how the actor exploited it, or how the accounts were reached. The report states the flaw was patched and the injected code removed and affected accounts secured early on November 17, and says nothing about the mechanism, so do not infer an access path when scoping.
notes: |
  Collection window - 30 days minimum. Third-party tag estates drift weekly as marketing campaigns start and stop, so a single crawl captures a moment rather than a norm. Thirty days of daily crawls plus continuous Content Security Policy reporting is enough to separate routine churn from a step change.

  Fields to collect, per page, per crawl.

  - Page identity and sensitivity class - URL, template, and whether the page collects credentials, payment card data or personal data. Unit 42's remediation guidance targets authentication and checkout pages specifically, so classify those first.
  - Script inventory - every loaded script URL, its origin, the vendor it belongs to, whether it was loaded directly in the markup or injected by another script, and its position in the load chain. Second- and third-order loads matter most: a tag manager that loads an experimentation platform that loads something else is three vendors deep and usually unmapped.
  - Integrity posture - whether each script tag carries a Subresource Integrity hash, and whether the vendor supports one at all. Scripts that cannot be pinned, which includes most tag managers and experimentation platforms by design, belong on a separate list because content-based detection will never work for them.
  - Content fingerprint - a hash of each response body for scripts that are genuinely pinned or versioned, plus size and a normalised structural fingerprint for those that are not.
  - Capability - whether the script can read form fields, access the clipboard, write cookies, or inject further scripts. This is the field that converts an inventory into a risk ranking, and it is what Unit 42's point about third-party scripts having the same privileges as your own developers actually means in practice.
  - Change control - for each vendor platform, who holds administrative access, who can edit a custom JavaScript or custom code field, whether changes require approval, and whether the vendor's audit log is exported anywhere the organisation controls.
  - Vendor contact and disclosure path - where a vendor compromise notification would arrive and who reads it. OPTIMJACK's customers learned from the vendor, not from their own telemetry.

  Deliverable. Four artefacts.

  1. A page-to-script map for every sensitive page, ranked by script capability. The immediate output is usually a surprise: the number of distinct third parties executing on a checkout or login page is routinely higher than anyone expects, and most of them are there for reasons nobody can still articulate.
  2. A removal list. Unit 42's first segmentation step is to strip all non-essential marketing, experimentation and analytics tags from authentication and checkout pages. The baseline turns that from a principle into a specific, reviewable list of tags to remove from specific pages.
  3. An integrity and isolation plan. For scripts that remain, record which can be pinned with Subresource Integrity and which cannot, and for the rest apply Unit 42's second step - place payment collection inside hardened, cross-origin iframes so a compromised vendor script cannot reach the fields. A Content Security Policy with an explicit script-src allowlist, built from the observed baseline, is the enforcement mechanism for both.
  4. A per-vendor administrative access review, with the custom-JavaScript-capable platforms listed first. These are the platforms where a vendor-side compromise or a stolen customer-side credential results in arbitrary code on your pages.

  Flag immediately, without waiting for the baseline to complete.

  - Any script origin on a sensitive page that is not in the approved vendor list, including a subdomain of an approved vendor that has not been seen before.
  - Any new third-party script appearing on an authentication or payment page at all. On those pages the correct baseline is close to empty, so any addition is a change worth a question.
  - Any change to a custom JavaScript or custom code field in an experimentation platform, tag manager or content management system, by any principal, at any time. This is the field OPTIMJACK was injected into, and it is the one place where content-based monitoring is hopeless and change-event monitoring is cheap.
  - Any Content Security Policy violation report naming a script origin that is not in the allowlist.
  - Any script tag on a sensitive page that previously carried a Subresource Integrity hash and now does not.
  - Any administrative access grant on a platform with script-injection capability.

  On what this baseline can and cannot see. The malicious code in OPTIMJACK ran in visitors' browsers and was served from the vendor's own CDN under the vendor's own certificate, so there was no anomalous origin to detect, no certificate error, and no server-side artefact on the customer's infrastructure. Enterprise endpoint and network telemetry would not have shown it, because the affected endpoints belonged to customers' website visitors rather than to the organisation. That is why the control is inventory and segmentation rather than detection: the realistic goal is to ensure that when a vendor script is compromised, it cannot reach a password field or a card number, and that the list of pages where it could is known in advance.

  Post-incident actions Unit 42 recommends for organisations that were affected, which also validate the baseline. Audit all project modifications made while the malicious code was available, double-check all code that may have been altered during that period, and treat exposed payment data as potentially compromised, including payment card details entered into checkout forms on affected pages. An organisation that cannot answer "which of our pages ran this vendor's script, and were any of them collecting card data" has established the gap this baseline fills.

  Cross-reference. This baseline is the inventory layer under the client-side skimming hunts already in the corpus - H045, H380 and H423 cover payment-card skimming and wallet-address swapping from the detection side, and H469 covers a browser extension that reaches page content through broad host permissions, which is the same privilege problem arriving through the browser rather than through the page. None of those can be scoped without knowing which third parties execute where, which is what this produces.

  Scope note on existing coverage. A grep of every hunt body for `Optimizely` returns one unrelated match on a substring, and a grep for `Subresource Integrity` and `third-party script` returns only H469. No existing HEARTH hunt baselines the third-party script estate. This is deliberately framed as an Embers baseline rather than a Flames hunt because the source report publishes no indicators, the malicious content was served from a legitimate origin under a valid certificate, and the actionable output is an inventory and a segmentation decision rather than a query that fires.

# B077

On 16 November 2026 a threat actor found a flaw in Optimizely's Web Experimentation platform and used it to write JavaScript into customer accounts — specifically into the custom Project JavaScript field, the one that exists so customers can run arbitrary code on their own pages.

At least 178 organisations then served that code to their visitors. Media brands, technology companies, financial services firms. The script swapped cryptocurrency wallet addresses as visitors copied them, harvested card details out of checkout forms, and tried to push the Coruna and DarkSword exploit kits at iPhones and iPads.

None of those 178 organisations was breached in any conventional sense. The tampered snippets came from the vendor's legitimate CDN, under the vendor's own certificate, through a tag those organisations had deliberately installed. There was no bad origin to block, no certificate warning, no server-side artefact, and nothing in enterprise endpoint telemetry — because the endpoints that ran the code belonged to the visitors.

Unit 42's conclusion is the uncomfortable one: if a third-party script executes on your page, it effectively has the same privileges as your own developers. Which means the practical question is not how to detect this, but which of your pages currently give that privilege away, and whether any of them is a login form or a checkout.

Almost nobody can answer that from memory. Hence the inventory.

## Why

- Detection was not available to the victims and will not be next time. The code arrived from a trusted origin under a valid certificate on a tag the organisation chose to install. There is no anomalous signal to alert on, so the only effective controls are knowing what loads where and ensuring it cannot reach sensitive inputs.
- Unit 42's segmentation advice cannot be executed without this baseline. "Strip all non-essential marketing, experimentation and analytics tags from authentication and checkout pages" presumes someone knows what currently loads on those pages. Turning that sentence into a specific removal list is the whole deliverable.
- The script count on sensitive pages is reliably higher than anyone expects. Second- and third-order loads — a tag manager that loads an experimentation platform that loads something else — mean the real vendor list is longer than the one in the markup, and the first crawl is usually the moment that becomes visible.
- Experimentation platforms are the one place where content monitoring is futile and change monitoring is trivial. Their job is to serve different code per visitor, so hashing is pointless; but somebody editing the custom JavaScript field is a single discrete event, and it is exactly the event OPTIMJACK was.
- The blast radius is customers rather than staff, which changes the obligation. Exposed card details and swapped wallet addresses land on visitors, so the response involves disclosure and payment-data assumptions rather than endpoint remediation — and Unit 42's guidance to treat exposed payment data as potentially compromised requires knowing which pages were in scope.
- It is the inventory layer the existing skimming hunts are missing. HEARTH already hunts card skimming and wallet swapping from the detection side; none of those hunts can be scoped to the right pages without a map of which third parties execute where.
