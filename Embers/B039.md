id: B039
category: Embers
title: Baseline of hidden and system-attributed directories under user-writable roots — who owns them, who made them, and when
hypothesis: >-
  `attrib +h +s` against a directory is a one-line evasion that works because nobody knows what is already hidden
  on their estate. Installers, updaters, backup agents, and DRM all hide their own working directories under
  `C:\ProgramData` and `%APPDATA%`, which means a rule that alerts on the hide operation drowns and a rule that
  allowlists vendor paths decays as soon as software inventory changes. Build a 30-day inventory of every
  directory carrying the Hidden and System attributes under `C:\ProgramData\`, `C:\Users\Public\`, `%APPDATA%`,
  `%LOCALAPPDATA%`, `%TEMP%` and `C:\Windows\Temp\` — the path, the owning product, the process that created it,
  the process that hid it, the fleet prevalence, and the name's entropy — so that the next hidden directory an
  intrusion creates is visible as a directory nobody in the estate has ever seen before, rather than as one more
  attrib event in a stream of them.

required_data_sources:
  - Live filesystem enumeration via the endpoint agent's live-response or query interface (Defender XDR live response, osquery `file` table with a path glob, Velociraptor Windows.Search.FileFinder) — this is the primary source and it is a POINT-IN-TIME SURVEY, not an event stream. The baseline is fundamentally a directory listing, not a log query
  - Sysmon Event ID 1 / Windows Security 4688 — every `attrib.exe` execution across the estate for 30 days, with CommandLine, ParentImage, ParentCommandLine, User and IntegrityLevel. This is what attributes each hidden directory to a creating process rather than leaving it as an anonymous path
  - PowerShell Script Block Logging (EID 4104) — the `Attributes = 'Hidden,System'` and `Set-ItemProperty ... Attributes` variants that create the same result with no `attrib.exe` process. Without this the process-attribution half of the inventory has a hole in it
  - Sysmon Event ID 11 (FileCreate) / DeviceFileEvents — directory and file creation under the user-writable roots, giving the directory's true creation time and the writing process, which is how directory AGE becomes a usable feature
  - Defender XDR DeviceProcessEvents and DeviceFileEvents — the Defender-native equivalents of the two above for estates without Sysmon
  - Software inventory / SCCM / Intune application catalogue — the authoritative list of installed products and their vendor install paths. Without it the inventory has paths but no owners, and an unowned path is exactly what needs identifying
  - Digital signature and file metadata for executables found inside each hidden directory — signer, OriginalFileName, Company. A hidden directory containing an unsigned binary is a different object from one containing a signed vendor updater
  - Fleet-wide asset list with host role — the prevalence denominator. "This directory name exists on 1 of 4,000 hosts" is the single most useful field the inventory produces and it cannot be computed without knowing the fleet size
false_positive_notes: |
  This baseline exists BECAUSE the benign population is large. Expect the initial survey to return hundreds of
  distinct hidden directories per estate, from:
  - Application installers and updaters hiding working, cache, or rollback directories under `C:\ProgramData\`.
    This is the dominant population and most of it is legitimate.
  - Backup, imaging, and endpoint-management agents with hidden state directories.
  - DRM, anti-cheat, and game launchers, which hide aggressively by design.
  - Explorer folder customisation, which sets `+s +h` on `desktop.ini` files. These are files, not directories —
    scope the survey to directories and most of this disappears.
  - Windows' own hidden system directories (`$Recycle.Bin`, `System Volume Information`, `ProgramData\Microsoft\`,
    WinSxS staging). Enumerate and exclude these once, by exact path, at the start.
  - Roaming-profile and folder-redirection artifacts.
  The point of the baseline is that none of these need to be judged individually. Each one is either (a) present
  on many hosts with a consistent name and an identifiable owning product — resolved, and it stays resolved, or
  (b) present on one host, created recently, named without a product string, and containing something unsigned —
  which is the entire output of the hunt. Do not attempt to write a filter list for the benign population; that
  is precisely the approach this Ember replaces, and it is why a pure Flames rule on `attrib +h +s` gets tuned
  into uselessness within a month.
notes: |
  PLATFORM: Windows. The Hidden+System attribute pair is a Windows filesystem concept; the dotfile convention on
  Linux/macOS is a different problem with a different baseline and is out of scope here.

  SOURCE: Microsoft Threat Intelligence, "TerminalFix campaign deploys a reverse tunnel through multistage
  intrusion" (2026-08-28). The campaign extracts its payload into `C:\ProgramData\f47f2a8c21c9df4e` and applies
  `attrib +h +s` to that directory, alongside DLL side-loading of `dui70.dll` by the legitimate signed
  `LockScreenContentServer.exe`, PNG steganography, AD reconnaissance, and a Python WebSocket reverse tunnel to
  `gitnow[.]dev`. Microsoft's own detection guidance for the campaign includes queries for the side-load, the
  ClickFix paste, and the C2 — but none for the hidden-directory step, which is the gap this Ember and its
  paired Flames hunt [[H272]] fill.

  COLLECTION WINDOW: 30 days for the process-attribution half (attrib executions and file creations). The
  filesystem survey itself is a point-in-time snapshot and should be run at least twice — once at the start and
  once at the end of the window — so that directories which appeared mid-window are visible as new. In estates
  with a monthly patch or deployment cycle, extend to 45 days so that at least one full cycle is inside the
  window; vendor updaters create and hide directories on their own schedules and a 30-day window that misses the
  cycle will report a burst of "new" directories in month two.

  FIELDS TO COLLECT PER HIDDEN DIRECTORY: full_path, host, first_seen, directory_created_time,
  attributes (H / S / both), directory_owner_sid, creating_process_image, creating_process_signer,
  hiding_process_image, hiding_process_commandline, hiding_process_parent, hiding_user, file_count,
  contained_executables (name, SHA256, signer, signature_status, OriginalFileName), total_size,
  fleet_prevalence_count, fleet_prevalence_percent, name_entropy, name_matches_installed_product (bool),
  path_root (ProgramData / Public / AppData / LocalAppData / Temp).

  NAME_ENTROPY AND FLEET_PREVALENCE ARE THE TWO FIELDS THAT DO THE WORK, and both are cheap. `f47f2a8c21c9df4e`
  is sixteen hex characters with no product string in it; `C:\ProgramData\Adobe` is not. Shannon entropy over the
  directory name, plus a simple "is this name a substring of any installed product name" check, separates the two
  populations with almost no tuning. Prevalence then does the rest: a vendor's hidden directory appears on
  hundreds of hosts under an identical name, an intrusion's appears on one, under a name generated per victim.

  DELIVERABLES — three artifacts, generated from the survey and refreshed monthly:
  (1) THE HIDDEN-DIRECTORY INVENTORY. Every Hidden+System directory under the in-scope roots, keyed by
      (normalised path pattern, owning product), with prevalence counts and first/last seen. This is the
      reference object; everything else is a query against it.
  (2) THE OWNERSHIP MAP. Each inventory entry resolved to an installed product from the software inventory, or
      explicitly marked UNATTRIBUTED. In a healthy estate the unattributed list should be short enough to read
      and every entry on it should be nameable by someone. That list is the standing risk register for this
      technique, and its length is a fair measure of how well this hunt is working.
  (3) THE HIDE-OPERATION PROFILE. From 30 days of process events: which processes legitimately invoke
      `attrib +h +s` or the PowerShell attribute equivalent in this estate, with what parents, as which users,
      against which path roots. This is what lets the paired Flames hunt key on lineage rather than on a decaying
      allowlist of vendor paths.

  IMMEDIATE FLAGS — escalate on sight, from day one, without waiting for the 30-day window to close:
  (1) A HIDDEN DIRECTORY CONTAINING AN UNSIGNED OR INVALIDLY-SIGNED EXECUTABLE OR DLL. This is the single
      highest-yield query in the hunt and it needs no baseline to interpret.
  (2) A HIDDEN DIRECTORY WHOSE NAME IS A HIGH-ENTROPY OR PURELY HEXADECIMAL STRING and which matches no
      installed product. `C:\ProgramData\f47f2a8c21c9df4e` is the source campaign; the shape generalises.
  (3) `attrib +h +s` INVOKED WITH AN INTERACTIVE SHELL ANCESTRY — `WindowsTerminal.exe`, `wt.exe`,
      `powershell.exe`, `cmd.exe`, `wscript.exe`, `mshta.exe` — rather than an installer or a deployment agent.
  (4) A DIRECTORY HIDDEN WITHIN MINUTES OF ITS OWN CREATION. Legitimate software hides directories it has owned
      for months. Join the attrib event to the directory creation time; a delta measured in minutes is the
      campaign pattern.
  (5) A HIDDEN DIRECTORY PRESENT ON EXACTLY ONE HOST in a fleet where every other hidden directory appears on
      dozens. Prevalence of one is not proof, but it is the correct sort order for the review queue.
  (6) A SIGNED MICROSOFT BINARY RUNNING FROM INSIDE A HIDDEN USER-WRITABLE DIRECTORY —
      `LockScreenContentServer.exe` outside `C:\Windows\SystemApps` is the source campaign's exact case, and
      the general form (in-box binary relocated into a hidden staging folder) is a reliable side-loading tell.

  VALIDATION: after the first survey, run Atomic Red Team T1564.001 tests (notably "Hide a Directory" and
  "Create Windows System File with Attrib") on an instrumented host and confirm the created directory appears in
  the next survey AND that the `attrib.exe` execution appears in the hide-operation profile with the correct
  parent. If the directory shows up but the process does not, `attrib.exe` is being missed by the process
  telemetry — usually a Sysmon config that excludes it as noise. If the process shows up but the directory does
  not, the survey's path globs are not recursing far enough.

  CATEGORY: Embers. Flames rejected as the sole approach — the discrete-IOC hunt is real and is written as
  [[H272]], but on its own it inherits a false-positive population (installers hiding `ProgramData` folders)
  that can only be resolved by an inventory or by an allowlist that ages badly. Both rubric triggers apply: the
  technique abuses a legitimate, signed, in-box utility where malicious use is command-for-command identical to
  administrative use, and no rule can fire cleanly without knowing what is already hidden in the environment.
  Alchemy rejected — name entropy and fleet prevalence are scoreable, but the underlying question is
  set-membership ("has this directory name ever been seen in this estate, and does it belong to a known
  product") which returns an exact, explainable answer. Statistical scoring would add tuning surface and opacity
  without improving on a lookup. Entropy is used here to SORT the review queue, not to decide it.

  CROSS-REF: [[H272]] is the Flames hunt this baseline enables — it keys on `attrib +h +s` with interactive-shell
  ancestry, and deliverable (3) is what makes its lineage filter accurate. [[B038]] baselines per-application DLL
  module loads and is the natural next pivot, because the hidden directory in this campaign exists to hold a
  side-loading pair. T1036.005 (the relocated in-box binary that lives in the hidden directory), T1074.001
  (Local Data Staging — the same directories get reused to stage collected data before exfiltration, so this
  inventory serves both techniques).

# B039

`attrib +h +s C:\ProgramData\f47f2a8c21c9df4e` is one line in the middle of a nine-stage intrusion, and it is the one line that assumes something about you: that you do not know what is already hidden on your own machines.

That assumption is usually correct. Run a survey for Hidden+System directories under `ProgramData` and `AppData` across a few thousand endpoints and you will get hundreds of hits, nearly all of them legitimate — installers, updaters, backup agents, anti-cheat, DRM. Which is exactly why the straightforward detection fails. Alert on the hide operation and you drown. Allowlist the vendor paths and your list is wrong the next time procurement buys something.

The durable answer is an inventory. Not "is this directory hidden" — hundreds are — but "has this directory name ever existed in this estate before, does it belong to a product we installed, and did it appear ninety seconds after something wrote an unsigned DLL into it."

## Why

- **The benign population is large, real, and stable — which is the definition of a baseline problem.** Software hides its working directories for legitimate reasons and will keep doing so. Every one of those directories has the same three properties: it appears on many hosts, its name matches a product, and it has existed since installation. An intrusion's staging directory has none of them. That contrast is only visible against an inventory, and once the inventory exists it resolves the entire benign population permanently rather than one filter rule at a time.

- **Fleet prevalence is the strongest feature available and it costs a count.** A per-victim staging directory is, by construction, unique — the name is generated fresh for each target, and in the TerminalFix chain it is also displayed back to the user as a fake "Cloudflare ID," which confirms it is per-victim rather than per-campaign. So the directory appears on exactly one host out of the estate. No vendor artifact does that. Sorting the survey by prevalence ascending puts the intrusion at the top of the page with no model, no threshold, and no tuning.

- **Name entropy separates the two populations almost for free.** Product directories are named after products. Staging directories are named by a random generator, because the attacker needs uniqueness and does not need meaning. Shannon entropy over the directory name, plus a substring check against the installed-software catalogue, is a few lines of code and it splits the survey cleanly enough to make the unattributed list short enough for a human to read. It also survives IOC rotation completely — the next campaign's hex string is different, and it is still a hex string.

- **The hide-operation profile is what makes the paired Flames hunt precise instead of noisy.** [[H272]] keys on `attrib +h +s` with an interactive-shell ancestry. Whether that filter is accurate depends entirely on knowing which processes legitimately invoke attrib in this specific environment — and that varies enormously between an estate that deploys everything through Intune and one that lets users install their own tools. Thirty days of process events answers it definitively, and the answer is usually a short list. A baseline hunt that makes an existing rule sharper is doing more work than one that only produces a report.

- **Directory age converts a static survey into an incident timeline.** The filesystem snapshot tells you what is hidden; joining it to file-creation events tells you when the directory came into existence and what was written into it. Legitimate hiding happens at install time, once, months ago. The malicious case hides a directory it created ninety seconds earlier and into which it has just extracted a signed executable and an unsigned DLL. That delta is the difference between a finding and a false positive, and it requires no judgement to compute.

- **Three of the immediate flags work on day one, so this hunt is not thirty days of nothing.** An unsigned binary inside a hidden directory, a hexadecimal directory name matching no installed product, and an interactive shell invoking `attrib +h +s` are all interpretable without any history at all. A baseline hunt that returns nothing until the window closes gets quietly abandoned in week two; this one should return its first real finding in the first survey.

- **The same inventory covers the next technique over.** Hidden user-writable directories are not only where side-loading pairs live — they are where collected data gets staged before exfiltration, where downloaded tooling lands, and where output files from a file-watch C2 loop get written. The TerminalFix chain uses its directory for all of these. Building the inventory once for T1564.001 gives you the denominator for T1074.001 and for the ingress-tool-transfer hunts as well, which is a large fraction of the return on the collection effort.

- **HEARTH had no T1564.001 coverage at all** before this pair, despite artifact hiding appearing in essentially every commodity intrusion chain as the step between staging and execution.
