id: B066
category: Embers
title: "Baseline of the AI coding-agent credential stores — which tools exist on which hosts, which process legitimately reads each store, and how often"
hypothesis: >-
  A hunt for one process sweeping several AI coding-agent credential stores is only as good as the estate's knowledge of what reads them normally. On an engineering workstation the answer is not obvious in advance: these tools are installed by developers rather than by deployment, several of them ship their own updaters and language servers, file-sync clients roam the whole user profile, and provisioning scripts legitimately write the same files that collection reads. Without a per-host record of which AI tools exist, which signed images touch each store and at what rhythm, every read looks equally suspicious and the read audit that makes the collection step visible will be turned off for noise. Collecting that record first turns the signal from "a credential file was read" into "a process that has never read this store, and does not own it, read three of them in a minute".

false_positive_notes: |
  This is a collection exercise, not a detection, so the usual false-positive framing is inverted: almost everything collected during the window is legitimate, and the deliverable is the description of that legitimate activity. Resist the urge to triage individual reads during collection.
  The baseline will be dominated by each tool reading its own store, which is the point. Record it as the owning-reader mapping rather than discarding it; the mapping is what lets the companion hunt distinguish a vendor-crossing sweep from ordinary use.
  Endpoint security, backup and indexing agents will appear against every store on every host. These belong in the allowlist as signed image paths, and they are the single largest noise reduction available, so capture their exact image paths rather than process names.
  Provisioning and onboarding bursts will look like collection. A new-machine setup script or dotfile manager can touch many stores in one run. Tag these windows using the joiner and device-refresh dates gathered above, and exclude them from the steady-state rhythm figures rather than from the record itself.
  Do not let the baseline window hide an infection already in progress. The immediate flags below are to be acted on during collection, not after it. A stealer running on day three of a thirty-day window would otherwise be averaged into normal.
  A host where these paths do not exist contributes a valid and useful observation. Record the absence; it defines the scope of the companion hunt and makes the first-ever appearance of such a path on a non-engineering host a finding in itself.
notes: |
  Platform - Windows developer and engineering workstations. The store set is the `aisessions` and `ide` target list published by Check Point and reproduced in [[H422]]; collect against the same paths so the baseline and the hunt describe the same objects.
  Fields to collect - For every access to a store in the set, record: host name and host class (engineering, general, kiosk, build agent); user name and role; the full object path of the store; the accessing process image name, full folder path, SHA256 and signer subject and signature status; the process parent image; whether the access was a read or a write; the event timestamp; and the host's installed-AI-tool list at the time of collection. For the write side, additionally record the destination folder path, because a copy landing outside the owning directory is the artefact the companion hunt keys on.
  Collection window - Thirty days. The term that needs the full window is per-host, per-store reader novelty: the companion hunt asks whether a process has ever read this store on this host before, and that question needs a month of history to be worth anything. A shorter window will report a tool's monthly update cycle as novel. Run the window across a month boundary if the estate has monthly patch or refresh cycles.
  Deliverable - Three artefacts, held as data rather than prose. First, a per-host AI tool inventory: host, host class, installed tools, install mechanism, owner role. Second, an owning-reader allowlist: store path pattern to the set of signed image paths that legitimately read it, with the estate's EDR, backup, indexing and sync agents recorded once as global entries. Third, per-host rhythm figures: for each store, the number of distinct reader images, reads per day, and the 99th percentile of distinct stores touched by any single process in a ten-minute window. That last figure is the threshold [[H422]] should use on that host class instead of the starting value of three.
  Immediate flags, do not wait for the window to close - Act on these during collection:
  - Any process reading stores belonging to three or more different vendors inside ten minutes. This is the companion hunt's core signal and needs no baseline to be suspicious.
  - A copy of `state.vscdb`, `data.sqlite3`, `credentials.json`, `auth.json`, `hosts.json` or `kiro-auth-token.json` written anywhere outside its own tool directory by a process that is not a known sync or backup agent.
  - Any read of a store by an unsigned process, or by a process running from `%TEMP%`, `%APPDATA%`, `%PUBLIC%`, `%PROGRAMDATA%` or a user Downloads directory.
  - Any read of a store by `explorer.exe`, `rundll32.exe`, `regsvr32.exe` or another signed Windows binary that has no business holding AI credentials. Injection into a signed host is how this family's relatives hide their collection, which is the subject of [[H419]].
  - Any AI credential store path appearing for the first time on a host whose inventory records no such tool installed.
  - A read of a store followed within the hour by egress carrying the upload fingerprint in [[H424]].
  Inventory query, the starting point - Establish where the tools are before auditing anything. Run this per host or through the estate's inventory tooling and keep the output as the first deliverable:
  ```powershell
  $roots = @(
      "$env:USERPROFILE\.claude", "$env:USERPROFILE\.codex",
      "$env:USERPROFILE\.copilot", "$env:USERPROFILE\.gemini",
      "$env:USERPROFILE\.codeium", "$env:USERPROFILE\.aws\sso\cache",
      "$env:APPDATA\Cursor\User\globalStorage",
      "$env:APPDATA\Windsurf\User\globalStorage",
      "$env:APPDATA\Code\User\globalStorage",
      "$env:APPDATA\Kiro\User\globalStorage",
      "$env:APPDATA\JetBrains", "$env:APPDATA\amazon-q"
  )
  foreach ($r in $roots) {
      if (Test-Path -LiteralPath $r) {
          [pscustomobject]@{
              Host    = $env:COMPUTERNAME
              User    = $env:USERNAME
              Root    = $r
              Files   = (Get-ChildItem -LiteralPath $r -Force -Recurse -File -ErrorAction SilentlyContinue).Count
              Updated = (Get-Item -LiteralPath $r).LastWriteTimeUtc
          }
      }
  }
  ```
  Reader-attribution query - During the window, build the owning-reader mapping from 4663 joined to process context. The signer matters more than the image name, so resolve it:
  ```kql
  let aiStores = dynamic([
      @"\.claude\credentials.json", @"\.claude.json",
      @"\.codex\auth.json", @"\.codex\config.toml", @"\.codex\.env",
      @"\Cursor\User\globalStorage\state.vscdb",
      @"\Windsurf\User\globalStorage\state.vscdb",
      @"\Code\User\globalStorage\state.vscdb",
      @"\.aws\credentials", @"\.aws\config", @"\.aws\sso\cache",
      @"\amazon-q\data.sqlite3",
      @"\.copilot\config.json", @"\.copilot\hosts.json",
      @"\.codeium\config.json",
      @"\gemini-cli-workspace-token.json", @"\.gemini-cli-workspace-master-key",
      @"\.gemini\.env", @"\.gemini\config.json",
      @"\options\AIAssistantQuotaManager2.xml"]);
  SecurityEvent
  | where TimeGenerated > ago(30d)
  | where EventID == 4663
  | where ObjectName has_any (aiStores)
  | summarize reads = count(), days = dcount(bin(TimeGenerated, 1d)),
              firstSeen = min(TimeGenerated), lastSeen = max(TimeGenerated)
          by Computer, SubjectUserName, ProcessName, ObjectName
  | order by Computer asc, ObjectName asc, reads desc
  ```
  Keep every row. The rows with high `days` and high `reads` are the owning readers and the agents; the rows with `days` equal to one are the candidates to look at, and whether they are provisioning or collection is decided by the host's joiner and refresh context rather than by the query.
  Per-host threshold query - At the end of the window, derive the figure the companion hunt needs rather than importing one:
  ```kql
  let aiArtefacts = dynamic(["state.vscdb", "credentials.json", "auth.json", "hosts.json",
                             "kiro-auth-token.json", "data.sqlite3",
                             "gemini-cli-workspace-token.json",
                             "AIAssistantQuotaManager2.xml"]);
  DeviceFileEvents
  | where Timestamp > ago(30d)
  | where FileName in~ (aiArtefacts)
  | summarize distinctStores = dcount(FileName)
          by DeviceName, InitiatingProcessFileName, bin(Timestamp, 10m)
  | summarize p99 = percentile(distinctStores, 99), maxSeen = max(distinctStores)
          by DeviceName
  | order by p99 desc
  ```
  Use the per-host `p99` as that host's threshold in [[H422]], and treat a host whose `p99` is already three or more as one to investigate before adopting its own number as normal.
  Why this is a baseline and not a rule - The decisive term in the companion hunt is reader novelty, and novelty is defined only against history. There is no portable threshold either: an engineering workstation with four AI tools, a password manager and several browsers legitimately shows far more cross-store activity than a finance laptop with none, so a single estate-wide number is simultaneously too loose for the first and too tight for the second. The read audit that makes any of this visible also has a cost that has to be measured on real hosts before it is deployed widely, and this exercise is where that measurement happens.
  Closest existing coverage - [[B035]] is the nearest baseline: it treats the AI coding agent itself as a signed, user-approved process and baselines what that process legitimately does. This baseline looks the other way down the same relationship and records what legitimately reads the agent's stored credential, which is a different object and a different sensor; run them together, because the agent appearing in both records is the case where one agent reads another vendor's store. [[H259]] covers the macOS keychain route to the same class of secret and is where the equivalent macOS baseline would attach.
  Adjacent coverage - [[H422]] is the hunt this baseline enables, and the per-host threshold and owning-reader allowlist produced here are direct inputs to it. [[M062]] scores credential-store breadth across coarse families when the target list is unknown; the inventory built here is what would let an AI-agent family be added to its map honestly. [[B064]] baselines GitHub API usage from the estate and overlaps on the same host population, so run the two together and share the host-class definitions. [[H409]] covers tampering with an agent's configuration rather than theft of its credential, and the inventory here is equally the prerequisite for noticing that.

# B066

Check Point Research's October 2026 analysis of the Aokigahara infostealer documents a dedicated collection handler for AI coding agents and their credential stores, listing exact paths for Claude Code, Codex, Cursor, Windsurf, VS Code, GitHub Copilot, the Gemini CLI, Kiro, Amazon Q, Codeium and JetBrains AI Assistant, alongside AWS credentials and the SSO cache. The report's conclusion is that these artefacts "should be treated as sensitive assets alongside browser sessions, cloud credentials, and developer keys."

Treating them that way means being able to tell a theft from a tool doing its job, and that is harder here than for the credential stores security teams already watch. Browser profiles and password-manager vaults are installed by deployment and read by one known program. AI coding agents are installed by developers, often several per machine, each with its own updater, language server and extension host. Several of the target paths are shared rather than tool-specific: `.aws\credentials` and the SSO cache are read by the whole AWS tooling ecosystem, and `kiro-auth-token.json` sits inside the SSO cache directory. File-sync clients roam the entire user profile and legitimately produce copies of these files outside their original directories, which is exactly the artefact a collection hunt wants to key on.

The practical consequence is that the companion hunt's decisive term cannot be evaluated without history. Catching one process that reads Claude Code's credential file, Codex's auth file and Cursor's state database in the same minute requires knowing which process owns each store on that host and which processes have read them before. A read audit is what makes the behaviour visible at all, because no file-creation sensor records a read, and an audit deployed without a measured volume estimate is an audit that gets switched off.

This baseline produces three things: a per-host inventory of which AI tools exist and who owns the machine, an allowlist mapping each store to the signed images that legitimately read it, and a per-host figure for how many distinct stores any single process touches in a ten-minute window. The third replaces the starting threshold in the companion hunt with a number derived from the estate rather than imported into it.

The immediate flags are listed so that collection is not a thirty-day blind spot. A process reading three vendors' stores in a minute, an unsigned binary reading any of them, or a copy of a state database landing outside its own directory are all actionable on the day they appear, whatever the baseline eventually says.

## Why

- The companion hunt's strongest term is novelty, and novelty has no meaning without recorded history. Knowing that a process has never before read this store on this host is what separates a stealer from a language server, and only a collection window produces that.
- The legitimate reader set here is unusually crowded and unusually variable per host. Multiple AI tools per machine, each with updaters and extension hosts, plus sync clients and shared cloud-credential paths, mean the owning-reader mapping has to be observed rather than assumed.
- Read auditing is the only sensor that sees the actual behaviour, and it is the one sensor with a real cost. Measuring 4663 volume against the named file set on a pilot group is the difference between a durable control and an audit policy that is rolled back after a week.
- A static cross-store threshold cannot generalise across host classes. An engineering workstation legitimately shows cross-tool activity that would be an incident on a finance laptop, so the threshold has to come from each host's own history.
- The inventory is independently valuable. Knowing which machines hold live credentials for AI services and cloud SSO is the scope statement for revocation during an incident, and most estates do not currently have it because these tools arrive without deployment.
