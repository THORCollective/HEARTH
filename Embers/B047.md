false_positive_notes: |
  This baseline produces an inventory rather than alerts, so the question is what belongs in the register rather than what to suppress. Several things will look alarming on first collection and are usually benign, and each should be dispositioned once and recorded. Service accounts and the RMS service identity itself generate the overwhelming majority of traffic to the certification and licensing pipelines — that is the product working, and it forms the bulk of the volume profile rather than an exception list. Client machines across the estate will legitimately hit `/_wmcs/certification/` and `/_wmcs/licensing/` constantly; these are the user-facing surfaces and are not the ones that matter here, so profile them for volume but focus the scrutiny on `/_wmcs/admin/`. Past TPD exports found during the file search are frequently legitimate — disaster-recovery backups of the cluster key are explicitly recommended practice — but a legitimate export stored on an ordinary file share, in an unencrypted backup, in a documentation wiki or in an engineer's mailbox is functionally a leaked key regardless of the intent behind it, so the correct disposition is to relocate it to a controlled key store rather than to mark it as expected. Expect the Service Group membership review to surface stale accounts belonging to departed administrators and to decommissioned management servers; these are the highest-value cleanup output of the whole exercise. Two population notes: organisations that have migrated to Azure Information Protection often leave the on-premises cluster running and still authoritative for historical documents, so "we don't use RMS any more" is not a reason to skip the baseline — it is a reason to prioritise it, because nobody is watching it. And HSM-backed clusters cannot have the key extracted through the export path, so confirming key protection mode early may legitimately reduce this from an urgent baseline to a documentation exercise.
notes: |
  Collection window - 30 days of IIS request data captures a full monthly administrative cycle and is sufficient for the access profile. The inventory components — cluster configuration, Service Group membership, key protection mode, and the TPD file search — are point-in-time state and should be collected on day one rather than accumulated, then re-snapshotted at the end of the window to produce the first diff. If IIS logs are not currently retained, start retention immediately and treat the 30 days as beginning then; do not delay the state inventory waiting for log data.
  Fields to collect, admin surface access - for every request to `/_wmcs/admin/`: `date`, `time`, `c-ip`, `cs-username`, `cs-method`, `cs-uri-stem`, `cs(User-Agent)`, `sc-status`, `sc-bytes` and `time-taken`. Profile by the tuple of username, source IP and user agent. In almost every environment this produces a handful of distinct combinations, which is precisely what makes the baseline valuable — the set is small enough to enumerate exhaustively and review by hand. Record `sc-bytes` and `time-taken` distributions explicitly, because the SOAP operation name is not in the URI and response SIZE is the only proxy available for distinguishing a key export from a routine administrative call.
  Fields to collect, the other RMS surfaces - request volume, distinct client count and status-code distribution for `/_wmcs/certification/` and `/_wmcs/licensing/`. These are the normal-usage surfaces and their profile matters for a different reason: forged Rights Account Certificates signed with a stolen cluster key appear as certification and licensing requests, so knowing the normal identity population and per-identity request rate is what allows a forged-identity request to stand out later.
  Fields to collect, privilege - the resolved membership of the AD RMS Service Group and of any group nested inside it, with each member's account type, last logon and owner. Reconcile the accounts that HOLD this privilege against the accounts observed actually USING the admin surface in the 30-day window. The gap between those lists is the attack surface, and in a decade-old deployment it is usually most of the list.
  Fields to collect, existing key copies - for every candidate TPD file found: path, hostname or repository, size, created and modified times, owner, access control list, and whether the containing location is encrypted or access-controlled. Note that the default export format is a 1172-byte CAPI `PRIVATEKEYBLOB` protected with AES-128-CBC under a hardcoded IV, so the file's protection reduces entirely to the password used at export — which means "it is password-protected" is not a sufficient disposition and the storage location must be assessed on its own.
  Deliverable - five artefacts, all diffable. (1) An RMS CLUSTER REGISTER: every cluster and node, its URL, version, key protection mode, configuration database location, in-service status, and a named business owner. (2) An ADMIN-ACCESS ALLOWLIST: the enumerated set of username plus source IP plus user agent combinations observed against `/_wmcs/admin/`, each dispositioned, with expected cadence. (3) A PRIVILEGE RECONCILIATION: Service Group members who have used the admin surface, members who have not, and the cleanup decision for each. (4) A KEY-COPY REGISTER: every exported TPD located in the estate, with its storage location assessed and a remediation decision recorded. (5) A TELEMETRY ATTESTATION: a written statement of whether IIS logs are collected from every node, how long they are retained, and whether SQL audit is enabled on the configuration database — because a baseline standing on absent telemetry is worse than none.
  Immediate flags, do not wait for the 30 days - any POST to `/_wmcs/admin/` from a source IP that is not an RMS node or a known management station; any admin-surface request whose user agent is a scripting library or a custom string rather than an RMS or Microsoft management client; any TPD file found outside a controlled key store, particularly on a general-purpose file share, in an unencrypted backup or in mail; any addition to the AD RMS Service Group; a cluster reporting `IsServicePrivateKeySoftwareBased: true` with no IIS log retention; RMS admin-surface traffic over plain HTTP rather than HTTPS, which exposes the exported blob to network capture; and any RMS node that is still live and authoritative but has no current owner.
  What this baseline enables - H308 hunts the `ExportTrustedPublishingDomain` call itself. That hunt is only executable if IIS logs exist and only precise if the normal admin-access population is already written down, because the operation name is not in the URI and every POST to the admin endpoint must therefore be triaged rather than alerted on. Without this baseline, H308 degrades into reviewing all administrative traffic to a server nobody currently owns.

# B047

Most AD RMS deployments are archaeology. They were installed a decade or more ago, by people who have since left, to protect documents that are still protected today. Many organisations have since moved to Azure Information Protection and left the on-premises cluster running because it is still authoritative for everything sealed before the migration. Nobody owns it, nobody monitors it, and nobody has looked at who can administer it since the day it went in.

Under that neglect sits a key that cannot be rotated. The Server Licensor Certificate is the root of trust for every document the cluster has ever protected, and anyone holding its private key can decrypt all of them offline — no server contact, no credentials, no rights evaluation. Rotating it would invalidate every protected document ever produced, so in practice it cannot be rotated at all. And as Huntress documented, the supported operation that exports it writes nothing to the Windows event log and nothing to the RMS logging database, which records certification and licensing calls but not the export of the cluster's own key. The single trace is an IIS request line that does not even name the operation, because the SOAP operation lives in the request body.

There is consequently no rule to write here, which is what makes this a baseline rather than a hunt. The defensive position has to be built in advance, and it has two halves. The first is behavioural and small: profile 30 days of requests to `/_wmcs/admin/` by username, source IP and user agent. In nearly every environment that produces a handful of distinct combinations — a set short enough to enumerate exhaustively and review by hand, which is exactly the property that makes an otherwise low-fidelity signal workable. The second half is state, and it is where most of the value actually sits: which clusters exist and who owns them, whether the key is software-protected or HSM-backed, who holds Service Group membership versus who has ever used it, and — most importantly — where copies of the key already are. Legitimate TPD exports happen during migrations, federation setup and disaster-recovery backups, and each one produces a key blob that has to be stored somewhere. An exported TPD sitting on an ordinary file share, in an unencrypted backup or in an engineer's mailbox is a leaked cluster key regardless of the intent behind the export, and finding those is often the most consequential output of the entire exercise.

## Why

- There is no log to alert on, so prevention of the "we had no idea what normal looked like" failure has to happen before the incident. The export operation is absent from both the Windows event log and the RMS logging database, leaving a baseline as the only viable defensive construction.
- The admin-surface population is genuinely tiny, which makes exhaustive enumeration possible rather than aspirational. A handful of username, source-IP and user-agent combinations can be written down and reviewed individually — a luxury that almost no other access baseline offers.
- The IIS request line does not name the operation, so every POST to the admin endpoint must be triaged rather than alerted on. That is only tractable against a known-good register, which is exactly what this produces, and without it H308 degrades into reviewing all administrative traffic to an unowned server.
- Copies of the key are likely to already exist in the estate. Backing up the cluster key is recommended practice, so past legitimate exports are probable, and locating them converts an abstract risk into a concrete, remediable list of files in the wrong place.
- The rights-held versus rights-used reconciliation reliably surfaces stale privilege. In a decade-old deployment, Service Group membership typically contains departed administrators and decommissioned management servers, and each is a viable path to an unrotatable key.
- The collection itself answers the prerequisite question. Confirming whether IIS logs are retained from every node, and whether the cluster is software-key or HSM-backed, determines whether the organisation is exposed to this technique at all — and either answer is more valuable than a detection that cannot fire.
- Perceived obsolescence increases rather than reduces the risk. A cluster left running after an Azure Information Protection migration is still authoritative for historical documents while having lost whatever ownership and monitoring it once had, which is the worst combination of high value and low visibility.
