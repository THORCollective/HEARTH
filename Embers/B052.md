title: "Baseline of trusted-binary name and location pairs: where does msedge.exe legitimately run from, and which Microsoft-branded paths does anything actually write to"
hypothesis: >-
  MovieReaper's loader persists as `C:\ProgramData\Microsoft\Windows\Telemetry\msedge.exe`. Every
  element of that path is chosen to survive a human glance - a real Microsoft product name, a real
  Microsoft directory tree, a plausible Microsoft-sounding subfolder, and a binary name that appears
  legitimately on the same machine thousands of times a day. Nothing about it is detectable as
  malware and no reputation control engages, because the discriminator is not the file, the name or
  the folder in isolation. It is the PAIRING - this name has never run from this location in this
  estate. That question is unanswerable during an incident and trivially answerable in advance.
  Build a 30-day inventory of every execution of a high-value trusted binary name, recorded as a
  NAME-AND-PATH-AND-SIGNER tuple, plus an inventory of what legitimately writes executables into the
  Microsoft-branded directory trees under `%PROGRAMDATA%` and `%PROGRAMFILES%`. The deliverable is
  an approved name-location register and a diffable snapshot, so that a single execution of a known
  name from an unknown path becomes a one-line finding rather than a research project.

false_positive_notes: |
  The central risk in this exercise is concluding too quickly that an unfamiliar path is wrong, because the legitimate population of name-and-path pairs is far larger and far stranger than most teams expect. Browsers in particular install to several locations by design - Chrome and Edge both support per-user installs under `%LOCALAPPDATA%` as well as per-machine installs under `%PROGRAMFILES%` and `%PROGRAMFILES(X86)%`, both keep multiple versioned subdirectories live simultaneously during an update, and both ship helper executables that run from `...\Application\<version>\` paths that change every few weeks. Edge additionally appears under `%WINDIR%\SystemApps\` and in WebView2 runtime directories, and `msedgewebview2.exe` is embedded in a long list of unrelated desktop applications - Teams, Outlook, Office add-ins, Visual Studio, many Electron-adjacent products - each running it from its own private path entirely legitimately.
  The same breadth applies beyond browsers. Software distribution systems (Configuration Manager, Intune, PDQ, Chocolatey, Winget) stage installers and helper binaries into `%PROGRAMDATA%` and `%WINDIR%\Temp` as a matter of routine, and `%PROGRAMDATA%` is a legitimately writable location that dozens of real products use for exactly what it was designed for. Antivirus and EDR agents, backup software, VPN clients, print drivers, and line-of-business applications all write executables into branded subdirectories that look exactly like the pattern being hunted. A naive rule that flags "executable under `%PROGRAMDATA%`" will bury the team on day one.
  Three properties turn the inventory into a decision. SIGNER is the strongest and should be collected first - a genuinely Microsoft-signed `msedge.exe` in an unusual directory is an update artefact or an embedded runtime, while an unsigned or self-signed binary named `msedge.exe` is unambiguous regardless of where it sits. `OriginalFileName` from the PE version resource is second, because it survives renaming - a file called `msedge.exe` whose `OriginalFileName` is something else entirely, or is absent, is the renamed-tool case. POPULATION SIZE is third and is what makes the baseline worth building at all - a legitimate name-path pair appears on hundreds or thousands of hosts because it comes from a package everyone has, whereas a masquerade appears on one host, or on a handful, and appeared for the first time last Tuesday. Stack by pair and sort ascending by host count; the finding is at the bottom of that list.
  Two cautions. First, an unfamiliar-looking Microsoft path is not automatically fake - `C:\ProgramData\Microsoft\Windows\` genuinely contains many real subdirectories, and the credibility of the MovieReaper path comes precisely from the fact that the surrounding tree is real. Verify against a known-clean reference build rather than against intuition. Second, this baseline is about NAME-LOCATION pairs and will not catch a payload that uses an original name in an original location while being malicious inside; it is one axis of several, and sideloading in particular is caught by the Event ID 7 axis rather than the Event ID 1 axis.
notes: |
  Collection window - 30 days of continuous process-creation and file-create collection, which covers a full patch cycle, a monthly maintenance window and at least one browser release train. Browsers update roughly every four weeks, so a shorter window will record a set of versioned paths that have already rotated by the time the register is published and will generate a wave of spurious diffs in month two. The configuration-side inputs - the software asset register, the packaging catalogue, the gold-build manifest - are point-in-time and should be collected on day one. Re-snapshot the whole inventory on day 30 to produce the first diff, which is the artefact that gives the exercise ongoing value.
  Scope - do not attempt every executable in the estate; the register becomes unmaintainable and nobody reads it. Scope to a defined HIGH-VALUE NAME LIST of binaries whose names carry implicit trust, and baseline those exhaustively. A workable starting list - `msedge.exe`, `chrome.exe`, `firefox.exe`, `msedgewebview2.exe`, `svchost.exe`, `lsass.exe`, `services.exe`, `winlogon.exe`, `explorer.exe`, `taskhostw.exe`, `RuntimeBroker.exe`, `dllhost.exe`, `rundll32.exe`, `regsvr32.exe`, `mshta.exe`, `wscript.exe`, `cscript.exe`, `powershell.exe`, `pwsh.exe`, `cmd.exe`, `msiexec.exe`, `OneDrive.exe`, `Teams.exe`, `Update.exe`, `setup.exe`, `install.exe`, `update.exe`, `notepad.exe`, `conhost.exe`, `SearchIndexer.exe`, `WmiPrvSE.exe`, `spoolsv.exe`, `ctfmon.exe`. Note that `RuntimeBroker.exe` and `explorer.exe` are on that list for a second reason - LegionLoader hollows the first and injects shellcode into the second, so their legitimate path and parent profile is directly useful to [[H331]] and [[H249]] as well.
  Fields to collect, execution side - for every process creation whose `Image` filename matches the high-value list, record the tuple `filename`, `full image path`, `OriginalFileName` from the version resource, `SHA256`, `Company`, `Product`, `Description`, `signer subject` and `signature status`, `parent image path`, `command line`, `user and integrity level`, `first seen` and `last seen` timestamps, and the `count of distinct hosts` the tuple appears on. The tuple is the unit of the register, not the file. Produce a per-tuple host count and a per-tuple first-seen date; those two columns are what make the register readable.
  Fields to collect, write side - for every executable file created anywhere under `%PROGRAMDATA%`, `%PROGRAMFILES%`, `%PROGRAMFILES(X86)%` and `%WINDIR%`, record `target path`, `creating process image and signer`, `creating user`, `SHA256`, `Zone.Identifier` presence, and `timestamp`. Aggregate by creating process to produce the list of things that legitimately install into those trees - in a healthy estate that list is short, dominated by a handful of installers and update agents, and is itself a useful deliverable because anything outside it is writing executables into a trusted location.
  Deliverable - four artefacts. (1) An APPROVED NAME-LOCATION REGISTER: every high-value binary name with its sanctioned paths, signers and expected host population, with an owner for each entry and an explicit residual list of pairs nobody can account for. (2) An APPROVED-WRITER LIST: the processes permitted to create executables under the four trusted trees. (3) A RARE-PAIR REPORT: every name-path tuple appearing on fewer than a defined threshold of hosts (five is a reasonable starting point in a mid-sized estate), sorted ascending, which is the standing triage queue this whole exercise exists to produce. (4) A DIFFABLE SNAPSHOT of all three, re-run on a schedule so subsequent reviews read only what changed.
  Immediate flags, do not wait for the 30 days to complete - (1) any binary whose filename matches the high-value list but whose `OriginalFileName` differs or is empty; (2) any such binary that is unsigned, self-signed, or signed by anyone other than the expected vendor; (3) any executable written into a `Microsoft`-branded subdirectory of `%PROGRAMDATA%` by a process that is not a signed Microsoft installer or the endpoint management agent; (4) a browser executable running from any path under `%PROGRAMDATA%` at all - there is no supported browser installation layout that puts one there, which is the specific MovieReaper case; (5) any high-value name running with a parent that is a script host, an archive utility, or a process in a user-writable directory; (6) a scheduled task (4698) or service (7045) whose `ImagePath` points at a high-value name in a non-standard location; (7) a name-path tuple that appears on exactly one host in the estate and was first seen in the last seven days.
  Reference incident, for calibration - Securelist's MovieReaper, distributed through compromised torrents targeting users in multiple countries. Stage 3 performs a UAC bypass and establishes persistence as `C:\ProgramData\Microsoft\Windows\Telemetry\msedge.exe`. Supporting artefacts for retrospective search - first-stage C2 `deadhub[.]org` with fallback IP `193.23.118[.]155`, second-stage C2 `208.64.33[.]90` and `208.94.246[.]53`, C2 resolution via the Solana RPC endpoint `api.mainnet.solana.com` (the blockchain dead-drop pattern hunted in [[H270]]), mutexes `Global\E4AyDKzvEhe2hgAr` and `Global\fnulSktzSqvVLXHU`, loader MD5 `A0B13781EDD7CFDAB13D79AFFF3C83C1`. The loader executes shellcode via `EtwpCreateEtwThread` and resolves its imports by walking the PEB `Ldr` double-linked list rather than by using the import table - neither of which produces telemetry, which is precisely why the durable detection opportunity is the path rather than the technique.
  Why this baseline is the precondition for several hunts at once - [[H330]], [[H331]], [[H332]] and [[H270]] all reduce at their final triage step to the same question: is this process supposed to be running from there? Each of those hunts is materially cheaper to run once the register exists, and noticeably unreliable until it does. Building it once serves all four.
  Detection content to run alongside the collection - SigmaHQ `proc_creation_win_susp_process_masquerading.yml` and the `OriginalFileName` mismatch family of rules, Elastic's "Masquerading as a Trusted Binary" and "Process Execution from an Unusual Directory" prebuilt rules, and Atomic Red Team's T1036.005 atomics for validating that the telemetry actually captures a renamed and relocated binary in this estate before the register is trusted.

# B052

Securelist's MovieReaper loader persists on disk as `C:\ProgramData\Microsoft\Windows\Telemetry\msedge.exe`. Read that path quickly and nothing is wrong with it: Microsoft is a real vendor, `ProgramData\Microsoft\Windows\` is a real tree with many real subdirectories, telemetry is a real thing Windows does, and `msedge.exe` is a binary that runs legitimately on the same machine hundreds of times a day. Read it carefully and one thing is wrong with it — Microsoft Edge does not install there, has never installed there, and no supported deployment layout puts a browser under `%PROGRAMDATA%`.

That is the entire finding, and it is invisible to every control that examines the file, the name or the directory in isolation. The discriminator is the pairing of a name with a location, evaluated against what that pairing has looked like historically in this specific estate. During an incident nobody can answer it, and the investigation stalls on an inventory question. Thirty days of ordinary process-creation telemetry, aggregated into name-and-path tuples with a host count against each, answers it in advance and turns a research project into a sorted list where the finding sits at the bottom.

## Why

- **The masquerade defeats reputation and signing by not being a file problem.** There is no malicious signature to match, no unusual API to trap, no network artefact at the moment of persistence. A control that asks "is this file bad" has nothing to work with. A register that asks "has this name ever run from this place here" answers instantly, and it is built from telemetry the estate is already collecting for other reasons.
- **Rarity is the signal, and rarity requires a corpus that only a baseline provides.** Legitimate name-path pairs come from packages that are deployed widely, so they appear on hundreds or thousands of machines. A masquerade appears on one, or on a handful, and appeared for the first time recently. Sorting the tuple inventory ascending by host count puts the interesting rows at the bottom of the report every time — but only if the inventory exists, because a single host in isolation offers nothing to be rare against.
- **The benign population is much weirder than intuition allows, which is exactly why it must be measured rather than assumed.** Browsers install per-user and per-machine simultaneously, keep several versioned directories live during updates, and embed `msedgewebview2.exe` inside a long list of unrelated desktop applications that each run it from their own private path. Any team that writes this rule from first principles instead of from data will flag several hundred legitimate things in the first hour and abandon it by lunchtime.
- **One register makes four separate hunts cheaper at once.** The blockchain C2 hunt, the script-host dropper hunt, the browser-credential-theft hunt and the sandbox-evasion hunt all terminate in the same triage question — should this binary be running from this directory? Each is slower and less reliable without an answer. Building the register once removes that bottleneck from all of them, which is a better return than tuning any one of them further.
- **The write side is a short list in a healthy estate, and that makes it a control as well as a baseline.** Very few processes should ever create an executable under `%PROGRAMDATA%\Microsoft\` or `%PROGRAMFILES%`. Enumerating the ones that legitimately do produces an approved-writer list that is genuinely small, genuinely stable, and immediately usable as an allowlist — and anything outside it is writing executables into a location the entire estate implicitly trusts.
