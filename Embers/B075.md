false_positive_notes: |
  This is a baseline, so the output is an inventory rather than alerts; the usual false-positive framing applies to the immediate-flag list. Three collection hazards are worth stating up front.

  Maintenance windows will pollute the process baseline badly. Upgrades, re-indexing, backup jobs and plug-in installations legitimately spawn helpers and fetch from vendor endpoints, and a 30-day window will almost certainly contain at least one. Record maintenance periods and tag them rather than excluding them silently, because an attacker working during a change window is a real scenario and the tagged data is what makes that case reviewable.

  Some plug-ins genuinely shell out, and a few products ship helper scripts invoked through a shell. The deliverable is an allowlist of parent-child pairs with a reason for each, not a claim that the JVM never spawns anything. An entry that nobody can explain is the finding.

  Egress inventories drift faster than process inventories, because integrations are added by application owners rather than by platform teams. Re-measure the destination list quarterly, and prefer a short list with named owners over a long list that is complete but unattributed.

  Rate thresholds do not transfer between hosts, let alone between estates. A host managed by configuration management produces command bursts that would be extraordinary on a hand-managed one. Express the rate baseline per host and per account, and keep the distribution rather than a single number.

  Containerised and orchestrated deployments change the shape of all three measurements - short-lived processes, ephemeral network identities and no persistent shell history. Record which deployment model each asset uses, because a baseline built on a virtual machine estate will not transfer to a Kubernetes one without adjustment.

  Finally, a baseline that only covers the products currently in the news is worth much less than one that covers the class. Collect for every internet-facing Java application server, including the ones nobody has filed a CVE against this month.
notes: |
  Collection window - 30 days of process, network and DNS telemetry, extended to 90 days where retention allows so that monthly maintenance and quarterly integration jobs are represented. Record explicitly which periods were maintenance.

  Fields to collect, per observation - hostname and application product and version; whether optional APIs are enabled, specifically Remote API covering XML-RPC and SOAP on Confluence and Legacy API on N-central, since those are the settings that expose the Axis attack surface; parent process image and command line; child process image, full command line and executing user; whether the child is interactive; destination hostname, resolved address and port for each outbound connection, with the initiating process; bytes in and out; and per-account command counts bucketed by hour.

  Leg one, the parent-child inventory - Enumerate every distinct parent-child process pair observed on each application server, with counts and a first-seen date:

      # auditd: every execve on the host, with parent, for inventory
      auditctl -a always,exit -F arch=b64 -S execve -k app_exec
      ausearch -k app_exec -i --start recent | \
        awk '/type=SYSCALL/ {for (i=1;i<=NF;i++) if ($i ~ /^(ppid|pid|uid|exe)=/) printf "%s ", $i; print ""}' | sort | uniq -c | sort -rn

  The deliverable is a short table - parent image, child image, count, first seen, reason. For most Confluence and N-central installations the JVM's legitimate children are few and a shell is not among them. Any pair involving `/bin/bash`, `/bin/sh`, `/usr/bin/curl`, `/usr/bin/wget`, `/usr/bin/python3`, `/usr/bin/perl` or `/usr/bin/nc` under the application JVM belongs on the immediate-flag list rather than in the baseline.

  Leg two, the egress allowlist - Inventory every outbound destination per host, with the initiating process and a named owner for each entry. Expect three groups and nothing else - vendor update and licensing endpoints, internal services such as the database, directory and SMTP, and named integrations. The product of this leg is the list that makes an ephemeral tunnel hostname anomalous by difference rather than by reputation, which is the only way `trycloudflare.com`, `free.pinggy.net` and `webhook.site` become visible given that all three are legitimate services with valid certificates.

  Leg three, the command-rate distribution - For each application service account, bucket command counts by hour over the window and keep the distribution, not just a mean. Record also the mix - the ratio of read-only enumeration commands to state-changing ones, the number of distinct binaries invoked per session, and whether any session includes an encoder or decoder in a pipeline. The purpose is to make H511's throughput leg usable, since hundreds of ordered commands in a single session is only a signal against a measured normal.

  Leg four, the exposure register - A row per internet-facing application server recording product, version, patch state and the state of each optional API. For Confluence Data Center, note that Remote API has been off by default for new installations since version 3.0, that 9.2.28 is the fixed release for CVE-2026-90436, that 10.x and later removed the feature, and that Atlassian Cloud is unaffected; record which integrations depend on Remote API, because clearing the setting takes effect without a restart but will break them. For N-central, record whether Legacy API is disabled and whether the instance is on 2026.4 HF3 or later. This register is the half of the work that closes the gap rather than observing it.

  Deliverables - four artefacts, each short enough to be read rather than queried:

  - A per-product allowlist of legitimate JVM child processes, with a reason per entry.
  - A per-host egress allowlist with a named owner per destination.
  - A per-account command-rate distribution and command-mix profile.
  - An exposure register covering version, patch state and optional-API configuration, with the integrations that depend on each enabled feature.

  Immediate flags, to raise before the baseline is complete - the application JVM parenting any interactive shell or download tool; any outbound connection from an application server to an ephemeral tunnel or request-capture provider; a command line containing a long hexadecimal argument or a hex decoder in a pipeline; a local database client authenticating with the application's own credentials from a shell rather than from the JVM; bulk sequential reads of the application's attachment or upload directory by anything other than the application itself; and any internet-facing instance where Remote API or Legacy API is enabled and the product is not on a fixed release.

  Hunts this baseline enables - H510 (Axis SOAP exploitation and the JVM-parents-a-shell lineage), H511 (hex-encoded automated post-exploitation from ephemeral tunnels), H512 (the identity pivot out of credentials stored in the wiki). Leg one is what makes H510 a two-line query; leg two is what makes H511's destination leg mean anything; leg three is what makes its rate leg defensible.

  Scope note: B017 and B025 are the closest existing baselines and they cover the content side of the same product - what legitimate access to Confluence credential material looks like, and a per-user and per-role baseline of normal information-repository access. This baseline covers the host and process side, which neither touches: what the JVM may parent, where the host may connect, and how much the service account normally does. B038 and B052 are the Windows equivalents for signed-binary and library behaviour and do not apply to a Linux application server. Run this one alongside B017 for any estate that runs self-hosted Confluence, because the two together cover both how an attacker gets in and what they find when they do.

# B075

Rapid7's MDR team did not find the Confluence intrusion by recognising CVE-2026-90436. They found it because alerts fired on abnormal child processes launched by an Atlassian Confluence server — while every one of the exploit requests in the access log was returning HTTP 500.

That is the argument for this baseline in a single sentence. The web log said nothing had happened. The host said a Java process had just spawned Bash and curl. Only one of those was true, and knowing which required knowing what that server normally does.

Internet-facing application servers are unusually good candidates for baselining, because they are among the most predictable hosts in any estate and among the most exposed. The JVM's legitimate children are few and rarely include a shell. Outbound destinations are a short list — vendor endpoints, internal services, named integrations. The service account does almost nothing interactive. Each of those is a measurement, each is cheap, and together they make three separate hunts into simple list comparisons.

The last point matters most: measure the class, not the product. The next unsafe-reflection flaw in a bundled Java library will look exactly the same at the host, and a baseline scoped to this month's CVE will not be there when it lands.

## Why

- The detection that worked was behavioural, not vulnerability-specific. A JVM parenting an interactive shell is anomalous whatever the root cause, so this measurement keeps paying out long after CVE-2026-90436 is patched everywhere.
- The exploit log was misleading and the host log was not. Any process that relies on reading web access logs for successful-looking responses will clear a compromised host, which makes host-side baselining the control of record rather than a supplement.
- Server egress lists are short, which makes the destination leg unusually cheap. Ephemeral tunnel providers like `trycloudflare.com` and `free.pinggy.net` are legitimate services with valid certificates, so reputation will never flag them — only difference from a known list will.
- Rate baselines are the only defensible way to call automated enumeration. Hundreds of ordered, evenly spaced commands in one session is a strong signal and an unusable one without a measured normal for that host and that account.
- The exposure register turns the baseline into remediation. Both affected products need a non-default feature enabled to be vulnerable, so the register answers "are we exposed" directly, and in Confluence the setting can be cleared without a restart once the dependent integrations are known.
