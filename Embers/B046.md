hypothesis: >-
  Every GPO-abuse hunt reduces to the same question — is this policy object supposed to be here — and
  no rule can answer it, because a malicious GPO and a legitimate one are the same object type carrying
  the same attributes, written by the same service, applied by the same client. What separates them is

  - 'Domain controller Security event 5137 (directory service object created) filtered to `Object Class` of `groupPolicyContainer`. This is the creation record and the single most important field set in the whole baseline. Requires Advanced Audit Policy > DS Access > Audit Directory Service Changes, which is OFF by default — verify it is enabled on EVERY domain controller, because an attacker only needs the one DC where it is not'
  - 'Domain controller Security event 5136 (directory service object modified) for the attributes that control policy behaviour: `gPLink` and `gPOptions` on domain and OU objects, and `gPCMachineExtensionNames`, `gPCUserExtensionNames`, `gPCFileSysPath`, `versionNumber` and `nTSecurityDescriptor` on the policy objects themselves'

  - 'Effective delegation on GPO objects and on the containers they are linked to - who actually holds Create, Edit, Delete and Link rights, resolved transitively through nested groups rather than read off the obvious admin groups. BloodHound or `Get-GPPermission` both produce this'

false_positive_notes: |
  This is a baseline, so the output is an inventory rather than an alert, and the tuning question is what belongs in the allowlist rather than what to suppress. Two things routinely inflate the raw event counts and should be understood before the data is read. First, `versionNumber` increments on `groupPolicyContainer` objects are extremely noisy and fire on every trivial edit — count them per object and per editor to find the normal cadence, but do not treat an individual increment as meaningful. Second, in environments running desktop or security baseline tooling (Microsoft Security Compliance Toolkit, LGPO imports, Intune co-management, third-party GPO management suites), automated service accounts will legitimately appear as frequent GPO editors; these belong in the baseline as named, expected identities with their own profile, not as exclusions from collection. Genuine periodic events that will look anomalous on first collection and are usually benign: quarterly security-baseline refreshes touching many objects at once, new-OU buildouts that copy an existing policy, domain migrations that recreate links, and SYSVOL replication or DFSR repair operations that rewrite file timestamps across the tree without changing content — hash rather than mtime is the reliable field there. A GPO with no links is common and is not by itself suspicious; unlinked policy objects accumulate as administrative debt. What the baseline exists to surface is the joint condition, not any single field.
notes: |
  Collection window - 30 days of directory service change events is the minimum that captures a monthly patch and policy cadence; 60 to 90 days is materially better because much GPO administration runs on a quarterly rhythm and a 30-day window will misclassify quarterly editors as first-time editors. Collect the SYSVOL file inventory and the delegation snapshot as point-in-time data on day one rather than over the window — they are state, not behaviour — and re-snapshot both at the end of the window to produce the first diff.
  Fields to collect, GPO creation (event 5137) - `Subject Account Name`, `Subject Domain Name`, `Subject Logon ID`, `Object DN`, `Object GUID`, `Object Class`, `Correlation ID`, `Computer` (which DC), and event time. The per-account creation count over the window is the single highest-value column the baseline produces: in most environments the set of accounts that has ever created a GPO is very small and very stable, and an account outside it is reviewable by hand.
  Fields to collect, GPO modification (event 5136) - `Subject Account Name`, `Object DN`, `Object GUID`, `Attribute LDAP Display Name`, `Attribute Value`, `Operation Type` (value added vs deleted), and `Correlation ID`. Profile separately by attribute: `gPLink` changes tell you where policy is being scoped, `gPCMachineExtensionNames` tells you which client-side extensions a policy will invoke, and `nTSecurityDescriptor` tells you the policy's own permissions changed. Record the CSE GUIDs seen in `gPCMachineExtensionNames` as their own frequency table — `{35378EAC-683F-11D2-A89A-00C04FBBCFA2}` is the Registry extension and `{827D319E-6EAC-11D2-A4EA-00C04F79F83A}` is Security, and knowing which of your policies legitimately carry each one is what lets a hunter judge a new value.
  Fields to collect, per-GPO inventory - GPO display name, GUID, creation time, last-modified time, owner, `gPCFileSysPath`, machine and user version numbers, CSE list, WMI filter, link targets with enforced/enabled state, and link order. Derive and store two computed columns: AGE IN DAYS at collection time, and LINKED AT DOMAIN ROOT (boolean). Those two plus creator account are the three fields that carry most of the detection value.
  Fields to collect, SYSVOL inventory - full path, filename, extension, size, SHA-256, owner SID, and mtime for every file under the policies tree. Derive an extension frequency table. A healthy SYSVOL policies tree contains essentially only `.pol`, `.inf`, `.ini`, `.xml`, `.adm`, `.admx`, `.adml`, `.aas`, and scripts under `Scripts\Startup` / `Scripts\Logon`. Everything else is worth an eyeball once.
  Deliverable - four artefacts, all diffable. (1) An APPROVED GPO REGISTER: one row per policy object with GUID, display name, purpose, business owner, expected link scope, expected CSE list, and an explicit yes/no on whether it is permitted to be linked at the domain root. (2) A GPO ADMINISTRATOR ALLOWLIST: the accounts and service principals that legitimately create, edit, link or delete policy, each with observed cadence and observed scope, derived from the 5137/5136 profile and reconciled against the delegation snapshot — the reconciliation matters, because accounts that HOLD the rights but have never USED them are the ones most attractive to an attacker. (3) A DOMAIN-ROOT LINK LIST: the complete, usually very short, set of GPOs linked at the domain naming context, held separately because that scope is the one the PAYLOAD intrusion used and because additions to it are individually reviewable. (4) A SYSVOL FILE-TYPE BASELINE: the extension frequency table plus the full path list of anything outside the expected policy file types, each dispositioned once.
  Immediate flags, do not wait for the 30 days to complete - a `groupPolicyContainer` created by an account with no prior creation history anywhere in the available logs; any new `gPLink` on the DOMAIN NAMING CONTEXT itself rather than a child OU; a GPO created and linked within the same `Subject Logon ID`; any file in SYSVOL whose extension is outside the policy file-type list, with image files and loose text files being the specific PAYLOAD pattern and any `.exe`, `.dll`, `.ps1`, `.bat` or `.vbs` outside the Scripts directories being more urgent still; `gPCMachineExtensionNames` gaining the Security CSE on a policy that has never carried it; `nTSecurityDescriptor` changing on a GPO such that a non-admin principal gains write; and any GPO creation or link change originating from a workstation rather than a management server or domain controller.
  What this baseline enables - H300 hunts a firewall-disable GPO linked at the domain root, and H301 hunts a ransom note delivered through the logon banner, wallpaper and lock screen from a SYSVOL-staged image. Both are precise only if the environment can answer "is this policy object new, and is this creator normal" in seconds. Without the register and the administrator allowlist, both hunts degrade into reviewing every GPO change in the domain, which is exactly the volume that causes GPO auditing to be switched off again.

# B046

Group Policy abuse keeps appearing in ransomware intrusions for a reason that is structural rather than technical. A malicious GPO is not a malformed object or an exploit — it is a completely ordinary policy object, created through the ordinary interface, replicated by the ordinary mechanism, and applied by the ordinary client. In the PAYLOAD intrusion Kaspersky documented in 2026, the operators created two policy objects, linked them at the domain root, and used them to disable the firewall on every domain-joined host and to display a ransom note through the logon banner and wallpaper. Nothing in that chain is anomalous in isolation. Every step is a supported administrative capability being used exactly as designed.

That means the discriminator is never the object and always the provenance: who created it, whether that account has ever created one before, where it is linked, how old it is, which client-side extensions it invokes, and whether the SYSVOL directory behind it holds policy files or a JPEG. An environment that has not written those facts down cannot evaluate them during an incident — and GPO change auditing is notorious for being enabled, generating thousands of `versionNumber` increments a week, and being switched off again before anyone builds the context that would make the volume interpretable.

This baseline exists to make that context a stored artefact. Two halves: a 30-day behavioural profile of who actually administers policy and how, built from directory service change events on the domain controllers, and a point-in-time state inventory of every GPO, every link and every file in the SYSVOL policies tree. The second half deserves particular attention because it is cheap and almost never done. SYSVOL is a small, slow-changing share whose legitimate contents are a short list of file types, and a single recursive inventory answers a question that no amount of event correlation will — whether anything is sitting in the policy tree that has no business being there. One of the most useful outputs is also one of the simplest: the reconciliation between accounts that *hold* GPO rights and accounts that have ever *used* them. The gap between those two lists is the attack surface, and in most domains it is much larger than the owners expect.

## Why

- Every GPO-abuse detection depends on a provenance judgement that no rule can make at alert time. "This policy object is new and its creator has never created one before" is a lookup against stored state, not a property of the event, so without the baseline the detections in H300 and H301 degrade into reviewing all GPO change activity in the domain.
- GPO administration is genuinely low-volume and highly stable in most environments, which makes it one of the highest-yield things to baseline per unit of effort. The set of accounts that has ever created a policy object is usually a handful, and the set of GPOs linked at the domain root is usually fewer than ten — small enough that additions to either are individually reviewable by a human.
- The SYSVOL file inventory catches a class of activity that event correlation misses entirely. Ransom-note images, rogue logon scripts and GPP credential files are all identifiable by file type against a share whose legitimate extension list is short, and that check costs one recursive enumeration.
- The rights-held versus rights-used reconciliation surfaces latent attack surface before it is exercised. Accounts with unexercised GPO write access — service accounts, legacy delegations, nested group membership nobody has audited — are the ones an attacker will find with BloodHound, and they are invisible to any behavioural baseline that only profiles observed activity.
- It converts an auditing subcategory that teams routinely abandon into a usable signal. The reason DS Access auditing gets disabled is unfiltered `versionNumber` noise; profiling that noise once and holding the result is what makes the remaining events worth reading.
- The collection itself validates the telemetry. Confirming that event 5137 is present from every domain controller, and that a SACL exists on SYSVOL so 4663 fires at all, closes the most common silent failure in this whole detection area — an attacker only needs the one DC where the audit policy was never applied.
