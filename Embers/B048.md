false_positive_notes: |
  This produces a register rather than alerts, so the work is dispositioning rather than suppressing, and most of what looks alarming on first collection is routine. Windows adds public roots on demand: when a client encounters content chaining to a root not yet installed, it consults the Microsoft Certificate Trust List, verifies the root is listed, and installs it — so the machine root store legitimately differs between two identically-built hosts purely as a function of which sites their users visited. Do not treat inter-host variance as suspicious by itself; treat ABSENCE FROM THE MICROSOFT CTL as the signal. Corporate TLS-inspection and DLP products install their own CA estate-wide and are usually the single largest non-public entry in the register; these must be confirmed against the network team's own list rather than assumed, because an inspection CA nobody can account for is itself a finding. Internal PKI roots are expected, but expect also to find retired internal CAs, roots from decommissioned products, and CAs from vendors the organisation no longer uses — these are among the most valuable outputs of the exercise, since a trusted root belonging to a defunct product is standing risk with no owner. Developer workstations will carry local development roots (`mkcert`, IIS Express, Docker Desktop) and interception-proxy roots (Fiddler, Burp, Charles); these are legitimate but mechanically identical to an attack, so the correct disposition is an explicit, named, time-bounded exception on identified engineering hosts, not a blanket allowlist by certificate name. On hosts files, expect legitimate entries from VPN clients, some endpoint agents, and developer workarounds; the population is small and every entry pointing a major public domain at loopback deserves individual review. On firewall rules, software installers create them constantly, so profile by program path and reconcile against installed products rather than trying to judge rule names.
notes: |
  Collection shape - unlike most baselines this is predominantly POINT-IN-TIME STATE rather than an accumulating event window. Collect the full inventory on day one, then re-snapshot at 30 days to produce the first diff; the event streams (Sysmon 12/13, CAPI2, Firewall 2004/2005) run continuously alongside to catch changes between snapshots and to attribute each change to a process. A baseline built only from events will miss everything installed before collection started, which on a long-lived estate is most of what matters.
  Fields to collect, certificates - for every certificate in every store on every host - `thumbprint`, `subject`, `issuer`, `serial number`, `not before`, `not after`, `key usage`, `enhanced key usage`, `SAN list`, whether it is SELF-SIGNED (subject equals issuer), the store it occupies, and the host it was found on. Then compute the two derived fields that do the actual work - HOST COUNT per thumbprint across the estate, and PRESENCE IN THE MICROSOFT CERTIFICATE TRUST LIST. A self-signed root present on a small number of hosts and absent from the Microsoft CTL and absent from the organisation's own intended list is the exact shape of [[H314]].
  Fields to collect, installation provenance - for every root-store write observed in the event stream - the writing process `Image`, its `ParentImage`, the user context, and the installation timestamp. Legitimate estate-wide CAs arrive via `svchost.exe` under the Group Policy service, the Intune management extension, or a named software-deployment agent. A root written by a process that is none of those - and in particular by a hollowed or unexpected binary such as `MsBuild.exe` - is a direct finding.
  Fields to collect, hosts file - the full contents per host, normalised, with each entry's `hostname`, `mapped address`, whether the address is loopback, and whether the hostname is a PUBLIC REGISTRABLE DOMAIN. Diff against the organisation's standard hosts file (usually empty apart from comments). Any public domain mapped to `127.0.0.1` or `::1` is an immediate flag.
  Fields to collect, firewall rules - per host, every enabled rule allowing INBOUND traffic, with `rule name`, `program path`, `direction`, `action`, `local port`, `profile`, and whether the program path resolves to a binary belonging to an installed, inventoried product. Rules whose program path sits in a user-writable directory, or that correspond to no known product, are the residual set to review.
  Immediate flags, do not wait for the 30-day re-snapshot - (1) a self-signed root present on fewer than a threshold number of hosts (set from your own distribution; single-digit host counts in a large estate) and absent from the Microsoft CTL; (2) a root whose subject impersonates a well-known public CA (Google Trust Services, DigiCert, Let's Encrypt, Microsoft) but whose chain terminates in itself; (3) any certificate whose SAN pairs a public domain with `localhost`; (4) a root-store write by a process that is not a recognised management agent; (5) a hosts-file entry mapping a public domain to loopback; (6) an inbound firewall rule whose program path is in a user-writable location.
  Deliverable - four artefacts, all diffable. (1) A TRUST REGISTER - every distinct certificate thumbprint in the estate, its host count, its disposition (public/CTL-backed, internal PKI, sanctioned inspection product, developer tool, unexplained), and a named owner for every non-public entry. (2) A PROVENANCE MAP - which management channel is expected to install each non-public CA, so that an out-of-channel write is detectable. (3) A HOSTS-FILE STANDARD plus the exception list of hosts that legitimately deviate and why. (4) A LOCAL-LISTENER REGISTER - every inbound firewall rule in the estate reconciled to a product and an owner. Re-snapshot quarterly thereafter; trust state changes slowly, which is precisely what makes the diff powerful.

# B048

Hunting a rogue root certificate as an event does not work, because the event is indistinguishable from the legitimate version of itself. A corporate TLS-inspection CA and an attacker's interception CA are both self-signed, both land in the same registry path, both are written by a SYSTEM-context process. What separates them is population and provenance: the legitimate one is on every machine in the estate and arrived through Group Policy or Intune, while the one Huntress documented in the Google Doc campaign — a self-signed CA presenting as "Google Trust Services" with `CN=WR3`, paired with a hosts entry and a `LocalProxy` firewall rule — was on one machine and arrived from a hollowed `MsBuild.exe`. Making that comparison takes seconds if an estate-wide register exists and is effectively impossible if it does not. This baseline builds the register, along with the two companion inventories that turn a suspicious certificate into a demonstrated interception rig: the hosts file and the set of firewall rules admitting traffic to local listeners.

## Why

- **Trust state is the rare security-relevant surface that is almost perfectly stable, which makes diffing it unusually powerful.** Root stores change rarely and for a small number of knowable reasons. A dataset with that little natural churn produces very few false positives per diff, so the signal-to-noise on this baseline is far better than on behavioural baselines — and unlike most inventories, it stays accurate for months.
- **It converts the single hardest triage question in [[H314]] into a lookup.** "Is this CA supposed to be here?" has no answer from the certificate itself. With host count and an intended-CA list in hand it is answered instantly, and without them an analyst is reduced to searching the subject name on the internet and guessing.
- **The exercise finds standing exposure that no detection would ever raise.** Retired internal CAs, roots from decommissioned products, unaccounted-for inspection CAs, and long-expired-but-still-trusted certificates are all sitting in production root stores right now in most estates, each one a usable trust anchor with no owner. Only an inventory surfaces them, and each is a remediation item independent of any intrusion.
- **It forces the PKI and network teams to state what they actually intend to distribute.** The most common finding in this exercise is not malware — it is an inspection or DLP CA that nobody can immediately account for, because the product was deployed by a team that no longer owns it. Reconciling installed trust against intended trust is valuable on its own and is the prerequisite for every certificate-related detection built afterwards.
