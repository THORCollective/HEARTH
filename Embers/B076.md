hypothesis: >-
  Rapid7's November 2026 scan found that more than half of exposed Ollama servers carried artefacts
  left by someone other than the owner, and its diagnosis was not primarily technical - when a
  stranger's model sits on your server for five months, the vulnerability isn't the main problem,
  the main problem is that nobody owns the server. Rapid7's own recommendation is to log API calls

false_positive_notes: |
  During the collection window this baseline will record plenty of legitimate activity that looks exactly like the malicious version - researchers pulling new models daily, MLOps pipelines copying models between environments, developers testing a tiny model to check a deployment works. That is the point of a 30-day window rather than a snapshot: the output is a description of normal, and the anomalies are judged against it afterwards.

  The population is unstable by nature, which is the finding rather than a defect. Model-serving hosts are spun up for an experiment and abandoned, so a host that appears once and never again is normal for this asset class and should be captured as a lifecycle fact, not discarded as noise. A host that appears, is never claimed by an owner, and keeps running is the risk.

  Development and research estates will legitimately carry uncensored or abliterated models and should not be scored against a production profile. Rapid7 notes 28% of exposed hosts carried at least one, and that running those is legal and often has good research reasons. Record them and segment the baseline by host role rather than flagging the model family.

  Rapid7 cautions that its own third-party activity indicators are inferred from model names only, and that a clean list doesn't prove a clean host, since names can be deleted. A baseline built from model names inherits that limitation - treat an empty artefact result as unproven rather than clean, and pair the name baseline with the state-change log, which an attacker cannot retroactively edit.

  Deception infrastructure distorts counts in both directions. Rapid7 removed 429 addresses as likely sensors after finding 148 hosts sharing an identical five-service fingerprint and 281 answering as two to five products on the same port. If the organisation runs honeypots, enumerate and exclude them before fitting anything.
notes: |
  Collection window - 30 days minimum. Model-runtime estates change faster than conventional server estates, and a snapshot cannot distinguish a host that pulls a new model every day from one that pulled once and has been untouched since.

  Fields to collect, per model runtime, per sweep.

  - Host identity - hostname, all IP addresses, cloud provider and account ID, region, instance type, and whether the instance carries a GPU.
  - Ownership - named owner, team, data classification, business purpose, and an expiry date. Rapid7's quarterly recommendation is to make registration a condition of AI infrastructure spend, with every model server given a named owner, a data classification and an expiry date, and the rule that if nobody owns it, it gets switched off.
  - Exposure posture - the bind address from `OLLAMA_HOST`, the listening ports, whether the service is reachable from outside the host, whether an authenticating reverse proxy or zero-trust layer sits in front, and whether TLS is in use. Rapid7 found only 0.3% of all findings were served over HTTPS, and notes Ollama has no built-in authentication, so this isn't optional.
  - Runtime version - the daemon version, compared against the Probllama fix in Ollama 0.1.34 and against current.
  - Model inventory - every model name and tag, its registry prefix, size, parameter count, family, and whether it is a local model or a `:cloud` routed tag.
  - Cloud linkage - whether `~/.ollama/id_ed25519` exists, which ollama.com account it is linked to, and whether spend alerts exist on that account.
  - Registry egress - every distinct destination the host pulled from over the window, with address, port and hostname.
  - State-change events - every pull, create, copy, push and delete, with timestamp, caller address, model name and the authenticated principal if any.
  - Pipeline linkage - whether an embedding model is present and which document stores or retrieval pipelines the host is wired into. Rapid7's interpretation is that embedding hosts are likely wired into pipelines that read internal documents, which makes the exposed box a bridge, not an island.

  Deliverable. Three artefacts a hunter and an asset owner can both use.

  1. A model-runtime register - one row per runtime with owner, classification, expiry, exposure posture, version and cloud linkage. Any row with no named owner is an action, not a finding.
  2. An approved-registry allowlist - the set of registry hosts the estate legitimately pulls from, derived from observed egress and then confirmed with owners rather than assumed. This list is what makes H516's raw-IP and tunnel-registry legs actionable; without it every internal registry reads as an attacker callback.
  3. A state-change profile per host - the normal rate and timing of pull, create, copy, push and delete, broken out by host role, so Rapid7's observation that on a stable production server they should be rare can be turned into a per-host expectation rather than a global assumption.

  Flag immediately, without waiting for the baseline to complete. These need no comparison to normal.

  - Any model runtime answering unauthenticated from a public address. Rapid7's containment guidance for a host with a stranger's artefact is to treat the host as compromised, not misconfigured.
  - Any model name carrying an artefact class from H516 - a raw IP and port registry prefix, a tunnel or throwaway registry, a `beacon`, `verify`, `probe` or `pwn` marker, the host's own IP embedded in a tag, a `-copy-test` suffix, or a Base64 or hex segment that decodes to a file path.
  - A `push` call to any destination. Reading and pulling have innocent explanations; pushing a model off the host to somewhere unapproved is exfiltration-shaped.
  - A pull from a raw IP and port, or from a `trycloudflare[.]com`, `ttl[.]sh`, `bore[.]pub` or Pinggy endpoint, which Rapid7 characterises as a callback confirming reachability and egress.
  - Any write to `/etc/ld.so.preload`, a new systemd unit, or the Ollama service `override.conf`. Rapid7 identifies the first two as persistence locations, not reading material, and the third as where people tend to put environment variables and API keys.
  - A model runtime with no named owner that has been running longer than 30 days.

  What the baseline enables, in Rapid7's own staging. This week - find them and check for guests, scanning your own public ranges and every paid cloud and VPS account, looking beyond default ports. Within 30 days - bind model runtimes to localhost or a private network, put an authenticating reverse proxy or zero-trust access layer in front where remote access is needed, restrict outbound traffic from model servers to approved registries, keep runtimes current, and log and alert on state-changing calls. Rapid7's framing for the egress control is that it is what turns a pull-based callback or SSRF attempt into a failed connection. This quarter - make ownership the default, decide in writing where uncensored models are allowed and what they may touch, and bring AI runtimes, notebooks and experiment trackers into exposure management and red-team scope, with the test being whether you can find, isolate and shut down one of these servers within an hour.

  Cross-reference. This baseline is the prerequisite for H516, which hunts stranger-created models in the model list and depends on an approved-registry list and a host inventory to be anything other than a source of false positives. It also scopes the blast radius for the existing managed-inference hunts - H446, H447, H448 and H449 - by establishing which self-hosted runtimes hold cloud credentials that could be ridden.

  Note on scope beyond Ollama. Rapid7's scan covered Jupyter Notebook, JupyterHub, MLflow, Streamlit and Grafana alongside Ollama, and found 7,714 findings on 7,627 hosts where an AI or notebook API answered without authentication, almost all of them Ollama. The report is careful that Streamlit, Grafana and JupyterHub results are presence checks proving exposure, not compromise, and that default-credential labels on Grafana were inferred by the scanner, not tested. Include all of these service types in the inventory; only Ollama exposes a model list with the visitors'-log property.

# B076

Rapid7 scanned 20,354 internet-facing hosts in November 2026 and found 7,627 where an AI or notebook API answered with no authentication at all. More than half the Ollama servers among them carried models that someone other than the owner had put there. Some of those had been sitting in place since June.

The report's diagnosis is not really about Ollama. It is that nobody owns the server. These machines get rented in five minutes on a credit card by a team that needed compute today, connected to company data later, and never enter a CMDB — so Rapid7's observation is that your attack surface now includes your developers' expense reports.

That is why the recommendation it lands on — log the API calls that change state, and alert on them, because on a stable production server they should be rare — cannot be implemented as written. "Rare" is a claim about a baseline nobody has. You cannot alert on an unapproved registry without a list of approved ones, and you cannot notice a stranger's model on a host you did not know you had.

So this is the inventory hunt that has to come first: find every model runtime the organisation pays for, record who owns it and what it may reach, and watch pull, create, copy, push and delete for 30 days until "rare" has a number attached.

## Why

- The detection Rapid7 recommends is a baseline statement in disguise. "On a stable production server they should be rare" is only actionable once rarity is measured per host and per role. Thirty days of state-change history converts that sentence into a threshold.
- An approved-registry list is the difference between H516 working and crying wolf. A pull from a raw IP and port is the single strongest artefact in that hunt, and it is also exactly what an internal model registry looks like. Only an enumerated allowlist separates them.
- This asset class is defined by its absence from inventory. Conventional discovery keys off procurement, agents and CMDB records, and these hosts have none of the three. The enumeration has to start from cloud billing and public ranges instead, which is a different exercise from normal asset management.
- Model runtimes hold credentials now, which changes what an unowned host costs. With a local ed25519 key linking the daemon to a paid account, and embedding models wiring hosts into document retrieval pipelines, an abandoned box is a credential broker and a bridge into internal data rather than spare CPU.
- Ownership is the control that actually closes this. Authentication, egress restriction and patching all require someone to be responsible for the host. Rapid7's rule — if nobody owns it, it gets switched off — is the only one of its recommendations that scales to servers you have not found yet.
