title: "Baseline every long-lived outbound session and every persistence surface on internet-facing Linux servers, so a relay client that owns no infrastructure has nothing left to hide behind"
hypothesis: >-
  A relay-based implant is invisible to every control that asks where the traffic is going, because the destination is a legitimate public service and the operator owns nothing. It is also invisible to every control that asks what is listening, because nothing listens. The only question that separates it from the host's normal behaviour is one the host cannot answer for itself: which processes on this server are supposed to hold a long-lived outbound session, under which account, to which destination, and which cron entries, systemd units and shell startup files are supposed to exist. Until that is written down per host, an outbound session from a web-service account to a shared relay service is indistinguishable from the dozens of legitimate outbound sessions an application server maintains, and a unit named after a system component is indistinguishable from one. Build the per-host answer first, then the anomaly is a one-line comparison rather than a judgement call.

required_data_sources:
  - 'Network connection telemetry attributing every outbound session to a process, an executable path and an account, with destination address, destination port, session start, session duration and byte counts in both directions'
  - 'Egress proxy or firewall logs capable of recording destination hostnames as well as addresses, since relay and distribution endpoints are reached by name'
  - 'Linux process execution telemetry with full command lines, parent lineage and effective user - auditd execve, Elastic Defend process events, or Sysmon for Linux Event ID 1'
  - 'Per-account cron tables for every user on the host, including service accounts, plus the system cron directories'
  - 'Systemd unit file inventory with enabled state, target links, the unit ExecStart line, and which installed package owns each unit file'
  - 'Shell startup file inventory for every account with a shell, with content hashes so modification is detectable'
  - 'Package-ownership data for every executable referenced by a unit, a cron entry or a long-lived session, so an unowned binary is identifiable'
  - 'A host inventory marking which Linux servers are internet-facing, which application stack each runs, and which account runs each service'
false_positive_notes: |
  This is a baseline, so its output is an inventory rather than a verdict, and the failure modes are about completeness rather than noise.
  - An application server legitimately holds many long-lived outbound sessions. Database connection pools, message brokers, caches, log shippers, metrics agents, update checkers, certificate renewal and content-delivery integrations all do it, and the count is routinely in the dozens. The deliverable has to accommodate that rather than flag it.
  - Service accounts legitimately make outbound connections, including to third-party services. A web-service account reaching a payment provider, an email relay or an object store is normal application behaviour. The baseline records which destinations each account legitimately reaches; it does not assume a service account should be silent.
  - Cron and systemd are genuinely crowded on a long-lived server. A mature host accumulates units and cron entries over years, some belonging to software nobody remembers installing. Expect the first pass to surface a backlog of legitimate-but-unexplained entries, and expect that to be the most time-consuming part of the exercise.
  - Short-lived outbound connections dominate by volume and are out of scope here. Scoping to sessions above a duration threshold is what keeps this tractable; set the threshold from the host’s own distribution rather than from a fixed number.
  - Unowned binaries are common and often legitimate. Software installed from source, language-specific package managers, vendored application dependencies and operator scripts all produce executables no system package owns. Package ownership narrows the population; it does not decide the case.
  - Relay and tunnelling tools may be approved. Developers and administrators use remote-access relays deliberately, and some support workflows depend on them. Record the approved uses during the baseline, because discovering them during an incident is how a legitimate tool becomes a false positive at the worst moment.
  - A baseline goes stale. Deployments add units, change destinations and rotate service accounts continuously. Without a refresh cadence and a diffing mechanism, the inventory is accurate on the day it is built and decorative a month later.
notes: |
  Source reporting is Microsoft Threat Intelligence November 11, 2026 analysis of GSocket deployment on compromised Linux servers across multiple incidents. The paired hypothesis-driven hunt is [[H473]], which covers the staging, permissions, timestamp and deletion sequence that deployment leaves behind. This baseline exists because the two detection surfaces that normally carry a backdoor hunt are both unavailable here, and because Microsoft’s own remaining recommended controls - egress filtering, outbound monitoring, and auditing persistence surfaces - all presuppose an inventory that most estates do not have. The closest existing baseline is [[B058]], which baselines the passive-implant surface on Linux network-edge appliances - packet sockets, daemon names, mapped shared objects and inbound port destinations. That one answers what is listening; this one answers what is reaching out, which is the inverse and the half that applies here.
  Why a baseline is the right instrument - Three of the Embers triggers apply directly. The technique abuses a legitimate protocol and a legitimate public service, so malicious use looks like administrative use. Microsoft’s detection guidance reduces in substance to constraining and watching egress - "apply deny-by-default egress rules, allow only required destinations, and monitor connections to relay infrastructure" - which is an instruction to know the normal set rather than to match a pattern. And the hunt requires knowing the host’s normal outbound destinations and persistence inventory before any rule can fire at all: Microsoft advises auditing cron entries, "systemd units with plausible service names", and shell startup files, which is a comparison against an expected set and is meaningless without one.
  Why the usual surfaces are empty - Worth stating in the baseline itself so the scope is not argued later. Microsoft reports that traffic passes through a public relay service, that "the threat actor does not register or host any infrastructure, so there is no threat actor-owned IP address or domain to block", and that both ends connect outbound so "the host needs no inbound listener or public IP address, and network address translation does not prevent the connection". Microsoft is explicit that "inbound firewall rules do not see this traffic, although egress filtering and outbound monitoring can". So destination reputation gives nothing, listening-port enumeration gives nothing, and what is left is the identity of the process holding the session and whether it belongs.
  Data to collect, per host, over a 30-day window - Collect in four groups so each produces an independently usable artefact.
  Outbound sessions: process identifier, executable path, whether any package owns that executable, command line, effective user and group, destination address, destination hostname where the proxy resolves it, destination port, session start time, session duration, bytes sent, bytes received, and whether the session survived a service restart. Keep sessions above a duration threshold set from the host’s own distribution.
  Process provenance for anything holding such a session: parent process and full ancestry, the mount the executable sits on, whether the executable path still exists on disk, and the file modification and change times.
  Persistence surfaces: every per-account crontab including service accounts, the system cron directories, every systemd unit file with its enabled state, target links, ExecStart line and owning package, and the content hash of every shell startup file for every account with a shell.
  Accounts and services: which account runs each service, which binaries each service account legitimately executes, and which accounts have a usable shell at all.
  Immediate flags, before the 30 days are up - These do not wait for the baseline to complete, because none of them has a benign reading that depends on knowing the host.
  - A process holding an open socket whose executable path is deleted, or whose executable sits on a memory-backed or temporary mount. Directly readable from the process table and covered in detail in [[H473]].
  - An outbound session held by an account that runs a web or application service, to a destination that is not in the application’s own dependency list.
  - A systemd unit or cron entry whose ExecStart or command references a binary under a memory-backed mount, a temporary directory, or a dot-prefixed path.
  - The relay client environment-variable names appearing in process telemetry, a unit file, a cron entry or a shell startup file. Microsoft reports the secret can be delivered through a notification channel configured with `GS_TG_TOKEN` and `GS_TG_CHATID`, which are specific enough to flag on sight.
  - A connection to the tool distribution endpoints Microsoft publishes - `gsocket[.]io`, `cdn[.]gsocket[.]io` and `gsgg[.]b-cdn[.]net`. Microsoft notes these are tool distribution endpoints rather than operator-owned command and control, so a hit means the tooling was fetched on this host, which is enough to open a case.
  - A systemd unit, service file or binary whose name resembles a system component but which no installed package owns. Microsoft reports observed names including `systemd-remount-d`, `defunct`, `defunct.service` and `.gsn_ora`, with a renamed payload at `/usr/bin/defunct` and a `multi-user.target.wants` link.
  A collection starting point, to be run per host and stored rather than read once:
  ```bash
  set -u
  echo "=== host: $(hostname)  collected: $(date -u +%Y-%m-%dT%H:%M:%SZ) ==="
  echo "--- established outbound sessions with owning process ---"
  ss -tnp state established 2>/dev/null
  echo "--- processes whose executable is deleted or on a memory-backed mount ---"
  ls -la /proc/*/exe 2>/dev/null | grep -Ei 'deleted|/dev/shm/|/tmp/'
  echo "--- crontabs for every account ---"
  cut -d: -f1 /etc/passwd | while read -r u; do
    out=$(crontab -l -u "$u" 2>/dev/null) || continue
    [ -n "$out" ] && { echo "## $u"; printf '%s\n' "$out"; }
  done
  echo "--- system cron directories ---"
  ls -la /etc/cron.d /etc/cron.daily /etc/cron.hourly 2>/dev/null
  echo "--- enabled systemd units and their ExecStart ---"
  systemctl list-unit-files --state=enabled --type=service --no-legend 2>/dev/null |
    awk '{print $1}' | while read -r unit; do
      exec_line=$(systemctl show -p ExecStart --value "$unit" 2>/dev/null)
      frag=$(systemctl show -p FragmentPath --value "$unit" 2>/dev/null)
      owner="unowned"
      if [ -n "$frag" ]; then
        if command -v dpkg >/dev/null 2>&1; then owner=$(dpkg -S "$frag" 2>/dev/null || echo unowned)
        elif command -v rpm >/dev/null 2>&1; then owner=$(rpm -qf "$frag" 2>/dev/null || echo unowned); fi
      fi
      printf '%s\t%s\t%s\n' "$unit" "$exec_line" "$owner"
    done
  echo "--- shell startup file hashes ---"
  for f in /etc/profile /etc/bash.bashrc /root/.bashrc /root/.profile /home/*/.bashrc /home/*/.profile /home/*/.bash_profile; do
    [ -f "$f" ] && sha256sum "$f"
  done
  ```
  Run it on a schedule and diff successive runs; the diff is the product, not the snapshot.
  Deliverable - Four artefacts per internet-facing host, version-controlled so they can be diffed. First, an outbound-session allowlist keyed on executable path, account and destination, with the expected duration and volume range for each entry and the application dependency that justifies it. Second, a persistence manifest listing every cron entry, every enabled unit with its ExecStart and owning package, and the hash of every shell startup file. Third, a service-account map recording which accounts run services, which binaries each legitimately executes, and which have a usable shell. Fourth, an explicit record of whether relay and tunnelling tools are permitted on this estate and, if so, by whom and where - so an approved use is not rediscovered mid-incident.
  What the baseline enables - Once the allowlist exists, the detection for this entire class is a set difference, and it does not depend on any indicator from this campaign. An outbound session that is not on the list. A unit or cron entry that is not in the manifest. A service account executing a binary outside its map. Microsoft recommended controls become implementable at that point rather than aspirational: deny-by-default egress needs the allowed-destination list, mounting temporary and memory-backed directories non-executable needs to know which legitimate software executes from there, and alerting on execution from hidden or world-writable paths needs the exception set.
  Scope and prioritisation - Internet-facing Linux web and application servers first. Microsoft telemetry puts web applications and hosting at 87.1% of attributable incidents, with PHP applications and cPanel hosting at 63.9% and Apache at 24.3% within that group, and reports education and research as the largest affected sector at 30.7%. Microsoft attributes that distribution to exposure rather than targeting, noting that academic institutions "often run large, decentralized web estates maintained outside central IT, which are harder to inventory and patch". That sentence is the prioritisation: the hosts where this baseline is most valuable are the ones least likely to be in any inventory at all, so building the host list is the first task and not a prerequisite that can be assumed.

# B071

Two questions normally find a backdoor on a server. Where is the traffic going, and what is listening.

Against a relay-based implant, both come back clean.

Microsoft Threat Intelligence described multiple Linux web-server compromises where the operator installed a relay client. Traffic goes to the Global Socket Relay Network — a legitimate public relay service. The operator registers no domain and hosts no address, so destination reputation has nothing to say. Both ends connect outbound and the relay pairs them, so nothing listens on the host and inbound firewall rules never see the session at all.

Microsoft names the controls that do still work: egress filtering and outbound monitoring, deny-by-default egress with only required destinations allowed, and auditing cron, systemd units with plausible service names, and shell startup files.

Every one of those is a comparison against an expected set. None of them is possible without the set.

That is what this baseline builds. For each internet-facing Linux server: which processes hold a long-lived outbound session, under which account, to which destination, for how long, moving how much — and which cron entries, which enabled units, and which shell startup files are supposed to be there, with the owning package for each.

It is unglamorous work and it is a backlog, not a project. A mature server has accumulated units nobody remembers enabling. Expect the first pass to be mostly archaeology.

But afterwards, the detection for this whole class of implant is a set difference. An outbound session not on the list. A unit not in the manifest. A service account running a binary outside its map. No indicator required, which matters, because the indicators in this campaign are a public tool's download URLs and they identify the tool rather than the operator.

A few things do not wait for the baseline. A process holding open sockets whose executable has been deleted. A unit pointing at a binary under `/dev/shm`. The relay's secret-delivery variables, `GS_TG_TOKEN` and `GS_TG_CHATID`, turning up anywhere on a web server. Those are findings on sight.

## Why

- **Both default detection surfaces are structurally empty, so the baseline is not a nice-to-have here.** No actor-owned destination to reputation-check and no listener to enumerate means the only remaining discriminator is whether the process holding the session belongs on the host. That is a question about the host, not about the threat, and it has to be answered in advance.
- **The vendor's own recommended controls are unimplementable without it.** Deny-by-default egress requires the allowed-destination list. Mounting memory-backed directories non-executable requires knowing what legitimately executes from them. Auditing units with plausible service names requires knowing which plausible names are real. The guidance is sound and it quietly assumes an inventory.
- **It collapses a judgement call into a lookup, which is what makes it survive contact with an on-call analyst.** Deciding whether an outbound session from a service account to a public relay is suspicious, at 2am, without a reference, is a coin flip. Checking whether it is on the list is not.
- **It generalises past this tool completely.** Relay services, tunnelling utilities, reverse-proxy clients and mesh VPN agents all share the same properties: legitimate shared infrastructure, outbound-only, no listener, nothing to blocklist. The population of such tools grows every year and a destination-based approach has to chase each one. An allowlist does not.
- **The persistence half is where incomplete remediation actually happens.** The report is explicit that persistence is layered across cron, systemd, shell profiles, watchdogs and redundant copies, and that stopping the process does not remove access. Remediation is therefore an enumeration task, and the manifest is what turns it from an open-ended search into a diff.
- **The hosts that need this most are the ones not in any inventory.** Education and research led the affected population, which the report attributes to large decentralised web estates maintained outside central IT. Building the host list is the first deliverable here, not an assumption — and on most estates it will be the finding.
