false_positive_notes: |
  Shadow copies are ordinary infrastructure and the legitimate volume is high, which is exactly why the register has to exist before any hunt can use it. Expect continuous activity from enterprise backup products (Veeam, Commvault, Rubrik, Veritas NetBackup, Acronis, Datto, Cohesity and their agents), Windows Server Backup, System Restore on workstations, Configuration Manager and Intune during servicing, SQL Server and Exchange VSS writers performing application-consistent backups, hypervisor-level snapshot coordination in virtualised estates, and user-facing Previous Versions. On a file server or database host several snapshots a day is healthy. On a domain controller a nightly application-consistent backup is not merely normal but mandatory - which is precisely why an intruder hides there.
  Because this baseline deliberately covers the API road rather than the command-line road, the bulk of what it collects is legitimate by construction: backup products do not shell out to `vssadmin`, they call the API, so almost every snapshot in the inventory will have been created by a signed backup agent doing its job. That is the point. The register's value is that it makes the population KNOWN, so the residual - a snapshot with no owning backup job, a snapshot created outside every documented window, a snapshot whose requesting process is not on the backup register - is a short list rather than a haystack.
  The decisive discriminator is not creation at all; it is WHAT IS READ AFTERWARDS. A backup agent streams the whole volume to a repository. An intruder takes three files - `ntds.dit`, `SAM`, `SYSTEM` - and nothing else. A snapshot whose only subsequent access is to the credential-bearing files has essentially no innocent explanation, and this is the axis that neither [[B015]] nor any command-line rule can see. Supporting discriminators are LIFETIME (a snapshot created and deleted within minutes has no backup analogue, since a backup needs the snapshot for the duration of the copy) and SCHEDULE (legitimate snapshots cluster tightly in documented windows, and writing those windows down is half the deliverable).
  Two cautions decide whether an empty result means anything. Object-access auditing on `ntds.dit` and the registry hives is not enabled by default and needs both a SACL and the audit subcategory; without it event 4663 never fires and the most valuable axis of this exercise silently produces nothing. Configure it on day one, then VALIDATE it by reading one of the files on a reference host and confirming the event appears — an unvalidated SACL is the commonest way this work is quietly wasted. Separately, the snapshot is only one road to this data: DCSync reaches directory contents through replication without any snapshot, and `esentutl` or a raw NTFS parser can read a locked file directly. Record the replication axis alongside, or the register will imply coverage it does not have.

# B053

Unit 42's campaign against Mexican transportation organisations stole credentials using the operating system's own backup machinery. Shadow copies were created across multiple drives, and batch scripts — run iteratively, permission-checking between attempts — copied the SAM hive and `NTDS.dit` out of the snapshots. No credential dumper was deployed, no memory was touched, and nothing had to defeat LSA protection, because the files were read from a snapshot where nothing held them open.

HEARTH already baselines part of this. B015 profiles who runs `vssadmin`, `diskshadow`, `ntdsutil` and `wbadmin` on domain controllers and compares that against maintenance windows. That is the right baseline for the command-line road, and this exercise does not rebuild it. It covers the two things that baseline structurally cannot see: snapshots created through the VSS COM or WMI API, which involve no process execution of any of those four binaries and are therefore invisible to a process-execution profile; and what is subsequently *read* out of a snapshot, which is where the actual theft happens and which no command-line rule observes at all.

## Why

- **A process-execution baseline cannot enumerate snapshots, only invocations.** Every real backup product calls `IVssBackupComponents` rather than shelling out, and so can any tooling that wants to avoid a conspicuous command line. An estate can have perfect coverage of `vssadmin` executions and still be unable to answer "which shadow copies exist on this domain controller right now" — which is the question an incident actually starts with.
- **Creation is not the objective, and the read is the part nobody logs.** Snapshotting a volume is preparatory and innocuous. Copying three specific files out of the snapshot is the theft. A backup agent streams an entire volume; an intruder takes `ntds.dit`, `SAM` and `SYSTEM` and stops. That contrast is close to unambiguous, and it is only visible if object-access auditing is configured — which is the single highest-value configuration change this exercise produces.
- **Running this audits visibility most estates wrongly assume they have.** VSS operational logs are rarely forwarded and SACLs on `ntds.dit` are rarely configured. The most common outcome of this work is not an intrusion — it is the discovery that the domain controllers were never instrumented for any of it, and that several existing NTDS detections have been structurally incapable of firing for as long as they have been deployed. That is worth knowing whether or not anyone is in the network.
- **Domain controllers are the cheap half and should be done first.** The legitimate snapshot population on a DC is small, scheduled, and owned by one product and one service account, so it can be fully characterised in days. Once it is, a single unattributed snapshot on a DC stops being ambiguous — and because the population is dominated by one well-behaved backup job, the residual list is genuinely short.
- **The same collection covers the destructive case at no extra cost.** Mass shadow-copy deletion is the standard ransomware precursor and is recorded by exactly the events gathered here. An organisation that builds this register for credential-theft reasons acquires ransomware-precursor visibility as a side effect, which makes it considerably easier to justify to the backup platform owners whose help is required to build it.
