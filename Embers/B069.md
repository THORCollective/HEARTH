false_positive_notes: |
  This is a baseline, so the deliverable is the allowlist itself and "false positive" means an entry that should have been on it. The entries that must be explicitly labelled during collection, rather than discovered during an incident:
  - Authorised scanning. The organisation's own external vulnerability scanning, attack-surface-management vendor, bug-bounty researchers and penetration testers all produce exactly the fingerprint and variety profile this baseline is built to surface. Record their source ranges and engagement windows as data, with dates, so a finding can be matched against them in seconds.
  - Search engine and SEO crawlers, uptime monitors, link checkers, social-media preview fetchers and archive bots. These are high-volume, declare themselves in the user agent, and are verifiable by reverse DNS for the major ones. Verify rather than trust the string - a user agent claiming to be a search crawler from an address that does not reverse-resolve to that provider is a finding, not an allowlist entry.
  - Partner and customer integrations using generic clients. A B2B partner calling an API with `python-requests` or `curl` is common and legitimate, which is exactly why the allowlist must be keyed on (application, client fingerprint, source network) together rather than on the user agent alone. A generic client from a known partner range is normal; the same client from a hosting provider is not.
  - Legitimate headless browsers. Internal end-to-end test suites, accessibility scanners and screenshot services run Playwright and Puppeteer against production. Label them by source range and schedule.
  - Background commodity scanning. Every internet-facing host is scanned constantly by research scanners and opportunistic actors. The baseline must measure this floor per application, because the hunt that depends on this baseline is about a source whose *variety and progression* exceed the floor, not about the existence of scanning.
  Collect in parallel with, not instead of, the existing WAF signatures. This baseline answers a question about populations; it does not replace request-level inspection.
notes: |
  Collection window - 30 days minimum, and 90 days if the application has a seasonal or business-cycle traffic pattern (quarter-end, enrolment periods, campaign launches). Anything shorter will miss the monthly scanner cadence and mistake it for novelty.
  Fields to collect per request, from the edge - timestamp; source IP; ASN and ASN name; hosting/VPN/Tor/cloud-provider classification; destination application identifier and hostname; HTTP method; URL path (normalised - replace numeric and GUID path segments with placeholders so paths group); query parameter *names* only, never values, so credentials and tokens are not copied into the baseline; HTTP status; request and response bytes; user agent string; HTTP version; TLS version and cipher; a client fingerprint (JA4 for the TLS handshake and JA4H for the HTTP request shape, or the CDN's equivalent field); and whether the request reached application logic or was terminated at the edge.
  Per-source, per-application aggregates to compute - these are what turn into the baseline:
  - Request rate: requests per minute, with the 50th, 95th and 99th percentiles across sources.
  - Path variety: the count of distinct normalised paths a single source touches in a 5-minute window, and the same figure as a fraction of the application's total distinct paths.
  - Error profile: the share of 4xx responses, broken out for 401/403 (authorisation probing) and 404 (path discovery).
  - Method mix: the set of HTTP methods one source uses, since a source that issues GET, POST, PUT and OPTIONS against one application is behaving unlike a browser or a crawler.
  - Progression: whether a source's requests move from discovery (404-heavy path probing) to interaction (POSTs with bodies, authenticated paths, upload handlers) inside one session, and how long that transition takes.
  - Client stability: whether a source presents one consistent client fingerprint or several, and whether its user agent and its JA4 fingerprint agree with each other.
  Fingerprints to enumerate and record explicitly - Microsoft's guidance for this activity names the default tooling of one framework: "ARTEX by default uses Nmap, curl, wget, Python HTTP clients, Norma SDK WebFetch, and headless Chromium through Playwright, among others." Build the baseline so each of these is a labelled bucket with a measured legitimate volume per application: Nmap's HTTP probes, `curl/<version>`, `Wget/<version>`, `python-requests/<version>`, `python-httpx/<version>`, `aiohttp/<version>`, Go's `Go-http-client/<version>`, and headless Chromium (recognisable by a Chrome user agent paired with a JA4H that lacks the header set a real browser sends, or by the absence of the request chain a browser makes for subresources). Microsoft is explicit about the limits of this: "These tools may send network traffic with distinctive characteristics, such as default user agent strings. While blocking network traffic with these characteristics will not stop an attack by an AI agent, which will quickly change them, identifying them can alert defenders to the activity." Treat the fingerprint list as a tripwire with a short half-life and the *variety and progression* metrics as the durable part of the baseline.
  Immediate flags - do not wait for the 30 days to finish before acting on these:
  - A source whose distinct-path count in 5 minutes exceeds the application's 99th percentile *and* whose session progresses from 404-heavy probing to a successful POST against an upload or authentication endpoint. This is the shape Microsoft describes: agentic frameworks "send a wide variety of requests in a brief time and retry variations on the same technique or move on to next-stage actions at machine speed."
  - A user agent claiming to be a browser or a known crawler whose client fingerprint contradicts it, or whose address does not reverse-resolve to the claimed provider.
  - Any successful (2xx) unauthenticated POST or PUT to an upload handler from a source classified as hosting, VPN or Tor.
  - An internet-facing application discovered by this collection that is absent from the asset inventory. Every exercise of this kind finds some; they are the highest-value output of the first week.
  - A request whose user agent field contains shell metacharacters or a command. Microsoft reports shell commands embedded in a user agent string, used to attempt exploitation, in its companion report on the same framework being used to find and abuse exposed secrets.
  Deliverable - per internet-facing application: (1) an allowlist of expected client fingerprints and source networks with a named owner for each, (2) the measured percentile curves for request rate, path variety, error share and method mix, (3) the labelled inventory of authorised scanners and monitors with their schedules, (4) a list of applications whose client population cannot be explained, each assigned to an owner, and (5) a note of which applications the edge cannot emit a client fingerprint for, since those are blind to the fingerprint half of the hunt.
  Flames hunts this baseline enables - H450 (web application service account fetching a RAT with netcat or curl after an anonymous upload or SSRF) needs the entry-point half of its correlation to be answerable, and that depends on knowing what normal looks like in the access log. It also sharpens any webshell hunt, because "a path no legitimate client has ever requested" is only computable from a path inventory.
  Expected, not observed by Microsoft: JA4/JA4H fingerprinting as the way to catch a user-agent string that has been changed is this baseline's recommendation, not Microsoft's. Microsoft states that actors change user agent strings and other fingerprints quickly, and recommends honeypots, decoys and tarpits as the countermeasure - "Defensive honeypots, decoys, tarpits, and fake wins can pull autonomous AI attacks away from legitimate targets." It does not name a specific fingerprinting scheme.

# B069

Microsoft Threat Intelligence gives defenders a list of the tools an agentic offensive framework reaches for by default: "ARTEX by default uses Nmap, curl, wget, Python HTTP clients, Norma SDK WebFetch, and headless Chromium through Playwright, among others." It then immediately tells defenders not to build a blocklist out of it, because the operator will change the strings as soon as they matter.

Both halves of that are right, and together they describe a baselining problem rather than a detection problem. The fingerprints are worth collecting - they are free, and an operator who has not yet bothered to change them hands over the first alert. But the signal that survives the operator caring is behavioural, and Microsoft states it precisely: agentic frameworks "send a wide variety of requests in a brief time and retry variations on the same technique or move on to next-stage actions at machine speed."

"A wide variety of requests in a brief time" is not a detection until an organisation knows what variety its applications normally see. Every internet-facing service is scanned continuously by research scanners, commodity bots, crawlers, uptime monitors, the organisation's own attack-surface tooling and, often, a partner integration nobody documented. Without the distribution, there is no way to say that a source touching 40 distinct paths in three minutes is unusual for *that* application - and no way to say that a source moving from path probing to a successful upload POST inside one session has done something no legitimate client does.

This is the baseline that makes that computable. It also tends to produce an unglamorous second finding on the first day: internet-facing applications nobody knew were internet-facing. Microsoft reports Storm-3358 using ARTEX "to scan systems connected to the public internet", and an agent enumerating an organisation's edge will find those hosts whether or not the organisation has.

Build this, and the pairing hunt H450 - a web application's service account fetching a RAT with netcat or curl after an anonymous upload or SSRF - gains the half of its correlation that lives in the access log.

## Why

- The indicators the vendor published have a deliberately short half-life, and the vendor says so. A baseline is the only form in which this intelligence keeps paying out after the operator changes their user agent, because it measures the thing the operator is optimising for throughput rather than the thing they are hiding.
- Request variety and session progression are per-application properties. A documentation site, a customer portal and a partner API have wildly different normal path counts, method mixes and error profiles, so a single organisation-wide threshold is simultaneously too loud for one and blind for another. Only a per-application distribution works.
- Machine-speed progression is the part agentic tooling cannot slow down without giving up its advantage. A human operator probes, reads, thinks and returns later; an agent probes, interprets and acts in one continuous session. Time-to-first-interaction after first-contact is a measurable feature, and it is one of the few that distinguishes agent-driven activity from commodity scanning on the same log line.
- Collection is cheap and already half-done. Edge access logs exist in every organisation with an internet presence; what is usually missing is the aggregation, the ASN and hosting enrichment, the client fingerprint field, and - most of all - the labelled list of which automation is authorised. That last item costs nothing to write down and saves hours on every subsequent investigation.
