false_positive_notes: |
  This is a baseline rather than a detection, so the objective is not to eliminate noise but to name it once and write it down. Three populations will dominate the collection and each must be labelled rather than filtered away. Developer workstations and build agents legitimately enable Developer Mode and register loose-file packages continuously; record them as a named population with their owners, because the value of the baseline is knowing exactly which hosts are entitled to that behaviour. Managed line-of-business deployment through Intune, Company Portal, Configuration Manager or a packaging agent also registers packages outside C:\Program Files\WindowsApps, and those should be captured as publisher-plus-deploying-agent pairs rather than as per-host exceptions, so a new host inherits the allowlist automatically. Third-party packaged applications reaching their own vendor infrastructure are legitimate AppX host egress, and enumerating those destinations is the single most useful output of this baseline, because it is the allowlist that makes the MSAppHost/3.0 proxy rule in [[H336]] operable instead of noisy. Two caveats on interpretation. Absence of evidence is weak here if collection is incomplete: the AppXDeploymentServer/Operational log is not always forwarded, so confirm ingestion per host before treating a quiet host as a clean host. And package publisher names are attacker-controllable in a sideloaded package, so allowlist on signing certificate thumbprint and signature kind (Store, Developer, Enterprise, None) rather than on display name.

  Collection window - 30 days of continuous collection, extended to 45 if the environment has a monthly patch or LOB release cycle that would otherwise be sampled only once. Re-baseline quarterly, and immediately after any change to Developer Mode policy or LOB packaging tooling.
  Fields to collect per package registration event - Hostname; host role and population label (developer, build agent, server, general business, kiosk/appliance); timestamp; user account and whether it is privileged; the full process command line; parent and initiating process image; package full name, package family name and display name; publisher display name AND signing certificate thumbprint; signature kind (Store, Developer, Enterprise, None); install or registration path, with an explicit flag for whether it is inside or outside C:\Program Files\WindowsApps; the AppXDeploymentServer/Operational result code; and the deploying agent if any (Intune management extension, Company Portal, ConfigMgr, packaging tool, interactive user).
  Fields to collect per Developer Mode state - Hostname; the value of AllowDevelopmentWithoutDevLicense and AllowAllTrustedApps under HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock; who set it and when (Sysmon Event ID 13 with the writing process and user); whether the host is in the developer population; and whether the setting was applied by policy or interactively. A per-host record of "Developer Mode on, no development role, set interactively" is the most valuable single row this baseline produces.
  Fields to collect per AppX host egress event - Hostname; initiating image (C:\Windows\System32\WWAHost.exe and any other AppX host binaries observed); the package identity responsible where telemetry exposes it; destination hostname, IP, ASN and owning organisation; client user agent as seen at the proxy (expect MSAppHost/3.0 with Edge/18 for AppX host traffic and Trident/7.0; MSAuthHost/1.0 for broker sign-in legs); destination classification as Microsoft-owned or not; bytes sent and received; and connection count per day. Collect with a query of the shape:
  DeviceNetworkEvents
  | where Timestamp > ago(30d)
  | where InitiatingProcessFileName =~ "WWAHost.exe"
  | summarize Days = dcount(bin(Timestamp, 1d)), Conns = count(), Sent = sum(tolong(coalesce(column_ifexists("SentBytes", 0), 0)))
      by DeviceName, RemoteUrl, RemoteIP
  | extend Microsoft = RemoteUrl has_any ("microsoft.com","microsoftonline.com","msauth.net","msftauth.net","windows.net","office365.com","sharepoint.com","windowsupdate.com")
  | order by Microsoft asc, Conns desc
  Fields to collect per host package inventory - Run Get-AppxPackage -AllUsers per host and record package family name, publisher, signature kind, install location, and whether InstallLocation sits outside C:\Program Files\WindowsApps; capture whether any AppxManifest.xml in a user-writable path declares ContentUriRules, and for each such rule the Match URL and the WindowsRuntimeAccess value.
  Deliverables - Four artefacts. (1) A population register naming every host entitled to Developer Mode and loose-file package registration, with owner and business justification, and a standing review date. (2) A publisher allowlist keyed on signing certificate thumbprint plus signature kind, covering Store packages, MDM-deployed LOB packages and the deploying agents that install them. (3) An AppX host egress allowlist of destination hosts and ASNs legitimately reached by packaged applications, expressed as the exception list for the MSAppHost/3.0 proxy rule, with the owning application named for each entry. (4) A per-host normal-volume profile for package registration events (most non-developer hosts should be zero) so that any non-zero value on a host outside the population register is a deviation by definition.
  Flag immediately, without waiting for the baseline to complete - Any AppxManifest.xml in a user-writable path that combines WindowsRuntimeAccess="all" with a ContentUriRule Match URL on a host the organisation does not own; this has no benign enterprise use outside active development and is the core enabling artefact. Any WWAHost.exe outbound connection carrying MSAppHost/3.0 to a non-Microsoft destination. Any Add-AppxPackage -Register against a path under \Downloads\, C:\Windows\Temp or a mounted removable or network volume. Developer Mode newly enabled interactively on a host with no development role, particularly by a standard user. Any package whose signature kind is None registered successfully. Treat each of these as an incident candidate rather than a baseline data point.
  What this baseline enables - [[H336]] hunts the specific abuse chain in which a sideloaded AppX package runs attacker JavaScript inside signed WWAHost.exe and drives the real Microsoft OAuth broker to steal Office tokens. That hunt's two workable legs — the proxy rule on MSAppHost/3.0 to non-Microsoft destinations, and package registration outside WindowsApps — are both unusable without the allowlists produced here, because in an unbaselined environment they fire on every developer and every legitimately sideloaded LOB app. Run this baseline first, or run it alongside, and treat its outputs as the exception lists that hunt consumes. The identity-side consequences of a successful token theft are covered by [[H272]] and [[H334]].

# B054

The AppX sideloading route to Microsoft 365 token theft is a genuinely difficult hunt, because it is assembled entirely from legitimate parts: a signed inbox binary (`WWAHost.exe`), a first-party client ID, the real `login.microsoftonline.com` dialog, and a package registration mechanism any standard user can invoke once Developer Mode is on. There is no malicious hash, no suspicious parent process, and no failed sign-in. The two detection surfaces that do work — a package registered from outside `C:\Program Files\WindowsApps`, and an AppX web host carrying the `MSAppHost/3.0` user agent to a destination Microsoft does not own — are both provenance questions, and provenance questions cannot be answered by a rule written in the abstract. In an environment with developers, MDM-deployed line-of-business apps, and third-party packaged software that talks to its own vendor cloud, both signals fire constantly and legitimately. This baseline exists to answer them once: which hosts are entitled to register loose-file packages, which publishers and deploying agents are expected, which hosts have Developer Mode on and why, and where packaged applications normally send traffic. With those four answers written down, the paired hunt becomes a short exception query; without them, it is unrunnable.

## Why

- The abuse chain has no malicious artefact to signature — signed binary, first-party app ID, authentic Microsoft login page, genuine MFA — so detection has to rest on what is normal for this estate, which is precisely what a baseline produces and a generic rule cannot.
- Both usable detection legs are dominated by legitimate activity in any real environment: developers register loose packages daily and MDM deploys LOB apps outside `WindowsApps`, so publishing the paired hunt without these allowlists would generate noise at a volume that guarantees it gets turned off.
- The enabling prerequisite is a user-writable setting rather than an administrative one, since Developer Mode is a registry value under `AppModelUnlock` and `Add-AppxPackage -Register` needs no elevation, which means the population entitled to this behaviour should be a short, named, reviewable list — and most organisations have never written that list down.
- Two of the baseline's outputs are actionable findings on their own even before the hunt runs: Developer Mode enabled interactively on a non-developer host, and any `AppxManifest.xml` granting `WindowsRuntimeAccess="all"` to a foreign URL, are exposures worth a ticket independent of whether token theft has occurred.
