false_positive_notes: |
  The collection phase has no findings to be false, but the allowlists it produces will be wrong in predictable ways unless these are handled during the build.
  - Instances are ephemeral and roles are not. An autoscaling group replaces instances continuously, so the address set behind a role changes by the hour while the role persists for years. Build the address allowlist from the subnet and NAT level upward rather than from individual instance addresses, or it will be stale within a day and every legitimate call will look like egress.
  - Shared NAT means many instances present one address. That is fine for the egress check - the address is still inside the environment - but it destroys per-instance attribution, so record the session name alongside the address and treat the instance ID in the session name as the unit of attribution rather than the address.
  - VPC endpoint traffic can appear with the endpoint's address or with a private address depending on service and configuration. Enumerate the endpoints in use during the build and include them explicitly; discovering them later, after the allowlist is in production, is how a baseline acquires a permanent exception nobody understands.
  - Roles used by both an instance and a human are common and ruin the vocabulary baseline. An administrator who assumes an instance role to debug contributes actions no instance ever calls. Record whether each session was established by the EC2 service or by a user and keep the two populations separate.
  - A new region or a new account looks exactly like anomalous behaviour. Capture the region set per role during the build and re-run the collection after any expansion, and keep an explicit note of which accounts were in scope, because an account missing from the baseline will generate findings for the life of the allowlist.
  - Entitlement is not usage and must not be substituted for it. A role's policy frequently permits far more than the role ever calls, which is the point of building the observed vocabulary. Do not shortcut the collection by generating the expected action set from the IAM policy.
notes: |
  Why this baseline exists - Elastic Security Labs' November 13, 2026 analysis of a CyberStrikeAI server in four AWS accounts turns on one observation that was only available because someone compared a source address against an inventory. Elastic reports that "the three role sessions were named after EC2 instance IDs, so the credentials came from instance profiles. Using them from an outside IP means they were taken from the instances, for example through SSRF or host compromise." That inference is trivially available to anyone holding the inventory and completely unavailable to anyone who is not, which is what makes it a baseline problem rather than a detection problem. Elastic's own closing guidance includes to "enable GuardDuty if it isn't already, and alert on credentials used from outside your expected IP ranges" - and the expected ranges are precisely what this hunt produces.
  What it enables - [[H474]] hunts a decrypting SSM parameter read followed by SendCommand and depends on being able to say that the calling session's address is not the instance or the NAT. [[H475]] hunts post-revocation success and uses the same per-identity normal-caller picture. [[B055]] is the Azure counterpart for service principal control-plane behaviour, and [[M050]] scores Azure service principals on cadence; this is the AWS instance-role equivalent of the data they rest on, and the three together cover the two major clouds. [[M072]] consumes the call-rate component of this baseline directly.
  Data collection fields - For every CloudTrail record whose userIdentity type is AssumedRole and whose sessionIssuer is an instance profile, collect: the role ARN; the session name, which carries the instance ID; the sessionContext creation date; sourceIPAddress; userAgent; awsRegion; eventSource; eventName; the request parameters that identify the target resource, specifically parameter names, secret identifiers, bucket names and instance IDs; errorCode and errorMessage where present; and the account ID. Alongside these, collect per instance profile: the set of instance IDs that have held it in the window; the private, public and elastic addresses of each; the subnet and VPC; the NAT gateway addresses for those subnets; the VPC endpoint identifiers in use; and the role's attached policies.
  Collection time window - 30 days, which covers a monthly batch cycle, quarter-end jobs that run on the last day, and enough autoscaling churn to make the subnet-level address allowlist stable. Extend to 90 days before finalising the action vocabulary for any role attached to infrastructure that runs on a quarterly cadence, because a role whose rarest legitimate action appears once a quarter will otherwise generate a finding the first time it runs.
  Deliverable format - Four artefacts, each machine-readable so a hunt can join against them.
  First, a source-address allowlist per instance profile: the set of CIDR ranges and endpoint identifiers from which that role may legitimately call, expressed at subnet and NAT level rather than per instance, with a last-verified date.
  Second, an action vocabulary per instance profile: every eventSource and eventName observed, with a call count, the number of distinct days it appeared on, and a flag for actions the policy permits but the role never called - that last column is a least-privilege work item as well as a baseline.
  Third, a rate profile per instance profile: median and 95th-percentile calls per hour, the maximum observed calls in any one minute, the median inter-call interval, and the distinct-resource count per hour, which is what [[M072]] needs to score a burst.
  Fourth, a region and account map per instance profile, so a call from an unused region is a one-line check.
  Immediate flags - Do not wait for the 30 days to complete. Escalate any of these on the day it is observed during collection.
  An instance-role session calling from an address outside every private range and outside the account's NAT and endpoint addresses - this is the condition Elastic's whole case rests on and it needs no baseline to recognise.
  An instance-role session calling sts:GetSessionToken or sts:GetCallerIdentity across more than one account, which an instance profile has no ordinary reason to do.
  An instance-role session reading EC2 userData for instances other than itself, since a legitimate instance role reads its own metadata through the local metadata service and not through the DescribeInstanceAttribute API against other instances.
  An instance-role session calling ssm:SendCommand where the role has never called it before.
  An instance-role session whose userAgent is a generic HTTP client or an SDK version inconsistent with every other session for that role.
  More than 20 distinct resources touched by one session inside 10 minutes, which is Elastic's own published rule threshold and a reasonable immediate flag while the local rate profile is still being built.
  How to build it - Run the collection from CloudTrail in Athena or an equivalent query layer rather than from an alerting pipeline, because the volume is large and the work is aggregation rather than matching. The one join that must be got right is the session name to the instance inventory: an instance that has been terminated since the call will not appear in a current inventory, so take the inventory from configuration-history records where available rather than from the live describe calls, or the baseline will report legitimate calls from retired instances as calls from unknown sources.
  Expected, not observed by Elastic - Any per-role rate figures. Elastic publishes two thresholds from its own detections - more than 20 distinct instances read for userData by one principal and source address in 10 minutes, and three or more distinct non-role identities calling GetCallerIdentity from one external address and ASN in 10 minutes - but these are product defaults rather than measurements of a particular environment, which is why the rate profile above is collected locally rather than adopted.
  Scope - Every AWS account in the organisation, not the production ones. Elastic's case spanned four accounts and the credentials used in it included a non-production role, with the report noting that "non-production environments often have weaker controls and sometimes share secrets with production, so access to one is worth treating as access to the other until shown otherwise." A baseline that covers only the accounts under close management describes the part of the estate that was never the problem.

# B072

Elastic's CyberStrikeAI case rests on one sentence that most organizations cannot write.

The role sessions were named after EC2 instance IDs, so the credentials came from instance profiles. Using them from an outside address means they were taken off the instances.

That is the whole inference. It took no malware analysis, no threat intelligence, no detection engineering. It took a source address and a list of which addresses that role is supposed to call from.

Try to produce that list for your own environment right now. For one role. Which addresses does it legitimately appear from — the instance, the subnet's NAT, which VPC endpoints? Which API calls does it actually make, as opposed to the ones its policy permits? How many distinct resources does it touch in an average hour, and what is the most it has ever touched in a minute?

Almost nobody has this. Which is why a stolen instance credential used from a server in Hong Kong reads as ordinary automation: every call is something an instance role does, from an address nobody has an opinion about, at a rate nobody has measured.

The good news is that the legitimate answer is small. An instance role's address set is the instance, the NAT, and the endpoints. Its action vocabulary is usually a handful of calls. Its rate is boring. This is one of the easier baselines in cloud, and it is the one that makes several specific hunts possible at all.

One warning about how to build it: do not anchor the allowlist to individual instance addresses. Autoscaling will churn them out from under you and the list will be wrong by tomorrow. Build it at subnet and NAT level, where it is stable.

## What to collect

Per CloudTrail record where the identity is an assumed role issued by an instance profile: role ARN, session name (which carries the instance ID), session creation time, source address, user agent, region, event source, event name, the request parameters naming the target resource, any error code, and the account ID.

Per instance profile: every instance ID that has held it in the window and each one's addresses, the subnet and VPC, the NAT gateway addresses, the VPC endpoints in use, and the attached IAM policies.

Take the instance inventory from configuration history rather than from live describe calls, so that instances terminated during the window still resolve.

## Window

Thirty days for the address allowlist and the rate profile. Ninety before finalising the action vocabulary for any role tied to quarterly infrastructure, or the first quarter-end run after you deploy will look like an intrusion.

## Deliverable

Four joinable tables: an address allowlist per role expressed as CIDRs and endpoint IDs; an action vocabulary per role with counts, day-coverage, and a column marking actions the policy permits but the role never uses; a rate profile per role with median and 95th-percentile hourly calls, peak calls per minute, and distinct resources per hour; and a region and account map per role.

The unused-but-permitted column in the second table is a least-privilege backlog that falls out of this work for free.

## Flag immediately, without waiting for the window to close

- An instance-role session calling from outside every private range and outside the account's NAT and endpoint addresses.
- An instance-role session calling `sts:GetSessionToken` or reaching across accounts with `sts:GetCallerIdentity`.
- An instance-role session reading EC2 `userData` for instances other than itself — a real instance role reads its own metadata locally, not through the API against its neighbours.
- A first-ever `ssm:SendCommand` from a role.
- A user agent that is a generic HTTP client, or an SDK version that matches nothing else that role has ever sent.
- More than twenty distinct resources touched by one session in ten minutes, as an interim threshold until the local rate profile exists.

## Why

- **It is the missing join, not a nice-to-have.** Several discrete hunts — the SSM credential-to-execution pair in [[H474]], the post-revocation check in [[H475]], the burst scoring in [[M072]] — all need to answer "is this caller where it should be?" and none of them can without this table. Building it once unblocks all of them.
- **The legitimate answer is genuinely small, which is rare in cloud baselining.** Instance roles are narrow by design: a short action list, a stable network position, a dull call rate. That makes this baseline cheap to build and unusually high-contrast once built, compared with baselining human or CI identities.
- **Session naming does the attribution work for you.** Because instance-profile sessions carry the instance ID, you get per-instance attribution even behind a shared NAT. That is a property of the platform you can rely on, and it means the baseline does not degrade in the common architecture.
- **It produces a least-privilege backlog as a side effect.** Comparing what each role may do against what it has ever done is the same collection, read a different way. Most estates find roles entitled to secrets and remote execution they have never once used.
- **Non-production is in scope or the baseline is decorative.** The reported intrusion used a non-production role, and non-production frequently shares secrets with production. A baseline scoped to the well-managed accounts describes the part of the estate that was never the risk.
