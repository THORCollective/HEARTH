false_positive_notes: |
  The hard part of this baseline is that in some organisations the answer to Unit 42 question is a
  perfectly legitimate yes, and in most organisations it is yes for a small number of hosts that nobody
  has written down. Expect genuine Web3 egress from several places. Engineers working on anything
  crypto-adjacent will talk to chains constantly, as will anyone evaluating a wallet SDK, a payments
  integration or a tokenisation feature, and that work is often exploratory and undocumented. Browser
  extensions are a large and surprising source - MetaMask and its equivalents poll RPC endpoints
  continuously from the browser process, so a developer who installed a wallet extension once will generate
  a steady stream of `eth_call` traffic forever, attributed to the browser rather than to any project. Some
  CI pipelines legitimately query chains in tests, and some test suites hit public testnets such as Sepolia
  or Goerli. A handful of mainstream packages pull chain data during install or postinstall for licence or
  telemetry reasons, which is bad practice but not malicious. And several non-blockchain products use
  JSON-RPC over HTTP, so matching on the transport rather than on the method plus destination will produce
  a flood of unrelated hits. Two rules keep the baseline honest. First, record rather than exclude - the
  deliverable is an allowlist of expected talkers with a stated owner and reason, not a filter, because an
  undocumented legitimate talker is itself a finding worth resolving. Second, attribute to a process and a
  project, not to a host: "this laptop talks to Ethereum" is useless, while "the browser wallet extension
  on this laptop polls Infura, and nothing else on it does" is a baseline entry. Finally, a warning that
  applies to every baseline but bites hardest here - a snapshot taken after a compromise enshrines the
  attacker resolver as normal. Where a supply-chain compromise is suspected, rebuild the expected set from
  lockfile history and pipeline definitions rather than from observed traffic.

  written against the mechanism with the method list treated as a per-chain vocabulary that keeps growing.
  The weak point in both versions is the exclusion clause - "not a browser and not developer Web3 tooling"
  is doing enormous work and nobody can enumerate it. This baseline is that enumeration. It is the artefact
  that makes [[H270]] precise instead of approximately right.
  The three architectural phases to cover, from Unit 42. Phase 1, EtherHiding: a hardcoded smart-contract
  address queried with read-only `eth_call` to retrieve a C2 domain from contract state. Unit 42 notes the
  weakness - the outbound payload exposes the contract address in the `to` field, so controls can block
  queries to that specific contract. Phase 2, cross-chain transaction data hiding, which Unit 42 calls
  TxDataHiding: encrypted C2 payloads embedded in the raw input data (calldata) of ordinary transactions
  sent to dynamic router contracts or burn addresses, read back via `eth_getTransactionByHash` or calldata
  parsing, with PolinRider implementing multi-tier fallback across TRON, Aptos and Binance Smart Chain so
  that a flagged chain is replaced by broadcasting a fresh transaction elsewhere. Phase 3, zero-data address
  resolution, which Unit 42 calls NullReceiver, identified in compromises of the front-end dependencies
  `bianira-ui` and `fluid-type-ui`: the loader queries an actor-controlled wallet for its latest zero-value
  transaction and extracts the C2 IPv4 address from the 20-byte recipient address itself - reading the
  recipient address, verifying an ASCII validation marker, converting the leading 4 bytes to decimal, and
  connecting outbound. Because the transaction carries zero value and zero data, Unit 42 notes "no code
  structure or domain string exists for security filters to inspect." Phase 3 is the reason the baseline
  must record destinations and methods rather than payload content: there is no payload.

  Source process name and full command line, where endpoint telemetry can attribute it.

  User or service identity, and for CI the pipeline identity and job ID.
  Destination hostname and resolved IP.

  Associated repository and lockfile entry, where the event can be tied to a dependency resolution.

  material change to the pipeline estate, because CI definitions drift weekly.

  (host plus process, or pipeline plus step), the destinations it reaches, the business reason, and a
  named owner. Plus two ranked reports that have value independent of any hunt - destinations by number
  of distinct talkers, which finds the shared gateway everything funnels through, and talkers by request
  volume, which finds the thing polling every thirty seconds. And an explicit organisational answer to
  Unit 42 question, recorded as a decision: is blockchain egress expected anywhere in this estate, and if
  not, is it blocked.

  chain families, which is the multi-tier fallback pattern Unit 42 describes for PolinRider.

# B060

Unit 42's first recommendation is a question: does your organisation have any reason to connect to a blockchain network at all? If the answer is no, they call it an easy win.

It is an easy win only if someone can answer it. Most organisations cannot, and the ones that think they can usually mean "no" when the truth is "yes, on four laptops and one build runner, for reasons nobody wrote down."

The reason it matters now is that Web3 C2 exists specifically to defeat everything downstream of a domain name. A loader that resolves its C2 from a smart contract has no domain to sinkhole, no IP to blocklist and no hardcoded endpoint for a registry scanner to find. Unit 42 traces three generations of this. EtherHiding reads a C2 domain out of contract state with `eth_call` — detectable, because the contract address is right there in the request. TxDataHiding moves the payload into transaction calldata and spreads fallbacks across TRON, Aptos and Binance Smart Chain, so blocking one chain just means the operator broadcasts on another. And NullReceiver removes the payload entirely: the loader asks a wallet for its most recent zero-value transaction and extracts the C2's IPv4 address from the 20-byte *recipient address* itself. No contract, no calldata, no string. As Unit 42 puts it, no code structure or domain exists for a filter to inspect.

Which is why this has to be a baseline and not a rule. [[H270]] already hunts the request shape — an HTTP POST to a chain RPC host carrying a read-only method. Read that hunt's own notes and you find the honest admission that its first version was EVM-specific and a Solana resolver slipped straight past it. But the deeper weakness is in its exclusion clause: *issued by a process that is not a browser and not developer Web3 tooling*. That phrase is carrying the entire detection, and nobody can enumerate it.

This baseline is that enumeration.

Collect per-event: source host and its role, process and parent, identity, destination and its classification, the JSON-RPC method where TLS inspection allows it, request cadence, whether DNS preceded the connection, and — where the event can be tied to a dependency resolution — the repository and lockfile entry. Thirty days minimum, and it has to span a release cycle, or the first production deploy after you finish will look like an attack.

Two things to expect, because they will otherwise look like failures. Browser wallet extensions are a large, boring source of chain traffic — MetaMask polls RPC endpoints forever, attributed to the browser, unrelated to any project. And some engineers legitimately talk to chains as exploratory work nobody documented. Record both rather than excluding them. An undocumented legitimate talker is a finding of its own; it just resolves differently.

What raises the stakes is what is on these hosts. Unit 42 notes that developer endpoints and runners hold elevated cloud tokens, service account keys and deployment secrets, and that ChainDrop searches *memory inside running build processes* for ephemeral IAM keys and short-lived OIDC federation tokens before the runner terminates. Short-lived credentials are no defence against a harvester running inside the build. And when the runner dies it takes the evidence with it — which means the egress record may be the only durable artefact the intrusion ever produces.

## Why

- **The mitigation Unit 42 leads with is unavailable without this list.** "Block blockchain egress if you never need it" requires knowing whether you need it, and nobody knows without collecting it.
- **It is the missing half of an existing hunt.** [[H270]] excludes "browsers and developer Web3 tooling" and that clause is unenumerated. The baseline turns an approximate exclusion into a named allowlist.
- **NullReceiver has no payload to inspect, so destination and sequence are all that remain.** Zero value, zero data, address extracted from the recipient field. Content inspection has nothing to work with; entitlement does.
- **Multi-chain fallback defeats per-chain blocking by design.** PolinRider spans TRON, Aptos and BSC so a flagged chain is replaced by a fresh transaction elsewhere. Only a list of who is *supposed* to talk to any chain survives that.
- **Process and project attribution is what makes the baseline usable.** "This laptop reaches Ethereum" is noise. "The wallet extension reaches Infura and nothing else on this host does" is an entry you can act on.
- **Browser wallet extensions will dominate the raw data and must be classified early.** They poll continuously and forever. Left unlabelled, they make the whole dataset look too noisy to use.
- **Short-lived credentials are not a control here, and the runner's death destroys the evidence.** A harvester reading memory inside the build gets valid tokens, and the ephemeral host that held the proof is gone minutes later. The network record outlives it.
- **A post-compromise snapshot enshrines the attacker's resolver as normal.** Where supply-chain compromise is suspected, rebuild the expected set from lockfile history and pipeline definitions rather than from observed traffic.
- **The ranked reports pay for themselves regardless.** Destinations by distinct talkers finds the shared gateway everything funnels through; talkers by volume finds the thing polling every thirty seconds. Both are hardening backlog, not hunt output.
