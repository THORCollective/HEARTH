false_positive_notes: |
  This is a baseline, so the output is an inventory rather than a verdict, and the usual false-positive framing is inverted - the risk is recording an attacker's artefact as normal. Two guards matter. First, do not seed the registers from observation alone; reconcile every VPN and remote-access product found against the approved-products list from change management, and treat an unknown-but-benign product as a governance finding to document and authorise rather than something to add silently. Second, run the H490 PE-metadata and configuration tests against each VPN-class binary found during collection before it enters the register, so an existing NtMonitor install is not baselined in as legitimate on day one.

  Legitimate SoftEther deployments will appear in the register with an `SEVPNBRIDGE` service and SoftEther Project registry keys. That is expected and useful - it is the control group. Record for each one the install path, the presence of `hamcore.se2` as a separate file, and the plaintext `vpn_bridge.config`, because those three facts are what an NtMonitor install cannot reproduce.

  Server and developer estates will produce large listening-socket inventories with high legitimate churn - container runtimes, local development servers, database engines and management agents all bind ports. Collect servers and workstations into separate registers with separate review cadences rather than one combined allowlist, or the server noise will swamp the workstation signal that this baseline exists to sharpen.

  Corporate VPN clients routinely hold long-lived sessions to hosting-provider address space, because the corporate concentrator may itself be hosted there. Record the approved concentrator endpoints explicitly so they can be excluded by identity rather than by ASN.
notes: |
  Collection window - 30 days, running continuously rather than as a single snapshot. Services, listening sockets and firewall rules all change on patch and deployment cycles, so a single enumeration will both miss legitimate variation and record whatever happened to be present. Re-enumerate services, sockets and firewall rules at least daily; collect the file inventory weekly; aggregate network sessions continuously.

  Fields to collect, per register.

  Register 1 - tunnelling-capable software. Per host and per binary - `device name`, `device role` (workstation or server), `file path`, `SHA256`, `OriginalFilename`, `FileDescription`, `ProductName`, `CompanyName`, `FileVersion`, `signer`, `signature trust state`, `file size`, `first seen`, `installing process command line`, and an `approved` flag resolved against the change-management list. Scope the sweep to the classes an actor can bridge with - SoftEther, OpenVPN, WireGuard, SSH clients and servers, `ngrok`, `frp`, `chisel`, `rathole`, `cloudflared`, `plink` and `stunnel` - but collect by capability rather than by name, since the point of the exercise is the tool whose name you do not yet know.

  Register 2 - services and listening sockets. Per service - `service name`, `display name`, `ImagePath`, `start type`, `run-as account`, `install event time`, `installing user`. Per socket - `process name`, `process path`, `PID`, `local address`, `local port`, `protocol`, `owning service`, `observation count over the window`. A per-host enumeration, with the output recorded rather than read interactively:

      powershell -NoProfile -Command "Get-NetTCPConnection -State Listen | Select-Object LocalAddress,LocalPort,OwningProcess,@{n='Process';e={(Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue).Path}} | Export-Csv -NoTypeInformation -Path C:\Windows\Temp\listeners.csv"

  Register 3 - host firewall rules and the processes that write them. Per rule - `display name`, `direction`, `action`, `enabled`, `profile`, `program path`, `local ports`, `remote ports`, `remote addresses`, `rule group`, `created or last modified time`. Per change - `initiating process path and command line`, `user`, and the rule as it stood before and after. Security Event IDs 4946, 4947 and 4948 record rule additions, changes and deletions when the Windows Filtering Platform audit subcategory is enabled, which is the collection prerequisite for this register; enable it before the window starts rather than discovering mid-window that the events are absent. The deliverable is the set of process paths that have ever legitimately created an inbound allow rule, which in most estates is a short list - the firewall MMC, Group Policy, the EDR installer, and a handful of named application installers.

      powershell -NoProfile -Command "Get-NetFirewallRule -Direction Inbound -Action Allow -Enabled True | Get-NetFirewallApplicationFilter | Select-Object Program | Sort-Object Program -Unique | Export-Csv -NoTypeInformation -Path C:\Windows\Temp\fw-inbound-programs.csv"

  Register 4 - normal long-lived outbound sessions. Per process and destination pair - `device name`, `initiating process path`, `signer`, `destination IP`, `destination ASN`, `destination organisation`, `ports`, `session span`, `connection count`, `bytes sent`, `bytes received`, `days observed in window`. The deliverable is a per-role threshold - what session span and byte volume to a hosting-provider ASN is unremarkable for a workstation, and separately for a server - so H491's `SessionSpan > 2h` filter can be tuned to the estate rather than used as a guess.

      DeviceNetworkEvents
      | where Timestamp > ago(30d)
      | where ActionType == "ConnectionSuccess"
      | where RemoteIPType == "Public"
      | summarize FirstSeen = min(Timestamp), LastSeen = max(Timestamp), Conns = count(), DaysSeen = dcount(bin(Timestamp, 1d)), Ports = make_set(RemotePort, 10)
          by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath, RemoteIP
      | extend SessionSpan = LastSeen - FirstSeen
      | summarize Hosts = dcount(DeviceName), Pairs = count(), MedianSpan = percentile(SessionSpan, 50), P95Span = percentile(SessionSpan, 95)
          by InitiatingProcessFileName, InitiatingProcessFolderPath
      | order by Pairs desc

  Immediate flags - escalate these during collection without waiting for the window to close.

  - Any unsigned or untrusted executable whose PE version resource describes it as a network monitor, or whose `OriginalFilename` is `netcapa.exe`, anywhere outside Program Files. Go straight to H490.
  - A service named `SEVPNBRIDGE`, or any new service whose `ImagePath` points outside Program Files, on a host that is not in the approved VPN-product list.
  - A `setting.conf` beside an unsigned executable, or an install directory carrying a SoftEther service registration with no `hamcore.se2` file present.
  - An inbound allow rule created by a process that is not on the short list of legitimate firewall writers, or any inbound allow rule whose display name references a product absent from the software register.
  - A listening socket bound by an unsigned binary outside Program Files on a workstation, in any profile other than loopback.
  - A host that has gained internal peers on 445, 3389, 5985, 5986, 389 or 636 that it never contacted in the preceding 30 days, which is H491's cascade leg.

  Deliverable format - four reviewed registers held where change management can see them, each as a host-and-process allowlist with an owner and a review date, plus one derived artefact per register. From Register 1, the list of approved VPN and tunnelling products with their expected paths, publishers and companion files. From Register 2, the expected service and listening-port set per host role. From Register 3, the short list of process paths permitted to write an inbound allow rule. From Register 4, per-role session-span and volume thresholds, and the named exclusion list of approved concentrator and SaaS endpoints.

  This baseline is what makes H490 and H491 runnable rather than theoretical, and it is also the control Rapid7 asks for directly - knowing intrinsic SoftEther behaviour in the estate is the only way to notice the next build, whose branding, endpoints and watermark will all differ. B048 baselines a different trust surface - root CAs, hosts-file entries and the local-proxy firewall rule that accompanies them - and overlaps with this register only in that both read firewall state; B070 baselines who may administer the hypervisor management plane, which is the equivalent exercise one layer down in the stack.

# B073

Rapid7's November 19, 2026 report on a custom SoftEther VPN Bridge build attributed to the China-aligned APT Webworm ends with an unusual recommendation for a threat report. Rather than a list of indicators to deploy, it tells defenders in the government sector to familiarise themselves with intrinsic SoftEther VPN behaviour, because the branding, the HTTP endpoints and the handshake watermark are all trivial for the actor to swap out, and the PE metadata already differs across the samples Rapid7 has seen.

That recommendation only works against a recorded normal. The structural artefacts that distinguish the actor's build from a legitimate one — a SoftEther service name with no `hamcore.se2` beside it, an encrypted `setting.conf` where a plaintext `vpn_bridge.config` belongs, an inbound firewall rule written by a process nobody authorised, a listening socket bound by an unsigned binary — are each anomalies only relative to an inventory. Without the inventory they are just facts about a Windows host, and the hunt degrades into reading version resources by hand on whichever machine someone thought to check.

This baseline builds the four registers the Flames hunts in this batch consume, and it is deliberately scoped by capability rather than by product name. The tool that matters next is the one whose name is not yet in any report.

## Why

- Every indicator in the source report is perishable by the vendor's own assessment, and the durable tests are all comparative. "No `hamcore.se2` in the install directory" requires knowing which directories hold legitimate SoftEther installs. "An unsigned network-monitor binary" requires knowing what is normally installed outside Program Files.
- The firewall-writer register is the cheapest and least-collected of the four, and it generalises well past this actor. In most estates the set of processes that legitimately create an inbound allow rule is a handful of named installers and Group Policy; the stock SoftEther functionality this tool inherits adds rules to the system firewall, so an unlisted writer is a high-signal, low-volume lead.
- Listening-socket and service inventories answer the lateral-movement question that outbound-only monitoring cannot. A bridged host is valuable to the actor because it mediates access to its neighbours, and that role shows up first as a bound port and a new set of internal peers, not as an outbound beacon.
- Collecting per-role session thresholds turns the duration filters in the accompanying Flames hunts from guesses into measurements. A two-hour session span is arbitrary until the estate can say what the 95th percentile looks like for the process in question.
