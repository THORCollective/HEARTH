false_positive_notes: |
  This is a baseline, so its output is an inventory rather than alerts, and the usual false-positive framing applies to the immediate-flag list rather than to the collection. The collection itself has two real hazards worth stating.

  The first is that a 30-day window under-counts monthly and quarterly automation. Integrations that run on a month-end schedule, certificate renewal jobs and quarterly reporting pipelines will be absent from a 30-day baseline and will then look novel the first time they fire. Where a longer window is not available from endpoint telemetry - Defender XDR advanced hunting keeps 30 days - carry the gap forward as a known limitation and reconcile the first month of findings against change records rather than treating them as detections.

  The second is that developer workstations and build agents will dominate the API-destination inventory and make it look unmanageably large. Partition by asset role before summarising. The useful product is not one list but several - what a developer workstation normally reaches, what a general user endpoint normally reaches, and what a server normally reaches - and the third is usually small enough to read line by line.

  Cross-tenant collaboration is legitimate and common, so a foreign tenant GUID in the register is not automatically hostile. The deliverable is attribution, not exclusion - every tenant on the allowlist should have a named owner and a reason.

  Service principals with long-lived client secrets are a finding in their own right and will surface in volume on most tenants. That is a hygiene result worth reporting separately; do not let it stall the baseline.

  Without TLS interception the grant-type and tenant-GUID legs cannot be measured at all, only the destination and process legs. Record which legs the estate can actually observe, because a hunt written against telemetry the estate does not collect reads as a clean result rather than as an unanswered question.
notes: |
  Collection window - 30 days of endpoint and proxy telemetry, which is the full Defender XDR advanced hunting retention; extend to 90 days where proxy or data-lake retention allows, specifically to capture monthly automation.

  Fields to collect, per observation - device name and asset role; initiating process name, full image path, signer, parent process and command line; remote hostname and URL path; destination tenant GUID and SharePoint hostname where present; OAuth grant type, scope and client ID where the proxy terminates TLS; authentication method, meaning client secret versus client assertion; first-seen and last-seen timestamps; connection count and byte volume; and for identity-side records, the service principal object ID and its credential type and expiry.

  Leg one, who asks for app-only tokens - Enumerate every `POST` to `login.microsoftonline.com` matching `/<GUID>/oauth2/v2.0/token` whose body contains `grant_type=client_credentials`, grouped by source host, initiating process and client ID. The deliverable is a table of approved application-credential holders - host, process, client ID, tenant, purpose, owner. In most estates this list is short and consists entirely of servers and management agents. Every workstation on it is either an exception with a named owner or a finding.

  Leg two, which API hostnames and which processes - Inventory outbound connections to cloud API hosts with the initiating process attached, partitioned by asset role:

      let apiHosts = dynamic(["graph.microsoft.com","login.microsoftonline.com","api.github.com",
                              "rest.ably.io","realtime.ably.io","main.pusher.ably.net",
                              "api.dropboxapi.com","content.dropboxapi.com","slack.com",
                              "api.telegram.org","discord.com","api.notion.com"]);
      DeviceNetworkEvents
      | where Timestamp > ago(30d)
      | where isnotempty(RemoteUrl)
      | extend Host = tostring(parse_url(strcat("https://", replace_string(RemoteUrl, "https://", ""))).Host)
      | where Host in~ (apiHosts) or RemoteUrl has_any (apiHosts)
      | summarize Connections = count(), TotalBytes = sum(toint(coalesce(column_ifexists("SentBytes", 0), 0))),
                  FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
          by DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath,
             InitiatingProcessParentFileName, RemoteUrl
      | order by DeviceName asc, Connections desc

  The `apiHosts` list is used and is a starting point, not a closed set - extend it with every SaaS the organisation has sanctioned, and then invert the question: run the same aggregation with no host filter at all, restricted to server assets, and read the long tail. The destinations nobody can account for are the output.

  Leg three, whose tenant - For every Graph request path, extract the SharePoint hostname and site GUID and compare against the register of owned and approved tenants. The Graph site-addressing form puts the hostname in clear text in the URL, so this is string comparison rather than inference. The deliverable is a tenant allowlist with an owner per entry; anything outside it is a question with a correct answer.

  Leg four, your own exposure - From the Entra side, enumerate service principals holding client secrets rather than certificate credentials, with secret expiry and assigned application permissions, and list which of those secrets exist anywhere on an endpoint. The ShadowCloud case runs on the attacker's own app registration, so this leg does not detect it - it measures the adjacent risk, which is one of your secrets being used the same way from outside.

  Deliverables - four artefacts, each a short document rather than a dashboard:

  - An approved application-credential register - host, process, client ID, tenant, owner, purpose. Anything performing a client-credentials grant and absent from this register is a detection.
  - A per-role SaaS API allowlist - which processes on which asset roles may reach which API hostnames, with normal connection counts and volumes.
  - A tenant allowlist - owned, acquired and approved partner tenant GUIDs and SharePoint hostnames, each with an owner.
  - A collection-gap statement - which of the four legs this estate can actually observe today, naming TLS interception coverage and retention explicitly.

  Immediate flags, to raise before the baseline is complete - a user workstation performing any client-credentials grant; a Graph or SharePoint request to a tenant GUID that is not on the register; any connection to a realtime-messaging or message-bus SaaS where the organisation has no sanctioned use, which for most estates includes everything in the Ably and Pusher families; a cloud API caller whose process image sits under `C:\Windows\System32` or `C:\ProgramData`; an API caller whose parent is services.exe; and any request to `api.github.com` or `graph.microsoft.com` carrying an `X-CSRF-TOKEN` header, a header neither API uses.

  Hunts this baseline enables - H503 (GitDoor over the GitHub API), H504 (Ably REST, WebSocket and SOCKS5 channels), H507 (GraphDoor app-only Graph channel to a foreign tenant). Each of those degrades to a process-attribution exercise without this measurement and becomes a single list comparison with it.

  Scope note: B064 is the closest existing baseline and the two are complements rather than duplicates. B064 answers one service deeply - what legitimate developer and tooling traffic to GitHub looks like, so an implant using a personal access token against a private repository is separable from a developer. This baseline answers the authentication and destination questions across the SaaS surface - who may hold application credentials, which API hosts each asset role may reach, and which tenants are ours - and it is the leg B064 does not cover, since GraphDoor and the Ably proxies never touch GitHub. B055 baselines service principals from the cloud side, including which ones legitimately read storage keys and at what rate, which is the inward-facing counterpart to leg four here. B020 and B035 cover dependency and package-install behaviour, a different surface. Run B052 alongside this one if the estate has not yet established where trusted binary names legitimately run from, because leg two's strongest red flag depends on it.

# B074

Operation ShadowCloud is a useful campaign to baseline against because it never once connects to anything suspicious.

GitDoor talks to `api.github.com`. GraphDoor authenticates to `login.microsoftonline.com` and then reads and writes through `graph.microsoft.com`. The proxy plug-ins tunnel TCP and SOCKS5 through a commercial realtime-messaging service with a valid certificate and real paying customers. Every destination is TLS, on 443, to a reputable and universally allowlisted host. Domain reputation finds nothing. Port and protocol analysis finds nothing. Certificate inspection finds nothing.

What does separate the implant from the environment is difference, and all three differences are measurements rather than indicators. A Java host process in System32 has never spoken to the GitHub API before. A user's workstation has never asked the Microsoft identity platform for an application-only token — that is something servers and automation do, not laptops. And the SharePoint tenant GUID in the Graph request path belongs to someone else entirely.

None of those questions can be answered during an incident. Each one needs a list that was built beforehand: who may hold application credentials, which processes may reach which cloud APIs, and which tenants are ours. This hunt builds those three lists, plus an honest statement of which of them the estate can actually observe.

## Why

- The whole class of SaaS-hosted command and control is defined by having no blockable infrastructure. Dead drops in GitHub issues, SharePoint lists, realtime-messaging channels and consumer storage all terminate at hosts the organisation cannot block and would not want to. Difference from a known-good list is the only control left, and it has to be measured in advance.
- An endpoint performing a client-credentials grant is a genuine anomaly, not a threshold. User endpoints authenticate users; application-only sign-in belongs to servers and automation. The exception list is short and enumerable, which makes this one of the highest-signal and lowest-cost measurements available on a Windows estate.
- The tenant question is answerable by string comparison and almost nobody has the string. Graph puts the target SharePoint hostname and site GUIDs in the URL path in clear text, so an implant uploading into the attacker's tenant is visible — if, and only if, a register of your own tenant GUIDs exists.
- Most estates have no sanctioned use for a realtime-messaging SaaS at all, which turns an entire destination family into a one-row answer. Establishing that once converts H504 from a hunt into a filter.
- Writing down what you cannot see is part of the deliverable. A hunt run against telemetry the estate does not collect returns a clean result that looks like absence of evidence, and the collection-gap statement is what stops that clean result from being believed.
