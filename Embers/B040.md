title: Baseline of update-themed scheduled tasks — which updater tasks are real, who registered them, and what they actually execute
hypothesis: >-
  Every LNK campaign type AhnLab tracked against South Korean targets in July 2026 ends the same way: a Task
  Scheduler entry named to look like a software updater. One is "disguised as a OneDrive update," another as a
  browser update, another registers `pythonw.exe` under a disguised name. The disguise works because Windows
  ships with hundreds of legitimate update-themed tasks — `MicrosoftEdgeUpdateTaskMachineCore`,
  `GoogleUpdateTaskMachineUA`, `OneDrive Standalone Update Task`, Defender scans — that run as SYSTEM on a
  schedule, and no defender knows the real list by heart. Build a 30-day fleet inventory of every scheduled task
  whose name suggests updating, keyed on the truth rather than the name: the `<Exec><Command>` path inside the
  task XML, the signer of that binary, the registering account, and the fleet prevalence. The alertable event is
  then a task whose NAME claims a vendor and whose COMMAND does not point at that vendor's install directory.

required_data_sources:
  - Windows Security Event ID 4698 (task created) fleet-wide — TaskName, **TaskContent (the full XML)**, SubjectUserName, SubjectDomainName, SubjectLogonId. The XML is the whole point — it carries `<Exec><Command>`, `<Arguments>`, `<Principal><UserId>`, `<Author>` and the trigger, so the claimed identity and the real one arrive in a single event
  - Windows Security Event ID 4702 (task updated) — the create-then-modify pattern, where the name is left intact and only the payload changes. This is stealthier than creation and is monitored far less
  - Windows Security Event IDs 4699 / 4700 / 4701 — deletion, disabling, enabling. Needed to see cleanup and to see a hidden task being re-enabled
  - Microsoft-Windows-TaskScheduler/Operational Event IDs 106 (registered), 140 (updated), 141 (deleted), 200/201 (action started/completed) — an independent record that survives when Security auditing is misconfigured, and the only source that shows what the task actually RAN as opposed to what it was defined to run
  - A live filesystem/registry survey of `C:\Windows\System32\Tasks\` and `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree` — the point-in-time inventory. This catches tasks that predate the collection window and tasks registered through the COM API without a `schtasks.exe` process. Tasks hidden by deleting the SD value from TaskCache are visible here and nowhere else
  - Sysmon Event ID 1 / Windows Security 4688 — `schtasks.exe` and `Register-ScheduledTask` invocations with parent lineage, so a task can be attributed to the process that created it. Note that COM-based and PowerShell-cmdlet registration produce no `schtasks.exe` event at all, which is why 4698 and the filesystem survey are both required
  - Code-signing and file metadata for every binary named in an `<Exec><Command>` — signer, OriginalFileName, CompanyName, and whether the path is user-writable. An "updater" task pointing at an unsigned binary in `ProgramData` is the finding
  - Software inventory / SCCM / Intune application catalogue and the deployment account list — the authoritative mapping from vendor to expected install path and to the accounts allowed to register tasks. Without this the inventory has task names but no way to judge them
  - Fleet asset list — the prevalence denominator. "This updater task exists on 1 host of 4,000" is the highest-value derived field in the inventory
false_positive_notes: |
  Update-themed scheduled tasks are overwhelmingly legitimate — that is exactly why the disguise is chosen, and
  why this is a baseline rather than a rule. Expect the initial inventory to be dominated by:
  - Microsoft's own: Edge (`MicrosoftEdgeUpdateTaskMachineCore`/`UA`), OneDrive Standalone Update Task,
    Office ClickToRun, Windows Update Medic, Defender scheduled scans, `\Microsoft\Windows\` subtree tasks.
  - Third-party updaters: Google Update, Adobe ARM/AGSUpdater, Java, Dropbox, Zoom, Slack, Chrome, browser
    vendors generally, and print/driver updaters.
  - Endpoint management and security agents registering their own maintenance tasks.
  - Line-of-business software with self-updating components, and in-house deployment tasks pushed by GPO,
    SCCM or Intune.
  None of these require individual judgement once inventoried, because each has the same three properties: it
  appears on many hosts, its `<Exec><Command>` points into that vendor's own install directory under
  `Program Files` or `%LOCALAPPDATA%\<Vendor>\`, and it was registered by SYSTEM, an installer, or a known
  deployment account. What must NOT be done is to build a name-based allowlist: the entire technique consists of
  choosing a name that is already on your allowlist. The inventory is keyed on the command path and the signer,
  and the name is treated as untrusted input.
  Two genuine tuning problems to expect:
  - Vendor updaters legitimately change their command paths across versions, producing "new" entries after
    patch cycles. Refresh the baseline monthly and treat the days after a major deployment as an expected burst.
  - Self-updating applications that relocate into `%LOCALAPPDATA%` legitimately blur the user-writable-path
    signal. Enumerate these specifically; there are usually fewer than a dozen and they should be named.

  PLATFORM: Windows. T1036.004 also covers Linux and macOS (systemd units, launchd jobs), which are a separate
  baseline with separate telemetry and are out of scope here.

  Kimsuky. The report cites no ATT&CK IDs; this mapping is derived from described behaviour. Scheduled-task
  persistence appears in five of the seven classified campaign types: Type A registers a task "disguised as a

  base64 payload in `%temp%`; Type D uses a task "disguised as a browser update" for periodic script execution;
  Type E registers VBS, BAT and PowerShell components with Task Scheduler; Type F's BAT "installs a Python
  package and registers `pythonw.exe` under a disguised name in the Task Scheduler." Critically, the report
  publishes NO actual task names and NO verbatim command lines — it describes them only. That is the shape of
  intel this Ember is built for: the behaviour is confirmed and repeated, but there is no IOC to write a rule
  against, so the only durable detection is knowing your own environment's real updater set.

  COLLECTION WINDOW: 30 days minimum for the event-based half, extended to 45 where the estate has a monthly
  patch cycle — vendor updaters register and re-register tasks around deployment, and a window that misses the
  cycle will report a false burst of novelty afterwards. The filesystem/registry survey is point-in-time and
  should be run at the start and end of the window, plus monthly thereafter.

  FIELDS TO COLLECT PER TASK: host, task_full_path (including folder, e.g. `\Microsoft\Windows\...`), task_name,
  exec_command_path, exec_arguments, working_directory, principal_userid, principal_runlevel, author,
  registered_by_account, registered_by_process, registration_time, trigger_type, trigger_interval,
  command_binary_signer, command_binary_signature_status, command_binary_original_filename,
  command_binary_company, command_path_is_user_writable (bool), name_claims_vendor (parsed from task name),
  command_matches_claimed_vendor_path (bool), fleet_prevalence_count, hidden_from_ui (bool, from missing
  TaskCache SD value), last_modified_time, modification_count.

  THE TWO DERIVED FIELDS THAT DO ALL THE WORK are `name_claims_vendor` and
  `command_matches_claimed_vendor_path`. Parse the vendor claim out of the task name — "OneDrive", "Edge",
  "Chrome", "Google", "Adobe", "Update", "Java", "Defender" — then check whether the `<Exec><Command>` actually
  resolves inside that vendor's install directory with that vendor's signature. A task called
  "OneDrive Update Task" whose command is `C:\ProgramData\<random>\svc.exe` fails that check instantly and
  needs no threshold, no history, and no analyst judgement. This one boolean is the deliverable that justifies
  the whole collection effort.

  DELIVERABLES — three artifacts, refreshed monthly:
  (1) THE UPDATER-TASK INVENTORY. Every scheduled task in the estate whose name suggests updating or
      maintenance, keyed by (task path, exec command path, signer), with prevalence counts and first/last seen.
      This is the reference object.
  (2) THE VENDOR-CLAIM MISMATCH REPORT. Every task where `name_claims_vendor` is true and
      `command_matches_claimed_vendor_path` is false. In a healthy estate this list should be short and every
      entry should be explainable — repackaged deployments, in-house wrappers, and legacy tooling. It is the
      standing risk register for this technique and its length is a fair measure of the estate's hygiene.
  (3) THE REGISTRATION PROFILE. From 30 days of 4698/4702: which accounts and which parent processes
      legitimately register scheduled tasks here, and at what times. This is what lets a Flames-style rule fire
      on "task registered by an interactive user session descended from an LNK" without an allowlist that ages.

  IMMEDIATE FLAGS — escalate on sight, no baseline needed to interpret:
  (1) A TASK WHOSE NAME CLAIMS A VENDOR BUT WHOSE `<Exec><Command>` POINTS OUTSIDE THAT VENDOR'S INSTALL PATH —
      especially into `C:\ProgramData\`, `%APPDATA%`, `%LOCALAPPDATA%\Temp`, `%TEMP%` or `C:\Users\Public\`.
  (2) A TASK COMMAND THAT IS A SCRIPT INTERPRETER — `powershell.exe`, `wscript.exe`, `cscript.exe`, `mshta.exe`,
      `pythonw.exe`, an AutoIt interpreter — with arguments pointing at a user-writable path. `pythonw.exe`
      "under a disguised name" is the source report's Type F verbatim.
  (3) BASE64, `-enc`, `-EncodedCommand`, `FromBase64String`, `IEX`, `DownloadString`, or an http/https URL
      anywhere in `<Arguments>`. No legitimate updater task needs any of these.
  (4) A TASK REGISTERED BY AN INTERACTIVE USER SESSION whose ancestry includes `explorer.exe` opening an LNK,
      or `powershell.exe`/`cmd.exe` from a temp path — rather than by SYSTEM, an installer, or a deployment
      account. Join 4698's SubjectLogonId to the 4624 for that session to get the answer.
  (5) 4698 FOLLOWED CLOSELY BY 4702 ON THE SAME TASK NAME — create the task, then change what it executes.
      Also 4702 alone against a long-standing Microsoft task, which is task hijacking and leaves the trusted
      name entirely intact.
  (6) A TASK PRESENT ON EXACTLY ONE HOST where every other updater task in the inventory appears on hundreds.
  (7) A TASK HIDDEN FROM THE TASK SCHEDULER UI — present in `TaskCache\Tree` with the SD value removed. There
      is no legitimate reason for this and it is only visible via the registry survey.

  PREREQUISITE, CHECK THIS FIRST: 4698 and its siblings do not appear unless the "Audit Other Object Access
  Events" subcategory is enabled. Many estates believe they collect task creation and do not. Verify on a
  sample of hosts before starting the window, and enable the TaskScheduler/Operational log as an independent
  second source — it is off by default on some builds and it is what catches COM-API registration that produces
  no `schtasks.exe` process event.

  VALIDATION: after the first inventory, run Atomic Red Team T1053.005 tests — including the WMI/CIM
  `RegisterByXml` variant against `PS_ScheduledTask`, which deliberately avoids `schtasks.exe` — and confirm all
  registration paths surface in the collection. Then register a benign task named `OneDrive Update Task` whose
  command points at a binary in `C:\ProgramData\` and confirm it appears in deliverable (2) within a day. If it
  does not, the vendor-claim parsing is not covering the naming pattern actually used, which is the most common
  silent failure of this hunt.

  use is structurally identical to administrative use, and no rule can fire without first knowing which updater
  tasks are real here. Alchemy rejected — it was a genuine contender, since task names could be scored on

  tuning surface and opacity to a question a lookup answers correctly, and analysts act on "the OneDrive task

# B040

Five of the seven campaign types in one month's Korean APT reporting end with a scheduled task. One calls itself a OneDrive update. One calls itself a browser update. One registers `pythonw.exe` under a name chosen to look like something you installed on purpose.

The report publishes no task names. No command lines. Nothing to write a rule against — which is honest, because the names were chosen to blend into whatever the victim already had, and would not have generalised anyway.

That leaves one durable question, and it is not "is this task name suspicious." Windows ships hundreds of legitimate update tasks running as SYSTEM, and no defender knows the real list from memory. The question is whether the task's `<Exec><Command>` points where its name claims it should. A task called "OneDrive Update Task" that runs a binary out of `C:\ProgramData\` is answering that question for you. You just have to be in a position to ask it.

## Why

- **The name is the lie and the XML is the truth, and Event 4698 hands you both in one record.** This is unusually convenient. The event carries the full task definition — the command path, the arguments, the principal, the author, the trigger — alongside the name the attacker chose. There is no join, no enrichment, no second source needed to compare the claim against the reality. Most estates collect 4698 already and use it only to note that a task was created, discarding the field that makes the event decisive.

- **A name-based allowlist is self-defeating, which is exactly why this must be a baseline.** The technique is choosing a name that is already trusted. Any list of "safe updater task names" is a list of names the adversary will pick from — APT29 named a task `\Microsoft\Windows\SoftwareProtectionPlatform\EventCacheManager` for precisely this reason. Keying the inventory on the command path and the binary's signer, and treating the name as untrusted input, inverts that: the closer the name is to a real Microsoft task, the more conclusive the path mismatch becomes.

- **One derived boolean does most of the work and it is cheap to compute.** Parse the vendor claim out of the task name; check whether the command resolves inside that vendor's install directory with that vendor's signature. `command_matches_claimed_vendor_path` is a few lines of string handling over data you already have, and it produces a report that needs no threshold and no analyst judgement to read. Everything else in this baseline exists to make that one field accurate.

- **Fleet prevalence separates the vendor population from the intrusion population for free.** Real updater tasks are deployed by installers to hundreds or thousands of hosts under identical names and identical paths. A campaign's persistence lands on one host, from one email, once. Sorting the inventory by prevalence ascending puts the anomaly at the top of the list with no model and no tuning, and it keeps working when the next campaign picks a different disguise.

- **Task hijacking is the variant nobody watches, and it hides inside a name you have already approved.** Event 4702 fires when an existing task is modified — leave the trusted Microsoft name intact and change only what it executes, and every name-based control in the estate is satisfied. Windows ships hundreds of SYSTEM-privileged tasks to choose from. 4702 is collected far less often than 4698, and a 4698 immediately followed by a 4702 on the same task is the create-then-swap pattern that defeats detections evaluating the definition only at creation time.

- **The registration profile is what makes the paired Flames hunts precise.** Both [[H275]] and [[H276]] want to alert on persistence registered by an interactive user session descended from an opened LNK. Whether that filter is accurate depends entirely on knowing which accounts and parent processes legitimately register tasks in this specific estate — which differs enormously between an Intune-managed fleet and one where users install their own software. Thirty days of 4698 with lineage answers it definitively, and it is usually a short list.

- **Check the audit prerequisite before anything else, because plenty of estates believe they collect this and don't.** 4698 and its siblings require the "Audit Other Object Access Events" subcategory, which is off by default. Registration through the COM API or `Register-ScheduledTask` produces no `schtasks.exe` process event at all, so a hunt built on process creation has a silent gap. And a task can be hidden from the Task Scheduler UI entirely by removing its SD value from `TaskCache\Tree` — invisible in the console, visible in the registry survey. Three separate collection blind spots, all of which this baseline is designed to surface on day one rather than discover during an incident.

- **HEARTH had no T1036.004 coverage,** despite masqueraded tasks and services being the standard persistence finish to nearly every commodity and state-aligned intrusion chain, and despite the disguise being the specific reason those tasks survive routine review.
