  applications, developer toolchains and imaging software all ship vendor guidance asking for specific

false_positive_notes: |
  This is an inventory exercise, so the operative question is what belongs in the register rather than what to suppress, and most of what you collect will be legitimate. Expect a large population of exclusions and expect to be surprised by its size. Backup and replication agents, SQL Server and other database engines, Exchange, domain controllers, Hyper-V and virtualisation hosts, EDA/CAD packages, developer toolchains, build agents, imaging and deployment software, and a long tail of line-of-business applications all have published vendor exclusion guidance, and following it is correct. Microsoft itself publishes automatic and recommended exclusions for server roles. None of that is a finding; all of it belongs in the register WITH A JUSTIFICATION AND AN OWNER.
  Two discriminators do nearly all the work. The first is BREADTH - a vendor-recommended exclusion is narrow and specific, naming a product directory, a database file extension or a named service binary. A drive-root exclusion (`C:\`), a user-profile-tree exclusion (`C:\Users`, `%TEMP%`, `%APPDATA%`), a wildcard (`*`), or an extension exclusion for `.exe` or `.dll` is not vendor guidance under any reading and should be treated as an immediate flag. The second is PROVENANCE - a sanctioned exclusion is applied by the endpoint management agent or by GPO/Intune policy, so the writing process is the policy application path (`svchost.exe -k netsvcs -p -s gpsvc`) or the management extension, and it appears identically across a policy-defined population. An exclusion set locally by `reg.exe`, `powershell.exe`, an MSI, a script host, or an installer running from a user's Downloads folder, present on one host or a handful, is the opposite shape on every axis.
  Three cautions that will corrupt the baseline if ignored. First and most important - AN EMPTY OR THIN RESULT IS AMBIGUOUS AND MUST BE RESOLVED BEFORE IT IS BELIEVED. It may mean the estate is clean; it may mean you are reading only one of the two hives; it may mean your collection reaches only the hosts your configuration-assessment coverage reaches; or it may mean `HideExclusionsFromLocalAdmins` is suppressing the API view on exactly the hosts you most need to see. Validate the collection path end to end by setting a known test exclusion on a reference host and confirming it appears in every path you intend to rely on, including as SYSTEM. Second, tamper protection legitimately prevents some reads and some tooling, which can make a well-protected host look unenumerable - distinguish "protected" from "concealed" by checking the tamper-protection state alongside the exclusion read, not by inferring from a failed query. Third, the two hives are not interchangeable - the Defender service writes exclusions set via PowerShell and WMI to `HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions`, while Group Policy writes to `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions`, and querying normally returns the union. An inventory that reads one hive and reports it as the answer is wrong by construction.
detection_queries:
  - platform: PowerShell (per-host collection, run as SYSTEM)
    description: Collect both views plus the concealment flag and protection state in one record. The ApiCount-versus-registry comparison is the enumeration-integrity result.
    query: |
      $pref = Get-MpPreference
      $mdavRoot = 'HKLM:\SOFTWARE\Microsoft\Windows Defender\Exclusions'
      $polRoot  = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions'
      function Get-ExclHive($root) {
        foreach ($t in 'Paths','Processes','Extensions','IpAddresses') {
          $k = Join-Path $root $t
          if (Test-Path $k) {
            (Get-Item $k).Property | ForEach-Object { [pscustomobject]@{Hive=$root;Type=$t;Value=$_} }
          }
        }
      }
      [pscustomobject]@{
        Host         = $env:COMPUTERNAME
        HideFlag     = (Get-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows Defender' -EA SilentlyContinue).HideExclusionsFromLocalAdmins
        ApiPaths     = @($pref.ExclusionPath).Count
        ApiProcesses = @($pref.ExclusionProcess).Count
        ApiExtensions= @($pref.ExclusionExtension).Count
        ApiIpAddress = @($pref.ExclusionIpAddress).Count
        RegistryList = @(Get-ExclHive $mdavRoot) + @(Get-ExclHive $polRoot)
        TamperState  = $pref.DisableTamperProtection
        RealTime     = -not $pref.DisableRealtimeMonitoring
        Behavior     = -not $pref.DisableBehaviorMonitoring
        CloudProt    = $pref.MAPSReporting
      }
  - platform: Microsoft Defender XDR (KQL)
    description: Event-driven axis - every exclusion and policy write across the estate with its writing process, so provenance can be classified rather than guessed.
    query: |
      DeviceRegistryEvents
      | where Timestamp > ago(30d)
      | where RegistryKey has @"\Windows Defender\Exclusions"
         or RegistryValueName =~ "HideExclusionsFromLocalAdmins"
      | summarize Hosts=dcount(DeviceName), FirstSeen=min(Timestamp), LastSeen=max(Timestamp),
                  SampleHosts=make_set(DeviceName, 10)
                by RegistryKey, RegistryValueName, RegistryValueData,
                   InitiatingProcessFileName, InitiatingProcessCommandLine
      | order by Hosts asc
  - platform: Microsoft Defender XDR (KQL)
    description: Stack the exclusion population by value to separate fleet-wide policy from one-host anomalies. A value present on 1-2 hosts is the tail worth reading line by line.
    query: |
      DeviceRegistryEvents
      | where Timestamp > ago(30d)
      | where RegistryKey has @"\Windows Defender\Exclusions\"
      | extend ExclType = tostring(split(RegistryKey, "\\")[-1])
      | summarize HostCount=dcount(DeviceName) by ExclType, RegistryValueName
      | order by HostCount asc
  - platform: Shell (immediate-flag screen)
    description: Patterns to flag without waiting for the baseline to complete - overbroad carve-outs.
    query: |
      reg query "HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions\Paths"
      reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions\Paths"
      reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows Defender" /v HideExclusionsFromLocalAdmins
notes: |
  Platform: Windows. Driven by Huntress (Jonathan Johnson), "You Can Run, but You Can't Hide: Defender Exclusions" (last updated September 30, 2026). This is the inventory half of that research; [[H355]] is the detection half, covering the `HideExclusionsFromLocalAdmins` registry write as a standing high-severity rule.
  Collection window - 30 days, running continuously, for the EVENT-driven axes (exclusion writes, Defender configuration changes, protection-state changes). Thirty days covers a full monthly cycle including patch Tuesday, monthly maintenance windows, MSP scheduled work and month-end processing, which is when most legitimate agent and management activity clusters. The CONFIGURATION axes - the two exclusion hives, the concealment flag, tamper-protection and real-time-protection state - are POINT-IN-TIME and should be snapshotted on day one and again on day thirty, because the value of this baseline is the diff. The sanctioned-exclusion list is not derived from telemetry at all - collect it on day one from vendor hardening guidance, the software asset register and the IT service catalogue.
  Why the double collection is the defining feature of this baseline - Huntress established that `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\HideExclusionsFromLocalAdmins`, when set, prevents the exclusion list being returned to queries, and that "although this registry value says 'HideExclusionsFromLocalAdmins,' it also stops SYSTEM users from querying this data". Their closing observation is the one this baseline is built on - "administrators and SYSTEM users can still query this data. They just need to do it through the registry directly." An inventory that calls `Get-MpPreference` and records the answer therefore has a failure mode where it reports a short, reassuring list from precisely the host an operator has carved open, with no error. Collecting the hives separately and comparing counts turns that failure mode into a positive detection - a per-host enumeration-integrity result that is a deliverable in its own right.
  Why both hives, not one - Huntress traced the write paths. PowerShell (`Set-MpPreference`/`Add-MpPreference`) routes through the `MSFT_MpPreference` WMI class, then COM and RPC, to `MsMpEng.exe`, which writes to `HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions`. Group Policy routes through the Group Policy `svchost` (`C:\Windows\system32\svchost.exe -k netsvcs -p -s gpsvc`) and writes to `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions`. These are different keys, and a query of exclusions returns both. Huntress also found that Defender locks down direct writes to the first key, making the POLICY hive the one an attacker can modify directly - for example `reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions\Paths" /v "C:\Temp" /t REG_SZ`, with the caveat that "this policy requires a reboot to take place". So the policy hive is simultaneously the attacker-writable one and the one that carries the concealment flag, which is why it must be read explicitly rather than trusted to the API union.
  Why registry-operation telemetry is the right event collection point - Huntress's engineering conclusion, which they adopted for their own agent, is that "no matter how someone sets an exclusion, it needs to be set in the registry. This allows us to see if someone sets this exclusion via PowerShell, WMI, GPO, or manually." A baseline built on PowerShell transcripts or WMI auditing alone misses the other methods; one built on registry writes to the two key paths sees all four, including methods not yet in use.
  The four exclusion types and what each actually disables, per Microsoft as summarised by Huntress - `Process` disables real-time scanning on files OPENED BY a specified source process (note the direction - it is the opening process that is excluded, not the files); `Path` excludes entire file paths from real-time and scheduled scans; `Extension` disables real-time, scheduled and custom scans for given extensions; `IpAddress` disables network packet inspection from a given IP. Huntress note `Path` and `Extension` are "the two types of exclusions that are most used and valuable to an attacker", because a match removes the target "from scheduled scans, on-demand scans, and always-on, real-time protection and monitoring". Record the type on every register entry, because the blast radius differs sharply between them - an `IpAddress` exclusion disabling packet inspection is a network-visibility loss that will not show up in any file-scanning review.
  Fields to collect, per exclusion - `exclusion type` (Path, Process, Extension, IpAddress), the `exact value`, the `hive` it lives in (Defender hive or Policy hive), `scope` (local registry, GPO, Intune/Configuration Manager), `who set it` (account and process image, from Sysmon Event ID 13 or Defender 5007 old/new values), `when`, the `host population` it appears on (count and business unit), and the `justification` with a NAMED BUSINESS OWNER. Produce a per-value host count - that number alone separates fleet policy from one-host anomalies better than any other single field.
  Fields to collect, per host - `HideExclusionsFromLocalAdmins` value, the API-visible counts for all four types, the registry-derived list, `tamper protection state`, `real-time protection state`, `behaviour monitoring state`, `cloud-delivered protection state`, and the ENUMERATION-INTEGRITY RESULT (do the API and registry views agree). Compute estate-wide coverage percentages for the protection states - those percentages are a headline deliverable.
  Immediate flags, do not wait for the baseline to complete - (1) `HideExclusionsFromLocalAdmins` set on any host, with no corresponding GPO or Intune profile and owner - escalate via [[H355]]; (2) any host where the API-visible exclusion list and the registry hives DISAGREE; (3) an exclusion at a drive root or of obviously excessive breadth - `C:\`, `C:\Users`, `%TEMP%`, `%APPDATA%`, `*`, or an extension exclusion for `.exe` or `.dll`; (4) any exclusion written by a process that is not the endpoint management agent or policy application - especially `reg.exe`, `powershell.exe`, `wmic.exe`, an MSI, or an installer running from a Downloads folder; (5) tamper protection or real-time protection disabled on any host; (6) an exclusion whose value points at a user-writable path (`Downloads`, `AppData`, `ProgramData` subdirectories created recently, `C:\Temp`); (7) a Defender 1116/1117 detection whose path falls inside an existing exclusion, which indicates the exclusion was added after malware was already present; (8) an exclusion present on exactly one host in a managed fleet.
  Deliverable format - three artifacts. An APPROVED-EXCLUSION REGISTER - one row per distinct exclusion value with type, hive, scope, host count, justification and named owner, reviewed and signed off by the application owners rather than by the security team alone. An ENUMERATION-INTEGRITY REPORT - per-host, whether the API and registry views agree and whether the concealment flag is set, with estate-wide protection-state coverage percentages. A DIFFABLE SNAPSHOT of both hives and the protection states, stored so that the day-thirty and subsequent runs report only changes. The register is what makes [[H355]] and every future exclusion alert actionable in minutes instead of hours - without it, the triage question "is this exclusion supposed to be here" has no answer.
  What this baseline enables - with the register in place, a new exclusion becomes a one-line question rather than an investigation, and the overbroad-and-locally-set shape becomes detectable as a deviation rather than needing a hand-written rule per pattern. It also answers a question most organisations cannot answer at all - which parts of the estate Defender is not actually scanning, and on whose authority.
  Detection breadth beyond what the report attests - Huntress documented the exclusion types, the four setting methods, the two hives, the registry-write convergence, and the concealment value's effect on administrators and SYSTEM. The 30-day baseline structure, the field lists, the immediate-flag set, the collection scripts and the enumeration-integrity concept as a reported deliverable are this hunt's construction from those facts; Huntress published no baseline methodology or queries. The registry paths, the `reg add` example, the setting-method tracing and the SYSTEM-level effect are the attested artifacts.

# B056

Huntress's September 2026 research on Microsoft Defender exclusions ends with a sentence that is really an instruction for defenders: administrators and SYSTEM can still read the exclusion list, they just have to go to the registry directly.

That sentence exists because of `HideExclusionsFromLocalAdmins`. Set it, and the exclusion list stops being returned to queries — not only for local administrators, as the name suggests, but for SYSTEM as well. Any inventory process that enumerates exclusions through the Defender API therefore has a silent failure mode: it reports a short, reassuring list from exactly the host an operator has carved wide open, and returns no error while doing so.

So this baseline collects every host's exclusions twice. Once through `Get-MpPreference` or the `MSFT_MpPreference` WMI class, and once by reading the registry hives directly — both of them, because Huntress traced PowerShell and WMI writes to `HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions` and Group Policy writes to the separate `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions`. Defender locks down direct writes to the first; the policy hive is the writable one, and it is also where the concealment flag lives. A host where the two views disagree is a detection in its own right.

The rest is ordinary inventory work, and it matters because exclusions are overwhelmingly legitimate. Backup agents, database engines, Exchange, virtualisation hosts, developer toolchains and a long tail of line-of-business applications all have published vendor exclusion guidance, and following it is correct. That is precisely why an attacker's exclusion is invisible — it is the same kind of object, created through the same supported interfaces. Nothing distinguishes the malicious one except a register saying what was supposed to be there, which almost no organisation has when it is needed.

Two properties separate the shapes once you have the data. Breadth: vendor guidance is narrow and names a product directory or a service binary, while `C:\`, `C:\Users`, `%TEMP%`, `*` and an `.exe` extension exclusion are not vendor guidance under any reading. Provenance: sanctioned exclusions are applied by the management agent or by policy, identically across a defined population, while an attacker's is set locally by `reg.exe` or PowerShell on one host.

## Why

- No detection on exclusions can work without this register, because the malicious and benign objects are identical in kind. Exclusions are legitimate, numerous and vendor-recommended, so the only durable discriminator is a documented answer to "was this supposed to exist" — which is an inventory problem, not a detection problem. [[H355]] depends on this baseline to be triageable in minutes.
- The API view can be suppressed, so the collection method is itself the finding. Because `HideExclusionsFromLocalAdmins` defeats enumeration for SYSTEM too, an API-only inventory is wrong without announcing it. Collecting both views converts that blind spot into a per-host enumeration-integrity result, and makes "an empty exclusion list" something to verify rather than celebrate.
- Reading one hive and calling it the answer is wrong by construction. PowerShell/WMI and Group Policy write to different keys, and the policy hive is simultaneously the attacker-writable one and the carrier of the concealment flag. Specifying both hives explicitly is what makes the inventory complete rather than plausible.
- Registry-operation telemetry is the one collection point that sees all four setting methods. Huntress's own conclusion — whatever interface is used, the setting lands in the registry — means a baseline built on registry writes covers PowerShell, WMI, GPO and manual editing, including methods nobody has used yet. A transcript-based or WMI-only approach misses most of them.
- Host count per exclusion value does more triage work than any rule. Stacking the population immediately separates fleet-wide policy from the one-host tail, and that tail is short enough to read line by line — which is where an attacker's carve-out lives.
- The exercise answers a question most organisations cannot answer at all: which parts of the estate Defender is not scanning, and on whose authority. That has standing value independent of this campaign, and the diffable snapshot makes every subsequent run cheap.
