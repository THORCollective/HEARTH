required_data_sources:
  - Sysmon Event ID 7 (ImageLoad) — ImageLoaded, Image (the loading process), Signed, SignatureStatus, Signature, Hashes, OriginalFileName, Company, Description. This is the primary and largely irreplaceable source
  - Defender XDR DeviceImageLoadEvents — FileName, FolderPath, SHA256, InitiatingProcessFileName, InitiatingProcessFolderPath, InitiatingProcessVersionInfoCompanyName, for estates on Defender rather than Sysmon
  - Sysmon Event ID 1 / Windows Security 4688 — process creation for the loading executable, its full path, signer, parent, and command line
  - Sysmon Event ID 11 (FileCreate) / DeviceFileEvents — DLL writes into user-writable directories, with the writing process and the SHA256, to catch the plant before the load
  - Sysmon Event ID 15 (FileCreateStreamHash) — Mark-of-the-Web on DLLs and their containing archives, showing internet provenance
  - Sysmon Event ID 3 / DeviceNetworkEvents — egress from the signed process after the anomalous load, which is where the sideloaded payload announces itself
  - Certificate and signature metadata — the DLL's own signing status, and critically whether the DLL's OriginalFileName and Company match the module the application legitimately ships
  - Software inventory — the authoritative list of installed applications, their vendor install paths, and their expected module sets, to give the profile a reference point
  - Windows Defender Application Control / AppLocker DLL-rule audit-mode logs, where deployed — an alternative high-quality source for "which modules loaded from where"
notes: |
  COLLECTION WINDOW:
  30 days minimum. The binding constraint is application update cadence, not attacker behaviour — browsers,
  collaboration clients, and runtimes ship new modules on 2-6 week cycles, and a 7-day profile will flag every
  Chrome, Teams, and .NET update as novel. Re-generate the profile monthly and treat a vendor update as a
  scheduled, expected burst of novel modules rather than an incident. Note explicitly which applications in scope
  are self-updating, because those are the ones that will produce recurring novelty forever.

  DELIVERABLE:
  Three artifacts, generated as data and refreshed monthly.
  (1) THE PER-APPLICATION MODULE PROFILE — for each in-scope signed executable, keyed by its own path and signer:
      the set of (module name, module directory, module SHA256, module signer) it has been observed loading, with
      counts, first-seen and last-seen. This is the core deliverable and the thing the alert differences against.
  (2) THE USER-WRITABLE LOAD INVENTORY — the subset of the above where the module was loaded from a
      user-writable path (%APPDATA%, %LOCALAPPDATA%, %TEMP%, %PROGRAMDATA%, a user profile directory, or any
      directory whose ACL grants write to Users/Authenticated Users). In a healthy estate this list is short and
      every entry on it should be nameable — Electron apps, some updaters, a few line-of-business tools. Its
      contents are the standing risk register for this technique.
  (3) THE NAME-COLLISION MAP — modules whose filename matches a known-good system or vendor DLL but whose signer,
      SHA256, or OriginalFileName does not. This catches the specific trick both source intrusions used and is
      the highest-value output for the effort.

  IMMEDIATE FLAGS (act on these before the baseline completes):
  Escalate on sight from day one; none of these need the 30-day profile to interpret:
  (1) AN UNSIGNED OR INVALIDLY-SIGNED DLL LOADED BY A VALIDLY SIGNED, REPUTABLE EXECUTABLE. Sysmon's Signed and
      SignatureStatus fields answer this directly. It is the single highest-yield query in the whole hunt and it
      should be running before the baseline is finished.
  (2) A SIGNED VENDOR EXECUTABLE RUNNING FROM A USER-WRITABLE PATH AT ALL. GoTo Meeting's binary belongs in
      Program Files, not AppData\Roaming\ServiceClients\. The relocation is the sideloading setup, and it is
      visible in process creation without touching image-load telemetry.
  (3) A DLL WHOSE FILENAME MATCHES A KNOWN SYSTEM OR VENDOR MODULE BUT WHOSE OriginalFileName, Company, OR
      SIGNER DOES NOT. `api-ms-win-crt-time-l1-1-0-2.dll` outside System32 is the example from this week.
  (4) DLL AND EXE WRITTEN TOGETHER, from the same archive, into the same user-writable directory, within seconds
      — the extraction signature of the delivery ZIP both campaigns used.
  (5) MARK-OF-THE-WEB ON A DLL. A module that arrived from the internet and is being loaded by a signed
      application has no benign explanation in a managed estate.
  (6) THE LOAD IMMEDIATELY FOLLOWED BY NOVEL EGRESS from the signed process — first-ever connection to a domain,
      or to a tunnelling service, within minutes of the anomalous module loading.

  PLATFORM: Windows (workstations first — both source intrusions began with a user opening a delivered archive;
  extend to servers where third-party agents run from non-standard paths).

  SOURCES — two independent reports in the same week, same delivery mechanic:

  1. Check Point Research, "Shattering the Dream — When a Job Offer Becomes a Zero-Day Attack" (2026-08-11).
     Lazarus / Operation Dream Job against the defence sector. An encrypted ZIP containing three files: a

  A third report the same week used the same mechanic for a different payload — Securelist's Armored Likho
  toolkit extracts and side-loads `libmp3lame.dll` — and Head Mare's PhantomCore dropped
  `%LOCALAPPDATA%\TrueConf\Client\api-ms-win-crt-time-l1-1-0-2.dll`, a name lifted from the Universal CRT stubs.
  Four campaigns, one delivery pattern.

  WHY THIS IS AN EMBER AND NOT A FLAME. Walking the rubric:
  - Flames rejected. The obvious Flames hunt is "alert when a signed binary loads a DLL from a user-writable
    path," and it does not survive contact with a real estate. Electron applications, self-updating clients,
    .NET and Python runtimes, game launchers, and a long tail of line-of-business software do this constantly
    and legitimately. Writing the rule against the specific module names from these reports — g2m.dll,
    libmupdf.dll — produces four IOCs with a shelf life measured in weeks, because the whole point of the
    technique is that the attacker picks whichever legitimate application they like. What is durable is the
    deviation from an application's own module set, and that requires the set to exist.
  - Alchemy rejected. It was a real contender: this could be framed as rarity-scoring module loads across the
    fleet. It was rejected because the question is cleanly binary — has THIS executable ever loaded THIS module
    from THIS directory before? — and a set-membership answer is both exact and explainable to an analyst.
    Statistical scoring would add tuning surface and opacity without improving on a lookup. If the estate is
    large and heterogeneous enough that the profile never converges, revisit; scope narrowly first instead.
  - Embers selected. Multiple triggers apply: the technique abuses legitimate, signed software where malicious
    use is structurally identical to normal use; the published detection guidance reduces to "look for unusual
    DLL loads"; and no rule can fire without knowing which loads are usual for each application.

  THE COLLECTION PROBLEM, stated honestly, because it will determine whether this baseline happens at all:
  Sysmon Event ID 7 is OFF by default and is extremely high-volume — every process loads dozens of modules at
  startup, and enabling it estate-wide unfiltered will overwhelm most pipelines. Do not attempt that. Scope it:

    SCOPE BY PROCESS — the applications actually targeted by this technique: browsers, Office applications,
      collaboration and conferencing clients, PDF readers, script hosts (wscript, cscript, mshta), and the
      LOLBins (rundll32, regsvr32, msiexec).
    SCOPE BY PATH — configure the Sysmon ImageLoad filter to include only modules loading from %APPDATA%,
      %LOCALAPPDATA%, %TEMP%, %PROGRAMDATA%, and user profile directories, and exclude C:\Windows\System32 and
      C:\Program Files. This alone cuts volume by well over an order of magnitude and, crucially, it retains
      exactly the events this hunt is about.
    SCOPE BY SIGNATURE — where the pipeline supports it, retain unsigned and invalidly-signed loads
      unconditionally and sample the signed ones.

  A path-and-signature-filtered EID 7 configuration is the difference between this being a two-week engineering
  project and an unbounded one. If EID 7 genuinely cannot be enabled, Defender XDR's DeviceImageLoadEvents or
  WDAC/AppLocker DLL rules in audit mode are usable substitutes for artifacts (1) and (2), though both are
  coarser on signer metadata.

  FIELDS TO COLLECT PER OBSERVATION:

    timestamp, host, loading_process_image, loading_process_sha256, loading_process_signer,
    loading_process_signature_status, module_name, module_directory, module_sha256, module_signer,
    module_signature_status, module_original_filename, module_company, module_description,
    is_user_writable_path, has_mark_of_the_web, parent_process_image, session_user

  ORIGINALFILENAME IS THE FIELD THAT DOES THE WORK and it is routinely dropped from ingest pipelines to save
  space. A malicious `g2m.dll` is trivially given the right filename; giving it the right OriginalFileName,
  Company, and Description in the PE version resource is extra effort that attackers frequently skip. The
  mismatch between filename and embedded metadata is the cheapest reliable discriminator available, and it only
  exists if the field is retained. Check your pipeline before starting.

  VALIDATION: after 30 days, run the set difference for a known-clean week and confirm novel-module counts fall
  to a manageable daily number outside vendor update windows. Then execute the Atomic Red Team T1574.001 tests
  on an instrumented host and confirm it surfaces. If it does not, the Sysmon path filter has excluded the
  directory the test used — a common and silent failure.

  ID NOTE: ATT&CK has retired T1574.002 (DLL Side-Loading) and merged it into T1574.001 (DLL). Search-order
  hijacking (attacker plants only the DLL) and side-loading (attacker supplies the legitimate EXE too — which is
  what all four source campaigns actually did) are now one technique with one ID. Older detection content,
  including some of the vendor rules referenced below, still carries the retired ID; treat those as T1574.001.

  CROSS-REF: this baseline is what makes DLL-sideloading Flames hunts possible at all. T1036.005 (Masquerading:
  Match Legitimate Name or Location) is the naming half of the trick. T1027.011 (Fileless Storage) and T1055.001 (DLL Injection)
  describe what the loaded module does next. [[H266]] and [[B037]] cover the later stages of the Deception.Pro
  intrusion this delivery mechanic began.

# B038

Two unrelated campaigns this week, two different targets, one delivery mechanic.

Lazarus sent defence-sector engineers an encrypted ZIP containing a legitimately signed PDF viewer, a malicious `libmupdf.dll`, and a decoy document. A commodity crew dropped a legitimately signed GoTo Meeting binary into `AppData\Roaming\ServiceClients\` with a malicious `g2m.dll` beside it. In both cases the executable that appears in EDR is signed, reputable, and doing exactly what it was built to do — loading a module it genuinely expects to find next to itself. The hostile code never gets a process of its own.

The only telemetry that shows this is the image-load event. And image-load telemetry has a bad reputation for good reasons: Sysmon Event ID 7 is off by default, every process loads dozens of modules at startup, and the naive rule — "signed binary loaded a DLL from AppData" — fires on every Electron app, every self-updating client, and half the line-of-business software in the building.

Which is exactly why it needs a baseline rather than a rule. The question is not "did a signed application load a DLL from a user-writable path." It is "has *this* application ever loaded *this* module from *this* directory before."

## Why

- **The attacker's freedom of choice is what defeats static rules, and what the baseline neutralises.** There is no fixed list of sideloadable applications — the technique works against thousands of them, and the attacker picks whichever they like. Writing detections against `g2m.dll` and `libmupdf.dll` yields four indicators that expire the moment someone picks a fifth application. A per-application module profile does not care which application is chosen, because every choice produces the same observable: a module this executable has never loaded before. That is the difference between chasing campaigns and covering a technique.

- **The signed executable is the point, and it neuters most of the detection stack.** Process-creation rules see a reputable vendor binary. Signature-based prevention sees a valid Authenticode chain. Reputation scoring sees a widely-deployed application. Application allowlisting configured at the executable level passes it. The malicious code is inside a module that never appears as a process at all. Estates that measure endpoint coverage by process telemetry have a genuine blind spot here, and the only place it closes is the image-load layer.

- **The path-scoped Sysmon configuration turns this from impossible to routine, and it is the whole engineering answer.** The reason most teams do not have this baseline is that they tried enabling Event ID 7 estate-wide, watched the pipeline buckle, and turned it off. Filtering the ImageLoad rule to *exclude* `System32` and `Program Files` and *include* the user-writable directories cuts volume by well over an order of magnitude while retaining precisely the events this technique generates — because a sideloaded DLL is, by definition, not in a protected system directory. That configuration change is the deliverable that makes everything else feasible.

- **`OriginalFileName` is the cheapest reliable discriminator available and it is usually thrown away.** Renaming a malicious DLL to `g2m.dll` is trivial. Populating the PE version resource so that `OriginalFileName`, `Company`, and `Description` also match what the real module carries is extra work that attackers routinely skip. A module whose filename matches a known-good library but whose embedded metadata does not is close to conclusive — and that check costs nothing at query time, provided the field survived ingest. It frequently does not. Verifying that is a five-minute task with a disproportionate payoff.

- **Three of the immediate flags work before the baseline finishes, so the hunt returns value on day one.** An unsigned DLL loaded by a validly-signed reputable executable; a vendor binary running from `AppData` rather than `Program Files`; an EXE and DLL extracted into the same user-writable directory within seconds. None of those require 30 days of history to interpret, all three fired in the source intrusions, and all three can be deployed while the profile is still being collected. A baseline hunt that delivers nothing for a month is a baseline hunt that gets abandoned in week two.

- **The load is the last quiet moment before the intrusion becomes expensive.** In the Lazarus chain, the sideloaded `libmupdf.dll` led to MISTPEN, then a kernel zero-day in `afd.sys`, then FudModule blinding ETW across 94 providers and tampering with Smart App Control. Once the rootkit is resident the telemetry this hunt depends on is being actively suppressed. The image load happens before any of that — while the host is still telling the truth. Detection latency at this specific step is what determines whether you are investigating a delivery attempt or a kernel compromise.

- **HEARTH had no T1574.001 coverage at all** — the technique that now absorbs both search-order hijacking and side-loading after ATT&CK merged the retired T1574.002 into it — despite DLL sideloading being one of the most consistently used delivery mechanics in targeted intrusions and appearing in four separate reports in this single week's intel.
