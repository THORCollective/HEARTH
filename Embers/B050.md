category: Embers
title: "Baseline of scheduled-task enumeration integrity — do the API, the filesystem and the registry agree about which tasks exist on this host"
hypothesis: >-
  Every scheduled-task baseline ever written assumes the enumeration that produced it is complete, and on
  Windows that assumption is false by design. A scheduled task has THREE independent representations - the
  Task Scheduler API that `schtasks` and `Get-ScheduledTask` read, the on-disk XML under
  `C:\Windows\System32\Tasks\`, and the registry mirror under
  `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\` - and they can be made to disagree.
  Delete the `SD` (Security Descriptor) value from a task's `TaskCache\Tree` key and the task vanishes from
  `schtasks /query`, from the Task Scheduler MMC snap-in and from essentially every inventory tool, while the
  task keeps running on its triggers. That is Tarrask, the HAFNIUM tooling Microsoft documented in 2022, and it
  defeats [[B040]] and every other task baseline by construction, because those baselines enumerate the exact
  view that has been blinded. So do not ask which tasks are legitimate - ask whether you can see all of your
  tasks at all. Collect all three views on every host, twice across a 30-day window, and diff them. The
  deliverable is a per-host three-way reconciliation plus a documented enumeration method that does not depend
  on the API telling the truth.

required_data_sources:
  - 'VIEW A - the Task Scheduler API enumeration. `schtasks /query /xml ONE` (full definitions, one XML document) and `Get-ScheduledTask` piped through `Get-ScheduledTaskInfo`, captured per host with the folder path preserved. This is the view that can lie, and it is collected precisely so the lie is measurable'
  - 'VIEW B - a recursive walk of `C:\Windows\System32\Tasks\`, where every task is a file with no extension and the file''s path RELATIVE to that root IS the task path. Record the relative path, the file size, the MFT created and modified timestamps, and a hash of the XML body'
  - 'VIEW C - the registry mirror. Enumerate every subkey under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree`, recording for each one whether the `Id`, `Index` and `SD` values are PRESENT, and then follow the `Id` GUID into `TaskCache\Tasks\{GUID}` to recover `Path`, `Actions`, `Triggers`, `Hash` and `URI`. Also enumerate `TaskCache\Boot`, `TaskCache\Plain` and `TaskCache\Logon`, which index tasks by trigger class'
  - 'Offline or raw-hive access to the SOFTWARE hive where possible - a live registry read through a blinded API path is fine for `TaskCache` today, but parsing the hive directly removes any dependency on the Task Scheduler service being honest'
  - 'Microsoft-Windows-TaskScheduler/Operational Event IDs 106 (registered), 140 (updated), 141 (deleted), 200 (action started) and 201 (action completed) - this log is disabled by default and is the ONLY source that shows a hidden task actually executing, because a task hidden from the API still logs 200/201 when it runs'
  - 'Sysmon Event ID 12 and 13 and Security event 4657 scoped to `Schedule\TaskCache`, specifically for DELETION of an `SD` or `Index` value under a `Tree` subkey. Note the two known blind spots - the write is normally performed by `svchost.exe` so process attribution is weak, and a task IMPORTED already missing its `SD` never generates the delete event at all'
  - 'Sysmon Event ID 1 / Security 4688 for `schtasks.exe` and `powershell.exe` with full `CommandLine`, used NEGATIVELY - the population of interest is tasks with NO corresponding creation process, because registration through the `Schedule.Service` COM object produces no command line whatsoever'
  - 'Security events 4698 and 4702 where available, used only to attribute a task discovered by the three-view diff back to a creation time and account - not as the enumeration itself'
  - 'A golden-image task list per OS build and edition in the estate, captured from a known-clean reference image. A production host is not an authority on what a clean host looks like'
  - 'Authenticode signing status, signer subject and full resolved path for every action binary named in any of the three views, resolved out-of-band from the task definition'
false_positive_notes: |
  The three views disagree for boring reasons more often than for interesting ones, and knowing which asymmetries are benign is most of the skill in this exercise. Expect ordinary, explainable noise first. A task created or deleted DURING collection will appear in one view and not another purely because the snapshots are not atomic - collect all three views within the same script invocation, record the timestamp of each, and re-check any singleton disagreement immediately rather than filing it. Task Scheduler writes the XML file and the registry keys at slightly different moments, so a task registered seconds before the sweep can show up mid-write. Installer and patch activity creates a burst of these; a snapshot taken during a maintenance window will be noisier than one taken outside it, which is an argument for taking both. Second, folder-level objects confuse naive diffs: `TaskCache\Tree` contains subkeys for FOLDERS as well as tasks, and a folder key legitimately has no `Id` and no corresponding `Tasks\{GUID}` entry, so a diff that does not distinguish folder keys from task keys will report every folder in the estate as an orphan. Distinguish them by the presence of an `Id` value. Third, some security and management products deliberately restrict access to their own tasks, and a task the collecting account cannot READ is missing from the API view for permission reasons rather than evasion reasons - run the API enumeration as SYSTEM, not as an administrator, and record the account used, because the whole point of the `SD` is access control and an under-privileged enumeration produces exactly the same asymmetry as an attack. Fourth, redirected or non-default task stores and heavily customised images can legitimately carry stale XML files left behind by an uninstall, which shows up as on-disk-but-not-in-Tree; these are real, common, and worth cleaning up, but they are hygiene rather than intrusion. Two interpretation traps matter more than the rest. An empty reconciliation report is ambiguous and must be resolved before it is believed - it means either that the estate is clean or that the collection never actually ran all three views on all hosts, and the way to tell them apart is to deliberately create a hidden task on a test host, confirm it appears in the report, and confirm a normal task does not. Do this on day one. And absence of the `SD` value is not the only hiding primitive - Binary Defense's ARC Labs showed that a task carrying a valid but DENY-READ security descriptor hides from the same tooling while leaving the `SD` value present, and Qualys showed the `Index` value can be deleted to blind `schtasks` wholesale. A report built only on "`SD` is missing" will pass a task hidden by the other two methods, which is why this baseline reconciles the VIEWS against each other rather than testing any single value.
notes: |
  Collection window - 30 days, with a full three-view snapshot taken on day one, a second at the end, and ideally weekly in between. The window matters less here than the REPEAT does - the deliverable is a diff, and a single snapshot cannot produce one. Thirty days covers a patch Tuesday and a monthly maintenance cycle, which is what makes the second snapshot interpretable rather than alarming. The golden-image task set is not collected over the window at all; it is captured once per OS build and edition from a clean reference image and versioned alongside the build.
  The three-view reconciliation, concretely - collect VIEW A (`schtasks /query /xml ONE` plus `Get-ScheduledTask`), VIEW B (recursive walk of `C:\Windows\System32\Tasks\`, relative path equals task path), and VIEW C (`TaskCache\Tree` subkeys with `Id`/`Index`/`SD` presence flags, each `Id` GUID followed into `TaskCache\Tasks\{GUID}`) in one invocation on one host, normalise all three to the same key - the full task path, case-insensitive, leading backslash preserved - and produce a set difference in both directions between every pair. Never join on task NAME alone; two tasks in different folders can share a name and the folder is half the identity.
  The four asymmetries and what each one means - (1) PRESENT ON DISK AND IN `Tree`, MISSING FROM THE API. This is the headline finding and the reason the baseline exists. It is the Tarrask condition - the `SD` value has been deleted from the task's `Tree` key, so the API and the MMC console refuse to list it while the task continues to fire on its triggers. Deleting that value requires SYSTEM, and there is no benign software that does it. Confirm by reading the `Tree` key's values directly and by looking for TaskScheduler/Operational 200/201 pairs naming a task the API says does not exist. (2) PRESENT IN `Tree`, NO XML ON DISK. Orphaned or mid-deletion - either a cleanup that stopped halfway, or a task whose file was removed to frustrate analysis while the registry definition survived. `TaskCache\Tasks\{GUID}` still holds `Actions` and `Triggers`, so the task is fully recoverable from the registry alone; recover it. (3) PRESENT ON DISK, ABSENT FROM `Tree`. Registered outside the normal path, or a stale file left by an uninstall. Benign more often than not, but the malicious version - a definition dropped into the Tasks directory by hand - is worth separating by MFT creation timestamp and by whether the XML parses. (4) A `Tree` KEY WHOSE `Id` GUID HAS NO `TaskCache\Tasks\{GUID}` ENTRY. Broken registration. Read it - the `Tree` key retains `Index` and `SD`, and the absence of the `Tasks` half is either corruption or a partially removed implant.
  Do not depend on the API being honest - the practical consequence is that VIEW C, parsed from the registry, is the AUTHORITY and VIEW A is the thing being tested. Where they disagree, the registry is right. Any inventory tooling in the estate that enumerates only through `Get-ScheduledTask`, the WMI/CIM `PS_ScheduledTask` class, osquery's `scheduled_tasks` table or an EDR product's task inventory is reading VIEW A and inherits the blindness; establish which of your tools do this, write it down, and stop treating their output as complete.
  Fields to collect, per task per view - `full task path` (folder plus name, never flattened), `present in view A` (bool), `present in view B` (bool), `present in view C` (bool), and for view C specifically `Id value present`, `Index value present`, `SD value present`, `SD SDDL string` where present, and `Tasks GUID resolved` (bool). For view B, `XML file MFT created` and `MFT modified` and an XML body hash. Record the collection account and whether it was SYSTEM.
  Fields to collect, naming and structure - `task name with all trailing characters preserved BYTE FOR BYTE` (a trailing dot or space is destroyed by any pipeline that trims whitespace, so collect raw and compare raw), `folder path`, `is folder under \Microsoft\Windows\` (bool), `in golden-image set for this OS build` (bool), `trigger type`, `repetition interval in minutes`, `repetition duration`, `principal / RunAs`, `RunLevel`, `action type`, `action binary full path`, `complete argument string verbatim`, `binary Authenticode status and signer`, `binary path is user-writable` (bool), and `fleet prevalence count` for the exact path.
  Fields to collect, creation method - for every task, whether a `schtasks.exe` or `Register-ScheduledTask` process execution exists in the 4688/Sysmon-1 record that can plausibly account for it, as a bool plus the matching process GUID. This field is used INVERTED - the interesting population is `has_schtasks_ancestor = false`. Registration through the `Schedule.Service` COM object creates no process at all, and both of the Exodus RAT's tasks were created that way, so any baseline resting on `schtasks.exe` telemetry sees nothing.
  Naming and structural invariants worth collecting once - these came out of four unrelated intrusions in a single week and they survive campaign rotation because they are properties of the mechanism rather than of the malware. TRAILING DOT OR WHITESPACE - when the MoiClient loader wants a task name that already exists, it appends a literal period to the EXISTING task's name, producing `Task Name.`. Windows tolerates it; nothing legitimate produces it; it is one line of query against either the API view or the on-disk relative path. FOLDER-TREE BURIAL - a task placed inside a genuine `\Microsoft\Windows\...` folder to sit among real siblings, observed as `Maps Performance Task` under `\Microsoft\Windows\Maps\` (hourly and at startup, running as SYSTEM) and `OOBETaskScheduler` under `\Microsoft\Windows\Servicing\`. The built-in task set for a given OS build is FIXED and enumerable from a golden image, so a task in a Microsoft folder that is not in the golden set is decisive rather than merely suspicious, and a flat alphabetical list of task names hides this perfectly while a per-folder comparison exposes it in one pass. REPETITION-INTERVAL DISTRIBUTION - build the histogram. Genuine Microsoft tasks are overwhelmingly daily, weekly or event-triggered, while the malicious population in these reports clusters at short fixed intervals - 14 minutes (Kimsuky's `MicrosoftOffice2016_<first 4 characters of a UUID>`, running a `.js` file via `wscript.exe`), 30 minutes (MoiClient's `MicrosoftWindowsUpdateTask####`), and 60 minutes or hourly (`Maps Performance Task`, and the Exodus RAT's `ExdBackupTool`, which ran hourly at 42 MINUTES PAST THE HOUR). Sub-hourly repetition is rare enough in a real estate that the list fits on a page.
  Immediate flags, do not wait for the baseline to complete - (1) ANY disagreement between the API, filesystem and registry views on any host, in any direction, that survives a same-minute re-collection; (2) any task name ending in a DOT or in whitespace; (3) any task inside a `\Microsoft\Windows\` folder that is not in the golden-image set for that OS build; (4) any repetition interval under 60 minutes on a task running as SYSTEM; (5) any task whose action binary is unsigned, or whose path resolves under `%APPDATA%`, `%LOCALAPPDATA%`, `%PROGRAMDATA%`, `%PUBLIC%` or `%TEMP%`; (6) any `TaskCache\Tree` key missing its `SD` value, or missing its `Index` value, or carrying an `SD` whose SDDL denies read to Administrators; (7) TaskScheduler/Operational 200/201 naming a task that the API enumeration on that host does not list.
  Deliverable - four diffable artifacts. (1) THE THREE-VIEW RECONCILIATION REPORT, per host, listing every task appearing in fewer than three views, classified into the four asymmetries above with the benign explanations already excluded. In a healthy estate this is short and every line has an owner. (2) THE ENUMERATION METHOD, written down - the exact collection script, the account it runs as, which of the three views each existing inventory tool actually reads, and therefore which of the estate's tooling is structurally blind to a hidden task. This is the artifact that outlives the exercise. (3) THE TRIGGER-INTERVAL HISTOGRAM per folder, which turns the sub-hourly flag from a hunch into a measured threshold for this estate. (4) THE NO-CREATOR REGISTER - every task with no `schtasks.exe` or `Register-ScheduledTask` ancestor, which is the COM-registration population and the one a process-creation baseline never sees. Re-snapshot at the end of the window to produce the first diff of all four.
  How this differs from [[B040]], stated plainly because a reviewer will check - [[B040]] asks whether an update-NAMED scheduled task is legitimate. It builds a fleet inventory of update-themed tasks keyed on the `<Exec><Command>` path, the signer, the registering account and fleet prevalence, and it answers "is this task what it claims to be". B050 asks a question one level below that - whether the ENUMERATION that produced any such inventory is trustworthy. It does not re-inventory update-themed tasks, does not re-derive the name-versus-vendor-path check, and does not restate [[B040]]'s 4698 collection design. It specifically finds tasks [[B040]] CANNOT SEE, because [[B040]] and every tool like it enumerate the API view, and the Tarrask technique exists to blind exactly that view. Run [[B040]] to judge the tasks; run B050 to establish that [[B040]] was handed the complete list. Where the two disagree about what exists on a host, B050's registry view is the authority.
  What this baseline enables - [[H321]] (the MoiClient chain, whose AppInfo-RPC UAC bypass and parent-PID spoofing reaches SYSTEM, which is the exact privilege the `SD` deletion requires), [[H324]] (the SYSVOL/GPO wiper, where a hidden task is the reliable way to survive a destructive run), [[H325]] (the macOS LaunchAgent equivalent - the same question of whether the enumeration is complete, on a platform where `launchctl list` is the blindable view) and [[H326]] (VS Code extension and git-hook persistence on Windows, the sibling exercise of enumerating a persistence surface nobody inventories).

# B050

A scheduled task is not one object. It is three: the definition the Task Scheduler API hands back to `schtasks` and `Get-ScheduledTask`, the XML file under `C:\Windows\System32\Tasks\` whose path relative to that directory *is* the task's path, and the registry mirror under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\` — `Tree`, `Tasks`, `Id`, `Boot`, `Plain`, `Logon`. Windows keeps them in sync. An attacker with SYSTEM can stop it.

Delete the `SD` value — the Security Descriptor — from a task's `TaskCache\Tree` key and the task disappears from `schtasks /query`, from the Task Scheduler MMC snap-in, and from every inventory product that asks the API instead of the registry. It does not stop running. It fires on its triggers, spawns its action, and logs its 200/201 pair in an Operational channel most estates have never enabled. Microsoft published this in April 2022 as Tarrask, tooling used by HAFNIUM against telecom and ISP targets, and the interesting detail was never the malware — it was that the hiding primitive is a single registry value deletion against a mechanism every defender believes they can enumerate.

That is the problem with task baselines, including good ones. [[B040]] builds a careful fleet inventory of update-themed tasks and asks whether each one's command path matches the vendor its name claims. It is the right question. But it is asked of a list, and the list came from the view that Tarrask blinds. So this baseline asks the question underneath: **can I see all of my scheduled tasks at all, and do my three views agree?** Not which tasks are legitimate — which tasks *exist*. The output is not a verdict on any task. It is a per-host diff of API against filesystem against registry, and a written enumeration method that does not take the API's word for anything.

## Why

- **The enumeration is the assumption nobody tests, and it is the one being attacked.** Every control in this area — the inventory, the allowlist, the EDR task view, the compliance scan — resolves to one call into the Task Scheduler API. Tarrask does not evade a detection rule; it removes the task from the data source those rules read, which is a category of evasion that produces no alert and no error, only a shorter list. The only way to find it is to hold a second and third enumeration against the first, which is an inventory exercise and cannot be a query.
- **Three views mean four distinct asymmetries, and each one means something different.** On disk and in `Tree` but missing from the API is the Tarrask condition and the headline finding. In `Tree` with no XML is orphaned or mid-deletion, and still fully recoverable from `TaskCache\Tasks\{GUID}`, which retains `Actions` and `Triggers`. On disk but absent from `Tree` is either a registration outside the normal path or an uninstall that left a file behind. A `Tree` key whose `Id` GUID resolves to nothing is a broken registration worth reading. None of these is visible from any single view, which is the entire argument for collecting all three in one pass.
- **`SD` deletion is not the only hiding primitive, so the test has to be the diff rather than the value.** Qualys showed that deleting the `Index` value blinds `schtasks` wholesale — it returns an internal error instead of a list. Binary Defense's ARC Labs showed that a task carrying a *valid but deny-read* SDDL hides from the same tooling with the `SD` value still present, and that a task imported already missing its `SD` never fires the 4657 event Microsoft's own detection guidance depends on. A rule that checks for a missing `SD` passes all three variants. A reconciliation between views catches every one of them, because whatever the mechanism, the symptom is that the views stop agreeing.
- **The cheap invariants are genuinely cheap and they survive the campaign.** Four unrelated intrusions in one week supplied a handful of structural tells worth collecting once. A task name ending in a literal period — MoiClient appends one to the existing task when its preferred name is taken, and nothing legitimate does. A task buried in a real `\Microsoft\Windows\` folder among genuine siblings, which is undetectable in a flat alphabetical list and obvious in a per-folder comparison against a golden image, because the built-in set for a given build is fixed and enumerable. A repetition interval of 14, 30 or 60 minutes where genuine Microsoft tasks are daily, weekly or event-triggered. None of these depends on a hash, a domain or a filename, and all three are one line of query against data this baseline already collects.
- **COM registration means a whole population of tasks has no creation event to find.** Tasks registered through the `Schedule.Service` COM object never produce a `schtasks.exe` command line — the Exodus RAT's `ExdBackupTool` and `INetHealth` were both created this way, after the MSI finished, with nothing in the installer tables to show for it. Any baseline resting on process-creation telemetry for task registration has a silent gap sized exactly to the adversaries who know about it. Recording, per task, whether a plausible creating process exists at all inverts the field into something useful: the tasks with no ancestor are the population to read.
- **A quiet result here is worth nothing until it is proven quiet.** The TaskScheduler/Operational log is off by default. Security 4698 needs a subcategory that is off by default. An estate collecting neither will produce an empty reconciliation report that looks like cleanliness and is actually silence. The fix is small and belongs on day one: create a hidden task on a test host by deleting its `SD`, confirm it appears in the report, confirm an ordinary task does not, and write down the result. That single test converts every subsequent empty report from an assumption into a measurement.
- **It fixes the input to a hunt that is otherwise correct.** [[B040]] asks the right question about the wrong list. Running both, in order, is what makes either one trustworthy — establish that the enumeration is complete, then judge what it returned.
