# B042

The AI-gateway intrusions in the source report include a step that is genuinely difficult to alert on:
the operators repeatedly sweep the process table. They fingerprint the host, run a silent
passwordless-sudo check, inspect listening ports, and — the characteristic move — `pgrep` for rival
miners, remote shells, competing infrastructure and their own previously dropped scripts. In the Kestra
case they went further and used a mounted Docker socket to enumerate `Config.Env` across every running
container.

Taken on its own, this is T1057, and T1057 is close to the canonical example of a technique too generic
to hunt directly. `ps` and `pgrep` are how monitoring agents, health checks, supervisors and
administrators do their jobs. A detection that fires on process enumeration fires all day, every day,
and gets disabled within a week. That is not a reason to ignore the behavior — it is the reason it
belongs in a baseline rather than in a rule.

Containers change the economics of that baseline substantially. A general-purpose Linux host has an
unbounded long tail of legitimate enumeration, and a profile of it may never converge. A container image
does not: its entrypoint defines a near-fixed process tree, the set of binaries present is whatever the
image ships, and enumeration from inside a running container is frequently anomalous simply by default.
That means the profile is per-image rather than per-host, it converges quickly, and it stays valid until
the image changes — at which point the image digest tells you to refresh it.

What makes the resulting baseline operationally valuable is the sequence it exposes. Discovery here is
never the objective; it is the first beat of a three-step rhythm. Enumerate, then kill what competes —
`pkill` against miner names, crontab entries stripped with `grep -v`, rival systemd units removed — then
hide, via LD_PRELOAD and a respawning watchdog. Any one of those steps is arguable in isolation. The
sequence, inside a container whose image has never done it before, is not.

## Why

- **T1057 is unhuntable as a rule and genuinely useful as a baseline, and the distinction is the whole
  point of this hunt.** The published detection guidance for process discovery reduces to matching `ps`,
  `pgrep`, `pstree` and `htop` executions — which is accurate, trivially implementable, and unusable at
  volume without knowing what normal looks like. This is the Embers trigger in its purest form: the
  technique abuses a legitimate administrative behavior where malicious use is structurally identical to
  benign use.
- **The per-image process set is a small, fast-converging, self-versioning baseline.** Unlike host-level
  behavioral profiles that drift continuously, a container image is immutable and its expected process
  tree is a property of the image digest. The profile does not decay; it is invalidated explicitly by a
  deployment. That makes this one of the few behavioral baselines that stays accurate without constant
  re-tuning.
- **It converts the intrusion's own automation into a detection advantage.** Microsoft notes the RAGFlow
  chain was "fully automated with no interactive shell." Automation means the enumeration is fast,
  ordered and repeatable — dozens of processes queried within seconds, immediately followed by other
  discovery — which is a very different temporal shape from an administrator typing `ps aux`, and a
  shape a baseline can encode as a rate and a sequence rather than as a command name.
- **The kill step is more specific than the discovery step and comes free with the same telemetry.**
  Rival-miner elimination is a well-documented, near-universal stage of cryptojacking: killing competing
  miners, deleting rival crontab entries and removing rival systemd units. Falco's malicious-binary lists
  even include `kill_miner` as a literal artifact. Collecting kill/pkill arguments alongside enumeration
  costs nothing extra and produces the higher-fidelity half of the signal.
- **It provides the interpretive context that [[H282]] and [[H283]] need to be triaged quickly.** Those
  hunts fire on persistence and hidden execution from the same intrusion set. When an analyst gets one
  of those hits, the immediate question is what else that workload did — and a per-image behavioral
  profile turns "is this container acting normally" from an investigation into a lookup.
- **Host-based monitoring placement is a real limitation worth documenting up front.** If credentials are
  compromised, an attacker can move container to container up to the host where the monitor runs, kill
  the monitoring process, and from then on no syscalls are generated for any container. That argues for
  collecting this telemetry off-host and for treating a monitoring agent going silent as an event in its
  own right — a point that belongs in the baseline's design, not discovered during an incident.

## Notes — collection specification

**COLLECTION WINDOW: 30 days**, refreshed on image change rather than on a calendar. Because the profile
is keyed to image digest, a redeploy legitimately invalidates it; treat a new digest as an expected burst
of novelty and re-profile rather than alerting.

**FIELDS TO COLLECT PER ENUMERATION OBSERVATION:** timestamp, hostname, container ID, image name, image
digest, pod/workload name where applicable, executing binary, full argv, uid/gid and effective user,
parent process image and argv, session/TTY context (or explicit absence of a TTY), whether the process
descends from the image entrypoint, count of distinct `/proc/<pid>` paths accessed within the event
window, and elapsed time from container start.

**ALSO COLLECT, for the sequence detection:** kill/pkill/killall executions with target arguments;
crontab executions and cron file writes; LD_PRELOAD environment writes and `/etc/ld.so.preload`
modifications; `/proc/1/environ` reads; and Docker socket access.

**DELIVERABLE — three artifacts:**

1. **THE PER-IMAGE ENUMERATION PROFILE.** For each in-scope image digest: which binaries perform process
   enumeration, under which accounts, with which argument patterns, at what cadence, and with what
   typical breadth (how many processes queried per burst). This is the set every alert is evaluated
   against.
2. **THE SANCTIONED ENUMERATOR LIST.** The monitoring agents, health checks, supervisors and cloud agents
   that enumerate legitimately across many images — the estate-wide exclusion set, maintained centrally
   so each image profile does not have to rediscover it.
3. **THE SEQUENCE RULE.** A correlation, tuned against the observed baseline, that fires on enumeration
   followed within a short window by rival-process killing, cron manipulation, or LD_PRELOAD writes from
   the same container. This is the artifact that actually produces alerts; artifacts 1 and 2 exist to
   make it precise.

**IMMEDIATE FLAGS — act on these before the baseline completes:**

1. **Any read of `/proc/1/environ`** by a shell, `cat`, `grep`, `python` or `python3` inside a container.
   In a containerized gateway, PID 1's environment holds the master keys and API tokens, and there is no
   routine reason to read it that way. Microsoft's published query treats this as a standalone condition.
2. **`pkill`/`kill` targeting known miner process names**, or crontab piped through `grep -v` to strip
   entries. Rival elimination has no benign reading.
3. **`modprobe msr allow_writes`** — a RandomX mining tuning step, and a single unambiguous string.
4. **Process enumeration by a binary executing from `/tmp`, `/var/tmp` or `/dev/shm`**, or by a process
   with no TTY that is not descended from the image entrypoint.
5. **Docker socket enumeration of `Config.Env` across containers** from a workload that has no
   orchestration role — the Kestra collection pattern.
6. **Writes to `/etc/ld.so.preload` or LD_PRELOAD injection from an application container.**

**PLATFORM: Linux — containerized workloads first** (AI inference gateways, orchestration platforms and
internet-facing application containers), extending to general-purpose hosts only where the profile proves
tractable.

**WHY THIS IS AN EMBER AND NOT A FLAME.** Three Embers triggers apply directly. The technique abuses a
legitimate administrative behavior where malicious use looks identical to monitoring-agent use. It is a
discovery technique that administrators and automation perform constantly. And the available detection
guidance reduces to "look for unusual process enumeration" with no IOC that separates malicious from
benign — no rule can fire without first knowing the environment's normal enumeration volume, cadence and
parentage. **Flames was rejected** because a hypothesis-driven hunt here would either be so narrow it
only catches this campaign's exact `pgrep` strings (worthless within weeks, since the argument list is
trivially changed) or so broad it alerts on every monitoring agent in the estate. **Alchemy was a real
contender and is the right next step, not the right first step:** per-container enumeration rate and
breadth are genuinely amenable to volumetric anomaly scoring, and at fleet scale that is likely how this
should eventually run. It is rejected here because the profile does not exist yet — statistical scoring
against an unestablished baseline produces confident nonsense, and the per-image set-membership question
("has this image ever done this?") is both exact and explainable while the baseline is being built.
Revisit Alchemy once artifact 1 is stable across a representative set of images.

**CROSS-REF:** [[H282]] (SSH key persistence) and [[H283]] (hidden `/tmp/.` execution) are the Flames
hunts covering the persistence and evasion stages of the same intrusion set; this baseline supplies the
behavioral context that makes their hits fast to triage.
