  An AI coding agent is a signed, user-approved process whose entire purpose is to spawn shells, read files, reach

  documented normal, not an alert. Expect and record heavy benign volume from:
  - The agent spawning `zsh`/`bash`, `git`, `node`, `npm`/`pnpm`/`yarn`, `python3`, `go`, `cargo`, `make`,

  PLATFORM: macOS (developer endpoints running AI coding agents and MCP servers). BASELINE FIRST.

  WHY A BASELINE AND NOT A RULE: the observed chain was agent (run with permission-bypass flags) → child `zsh` →
  `security find-generic-password` → `curl -X POST` of credentials to an ephemeral tunnel URL →
  `cloudflared tunnel --url http://localhost:<port>` / ngrok / localhost.run → LaunchAgent plist +
  `PlistBuddy -c "Set :StartInterval 60"` → `launchctl bootstrap gui/$(id -u)/<label>` → `pgrep` discovery →
  `python3 /tmp/mcp_clean_landers.py`. Every one of those is a thing a coding agent may legitimately be asked to
  do. Nothing is unsigned. Nothing has bad reputation. The signal is entirely in which of these the agent has
  NEVER done before on this host, and in their co-occurrence inside one session.

  COLLECTION FIELDS (per agent-descended event):
  - hostname, developer role/team, agent name and version, agent process path and signing ID/team ID
  - the agent's own invocation command line, and specifically whether permission-bypass flags were present
    (`--dangerously-skip-permissions` and equivalents) — record this as a per-host boolean over time
  - MCP server inventory: each configured server, its transport, its command line, and its signing state
  - for each child exec: executable path, full argv, signing ID, RESPONSIBLE process (ESF), immediate parent,
    working directory, and whether the working directory is a git repo (and which one)
  - for each credential-store touch: the keychain SERVICE name read, the flags used (`-w`/`-wa`/`-ga`), and the
    responsible process — stored as (process, service) pairs
  - for each credential FILE read: path (~/.aws/credentials, ~/.config/gcloud/*, ~/.npmrc, ~/.netrc,
    ~/.ssh/id_*, ~/.kube/config, ~/.docker/config.json, .env files), and responsible process
  - for each network connection: destination FQDN, IP, port, and whether the FQDN is an ephemeral tunnel or
    dynamic-DNS domain
  - for each LaunchAgent/LaunchDaemon plist write: path, Label, ProgramArguments, RunAtLoad, StartInterval,
    KeepAlive, and the responsible process
  - timestamp to the second, and a session identifier so co-occurrence inside one agent session is measurable

  METRICS TO DERIVE (the actual deliverable):
  1. Per-agent child-process distribution — the ranked set of executables the agent spawns, with per-day median
     and 95th percentile counts. The long tail is the interesting part: the executables spawned once ever.
  2. Per-host, per-agent NOVELTY list — executables the agent has spawned fewer than N times in the window. On
     most developer hosts the agent's realistic vocabulary is a few dozen binaries; `launchctl`, `PlistBuddy`,
     `cloudflared`, `ngrok`, `osascript`, and `security` are usually absent or near-absent, and that absence is
     the most valuable single artifact this baseline produces.
  3. Keychain (process, service) pair inventory — every service name read, by which responsible process. Any pair
     where the process does not own the service is a standing exception requiring justification.
  4. Egress destination profile — the enumerated set of FQDNs reached by agent-descended processes, split into
     model API / package registries / source hosting / everything else. Baseline the size of "everything else";
     it should be small and stable.
  5. LaunchAgent write attribution — over 30 days, the count of LaunchAgent/LaunchDaemon plist writes whose
     responsible process is agent-descended. On a healthy fleet this number is ZERO, which makes it a
     ready-made threshold rather than a distribution.
  6. Tunnel-use inventory — which users and hosts legitimately run cloudflared/ngrok, and critically whether the
     tunnels are NAMED (credentials file, stable ID) or EPHEMERAL quick tunnels. Sanctioned corporate connectors
     are named; ad-hoc quick tunnels are the population [[H260]] targets.
  7. Permission-bypass prevalence — the fraction of agent invocations per host and per team started with approval
     checks disabled. This is a control-posture metric that produces remediation work independently of any hunt.
  8. Session co-occurrence — how often a single agent session legitimately combines a credential read AND novel
     egress AND a persistence write. The expected answer is essentially never, which is what makes the composite
     detectable.

  COLLECTION WINDOW: 30 days minimum. Extend to 60–90 days for metrics 2 and 3, where the claim being made is
  "this has never happened" and confidence depends on the window. Ensure the window includes at least one
  onboarding/laptop-setup event and one major dependency upgrade cycle, since both legitimately widen the agent's
  child-process vocabulary and would otherwise present as anomalies later.

  DELIVERABLE: a per-agent, per-role behavioural profile containing (a) the allowlisted child-process vocabulary
  with expected volumes, (b) the enumerated (responsible process, keychain service) pairs, (c) the enumerated
  egress destination set with the "everything else" threshold, (d) the named-tunnel inventory with owners, (e) the
  documented expectation that agent-descended LaunchAgent writes are zero, and (f) the per-team permission-bypass
  posture with an owner for reducing it.

  FLAG IMMEDIATELY (do not wait for the baseline to complete):
  - Any LaunchAgent or LaunchDaemon plist written by an agent-descended process — see [[H260]].
  - `launchctl bootstrap|load|enable` or `/usr/libexec/PlistBuddy` executed by an agent-descended shell.
  - A keychain read where the service name does not belong to the reading process — see [[H259]].
  - Agent-descended egress to `*.trycloudflare.com`, `*.lhr.life`, `*.ngrok.io`, `*.ngrok-free.app`,
    `*.workers.dev`, or a paste service, and any `cloudflared tunnel --url http://localhost:` invocation.
  - `curl -X POST` from an agent-descended process carrying anything resembling credentials in the body.
  - An agent-descended process writing to or executing from `/tmp`, especially a Python or shell script.
  - Any agent invocation with permission-bypass flags on a host holding production credentials.
  - An agent-descended process reading a credential file belonging to a cloud provider the developer's team does
    not use.

  ENABLES: [[H259]] (the keychain read — needs metric 3 to be usable at all) and [[H260]] (the LaunchAgent +
  tunnel persistence — needs metrics 5 and 6). Also provides the provenance layer for [[H082]], which covers
  poisoning of AI coding tool project configuration in shared repositories; that hunt describes how injected
  instructions ARRIVE, this baseline describes what they can be seen DOING.

  CROSS-REF: T1555.001 (Keychain), T1543.001 (Launch Agent), T1572 (Protocol Tunneling), T1552.001 (Credentials

  baselined together, because it is the co-occurrence within one agent session that is detectable, not any single
  action.

# B035

Elastic ships the detection at the heart of this as a *building-block* rule: "GenAI or MCP Server Child Process Execution." Building-block rules are what you write when the event matters but is far too common to alert on. That is the honest summary of the problem — an AI coding agent spawning a shell is not suspicious, it is the product working.

The chain Elastic documented was a keychain read, a credentialed HTTP POST, a Cloudflare quick tunnel, a LaunchAgent, and a sixty-second respawn timer. Taken one at a time, a developer could defend every single step in a meeting. Taken together, inside one agent session, on a host that has never done any of them before, it is an intrusion. You cannot make that second statement without having written down the first.

There is a second reason this belongs in Embers rather than Flames. The agent is not just a trusted parent — it is a trusted parent that takes instructions from repository contents, fetched web pages, and MCP tool responses. The question "did a human ask for this?" is not answerable from process telemetry alone, which makes "has this host's agent ever done this before?" the practical substitute.

## Why

- **The trusted-parent heuristic inverts here, and nothing else fills the gap.** Detection engineering leans hard on lineage: browsers and Office applications should not spawn interpreters. A coding agent spawning `zsh`, `python3`, `curl`, and `git` is not an anomaly to be explained — it is the entire feature. Every lineage-based rule reads the chain as normal, so the only remaining discriminator is *this agent, on this host, has never spawned `launchctl`*. That is a baseline claim by construction.
- **Metric 5 is a threshold you get for free.** Most baseline work ends in percentile tuning. This one does not: on a healthy fleet, the number of LaunchAgent plists written by an agent-descended process over thirty days is zero. Confirming that zero is cheap, and it converts [[H260]] from a fuzzy provenance argument into a binary condition. Metric 3 behaves similarly — the set of keychain services an agent legitimately reads is small, enumerable, and stable.
- **The agent's own legitimate credential access is the trap.** `security find-generic-password -s "Claude Code-credentials"` is documented, expected behaviour. A team that discovers this event, writes a rule on it, and drowns will conclude the whole area is unhuntable. Enumerating (process, service) pairs first is what prevents that outcome, and it costs one query.
- **This baseline produces hardening work, not just detection content.** Metric 7 — how often agents are launched with approval checks disabled — is a control-posture number with a named owner and a clear remediation. Very few baselines hand you something you can fix on day one; this one does, and reducing that number shrinks the attack surface for every hunt above it.
- **The population is small and the value is concentrated.** This is not a fleet-wide baseline of thousands of hosts. It is the subset of developer endpoints running coding agents — which happen to be the machines holding cloud credentials, signing keys, and write access to source. The collection cost is low and the blast radius of missing it is a build pipeline.
- **Ephemeral versus named tunnels is a distinction almost nobody has made.** `cloudflared` is legitimate and probably sanctioned somewhere in your estate. Splitting named corporate connectors from anonymous `--url http://localhost:` quick tunnels turns "this tool is allowed" into "this tool is allowed in one specific shape," which is enforceable and survives the attacker switching brokers.
