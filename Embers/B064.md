hypothesis: >-
  GitHub is a dependency, a package registry and, increasingly, a command-and-control channel. An implant that authenticates to a private repository with a personal access token and exchanges files and issue comments with its operator produces network flows and process behaviour that are indistinguishable from a developer's tooling until you know what the developer's tooling actually looks like. This baseline establishes that: which hosts reach api.github.com at all, which processes on those hosts do it, whether the credential is an OAuth app, a GitHub App installation or a classic personal access token, and what the normal request rhythm and volume are per process. Without it, "an unknown binary is calling the GitHub API" cannot be separated from "a build agent is calling the GitHub API", and every repository-as-C2 hunt collapses into noise on developer endpoints while staying invisible on servers.

false_positive_notes: |
  This is a baseline, so the output is a description rather than a verdict, but a few things will mislead the collection itself.
  Package managers and IDEs dominate the volume. npm, pip, NuGet, Go modules, Homebrew, git itself, VS Code and JetBrains products all reach GitHub endpoints routinely, often many times a minute during a build. Record them as the baseline rather than filtering them out, because a later hunt needs to know their normal rhythm, not just their existence.
  Not all GitHub traffic is api.github.com. Clones and release downloads go to codeload.github.com and objects.githubusercontent.com; raw file reads go to raw.githubusercontent.com. Collect all four or the baseline will understate normal volume and overstate anomalies.
  Personal accounts are a real pattern in most estates. Developers authenticate to their own accounts from corporate endpoints. Capture that as a documented category, with the account names where your tooling can see them, instead of treating it as a finding.
  CI runners and container builds skew everything. A build agent can generate more GitHub traffic in an hour than a workstation does in a month. Baseline them as a separate class with their own thresholds or the workstation numbers become meaningless.
  TLS hides the detail you most want. Without inspection you get destination, timing and byte counts but not the path or method, so an issue-comment exchange and a repository clone look similar in size terms. Note which segments of the estate are inspected, and set expectations for the dependent hunts accordingly.
  Allowlisting by domain is what creates the gap in the first place. api.github.com is almost always permitted at the proxy, so record it as permitted-and-therefore-unmonitored and prioritise the process-level baseline over the network one.
notes: |
  Collection window - 30 days minimum, and prefer a window that contains at least one full release or sprint cycle. Build and dependency traffic is bursty on a weekly and monthly rhythm, so a 7-day window will produce thresholds that fire every time a release is cut.
  Fields to collect, per host and per process:
  - Host identity and class: `DeviceName`, device ID, OS, and the asset-inventory class (developer workstation, build agent, server, kiosk, general user endpoint).
  - Process identity: `InitiatingProcessFileName`, `InitiatingProcessFolderPath`, `InitiatingProcessCommandLine`, `InitiatingProcessParentFileName`, signer and signature status, and file hash.
  - Account context: the user the process runs as, and whether it is a service account, a machine account or an interactive user.
  - Destination: `RemoteUrl` where available, `RemoteIP`, `RemotePort`, and which of the GitHub hostnames was contacted.
  - Request shape, where a proxy or TLS inspection provides it: method, URL path, user agent, response status, request and response byte counts.
  - Credential class, from the GitHub side for your own organisation: OAuth app, GitHub App installation, classic personal access token, fine-grained personal access token, or deploy key, plus the token name, scopes and creator.
  - Rhythm: requests per hour per process, interval between requests, and the distribution of those intervals. Record the median and the variance, not just the mean, because the variance is what separates a poller from a human.
  - Volume and direction: bytes sent versus bytes received per session, and whether the process is predominantly downloading or uploading.
  Baseline query - the inventory to start from, Defender XDR, 30-day retention:
  ```kql
  DeviceNetworkEvents
  | where Timestamp > ago(30d)
  | where RemoteUrl has_any ("api.github.com", "codeload.github.com", "objects.githubusercontent.com", "raw.githubusercontent.com")
  | summarize Connections = count(), Hosts = dcount(DeviceName),
              FirstSeen = min(Timestamp), LastSeen = max(Timestamp),
              Urls = make_set(RemoteUrl, 10)
            by InitiatingProcessFileName, InitiatingProcessFolderPath
  | order by Connections desc
  ```
  Then invert it to find the rare side, which is where the dependent hunts will live:
  ```kql
  DeviceNetworkEvents
  | where Timestamp > ago(30d)
  | where RemoteUrl has "github"
  | summarize Hosts = dcount(DeviceName), Connections = count(),
              Devices = make_set(DeviceName, 10), FirstSeen = min(Timestamp)
            by InitiatingProcessFileName
  | where Hosts <= 2
  | order by FirstSeen desc
  ```
  Interval regularity - For each process that contacts the API more than a handful of times, compute the gaps between consecutive connections and summarise their spread. Human-driven and build-driven traffic is bursty and irregular; a polling implant is not. Keep the per-process interval profile in the deliverable, because this is the single most useful column for the hunts this baseline enables.
  Deliverable - A per-class allowlist document containing: (1) the approved set of GitHub-talking process images with their folder paths, signers and hashes, broken out by host class; (2) for each approved process, its normal requests-per-hour range, interval profile and typical direction of transfer; (3) the set of hosts in each class that legitimately reach GitHub at all, and the much larger set that never does; (4) the organisation's token and app inventory mapped to the processes that use them, with owner and scope; (5) an explicit list of host classes where any GitHub API contact is unexpected, which is usually servers, domain controllers and fixed-function endpoints. Review quarterly and after any change to the build toolchain.
  Flag immediately, without waiting for the 30 days to finish:
  - Any process reaching api.github.com from a host class that has no developer or build role, especially a domain controller, a file server or a fixed-function endpoint.
  - An unsigned binary, or a binary running from `C:\ProgramData`, `C:\Windows\Temp`, a user temp directory or a newly created System32 subdirectory, contacting any GitHub endpoint.
  - A process whose only network destination is a GitHub endpoint and which makes contact on a near-constant interval. A regular heartbeat with no accompanying clone or package download has no legitimate analogue.
  - Service-account or machine-account context on GitHub API traffic where the account has no documented repository role.
  - Authentication to a private repository with a classic personal access token from a host with no developer role, which is the credential class with the broadest scope and the weakest attribution.
  - Any GitHub contact from a host in the "never does this" set established in the deliverable.
  Hunts this baseline enables - [[H357]] hunts an implant that re-resolves its operator from date-keyed issue text once its API token is revoked, and [[M036]] scores endpoint traffic to legitimate platforms for bidirectional C2 using process rarity, interval regularity and flow asymmetry. Both need exactly the per-process rhythm and rarity figures collected here; without them the rarity term is computed against an unknown population and the interval term has no normal to compare to. This baseline is also what makes the issue-based handshake described in the FlashHole reporting separable from ordinary API use, because that handshake is a low-volume, highly regular exchange against a private repository rather than a burst of package traffic.

# B064

Kaspersky's October 2026 Operation FlashHole report describes a Lazarus Group downloader, TechHub, that uses GitHub as its command-and-control channel. It authenticates to a private repository with a personal access token, creates an issue to signal availability, exchanges RSA and AES key material as files whose names encode a host identifier, posts collected host data back as encrypted files, and then edits the body of its own issue to mark the handshake complete. Four commands are driven from the repository. Kaspersky also records that the group has been using GitHub this way "since at least July 2025", across at least three primary repositories and one fallback, under accounts made to look like ordinary projects.

None of that traffic is anomalous at the network layer. It is TLS to `api.github.com`, a host that virtually every enterprise permits and almost none inspects, from an endpoint that may well have a legitimate reason to talk to GitHub all day. The existing HEARTH hunts for this pattern — scoring process rarity and interval regularity, or looking for an implant re-resolving its operator through issue text — all depend on knowing what ordinary GitHub API use looks like in *this* estate. On a developer workstation, package managers and IDEs produce so much GitHub traffic that an implant's handshake disappears into it. On a domain controller, a single API call is remarkable. Neither statement can be made without the baseline.

This hunt builds that baseline: the inventory of which host classes and which processes reach GitHub endpoints, under which account, with which credential class, and on what rhythm — recording the interval distribution rather than just the volume, because regularity is what separates a poller from a person.

## Why

- The destination is permitted by policy nearly everywhere, which makes it attractive as a channel precisely because the network control that would normally apply has been deliberately removed. The compensating control has to be process-level and host-class-level, and that requires an inventory.
- The population is bimodal in a way that defeats a single threshold. Build agents and developer workstations generate orders of magnitude more GitHub traffic than the rest of the estate, so one estate-wide threshold is simultaneously too loose for servers and too tight for developers. Separate baselines per host class are the only way to get a usable signal on both.
- Interval regularity is the discriminator, and it only exists relative to a known normal. Package and clone traffic is bursty and tied to human or pipeline activity; an implant polling for tasks is metronomic. The variance figure collected here is the input that makes that comparison possible.
- The "never does this" set is the highest-value product of the exercise and the cheapest to act on. Most hosts in most estates never contact the GitHub API. Enumerating them converts a noisy scored detection into a short list of hosts where any contact at all warrants a look.
- Credential class narrows attribution and response. Knowing which processes legitimately authenticate with which token, and who owns it, turns "a token was used from an odd host" into a revocation decision rather than an investigation.
