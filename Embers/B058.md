false_positive_notes: |
  Firmware is the tuning problem, exactly as in [[B057]]. Vendor upgrades replace binaries wholesale, add and remove daemons, change library paths and occasionally introduce new legitimate packet-socket users, so an untagged baseline produces a diff the size of the upgrade on every patch cycle and gets abandoned. Tag every snapshot with the exact firmware build, compare build-to-build, and make re-baselining a required step of the upgrade change rather than an afterthought. The second problem is that these devices are a heterogeneous population - a mail gateway, a DVR and a NAS share almost nothing, so a single estate-wide baseline is useless. Baseline per device class, per firmware build; the unit of comparison is "all Model X on build Y," which also means a compromise affecting one device in a class of thirty stands out as a population outlier without needing a prior snapshot at all. The third is legitimate churn - rotated logs, caches and temporary files change constantly, so scope the file inventory to paths that should be static (`/sbin`, `/usr/sbin`, library directories, the vendor add-on package directory) and exclude the ones that should not. Fourth, some appliances genuinely do capture packets - IDS, NDR and monitoring appliances, and firewalls doing deep inspection, will have legitimate long-lived packet sockets, so the expected packet-socket count for those classes is non-zero and must be recorded as such rather than treated as a finding. Finally, and most important - a baseline taken from an already-compromised appliance bakes the implant in as normal. These devices are chosen because they are unpatched and unaudited, which means some of them already have tenants. The BPF Rekoobe build spoofs `/sniper/bin/crond -n`, `/sniper/bin/earsd --start`, `/sniper/apache/bin/httpd -k start` and `/sniper/snipe/bin/snipe-smtpd` - names that only read as legitimate on a host actually running that platform.   Collection fields, grouped by what they unlock.
  - Packet-socket inventory. For each device - the contents of `/proc/net/packet`, each entry's inode mapped to a PID through `/proc/*/fd`, and for each owning process its `exe` target, `cmdline`, UID and start time relative to boot. Record the *expected count* per device class explicitly, including zero. This is what makes [[H366]] a one-line diff.
  - Daemon identity. For every process - `/proc/<pid>/exe`, `/proc/<pid>/cmdline`, and a flag for disagreement between them. Record the legitimate daemon name set per device class. A name in square brackets belonging to a process with a real executable is never legitimate and should be recorded as a permanent immediate flag rather than as baseline data.
  - Mapped shared objects. Per long-running daemon, the distinct backing paths of executable regions from `/proc/<pid>/maps`, with package ownership resolved where the appliance has a package manager. Record which daemons legitimately have plugin architectures. This is the allowlist [[H368]] subtracts from.
  - Static file inventory. `/sbin` and `/usr/sbin` contents with hashes, the complete setuid and setgid set, the vendor add-on package directory contents, and library-directory hashes - all tagged to firmware build. [[H367]]'s staging sequence writes into exactly these paths.
  - Mount options. Whether each bulk-storage mount is writable and exec-capable. This is a triage field and a mitigation in one - the dropper's `system()` call needs an exec-capable mount, and `noexec` breaks the chain outright with no interpreter fallback.
  - Egress profile. Per device class, the destination ports and address classes the device legitimately reaches, the hosts that have a genuine mail-sending role, and the TLS client fingerprint its own MTA presents on port 25. [[M055]] consumes all three.
  Collection window. Thirty days of egress telemetry to establish destination and volume profiles, and at least two firmware builds of on-device snapshots before the diff job is trusted, so that build-driven change can be distinguished from drift. On-device snapshots should be taken at least weekly and immediately before and after every firmware upgrade.
  Deliverable format. Per device class and firmware build, a signed snapshot stored off-appliance containing - the expected packet-socket count and owners; the legitimate daemon name set; the per-daemon mapped-library allowlist; hashes for `/sbin`, `/usr/sbin`, the setuid set and the add-on package directory; mount options; and the egress destination, port and TLS-fingerprint profile. Plus a scheduled diff job that reports additions, removals and `exe`-to-`cmdline` disagreements, and a population-outlier report comparing every device in a class against its peers.
  Immediate flags - do not wait for the baseline to complete. (1) Any process whose `cmdline` is bracketed like a kernel thread but whose `/proc/<pid>/exe` resolves to a real file. (2) Any process whose `/proc/<pid>/exe` resolves to a path suffixed `(deleted)` that the package database never owned. (3) A PID file for a product the device does not run, or one whose contents do not match a live PID - Rapid7 found `/var/run/spamsniper.pid` used as a mutex. (4) Any file whose extension is `.php` but whose first bytes are `#!/bin/sh`. (5) The existence of `/tmp/flag`, a marker named `execProcEnd` containing `end`, or a directory `/HDD/ms6x2xTo64/`. (6) A packet socket on a device class whose expected count is zero. (7) A second TLS client fingerprint on port 25 from a device that has exactly one MTA. (8) Outbound SMTP from an appliance to a mail-role hostname that resolves to consumer-grade or embedded address space.
  Enables. [[H366]] (packet socket with attached BPF filter), [[H367]] (guardrail-gated staging and unlinked executables), [[H368]] (runtime shared-object loading) and [[M055]] (port-25 beacon interval scoring). [[B057]] is the sibling baseline for internet-facing web appliances; the two overlap on file integrity and should share storage and tagging conventions but not be merged, since the collection surface and the device populations differ.

# B058

Rapid7's BPFDoor and AVERAT research contains one sentence that is really a statement about baselines: "each sample is aware of the vendor's software running on the targeted systems and implements process spoofing accordingly."

The South Korean builds impersonate the PID file of SpamSniper, a Korean anti-spam product. The Rekoobe build claims names like `/sniper/bin/earsd --start` and `/sniper/snipe/bin/snipe-smtpd`. One variant calls itself `ora_ppmond`, imitating the naming convention of Oracle-backed telecom provisioning platforms — a disguise that only reads as legitimate on a host actually running that class of infrastructure. The dropper derives its encryption key from `SHA1("ShareTech")` and installs from that vendor's own add-on package directory.

None of this is generic malware wearing a generic costume. Each build is tailored to the specific product running on the specific device, which means a generic signature was never going to catch it and a knowledgeable human reading a process list was never going to blink. What defeats all of it, cheaply, is knowing what the device is supposed to run.

That knowledge does not exist anywhere today for most estates. Appliances are the one class of production system with no EDR agent, no software-inventory entry and no file-integrity monitoring — which is exactly why they were chosen. Rapid7's own C2 relays make the point from the other direction: a fuel retailer's Synology NAS still serving an expired 2021 certificate, an embedded appliance with a self-signed cert valid from 2004 to 2014, a Dahua recorder. Reachable, unpatched, unmonitored, unlikely to be audited.

So the four hunts this baseline enables each ask a question the appliance cannot answer alone. Is this packet socket expected? Does this daemon's name match its executable? Is this shared object package-owned? Should this device be sending mail to a consumer broadband address every ten minutes? With a per-device-class, per-firmware-build snapshot, each becomes a diff. Without one, each becomes an investigation nobody has time for.

One warning worth stating plainly: these devices are selected because they are already neglected, so some of them already have tenants. A baseline captured from a compromised appliance enshrines the implant as normal. Where a device has sat internet-facing and unpatched through a known exploitation window, the first snapshot is evidence, not a baseline.

## Why

- **The disguises are vendor-specific, so only local knowledge defeats them.** `ora_ppmond` and `snipe-smtpd` are convincing precisely to the engineer most likely to review the process list. A recorded daemon set is the only thing that makes the imitation visible.
- **Appliances are the gap in every other control.** No agent, no inventory, no FIM. A scheduled off-device snapshot is the cheapest way to create the telemetry that should have existed, and it works on devices that will never host a sensor.
- **Expected packet-socket count is the single highest-value field.** On a mail gateway or a DVR it is usually zero, and recording that fact converts [[H366]] from an analysis task into a one-line comparison.
- **A heterogeneous population is a feature once you baseline per class.** Thirty identical devices on one firmware build mean a compromise on one shows up as a population outlier — detectable even before any historical snapshot exists.
- **`exe`-versus-`cmdline` disagreement is a permanent immediate flag.** It costs nothing to collect, has essentially no benign case on an appliance, and defeats `prctl(PR_SET_NAME)` and `argv` rewriting generically rather than name by name.
- **Mount options are a mitigation hiding in an inventory field.** The dropper's `system()` call requires an exec-capable bulk-storage mount; `noexec` returns `EACCES` and the shell offers no fallback. Recording the mount table tells you which devices are already immune.
- **Firmware-build tagging is what keeps the baseline alive.** Untagged snapshots produce upgrade-sized diffs every patch cycle and get switched off within two months. Build-to-build comparison, with re-baselining as a required upgrade step, is the difference between a control and an abandoned script.
- **It supplies the asset roles the network model needs.** [[M055]] cannot score port-25 egress without knowing which hosts have a legitimate mail-sending role and what TLS fingerprint their real MTA presents. That is baseline data, not detection data.
