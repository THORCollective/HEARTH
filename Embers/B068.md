false_positive_notes: |
  A new application release changes traffic shape across every endpoint at once - new routes appear, old ones fall away, retry behaviour changes and object-access patterns shift. Baselines must be versioned against the client release, not maintained as a single rolling profile, or every release will invalidate the model.
  Legitimate batch and integration traffic looks exactly like enumeration: reporting jobs, partner integrations, data warehouse extracts and reconciliation runs all touch many distinct objects quickly under one principal. These must be enumerated and profiled separately during the baseline window rather than discovered later as alerts.
  Customer support and administrative staff legitimately access many unrelated customer objects in a day, which is the single most common source of false positives on the object-breadth measure. Baseline internal roles separately from end-user cohorts; a support principal and a mobile user should never be compared against the same threshold.
  Sequential or near-sequential object identifiers are common in legitimate pagination and in clients that prefetch. Sequence alone is weak. It matters in conjunction with breadth and with a high ratio of distinct objects to session length.
  Source address and user agent are supplied by the client and are trivially forged, so they can shape cohorts but must never gate a decision. A baseline that keys trust on user agent is teaching the attacker exactly what to send.
  Shared egress - carrier-grade NAT, corporate proxies, VPN concentrators - collapses many users behind one address, so per-address thresholds will be wrong in both directions. Key the baseline on the authenticated principal, falling back to address only where no principal exists, and record which fallback was used.
notes: |
  Platform - externally exposed application backends and API gateways, serving mobile and web clients. This is deliberately not an endpoint hunt: the activity never touches a managed host, which is why endpoint telemetry contributes nothing and why this surface is commonly unmonitored.
  Why a baseline rather than a hunt - the defining property of this activity is that every request is valid. The route exists, the method is right, the parameters are well-formed, and in the authenticated case the credential is real. There is no payload to signature, no exploit string, no anomalous process and no malware. What distinguishes an attacker is how many distinct objects one principal touched, how fast, and whether the identifiers they addressed look like the ones real clients address. Each of those is a comparison against normal, and none can be computed until normal has been measured. That is the Embers case in its purest form, and it is why this file deliberately ships before any hunt built on it.
  What the reporting states - AhnLab synthesises breaches disclosed across Korea and Japan in October 2026 and finds the entry points were consistently peripheral rather than core. On the Japanese analysis: on October 13 the National Institute of Information and Communications Technology "analyzed publicly available Android apps to identify the target servers and API structures, then named the method of exploiting server-side vulnerabilities" A2B. The flaw classes are listed: "The vulnerabilities primarily targeted include SSRF, RCE, SQL injection, and IDOR/BOLA; even if the app itself has no flaws, data leaks can occur if there are vulnerabilities in the server-side API." The scale is in the incident lines - one case where "The API was misused for four days", with a potential leak of roughly 22.5 million member records including passwords, and a Korean case where "By bypassing standard authentication and repeatedly entering query values" loan information on about 25,000 people was retrieved. The recommendation AhnLab draws is the one this baseline operationalises: "Verify server-side authentication and object-level authorization for all API requests, and do not embed API keys or authentication credentials within the app."
  The four-day detail is the one worth dwelling on - an API misused for four days before anyone noticed is not a detection-tuning problem, it is an absence of any per-principal volumetric view at all. A baseline that produced a daily distribution of objects-touched-per-principal would have surfaced that on day one, without any threat intelligence and without knowing the flaw existed.
  Collection window - 30 days minimum, covering at least one full billing or reporting cycle and at least one application release, because both produce legitimate traffic shapes that a shorter window will misread as anomalous.
  Data to collect, per request, over the window:
  1. Endpoint identity - the route template rather than the literal path, so that per-object URLs collapse into one endpoint for counting.
  2. Authenticated principal identifier, and the authentication method used.
  3. Object or resource identifier addressed, stored as a tokenised or hashed value, plus its format and whether it is sequential, a UUID or an opaque token.
  4. HTTP method and response status, including the authorization-failure statuses, which are the signal that enumeration is being refused.
  5. Response size in bytes and record count in the body, since a one-record read and a bulk export often share a URL.
  6. Timestamp at second resolution, needed for rate and burst measurement.
  7. Client-declared user agent, app version, platform; source address and autonomous system - cohort shape only, never trust.
  8. Session or token identifier, so that objects touched per session can be computed rather than only per principal per day.
  Derived measures to compute for each endpoint, and for each consumer cohort separately:
  - Distinct objects accessed per principal per hour and per day, as a full distribution with median, 95th and 99th percentiles, not as a mean. The distribution is the deliverable; the mean is useless because these populations are heavily skewed.
  - Requests per principal per minute, with the normal burst profile, so that a rate limit can be set from evidence rather than from a guess.
  - Ratio of distinct objects to total requests per session. A real user reads the same few objects repeatedly; an enumerator reads many objects once. This ratio is the single most discriminating measure in the set.
  - Identifier-range profile per endpoint: what proportion of accessed identifiers fall within the ranges a legitimate client would hold, and what sequential-access looks like in normal pagination.
  - Authorization-failure rate per principal, baselined, since a working object-level check turns an enumeration attempt into a burst of refusals rather than into a leak.
  - Response-size distribution per endpoint, which catches a parameter that quietly converts a single-record endpoint into a bulk one.
  - Endpoint inventory difference: routes observed in logs that do not appear in the API inventory. Undocumented routes are the ones with no review and no rate limit.
  Deliverable - a per-endpoint, per-cohort profile document recording: the normal distribution of objects-touched-per-principal, an evidence-based rate limit, the expected identifier format and range behaviour, the legitimate batch and integration principals with their own separate profiles, the baselined authorization-failure rate, and the list of undocumented routes found. The profile should be versioned against the client release it was measured on. That document is the deliverable; the detections that follow are thresholds read off it.
  Flag immediately, without waiting for the window to complete - these do not need a baseline to be wrong:
  - Any endpoint returning object data with no authorization check at all, discovered by replaying a valid session against an object identifier that principal does not own. This is the IDOR and BOLA case and it is a finding on sight.
  - Any undocumented route that returns customer data.
  - Any principal whose distinct-object count in a single day exceeds the total number of objects that principal could plausibly own - a retail customer reading ten thousand account records needs no statistical context.
  - Credentials or API keys recoverable from a published client package, which AhnLab names directly in its recommendation.
  - Any endpoint with no rate limit that returns personal data.
  - Sustained authorization-failure bursts from one principal against sequential identifiers, which is enumeration being correctly refused and is still an incident.
  Inference, not stated in the reporting - every measure, field list, derived metric and immediate-flag criterion above is mine. AhnLab and the Japanese agencies described the attack class, the flaw types and the breach outcomes; they did not publish detection logic, telemetry schemas or thresholds, and no numbers in the measures section come from the reporting. AhnLab is also explicit that attribution and causes remain under investigation in most of the individual incidents it lists, and that neither Japanese organisation named specific victim companies, so individual cases should not be treated as confirmed A2B attacks.
  Why this file exists at all - this organisation has no existing baseline or hunt covering mobile and web application backends, which is a gap worth naming rather than quietly filling. [[B022]] is the closest existing baseline and covers legitimate management-plane access, which is a different population, a different identity model and a different consumer set. No Flames hunt currently depends on this baseline; it is the prerequisite for writing one, and the object-breadth and identifier-range profiles are the specific outputs a future enumeration hunt would need.

# B068

A mobile app is a specification of your API that you handed to everyone. Pulling it apart to learn the backend routes, the parameter names and the object identifier format takes an afternoon, and nothing about that is an attack. The attack is what comes next, and it consists of making correct requests.

That is the pattern behind a run of October 2026 breaches across Korea and Japan. Japan's national research institute analysed public Android apps "to identify the target servers and API structures" and named the class "A2B (App-to-Backend) attacks" — noting that "even if the app itself has no flaws, data leaks can occur if there are vulnerabilities in the server-side API." The Korean cases have the same shape. In one, "By bypassing standard authentication and repeatedly entering query values," loan information on roughly 25,000 people came out. In a Japanese case, "The API was misused for four days," with up to 22.5 million member records exposed.

Four days is the number that matters. That is not a tuning failure — a tuned detection would have fired on day one. It is the signature of having no per-principal volumetric view of the API at all. The requests were well-formed, the routes existed, the responses were 200s. There was no exploit string to match, no malware, no process, no managed host involved anywhere in the chain, which is exactly why endpoint tooling contributes nothing here and why this surface tends to go unwatched.

What separates an attacker from a customer is arithmetic: how many distinct objects one principal touched, how quickly, and whether the identifiers they addressed are ones a real client would hold. The most discriminating single measure is the ratio of distinct objects to total requests within a session — a genuine user reads the same handful of records over and over, while an enumerator reads thousands of records exactly once. But that ratio means nothing without a measured distribution behind it, and the distribution has to be built per endpoint and per cohort, because a support agent and a retail customer are not comparable populations.

Hence a baseline rather than a hunt. The output is a profile document: normal objects-per-principal distributions, an evidence-based rate limit, expected identifier ranges, the legitimate batch integrations profiled separately, and the list of undocumented routes nobody knew were serving data. Version it against the client release, because every app release reshapes the traffic.

Some things should not wait for the window to finish. An endpoint that returns object data with no authorization check is a finding the moment it is found. So is a published client package with a recoverable API key — AhnLab's recommendation says it directly: "Verify server-side authentication and object-level authorization for all API requests, and do not embed API keys or authentication credentials within the app."

## Why

- Every request in this activity is valid by construction, so signature, exploit and malware detection have nothing to act on and only comparison against normal can work.
- The entire chain happens off managed endpoints, which means endpoint telemetry never sees it and most organisations have no compensating view of the API layer.
- A four-day undetected misuse window indicates a missing volumetric view rather than a mis-tuned threshold — a measured per-principal distribution would have surfaced it immediately.
- The attack surface is peripheral by nature: auxiliary inquiry services, support systems and forgotten routes attract less review than core systems while reaching the same data.
- Every client-supplied field is attacker-controlled, so the baseline has to key on the authenticated principal, and one built on user agent or source address teaches the attacker what to send.
- The baseline produces immediate value independent of any adversary, because the endpoint inventory difference surfaces undocumented routes serving customer data and the rate profile turns a guessed limit into a measured one.
- This organisation currently has no coverage of mobile and web application backends at all, so this is a named gap being closed rather than an incremental addition.
