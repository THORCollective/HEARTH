notes: |
  The two incidents behind this baseline are Kaspersky GERT's ESXi and Proxmox ransomware cases. In the first, a PRTG Network Monitor deployment held credentials with broad access to the ESXi hosts and the same root password was reused across several nodes, so compromise of the monitoring platform produced hypervisor administration. Kaspersky's framing of the structural fault is the reason this baseline exists: "This design joined monitoring, credential storage, and direct administration into one attack path." In the second, plaintext credential notes on an administrator workstation yielded the Proxmox realm root account. The hunts this baseline enables are [[H458]] for the ESXi execution-policy chain and [[H459]] for the Proxmox console sweep.
  Collection window - thirty days, covering at least one full patch cycle and one backup-retention cycle, so scheduled automation appears in the record. Extend to forty-five days if the estate has a monthly maintenance window that would otherwise fall outside the period. Re-baseline quarterly, and after every monitoring, backup or automation deployment, because those are the changes that silently add a privileged identity.
  Fields to collect, per authentication event - the hypervisor or node name; the account name with its realm or domain; the authentication result; the protocol and port; the source IP address and the resolved host name of that source; the client user agent where the platform records one; the session identifier; the timestamp; and whether the session was interactive (a shell or a console) or programmatic (an API call or a token use). For ESXi specifically, also record whether the session arrived through vCenter or directly to the host, because that distinction is the whole point.
  Fields to collect, per identity - the account name; whether it is local to the host, defined in a realm, or federated; its assigned role and the objects that role applies to; whether multifactor authentication is enforced; whether the credential is stored anywhere outside a vault, and if so in which platform; the last rotation date; and the named owner. An identity with no named owner is a finding before the baseline is even finished.
  Fields to collect, per host configuration - SSH service state and whether it starts at boot; Lockdown Mode state; the SSH exception-user list; the set of local accounts; the values of the advanced security settings that matter (execution policy, Secure Boot enforcement, TPM-backed configuration protection); firewall rule set; and the remote logging destination. Capture these on a schedule, not once, because Kaspersky's point is that a secure configuration set once does not mean the control remains active on the host.
  Deliverable - a management-plane access register with four tables. First, an identity table: every account that can authenticate to each hypervisor, its role scope, its owner, its multifactor state, and whether it is a person or automation. Second, a path table: for each identity, the source addresses and protocols from which it was actually observed authenticating, expressed as named hosts rather than bare addresses. Third, a credential-location table: which external platform holds which hypervisor credential, built from the credential-store inventory rather than from assumption. Fourth, a shared-secret table: which hosts share a local account password, established by deliberate test or by rotation records, since this is the number that determines blast radius and it is almost never written down.
  Flag immediately, without waiting for the thirty days - these do not need a baseline to be wrong.
  - A monitoring, backup or replication platform's identity opening an interactive session (an ESXi shell, an SSH session, a Proxmox console) rather than making API calls. Kaspersky's remediation guidance is explicit that monitoring servers should be prevented from starting interactive administrator sessions unless a separately approved support workflow requires it.
  - One local root or administrator account authenticating successfully to two or more hosts within an hour from different source addresses.
  - A successful hypervisor authentication from a source that is an end-user workstation or laptop rather than a jump host or management server.
  - Any change to SSH service state, Lockdown Mode, the exception-user list, local accounts, firewall rules, remote logging settings, or the execution-policy and Secure Boot settings, with no matching change record or vCenter task.
  - A hypervisor credential discovered stored in a monitoring tool, script, scheduled task, connection manager or service configuration where the inventory did not expect one.
  - An administrative identity with no named owner, or whose owner has left.
  - Remote log forwarding absent or broken on any host, since that silently removes the evidence both enabled hunts depend on.
  What the baseline is expected to reveal - in most estates, three things. That the set of identities able to administer hypervisors is larger than anyone's mental model, mainly because of automation added over years. That a handful of local accounts share one password across many hosts, which no document records. And that interactive administration still happens directly to hosts rather than through the central management plane, which is the path Kaspersky identifies as bypassing role controls entirely. Each of those is actionable without any intrusion, which is why this baseline is worth running on its own merits.
  How to use it once built - the access register turns both enabled hunts from statistical exercises into exception reports. For [[H458]], the shared-secret table tells you, at the moment one host is hit, exactly which other hosts are already reachable. For [[H459]], the path table tells you whether a console sweep came from a host that identity has ever used. Without the register, both hunts still work but produce a queue; with it, they produce findings.

# B070

Kaspersky's Global Emergency Response Team published two ransomware cases in virtualized environments. Neither involved an exploit against the hypervisor. Both involved a valid credential arriving over a path that was allowed.

In the first, the environment monitored its virtual infrastructure with PRTG. PRTG supports storing VMware credentials at the device or inherited group level, which is a useful feature and also means a monitoring server becomes privileged infrastructure. Those stored credentials had broad access to the ESXi hosts, and the same root password was reused across several nodes. Compromising the monitoring platform produced hypervisor administration, and one recovered secret reached every node that shared it.

In the second, an administrator's workstation held plaintext notes containing the Proxmox root credential. The actor logged in to the management interface and drove the cluster through its own API.

Neither case produces an anomalous event in isolation. Root authenticating over SSH to an ESXi host is normal in many estates. The realm root account opening a console is normal. A monitoring server reaching the hypervisor is normal, because that is its job. The activity only becomes visible against a record of what each identity normally does, from where, and by which protocol - and that record is exactly what most environments do not have.

This baseline builds it. It is a detection prerequisite, and it is also a standing control inventory: the shared-password table and the credential-location table are findings in their own right, available before anything happens.

## Why

- Both incidents used valid credentials over permitted paths, which means no behavioural detection can fire without a notion of normal. The hunts that cover the ESXi execution-policy chain and the Proxmox console sweep are both written against this baseline, and both degrade to a triage queue without it.
- The number that determines blast radius is undocumented almost everywhere. Which hosts share a local root password is rarely written down, is not visible in any log, and is the single fact that converts one compromised host into a farm. Establishing it is a deliberate exercise, not a query.
- Monitoring and backup platforms are privileged infrastructure that is usually governed as if it were not. They hold administrative credentials for the systems they observe, they are reachable from the server network, and they are rarely in scope for privileged-access review. An inventory of which platform holds which hypervisor credential is cheap and consistently surprising.
- Hypervisors have almost no endpoint telemetry, so the management plane's own authentication records are the primary evidence source. That makes verifying remote log forwarding on every host part of the baseline rather than an assumption, particularly since the encryptor in the ESXi case wiped logs as part of its own execution.
- Configuration drift is the quiet failure mode. Security settings that were enabled once can be switched off by the same credential used for daily administration, so capturing configuration state repeatedly - rather than at build time - is what makes a change detectable at all.
