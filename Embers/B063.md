id: B063
category: Embers
title: Baseline of sanctioned security testing - which engagements, accounts, hosts and markers are authorised, so an intruder cannot borrow the label
hypothesis: >-
  An intrusion that announces itself as a red team engagement is asking the defender a question the
  defender usually cannot answer quickly: is this ours? Unit 42 reports that it "observed the attackers
  employing planted deception techniques to mislead post-incident analysis", attempting "to disguise
  their activity as a red team operation, by using operational indicators such as the key
  RedTeamOps2025 in one of the malicious scripts, and pentest123 as a password for a user the attackers
  created". That works only against an organisation with no authoritative record of what testing is
  sanctioned. Build the record: every authorised engagement with its dates, scope, source addresses,
  operator accounts, tooling and agreed markers, so that an artefact claiming to be security testing can
  be confirmed or refuted in minutes rather than argued about for days. The deliverable is a lookup an
  analyst can query mid-incident, not a document in a shared drive.

required_data_sources:
  - 'The authoritative record of engagements - penetration test scopes, red team rules of engagement, vulnerability scan schedules and bug bounty authorisations - with start and end dates, which most organisations hold in a ticketing system or a contract folder rather than anywhere an analyst can query'
  - 'Source address allocations for each engagement, including the testing vendor''s egress ranges and any cloud infrastructure they declared'
  - 'The accounts created for or used by testers, including local accounts on target hosts, and the naming convention they were asked to follow'
  - 'Agreed engagement markers - file naming patterns, user-agent strings, canary values or header tokens the testers committed to use, which is the half of deconfliction most organisations never ask for'
  - 'Process and file telemetry across the estate for the strings that engagements legitimately produce, so the baseline can be validated against what actually appears'
  - 'Local account creation events (Linux /etc/passwd changes and auditd records; Windows Event ID 4720) across the estate, for the account-naming half of the baseline'
  - 'An inventory of sanctioned offensive tooling and where it is licensed to run, so a known tool in an unsanctioned location is distinguishable from a known tool doing its job'
false_positive_notes: |
  This baseline inverts the usual false-positive problem: the risk is not noise but a stale or
  incomplete record that launders real intrusions. Three failure modes matter more than any query. An
  engagement record that is not updated when scope changes mid-test will mark genuine tester activity as
  unauthorised, which trains analysts to ignore the lookup - so the record must be owned by whoever
  approves engagements and updated as a condition of the engagement, not reconstructed afterwards. A
  record that is too permissive is worse: "the vendor may use any cloud egress" authorises the entire
  internet and is how a deception marker succeeds. And legitimate security tooling genuinely litters the
  estate with testing-adjacent strings - Atomic Red Team test artefacts, Caldera and Metasploit
  installations on sanctioned hosts, BloodHound collection output, vulnerability scanner credentials
  named for the scanner, EICAR test files, and training-range material - all of which are real and all
  of which must be in the baseline rather than treated as findings each time. Expect developers to use
  `test`, `pentest` and `admin123`-class passwords in non-production environments, which is a genuine
  hygiene problem but not this one; keep the two queues separate or the baseline drowns. One asymmetry
  to state plainly: a mature red team will deliberately avoid obvious markers, so the absence of a
  marker does not indicate an intruder and the baseline's value is confirmation, not exclusion.
notes: |
  Platform: Linux and Windows (estate-wide; the record itself is platform-independent). Driven by Unit 42
  (Palo Alto Networks), "AI-Powered Espionage Campaign Targets Government Linux Infrastructure"
  (15 October 2026), by Roey Porat and Tom Fakterman, which tracks the cluster as CL-UNK-1211 and
  reports activity "spanning from October 2025-April 2026" against government entities and
  state-affiliated infrastructure.
  Why this is a baseline rather than a detection. There is no query that distinguishes an authorised
  tester from an intruder impersonating one, because the artefacts are deliberately identical - that is
  the entire point of the technique. The discriminating information does not live in telemetry at all;
  it lives in the organisation's own records of what it authorised. If those records are a contract PDF
  and somebody's memory, the deception works. If they are a queryable lookup, it fails immediately.
  This is the rare case where the hunt's deliverable is a data source the organisation does not yet
  have, which is exactly what the Embers category is for.
  What the report attests. Unit 42 names two specific markers: the key `RedTeamOps2025` found in one of
  the malicious scripts, and `pentest123` used as the password for a user the attackers created. The
  report does not say the deception succeeded, nor that any responder was misled, nor how long the
  activity went unexamined - it describes the attempt and its purpose, which Unit 42 frames as intending
  "to mislead post-incident analysis". The generalisation below, that organisations commonly lack a
  queryable authorisation record, is observation rather than reported detail and is not attributed to
  Unit 42.
  Why the technique is well chosen. A responder who finds `pentest123` on a newly created account faces
  a question with an expensive wrong answer in both directions. Escalate, and you may be burning hours
  and goodwill on an authorised engagement - a mistake people remember. Stand down, and you have
  dismissed an intrusion. Under time pressure, with no authoritative record, the socially cheaper answer
  is to assume it is internal and ask around, and asking around takes days. The deception does not need
  to be believed. It only needs to delay.
  Data to collect, per engagement. Engagement identifier and the approving owner; exact start and end
  timestamps including any extension; in-scope hosts, networks and applications; the tester source
  addresses, with the vendor's declared egress ranges enumerated rather than described; every account
  created for or used by testers, including local accounts, with their naming convention; the tooling
  authorised and the hosts it is licensed to run from; and the agreed markers - file naming patterns,
  user-agent strings, canary tokens or header values the testers commit to. Collect the same fields for
  recurring activity that is not an engagement at all: vulnerability scan windows and scanner source
  addresses, bug bounty researcher activity, and any purple team or detection-validation tooling such as
  Atomic Red Team that runs on a schedule.
  Collection window. Thirty days of estate telemetry is enough to validate the marker and account
  queries against reality and to find the testing-adjacent strings that already exist legitimately, but
  the engagement record itself should be populated for a rolling twelve months, because an intruder's
  claimed engagement will often reference a real past test. A record that covers only the current month
  cannot refute "this is left over from the assessment in March".
  Deliverable format. A queryable lookup - a CSV, a lookup table in the SIEM, or a small table an
  analyst can join against - keyed so that three questions can be answered in one step: is this source
  address authorised to be testing this host today; is this account one the testers created; and is this
  marker string one anybody committed to use. Alongside it, an allowlist of the legitimate
  testing-adjacent artefacts already present in the estate (Atomic Red Team paths, sanctioned tooling
  installations, scanner service accounts, EICAR files) so each one is explained once rather than
  rediscovered. The lookup must be reachable from the incident queue, not from a document library.
  Immediate flags, which do not wait for the baseline to be complete. An account created outside change
  control whose password or name carries testing branding, on a production host, where no engagement is
  open. Testing-branded strings in scripts under `/tmp`, in web-accessible directories, or in service
  configuration - locations no engagement deliverable belongs in. A testing-branded artefact on a host
  that is out of scope for every engagement in the record, which is the cleanest version of this
  finding. Any engagement marker appearing from a source address outside the declared ranges. And a
  claimed engagement reference that does not resolve to a record at all, which should be treated as an
  intrusion until someone with authority says otherwise.
  Core filter. Sweep the estate for testing-branded artefacts and accounts, then join each hit against
  the engagement record; anything that does not join is a finding.
  Sample shell for the artefact sweep on Linux hosts, looking for testing branding in the locations
  where engagement deliverables do not belong.
  `grep -rliE 'red ?team|pentest|RedTeamOps|purple ?team' /tmp /var/tmp /dev/shm /opt /usr/local/bin /var/www 2>/dev/null | head -50`
  Sample shell for the account half on Linux - locally created accounts, newest first, for comparison
  against the tester account list.
  `awk -F: '$3 >= 1000 && $3 < 65534 { print $1, $3, $6, $7 }' /etc/passwd | sort -k2 -n`
  Sample KQL for Microsoft Defender XDR, for testing-branded files written across the estate. The 30-day
  bound is the advanced hunting retention limit.
  `DeviceFileEvents | where Timestamp > ago(30d) | where FileName matches regex @"(?i)(redteam|pentest|purpleteam|c2test)" | summarize Writes = count(), Hosts = dcount(DeviceName), Devices = make_set(DeviceName, 20), FirstSeen = min(Timestamp) by FileName, InitiatingProcessFileName | order by FirstSeen desc`
  Sample KQL for local account creation carrying testing branding, which is the shape Unit 42 describes.
  `DeviceEvents | where Timestamp > ago(30d) | where ActionType == "UserAccountCreated" | where AccountName matches regex @"(?i)(test|pentest|redteam|audit|assess)" | project Timestamp, DeviceName, AccountName, InitiatingProcessAccountName, InitiatingProcessFileName, InitiatingProcessCommandLine | order by Timestamp desc`
  Sample Splunk SPL for the join that is the whole point of this baseline - testing-branded activity
  checked against the engagement lookup, surfacing only what fails to match. Note the parenthesised OR,
  since Splunk binds OR tighter than the implicit AND.
  `index=* (process_name="*pentest*" OR process_name="*redteam*" OR (user="*pentest*" action=created)) | lookup authorised_engagements src_ip AS src OUTPUT engagement_id, scope_end | where isnull(engagement_id) OR _time > scope_end | table _time, host, user, src, process_name, engagement_id | sort - _time`
  Sample Splunk SPL for the scope test - a marker from an engagement that is real but is appearing
  somewhere it was never authorised to appear, which is how a borrowed label is caught.
  `index=* marker_string=* | lookup authorised_engagements marker_string OUTPUT engagement_id, in_scope_hosts | where isnotnull(engagement_id) | eval in_scope = if(match(in_scope_hosts, host), 1, 0) | where in_scope = 0 | stats values(host) AS out_of_scope_hosts, count BY engagement_id, marker_string`
  Relationship to existing HEARTH coverage, stated plainly. A search of hunt titles and hypotheses for
  disguising activity as authorised testing returns nothing - the many hunts that match "red team" do so
  only through Atomic Red Team references in their reference lists, which is not coverage of this
  behaviour. The Flames hunts this Ember supports are the other legs of the same intrusion: [[H399]] on
  PHP configuration persistence, [[H400]] on the `.bashrc` credential interception whose log file was
  likewise named to mislead, and [[H401]] on mailbox collection. The naming-deception idea is shared with
  [[H400]] and [[H391]], where a monitoring product and a software vendor respectively are impersonated
  in a filename and a User-Agent; this Ember generalises that to the organisation's own security
  programme, which is the one label a defender is least likely to challenge. [[B021]] and [[B022]]
  baseline sanctioned remote access and appliance management respectively and are adjacent records with
  the same structure.

# B063

`pentest123`.

You find that as the password on an account created two weeks ago on a production Linux host. What do you do in the next ten minutes?

Unit 42 found the CL-UNK-1211 operators betting that the answer is "ask around." They report that they "observed the attackers employing planted deception techniques to mislead post-incident analysis", attempting "to disguise their activity as a red team operation, by using operational indicators such as the key RedTeamOps2025 in one of the malicious scripts, and pentest123 as a password for a user the attackers created."

This is cheap. It costs the attacker one string. And it works against the organisation's social structure rather than its technology.

Think about the responder's position. Escalate, and you might be burning a Saturday and a lot of goodwill on an authorised engagement — the kind of mistake colleagues bring up months later. Stand down, and you have waved through an intrusion. With no authoritative record and a clock running, the socially cheaper move is to assume it is internal and start asking. Asking takes days.

The deception does not need to be believed. It only needs to delay.

And notice there is no query that fixes this. The artefacts an intruder plants and the artefacts a real red team leaves are *deliberately identical* — that is the whole technique. The discriminating information is not in your telemetry at all. It is in your own records of what you authorised.

Which is the problem, because in most organisations those records are a contract PDF, a Jira ticket nobody can find, and somebody's memory of a kickoff call.

So the deliverable here is not a detection. It is a data source you probably do not have yet: a queryable lookup that answers three questions in one step.

Is this source address authorised to be testing this host today? Is this account one the testers created? Is this marker string one anybody actually committed to use?

Minutes instead of days. That is the entire value.

Two design notes decide whether it works.

The record has to be owned by whoever approves engagements, and updated *as a condition of the engagement* rather than reconstructed afterwards. A record that goes stale when scope changes mid-test will flag real testers as intruders, analysts will learn the lookup is wrong, and it dies.

And it must be specific. "The vendor may use any cloud egress" authorises the entire internet. That is not a record; it is a loophole, and it is precisely the loophole a planted marker walks through. Enumerate the ranges. Agree the markers in advance — file naming patterns, user-agent strings, canary values — because asking testers to commit to a marker is the half of deconfliction almost nobody does, and it is the half that makes refutation possible.

One honest limit. A good red team deliberately avoids obvious branding, so the absence of a marker tells you nothing about whether activity is authorised. This baseline is for confirmation, not exclusion. It cannot tell you an intruder is an intruder; it can tell you quickly that they are not yours.

A few things should not wait for the record to be finished. A testing-branded artefact on a host that is out of scope for every engagement you have. Testing-branded scripts in `/tmp` or a web root, where no engagement deliverable belongs. An account with testing branding created outside change control while no engagement is open. And a claimed engagement reference that resolves to nothing at all — treat that as an intrusion until somebody with authority says otherwise.

## Why

- **The discriminating data is organisational, not technical.** No telemetry separates an authorised tester from an impersonator, because the artefacts are identical by design — only the authorisation record resolves it.
- **The attack targets response time rather than detection.** A planted marker does not have to be believed to succeed; buying days of hesitation during an active intrusion is the entire return on one string.
- **Responders face asymmetric social cost.** Escalating against your own red team is a visible, memorable mistake, which biases the quick answer toward "probably ours" exactly when that is most dangerous.
- **Most organisations cannot answer the question at speed.** Engagement scope typically lives in contracts and tickets rather than anywhere joinable to an alert, which is the gap this deception exploits.
- **Agreed markers make refutation instant.** If testers commit in advance to a naming pattern or token, an artefact that does not carry it is immediately not theirs — but only if someone asked for that commitment.
- **Vague authorisation is worse than none.** Permitting unspecified cloud egress or open-ended scope launders intruder activity through a real engagement record.
- **The legitimate testing litter must be catalogued once.** Atomic Red Team artefacts, sanctioned C2 installations, scanner accounts and EICAR files are real and permanent, so explaining them in the baseline prevents rediscovering them every incident.
- **A twelve-month record is needed, not a current-month one.** Intruders reference real past engagements, and a record that cannot speak to March cannot refute a claim about March.
- **It must be reachable from the incident queue.** A document in a shared drive is not a control; the test of this baseline is whether an analyst can join against it mid-incident without asking a human.
