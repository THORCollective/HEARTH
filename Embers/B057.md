false_positive_notes: |
  The central tuning problem here is firmware, not malice. Vendor upgrades rewrite configuration files, replace web-root content, change file hashes wholesale and occasionally add or remove setuid binaries, so a baseline that is not tagged to an exact build will produce a diff the size of the upgrade on every patch cycle and be abandoned within two months. Tag every snapshot with the exact firmware build and compare build-to-build, re-baselining immediately after each upgrade as a required step of the change. The second source of noise is legitimate customisation - branded VPN portal themes, custom logon pages, and vendor support bundles all place files in the web root. These are not noise to be suppressed but inventory to be recorded, with a named owner, at the time they are introduced. The third is the appliance's own operational churn - temporary files, rotated logs and cache directories change constantly, so scope the file inventory to the directories that should be static (web root, client plug-in staging, binary and configuration paths) and exclude the ones that should not. Finally, note that a baseline taken from an already-compromised appliance bakes the compromise in as normal. Where an appliance has been internet-facing and unpatched through a known exploitation window, treat the first snapshot as evidence to be reviewed against the vendor image, not as a baseline to trust.
notes: |
  Platform: internet-facing network appliances — written against Citrix NetScaler ADC and Gateway, and directly portable to Ivanti, Fortinet, SonicWall, F5 and similar devices. Driven by Google Threat Intelligence Group / Mandiant, "Defending Against Active Exploitation of Citrix NetScaler ADC and Gateway Appliances" (29 September 2026), covering CVE-2026-88772 and CVE-2026-88771. Every triage command Mandiant published is a comparison in disguise - `grep -En -i "application/x-httpd-php|php_flag|AliasMatch" /etc/httpd.conf` asks whether a directive is new; `file ... | grep -E "ASCII text|PHP script"` asks whether a file type belongs; `ls -l /bin/sh` asks whether a permission bit changed. Each is fast and high-yield precisely because the expected answer is known — and on most estates it is known only in the responder's head, during an incident, under time pressure. This baseline writes it down in advance.
  What to collect, per appliance, per firmware build
  - Device identity - hostname, management IP, model, exact firmware build string, HA role and partner, internet exposure, owning team, and whether the device is vendor-managed.
  - Web root and staging inventory - full recursive listing of the GUI and portal directories (on NetScaler - `/var/netscaler/gui/`, `/netscaler/ns_gui/`, `/var/vpn/`, `/netscaler/portal/`, and the client plug-in script directories for linux, vista and mac), recording for each file - path, size, mtime, ctime, owner, mode, SHA256, and the output of `file` for its detected type. The detected type is the field that matters most - these directories should hold binaries, archives and media, so recording the type makes "an ASCII text file appeared here" a one-line diff.
  - Web server configuration - the full contents of `/etc/httpd.conf`, `/nsconfig/httpd.conf` and `/flash/nsconfig/httpd.conf`, plus an extracted list of every `AddHandler`, `AddType`, `AliasMatch`, `SetEnvIf`, `php_flag` and `<FilesMatch>` directive. Store the extracted directive list separately from the file - it is small, stable, and diffs cleanly across builds where the whole file does not.
  - Privileged binary set - the complete output of a setuid and setgid sweep (`find / -xdev -type f -perm -4000 -o -perm -2000`), with path, owner, mode and SHA256 for each, and explicitly including the mode of `/bin/sh` and the other base shells.
  - Process and persistence state - the running process list, enabled services and startup items, cron entries, and any `authorized_keys` files, each with the account they belong to.
  - Configured destinations - from the appliance's own configuration, every backend service and service group, authentication server (LDAP, RADIUS, TACACS, Kerberos), DNS resolver, NTP source, syslog target and management system, as IP and port pairs. This list is the allowlist that makes appliance-sourced internal traffic interpretable.
  - Log shipping state - whether `/var/log/httpaccess.log`, `/var/log/httperror*`, `/var/log/messages` and `/var/log/sh.log` are forwarded off-box, and the last-received timestamp per stream. An appliance whose logs are only on the appliance has no usable history, because the attacker edits them.
  Collection window and cadence - This is not a 30-day observational baseline like an endpoint behavioural Ember; appliance state is meant to be static, so the first complete snapshot is the baseline. Capture it now for every internet-facing appliance, then re-capture on a weekly schedule and as a mandatory step immediately before and immediately after every firmware upgrade and every configuration change window. Four weeks of weekly snapshots is enough to see which fields are genuinely stable and which drift, which is what lets the diff job be tuned down to a short, meaningful alert.
  Deliverable - Three artefacts. First, a per-appliance, build-tagged snapshot stored off the appliance with integrity protection, because a baseline kept on the device is editable by whoever compromises the device. Second, an approved-deviation register - every file, directive, setuid binary and destination that differs from the vendor image, each with a reason and a named owner; portal branding and support bundles live here. Third, an automated diff that runs each snapshot against the previous one and against the vendor reference for that build, emitting only changes, routed to the security team rather than to the network team's change queue.
  Flag immediately, without waiting for the baseline to complete
  - Any `AddHandler` or `AddType` registering a non-`.php` extension as `application/x-httpd-php`, and any `AliasMatch` whose target is inside a scripts or plug-in staging directory. Zero legitimate instances on stock firmware — see [[H358]].
  - `/bin/sh` or any base shell carrying the setuid bit, or any setuid binary not present in the vendor image for that build — see [[H359]].
  - Any file in the web root or client plug-in directories whose `file` type is ASCII text or PHP script, or which contains `<?php`, `eval(`, `base64_decode(` or `shell_exec(`, regardless of extension.
  - Any `python` process on the appliance with `-c` and `base64` on its command line, any process launched via `nohup` with output to `/dev/null`, or IPC artefacts such as `/tmp/.uxdport` and `/tmp/.uxdlock` — see [[H360]].
  - Any internal flow sourced from the appliance to an IP and port pair absent from its own configured destination list, especially 445, 3389, 22, 5985 or database ports.
  - A gap in forwarded access logs for the portal's static asset paths during a period when the portal was authenticating users — the fingerprint of log scrubbing.
  - Appliance crash evidence - `NSPPE` termination with `pitboss` declining to restart, or new core files under `/var/core/` — which dates an exploitation attempt independently of any file timestamp.
  Which hunts this enables - [[H358]] (webshell registered through handler directives), [[H359]] (setuid root shell), [[H360]] (PHP-plus-Python tunnel pivoting internally) and [[M054]] (scoring portal request and response sizes to surface webshell traffic) all assume the reader can answer "is this normal for this device". Without this baseline each of them degrades into a manual investigation per appliance; with it, each becomes a diff. The destination list in particular is what converts [[M054]] and the network leg of [[H360]] from broad anomaly hunting into a precise exception report.

# B057

Every appliance-compromise hunt runs into the same wall. Mandiant's September 2026 NetScaler report gives responders a set of genuinely excellent triage commands — grep the Apache config for handler directives, run `file` over the client plug-in directories, `ls -l /bin/sh` — and every one of them works by comparison. The commands tell you what to look at. They cannot tell you what should have been there.

On an endpoint that gap is covered by EDR, software inventory and file integrity monitoring. On an internet-facing appliance there is no agent, usually no inventory entry, and often no log retention off the device. The appliance is simultaneously the most exposed system in the estate and the least recorded.

The problem is made worse by firmware. Upgrades rewrite `httpd.conf`, replace web-root content and change hashes in bulk, so a baseline that is not pinned to an exact build produces an unreadable diff every patch cycle and gets switched off. The fix is not more data; it is build-tagged snapshots, stored off the appliance, diffed build-to-build, with an explicit register of approved deviations like portal branding.

Collect five things per device — file inventory with detected types, web server directives, the setuid set, the process and persistence state, and the destinations the appliance's own configuration says it may contact. The last one is the quiet prize: it is a device-authored allowlist that makes "the appliance connected to a file server" immediately interpretable as the anomaly it is.

## Why

- **It converts four hunts from investigations into diffs.** [[H358]], [[H359]], [[H360]] and [[M054]] all ask whether something on an appliance is normal. Answering that per device during an incident does not scale; answering it from a snapshot does.
- **Appliances are the EDR blind spot that faces the internet.** No agent, no inventory, no file integrity monitoring — and a management plane that terminates VPN sessions and holds directory credentials.
- **Configuration-resident persistence survives patching.** A handler directive and a permission bit are untouched by applying a CVE fix, and both ride along in the saved configuration that administrators deliberately preserve across upgrades. Only a comparison finds them.
- **The appliance's own configuration is the best allowlist available.** Service groups, authentication servers, DNS, NTP and syslog targets enumerate every internal destination the device is supposed to reach, which turns east-west flow analysis from guesswork into an exception report.
- **Logs that live only on the appliance are not evidence.** Mandiant observed access-log scrubbing. Recording whether each log stream is forwarded, and when it was last received, is what makes a scrubbing gap visible at all.
- **Snapshots on the device are worthless.** Anyone who can modify the appliance can modify its baseline. Off-box, integrity-protected storage is the requirement that makes the whole exercise meaningful.
- **It fails safely into incident response.** Even where the diff job is never automated, a build-tagged snapshot taken today is the artefact that lets a responder next year answer "was this file here before" in seconds rather than by argument.
